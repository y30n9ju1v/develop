[5편](../05-vectorization/)에서 우리 예제는 하드웨어의 벡터 폭에 맞춘 `vector` dialect 표현까지 내려왔습니다. 이 마지막 편은 이 표현이 실제로 **서로 다른 하드웨어**를 만났을 때 어떻게 완전히 다른 최종 형태로 갈라지는지 — 범용 GPU 경로와, 우리가 가정할 작은 커스텀 NPU 가속기 경로 — 를 다루고, 양자화라는 하드웨어 최적화의 마지막 축을 더해 시리즈를 정리합니다.

---

## 1. 왜 여기서부터는 "낮추기"가 아니라 "갈라지기"인가

1편부터 5편까지 각 단계는 이전 단계의 정보를 최대한 보존하며 한 단계씩 구체화하는 흐름이었습니다 — `onnx` → `linalg` → 타일링된 `affine`/`scf` → `vector`까지, 표현은 계속 저수준이 되어갔지만 경로는 하나였습니다. 그런데 실제 계산을 담당하는 마지막 유닛(CPU 벡터 유닛, GPU 스트리밍 멀티프로세서, NPU의 전용 곱셈-누산기 배열)은 서로 실행 모델 자체가 다르기 때문에, 이 지점부터는 하나의 표현이 여러 타겟별 conversion pattern으로 **갈라집니다**. 이건 [Lean4-MLIR 시리즈 6편](../../lean/lean4-mlir-codegen/06-circt-systemverilog/)에서 C와 SystemVerilog가 같은 `safec` dialect에서 갈라졌던 것과 정확히 같은 구조입니다 — 앞단(1~5편)은 공유하고, 마지막 conversion pattern만 타겟에 따라 바뀝니다.

```
vector dialect (5편의 결과물)
   ↓ (conversion pattern이 여기서 갈라진다)
   ├─→ gpu dialect          → nvvm/rocdl → GPU 커널 바이너리   [2절]
   └─→ 커스텀 accelerator dialect → 명령 인코딩              → NPU 명령 스트림 [3절]
```

## 2. GPU 경로: 타일이 스레드 블록이 되고, 벡터 레지스터가 스레드 병렬성이 된다

GPU에서는 "벡터 레지스터 하나에 여러 원소를 담는다"는 개념 대신, **스레드 여러 개가 각자 원소 하나씩 맡아 동시에 실행**됩니다. 4편에서 만든 32×32 타일은 GPU에서 **스레드 블록** 하나에 정확히 대응시킬 수 있습니다 — 타일 안의 각 출력 원소를 스레드 하나가 맡습니다.

```mlir
gpu.launch blocks(%bx, %by) in (%grid_x = 7, %grid_y = 7)   // 224/32 = 7
           threads(%tx, %ty) in (%block_x = 32, %block_y = 32) {
  %h = arith.addi %by_offset, %ty : index
  %w = arith.addi %bx_offset, %tx : index
  // 이 스레드가 담당하는 (h, w) 위치의 출력 채널 64개를 계산
  scf.for %co = 0 to 64 step 1 {
    %acc = ... // 4~5편의 융합·벡터화된 연산이 여기서 그대로 재사용됨
  }
  gpu.terminator
}
```

여기서 4편에서 캐시 크기로 정했던 타일 크기(32×32)가, GPU에서는 **shared memory(블록 내 스레드들이 공유하는 저지연 메모리) 용량**으로 그 의미가 바뀝니다 — 캐시 계층이 아니라 shared memory 예산에 맞춰 다시 계산해야 하는 숫자입니다. 5편의 `vector<8xf32>` 벡터 명령은 GPU 경로에서는 보통 그대로 쓰이지 않고, 대신 "스레드 하나가 8개 원소를 순차 처리"하거나 "스레드 8개가 각자 하나씩 맡는다"는 형태로 재해석됩니다 — 벡터 유닛의 폭이 스레드 수로 치환되는 셈입니다. 이 `gpu` dialect는 이후 NVIDIA GPU라면 `nvvm`(PTX로 이어짐), AMD GPU라면 `rocdl`로 한 번 더 낮춰져 최종 커널 바이너리가 됩니다.

## 3. 커스텀 NPU 경로: 곱셈-누산기 배열에 맞춘 전용 명령

이제 이 시리즈의 마지막 갈래로, 작은 엣지 추론용 NPU를 하나 가정해봅시다. 이 NPU는 CPU나 GPU 같은 범용 연산 유닛 대신, **8×8 크기의 곱셈-누산기(MAC) 배열**을 하드웨어에 고정으로 박아 놓은 형태입니다. 이 배열은 입력 벡터 8개와 커널 벡터 8개를 받아 내적을 한 사이클에 계산하도록 설계되어 있습니다 — 딱 5편에서 다룬 `vector.fma`가 하려던 일을, 범용 CPU 명령이 아니라 **전용 회로**로 굳혀 놓은 것입니다.

이런 하드웨어를 타겟으로 삼으려면, [Lean4-MLIR 시리즈](../../lean/lean4-mlir-codegen/)에서 `safec`이라는 커스텀 dialect를 직접 정의했던 것과 같은 이유로, 이 NPU 전용 오퍼레이션을 담을 dialect(`npu`라고 부르겠습니다)가 필요합니다.

```mlir
"npu.mac8x8"(%in_vec, %kernel_vec, %acc) {
  input_offset = 0, kernel_offset = 0
} : (vector<8xf32>, vector<8xf32>, f32) -> f32
```

5편의 `vector.fma`와 `npu.mac8x8`은 수학적으로 완전히 같은 계산(내적 후 누적)을 하지만, 후자는 "이 NPU가 물리적으로 갖고 있는 8×8 MAC 배열의 한 번 실행"이라는 하드웨어 자원에 직접 대응한다는 점이 다릅니다. conversion pattern은 4~5편에서 만든 타일링된 벡터 반복문을 순회하며, 벡터 크기가 정확히 8이고 누적 대상이 하나뿐인 패턴을 찾아 `npu.mac8x8` 호출로 바꿔치기합니다. 만약 벡터 크기가 8의 배수가 아니라면(우리 예제의 `ci=3`처럼), 이 하드웨어의 고정 크기 배열에 맞춰 나머지를 0으로 채우는 패딩이 추가로 필요합니다 — 이 역시 4편의 타일 크기, 5편의 벡터 폭 선택이 하드웨어 자원 크기에 종속적이었던 것과 같은 이유입니다.

## 4. 양자화: 이 마지막 단계에서만 등장하는 새로운 축

지금까지는 계산의 정밀도(전부 `f32`)를 한 번도 바꾸지 않았습니다. 그런데 NPU 같은 전력 제약이 큰 하드웨어는 종종 `f32` 대신 **int8** 곱셈-누산기를 쓰는 경우가 많습니다 — int8 MAC 배열은 f32 MAC 배열보다 훨씬 작고 전력을 덜 씁니다. 이 선택은 지금까지 다룬 어떤 최적화와도 다른 성격을 갖습니다 — 타일링이나 벡터화는 **같은 계산을 다른 방식으로 배치**했을 뿐이지만, 양자화는 **계산 자체의 결과가 미세하게 달라지는** 근사입니다.

이 근사를 다루는 값이 **스케일(scale)**과 **영점(zero-point)**입니다. float 값 $x$를 int8로 표현할 때 $x \approx \text{scale} \times (q - \text{zero\_point})$($q$는 int8 정수)라는 관계로 근사하고, Conv 연산 자체는 int8 곱셈-누산으로 실행한 뒤, 그 결과에 스케일을 다시 곱해 float로 되돌립니다.

```mlir
"npu.mac8x8_int8"(%in_vec_i8, %kernel_vec_i8, %acc_i32) {
  input_scale = 0.0078125 : f32, kernel_scale = 0.0034 : f32
} : (vector<8xi8>, vector<8xi8>, i32) -> i32
```

이 스케일 값들은 3편에서 다룬 상수 접기와 비슷하게 **컴파일 시점에 미리 계산**되지만, 그 값을 계산하는 방법 자체가 이 시리즈에서 다룬 다른 어떤 것과도 다릅니다 — 실제 학습 데이터(또는 대표 데이터셋)를 모델에 흘려보내 각 텐서의 값 분포(최댓값, 최솟값)를 관찰해야만 적절한 스케일을 정할 수 있기 때문입니다(post-training quantization의 캘리브레이션 과정). 즉 이 마지막 최적화만큼은 컴파일러가 그래프 구조만 보고 판단할 수 없고, **데이터를 봐야만 결정할 수 있는 정보**가 파이프라인에 새로 들어옵니다. 이 캘리브레이션과, int8로 인한 정밀도 손실이 최종 정확도에 얼마나 영향을 주는지를 검증하는 문제는 그 자체로 다른 논의를 필요로 할 만큼 큰 주제라, 이 시리즈에서는 "양자화가 파이프라인의 어느 지점에서, 어떤 새로운 종류의 정보를 요구하며 개입하는가"까지만 짚고 넘어갑니다.

## 5. 시리즈 정리

여섯 편에 걸쳐 Conv → BatchNorm → Relu라는 예제 하나를 따라가며 ONNX 그래프가 특정 하드웨어의 실행 가능한 형태로 바뀌는 전체 파이프라인을 살펴봤습니다.

1. **[왜 ONNX 모델을 MLIR로 최적화하는가](../01-why-onnx-and-mlir/)**: ONNX는 "무엇을 계산할지"만 정의할 뿐 "어떻게 빠르게 계산할지"는 정의하지 않으며, 이 간극을 메우는 최적화들은 저마다 다른 추상화 수준의 정보를 요구하기 때문에 MLIR의 다단계 dialect 스택이 필요하다.
2. **[ONNX를 MLIR로 들여오기](../02-importing-onnx-and-shape-inference/)**: ONNX 노드가 `onnx` dialect 오퍼레이션으로 그대로 옮겨지고, 이후 모든 최적화의 전제 조건인 shape inference가 물음표였던 텐서 shape를 구체적인 숫자로 채운다.
3. **[그래프 수준 최적화](../03-graph-level-optimization/)**: 연산 융합이 메모리 왕복을 없애고, 상수 접기가 반복되는 계산을 미리 끝내며, 레이아웃 변환이 하드웨어 친화적인 메모리 순서로 텐서를 재배치한다.
4. **[linalg dialect로 낮추기](../04-lowering-to-linalg-and-tiling/)**: 그래프 수준에서 하나였던 오퍼레이션이 반복문 구조로 펼쳐지고, 캐시 크기에 맞춘 타일링과 텐서-메모리 전환(버퍼화)이 이루어진다.
5. **[벡터화](../05-vectorization/)**: 타일 안쪽 반복문이 하드웨어의 SIMD 폭에 맞춰 벡터 명령으로 접히며, `iterator_types`의 parallel/reduction 구분이 이 변환의 안전성을 결정한다.
6. **하드웨어별 최종 낮추기 (이 글)**: 같은 벡터 표현이 GPU의 스레드 병렬성과 커스텀 NPU의 고정 크기 MAC 배열로 각각 다르게 재해석되며, 양자화는 데이터 분포를 관찰해야만 결정할 수 있는 전혀 새로운 종류의 정보를 파이프라인에 더한다.

여섯 편이 함께 그리는 그림은, "하드웨어에 맞는 최적화는 한 번에 끝나는 단일 변환이 아니라, 그래프·반복문·벡터·명령이라는 서로 다른 추상화 수준에서 각각 그 수준에 맞는 결정(무엇을 합칠지, 얼마나 쪼갤지, 몇 개씩 묶을지, 어떤 정밀도로 계산할지)이 순서대로 쌓여야 완성된다"는 것입니다.
