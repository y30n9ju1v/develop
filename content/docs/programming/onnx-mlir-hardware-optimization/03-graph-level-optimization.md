[2편](../02-importing-onnx-and-shape-inference/)에서 shape가 전부 확정된 `onnx` dialect 그래프를 손에 넣었습니다. 이 글은 그 그래프에 아직 아무 반복문도 드러나지 않은 **그래프 수준**에서 적용할 수 있는 세 가지 최적화 — 연산 융합, 상수 접기, 레이아웃 변환 — 을 다룹니다. 이 단계에서 하는 결정들이 이후 편(4~6편)에서 생성되는 저수준 코드의 모양을 크게 좌우하기 때문에, 순서상 가장 먼저 옵니다.

---

## 1. 연산 융합(Operator Fusion): Conv-BatchNorm-Relu를 하나로

2편의 그래프를 다시 보면, Conv의 출력은 오직 BatchNorm 하나에서만 쓰이고, BatchNorm의 출력은 오직 Relu 하나에서만 쓰입니다. 이렇게 "한 연산의 출력이 정확히 다음 연산 하나로만 흘러 들어가는" 관계를 그래프에서 찾아내는 게 융합 pass가 하는 첫 번째 일입니다 — 스칼라 변수를 다루는 고전적인 컴파일러의 죽은 코드 제거·데이터플로우 분석([컴파일러(MIT 6.035) 시리즈 8편](../../compilers/08-optimization-dataflow-analysis/#4-지역-최적화-2-죽은-코드-제거)이 다룬 "이 값을 나중에 쓰는 곳이 있는가")과 완전히 같은 질문을 텐서 그래프 노드 단위로 묻는 것입니다.

```
패턴 매칭:
  %a = onnx.Conv(...)
  %b = onnx.BatchNormalization(%a, ...)   ← %a를 쓰는 곳이 여기 하나뿐
  %c = onnx.Relu(%b)                       ← %b를 쓰는 곳이 여기 하나뿐
```

이 패턴이 매칭되면, MLIR의 rewrite pattern은 이 세 오퍼레이션을 하나의 융합된 오퍼레이션으로 바꿔치기합니다.

```mlir
%c = "onnx.ConvBatchNormReluFused"(%x, %w, %scale, %bias, %mean, %var) {
  strides = [1, 1], pads = [1, 1, 1, 1], epsilon = 1.0e-5
} : (...) -> tensor<1x64x224x224xf32>
```

이 융합이 왜 속도를 바꾸는지는 **메모리 이동**을 생각하면 분명해집니다. 융합 전에는 Conv의 출력(`1x64x224x224` 크기의 float 텐서, 약 12.8MB)을 메모리에 전부 썼다가, BatchNorm이 그걸 다시 읽어서 정규화한 값을 또 전부 쓰고, Relu가 그걸 또 읽어서 처리합니다. 세 번의 큰 텐서 왕복이 생깁니다. 융합 후에는 한 원소가 Conv에서 계산되는 즉시 그 자리에서 BatchNorm 정규화와 Relu 클리핑까지 끝내고 최종 결과 하나만 메모리에 씁니다 — 중간 결과 두 개(Conv 출력, BatchNorm 출력)가 메모리에 나타날 필요 자체가 없어집니다. 4편에서 이 융합된 오퍼레이션을 반복문으로 낮출 때, 이 "중간값을 메모리에 쓰지 않고 레지스터에서 바로 다음 계산으로 넘긴다"는 성질이 실제 반복문 구조에 그대로 반영됩니다.

여기서 융합이 **항상** 가능한 건 아니라는 점도 중요합니다. 만약 Conv의 출력이 BatchNorm 말고 다른 곳(예: 스킵 커넥션)에서도 쓰인다면, 그 값을 메모리에 남겨둬야 하므로 이 패턴은 매칭되지 않습니다 — 이게 바로 "출력을 쓰는 곳이 정확히 하나뿐"이라는 조건이 패턴에 들어간 이유입니다.

## 2. 상수 접기(Constant Folding): 추론 시점엔 이미 답이 정해진 계산을 미리 해버린다

BatchNorm의 네 파라미터(`scale`, `bias`, `mean`, `var`)는 학습이 끝난 뒤에는 절대 바뀌지 않는 상수입니다. 이 절이 하는 일은 [컴파일러(MIT 6.035) 시리즈 8편](../../compilers/08-optimization-dataflow-analysis/#3-지역-최적화-1-상수-접기와-상수-전파)에서 다룬 상수 접기(Constant Folding)와 원리가 완전히 같습니다 — "컴파일 타임에 이미 값이 정해지는 계산은 실행 시점까지 미루지 않는다"는 규칙을 딥러닝 그래프의 파라미터에 적용한 것뿐입니다. 그런데 BatchNorm의 실제 계산식을 보면,

$$y = \frac{x - \text{mean}}{\sqrt{\text{var} + \epsilon}} \times \text{scale} + \text{bias}$$

이 식에서 $x$(Conv의 출력, 매 추론마다 달라짐)를 제외한 나머지는 전부 상수입니다. 따라서 이 식을

$$y = x \times \underbrace{\frac{\text{scale}}{\sqrt{\text{var} + \epsilon}}}_{\text{미리 계산 가능}} + \underbrace{\left(\text{bias} - \frac{\text{scale} \times \text{mean}}{\sqrt{\text{var} + \epsilon}}\right)}_{\text{미리 계산 가능}}$$

로 다시 쓰면, 밑줄 친 두 항은 컴파일 시점에 딱 한 번만 계산해서 새로운 상수(`%scale'`, `%bias'`)로 만들어 둘 수 있습니다. 이러면 추론할 때마다 반복되던 나눗셈과 제곱근 계산이 통째로 사라지고, BatchNorm은 사실상 "곱하고 더하기"(affine transform) 한 줄로 줄어듭니다.

```mlir
// 컴파일 타임에 한 번만 계산됨
%scale_prime = "onnx.Constant"() {value = dense<...> : tensor<64xf32>} : () -> tensor<64xf32>
%bias_prime  = "onnx.Constant"() {value = dense<...> : tensor<64xf32>} : () -> tensor<64xf32>
```

이 최적화는 1편의 원래 그래프에 있던 `onnx.Constant`(scale, bias, mean, var)를 그대로 두는 대신, **그래프를 순회하며 오퍼레이션들의 입력이 전부 상수인지 확인하고, 전부 상수라면 그 계산을 컴파일러가 대신 실행해서 결과를 새 상수로 치환하는** 일반적인 패턴(constant folding)의 한 사례입니다. Conv의 가중치 자체도 상수이므로, 만약 그래프 어딘가에 "가중치에 어떤 고정된 스케일을 곱하는" 연산이 남아 있었다면 그 역시 같은 방식으로 미리 접힐 수 있습니다.

**실전 NPU 컴파일러에서는 이 상수 접기가 산술 계산을 없애는 데서 끝나지 않습니다.** 접혀서 확정된 가중치 텐서(`%scale_prime`처럼)는 [6편](../06-hardware-backend-lowering/)에서 다룰 `npu.mac8x8` 같은 고정 크기 MAC 배열에 맞춰 메모리 상에서 **미리 재배열(Weight Packing / Block-Layout 변환)**되는 경우가 많습니다 — 예를 들어 64개 채널을 8개씩 묶어 MAC 배열의 폭에 맞춘 블록 순서로 다시 늘어놓는 식입니다. 이렇게 하드웨어가 원하는 순서로 가중치를 컴파일 타임에 미리 정렬해 두면, 실행 중에는 그 배열을 그대로 읽어 MAC 유닛에 바로 흘려보내기만 하면 되어 정렬 오버헤드(unaligned access, 여분의 shuffle 명령)가 사라집니다. 이 재배열 역시 "컴파일 타임에 이미 정해지는 계산은 실행 시점까지 미루지 않는다"는 상수 접기와 정확히 같은 원리를, 산술 값이 아니라 **메모리 레이아웃**에 적용한 것입니다 — 실전 NPU 컴파일러 개발에서 이 정렬·패킹 문제가 상수 접기 자체보다 오히려 더 큰 실무적 난제인 경우가 많습니다.

## 3. 레이아웃 변환: `NCHW`와 `NHWC` 사이의 선택

지금까지 우리 예제 텐서는 `1x64x224x224`(배치, 채널, 높이, 너비 순서 — `NCHW`)로 표기했는데, ONNX의 기본 관례가 이 순서입니다. 그런데 하드웨어에 따라 `NHWC`(배치, 높이, 너비, 채널 순서)가 훨씬 빠른 경우가 많습니다.

이유는 Conv 연산의 안쪽 반복문이 채널 축을 따라 값을 누적하기 때문입니다. `NHWC`에서는 같은 공간 위치의 모든 채널 값이 메모리에 연속으로 붙어 있어서, 채널 축을 순회하는 이 누적 계산이 캐시 라인 하나를 그대로 쭉 읽는 순차 접근이 됩니다. `NCHW`에서는 같은 공간 위치라도 채널이 다르면 값이 `224×224`칸(한 채널 평면 전체)만큼 떨어져 있어서, 채널 축 순회가 메모리를 듬성듬성 건너뛰는 접근이 됩니다. 많은 GPU/NPU 벡터 연산 유닛이 "연속된 채널 값 여러 개를 한 번에 로드"하는 방식으로 설계되어 있어서, `NHWC`가 이런 하드웨어에서 유리합니다.

이 변환은 그래프에 트랜스포즈 오퍼레이션을 끼워 넣는 형태로 이루어집니다.

```mlir
%x_nhwc = "onnx.Transpose"(%x) {perm = [0, 2, 3, 1]}
  : (tensor<1x3x224x224xf32>) -> tensor<1x224x224x3xf32>
%w_nhwc = "onnx.Transpose"(%w) {perm = [0, 2, 3, 1]}
  : (tensor<64x3x3x3xf32>) -> tensor<64x3x3x3xf32>  // 커널 레이아웃도 함께 바뀜
%conv_nhwc = "onnx.Conv"(%x_nhwc, %w_nhwc) { ... , layout = "NHWC" }
  : (...) -> tensor<1x224x224x64xf32>
```

여기서 실무적으로 중요한 점 하나 — 입력 하나마다 트랜스포즈를 넣으면 그 트랜스포즈 자체가 메모리 왕복 비용이므로, 최적화 pass는 **그래프 전체에서 레이아웃을 한 번에 통일**하려 합니다. 즉 입력을 진입점에서 한 번 `NHWC`로 바꾼 뒤, 이어지는 Conv·BatchNorm·Relu가 전부 `NHWC`인 채로 체인을 이루게 하고, 최종 출력 직전에만 필요하다면 다시 `NCHW`로 되돌립니다. 트랜스포즈를 그래프 중간마다 넣었다 뺐다 하면 융합(1절)으로 없앤 메모리 왕복을 레이아웃 변환이 도로 만들어내는 셈이 되어 버립니다.

## 4. 세 최적화가 서로 순서를 타는 이유

이 세 최적화는 독립적이지 않고 순서가 있습니다.

1. **상수 접기가 먼저 끝나야** BatchNorm이 단순한 affine 변환으로 줄어들고, 그래야 연산 융합 패턴(1절)이 "Conv 다음에 간단한 곱셈-덧셈, 그다음 Relu"라는 더 단순한 형태를 매칭 대상으로 삼을 수 있습니다.
2. **연산 융합이 레이아웃 변환보다 먼저** 이루어지는 게 유리합니다. 융합된 오퍼레이션 하나에 대해 레이아웃을 한 번만 결정하면 되는 것과, Conv/BatchNorm/Relu 세 개 각각에 대해 레이아웃을 따로 결정하는 것 사이엔 최적화 pass가 고려해야 할 경우의 수 차이가 있습니다.
3. **레이아웃 변환은 shape inference([2편](../02-importing-onnx-and-shape-inference/))가 끝난 뒤에만 안전합니다.** 트랜스포즈로 축의 순서를 바꾸려면 애초에 어느 축이 채널 축이고 그 크기가 몇인지 알아야 하기 때문입니다.

이 순서를 지켜 세 최적화를 전부 적용하고 나면, 우리 예제는 `onnx.ConvBatchNormReluFused` 하나(내부에 미리 계산된 affine 파라미터를 담은)에 `NHWC` 레이아웃이 적용된 형태로 정리됩니다. 그래프 수준에서 할 수 있는 일은 여기까지입니다 — 이 오퍼레이션 하나가 실제로 몇 겹의 반복문으로, 어떤 순서로 실행되어야 하는지는 아직 전혀 정해지지 않았습니다.

다음 편에서는 이 융합된 오퍼레이션을 **linalg dialect**로 낮추면서 처음으로 반복문 구조가 텍스트에 드러나는 과정과, 그 반복문에 타일링을 적용해 캐시에 맞게 쪼개는 과정을 다룹니다.
