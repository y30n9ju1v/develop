1~6편은 Conv → BatchNorm → Relu라는 비교적 다루기 쉬운 예제 하나로 MLIR 최적화의 뼈대(그래프 융합 → `linalg` → 타일링 → 벡터화 → 하드웨어별 낮추기)를 세웠습니다. 이 글은 그 뼈대가 그대로 유지된다는 걸 전제로, Transformer 계열 모델의 핵심인 **대형 MatMul**과 **Attention**이 이 뼈대 위에 무엇을 추가로 요구하는지를 다룹니다. 새로운 예제로 시퀀스 길이 $N$, 은닉 차원 $D$인 attention 블록(Q·Kᵀ → softmax → ·V)을 씁니다.

## 1. 대형 MatMul: 왜 타일 한 겹으로는 부족한가

[4편](../04-lowering-to-linalg-and-tiling/)에서 Conv를 타일링할 때는 캐시 크기에 맞춘 32×32 타일 한 겹이면 충분했습니다. `linalg.matmul`(예: $[N, D] \times [D, D]$)에 같은 전략을 그대로 적용하면 이런 문제가 생깁니다 — 행렬이 캐시보다 훨씬 크면, 타일 하나를 계산하는 동안에도 그 타일이 참조하는 입력 조각이 캐시 안에 다 들어가지 못해 여전히 메모리 왕복이 남습니다.

실전 GEMM(General Matrix Multiply) 최적화는 그래서 **캐시 계층 하나당 타일 한 겹씩, 여러 겹을 중첩**합니다.

```
L2 캐시 타일 (수백 KB, 예: 256×256)
   ↓
L1 캐시 타일 (수십 KB, 예: 64×64)
   ↓
레지스터 타일 (예: 6×16 — 벡터 레지스터 개수만큼)
   ↓
vector.fma 명령 (5편과 동일)
```

바깥 두 겹(L2, L1)은 4편에서 다룬 것과 똑같은 이유(캐시 안에 재사용 데이터를 붙잡아 두기)로 존재하지만, 크기가 다른 캐시 계층 각각에 맞춰 겹겹이 쌓인다는 점이 다릅니다. 가장 안쪽 레지스터 타일은 "이 계산 동안 레지스터 몇 개를 쓸지"를 결정하는데, 이 크기를 하드웨어의 레지스터 개수보다 크게 잡으면 레지스터가 부족해 값이 다시 메모리로 밀려나는(spill) 역효과가 납니다. 즉 타일 크기 하나만 고르면 됐던 4편과 달리, 여기서는 **여러 겹의 타일 크기를 캐시 각 층의 용량에 맞춰 동시에 맞춰야** 합니다. IREE나 TVM 같은 프로젝트가 이 여러 겹의 크기 조합을 손으로 정하지 않고 실제로 여러 조합을 실행해보며 가장 빠른 조합을 찾는 **오토튜닝**을 쓰는 이유가 여기 있습니다 — 조합의 경우의 수가 사람이 손으로 다루기엔 너무 많습니다.

## 2. Softmax: reduction 축이 통째로인 연산을 병렬화하기

Attention의 softmax는 $\text{softmax}(x)_i = \dfrac{e^{x_i - \max(x)}}{\sum_j e^{x_j - \max(x)}}$로 정의되고, 이 연산의 `linalg.generic`은 [4편](../04-lowering-to-linalg-and-tiling/)의 Conv와 다른 형태를 띱니다 — Conv는 `iterator_types`가 대부분 `"parallel"`이고 `"reduction"`은 안쪽 세 축(`kh, kw, ci`)뿐이었지만, softmax는 **전체 축이 사실상 하나의 reduction**(최댓값 구하기, 그다음 합 구하기)입니다.

```
1단계: 이 행의 최댓값을 구한다        (reduction, 순서 무관)
2단계: 각 원소에서 최댓값을 빼고 exp   (parallel)
3단계: 그 결과들의 합을 구한다         (reduction, 순서 무관)
4단계: 각 원소를 그 합으로 나눈다      (parallel)
```

문제는 [5편](../05-vectorization/)에서처럼 벡터 레지스터 하나에 원소 여러 개를 태웠을 때, "이 레지스터 안의 8개 값을 하나의 최댓값/합으로 접는" 작업이 단순한 `vector.fma` 하나로 되지 않는다는 점입니다. 이 작업은 보통 **트리 형태로 절반씩 접는 방식**(`vector.reduction` 같은 전용 오퍼레이션, 또는 GPU라면 warp 안의 스레드끼리 값을 직접 주고받는 shuffle 명령)으로 처리됩니다.

```
[a0 a1 a2 a3 a4 a5 a6 a7]
   ↓ 절반씩 짝지어 최댓값
[max(a0,a4) max(a1,a5) max(a2,a6) max(a3,a7)]
   ↓
[max(...) max(...)]
   ↓
[최종 최댓값]
```

그리고 여기 한 가지 함정이 더 있습니다 — 3단계는 2단계가 전부 끝난 뒤에만 시작할 수 있고, 4단계는 3단계가 전부 끝난 뒤에만 시작할 수 있습니다. Conv에서는 타일 하나의 계산이 다른 타일과 거의 독립적이었지만, softmax는 **한 행 전체를 두 번 훑어야** 최종 값이 나옵니다(최댓값을 구하는 패스, 합을 구하는 패스). 이 "여러 패스가 순서를 지켜야 한다"는 제약이 융합을 어렵게 만드는데, 이건 바로 다음 절의 문제로 이어집니다.

## 3. Attention 전체를 융합하기: FlashAttention이 푸는 문제

Attention 블록 전체($QK^\top \to \text{softmax} \to \cdot V$)를 [3편](../03-graph-level-optimization/)의 융합 원리대로 그냥 이어붙이면, $QK^\top$의 결과인 **$N \times N$ attention 행렬**을 통째로 메모리에 썼다가 softmax가 다시 읽고, 그 결과를 또 메모리에 썼다가 $V$와의 곱셈이 다시 읽어야 합니다. 시퀀스 길이 $N$이 커지면(예: $N=8192$) 이 $N \times N$ 행렬 하나가 수백 MB에 달해, 3편에서 다뤘던 "중간 결과를 메모리에 쓰지 않는" 융합의 이점이 가장 절실해지는 지점이 바로 여기입니다.

문제는 2절에서 본 것처럼 softmax가 "한 행 전체를 봐야 최종 값이 나오는" 연산이라, $QK^\top$의 타일 하나를 계산하자마자 곧바로 softmax까지 끝내버릴 수 없다는 점입니다 — 그 행의 나머지 타일들이 아직 계산되지 않았으면 최댓값도 합도 확정되지 않기 때문입니다.

**FlashAttention**이 푸는 문제가 정확히 이것입니다. 핵심 아이디어는 "최댓값과 합을 미리 다 구하고 나서 정규화하는" 대신, **타일을 하나씩 처리하면서 지금까지 본 부분에 대한 최댓값/합을 계속 온라인으로 갱신**하는 것입니다.

```
누적 상태: (지금까지의 최댓값 m, 지금까지의 지수합 l, 지금까지의 가중합 acc)

각 K, V 타일을 순서대로 처리:
  1. 이번 타일의 QK^T를 계산 (레지스터/SRAM 안에서, 메모리에 쓰지 않음)
  2. 이번 타일의 최댓값과 이전 m을 비교해 새 m을 구한다
  3. m이 바뀌었다면, 이미 누적해둔 acc와 l을 새 m 기준으로 다시 스케일한다
  4. 이번 타일의 softmax 가중치를 곱해 acc, l을 갱신한다
```

이 "온라인 갱신" 덕분에 $N \times N$ 행렬 전체를 메모리에 올릴 필요 자체가 없어지고, 타일 하나 크기만큼만 SRAM/레지스터에 있으면 됩니다 — [4편](../04-lowering-to-linalg-and-tiling/)에서 타일링이 캐시 크기에 맞춰 반복문을 쪼갰던 것과 똑같은 이유(재사용 데이터를 빠른 메모리에 붙잡아 두기)지만, 여기서는 타일링이 **속도 최적화를 넘어 애초에 이 알고리즘이 메모리에 다 못 올라가는 문제를 우회하는 방법** 자체가 됩니다. MLIR 레벨에서 이걸 표현하려면 3편의 그래프 융합 pass가 "출력을 쓰는 곳이 하나뿐인 연쇄"만 인식하는 수준을 넘어, 이런 **누적 상태를 타일마다 갱신하는 순차적 패턴 전체**를 하나의 커스텀 융합 규칙으로 인식해야 합니다 — 이런 패턴을 자동으로 찾아 생성하는 것이 Triton이나 최신 MLIR 기반 컴파일러 연구의 활발한 주제 중 하나입니다.

## 4. 동적 shape: 시퀀스 길이가 실행 시점에만 정해진다면

[2편](../02-importing-onnx-and-shape-inference/)에서 shape inference가 모든 텐서 타입에 구체적인 숫자를 채운다고 봤지만, 실제 언어 모델 서빙에서는 시퀀스 길이 $N$이 입력마다 다릅니다. 이 경우 `tensor<?x512xf32>`처럼 그 축만 물음표로 남습니다.

이건 [4편](../04-lowering-to-linalg-and-tiling/)의 타일링과 [5편](../05-vectorization/)의 벡터화 양쪽에 영향을 줍니다 — 타일 개수(`224/32`처럼 나눠떨어지는 계산)를 컴파일 타임에 확정할 수 없으므로, 반복 횟수를 런타임에 실제 길이를 읽어 계산하는 코드가 추가로 필요합니다. 벡터화 역시 "마지막 타일이 벡터 폭보다 작게 남는 경우"(예: 길이 8 벡터인데 3개만 남은 경우)를 처리하는 마스킹된 벡터 연산(`vector.maskedload` 등, 범위를 벗어난 나머지를 0으로 채워 안전하게 처리)이 필요해집니다. 원리 자체(타일링, 벡터화)는 그대로지만, "크기를 안다"는 전제가 빠지는 순간 코드가 그만큼 더 보수적이고 복잡해집니다.

## 5. 텐서 코어: "벡터 하나"가 아니라 "작은 행렬곱 하나"가 명령 단위가 될 때

[6편](../06-hardware-backend-lowering/)에서 다룬 커스텀 NPU의 `npu.mac8x8`는 "벡터 8개의 내적"을 명령 하나로 처리했습니다. GPU의 텐서 코어(NVIDIA Tensor Core, AMD Matrix Core)는 한 단계 더 나아가 **작은 행렬곱 자체**(예: $16 \times 16 \times 16$)를 명령 하나로 처리합니다. MatMul이 Conv보다 훨씬 무거운 이유 중 하나가 바로 이 하드웨어를 제대로 쓰지 못하면 이론 성능의 일부만 쓰게 된다는 점입니다.

MLIR에서 이 경로는 `vector.contract`(추상적인 "텐서 축약" 오퍼레이션)를 거쳐 `nvgpu.mma`(NVIDIA) 같은 전용 오퍼레이션으로 낮춰집니다.

```mlir
// vector.contract: "이 두 벡터/행렬을 축약하라"는 추상적 표현 (5편의 vector.fma를 행렬 단위로 일반화한 것)
%acc = vector.contract %a, %b, %acc_init
  { indexing_maps = [...], iterator_types = ["parallel", "parallel", "reduction"] }
  : vector<16x16xf16>, vector<16x16xf16> into vector<16x16xf32>
   ↓ (텐서 코어 타겟 conversion pattern)
%acc = nvgpu.mma.sync %a, %b, %acc_init : (vector<16x16xf16>, vector<16x16xf16>, vector<16x16xf32>) -> vector<16x16xf32>
```

`vector.contract`가 존재하는 이유는 정확히 [1편](../01-why-onnx-and-mlir/)에서 다단계 dialect가 필요했던 이유와 같습니다 — "두 텐서를 축약해 결과를 낸다"는 정보를 CPU 벡터 명령으로 낮출 때와 텐서 코어로 낮출 때 각각 다르게 재해석할 수 있으려면, 그 중간에 "아직 특정 하드웨어에 묶이지 않은" 추상 표현이 있어야 하기 때문입니다. 텐서 코어가 요구하는 입력 정밀도(fp16, bf16, 또는 int8)와 축적 정밀도(보통 fp32)가 다르다는 점도 [6편](../06-hardware-backend-lowering/)에서 다룬 양자화와 비슷한 종류의 "정밀도를 낮춰 하드웨어 자원에 맞추는" 결정이 여기서도 반복된다는 걸 보여줍니다.

## 6. 정리: 원리는 그대로, 겹치는 정도가 달라진다

이 글에서 다룬 네 가지(다단계 타일링, reduction 병렬화, FlashAttention 융합, 텐서 코어 매핑)를 1~6편의 원리와 대응시켜보면:

- **다단계 타일링**은 [4편](../04-lowering-to-linalg-and-tiling/)의 타일링이 캐시 계층 수만큼 중첩된 것입니다.
- **reduction 병렬화**는 [5편](../05-vectorization/)의 `iterator_types` 안전성 판단이 그대로 적용되지만, 접는 방법(트리 리덕션)이 추가로 필요합니다.
- **FlashAttention류 융합**은 [3편](../03-graph-level-optimization/)의 "출력을 쓰는 곳이 하나뿐인 연쇄" 융합보다 훨씬 정교한, 순차적 상태 갱신을 포함하는 융합 패턴입니다.
- **텐서 코어 매핑**은 [6편](../06-hardware-backend-lowering/)에서 벡터 하나였던 명령 단위가 작은 행렬 하나로 커진 것뿐, "추상 오퍼레이션 → 하드웨어 전용 오퍼레이션"이라는 낮추기 구조는 동일합니다.

즉 "더 무거운 연산자는 MLIR로 최적화가 안 되는가"라는 질문의 답은, 안 되는 게 아니라 **1~6편에서 세운 원리(융합, 타일링, 벡터화, 하드웨어별 낮추기) 위에 그 연산자의 성격에 맞는 기법을 한 겹씩 더 쌓아야 한다**는 것입니다. Triton, IREE, XLA/StableHLO 같은 실전 컴파일러들이 활발히 연구하는 지점도 정확히 이 "겹쳐야 할 기법을 사람이 손으로 짜지 않고 자동으로 찾아내는" 부분입니다.
