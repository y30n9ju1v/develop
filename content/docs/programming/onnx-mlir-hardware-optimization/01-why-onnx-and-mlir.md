이 시리즈는 "PyTorch나 TensorFlow에서 학습한 모델을 ONNX로 export한 뒤, 그 그래프를 특정 하드웨어(서버 GPU, 엣지 NPU, 커스텀 가속기)에서 최대한 빠르게 돌아가는 실행 파일로 바꾼다"는 문제를 다룹니다. 이 변환을 MLIR이 맡는 이유와 그 과정에서 실제로 무엇이 최적화되는지를, **하나의 작은 예제**를 시리즈 내내 따라가며 살펴봅니다.

예제는 이미지 분류 모델에서 가장 흔한 블록인 **Conv2D → BatchNorm → ReLU**입니다. 이 블록 하나가 1편에서는 문제로, 2~3편에서는 MLIR의 여러 dialect로, 4~5편에서는 최적화가 적용된 저수준 표현으로, 6편에서는 특정 하드웨어를 겨냥한 최종 형태로 계속 모습을 바꿉니다.

이 시리즈는 [Lean4로 MLIR 만들기](../../lean/lean4-mlir-codegen/) 시리즈와 같은 MLIR 인프라를 다루지만 완전히 독립적으로 읽을 수 있습니다. MLIR의 dialect·operation·attribute 같은 기본 개념이 낯설다면, 그 시리즈의 [0편: MLIR이란 무엇인가](../../lean/lean4-mlir-codegen/00-what-is-mlir/)를 먼저 훑어봐도 좋습니다.

---

## 1. ONNX 그래프는 "무엇을 계산하는지"만 말해줄 뿐, "어떻게 빠르게 계산할지"는 말해주지 않는다

ONNX(Open Neural Network Exchange)는 딥러닝 모델을 프레임워크 중립적으로 표현하는 포맷입니다. PyTorch로 학습한 모델을 `torch.onnx.export`로 내보내면, 이런 식의 연산 그래프가 나옵니다.

```
input (1, 3, 224, 224)
   │
   ▼
Conv (weight: 64×3×3×3, stride=1, pad=1)
   │
   ▼
BatchNormalization (scale, bias, mean, var)
   │
   ▼
Relu
   │
   ▼
output (1, 64, 224, 224)
```

이 그래프는 "Conv 다음에 BatchNorm을 하고 그다음 Relu를 한다"는 **수학적으로 무엇을 계산해야 하는지**만 정의합니다. 각 연산을 실제 하드웨어에서 어떤 순서로, 어떤 메모리 레이아웃으로, 얼마나 크게 잘라서(tile) 실행할지는 전혀 정해져 있지 않습니다. 그런데 바로 이 "어떻게"가 실행 속도의 대부분을 결정합니다.

몇 가지 예를 들면:

- **연산 경계에서 메모리를 왕복하는 비용**: Conv의 출력을 전부 메모리에 썼다가, BatchNorm이 그걸 다시 읽고, 다시 썼다가, Relu가 또 읽는다면, 세 연산 모두 계산량 자체는 크지 않은데도 메모리 대역폭에 발목이 잡힙니다. 세 연산을 하나로 합쳐(fusion) 값을 레지스터나 캐시에 둔 채로 연쇄 계산하면 이 왕복이 사라집니다.
- **메모리 레이아웃**: 텐서를 `NCHW`(채널이 앞)로 저장할지 `NHWC`(채널이 뒤)로 저장할지에 따라, 같은 Conv 연산이라도 캐시 히트율과 SIMD 활용도가 하드웨어마다 다르게 나옵니다. ONNX 그래프 자체는 이 선택에 무관심합니다.
- **타일 크기**: Conv를 한 번에 통째로 계산할지, 캐시 크기에 맞춰 잘게 쪼개 계산할지는 대상 하드웨어의 캐시/레지스터 용량에 따라 달라져야 하는데, ONNX 레벨에는 이런 정보가 들어설 자리가 없습니다.

즉 ONNX 그래프를 "그대로 인터프리터로 돌리는" 것과 "그 그래프가 뜻하는 계산을 특정 하드웨어에 맞게 재구성해서 돌리는" 것 사이에는 큰 간극이 있고, 이 시리즈가 다루는 게 바로 그 간극을 메우는 작업입니다.

---

## 2. 프레임워크 개수 × 하드웨어 개수 문제, 다시 등장

이 간극을 메우는 컴파일러를 만드는 문제는, [Lean4-MLIR 시리즈 0편](../../lean/lean4-mlir-codegen/00-what-is-mlir/)에서 다룬 "N개 언어 × M개 타겟" 문제와 똑같은 모양으로 다시 나타납니다. 프레임워크가 PyTorch, TensorFlow, JAX로 여러 개이고, 타겟이 CPU, GPU, TPU, 각종 엣지 NPU로 여러 개입니다.

```
        PyTorch  TensorFlow  JAX
CPU       ✕         ✕         ✕
GPU       ✕         ✕         ✕
NPU       ✕         ✕         ✕
```

ONNX는 이 문제의 절반(프레임워크 쪽)을 이미 풀어줍니다 — 어느 프레임워크에서 왔든 ONNX라는 공통 포맷으로 모이기 때문입니다. 하지만 나머지 절반, "이 공통 그래프를 각 하드웨어에 맞게 최적화해서 내리는" 문제는 여전히 남아 있습니다. 그리고 이 문제도 프레임워크 쪽과 마찬가지로 **공통 중간 표현**으로 풀 수 있습니다 — 다만 이번엔 표현 하나가 아니라, 추상화 수준이 다른 **여러 겹의 표현**이 필요합니다.

---

## 3. 왜 "여러 겹"이어야 하는가: 최적화마다 필요한 정보의 수준이 다르다

앞서 든 세 가지 예(연산 융합, 레이아웃, 타일링)를 다시 보면, 각각이 요구하는 정보의 수준이 다릅니다.

- **연산 융합**은 "이 Conv의 출력이 오직 이 BatchNorm에서만 쓰인다"는 **그래프 수준**의 정보가 있어야 판단할 수 있습니다.
- **타일링**은 "이 연산이 반복문 몇 겹으로 이루어져 있고, 각 축의 크기가 얼마인지"라는 **반복문 수준**의 정보가 있어야 합니다.
- **레지스터 배치나 SIMD 명령 선택**은 "이 값이 지금 레지스터에 있는지 메모리에 있는지"라는 **명령어 수준**의 정보가 있어야 합니다.

ONNX 그래프 하나만으로는 이 세 가지 정보 수준을 동시에 다룰 수 없습니다. 그래프 수준의 노드 하나(`Conv`)가 명령어 수준으로 완전히 풀어헤쳐지는 순간, 그래프 수준의 정보("이게 Conv였다")는 사라져 버리기 때문입니다. 그렇다고 그래프 수준에만 머무르면 타일링이나 레지스터 배치 같은 저수준 최적화를 표현할 수 없습니다.

MLIR이 이 문제에 들어맞는 이유가 여기 있습니다. MLIR은 하나의 표현 수준을 고르는 대신, **dialect**라는 단위로 여러 추상화 수준을 같은 인프라 위에서 동시에 다룰 수 있게 해줍니다. 이 시리즈에서 우리 예제가 실제로 거치게 될 dialect들을 미리 그려보면 이렇습니다.

```
onnx dialect        (그래프 수준: Conv, BatchNormalization, Relu 노드 — 2편)
   ↓ 그래프 최적화 (연산 융합, 상수 접기, 레이아웃 변환 — 3편)
linalg dialect       (반복문 구조가 드러난 텐서 연산 — 4편)
   ↓ 타일링, 버퍼화
affine / scf dialect (구체적인 반복문, 메모리 접근 — 4~5편)
   ↓ 벡터화
vector dialect       (SIMD 단위 연산 — 5편)
   ↓ 하드웨어별 최종 낮추기
gpu / llvm / 커스텀 accelerator dialect (6편)
```

각 화살표가 이 시리즈의 한 편에 대응합니다. 중요한 건 각 단계에서 "그 단계에 맞는 최적화만" 판단하면 된다는 점입니다 — 연산 융합은 `onnx` 수준에서, 타일링은 `linalg`/`affine` 수준에서, 명령어 선택은 그 아래 수준에서 각각 독립적으로 다뤄집니다.

---

## 4. 이 시리즈에서 다루는 파이프라인 전체 그림과 각 편의 역할

```
PyTorch 모델
   ↓ torch.onnx.export
ONNX 그래프 (Conv → BatchNorm → Relu)
   ↓ 2편: onnx dialect로 import, shape inference
onnx dialect의 MLIR 표현
   ↓ 3편: 그래프 수준 최적화 (연산 융합, 상수 접기, 레이아웃 변환)
융합된 onnx/tosa 표현
   ↓ 4편: linalg dialect로 낮추기, 타일링, 버퍼화
타일링된 affine/scf 반복문
   ↓ 5편: 벡터화, 루프 순서 재배치
vector dialect 표현
   ↓ 6편: 하드웨어별 최종 낮추기 (GPU 커널 또는 커스텀 가속기 명령)
실행 가능한 바이너리 / 가속기 명령 스트림
```

다음 편에서는 이 그림의 첫 화살표 — ONNX 그래프가 실제로 어떤 MLIR 텍스트(`onnx` dialect)로 들어오는지, 그리고 그 과정에서 왜 **shape inference**가 그래프 최적화의 전제 조건이 되는지를 우리 예제로 직접 확인합니다.
