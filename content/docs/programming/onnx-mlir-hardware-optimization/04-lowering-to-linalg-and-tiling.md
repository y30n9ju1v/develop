[3편](../03-graph-level-optimization/)에서 우리 예제는 `onnx.ConvBatchNormReluFused` 오퍼레이션 하나(NHWC 레이아웃)로 정리됐습니다. 이 글은 그 오퍼레이션이 **linalg dialect**로 낮춰지면서 처음으로 "몇 겹의 반복문으로, 각 축을 얼마나 순회하며" 계산되는지가 텍스트에 드러나는 과정을 다룹니다.

---

## 1. `onnx` dialect와 `linalg` dialect의 근본적인 차이

`onnx.Conv`는 "입력과 커널을 받아서 컨볼루션 결과를 낸다"는 사실만 선언할 뿐, 그 계산이 정확히 어떤 반복문으로 이루어지는지는 말하지 않습니다. `linalg` dialect의 오퍼레이션은 정반대입니다 — **각 출력 원소가 어떤 입력 원소들의 조합으로 계산되는지를 인덱싱 수식으로 명시**합니다.

컨볼루션을 `linalg.generic`으로 옮기면 이렇게 생겼습니다 (이해를 돕기 위해 필드를 간략화했습니다).

```mlir
linalg.generic {
  indexing_maps = [
    affine_map<(n, h, w, co, kh, kw, ci) -> (n, h + kh, w + kw, ci)>,  // 입력 텐서 접근
    affine_map<(n, h, w, co, kh, kw, ci) -> (co, kh, kw, ci)>,          // 커널 텐서 접근
    affine_map<(n, h, w, co, kh, kw, ci) -> (n, h, w, co)>              // 출력 텐서 접근
  ],
  iterator_types = ["parallel", "parallel", "parallel", "parallel", "reduction", "reduction", "reduction"]
} ins(%input, %kernel : tensor<1x224x224x3xf32>, tensor<64x3x3x3xf32>)
  outs(%output : tensor<1x224x224x64xf32>) {
^bb0(%in: f32, %k: f32, %acc: f32):
  %prod = arith.mulf %in, %k : f32
  %sum  = arith.addf %acc, %prod : f32
  linalg.yield %sum : f32
}
```

이 텍스트가 말하는 건 정확히 이겁니다 — "일곱 겹의 인덱스(`n, h, w, co, kh, kw, ci` — 배치, 출력 높이, 출력 너비, 출력 채널, 커널 높이, 커널 너비, 입력 채널)를 돌면서, 각 조합마다 입력 값과 커널 값을 곱해 누적한다." `iterator_types`의 `"parallel"`은 "이 축의 순회 순서는 결과에 영향을 주지 않으니 마음대로 재배치하거나 병렬화해도 된다"는 뜻이고, `"reduction"`은 "이 축은 누적(덧셈)이 일어나므로 순서를 함부로 바꾸면 부동소수점 결과가 미세하게 달라질 수 있다"는 뜻입니다. 이 구분이 5편에서 다룰 벡터화·병렬화가 "어느 축을 건드려도 안전한지" 판단하는 근거가 됩니다.

`onnx` 수준에서는 "Conv"라는 이름 하나로 표현되던 것이, 여기서는 이렇게 인덱싱 수식과 반복 종류가 전부 펼쳐진 형태로 바뀝니다. 이게 이 시리즈 1편에서 그렸던 dialect 스택의 두 번째 단(`linalg`)이 하는 역할입니다 — "무엇을 계산하는가"에서 "그 계산이 어떤 반복 구조를 갖는가"로 넘어가는 지점입니다.

## 2. 타일링: 왜 224×224를 한 번에 계산하면 안 되는가

`linalg.generic`이 반복문 구조를 드러내긴 했지만, 아직 이 반복문을 "어떤 순서로, 얼마나 큰 덩어리로" 실행할지는 정해지지 않았습니다. 이걸 그대로 가장 바깥 축부터 안쪽 축까지 순진하게 중첩 for문으로 펼치면 문제가 생깁니다.

우리 예제에서 출력 채널(`co`) 하나를 계산하려면 입력 채널(`ci`) 3개 × 커널 위치(`kh, kw`) 9개, 총 27개의 입력 값을 읽어야 합니다. 그런데 출력 채널이 64개이고 공간 위치가 224×224개이므로, 전체 계산에서 같은 입력 값이 반복해서 여러 번 읽힙니다 — 문제는 이 반복되는 접근 사이의 **거리**입니다. 만약 반복문이 `co`를 가장 안쪽에 두고, 그 안에서 `ci, kh, kw`를 매번 처음부터 다시 읽는다면, 캐시가 그 사이의 다른 데이터로 이미 밀려나 있어 매번 메모리에서 다시 읽어와야 합니다.

**타일링(tiling)**은 이 문제를, 반복문을 큰 덩어리 하나로 도는 대신 **작은 블록 단위로 쪼개서, 한 블록 안에서 재사용되는 데이터가 캐시에 남아 있는 동안 그 블록을 전부 끝내는** 방식으로 해결합니다.

```mlir
// 출력 공간(h, w)을 32×32 블록으로 타일링
scf.for %h_tile = 0 to 224 step 32 {
  scf.for %w_tile = 0 to 224 step 32 {
    // 이 32×32 블록 안에서는 co, kh, kw, ci를 도는 동안
    // 관련된 입력·커널 값들이 캐시에 계속 머무른다
    linalg.generic { ... } ins(%input_tile, %kernel : ...) outs(%output_tile : ...)
  }
}
```

타일 크기(여기서는 32)는 아무렇게나 고른 숫자가 아니라 **대상 하드웨어의 캐시 크기로부터 거꾸로 계산**됩니다. `32×32` 크기의 float 입력 타일 하나가 차지하는 메모리는 `32 × 32 × 4바이트 = 4KB`이고, 여기에 커널(`64×3×3×3×4바이트 ≈ 6.9KB`)과 출력 타일(`32×32×64×4바이트 = 256KB`)까지 더하면, 이 블록 하나가 L2 캐시(보통 수백 KB~수 MB) 안에 들어가는지가 타일 크기를 정하는 기준이 됩니다. 이 계산이 CPU와 GPU, 그리고 6편에서 다룰 커스텀 가속기마다 전부 다르기 때문에, **타일 크기는 대상 하드웨어를 알아야만 결정할 수 있는, 이 시리즈 전체에서 최초로 등장하는 "하드웨어 종속적" 파라미터**입니다.

## 3. 버퍼화(Bufferization): 텐서에서 메모리로

지금까지의 모든 텍스트는 `tensor<...>` 타입을 다뤘습니다. 텐서는 수학적인 값이지, 메모리 위의 실제 배열이 아닙니다 — MLIR의 텐서는 SSA(정적 단일 대입) 값처럼 "한 번 정의되면 값이 바뀌지 않는" 불변 객체로 다뤄집니다. 하지만 실제 하드웨어에서 실행되려면 결국 이 값들이 **메모리 버퍼**(`memref<...>`)로 바뀌어야 합니다.

**버퍼화**는 이 전환을 담당하는 pass로, 두 가지를 결정합니다.

1. **어느 텐서가 새 메모리를 할당받아야 하는가.** 예를 들어 최종 출력은 새로 할당된 버퍼에 쓰여야 합니다.
2. **어느 텐서가 다른 텐서의 메모리를 재사용할 수 있는가(in-place bufferization).** 만약 Relu 연산이 "입력을 읽어서 결과를 내는" 대신 "입력 버퍼를 그대로 덮어써서 결과로 삼는다"면, 별도의 출력 버퍼를 새로 할당할 필요가 없습니다. 이건 3편에서 다룬 연산 융합과 비슷한 효과를 메모리 할당 단계에서 한 번 더 만들어내는 것입니다 — 불필요한 할당과 해제 자체가 사라집니다.

```mlir
// 버퍼화 이후: tensor → memref
func.func @block(%x: memref<1x224x224x3xf32>, %out: memref<1x224x224x64xf32>) {
  scf.for %h_tile = 0 to 224 step 32 {
    scf.for %w_tile = 0 to 224 step 32 {
      linalg.generic { ... } ins(%x_tile : memref<...>) outs(%out_tile : memref<...>)
    }
  }
  return
}
```

이 단계를 거치고 나면 `tensor`는 텍스트에서 완전히 사라지고, 이후 5편에서 다룰 벡터화는 이 `memref` 위에서 "메모리의 어느 주소를 얼마나 넓게 한 번에 읽을 것인가"를 결정하는 작업이 됩니다.

## 4. 이번 편에서 정해진 것과, 아직 정해지지 않은 것

이번 편이 끝나는 시점에서 우리 예제는:

- **정해진 것**: 반복문의 구조(7겹 인덱스), 어느 축이 병렬화 가능하고 어느 축이 누적인지, 타일 크기(캐시에 맞춘 32×32), 어느 텐서가 메모리를 재사용하는지.
- **아직 정해지지 않은 것**: 타일 안의 반복문이 한 원소씩 처리되는지 아니면 SIMD 명령으로 여러 원소를 한 번에 처리하는지, 그리고 최종적으로 CPU 명령어인지 GPU 커널인지 커스텀 가속기 명령인지.

다음 편에서는 타일 안쪽의 반복문에 **벡터화**를 적용해 "한 번에 여러 원소를 처리하는" `vector` dialect로 낮추는 과정과, 이 선택이 하드웨어의 SIMD/벡터 유닛 폭에 어떻게 맞춰지는지를 다룹니다.
