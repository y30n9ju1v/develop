> [2편](../02-safety-encoded-ir/) 6절에서 "변수 사용 횟수를 추적하는 elaboration 확장은 훨씬 큰 별도의 프로젝트"라며 남겨둔 부분을 이 글이 이어서 다룹니다. [Counting Immutable Beans (Ullrich & de Moura, IFL'19)](https://arxiv.org/pdf/1908.05647)와 [FBIP 논문](https://www.microsoft.com/en-us/research/wp-content/uploads/2023/05/fbip.pdf)을 참고해 작성했습니다.

---

## 1. 2편에서 남겨둔 질문: "왜 타입 하나로는 안 되는가"

[2편](../02-safety-encoded-ir/)은 `Fin n` 타입 하나로 배열 범위 초과를 컴파일 에러로 만드는 데 성공했지만, 같은 전략을 이중 해제(double-free)에 그대로 적용하면 실패한다는 걸 실제 코드로 보여줬습니다. 이유는 배열 범위와 자원 소유권이 **근본적으로 다른 종류의 질문**이기 때문입니다.

- `i < 5` — **값에 대한 명제**. `i`가 실제로 무엇인지 elaboration이 들여다보기만 하면 참·거짓을 판정할 수 있습니다.
- "`o`가 이미 `release`에 쓰였는가" — **항의 구조에 대한 사실**. 코드가 그 변수를 몇 번 언급했는지를 세야 하는 질문이고, Lean4의 타입 체커는 이걸 검사해서 거부하는 기능을 애초에 갖고 있지 않습니다.

이 글은 "그렇다면 이 검사기를 실제로 어떻게 설계할 것인가"에 답합니다.

## 2. "참조 카운트가 1이면 선형 타입도 공짜"라는 오해를 정확히 짚기

2편이 짚었던 오해를 조금 더 파고들 필요가 있습니다. Lean4는 실제로 컴파일러 내부에서 **"이 값이 유일하게 참조되는가"**를 추적합니다 — 이게 [Perceus](https://arxiv.org/pdf/1908.05647) 알고리즘과 **FBIP(Functional But In-Place)** 최적화의 핵심입니다. 참조 카운트가 1인 값을 갱신할 때는 새 메모리를 할당하는 대신 **그 자리에서 바로 덮어쓸 수 있다**는 걸 알고 있으면, 함수형 스타일의 불변 데이터 구조를 명령형 코드만큼 빠르게 실행할 수 있습니다.

문제는 이 추적의 **목적**입니다. FBIP의 참조 카운트 분석은 "이 최적화를 적용해도 관찰 가능한 동작이 똑같은가"만 확인하면 충분합니다 — 최적화가 적용되지 않아도(참조 카운트가 1보다 커서 새로 복사해야 해도) 프로그램은 여전히 올바르게 실행됩니다. 반면 우리가 원하는 건 정반대입니다 — **"이 변수가 두 번 쓰이면 컴파일을 거부"**하는 것이므로, 분석 결과가 최적화 여부를 조용히 바꾸는 게 아니라 **사용자에게 보이는 에러**로 이어져야 합니다. 즉 같은 종류의 정보(참조/사용 횟수)를 이미 컴파일러가 계산하고 있지만, 그 정보를 "빠르게 실행하기 위한 힌트"로 쓰느냐 "프로그램을 거부하는 근거"로 쓰느냐가 완전히 다른 설계입니다.

## 3. elaboration 확장 설계: `Expr` 트리를 순회하며 변수 등장 횟수를 센다

Lean4의 elaboration은 표면 문법(`Syntax`)을 최종 항(`Expr`)으로 바꾸는 과정입니다. 이 시리즈가 지금까지 써온 전략 — "elaboration에 개입해 통과 여부를 판단한다" — 을 이번엔 **항의 구조**에 적용합니다.

```lean
-- 자원을 감싸는 마커 타입 (실제로는 아무 데이터도 추가하지 않음)
def Owned (α : Type) := α

partial def countUses (fvar : FVarId) (e : Expr) : Nat :=
  match e with
  | .fvar id => if id == fvar then 1 else 0
  | .app f a => countUses fvar f + countUses fvar a
  | .lam _ _ b _ => countUses fvar b
  | .letE _ _ v b _ => countUses fvar v + countUses fvar b
  -- ... 나머지 Expr 생성자도 재귀적으로 순회
  | _ => 0
```

이 `countUses`가 이 시스템의 핵심입니다 — `Owned`로 표시된 변수 하나를 골라, 함수 본문을 나타내는 `Expr` 트리 전체를 순회하며 그 변수가 몇 번 등장하는지 셉니다. 이 결과를 elaboration 후처리 단계(Lean4의 `elab_rules`나 커맨드 확장으로 등록하는 linter)에 연결하면 됩니다.

```lean
-- elaboration이 끝난 뒤 실행되는 검사
def checkLinearUse (declName : Name) (ownedVars : List FVarId) (body : Expr) : MetaM Unit := do
  for fvar in ownedVars do
    let uses := countUses fvar body
    if uses > 1 then
      throwError s!"{declName}: 소유된 값이 {uses}번 쓰였습니다 (최대 1번만 허용)"
```

이 검사기가 [2편](../02-safety-encoded-ir/)의 `useTwice` 예제를 만나면, `release o`가 본문에서 두 번 등장하는 걸 세어 컴파일 에러를 냅니다 — `Fin n`이 값에 대한 증명 의무를 자동 생성했던 것과 달리, 여기서는 **우리가 직접 만든 순회 로직이 통과 여부를 판단**한다는 점이 근본적으로 다릅니다.

## 4. Rust의 대여 검사기와 무엇이 같고, 무엇이 다른가

이 설계는 Rust의 오너십 모델과 같은 문제를 풀지만, 위치가 다릅니다.

| | Rust | 이 글의 Lean4 확장 |
|---|---|---|
| 검사 시점 | 컴파일러 자체에 내장(MIR 위에서 실행되는 borrow checker) | 사용자가 라이브러리로 얹는 elaboration 확장 |
| 검사 범위 | 이동(move)뿐 아니라 **대여(borrow)의 생존 기간(lifetime)**까지 정교하게 추적 | 이 글의 최소 버전은 "몇 번 쓰였는가"만 세는, Rust 대비 훨씬 거친 근사 |
| 실패 시 메시지 | 컴파일러가 표준으로 제공하는, 수년간 다듬어진 진단 메시지 | 우리가 `throwError`로 직접 작성해야 하는 메시지 |
| 이식성 | 이 규칙이 Rust라는 언어 자체의 일부 | Lean4 코드베이스마다 이 확장을 개별적으로 가져다 써야 함 |

Rust가 이 문제를 "언어 설계 단계에서 컴파일러에 박아 넣은" 것과 달리, 우리는 Lean4의 **메타프로그래밍 능력(elaboration에 개입하는 API)**을 이용해 **같은 효과를 라이브러리 수준에서 재현**하고 있습니다. 이게 [1편](../01-why-lean4-for-mlir/)에서 다룬 "Lean4의 elaboration이 컴파일러 프론트엔드와 구조적으로 닮았다"는 관찰이 갖는 실질적인 힘입니다 — 새로운 정적 검사가 필요할 때마다 언어 자체를 포크하지 않고도, 이런 확장을 라이브러리로 추가할 수 있습니다.

## 5. 이 검사 결과를 파이프라인에 잇기: attribute로 실어 보내기

[3편](../03-emitting-mlir-text/)에서 `bounds_checked` attribute로 배열 범위 증명 여부를 MLIR 텍스트에 실어 보냈던 것과 정확히 같은 방식으로, 이 소유권 검사 결과도 attribute로 실어 보낼 수 있습니다.

```mlir
"safec.release"(%o) {ownership_verified = true} : (!safec.owned<i32>) -> ()
```

`ownership_verified = true`는 "이 값이 여기서 정확히 한 번만 해제된다는 걸 Lean4 elaboration이 확인했다"는 뜻이고, [4편](../04-mlir-pipeline-integration/)의 dialect conversion이 이 attribute를 신뢰해 별도의 런타임 참조 카운트 검사 없이 직접 `free()` 호출로 낮출 수 있습니다. 그리고 이 attribute도 결국 방출 코드가 만든 텍스트이므로, [5편](../05-translation-validation/)이 다룬 신뢰 경계 문제가 여기서도 똑같이 적용됩니다 — `ownership_verified`를 파싱하는 코드 자체도 최소화된 TCB에 포함시켜야 하고, 독립 검사기로 이 attribute의 값이 실제 사용 횟수와 일치하는지 다시 확인하는 게 안전합니다.

## 6. 이 최소 버전의 한계

이 글의 `countUses`는 의도적으로 단순화된 버전이고, 실전에서는 최소 이런 지점들이 더 필요합니다.

- **분기(if/match) 안에서의 사용**: `if c then release o else release o`는 실행 경로상 `o`가 정확히 한 번만 쓰이지만, 단순히 트리 전체를 순회하며 세면 2번으로 잘못 셀 수 있습니다. Rust의 대여 검사기가 제어 흐름 그래프(CFG) 위에서 동작하는 이유가 바로 이것입니다.
- **클로저로의 캡처**: 값이 클로저 안으로 이동(move)된 뒤 그 클로저가 여러 번 호출되면, 클로저 "생성"은 한 번이지만 "실행"은 여러 번일 수 있어 별도의 규칙이 필요합니다.
- **재귀 함수**: 재귀 호출 안에서 자원이 몇 번 쓰이는지는 호출 횟수(런타임에만 정해짐)에 따라 달라지므로, 정적 분석은 "재귀 호출 하나당 최대 한 번"처럼 더 보수적인 규칙으로 근사해야 합니다.

이 세 가지가 바로 Rust의 대여 검사기가 수년에 걸쳐 다듬어온 지점들이고, 이 글의 최소 버전은 그중 가장 단순한 경우(분기도 재귀도 없는 직선형 코드)만 정확히 처리합니다 — 하지만 2편이 짚었던 "이중 해제를 완전히 봉쇄하는 것"이 아니라 "가장 흔한 실수 패턴 하나를 잡아내는 것"이 목표라면, 이 최소 버전만으로도 실용적인 출발점이 됩니다.

## 7. 정리

- 배열 범위(`Fin n`)와 자원 소유권은 "값에 대한 증명"과 "항의 구조에 대한 사실"이라는 근본적으로 다른 종류의 정적 검사이고, Lean4의 타입 체커는 전자만 자연스럽게 다룹니다.
- Lean4가 내부적으로 추적하는 참조 카운트(FBIP/Perceus)는 **최적화를 위한 힌트**일 뿐, 사용자 코드를 거부하는 근거로 노출되지 않습니다 — 우리가 원하는 검사는 별도로 만들어야 합니다.
- `Expr` 트리를 순회하며 변수 등장 횟수를 세는 elaboration 확장으로 이 검사를 라이브러리 수준에서 구현할 수 있고, 이 결과를 [3편](../03-emitting-mlir-text/)의 attribute 패턴으로 실어 보내면 파이프라인에 그대로 연결됩니다.
- Rust의 대여 검사기와 같은 문제를 풀지만, Rust는 이걸 컴파일러 자체에 내장한 반면 우리는 elaboration API로 라이브러리 수준에서 재현합니다 — 다만 분기·클로저·재귀를 정확히 다루려면 이 글의 최소 버전보다 훨씬 정교한 제어 흐름 분석이 필요합니다.
