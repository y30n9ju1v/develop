## 1. 5편에서 남겨둔 질문: "검사기는 결국 누가 짜는가"

[5편](../05-translation-validation/)은 번역 검증을 "방출 코드가 만든 각 출력을 독립적으로 재확인한다"는 접근으로 소개하고, `bounds_proof` attribute를 힌트로 받아 값싸게 재확인하는 증명 운반 코드(PCC) 설계까지 다뤘습니다. 그런데 이 verifier 자체는 여전히 **사람이 손으로 작성한 코드**입니다 — "`getUpper()`와 `getVar()`가 일치하는지 확인한다"는 로직을 우리가 직접 짰습니다. 이 verifier에 버그가 있으면(5편이 지적한 것처럼), 우리는 또 다른 손으로 짠 코드로 그 verifier를 검증해야 하는 무한 후퇴에 빠질 위험이 있습니다.

**SMT(Satisfiability Modulo Theories) 기반 번역 검증**은 이 문제를 다른 각도에서 풉니다 — "이 두 코드가 같은 일을 하는가"라는 질문 자체를 논리식으로 바꾸고, 그 논리식이 참인지를 **범용 자동 증명 도구(SMT solver)**에게 맡깁니다. 우리가 짜는 건 개별 사례에 특화된 검사 로직이 아니라, "프로그램을 논리식으로 바꾸는 규칙" 하나뿐이고, 이 규칙은 훨씬 재사용 가능합니다.

## 2. 핵심 아이디어: 프로그램을 입출력 관계를 나타내는 논리식으로 바꾼다

SMT 기반 동등성 검사의 기본 틀은 이렇습니다.

1. 원본 프로그램(우리 예제라면 Lean4 IR, `arr.get ⟨i, h⟩`)을 "입력이 주어졌을 때 출력이 무엇인가"를 나타내는 논리식으로 인코딩합니다.
2. 방출된 프로그램(C나 MLIR 코드)도 같은 방식으로 논리식으로 인코딩합니다.
3. **"두 논리식이 모든 입력에 대해 같은 결과를 낸다"의 부정**, 즉 "이 두 식이 다른 결과를 내는 입력이 존재한다"는 식을 만들어 SMT solver에게 묻습니다.
4. solver가 "충족 불가능(UNSAT)"이라고 답하면 그런 입력이 존재하지 않는다는 뜻 — 즉 **두 프로그램이 동등하다는 증명**을 얻습니다. 반대로 "충족 가능(SAT)"이라고 답하면, solver는 두 프로그램이 실제로 다르게 동작하는 **구체적인 반례**까지 함께 내놓습니다.

이 마지막 지점이 손으로 짠 verifier와 결정적으로 다릅니다 — verifier는 "이 특정 실행에서 값이 맞는지"만 확인하지만, SMT solver는 원칙적으로 **가능한 모든 입력에 대해** 동등성을 확인합니다(물론 인코딩 가능한 범위 안에서라는 단서가 붙습니다 — 4절에서 다룹니다).

## 3. 우리 예제를 SMT 공식으로 인코딩하기

[3편](../03-emitting-mlir-text/)의 `get_element` 예제(`arr.get ⟨2, by decide⟩`, 배열 크기 5)로 인코딩을 구체적으로 따라가 봅니다.

**Lean4 쪽 의미**: 배열 크기가 5이고 인덱스가 정적으로 2로 고정된 `get` — "인덱스가 항상 유효하므로 결과는 항상 `arr[2]`".

```smt2
; 배열은 정수 인덱스에서 정수 값으로 가는 함수로 모델링(SMT의 배열 이론)
(declare-fun arr () (Array Int Int))
(declare-const result_lean Int)
(assert (= result_lean (select arr 2)))
```

**방출된 C 쪽 의미**: `bounds_checked = true`를 신뢰해 런타임 검사 없이 바로 `arr[2]`를 읽는 코드.

```smt2
(declare-const result_c Int)
(assert (= result_c (select arr 2)))
```

이제 **동등성의 부정**을 solver에게 묻습니다.

```smt2
(assert (not (= result_lean result_c)))
(check-sat)  ; UNSAT이 나와야 두 결과가 항상 같다는 뜻
```

이 경우는 두 식이 문자 그대로 동일하므로 당연히 UNSAT이 나옵니다 — 하지만 [3편](../03-emitting-mlir-text/)의 `get_user_index` 예제(`if h : i < 5 then ... else ...`)처럼 **런타임 분기가 있는 경우**가 진짜 흥미로운 지점입니다. 이 경우 Lean4 쪽 의미는 "`i < 5`가 참일 때만 `arr[i]`, 아니면 정의되지 않음(또는 별도 처리)"이 되고, 방출된 C 코드도 똑같이 `if (i < size) return arr[i]; else ...`라는 조건 분기를 포함해야 이 인코딩이 성립합니다. **분기 조건 자체가 정확히 대응하는지가 SMT 인코딩이 실제로 잡아낼 수 있는 버그의 핵심**입니다 — 예를 들어 방출 코드가 실수로 `i <= size`라고 썼다면, solver는 `i = 5`(원본에서는 범위 밖, 방출 코드에서는 범위 안으로 잘못 판정)라는 구체적인 반례를 SAT 결과로 즉시 찾아냅니다.

## 4. 이 접근이 실제로 어디까지 통하는가: 루프와 재귀의 벽

SMT 인코딩은 강력하지만 공짜가 아닙니다. **유한한 직선형 코드(분기는 있어도 반복이 없는 코드)**는 이렇게 비교적 기계적으로 논리식으로 옮길 수 있지만, **루프나 재귀**가 들어오면 사정이 달라집니다.

```c
for (int i = 0; i < n; i++) { sum += arr[i]; }
```

이 코드를 "입력과 출력의 관계"로 인코딩하려면, `n`번 반복한 뒤의 `sum` 값을 하나의 논리식으로 표현해야 하는데, `n`이 구체적인 숫자로 고정되지 않는 한 이건 **일반적으로 유한한 논리식으로 표현할 수 없습니다**(반복 횟수가 정해지지 않은 루프의 의미는 본질적으로 귀납적입니다). 이 문제를 다루는 표준적인 방법이 두 가지입니다.

- **루프 전개(bounded unrolling)**: "최대 N번까지만 반복한다"고 가정하고 그 범위 안에서만 검증합니다 — 완전한 증명은 아니지만, 실무에서 흔히 쓰이는 실용적 타협입니다.
- **루프 불변식(loop invariant) 제공**: "이 루프가 매 반복마다 유지하는 성질"을 별도로 명시해서, 그 불변식을 이용해 귀납적으로 증명합니다 — 이건 정확히 [5편](../05-translation-validation/)의 PCC가 `bounds_proof` 같은 힌트를 요구했던 것과 같은 종류의 타협입니다. **자동화의 정도가 다를 뿐, "복잡한 증명은 힌트를 받아서 값싸게 확인한다"는 원칙 자체는 PCC와 SMT 기반 검증이 공유합니다.**

즉 SMT 기반 검증이 verifier를 손으로 짜는 수고를 없애주는 건 사실이지만, **루프·재귀가 있는 순간 다시 "누군가 불변식이라는 형태의 힌트를 줘야 한다"는 지점으로 돌아옵니다** — 다만 이번엔 그 힌트가 개별 verifier 코드가 아니라, SMT solver가 이해할 수 있는 논리식 형태라는 점이 다릅니다.

## 5. PCC와 SMT 기반 검증의 관계: 경쟁이 아니라 같은 축의 다른 지점

[5편](../05-translation-validation/)이 다룬 PCC와 이 글의 SMT 기반 검증은 서로 대체재가 아니라, **"증명 자동화의 정도"라는 하나의 축 위에 있는 서로 다른 지점**입니다.

| | 손으로 짠 verifier (5편) | PCC (5편) | SMT 기반 검증 (이 글) |
|---|---|---|---|
| 검사 대상 | 특정 attribute 값 하나 | attribute + 그걸 뒷받침하는 힌트 | 프로그램 전체의 입출력 관계 |
| 재사용성 | 이 attribute에만 특화 | 이 attribute 종류에만 특화 | 인코딩 규칙만 있으면 임의의 직선형 코드에 재사용 |
| 루프/재귀 대응 | 애초에 다루지 않음(범위 밖) | 힌트로 우회 가능 | 전개 또는 불변식 힌트로 우회(결국 힌트가 다시 필요) |
| 새 신뢰 지점 | verifier 코드 자체 | 힌트 파싱 코드 | 인코딩 규칙 + SMT solver 자체(신뢰하거나, solver의 증명 항을 재검증) |

마지막 행이 중요합니다 — SMT 기반 검증도 **TCB를 0으로 만들지는 못합니다**. solver 자체를 신뢰하거나(대부분의 실전 프로젝트가 택하는 타협), 아니면 solver가 UNSAT일 때 함께 내놓는 **증명 항(proof term)**을 별도로 재검증해야 합니다 — 이건 결국 [5편](../05-translation-validation/)의 "TCB를 어디까지 좁힐 것인가"라는 질문을 이번엔 "우리 verifier 코드"가 아니라 "SMT solver라는 범용 도구"로 옮겨서 다시 묻는 것입니다.

---

## 6. 정리

- SMT 기반 번역 검증은 두 프로그램의 의미를 논리식으로 인코딩하고, "동등성의 부정"이 충족 불가능(UNSAT)임을 SMT solver로 확인해 동등성을 증명합니다 — SAT가 나오면 solver가 구체적인 반례까지 제공합니다.
- 우리 시리즈의 배열 접근 예제(정적 인덱스, 런타임 분기)는 SMT의 배열 이론과 조건식으로 비교적 직접 인코딩할 수 있고, 분기 조건이 잘못 방출된 버그(`<` 대신 `<=`)를 정확히 잡아낼 수 있습니다.
- 루프·재귀가 있는 코드는 유한한 논리식으로 직접 인코딩할 수 없고, **전개(bounded unrolling)**나 **루프 불변식**이라는 형태의 힌트가 다시 필요합니다 — [5편](../05-translation-validation/)의 PCC가 요구했던 힌트와 원리적으로 같은 타협입니다.
- SMT 기반 검증은 손으로 짠 verifier를 대체할 수 있지만 TCB를 0으로 만들지는 못합니다 — 신뢰 지점이 "우리가 짠 검사 코드"에서 "인코딩 규칙과 SMT solver 자체"로 옮겨갈 뿐입니다.
