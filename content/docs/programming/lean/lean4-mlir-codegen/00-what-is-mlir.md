이 시리즈는 다음 편([1편: 왜 Lean4로 MLIR을 만드는가](01-why-lean4-for-mlir/))부터 Lean4와 MLIR을 곧바로 연결하기 시작합니다. 그 전에, MLIR 자체가 무엇이고 왜 존재하는지를 모르면 "왜 굳이 이걸 중간에 끼우는가"라는 질문에 감이 잡히지 않습니다. 이 글은 그 배경 지식만 다룹니다 — Lean4는 등장하지 않습니다.

---

## 1. 컴파일러가 흔히 겪는 문제: N개 언어 × M개 타겟

컴파일러를 만든다는 건 결국 "이 언어로 쓰인 프로그램을 저 하드웨어에서 실행 가능한 형태로 바꾼다"는 일입니다. 문제는 언어도 여러 개이고 타겟도 여러 개라는 겁니다 — C, Rust, Swift, Julia 같은 언어들이 있고, x86, ARM, GPU 같은 타겟들이 있습니다.

가장 순진한 접근은 언어마다 타겟마다 전용 변환기를 하나씩 짜는 것입니다. 하지만 이러면 언어가 $N$개, 타겟이 $M$개일 때 최악의 경우 $N \times M$개의 변환기가 필요해집니다. 언어 하나가 추가될 때마다 모든 타겟에 대한 변환기를 새로 짜야 하고, 타겟 하나가 추가될 때도 마찬가지입니다.

```
     C   Rust  Swift  Julia
x86  ✕    ✕     ✕     ✕
ARM  ✕    ✕     ✕     ✕
GPU  ✕    ✕     ✕     ✕
```

이 문제를 풀기 위해 컴파일러들은 오래전부터 **공통 중간 표현(IR, Intermediate Representation)**이라는 답을 써 왔습니다. 모든 언어가 일단 같은 IR로 내려가고, 그 IR에서 모든 타겟으로 다시 올라가면, 필요한 변환기는 $N + M$개로 줄어듭니다. LLVM IR이 바로 이 자리를 맡아서 지난 20년간 C, Rust, Swift 같은 언어들의 공통 백엔드 역할을 해 왔습니다.

```
     C   Rust  Swift  Julia
      ╲   │     │    ╱
       ╲  │     │   ╱
        [ 공통 IR (예: LLVM IR) ]
       ╱  │     │   ╲
      ╱   │     │    ╲
x86      ARM        GPU
```

## 2. LLVM IR로는 부족해지는 지점: 정보가 너무 일찍 사라진다

LLVM IR은 훌륭한 공통 IR이지만, 한 가지 특성이 있습니다 — **낮은 수준(low-level)**입니다. LLVM IR에는 기본적으로 정수 덧셈, 메모리 로드/스토어, 분기 같은 명령들만 있습니다. "이건 행렬 곱셈이다"라거나 "이 반복문은 배열을 순회한다" 같은 고수준 의미는 LLVM IR에 도달하는 순간 이미 개별 덧셈·곱셈·분기 명령의 나열로 풀어헤쳐져 사라집니다.

문제는 컴파일러가 하고 싶은 최적화 중 상당수가 바로 이 고수준 의미를 필요로 한다는 것입니다. 예를 들어 "이 두 행렬 곱셈을 타일 단위로 쪼개 캐시에 맞게 재배열하라"는 최적화는, 그 연산이 애초에 "행렬 곱셈"이라는 걸 알고 있어야 판단할 수 있습니다. LLVM IR 수준까지 내려가 개별 덧셈 명령들만 남은 뒤에는 이 정보를 되살릴 방법이 없습니다.

그렇다고 모든 언어·모든 도메인(딥러닝 텐서 연산, SQL 쿼리 계획, 하드웨어 회로 등)마다 처음부터 끝까지 전용 컴파일러 인프라를 새로 만드는 건 앞서 본 $N \times M$ 문제로 되돌아가는 것입니다. 딥러닝 컴파일러(TensorFlow의 XLA, PyTorch의 여러 백엔드), 하드웨어 합성 도구, SQL 엔진이 실제로 이런 이유로 각자 따로 IR과 최적화 인프라를 만들어 쓰고 있었습니다 — 서로 다른 도메인인데도 "그래프를 순회하며 패턴을 찾아 바꿔치기한다", "타입을 확인한다", "출력용 텍스트로 직렬화한다" 같은 인프라 코드는 놀랍도록 비슷하게 중복되어 있었습니다.

## 3. MLIR의 답: 표현 수준 자체를 프레임워크로 만든다

**MLIR(Multi-Level Intermediate Representation)**은 Google에서 시작해 현재 LLVM 프로젝트의 일부로 개발되는 컴파일러 인프라입니다. MLIR의 핵심 아이디어는 "고수준 표현이냐 저수준 표현이냐" 사이에서 하나를 고르는 대신, **여러 수준의 표현을 같은 프레임워크 위에서 동시에 다루게 만드는 것**입니다.

이걸 가능하게 하는 장치가 **dialect**입니다. dialect는 특정 도메인이나 추상화 수준에 맞는 오퍼레이션(연산)들의 집합입니다. "행렬 곱셈"이라는 고수준 개념이 필요하면 그런 오퍼레이션을 가진 dialect를 새로 정의하면 되고, "정수 덧셈"이라는 저수준 개념이 필요하면 그런 dialect를 쓰면 됩니다. 같은 프로그램이 여러 dialect의 오퍼레이션을 동시에 담고 있을 수도 있고, 한 dialect에서 다른 dialect로 점진적으로 **낮추는(lowering)** 변환을 거치며 고수준 정보를 최대한 오래 유지한 채로 저수준까지 내려갈 수 있습니다.

```
고수준 dialect (예: 행렬 곱셈, 텐서 연산)
   ↓ 낮추기 (고수준 정보를 최대한 활용해 최적화)
중간 dialect (예: 반복문, 조건 분기)
   ↓ 낮추기
저수준 dialect (예: 개별 산술 연산, 메모리 접근)
   ↓ 최종 변환
LLVM IR / C / SystemVerilog / ...
```

중요한 건 이 dialect들을 MLIR이 전부 미리 만들어 두는 게 아니라는 점입니다. MLIR은 "오퍼레이션을 정의하는 방법", "그 오퍼레이션들을 그래프로 묶는 방법", "한 dialect의 오퍼레이션을 다른 dialect의 오퍼레이션으로 바꾸는 방법"이라는 **공통 뼈대**만 제공하고, 실제 오퍼레이션의 목록과 의미는 누구나 자신의 도메인에 맞게 새로 정의할 수 있습니다. 이 시리즈의 뒷부분(3편)에서 우리가 `safec`이라는 이름의 커스텀 dialect를 직접 정의하게 되는 이유가 바로 이것입니다 — MLIR을 쓴다는 건 정해진 언어 하나를 배우는 게 아니라, 이 뼈대 위에 우리 도메인(안전성이 증명된 배열 접근)에 맞는 표현을 짓는 일입니다.

## 4. MLIR 프로그램을 이루는 네 가지 조각

dialect가 무엇이든, MLIR로 표현된 프로그램은 항상 다음 네 가지 조각의 조합으로 이루어집니다. (구체적인 예제는 3편에서 우리 dialect로 직접 손으로 짜 봅니다.)

1. **Operation (오퍼레이션)**: 프로그램의 기본 단위입니다. "값을 몇 개 받아서(operand), 값을 몇 개 만들어낸다(result)"는 함수 호출과 비슷한 모양이며, 오퍼레이션의 이름 자체가 `dialect이름.오퍼레이션이름`(예: `arith.addi`, `scf.for`) 형태로 어느 dialect에 속하는지 드러냅니다.
2. **Region과 Block**: 반복문이나 조건 분기처럼 오퍼레이션 하나가 코드 블록을 통째로 품어야 하는 경우가 있습니다. 이 코드 블록이 **region**이고, region 안의 명령들이 순서대로 나열된 단위가 **block**입니다. LLVM IR의 기본 블록(basic block)과 비슷하지만, MLIR에서는 오퍼레이션이 region을 몇 개든, 중첩해서든 가질 수 있습니다.
3. **Attribute**: 오퍼레이션에 붙는 컴파일 타임 상수 메타데이터입니다. "이 정수 상수의 값은 5다"부터 "이 배열 접근은 범위 검사가 이미 끝났다"처럼 임의의 정적 정보를 담을 수 있습니다. 이 시리즈에서 Lean4가 증명해낸 안전성 정보가 최종적으로 실려 가는 자리가 바로 이 attribute입니다.
4. **Type**: 값(operand, result)마다 붙는 타입입니다. 정수, 부동소수점 같은 기본 타입 외에도 dialect가 텐서, 행렬, 회로 신호 같은 자기만의 타입을 새로 정의할 수 있습니다.

이 네 조각이 전부입니다. 어떤 dialect든 — 딥러닝 텐서 연산이든, 우리가 3편에서 만들 안전 배열 접근이든 — 결국 오퍼레이션·region/block·attribute·type의 조합으로 표현됩니다.

## 5. 낮추기(Lowering)와 검증(Verification)이라는 두 가지 표준 절차

dialect를 자유롭게 정의할 수 있다고 해서 아무렇게나 표현해도 된다는 뜻은 아닙니다. MLIR은 모든 dialect에 공통으로 적용되는 두 가지 절차를 인프라 차원에서 제공합니다.

**낮추기(Lowering, 또는 dialect conversion)**는 한 dialect의 오퍼레이션들을 다른(보통 더 저수준인) dialect의 오퍼레이션들로 규칙에 따라 바꾸는 변환입니다. "이 오퍼레이션을 저 오퍼레이션들의 조합으로 바꿔라"는 규칙(conversion pattern)을 여러 개 등록해 두면, MLIR의 인프라가 프로그램 전체를 순회하며 규칙을 일괄 적용해 줍니다. 이 규칙을 직접 짜는 사람이 매번 새로 만들어야 하는 건 딱 "무엇을 무엇으로 바꿀지"이지, "그래프를 어떻게 순회할지" 같은 반복 작업이 아닙니다.

**검증(Verification)**은 각 오퍼레이션이 스스로 지켜야 할 구조적 규칙(예: "이 오퍼레이션은 정확히 두 개의 operand를 받아야 한다")을 선언해 두면, MLIR이 프로그램을 만들거나 변환할 때마다 자동으로 그 규칙을 확인해 주는 절차입니다. 오퍼레이션을 새로 정의하는 사람은 "무엇이 잘못된 형태인지"만 선언하면 되고, 그 확인을 실행하는 순회 로직은 다시 만들 필요가 없습니다.

이 두 절차가 왜 중요한지는 이 시리즈 전체에서 반복해서 등장합니다 — Lean4가 증명한 안전성이 attribute로 실려 MLIR에 들어온 뒤, 그 사실이 다음 단계로 넘어갈 때마다 검증과 낮추기라는 이 표준 절차 위에서 다시 확인되고 다시 변환됩니다.

## 6. 이 시리즈에서 MLIR이 맡는 역할

정리하면, MLIR은 "언어와 타겟 사이를 잇는 공통 IR"이라는 문제를, 표현 수준 하나를 고정하는 대신 **dialect라는 확장 가능한 단위로 여러 표현 수준을 같은 인프라 위에서 다루게 만드는 것**으로 풀어낸 프레임워크입니다.

이 시리즈에서 우리가 MLIR을 쓰는 이유도 정확히 이 지점과 맞닿아 있습니다. Lean4가 증명한 "이 배열 접근은 안전하다"는 사실을 최종 C 코드로 곧장 떨어뜨리는 대신, 그 사실을 실어 나를 우리만의 dialect(`safec`)를 MLIR 위에 정의하고, 이미 갖춰진 검증·낮추기 인프라를 그대로 빌려 씁니다. 다음 편([1편: 왜 Lean4로 MLIR을 만드는가](01-why-lean4-for-mlir/))부터는 이 자리에 Lean4가 어떻게 연결되는지 — 그리고 이 연결이 C를 직접 찍는 것보다 왜 유리한지 — 를 다룹니다.
