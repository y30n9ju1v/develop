[1편](../01-why-lean4-for-mlir/)에서 "길이 5인 배열 `arr`에서 `arr[i]`를 안전하게 꺼낸다"는 예제를 소개했습니다. 이 글은 그 예제를 실제 Lean4 코드로 만들어보면서, 안전성을 "검사"가 아니라 "타입으로 표현 불가능하게 만들기"로 확보하는 원리를 다룹니다.

---

## 1. "검사"와 "표현 불가능"의 차이를 예제로 보기

C의 `arr[i]`는 `i`가 어떤 정수든 다 받아줍니다. 컴파일러는 이걸 막지 않고, 대신 우리가 직접 검사 코드를 넣어야 합니다.

```c
int get_checked(int i) {
    if (i < 0 || i >= 5) {
        // 여기서 뭘 해야 할까? 에러 코드 반환? 프로그램 종료?
        return -1;
    }
    return arr[i];
}
```

이 방식의 문제는, 검사를 깜빡한 곳이 프로그램 어딘가에 딱 하나만 있어도 버그가 됩니다. 검사가 필요한 모든 지점을 사람이 빠짐없이 챙겨야 합니다.

Lean4에서는 이 문제를 뒤집습니다. "범위를 벗어난 인덱스"라는 값 자체를 아예 만들 수 없는 타입을 씁니다.

```lean
#check (⟨2, by decide⟩ : Fin 5)  -- Fin 5, 값은 2
-- #check (⟨7, by decide⟩ : Fin 5)  -- 에러! 7 < 5를 증명할 수 없음
```

`Fin 5`는 "0 이상 5 미만인 자연수"만 담을 수 있는 타입입니다. `Fin 5` 타입의 값은 항상 숫자와 "이 숫자가 5보다 작다"는 증명, 이 둘의 쌍입니다. 증명이 없으면 애초에 값을 만들 수 없으므로, `Fin 5` 타입의 변수를 손에 쥐고 있다는 것 자체가 "이 값은 반드시 0~4 사이"라는 걸 이미 보장합니다. `if`문으로 매번 확인할 필요가 없습니다 — 확인이 필요 없는 게 아니라, **확인이 이미 그 값을 만드는 순간에 끝나 있는 것**입니다.

이게 왜 가능한지는 *Theorem Proving in Lean 4*의 [종속 타입 이론](../../theorem-proving-in-lean4/02-dependent-type-theory/#what-makes-dependent-type-theory-dependent) 장이 정확히 짚습니다 — "타입이 값에 따라 달라질 수 있다"는 게 종속 타입 이론의 정의 자체이고, 그 장이 예시로 드는 `Vector α n`(길이 `n`이 타입에 박힌 벡터)이 `Fin n`과 같은 발상을 보여줍니다. `Fin n` 자체는 Lean4 코어에서 `structure Fin (n : Nat) where val : Nat; isLt : val < n`으로 정의된 **평범한 구조체**입니다 — 정확히 [구조체와 레코드](../../theorem-proving-in-lean4/09-structures-and-records/) 장에서 배우는 "필드가 데이터와 그 데이터에 대한 증명을 함께 담는" 패턴 그대로이고, 바로 다음 절에서 만들 `CArray`도 이 패턴을 그대로 재사용합니다.

## 2. 우리 예제를 Lean4로: 안전한 배열 만들기

이제 이 아이디어로 "길이 5인 배열" 자체를 타입으로 표현해봅니다.

```lean
structure CArray (α : Type) (n : Nat) where
  data : Array α
  hlen : data.size = n

def CArray.get (a : CArray α n) (i : Fin n) : α :=
  a.data[i.val]'(by rw [a.hlen]; exact i.isLt)
```

`CArray α n`은 원소 타입이 `α`이고 길이가 정확히 `n`인 배열입니다(`hlen`이 그 길이가 실제로 `n`임을 증명합니다). `get` 함수는 인덱스로 `Nat`(임의의 자연수)이 아니라 **`Fin n`**을 요구합니다. 즉 `get` 함수의 시그니처 자체가 "범위를 벗어난 인덱스로는 이 함수를 호출할 방법이 없다"고 선언하고 있는 셈입니다. (`a.data[i.val]'proof`는 `GetElem` 타입 클래스가 제공하는 인덱싱 표기법으로, `proof : i.val < a.data.size`를 요구합니다 — 옛 API의 `Array.get`과 정확히 같은 역할이지만, 현재 Lean4 표준 라이브러리는 이 표기법을 씁니다.)

이걸로 우리 예제를 실제로 써보면:

```lean
def arr : CArray Nat 5 := ⟨#[10, 20, 30, 40, 50], by decide⟩

#eval arr.get ⟨2, by decide⟩   -- 30, 문제 없음
-- #eval arr.get ⟨7, by decide⟩  -- 컴파일 에러! 7 < 5를 증명 못 함
```

`arr.get ⟨7, ...⟩`을 쓰려는 순간, `7 < 5`라는 거짓 명제를 증명하라고 요구받고, 이걸 증명할 방법이 없으니 **컴파일 자체가 실패합니다.** C였다면 컴파일은 되고 실행 중에 문제가 생겼을 코드가, 여기서는 컴파일러가 거부합니다.

## 3. 매크로로 표기를 다듬기 — 단, 적용 범위는 그대로

`arr.get ⟨2, by decide⟩`는 안전하지만 매번 손으로 쓰기엔 번잡합니다. Lean4의 `syntax`/`macro_rules`로 이 번잡함을 걷어낼 수 있습니다.

```lean
syntax "safec.get%" term:max term:max : term

macro_rules
  | `(safec.get% $arr $i) => `(CArray.get $arr ⟨$i, by decide⟩)

#eval safec.get% arr 2   -- 30, ⟨2, by decide⟩를 손으로 쓴 것과 완전히 동일하게 전개됨
```

(`term:max`는 각 인자를 가장 높은 우선순위로, 즉 공백으로만 구분되는 하나의 원자적 항으로 파싱하라는 지정입니다. 그냥 `term term`으로 두 항을 나란히 선언하면 파서가 첫 번째 `term`을 어디까지 읽어야 할지 모호해져서 파싱 자체가 실패합니다.)

이 매크로는 `safec.get% arr 2`라는 표기를 받아, 그대로 `CArray.get arr ⟨2, by decide⟩`로 **전개(expand)**합니다. 여기서 중요한 건 이 매크로가 안전성 검사를 새로 하는 게 아니라는 점입니다 — elaboration은 여전히 전개된 뒤의 코드(`⟨2, by decide⟩`)를 놓고 똑같이 증명을 요구합니다. 매크로는 순전히 표기의 편의만 담당하고, 안전성의 책임은 여전히 [1편](../01-why-lean4-for-mlir/)에서 다룬 elaboration에 있습니다.

이 매크로가 커버하는 범위도 정확히 짚어야 합니다. `by decide`로 증명하는 방식은 **컴파일 타임에 이미 값이 정해진 인덱스**(`2`처럼)에만 통합니다. 바로 다음 절에서 다룰 반복문 변수나 사용자 입력값에는 이 매크로를 그대로 쓸 수 없습니다 — `by decide`가 그 경우엔 증명할 방법을 찾지 못하고 실패하기 때문입니다. 즉 이 매크로는 "상수 인덱스를 더 짧게 쓰기 위한 편의 문법"이고, 나머지 두 경우(자동 증명, 명시적 런타임 검사)는 아래에서 보게 될 원래 패턴을 그대로 따라야 합니다.

## 4. 인덱스가 상수가 아니라 변수라면? — 증명이 자동으로 채워지는 경우

문제는 실전 코드에서 인덱스가 `2`처럼 손으로 쓴 상수가 아니라, 반복문 변수처럼 실행 중에 계산되는 값이라는 점입니다.

```lean
def sumAll (a : CArray Nat 5) : Nat := Id.run do
  let mut total := 0
  for h : i in [0:5] do
    total := total + a.get ⟨i, h.2.1⟩  -- i가 0~4 범위라는 사실이 반복문 구조에서 나옴
  return total
```

여기서 `i`는 반복문이 만들어내는 값이라 컴파일 타임 상수가 아니지만, "이 반복문은 0부터 5 미만까지만 돈다"는 사실 자체가 Lean4의 반복문 구조 안에 이미 들어있습니다 — `for h : i in [0:5]`가 만드는 `h`는 `i`가 범위의 시작과 끝을 만족한다는 증명의 쌍(`h.1 : 0 ≤ i`와 `h.2 : i < 5 ∧ ...`)이고, 그중 `h.2.1`이 우리가 필요한 `i < 5`입니다. elaboration은 이 사실을 자동으로 찾아내 `i < 5`라는 증명 의무를 곧바로 닫아버립니다. 사용자는 증명이 필요했다는 사실조차 의식하지 못하고 넘어갑니다.

## 5. 정말 자동으로 안 풀리는 경우: 런타임 검사로 후퇴

이번엔 인덱스가 사용자 입력처럼, 반복문 구조에서 범위를 알아낼 수 없는 값이라고 해봅시다.

```lean
def getUserIndex (a : CArray Nat 5) (userInput : Nat) : Option Nat :=
  if h : userInput < 5 then
    some (a.get ⟨userInput, h⟩)
  else
    none
```

이 경우 elaboration은 `userInput < 5`를 정적으로 증명할 방법이 없습니다(`userInput`이 뭐가 들어올지 컴파일 타임엔 알 수 없으니까요). 그래서 우리는 `if h : userInput < 5`라는 **런타임 검사**를 직접 써서, 검사를 통과한 분기 안에서만 `h`라는 증명을 손에 넣어 `get`을 호출합니다. 검사를 통과하지 못하면 `none`을 돌려줍니다.

`if h : c then t else e`라는 이 문법과, 앞서 계속 써온 `by decide`가 어디서 오는지는 *Theorem Proving in Lean 4*의 [타입 클래스 — 10.8 Decidable Propositions](../../theorem-proving-in-lean4/10-type-classes/#decidable-propositions) 장이 정확히 다룹니다. `<`처럼 참·거짓을 실제로 계산해서 판정할 수 있는 명제는 `Decidable` 타입 클래스의 인스턴스이고, `by decide`는 그 계산을 그 자리에서 실행해 증명을 만들어내는 전술입니다. 그리고 `if h : c then t else e`는 그 장이 소개하는 **`dite`**(dependent if-then-else)의 표기일 뿐입니다 — 일반 `if-then-else`(`ite`)와 달리 `then` 분기 안에서 `h : c`를, `else` 분기 안에서 `h : ¬c`를 쓸 수 있게 해주는데, 우리 `getUserIndex`가 `then` 분기 안에서 `h`를 그대로 `get`의 증명 인자로 넘길 수 있는 이유가 바로 이것입니다.

이 패턴이 이 시스템 전체의 실용적인 균형점입니다. 정리하면:

- **정적으로 증명 가능** (반복문 예제처럼): 증명이 자동으로 채워지고, 최종적으로 생성되는 코드에는 런타임 검사가 전혀 남지 않습니다.
- **정적으로 증명 불가능하지만 실제로는 안전한 경우**: 위 예제처럼 사용자가 직접 `if h : ...` 형태로 명시적인 런타임 검사를 써서 증명을 손에 넣습니다.
- **아예 안전하지 않은 경우** (`arr.get ⟨7, ...⟩`처럼): 컴파일 자체가 거부됩니다.

모든 걸 정적으로 증명하라고 강제했다면 이 언어는 아무도 못 쓰는 언어가 됐을 것이고, 아무것도 증명하지 않았다면 C와 다를 바 없었을 겁니다. "가능하면 자동으로 증명하고, 안 되면 명시적 런타임 검사로 후퇴한다"는 게 실용성을 지키는 핵심 설계입니다.

## 6. "몇 번 쓰였는가"의 문제: 배열 범위와는 다른 종류의 어려움

배열 범위는 "값이 어떤 범위에 속하는가"의 문제였지만, 널 역참조나 이중 해제는 성격이 다릅니다 — **"값이 몇 번 쓰였는가"**의 문제입니다.

```c
free(ptr);
free(ptr);  // 이중 해제! 이미 해제된 메모리를 또 해제
```

직관적으로는 이것도 `Fin n`과 비슷하게 풀릴 것 같습니다 — 값이 한 번 "소비"되면 다시 쓸 수 없는 타입을 만들면 되지 않을까요.

```lean
structure Owned (α : Type) where
  ptr : α

def release (o : Owned α) : Unit := ()

def useTwice (o : Owned Nat) : Unit :=
  let _ := release o
  release o
```

**하지만 이 코드는 실제로 컴파일됩니다 — 아무 에러도 나지 않습니다.** 직접 실행해보면 확인할 수 있습니다. `Fin n`의 경우와 정직하게 비교해보면 왜 그런지 드러납니다: `i < 5`는 **값에 대한 명제**이고, 그 값이 실제로 무엇인지 elaboration이 들여다보기만 하면 참·거짓을 판정할 수 있는 대상입니다. 반면 "`o`가 이미 `release`에 쓰였는가"는 값이 아니라 **코드가 그 변수를 몇 번 언급했는가**, 즉 항의 구조 자체에 대한 사실입니다. Lean4의 타입 체커는 전자(값에 대한 증명 의무)는 우리가 지금까지 본 것처럼 자연스럽게 다루지만, 후자(변수 사용 횟수 추적)를 검사해서 거부하는 기능은 애초에 없습니다.

흔히들 "Lean4는 러스트처럼 참조 카운트가 1인 값을 추적하니 선형 타입도 공짜로 따라온다"고 오해하기 쉬운데, 이건 절반만 맞습니다. Lean4는 실제로 "이 값이 유일하게 참조되는가"를 내부적으로 추적하지만, 그건 **실행 속도를 위한 최적화**(참조 카운팅을 생략하고 메모리를 제자리에서 바로 갱신하는 FBIP)를 위해서입니다. 이 추적 결과는 컴파일러 백엔드에서만 쓰이고, 사용자 코드를 거부하는 판단 근거로는 노출되지 않습니다 — `useTwice`가 실제로는 `o`를 두 번 참조하니 두 번째 `release o`에서는 이 최적화가 그냥 조용히 생략될 뿐이고, 그게 컴파일 에러로 이어지지는 않습니다.

그렇다면 이중 해제를 정말 컴파일 에러로 만들려면 어떻게 해야 할까요. `Fin n`이 "값에 대한 증명 의무를 elaboration에 맡기는" 전략이었다면, 이번엔 "코드가 이 변수를 몇 번 썼는지"를 직접 세는 검사기를 elaboration 파이프라인에 끼워 넣어야 합니다 — [1편](../01-why-lean4-for-mlir/)에서 본 "elaboration에 개입해 통과 여부를 판단한다"는 아이디어를 이번엔 값이 아니라 **항의 구조**에 대해 적용하는 것입니다. 구체적으로는 `Owned`로 감싼 변수가 함수 본문(elaborate된 `Expr` 트리) 안에서 몇 번 나타나는지를 순회하며 세고, 둘 이상이면 커스텀 에러를 내는 linter나 elaboration 확장을 만들어야 합니다. 이건 `Fin n`처럼 "타입만 정의하면 나머지는 기존 타입 체커가 대신해주는" 문제가 아니라, **타입 체커가 원래 하지 않는 일을 우리가 새로 만들어 얹어야 하는 문제**라는 점에서 이 시리즈에서 지금까지 다룬 것 중 가장 어렵습니다.

배열 범위 검사와 자원 소유권은 이래서 난이도가 다른 두 문제입니다. 실용적인 시작점은 이미 만든 배열 범위 검사(`Fin n`)만으로 시작하는 것입니다 — 이것만으로도 C에서 가장 흔한 버그 범주 하나를 완전히 봉쇄할 수 있고, "변수 사용 횟수를 추적하는 elaboration 확장"은 뒤에서 매크로와 elaboration을 더 깊이 다룰 때 다시 짚어볼 만한, 훨씬 큰 별도의 프로젝트입니다. 이 확장을 실제로 어떻게 설계할 수 있는지는 [9편: 자원 소유권 딥다이브](../09-ownership-linear-types-deep-dive/)에서 더 깊게 다룹니다.

## 7. 정리

이 글에서 예제로 확인한 원칙을 요약하면:

1. **`Fin n`처럼 값의 범위를 타입으로 좁히면, 범위를 벗어난 값은 애초에 만들 수 없다.** 별도의 `if` 검사가 필요 없어진다.
2. **매크로는 표기를 다듬을 뿐 안전성 검사를 대신하지 않는다.** `safec.get%` 같은 편의 문법도 결국 전개된 뒤에는 elaboration의 검증을 그대로 통과해야 한다.
3. **반복문처럼 범위가 구조에서 드러나는 경우, 증명은 자동으로 채워진다.**
4. **자동으로 안 풀리는 경우, 사용자가 `if h : ...` 형태의 명시적 런타임 검사로 증명을 손에 넣을 수 있다.** 이 유연성이 언어를 실용적으로 만든다.
5. **다만 이 전략이 모든 안전성 문제에 똑같이 적용되지는 않는다.** "값이 몇 번 쓰였는가"(이중 해제 등)는 값이 아니라 코드 구조에 대한 사실이라 Lean4의 타입 체커가 기본으로 검사해주지 않는다 — `Fin n`처럼 타입만 정의해서 끝나지 않고, 항의 구조를 직접 순회하는 elaboration 확장을 새로 만들어야 하는, 훨씬 어려운 문제다.

다음 편에서는 여기서 만든 `arr.get ⟨2, ...⟩` 같은 Lean4 표현이, 실제로 어떤 MLIR 텍스트로 옮겨지는지 — 한 줄 한 줄 직접 손으로 짜보면서 확인합니다.
