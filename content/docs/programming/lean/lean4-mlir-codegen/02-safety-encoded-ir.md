[1편](../01-why-lean4-for-mlir/)에서 "길이 5인 배열 `arr`에서 `arr[i]`를 안전하게 꺼낸다"는 예제를 소개했습니다. 이 글은 그 예제를 실제 Lean4 코드로 만들어보면서, 안전성을 "검사"가 아니라 "타입으로 표현 불가능하게 만들기"로 확보하는 원리를 다룹니다.

---

## 1. "검사"와 "표현 불가능"의 차이를 예제로 보기

C의 `arr[i]`는 `i`가 어떤 정수든 다 받아줍니다. 컴파일러는 이걸 막지 않고, 대신 우리가 직접 검사 코드를 넣어야 합니다.

```c
int get_checked(int i) {
    if (i < 0 || i >= 5) {
        // 여기서 뭘 해야 할까? 에러 코드 반환? 프로그램 종료?
        return -1;
    }
    return arr[i];
}
```

이 방식의 문제는, 검사를 깜빡한 곳이 프로그램 어딘가에 딱 하나만 있어도 버그가 됩니다. 검사가 필요한 모든 지점을 사람이 빠짐없이 챙겨야 합니다.

Lean4에서는 이 문제를 뒤집습니다. "범위를 벗어난 인덱스"라는 값 자체를 아예 만들 수 없는 타입을 씁니다.

```lean
#check (⟨2, by decide⟩ : Fin 5)  -- Fin 5, 값은 2
-- #check (⟨7, by decide⟩ : Fin 5)  -- 에러! 7 < 5를 증명할 수 없음
```

`Fin 5`는 "0 이상 5 미만인 자연수"만 담을 수 있는 타입입니다. `Fin 5` 타입의 값은 항상 숫자와 "이 숫자가 5보다 작다"는 증명, 이 둘의 쌍입니다. 증명이 없으면 애초에 값을 만들 수 없으므로, `Fin 5` 타입의 변수를 손에 쥐고 있다는 것 자체가 "이 값은 반드시 0~4 사이"라는 걸 이미 보장합니다. `if`문으로 매번 확인할 필요가 없습니다 — 확인이 필요 없는 게 아니라, **확인이 이미 그 값을 만드는 순간에 끝나 있는 것**입니다.

## 2. 우리 예제를 Lean4로: 안전한 배열 만들기

이제 이 아이디어로 "길이 5인 배열" 자체를 타입으로 표현해봅니다.

```lean
structure CArray (α : Type) (n : Nat) where
  data : Array α
  hlen : data.size = n

def CArray.get (a : CArray α n) (i : Fin n) : α :=
  a.data.get ⟨i.val, by rw [a.hlen]; exact i.isLt⟩
```

`CArray α n`은 원소 타입이 `α`이고 길이가 정확히 `n`인 배열입니다(`hlen`이 그 길이가 실제로 `n`임을 증명합니다). `get` 함수는 인덱스로 `Nat`(임의의 자연수)이 아니라 **`Fin n`**을 요구합니다. 즉 `get` 함수의 시그니처 자체가 "범위를 벗어난 인덱스로는 이 함수를 호출할 방법이 없다"고 선언하고 있는 셈입니다.

이걸로 우리 예제를 실제로 써보면:

```lean
def arr : CArray Nat 5 := ⟨#[10, 20, 30, 40, 50], by decide⟩

#eval arr.get ⟨2, by decide⟩   -- 30, 문제 없음
-- #eval arr.get ⟨7, by decide⟩  -- 컴파일 에러! 7 < 5를 증명 못 함
```

`arr.get ⟨7, ...⟩`을 쓰려는 순간, `7 < 5`라는 거짓 명제를 증명하라고 요구받고, 이걸 증명할 방법이 없으니 **컴파일 자체가 실패합니다.** C였다면 컴파일은 되고 실행 중에 문제가 생겼을 코드가, 여기서는 컴파일러가 거부합니다.

## 3. 매크로로 표기를 다듬기 — 단, 적용 범위는 그대로

`arr.get ⟨2, by decide⟩`는 안전하지만 매번 손으로 쓰기엔 번잡합니다. Lean4의 `syntax`/`macro_rules`로 이 번잡함을 걷어낼 수 있습니다.

```lean
syntax "safec.get%" term term : term

macro_rules
  | `(safec.get% $arr $i) => `(CArray.get $arr ⟨$i, by decide⟩)

#eval safec.get% arr 2   -- 30, ⟨2, by decide⟩를 손으로 쓴 것과 완전히 동일하게 전개됨
```

이 매크로는 `safec.get% arr 2`라는 표기를 받아, 그대로 `CArray.get arr ⟨2, by decide⟩`로 **전개(expand)**합니다. 여기서 중요한 건 이 매크로가 안전성 검사를 새로 하는 게 아니라는 점입니다 — elaboration은 여전히 전개된 뒤의 코드(`⟨2, by decide⟩`)를 놓고 똑같이 증명을 요구합니다. 매크로는 순전히 표기의 편의만 담당하고, 안전성의 책임은 여전히 [1편](../01-why-lean4-for-mlir/)에서 다룬 elaboration에 있습니다.

이 매크로가 커버하는 범위도 정확히 짚어야 합니다. `by decide`로 증명하는 방식은 **컴파일 타임에 이미 값이 정해진 인덱스**(`2`처럼)에만 통합니다. 바로 다음 절에서 다룰 반복문 변수나 사용자 입력값에는 이 매크로를 그대로 쓸 수 없습니다 — `by decide`가 그 경우엔 증명할 방법을 찾지 못하고 실패하기 때문입니다. 즉 이 매크로는 "상수 인덱스를 더 짧게 쓰기 위한 편의 문법"이고, 나머지 두 경우(자동 증명, 명시적 런타임 검사)는 아래에서 보게 될 원래 패턴을 그대로 따라야 합니다.

## 4. 인덱스가 상수가 아니라 변수라면? — 증명이 자동으로 채워지는 경우

문제는 실전 코드에서 인덱스가 `2`처럼 손으로 쓴 상수가 아니라, 반복문 변수처럼 실행 중에 계산되는 값이라는 점입니다.

```lean
def sumAll (a : CArray Nat 5) : Nat := Id.run do
  let mut total := 0
  for h : i in [0:5] do
    total := total + a.get ⟨i, h.2⟩  -- i가 0~4 범위라는 사실이 반복문 구조에서 나옴
  return total
```

여기서 `i`는 반복문이 만들어내는 값이라 컴파일 타임 상수가 아니지만, "이 반복문은 0부터 5 미만까지만 돈다"는 사실 자체가 Lean4의 반복문 구조 안에 이미 들어있습니다(`h.2`가 그 증명입니다). elaboration은 이 사실을 자동으로 찾아내 `i < 5`라는 증명 의무를 곧바로 닫아버립니다. 사용자는 증명이 필요했다는 사실조차 의식하지 못하고 넘어갑니다.

## 5. 정말 자동으로 안 풀리는 경우: 런타임 검사로 후퇴

이번엔 인덱스가 사용자 입력처럼, 반복문 구조에서 범위를 알아낼 수 없는 값이라고 해봅시다.

```lean
def getUserIndex (a : CArray Nat 5) (userInput : Nat) : Option Nat :=
  if h : userInput < 5 then
    some (a.get ⟨userInput, h⟩)
  else
    none
```

이 경우 elaboration은 `userInput < 5`를 정적으로 증명할 방법이 없습니다(`userInput`이 뭐가 들어올지 컴파일 타임엔 알 수 없으니까요). 그래서 우리는 `if h : userInput < 5`라는 **런타임 검사**를 직접 써서, 검사를 통과한 분기 안에서만 `h`라는 증명을 손에 넣어 `get`을 호출합니다. 검사를 통과하지 못하면 `none`을 돌려줍니다.

이 패턴이 이 시스템 전체의 실용적인 균형점입니다. 정리하면:

- **정적으로 증명 가능** (반복문 예제처럼): 증명이 자동으로 채워지고, 최종적으로 생성되는 코드에는 런타임 검사가 전혀 남지 않습니다.
- **정적으로 증명 불가능하지만 실제로는 안전한 경우**: 위 예제처럼 사용자가 직접 `if h : ...` 형태로 명시적인 런타임 검사를 써서 증명을 손에 넣습니다.
- **아예 안전하지 않은 경우** (`arr.get ⟨7, ...⟩`처럼): 컴파일 자체가 거부됩니다.

모든 걸 정적으로 증명하라고 강제했다면 이 언어는 아무도 못 쓰는 언어가 됐을 것이고, 아무것도 증명하지 않았다면 C와 다를 바 없었을 겁니다. "가능하면 자동으로 증명하고, 안 되면 명시적 런타임 검사로 후퇴한다"는 게 실용성을 지키는 핵심 설계입니다.

## 6. 선형성: "몇 번 쓰였는가"로 자원 안전성 지키기

배열 범위는 "값이 어떤 범위에 속하는가"의 문제였지만, 널 역참조나 이중 해제는 성격이 다릅니다 — **"값이 몇 번 쓰였는가"**의 문제입니다.

```c
free(ptr);
free(ptr);  // 이중 해제! 이미 해제된 메모리를 또 해제
```

**선형 타입(linear type)**은 어떤 값이 정확히 한 번만 쓰이도록 강제합니다.

```lean
structure Owned (α : Type) where
  ptr : α

def release (o : Owned α) : Unit := ()

def useTwice (o : Owned Nat) : Unit :=
  let _ := release o
  release o  -- 에러! o는 이미 release에서 소비됨
```

`o`가 `release`에 한 번 넘어가고 나면, elaboration은 그 변수가 "이미 소비됨"으로 표시하고, 다시 쓰려는 코드를 거부합니다. C의 `free(ptr); free(ptr);`에 해당하는 실수가 여기서는 컴파일 에러입니다.

흥미로운 점은, Lean4가 이 "값이 유일하게 참조되는가"라는 정보를 원래 안전성이 아니라 **실행 속도를 위한 최적화**(참조 카운팅을 생략하고 메모리를 제자리에서 바로 갱신) 목적으로 이미 내부적으로 추적하고 있다는 것입니다. 우리는 이 기존 메커니즘을 그대로 안전성 목적으로 재활용할 수 있습니다.

배열 범위 검사와 자원 소유권은 서로 독립적인 메커니즘입니다. 실용적인 시작점은 배열 범위 검사(`Fin n`)만 먼저 만들고, 선형성은 나중에 추가하는 것입니다 — 배열 범위 검사 하나만으로도 C에서 가장 흔한 버그 범주를 봉쇄할 수 있고, 선형성은 사용성 저하가 더 크기 때문입니다.

---

## 7. 정리

이 글에서 예제로 확인한 원칙을 요약하면:

1. **`Fin n`처럼 값의 범위를 타입으로 좁히면, 범위를 벗어난 값은 애초에 만들 수 없다.** 별도의 `if` 검사가 필요 없어진다.
2. **매크로는 표기를 다듬을 뿐 안전성 검사를 대신하지 않는다.** `safec.get%` 같은 편의 문법도 결국 전개된 뒤에는 elaboration의 검증을 그대로 통과해야 한다.
3. **반복문처럼 범위가 구조에서 드러나는 경우, 증명은 자동으로 채워진다.**
4. **자동으로 안 풀리는 경우, 사용자가 `if h : ...` 형태의 명시적 런타임 검사로 증명을 손에 넣을 수 있다.** 이 유연성이 언어를 실용적으로 만든다.
5. **선형성은 "값이 몇 번 쓰였는가"를 추적해 이중 해제 같은 문제를 컴파일 에러로 바꾼다.**

다음 편에서는 여기서 만든 `arr.get ⟨2, ...⟩` 같은 Lean4 표현이, 실제로 어떤 MLIR 텍스트로 옮겨지는지 — 한 줄 한 줄 직접 손으로 짜보면서 확인합니다.
