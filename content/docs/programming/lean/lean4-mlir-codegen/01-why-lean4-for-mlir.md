이 시리즈는 "Lean4로 안전한 IR을 설계하고, 그 IR을 MLIR로 방출한 뒤, MLIR의 인프라를 거쳐 최종적으로 C 코드까지 뽑아낸다"는 파이프라인을 다룹니다. 시리즈 내내 **같은 예제 하나**를 계속 따라갑니다 — "길이 5인 배열 `arr`에서 인덱스 `i`로 원소를 꺼낸다"는, C 프로그래밍에서 가장 흔하고 가장 흔하게 버그가 나는 연산입니다. 이 예제가 1편에서는 문제로, 2편에서는 Lean4 코드로, 3편에서는 MLIR 텍스트로, 4편에서는 최종 C 코드로 형태를 바꾸며 계속 등장합니다.

첫 편은 코드를 많이 다루기 전에 먼저 짚어야 할 질문에 답합니다 — 애초에 왜 Lean4가 이 역할에 적합한가, 그리고 최종 타겟을 C로 바로 잡지 않고 MLIR을 중간에 끼우는 것이 무엇을 얻는가입니다. MLIR 자체가 무엇이고 왜 존재하는지(dialect, operation, attribute 같은 기본 개념)는 다루지 않으므로, 처음 접한다면 [0편: MLIR이란 무엇인가](../00-what-is-mlir/)를 먼저 읽는 걸 권합니다.

---

## 1. 우리가 풀려는 문제: 배열 접근이라는 흔한 버그

C로 배열에 접근하는 코드는 이렇게 생겼습니다.

```c
int arr[5] = {10, 20, 30, 40, 50};
int get(int i) {
    return arr[i];  // i가 0~4 범위를 벗어나면?
}
```

`i`가 5 이상이거나 음수면 이 코드는 배열 바깥의 메모리를 읽습니다. C 컴파일러는 이걸 막지 않습니다 — 컴파일은 성공하고, 프로그램은 실행되다가 예측할 수 없는 값을 읽거나 크래시하거나, 최악의 경우 조용히 잘못된 값을 계속 씁니다. 이게 C에서 가장 흔한 버그 범주(버퍼 오버플로우)이고, 우리가 이 시리즈에서 만들려는 시스템의 목표는 정확히 이겁니다 — **`i`가 범위를 벗어날 수 있는 코드는 애초에 컴파일이 안 되게 만든다.**

이 목표를 달성하는 방법 자체는 이후 편들(특히 2편)에서 다룹니다. 이번 편의 질문은 "이런 검사를 하는 새 언어를 왜 Lean4로 만드는가"입니다.

---

## 2. Lean4의 elaboration이 하는 일: 엄격한 편집자

Lean4로 코드를 쓸 때 실제로 일어나는 일을 감 잡기 위해, 아주 단순한 예를 봅시다.

```lean
#eval (2 : Nat) + (3 : Nat)  -- 5
```

이 한 줄 뒤에서 Lean4는 생각보다 많은 일을 합니다. `+`라는 기호가 정확히 어떤 덧셈 함수를 가리키는지(정수 덧셈인지, 실수 덧셈인지) 타입을 보고 결정하고, `2`와 `3`이라는 리터럴을 `Nat` 타입의 값으로 변환하는 과정도 함수 호출로 채워 넣습니다. 사람이 쓴 건 `2 + 3`이라는 짧은 표기지만, Lean4 내부에서는 이게 완전히 풀어헤쳐진, 모든 타입과 함수가 명시된 형태로 다시 쓰입니다. 이 "짧은 표기를 완전히 풀어헤친 형태로 바꾸는" 과정을 **elaboration**이라고 부릅니다.

비유하자면 elaboration은 아주 꼼꼼한 편집자입니다. 여러분이 "3번째 항목을 가져와"라고 대충 쓴 초안을 받아서, "이 문서에서 항목이 총 몇 개인지 확인했는가? 3번째가 실제로 존재하는가?"까지 전부 확인한 뒤에야 최종 원고로 넘겨주는 편집자입니다. 확인 과정에서 뭔가 걸리면(3번째 항목이 없다면), 편집자는 원고를 통과시키지 않고 되돌려 보냅니다.

이 "확인하고 통과 여부를 결정한다"는 동작이, 우리가 만들려는 안전한 배열 접근 언어에 정확히 필요한 동작입니다. `arr[i]`라는 표기를 받았을 때, elaboration이 "이 `i`가 항상 0~4 범위 안에 있다는 게 증명 가능한가?"까지 확인하고, 증명되지 않으면 컴파일 자체를 거부하게 만들 수 있습니다. 이게 2편에서 실제로 만들 내용입니다.

여기서 중요한 포인트는, Lean4를 쓰면 이 "확인 로직을 실행하는 인프라"(문법을 읽어들이는 파서, 타입을 추론하는 엔진, 확인이 실패했을 때 에러 메시지를 내는 시스템)를 새로 만들 필요가 없다는 것입니다. 이 모든 게 이미 Lean4 언어 자체에 내장되어 있고, 우리는 "무엇을 확인할지"만 정의하면 됩니다.

## 3. 컴파일 타깃을 왜 C가 아니라 MLIR로 잡는가

Lean4에서 안전성을 확인한 IR을 손에 넣었다고 해도, 이걸 실제로 실행 가능한 코드로 만들려면 어딘가로는 낮춰야(lowering) 합니다. C를 직접 찍는 것도 방법이지만, 그 사이에 **MLIR**을 끼우면 세 가지를 얻습니다.

**(1) 하나의 큰 도약을 여러 개의 작은 도약으로 쪼갤 수 있다.** 우리 예제로 생각해보면, "Lean4의 안전한 배열 접근"에서 곧바로 "C의 포인터 연산"으로 한 번에 뛰어내리는 건 사실 여러 결정을 한꺼번에 뭉뚱그리는 일입니다 — 범위 검사를 완전히 생략할지, 배열 인덱싱을 어떤 C 표현식으로 쓸지, 만약 검사가 필요하다면 실패 시 무엇을 할지가 전부 한 단계에서 결정됩니다. MLIR은 이 하나의 큰 도약을 여러 단계로 나눌 수 있게 해줍니다. 이 시리즈에서는 우리 배열 접근 예제가 **우리가 만든 전용 표현(3편) → 검사 여부가 반영된 표현 → 최종 C 표현(4편)**까지 단계별로 형태를 바꾸는 걸 직접 보게 됩니다.

**(2) 각 단계에서 다시 검증할 수 있다.** MLIR의 각 표현 단위는 스스로 지켜야 할 규칙(verifier)을 가질 수 있습니다. Lean4가 "이 인덱스는 안전하다"고 확인한 사실을 다음 단계로 넘길 때, 그 사실이 실제로 맞는지 다음 단계에서 한 번 더 확인할 수 있는 여지가 생깁니다. 하나의 도구(Lean4)만 믿는 게 아니라 여러 지점에서 재확인하는 구조입니다.

**(3) 정리 작업을 직접 만들지 않아도 된다.** Lean4가 안전성을 확인하는 과정에서 만들어내는 IR은 필연적으로 다소 장황합니다. 이 장황함을 정리하는 작업(불필요한 계산 제거, 반복되는 계산 합치기)을 직접 구현하는 대신, MLIR이 이미 갖춘 표준 도구를 그대로 가져다 쓸 수 있습니다.

---

## 4. 이 시리즈에서 다루는 파이프라인의 전체 그림

```
표면 문법: arr[i]
   ↓ elaboration (i가 항상 안전한 범위인지 확인 — 2편)
안전성이 확인된 내부 표현 (Lean4 코드)
   ↓ Lean4로 순회하며 텍스트로 옮겨쓰기 — 3편
MLIR 텍스트 (우리가 정의한 전용 표현)
   ↓ MLIR의 표준 변환 도구 — 4편
최종 C 소스: arr[i] 그대로, 또는 검사 코드가 붙은 형태
```

각 화살표가 이 시리즈의 한 편에 대응합니다. 다음 편에서는 "`i`가 항상 안전한 범위 안에 있다"를 Lean4 타입으로 실제로 어떻게 쓰는지 — `Fin n`이라는 타입 하나로 이 문제 전체가 어떻게 해결되는지를 코드로 직접 봅니다.
