[4편](../04-mlir-pipeline-integration/)에서 Lean4가 증명한 안전 IR을 MLIR을 거쳐 결국 C 소스로 뽑아내는 파이프라인을 완성했고, [5편](../05-translation-validation/)에서 그 파이프라인의 가장 취약한 연결 고리(attribute 방출 코드)를 번역 검증과 증명 운반 코드로 검증하는 방법까지 다뤘습니다. 이 마지막 글은 같은 프론트엔드(Lean4 elaboration, 커스텀 dialect, attribute를 통한 증명 전달과 그 검증)를 그대로 두고, 마지막 타겟만 C에서 **SystemVerilog**로 바꾸면 무엇이 달라지는지를 다룹니다. 이 전환을 담당하는 MLIR 하위 프로젝트가 [CIRCT](https://circt.llvm.org/)(Circuit IR Compilers and Tools)입니다.

---

## 1. 왜 이게 "타겟 하나 바꾸기"로 끝나지 않는가

앞선 시리즈에서 EmitC는 "C로 표현 가능한 것만 표현하는 dialect"였고, C가 전제하는 실행 모델은 **순차적, 명령형(imperative)** 이었습니다 — 명령어가 하나씩 순서대로 실행되고, 값은 메모리 어딘가에 저장되어 다음 명령어가 읽을 때까지 유지됩니다. SystemVerilog가 기술하는 하드웨어 회로는 이 전제가 통째로 바뀝니다. 회로 안의 모든 로직은 **동시에, 계속** 동작합니다. "이 신호를 계산한다"는 건 한 번 실행되고 끝나는 명령이 아니라, 입력이 바뀌는 순간 즉시 재계산되는 상시 활성 배선입니다. 순서라는 개념 자체가 소프트웨어와 다르게 작동합니다 — 클럭 신호에 맞춰 상태가 갱신되는 시점(순차 로직)과, 입력이 바뀌면 지연 없이 즉시 반영되는 부분(조합 로직)만 구분될 뿐, "다음 줄로 넘어간다"는 개념이 없습니다.

그래서 이건 단순히 "번역기의 출력 문법만 바꾸는" 문제가 아닙니다. Lean4가 방출한 안전 IR 자체는 여전히 유효하지만(배열 접근, 조건 분기, 산술 연산이라는 개념은 하드웨어에서도 그대로 필요합니다), **그 개념들을 실행 모델이 근본적으로 다른 세계의 어휘로 다시 번역**해야 합니다. 이 재번역을 어디서 하느냐가 이 글의 핵심입니다 — 답은 "Lean4 쪽에서는 아무것도 바뀌지 않고, MLIR 이후 단계의 dialect 선택과 conversion pattern만 바뀐다"입니다.

## 2. CIRCT의 dialect 스택: EmitC의 자리에 sv가 들어온다

[3편](../03-emitting-mlir-text/)에서 우리는 커스텀 `safec` dialect를 정의하고, 이를 낮춰서 최종적으로 "C로 표현 가능한 것만 표현하는" EmitC dialect에 도달하는 구조를 설계했습니다. CIRCT는 이 자리에 하드웨어 버전의 dialect 스택을 제공합니다.

- **`hw`**: 구조적(structural) 층입니다. 모듈, 포트, 모듈 인스턴스화처럼 "회로가 어떤 부품들로 구성되어 서로 어떻게 연결되는가"를 표현합니다. 소프트웨어의 함수 정의·호출에 대응하지만, 호출이 아니라 배선 연결이라는 점이 다릅니다.
- **`comb`**: 조합 로직 층입니다. 덧셈, 비교, 멀티플렉서(선택 회로)처럼 입력이 바뀌면 지연 없이 즉시 재계산되는 연산들을 표현합니다. 소프트웨어의 순수 함수 계산과 개념적으로 가장 가깝습니다.
- **`seq`**: 순차 로직 층입니다. 레지스터, 클럭에 맞춰 갱신되는 상태를 표현합니다. 소프트웨어의 "변수에 값을 대입하고 다음 스텝에서 그 값을 읽는다"는 개념이 여기에 대응되지만, 그 갱신이 클럭 엣지라는 명시적 시간 신호에 묶여 있다는 점이 다릅니다.
- **`sv`**: EmitC와 정확히 같은 역할을 하는 리프(leaf) dialect입니다. SystemVerilog 문법으로 표현 가능한 구조(`always_comb`, `always_ff`, `initial` 블록)만 담습니다.

즉 [4편](../04-mlir-pipeline-integration/)에서 그렸던 파이프라인의 뒷부분이 이렇게 갈라집니다.

```
안전성이 인코딩된 Lean4 IR
   ↓
safec dialect (동일)
   ↓ (conversion pattern이 여기서 갈라진다)
   ├─→ arith/scf/... → EmitC → C 소스   [4편까지의 경로]
   └─→ hw/comb/seq   → sv    → SystemVerilog 소스   [이 글의 경로]
```

두 경로 모두 같은 `safec` dialect에서 출발한다는 점이 중요합니다. Lean4 프론트엔드는 "이 프로그램이 안전하다"는 증명만 책임지고, 그 증명된 IR을 소프트웨어로 실행할지 하드웨어로 합성할지는 순전히 뒷단의 conversion pattern 선택에 달려 있습니다. 같은 안전 IR에서 두 가지 서로 다른 타겟이 나온다는 사실 자체가, [1편](../01-why-lean4-for-mlir/)에서 MLIR을 중간 타겟으로 삼는 이유로 들었던 "낮추기를 여러 단계로 쪼갤 수 있다"는 이점이 실제로 갈래를 만들어낼 만큼 유연하다는 것을 보여줍니다.

## 3. 배열 접근이 멀티플렉서가 될 때, 안전성 증명은 형태를 바꾼다

[2편](../02-safety-encoded-ir/)에서 `Fin n` 타입으로 배열 범위를 증명하고, 그 증명이 [3편](../03-emitting-mlir-text/)에서 `bounds_checked` attribute로 실려 간다고 설명했습니다. C를 타겟으로 할 때 이 attribute는 "런타임 범위 검사 코드를 생략해도 되는가"를 결정했습니다. 하드웨어를 타겟으로 하면 이 attribute가 결정하는 것 자체가 달라집니다.

소프트웨어에서 `arr[i]`는 메모리 주소를 계산해 그 위치를 읽는 연산이지만, 하드웨어에서는 이런 "주소로 찾아가서 읽기"라는 개념이 없습니다. 배열의 각 원소는 각자 고정된 배선이고, 인덱스 `i`로 원소를 고르는 연산은 **모든 원소를 입력으로 받아 `i` 값에 따라 그중 하나를 출력으로 내보내는 멀티플렉서(mux) 회로**로 합성됩니다. 이 멀티플렉서를 얼마나 크게 만들어야 하는지가 바로 우리의 안전성 증명이 개입하는 지점입니다.

`i`의 타입이 `Fin n`으로 증명되어 있다면(즉 `i`가 항상 0부터 n-1 사이의 값이라는 게 정적으로 보장되어 있다면), 멀티플렉서는 정확히 n개의 입력만 처리하면 됩니다. 반대로 이 증명이 없다면(정적 범위 증명이 실패해 런타임 검사로 대체된 경우), 합성 도구는 범위를 벗어난 인덱스가 들어왔을 때 무엇을 출력해야 하는지도 정의해야 하고, 이는 멀티플렉서에 "그 외의 경우" 처리 경로를 추가로 만들어야 한다는 뜻입니다. 이 "그 외의 경우"를 명시적으로 정의하지 않고 넘어가면, 합성 도구가 그 미정의 상태를 회로에서 자연스럽게 유지하는 **래치(latch)**를 의도치 않게 추론해버릴 수 있습니다. 래치는 클럭에 동기화되지 않은 상태 유지 회로라 타이밍 분석을 어렵게 만들고, RTL 설계에서 대표적인 버그 원인으로 취급됩니다.

이 차이를 ExportVerilog가 실제로 찍어내는 두 코드로 대조해보면 더 분명해집니다. 길이 5인 배열에서 `bounds_checked = true`(정적으로 안전이 증명된 경우)는 이렇게 합성됩니다.

```systemverilog
// bounds_checked = true — "그 외의 경우"가 애초에 없다
always_comb begin
  unique case (idx)
    3'd0: val = arr_0;
    3'd1: val = arr_1;
    3'd2: val = arr_2;
    3'd3: val = arr_3;
    3'd4: val = arr_4;
  endcase
end
```

`idx`가 항상 0~4 중 하나라는 게 이미 증명되어 있으니, `case`문은 그 5가지 경우만 나열하면 됩니다. `unique` 키워드는 "이 케이스들이 서로 겹치지 않고, 이 케이스들 외의 값은 절대 들어오지 않는다"는 걸 합성 도구에 명시적으로 선언하는 것이고, 이 선언이 실제로 참이라는 걸 Lean4의 증명이 보장해줍니다. `bounds_checked = false`(런타임 검사가 필요한 경우)는 같은 배열이라도 이렇게 달라집니다.

```systemverilog
// bounds_checked = false — 정의되지 않은 idx 값에 대비해야 한다
always_comb begin
  case (idx)
    3'd0: val = arr_0;
    3'd1: val = arr_1;
    3'd2: val = arr_2;
    3'd3: val = arr_3;
    3'd4: val = arr_4;
    default: val = 32'd0;  // 이 분기가 없으면 래치가 추론될 수 있다
  endcase
end
```

`idx`가 5 이상일 가능성을 배제할 수 없으므로, `unique` 없이 일반 `case`를 쓰고 `default` 분기를 강제로 추가해 모든 입력값에 대해 `val`이 항상 정의되도록 만듭니다. `default`가 빠지면, 5개 케이스에 해당하지 않는 `idx` 값이 들어왔을 때 `val`이 "이전 값을 그대로 유지"하도록 회로가 합성되는데, 이게 바로 의도치 않은 래치입니다.

즉 C 타겟에서 `bounds_checked` attribute가 "런타임 분기문 하나를 켜고 끄는" 역할이었다면, SystemVerilog 타겟에서 같은 attribute는 **"`unique case`로 합성할지, `default` 분기가 붙은 일반 `case`로 합성할지를 결정하고, 그 결정을 통해 의도치 않은 래치 추론을 피하는"** 역할로 바뀝니다. 증명된 안전성이 향하는 목적지(런타임 분기 제거 vs 조합 로직 완전성 보장)는 다르지만, "Lean4의 증명 결과가 attribute를 통해 뒷단의 코드 생성 방식을 조건부로 바꾼다"는 [4편](../04-mlir-pipeline-integration/)의 원리는 그대로 재사용됩니다.

## 4. 순차 대입이 사라지고 클럭 도메인이 등장한다

[2편](../02-safety-encoded-ir/)에서 다룬 선형성(자원이 한 번만 소비된다는 성질)도 하드웨어 타겟에서 의미가 바뀝니다. 소프트웨어에서 선형성은 "이중 해제를 막는다"는 메모리 안전성 문제였지만, 하드웨어에는 애초에 동적 메모리 할당이나 해제라는 개념이 없습니다. 대신 선형성이 유용해지는 지점은 **클럭 도메인 교차(clock domain crossing)**입니다. 서로 다른 클럭에 맞춰 동작하는 두 회로 블록 사이에서 신호를 주고받을 때, 그 신호가 정확히 한쪽에서만 구동(drive)되고 있다는 사실을 보장하지 못하면 신호 충돌이나 정의되지 않은 논리 상태(X-propagation, 시뮬레이션에서 값이 0도 1도 아닌 불확정 상태로 전파되는 현상)로 이어집니다. Lean4의 elaboration 단계에서 "이 신호는 이 클럭 도메인에서 유일하게 구동된다"는 선형성 증명을 만들 수 있다면, 이 정보 역시 attribute로 실려 가 `seq` dialect의 레지스터 삽입 패턴이 안전한 동기화 구조(예: 이중 플립플롭 동기화기)를 자동으로 끼워 넣을지 판단하는 근거가 됩니다.

제어 흐름의 번역도 근본적으로 달라집니다. C 타겟에서는 우리 IR의 조건 분기가 그대로 C의 `if`문으로 내려갔습니다. 하드웨어 타겟에서는 조건 분기가 클럭과 무관한지(조합 로직) 아니면 클럭에 걸쳐 상태를 바꾸는지(순차 로직)에 따라 완전히 다른 두 가지 구조 중 하나로 갈라집니다. 클럭과 무관한 조건이라면 `comb.mux`(즉시 반영되는 선택 회로)로, 클럭에 걸쳐 상태가 바뀌는 대입이라면 `seq.compreg`(클럭 엣지에서만 갱신되는 레지스터)로 내려갑니다. 이 판단 자체가 새로운 conversion pattern이 담당하는 로직이며, Lean4 IR 단계에서 애초에 "이 값은 상태를 유지해야 하는가"라는 정보가 명시적으로 구분되어 있어야 이 판단이 자동화될 수 있습니다 — 이건 [2편](../02-safety-encoded-ir/)에서 다룬 IR 설계 단계로 되짚어 올라가야 하는 요구사항입니다.

## 5. ExportVerilog: EmitC와 같은 역할, 다른 완전성 기준

CIRCT는 `sv` dialect에 도달한 IR을 실제 SystemVerilog 소스로 바꾸는 `ExportVerilog`(CIRCT의 `circt-translate` 도구나 `firtool`을 통해 노출됨)를 제공합니다. 이건 [4편](../04-mlir-pipeline-integration/)에서 다룬 `mlir-translate --mlir-to-cpp`와 정확히 같은 자리 — "우리가 손댈 필요 없는, 이미 완성된 표준 인프라"입니다.

다만 이 마지막 단계가 보증하는 "완전성"의 기준이 다릅니다. EmitC는 "C 컴파일러가 컴파일할 수 있는 텍스트인가"를 보증했다면, ExportVerilog는 "SystemVerilog 시뮬레이터/합성 도구가 모호함 없이 해석할 수 있는 텍스트인가"를 보증해야 합니다. 특히 `sv` dialect 오퍼레이션들은 `always_comb` 블록이 모든 경우를 완전하게 다루고 있는지 같은, 소프트웨어에는 없는 하드웨어 고유의 완전성 조건을 스스로 강제합니다. 우리가 3절에서 다룬 멀티플렉서의 완전성 문제가 여기서 다시 한번 검증되는 마지막 관문인 셈입니다.

## 6. 신뢰 사슬의 마지막 고리가 하드웨어에서는 더 무겁다

[4편](../04-mlir-pipeline-integration/)에서 이 파이프라인의 가장 취약한 연결 고리가 "Lean4의 증명을 attribute로 압축하는 방출 코드"라고 짚었습니다. 이 결론은 하드웨어 타겟에서 그대로 유지되지만, 실패했을 때의 무게가 다릅니다. C 타겟에서 attribute 압축이 잘못되면 최악의 경우 런타임 검사가 하나 누락되어 크래시나 메모리 손상으로 이어지지만, 실행 중에 관측 가능하고 패치로 고칠 수 있습니다. 하드웨어 타겟에서 같은 실수(예: 완전성 증명이 잘못되어 의도치 않은 래치가 합성됨)는 칩이 제작(fabrication)된 이후에는 되돌릴 수 없는 결함이 됩니다. 이 비대칭성 때문에, 같은 Lean4 프론트엔드를 하드웨어 타겟에 쓸 때는 [2편](../02-safety-encoded-ir/)에서 논의한 "정적 증명 실패 시 런타임 계약으로 대체"라는 타협이 훨씬 보수적으로 적용되어야 합니다 — 하드웨어에는 "일단 합성해보고 문제가 생기면 다음 배포에서 고친다"는 선택지가 없기 때문입니다.

---

## 7. 이 글의 정리

1. **C와 SystemVerilog는 같은 Lean4 프론트엔드와 같은 `safec` dialect를 공유하는 두 개의 서로 다른 리프(leaf) 타겟이다.** 갈라지는 지점은 conversion pattern이 `arith`/`scf`(소프트웨어) 계열로 갈지 `hw`/`comb`/`seq`(하드웨어) 계열로 갈지의 선택뿐이다.
2. **실행 모델 자체가 순차적(소프트웨어)에서 동시적·공간적(하드웨어)으로 바뀐다.** 배열 접근은 메모리 참조가 아니라 멀티플렉서가 되고, 대입은 메모리 갱신이 아니라 클럭에 묶인 레지스터 갱신이 된다.
3. **안전성 증명(attribute)이 결정하는 대상이 바뀐다.** C에서는 런타임 분기 제거를, SystemVerilog에서는 멀티플렉서 크기와 조합 로직의 완전성(래치 추론 회피)을 결정한다.
4. **선형성은 메모리 해제 문제에서 클럭 도메인 교차 안전성 문제로 의미를 옮겨간다.**
5. **신뢰 사슬의 구조는 동일하지만, 하드웨어 타겟에서는 실패의 대가가 훨씬 크므로 정적 증명에 대한 요구가 더 엄격해져야 한다.** [5편](../05-translation-validation/)에서 다룬 번역 검증과 PCC는 그래서 소프트웨어 타겟보다 하드웨어 타겟에서 오히려 더 절실하게 요구된다 — 합성 이후에는 되돌릴 방법이 없기 때문이다.

## 8. 시리즈 정리

여섯 편에 걸쳐 하나의 예제(`arr[i]`)를 계속 따라가며 안전한 언어 파이프라인을 설계했습니다.

1. **[왜 Lean4로 MLIR을 만드는가](../01-why-lean4-for-mlir/)**: elaboration은 컴파일러 프론트엔드와 구조적으로 닮았고, MLIR은 낮추기를 여러 단계로 쪼개 각 단계에서 재검증할 여지를 준다.
2. **[안전성이 타입에 인코딩된 내부 IR 설계](../02-safety-encoded-ir/)**: `Fin n`으로 위험한 인덱스를 표현 불가능하게 만들고, 증명은 자동 해소 또는 명시적 런타임 검사로 채워진다.
3. **[MLIR 텍스트 방출과 커스텀 dialect 설계](../03-emitting-mlir-text/)**: `bounds_checked` attribute가 증명 결과를 다음 단계로 운반하며, 커스텀 dialect 없이는 이 정보가 소실된다.
4. **[MLIR 파이프라인과의 접합](../04-mlir-pipeline-integration/)**: attribute 하나가 최종 C 코드의 모양을 결정하며, 신뢰가 방출 코드 한 곳에 집중된다는 문제를 남긴다.
5. **[번역 검증](../05-translation-validation/)**: 번역 검증과 증명 운반 코드로 매 출력을 값싸게 재확인하고, 차등 테스트로 검사기 자체의 결함까지 잡아 TCB를 실질적으로 줄인다.
6. **CIRCT로 SystemVerilog 만들기 (이 글)**: 검증까지 끝난 같은 파이프라인을 완전히 다른 실행 모델(하드웨어)로 확장하면, attribute가 결정하는 대상은 바뀌지만 "증명 → attribute → 조건부 코드 생성 → 검증"이라는 구조 자체는 그대로 재사용된다.

여섯 편이 함께 그리는 그림은, "안전성은 한 곳에서 한 번에 증명되는 게 아니라, 파이프라인 전체에 걸쳐 서로 다른 도구가 서로 다른 방식으로 반복해서 확인할 때 비로소 실전에서 믿을 만해진다"는 것입니다.

여기까지는 전부 손으로 그린 예시였습니다. [7편: 실습](../07-hands-on-c-emission/)에서는 이 C 타겟 파이프라인(1~5편)을 실제로 실행되는 Lean4 코드로 직접 돌려보고, 방출 코드에 버그가 있을 때 독립 검사기가 그걸 잡아내는 순간을 눈으로 확인합니다.
