[4편](../04-mlir-pipeline-integration/)에서 이 파이프라인 전체의 신뢰가 딱 한 곳 — Lean4의 증명 결과를 `bounds_checked` attribute로 옮기는 방출 코드 — 에 걸려 있다고 결론지었습니다. 그 코드에 버그가 있어서 증명되지 않은 인덱스에 실수로 `true`를 붙이면, 뒤따르는 모든 단계는 "정확하게" 동작하면서도 검사 없는 위험한 C 코드를 만들어냅니다. 이 글은 그 방출 코드를 어떻게 신뢰할 것인가라는, 4편이 열어놓고 답하지 않은 질문에 답합니다.

## 1. 두 가지 다른 철학: 컴파일러를 한 번 증명할까, 매번 검증할까

컴파일러의 신뢰성을 확보하는 접근은 크게 두 갈래로 나뉩니다.

**컴파일러 자체를 증명하는 접근**은 방출 코드가 항상 옳다는 걸 수학적으로 한 번 증명해두고, 그 뒤로는 어떤 입력이 들어와도 그 증명을 믿습니다. CompCert(Coq로 전체를 증명한 C 컴파일러)가 이 방식의 대표 사례입니다. 이 접근의 장점은 한 번 증명하면 끝이라는 것이고, 단점은 증명 자체가 극도로 비쌉니다 — 방출 코드가 다루는 모든 경우의 수(모든 프로그램 구조, 모든 타입 조합)에 대해 "이 변환이 의미를 보존한다"를 증명해야 합니다. 우리 파이프라인의 방출 코드를 이 수준으로 증명하려면, 사실상 Lean4로 또 다른 정리 증명 프로젝트를 시작해야 합니다.

**매번 검증하는 접근**은 방출 코드 자체는 증명하지 않은 채로 두고, 대신 **그 코드가 만들어낸 각각의 출력**을 독립적으로 다시 확인합니다. 방출 코드에 버그가 있어도, 그 버그가 만들어낸 특정 출력이 잘못됐다는 걸 별도의 검사기가 잡아내면 문제가 생기기 전에 걸러집니다. 이 접근을 **번역 검증(translation validation)**이라고 부르며, 우리 파이프라인처럼 방출 코드가 계속 바뀌고 발전하는 프로젝트 초기 단계에는 이쪽이 훨씬 현실적입니다. 이번 편은 이 두 번째 접근을 중심으로 다룹니다.

## 2. 순진한 번역 검증: 최종 결과에서 거꾸로 다시 확인하기

가장 단순한 형태의 번역 검증은, 방출 코드가 만든 MLIR 텍스트를 **Lean4의 증명을 다시 보지 않고, 그 텍스트 자체만으로** 독립적인 검사기가 재확인하는 것입니다. [3편](../03-emitting-mlir-text/)의 예제로 확인해봅시다.

```mlir
func.func @get_element(%arr: !safec.array<5xi32>) -> i32 {
  %idx = safec.const_index 2 : index
  %val = safec.array_get %arr[%idx] {bounds_checked = true} : (!safec.array<5xi32>, index) -> i32
  return %val : i32
}
```

독립 검사기는 Lean4가 뭘 증명했는지 전혀 모릅니다. 대신 이 텍스트만 보고 스스로 판단합니다 — `%arr`의 타입이 `!safec.array<5xi32>`이니 길이는 5, `%idx`는 `safec.const_index 2`로 정의된 상수 2. "2가 5보다 작은가?"는 검사기가 산술만으로 즉시 재확인할 수 있습니다. `bounds_checked = true`라는 표식을 그냥 믿는 대신, 검사기가 스스로 같은 결론에 다시 도달한 것입니다. 만약 방출 코드에 버그가 있어서 실제로는 인덱스가 `7`인데 실수로 `bounds_checked = true`를 붙였다면, 이 독립 검사기는 `7 < 5`가 거짓이라는 걸 그 자리에서 잡아내고 빌드를 실패시킵니다.

이 검사기는 실제로는 `safec.array_get` 오퍼레이션에 붙는 MLIR verifier로 구현됩니다. 상수 인덱스 케이스만 놓고 보면 대략 이런 모양입니다.

```cpp
// safec.array_get 오퍼레이션의 verifier (의사코드)
LogicalResult ArrayGetOp::verify() {
  auto boundsChecked = (*this)->getAttrOfType<BoolAttr>("bounds_checked");
  if (!boundsChecked || !boundsChecked.getValue())
    return success();  // false면 이 verifier가 검증할 게 없음 — 런타임 검사가 대신 처리

  // 인덱스가 상수로 정의됐는지 확인 (safec.const_index)
  auto idxOp = getIndex().getDefiningOp<ConstIndexOp>();
  if (!idxOp)
    return emitOpError("bounds_checked=true이지만 인덱스가 상수가 아님 — 재확인 불가");

  int64_t idx = idxOp.getValue();
  int64_t arraySize = getArray().getType().cast<ArrayType>().getSize();

  if (idx < 0 || idx >= arraySize)
    return emitOpError("PCC 재검증 실패: 인덱스 ")
           << idx << "가 배열 크기 " << arraySize << "를 벗어남";

  return success();  // 재확인 완료 — Lean4의 증명과 별개로 이 검사기도 안전을 확인함
}
```

이 verifier는 Lean4가 무엇을 증명했는지 전혀 참조하지 않습니다. `bounds_checked` attribute가 참인 오퍼레이션을 만나면, 그 근거(여기서는 상수 인덱스)를 IR에서 직접 찾아 산술로 재확인하고, 맞지 않으면 컴파일 자체를 실패시킵니다 — Lean4의 elaboration이 잘못된 attribute를 방출했더라도, 이 독립적인 두 번째 관문이 최종 방어선이 됩니다.

이 방식이 좋은 이유는 검사기가 Lean4의 타입 체커만큼 강력할 필요가 없다는 것입니다. "상수 대 상수 비교" 같은 얕은 사실은 위 코드처럼 아주 단순한 산술 검사만으로 재확인됩니다. 하지만 이게 이 접근의 한계이기도 합니다.

이 verifier를 실전에서 매번 위와 같은 C++로 손수 짜지는 않습니다. MLIR은 오퍼레이션을 TableGen 파일(ODS, Operation Definition Specification)로 선언할 때 `Confined` 타입이나 제약 조건(Constraints/Predicates)을 함께 명시할 수 있게 해두었고, 이 선언만으로도 "이 값은 0 이상이어야 한다" 같은 얕은 검사는 자동으로 검증 코드가 생성됩니다. 위 `ArrayGetOp::verify()`처럼 손으로 C++을 쓰는 건, ODS의 선언적 제약만으로는 표현할 수 없는(예: 다른 오퍼레이션을 거슬러 올라가 `ConstIndexOp`인지 확인하는 것 같은) 조금 더 복잡한 검사가 필요할 때로 한정됩니다 — 이 시리즈에서 C++ 의사코드로 verifier를 계속 손으로 짜는 것도, 우리 검사가 정확히 그런 "선언만으로는 안 되는" 부류에 속하기 때문입니다.

## 3. 순진한 접근이 무너지는 지점: 깊은 증명은 재현할 수 없다

[2편](../02-safety-encoded-ir/)의 반복문 예제를 같은 방식으로 검사하려고 해봅시다.

```mlir
%sum = safec.for_range 0 to 5 iter_args(%acc = %init) -> i32 {
^bb0(%i: index, %acc: i32):
  %val = safec.array_get %arr[%i] {bounds_checked = true} : (...) -> i32
  ...
}
```

여기서 `%i`는 상수가 아니라 반복문이 만들어내는 값입니다. 독립 검사기가 `bounds_checked = true`를 재확인하려면 "이 `%i`는 `safec.for_range 0 to 5`라는 구조 안에서 나온 값이니 항상 0~4 범위"라는 걸 스스로 추론해야 합니다. 이 정도는 여전히 검사기가 `for_range` 오퍼레이션의 구조를 이해하고 있다면 재현 가능합니다.

문제는 Lean4의 증명이 이보다 훨씬 복잡해질 때입니다. 예를 들어 "이 인덱스는 이전 조건 분기에서 이미 범위를 확인했기 때문에 안전하다"거나, "이 값은 여러 단계의 계산을 거쳤지만 그 계산 전체가 범위를 벗어나지 않는다는 게 여러 보조 정리를 조합해야 증명된다"는 경우, 독립 검사기가 MLIR 텍스트만 보고 그 증명을 처음부터 다시 재구성하는 건 사실상 **Lean4의 타입 체커를 통째로 다시 만드는 것**과 다르지 않습니다. 이러면 번역 검증을 도입한 의미가 없어집니다 — 검사기 자체가 또 하나의 거대하고 신뢰해야 할 코드가 되어버리기 때문입니다.

즉 순진한 번역 검증은 **얕고(shallow) 국소적인 사실**에는 잘 맞지만, **깊고 전역적인 증명**에는 확장되지 않습니다. 다행히 배열 범위 검사처럼 우리가 다루는 안전 속성들은 대체로 "이 값이 이 범위 안에 있다"는 국소적인 산술 사실에 가까워서, 이 한계에 자주 부딪히지는 않습니다. 하지만 언어가 커지면서 증명이 복잡해질 걸 대비해, 더 견고한 방법을 알아둘 필요가 있습니다.

## 4. 증명 운반 코드: 증명을 다시 찾지 말고, 힌트로 받아서 값싸게 확인하기

깊은 증명을 검사기가 처음부터 재발견하게 하는 대신, **Lean4가 증명 과정에서 이미 알아낸 핵심 단서를 attribute에 함께 실어 보내면** 어떨까요. 검사기는 그 단서를 "찾아내는" 대신 "확인만" 하면 되므로 훨씬 가벼워집니다. 이 아이디어를 **증명 운반 코드(Proof-Carrying Code, PCC)**라고 부릅니다 — 코드를 만든 쪽이 증명 자체를 코드에 실어 보내고, 실행하는 쪽은 그 증명을 검증만 하는(재발견하지 않는) 구조입니다.

우리 예제에 적용하면, attribute를 단순한 불리언에서 **구조화된 근거**로 바꿉니다.

```mlir
// 이전: 검사기가 왜 안전한지 스스로 추론해야 함
%val = safec.array_get %arr[%i] {bounds_checked = true} : (...) -> i32

// PCC 스타일: 왜 안전한지 근거 자체가 attribute에 실려 있음
%val = safec.array_get %arr[%i] {
  bounds_proof = #safec.loop_bound<lower = 0, upper = 5, var = "i">
} : (...) -> i32
```

`bounds_proof`가 "이 인덱스가 안전한 이유는, `i`가 0부터 5 미만까지 도는 반복문 변수이기 때문"이라는 근거를 명시적으로 담고 있습니다. 독립 검사기는 이제 "이 반복문이 정말 그렇게 도는가?"와 "그 범위가 정말 배열 길이 안에 드는가?"만 국소적으로 재확인하면 됩니다 — 어떻게 그 사실을 알아낼지 스스로 탐색할 필요가 없습니다. 더 복잡한 증명(여러 조건 분기의 조합 등)이라도, Lean4가 그 증명 트리의 핵심 구조를 attribute로 요약해 실어 보내면, 검사기는 그 구조를 따라가며 각 단계가 실제로 성립하는지만 값싸게 확인하는 역할로 남습니다.

이 PCC 스타일 attribute를 검증하는 verifier는, 2절에서 본 상수 케이스보다 조금 더 일반적이지만 여전히 국소적인 검사만 합니다.

```cpp
// safec.array_get 오퍼레이션의 verifier — PCC(loop_bound) 버전
LogicalResult ArrayGetOp::verify() {
  auto proof = (*this)->getAttrOfType<LoopBoundAttr>("bounds_proof");
  if (!proof)
    return success();  // PCC 근거가 없으면 이 verifier가 검증할 게 없음

  int64_t arraySize = getArray().getType().cast<ArrayType>().getSize();

  // 증명을 "발견"하지 않는다 — proof가 제시한 upper bound만 재확인
  if (proof.getUpper() > arraySize)
    return emitOpError("PCC 검증 실패: loop_bound의 upper(")
           << proof.getUpper() << ")가 배열 크기(" << arraySize << ")를 초과함";

  // proof가 가리키는 변수(var)가 실제로 이 오퍼레이션의 인덱스와 같은지도 확인
  if (proof.getVar() != getIndexVarName())
    return emitOpError("PCC 검증 실패: 증명의 대상 변수가 실제 인덱스와 불일치");

  return success();
}
```

이 verifier는 "`i`가 왜 0~5 범위인지"는 전혀 재추론하지 않습니다. Lean4가 이미 그 이유(반복문 구조)를 근거로 제시했으니, 검사기는 그 근거의 `upper` 값이 배열 크기를 넘지 않는지, 근거가 가리키는 변수가 실제 사용된 인덱스와 일치하는지, 이 두 가지 국소적인 사실만 확인합니다. 2절의 verifier와 이 verifier가 하는 일의 성격은 같습니다 — attribute에 실린 근거를 그대로 믿지 않고 한 번 더 산술로 재확인하는 것 — 다만 이번엔 근거가 상수 하나가 아니라 "반복문 구조"라는 조금 더 풍부한 형태라는 차이만 있습니다.

이 설계의 힘은, 검사기가 필요로 하는 능력이 "증명을 발견하는 능력"에서 "제시된 증명 구조를 따라가며 각 단계를 확인하는 능력"으로 낮아진다는 데 있습니다. 후자는 일반적으로 훨씬 단순하고, 그만큼 검사기 자체를 감사(audit)하기도 쉬워집니다.

다만 이 설계에는 한 가지 조심할 지점이 새로 생깁니다 — `bounds_proof`라는 힌트 자체도 결국 신뢰할 수 없는 방출 코드가 만들어낸 텍스트라는 사실입니다. `LoopBoundAttr`를 파싱해서 `getUpper()`, `getVar()` 같은 필드를 꺼내는 코드에 버그가 있다면(예: 파싱이 두 필드를 뒤바꿔 읽는다거나, 정수 오버플로우로 `upper` 값이 잘못 해석된다면), verifier는 애초에 잘못된 근거를 "성공적으로" 재확인해버리는 셈이 됩니다 — 검증 로직 자체는 멀쩡한데, 그 로직에 들어가는 입력이 이미 오염된 경우입니다. 그래서 PCC를 도입하면 **힌트를 파싱하는 코드 그 자체도 최소화된 TCB에 새로 포함시켜야** 합니다 — attribute를 믿지 않는 것만큼이나, "이 attribute를 올바르게 읽어내는 코드"도 별도로 감사 대상이 되어야 한다는 뜻입니다. 실전에서는 이 파싱 계층을 최대한 얇고 단순하게(가급적 ODS가 자동 생성하는 접근자만 쓰고, 손으로 짠 파싱 로직은 최소화) 유지하는 것이, PCC가 약속하는 "검사기를 가볍게 만든다"는 이점을 파싱 버그로 다시 잃지 않는 방법입니다.

## 5. 세 번째 방어선: 차등 테스트로 검사기 자체의 빈틈을 잡기

번역 검증이나 PCC 검사기도 결국 사람이 짠 코드이고, 그 자체에 버그가 있을 수 있습니다. 이걸 보완하는 마지막 방어선은 **정적 검증이 아니라 실행 결과를 비교하는 테스트**입니다.

우리 예제로 구체적으로 해보면: Lean4로 짠 `arr.get` 함수는 Lean4 안에서 그 자체로 실행 가능한 참조 구현(reference implementation)입니다. 이걸 최종적으로 컴파일된 C 바이너리와 같은 입력으로 나란히 돌려 결과를 비교합니다.

```
for 배열 크기 n in [1, 5, 100, ...]:
  for 인덱스 i in [무작위로 뽑은 값들, 특히 0, n-1, n, -1 같은 경계값]:
    lean_result := Lean4 참조 구현으로 arr.get 실행 (안전하지 않으면 컴파일 자체가 안 됨)
    c_result    := 컴파일된 C 바이너리로 같은 입력 실행
    assert lean_result == c_result
```

이 테스트가 중요한 이유는, 번역 검증이나 PCC가 놓친 실수를 잡아내는 게 아니라 — 애초에 그 검사기 자체를 짜는 사람이 놓친 실수, 예를 들어 "검사기가 `bounds_proof`의 `upper` 필드를 확인할 때 부등호 방향을 반대로 짰다"는 종류의 버그를 잡아낸다는 점입니다. 정적 검증 도구는 스스로의 논리적 결함을 스스로 발견하지 못하지만, 실행 결과를 비교하는 테스트는 검증 로직과 무관하게 "결과가 다르다"는 사실만으로 문제를 드러냅니다. 경계값(인덱스가 정확히 배열 크기와 같을 때, 배열 크기가 1일 때)을 의도적으로 많이 포함시키는 게 이런 테스트에서 특히 중요합니다 — 범위 검사 버그는 거의 항상 경계 바로 위나 아래에서 드러납니다.

이 방식이 주는 확신은 정적 검증과 성격이 다릅니다. "이 프로그램은 항상 옳다"는 증명이 아니라 "우리가 시도해본 모든 경우에서는 옳았다"는 확률적 확신입니다. 하지만 정적 검증(번역 검증, PCC)과 결합하면, 서로 다른 종류의 실수를 서로 다른 방식으로 잡아내는 **다층 방어**가 됩니다 — 하나가 놓친 걸 다른 하나가 잡을 가능성이 생깁니다.

## 6. TCB가 실제로 얼마나 줄어드는가

[4편](../04-mlir-pipeline-integration/)의 결론을 다시 보면, TCB(신뢰해야 하는 최소 코드 범위)가 "attribute를 방출하는 코드 전체"였습니다. 이 글에서 다룬 세 가지 방어를 겹쳐 놓으면 이 TCB가 실제로 어떻게 줄어드는지 정리할 수 있습니다.

- **방출 코드 자체**는 여전히 완전히 신뢰되지 않습니다. 대신 그 코드가 만든 결과물이 아래 두 검사를 통과해야만 최종 결과로 인정됩니다.
- **번역 검증/PCC 검사기**가 각 attribute의 근거를 재확인합니다. 이 검사기는 방출 코드보다 훨씬 작고 단순한 로직(제시된 증명 구조를 따라가며 국소적 산술만 확인)만 담당하므로, 방출 코드 전체를 신뢰하는 것보다 훨씬 적은 코드를 신뢰하면 됩니다.
- **차등 테스트**가 검사기 자체의 논리적 결함을, 검사기와 무관한 방식(실행 결과 비교)으로 잡아냅니다.

결국 우리가 최종적으로 신뢰해야 하는 범위는 "방출 코드 전체가 항상 옳다"에서 "PCC 검사기의 국소적 확인 로직이 옳다 + 참조 구현과 컴파일된 코드가 우리가 테스트한 범위에서 일치했다"로 좁아집니다. 전자를 통째로 신뢰하는 것보다 후자 두 가지를 각각 신뢰하는 편이 감사하기 훨씬 쉽고, 무엇보다 **서로 다른 두 메커니즘이 동시에 같은 실수를 저지를 가능성은 하나의 메커니즘이 실수할 가능성보다 훨씬 낮습니다.**

## 7. 정리

1. **컴파일러를 통째로 증명하는 것과 매 출력을 검증하는 것은 서로 다른 철학이다.** 방출 코드가 계속 바뀌는 프로젝트 초기에는 번역 검증 쪽이 훨씬 현실적이다.
2. **순진한 번역 검증(독립 검사기가 최종 IR만 보고 재확인)은 얕고 국소적인 안전 사실에는 잘 맞지만, 깊고 전역적인 증명에는 확장되지 않는다.**
3. **증명 운반 코드(PCC)는 검사기가 증명을 "발견"하는 대신 "확인"만 하도록, attribute에 증명의 핵심 구조를 함께 실어 보낸다.** 이게 순진한 접근의 한계를 늦춘다. 다만 그 힌트를 파싱하는 코드도 검증되지 않은 방출 코드의 산물이므로, 이 파싱 계층 자체를 최소화된 TCB에 포함시켜 함께 감사해야 한다.
4. **차등 테스트는 검사기 자체의 논리적 결함을, 검증 로직과 무관한 방식(실행 결과 비교)으로 잡아내는 마지막 방어선이다.**
5. 이 세 가지를 겹치면, [4편](../04-mlir-pipeline-integration/)에서 지목한 "방출 코드 전체를 신뢰해야 한다"는 TCB가 "PCC 검사기의 국소적 로직 + 테스트한 범위에서의 일치"로 실질적으로 좁아진다.

이렇게 검증까지 마친 파이프라인을 이제 C가 아닌 완전히 다른 타겟 — 하드웨어 — 로 확장하면 무슨 일이 벌어지는지, [6편: CIRCT로 SystemVerilog 만들기](../06-circt-systemverilog/)에서 마무리합니다.
