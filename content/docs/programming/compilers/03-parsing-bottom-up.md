[2편](02-parsing-top-down/)에서 LL(1) 파서가 "다음 토큰 하나로 어느 규칙을 적용할지" 미리 예측해야 한다는 제약을 봤습니다. 이 글은 그 제약이 필요 없는, 훨씬 강력한 파싱 방식 — 트리를 아래(잎)에서부터 위(뿌리)로 세워가는 **상향식(Bottom-up) 파싱**을 다룹니다.

---

## 1. 하향식과 정반대의 전략: 조각을 모아 규칙으로 뭉치기

[2편](02-parsing-top-down/) 2절의 예제 `n == 0`을 다시 봅시다. 하향식 파서는 `Expr`에서 시작해 "이게 어떤 규칙으로 전개될까"를 미리 예측하며 아래로 내려갔습니다. 상향식 파서는 정반대입니다 — 토큰을 하나씩 읽어 쌓아두다가, 쌓인 것이 문법 규칙의 오른쪽 변(우변)과 정확히 일치하면 그 조각을 규칙의 좌변(non-terminal) 하나로 **뭉칩니다**.

```
입력을 읽어 스택에 쌓기:  ID
                          ↓ (여기서 멈추고 EQEQ가 아직 안 왔으므로 계속 읽음)
스택: ID EQEQ INT
                          ↓ "ID"가 "Factor → ID" 규칙의 우변과 일치 → 뭉침
스택: Factor EQEQ INT
                          ↓ "INT"도 "Factor → INT"와 일치 → 뭉침
스택: Factor EQEQ Factor
                          ↓ 이 전체가 "Expr → Expr EQEQ Expr" 우변과 일치 → 뭉침
스택: Expr
```

이 두 동작 — 토큰을 스택에 밀어 넣는 **Shift**와, 스택 맨 위 몇 개를 규칙 좌변으로 뭉치는 **Reduce** — 이름을 따서 이 방식을 **Shift-Reduce 파싱**이라고 부릅니다.

---

## 2. 핵심 질문: 언제 Shift하고 언제 Reduce할까

Shift-Reduce 파싱의 전부는 사실 매 순간 이 하나의 결정입니다 — "지금 스택 맨 위가 어떤 규칙의 우변과 일치하는 것처럼 보이는데, 지금 당장 뭉쳐야(Reduce) 할까, 아니면 토큰을 하나 더 읽어야(Shift) 할까?"

```
스택: ... Expr STAR Factor        입력에 남은 것: STAR Expr ...
```

여기서 `Expr STAR Factor`는 `Term → Expr STAR Factor` 같은 규칙(또는 [2편](02-parsing-top-down/)에서 다룬 문법이라면 다른 우변)과 일치해 보일 수 있지만, 만약 다음 입력이 또 `STAR Expr`로 이어진다면 지금 뭉치는 게 맞는지, 아니면 뒤의 곱셈까지 먼저 처리해야 하는지가 **연산자 우선순위**에 따라 달라집니다. 이 판단을 스택의 내용과 다음 입력 토큰(lookahead)만으로 내릴 수 있어야 파싱이 성립하고, 이 판단 근거를 표로 미리 만들어두는 것이 이번 편의 핵심입니다.

---

## 3. 지금 뭉칠 수 있는 조각을 정확히 찾아내기: 핸들(Handle)

스택에 쌓인 것 중 "지금 당장 reduce해야 할 올바른 조각"을 **핸들(Handle)**이라고 부릅니다. 문제는 스택 맨 위 몇 글자가 우연히 어떤 규칙의 우변과 겹쳐 보여도, 그게 지금 이 문맥에서 진짜 핸들이 아닐 수 있다는 것입니다 — 3절 예제의 `Expr STAR Factor`가 그 사례입니다.

핸들을 정확히 찾아내기 위해, LR 파서는 "지금까지 무엇을 얼마나 인식했는지"를 단순한 스택 내용이 아니라 **아이템(Item)**이라는 더 정밀한 단위로 추적합니다. 아이템은 문법 규칙에 "지금까지 어디까지 읽었는지"를 표시하는 점(`•`)을 하나 찍은 것입니다.

```
Expr → Expr • STAR Factor    (Expr까지는 인식했고, 다음에 STAR가 오면 계속 진행 가능)
Expr → Expr STAR Factor •    (우변 전체를 인식 완료 — 여기서 reduce 가능)
```

파서는 가능한 아이템들의 집합을 상태로 삼아 움직입니다 — 이게 바로 [1편](01-lexical-analysis/)에서 다룬 DFA와 근본적으로 같은 발상입니다. 다만 이번엔 상태가 "정규 표현식의 어디까지 읽었는가"가 아니라 "문법 규칙의 어디까지 읽었는가"를 나타냅니다.

---

## 4. LR(0) 아이템으로 상태 기계 만들기

문법의 모든 아이템을 모아, [1편](01-lexical-analysis/#4-nfa의-문제-어느-상태로-가야-할지-비결정적이다)에서 다룬 것과 똑같은 방식으로 상태들을 만듭니다 — 시작 아이템에서 출발해, 각 기호를 읽었을 때 도달 가능한 아이템들의 집합을 새 상태로 삼는 걸 반복합니다.

```
상태 0: { Expr → • Expr STAR Factor, Expr → • Factor, Factor → • ID, Factor → • INT }
              │ ID를 읽으면
              ▼
상태 1: { Factor → ID • }               ← 점이 맨 끝, reduce 가능
```

`Factor → ID •`처럼 점이 규칙의 맨 끝에 도달한 상태에 있다면, 그 상태는 **reduce 상태**입니다 — 지금 스택에 쌓인 것이 정확히 이 규칙의 우변과 일치하니 뭉치라는 뜻입니다. 점이 아직 중간에 있는 상태는 다음 기호를 **shift**해서 더 읽어야 한다는 뜻입니다. 이 상태 기계 전체를 미리 만들어 두면, 파서는 실행 중에 "지금 스택이 어느 상태에 있는지"만 추적하면서 그 상태가 알려주는 대로 shift하거나 reduce하면 됩니다 — [1편](01-lexical-analysis/)에서 DFA가 "다음 문자를 보고 다음 상태로만 가면 되는" 단순한 실행 구조를 줬던 것과 정확히 같은 이유로, LR 파싱도 이 상태 기계 덕분에 매 순간의 결정이 빠르고 명확해집니다.

---

## 5. LR(0)만으로 부족한 지점: Shift/Reduce 충돌

상태 하나에 "여기서 reduce하라"는 아이템과 "여기서 shift하라"는 아이템이 동시에 들어 있으면, 파서는 어느 쪽을 따라야 할지 알 수 없습니다 — 이걸 **Shift/Reduce 충돌**이라고 부릅니다. 2절에서 짚은 `Expr STAR Factor` 다음에 또 `STAR`가 오는 상황이 정확히 이 충돌의 사례입니다.

이 충돌을 해소하는 표준 방법이 **1개 토큰의 lookahead**를 추가로 보는 것입니다 — 이렇게 확장한 방식이 **SLR(1)**, **LALR(1)**, **LR(1)**이며, 각각 lookahead를 계산하는 정밀도가 다릅니다(LR(1)이 가장 정밀하지만 상태 수가 폭발적으로 늘어날 수 있어서, 실전에서는 상태 수를 억제하면서도 대부분의 문법을 처리할 수 있는 **LALR(1)**이 가장 널리 쓰입니다). 곱셈이 뺄셈보다 강하게 묶여야 한다는 우선순위 정보를 lookahead와 결합하면, `Expr STAR Factor` 다음에 `STAR`가 보이는 상황에서 "지금 reduce하지 말고 먼저 뒤의 곱셈을 shift해서 처리하라"는 결정을 정확히 내릴 수 있습니다.

---

## 6. 왜 상향식이 하향식보다 강력한가

[2편](02-parsing-top-down/#5-재귀-하강이-실패하는-경우-좌재귀와-예측-불가능성)에서 재귀 하강이 좌재귀를 다루지 못한다고 했는데, LR 파싱은 좌재귀 문법을 **아무 변형 없이 그대로** 처리할 수 있습니다 — `Expr → Expr STAR Factor`라는 좌재귀 규칙 자체가 4절의 상태 기계에 별문제 없이 들어갔다는 걸 이미 확인했습니다. 이게 상향식 파싱이 하향식보다 다룰 수 있는 문법의 범위가 넓은 핵심 이유입니다 — "위에서부터 무엇이 나올지 미리 예측"할 필요 없이, "지금까지 읽은 것이 우변과 일치하는가"만 확인하면 되기 때문입니다.

---

## 7. 파서 생성기가 대신 해주는 일

지금까지 다룬 아이템 집합 계산, 상태 기계 구성, Shift/Reduce 충돌 해소는 전부 기계적인 절차이고, 실전에서는 사람이 손으로 하지 않습니다. `yacc`(또는 GNU 버전인 `bison`) 같은 **파서 생성기**에 문법 규칙과 우선순위 선언만 적으면, 이 도구가 4~5절의 상태 기계와 파싱 테이블을 자동으로 만들어줍니다.

```yacc
%left MINUS
%left STAR

expr: expr MINUS expr   { $$ = mkExpr('-', $1, $3); }
    | expr STAR expr    { $$ = mkExpr('*', $1, $3); }
    | ID                 { $$ = mkVar($1); }
    | INT                { $$ = mkConst($1); }
    ;
```

`%left STAR`가 `%left MINUS` 뒤에 선언되어 있다는 것 자체가 "STAR가 MINUS보다 우선순위가 높다"는 뜻입니다 — [2편](02-parsing-top-down/#3-모호함-같은-토큰-나열에-트리가-두-개-이상-나올-수-있다)에서 우리가 `Expr`/`Term`/`Factor`로 계층을 나눠 손으로 우선순위를 문법 구조에 인코딩했던 것과 달리, `yacc`는 이 선언 하나로 모호한 문법을 그대로 두고도 5절의 Shift/Reduce 충돌을 우선순위 정보로 자동 해소합니다. 각 규칙 옆의 `{ ... }`는 그 규칙이 reduce될 때 실행할 액션으로, 이 자리에서 파스 트리(또는 바로 다음 편에서 다룰 AST) 노드를 실제로 만들어냅니다.

---

## 8. 정리

- 상향식 파싱은 토큰을 스택에 쌓다가(**Shift**), 쌓인 조각이 문법 규칙의 우변과 일치하면 좌변으로 뭉치는(**Reduce**) 과정을 반복합니다.
- 지금 뭉쳐야 할 올바른 조각을 **핸들**이라 부르고, 이를 정확히 찾기 위해 규칙에 "어디까지 읽었는지" 표시하는 **아이템**과 그 아이템들의 상태 기계(**LR 자동자**)를 씁니다.
- 상태 하나에 shift 결정과 reduce 결정이 동시에 있으면 **충돌**이 나며, 이를 해소하려고 **lookahead**(SLR/LALR/LR(1))와 **연산자 우선순위 선언**을 함께 씁니다.
- LR 파싱은 [2편](02-parsing-top-down/)의 재귀 하강이 다루지 못한 좌재귀 문법도 그대로 처리할 수 있어, 실전 언어의 문법 대부분이 `yacc`/`bison` 같은 LALR(1) 기반 파서 생성기로 처리됩니다.

다음 편에서는 이렇게 세운 파스 트리(또는 그 액션이 만든 AST)를 받아, "이 프로그램이 타입 규칙과 스코프 규칙을 지키는가"를 검사하는 **의미 분석**을 다룹니다.
