[1~7편](01-lexical-analysis/)에 걸쳐 MiniLang의 `fact` 함수를 문자열에서 시작해 올바르게 실행되는 레지스터 머신 코드까지 만들었습니다. 이 마지막 편은 "올바르게 동작한다"는 조건은 그대로 지키면서 그 코드를 **더 빠르게, 더 작게** 만드는 **최적화(Optimization)**를 다룹니다.

---

## 1. 최적화의 절대 원칙: 프로그램의 관찰 가능한 동작을 바꾸지 않는다

최적화가 지켜야 할 단 하나의 규칙은, 최적화 전후로 프로그램이 **똑같이 동작해야 한다**는 것입니다 — 실행 결과, 출력, (일반적으로) 종료 여부가 전부 같아야 합니다. 이 제약이 있기 때문에 최적화는 "더 빠른 코드를 아무렇게나 짜는" 게 아니라, "지금 이 변환이 정말 안전한지"를 매번 증명해야 하는 작업입니다 — 이번 편에서 다룰 분석들이 전부 이 안전성을 확인하기 위한 도구입니다.

---

## 2. 기본 블록: 분기가 없는 코드의 최대 단위

최적화를 이야기하려면 먼저 코드를 분석 단위로 쪼개야 합니다. **기본 블록(Basic Block)**은 "중간에 분기가 끼어들지 않는, 처음부터 끝까지 순서대로만 실행되는 최대 길이의 명령어 나열"입니다. [6편](06-code-generation-register-machine/)의 `fact` 코드를 기본 블록으로 나누면:

```
BB1:  addi $sp, $sp, -12
      sw   $ra, 8($sp)
      sw   $s0, 4($sp)
      move $s0, $a0
      beq  $s0, $zero, BB3      ← 블록의 끝 (분기)

BB2:  addi $a0, $s0, -1
      jal  fact
      ...                       ← 블록의 끝 (jal 이후 흐름이 이어지지만, 호출 지점이라 경계로 취급하기도 함)

BB3:  li   $v0, 1
      ...
```

각 블록 안에서는 실행 순서가 고정되어 있으므로, 이 안에서만 적용하는 최적화(**지역 최적화, Local Optimization**)는 분기를 신경 쓸 필요가 없어 상대적으로 간단합니다.

---

## 3. 지역 최적화 (1): 상수 접기와 상수 전파

**상수 접기(Constant Folding)**는 컴파일 시점에 이미 값이 정해지는 계산을 미리 계산해버리는 최적화입니다.

```
최적화 전:  t1 = 2 + 3
           t2 = t1 * 4

최적화 후:  t1 = 5          ; 2+3을 컴파일 타임에 계산
           t2 = 20          ; 5*4도 마찬가지
```

이 최적화는 스칼라 값에만 국한되지 않습니다. [ONNX 모델을 MLIR로 최적화하기 3편](../onnx-mlir-hardware-optimization/03-graph-level-optimization/#2-상수-접기constant-folding-추론-시점엔-이미-답이-정해진-계산을-미리-해버린다)에서 다룬 BatchNorm의 정규화 계수 계산도, 학습이 끝난 뒤 절대 바뀌지 않는 값들(scale, mean, var)에 대해 정확히 같은 원리(추론 시점엔 이미 답이 정해진 계산은 컴파일 타임에 미리 끝낸다)를 딥러닝 그래프 수준에 적용한 것입니다.

**상수 전파(Constant Propagation)**는 한 걸음 더 나아가, 변수에 상수가 대입된 걸 알면 그 변수를 쓰는 자리에 값을 직접 대입해버립니다.

```
최적화 전:  x = 5
           y = x + 2

최적화 후:  x = 5
           y = 5 + 2   → 상수 접기와 조합하면 y = 7
```

이 두 최적화가 조합되면, [5편](05-intermediate-representation-stack-machine/)에서 다룬 스택 머신 코드에도 `PUSH 5; PUSH 2; ADD` 대신 `PUSH 7` 하나만 남길 수 있습니다 — 중요한 건 두 최적화가 서로를 계속 더 많은 기회로 이어준다는 점입니다. 상수 전파가 새 상수를 만들면 상수 접기가 그걸 계산하고, 그 결과가 또 다른 상수 전파의 재료가 됩니다.

---

## 4. 지역 최적화 (2): 죽은 코드 제거

**죽은 코드 제거(Dead Code Elimination)**는 계산은 하지만 그 결과가 어디서도 쓰이지 않는 코드를 통째로 지웁니다.

```
최적화 전:  t1 = n * 2
           t2 = n + 1
           return t2        ; t1은 어디서도 쓰이지 않음

최적화 후:  t2 = n + 1
           return t2        ; t1을 계산하는 코드 자체가 사라짐
```

문제는 "이 값이 어디서도 쓰이지 않는다"는 걸 어떻게 아느냐는 것입니다. 기본 블록 하나 안에서는 뒤에서부터 앞으로 훑으며 "이 시점 이후로 이 변수가 다시 읽히는가"를 추적하면 되지만, `t1`이 이 블록 끝에서 다른 블록으로 넘어가 그 블록에서 쓰일 수도 있습니다 — 즉 **이 값이 나중에 쓰이는지 안 쓰이는지는 블록 하나만 봐서는 알 수 없는 경우가 있습니다.** 이게 바로 다음 절에서 다룰 문제입니다.

"이 값을 쓰는 곳이 정확히 어디인가"라는 질문은 딥러닝 컴파일러에서도 형태만 바꿔 등장합니다. [ONNX 모델을 MLIR로 최적화하기 3편](../onnx-mlir-hardware-optimization/03-graph-level-optimization/#1-연산-융합operator-fusion-conv-batchnorm-relu를-하나로)에서 Conv-BatchNorm-Relu 세 연산을 하나로 합칠 수 있었던 조건이 "Conv의 출력을 쓰는 곳이 정확히 BatchNorm 하나뿐"이라는 것이었는데, 이건 정확히 이 절의 "이 값을 나중에 다시 읽는 곳이 있는가"를 텐서 그래프 수준에서 확인한 것입니다 — 스칼라 변수의 def-use 관계를 확인하는 대신 텐서 연산 노드의 def-use 관계를 확인한다는 차이뿐, 질문의 형태는 같습니다.

## 5. 블록 경계를 넘는 질문: 왜 전역 분석이 필요한가

`fact` 함수의 제어 흐름 그래프(Control Flow Graph, CFG — 기본 블록들을 노드로, 분기를 간선으로 그린 그래프)를 생각해봅시다.

```
     BB1
    /    \
  BB2    BB3
    \    /
     BB4
```

`BB2`에서 정의된 값이 `BB4`에서 쓰인다면, `BB2`만 봐서는 "이 값이 나중에 쓰이는지"를 알 수 없습니다 — `BB4`까지 살펴봐야 합니다. 이렇게 **CFG 전체를 가로질러 정보를 전파해야 답할 수 있는 질문**을 다루는 게 **전역 최적화(Global Optimization)**이고, 이 정보를 CFG 위에서 체계적으로 계산하는 방법이 **데이터플로우 분석(Dataflow Analysis)**입니다.

---

## 6. 데이터플로우 분석의 대표 사례: Liveness

[6편](06-code-generation-register-machine/#3-레지스터-할당-그래프-컬러링으로-충돌을-피하기)에서 레지스터 할당이 "두 값이 동시에 살아있는가"를 알아야 한다고 했는데, 이 "살아있음(live)"을 CFG 전체에 걸쳐 정확히 계산하는 게 **Liveness 분석**입니다. 정의는 이렇습니다 — 변수 `x`는 "지금 이 지점에서 `x`가 나중에(현재 값이 덮어써지기 전에) 읽힐 가능성이 있다면" 살아있습니다.

이 정보는 각 기본 블록의 **끝에서 시작**을 향해(즉 실행 순서의 반대 방향으로) CFG를 거슬러 올라가며 계산합니다 — "이 블록을 나간 뒤에 무엇이 필요한지"를 알아야 "이 블록 안에서 무엇이 필요한지"를 계산할 수 있기 때문입니다.

```
각 블록에 대해:
  live_out(B) = 그 뒤에 오는 블록들의 live_in의 합집합
  live_in(B)  = use(B) ∪ (live_out(B) - def(B))
```

`use(B)`는 "이 블록이 자신의 정의보다 먼저 읽는 변수들"(블록에 들어오기 전부터 이미 값이 있어야 하는 변수), `def(B)`는 "이 블록이 값을 새로 정의하는 변수들"입니다. 이 계산을 CFG 전체에 대해 **더 이상 값이 바뀌지 않을 때까지(고정점, Fixed Point) 반복**합니다 — `BB4`의 `live_in`이 바뀌면 그 앞의 `BB2`, `BB3`의 `live_out`도 다시 계산해야 하고, 이게 다시 그 앞의 `BB1`에 영향을 줄 수 있으므로, 그래프에 순환(반복문에 의한)이 있으면 한 번의 순회로 끝나지 않습니다.

이렇게 계산된 `live_in`/`live_out`이 바로 [6편](06-code-generation-register-machine/#3-레지스터-할당-그래프-컬러링으로-충돌을-피하기)에서 그래프 컬러링의 재료로 쓰인 "동시에 살아있는 값들의 관계"입니다 — 이번 편에서 처음으로, 레지스터 할당이 어떻게 그 정보를 실제로 얻는지가 드러난 셈입니다.

## 7. 데이터플로우 분석의 일반적인 틀

Liveness는 데이터플로우 분석의 한 사례일 뿐이고, 다른 분석들도 같은 틀 — **각 프로그램 지점에 정보를 붙이고, 이웃 지점과의 관계를 방정식으로 표현한 뒤, 고정점에 도달할 때까지 반복 계산**하는 구조를 공유합니다.

| 분석 | 방향 | 계산하는 것 |
|---|---|---|
| Liveness | 뒤에서 앞으로 | 이 변수가 나중에 다시 읽히는가 |
| Reaching Definitions | 앞에서 뒤로 | 이 지점에 어느 대입이 영향을 미칠 수 있는가 |
| Available Expressions | 앞에서 뒤로 | 이 식이 이미 계산되어 재사용 가능한가 |

**Reaching Definitions**가 "이 변수를 마지막으로 정의한 게 어느 대입문인가"를 알려주면, 3~4절의 상수 전파를 블록 경계를 넘어(전역적으로) 적용할 수 있습니다 — `x`를 쓰는 지점에 도달하는 정의가 단 하나뿐이고 그게 상수 대입이라면, 그 지점의 `x`를 안전하게 상수로 바꿀 수 있습니다. **Available Expressions**는 "`t1 = a + b`를 이미 계산해뒀는데, 뒤에서 또 `a + b`가 나오면 다시 계산하지 않고 `t1`을 재사용해도 되는가"(공통 부분식 제거, Common Subexpression Elimination)를 판단하는 근거가 됩니다.

## 8. 현대 컴파일러가 한 걸음 더 나아간 지점: SSA Form

지금까지 다룬 데이터플로우 분석(Reaching Definitions로 "이 변수를 마지막으로 정의한 게 어디인가"를 찾는 것)은 원리상 올바르지만, 한 변수가 프로그램 여러 곳에서 재대입될 수 있다는 사실 때문에 매번 "지금 이 지점에 도달하는 정의가 정확히 몇 개인가"를 다시 계산해야 합니다. LLVM, GCC, 그리고 [MLIR 같은 최신 컴파일러 인프라](../lean/lean4-mlir-codegen/00-what-is-mlir/)는 이 계산 자체를 거의 필요 없게 만드는 중간 표현을 씁니다 — **SSA(Static Single Assignment) Form**입니다.

핵심 규칙은 하나입니다 — **모든 변수는 프로그램 텍스트 안에서 딱 한 번만 대입될 수 있습니다.** 같은 이름을 여러 번 대입해야 하는 코드는, 대입마다 새 이름(보통 아래첨자로 구분)을 붙여 서로 다른 변수로 쪼갭니다.

```
SSA 이전:              SSA 이후:
x = 5                 x1 = 5
x = x + 1             x2 = x1 + 1
y = x * 2             y1 = x2 * 2
```

이렇게 바꾸고 나면, Reaching Definitions가 "이 변수를 정의하는 지점이 여러 개일 수 있다"는 문제를 아예 풀 필요가 없어집니다 — `x2`를 쓰는 자리는 정의상 `x2 = x1 + 1`이라는 단 하나의 대입문에서만 왔다는 게 이름 자체로 보장되기 때문입니다. **6절의 Liveness**나 3절의 상수 전파도 마찬가지로 단순해집니다 — "이 값이 어디서 왔는지"를 흐름을 따라 추적할 필요 없이, 변수 이름만 보면 바로 알 수 있습니다.

문제는 분기가 있으면 이 규칙이 곧바로 막힙니다.

```
if (cond) { x1 = 1; } else { x2 = 2; }
y = ??? * 2   // 여기서 x는 x1일 수도 x2일 수도 있음
```

SSA는 이 지점에 **φ(파이) 함수**라는 특수한 합류 지점 표시를 둡니다.

```
if (cond) { x1 = 1; } else { x2 = 2; }
x3 = φ(x1, x2)   // 어느 분기로 왔는지에 따라 x1 또는 x2를 선택
y1 = x3 * 2
```

`φ(x1, x2)`는 "이 지점에 `if` 분기에서 왔으면 `x1`을, `else` 분기에서 왔으면 `x2`를 쓴다"는 뜻이고, 실제 코드로 낮출 때는(예: [6편](06-code-generation-register-machine/)의 레지스터 머신 코드로) 각 분기 끝에 `x3`에 해당 값을 옮기는 명령을 삽입하는 형태로 없어집니다.

이 시리즈의 파이프라인(AST → 스택 머신 IR → 레지스터 머신 코드)에 SSA를 끼워 넣는다면, [5편](05-intermediate-representation-stack-machine/)의 스택 머신 IR과 [6편](06-code-generation-register-machine/)의 레지스터 할당 사이에 한 단계가 추가됩니다 — 스택 머신 코드를 SSA 형태로 한 번 바꾼 뒤, 이 편에서 다룬 최적화(상수 전파, 죽은 코드 제거, Liveness 기반 레지스터 할당)를 SSA 위에서 수행하고, 마지막에 φ 함수를 제거하며 레지스터 머신 코드로 낮춥니다. 원리는 이 시리즈에서 다룬 것과 같지만, 대입이 단 한 번이라는 보장 덕분에 각 분석이 훨씬 적은 계산으로 끝납니다.

## 9. 최적화가 서로를 여는 문: 왜 여러 번 반복하는가

3절에서 상수 접기와 상수 전파가 서로 기회를 만들어준다고 했는데, 이 상호작용은 전역 최적화 사이에서도 똑같이 일어납니다 — 죽은 코드 제거가 어떤 코드를 지우면, 그 코드가 쓰던 값을 정의하던 다른 코드도 이제 쓸모없어져(다시 죽은 코드가 되어) 지울 수 있게 될 수 있습니다. 이 때문에 실전 컴파일러는 이런 최적화들을 한 번만 돌리지 않고, **더 이상 코드가 바뀌지 않을 때까지 여러 번 반복**해서 돌립니다 — 한 최적화가 만든 기회를 다른 최적화가 활용하고, 그게 다시 첫 번째 최적화의 기회를 새로 만드는 순환이 자연스럽게 안정될 때까지입니다.

## 10. 정리

- 최적화는 **관찰 가능한 동작을 바꾸지 않는다**는 전제 위에서만 정당화되며, 이번 편의 모든 분석은 이 안전성을 확인하는 도구입니다.
- **기본 블록** 안에서만 적용하는 **지역 최적화**(상수 접기, 상수 전파, 죽은 코드 제거)는 실행 순서가 고정되어 있어 비교적 단순합니다.
- 블록 경계를 넘는 질문(이 값이 다른 블록에서도 쓰이는가)은 **데이터플로우 분석**으로 CFG 전체에 걸쳐 고정점까지 반복 계산해야 답할 수 있습니다.
- **Liveness 분석**이 계산한 정보가 [6편](06-code-generation-register-machine/)의 레지스터 할당(그래프 컬러링)의 재료가 되고, Reaching Definitions·Available Expressions 같은 다른 분석들이 전역 상수 전파나 공통 부분식 제거의 근거가 됩니다.
- 최적화들은 서로의 기회를 열어주므로, 실전에서는 더 이상 바뀌지 않을 때까지 여러 번 반복해서 적용합니다.
- LLVM·GCC·MLIR 같은 현대 컴파일러는 "변수는 딱 한 번만 대입된다"는 **SSA Form**을 중간 표현으로 채택해, 이번 편에서 다룬 데이터플로우 분석을 변수 이름만으로 사실상 자명하게 만듭니다 — 분기 합류 지점의 φ 함수만 처리하면 됩니다.

여기까지 여덟 편으로, `fact`라는 함수 하나가 문자열 → 토큰([1편](01-lexical-analysis/)) → 파스 트리([2~3편](02-parsing-top-down/)) → 타입이 검사된 AST([4편](04-semantic-analysis/)) → 스택 머신 코드([5편](05-intermediate-representation-stack-machine/)) → 레지스터 머신 코드와 활성화 레코드([6편](06-code-generation-register-machine/)) → 힙 객체를 회수하는 런타임([7편](07-garbage-collection/)) → 더 빠른 코드(이 글)로 이어지는 전체 파이프라인을 따라왔습니다. 이 순서 자체가 MIT 6.035가 다루는 컴파일러 한 학기 분량의 뼈대입니다.
