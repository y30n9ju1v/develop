[5편](05-intermediate-representation-stack-machine/)에서 AST를 스택 머신 코드로 낮췄습니다. 이 글은 그 코드를 실제 CPU(MIPS 스타일 레지스터 머신을 예로 듭니다)가 직접 실행할 수 있는 코드로 한 번 더 낮추면서, 스택 머신에서는 신경 쓸 필요 없었던 두 가지 새 문제 — **레지스터는 몇 개뿐인데 값은 얼마든지 있을 수 있다**는 문제와, **함수가 호출될 때마다 그 함수만의 데이터를 어디에 둘 것인가**라는 문제를 다룹니다.

---

## 1. 스택 머신과 레지스터 머신의 근본적 차이

[5편](05-intermediate-representation-stack-machine/) 1절에서 스택 머신이 "레지스터 이름을 신경 쓸 필요가 없다"는 이유로 유용했다고 했습니다. 레지스터 머신은 정확히 그 반대 제약을 갖습니다 — MIPS는 범용 레지스터가 32개뿐이고, 그마저도 관례상 일부는 특수 용도로 예약되어 있습니다. `n * fact(n - 1)`처럼 값 여러 개가 동시에 살아있어야 하는 식을 레지스터 머신으로 옮기려면, "이 값을 지금 어느 레지스터에 넣어야 다른 살아있는 값을 덮어쓰지 않는가"를 결정해야 합니다 — 이게 이 편의 3절에서 다룰 **레지스터 할당** 문제입니다.

---

## 2. 스택 연산을 레지스터 연산으로: 직접적인 변환

가장 단순한 접근은 [5편](05-intermediate-representation-stack-machine/)의 스택을 그대로 메모리에 남겨두고, 스택 맨 위 값을 계산 직전에 레지스터로 불러오는 것입니다.

```
스택 머신:              레지스터 머신 (단순 변환):
LOAD n                  lw   $t0, n
LOAD n                  lw   $t1, n
PUSH 1                  li   $t2, 1
SUB                     sub  $t1, $t1, $t2      ; t1 = n - 1
CALL fact, 1            move $a0, $t1           ; 관례: 첫 인자는 $a0
                        jal  fact                ; 호출, 결과는 관례상 $v0
MUL                     mul  $t0, $t0, $v0
```

이 변환은 항상 올바르지만 비효율적입니다 — `LOAD n`을 두 번 했다는 건 메모리에서 `n`을 두 번 읽어왔다는 뜻인데, `n`의 값은 두 번 다 똑같습니다. 스택 머신 코드를 그대로 1:1로 옮기는 대신, 값을 레지스터에 최대한 오래 붙잡아 두고 재사용하는 게 3절에서 다룰 레지스터 할당이 실제로 하는 일입니다.

---

## 3. 레지스터 할당: 그래프 컬러링으로 충돌을 피하기

레지스터 할당의 핵심 질문은 "두 값을 같은 레지스터에 넣어도 안전한가"입니다. 안전하려면 두 값이 **동시에 살아있지(live) 않아야** 합니다 — 한 값이 더 이상 쓰이지 않게 된 뒤에야 그 레지스터를 다른 값에 재사용할 수 있습니다. 이 "동시에 살아있는가"라는 관계를 그래프로 그리면, 레지스터 할당은 **그래프 컬러링(Graph Coloring)** 문제가 됩니다.

```
1. 각 값(변수, 임시값)을 그래프의 노드로 표현
2. 두 값이 동시에 살아있으면 그 둘 사이에 간선을 그림 (간선 = "같은 레지스터를 쓰면 안 됨")
3. 사용 가능한 레지스터 개수만큼의 색으로 이 그래프를 칠함 (인접한 노드는 다른 색)
```

`n * fact(n - 1)`에서는 `n`의 값이 `fact(n-1)` 호출 **이후에도** `MUL`에서 다시 쓰이므로, `n`은 함수 호출 전체에 걸쳐 살아있어야 합니다 — 즉 `n`을 담은 레지스터와 `fact` 호출 중에 쓰이는 레지스터들 사이에 간선이 생겨, 이 값을 함부로 덮어쓸 레지스터에 배정할 수 없습니다.

```
n의 값이 살아있는 구간:  ────────────────────────────
fact(n-1) 계산 구간:              ──────────
                                  ↑ 이 구간 동안 n도 여전히 살아있음 → 같은 레지스터 재사용 불가
```

이 "언제부터 언제까지 살아있는가"를 계산하는 분석(**liveness analysis**)이 그래프를 만드는 전제 조건이고, 이 분석은 [8편](08-optimization-dataflow-analysis/)에서 다룰 데이터플로우 분석의 대표적인 사례이기도 합니다 — 레지스터 할당과 최적화가 결국 같은 분석 도구를 공유합니다.

### 그래프를 실제로 어떻게 칠하는가: Chaitin-Briggs 휴리스틱

그래프 컬러링 자체는 일반적으로 NP-complete 문제입니다 — 즉 "이 그래프를 $k$개의 색으로 칠할 수 있는가"를 빠르게 정확히 답하는 알고리즘은 (일반적으로는) 없습니다. 그렇다고 컴파일러가 매번 지수 시간을 쓸 수는 없으니, 실전 컴파일러는 정확한 최적해 대신 빠르고 대부분 잘 맞는 **휴리스틱**을 씁니다. 그중 가장 널리 쓰이는 게 **Chaitin-Briggs 알고리즘**이고, 세 단계로 이루어집니다.

```
1. Simplify (간소화)
   차수(간선 개수)가 사용 가능한 레지스터 수 k보다 작은 노드를 찾아
   그래프에서 제거하고 스택에 쌓는다. (이 노드는 이웃이 몇 색을 쓰든
   남는 색이 항상 하나는 있다는 게 보장되므로, 나중에 반드시 칠할 수 있다.)
   더 이상 이런 노드가 없을 때까지 반복한다.

2. Spill (스필 후보 지정)
   1번을 반복하다 모든 남은 노드의 차수가 k 이상이 되어 막히면,
   "스필했을 때 손해가 가장 적어 보이는" 노드 하나를 골라
   일단 스필 후보로 표시하고 그래프에서 제거해 스택에 쌓는다.
   (이 노드가 실제로 스필될지는 3번에서 다시 판단한다.)

3. Select (역순 색칠)
   스택에서 노드를 하나씩 꺼내며(쌓은 순서의 역순 = 나중에 제거된 것부터)
   그 노드가 그래프에 있을 때 이웃이었던 노드들이 이미 쓴 색을 피해 색을 정한다.
   - 남는 색이 있으면 그 색으로 칠하고 끝.
   - 2번에서 스필 후보였던 노드인데도 정말 남는 색이 없다면,
     그제서야 진짜로 메모리에 스필한다.
```

3번의 마지막 줄이 중요합니다 — 2번에서 "스필 후보"로 찍혔다고 반드시 스필되는 게 아닙니다. 스택을 거꾸로 꺼내며 실제로 칠해보면, 이웃 노드들이 이미 스필되어 그래프에서 빠졌거나 우연히 색이 남아서 스필 없이 넘어가는 경우가 많습니다 — 그래서 이 알고리즘을 **낙관적 스필링(Optimistic Coloring)**이라고도 부릅니다. "안 될 것 같아도 일단 끝까지 칠해보고, 정말 안 될 때만 스필한다"는 태도가 4절에서 다룬 스필 자체를 최대한 아끼는 핵심 아이디어입니다.

## 4. 레지스터가 모자랄 때: 스필링(Spilling)

그래프의 색(레지스터) 수보다 동시에 살아있는 값이 많으면, 컬러링이 불가능한 노드가 생깁니다. 이 경우 어떤 값은 레지스터가 아니라 **메모리(스택)에 임시로 저장**해야 하는데, 이를 **스필(Spill)**이라고 부릅니다.

```
r1 = load n
r2 = ...              ; 레지스터가 부족해 n을 잠시 메모리에 스필
store r1, [spill_slot]
... (r1을 다른 값에 재사용) ...
r1 = load [spill_slot] ; 나중에 n이 다시 필요할 때 메모리에서 복원
r3 = r1 * v0
```

스필은 "메모리 접근이 레지스터 접근보다 훨씬 느리다"는 대가를 치르므로, 컴파일러는 보통 "가장 적게, 가장 늦게 다시 쓰이는 값"을 스필 후보로 고릅니다 — 어차피 스필해야 한다면 그 손해를 최소화하는 값을 고르는 것입니다.

## 5. 함수 호출마다 필요한 데이터: 활성화 레코드

[5편](05-intermediate-representation-stack-machine/#4-함수-호출과-지역-변수-매개변수는-어디에-있는가)에서 스택 머신의 인자 전달 규약을 봤는데, 레지스터 머신에서는 이 규약이 훨씬 정교해야 합니다. 함수가 호출될 때마다 필요한 것들 — 매개변수, 지역 변수, 반환 주소, 호출자의 레지스터 값 — 을 담는 메모리 영역을 **활성화 레코드(Activation Record)** 또는 **스택 프레임(Stack Frame)**이라고 부릅니다.

```
높은 주소
┌─────────────────────┐
│ 호출자의 활성화 레코드  │
├─────────────────────┤
│ 인자 (n-1의 값)        │  ← 호출자가 채워 넣음
├─────────────────────┤
│ 반환 주소              │  ← jal 명령이 자동으로 저장
├─────────────────────┤
│ 저장된 레지스터 값      │  ← 이 함수가 다시 쓰기 전에 백업
├─────────────────────┤
│ 지역 변수 (fact에는 없음)│
└─────────────────────┘
낮은 주소                    ← 스택 포인터(SP)가 이 지점을 가리킴
```

`fact(n - 1)`을 호출하는 순간의 코드로 이 레코드가 실제로 어떻게 쌓이는지 보면:

```mips
fact:
  addi $sp, $sp, -12       # 활성화 레코드 공간 확보 (12바이트)
  sw   $ra, 8($sp)         # 반환 주소 저장
  sw   $s0, 4($sp)         # 이 함수가 쓸 레지스터 $s0을 나중을 위해 백업
  move $s0, $a0            # 매개변수 n을 $s0에 (함수 본문 동안 계속 유지)

  beq  $s0, $zero, L_base
  # ... n * fact(n-1) 계산 ...
  addi $a0, $s0, -1        # 다음 호출의 인자(n-1) 준비
  jal  fact                # 재귀 호출 — 여기서 새 활성화 레코드가 또 쌓임

  lw   $ra, 8($sp)         # 반환 주소 복원
  lw   $s0, 4($sp)         # 백업해둔 레지스터 복원
  addi $sp, $sp, 12        # 활성화 레코드 반납
  jr   $ra                 # 호출자로 복귀
```

`fact(5)`가 `fact(4)`를 호출하고, 그게 다시 `fact(3)`을 호출하는 식으로 재귀가 깊어질 때마다 이 활성화 레코드가 스택에 계속 쌓입니다 — 재귀 호출 하나마다 각자의 `n` 값을 독립적으로 유지할 수 있는 이유가, 바로 각 호출이 자기만의 활성화 레코드(그리고 그 안의 `$s0` 백업)를 갖기 때문입니다.

## 6. 호출 규약: 누가 어느 레지스터를 지킬 책임이 있는가

5절의 `$s0`을 백업하고 복원하는 코드가 왜 필요한지는 **호출 규약(Calling Convention)** — 함수 호출 시 누가 무엇을 지켜야 하는지에 대한 약속 — 을 봐야 이해됩니다.

- **Callee-saved 레지스터**(예: `$s0`~`$s7`): 이 레지스터를 쓰려는 함수(callee, 즉 `fact` 자신)가 "쓰기 전에 백업하고, 반환 전에 복원할" 책임을 집니다. 그래서 5절 코드에서 `fact`가 직접 `$s0`을 저장/복원했습니다.
- **Caller-saved 레지스터**(예: `$t0`~`$t9`): 함수를 호출하는 쪽(caller)이 "이 값이 호출 후에도 필요하다면 호출 전에 스스로 백업해야" 합니다 — 피호출자는 이 레지스터를 마음대로 덮어써도 됩니다.

이 구분이 왜 있냐면, 만약 규약이 없다면 모든 함수가 자신이 건드리는 레지스터를 전부 저장/복원해야 하는데(안전하지만 느림), 이 관례를 나눠두면 각 레지스터가 "이 상황엔 저장할 필요 없다"는 걸 양쪽이 미리 알 수 있어 불필요한 저장을 줄일 수 있습니다. 3절의 레지스터 할당기도 이 규약을 알아야 합니다 — "함수 호출을 넘어 오래 살아있어야 하는 값"은 callee-saved 레지스터에 배정하는 게 유리하고(백업/복원 책임이 명확하니까), "호출 전에 끝나는 짧은 임시값"은 caller-saved 레지스터를 자유롭게 씁니다.

## 7. 스택 머신에서 레지스터 머신으로, 무엇이 달라졌는가

[5편](05-intermediate-representation-stack-machine/)과 이 편을 나란히 놓으면, "값을 계산해 어딘가에 남긴다"는 목표는 같지만 그 "어딘가"의 성격이 완전히 달라졌다는 걸 알 수 있습니다.

| | 스택 머신 (5편) | 레지스터 머신 (이 글) |
|---|---|---|
| 값을 두는 곳 | 스택 맨 위 (무한히 쌓을 수 있음) | 유한한 개수의 레지스터 |
| 값의 재사용 | 신경 쓸 필요 없음 | 그래프 컬러링으로 계획 필요 |
| 레지스터 부족 시 | 해당 없음 | 스필로 메모리에 임시 저장 |
| 함수 호출 규약 | 인자를 스택에 쌓기만 하면 됨 | 활성화 레코드, callee/caller-saved 구분 필요 |

[5편](05-intermediate-representation-stack-machine/)에서 스택 머신이라는 중간 표현을 거친 이유가 여기서 분명해집니다 — AST에서 곧바로 이 편의 복잡도(레지스터 할당 + 활성화 레코드 설계)로 뛰어드는 대신, 두 문제를 단계별로 나눠 다룰 수 있었습니다.

## 8. 정리

- 스택 머신 코드를 레지스터 머신 코드로 낮출 때 가장 단순한 변환은 항상 올바르지만 비효율적이며, 값을 레지스터에 오래 붙잡아 재사용하는 게 **레지스터 할당**이 실제로 하는 일입니다.
- 레지스터 할당은 "동시에 살아있는 값들 사이에 간선을 그리고, 레지스터 개수만큼의 색으로 칠하는" **그래프 컬러링** 문제이며, 색칠이 불가능하면 일부 값을 메모리로 **스필**합니다. 실전 컴파일러는 이 NP-complete 문제를 **Chaitin-Briggs**의 Simplify-Spill-Select 3단계 휴리스틱으로 빠르게 근사해서 풉니다.
- 함수 호출마다 매개변수·반환 주소·백업 레지스터를 담는 **활성화 레코드**가 스택에 쌓이고, 재귀 호출이 깊어질수록 각 호출이 독립된 활성화 레코드를 가지므로 값이 서로 섞이지 않습니다.
- **Callee-saved**/**caller-saved** 레지스터 구분이라는 호출 규약이, 함수 호출 시 누가 어떤 레지스터를 지킬 책임이 있는지를 명확히 해 불필요한 저장/복원을 줄입니다.

다음 편에서는 이 활성화 레코드가 함수 반환 후에도 자동으로 정리되지 않는 경우 — 힙에 동적으로 할당된 객체를 언제, 어떻게 회수할 것인가라는 **가비지 컬렉션**을 다룹니다.
