[4편](04-semantic-analysis/)에서 MiniLang의 AST가 이름과 타입 규칙을 모두 지킨다는 걸 확인했습니다. 이 글부터는 그 AST를 실제로 **실행 가능한 코드**로 낮추는 단계를 다룹니다. 첫걸음으로, AST를 실제 하드웨어 명령어가 아니라 **스택 기반 추상 머신**의 명령어로 옮깁니다 — 이 중간 단계를 왜 거치는지가 이 글의 핵심입니다.

---

## 1. 왜 AST에서 곧바로 기계어로 가지 않는가

AST는 각 노드가 하위 노드 두세 개를 자식으로 가지는 트리 구조입니다. 반면 실제 CPU가 실행하는 기계어는 "레지스터 R1과 R2를 더해서 R3에 저장하라"는 식의 평평한 명령어 나열입니다. 이 둘 사이의 간극이 크기 때문에, 트리 구조의 AST를 곧바로 레지스터 기반 기계어로 옮기려 하면 "지금 이 값을 어느 레지스터에 넣어야 다른 값과 충돌하지 않는가"라는 문제([6편](06-code-generation-register-machine/)에서 다룰 레지스터 할당)까지 한 번에 풀어야 합니다.

**스택 기반 추상 머신**은 이 문제를 트리 구조와 훨씬 잘 맞는 형태로 우회합니다 — 레지스터 대신 값을 쌓는 스택 하나만 있고, 모든 연산은 "스택 맨 위 몇 개를 꺼내 계산하고 결과를 다시 스택에 넣는다"는 동일한 패턴을 따릅니다.

```
명령       스택 변화
PUSH 3     [3]
PUSH 4     [3, 4]
ADD        [7]        (맨 위 두 개를 꺼내 더하고 결과를 다시 쌓음)
```

이 "레지스터 이름을 신경 쓸 필요가 없다"는 성질 덕분에, AST에서 스택 머신 코드로의 변환은 뒤에서 볼 것처럼 각 노드 종류마다 정해진 규칙을 그대로 적용하는 **기계적인 재귀 번역**이 됩니다.

---

## 2. AST를 스택 머신 코드로: 재귀적 변환 규칙

핵심 아이디어는 하나입니다 — **"이 식을 계산하는 코드"는 그 코드가 실행된 뒤 결과 값 하나를 스택 맨 위에 남긴다**는 불변식(invariant)을 모든 노드 종류에 대해 지키는 것입니다.

```python
def codegen(expr):
    match expr:
        case Const(n):
            emit(f"PUSH {n}")
        case Var(name):
            emit(f"LOAD {name}")           # 변수의 현재 값을 스택에 올림
        case BinOp(op, left, right):
            codegen(left)                  # left의 값이 스택에 쌓임 (재귀 호출의 불변식)
            codegen(right)                 # right의 값이 그 위에 쌓임
            emit(f"{op_to_instr(op)}")     # 스택 맨 위 두 개를 꺼내 연산, 결과를 다시 쌓음
        case Call(name, args):
            for arg in args:
                codegen(arg)                # 각 인자의 값을 순서대로 스택에 쌓음
            emit(f"CALL {name}, {len(args)}")
```

`BinOp` 케이스를 보면, `codegen(left)`를 호출하기만 하면 그 결과로 `left`의 값이 스택에 놓여 있다는 걸 **그대로 믿고** `codegen(right)`를 이어서 호출합니다 — 이게 바로 [4편](04-semantic-analysis/#3-두-번째-질문-이-식의-결과는-무슨-타입인가-타입-검사)에서 타입 검사가 AST를 재귀적으로 순회했던 것과 정확히 같은 재귀 구조입니다. 다만 이번엔 "타입을 계산해 반환"하는 대신 "명령어를 내보내는" 부수 효과(side effect)를 낸다는 점이 다릅니다.

`n * fact(n - 1)`을 이 규칙으로 번역해보면:

```
LOAD n              ; n의 값을 스택에
LOAD n               ; fact(n-1)의 인자를 준비하기 위해 n을 다시 로드
PUSH 1
SUB                  ; 스택: [n, n-1]
CALL fact, 1         ; 스택 맨 위(n-1)를 인자로 fact 호출, 결과로 fact(n-1)의 값이 스택에 남음 (스택: [n, fact(n-1)])
MUL                  ; 스택 맨 위 두 개(n과 fact(n-1))를 곱함
```

## 3. 제어 흐름: `if`는 스택 연산이 아니라 점프다

`BinOp`는 "값을 계산해 스택에 남긴다"는 패턴이 자연스러웠지만, `if`는 다릅니다 — 조건에 따라 **서로 다른 코드 블록 중 하나만** 실행해야 합니다. 스택 머신에서 이건 **레이블(label)과 조건부 점프**로 구현합니다.

```python
def codegen_stmt(stmt):
    match stmt:
        case If(cond, then_block, else_block):
            else_label = new_label()
            end_label = new_label()
            codegen(cond)                        # 조건식의 값(0 또는 1)을 스택에 남김
            emit(f"JMP_IF_FALSE {else_label}")    # 스택 맨 위를 꺼내 확인, 거짓이면 else로 점프
            codegen_block(then_block)
            emit(f"JMP {end_label}")
            emit(f"{else_label}:")
            codegen_block(else_block)
            emit(f"{end_label}:")
        case Return(expr):
            codegen(expr)                          # 반환값을 스택에 남김
            emit("RET")                             # 이 값을 호출자에게 돌려주며 함수 종료
```

`fact` 함수 전체를 이 규칙으로 번역하면 이렇게 됩니다.

```
fact:
  LOAD n
  PUSH 0
  EQ                    ; 스택: [n == 0의 결과]
  JMP_IF_FALSE L_else
  PUSH 1
  RET
L_else:
  LOAD n
  LOAD n
  PUSH 1
  SUB
  CALL fact, 1
  MUL
  RET
```

[2편](02-parsing-top-down/#2-cfg로-파스-트리-만들기)에서 파스 트리가 `if`의 두 분기를 트리 구조로 나란히 담고 있었던 것과 달리, 이 코드에서는 두 분기가 `JMP_IF_FALSE`라는 **선형적인 점프 명령**으로 바뀌었습니다 — 트리의 "두 가지 대안"이라는 구조가, 스택 머신의 "순서대로 실행되다가 조건에 따라 건너뛴다"는 실행 모델에 맞게 재구성된 것입니다.

---

## 4. 함수 호출과 지역 변수: 매개변수는 어디에 있는가

`CALL fact, 1` 명령이 실행되면, 새로 시작되는 `fact` 함수 본문에서 `LOAD n`이 무엇을 읽어와야 할까요? 스택 머신에서는 보통 **함수가 호출되기 직전에 쌓인 인자들이 그 함수의 매개변수 자리**라는 규약을 씁니다.

```
호출 직전 스택: [..., n-1]         ← CALL fact, 1 실행 (인자 1개)
fact 함수 진입 시:                   이 n-1이 fact의 매개변수 n의 값
  LOAD n  →  스택에서 "매개변수 영역의 n번째"를 찾아 로드
```

이 "매개변수와 지역 변수가 스택의 특정 위치에 대응한다"는 규약이, [6편](06-code-generation-register-machine/)에서 다룰 **활성화 레코드(Activation Record)**의 가장 단순한 형태입니다 — 스택 머신에서는 이 대응 관계가 비교적 단순하지만, 실제 레지스터 머신으로 가면 이 규약이 훨씬 정교해져야 합니다.

## 5. 스택 머신 코드를 어떻게 실행하는가: 인터프리터 vs 추가 낮추기

이 시점에서 두 가지 갈래가 있습니다.

1. **이 스택 머신 코드를 그대로 인터프리터로 실행한다**: 스택 머신 명령을 하나씩 해석해 실행하는 프로그램(가상 머신)을 만드는 방식으로, JVM 바이트코드나 Python 바이트코드가 실제로 이 접근을 씁니다. 구현이 간단하지만, 매 명령마다 해석 비용이 붙어 네이티브 코드보다 느립니다.
2. **이 스택 머신 코드를 실제 레지스터 머신(x86, MIPS 등)의 코드로 한 번 더 낮춘다**: 스택 연산(`PUSH`, `ADD`)을 레지스터 연산으로 번역하는 추가 단계를 거쳐, CPU가 직접 실행할 수 있는 네이티브 코드를 만듭니다.

[6편](06-code-generation-register-machine/)은 두 번째 갈래를 다룹니다 — 스택 머신이라는 중간 표현이 왜 유용했는지(트리 구조와 잘 맞는 기계적 번역)는 그대로 인정하면서, 이 표현을 실제 레지스터가 유한한 진짜 하드웨어에 맞게 다시 낮추는 문제(레지스터 할당, 활성화 레코드 설계)를 다룹니다.

---

## 6. 정리

- AST를 곧바로 레지스터 머신 코드로 옮기는 대신, **스택 기반 추상 머신**이라는 중간 표현을 먼저 거치면 "레지스터를 어떻게 배정할지"를 신경 쓸 필요 없이 트리 구조를 그대로 반영한 기계적 번역이 가능해집니다.
- 코드 생성의 핵심 불변식은 **"이 식의 코드는 실행 후 결과 값 하나를 스택에 남긴다"**이며, 이 불변식 덕분에 `BinOp`처럼 자식이 있는 노드도 재귀 호출만으로 올바른 코드를 조립할 수 있습니다.
- `if`처럼 값을 계산하지 않는 제어 구조는 스택 연산이 아니라 **레이블과 조건부 점프**로 번역되며, 트리의 "두 대안" 구조가 "순서대로 실행하다 건너뛴다"는 선형 구조로 재구성됩니다.
- 함수 호출 시 인자들이 스택에 놓이는 규약이, [6편](06-code-generation-register-machine/)에서 다룰 활성화 레코드의 가장 단순한 원형입니다.

다음 편에서는 이 스택 머신 코드를 실제 레지스터 머신(MIPS 스타일)의 코드로 다시 낮추면서, 유한한 개수의 레지스터를 어떻게 배정할지와 함수 호출마다 필요한 활성화 레코드·런타임 스택을 다룹니다.
