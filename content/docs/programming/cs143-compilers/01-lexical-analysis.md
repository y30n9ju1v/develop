이 시리즈는 Stanford CS143(Alex Aiken)의 컴파일러 강의가 다루는 순서 — 어휘 분석 → 구문 분석(하향식/상향식) → 의미 분석 → 중간 표현과 스택 머신 코드 생성 → 레지스터 머신 코드 생성과 런타임 → 가비지 컬렉션 → 최적화 — 를 따라갑니다. **MiniLang**이라는 아주 작은 언어 하나를 시리즈 내내 컴파일해 나가며, 각 단계가 앞 단계의 결과물을 어떻게 받아 다음 단계로 넘기는지를 계속 확인합니다.

```
def fact(n) {
  if (n == 0) { return 1; }
  else { return n * fact(n - 1); }
}
```

정수, 불리언, `if`/`else`, 함수 정의와 호출만 있는 이 작은 함수 하나가 1편에서는 문자열로, 2~3편에서는 파스 트리로, 4편에서는 타입이 검사된 AST로, 5~6편에서는 실행 가능한 코드로 계속 형태를 바꿉니다.

---

## 1. 컴파일러의 첫 관문: 문자열을 토큰으로

컴파일러가 받는 입력은 그냥 문자들의 나열입니다. `if (n == 0) { return 1; }`이라는 줄은 컴파일러 입장에서 `'i', 'f', ' ', '(', 'n', ' ', ...`처럼 한 글자씩 이어진 문자열일 뿐입니다. **어휘 분석(Lexical Analysis)**은 이 문자열을 의미 있는 최소 단위인 **토큰(token)**으로 잘라내는 단계입니다.

```
"if (n == 0) { return 1; }"
   ↓ 어휘 분석
[IF] [LPAREN] [ID "n"] [EQ] [INT 0] [RPAREN] [LBRACE] [RETURN] [INT 1] [SEMI] [RBRACE]
```

토큰은 두 부분으로 이루어집니다 — **종류**(`IF`, `ID`, `INT` 같은 카테고리)와 **값**(`ID`라면 실제 식별자 문자열, `INT`라면 실제 숫자값). 이 뒤에 오는 2편의 구문 분석은 문자를 하나씩 보는 대신, 이 토큰들의 나열만 보고 작업합니다 — 어휘 분석이 이렇게 입력을 미리 정리해 주기 때문에 구문 분석기가 공백이나 주석 같은 잡음을 신경 쓸 필요가 없어집니다.

---

## 2. 토큰의 패턴을 정의하는 언어: 정규 표현식

각 토큰 종류가 어떤 문자열 모양인지를 정의하는 표준 도구가 **정규 표현식(Regular Expression)**입니다. MiniLang의 토큰 몇 개를 정규 표현식으로 적어보면:

```
IF      = if
ID      = letter (letter | digit)*
INT     = digit+
WS      = (space | tab | newline)+   (버려질 토큰)
```

여기서 `ID`의 정의(`letter (letter | digit)*`)를 눈여겨봐야 합니다 — 이 정의가 정확히 "글자로 시작해서, 그 뒤에 글자나 숫자가 몇 개든 이어질 수 있다"는 걸 뜻하고, 이게 바로 `n`, `fact`, `x1` 같은 식별자가 유효한 이유입니다. `IF`와 `ID`의 정의가 겹치는 지점도 있습니다 — `if`라는 문자열은 `IF`의 정의도 만족하고 `ID`의 정의(`letter letter*`)도 만족합니다. 이 모호함을 어떻게 해소하는지는 4절에서 다룹니다.

---

## 3. 정규 표현식을 실행 가능하게 만들기: Thompson 구성

정규 표현식은 "무엇이 유효한 토큰인지"를 정의할 뿐, 그 자체로는 실행되지 않습니다. 이걸 실제로 문자열을 한 글자씩 읽으며 판정하는 기계로 바꾸는 표준 절차가 **Thompson 구성(Thompson's Construction)**입니다 — 정규 표현식의 각 구성 요소(문자, 이어붙이기, 선택, 반복)마다 대응하는 작은 **NFA(비결정적 유한 오토마타)** 조각을 정의하고, 이 조각들을 정규 표현식의 구조 그대로 이어붙입니다.

```
정규 표현식 "a"     →  ──a──▶ (하나의 문자를 읽는 최소 조각)

정규 표현식 "AB"     →  [NFA(A)] ──ε──▶ [NFA(B)]   (이어붙이기)

정규 표현식 "A|B"    →       ┌──ε──▶ [NFA(A)] ──ε──┐
                     start ─┤                      ├─▶ end
                             └──ε──▶ [NFA(B)] ──ε──┘

정규 표현식 "A*"     →       ┌────────ε────────┐
                     start ─┼──ε──▶[NFA(A)]──ε─┴─▶ end
                             └────────ε─────────────▶ (0번 반복 허용)
```

`ε`(엡실론) 화살표는 "아무 문자도 읽지 않고 상태만 이동한다"는 뜻입니다. `INT = digit+`(숫자 하나 이상)를 이 규칙으로 조립하면 이렇게 됩니다.

```
      ┌──digit──┐
      │         ▼
start ─▶ (s1) ──┴──▶ (s2, 수락 상태)
```

`digit`를 한 번 읽으면 수락 상태(s2)에 도달하고, s2에서 다시 `digit`로 s1로 돌아갈 수 있어 숫자가 몇 자리든 계속 읽을 수 있습니다. 이 조립 과정이 기계적이라는 게 중요합니다 — 정규 표현식이 아무리 복잡해도, 그 구조(이어붙이기/선택/반복)를 그대로 따라가며 NFA 조각을 붙이기만 하면 되므로, 이 변환 자체를 컴파일러(정확히는 렉서 생성기)가 자동으로 해낼 수 있습니다.

---

## 4. NFA의 문제: 어느 상태로 가야 할지 "비결정적"이다

NFA는 이름 그대로 비결정적(Nondeterministic)입니다 — 같은 문자를 읽어도 여러 상태로 동시에 이동할 수 있는 경우가 있고, `ε` 화살표로 문자를 읽지 않고도 이동할 수 있습니다. 이건 사람이 손으로 이해하기엔 편하지만, 실제로 한 글자씩 읽어나가며 "지금 내가 어느 상태에 있는지" 추적해야 하는 스캐너 입장에서는 그대로 실행하기 곤란합니다 — 매 순간 "가능한 모든 상태의 집합"을 유지해야 하기 때문입니다.

**부분집합 구성(Subset Construction)**은 이 문제를, "NFA가 가질 수 있는 상태 집합 하나"를 "**DFA(결정적 유한 오토마타)**의 상태 하나"로 뭉쳐서 해결합니다.

```
NFA 상태 {s1, s2, s5}에서 문자 'a'를 읽으면 → NFA 상태 {s2, s3}로 갈 수 있음
   ↓ 이 전체를 DFA의 전이 하나로 뭉침
DFA 상태 A = {s1, s2, s5}  --'a'-->  DFA 상태 B = {s2, s3}
```

이렇게 만들어진 DFA는 각 상태에서 각 문자에 대해 **정확히 하나의** 다음 상태만 갖습니다 — 스캐너는 이제 "현재 상태 하나"만 기억하면서 한 글자씩 읽어 다음 상태로 넘어가기만 하면 되므로, 실제로 실행하기에 훨씬 간단해집니다. 이 변환 역시 기계적인 절차라 렉서 생성기가 자동으로 수행합니다 — 사람은 3절의 정규 표현식만 적으면 되고, NFA 구성과 DFA 변환은 도구가 대신 해줍니다.

---

## 5. 여러 토큰의 DFA를 하나로 합치기, 그리고 모호함 해소

MiniLang에는 토큰 종류가 여러 개(`IF`, `ID`, `INT`, ...)이므로, 이들의 DFA를 전부 하나의 큰 DFA로 합쳐야 합니다. 이때 여러 DFA의 수락 상태가 겹칠 수 있습니다 — 2절에서 짚었던 `if` 문자열이 `IF`의 DFA도, `ID`의 DFA도 동시에 수락 상태로 이끄는 경우입니다.

이 모호함을 해소하는 표준 규칙이 두 가지입니다.

- **최장 일치(Maximal Munch)**: 여러 해석이 가능하면, 가장 긴 문자열로 매칭되는 쪽을 택합니다. `fact`라는 입력을 보면, `f`만 읽고 멈추는 대신 `fact` 전체를 읽어 하나의 `ID` 토큰으로 만듭니다.
- **우선순위(Priority)**: 같은 길이로 매칭된다면, 정규 표현식을 적은 순서(보통 키워드를 식별자보다 먼저 적음)로 우선순위를 둡니다. `if`는 길이가 같은 `IF`와 `ID` 규칙 중 먼저 선언된 `IF`가 이깁니다.

이 두 규칙 덕분에 `if`는 항상 `IF` 토큰으로, `fact`는 항상 하나의 `ID` 토큰으로 결정됩니다.

## 6. MiniLang의 어휘 분석 결과

이 편의 예제 함수를 어휘 분석기에 통과시키면 이런 토큰 나열이 나옵니다.

```
DEF ID("fact") LPAREN ID("n") RPAREN LBRACE
  IF LPAREN ID("n") EQEQ INT(0) RPAREN LBRACE RETURN INT(1) SEMI RBRACE
  ELSE LBRACE RETURN ID("n") STAR ID("fact") LPAREN ID("n") MINUS INT(1) RPAREN SEMI RBRACE
RBRACE
```

공백과 줄바꿈은 `WS` 토큰으로 매칭되었다가 버려지고(2절에서 언급한 "버려질 토큰"), 남은 토큰들만 다음 단계로 전달됩니다. 이 토큰 나열이 정확히 [2편](02-parsing-top-down/)의 구문 분석기가 받게 될 입력입니다.

---

## 7. 정리

- 어휘 분석은 문자열을 **토큰**(종류 + 값)의 나열로 바꾸는, 컴파일러의 첫 단계입니다.
- 각 토큰의 모양은 **정규 표현식**으로 정의하고, **Thompson 구성**이 이를 실행 가능한 **NFA**로, **부분집합 구성**이 그 NFA를 실행하기 쉬운 **DFA**로 자동 변환합니다.
- 여러 토큰의 매칭이 겹치는 모호함은 **최장 일치**와 **선언 순서 우선순위** 두 규칙으로 기계적으로 해소됩니다.
- 이 모든 과정(정규 표현식 → NFA → DFA)이 자동화될 수 있기 때문에, 실제로 렉서를 만드는 사람은 정규 표현식만 적으면 되고 나머지는 렉서 생성기(Lex, Flex 등)가 대신합니다.

다음 편에서는 이렇게 만들어진 토큰 나열을 받아, "이 토큰들이 문법적으로 올바른 프로그램을 이루는가"를 판단하고 그 구조를 트리로 세우는 **구문 분석(하향식 파싱)**을 다룹니다.
