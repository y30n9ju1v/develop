[지난 글](../apache-arrow-internals/)에서는 Arrow가 컬럼 레이아웃과 SIMD, 비트맵 Null 처리, 그리고 **Zero-Copy 공유 메모리**로 같은 머신 안에서 얼마나 빠른지 살펴봤습니다. 그런데 만약 C++ 프로세스와 Python 프로세스가 아니라, **서로 다른 PC**에 있다면 어떨까요? 공유 메모리는 한 머신을 벗어나는 순간 쓸 수 없습니다. 결국 네트워크로 데이터를 보내야 하는데, 이때 다시 예전의 문제가 등장합니다 — 직렬화/역직렬화 비용. **Arrow Flight**는 이 문제를 gRPC 위에서 풀기 위해 만들어진 프레임워크입니다.

---

## 1. 문제: 네트워크를 건너는 순간 Zero-Copy가 깨진다

전통적으로 서로 다른 머신 간에 데이터프레임을 주고받으려면 이런 경로를 거칩니다.

```
머신 A의 데이터 → JSON/CSV/Protobuf 직렬화 → 네트워크 전송 → 역직렬화 → 머신 B의 객체
```

DB 커넥터라면 ODBC/JDBC를 통해 **행(Row) 단위**로 한 줄씩 가져오고, REST API라면 JSON으로 감싸서 보냅니다. 두 방식 모두 다음 비용을 피할 수 없습니다.

* **행 단위 변환 비용**: 컬럼 지향으로 저장된 데이터를 행 단위 포맷으로 바꿨다가, 받는 쪽에서 다시 컬럼으로 재구성.
* **직렬화/역직렬화(Serde) 비용**: JSON은 숫자를 문자열로 풀어 쓰고 파싱해야 하고, Protobuf도 자체 스키마로 한 번 더 인코딩/디코딩해야 합니다.
* **메타데이터 재협상**: 매 요청마다 컬럼 이름과 타입을 다시 확인하거나 별도로 관리해야 합니다.

수백만 행짜리 데이터셋이라면 이 변환 비용이 실제 네트워크 전송 시간보다 커지는 경우도 흔합니다. Arrow Flight는 "애초에 Arrow 포맷 그대로, 네트워크에서도 컬럼 단위로 흐르게 하자"는 아이디어에서 출발합니다.

## 2. Arrow Flight의 핵심 아이디어: gRPC + Arrow IPC

Arrow Flight는 두 가지를 결합합니다.

1. **gRPC**: HTTP/2 기반의 고성능 RPC 프레임워크. 스트리밍, 멀티플렉싱, 언어 무관(다양한 언어에서 클라이언트/서버 생성 가능)을 기본 제공합니다.
2. **Arrow IPC 포맷**: 메모리에 있는 RecordBatch를 그대로 바이트로 옮겨 적은 표준 스트리밍 포맷.

여기서 중요한 설계 결정은, **gRPC/Protobuf는 메타데이터(스키마, 티켓, 위치 정보)를 감싸는 봉투 역할만 하고, 실제 대용량 데이터 본문은 Arrow IPC 포맷 그대로 얹는다**는 점입니다.

```
[gRPC 프레임]
  ┌─────────────────────────────┐
  │ Protobuf 메타데이터 (얇음)    │  ← 스키마, 티켓 등
  ├─────────────────────────────┤
  │ Arrow IPC RecordBatch (두꺼움)│  ← 실제 컬럼 데이터, 변환 없이 그대로
  └─────────────────────────────┘
```

받는 쪽은 이 바이트를 파싱해서 새 객체로 재조립하는 게 아니라, Arrow 버퍼 위에 **그대로 매핑**합니다. 로컬 Zero-Copy와 완전히 동일하지는 않지만(네트워크 전송 자체는 피할 수 없으니), 그 앞뒤에 붙던 **행↔컬럼 변환**과 **포맷 재해석 비용**을 제거한다는 점에서 "네트워크판 Zero-Copy"에 가장 가깝습니다.

## 3. gRPC가 밑바탕에서 해주는 일

Arrow Flight를 이해하려면 먼저 gRPC가 HTTP/2 위에서 무엇을 해결하는지 짚을 필요가 있습니다. Flight가 REST가 아니라 굳이 gRPC를 고른 이유이기도 합니다.

* **스트림 멀티플렉싱**: HTTP/1.1은 커넥션 하나당 요청 하나만 처리하고 응답을 기다려야 합니다(Head-of-Line Blocking). HTTP/2는 하나의 TCP 커넥션 위에 여러 스트림을 동시에 열어, 커넥션을 새로 맺는 비용 없이 여러 `DoGet`/`DoPut` 요청을 병렬로 흘려보낼 수 있습니다.
* **양방향 스트리밍**: gRPC는 단순 요청-응답뿐 아니라 클라이언트 스트리밍, 서버 스트리밍, 양방향 스트리밍을 프로토콜 차원에서 지원합니다. Flight의 `DoExchange`가 "요청을 보내면서 동시에 결과를 실시간으로 받는" 구조를 가질 수 있는 것도 이 덕분입니다. 예를 들어 센서 원본을 계속 올리면서, 서버가 처리한 요약 통계를 그 자리에서 받아오는 식의 파이프라인이 하나의 RPC로 표현됩니다.
* **흐름 제어(Flow Control)**: HTTP/2 스트림에는 윈도우 기반 흐름 제어가 내장되어 있어, 수신 측이 처리 속도를 못 따라가면 송신 측이 자동으로 속도를 늦춥니다. 대용량 RecordBatch를 무작정 쏟아부어 수신 측 메모리를 터뜨리는 상황을 프로토콜 레벨에서 막아줍니다.
* **연결 재사용과 헤더 압축(HPACK)**: 매 요청마다 TLS 핸드셰이크와 헤더를 새로 주고받지 않아, 짧은 요청이 반복되는 워크로드에서도 오버헤드가 누적되지 않습니다.

즉 Arrow Flight는 "빠른 직렬화 포맷(Arrow IPC)"과 "빠른 전송 계층(gRPC/HTTP2)"을 각자의 강점 그대로 결합한 조합입니다. 어느 한쪽만 있었다면 반쪽짜리 최적화에 그쳤을 것입니다 — Arrow IPC만 있고 전송 계층이 HTTP/1.1이었다면 스트리밍 병렬성을 못 살렸을 것이고, gRPC만 있고 페이로드가 Protobuf였다면 컬럼 데이터를 다시 행 단위 메시지로 욱여넣어야 했을 것입니다.

## 4. Arrow IPC 스트리밍 포맷: "직렬화 없는 직렬화"

Arrow Flight가 데이터를 감싸는 방식을 좀 더 들여다보면, 왜 이게 일반적인 직렬화와 다른지 이해할 수 있습니다. Arrow IPC 스트리밍 포맷은 두 종류의 메시지를 순서대로 주고받습니다.

```
[Schema 메시지]                ← 컬럼 이름, 타입, 순서를 한 번만 전달
[RecordBatch 메시지 1] (메타데이터 + Body)
[RecordBatch 메시지 2] (메타데이터 + Body)
...
[End-of-Stream 마커]
```

각 메시지의 **메타데이터**(어떤 버퍼가 몇 바이트인지, Null 비트맵 위치 등)는 FlatBuffers로 인코딩됩니다. FlatBuffers를 고른 이유가 중요한데, Protobuf나 JSON과 달리 **파싱 과정 자체가 없습니다**. 수신한 바이트 배열 위에 포인터를 얹기만 하면 필드에 바로 접근할 수 있어, "역직렬화"라는 단계가 사실상 생략됩니다.

그리고 **Body**(실제 컬럼 값이 담긴 버퍼들)는 메모리에 있던 레이아웃 그대로, 별도 인코딩 없이 바이트로 복사됩니다. 즉 로컬에서 Zero-Copy 공유 메모리에 쓰던 것과 **동일한 비트 패턴**이 네트워크 위를 그대로 흘러갑니다. 받는 쪽은 이 Body 바이트를 다시 파싱해 언어별 객체(Python list, Java 배열 등)로 바꾸는 게 아니라, Arrow 버퍼로 바로 매핑해 사용합니다.

정리하면 Arrow Flight가 없애는 것은 "네트워크 전송" 자체가 아니라, 그 전후에 있던 **표현 변환(representation conversion)**입니다.

```
일반적인 방식:  메모리 레이아웃 → (변환) → 직렬화 포맷 → 전송 → (역변환) → 메모리 레이아웃
Arrow Flight:   메모리 레이아웃 == 전송 포맷 → 전송 → 메모리 레이아웃 (그대로)
```

이 지점이 "네트워크판 Zero-Copy"라고 부르는 근거이자, 동시에 한계이기도 합니다. TCP/IP 스택을 거치는 이상 커널 버퍼로의 물리적 복사 자체는 피할 수 없습니다. Arrow Flight가 없애는 것은 **CPU가 데이터를 이해하고 다시 쓰는 비용**이지, 데이터가 회선을 타고 이동하는 물리적 비용이 아닙니다.

## 5. 동작 구조: FlightServer와 다섯 가지 액션

Arrow Flight는 클라이언트가 서버에 요청할 수 있는 동작을 다섯 가지 RPC로 정의합니다.

| RPC | 역할 |
|-----|------|
| `GetFlightInfo` | "이 쿼리/데이터셋을 어디서 가져올 수 있나?" 위치와 스키마를 조회 |
| `DoGet` | 서버 → 클라이언트로 RecordBatch 스트림을 **다운로드** |
| `DoPut` | 클라이언트 → 서버로 RecordBatch 스트림을 **업로드** |
| `DoExchange` | 양방향으로 동시에 스트림을 주고받기 (요청하며 결과를 실시간으로 받는 구조) |
| `DoAction` / `ListActions` | 임의의 커스텀 명령 실행 (예: 캐시 무효화, 작업 트리거) |

실제 흐름은 이렇습니다.

```
1. Client → Server : GetFlightInfo("SELECT * FROM sensor_log")
2. Server → Client  : FlightInfo { schema, endpoint 목록, Ticket }
3. Client → Server  : DoGet(Ticket)      ← 실제 데이터가 필요한 시점에만 요청
4. Server → Client  : RecordBatch 스트림 (Arrow IPC, gRPC 스트리밍)
```

`GetFlightInfo`가 스키마와 **Ticket**(데이터의 위치를 가리키는 불투명한 토큰)만 먼저 돌려주고, 실제 데이터는 `DoGet`에서 스트리밍한다는 점이 핵심입니다. 이 덕분에 하나의 논리적 데이터셋을 여러 `endpoint`(여러 서버 노드)로 쪼개 병렬로 가져오는 구성도 자연스럽게 표현됩니다 — 분산 저장된 데이터를 여러 노드에서 동시에 스트리밍받는 형태입니다.

## 6. 왜 REST+JSON이나 JDBC보다 빠른가

세 가지가 겹쳐서 효과를 냅니다.

* **컬럼 포맷 유지**: DB에서 컬럼 단위로 저장된 데이터를 행 단위 프로토콜(JDBC row cursor)로 바꿨다가 다시 컬럼으로 합치는 왕복이 없습니다. Arrow RecordBatch는 처음부터 끝까지 컬럼입니다.
* **스트리밍**: gRPC는 HTTP/2 스트림 위에서 동작하므로, 전체 데이터를 다 만들 때까지 기다리지 않고 준비되는 대로 청크(RecordBatch) 단위로 흘려보냅니다. 클라이언트는 첫 배치가 오면 바로 처리를 시작할 수 있습니다.
* **압축과 병렬성**: RecordBatch 단위 압축(LZ4, Zstd)과, 여러 `DoGet` 스트림을 동시에 여는 병렬 다운로드를 프로토콜 차원에서 지원합니다.

Dremio 등에서 공개한 벤치마크에서 Arrow Flight가 동일 데이터 전송에서 ODBC/JDBC 대비 수배~수십 배 처리량을 보인 사례가 보고된 것도 이 조합 덕분입니다. 병목이 "네트워크 대역폭"이 아니라 "직렬화 CPU 시간"이었던 워크로드일수록 효과가 큽니다.

## 7. 최소 예제로 감 잡기 (Python, pyarrow.flight)

서버는 요청받은 Ticket에 대해 RecordBatch 스트림을 돌려주기만 하면 됩니다.

```python
import pyarrow as pa
import pyarrow.flight as flight

class SensorFlightServer(flight.FlightServerBase):
    def do_get(self, context, ticket):
        table = pa.table({"timestamp": [1, 2, 3], "speed": [10.2, 11.5, 9.8]})
        return flight.RecordBatchStream(table)

server = SensorFlightServer("grpc://0.0.0.0:8815")
server.serve()
```

클라이언트는 서버 스키마를 몰라도, 연결만 하면 그대로 Arrow Table로 받습니다.

```python
import pyarrow.flight as flight

client = flight.FlightClient("grpc://192.168.0.10:8815")
reader = client.do_get(flight.Ticket(b"sensor_log"))
table = reader.read_all()   # pyarrow.Table, 변환 없이 바로 사용 가능
```

이기종 환경이라는 점은 여기서 잘 드러납니다. 서버가 Rust나 C++로 짜여 있어도, 클라이언트는 Python이든 Java든 상관없이 **같은 Arrow 스키마**를 그대로 받습니다. 언어 경계를 넘을 때 겪던 "타입을 문자열로 풀었다가 다시 파싱하는" 과정 자체가 없습니다.

## 8. 이기종 PC 간 전송에서 실질적으로 얻는 것

* **OS/언어 무관**: gRPC와 Protobuf 스키마 정의(IDL)를 쓰므로, Windows의 C++ 프로세스와 Linux의 Python 프로세스가 프로토콜 걱정 없이 통신합니다.
* **스키마가 데이터와 함께 이동**: 컬럼 이름·타입이 매 전송마다 함께 전달되므로, 수신 측에서 별도 스키마 관리 없이 즉시 Arrow Table로 활용 가능합니다.
* **대용량 스트리밍에 적합**: 센서 로그, LiDAR 포인트 클라우드처럼 큰 배치를 다루는 워크로드에서, 전체를 메모리에 모았다가 보내는 대신 RecordBatch 단위로 흘려보낼 수 있습니다.
* **인증/암호화**: gRPC의 TLS, 인터셉터 기반 인증(mTLS, 토큰 등)을 그대로 활용할 수 있어, 별도의 보안 계층을 새로 설계할 필요가 없습니다.

이 조합이 실제로 빛을 발하는 지점은, 자율주행 데이터 파이프라인에서 흔히 마주치는 구성입니다. 차량 내부의 로깅 유닛(임베디드 Linux, C++로 기록)에서 나온 센서 로그를, 사무실의 분석 워크스테이션(Python/Jupyter)이나 클러스터의 학습 노드(다른 OS, 다른 계정 체계)로 옮겨야 하는 상황을 생각해 보면, 세 주체가 이미 서로 다른 언어와 환경으로 짜여 있습니다. Arrow Flight는 이 경계마다 "우리끼리 통하는 포맷으로 다시 짠다"는 특수 처리를 반복하는 대신, 하나의 표준 스키마·프로토콜로 전 구간을 관통시킵니다.

## 9. 한계와 트레이드오프

Arrow Flight가 모든 상황에서 정답은 아닙니다. 이론적으로 짚어볼 만한 한계도 분명합니다.

* **압축은 여전히 CPU를 씁니다.** 네트워크 대역폭이 병목인 환경에서는 LZ4/Zstd 압축을 켜야 하는데, 이 경우 "직렬화 비용은 없앴지만 압축 비용은 남는다"는 트레이드오프가 생깁니다. 반대로 대역폭이 넉넉하고 CPU가 귀한 환경(예: 차량 내 임베디드 보드)이라면 압축을 끄고 순수 스트리밍 이점만 취하는 편이 나을 수 있습니다.
* **스키마 진화(Schema Evolution) 문제.** 컬럼이 추가/삭제되거나 타입이 바뀌면, 송신·수신 양쪽이 같은 버전의 스키마를 공유해야 합니다. JSON처럼 느슨하게 필드를 무시하고 넘어가는 방식에 비해, 스키마 불일치에 더 엄격하게 반응합니다. 장기간 운영되는 이기종 시스템이라면 스키마 버저닝 전략이 별도로 필요합니다.
* **작은 요청·응답에는 과한 프레임워크일 수 있습니다.** 레코드 몇 개짜리 조회처럼 페이로드가 작은 워크로드에서는, RecordBatch 헤더(FlatBuffers 메타데이터)와 gRPC 프레이밍 자체의 고정 오버헤드가 상대적으로 커 보일 수 있습니다. Arrow Flight의 이점은 데이터가 커질수록, 그리고 반복적으로 스트리밍될수록 뚜렷해집니다.
* **"Zero-Copy"라는 표현의 함정.** 앞서 언급했듯 네트워크 구간의 물리적 복사(NIC → 커널 버퍼 → 애플리케이션 버퍼)는 사라지지 않습니다. Arrow Flight가 없애는 것은 그 위에 얹혀 있던 **의미론적 변환 비용**이지, 바이트가 회선을 타고 이동하는 비용 자체가 아닙니다. 이 구분을 명확히 하지 않으면 "Zero-Copy니까 공짜"라는 오해로 이어지기 쉽습니다.

이런 한계들은 대체로 "데이터가 크고, 자주 오가고, 컬럼 구조가 명확한" 워크로드일수록 옅어지고, 반대의 조건일수록 두드러집니다. 즉 Arrow Flight는 만능 전송 계층이 아니라, **대용량 컬럼 데이터를 반복적으로 주고받는 상황에 맞춰 설계된 특화 도구**로 이해하는 편이 정확합니다.

## 10. Flight SQL: 데이터베이스 프로토콜로의 확장

Arrow Flight 위에는 **Flight SQL**이라는 한 단계 더 특화된 프로토콜이 있습니다. 앞서 다룬 다섯 가지 액션이 "임의의 데이터셋 전송"을 위한 범용 뼈대였다면, Flight SQL은 여기에 SQL 실행에 필요한 표준 동작(쿼리 실행, 프리페어드 스테이트먼트, 카탈로그·스키마 조회, 트랜잭션)을 얹은 스펙입니다.

기존에는 데이터베이스마다 JDBC/ODBC 드라이버를 따로 구현해야 했고, 그 드라이버들은 대부분 행 단위 커서를 전제로 설계되어 있었습니다. Flight SQL은 "쿼리 결과를 Arrow 컬럼 스트림으로 돌려준다"는 하나의 인터페이스를 표준화해, Dremio·InfluxDB·DuckDB 등 여러 분석 엔진이 같은 클라이언트 라이브러리로 접근할 수 있게 합니다. 이는 Arrow Flight의 설계가 단순한 "빠른 파일 전송"을 넘어, **분석 워크로드를 위한 차세대 DB 프로토콜**을 지향하고 있다는 점을 보여줍니다.

## 정리

| 방식 | 데이터 흐름 | 변환 비용 |
|------|------------|-----------|
| REST + JSON | 컬럼 → 텍스트 직렬화 → 파싱 → 컬럼 | 높음 (타입 변환·문자열 파싱) |
| JDBC/ODBC | 컬럼 → 행 단위 커서 → 컬럼 | 중간 (행↔컬럼 왕복) |
| **Arrow Flight** | 컬럼(Arrow IPC) → gRPC 스트림 → 컬럼(Arrow IPC) | 낮음 (포맷 변환 없음) |

Arrow Flight는 로컬 Zero-Copy의 "포인터만 넘긴다"는 개념을 네트워크 세계로 그대로 옮기지는 못하지만, **그 앞뒤에 있던 직렬화·행렬 변환 비용을 없앤다**는 점에서 같은 철학을 이어받습니다. 같은 머신 안에서는 공유 메모리로, 머신 경계를 넘을 때는 Arrow Flight로 — Arrow 생태계가 "Zero-Copy를 어디까지 확장할 수 있는가"에 대한 하나의 완결된 답을 제공하는 셈입니다.
