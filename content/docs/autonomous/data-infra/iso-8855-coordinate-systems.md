> Ego/World/Sensor 좌표계 개념과 변환의 기초 직관은 [자율주행 좌표계 입문](/docs/autonomous/sensor/ego-coordinate-system-for-beginners/)을 먼저 읽으세요. 이 글은 규약 비교(ISO 8855 vs SAE J670 vs CARLA vs ROS)와 파이프라인 경계에서의 실무 변환에 집중합니다.

> 이 글은 [py123d 입문](../py123d-for-beginners/)과 연결됩니다. py123d가 ISO 8855를 왜 표준 좌표계로 채택했는지, CARLA 연동 시 왜 Y축 부호를 뒤집어야 하는지를 이해하는 데 필요한 배경입니다.

자율주행 파이프라인에서 좌표계 불일치는 **소리 없이 스며드는 버그**입니다. 코드가 실행되고 수치도 나오는데 바운딩 박스가 좌우 반전되거나, 회전 방향이 반대로 계획되거나, 시뮬레이터에서 잘 되던 것이 실 차량에서 틀려집니다. 원인은 대부분 좌표계 규약이 달라서입니다.

## 1. 좌표계가 왜 이렇게 많은가

자율주행에는 적어도 네 종류의 좌표계가 동시에 등장합니다.

**차량 좌표계(Vehicle Frame)**: 차량 자체를 기준으로 합니다. 앞이 어디고 왼쪽이 어디인지를 정의합니다.

**센서 좌표계(Sensor Frame)**: 카메라, LiDAR, IMU 각각이 자기 중심을 원점으로 합니다. 카메라와 LiDAR는 차량에 같이 달려있어도 서로 다른 좌표계를 씁니다.

**글로벌 좌표계(Global Frame)**: UTM, WGS84 같은 지도 기반 좌표입니다. 차량이 어디 있는지 전세계 맥락에서 표현합니다.

**시뮬레이터 좌표계**: CARLA(Unreal Engine), LGSVL 등 시뮬레이터마다 자기 규약이 있습니다.

이 네 종류가 데이터셋마다, 툴마다 서로 다른 규약을 씁니다. 데이터가 파이프라인을 지나며 좌표계 경계를 넘을 때마다 변환이 필요합니다. 규약을 명확히 알지 못하면 변환 코드에 부호 하나가 잘못 들어가고, 그 버그는 박스가 반대 방향에 그려지거나 계획 모듈이 왼쪽으로 가야 할 때 오른쪽으로 조향할 때가 되어서야 드러납니다.

## 2. ISO 8855 — 차량 좌표계의 국제 표준

**ISO 8855:2011 "Road vehicles — Vehicle dynamics and road-holding ability — Vocabulary"**는 차량 역학에서 쓰는 좌표계와 용어를 정의하는 국제 표준입니다.

### 세 축의 정의

```
        Z (위)
        │
        │
        │_______ Y (좌)
       /
      /
     X (전방)
```

| 축 | 방향 | 의미 |
|----|------|------|
| **X** | 차량 전방 (앞) | 종방향(Longitudinal) |
| **Y** | 차량 좌측 (왼쪽) | 횡방향(Lateral) |
| **Z** | 위 | 수직(Vertical) |

**오른손 법칙**을 따릅니다. 오른손 엄지를 Z(위)로 향하면 손가락이 감기는 방향이 양의 회전 방향(반시계)입니다.

### 원점

ISO 8855는 원점 위치를 고정하지 않습니다. 실무에서는 세 가지가 쓰입니다.

- **CG(Center of Gravity)**: 차량 무게 중심. 차량 역학 시뮬레이션에서 주로 씁니다.
- **Rear Axle Center**: 후축 중심. NVIDIA NCore/NuRec가 이 위치를 원점(`rig` 프레임)으로 씁니다.
- **IMU 위치**: py123d가 기준으로 쓰는 원점. 관성 센서 측정값을 그대로 쓸 수 있어 자율주행 소프트웨어에 편리합니다.

원점이 다르면 같은 축 방향이어도 바운딩 박스의 절대 위치가 다릅니다. 원점 변환은 단순 평행이동(translation)이라 회전보다 처리가 쉽지만, 어느 원점인지 명시하지 않으면 좌표 값이 맞지 않는 원인이 됩니다.

### 회전 규약 (Yaw, Pitch, Roll)

| 회전 | 축 | 양의 방향 | 의미 |
|------|-----|---------|------|
| **Yaw** | Z축 회전 | 반시계 (위에서 볼 때) | 차량이 좌회전 = 양의 yaw |
| **Pitch** | Y축 회전 | 앞이 내려가는 방향 | 내리막 = 양의 pitch |
| **Roll** | X축 회전 | 우측이 내려가는 방향 | 우측 기울기 = 양의 roll |

Yaw가 양수일 때 차량이 왼쪽으로 돕니다. 직관적으로 느껴지지 않을 수 있는데, Y가 왼쪽이고 오른손 법칙으로 Z축을 기준으로 Y 방향으로 회전하면 왼쪽 회전이 됩니다.

## 3. 주요 좌표계 비교

### SAE J670 — 미국 자동차 공학 표준

| 축 | 방향 |
|----|------|
| X | 전방 |
| Y | **오른쪽** |
| Z | **아래** |

ISO 8855와 X축만 같고, Y와 Z 모두 반대입니다. Y=오른쪽, Z=아래이기 때문에 **오른손 법칙**을 그대로 유지합니다. Yaw가 양수이면 **시계 방향(우회전)**입니다 — ISO 8855와 정반대입니다.

미국 OEM과 협력하거나 미국산 AV 데이터셋을 쓸 때 이 차이가 나타납니다.

### CARLA / Unreal Engine 4

```
        Z (위)
        │
        │_______ Y (오른쪽)
       /
      /
     X (전방)
```

| 축 | 방향 |
|----|------|
| X | 전방 |
| Y | **오른쪽** |
| Z | 위 |

Z가 위로 ISO 8855와 같지만 Y가 오른쪽입니다. 그런데 UE4는 **왼손 좌표계**입니다. 같은 X·Y·Z 방향이어도 회전 규약이 반대입니다. Yaw 양수가 시계 방향 회전입니다.

py123d → CARLA 변환 시 Y 부호 반전(`y_carla = -y_iso`) + 회전 부호 반전이 필요합니다. CARLA 공식 문서도 "좌표계 변환을 주의하라"고 반복해서 경고합니다.

### ROS REP 103

ROS 표준(REP 103)은 로봇 바디 프레임(`base_link`)을 ISO 8855와 동일하게 정의합니다.

| 축 | 방향 |
|----|------|
| X | 전방 |
| Y | 왼쪽 |
| Z | 위 |

자율주행에서 ROS2 기반 스택을 쓴다면 차량 좌표계는 ISO 8855와 일치합니다. 다만 카메라 프레임(`camera_link`)은 REP 103에서 X=오른쪽, Y=아래, Z=전방으로 별도 정의합니다 — OpenCV 컨벤션과 동일합니다.

### OpenCV 카메라 컨벤션

카메라 영상 처리에서 쓰는 좌표계입니다.

| 축 | 방향 |
|----|------|
| X | 이미지 오른쪽 |
| Y | 이미지 아래 |
| Z | 카메라 전방 (광축) |

이미지 픽셀 좌표(u, v)와 일치하도록 Y가 아래를 향합니다. 차량 좌표계에서 카메라 좌표계로 변환할 때 이 변환이 필요합니다. py123d도 카메라 데이터에는 ISO 8855(차량 프레임)와 별도로 OpenCV 컨벤션을 씁니다.

## 4. 한눈에 보는 비교표

| 규약 | X | Y | Z | 손 | Yaw 양수 |
|------|---|---|---|----|---------|
| **ISO 8855** | 전방 | 왼쪽 | 위 | 오른손 | 좌회전 (반시계) |

| **OpenCV 카메라** | 오른쪽 | 아래 | 전방 | 오른손 | — |

## 5. 실무 변환: 부호 하나의 차이

### CARLA → ISO 8855 (py123d)

CARLA와 py123d 사이의 차이는 두 가지입니다.

**Y축 부호**: CARLA Y=오른쪽, ISO 8855 Y=왼쪽. 모든 Y 좌표를 부호 반전합니다.

**Yaw 부호**: CARLA는 왼손계로 시계 방향이 양수, ISO 8855는 반시계 방향이 양수. Yaw 각도를 부호 반전합니다.

```
포인트 클라우드 변환:
  x_iso = x_carla
  y_iso = -y_carla     ← Y 부호 반전
  z_iso = z_carla

바운딩 박스 방위각:
  yaw_iso = -yaw_carla  ← Yaw 부호 반전
```

이 두 변환을 하지 않으면 LiDAR 포인트 클라우드가 좌우 대칭으로 반전되어 나타나고, 바운딩 박스가 물체의 반대쪽을 가리킵니다.

### nuScenes → ISO 8855

nuScenes는 글로벌 좌표계(지도 기반)를 씁니다. 이고 포즈가 차량의 글로벌 위치와 방위를 정의하며, 물체 좌표도 글로벌 프레임으로 주어집니다. 차량 프레임으로 변환하려면 이고 포즈의 역변환을 적용합니다.

nuScenes 내부 차량 프레임은 사실상 ISO 8855와 같은 방향입니다(X=전방, Y=왼쪽, Z=위). 그래서 py123d 파서는 nuScenes 데이터에 축 방향 변환 없이 이고 포즈 역변환만 적용합니다.

### Waymo → ISO 8855

Waymo는 차량 프레임이 X=전방, Y=왼쪽, Z=위로 ISO 8855와 동일합니다. 다만 LiDAR 스윕 타임스탬프가 스윕 시작 시각 기준이고, 포즈는 스윕 중간(~50ms) 시각 기준입니다. 좌표축 방향은 동일하지만 이 타임스탬프 오프셋을 보정하지 않으면 박스와 포인트가 시간상 엇갈립니다.

## 6. 왜 py123d는 ISO 8855를 선택했나

py123d가 ISO 8855를 표준 좌표계로 선택한 이유는 세 가지입니다.

**국제 표준**: ISO 8855는 차량 역학 분야의 공식 국제 표준입니다. SAE J670은 미국 중심이고, 특정 시뮬레이터 좌표계는 소프트웨어 관습입니다. 표준에 기반한 좌표계는 데이터셋 간 이식성이 가장 높습니다.

**오른손 법칙 + 직관적 부호**: Y=왼쪽, Z=위이므로 Yaw 양수가 좌회전입니다. 차량이 왼쪽으로 도는 것이 양수 조향이라는 것은 대부분의 제어 이론과 직관적으로 일치합니다.

**ROS2와 호환**: ROS REP 103의 base_link와 동일해서, ROS2 기반 스택과 py123d 데이터를 연결할 때 차량 프레임 레벨에서 별도 변환이 없습니다.

## 7. 정리

좌표계 문제는 "한번 정하면 끝"이 아닙니다. 데이터셋, 시뮬레이터, 시각화 툴, 실 차량 하드웨어가 파이프라인 안에 섞이면 각 경계마다 변환이 필요합니다. 중요한 것은 **각 단계에서 어느 좌표계를 쓰는지 명시하고, 변환이 일어나는 경계를 한 곳에 집중**하는 것입니다.

py123d가 하는 일이 정확히 그것입니다. nuScenes·Waymo·CARLA·사내 데이터가 어떤 좌표계를 쓰든, 파서가 그 경계에서 ISO 8855로 변환합니다. 이후 파이프라인 — DORA 노드, evaluator, Rerun 시각화, NuRec 변환 — 은 ISO 8855만 알면 됩니다.

| 파이프라인 위치 | 좌표계 | 변환 지점 |
|--------------|--------|---------|
| 원본 데이터셋 | 각각 상이 | ↓ py123d 파서 |
| py123d / DORA 파이프라인 | **ISO 8855** | — |
| CARLA 브리지 | ↕ ISO 8855 ↔ UE4 | carla-bridge 노드 경계 |
| OpenCV 처리 (카메라) | OpenCV 컨벤션 | 카메라 캘리브레이션 행렬 |
| NCore / NuRec | rig (후축) 기준 ISO 8855 | NCore Writer 변환 레이어 |
