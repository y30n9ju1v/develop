빅데이터 처리나 데이터 엔지니어링을 공부하다 보면 한 번쯤 **Apache Arrow**라는 이름을 듣게 됩니다. "대용량 데이터 처리를 혁신적으로 빠르게 만들어 준다"고 하는데, 도대체 메모리 단에서 어떤 마법을 부리길래 빠른 걸까요? 핵심 아키텍처 4가지를 정리해 봤습니다.

---

## 1. CPU가 가장 좋아하는 컬럼 기반 메모리 레이아웃

전통적인 데이터베이스는 **행(Row) 단위**로 데이터를 저장합니다.

```
[이름1, 나이1, 직업1], [이름2, 나이2, 직업2], [이름3, 나이3, 직업3] ...
```

100만 명의 나이 평균을 구하고 싶다면? 나이 데이터만 필요한데, 이름과 직업까지 메모리에서 읽어오며 건너뛰어야 합니다. 불필요한 데이터가 CPU 캐시를 오염시킵니다.

Arrow는 **열(Column) 단위**로 같은 타입의 데이터를 연속으로 배열합니다.

```
[이름1, 이름2, 이름3, ...]
[나이1, 나이2, 나이3, ...]   ← 여기만 읽으면 됨
[직업1, 직업2, 직업3, ...]
```

나이 열만 쭉 읽으면 됩니다. 이게 왜 빠를까요?

CPU가 메모리에서 데이터를 읽을 때는 필요한 바이트 하나만 가져오는 게 아닙니다. 그 주변 64바이트(캐시 라인)를 통째로 캐시에 올립니다. 컬럼이 연속 메모리에 있으면 한 번의 캐시 라인 적재로 많은 값을 처리할 수 있지만, 행 기반이면 이름·나이·직업이 섞인 64바이트가 올라오므로 실제로 쓰이는 나이 데이터는 극히 일부입니다. 같은 캐시를 써도 훨씬 적은 양의 데이터를 처리하게 되는 셈입니다. Arrow의 컬럼 레이아웃은 이 **CPU 캐시 적중률(Cache Locality)을 극대화**합니다.

---

## 2. 하드웨어의 한계를 쓰는 SIMD 연산

현대 CPU는 한 번의 명령어로 여러 데이터를 동시에 처리하는 **SIMD(Single Instruction, Multiple Data)** 기능을 가지고 있습니다.

```
일반 루프:   a[0]+b[0], a[1]+b[1], a[2]+b[2], a[3]+b[3]  → 4번의 명령
SIMD:       [a[0], a[1], a[2], a[3]] + [b[0], b[1], b[2], b[3]]  → 1번의 명령
```

AVX-512 기준으로 한 번에 정수 16개(64바이트)를 동시에 연산합니다.

단, SIMD를 쓰려면 데이터가 메모리에 **연속적으로** 나열되어 있어야 합니다. 행 기반처럼 타입이 다른 데이터가 섞여 파편화되어 있으면 이 기능을 쓸 수 없습니다. Arrow는 컬럼 기반 레이아웃 덕분에 같은 타입 데이터가 빽빽이 나열되어 있어 SIMD를 바로 투입할 수 있습니다. 덕분에 루프를 돌며 하나씩 처리하는 대신 **한 번의 CPU 사이클로 수많은 데이터를 동시에 연산**할 수 있습니다.

## 3. 조건문(if)을 지워버리는 Null 값 처리

"어차피 Null인지 아닌지 0과 1로 비교하는 거라면, 일반적인 if문이랑 속도가 똑같지 않나요?" 라는 의문이 들 수 있습니다. 하지만 Arrow는 조건문 자체를 없애거나 CPU가 가장 좋아하는 방식으로 처리합니다.

### 전통적인 방법의 문제

각 값 옆에 Null 여부 플래그를 붙이면, 데이터를 처리할 때마다 `if isNull` 분기가 발생합니다.

```
[값1, isNull=false], [값2, isNull=true], [값3, isNull=false] ...
```

현대 CPU는 파이프라인 방식으로 동작합니다. 분기 명령(if)을 만나면 결과가 나오기 전에 다음 명령을 미리 실행합니다(분기 예측). 예측이 맞으면 빠르지만, 틀리면 이미 실행한 명령을 버리고 다시 시작해야 합니다. Null이 무작위로 섞인 100만 개 데이터라면 예측 실패가 빈번하게 일어나 성능이 크게 떨어집니다.

### Arrow의 방법: 비트맵과 쓰레기 값의 콜라보

Arrow는 값 배열과 Null 여부를 완전히 분리합니다.

```
값 배열:  [값1,  0, 값3,  0, 값5, ...]   ← Null 자리엔 쓰레기 값(0)을 채움
비트맵:   [  1,  0,   1,  0,   1, ...]   ← 1=유효, 0=Null
```

Null 자리에 0 같은 무해한 값을 채워두어 **하드웨어가 에러 없이 그냥 계산**합니다. `Null + 10`은 실제로 `0 + 10 = 10`으로 계산되고, 나중에 비트맵으로 걸러냅니다. 그리고 이 걸러내는 과정도 앞서 살펴본 **SIMD 마스킹** 기능을 통해 "비트맵이 0인 자리는 결과에 포함하지 마라"라는 단 하나의 벡터 명령으로 끝납니다. 반복되는 `if isNull` 대신 비트 연산 한 방으로, if 없이 고속도로를 달리는 구조입니다.

## 4. 데이터 이동 비용을 제로로 만드는 Zero-Copy 공유

기존 방식에서는 서로 다른 프로세스나 언어(예: C++ 백엔드 → Python Pandas) 간에 데이터를 주고받으려면 아래 과정이 필요했습니다.

```
C++ 데이터 → 직렬화(JSON/Protobuf 등) → 전송 → 역직렬화 → Python 객체
```

직렬화/역직렬화는 CPU를 많이 씁니다. 데이터가 클수록 복사 시간도 선형으로 늘어납니다.

Arrow는 처음부터 데이터를 **OS 레벨의 공유 메모리(Shared Memory)**에 Arrow 표준 포맷으로 생성합니다.

```
공유 메모리: [Arrow 포맷 데이터]
                ↑                  ↑
          C++ 프로세스        Python 프로세스
         (포인터만 보유)      (포인터만 보유)
```

다른 언어/프로세스에 데이터를 넘길 때는 실제 데이터를 복사하는 게 아니라, "공유 메모리 몇 번지에 데이터가 있으니 읽어라"하고 **포인터(주소)만** 전달합니다.

모든 언어(Rust, Python, C++, Java, Go 등)가 동일한 Arrow 메모리 포맷 표준을 구현하고 있으므로, 변환도 복사도 없는 진정한 **Zero-Copy**가 실현됩니다. [DORA 아키텍처](../dora/dora-rs-architecture/)에서 4KiB 이상 메시지에 공유 메모리를 쓰는 것도 같은 원리입니다. Rust로 만든 Daemon이 공유 메모리에 Arrow 포맷으로 데이터를 쓰면, Python 노드가 복사 없이 같은 메모리를 그대로 읽습니다.

## 정리

| 기법 | 해결하는 문제 | 핵심 원리 |
|------|--------------|-----------|
| **컬럼 기반 레이아웃** | 불필요한 데이터 읽기 | CPU 캐시 적중률 극대화 |
| **SIMD 벡터 연산** | 데이터 하나씩 처리 | 연속 메모리 덕분에 병렬 연산 가능 |
| **비트맵 Null 처리** | 조건 분기 실패 | 쓰레기 값으로 채우고 SIMD 마스크로 필터링 |
| **Zero-Copy 공유** | 직렬화/복사 비용 | 공유 메모리 + 포인터 전달 |

네 가지가 각각 독립적으로도 효과적이지만, **서로를 강화**합니다. 컬럼 레이아웃이 있어야 SIMD가 가능하고, 비트맵 Null 처리가 있어야 SIMD 마스킹이 가능합니다. Zero-Copy는 이 표준 포맷을 언어 경계를 넘어 그대로 공유합니다. 이 조합이 Arrow를 단순한 데이터 포맷이 아닌 **고성능 데이터 처리 인프라**로 만드는 이유입니다.

다음 글에서는 이 Arrow를 내부 포맷으로 쓰는 **[py123d](../py123d-for-beginners/)**를 통해, 파편화된 자율주행 데이터셋을 단 하나의 API로 다루는 방법을 살펴봅니다.
