지난 두 글에서는 **[Apache Arrow가 왜 압도적으로 빠른지](../apache-arrow-internals/)** — 컬럼 기반 레이아웃, SIMD, Null 비트맵, Zero-Copy — 그 원리를, 그리고 **[py123d가 무엇인지](../py123d-for-beginners/)** — 9개 데이터셋을 Arrow 기반 공통 스키마로 통일하는 방법을 살펴봤습니다.

오늘은 이 두 가지를 바탕으로, **py123d를 FiftyOne, Rerun과 연결해 실제 데이터 파이프라인을 구축하는 방법**을 소개합니다.

---

## 1. 자율주행 데이터셋의 고질병: 파편화

자율주행 연구를 하다 보면 nuScenes, Waymo, Argoverse, 그리고 회사 내부의 자체 수집 데이터까지 수많은 데이터셋을 다루게 됩니다. 그런데 이 데이터셋들은 사이좋게 통일된 규격을 쓰지 않습니다.

- 데이터셋마다 **좌표계(Coordinate Convention)가 제각각**입니다. X축이 앞을 가리키는 곳도 있고, Y축이 앞인 곳도 있습니다.
- 카메라, 라이다(LiDAR), HD Map, 3D 바운딩 박스 라벨을 저장하는 **파일 포맷과 폴더 구조**가 완전히 다릅니다. nuScenes는 JSON 기반, Waymo는 Protobuf 기반입니다.
- 데이터셋 하나 파싱하려고 전용 파이썬 패키지를 설치하다 보면, 서로 다른 패키지의 의존성이 충돌해 개발 환경이 꼬이기 일쑤입니다.

결국 개발자는 데이터셋마다 별도의 파싱 코드를 작성하게 되고, 데이터셋을 바꿀 때마다 파이프라인을 새로 짭니다. 이 반복 작업이 자율주행 연구에서 가장 큰 낭비 중 하나입니다.

---

## 2. `py123d`: 데이터셋의 공통어

[py123d 입문 글](../py123d-for-beginners/)에서 다뤘듯이, `py123d`는 nuScenes·Waymo·AV2 등 파편화된 데이터셋을 Apache Arrow 기반 공통 스키마로 통일하고 단 하나의 API로 접근하게 해주는 라이브러리입니다. ISO 8855 좌표계 통일, 센서별 독립 타임스탬프 스트림, Zero-Copy 로딩이 핵심입니다.

이 글에서 주목하는 것은 그 다음 단계입니다. py123d를 **FiftyOne, Rerun과 유기적으로 연결**해 큐레이션과 시각화까지 Arrow 한 포맷으로 관통하는 파이프라인을 구성하는 방법입니다.

---

## 3. 모던 자율주행 데이터 파이프라인 3단계

단순히 데이터 포맷을 통일하는 것을 넘어, 최근 트렌드는 `py123d`를 중심으로 데이터 큐레이션과 시각화 레이어를 유기적으로 연결하는 것입니다.

```
원본 데이터 (nuScenes / Waymo / 사내 데이터)
         ↓
  [1단계] py123d — 표준화 & 통합
         ↓
  [2단계] FiftyOne — 데이터 큐레이션
         ↓
  [3단계] Rerun — 3D 시각화
```

### 1단계: 전처리 & 표준화 (`py123d`)

사내 센서 배치나 자체 라벨링 포맷이 어떻게 변경되든, `py123d` 레이어에서 공통 스키마로 묶어줍니다. 이 시점부터 사내 데이터셋은 글로벌 공개 데이터셋과 **완벽히 호환되는 표준 규격**을 갖추게 됩니다.

### 2단계: 데이터 큐레이션 (`FiftyOne`)

**FiftyOne**은 Voxel51이 만든 컴퓨터 비전 데이터 관리 툴입니다. 표준화된 `py123d` 스키마를 FiftyOne으로 로드하면, GUI 환경에서 복잡한 조건으로 데이터를 필터링하고 분석할 수 있습니다.

예를 들어 이런 슬라이싱이 가능합니다:

- "비 오는 날 야간에 촬영된 장면"
- "보행자가 3명 이상 감지되고 라이다 반사율이 낮은 프레임"
- "모델 추론 결과와 Ground Truth의 IoU가 0.5 미만인 케이스"

엣지 케이스를 직접 눈으로 보며 수집하는 데이터 큐레이션 작업이 GUI에서 이루어집니다. 코드 없이 클릭만으로 조건을 조합할 수 있어, 데이터 엔지니어와 ML 엔지니어가 함께 작업하기에 좋습니다.

여기서 한 가지 의문이 들 수 있습니다. **"FiftyOne이 이렇게 강력하다면 IR로 써도 되지 않나?"**

그렇지 않습니다. FiftyOne은 좋은 툴이지만 IR로 쓰기에는 근본적인 한계가 있습니다.

첫째, **설계 목적이 다릅니다.** FiftyOne은 이미지·비디오 중심의 컴퓨터 비전 워크플로우를 위해 만들어진 애플리케이션입니다. 라이다 포인트 클라우드, HD Map, 다중 센서 타임스탬프 동기화처럼 자율주행에 필수적인 멀티모달 개념을 네이티브로 표현하는 스키마가 없습니다.

둘째, **데이터 교환 표준이 아닙니다.** FiftyOne은 메타데이터를 MongoDB에 저장하고 실제 미디어 파일은 경로 포인터로 참조합니다. 파일을 복사하지 않는다는 점에서는 효율적이지만, 이 포맷은 FiftyOne 애플리케이션 내부용입니다. Rerun 같은 다른 툴이 FiftyOne의 내부 포맷을 직접 읽을 수 없으므로, 다운스트림 연결을 위해 별도의 변환 레이어가 필요합니다.

셋째, **Arrow 파이프라인이 끊깁니다.** py123d는 Arrow를 데이터 교환 포맷으로 노출하기 때문에 Rerun까지 Arrow가 일관되게 흐릅니다. FiftyOne을 IR로 쓰면 이 흐름이 FiftyOne 내부 포맷에서 한 번 끊기고, Rerun으로 넘길 때 다시 변환이 필요합니다.

결론적으로 FiftyOne은 "중간에서 통일하는 표준"이 아니라 "표준화된 데이터를 소비하는 전문 도구"입니다. py123d가 번역기라면 FiftyOne은 번역된 글을 편집하는 워드프로세서에 해당합니다.

### FiftyOne이 데이터를 다루는 방식

FiftyOne의 내부 구조는 두 레이어로 나뉩니다. 메타데이터(라벨, 태그, 모델 출력, 씬 정보)는 **MongoDB**에 저장하고, 실제 미디어 파일(이미지, 영상)은 **원본 경로만 참조**합니다. 파일을 FiftyOne 전용 폴더로 복사하지 않는다는 뜻입니다. py123d가 경로 포인터로 원본 데이터를 참조하는 방식과 같은 철학입니다.

이 덕분에 수십만 장의 이미지를 가진 데이터셋도 FiftyOne에 등록하는 데 걸리는 시간은 메타데이터를 MongoDB에 쓰는 시간뿐입니다. 실제 이미지는 GUI에서 해당 샘플을 열 때만 그 자리에서 읽어옵니다.

큐레이션 워크플로우는 대략 이런 흐름입니다.

```
1. 임포트     py123d 데이터를 FiftyOne 샘플로 변환해 등록
      ↓
2. 탐색       GUI에서 이미지 그리드를 훑으며 전반적인 분포 파악
      ↓
3. 필터링     조건(라벨, 날씨 태그, 모델 신뢰도 등)으로 서브셋 추출
      ↓
4. 분석       FiftyOne Brain — 임베딩 기반 중복 탐지, 엣지 케이스 클러스터링
      ↓
5. 익스포트   선별된 서브셋을 Arrow 포맷 또는 파일 목록으로 내보내기
```

특히 **FiftyOne Brain**은 시각적 유사도를 임베딩 벡터로 계산해 비슷한 이미지를 묶거나, 반대로 다양성이 높은 샘플만 골라내는 기능을 제공합니다. "이 데이터셋에서 지금껏 한 번도 못 본 낯선 장면들만 뽑아줘"라는 요청을 처리할 수 있습니다. 단순 조건 필터링이 아니라 의미 기반 슬라이싱이 가능해집니다.

익스포트 단계에서 선별된 샘플의 py123d Arrow 파일 경로와 씬 ID가 JSON 재생 목록으로 출력됩니다. 이 목록 파일이 DORA `scenario-player` 노드와 FiftyOne을 연결하는 징검다리입니다. `scenario-player`가 목록을 읽어 Arrow 파일을 순서대로 DORA 토픽에 발행하면, 나머지 파이프라인(perception, evaluator, Rerun 시각화)은 데이터 출처를 모른 채 동일하게 동작합니다.

### 3단계: 고속 3D 시각화 (`Rerun`)

큐레이션된 주행 로그를 시각화할 때는 **Rerun**을 사용합니다. Rerun은 시계열 멀티모달 데이터를 위한 시각화 툴로, 타임라인 기반으로 여러 센서 데이터를 동기화해서 재생할 수 있습니다.

### Rerun이 멀티모달 동기화를 푸는 방식

자율주행 데이터를 시각화할 때 가장 어려운 문제는 **센서 주기가 다르다**는 점입니다. 카메라는 30Hz, LiDAR는 10Hz, 레이더는 20Hz입니다. 타임라인을 앞으로 한 칸 움직이면 카메라 이미지는 바뀌는데 LiDAR는 안 바뀌거나, 반대로 LiDAR가 바뀌는데 카메라는 그대로인 상황이 됩니다. 이걸 프레임 단위로 억지로 묶으면 이미 데이터를 왜곡한 것입니다.

Rerun은 이 문제를 **엔티티-컴포넌트 타임라인** 구조로 풉니다. 각 데이터 스트림(카메라, LiDAR, 박스 등)이 각자의 타임스탬프를 갖는 독립적인 엔티티로 등록됩니다. 타임라인 슬라이더를 t=1.23초로 이동하면 Rerun은 각 엔티티에 대해 "t=1.23초 시점에서 가장 최근에 기록된 값"을 독립적으로 꺼내 화면에 표시합니다. LiDAR는 t=1.20초 값을, 카메라는 t=1.23초 값을 보여주는 식입니다. 강제 동기화 없이 각 센서의 실제 샘플링 타임스탬프를 그대로 존중합니다.

이 방식이 py123d의 독립 타임스탬프 스트림 설계와 철학적으로 완전히 일치합니다. py123d가 센서마다 독립 스트림으로 데이터를 저장하는 이유가 정확히 이 동기화 방식을 지원하기 위해서입니다.

`py123d`의 타임스탬프 스트림 구조가 Rerun의 타임라인 시스템과 직결되므로, 차량 주행 궤적에 따른 대용량 3D 포인트 클라우드, 바운딩 박스, 카메라 영상을 동기화하여 지연 없이 부드럽게 재생할 수 있습니다.

**원격 모니터링 시 대역폭 고려**: Rerun과 DORA가 같은 머신에서 실행되면 OS 공유 메모리로 대용량 포인트 클라우드와 카메라 이미지가 Zero-Copy로 전달되어 렌더링 오버헤드가 거의 없습니다. 반면 DORA는 GPU 서버에서, Rerun Viewer는 로컬 PC에서 실행하는 원격 모니터링 환경에서는 네트워크 대역폭이 병목이 됩니다. 30Hz 멀티카메라 Raw 스트림은 기가비트 네트워크도 쉽게 포화시킵니다. 이 경우 visualizer 노드에서 카메라 이미지를 JPEG로 압축하거나 포인트 클라우드를 Voxel Grid Filter로 다운샘플링한 뒤 Rerun으로 보내면 대역폭을 10배 이상 줄일 수 있습니다.

## 4. 이 아키텍처가 강력한 진짜 이유: Arrow가 파이프라인 전체를 관통한다

재밌는 점은 **Rerun 역시 내부적으로 Apache Arrow IPC 방식을 표준으로 채택**하고 있다는 사실입니다.

결국 전체 파이프라인이 Arrow 하나로 연결됩니다.

```
py123d (Arrow) ──→ FiftyOne ──→ Rerun (Arrow IPC)
```

중간에 데이터를 다른 포맷으로 변환하거나 직렬화하는 오버헤드가 없습니다. Arrow 메모리 포맷이 파이프라인 처음부터 끝까지 그대로 유지되므로, 전체 인프라의 메모리 효율과 렌더링 성능이 극대화됩니다.

그리고 또 하나의 강점은 **확장성**입니다. 사내 데이터 포맷이 바뀌거나 새 센서가 추가되더라도, 맨 앞단의 `py123d` 스키마 레이어만 업데이트하면 됩니다. FiftyOne 큐레이션 로직이나 Rerun 시각화 코드는 단 한 줄도 고칠 필요가 없습니다. 변경의 영향이 첫 번째 레이어에서 완전히 흡수됩니다.

---

## 정리

| 레이어 | 툴 | 역할 |
|--------|----|------|
| 표준화 | `py123d` | 파편화된 데이터셋을 Arrow 기반 공통 스키마로 통합 |
| 큐레이션 | `FiftyOne` | 조건 기반 필터링, 엣지 케이스 수집, 모델 결과 비교 |
| 시각화 | `Rerun` | 타임라인 기반 3D 포인트 클라우드·바운딩 박스·카메라 동기화 재생 |

자율주행 데이터의 파편화로 고통받고 있거나, 테라바이트 단위의 멀티모달 데이터를 효율적으로 관리하고 디버깅할 수 있는 파이프라인을 고민 중이라면 **`py123d + FiftyOne + Rerun`** 조합은 현시점 가장 모던한 해답입니다.
