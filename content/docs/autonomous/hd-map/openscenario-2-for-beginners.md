[OpenSCENARIO 1.x](../openscenario-for-beginners/)는 "언제·누가·무엇을"을 XML 태그로 조합해 시나리오 하나를 정확히 기술하는 방식이었습니다. 이 방식은 명확하지만, 시나리오 하나 늘어날 때마다 태그 뭉치도 함께 늘어난다는 문제가 있습니다. 앞차 속도를 60km/h에서 80km/h까지 5km/h 간격으로 바꿔가며 같은 시나리오를 5개 만들고 싶다면, `.xosc` 파일도 5개 복사해서 숫자만 바꿔야 합니다.

**OpenSCENARIO 2.0(OSC2)**는 이 문제를 정반대 방향에서 풉니다. XML 태그 대신 **Python/C++처럼 읽히는 DSL(Domain Specific Language)**로 시나리오를 "코드"로 짜고, 그 코드가 조건·범위·분포를 표현하면 실행기가 그로부터 **구체적인 시나리오 인스턴스를 여러 개 생성**합니다. 시나리오 하나가 파일 하나가 아니라, 시나리오 하나가 시나리오 "가족"이 되는 셈입니다.

---

## 1.x와 2.0, 뭐가 근본적으로 다른가요?

| | OpenSCENARIO 1.x | OpenSCENARIO 2.0 (OSC2) |
|---|---|---|
| 표현 형식 | XML | 텍스트 기반 DSL (`.osc`) |
| 시나리오 하나의 의미 | 정확히 하나의 실행 인스턴스 | 파라미터 범위를 포함한 **시나리오 클래스** |
| 파생 시나리오 생성 | 파일을 복사해 값만 수정 | 같은 정의에서 조합적으로 자동 생성 |
| 문법 기반 | XML 스키마 | Foretellix의 M-SDL, Scenic 언어의 영향을 받은 문법 |
| 물리 단위 | 속성값 + 별도 단위 규칙 | `60kph`, `30m`, `5s`처럼 리터럴에 단위 내장 |
| 실행 방식 | 시뮬레이터가 직접 해석 | 대개 1.x 스토리보드로 컴파일된 뒤 실행 |
| 표준화 상태 | 업계 표준, 도입 성숙 | ASAM 표준으로 확정되었으나 도구 생태계는 아직 초기 |

가장 중요한 차이는 표 마지막 줄 바로 위, **"시나리오 하나의 의미"**입니다. 1.x에서 시나리오 파일은 "이 실행이 정확히 이렇게 일어난다"는 완결된 서술입니다. 2.0에서 시나리오 파일은 오히려 **"이런 조건을 만족하는 실행들의 집합"**을 정의하는 쪽에 가깝습니다. 뒤에서 보겠지만 이 차이가 회귀 테스트 규모를 다루는 방식 자체를 바꿉니다.

---

## 핵심 문법: actor, scenario, action, modifier

OSC2는 크게 네 가지 요소로 시나리오를 구성합니다.

- **actor**: 시나리오에 등장하는 객체(차량, 보행자)의 타입. 필드로 상태를 가집니다.
- **scenario**: 시나리오 자체의 정의. 함수 정의처럼 보이지만 실행 가능한 행동의 나열입니다.
- **action / behavior**: actor가 취하는 동작. `drive()`, `change_lane()`처럼 메서드 호출 형태로 씁니다.
- **modifier (`with`, `keep`, `until`)**: action에 조건이나 제약을 덧붙입니다.

가장 눈에 띄는 특징은 **`do` 블록의 `serial` / `parallel`**입니다. 1.x에서 `ManeuverGroup`과 `Event` 계층으로 표현하던 순서·동시성 관계를, 2.0에서는 코드 블록 중첩으로 표현합니다. "앞차가 자차 앞으로 끼어드는" 시나리오라면 자차는 `parallel` 블록 한 갈래에서 그냥 계속 주행하고, 앞차는 다른 갈래에서 `serial` 블록으로 "먼저 주행 → 거리가 좁혀지면 차선 변경"을 순서대로 실행하도록 구성합니다. 1.x 예시에서 `ManeuverGroup`, `Actors`, `Maneuver`, `Event`, `StartTrigger`로 5단 중첩되던 구조가, `do parallel: ... serial: ...`이라는 블록 중첩 두 단으로 줄어드는 셈입니다.

트리거 표현 방식도 달라집니다. 1.x는 `StartTrigger`를 action과 분리된 별도 XML 서브트리로 뒀지만, 2.0은 `keep(distance(npc, ego) < 30m)`처럼 action 선언 바로 옆에 조건을 붙입니다. `keep()`은 1.x의 `Condition`에 해당하고 "조건이 참인 동안 이 action을 유지한다"는 뜻입니다. 조건을 action에서 멀리 떨어뜨려 놓지 않기 때문에 "이 행동이 언제 시작·유지되는가"를 눈으로 따라가기가 더 쉽습니다.

## 진짜 차이는 파라미터화입니다

OSC2가 XML보다 "코드처럼 보인다"는 건 표면적인 차이일 뿐, 실제로 회귀 테스트에 의미 있는 변화는 **범위와 분포를 리터럴로 표현할 수 있다**는 점입니다. 앞의 끼어들기 시나리오에서 끼어드는 속도와 거리를 고정값 대신 `range(50kph..80kph)`, `range(15m..40m)`처럼 범위로 선언하면, 실행기가 이 두 축을 조합해 구체적인 값 조합(예: 5km/h · 5m 간격 그리드, 혹은 무작위 샘플링)을 생성합니다. 시나리오 정의는 하나인데, 실제로 돌아가는 테스트 케이스는 수십~수백 개가 됩니다.

[FiftyOne으로 회귀 테스트용 시나리오를 큐레이션하던 것](../../data-infra/closed-loop-regression-with-dora/)과 반대 방향의 작업이라고 볼 수 있습니다 — FiftyOne은 이미 있는 대량의 클립에서 대표 시나리오를 골라내는 쪽이고, OSC2 파라미터화는 시나리오 하나에서 대량의 변형을 만들어내는 쪽입니다. 클라우드 환경에서 회귀 테스트를 구성한다면 이 둘은 상호보완적입니다. 실도로 로그에서 뽑은 엣지 케이스를 OSC2로 파라미터화해서 그 주변 공간을 촘촘히 스윕하면, 로그 하나가 커버하던 지점 하나가 테스트 커버리지 영역으로 확장됩니다.

## 어떻게 실행되나요?

OSC2 표준 자체는 "이 문법으로 시나리오를 정의한다"까지만 규정하고, 실제 시뮬레이터 실행은 규정하지 않습니다. 현재 실무에서 쓰이는 흐름은 대체로 이렇습니다.

```
.osc (OSC2 DSL)
      │  ASAM 참조 구현 / 컴파일러
      ▼
파라미터 공간 전개 (concretization)
      │
      ▼
.xosc 인스턴스 N개 (OpenSCENARIO 1.x)
      │
      ▼
CARLA ScenarioRunner, esmini 등 기존 1.x 실행기
```

즉 OSC2는 대부분의 경우 **최종 실행 포맷이 아니라 상위 생성 포맷**입니다. `range(50kph..80kph)` 같은 선언이 컴파일 단계에서 구체적인 숫자로 확정(concretize)되고 나면, 그 결과는 1.x가 표현하던 것과 똑같은 "정확히 하나의 실행"이 됩니다. 실행기 생태계가 아직 1.x 중심이기 때문에, 2.0의 실질적인 가치는 시나리오 저작·조합 단계에 있고 실행 단계는 기존 1.x 파이프라인을 그대로 재사용하는 구조입니다.

이 구조는 [DORA 기반 회귀 테스트 파이프라인](../../data-infra/closed-loop-regression-with-dora/)에도 자연스럽게 얹을 수 있습니다. `scenario-player` 노드가 읽는 재생 목록을, FiftyOne이 고른 실도로 클립뿐 아니라 OSC2 컴파일 단계에서 쏟아져 나온 `.xosc` 인스턴스 묶음으로도 채울 수 있기 때문입니다. 두 소스가 결국 같은 실행 포맷(1.x 스토리보드)으로 수렴하므로, CI 단계에서는 "이 테스트 케이스가 실도로 로그에서 왔는지 파라미터 스윕에서 왔는지"를 구분할 필요조차 없습니다.

## 지금 도입해도 될까요?

| 상황 | 권장 |
|---|---|
| CARLA ScenarioRunner, Autoware 등 기존 1.x 도구 체인이 이미 구축됨 | 당장 전환할 필요 없음. 1.x로 충분히 표현 가능한 시나리오라면 굳이 옮길 이유가 적음 |
| 같은 시나리오 골격에서 파라미터만 바꾼 변형이 수십~수백 개씩 필요함 | OSC2 도입을 검토할 가치가 큼 — `range()`/`one_of()` 하나가 XML 파일 수십 개를 대체 |
| 회귀 테스트에서 "실패한 시나리오 주변을 촘촘히 스윕"하는 절차가 수작업임 | OSC2가 이 반복 작업을 문법 차원에서 흡수함 |
| 표준화된 상용 도구(dSPACE 등) 지원을 그대로 쓰고 싶음 | 지원 현황을 먼저 확인 — 2.0 지원은 도구마다 성숙도 차이가 큼 |

결론적으로 OSC2는 "1.x를 대체한다"기보다 "1.x가 표현하지 못하던 축 — 파라미터 공간 — 을 표현 가능하게 만든다"는 쪽에 가깝습니다. 실행 단계에서는 결국 1.x 스토리보드로 수렴하므로, 기존 CARLA/DORA 파이프라인을 버릴 필요 없이 시나리오 생성 단계에만 얹는 방식으로 도입 부담을 낮출 수 있습니다.

## 정리

| 개념 | 한 줄 요약 |
|---|---|
| **OSC2** | XML 대신 텍스트 DSL로 시나리오를 기술하는 OpenSCENARIO 2.0 |
| **scenario / actor / action** | 시나리오 정의, 등장 객체, 그 객체가 취하는 동작 |
| **do serial / parallel** | 1.x의 ManeuverGroup·Event 계층을 대체하는 순서·동시성 블록 |
| **range() / one_of()** | 파라미터 공간을 선언해 시나리오 하나에서 여러 변형을 생성 |
| **concretization** | OSC2 선언을 1.x 스토리보드 인스턴스로 확정하는 컴파일 단계 |

OSC2의 핵심은 시나리오를 "값"이 아니라 "값들의 공간"으로 기술할 수 있게 됐다는 점입니다. 클라우드에서 대규모 회귀 테스트를 돌린다면, 시나리오를 몇 개 손으로 늘리는 것보다 이 공간을 어떻게 설계하고 얼마나 촘촘히 스윕할지가 훨씬 더 큰 레버리지를 가집니다.
