## 왜 웹 뷰어가 필요한가

6.5절에서 정리했듯, CARLA·NuRec 같은 렌더링 기반 시뮬레이터는 GPU 자원을 많이 써서 별도 렌더링 서버에 두는 구성이 흔합니다. 우리 경우엔 그 위에서 dora-rs가 실제 자율주행 로직(perception/planning/control)까지 돌리는 클로즈드 루프입니다 — carla-bridge가 만들어낸 센서 데이터를 driving-stack 노드가 받아 판단하고, 그 제어 명령이 다시 carla-bridge를 거쳐 CARLA로 돌아가 차량을 움직입니다. 여기까지는 [CARLA 연동 글](../dora-rs-simulator-integration/)에서 이미 다룬 내용입니다.

문제는 이 루프가 사람 눈에는 안 보인다는 것입니다. 시뮬레이션이 지금 뭘 보고 있고 driving-stack이 뭘 판단하고 있는지 확인하려면 어떻게 해야 할까요. 렌더링 서버에 직접 SSH로 들어가 X11 포워딩을 켜거나 VNC를 붙이는 방법도 있지만, 둘 다 무겁고 팀원 여럿이 동시에 보기에는 불편합니다. 이 글은 dora-rs 파이프라인에 **관찰 전용 구독자**를 하나 추가해서, 클로즈드 루프 자체는 건드리지 않으면서 브라우저로 그 내부를 들여다보는 방법을 다룹니다.

## 아키텍처

```
[GPU 렌더링 서버]
  CARLA (+ NuRec으로 재구성한 씬)
       │ Python API
       ▼
  carla-bridge 노드 (센서 데이터 → dora 출력: camera)
       │ Zenoh (fan-out — 구독자마다 독립적으로 전달)
       ├─────────────────────────┐
       ▼                         │
  driving-stack 노드              │ (raw 센서 프레임)
  (perception/planning/           │
   control)                       │
       │  ├─ 제어 명령 ───────────┼──────────────┐
       │  └─ 인지·판단 결과 ───────┼───────┐      ▼
       │     (detections,         │       │  carla-bridge (역방향)
       │      trajectory,         ▼       │       │ Python API
       │      freespace)      web-sink 노드 │       ▼
       │                      (관찰 전용)  │     CARLA (차량 제어 반영)
       │                          ├─ FastAPI 서버를 백그라운드 스레드로 구동
       │                          └─ 수신한 프레임 + 판단 결과를 연결된 모든
       │                              WebSocket 클라이언트에 브로드캐스트
       │                                  │
       └──────────────────────────────────┴─────→ [브라우저] — <canvas>에 겹쳐 그려서 표시
```

web-sink가 구독하는 건 두 종류입니다 — carla-bridge가 내보내는 **원본 카메라 프레임**과, driving-stack이 내보내는 **인지·판단 결과**(탐지된 객체, 계획 궤적, 프리스페이스)입니다. 원본 프레임 없이 판단 결과만 봐서는 무엇 위에 겹쳐 그려야 할지 알 수 없고, 판단 결과 없이 원본만 봐서는 "이 상황에서 스택이 뭘 결정했는지"가 안 보이므로 web-sink는 이 둘을 같은 브라우저 클라이언트에 함께 전달합니다.

핵심은 **web-sink 노드가 dora 파이프라인의 평범한 노드이면서 동시에 웹 서버**라는 점, 그리고 **driving-stack의 제어 루프와는 완전히 독립적인 별도 구독자**라는 점입니다. carla-bridge와 driving-stack 입장에서는 web-sink도 그냥 구독자 하나가 더 붙은 것뿐이고, 6.5절에서 정리한 Zenoh의 push 모델(fan-out)을 그대로 씁니다 — 브라우저까지 가는 마지막 구간만 WebSocket으로 바꿔주면 됩니다.

## 왜 Arrow Flight가 아니라 WebSocket인가

6.5절에서 "지속적으로 밀어내야 하는 실시간 스트림에는 pull 모델인 Arrow Flight가 맞지 않는다"고 정리했는데, 브라우저로 가는 마지막 구간을 설계하면서 이 설명을 좀 더 정확히 다듬을 필요가 있었습니다. Arrow Flight의 `DoGet`은 사실 **서버 스트리밍 RPC**입니다 — 클라이언트가 `Ticket`으로 요청을 한 번 열면 서버는 그 연결 위에서 `RecordBatch`를 계속 흘려보낼 수 있어서, "한 번 당겨오면 끝"이라는 순수 pull 모델은 아닙니다. 그러니 "pull이라서 못 쓴다"는 이유만으로는 충분하지 않습니다.

브라우저 쪽에 Arrow Flight 대신 WebSocket을 쓰는 진짜 이유는 두 가지입니다.

1. **브라우저가 raw gRPC를 못 씁니다.** Flight는 gRPC(HTTP/2) 위에 있는데, 브라우저에서 쓰려면 `grpc-web`이 필요하고 이건 서버 앞에 Envoy 같은 프록시를 하나 더 세워야 합니다(브라우저가 HTTP/2 트레일러를 직접 못 다루기 때문). WebSocket은 모든 브라우저가 네이티브로 지원해서 이 프록시 계층이 아예 필요 없습니다.
2. **컬럼형 포맷의 이점이 여기선 안 살아납니다.** `RecordBatch`는 여러 타입의 열이 섞인 표 형태 데이터를 다룰 때 강력한데, 지금 보내는 건 JPEG 바이트 하나 또는(뒤에서 다룰) XYZ 3개짜리 동질적인 float 배열입니다. 스키마 협상과 배치 프레이밍이 오히려 오버헤드만 더하고, 브라우저에서도 Arrow IPC 포맷을 한 번 더 역직렬화해야 합니다.

물론 Flight가 완전히 밀려나는 건 아닙니다 — 뷰어가 아닌 **다른 소비자**(예: 라이다 프레임을 나중에 분석·재생하려고 intensity, ring index, timestamp 같은 열까지 포함해 구조화된 배치로 조회하는 시스템)에게는 py123d가 이미 쓰고 있는 Flight 경로가 여전히 맞습니다. 즉 "브라우저 뷰어는 WebSocket, 오프라인 분석/재생은 기존 Flight"로 **같은 데이터를 두 갈래로 소비**하는 게 자연스러운 구성입니다.

브라우저로 가는 마지막 구간에서 WebSocket을 쓰는 실무적인 이유도 하나 더 있습니다 — 매 프레임 새 HTTP 요청을 여는 것보다, 연결 하나를 열어두고 서버가 준비되는 대로 밀어 넣는 편이 지연시간과 연결 오버헤드 양쪽에서 낫습니다.

다만 WebSocket으로 바이너리 JPEG 프레임을 그대로 보내는 이 방식에는 뚜렷한 한계가 있습니다. 프레임마다 JPEG 헤더를 새로 붙이고 매번 새 `Image` 객체로 디코딩하기 때문에, 지연시간이 수백 ms 단위로 잡힙니다. 여러 카메라를 동시에 스트리밍하거나 지연시간이 중요해지면 WebRTC(`aiortc` 등)로 옮겨야 하는데, 이건 STUN/TURN과 SDP 협상이 추가로 필요해 별도로 다룰 만한 주제입니다. 이 글은 "일단 서버의 시뮬레이션이 브라우저에 보인다"를 검증하는 최소 구성에 집중합니다.

## web-sink 노드: dora 노드이자 웹 서버

가장 까다로운 설계 지점은 dora 노드의 메인 루프와 FastAPI(uvicorn)의 asyncio 이벤트 루프를 한 프로세스 안에서 공존시키는 것입니다. dora의 Python API는 `for event in node:` 형태의 동기 루프를 기대하는데, uvicorn 서버는 자체 asyncio 루프 위에서 계속 돌아야 합니다. 두 루프를 한 스레드에 억지로 합치려 하면 서로가 서로를 막습니다.

이를 푸는 방법은 uvicorn 서버를 별도 스레드에서 독립적으로 구동하고, dora 쪽 메인 루프는 자기 스레드에서 이벤트를 계속 받으면서 프레임이 도착할 때마다 "이 프레임을 브로드캐스트하라"는 코루틴을 스레드 안전한 방식으로 서버 스레드의 이벤트 루프에 넘겨주는 것입니다. 두 스레드가 각자의 일(dora 이벤트 수신, WebSocket 브로드캐스트)을 하면서, 그 경계에서만 스레드 안전한 브릿지로 연결되는 구조입니다.

연결된 클라이언트 목록은 WebSocket 접속/해제 시 갱신되는 집합이고, 프레임이 도착할 때마다 그 목록 전체에 전송을 돌립니다. 연결이 끊긴 클라이언트는 전송 중 예외로 걸러내 제거합니다.

## 엔드투엔드 검증: 더미 소스로 먼저 확인

carla-bridge를 바로 붙이기 전에, GPU 없는 환경에서도 파이프라인 자체가 옳은지 먼저 확인하는 게 순서에 맞습니다. carla-bridge 자리에 매 33ms(약 30fps)마다 합성 프레임을 그려 JPEG으로 인코딩해 내보내는 더미 `camera-source` 노드를 임시로 두고, 그 출력을 web-sink의 입력으로 연결하는 최소 데이터플로우를 구성했습니다.

빌드해서 띄운 뒤, WebSocket 클라이언트로 직접 접속해 수신한 바이트가 실제 JPEG인지 확인했습니다.

```text
frame 1: 13145 bytes, starts with b'\xff\xd8\xff'
frame 2: 13336 bytes, starts with b'\xff\xd8\xff'
frame 3: 13292 bytes, starts with b'\xff\xd8\xff'
```

`\xff\xd8\xff`는 JPEG 파일의 표준 매직 넘버입니다. 이게 세 프레임 연속으로 확인됐다는 건 dora 노드 간 전달(Zenoh) → web-sink의 스레드 간 브로드캐스트 → WebSocket 전송까지 전체 경로가 프레임 손상 없이 동작한다는 뜻입니다. 브라우저의 `<canvas>`는 이 바이트를 이미지로 디코딩해 그리기만 하면 되므로, 여기서부터는 표준적인 웹 클라이언트 작업입니다.

## carla-bridge로 교체하기

더미 노드에서 실제 CARLA로 넘어가는 건 데이터플로우 정의의 소스 노드를 [CARLA 연동 글](dora-rs-simulator-integration/)에서 다룬 carla-bridge로 바꾸는 것뿐입니다 — web-sink는 입력이 "JPEG으로 인코딩된 바이트 배열"이기만 하면 되므로, 소스가 합성 프레임이든 CARLA 카메라 센서든 신경 쓰지 않습니다. 이게 dora의 노드 단위 분리가 주는 실질적인 이득입니다.

NuRec으로 재구성한 씬을 CARLA에 로드하는 절차는 이 글의 범위 밖입니다 — NuRec의 설치 방식과 CARLA 애셋/맵으로의 변환 인터페이스는 계속 바뀌고 있어서, 실제로 붙이기 전에 최신 문서를 다시 확인하는 게 안전합니다. 다만 일단 CARLA가 카메라 프레임을 내보내는 지점까지만 붙으면, 그 뒤(carla-bridge → web-sink → 브라우저)는 이 글에서 검증한 경로를 그대로 탑니다.

렌더링 서버와 웹 서버를 같은 머신에 둘지 나눌지도 선택할 수 있습니다. 나눈다면 6.5절에서 다룬 대로 carla-bridge를 렌더링 서버의 Daemon에, web-sink를 별도 머신(또는 같은 서버의 다른 포트)에 배치하면 되고, 데이터플로우 정의와 노드 코드는 바뀌지 않습니다 — Zenoh가 그 전송 경로 전환을 대신 처리해준다는 게 6.5절의 핵심이었고, 여기서도 그대로 적용됩니다.

## 클로즈드 루프 안에서의 관찰자: 격리와 판단 오버레이

앞의 아키텍처에서 web-sink를 driving-stack과 나란히 그린 이유를 여기서 자세히 다룹니다. 이 뷰어는 "제어 루프의 일부"가 아니라 "제어 루프를 곁에서 지켜보는 별도 구독자"여야 합니다. 이 둘을 헷갈리면 두 가지 문제가 생깁니다.

### 관찰자 격리: web-sink는 제어 루프를 절대 지연시키면 안 된다

carla-bridge가 센서 데이터를 publish하면 Zenoh가 driving-stack과 web-sink 양쪽에 각자 독립적으로 전달합니다. 이게 fan-out 구조의 요점입니다 — 한 구독자가 느려도 다른 구독자의 수신 속도에 영향을 주지 않아야 합니다. web-sink는 브라우저 여러 개가 동시에 붙거나 네트워크가 느려질 수 있는, 파이프라인에서 가장 예측하기 어려운 부분입니다. 만약 web-sink의 지연이 carla-bridge → driving-stack 경로까지 늦춘다면, "그냥 보기만 하는" 기능 때문에 실제 주행 판단이 프레임을 놓치는 최악의 상황이 됩니다.

이 격리를 실무적으로 보장하려면 두 가지를 확인해야 합니다. 첫째, **입력 큐를 노드마다 독립적으로 설정**합니다. dora의 입력 큐 깊이 설정을 driving-stack은 지연 없이 최신 프레임을 받도록, web-sink는 큐가 밀리면 오래된 프레임을 과감히 버리도록(얕은 큐, drop-oldest) 다르게 잡습니다. web-sink 입장에서는 사람이 보는 것이므로 프레임 몇 개가 빠져도 무방하지만, driving-stack은 그렇지 않습니다. 둘째, **web-sink 내부에서도 브로드캐스트가 블로킹되지 않게** 합니다. 느린 클라이언트 하나 때문에 전체 브로드캐스트가 지연되지 않도록, 각 클라이언트로의 전송에 짧은 타임아웃을 걸고 실패하면 그 클라이언트만 끊어내는 편이 안전합니다.

정리하면: web-sink가 무슨 일을 겪든 driving-stack의 판단 주기에는 영향이 없어야 하고, 이건 dora의 fan-out 구조가 기본적으로 보장해주는 성질을 web-sink 쪽 설정으로 한 번 더 지키는 문제입니다.

### driving-stack의 판단을 오버레이하기

단순히 카메라 원본만 보여주는 것보다, driving-stack이 지금 뭘 인지하고 뭘 계획하고 있는지까지 겹쳐 보이면 디버깅 가치가 훨씬 커집니다. 카메라 프레임 위에 인지된 객체의 바운딩박스와, 계획된 궤적을 그려 넣는 방식입니다.

여기서 서버 쪽(Python)에서 이미지를 합성해 보낼지, 원본과 판단 결과를 각각 보내고 브라우저가 겹쳐 그릴지 선택해야 합니다. 이 글에서는 지금까지 일관되게 써온 원칙 — "가공은 최소화하고 원본에 가까운 데이터를 보내서 브라우저가 그리게 한다" — 을 그대로 따라 **클라이언트 오버레이**를 택합니다. 서버에서 매 프레임 OpenCV로 다시 그려 JPEG을 재인코딩하는 것보다 가볍고, 나중에 "바운딩박스만 끄고 보기" 같은 UI 토글도 브라우저 쪽에서 자유롭게 만들 수 있습니다.

카메라 프레임은 지금처럼 바이너리 메시지로, driving-stack의 판단 결과는 같은 WebSocket 연결 위에 **텍스트(JSON) 메시지**로 보냅니다. WebSocket은 한 연결에서 바이너리와 텍스트 프레임을 섞어 보낼 수 있어서, 브라우저는 메시지 타입으로 둘을 구분하면 됩니다. 판단 결과에는 궤적(이미지 픽셀 좌표의 점 목록)과 인지된 객체(각각의 클래스, 바운딩박스, 신뢰도)가 담깁니다.

궤적과 바운딩박스는 이미 이미지 픽셀 좌표로 실어 보냅니다. driving-stack이 갖고 있는 계획된 경로나 객체 위치는 보통 ego 좌표계(3D)이므로, [카메라 모델](../../sensor/camera-models-for-beginners/)과 [LiDAR-카메라 투영](../../sensor/lidar-to-camera-projection/) 글에서 다룬 핀홀 투영으로 픽셀 좌표로 변환한 뒤 실어 보내는 게 핵심입니다 — 이 변환을 브라우저에서 하지 않고 서버(Python) 쪽에서 미리 끝내는 이유는, 카메라 내부/외부 파라미터를 다루는 로직을 한 곳(서버)에만 두고 싶기 때문입니다.

브라우저는 가장 최근에 받은 판단 결과를 변수 하나에 캐시해두고, 새 카메라 프레임을 그릴 때마다 그 캐시된 값을 함께 겹쳐 그립니다. 이렇게 하면 판단 메시지와 카메라 프레임의 타이밍이 프레임 단위로 완벽히 맞을 필요가 없습니다. 이건 의도적인 단순화입니다 — 클로즈드 루프 자체의 정밀한 틱 동기화는 [CARLA 연동 글의 4절](../dora-rs-simulator-integration/)에서 이미 다뤘고, 그건 제어에 직접 관여하는 driving-stack과 carla-bridge 사이에서만 엄격하게 지키면 됩니다. 사람이 보는 뷰어는 몇 프레임 정도 어긋나도 무방하다는 점이, 관찰자를 제어 루프와 분리해서 얻는 또 다른 이득입니다.

## 인지 결과 확장: 3D 객체 박스와 프리스페이스

앞서 "판단 오버레이" 절에서는 driving-stack의 2D 바운딩박스와 궤적만 다뤘습니다. 실제로는 딥러닝 인지 노드가 3D 객체 박스와 프리스페이스(주행 가능 영역)까지 만들어내므로, 이 둘도 같은 원칙 위에서 스트리밍에 얹습니다. LiDAR 원본 포인트클라우드 자체를 브라우저에 3D로 렌더링할 필요는 없습니다 — 뷰어의 목적은 driving-stack이 뭘 인지·판단했는지 확인하는 것이지 원본 센서 데이터를 그대로 재현하는 것이 아니므로, 인지 결과를 카메라 화면 위에 겹쳐 보여주는 것으로 충분합니다.

### 3D 객체 박스: 기존 GT 스키마를 그대로 재사용, 카메라 화면에 투영

[CARLA 연동 글의 "Ground Truth 바운딩 박스" 절](../dora-rs-simulator-integration/)에서 CARLA GT를 `actor_id`, `class`, `x`, `y`, `z`, `width`, `height`, `length`, `yaw` 열을 가진 Arrow RecordBatch로 표현했고, evaluator 노드가 이 GT와 예측 박스를 같은 스키마로 비교한다고 했습니다. 딥러닝 인지 노드의 출력도 이미 이 형식이므로, 웹 뷰어를 위해 새 스키마를 만들 필요 없이 **evaluator가 쓰는 것과 같은 필드를 그대로 web-sink로도 fan-out**하면 됩니다. 이게 처음에 정한 관찰자 격리 원칙과도 맞습니다 — web-sink는 evaluator와 마찬가지로 그저 또 하나의 구독자일 뿐입니다.

객체가 3D 박스(위치·크기·yaw)로 표현되어 있어도, 웹 뷰어에서는 서버에서 카메라 내부/외부 파라미터로 픽셀 좌표에 투영한 2D 박스만 실어 보내면 됩니다 — "판단 오버레이" 절에서 궤적을 픽셀 좌표로 미리 변환해 보냈던 것과 같은 방식입니다. 3D 박스 원본을 그대로 보내 브라우저에서 다시 그리는 것보다, 서버에서 한 번만 투영해 카메라 화면에 사각형으로 그리는 쪽이 구현도 단순하고 카메라 파라미터를 다루는 로직도 한 곳에만 남습니다.

### 프리스페이스: 마스크 그대로 보낼지, 윤곽선만 보낼지

프리스페이스는 보통 두 형태 중 하나로 나옵니다 — 카메라 이미지 크기의 픽셀 단위 세그멘테이션 마스크, 또는 BEV(조감도) 격자의 점유 그리드. 어느 쪽이든 원본 그대로 보내면 매 프레임 상당한 크기가 됩니다(예: 640×480 마스크는 픽셀당 1바이트만 써도 300KB). "원본을 보낼지, 압축된 표현을 보낼지"는 데이터를 웹으로 스트리밍할 때 반복해서 마주치는 질문입니다.

이 뷰어의 목적이 "주행 가능 영역의 경계를 사람이 확인하는 것"이라면, **마스크 전체가 아니라 윤곽선(폴리곤)만 추출해서 보내는 편**이 압도적으로 효율적입니다. 서버에서 마스크의 외곽 경계만 뽑는 표준적인 윤곽선 추출을 쓰면, 점 몇십 개짜리 리스트로 줄어듭니다.

세그멘테이션 품질 자체를 픽셀 단위로 디버깅해야 하는 상황(윤곽선만으로는 안 보이는 내부의 잘못된 예측을 찾는 경우)이라면 원본 마스크가 필요합니다. 이때는 별도 스트림으로 마스크를 보내되, JPEG 대신 **PNG**로 인코딩하는 걸 추천합니다 — 세그멘테이션 마스크는 이진값(또는 소수의 클래스)이 넓은 영역에 걸쳐 반복되는 형태라, JPEG의 손실 압축(블록 경계에 잡음이 낌)보다 PNG의 무손실 압축이 크기도 더 작고 경계도 정확합니다.

프리스페이스가 카메라 이미지 공간의 폴리곤이라면 카메라 캔버스 위에, BEV(조감도) 공간이라면 별도의 상단뷰 캔버스에 그려야 합니다 — 이건 driving-stack이 프리스페이스를 이미지 공간으로 내는지 BEV 공간으로 내는지에 따라 달라지므로, 실제 연동 시 확인이 필요합니다.

## 남은 과제

- **지연시간**: JPEG-over-WebSocket은 수백 ms 단위 지연이 생깁니다. 실시간 조작이 필요하면 WebRTC로 옮겨야 합니다.
- **다중 카메라**: 지금 구성은 카메라 하나 기준입니다. CARLA의 다중 카메라 리그를 그대로 보여주려면 프레임에 카메라 ID를 실어 보내고, 프런트엔드에서 여러 `<canvas>`로 분기하는 작업이 필요합니다.
- **NuRec 연동 세부사항**: 위에서 언급했듯 최신 설치/라이선스 요건을 별도로 확인해야 합니다.

## 정리

렌더링 서버의 시뮬레이션을 웹으로 보여주는 문제는, dora의 노드 분리 구조 덕분에 "web-sink라는 노드 하나를 추가하는" 문제로 축소됩니다. carla-bridge가 이미 만들어내는 출력을 구독자 하나 더 붙이는 것뿐이라, 6.5절의 멀티 머신 배치나 다른 노드들에는 아무 영향이 없습니다. 더미 소스로 이 경로를 먼저 검증해두면, 실제 CARLA/NuRec을 붙일 때는 소스 노드 하나만 교체하면 되므로 디버깅 범위가 크게 줄어듭니다.
