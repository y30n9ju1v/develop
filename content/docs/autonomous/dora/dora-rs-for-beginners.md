## 1. DORA가 뭔가요?

**DORA**는 **Dataflow-Oriented Robotic Architecture**의 약자로, Rust로 만들어진 실시간 로보틱스 및 AI 애플리케이션 개발 프레임워크입니다.

로봇을 만들 때 가장 많이 쓰는 표준이 ROS2(Robot Operating System 2)인데, DORA는 ROS2의 개발 경험을 유지하면서 성능과 편의성을 크게 끌어올리는 것을 목표로 만들어졌습니다.

> 한 줄 요약: **"ROS2보다 10~17배 빠르고, 쓰기 더 편한 로보틱스 프레임워크"**

## 2. 왜 만들어졌나요?

### DDS가 느린 이유

ROS2의 기본 통신 미들웨어인 DDS(Data Distribution Service)는 원래 군사·항공·금융 같은 **엔터프라이즈 분산 시스템**을 위해 설계되었습니다. 서로 다른 회사의 장비가 네트워크로 연결되는 환경에서 신뢰성 있는 데이터 교환을 보장하는 것이 목표였습니다.

이 목표를 달성하기 위해 DDS는 두 가지 무거운 메커니즘을 씁니다.

첫째, **IDL(Interface Definition Language) 직렬화**입니다. DDS 메시지는 언어 중립적인 IDL로 스키마를 정의하고, 전송 시 IDL 포맷으로 변환한 뒤, 수신 측에서 역변환합니다. 이 과정이 매 메시지마다 일어납니다. 카메라 이미지(약 2MB)를 30fps로 전송하면, 초당 60MB를 직렬화·역직렬화하는 CPU 부하가 생깁니다.

둘째, **동적 디스커버리 프로토콜**입니다. DDS는 네트워크에 참여하는 노드를 자동으로 발견하기 위해 멀티캐스트 패킷을 주기적으로 브로드캐스트합니다. 노드가 많아지면 이 디스커버리 트래픽만으로도 상당한 오버헤드가 생깁니다.

이 설계는 에어버스 항공기와 보잉 지상 장비가 통신하는 상황에서는 합리적입니다. 그러나 하나의 자율주행 차량 위에서 여러 노드가 초당 수십 번 통신하는 환경에서는 과설계입니다. 필요하지 않은 기능의 비용을 계속 지불하게 됩니다.

DORA는 이 문제를 **4KB 이상의 메시지에 제로카피 공유 메모리를 사용**함으로써 해결합니다. 직렬화 자체가 없습니다. "이 메모리 주소에 데이터가 있으니 가져가라"고 포인터만 넘기는 방식입니다. 결과적으로 ROS2 Python 대비 **10~17배 빠른 지연시간**을 달성했고, 페이로드 크기가 커져도 지연시간이 안정적으로 유지됩니다.

### 왜 Rust인가

C++도 빠릅니다. 그런데 DORA는 C++ 대신 Rust를 선택했습니다. 이유는 **메모리 안전성을 런타임 비용 없이 보장**하기 때문입니다.

C++에서 공유 메모리를 쓰면 데이터 경쟁(data race), 해제 후 사용(use-after-free), 이중 해제(double-free) 같은 버그가 발생할 수 있습니다. 이런 버그는 재현이 어렵고, 발생했을 때 로봇이 예측 불가능하게 동작합니다. 자율주행 차량이라면 안전 문제로 직결됩니다.

Rust는 컴파일러가 소유권(ownership)과 빌림(borrow) 규칙을 강제해 이런 버그를 컴파일 타임에 차단합니다. 가비지 컬렉터(GC)처럼 런타임에 오버헤드를 추가하지 않습니다. "C++ 수준의 속도 + 메모리 안전성 보장"이 DORA가 Rust를 선택한 핵심 이유입니다.

또한 Rust의 비동기 생태계(Tokio)는 Daemon이 여러 이벤트 소스를 동시에 처리하는 구조에 잘 맞습니다. Coordinator 명령, 노드 상태 보고, Zenoh 메시지, 타이머를 하나의 비동기 루프에서 처리하는 것이 Rust에서 자연스럽습니다.

### 도구 파편화 문제

로봇 소프트웨어를 개발하다 보면 로컬 실행, 배포, 모니터링 각각에 서로 다른 도구를 써야 하는 경우가 많습니다. DORA는 **하나의 CLI**로 전체 개발 라이프사이클을 관리합니다. 개발 중에는 단일 명령으로 파이프라인을 로컬에서 실행하고, 프로덕션에서는 같은 YAML 파일을 그대로 분산 환경에 배포할 수 있습니다.

## 3. 데이터플로우(Dataflow) 구조

DORA는 로봇 애플리케이션을 **방향 그래프(Directed Graph)**로 표현합니다. 노드(Node)가 그래프의 꼭짓점이고, 노드 사이의 데이터 흐름이 간선(edge)입니다.

자율주행을 예로 들면, 카메라 노드가 이미지를 내보내면 감지 노드가 그것을 받아 바운딩 박스를 계산하고, 계획 노드가 그 박스를 받아 다음 제어 명령을 생성합니다. 각 노드는 자기 입력과 출력만 알면 됩니다. 데이터가 어떤 경로로 전달되는지는 YAML 선언 파일이 정의하고, DORA가 그 선언대로 라우팅과 스케줄링을 처리합니다.

이 구조의 강점은 **모듈 교체가 쉽다**는 것입니다. 감지 모델을 새 버전으로 바꿔도 YAML에서 해당 노드의 경로만 바꾸면 됩니다. 나머지 파이프라인은 그대로입니다.

## 4. 핵심 기술 스택

### Apache Arrow

노드 간 메시지 포맷으로 **Apache Arrow**의 컬럼 메모리 포맷을 사용합니다. Arrow는 언어에 상관없이 같은 메모리 레이아웃을 공유하므로, Rust·Python·C·C++ 노드 사이에서 데이터를 복사 없이 주고받을 수 있습니다. Arrow의 동작 원리가 궁금하다면 [Apache Arrow 내부 동작 글](../../data-infra/apache-arrow-internals/)을 참고하세요.

### Zenoh와 공유 메모리

데이터 전송 레이어로 **Zenoh**를 사용합니다. DDS의 동적 디스커버리는 멀티캐스트 기반이라 노드가 많아질수록 브로드캐스트 오버헤드가 쌓입니다. Zenoh는 **P2P 라우팅 기반**으로, 세션을 수립한 피어들 사이에서 직접 데이터를 교환합니다. 브로커나 멀티캐스트 없이 경로를 동적으로 계산하므로 DDS보다 디스커버리 오버헤드가 훨씬 낮습니다.

같은 머신 안에서는 Zenoh가 OS 레벨 공유 메모리로 제로카피 전송을 합니다. 네트워크가 필요한 분산 배포 환경에서는 자동으로 네트워크 전송으로 전환합니다. 개발자는 이 전환을 신경 쓸 필요가 없습니다.

### Arrow + Zenoh 조합의 시너지

Arrow와 Zenoh의 역할을 정확하게 구분하면 이렇습니다.

**Arrow**는 공유 메모리에 올렸을 때 데이터를 **어떤 포맷으로 배치**할지를 정의합니다. Arrow 자체도 mmap 기반 공유 메모리를 지원하므로, Arrow만으로도 같은 머신 안에서 프로세스 간 제로카피 읽기가 가능합니다.

**Zenoh**는 **어느 프로세스가 어느 데이터를 구독하는지**를 관리합니다 — 구독 라우팅, 피어 디스커버리, 로컬/네트워크 자동 전환. Arrow만 mmap에 올리면 "어느 프로세스가 어느 데이터를 봐야 하는지"를 직접 관리해야 하고, 다른 머신으로 넘어가는 순간 네트워크 전송 로직도 별도로 작성해야 합니다. Zenoh가 이 라우팅과 전환을 자동으로 처리합니다.

둘을 함께 쓰면 이 역할 분리가 완성됩니다. Rust 노드가 Arrow 포맷으로 공유 메모리에 데이터를 쓰면, Zenoh가 구독 관계를 보고 Python 노드에게 해당 메모리의 포인터를 전달합니다. Python 노드는 역직렬화 없이 Arrow 라이브러리로 그 메모리를 바로 읽습니다. NumPy 배열로 변환할 때도 복사가 아니라 포인터 재해석입니다. 그리고 같은 노드가 다른 머신으로 이동해도 Zenoh가 자동으로 네트워크 전송으로 전환하므로 코드는 변경이 없습니다.

자율주행에서 이게 중요한 이유는 LiDAR 포인트 클라우드나 카메라 이미지가 감지 → 예측 → 계획 노드를 차례로 지나가기 때문입니다. 각 단계에서 복사와 역직렬화가 일어나면 그 비용이 프레임마다 누적됩니다. Arrow + Zenoh 조합은 이 경로 전체에서 데이터 포맷과 라우팅을 동시에 해결합니다.

### 멀티언어 지원

노드를 Rust, Python, C, C++ 중 원하는 언어로 작성할 수 있습니다. 래퍼(wrapper) 방식이 아니라 **각 언어의 네이티브 API**를 제공합니다. Arrow + Zenoh 시너지 덕분에 C++ 노드가 공유 메모리에 쓴 Arrow 버퍼를 Python 노드가 NumPy 배열로 바로 읽을 수 있습니다. 언어 경계에서 직렬화 비용이 발생하지 않습니다.

## 5. 4계층 아키텍처

DORA는 아래에서 위로 쌓이는 4계층 구조로 설계되어 있습니다.

```
┌──────────────────────────────────────┐
│  4. Orchestration  CLI + Coordinator │  ← 분산 배포, 전체 조율
├──────────────────────────────────────┤
│  3. Execution      Daemon + Runtime  │  ← 머신별 프로세스 관리
├──────────────────────────────────────┤
│  2. Core Libraries dora-core + APIs  │  ← 공유 메모리, 노드 API
├──────────────────────────────────────┤
│  1. Protocol       Apache Arrow      │  ← 메시지 직렬화 포맷
└──────────────────────────────────────┘
```

각 계층의 관심사가 명확히 분리되어 있습니다. 개발자가 실제로 작성하는 노드 코드는 2계층 API만 알면 되고, 나머지는 DORA가 처리합니다.

### Coordinator (조율자)

**시스템 전체에 하나만 존재**하며, 분산 배포 시 모든 Daemon을 조율하는 중앙 관제탑입니다. CLI 명령을 받아 각 머신의 Daemon에 전달하고, Daemon 등록 상태를 관리하고, 실행 중인 노드들의 상태를 실시간으로 스트리밍해 모니터링 도구에 제공합니다.

로컬에서 `dora run`만 쓸 때는 Coordinator가 필요 없습니다. `dora up`으로 네트워크 모드를 시작할 때 비로소 활성화됩니다.

### Daemon (데몬)

**머신마다 하나씩** 실행되며, 그 머신 위의 노드 생명주기를 관리합니다. Coordinator 명령, 노드 상태 보고, 다른 Daemon에서 오는 Zenoh 메시지, 주기 타이머 — 네 가지 신호를 하나의 비동기 이벤트 루프에서 처리합니다. 어느 하나가 느려도 나머지 처리를 막지 않습니다.

Daemon은 노드를 **자식 프로세스**로 생성합니다. 노드가 죽으면 재시작 정책에 따라 다시 띄웁니다. Coordinator와의 연결이 끊어지면 지수 백오프로 자동 재연결을 시도하고, 그 동안에도 로컬 파이프라인은 계속 동작합니다.

다만 이 "연결이 끊겨도 로컬은 계속 돈다"는 성질은 **모니터링/제어 채널이 끊겨도 온보드 파이프라인은 죽지 않는다**는 뜻이지, 그 자체로 안전을 보장한다는 뜻은 아닙니다. 실차에서 온보드 컴퓨터와 지상 기지국(원격 모니터링·원격 개입 채널) 사이의 Zenoh 연결이 실제로 끊기는 상황(네트워크 파티션)을 가정하면, DORA 프레임워크 자체는 "로컬 파이프라인이 계속 실행된다"는 것까지만 보장하고, 그 이후의 안전 대응(하드웨어 워치독 연계, 통신 유실 시 긴급 제동 모드 전환 같은)은 DORA 바깥에서 별도로 설계해야 하는 안전 계층입니다 — [DORA를 실차/실제 하드웨어에 올리기](dora-rs-real-hardware-deployment/#4-페일세이프-시뮬레이터에는-없던-안전-경로)에서 다룬 `watchdog` 노드 패턴이 바로 이 계층을 채우는 예시입니다.

### Runtime (런타임)

**인프로세스(in-process) 오퍼레이터**를 실행하는 레이어입니다. 각 노드가 독립 프로세스로 실행되면 노드 수가 많아질수록 IPC 비용이 쌓입니다. Runtime은 여러 오퍼레이터를 한 프로세스 안에서 실행해 이 문제를 해결합니다. Python 오퍼레이터는 PyO3로, 네이티브 라이브러리는 `dlopen`으로 로드합니다.

격리가 중요한 노드는 독립 프로세스로, 지연시간이 중요한 노드는 오퍼레이터(Runtime)로 구성하는 것이 일반적인 선택입니다.

### Node (노드)

**독립 프로세스**로 실행되는 기본 실행 단위입니다. 개발자가 실제로 코드를 작성하는 곳입니다. 노드는 자기 입력과 출력만 선언하면 되고, 라우팅은 DORA가 처리합니다.

메시지 크기에 따라 전송 방식이 자동으로 달라집니다. **4KB 미만은 TCP**, **4KB 이상은 제로카피 공유 메모리**입니다. 4KB라는 숫자는 OS 메모리 페이지 크기와 관련이 있습니다. 공유 메모리 설정에는 최소 하나의 페이지(보통 4KB)가 필요하므로, 그보다 작은 메시지에 공유 메모리를 쓰면 설정 오버헤드가 데이터보다 커집니다. 4KB 이상이 되면 설정 비용이 무시할 수 있는 수준이 되고, 포인터만 넘기는 이득이 압도적입니다. LiDAR 포인트 클라우드나 카메라 이미지처럼 자율주행 환경의 센서 데이터는 거의 항상 이 임계값을 넘습니다.

## 6. 통신 흐름

```
CLI ──WebSocket──→ Coordinator ──WebSocket──→ Daemon ──TCP/SharedMem──→ Node
                                                  │
                                           Zenoh pub-sub
                                                  │
                                             Daemon (다른 머신)
```

CLI 명령 → Coordinator → Daemon → 노드 프로세스 순으로 전달됩니다. 다른 머신의 노드와 통신할 때는 Daemon 간 Zenoh 채널을 씁니다. 로컬 개발 시에는 `dora run` 하나로 Daemon이 직접 노드들을 관리합니다. 분산 배포 시에는 `dora up`으로 Coordinator를 띄우고, 각 머신의 Daemon이 Coordinator에 연결해 조율을 받습니다. 개발자는 두 환경에서 같은 YAML 파일을 씁니다.

| 기능 | 동작 |
|------|------|
| **재시작 정책** | Never / OnFailure / Always, 지수 백오프 설정 가능 |
| **헬스 모니터링** | 5초마다 하트비트·헬스체크, 2초마다 메트릭 수집 |
| **서킷 브레이커** | 입력 타임아웃 → Degraded 상태 전환, 복구 시 `InputRecovered` 이벤트 발생 |
| **에러 전파 추적** | 업스트림 실패가 다운스트림 크래시를 유발했는지 기록 |

서킷 브레이커가 왜 중요한지 구체적인 시나리오로 이해하면 더 명확합니다. 카메라 드라이버 노드가 잠시 멈췄다고 가정합니다. 서킷 브레이커가 없다면, 감지 노드는 이미지를 기다리다 큐가 가득 차거나 타임아웃이 발생해 크래시합니다. 그러면 감지 결과를 기다리던 계획 노드도 크래시합니다. 하나의 센서 문제가 전체 파이프라인을 무너뜨리는 연쇄 장애입니다.

서킷 브레이커는 이 전파를 차단합니다. 카메라 응답이 타임아웃을 초과하면, 감지 노드는 크래시 대신 Degraded 상태로 전환됩니다. 이 상태에서 LiDAR 데이터만으로 동작하거나 마지막 유효 결과를 유지하는 폴백 동작을 구현할 수 있습니다. 카메라가 복구되면 `InputRecovered` 이벤트가 발생하고 정상 상태로 돌아옵니다.

## 8. ROS2와 비교

| | ROS2 | DORA |
|-|------|------|
| **구현 언어** | C++, Python | Rust |
| **통신 방식** | DDS (IDL 직렬화 + 동적 디스커버리) | Zenoh + 공유 메모리 (제로카피) |
| **메시지 포맷** | IDL | Apache Arrow |
| **성능** | 기준 | ~10~17× 빠름 |
| **멀티언어** | 래퍼 방식 | 네이티브 API |
| **파이프라인 정의** | launch 파일 (Python/XML) | YAML 선언형 |
| **생태계 성숙도** | 매우 성숙 | 빠르게 성장 중 |

ROS2는 수십 년간 쌓인 패키지 생태계가 강점이고, DORA는 성능과 개발자 경험이 강점입니다. 신규 프로젝트라면 DORA를 검토할 가치가 있고, 기존 ROS2 프로젝트라면 ROS2 브리지를 통한 병행 사용도 가능합니다.

## 9. 정리

DORA는 로보틱스 소프트웨어 개발의 세 가지 문제를 동시에 해결하려 합니다.

1. **성능**: DDS의 IDL 직렬화와 동적 디스커버리 오버헤드를 Zenoh + 공유 메모리로 구조적으로 제거합니다.
2. **안전성**: Rust의 소유권 규칙으로 메모리 안전성을 런타임 비용 없이 컴파일 타임에 보장합니다.
3. **운영**: 4계층 아키텍처로 로컬 개발과 분산 배포를 같은 YAML 파일로 처리하고, 서킷 브레이커와 재시작 정책으로 연쇄 장애를 차단합니다.

다음 글에서는 이 아키텍처를 실제로 정의하는 [데이터플로우 YAML과 통신 패턴](dora-rs-dataflow-yaml/)을 살펴봅니다.
