> 이 글은 [DORA 입문](dora-rs-for-beginners/)과 [DORA로 자율주행 E2E 회귀 테스트 구성하기](dora-rs-av-regression-testing/)에 이어집니다.

회귀 테스트 글에서 다룬 파이프라인은 미리 녹화된 데이터를 재생하는 **오픈 루프** 방식이었습니다. 스택의 결정이 다음 프레임에 영향을 주지 않았습니다. 진짜 클로즈 루프를 구성하려면 시뮬레이터가 필요합니다. 자율주행 스택이 내린 제어 명령(조향, 가속, 제동)이 시뮬레이터에 피드백되고, 시뮬레이터가 그 명령에 따라 차량을 움직인 뒤 새로운 센서 데이터를 생성하는 루프입니다.

CARLA는 이 클로즈 루프 테스트에 가장 널리 쓰이는 오픈소스 자율주행 시뮬레이터입니다. DORA와 CARLA를 연동할 때 핵심 문제는 세 가지입니다. **포맷**(CARLA의 데이터를 어떻게 Arrow로 변환하는가), **방향**(데이터가 양방향으로 흘러야 한다), **동기화**(DORA 파이프라인과 CARLA의 시뮬레이션 시간이 맞아야 한다).

---

## 1. 전체 구조

```
CARLA
  │
  ├─ 카메라 이미지 ──┐
  ├─ LiDAR 포인트 ───┤
  ├─ IMU/GPS ────────┤──→  carla-bridge 노드  ──→  DORA 파이프라인
  └─ GT 바운딩박스 ──┘           ↑
                                 │
                          VehicleControl
                         (조향·가속·제동)
```

CARLA와 DORA 사이에 **carla-bridge 노드** 하나를 둡니다. 이 노드가 두 가지 역할을 동시에 합니다. 첫째, CARLA에서 받은 센서 데이터를 Arrow 포맷으로 변환해 DORA 토픽으로 발행합니다. 둘째, DORA 파이프라인에서 나온 제어 명령을 구독해 CARLA 차량에 적용합니다.

브리지를 별도 노드로 분리하는 이유는 **CARLA API와 DORA API의 관심사를 분리**하기 위해서입니다. perception 노드나 planning 노드는 데이터가 시뮬레이터에서 왔는지, 실제 차량에서 왔는지 알 필요가 없습니다. Arrow 메시지를 받아서 처리할 뿐입니다. 나중에 실제 차량으로 전환할 때 carla-bridge만 실제 센서 드라이버 노드로 교체하면 됩니다.

---

## 2. 왜 ROS2 브리지 체인을 쓰지 않는가

CARLA는 공식 ROS2 브리지를 제공합니다. DORA도 ROS2 브리지가 있습니다. 그러면 "CARLA → ROS2 → DORA"를 연결하면 되는 것 아닐까요?

문제는 **직렬화가 두 번** 일어난다는 것입니다. CARLA가 센서 데이터를 ROS2 메시지로 직렬화하고, DORA의 ROS2 브리지가 그것을 다시 Arrow로 변환합니다. LiDAR 포인트 클라우드(수백 KB)가 매 프레임 이 경로를 지나가면 변환 비용이 누적됩니다.

또한 두 브리지가 체인으로 연결되면 **클럭 동기화가 복잡**해집니다. CARLA 동기 모드에서 타이밍을 정밀하게 제어하려면 브리지가 중간에 끼어드는 것이 방해가 됩니다.

직접 Python으로 carla-bridge 노드를 작성하는 것이 더 단순하고 효율적입니다. CARLA Python API와 DORA Python API 모두 잘 지원되므로 어렵지 않습니다.

---

## 3. 센서 데이터 포맷

CARLA가 제공하는 센서 데이터를 Arrow로 변환할 때, 각 센서마다 자연스러운 포맷이 다릅니다.

### 카메라 이미지

CARLA 카메라는 BGRA 포맷의 픽셀 버퍼를 줍니다. 이것을 Arrow로 표현하는 방법은 두 가지입니다.

첫째, **Arrow LargeBinary**로 raw 바이트를 그대로 담고, 메타데이터에 높이·너비·채널·인코딩을 붙이는 방식입니다. 가장 단순합니다. 수신 노드가 메타데이터를 보고 버퍼를 해석합니다.

둘째, **py123d의 `ParsedCamera` 스키마**를 따르는 방식입니다. 파이프라인이 py123d 기반이라면 이 쪽이 일관성이 높습니다. 실제 녹화 데이터와 시뮬레이터 데이터를 같은 스키마로 처리할 수 있어, 동일한 perception 노드가 두 소스를 모두 소화합니다.

이미지 데이터는 크기가 크므로 4KB 임계값을 훨씬 넘습니다. Zenoh가 자동으로 공유 메모리 경로를 씁니다.

### LiDAR 포인트 클라우드

CARLA LiDAR는 포인트마다 `(x, y, z, intensity)` 네 개의 float32를 줍니다. Arrow **RecordBatch**로 열 단위로 저장하는 것이 자연스럽습니다. 열은 `x`, `y`, `z`, `intensity` 네 개의 float32 배열입니다.

열 기반 저장이 좋은 이유는 perception 노드가 보통 특정 열만 씁니다. 포인트 필터링에는 `z`만, 강도 기반 필터링에는 `intensity`만 필요합니다. 행 기반 구조라면 필요 없는 열을 함께 읽어야 하지만, RecordBatch는 필요한 열만 선택적으로 접근합니다. Arrow의 컬럼 기반 설계 원리가 그대로 적용됩니다.

CARLA의 semantic LiDAR는 포인트마다 `object_idx`와 `object_tag`도 제공합니다. 이를 추가 열로 붙이면 evaluator 노드가 GT 레이블을 별도로 관리할 필요가 없습니다.

### IMU / GPS

IMU는 가속도·각속도, GPS는 위도·경도·고도입니다. 데이터 크기가 작아 4KB 임계값 아래입니다. TCP 경로로 전달됩니다. Arrow Struct 타입이나 단순 float64 배열로 표현합니다.

### Ground Truth 바운딩 박스

CARLA는 시뮬레이션 세계의 모든 액터에 대한 GT 바운딩 박스를 제공합니다. 이것을 Arrow RecordBatch로 표현합니다. 열은 `actor_id`, `class`, `x`, `y`, `z`, `width`, `height`, `length`, `yaw` 등입니다. evaluator 노드가 이 GT와 perception의 예측 박스를 비교해 mAP를 계산합니다.

### 제어 명령 (DORA → CARLA)

DORA planning/control 노드에서 carla-bridge로 돌아오는 제어 명령은 구조가 단순합니다. `throttle` (0~1 float), `steer` (-1~1 float), `brake` (0~1 float), `hand_brake` (bool), `reverse` (bool). 크기가 수십 바이트에 불과해 TCP로 전달됩니다.

## 4. 틱 동기화: 클로즈 루프의 핵심

CARLA에는 두 가지 실행 모드가 있습니다. **비동기 모드**와 **동기 모드**입니다. 클로즈 루프 테스트에는 반드시 동기 모드를 써야 합니다.

### 비동기 모드의 문제

비동기 모드에서 CARLA는 자체 속도로 시뮬레이션을 진행합니다. DORA 파이프라인이 한 프레임을 처리하는 동안 CARLA는 이미 다음 프레임으로 넘어갑니다. 제어 명령이 도착했을 때 차량은 이미 다른 위치에 있습니다.

이 불일치가 누적되면 테스트 결과가 재현 불가능해집니다. 같은 코드를 두 번 돌렸을 때 결과가 달라집니다. 회귀 테스트의 기본 전제인 재현성이 무너집니다.

### 동기 모드의 동작 방식

동기 모드에서 CARLA는 **`world.tick()`을 받을 때까지 시뮬레이션 시간을 멈춥니다**. 클라이언트(carla-bridge 노드)가 명시적으로 틱을 보내야 다음 프레임으로 넘어갑니다.

클로즈 루프 한 사이클의 순서는 이렇습니다.

```
1. carla-bridge가 현재 프레임 센서 데이터를 DORA로 발행
2. DORA 파이프라인이 데이터를 처리해 제어 명령 생성
3. carla-bridge가 제어 명령을 수신해 CARLA 차량에 적용
4. carla-bridge가 world.tick() 호출
5. CARLA가 제어 명령대로 차량을 움직이고 다음 프레임 생성
6. 1로 돌아감
```

`world.tick()`은 DORA 파이프라인이 제어 명령을 돌려준 뒤에 호출해야 합니다. 제어 명령이 오기 전에 틱을 보내면, 이전 프레임의 명령으로 차량이 움직입니다.

### carla-bridge 노드의 설계 과제

동기 모드에서 carla-bridge는 **두 방향의 이벤트를 순서대로 처리**해야 합니다. CARLA 센서 콜백(비동기로 들어옴)과 DORA 제어 명령 수신(DORA 이벤트 루프에서 들어옴)을 조율해야 합니다.

가장 단순한 설계는 carla-bridge를 **상태 머신**으로 보는 것입니다.

- **WAITING_FOR_CONTROL** 상태: 센서 데이터를 발행하고 제어 명령을 기다립니다.
- **CONTROL_RECEIVED** 상태: 제어 명령을 CARLA에 적용하고 `world.tick()`을 호출합니다. 그 다음 다시 WAITING_FOR_CONTROL 상태로 전환합니다.

제어 명령이 일정 시간 안에 도착하지 않으면 타임아웃을 걸어 이전 명령을 유지하거나 제동을 겁니다. 이 타임아웃을 어떻게 설정하느냐가 테스트의 실시간성 요구사항을 결정합니다.

### 동기 모드가 감추는 실시간성 문제

CARLA 동기 모드는 기능적 재현성에는 완벽하지만 **레이턴시(latency)는 검증하지 않습니다**. 자율주행 스택의 추론이 1초가 걸려도 시뮬레이션 시간은 20ms만 흐릅니다. CARLA 테스트를 통과해도 실제 차량에서 처음 레이턴시 위반이 드러나는 이유입니다.

실제 차량에 배포할 때는 제어 주기(일반적으로 50Hz, 20ms) 안에 센서 수신 → 인지 추론 → 계획 → 제어 명령 생성 전체가 완료되어야 합니다. 이를 검증하려면 carla-bridge의 센서 데이터 발행 타임스탬프와 제어 명령 수신 타임스탬프 차이를 **프레임별 처리 시간**으로 측정합니다. DORA result-writer를 활용해 이 지연시간이 목표 제어 주기를 초과하는 프레임 비율을 회귀 지표에 포함하면, "기능적으로 올바른가"와 "시간 안에 올바른가"를 분리해서 검증할 수 있습니다.

## 5. 타임스탬프 처리

CARLA 동기 모드에서 시뮬레이션 시간은 `world.tick()`마다 고정 간격으로 증가합니다. 기본값은 20ms(50Hz)입니다. 이 시뮬레이션 타임스탬프를 Arrow 메시지의 타임스탬프로 씁니다.

중요한 점은 **시뮬레이션 시간이 실제 경과 시간과 다르다**는 것입니다. DORA 파이프라인이 한 프레임을 처리하는 데 실제로 500ms가 걸려도, CARLA 시뮬레이션 시간은 20ms만 흐릅니다. 이것은 버그가 아니라 동기 모드의 의도적인 동작입니다.

이 시뮬레이션 타임스탬프를 Arrow 메시지에 포함하면, evaluator 노드나 시각화 노드가 "이 예측 박스는 시뮬레이션 t=1.24s의 센서 데이터에서 나온 것"임을 알 수 있습니다.

## 6. 멀티 에이전트와 병렬 시나리오

하나의 DORA 파이프라인이 하나의 CARLA 인스턴스와 연결됩니다. 여러 시나리오를 병렬로 테스트하려면, 각 시나리오마다 별도의 CARLA 인스턴스와 DORA 파이프라인을 띄워야 합니다.

CARLA는 서버 포트를 바꿔 같은 머신에서 여러 인스턴스를 실행할 수 있습니다. GPU 메모리가 충분하다면(인스턴스당 2~4GB) 병렬로 돌릴 수 있습니다. 오픈 루프 회귀 테스트보다 자원 소모가 크지만, 클로즈 루프의 현실성을 얻는 대가입니다.

## 6.5. 시뮬레이터를 다른 머신에 둘 때

CARLA·NuRec 같은 렌더링 기반 시뮬레이터는 GPU 자원을 많이 씁니다. perception/planning 스택을 실행하는 머신과 별도로, 렌더링 전용 GPU 서버에 시뮬레이터를 띄우는 구성이 흔합니다. 이 경우 carla-bridge 노드가 만들어내는 센서 데이터(카메라 프레임, LiDAR 포인트 클라우드)가 매 틱마다 네트워크를 건너야 합니다.

이 문제는 앞서 [py123d 입문](../../data-infra/py123d-for-beginners/) 시리즈에서 다룬 [Arrow Flight](../../data-infra/arrow-flight-network-transfer/)로 풀고 싶어질 수 있지만, 이 상황에는 맞지 않습니다. Arrow Flight의 `DoGet`/`Ticket`은 "클라이언트가 필요한 시점에 당겨오는" pull 모델을 전제로 설계되었습니다. 반면 시뮬레이터가 매 틱 100ms(또는 그보다 빠르게)마다 끊김없이 밀어내야 하는 실시간 스트림은 pull이 아니라 **지속적인 push**가 자연스럽습니다. 매 프레임마다 새 RPC를 여닫는 구조로 만들면 오히려 지연시간이 늘어납니다.

DORA는 이 문제를 이미 프레임워크 차원에서 해결해 둡니다. [DORA 입문 글](../dora-rs-for-beginners/)에서 다뤘듯, 노드 간 통신은 **Zenoh**가 담당하며, 같은 머신이면 Arrow 공유 메모리로 제로카피 전달하고, 다른 머신이면 코드 변경 없이 자동으로 네트워크 전송으로 전환합니다. carla-bridge 노드를 렌더링 서버의 Daemon에, perception/planning 노드를 다른 머신의 Daemon에 배치하고 `dora up`으로 Coordinator를 띄우기만 하면, 같은 YAML 데이터플로우 정의가 그대로 멀티 머신 구성으로 동작합니다.

정리하면, **배치/온디맨드로 조회하는 정적 데이터**(녹화된 시나리오 풀, py123d Arrow IPC 파일)는 Arrow Flight가, **지속적으로 밀어내야 하는 실시간 스트림**(시뮬레이터 센서 출력, 클로즈 루프 제어 피드백)은 DORA의 Daemon-Zenoh 배치가 맡는 것이 자연스러운 역할 분담입니다. 같은 Arrow 포맷을 공유하지만, 전송 계층은 데이터의 접근 패턴(pull vs. push)에 맞춰 다르게 골라야 합니다.

## 7. LGSVL, Isaac Sim 등 다른 시뮬레이터

CARLA 이외의 시뮬레이터도 같은 원칙으로 연동할 수 있습니다.

**LGSVL**: CARLA와 유사한 Python API를 제공합니다. 동기 모드 지원, 센서 콜백 방식도 거의 같습니다. carla-bridge 노드를 조금 수정해 lgsvl-bridge 노드로 만들 수 있습니다.

**NVIDIA Isaac Sim**: ROS2 네이티브 지원이 강합니다. DORA의 ROS2 브리지를 통해 연동하는 것이 자연스럽습니다. 다만 앞서 언급한 이중 직렬화 문제가 있으므로, 성능이 중요한 경우 직접 브리지 노드를 작성하는 것이 낫습니다.

**Waymax**: Google의 JAX 기반 시뮬레이터입니다. 실시간 3D 렌더링이 없고 완전히 데이터 기반입니다. 센서 데이터 대신 에이전트 상태(위치, 속도, 진행 방향)를 직접 제공합니다. 렌더링 비용이 없어 매우 빠르지만, 카메라나 LiDAR 기반 perception을 테스트할 수는 없습니다. 계획(planning) 알고리즘을 대규모로 빠르게 평가할 때 적합합니다.

---

## 8. 실도로 데이터와 시뮬레이터 데이터의 도메인 갭

시뮬레이터 연동 글에서 빼놓을 수 없는 주제가 도메인 갭입니다.

CARLA에서 잘 동작하는 perception 모델이 실제 차량에서는 성능이 떨어지는 경우가 많습니다. CARLA의 카메라 이미지는 실제 카메라의 노이즈, 렌즈 왜곡, 조명 변화를 완벽하게 재현하지 못합니다. LiDAR도 마찬가지입니다. 이 차이를 도메인 갭이라고 합니다.

이 문제를 줄이는 실용적인 접근은 **파이프라인에서 시뮬레이터 데이터와 실도로 데이터를 혼용**하는 것입니다. perception 노드는 실도로 데이터로 학습한 모델을 씁니다. 시뮬레이터는 planning과 control을 테스트하는 데 집중합니다. 즉, CARLA 클로즈 루프 테스트는 "인지가 완벽하다고 가정했을 때 계획이 올바른가"를 검증하고, 실도로 녹화 데이터의 오픈 루프 테스트는 "실제 센서 데이터에서 인지가 올바른가"를 검증하는 방식으로 역할을 나눕니다.

py123d가 이 두 데이터 소스를 같은 스키마로 표현해주므로, DORA 파이프라인에서 데이터 출처에 상관없이 동일한 evaluator 노드를 쓸 수 있습니다.

---

## 9. py123d 오픈루프와 CARLA 클로즈루프의 통일

앞서 도메인 갭 절에서 "실도로 데이터로는 perception을, 시뮬레이터로는 planning/control을 검증한다"고 나눴습니다. 그런데 이 두 경로를 **같은 DORA 파이프라인**에서 돌리려면 어떻게 해야 할까요?

핵심 원리는 간단합니다. DORA 토픽 이름과 Arrow 스키마가 통일되어 있으면, **데이터를 생산하는 노드만 교체**하면 됩니다.

```
오픈루프 (py123d):   scenario-player ─→ /sensor/camera
                                     ─→ /sensor/lidar     ─→  perception
클로즈루프 (CARLA):   carla-bridge    ─→ /sensor/camera       ─→  planning
                                     ─→ /sensor/lidar         ─→  control
                          ↑
                   VehicleControl 피드백
```

perception, planning, control, evaluator 노드는 손대지 않습니다. 오직 파이프라인의 맨 앞에 있는 소스 노드만 바뀝니다.

### py123d 스키마를 공통 계약으로 사용하기

이 통일이 가능하려면 carla-bridge가 CARLA의 출력을 **py123d 스키마에 맞게 변환**해야 합니다. py123d가 데이터를 저장하는 방식이 곧 파이프라인 전체의 Arrow 스키마 계약이 됩니다.

두 가지 변환이 필요합니다.

**좌표계 변환**: CARLA는 Unreal Engine 4의 왼손 좌표계를 씁니다. X가 앞, Y가 오른쪽, Z가 위입니다. py123d는 ISO 8855 기반으로 X가 앞, Y가 왼쪽, Z가 위입니다. Y축 부호가 반대입니다. carla-bridge가 LiDAR 포인트의 Y 좌표를 부호 반전하고, 바운딩 박스의 yaw 각도를 변환합니다.

**클래스 분류 정렬**: CARLA 액터에는 `vehicle.car`, `vehicle.truck`, `walker.pedestrian` 같은 블루프린트 이름이 붙습니다. py123d는 nuScenes·Waymo·AV2의 분류 체계를 통일한 자체 클래스 이름을 씁니다. carla-bridge 안에 CARLA 블루프린트 → py123d 클래스 매핑 테이블을 두면 evaluator 노드가 GT 박스와 예측 박스를 같은 클래스 체계로 비교할 수 있습니다.

이 두 변환을 carla-bridge 안에 캡슐화하면, 파이프라인의 나머지 노드는 데이터 출처를 전혀 몰라도 됩니다.

### 모드 전환은 DORA YAML에서

DORA의 선언형 YAML 덕분에 모드 전환이 코드 변경 없이 가능합니다. 오픈루프 파이프라인은 `scenario-player` 노드를 정의하고, 클로즈루프 파이프라인은 `carla-bridge` 노드를 정의합니다. 두 노드가 같은 토픽 이름으로 발행하므로 하위 노드는 동일합니다.

CI 파이프라인에서는 이를 자연스럽게 활용할 수 있습니다. PR마다 빠르게 돌릴 회귀 테스트에는 오픈루프 py123d 파이프라인을 씁니다. 주요 릴리스 브랜치나 병합 후 파이프라인에서는 CARLA 클로즈루프로 전환해 planning/control까지 검증합니다. 두 파이프라인이 같은 evaluator 노드와 같은 지표 정의를 쓰므로 결과를 직접 비교할 수 있습니다.

## 10. 정리

CARLA와 DORA를 연동할 때 핵심 결정은 세 가지입니다.

**직접 브리지 노드**: ROS2 이중 브리지 대신 carla-bridge 노드를 직접 작성합니다. 직렬화 경계가 하나로 줄고, 틱 동기화 제어가 명확해집니다.

**Arrow 포맷 선택**: 카메라는 raw 바이트 + 메타데이터 또는 py123d 스키마, LiDAR는 RecordBatch(열: x/y/z/intensity), 제어 명령은 간단한 struct. 파이프라인 전체가 py123d 기반이라면 py123d 스키마를 따르는 것이 실도로 데이터와의 호환성을 유지하는 가장 자연스러운 선택입니다.

**동기 모드 필수**: 클로즈 루프 테스트에서 재현성을 보장하려면 CARLA 동기 모드와 명시적 틱 제어가 반드시 필요합니다. carla-bridge 노드가 제어 명령 수신 확인 후 `world.tick()`을 호출하는 상태 머신 구조로 설계합니다.
