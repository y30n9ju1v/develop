> [CARLA 시뮬레이터와 DORA 연동하기](dora-rs-simulator-integration/)에서 만든 클로즈 루프 파이프라인을 이어서 다룹니다. 이 글은 그 파이프라인을 시뮬레이터가 아니라 실제 차량/로봇에 올리는 다음 단계를 다룹니다.

[시뮬레이터 연동 편](dora-rs-simulator-integration/) 8절에서 "실도로 데이터와 시뮬레이터 데이터의 도메인 갭"을 다뤘습니다. 그 갭은 인지 모델의 정확도 문제였지만, 실제 하드웨어에 파이프라인을 올릴 때는 그보다 먼저 **인프라 수준의 갭**을 넘어야 합니다 — 시뮬레이터에서는 CARLA가 무한한 컴퓨팅 자원을 가진 서버에서 돌지만, 실차의 온보드 컴퓨터는 전력·발열·CPU 코어 수 전부 제한적입니다.

---

## 1. 시뮬레이터 노드를 실제 드라이버 노드로 교체하기

[시뮬레이터 연동 편](dora-rs-simulator-integration/) 9절에서 py123d 오픈 루프와 CARLA 클로즈 루프를 "공통 계약(스키마)으로 통일"했던 설계가 여기서 그대로 값을 발휘합니다 — `carla-bridge` 노드가 하던 역할(카메라·LiDAR 데이터를 Arrow 포맷으로 변환해 같은 이름의 출력을 내보내는 것)을 실제 센서 드라이버 노드로 바꿔치기하기만 하면 됩니다.

```yaml
# 시뮬레이션용
nodes:
  - id: carla-bridge
    outputs: [camera_front, lidar_points, imu, gps]

# 실차용 — 노드 이름과 출력 이름은 동일하게 유지
nodes:
  - id: sensor-driver
    outputs: [camera_front, lidar_points, imu, gps]
```

다운스트림 노드(인지, 계획, 제어)는 `camera_front`라는 이름과 그 안의 Arrow 스키마만 보고 동작하므로, 이 이름과 스키마가 시뮬레이션과 실차 사이에서 정확히 같다면 **다운스트림 코드는 한 줄도 바꿀 필요가 없습니다.** 반대로 말하면, 이 계약이 조금이라도 어긋나면(예: 실제 카메라 드라이버가 BGR을 주는데 시뮬레이터는 RGB를 줬다면) 문제는 다운스트림 어딘가에서 원인 불명의 성능 저하로만 나타나므로, 센서 드라이버 노드를 새로 짤 때는 [시뮬레이터 연동 편](dora-rs-simulator-integration/#3-센서-데이터-포맷)에서 정의한 스키마와 값의 의미(단위, 좌표계, 색 순서)까지 한 항목씩 대조해야 합니다.

## 2. 리소스 제약: 온보드 컴퓨터는 서버가 아니다

시뮬레이션 환경에서는 인지 모델이 GPU 서버에서 30fps로 잘 돌았더라도, 온보드 컴퓨터(예: Jetson 계열, 임베디드 x86)에서는 같은 모델이 그 속도로 돌지 않는 경우가 흔합니다. [관측/디버깅 편](dora-rs-observability-debugging/#2-역압backpressure이-걸렸는지-확인하기)에서 다룬 역압 진단이 여기서 실전 도구가 됩니다 — 실차에 배포한 뒤 가장 먼저 확인할 것은 각 노드의 큐 길이입니다.

```bash
dora list --metrics
```

인지 노드의 큐가 계속 쌓인다면, 선택지는 셋입니다.

1. **모델을 경량화한다** (양자화, 작은 백본으로 교체) — 컴퓨팅 문제를 근본적으로 줄이는 방법이지만 정확도 트레이드오프가 있습니다.
2. **입력 주기를 낮춘다** — [2편](dora-rs-dataflow-yaml/#2-내장-타이머)에서 다룬 타이머 설정을 33ms(30fps)에서 66ms(15fps)로 늦추는 식입니다. 계획·제어처럼 더 빠른 주기가 필요한 다운스트림 노드에는 영향이 없도록, 느려진 인지 결과를 그다음 노드가 "새 값이 없으면 이전 값을 재사용"하는 방식으로 흡수해야 합니다.
3. **노드를 여러 프로세스/코어에 분산한다** — [1편](dora-rs-for-beginners/#5-4계층-아키텍처)에서 다룬 Daemon-Runtime 구조 덕분에, 노드 하나를 다른 코어(또는 [2편](dora-rs-dataflow-yaml/#7-분산-배포와-ros2-브리지)에서 다룬 대로 다른 머신)에 배정하는 것만으로 병목을 옮길 수 있습니다.

셋 다 근본적으로는 "온보드 컴퓨터의 자원이 시뮬레이션 서버보다 훨씬 적다"는 하나의 제약을 다른 방식으로 우회하는 것이며, 실제로는 세 가지를 조합해서 씁니다.

## 3. 실시간성 검증: "평균적으로 빠르다"는 충분하지 않다

시뮬레이션에서는 평균 지연시간(latency)이 성능 지표의 전부인 경우가 많지만, 실차에서는 **최악의 경우(worst-case) 지연**이 훨씬 중요합니다. 제어 노드가 평균 10ms 만에 응답하더라도, 100번에 한 번 50ms까지 튄다면 그 한 번이 실제 주행에서 급제동 지연으로 이어질 수 있습니다.

```bash
dora list --metrics --percentile 99
```

이런 식으로 p50(중앙값)이 아니라 **p99, p99.9** 같은 꼬리 지연을 확인해야 합니다. [1편](dora-rs-for-beginners/#7-장애-내성)에서 다룬 장애 내성 메커니즘(노드 재시작 정책)이 이 지점에서 다시 중요해지는데, 재시작 자체가 걸리는 시간 동안 그 노드의 출력이 끊긴다는 뜻이므로, 안전이 중요한 노드(제어)는 재시작에 의존하기보다 애초에 꼬리 지연 자체를 줄이는 튜닝(우선순위 스케줄링, 메모리 사전 할당으로 GC/할당 지연 제거)이 우선되어야 합니다.

또한 [1편](dora-rs-for-beginners/#4-핵심-기술-스택)에서 다룬 Zenoh 통신도 실제 차량 네트워크(이더넷 스위치, 여러 컴퓨팅 유닛 간 배선)에서는 시뮬레이션 시절의 로컬 통신과 다른 지연 특성을 보일 수 있습니다 — 배포 전에 반드시 실제 네트워크 토폴로지 위에서 지연을 재측정해야 합니다.

## 4. 페일세이프: 시뮬레이터에는 없던 안전 경로

시뮬레이터에서는 인지 노드가 죽으면 그냥 테스트가 실패로 끝나지만, 실차에서 인지 노드가 죽으면 **차량이 그 순간에도 움직이고 있습니다.** [1편](dora-rs-for-beginners/#7-장애-내성)에서 다룬 재시작 정책만으로는 부족하고, 재시작이 끝날 때까지의 공백을 메우는 별도의 안전 경로가 필요합니다.

```yaml
nodes:
  - id: perception
    outputs: [detections]
    restart_policy: on-failure

  - id: watchdog
    inputs:
      detections: perception/detections
      tick: dora/timer/millis/100
    outputs: [safe_stop_signal]
```

`watchdog` 노드는 `perception/detections`가 일정 시간(예: 200ms) 이상 갱신되지 않으면 `safe_stop_signal`을 내보내, 제어 노드가 이를 받아 안전 정지 절차로 전환하게 만드는 식입니다. 이건 DORA가 기본 제공하는 기능이 아니라, [2편](dora-rs-dataflow-yaml/#6-동적-토폴로지-변경)에서 다룬 그래프 설계 능력을 이용해 **개발자가 직접 얹어야 하는 안전 계층**입니다 — 시뮬레이션 검증 단계에는 없던, 실차 배포에서만 요구되는 노드입니다.

## 5. 시뮬레이션에서 잡히지 않던 문제가 실차에서 드러나는 경우

- **센서 타이밍 지터**: 시뮬레이터의 카메라는 정확히 33.33ms마다 프레임을 냈지만, 실제 카메라 드라이버는 온도나 USB 대역폭에 따라 주기가 흔들립니다. [시뮬레이터 연동 편](dora-rs-simulator-integration/#5-타임스탬프-처리)에서 다룬 타임스탬프 처리가 여기서 "타이머 주기를 신뢰하지 말고 각 메시지의 실제 타임스탬프를 봐야 한다"는 원칙으로 이어집니다.
- **콜드 스타트**: 시뮬레이션은 보통 모델이 이미 로드된 상태에서 시작하지만, 실차는 부팅 후 모든 노드가 처음부터 초기화됩니다. 인지 모델 로딩에 5초가 걸린다면, 그 5초 동안 다른 노드들이 "인지 결과 없음"을 어떻게 처리하는지가 시뮬레이션에서는 한 번도 테스트되지 않았을 가능성이 큽니다.
- **전력/발열에 따른 스로틀링**: 장시간 주행 시 온보드 컴퓨터가 열을 받아 클럭을 낮추면, 앞서 2절에서 측정한 큐 길이가 시간이 지날수록 서서히 나빠지는 패턴으로 나타납니다. 이건 짧은 시뮬레이션 세션으로는 재현되지 않고, 실차에서 장시간 로그를 쌓아야 발견됩니다.

---

## 6. 정리

- 시뮬레이터의 브리지 노드를 실제 센서 드라이버 노드로 바꿀 때, 다운스트림 코드는 그대로 두려면 [시뮬레이터 연동 편](dora-rs-simulator-integration/)에서 정한 출력 이름과 스키마 계약을 한 글자도 어기지 않아야 합니다.
- 리소스 제약은 모델 경량화·주기 조정·노드 분산 세 방법을 조합해 다루고, [관측/디버깅 편](dora-rs-observability-debugging/)의 큐 길이 메트릭이 병목을 찾는 첫 도구입니다.
- 실차 성능은 평균이 아니라 **꼬리 지연(p99 이상)**으로 검증해야 하며, 이 지연은 반드시 실제 네트워크·하드웨어 위에서 재측정해야 합니다.
- 시뮬레이션에는 없던 **watchdog 기반 안전 경로**를 직접 설계해 얹어야, 인지처럼 중요한 노드가 실제로 멈췄을 때 차량이 안전하게 반응합니다.
- 센서 지터, 콜드 스타트, 열에 의한 스로틀링처럼 시뮬레이션 세션에서는 재현되지 않는 문제들은 실차의 장시간 로그를 통해서만 드러납니다.

다음 글에서는 이 시리즈 전체에서 반복해서 언급된 "ROS2보다 10~17배 빠르다"는 주장을, 실제로 어떻게 측정하고 검증하는지 — 벤치마킹 방법론을 다룹니다.
