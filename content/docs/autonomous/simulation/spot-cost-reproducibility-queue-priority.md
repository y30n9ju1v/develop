[이전 글](../cpu-gpu-mixed-batch-scheduling/)에서 CPU/GPU 파이프라인을 쪼개고 fractional 할당과 LPT 정렬로 자원을 촘촘히 채우는 방법을 다뤘습니다. 자원을 효율적으로 채우고 나면 남는 두 가지 실전 문제가 있습니다. 하나는 **비용을 더 줄이려다 재현성을 잃는 문제**, 다른 하나는 **급한 검증이 대규모 배치 뒤에 밀리는 문제**입니다.

---

## 1. 스팟 인스턴스와 재현성의 충돌

GPU 비용 절감을 위해 스팟(Spot)/프리엠프터블 인스턴스를 쓰고 싶지만, 회귀 테스트는 실패 원인 재현이 핵심입니다. 스팟 인스턴스는 클라우드 제공자가 언제든 회수(preemption)할 수 있어서, 회수 시점에 스케줄링이 꼬이면 "어제 실패했던 시나리오가 오늘은 재현이 안 되는" 상황이 생깁니다.

- **체크포인팅**: 시나리오 실행 중간 상태(시뮬레이션 스텝, 랜덤 시드)를 주기적으로 저장해, 스팟 회수 시 처음부터 재시작하지 않도록 합니다. Ray라면 태스크 단위 재시도(`max_retries`)와 체크포인트를 조합해, 회수된 워커의 작업만 다른 워커에서 이어받게 할 수 있습니다.
- **시드 고정**: 물리 엔진·센서 노이즈·에이전트 행동의 랜덤 시드를 시나리오 메타데이터에 명시적으로 박아두고, 재실행 시 동일 시드로 스케줄링해야 "같은 실패"를 재현할 수 있습니다. 어떤 노드/GPU에서 돌았는지가 아니라 시드와 입력이 결과를 결정하도록 파이프라인을 설계하는 것이 핵심입니다. 즉 재현성의 책임을 인프라(어느 노드에서 돌았는가)가 아니라 애플리케이션 레이어(시드가 고정됐는가)로 옮겨야, 스팟처럼 비결정적인 인프라 위에서도 안전합니다.
- **단계별 차등**: 온디맨드/스팟 혼합 노드 풀을 두고, CPU 단계는 스팟에, 마지막 GPU 인지 단계처럼 중단 시 재실행 비용이 큰 단계는 온디맨드에 배치하는 식으로 단계별로 차등을 두는 것도 실전에서 자주 쓰는 절충입니다. 파이프라인 앞단(재실행이 싸다)일수록 스팟 비중을 높이고, 뒷단(재실행이 비싸다)일수록 온디맨드 비중을 높이는 것이 원칙입니다.

## 2. GPU 큐 우선순위와 공정 배분

수천 개 시나리오가 GPU 큐 하나에 몰리면, 급한 PR 검증(수십 개 스모크 테스트)이 야간 풀 회귀(수천 개) 뒤에 밀려 몇 시간씩 기다리는 문제가 생깁니다. 이건 단순히 "먼저 온 순서대로 처리"하는 FIFO 큐의 구조적 한계입니다.

- [Kueue](https://kueue.sigs.k8s.io/)(K8s)나 Slurm의 QoS/우선순위 큐처럼, **워크로드 클래스별로 별도 큐 + 우선순위 + 쿼터**를 두는 것이 표준적인 해법입니다. PR 검증용 큐는 낮은 지연시간을 보장받는 소규모 쿼터를, 야간 풀 회귀 큐는 유휴 자원을 흡수하는 낮은 우선순위 큐를 갖는 구조가 흔합니다.
- Ray 클러스터를 워크로드별로 분리(경량 PR 검증 클러스터 vs 대규모 야간 클러스터)해서 애초에 자원 경합 자체를 없애는 방법도 있습니다. 비용은 늘지만 운영이 단순해집니다.
- Kueue를 쓴다면 `ClusterQueue`에 `nominalQuota`로 PR 검증 큐의 최소 GPU 보장량을 설정하고, 야간 배치 큐는 `borrowingLimit`으로 유휴 자원만 빌려 쓰게 하는 식으로 두 워크로드가 서로를 굶기지 않게 합니다.

## 3. 정리

비용과 속도, 재현성은 셋 다 동시에 최대화할 수 없는 트레이드오프입니다. 이 시리즈에서 다룬 흐름을 정리하면:

1. **[오케스트레이터 선택](../cloud-orchestrator-comparison/)**: K8s(인프라 기반) + Ray(KubeRay, 태스크 세밀 스케줄링) 조합이 현실적인 시작점이고, 온프레미스 GPU 자산이 있다면 Slurm을 클라우드 버스트 대상으로 연결한다.
2. **[CPU/GPU 혼합 배치 스케줄링](../cpu-gpu-mixed-batch-scheduling/)**: 파이프라인을 CPU/GPU 단계로 쪼개고, fractional GPU 할당과 LPT 정렬로 자원을 촘촘히 채운다.
3. **스팟 비용·재현성·큐 우선순위 (이 글)**: 체크포인팅과 시드 고정으로 스팟 인스턴스의 비결정성을 흡수하고, 워크로드 클래스별 큐 분리로 급한 검증이 야간 배치에 밀리지 않게 한다.

이 파이프라인의 출력(시나리오별 메트릭, 실패 케이스)을 다시 [Arrow 기반 데이터 스택](../../data-infra/closed-loop-regression-with-dora/)에 태우면, 회귀 테스트 결과를 py123d/FiftyOne/Rerun으로 그대로 이어서 분석할 수 있습니다.
