## 1. 왜 오케스트레이터 선택이 중요한가

시뮬레이션 회귀 테스트를 클라우드에서 돌린다고 하면 "그냥 Job을 N개 만들면 되는 거 아닌가?"라고 생각하기 쉽습니다. 하지만 자율주행 시뮬레이션 워크로드는 일반적인 배치 작업과 다른 성격을 갖습니다.

- **작업 하나가 이종(heterogeneous) 리소스를 요구합니다.** 시나리오 재생·물리 시뮬레이션은 CPU 바운드지만, 센서 렌더링(카메라·LiDAR)과 인지 모델 추론은 GPU가 필요합니다. 같은 파이프라인 안에 CPU 전용 단계와 GPU 필수 단계가 섞여 있습니다.
- **시나리오마다 실행 시간 편차가 큽니다.** 5초짜리 단순 차선 유지 시나리오와 120초짜리 다중 에이전트 교차로 시나리오가 같은 큐에 섞여 있으면, naive한 균등 분배는 GPU를 놀립니다.
- **수천 개를 한꺼번에 던지면 GPU 노드는 항상 병목입니다.** CPU 노드는 오토스케일링으로 쉽게 늘릴 수 있지만 GPU는 비싸고 쿼터가 제한적입니다.
- **실패 시나리오의 재현성이 생명입니다.** 회귀 테스트는 "왜 실패했는지" 나중에 다시 돌려봐야 하므로, 스케줄링이 비결정적으로 자원을 섞어버리면 재현이 깨집니다.

결국 문제는 "병렬로 많이 돌리는 것"이 아니라 **"이종 자원 요구를 가진 수천 개의 불균일한 작업을 자원 낭비 없이, 재현 가능하게 스케줄링하는 것"**이고, 이 목표를 어떤 도구로 달성할지가 이 글의 주제입니다.

## 2. Kubernetes (K8s)

원래 장기 실행 서비스를 위한 오케스트레이터지만, `Job`/`Indexed Job`과 오토스케일러(Cluster Autoscaler, Karpenter)를 결합하면 배치 워크로드에도 쓸 수 있습니다.

- **장점**: 클라우드 네이티브 생태계(스토리지, 네트워킹, IAM, 모니터링)와 자연스럽게 통합됩니다. 이미 마이크로서비스를 K8s로 운영 중이라면 인프라를 하나로 통일할 수 있습니다.
- **단점**: 태스크 간 의존성(DAG), 세밀한 리소스 fractional allocation, 동적 리소스 재할당 같은 배치 스케줄링 기능이 기본적으로 약합니다. [Volcano](https://volcano.sh/), [Kueue](https://kueue.sigs.k8s.io/) 같은 배치 스케줄러 플러그인을 얹어야 실전에서 쓸 만해집니다.

## 3. Ray

파이썬 네이티브 분산 컴퓨팅 프레임워크로, `ray.remote` 데코레이터 하나로 함수를 클러스터 어디서든 실행할 수 있습니다.

- **장점**: 이종 리소스 요청(`num_cpus`, `num_gpus`, `resources={"custom": 1}`)을 태스크 단위로 세밀하게 지정할 수 있어, CPU 시뮬레이션 단계와 GPU 렌더링 단계를 같은 파이프라인 안에서 자연스럽게 나눠 스케줄링합니다. Ray Data / Ray Train과의 통합도 좋아서, 시뮬레이션 결과를 바로 다음 학습 파이프라인으로 흘릴 수 있습니다.
- **단점**: 클러스터 운영(오토스케일러, 장애 복구, 멀티테넌시 격리)을 K8s만큼 성숙하게 지원하려면 [KubeRay](https://github.com/ray-project/kuberay)를 얹어야 합니다. 즉 "Ray 단독"보다는 "K8s 위의 Ray"가 실전 조합이 됩니다.

## 4. Slurm

HPC 진영에서 수십 년간 검증된 배치 스케줄러입니다.

- **장점**: gang scheduling(작업에 필요한 모든 노드를 한 번에 확보), 세밀한 큐/우선순위/공정 배분(fair-share) 정책, GPU 토폴로지를 고려한 배치가 매우 성숙합니다. 온프레미스 GPU 클러스터나 슈퍼컴퓨팅 자원을 쓰는 조직이면 이미 Slurm 위에 다른 워크로드가 돌고 있을 가능성이 높습니다.
- **단점**: 클라우드 오토스케일링, 컨테이너 네이티브 워크플로우, 서비스 메시 같은 클라우드 네이티브 도구들과의 통합이 K8s보다 무겁습니다.

---

## 5. 실전 조합: 하나를 고르지 않는다

세 개 중 하나를 고르는 문제라기보다, **역할을 나눠 조합하는 경우가 많습니다.**

- K8s를 클러스터의 기반 레이어(노드 프로비저닝, 네트워킹, 시크릿, 모니터링)로 두고
- 그 위에 Ray(KubeRay)를 얹어 시나리오 단위 태스크 스케줄링과 CPU/GPU 이종 자원 배분을 맡기고
- 온프레미스 GPU 팜이 따로 있다면 Slurm 클러스터를 별도로 두고 클라우드 버스트(cloud burst)로 K8s/Ray 쪽에 오버플로우 물량을 흘려보내는 구조가 흔합니다.

수천 개 시나리오 규모라면, **K8s + Ray(KubeRay) 조합**이 클라우드 자원 탄력성과 태스크 세밀도 사이에서 가장 균형 잡힌 선택지인 경우가 많습니다.

각 도구를 실제로 어떻게 구성하는지는 [Kubernetes 실전](../k8s-batch-scheduling-with-kueue/), [Ray/KubeRay 입문](../ray-kuberay-for-beginners/), [Slurm 실전](../slurm-batch-scheduling/)에서 각각 다룹니다. 이어서 [시뮬레이션 배치 스케줄링 실전](../batch-scheduling-strategies/)에서 도구와 무관하게 적용되는 범용 전략을 정리합니다.
