## 1. 인프라와 도구 사이의 빠진 층

지금까지 이 시리즈가 다룬 것들 — K8s Job, Kueue, LPT 스케줄링, 재현성 — 은 전부 "시나리오 하나를 어떻게 정확하고 효율적으로 돌리는가"에 대한 답입니다. 그런데 실무에서 회귀 테스트가 실제로 굴러가려면 다른 질문에도 답해야 합니다 — **"오늘 이 지도 20개에 이 시나리오 50개를 돌려보고 싶은데, 누가 무엇을 어떻게 트리거하고, 그 결과를 누가 어떻게 확인하는가?"**

이 질문에 CLI나 사내 스크립트로 답하면 당장은 되지만, 몇 가지가 반드시 새기 시작합니다.

- 트리거할 수 있는 사람이 인프라를 이해하는 소수로 좁혀집니다 — 시나리오 작성자나 QA는 결국 인프라 담당자에게 "이거 좀 돌려주세요"라고 부탁하게 됩니다.
- 결과가 로그 파일이나 Slack 메시지로 흩어지고, "이 지도에서 최근 한 달간 실패율이 어떻게 바뀌었는가" 같은 질문에 답하려면 누군가 수작업으로 집계해야 합니다.
- 실패 케이스를 실제로 들여다보려면(영상, 센서 로그) 담당자만 아는 경로를 찾아 들어가야 합니다.

즉 인프라 레이어(Argo/K8s)와 분석 레이어([FiftyOne/Rerun 파이프라인](../../data-infra/autonomous-data-pipeline/)) 사이에, 그 둘을 이어주고 접근성을 팀 전체로 넓히는 **제품 레이어**가 빠져 있습니다. 이 글은 그 레이어를 무엇으로 채울지에 대한 이야기입니다.

## 2. 오케스트레이션: Argo Workflows를 얹는 이유

[K8s 실전](../k8s-batch-scheduling-with-kueue/)에서 Indexed Job과 Kueue로 배치를 돌리는 법을 다뤘습니다. 이 위에 Argo Workflows를 얹는 이유는 도구를 하나 더 배우기 위해서가 아니라, 웹 대시보드가 백엔드에 요구하는 것과 Argo가 기본 제공하는 것이 정확히 겹치기 때문입니다.

- **파라미터화된 대량 병렬 실행이 Argo의 1급 기능입니다.** "같은 템플릿을 (지도, 시나리오) 조합만 바꿔 수천 번 실행"은 ML 그리드 서치에서 이미 검증된 Argo의 대표 사용 패턴과 구조적으로 동일합니다.
- **Job 정리(GC)와 결과 아카이빙을 직접 안 짜도 됩니다.** 순수 K8s Job을 수천 개 직접 만들면 완료된 오브젝트가 etcd에 쌓이는 걸 스스로 정리해야 하는데, Argo의 Workflow Archive는 완료된 실행을 자동으로 Postgres에 적재합니다 — 대시보드가 어차피 필요로 하는 "결과를 DB에 쌓기"의 상당 부분을 공짜로 얻습니다.
- **재시도·백오프가 필드 설정만으로 됩니다.** "인프라 일시 오류"와 "진짜 테스트 실패"를 구분하는 로직은 직접 짜면 은근히 버그가 잦은 지점인데, Argo는 이 정책을 선언적으로 붙일 수 있습니다.
- **디버깅용 웹 UI가 따로 딸려 옵니다.** (3절에서 이어서 다룹니다.)

주의할 점은, Argo의 핵심 강점(DAG, 단계 간 의존성)은 이 워크로드에서 거의 안 쓴다는 것입니다 — 지도×시나리오 조합은 서로 완전히 독립적인 병렬 작업이라 파이프라인 엔진이 원리적으로 필요하지 않습니다. 그럼에도 Argo를 택하는 이유는 DAG가 아니라 **대량 파라미터화 실행·재시도·아카이빙이라는 운영 편의**에 있습니다. 오케스트레이션 코드를 백엔드 안에서 독립된 모듈로 분리해두면, 나중에 이 판단이 틀렸다고 밝혀져도(예: DAG가 필요 없으니 순수 K8s Job으로 충분하다는 결론이 나면) 그 모듈만 바꾸면 되고 나머지 시스템은 그대로 남습니다.

### 왜 Tekton·Airflow·Volcano가 아닌가

- **Tekton**도 K8s 네이티브 CRD 기반이지만, 원래 CI/CD(빌드→테스트→배포)처럼 **순차 파이프라인**에 맞춰 설계됐습니다. "독립적인 작업 수천 개를 매트릭스로 펼치는" 패턴은 Argo의 `withParam`만큼 관용적으로 지원하지 않습니다.
- **Airflow**(KubernetesExecutor)는 백엔드가 이미 Python이라는 점에서 매력적이고, 스케줄링·모니터링 UI는 오히려 Argo보다 성숙합니다. 다만 스케줄러·웹서버·메타데이터 DB를 별도로 운영해야 해서 이 정도 규모에 비해 무겁고, 원래 ETL류의 정기 파이프라인에 맞춰진 도구라 "대량 병렬 배치 제출"은 부차적인 사용 사례입니다.
- **Volcano**는 애초에 워크플로우 엔진이 아니라 **배치 스케줄러**라 비교 대상이 아닙니다 — GPU 노드가 부족해 여러 팀이 경쟁하는 공정 분배(gang scheduling) 문제가 실제로 커지면, Argo를 대체하는 게 아니라 그 아래에 Volcano를 얹어 "Argo가 제출한 Pod를 Volcano가 공정하게 스케줄링"하는 조합으로 가는 경우가 많습니다.

## 3. Argo UI와 대시보드: 왜 둘 다 필요한가

Argo Server를 띄우면 워크플로우 그래프, 파드 상태, 실시간 로그를 보여주는 웹 UI가 기본으로 딸려 옵니다. 이걸 보면 "그럼 대시보드를 따로 만들 필요가 있나"라는 질문이 자연스럽게 나오는데, 둘은 보는 관점 자체가 다릅니다.

- **Argo UI는 엔지니어의 운영 관점입니다.** "이 특정 실행이 왜 멈췄는가", "이 파드가 지금 뭘 찍고 있는가"처럼 실행 하나를 파고드는 질문에 답합니다.
- **커스텀 대시보드는 팀의 제품 관점입니다.** "이번 배치 합격률이 87%다", "이 지역 지도에서 유독 실패가 몰린다"처럼 수천 개를 가로질러 요약하는 질문에 답합니다.

Argo UI가 실시간 로그 스트리밍 같은 걸 이미 잘 하고 있으므로, 그걸 대시보드 안에 다시 구현하는(웹소켓 붙이고 로그 파싱하는) 대신, **결과 테이블의 각 행에 "원본 로그는 Argo UI에서" 링크 하나만 걸어주는 것**이 훨씬 적은 코드로 같은 가치를 냅니다 — 앞서 뷰어 통합에서 FiftyOne/Rerun에 적용한 "새로 만들지 않고 딥링크로 연결한다"는 원칙을 Argo UI에도 그대로 적용하는 것뿐입니다. 다만 Argo UI를 팀 전체에 노출하려면 대시보드의 로그인과는 별개로 자체 인증(SSO/RBAC)을 설정해야 한다는 점은 미리 챙겨둬야 합니다.

## 4. 백엔드: FastAPI를 택하는 이유는 취향이 아니다

프론트엔드 언어(TypeScript)와 달리, 백엔드 언어는 사실상 정해져 있었습니다 — 이 시리즈가 지금까지 다뤄온 도구들이 전부 Python 중심이기 때문입니다.

- **FiftyOne**은 범용 REST API가 없고, 데이터셋에 샘플을 추가하거나 태깅하는 작업은 공식적으로 Python SDK로만 합니다.
- **Kubernetes 파이썬 클라이언트**가 가장 성숙하고 예제가 많습니다.
- **Rerun**도 Python SDK가 1급으로 지원됩니다.

백엔드가 Node.js나 Go였다면, 이 셋을 다루기 위해 별도 Python 사이드카나 스크립트 실행 계층을 하나 더 둬야 했을 것입니다. FastAPI를 택하면 "k8s에 Job/Workflow를 제출하고, 결과를 FiftyOne 데이터셋에 등록하고, DB에 기록하는" 세 가지 일을 한 언어, 한 프로세스 안에서 자연스럽게 연결할 수 있습니다. 프론트엔드와는 REST로 완전히 분리되어 있으므로, 프론트가 어느 언어든 이 선택에 영향을 주지 않습니다.

## 5. 프론트엔드: TypeScript + Refine — 코드보다 패턴을 산다

프론트엔드에서 필요한 화면은 결국 세 가지입니다 — 지도·시나리오를 고르는 폼, 실행 현황 테이블, 결과 집계 대시보드. 이건 전부 "목록 + 필터 + 폼"이라는, 어드민 도구가 수백 번 반복해온 패턴입니다.

React를 그대로 쓰면 이 패턴(API 연동, 테이블 정렬·페이지네이션, 폼 검증, 라우팅)을 매번 직접 조립해야 합니다. **Refine.dev**는 React 위에서 이 반복 작업을 프레임워크가 대신 처리해주는 계층입니다 — `useTable()`, `useForm()` 같은 훅이 API 연동부터 상태 관리까지 알아서 하고, 리소스를 하나 등록하면 목록/상세/생성/수정 화면과 라우팅이 자동으로 따라옵니다. 이 프로젝트에 필요한 화면 종류(테스트 실행, 테스트 결과, 가상 데이터 카탈로그)가 전부 같은 "리소스 하나 = CRUD 화면 세트"라는 틀에 들어맞기 때문에, Refine이 아끼는 코드량이 큽니다.

여기서 파이썬 기반 프레임워크(Streamlit 등)를 쓰지 않은 이유도 짚어둘 만합니다. Streamlit류는 위젯이 바뀔 때마다 스크립트 전체를 다시 실행하는 구조라, 기능이 늘고 데이터가 커질수록 그 자체가 병목이 됩니다. 화면이 세 개 이상으로 늘어나고 인터랙션이 복잡해질 걸 예상한다면, 처음부터 이벤트 기반으로 동작하는 React 계열이 나중에 다시 짜지 않아도 되는 선택입니다.

### 왜 Dash·Appsmith가 아닌가

- **Dash**(Plotly)는 콜백 기반이라 Streamlit의 "전체 재실행" 문제를 구조적으로 피하면서도 파이썬 언어를 유지할 수 있는 좋은 대안입니다. 다만 백엔드(FastAPI)와 프론트엔드를 완전히 분리해 REST로만 통신하게 하려는 이번 설계 방향과는, 파이썬 하나로 프론트/백을 합치는 Dash의 철학이 맞지 않습니다.
- **Appsmith**(오픈소스 로우코드)는 테이블·폼·차트를 DB/API에 드래그앤드롭으로 붙이는 전형적인 내부 어드민 패턴에 가장 빠른 선택지입니다. 프론트엔드 코드를 사실상 안 짜도 되는 대신, 나중에 지도 위에 커스텀 인터랙션(시나리오를 지도에서 직접 선택하는 등)을 얹으려면 로우코드 도구의 한계에 부딪히기 쉽습니다. 커스텀 UI로 자라날 여지를 열어두고 싶어서 진짜 React 앱(Refine)을 택했습니다.

## 6. 뷰어 통합: 새로 만들지 않고 공유 서비스로 연결한다

[FiftyOne/Rerun 파이프라인](../../data-infra/autonomous-data-pipeline/)이 이미 있다는 전제에서, 대시보드가 할 일은 뷰어를 다시 만드는 게 아니라 **이미 있는 뷰어에 정확한 데이터를 연결**하는 것뿐입니다.

- **Rerun**은 recording(`.rrd`)이 그냥 정적 파일이라, NuRec 파드가 끝날 때 결과와 함께 오브젝트 스토리지에 올려두면 됩니다. Rerun 웹 뷰어는 `?url=`로 임의의 `.rrd`를 로드하므로, 뷰어는 공유 인스턴스 하나만 띄워두고 결과 테이블에서 각 케이스의 `.rrd` URL만 넘겨주면 됩니다.
- **FiftyOne**도 마찬가지로 App 인스턴스 하나를 공유하고, 각 테스트 결과를 데이터셋 샘플로 등록할 때 `test_case_id`를 태그로 붙여, 대시보드에서 그 태그로 필터링된 뷰로 딥링크합니다.

수천 개 조합 규모에서 테스트마다 뷰어 인스턴스를 새로 띄우는 건 감당이 안 됩니다 — "뷰어는 하나, 대시보드는 그 뷰어에 맞는 URL/쿼리를 만들어주는 역할만 한다"는 원칙이 이 규모에서 유일하게 현실적인 접근입니다.

## 7. 전체 그림과 각 선택의 대가

```
[TS + Refine 프론트]  ──REST──▶  [FastAPI 백엔드]  ──워크플로우 제출──▶  [Argo Workflows]
                                        │                                      │
                                        │                                Pod 생성·재시도
                                        ▼                                      ▼
                                  [Postgres]  ◀──아카이브──────────  (NuRec 컨테이너 실행)
                                        │                                      │
                                        │                              결과 업로드(S3 등)
                                        ▼                                      ▼
                              (결과 집계·필터 조회)              [공유 Rerun 뷰어] [공유 FiftyOne App]
                                                                   (URL/필터 딥링크로 연결)
```

이 조합에서 대가로 치른 것도 정직하게 짚어야 합니다 — Argo는 이 워크로드에서 안 쓰는 기능(DAG)까지 포함된 도구를 들여오는 것이고, Refine은 아주 특이한 인터랙션을 만들 때는 순수 React보다 손이 더 갈 수 있습니다. 두 경우 다, "지금 반복적으로 발생하는 문제(대량 파라미터 실행, CRUD 화면 반복)를 얼마나 줄여주는가"가 "이 도구가 안 쓰는 기능이 있다"는 단점보다 크다고 판단했기 때문에 고른 선택입니다 — 프로젝트가 자라면서 이 판단이 바뀔 수 있다는 것 자체를, 오케스트레이션 모듈을 백엔드 안에서 분리해두는 식으로 미리 대비해두는 게 이런 종류의 아키텍처 결정에서는 항상 남는 숙제입니다.
