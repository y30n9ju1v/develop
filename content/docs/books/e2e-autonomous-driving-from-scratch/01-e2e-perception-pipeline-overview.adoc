'''

이 책은 "센서 데이터가 들어가서 궤적이 나오는" 하나의 파이프라인을 처음부터 끝까지 짓습니다. 코드를 쓰기 전에, 그 파이프라인이 어떤 모양의 데이터를 어떤 순서로 거쳐가는지 먼저 확정해두면, 이후 각 장에서 "지금 이 텐서가 무슨 의미인지" 헷갈릴 일이 줄어듭니다. 이 장에서는 실제 계산 내용 없이, 파이프라인 전체의 텐서 모양(shape)만 PyTorch로 확인합니다.

== 이 책의 표준 설정

[source,python]
----
N_CAMS = 6              # nuScenes 스타일: 전방/전측방/후측방 6대
IMG_H, IMG_W = 32, 32     # 이 책에서 다루는 특징맵 크기 (실전은 보통 훨씬 큼)
FEAT_C = 16
BEV_H, BEV_W = 40, 40      # BEV 격자: 자아차량 기준 전후좌우 각 20m, 1m 해상도
BEV_C = 32
N_FUTURE_STEPS = 12        # 미래 6초를 0.5초 간격으로 예측
----

`BEV_H, BEV_W = 40, 40`은 자아차량을 중심으로 가로세로 `40m`(한 칸이 `1m`)를 내려다본 격자를 뜻합니다 — "지금 내 주변 어디에 무엇이 있는가"를 위에서 내려다본 지도 한 장으로 표현하는 것이 BEV(Bird's Eye View)의 핵심 아이디어이고, 2부에서 이 격자를 실제로 채우는 법을 다룹니다.

== 1~3단계: 원시 센서 입력

[source,python]
----
images = torch.randn(N_CAMS, 3, 128, 128)   # (카메라 수, RGB, H, W)
lidar_points = torch.randn(5000, 4)          # (포인트 수, [x,y,z,반사강도])
----

`6`대의 카메라가 각자 `128×128` RGB 이미지를(실전에서는 훨씬 크지만, 이 책에서는 원리에 집중하기 위해 축소합니다), 라이다가 `5000`개의 3D 점을 냅니다. 이 시점에서 카메라 이미지와 라이다 점은 **서로 다른 좌표계**에 있습니다 — 카메라 이미지는 각 카메라 렌즈를 중심으로 한 2D 픽셀 좌표, 라이다 점은 자아차량을 중심으로 한 3D 좌표입니다. 2~3장에서 이 좌표계들을 하나로 통일합니다.

== 4단계: BEV로 융합

[source,python]
----
bev_features = torch.randn(BEV_C, BEV_H, BEV_W)
assert bev_features.shape == (BEV_C, BEV_H, BEV_W)
----

서로 다른 좌표계에 있던 카메라 특징과 라이다 점들이, `40×40` 크기의 공통 BEV 격자 위의 `32`차원 특징 벡터로 합쳐집니다 — 이게 이 책 2부의 핵심 목표입니다.

== 5단계: Transformer로 BEV를 더 풍부하게

[source,python]
----
bev_tokens = bev_features.flatten(1).transpose(0, 1)   # (BEV_H*BEV_W, BEV_C)
assert bev_tokens.shape == (BEV_H * BEV_W, BEV_C)
----

Transformer는 격자가 아니라 "토큰의 나열"을 다루므로, `40×40` 격자를 `1600`개의 토큰으로 펼칩니다 — 격자 칸 하나하나가 토큰 하나가 됩니다. 3부에서 이 토큰들이 서로(그리고 원본 카메라 특징과) attention을 주고받으며 각 칸의 특징이 더 풍부해지는 과정을 다룹니다. 인코더를 거쳐도 모양 자체는 그대로입니다 — attention은 내용을 바꿀 뿐 모양을 바꾸지 않습니다.

== 6단계: Planning Head로 궤적 뽑아내기

[source,python]
----
trajectory = torch.randn(N_FUTURE_STEPS, 2)   # 미래 각 시점의 (x, y)
assert trajectory.shape == (N_FUTURE_STEPS, 2)
----

최종 출력은 미래 `12`개 시점(`0.5`초 간격, `6`초 앞까지) 각각의 `(x, y)` 위치입니다 — `1600`개의 BEV 토큰이라는 풍부한 표현이, 최종적으로는 이 작은 숫자 `24`개(`12×2`)로 압축됩니다. 4부에서 이 압축을 담당하는 Planning Head를 다룹니다.

== 전체 흐름을 한 번에

[source,python]
----
print(images.shape)             # torch.Size([6, 3, 128, 128])
print(camera_features.shape)    # torch.Size([6, 16, 32, 32])
print(bev_features.shape)       # torch.Size([32, 40, 40])
print(encoded_bev_tokens.shape) # torch.Size([1600, 32])
print(trajectory.shape)         # torch.Size([12, 2])
----

이 다섯 줄이 이 책 전체의 지도입니다 — 2부는 첫 세 줄 사이(카메라·라이다 → BEV)를, 3부는 네 번째 줄(BEV → 인코딩된 BEV)을, 4부는 마지막 줄(인코딩된 BEV → 궤적)을 다룹니다.

== 왜 이 책은 "축소된" 스케일을 쓰는가

[source,python]
----
full_scale_bev = (256, 200, 200)      # 실전 BEVFormer 근처 스케일
this_book_bev = (32, 40, 40)           # 이 책의 스케일
ratio = np.prod(full_scale_bev) / np.prod(this_book_bev)
print(ratio)   # 200
----

실전 BEVFormer 스케일의 BEV 텐서는 이 책에서 다루는 것보다 원소 개수 기준으로 `200`배 큽니다 — 채널 수(`256` vs `32`), 격자 해상도(`200×200` vs `40×40`) 모두에서 훨씬 큽니다. 이 책이 작은 스케일을 쓰는 이유는 명확합니다 — 원리(좌표 변환의 정확성, attention이 실제로 올바른 곳을 참조하는지, 궤적 예측의 손실이 실제로 내려가는지)를 검증하는 데는 실전 스케일이 전혀 필요 없고, 오히려 작은 스케일이라야 한 장 한 장 실제로 실행하고 눈으로 확인할 수 있습니다. 원리를 다진 뒤에 스케일을 키우는 건 순전히 계산 자원의 문제이지, 이 책에서 다루는 개념적인 어려움은 아닙니다.

== 직접 해보기

* `N_CAMS`를 `6`에서 `1`(전방 카메라 하나만)로 줄이면, 파이프라인의 어느 단계까지는 그대로 작동하고 어느 단계부터 문제가 생기는지 생각해보세요(아직 구현 전이니, 셰이프 설계도만으로 추론해보세요).

.해답 보기
[%collapsible]
====
[source,python]
----
N_CAMS_single = 1
images_single = torch.randn(N_CAMS_single, 3, 128, 128)
camera_features_single = torch.randn(N_CAMS_single, 16, 32, 32)
# BEV 융합 단계까지는 셰이프상 문제없이 흘러감 (카메라가 몇 대든 BEV_H x BEV_W는 고정)
bev_features_single = torch.randn(32, 40, 40)
print(bev_features_single.shape)   # 여전히 (32, 40, 40)
----

셰이프만 놓고 보면 카메라가 `1`대든 `6`대든 파이프라인은 끝까지 잘 흘러갑니다 — BEV 격자의 크기는 카메라 개수와 무관하게 고정이기 때문입니다. 하지만 **내용**은 완전히 달라집니다 — 카메라가 `1`대(전방)뿐이면, 차량 후방이나 측면에 있는 물체는 어느 카메라에서도 안 보이므로 BEV 격자의 그 부분은 텅 비게(또는 순전히 라이다에만 의존하게) 됩니다. 셰이프 검증은 "코드가 에러 없이 돌아가는가"만 확인해줄 뿐, "그 결과가 실제로 의미 있는가"는 전혀 보장하지 않는다는 걸 기억해둘 만합니다 — 이후 장들에서 실제 값을 채워가며 이 차이를 계속 마주치게 될 것입니다.
====

== 요약

* 이 책의 파이프라인은 다중 카메라 이미지 + 라이다 점군 → BEV 융합 → Transformer 인코더 → Planning Head → 미래 궤적 순서로 흐릅니다.
* 각 단계에서 텐서의 모양이 어떻게 바뀌는지(그리고 언제 모양이 그대로 유지되는지) 미리 확인해뒀습니다 — `(6,3,128,128)` → `(32,40,40)` → `(1600,32)` → `(12,2)`.
* 이 책은 실전 스케일보다 `200`배 작은 BEV 텐서로 원리를 다루며, 이는 계산 자원의 선택이지 개념의 단순화가 아닙니다.
* 셰이프가 맞는다고 결과가 의미 있는 건 아니라는 것 — 앞으로의 장들에서 각 단계가 실제로 "옳은" 값을 만들어내는지를 검증하는 것이 이 책의 핵심 작업입니다.
