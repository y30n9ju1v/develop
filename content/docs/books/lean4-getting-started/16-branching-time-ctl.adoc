NOTE: 14~16장 보너스 3부작의 마지막입니다. 이 장은 14~15장의 ``LTL``과 독립적인 새 타입(``CTL``)을 만들지만, 그 설계 방식(`inductive` 문법 + 재귀적 만족 관계)은 그대로 재사용합니다.

== LTL이 놓친 것: "경로가 하나뿐"이라는 가정

14장의 ``Trace``는 ``Nat → Atom → Bool``, 즉 **하나로 정해진** 무한 실행 흐름이었습니다. 그런데 실제 시스템 — 동시성 프로그램, 사용자 입력을 받는 상태 기계, 네트워크 프로토콜 — 은 한 상태에서 다음 상태로 갈 때 선택지가 여러 개인 경우가 많습니다. "지금 상태에서 어떤 선택을 하든" 성립해야 하는 성질과 "어떤 선택을 하면" 성립할 수 있는 성질은 서로 다른 이야기입니다.

* "신호등이 고장 나면, **어떤 경로를 밟든** 결국 빨간불로 복귀한다" — 모든 경로에서.
* "이 버튼을 누르면, **적어도 한 가지 방법으로는** 목표 상태에 도달할 수 있다" — 어떤 경로가 존재해서.

이 둘을 구분하려면 "실행 흐름 하나"가 아니라 "상태에서 상태로의 전이 관계" 자체를 다뤄야 합니다. 이런 논리를 **분기 시제논리(Computation Tree Logic, CTL)**라고 부릅니다 — 매 상태가 트리처럼 여러 갈래로 뻗어나갈 수 있다는 뜻입니다.

== 전이 관계: 함수 대신 관계

14장의 ``Trace``는 "다음이 무엇인지 이미 정해진" 함수였습니다. 분기를 표현하려면 "``s``에서 ``s'``로 갈 수 **있다**"는 관계로 바꿔야 합니다. 3장에서 ``inductive``로 자료구조를 빚었던 것과 똑같은 도구로, 이번엔 **관계**를 빚습니다.

[source,lean]
----
inductive St where | A | B | C
  deriving DecidableEq, Repr

inductive step : St → St → Prop where
  | AB : step .A .B
  | AC : step .A .C
  | BA : step .B .A
  | CC : step .C .C
----

``step``은 세 상태 ``A``, ``B``, ``C``로 이뤄진 아주 작은 시스템입니다 — ``A``에서는 ``B``로도 ``C``로도 갈 수 있고(**분기**가 일어나는 지점), ``B``에서는 다시 ``A``로 돌아오고, ``C``는 한번 도달하면 계속 ``C``에 머뭅니다(자기 자신으로의 전이). ``step``이 ``Prop``을 반환한다는 게 핵심입니다 — "``A``에서 다음 상태"는 함수처럼 하나로 정해지지 않고, "``A``에서 ``B``로 가는 것이 성립한다"는 증명 가능한 사실일 뿐입니다.

== CTL 논리식과 경로 정량화

CTL 논리식 자체는 14장의 ``LTL``과 거의 같은 모양입니다. 다른 건 ``eventually``/``always`` 대신, "경로를 하나 골라서"(``EF``)와 "어떤 경로를 고르든"(``AG``)이라는 **경로에 대한 정량화**가 논리식 안에 직접 들어간다는 점입니다.

[source,lean]
----
inductive CTL (State : Type) where
  | atomP (p : State → Prop)
  | not (φ : CTL State)
  | and (φ ψ : CTL State)
  | EF (φ : CTL State)   -- 어떤 경로가 존재해서, 그 경로 위 어느 시점에 φ
  | AG (φ : CTL State)   -- 모든 경로에서, 항상 φ
----

``EF``(Exists-Finally)는 "존재하는 어떤 경로 위에서 언젠가"라는 뜻으로 14장의 ``◇``에 경로의 존재성이 더해진 것이고, ``AG``(All-Globally)는 "모든 경로 위에서 항상"이라는 뜻으로 14장의 ``□``에 "모든 경로에 대해"가 더해진 것입니다. ``atomP``가 ``LTL``의 ``atom``과 달리 ``State → Prop``(술어)을 직접 받는 것도 눈여겨볼 만합니다 — 14장에서는 원자명제가 참/거짓 표를 미리 정해둔 ``Trace``에 의존했지만, 여기서는 굳이 그럴 필요 없이 "이 상태가 만족하는 조건"을 직접 함수로 씁니다.

== 만족 관계: 경로를 직접 만들어 증명하는 존재문

[source,lean]
----
def satC {State : Type} (step : State → State → Prop) (s : State) : CTL State → Prop
  | .atomP p => p s
  | .not φ => ¬ satC step s φ
  | .and φ ψ => satC step s φ ∧ satC step s ψ
  | .EF φ => ∃ path : Nat → State, path 0 = s ∧ (∀ n, step (path n) (path (n+1))) ∧
      ∃ n, satC step (path n) φ
  | .AG φ => ∀ path : Nat → State, path 0 = s → (∀ n, step (path n) (path (n+1))) →
      ∀ n, satC step (path n) φ
----

``EF``와 ``AG``의 차이는 딱 하나입니다 — "``s``에서 시작해 ``step``을 따라가는 무한 경로"(``path``)를 ``EF``는 ``∃``로, ``AG``는 ``∀``로 정량화합니다. ``EF φ``를 증명하려면 조건을 만족하는 경로를 **직접 하나 만들어서** 보여주면 되고(8장에서 존재 증명에 증인을 제시했던 패턴 그대로), ``AG φ``를 증명하려면 **가능한 모든 경로**에 대해 성립함을 보여야 합니다 — 임의의 ``path``를 받아 그게 무엇이든 결론이 성립함을 보이는, 2장부터 익숙한 "임의의 값에 대한 함수"입니다.

== 예제: A에서 출발해 C에 도달하는 경로가 존재한다

``A``에서 ``B``로도 ``C``로도 갈 수 있었죠. 그중 ``C``로 가는 쪽을 골라 경로를 직접 만들면 ``EF isC``를 증명할 수 있습니다.

[source,lean]
----
def isC : CTL St := .atomP (· = St.C)

example : satC step .A (.EF isC) := by
  refine ⟨fun n => if n = 0 then .A else .C, rfl, ?_, ⟨1, rfl⟩⟩
  intro n
  cases n with
  | zero => exact step.AC
  | succ n => simp; exact step.CC
----

증인으로 제시한 경로는 "``0``번째는 ``A``, 그 이후로는 계속 ``C``"입니다. ``0``에서 ``1``로 넘어갈 때는 ``step.AC``(``A → C``)를, ``1``에서 ``2``로, ``2``에서 ``3``으로... 넘어갈 때는 전부 ``step.CC``(``C``의 자기 전이)를 씁니다. 14장에서 신호등 trace를 손으로 짜 맞췄던 것과 똑같은 감각입니다 — 다만 이번엔 "그 경로가 실제로 ``step``을 따라가는지"까지 증명에 포함됩니다.

== 예제: C에 도달하면 그 뒤로는 항상 C다

``C``는 자기 자신으로만 전이하므로, ``C``에서 시작하는 경로는 사실 단 하나뿐입니다 — 그렇다면 ``AG isC``도 성립해야 합니다. 이번엔 임의의 경로를 받아서 8장 스타일의 귀납 증명으로 보입니다.

[source,lean]
----
theorem step_C_inv {y : St} (h : step .C y) : y = .C := by
  cases h; rfl

example : satC step .C (.AG isC) := by
  intro path hpath0 hstep n
  induction n with
  | zero => exact hpath0
  | succ n ih =>
    show path (n+1) = St.C
    have hs : step (path n) (path (n+1)) := hstep n
    have hn : path n = St.C := ih
    rw [hn] at hs
    exact step_C_inv hs
----

``step_C_inv``는 "``C``에서 갈 수 있는 곳은 ``C``뿐"이라는, ``step``의 정의(생성자가 ``step.CC`` 하나)로부터 바로 나오는 사실입니다. 본 증명은 8장의 귀납법 그대로입니다 — ``n = 0``이면 가정 ``hpath0``으로 바로 끝나고, ``n+1``에서는 귀납 가정(``path n = C``)과 ``step_C_inv``를 이어붙여 ``path (n+1) = C``를 얻습니다.

== 왜 EF와 AG를 구분해야 하는가: A에서는 AG가 성립하지 않는다

``A``에서는 ``B``로 가는 선택지도 있었죠. ``A``와 ``B``를 영원히 오가기만 하고 ``C``로는 절대 가지 않는 경로도 ``step``을 따르는 엄연한 경로입니다 — 그러니 ``A``에서는 "**모든** 경로에서 결국 ``C``"(``AG isC``)가 성립하지 않습니다. ``EF``와 ``AG``가 서로 다른 연산자라는 걸 반증(counterexample)으로 확인해봅시다.

[source,lean]
----
example : ¬ satC step .A (.AG isC) := by
  intro h
  have := h (fun n => if n % 2 = 0 then .A else .B) rfl (by
    intro n
    by_cases hn : n % 2 = 0
    · simp [hn]
      have : (n+1) % 2 = 1 := by omega
      simp [this]
      exact step.AB
    · simp [hn]
      have h2 : (n+1) % 2 = 0 := by omega
      simp [h2]
      exact step.BA) 0
  simp [isC, satC] at this
----

``AG isC``가 참이라고 가정한 뒤(`intro h`), ``A``와 ``B``를 번갈아 오가는 경로를 그 가정에 직접 대입합니다. ``AG``는 "**모든** 경로에서" 성립해야 하므로, 이 특정 경로에도 통해야 합니다 — 그런데 이 경로의 ``0``번째 상태는 ``A``이지 ``C``가 아니므로 모순이 나옵니다. 9장에서 배운 태도 그대로입니다 — "모든 경로"라는 전칭 주장을 반증하려면, 그걸 무너뜨리는 경로 하나만 콕 집어 대입하면 충분합니다.

== 직접 해보기

* ``EF``와 ``or``를 이용해서 "``B``에서도 결국 ``C``에 도달하는 경로가 있다"(``satC step .B (.EF isC)``)를 증명해보세요. ``B → A → C`` 경로를 손으로 만들면 됩니다.
* ``AG``의 정의를 이용해서 "``C``에서 ``AG φ``가 성립하면, ``C`` 자신도 ``φ``를 만족한다"(``satC step .C (.AG φ) → satC step .C φ``)를 증명해보세요. ``C``는 자기 자신으로만 전이하니, "영원히 ``C``에 머무는 경로"(``fun _ => .C``)를 직접 만들어 ``AG``의 정의에 대입하면 됩니다.

.해답 보기
[%collapsible]
====
[source,lean]
----
example : satC step .B (.EF isC) := by
  refine ⟨fun n => match n with | 0 => .B | 1 => .A | _ => .C, rfl, ?_, ⟨2, rfl⟩⟩
  intro n
  match n with
  | 0 => exact step.BA
  | 1 => exact step.AC
  | (k+2) => exact step.CC

example (φ : CTL St) (h : satC step .C (.AG φ)) : satC step .C φ := by
  have := h (fun _ => .C) rfl (fun _ => step.CC) 0
  exact this
----

두 번째 해답이 보여주는 건 ``AG``를 실제로 써먹으려면 정의 안의 ``∀ path``에 **구체적인 경로**를 대입해야 한다는 점입니다 — 여기서는 ``C``가 자기 자신으로만 전이한다는 사실(``step.CC``)이 "영원히 ``C``에 머무는 경로"가 실제로 ``step``을 따른다는 증거를 공짜로 제공해줍니다. 일반적인 상태에서는 이런 경로가 항상 존재하리라는 보장이 없다는 점도 함께 기억해두면 좋습니다 — ``AG``의 정의 자체는 그 경로의 존재를 요구하지 않고, 존재하는 모든 경로에 대해서만 이야기합니다.
====

== 이 장이 왜 중요한가

이 3부작 전체를 관통하는 태도를 마지막으로 확인해봅시다. 14장은 `inductive`로 논리식의 **문법**을 만들고 재귀 함수로 **뜻**을 부여하는 게 다였고, 15장은 그 문법을 새 생성자 없이 조합만으로 확장했고, 16장인 지금은 "실행 흐름이 하나"라는 가정 하나만 "여러 갈래로 갈라질 수 있다"로 바꿨을 뿐인데 완전히 다른 논리 체계(CTL)가 나왔습니다. `inductive` 타입 + 재귀적 만족 관계라는 조합이 얼마나 다양한 논리를 표현할 수 있는지가 이 3부작의 결론입니다.

실제 모델체킹 도구(SPIN, NuSMV 등)는 바로 이런 CTL/LTL 위에서 상태 공간을 자동으로 탐색해 ``EF``/``AG`` 같은 성질을 기계적으로 검사합니다. 이 3부작에서 만든 ``sat``/``satC``는 그 알고리즘이 "무엇을 계산해야 하는가"에 대한 명세이지, 그 계산을 자동으로 해주는 도구는 아닙니다 — 자동 검사 알고리즘까지 Lean으로 구현하는 건 이 책의 범위를 훌쩍 넘어서지만, 여기서 만든 정의가 정확히 그 알고리즘이 옳은지 증명할 때 기준이 되는 명세입니다.

== 요약

* `Trace`(함수)로는 "여러 갈래로 갈라지는" 시스템을 표현할 수 없다 — 전이 **관계**(``State → State → Prop``)가 필요하다.
* CTL 논리식은 ``LTL``과 같은 방식(`inductive` + 재귀적 만족 관계)으로 만들어지지만, ``EF``/``AG``처럼 경로에 대한 ``∃``/``∀``가 논리식 안에 직접 들어간다.
* ``EF φ``를 증명하려면 조건을 만족하는 경로를 직접 만들어 제시하면 되고, ``AG φ``를 증명하려면 임의의 경로를 받아 일반적으로 성립함을 보여야 한다.
* 같은 상태에서도 ``EF``와 ``AG``는 서로 다른 성질이다 — 분기가 있는 시스템에서는 "어떤 경로가 존재해서"와 "모든 경로에서"가 갈릴 수 있고, 이걸 구분하는 게 CTL이 LTL에 없는 표현력이다.
