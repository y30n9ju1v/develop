== 타입 인자로 코드를 재사용하기

3장에서 `MyList α`처럼 타입이 인자를 받는 걸 봤습니다. 함수도 똑같이 타입을 인자로 받을 수 있습니다. 리스트의 첫 원소를 꺼내는 함수를 자연수 리스트, 문자열 리스트마다 따로 짤 필요가 없습니다.

[source,lean]
----
def firstOr (default : α) : List α → α
  | []     => default
  | x :: _ => x

#eval firstOr 0 [1, 2, 3]        -- 1
#eval firstOr "?" (["a"] : List String)  -- "a"
----

`α`는 "아무 타입이나 와도 된다"는 뜻의 자리표시자입니다. `firstOr`는 `α`가 무엇이든 상관없이 똑같은 로직으로 동작하므로, 코드를 한 번만 쓰고 모든 타입에 재사용합니다. 이게 다형성(polymorphism)입니다 — Lean4는 `firstOr 0 [1,2,3]`을 보는 순간 `α`가 `Nat`이라고 스스로 알아채므로, 여러분이 타입을 매번 손으로 지정할 필요는 거의 없습니다.

== 문제: 타입마다 동작이 다른 연산자

다형성만으로는 못 푸는 문제가 있습니다. `==`(같음 비교)는 `Nat`끼리 비교하는 법과 `Point`끼리 비교하는 법이 서로 다릅니다 — `firstOr`처럼 "모든 타입에 대해 완전히 똑같은 코드"가 아니라, "타입마다 다르게 동작하지만 이름은 같은 연산"이 필요합니다.

[source,lean]
----
structure Point where
  x : Float
  y : Float

-- p1 == p2  -- 이대로는 에러: Point에는 아직 "같음"이 뭔지 정의되지 않았다
----

== 해법: 타입 클래스

타입 클래스는 "이 타입은 이런 연산을 지원한다"는 계약입니다. `BEq`(같음 비교를 지원하는 타입)라는 계약에 `Point`가 맞춰 답을 채우면, 그때부터 `Point`도 `==`를 쓸 수 있습니다.

[source,lean]
----
instance : BEq Point where
  beq a b := a.x == b.x && a.y == b.y

#eval (Point.mk 1.0 2.0) == (Point.mk 1.0 2.0)  -- true
#eval (Point.mk 1.0 2.0) == (Point.mk 0.0 0.0)  -- false
----

`instance : BEq Point where ...`가 하는 일은 "`Point`를 위한 `BEq` 계약의 구체적인 구현"을 등록하는 것입니다. 이후로 `==`를 쓰는 코드는 인자의 타입이 `Point`인 걸 보고, 방금 등록한 구현을 자동으로 찾아 씁니다. 이 "자동으로 찾는" 과정을 인스턴스 탐색(instance search)이라고 부릅니다 — 여러분이 직접 `PointBEq.beq p1 p2`라고 적을 필요 없이, `==`라는 이름 하나로 타입에 맞는 구현이 알아서 골라집니다.

== 직접 타입 클래스 만들기

`BEq`는 표준 라이브러리가 미리 만들어둔 계약이지만, 여러분도 새 계약을 선언할 수 있습니다. "이 값을 사람이 읽을 문자열로 요약하는" 계약을 만들어봅시다.

[source,lean]
----
class Summary (α : Type) where
  summarize : α → String

instance : Summary Point where
  summarize p := s!"({p.x}, {p.y})"

def describe [Summary α] (x : α) : String :=
  "값: " ++ Summary.summarize x

#eval describe (Point.mk 3.0 4.0)  -- "값: (3.000000, 4.000000)"
----

먼저 사소한 새 문법 하나 — `s!"({p.x}, {p.y})"`는 문자열 보간입니다. 중괄호 `{}` 안의 식을 계산해서 문자열에 끼워 넣습니다.

`describe`의 타입 시그니처에 있는 `[Summary α]`가 핵심입니다. 이건 "`α`가 무엇이든 상관없지만, 그 타입이 `Summary` 계약을 만족한다는 증거를 달라"는 요청입니다. `describe`를 호출하는 쪽이 그 증거를 손으로 넘길 필요는 없습니다 — 인스턴스 탐색이 `Point`용 `Summary` 구현을 자동으로 찾아 대신 넘겨줍니다.

== 이 장이 왜 중요한가

`+`, `==`, `<`, 심지어 `#eval`이 값을 화면에 찍을 때 쓰는 방식(`ToString`)까지, Lean4의 거의 모든 "연산자처럼 보이는 것"은 사실 타입 클래스입니다. 다르게 생긴 타입들이 같은 이름의 연산을 공유할 수 있는 이유가 바로 이 인스턴스 탐색 메커니즘입니다. 3부에서 메타프로그래밍을 다룰 때, 여러분이 새로 만든 문법이 어떤 타입에 어떻게 연결되는지 결정하는 데도 같은 발상(계약과 그 계약을 만족시키는 구현의 자동 탐색)이 재사용됩니다.

다음 장에서는 "실패할 수도 있는 계산", "값을 여러 개 낼 수 있는 계산", "입출력이 섞인 계산"처럼 서로 다른 종류의 계산을 하나의 공통 패턴으로 묶는 모나드를 다룹니다 — 사실 모나드도 타입 클래스의 한 종류일 뿐입니다.

TIP: 더 깊이 들어가려면 — 타입 클래스와 인스턴스 탐색의 전모는 link:../../../programming/lean/functional-programming-in-lean/ch03/[Functional Programming in Lean Ch.3: 오버로딩과 타입 클래스]에서 다룹니다.

== 직접 해보기

* 3장의 `Shape`에 `Summary` 인스턴스를 만들어 `describe (Shape.circle 2.0)`이 동작하게 해보세요.
* `firstOr`를 참고해 리스트의 마지막 원소를 돌려주는 `lastOr (default : α) : List α → α`를 정의해보세요. (끝까지 재귀로 내려가야 합니다 — 원소가 하나 남은 경우를 잡는 `[x]` 패턴이 유용합니다.)
* `Point`에 `ToString` 인스턴스(문자열 변환 함수 `toString` 하나를 요구하는 표준 계약)를 만들어보세요. 만들고 나면 `#eval (Point.mk 1.0 2.0)`이 바로 동작하게 됩니다 — `#eval`이 값을 찍을 때 찾는 계약이 바로 이것이기 때문입니다.

.해답 보기
[%collapsible]
====
[source,lean]
----
instance : Summary Shape where
  summarize
    | .empty => "빈 도형"
    | .circle r => s!"반지름 {r}인 원"
    | .rect w h => s!"{w}×{h} 직사각형"

#eval describe (Shape.circle 2.0)  -- "값: 반지름 2.000000인 원"

def lastOr (default : α) : List α → α
  | [] => default
  | [x] => x
  | _ :: xs => lastOr default xs

#eval lastOr 0 [1, 2, 3]  -- 3

instance : ToString Point where
  toString p := s!"({p.x}, {p.y})"

#eval Point.mk 1.0 2.0  -- (1.000000, 2.000000)
----
====

== 요약

* 다형성(`α`처럼 타입을 인자로 받는 함수)은 "모든 타입에 대해 완전히 같은 코드"를 재사용하게 해준다.
* 타입 클래스(`class`/`instance`)는 "타입마다 다르게 동작하지만 이름은 같은 연산"(`==`, `+` 등)의 계약이다.
* `instance`로 구현을 등록해두면, 이후 `==` 같은 이름을 쓸 때 Lean4가 타입에 맞는 구현을 자동으로 찾는다(인스턴스 탐색).
* `[Summary α]`처럼 함수 시그니처에 계약을 요구하면, 호출자가 증거를 손으로 넘기지 않아도 인스턴스 탐색이 대신 채운다.
