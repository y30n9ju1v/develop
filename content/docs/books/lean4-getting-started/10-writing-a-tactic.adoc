== tactic도 결국 하나의 elab이다

9장에서 `elab`으로 정교화 단계에 개입하는 걸 봤습니다. tactic은 그 응용의 한 갈래입니다 — 다른 점은, tactic이 다루는 대상이 "만들어야 할 값"이 아니라 "지금 열려 있는 목표들의 목록"이라는 것뿐입니다. 이 목표 목록을 조작하는 전용 모나드가 `TacticM`입니다.

가장 간단한 예로, 목표가 `True`일 때 자동으로 끝내주는 tactic을 만들어봅시다. (9장과 마찬가지로 파일 맨 위에 `import Lean`이 필요합니다.)

[source,lean]
----
import Lean

open Lean Elab Tactic in
elab "close_trivial" : tactic => do
  liftMetaTactic fun mvarId => do
    mvarId.assign (mkConst ``True.intro)
    return []

theorem t1 : True := by close_trivial
----

새 용어 하나 — Lean4는 "아직 채워지지 않은 구멍"을 metavariable이라고 부릅니다. 증명 도중의 목표 하나하나가 곧 채워야 할 구멍이고, `mvarId`는 그 구멍을 가리키는 식별자(metavariable id)입니다. `liftMetaTactic`은 "그 구멍을 받아서, 자리에 채울 값을 정해주는" 작업을 하게 해주는 통로입니다. `mvarId.assign (mkConst ``True.intro)`가 하는 일은 "이 목표 자리에 `True.intro`라는 이미 정의된 증명 값을 채워 넣어라"는 것입니다. 마지막의 `return []`은 "새로 남는 하위 목표는 없다"는 뜻입니다 — 목표를 완전히 닫았기 때문입니다.

== 목표를 보고 판단하는 tactic

방금 예제는 아무것도 검사하지 않고 무작정 `True.intro`를 넣었습니다. 실전에서는 지금 목표가 정말 원하는 모양인지 먼저 확인해야 합니다. "목표가 `n = n` 꼴이면 `rfl`을, 아니면 실패로 알려주는" tactic을 만들어봅시다.

[source,lean]
----
open Lean Elab Tactic Meta in
elab "close_refl" : tactic => do
  liftMetaTactic fun mvarId => do
    let target ← mvarId.getType
    match target.eq? with
    | some (_, lhs, rhs) =>
      if ← isDefEq lhs rhs then
        mvarId.assign (← mkEqRefl lhs)
        return []
      else
        throwError "좌변과 우변이 같지 않습니다"
    | none => throwError "목표가 등식이 아닙니다"

theorem t2 : 3 + 4 = 7 := by close_refl
----

`mvarId.getType`으로 지금 목표의 타입(`Expr`)을 꺼내고, `target.eq?`로 그게 등식(`_ = _`) 모양인지 확인합니다. 등식이면 `isDefEq`(계산해서 같은 값이 되는지 확인하는 함수 — `rfl`이 내부적으로 쓰는 바로 그 판정)로 좌변과 우변을 비교하고, 같으면 그 증명(`mkEqRefl`)을 만들어 목표에 채웁니다. 등식이 아니거나 값이 다르면 `throwError`로 실패를 알립니다.

이 코드는 사실상 `rfl`의 아주 단순화된 재구현입니다. 7장에서 `rfl`을 그냥 "당연히 되는 것"으로 썼는데, 이제 그 뒤에 있는 게 목표의 `Expr`을 읽고 계산 결과를 비교하는 평범한 Lean4 프로그램이라는 걸 확인했습니다.

== 여러 하위 목표를 남기는 tactic

8장에서 본 `induction`처럼, tactic은 하나의 목표를 여러 하위 목표로 쪼갤 수도 있습니다. `close_trivial`에서 `return []`으로 하위 목표가 없다고 했던 자리에, 대신 새로 만든 metavariable들의 목록을 돌려주면 됩니다. 그 하위 목표들이 바로 7장에서 `constructor`를 쓴 뒤 `·`(불릿)로 하나씩 처리했던 그 목표들입니다 — `constructor`도 결국 "지금 목표의 타입이 어떤 구조체/귀납 타입인지 보고, 그 생성자가 요구하는 필드 수만큼 새 목표를 만들어 돌려주는" tactic입니다.

== 이 장이 왜 중요한가

지금까지 만든 tactic은 장난감 수준이지만, 원리는 실제 `simp`, `omega`, `induction`과 다르지 않습니다 — 목표의 `Expr`을 읽고, 판단하고, 값을 채우거나 새 목표로 쪼갭니다. 이 사실이 왜 중요할까요? 여러분이 반복해서 손으로 쓰는 증명 패턴이 있다면, 그건 언젠가 tactic으로 자동화할 수 있는 후보라는 뜻입니다. 이 책 범위를 벗어난 실전에서는 특정 도메인(선형대수, 컴파일러 IR 등)에 맞춘 전용 tactic을 만들어 증명을 대폭 줄이는 일이 흔합니다.

마지막 장에서는 이 책이 다루지 못한 부분, 그리고 더 깊이 들어가고 싶을 때 원본 세 책 중 어디로 가면 되는지 정리합니다.

TIP: 더 깊이 들어가려면 — tactic 작성의 본격적인 안내는 link:../../../programming/lean/metaprogramming-in-lean4/09-tactics/[Metaprogramming in Lean 4의 9장: Tactic 작성하기], 그 재료인 `Expr`과 `MetaM`은 link:../../../programming/lean/metaprogramming-in-lean4/03-expressions/[3장]과 link:../../../programming/lean/metaprogramming-in-lean4/04-metam/[4장]에서 다룹니다.
