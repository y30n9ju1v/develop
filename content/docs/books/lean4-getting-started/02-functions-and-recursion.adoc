== 왜 반복문이 없는가

C나 Python에서 배열의 합을 구하라고 하면 대부분 `for` 루프를 씁니다. Lean4에도 ``for``가 있긴 하지만, 함수형 스타일에서는 잘 안 씁니다. 이유는 1장에서 본 원칙으로 돌아갑니다 — Lean4의 이름은 한 번 정의되면 바뀌지 않습니다. `for` 루프는 보통 "누적 변수를 매 반복마다 덮어쓰는" 방식으로 동작하는데, 그 "덮어쓰기"가 바로 Lean4가 기본적으로 지양하는 동작입니다.

대신 함수형 언어는 반복을 **재귀**로 표현합니다. "n부터 1까지 더한 값"을 반복문이 아니라 이렇게 정의합니다.

[source,lean]
----
def sumTo : Nat → Nat
  | 0 => 0
  | n + 1 => (n + 1) + sumTo n

#eval sumTo 5  -- 15
----

``sumTo n``은 "``n``이 0이면 0, 아니면 ``n``에 ``sumTo (n-1)``을 더한 것"이라고 자기 자신을 이용해 정의됩니다. 반복 대신 "더 작은 문제로 쪼개고, 그 답을 조합한다"는 발상입니다.

== 패턴 매칭: 값의 모양으로 분기하기

방금 정의에서 ``| 0 => ...``와 ``| n + 1 => ...``가 나눠진 걸 눈여겨보세요. 이건 ``if``로 "0인가 아닌가"를 검사하는 것과 결과는 같지만, 표현 방식이 다릅니다 — **패턴 매칭**은 입력값이 어떤 모양인지에 따라 정의를 나눕니다. `Nat`(자연수)은 "0이거나, 어떤 자연수에 1을 더한 것"이라는 두 가지 모양 중 하나이므로, 그 두 모양 각각에 대해 무엇을 할지 정의하면 모든 자연수를 다룬 셈이 됩니다. ``n + 1``이 패턴 자리에 올 수 있는 건 우연이 아닙니다 — ``Nat``은 실제로 `Nat.zero`(0)와 `Nat.succ n`(어떤 수의 다음 수)이라는 딱 두 가지 생성 방법으로 정의된 타입이고, `n + 1` 패턴은 ``Nat.succ n``을 읽기 좋게 쓴 표기입니다. 이런 타입을 3장에서 직접 만들어봅니다.

이 패턴 매칭은 자연수보다 훨씬 강력합니다. 리스트에도 똑같이 적용됩니다.

[source,lean]
----
def listLen : List Nat → Nat
  | []      => 0
  | _ :: xs => 1 + listLen xs

#eval listLen [10, 20, 30]  -- 3
----

리스트는 "빈 리스트(`[]`)거나, 원소 하나(head)와 나머지 리스트(tail)를 `::` 연산자로 이어붙인 것"이라는 두 모양 중 하나입니다. 여기서 ``::``는 원소를 리스트 맨 앞에 덧붙여 새 리스트를 만드는 연산자입니다(예: ``10 :: [20, 30]``은 `[10, 20, 30]`). 패턴 매칭에 쓰인 ``_ :: xs``에서 ``_``는 맨 앞 원소를 안 쓰겠다는 뜻이고 ``xs``는 나머지 리스트(tail)에 붙인 이름입니다. 이렇게 "값이 어떻게 만들어졌는지"를 그대로 정의의 형태로 삼는 게 함수형 프로그래밍의 핵심 스타일입니다.

[NOTE]
====
다른 언어의 ``if-else``도 결국 패턴 매칭 아닌가요?

맞습니다! 사실 ``if b then x else y``는 `Bool` 타입(`true` 또는 `false`) 두 모양에 대한 패턴 매칭(`match b with | true => x | false => y`)의 줄임 표기에 불과합니다.

다만 패턴 매칭은 ``Bool``뿐 아니라 `Nat`, `List` 등 모든 타입에 적용되고, 단순 ``if-else``와 달리 두 가지가 더 있습니다.

* *값 해체(destructuring)*: 모양을 검사함과 동시에 내부 값(`xs` 등)을 꺼내 새 이름에 즉시 붙인다.
* *빠짐없는 검사(exhaustiveness checking)*: 가능한 모든 모양을 다 다뤘는지 컴파일러가 확인해, 한 경우라도 빠뜨리면 컴파일을 거부한다.
====

== match 식과 이름 없는 함수

방금까지 쓴 `| 패턴 => 결과` 나열은 사실 `match` 식의 줄임 표기입니다. ``match``는 정의 첫머리뿐 아니라 아무 식 안에서나 쓸 수 있습니다.

[source,lean]
----
def isZero (n : Nat) : String :=
  match n with
  | 0 => "yes"
  | _ => "no"
----

또 하나, 함수를 꼭 ``def``로 이름 붙여 만들 필요는 없습니다. 한 번 쓰고 말 작은 함수는 `fun 인자 => 식` 문법으로 그 자리에서 만듭니다.

[source,lean]
----
#eval List.map (fun n => n * 2) [1, 2, 3]  -- [2, 4, 6]
----

``List.map``은 리스트의 모든 원소에 함수를 하나씩 적용하는 표준 함수인데, 여기에 이름 없는 함수를 즉석에서 만들어 넘겼습니다. 이 `fun` 문법은 5장에서 계산을 이어붙일 때 계속 나옵니다.

== 왜 이런 재귀가 안전한가: 종료성

C에서 재귀 함수를 잘못 짜면 스택이 넘칠 때까지 영원히 돌 수 있습니다. Lean4는 이걸 훨씬 엄격하게 다룹니다 — 컴파일러가 재귀 정의를 보고 "매 호출마다 진짜로 더 작은 입력으로 줄어드는가"를 확인합니다. ``sumTo``에서 ``sumTo n``을 ``n + 1``이 아니라 ``n``으로 호출한 게 바로 그 증거입니다. 만약 이 조건을 만족하지 못하면 Lean4는 정의를 아예 거부합니다.

[source,lean]
----
-- 이 정의는 컴파일 에러가 난다: 입력이 줄어든다는 근거가 없다
-- def bad : Nat → Nat
--   | n => bad n
----

당장은 "컴파일러가 좀 깐깐하다" 정도로 느껴지겠지만, 이 종료성 검사가 나중에 아주 중요한 결과를 냅니다 — Lean4에서 짠 함수는 항상 멈추고 값을 낸다는 게 보장되므로, "이 함수는 이런 값을 낸다"는 증명을 쓸 때 무한 루프에 빠질 걱정을 할 필요가 없습니다. 8장에서 이 종료성 증명을 직접 다룹니다.

== 여러 인자를 받는 재귀

인자가 둘 이상인 함수도 자연스럽게 재귀를 씁니다. 두 리스트를 지퍼처럼 짝짓는 함수를 봅시다.

[source,lean]
----
def zip : List Nat → List String → List (Nat × String)
  | a :: as, b :: bs => (a, b) :: zip as bs
  | _, _ => []

#eval zip [1, 2, 3] ["a", "b"]  -- [(1, "a"), (2, "b")]
----

둘 다 원소가 있을 때만 짝을 짓고, 어느 한쪽이 비면(길이가 다르면) 거기서 멈춥니다. ``_, _``는 "나머지 모든 경우"를 뜻하는 와일드카드 패턴입니다 — 패턴은 위에서부터 순서대로 검사되므로, 앞의 패턴에 안 걸린 경우만 여기로 떨어집니다.

``(a, b)``는 1장에서 본 그 튜플입니다 — ``a : Nat``과 ``b : String``을 그냥 나란히 묶은 값이고, 타입도 ``Nat × String``으로 묶여서 나옵니다. ``zip``의 반환 타입 ``List (Nat × String)``이 바로 이 튜플들의 리스트라는 뜻입니다.

== 이 장이 왜 중요한가

재귀와 패턴 매칭은 단순히 "반복문의 함수형 대체품"이 아닙니다. "값이 어떻게 만들어졌는지에 따라 경우를 나눈다"는 이 발상이 3장에서는 자료구조를 설계하는 원리가 되고, 8장에서는 무한히 많은 경우를 유한한 단계로 증명하는 귀납법이 됩니다. 종료성 검사도 마찬가지입니다 — 지금은 깐깐한 제약처럼 보이지만, "모든 함수는 반드시 멈춘다"는 이 보장이 2부에서 증명의 토대가 됩니다.

다음 장에서는 이런 자료구조 자체를 직접 설계하는 법 — 구조체와 귀납적 타입 — 을 다룹니다. ``List``나 ``Nat``도 사실 Lean4 안에서 여러분이 만들 수 있는 것과 똑같은 방식으로 정의된 평범한 타입입니다.

TIP: 더 깊이 들어가려면 — 재귀와 패턴 매칭의 더 많은 예제는 link:../../../programming/lean/functional-programming-in-lean/ch01/[Functional Programming in Lean Ch.1], 종료성 증명의 세부 기법은 link:../../../programming/lean/functional-programming-in-lean/ch08/[같은 책 Ch.8: 프로그래밍, 증명, 성능]을 보세요.

== 직접 해보기

* ``sumTo``를 참고해 ``factorial : Nat → Nat``을 재귀로 정의해보세요. ``#eval factorial 5``는 120이 나와야 합니다.
* 리스트의 합을 구하는 ``listSum : List Nat → Nat``을 패턴 매칭으로 정의해보세요.
* ``zip``을 고쳐, 두 리스트의 대응 원소끼리 더한 리스트를 돌려주는 ``pairSum : List Nat → List Nat → List Nat``을 만들어보세요. ``#eval pairSum [1, 2] [10, 20]``은 ``[11, 22]``가 나와야 합니다.

.해답 보기
[%collapsible]
====
[source,lean]
----
def factorial : Nat → Nat
  | 0 => 1
  | n + 1 => (n + 1) * factorial n

#eval factorial 5  -- 120

def listSum : List Nat → Nat
  | [] => 0
  | x :: xs => x + listSum xs

#eval listSum [1, 2, 3]  -- 6

def pairSum : List Nat → List Nat → List Nat
  | a :: as, b :: bs => (a + b) :: pairSum as bs
  | _, _ => []

#eval pairSum [1, 2] [10, 20]  -- [11, 22]
----
====

== 요약

* Lean4는 이름의 값이 바뀌지 않으므로, 반복은 ``for``가 아니라 재귀로 표현한다.
* 패턴 매칭(`| 패턴 => 식`)은 값이 어떻게 만들어졌는지에 따라 정의를 나눈다 — ``Nat``은 `0` 또는 `n + 1`, ``List``는 `[]` 또는 `head :: tail`.
* 컴파일러가 재귀 정의마다 "매 호출이 정말 더 작은 입력으로 줄어드는가"(종료성)를 검사하므로, Lean4 함수는 항상 멈춘다.
* `match` 식과 `fun` 익명 함수는 ``def``의 `|` 절과 같은 패턴 매칭을 아무 식 안에서나 쓸 수 있게 해준다.
