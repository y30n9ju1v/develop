== 증명도 def다

1부에서 계속 `def 이름 : 타입 := 식`을 써왔습니다. 이제 이렇게 적어봅시다.

[source,lean]
----
theorem two_plus_two : 2 + 2 = 4 := rfl
----

`theorem`이라는 새 키워드가 나왔지만, 사실 `theorem`은 `def`와 거의 같습니다 — "이 이름의 타입은 `2 + 2 = 4`이고, 그 값은 `rfl`이다"라고 읽으면 됩니다. `2 + 2 = 4`가 여기서는 **타입**으로 취급되고 있다는 게 이 장의 핵심입니다. 그리고 `rfl`은 그 타입의 값입니다.

`rfl`은 "reflexivity"의 줄임말로, "양쪽을 각각 계산해보면 결국 같은 값이 나온다"는 걸 확인해주는 가장 단순한 증명입니다. Lean4는 `2 + 2`를 계산해 `4`가 나오는지 확인하고, 실제로 같으면 `rfl`을 그 타입의 유효한 값으로 받아들입니다.

== 명제가 타입이라는 게 무슨 뜻인가

1장에서 "모든 식은 타입을 갖는다"고 했습니다. `2 + 2 = 4`도 식이니 타입을 가져야 하는데, 여기서는 거꾸로 `2 + 2 = 4` **자신이** 타입이 됩니다. 헷갈릴 수 있으니 정리하면:

* `2 + 2 = 4`는 명제(주장)이고, 동시에 Lean4 안에서는 하나의 타입입니다.
* `rfl`은 그 타입에 속하는 값이고, 동시에 "이 주장이 참이라는 증명"입니다.
* "이 명제가 참임을 증명한다" = "이 타입에 속하는 값을 하나 만들어낸다."

이걸 Curry-Howard 대응이라고 부릅니다. 3장에서 `Shape` 타입의 값이 `.empty`, `.circle r`, `.rect w h` 중 하나로만 만들어질 수 있다고 했던 것 기억하시나요? 명제도 똑같습니다 — "이 명제 타입의 값을 만드는 방법"이 정해져 있고, 그 방법을 실제로 실행하는 게 증명을 쓰는 일입니다. 참인 명제는 값을 만들 수 있는 타입이고, 거짓인 명제는 값을 하나도 만들 수 없는 타입입니다(3장의 `Option`에서 `none`이 "값이 없는 경우"였던 것과 비슷하게, 거짓 명제는 "만들 방법이 없는 타입"이라고 생각하면 됩니다).

지금까지 나온 대응 관계를 표로 정리하면 이렇습니다. 오른쪽 끝 칸은 뒤에 나올 장에서 실제로 마주칠 문법입니다.

[cols="1,1,1"]
|===
| 프로그래밍 쪽 개념 | 논리·증명 쪽 개념 | Lean4에서 보는 형태

| 타입(Type)
| 명제(Proposition)
| `Prop`, `2 + 2 = 4`

| 값(Value)
| 증명(Proof)
| `rfl`, `theorem ... := ...`

| 함수 타입 `A → B`
| 함의("A면 B다")
| `theorem t (h : A) : B := ...`

| 구조체(두 값을 묶은 것)
| 논리곱 `∧`("그리고")
| `And`, `⟨h1, h2⟩`

| 귀납 타입(여러 모양 중 하나)
| 논리합 `∨`("또는")
| `Or`, `Or.inl`, `Or.inr`

| 값을 하나도 못 만드는 타입
| 거짓 `False`
| `False`, 생성자가 없음
|===

== 함수를 만드는 것 = 함의를 증명하는 것

"A면 B다"라는 함의는 `A → B` 타입으로 나타납니다 — 2장에서 봤던 그 함수 화살표와 문법이 완전히 같습니다. 정말로 같은 것이기 때문입니다.

[source,lean]
----
theorem modus_ponens (p q : Prop) (h : p → q) (hp : p) : q := h hp
----

``h : p → q``는 "``p``면 ``q``다"라는 함의의 증명을 ``h``라는 이름으로 받는다는 뜻이고, ``hp : p``는 "``p``가 참이다"라는 증명입니다. 몸통의 ``:= h hp``는 문자 그대로 **함수 호출**입니다 — ``h``는 "``p``의 증명을 받아 ``q``의 증명을 내놓는 함수"이므로, 우리가 이미 가진 증명 ``hp``를 넘겨 호출하기만 하면 목표인 `q` 타입의 증명이 나옵니다.

논리학에서 삼단논법(Modus Ponens)이라 부르는 유서 깊은 추론 규칙이, Lean4에서는 특별한 룰이 아니라 단지 2장에서 배운 **평범한 함수 호출(`h hp`)**에 불과합니다. `Nat → Nat` 같은 평범한 계산 함수와 `p → q` 같은 논리적 함의가 Lean4 안에서는 완전히 같은 개념(함수 타입)이라는 게 이 장에서 가장 중요한 통찰입니다.

이렇게 증명 값을 한 방에 손으로 조립하는 방식은 명제가 단순할 땐 잘 통하지만, 복잡해지면 조립할 값을 미리 통째로 그려내기가 어려워집니다. 그럴 때 한 걸음씩 다가가며 쓰는 방법을 다음 장(전술)에서 다룹니다.

== 논리 연결사도 결국 3장의 그 타입들이다

"그리고(And)", "또는(Or)"도 3장에서 배운 도구로 정의됩니다.

[source,lean]
----
structure And' (p q : Prop) : Prop where
  left : p
  right : q

inductive Or' (p q : Prop) : Prop where
  | inl (h : p) : Or' p q
  | inr (h : q) : Or' p q
----

`And'`는 `p`의 증명과 `q`의 증명을 둘 다 담은 `structure`입니다 — "그리고"를 증명하려면 양쪽을 다 증명해야 한다는 게 자연스럽게 이 정의에서 나옵니다. `Or'`는 `p`를 증명하거나(`inl`) `q`를 증명하거나(`inr`) 둘 중 하나면 충분하다는 `inductive`입니다 — 3장의 `Shape`가 세 가지 모양 중 하나였던 것과 정확히 같은 구조입니다. Lean4 표준 라이브러리의 진짜 `And`, `Or`도 이것과 거의 똑같이 정의되어 있습니다.

== 이 장이 왜 중요한가

이 장에서 실제로 배운 새 지식은 놀랍도록 적습니다 — `structure`, `inductive`, 함수 타입 `→`, 이미 다 아는 것들입니다. 달라진 건 그 도구들을 "값을 계산하는 프로그램"이 아니라 "명제가 참이라는 증거"를 만드는 데 쓴다는 관점뿐입니다. 이게 이 책 서문에서 말한 "코드를 짜는 것과 정리를 증명하는 것이 같은 행위"라는 말의 실체입니다.

다음 장에서는 `And'`나 `Or'`의 값을 매번 손으로 조립하는 대신, "전술"이라는 반자동 도구로 증명을 훨씬 편하게 쓰는 법을 다룹니다.

== 직접 해보기

* `5 * 5 = 25`를 `rfl`로 증명해보세요. 그다음 우변을 `26`으로 바꿔보고, Lean4가 어떤 에러로 거부하는지 읽어보세요.
* `p ∧ q → p`를 증명해보세요. 함의는 함수이므로 증명은 `fun h => ...` 꼴이고, `h`에서 왼쪽 증명을 꺼내면 됩니다.
* `p → p ∨ q`를 증명해보세요. `Or`의 두 생성자(`Or.inl`, `Or.inr`) 중 하나면 충분합니다.

.해답 보기
[%collapsible]
====
[source,lean]
----
theorem five_sq : 5 * 5 = 25 := rfl
-- 우변을 26으로 바꾸면 rfl이 거부됩니다 —
-- 양변을 계산한 결과가 같은 값이 아니기 때문입니다.

theorem and_left (p q : Prop) : p ∧ q → p := fun h => h.left

theorem or_intro (p q : Prop) : p → p ∨ q := fun hp => Or.inl hp
----
====

== 요약

* Curry-Howard 대응: 명제는 타입이고, 증명은 그 타입에 속하는 값이다 — "참임을 증명한다" = "그 타입의 값을 하나 만들어낸다."
* `theorem`은 사실상 `def`와 같다 — 이름·타입·값(증명)을 정의하는 문법이 동일하다.
* 함수 타입 `A → B`가 곧 함의("A면 B다")다 — 함수를 만드는 것과 함의를 증명하는 것은 같은 행위다.
* "그리고(`∧`)"는 3장의 `structure`(양쪽을 다 가짐), "또는(`∨`)"는 `inductive`(둘 중 하나면 충분)로 정의된다.
