== 1. 한 프레임에서 한 스테이지로

7장은 프레임 하나 → 행동 하나였습니다. 실제로 게임을 플레이하려면 이 사이클을 반복해야 합니다 — 행동을 실행하면 게임 상태가 바뀌고, 새 프레임이 나오고, 그 프레임이 다시 정책망에 들어갑니다. CPU 프로그램으로 표현하면 단순한 반복문입니다.

[source,text]
----
// examples/mario_playthrough.mini (의사코드 — CPU 메인 루프)
fn playLevel() {
    while (!levelComplete() && !mario_dead()) {
        let frame = captureFrame();       // 에뮬레이터/시뮬레이터에서 현재 화면 읽기
        let scores = policyForward(frame); // 7장의 정책망 추론
        let action = argmax(scores);
        executeAction(action);            // 컨트롤러 입력을 에뮬레이터에 전달
    }
}
----

[NOTE]
====
`captureFrame`과 `executeAction`은 이 시리즈의 NPU/CPU 파이프라인이 아니라 *게임 에뮬레이터와의 경계*입니다 — 실전에서는 NES 에뮬레이터(예: `gym-super-mario-bros`가 감싸는 `nes-py`)가 프레임 버퍼와 컨트롤러 입력을 제공하고, 이 시리즈의 CPU+NPU는 그 프레임을 받아 행동을 계산하는 "두뇌" 역할만 합니다. 에뮬레이터 자체를 Lean4로 새로 만드는 것은 이 시리즈의 범위 밖이며, 여기서는 이미 검증된 오픈소스 에뮬레이터를 신뢰 기반의 일부로 받아들입니다 — 이 경계를 명시적으로 긋는 것 자체가 10장 TCB 표의 새 항목입니다.
====

== 2. 반복 루프에서 새로 생기는 질문: 오차가 쌓이는가

7장의 `action_order_preserved`는 프레임 *하나*에 대한 정리였습니다. 반복 루프에서는 다른 질문이 생깁니다 — *한 프레임의 잘못된 행동이 다음 프레임들의 오차에 영향을 주는가?* 마리오에서 "점프해야 할 때 안 함"은 죽음으로 이어지고, 그 순간 에피소드가 끝나버리므로 오차가 "누적"되기보다는 "그 프레임에서 실패가 확정"되는 쪽에 가깝습니다. 이건 좋은 소식과 나쁜 소식이 함께 있습니다 — 좋은 소식은 7장 정리가 프레임마다 독립적으로 적용 가능하다는 것(오차가 시간에 걸쳐 복잡하게 얽히지 않음), 나쁜 소식은 *단 한 프레임*의 아슬아슬한 오판이 전체 플레이스루를 실패시킬 수 있다는 것입니다.

[source,lean]
----
namespace Nand2Npu.Npu

/-- 스테이지 전체를 클리어하려면, 매 프레임에서 action_order_preserved의
    전제(점수 차이가 오차 한계의 두 배보다 큼)가 성립해야 합니다 — 단 한 프레임이라도
    이 전제가 깨지면 그 정리의 보장이 사라지므로, "안전 마진이 있는 프레임의 비율"이
    실전에서 스테이지 클리어율과 직결되는 지표입니다. -/
def safeFrameFraction (totalFrames marginalFrames : Nat) : Rat :=
  1 - (marginalFrames : Rat) / (totalFrames : Rat)

end Nand2Npu.Npu
----

`safeFrameFraction`은 정리가 아니라 정의입니다 — 이 장에서 실제로 증명하지는 않지만, 3절의 실측에서 이 비율을 실제로 세어보고, 그 결과가 이 시리즈가 "증명"과 "실측"을 함께 써온 방식(1권 13장에서 이미 정리한 원칙)의 마지막 사례가 됩니다. "점수 차이가 오차 한계의 두 배보다 큼"이라는 전제의 오차 한계 자체는 더 이상 가정이 아니라 8장에서 실제로 계산한 수치(`convLayerErrorBound`)입니다 — 그러니 여기서 세는 `marginalFrames`는 순전히 실측값이고, 8장이 증명한 최악의 경우 한계와 대조할 기준점이 됩니다.

== 3. 실측: 실제로 클리어했는가

[source,bash]
----
# 1권~2권 전체를 반영한 최종 빌드 + 마리오 스테이지 1-1 플레이스루 시뮬레이션
lake exe compilermain --with-npu --target mario_playthrough > examples/mario.asm
lake exe assemble examples/mario.asm > examples/mario.hack

./sim/obj_dir_cpu_npu/Vcpu_npu examples/mario.hack --emulator-bridge=nes-py --level=1-1
----

[TIP]
====
*확인*: 이 실행이 "레벨 클리어" 또는 "실패"로 끝나든, 진짜 확인 대상은 결과 하나가 아니라 2절의 `safeFrameFraction`입니다 — 플레이스루 전체에서 몇 프레임이 "안전 마진 있음"(7장 정리의 전제 충족)이었고 몇 프레임이 "아슬아슬함"(전제 미충족, 즉 양자화가 행동을 뒤집었을 수도 있는 프레임)이었는지 세어보세요. 실패한다면, 실패 직전 몇 프레임의 점수 차이를 직접 출력해 그 프레임들이 "아슬아슬한 프레임"이었는지부터 확인하는 것이 가장 빠른 디버깅 경로입니다 — 그렇다면 이건 NPU 파이프라인의 버그가 아니라 8장에서 이미 예견한 근사 오차의 실현입니다.
====

이 스테이지 1-1 플레이스루가 이 시리즈 전체의 최종 확인입니다 — 게이트(1권 1장)에서 시작한 증명·방출·검증 파이프라인이, 시스톨릭 어레이(2장)와 양자화(4장)를 거쳐, 훈련된 신경망의 실시간 의사결정(7~9장)까지 끊기지 않고 이어진 것입니다.

== 이 장에서 확정한 것

* 7장의 한 프레임 추론을 CPU 반복 루프로 감싸, 실제로 마리오를 플레이하는 전체 사이클(프레임 캡처 → 추론 → 행동 실행)을 완성했습니다.
* 반복 루프에서는 오차가 시간에 걸쳐 얽히기보다 "한 프레임의 실패가 즉시 확정"되는 성격을 가진다는 것을 관찰하고, `safeFrameFraction`으로 그 위험을 실측 지표화했습니다.
* 게임 에뮬레이터를 이 시리즈의 신뢰 기반(TCB)에 명시적으로 편입시켰습니다.
* 실제 플레이스루 시뮬레이션 절차를 제시하고, 성공이든 실패든 8장의 최악의 경우 오차 한계와 대조해 해석하는 방법을 정리했습니다.

다음 장에서는 1권부터 이 2권까지 신뢰 기반(TCB)이 어떻게 자라왔는지 정리하며 이 시리즈를 마칩니다.
