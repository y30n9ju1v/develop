'''

5장은 순진한 행렬곱 커널이 왜 느린지(같은 데이터를 스레드마다 중복해서 전역 메모리에서 읽음) 진단했습니다. 이 장은 그 진단을 고칩니다 — 워크그룹이 필요한 데이터 조각을 **로컬 메모리에 한 번만 읽어와서 나눠 쓰는** 타일링(tiling) 기법으로 실제 속도를 개선합니다.

== 아이디어: 타일 단위로 로컬 메모리에 캐싱하기

`M×M` 행렬을 `TILE×TILE`(이 장에서는 16×16) 크기의 작은 정사각형(타일)들로 쪼갠다고 생각합니다. 워크그룹 하나를 타일 하나에 대응시키면 — 워크그룹 안의 16×16=256개 스레드가 힘을 합쳐, 그 타일이 필요로 하는 `A`의 16×16 조각과 `B`의 16×16 조각을 **딱 한 번만** 전역 메모리에서 읽어 로컬 메모리에 저장해두고, 그다음 그 워크그룹의 모든 스레드가 로컬 메모리에서 반복해서 읽어씁니다.

[source,python]
----
TILE = 16
prg_tiled = cl.Program(ctx, f"""
#define TILE {TILE}
__kernel void matmul_tiled(__global const float* A, __global const float* B,
                            __global float* C, int M,
                            __local float* Asub, __local float* Bsub) {{
    int row = get_global_id(0);
    int col = get_global_id(1);
    int lrow = get_local_id(0);
    int lcol = get_local_id(1);
    float sum = 0.0f;
    int ntiles = M / TILE;
    for (int t = 0; t < ntiles; t++) {{
        // 이 워크그룹이 담당하는 타일 조각을 각 스레드가 한 원소씩 로컬 메모리로 읽어옴
        Asub[lrow*TILE + lcol] = A[row*M + (t*TILE + lcol)];
        Bsub[lrow*TILE + lcol] = B[(t*TILE + lrow)*M + col];
        barrier(CLK_LOCAL_MEM_FENCE);  // 타일 전체가 로컬 메모리에 다 채워질 때까지 대기

        // 이제 전역 메모리를 다시 안 가고, 로컬 메모리에서 부분합을 누적
        for (int k = 0; k < TILE; k++) {{
            sum += Asub[lrow*TILE + k] * Bsub[k*TILE + lcol];
        }}
        barrier(CLK_LOCAL_MEM_FENCE);  // 다음 타일로 넘어가기 전, 이 타일 사용이 다 끝날 때까지 대기
    }}
    C[row*M + col] = sum;
}}
""").build()
----

4장에서 배운 `barrier`가 여기서도 핵심입니다 — 두 번의 배리어가 각각 다른 이유로 필요합니다. 첫 번째는 "아직 로딩이 덜 끝난 타일을 계산에 쓰지 않게" 막고, 두 번째는 "아직 계산이 안 끝난 타일을 다음 반복이 덮어쓰지 않게" 막습니다. 어느 하나라도 빠지면 4장에서 봤던 것과 같은 조용한 오답 버그가 생깁니다.

== 실측: 얼마나 빨라지는가

5장과 같은 1024×1024 행렬로, 순진한 버전과 타일링 버전을 나란히 비교합니다.

[source,python]
----
local_mem_A = cl.LocalMemory(TILE*TILE*4)
local_mem_B = cl.LocalMemory(TILE*TILE*4)
k_tiled(q, (M, M), (TILE, TILE), A_buf, B_buf, C_buf, np.int32(M),
        local_mem_A, local_mem_B)
q.finish()
----

[source]
----
naive: 16.67ms  err=0.0
tiled: 4.93ms   err=0.0
----

**3.4배 빨라졌습니다**(16.67ms → 4.93ms), 결과 오차는 여전히 0 — 계산 결과는 정확히 같은데 속도만 개선됐습니다. 5장에서 NumPy(4.31ms)보다 3.9배 느렸던 걸 기억하면, 이 타일링 버전(4.93ms)은 이제 NumPy와 **거의 같은 수준**까지 따라잡았습니다(0.6배 차이, 여전히 NumPy가 약간 빠르지만 같은 자릿수).

== 왜 3.4배인가 — 전역 메모리 접근 횟수를 세어보기

5장에서 순진한 커널은 스레드 하나가 원소 하나(`C[row][col]`)를 계산하는 데 전역 메모리를 `2×M`번(`A`에서 M번, `B`에서 M번) 읽는다고 했습니다. `M=1024`면 스레드 하나당 2048번입니다.

타일링 버전은 다릅니다 — 스레드 하나는 각 타일마다 `Asub`/`Bsub`에 **한 원소씩만** 씁니다(전역 메모리 읽기 2번, `t`가 `ntiles=M/TILE=64`번 도니까 총 128번). 로컬 메모리에서 읽는 건 타일마다 `TILE×2=32`번이지만 로컬 메모리 접근은 전역 메모리보다 훨씬 빠르므로 병목이 아닙니다. 전역 메모리 접근만 비교하면 `2048`번(순진) vs `128`번(타일링) — **정확히 16배** 줄었습니다. 이게 우연이 아닙니다 — `TILE=16`이므로, 워크그룹 안의 스레드 256개(16×16)가 원래 각자 읽었을 데이터를 **딱 16개(TILE)씩만 나눠 읽고 공유**하기 때문에, 전역 메모리 접근이 정확히 `TILE`배 줄어드는 구조입니다.

실측 속도 개선(3.4배)이 전역 메모리 접근 감소(16배)보다 작은 이유는, 이 GPU가 순수 메모리 대역폭만으로 병목이 걸리는 게 아니라 커널 디스패치 오버헤드·로컬 메모리 배리어 대기·워크그룹 스케줄링 등 다른 비용도 섞여 있기 때문입니다 — 이론적 상한(16배)과 실측값(3.4배) 사이의 간극 자체가 "이론적 개선이 그대로 실측 성능으로 옮겨가지 않는다"는 이 시리즈 전체의 교훈을 다시 보여줍니다.

== 직접 해보기

`TILE`을 16 대신 8로 바꾸면 속도가 더 빨라질까 느려질까? 전역 메모리 접근 횟수는 `TILE`배만큼 줄어드는데, `TILE`이 작아지면 반복 횟수(`ntiles = M/TILE`)는 오히려 늘어난다는 걸 감안해서 예상해보고 실행해서 확인해보세요.

.해답 보기
[%collapsible]
====
[source,python]
----
TILE = 8
# ... (본문과 동일한 커널, TILE만 8로)
----

[source]
----
tiled (TILE=8): 7.92ms  err=0.0
----

`TILE=16`일 때(4.93ms)보다 **느려졌습니다**(7.92ms). `TILE`이 작아지면 전역 메모리 접근은 스레드당 `2×ntiles=2×(1024/8)=256`번으로 늘어나서(`TILE=16`일 때는 128번), 오히려 전역 메모리 접근 횟수 자체가 늘어난 겁니다 — "타일이 작을수록 좋다"는 예상과 반대입니다. `TILE`은 워크그룹이 한 번에 처리하는 조각의 크기이자 반복 횟수를 결정하는 트레이드오프 변수라서, 무조건 크게도 작게도 아니라 하드웨어의 로컬 메모리 용량과 워크그룹 최대 크기(이 GPU는 256, 1~3장 참고)에 맞는 값을 찾아야 합니다 — 이 장에서 고른 `TILE=16`은 `16×16=256`으로 정확히 이 GPU의 `max_work_group_size`를 꽉 채우는 값이었습니다.
