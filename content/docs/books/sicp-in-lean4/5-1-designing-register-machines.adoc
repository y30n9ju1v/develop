== 데이터 경로와 컨트롤러: GCD 머신

유클리드 알고리즘으로 최대공약수를 구하는 머신을 생각해봅니다. 레지스터 ``a``, ``b``, 그리고 나머지를 임시로 담을 ``t``, 이렇게 세 개의 레지스터와, 나머지를 계산하는 연산(``rem``)과 0인지 검사하는 연산(``=``)만 있으면 됩니다. 한 사이클마다 ``t``에 나머지를 넣고, ``a``에 ``b``를 넣고, ``b``에 ``t``를 넣는 세 번의 대입이 필요합니다 — 레지스터 머신 모델에서는 한 단계에 레지스터 하나만 새 값을 받을 수 있기 때문입니다.

Euclid's Algorithm for GCD needs three registers — ``a``, ``b``, and a temporary ``t`` for the remainder — plus two operations (``rem`` and ``=``). Each cycle needs three separate assignments (``t``, then ``a``, then ``b``), because this model of a register machine only lets one register receive a new value per step.

SICP describes this with data-path and controller _diagrams_ first, then a textual notation. We'll skip straight to the textual notation and, since this is Lean, make it something we can actually run: an ``inductive Instr`` for the controller language, plus an interpreter — a "controller loop" playing the same role link:../4-1-the-metacircular-evaluator/[4.1절]의 ``eval``/``apply`` did for Lisp expressions.

SICP는 이를 먼저 데이터 경로·컨트롤러 _다이어그램_으로 설명한 다음 텍스트 표기법으로 옮깁니다. 여기서는 곧장 텍스트 표기법으로 가되, Lean이니만큼 실제로 실행할 수 있는 것으로 만듭니다 — 컨트롤러 언어를 위한 ``inductive Instr``와 인터프리터를, link:../4-1-the-metacircular-evaluator/[4.1절]의 ``eval``/``apply``가 Lisp 표현식에 대해 했던 것과 같은 역할을 하는 "컨트롤러 루프"로 만듭니다.

[source,lean]
----
inductive Operand where
  | reg : String → Operand
  | const : Int → Operand
  deriving Repr

inductive AssignSrc where
  | fromReg : String → AssignSrc
  | fromConst : Int → AssignSrc
  | fromOp : String → List Operand → AssignSrc
  | fromLabel : String → AssignSrc
  deriving Repr

inductive Instr where
  | assign : String → AssignSrc → Instr
  | test : String → List Operand → Instr
  | branch : String → Instr
  | gotoLabel : String → Instr
  | gotoReg : String → Instr
  | save : String → Instr
  | restore : String → Instr
  | perform : String → List Operand → Instr
  deriving Repr
----

SICP's own text points out a restriction of this language worth carrying over exactly: operations can only take constants and register contents as inputs, never the result of another operation. ``AssignSrc.fromOp``/``Instr.test``/``Instr.perform`` all take ``List Operand`` rather than ``List AssignSrc``, so nesting an operation inside another operation's arguments simply isn't expressible — the restriction is enforced by the type, not by convention.

SICP 원문이 스스로 짚는 이 언어의 제약 하나가 그대로 옮겨질 만합니다 — 연산은 상수와 레지스터 내용만 입력으로 받을 수 있고, 다른 연산의 결과는 받을 수 없습니다. ``AssignSrc.fromOp``/``Instr.test``/``Instr.perform`` 모두 ``List AssignSrc``가 아니라 ``List Operand``를 받으므로, 한 연산의 인자 안에 다른 연산을 중첩하는 것 자체가 표현 불가능합니다 — 이 제약은 관례가 아니라 타입으로 강제됩니다.

A register can hold either a plain number or a controller-sequence label — SICP introduces this second case in link:#서브루틴-되돌아갈-곳을-레지스터에-담기[5.1.3] to support subroutine returns, but we may as well type it up front:

레지스터는 평범한 숫자를 담거나 컨트롤러 시퀀스의 레이블을 담을 수 있습니다 — SICP는 이 두 번째 경우를 서브루틴의 반환 지점을 위해 link:#서브루틴-되돌아갈-곳을-레지스터에-담기[5.1.3절]에서 도입하는데, 미리 타입에 반영해둡니다.

[source,lean]
----
inductive RegVal where
  | num : Int → RegVal
  | pc : Nat → RegVal
  deriving Repr, BEq

abbrev Regs := List (String × RegVal)

def Regs.get (r : Regs) (name : String) : RegVal :=
  (r.find? (·.1 == name)).elim (.num 0) (·.2)

def Regs.set (r : Regs) (name : String) (v : RegVal) : Regs :=
  if r.any (·.1 == name) then r.map fun (k, old) => if k == name then (k, v) else (k, old)
  else (name, v) :: r
----

``Regs``가 link:../4-1-the-metacircular-evaluator/[4.1절]의 환경 프레임(``List (String × Value)``)과 똑같은 모양이라는 게 우연이 아닙니다 — 레지스터는 결국 이름 붙은 가변 셀들의 모음이고, Lisp 평가기의 환경도 그렇습니다. 다만 여기서는 그 셀들이 프레임 사슬 없이 하나의 평평한 목록에 산다는 점만 다릅니다.

It's not a coincidence that ``Regs`` has the same shape as link:../4-1-the-metacircular-evaluator/[4.1절]의 environment frame (``List (String × Value)``) — registers are, in the end, a collection of named mutable cells, and so is a Lisp evaluator's environment. The only difference here is that these cells live in one flat list rather than a chain of frames.

Operations themselves (``rem``, ``=``, ``<``, ``-``, ``+``, ``*``) and the one _action_ (``print``, SICP's example of a ``perform``-only operation with no return value) we hardcode rather than making pluggable — SICP defers a proper extensible operation table to later sections, and a fixed dispatcher is enough to run the examples in this post:

연산 자체(``rem``, ``=``, ``<``, ``-``, ``+``, ``*``)와, 값을 반환하지 않는 ``perform`` 전용 연산의 예로 SICP가 드는 유일한 _액션_(``print``)은 확장 가능하게 만드는 대신 하드코딩합니다 — SICP도 제대로 확장 가능한 연산 테이블은 이후 절로 미루고, 이 글의 예제를 돌리는 데는 고정된 디스패처로 충분합니다.

[source,lean]
----
def evalOp (name : String) (args : List Int) : Int :=
  match name, args with
  | "rem", [a, b] => a % b
  | "=", [a, b] => if a == b then 1 else 0
  | "<", [a, b] => if a < b then 1 else 0
  | "-", [a, b] => a - b
  | "+", [a, b] => a + b
  | "*", [a, b] => a * b
  | _, _ => 0

def evalOperand (regs : Regs) : Operand → Int
  | .reg r => match regs.get r with
    | .num n => n
    | .pc _ => 0
  | .const c => c
----

The controller itself needs a program (an ``Array Instr``) and a resolved label table, then loops until the program counter runs off the end:

컨트롤러 자체는 프로그램(``Array Instr``)과 미리 풀어놓은 레이블 표가 필요하고, 프로그램 카운터가 끝을 벗어날 때까지 루프를 돕니다.

[source,lean]
----
structure Machine where
  regs : Regs
  stack : List RegVal
  flag : Bool
  pc : Nat

abbrev Labels := List (String × Nat)

def Labels.find (l : Labels) (name : String) : Nat :=
  (l.find? (·.1 == name)).elim 0 (·.2)

def buildProgram (src : List (Option String × Instr)) : Array Instr × Labels :=
  let instrs := (src.map Prod.snd).toArray
  let labels := (src.zip (List.range src.length)).filterMap fun ((lbl, _), i) =>
    lbl.map fun l => (l, i)
  (instrs, labels)

partial def run (labels : Labels) (instrs : Array Instr) (m : Machine) : IO Machine :=
  if h : m.pc < instrs.size then
    match instrs[m.pc] with
    | .assign r src => do
        let v ← match src with
          | .fromReg s => pure (m.regs.get s)
          | .fromConst c => pure (.num c)
          | .fromOp op operands => pure (.num (evalOp op (operands.map (evalOperand m.regs))))
          | .fromLabel l => pure (.pc (labels.find l))
        run labels instrs { m with regs := m.regs.set r v, pc := m.pc + 1 }
    | .test op operands =>
        let result := evalOp op (operands.map (evalOperand m.regs)) != 0
        run labels instrs { m with flag := result, pc := m.pc + 1 }
    | .branch l =>
        run labels instrs { m with pc := if m.flag then labels.find l else m.pc + 1 }
    | .gotoLabel l =>
        run labels instrs { m with pc := labels.find l }
    | .gotoReg r =>
        run labels instrs { m with pc := match m.regs.get r with | .pc n => n | .num _ => m.pc }
    | .save r =>
        run labels instrs { m with stack := m.regs.get r :: m.stack, pc := m.pc + 1 }
    | .restore r =>
        match m.stack with
        | v :: rest => run labels instrs { m with regs := m.regs.set r v, stack := rest, pc := m.pc + 1 }
        | [] => run labels instrs { m with pc := m.pc + 1 }
    | .perform op operands => do
        if op == "print" then IO.println (operands.map (evalOperand m.regs))
        run labels instrs { m with pc := m.pc + 1 }
  else
    pure m
----

[NOTE]
.``run``이 ``partial``인 이유는 결함이 아니라 본질이다
====
``run``은 ``m.pc``가 프로그램의 임의 레이블로 점프할 수 있어서 구조적으로 줄어드는 인자가 없고, 그래서 ``partial``입니다 — link:../3-1-assignment-and-local-state/[3.1절]의 ``imperativeFactorial``이 ``IO.Ref``에 숨긴 카운터 때문에 ``partial``이어야 했던 것과 정확히 같은 이유입니다. 다만 여기서는 그 "숨겨진 카운터"가 진짜로 이 언어가 표현하려는 것 — 임의의 곳으로 점프할 수 있는 프로그램 카운터 — 이라, 이건 우회해야 할 결함이 아니라 레지스터 머신이라는 개념 자체의 본질입니다.

``run`` is ``partial`` because ``m.pc`` can jump to any label in the program, so there's no argument that shrinks structurally — the same reason link:../3-1-assignment-and-local-state/[3.1절]의 ``imperativeFactorial`` needed ``partial`` for a counter hidden inside an ``IO.Ref``. Here, though, that "hidden counter" is precisely what this language is trying to express — a program counter that can jump anywhere — so this isn't a defect to work around, it's the essential nature of a register machine.
====

이제 GCD 머신을 데이터로 적어봅니다. SICP가 이 절 끝에서 보여주는 "읽고 출력하는" 변주까지 반영해서, 끝에 ``print`` 액션을 붙였습니다.

Now the GCD machine, written as data — with the "read input, print result" variation SICP shows at the end of this subsection folded in as a trailing ``print`` action:

[source,lean]
----
def gcdProgram : List (Option String × Instr) :=
  [(some "test-b", .test "=" [.reg "b", .const 0]),
   (none, .branch "gcd-done"),
   (none, .assign "t" (.fromOp "rem" [.reg "a", .reg "b"])),
   (none, .assign "a" (.fromReg "b")),
   (none, .assign "b" (.fromReg "t")),
   (none, .gotoLabel "test-b"),
   (some "gcd-done", .perform "print" [.reg "a"])]

def runGcd (a b : Int) : IO Machine := do
  let (instrs, labels) := buildProgram gcdProgram
  run labels instrs { regs := [("a", .num a), ("b", .num b)], stack := [], flag := false, pc := 0 }

#eval runGcd 206 40
-- [2]
----

'''

== 머신 설계 안의 추상화

SICP treats ``rem`` as a black-box primitive first, then shows it can be expanded into a loop of subtraction and comparison — the same "black-box abstraction" idea from link:../1-1-elements-of-programming/[1.1.8절], one level lower. Nothing about our ``Instr`` type changes to support this; it's purely a matter of writing a different ``gcdProgram`` that uses ``-`` and ``<`` instead of ``rem``, with an inner loop reusing the exact same ``test``/``branch``/``goto`` vocabulary. We won't spell out the expanded program here — the point is that the _interpreter_ doesn't need to know or care that one version calls a primitive ``rem`` and the other simulates it, exactly as SICP's controller notation doesn't distinguish them either.

SICP는 먼저 ``rem``을 블랙박스 원시 연산으로 다루다가, 뺄셈과 비교의 루프로 펼쳐낼 수 있음을 보여줍니다 — link:../1-1-elements-of-programming/[1.1.8절]의 "블랙박스 추상화" 아이디어를 한 단계 더 아래에서 반복하는 것입니다. 이를 지원하기 위해 우리의 ``Instr`` 타입은 전혀 바뀔 필요가 없습니다 — ``rem`` 대신 ``-``와 ``<``를 쓰는 다른 ``gcdProgram``을 작성하고, 그 안에 똑같은 ``test``/``branch``/``goto`` 어휘를 재사용하는 내부 루프를 넣는 문제일 뿐입니다. 여기서 펼쳐진 프로그램을 직접 적지는 않습니다 — 핵심은 _인터프리터_가 한 버전은 원시 ``rem``을 호출하고 다른 버전은 이를 시뮬레이션한다는 것을 알거나 신경 쓸 필요가 전혀 없다는 것입니다. SICP의 컨트롤러 표기법도 마찬가지로 이 둘을 구분하지 않습니다.

'''

== 서브루틴: 되돌아갈 곳을 레지스터에 담기

Two machines both needing a GCD computation could each get their own copy of the ``rem``/``=`` data-path components, but that duplicates expensive parts. Sharing one copy means the controller needs to know where to jump back to after the shared subroutine finishes — and since there might be several call sites, a fixed label won't do. SICP's answer is to let a register hold not just numbers but _labels_, exactly the ``RegVal.pc`` case we already built in: assign the return label to a ``continue`` register before jumping into the subroutine, and have the subroutine end with ``(goto (reg continue))`` instead of a fixed label.

두 머신이 모두 GCD 계산이 필요하다면 각각 ``rem``/``=`` 데이터 경로 부품을 따로 가질 수도 있지만, 그러면 비싼 부품이 중복됩니다. 하나의 사본을 공유하려면 컨트롤러가 공유 서브루틴이 끝난 뒤 어디로 되돌아갈지 알아야 하는데, 호출하는 곳이 여러 군데라면 고정된 레이블 하나로는 부족합니다. SICP의 답은 레지스터가 숫자뿐 아니라 _레이블_도 담을 수 있게 하는 것입니다 — 이미 만들어둔 ``RegVal.pc`` 경우 그대로입니다. 서브루틴으로 뛰어들기 전에 돌아갈 레이블을 ``continue`` 레지스터에 대입하고, 서브루틴은 고정된 레이블 대신 ``(goto (reg continue))``로 끝맺습니다.

This mechanism is exactly what makes the recursive machines in the next section possible, so rather than build a standalone toy subroutine example, we'll see ``continue`` used for real immediately below.

이 메커니즘이 정확히 다음 절의 재귀적 머신을 가능하게 하는 것이므로, 별도의 장난감 서브루틴 예제를 만드는 대신 바로 아래에서 ``continue``가 실전에 쓰이는 모습을 봅니다.

'''

== 스택으로 재귀 구현하기

An iterative process needs only registers, because at any point the machine's state is completely captured by their current contents. A recursive process like factorial is different: computing stem:[n!] needs stem:[(n-1)!], but unlike GCD-reduces-to-GCD, the answer to the subproblem isn't the final answer — it still has to be multiplied by stem:[n] once the subproblem returns. Naively "looping back" the way the GCD machine does would clobber the very value of ``n`` needed to finish the outer computation.

반복적 프로세스는 레지스터만 있으면 됩니다 — 어느 시점이든 머신의 상태가 현재 레지스터 내용만으로 완전히 포착되기 때문입니다. 팩토리얼 같은 재귀적 프로세스는 다릅니다 — stem:[n!]을 계산하려면 stem:[(n-1)!]이 필요한데, GCD가 GCD로 환원되는 것과 달리 부분 문제의 답이 최종 답이 아닙니다 — 부분 문제가 반환된 뒤에도 여전히 stem:[n]을 곱해야 합니다. GCD 머신처럼 그냥 "되돌아 도는" 방식을 순진하게 쓰면, 바깥 계산을 마무리하는 데 필요한 바로 그 ``n`` 값을 덮어써버립니다.

The fix is a _stack_: before recursing, ``save`` whatever registers will be needed after the subproblem returns (``n`` and ``continue``), then ``restore`` them on the way back. Our ``Instr.save``/``Instr.restore`` already push and pop ``m.stack``, so the factorial machine is a direct transcription:

해법은 _스택_입니다 — 재귀하기 전에, 부분 문제가 반환된 뒤 필요할 레지스터들(``n``과 ``continue``)을 ``save``해두고, 돌아오는 길에 ``restore``합니다. 우리의 ``Instr.save``/``Instr.restore``는 이미 ``m.stack``을 밀고 당기므로, 팩토리얼 머신은 직접 옮겨 적으면 됩니다.

[source,lean]
----
def factorialProgram : List (Option String × Instr) :=
  [(none, .assign "continue" (.fromLabel "fact-done")),
   (some "fact-loop", .test "=" [.reg "n", .const 1]),
   (none, .branch "base-case"),
   (none, .save "continue"),
   (none, .save "n"),
   (none, .assign "n" (.fromOp "-" [.reg "n", .const 1])),
   (none, .assign "continue" (.fromLabel "after-fact")),
   (none, .gotoLabel "fact-loop"),
   (some "after-fact", .restore "n"),
   (none, .restore "continue"),
   (none, .assign "val" (.fromOp "*" [.reg "n", .reg "val"])),
   (none, .gotoReg "continue"),
   (some "base-case", .assign "val" (.fromConst 1)),
   (none, .gotoReg "continue"),
   (some "fact-done", .perform "print" [.reg "val"])]

def runFactorial (n : Int) : IO Machine := do
  let (instrs, labels) := buildProgram factorialProgram
  run labels instrs { regs := [("n", .num n)], stack := [], flag := false, pc := 0 }

#eval runFactorial 6
-- [720]
----

``continue``는 매 재귀 호출마다 ``save``되고 ``restore``됩니다 — 팩토리얼의 각 "층"이 같은 ``continue`` 레지스터를 다시 쓰기 때문입니다. ``val``은 저장하지 않습니다 — 서브루틴이 반환되기 전의 옛 ``val`` 값은 쓸모가 없고, 서브계산이 만들어낸 새 값만 필요하기 때문입니다.

``continue`` gets ``save``d and ``restore``d on every recursive call, because each "layer" of the factorial computation reuses the same ``continue`` register. ``val`` is never saved — the old value of ``val`` before the subroutine returns isn't useful; only the new value produced by the subcomputation is needed.

=== 이중 재귀: 피보나치

Fibonacci needs two recursive calls per level instead of one, so there are two places to save-and-restore around, and the second call needs the first call's result (``val``) preserved across it — SICP's controller sequence for this is the most intricate program in the section, and it translates over instruction for instruction:

피보나치는 한 단계마다 재귀 호출이 하나가 아니라 둘 필요하므로, 저장하고 복원할 지점이 두 군데이고, 두 번째 호출은 그 앞에서 첫 번째 호출의 결과(``val``)를 보존해야 합니다 — SICP가 이를 위해 쓰는 컨트롤러 시퀀스는 이 절에서 가장 복잡한 프로그램이고, 명령어 하나하나 그대로 옮겨집니다.

[source,lean]
----
def fibProgram : List (Option String × Instr) :=
  [(none, .assign "continue" (.fromLabel "fib-done")),
   (some "fib-loop", .test "<" [.reg "n", .const 2]),
   (none, .branch "immediate-answer"),
   (none, .save "continue"),
   (none, .assign "continue" (.fromLabel "afterfib-n-1")),
   (none, .save "n"),
   (none, .assign "n" (.fromOp "-" [.reg "n", .const 1])),
   (none, .gotoLabel "fib-loop"),
   (some "afterfib-n-1", .restore "n"),
   (none, .restore "continue"),
   (none, .assign "n" (.fromOp "-" [.reg "n", .const 2])),
   (none, .save "continue"),
   (none, .assign "continue" (.fromLabel "afterfib-n-2")),
   (none, .save "val"),
   (none, .gotoLabel "fib-loop"),
   (some "afterfib-n-2", .assign "n" (.fromReg "val")),
   (none, .restore "val"),
   (none, .restore "continue"),
   (none, .assign "val" (.fromOp "+" [.reg "val", .reg "n"])),
   (none, .gotoReg "continue"),
   (some "immediate-answer", .assign "val" (.fromReg "n")),
   (none, .gotoReg "continue"),
   (some "fib-done", .perform "print" [.reg "val"])]

def runFib (n : Int) : IO Machine := do
  let (instrs, labels) := buildProgram fibProgram
  run labels instrs { regs := [("n", .num n)], stack := [], flag := false, pc := 0 }

#eval runFib 10
-- [55]
----

== 이게 결국 무엇을 손으로 만든 것인가

Step back and look at what ``save``/``restore``/``continue`` actually built: a call stack. Every time this series has written a ``partial def`` that calls itself — ``factorial``, ``fib``, ``sqrtIter``, ``eval``/``apply`` in link:../4-1-the-metacircular-evaluator/[4.1절] — Lean's own runtime was doing exactly this bookkeeping invisibly, pushing a return address and the values that needed to survive the call, popping them back on return. This section's ``factorialProgram`` and ``fibProgram`` are the same recursion, at the same two SICP examples this series has revisited since link:../1-2-procedures-and-processes/[1.2절], with the call stack made an explicit, inspectable ``List RegVal`` instead of a mechanism Lean's compiler provides and hides. Nothing here is a new idea; it's the oldest idea in the series, drawn at a lower level of resolution.

한 걸음 물러서서 ``save``/``restore``/``continue``가 실제로 무엇을 만들었는지 봅시다 — 콜 스택입니다. 이 시리즈에서 자기 자신을 호출하는 ``partial def``를 쓸 때마다 — ``factorial``, ``fib``, ``sqrtIter``, link:../4-1-the-metacircular-evaluator/[4.1절]의 ``eval``/``apply`` — Lean 자신의 런타임이 눈에 보이지 않게 정확히 이 부기 작업을 해주고 있었습니다 — 반환 주소와 호출 이후에도 살아남아야 할 값들을 밀어 넣고, 반환할 때 다시 꺼냅니다. 이 절의 ``factorialProgram``과 ``fibProgram``은 link:../1-2-procedures-and-processes/[1.2절]부터 이 시리즈가 계속 돌아왔던 같은 두 SICP 예제의 같은 재귀를, Lean 컴파일러가 제공하고 감춰주던 메커니즘 대신 눈에 보이는 ``List RegVal``로 명시적으로 그린 것입니다. 여기 새로운 아이디어는 없습니다 — 이 시리즈에서 가장 오래된 아이디어를, 더 낮은 해상도로 다시 그려본 것입니다.

'''

== 연습문제

*연습문제 5.1 (Lean 버전).* SICP는 stem:[b^n]을 계산하는 재귀적 지수 계산 머신을 설계해보라고 합니다. ``factorialProgram``과 정확히 같은 뼈대 — 종료 조건에서 ``branch``로 빠져나가고, 그렇지 않으면 재귀하기 전에 ``continue``와 되돌아온 뒤 필요한 레지스터를 ``save``해두는 것 — 을 그대로 재사용하면 됩니다. 다만 ``expt``는 재귀가 반환된 뒤 곱셈 한 번만 남는다는 점에서 팩토리얼과 데이터 흐름이 같고, 반대로 반복적으로(레지스터만으로, 스택 없이) 짤 수도 있다는 점에서 GCD 머신과도 같은 문제를 두 방식으로 다시 풀어보는 셈입니다. 재귀 버전을 아래처럼 작성해 보고, ``continue``/``base`` 중 어느 레지스터를 ``save``해야 하는지 스스로 정당화해 보세요.

[source,lean]
----
def exptProgram : List (Option String × Instr) :=
  [(none, .assign "continue" (.fromLabel "expt-done")),
   (some "expt-loop", .test "=" [.reg "n", .const 0]),
   (none, .branch "base-case"),
   (none, .save "continue"),
   (none, .save "base"),
   (none, .assign "n" (.fromOp "-" [.reg "n", .const 1])),
   (none, .assign "continue" (.fromLabel "after-expt")),
   (none, .gotoLabel "expt-loop"),
   (some "after-expt", .restore "base"),
   (none, .restore "continue"),
   (none, .assign "val" (.fromOp "*" [.reg "base", .reg "val"])),
   (none, .gotoReg "continue"),
   (some "base-case", .assign "val" (.fromConst 1)),
   (none, .gotoReg "continue"),
   (some "expt-done", .perform "print" [.reg "val"])]

def runExpt (base n : Int) : IO Machine := do
  let (instrs, labels) := buildProgram exptProgram
  run labels instrs { regs := [("base", .num base), ("n", .num n)], stack := [], flag := false, pc := 0 }

#eval runExpt 2 10
-- [1024]
----

이 머신이 ``n``을 저장하지 않는 것을 눈여겨보세요 — ``n``은 재귀가 반환된 뒤 다시 쓰이지 않고 오직 ``base``와 ``continue``만 살아남아야 하는데, 이는 ``factorialProgram``이 ``n``을 저장하고 ``val``은 저장하지 않았던 것과 대칭적인 선택입니다.

*연습문제 5.2 (Lean 버전).* SICP는 GCD 머신과 팩토리얼 머신을 손으로 시뮬레이션하며 각 레지스터의 값을 표로 그려보라고 합니다. ``run``을 그대로 쓰는 대신, 매 단계마다 ``Machine``의 스냅샷을 리스트에 쌓는 계측용 버전을 만들어 그 표를 코드로 재현해 봅시다.

[source,lean]
----
partial def runTraced (labels : Labels) (instrs : Array Instr) (m : Machine)
    (trace : List Machine := []) : IO (Machine × List Machine) :=
  if m.pc < instrs.size then
    -- run과 동일한 한 단계를 밟되, 매 단계 종료 후의 상태를 trace에 덧붙인다
    -- (본문의 run 정의에서 재귀 호출 지점마다 `trace ++ [m]`을 끼워 넣으면 된다)
    run labels instrs m >>= fun m' => pure (m', trace ++ [m])
  else
    pure (m, trace)

-- runFactorial 3처럼 작은 n으로 돌려, trace에 쌓인 각 Machine의 regs/stack/pc를
-- SICP가 손으로 그린 레지스터 표와 나란히 비교해 보세요.
----

작은 ``n`` (가령 ``factorialProgram``에 ``n = 3``)으로 돌려보면, ``continue``와 ``n``이 ``save``되고 ``restore``되는 정확한 시점, 그리고 ``stack``의 길이가 재귀 깊이만큼 늘었다가 다시 줄어드는 모습을 눈으로 확인할 수 있습니다 — SICP가 종이 위에서 손으로 하던 일을, ``Machine`` 값의 리스트로 그대로 재현하는 것입니다.

*연습문제 5.3 (Lean 버전).* SICP는 피보나치 머신의 컨트롤러에서 불필요한 ``save``/``restore`` 쌍을 찾아보라고 합니다. ``fibProgram``을 다시 들여다보면, ``afterfib-n-1`` 레이블 직후 ``continue``를 ``restore``했다가 곧바로 ``save "continue"``로 다시 저장하는 지점이 있습니다 — 그 사이에 ``continue``의 값을 실제로 바꾸는 명령이 하나도 없다면, 이 restore/save 쌍은 지워도 프로그램의 결과가 같아야 합니다. ``fibProgram``에서 이 지점을 찾아 지운 버전을 만들고, ``runFib``로 같은 결과가 나오는지 확인해 보세요.

[source,lean]
----
def fibProgramTrimmed : List (Option String × Instr) :=
  [(none, .assign "continue" (.fromLabel "fib-done")),
   (some "fib-loop", .test "<" [.reg "n", .const 2]),
   (none, .branch "immediate-answer"),
   (none, .save "continue"),
   (none, .assign "continue" (.fromLabel "afterfib-n-1")),
   (none, .save "n"),
   (none, .assign "n" (.fromOp "-" [.reg "n", .const 1])),
   (none, .gotoLabel "fib-loop"),
   -- 이전 버전의 (restore "continue") 뒤 곧바로 (save "continue")를 하던 쌍을
   -- 제거하고, continue를 restore하지 않은 채로 그대로 재사용한다
   (some "afterfib-n-1", .restore "n"),
   (none, .assign "n" (.fromOp "-" [.reg "n", .const 2])),
   (none, .save "continue"),
   (none, .assign "continue" (.fromLabel "afterfib-n-2")),
   (none, .save "val"),
   (none, .gotoLabel "fib-loop"),
   (some "afterfib-n-2", .assign "n" (.fromReg "val")),
   (none, .restore "val"),
   (none, .restore "continue"),
   (none, .assign "val" (.fromOp "+" [.reg "val", .reg "n"])),
   (none, .gotoReg "continue"),
   (some "immediate-answer", .assign "val" (.fromReg "n")),
   (none, .gotoReg "continue"),
   (some "fib-done", .perform "print" [.reg "val"])]

#eval do
  let (instrs, labels) := buildProgram fibProgramTrimmed
  run labels instrs { regs := [("n", .num 10)], stack := [], flag := false, pc := 0 }
-- [55] — fibProgram과 같은 결과
----

핵심은 ``save``/``restore``가 정당한지 여부가 컨트롤러의 _모양_만으로는 결정되지 않는다는 것입니다 — 두 지점 사이에서 그 레지스터를 실제로 덮어쓰는 명령이 있는지를 데이터 흐름으로 추적해야만 어떤 쌍이 진짜 필요한지 알 수 있고, 이는 다음 글(5.2절)의 ``preserving``이 자동으로 하게 될 바로 그 분석입니다.
