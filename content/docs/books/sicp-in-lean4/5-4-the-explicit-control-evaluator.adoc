'''

Every evaluator this series has written — the metacircular one, the lazy one, the ``amb`` one, the query engine — has quietly borrowed something from its host language: a call stack it never had to manage, recursive calls it never had to schedule by hand. This section is where SICP stops borrowing. The explicit-control evaluator takes the same ``eval``/``apply`` logic and rewrites it as a register machine with an actual stack register that the evaluator itself pushes to and pops from, on purpose, at named points in the control flow — the same procedure-calling mechanism every earlier evaluator got for free, now visible as data.

이 시리즈가 지금까지 만든 모든 평가기 — 메타순환 평가기, 지연 평가기, ``amb`` 평가기, 질의 엔진 — 은 모두 호스트 언어에서 무언가를 조용히 빌려왔습니다. 관리할 필요가 없던 호출 스택, 손으로 스케줄링할 필요가 없던 재귀 호출 말이죠. 이번 절은 SICP가 그 빌려오기를 그만두는 지점입니다. 명시적 제어 평가기는 같은 ``eval``/``apply`` 로직을 가져다가, 평가기 자신이 제어 흐름의 이름 붙은 지점에서 의도적으로 밀고 꺼내는 진짜 스택 레지스터를 가진 레지스터 머신으로 다시 씁니다 — 앞선 모든 평가기가 공짜로 얻었던 그 프로시저 호출 메커니즘이, 이제 데이터로 드러납니다.

Lean is in a strange position for this exercise, because it already resolved the underlying question a different way: Lean's own compiler performs tail-call optimization on structurally-recursive functions written in tail position, meaning the "does this call grow the stack or not" question this section obsesses over is something Lean's compiler already answers for you, silently, every time it compiles a function. To actually see the mechanism SICP is describing, we have to build a small interpreter that manages its own explicit control stack — refusing Lean's native call stack the same way SICP refuses Scheme's.

Lean은 이 연습에서 이상한 위치에 있습니다 — Lean 자신이 이미 이 근본 질문을 다른 방식으로 해결해 두었기 때문입니다. Lean의 컴파일러는 꼬리 위치에 있는 구조적 재귀 함수에 대해 꼬리 호출 최적화를 수행합니다. 즉 "이 호출이 스택을 늘리는가 아닌가"라는, 이 절이 그토록 집착하는 질문을, Lean 컴파일러는 함수를 컴파일할 때마다 이미 조용히 답해줍니다. SICP가 설명하는 메커니즘을 실제로 보려면, 자신만의 명시적 제어 스택을 직접 관리하는 작은 인터프리터를 만들어야 합니다 — SICP가 Scheme의 호출 스택을 거부한 것과 같은 방식으로 Lean의 네이티브 호출 스택을 거부하면서요.

'''

== 5.4.1. 명시적 스택으로 ``eval``/``apply`` 다시 쓰기

To build a register machine's worth of explicit control in Lean, we need a term language, a stack of _frames_ that record what to do with a value once it's computed, and a single loop that alternates between "evaluate an expression" and "resume a frame with a value" — exactly the two-mode structure of SICP's ``eval-dispatch``/frame-restoring code, spelled out as an explicit data type instead of labeled machine instructions:

Lean에서 레지스터 머신 수준의 명시적 제어를 만들려면, 항 언어와, 값이 계산되면 그것으로 무엇을 할지 기록하는 _프레임_들의 스택, 그리고 "식을 평가하기"와 "값으로 프레임을 재개하기" 사이를 오가는 하나의 루프가 필요합니다 — SICP의 ``eval-dispatch``/프레임 복원 코드와 정확히 같은 두 모드 구조를, 이름 붙은 기계 명령어 대신 명시적 데이터 타입으로 풀어쓴 것입니다.

[source,lean]
----
inductive Expr where
  | lit (n : Int)
  | var (name : String)
  | add (l r : Expr)
  | mul (l r : Expr)
  | ifz (c t e : Expr)   -- c = 0이면 t, 아니면 e
deriving Repr

abbrev Env := Std.HashMap String Int

inductive Frame where
  | addR (r : Expr) (env : Env)
  | addDone (l : Int)
  | mulR (r : Expr) (env : Env)
  | mulDone (l : Int)
  | ifzDone (t e : Expr) (env : Env)

def step (stack : List Frame) (env : Env) : Expr → (List Frame × Env × Expr) ⊕ Int
  | .lit n => .inr n
  | .var x => .inr (env.getD x 0)
  | .add l r => .inl (Frame.addR r env :: stack, env, l)
  | .mul l r => .inl (Frame.mulR r env :: stack, env, l)
  | .ifz c t e => .inl (Frame.ifzDone t e env :: stack, env, c)
----

``step`` never recurses — this is the whole point of writing it in explicit-control style. Every case either produces a final ``Int`` (a leaf, requiring no further evaluation) or hands back the _next_ thing to evaluate plus an updated stack. The recursion that used to be implicit in the host language's own call stack has been reified into ``List Frame``, and the driver loop that ties ``step`` together is where SICP's ``eval-dispatch``/``ev-*``/``apply-dispatch`` labels all collapse into one function:

``step``은 절대 재귀하지 않습니다 — 이것이 명시적 제어 스타일로 쓰는 요점 전체입니다. 모든 케이스는 최종 ``Int``(더 이상 평가할 필요 없는 잎)를 만들어내거나, 다음으로 평가할 것과 갱신된 스택을 돌려줍니다. 호스트 언어 자신의 호출 스택에 암묵적으로 있던 재귀가 ``List Frame``으로 구체화되었고, ``step``을 하나로 엮는 드라이버 루프가 SICP의 ``eval-dispatch``/``ev-*``/``apply-dispatch`` 레이블이 전부 하나의 함수로 붕괴되는 지점입니다.

[source,lean]
----
partial def resume (stack : List Frame) (v : Int) : (List Frame × Env × Expr) ⊕ Int :=
  match stack with
  | [] => .inr v
  | .addR r env :: rest => .inl (Frame.addDone v :: rest, env, r)
  | .addDone l :: rest => resume rest (l + v)
  | .mulR r env :: rest => .inl (Frame.mulDone v :: rest, env, r)
  | .mulDone l :: rest => resume rest (l * v)
  | .ifzDone t e env :: rest => .inl (rest, env, if v == 0 then t else e)

partial def run (env : Env) (e : Expr) : Int :=
  let rec loop (stack : List Frame) (env : Env) (e : Expr) : Int :=
    match step stack env e with
    | .inr v => match resume stack v with
      | .inr result => result
      | .inl (stack', env', e') => loop stack' env' e'
    | .inl (stack', env', e') => loop stack' env' e'
  loop [] env e

#eval run {} (.ifz (.add (.lit 1) (.lit (-1))) (.lit 100) (.lit 200))
-- 100
----

[IMPORTANT]
.이 ``partial``은 이 시리즈의 다른 ``partial``들과 이유가 다르다
====
Both ``resume`` and ``run.loop`` are marked ``partial``, and it's worth being precise about why, because it's a different reason than most ``partial``s in this series. Here, ``stack`` is a ``List Frame`` that genuinely does grow and shrink unpredictably — an ``.addR`` frame pushes onto the stack, and its matching ``.addDone`` case pops. Lean's structural-recursion checker has no way to see that this push/pop discipline is balanced and terminating, because the "argument" that would need to shrink (the whole ``(stack, env, expr)`` triple threading through ``loop``) doesn't shrink monotonically at every step — it grows on the way into a subexpression and shrinks on the way back out. This is precisely SICP's own point about a stack machine: whether the stack depth stays bounded is a property of the _specific program_ being evaluated, not something guaranteed by the shape of the interpreter.

``resume``와 ``run.loop`` 둘 다 ``partial``로 표시되어 있는데, 왜 그런지 정확히 짚어볼 가치가 있습니다 — 이 시리즈의 다른 ``partial``들과는 다른 이유이기 때문입니다. 여기서 ``stack``은 실제로 예측 불가능하게 늘었다 줄었다 하는 ``List Frame``입니다 — ``.addR`` 프레임은 스택에 밀어넣고, 짝이 되는 ``.addDone`` 케이스는 꺼냅니다. Lean의 구조적 재귀 검사기는 이 밀기/꺼내기 규율이 균형 잡혀 있고 종료한다는 것을 볼 방법이 없습니다. ``loop``을 관통하는 ``(stack, env, expr)`` 삼중조 전체라는 "인자"가 매 단계 단조롭게 줄어들지 않기 때문입니다 — 부분식으로 들어갈 때는 커지고, 돌아나올 때는 줄어듭니다. 이것이 정확히 SICP 자신이 스택 머신에 대해 짚는 지점입니다 — 스택 깊이가 유계로 유지되는가는 인터프리터의 모양이 보장해주는 것이 아니라, 평가되는 _특정 프로그램_의 성질입니다.
====

'''

== 5.4.2. 꼬리 재귀 — Lean이 이미 답을 알고 있는 곳

SICP's key observation about ``ev-sequence`` is that evaluating the _last_ expression in a sequence needs no saved registers at all — the ``continue`` register can be restored and jumped to directly, rather than pushed again, because there is nothing left to do after that final evaluation completes. Get this wrong (save registers uniformly, even for the last expression) and an iterative Scheme loop written as a self-recursive procedure call starts consuming stack proportional to the number of iterations, turning an $\Theta(1)$-space loop into an $\Theta(n)$-space one.

``ev-sequence``에 대한 SICP의 핵심 관찰은, 시퀀스의 _마지막_ 식을 평가하는 데는 저장된 레지스터가 전혀 필요 없다는 것입니다 — ``continue`` 레지스터는 다시 밀어넣는 대신 곧바로 복원되어 점프될 수 있습니다. 그 마지막 평가가 끝난 뒤에는 더 할 일이 없기 때문입니다. 이를 잘못하면(마지막 식에 대해서도 균일하게 레지스터를 저장하면), 자기 자신을 재귀 호출하는 프로시저 호출로 쓰인 반복적인 Scheme 루프가 반복 횟수에 비례하는 스택을 소모하기 시작해서, $\Theta(1)$ 공간 루프가 $\Theta(n)$ 공간 루프로 바뀌어버립니다.

Lean's compiler makes exactly this call-site distinction automatically, for any function call that appears in _tail position_ — the last thing a branch does before returning — regardless of whether the function is user-defined or a self-recursive loop. We can watch the two ``factorial`` variants from SICP's own comparison (link:#[Exercise 5.26]/link:#[5.27]) behave exactly as SICP predicts, at the level Lean actually runs at rather than at the level of our hand-rolled stack-frame interpreter:

Lean 컴파일러는 함수가 사용자 정의든 자기 재귀 루프든 상관없이, _꼬리 위치_(어떤 갈래가 반환하기 직전에 마지막으로 하는 일)에 나타나는 모든 함수 호출에 대해 정확히 이 구분을 자동으로 해줍니다. SICP 자신의 비교(연습문제 5.26/5.27)에 나오는 두 ``factorial`` 변형이, 우리가 손으로 만든 스택-프레임 인터프리터 수준이 아니라 Lean이 실제로 실행되는 수준에서, SICP가 예측하는 그대로 동작하는 것을 볼 수 있습니다.

[source,lean]
----
def factorialIter (n : Nat) : Nat :=
  let rec go (product counter : Nat) : Nat :=
    if counter > n then product else go (product * counter) (counter + 1)
  go 1 1

def factorialRec : Nat → Nat
  | 0 => 1
  | n + 1 => (n + 1) * factorialRec n

#eval factorialIter 10
-- 3628800
#eval factorialRec 10
-- 3628800
----

``factorialIter``'s recursive call to ``go`` sits in tail position in both branches of the ``if`` — nothing happens to its result before ``go`` returns it — so Lean compiles it to a loop with constant stack usage, exactly SICP's tail-recursive ``ev-sequence`` behavior. ``factorialRec``'s recursive call to itself is _not_ in tail position: its result gets multiplied by ``n + 1`` before the function returns, which is exactly the extra work SICP's non-tail-recursive ``ev-sequence`` variant does by saving registers "just in case," and it costs the same thing here — stack space proportional to ``n``, matching SICP's own measurements in Exercises 5.26/5.27 almost formula for formula.

``factorialIter``의 ``go`` 재귀 호출은 ``if``의 두 갈래 모두에서 꼬리 위치에 있습니다 — ``go``가 결과를 반환하기 전에 그 결과에 아무 일도 일어나지 않습니다 — 그래서 Lean은 이를 상수 스택 사용량을 갖는 루프로 컴파일합니다. SICP의 꼬리 재귀 ``ev-sequence`` 동작과 정확히 같습니다. ``factorialRec``의 자기 재귀 호출은 꼬리 위치가 _아닙니다_ — 함수가 반환하기 전에 결과에 ``n + 1``이 곱해지는데, 이는 SICP의 비-꼬리-재귀 ``ev-sequence`` 변형이 "혹시 몰라서" 레지스터를 저장할 때 하는 여분의 일과 정확히 같고, 비용도 똑같습니다 — ``n``에 비례하는 스택 공간이, SICP 자신이 연습문제 5.26/5.27에서 측정한 것과 거의 공식 대 공식으로 일치합니다.

The difference from SICP's presentation isn't in the underlying phenomenon — it's that SICP has to _build_ an evaluator capable of making this distinction, instruction by instruction, and prove to itself that ``ev-sequence``'s last-expression special case is what makes the difference. Lean's compiler makes the same distinction as an optimization pass you never have to write, but also never get to inspect from user-level code — if you want to see whether your own recursive function will blow the stack, you have to reason about tail position the same way SICP's assembly-level trace does, just without a register-machine simulator to watch it happen.

SICP의 설명과의 차이는 그 근본 현상에 있는 게 아니라, SICP는 이 구분을 할 수 있는 평가기를 명령어 하나하나 _만들어야_ 하고, ``ev-sequence``의 마지막-식 특수 케이스가 그 차이를 만든다는 것을 스스로 증명해야 한다는 데 있습니다. Lean의 컴파일러는 같은 구분을 여러분이 직접 쓸 필요 없는 최적화 단계로 해주지만, 사용자 수준 코드에서 들여다볼 수도 없습니다 — 여러분 자신의 재귀 함수가 스택을 터뜨릴지 보고 싶다면, SICP의 어셈블리 수준 추적과 같은 방식으로 꼬리 위치를 추론해야 합니다. 다만 그 과정을 지켜볼 레지스터 머신 시뮬레이터가 없을 뿐입니다.

*연습문제 5.26/5.27 (Lean 버전).* SICP는 스택 통계를 계측해 반복적 ``factorial``과 재귀적 ``factorial``의 최대 깊이·푸시 횟수를 표로 만들어보라고 합니다. 우리의 손으로 만든 ``step``/``resume``/``run`` 인터프리터는 이 실험을 문자 그대로 재현할 수 있는 자리입니다 — ``List Frame``의 길이가 SICP의 "푸시 횟수"에 해당하기 때문입니다.

[source,lean]
----
partial def runWithMaxDepth (env : Env) (e : Expr) : Int × Nat :=
  let rec loop (stack : List Frame) (env : Env) (e : Expr) (maxDepth : Nat) : Int × Nat :=
    let maxDepth' := max maxDepth stack.length
    match step stack env e with
    | .inr v => match resume stack v with
      | .inr result => (result, maxDepth')
      | .inl (stack', env', e') => loop stack' env' e' maxDepth'
    | .inl (stack', env', e') => loop stack' env' e' maxDepth'
  loop [] env e 0

#eval runWithMaxDepth {} (.add (.add (.lit 1) (.lit 2)) (.add (.lit 3) (.lit 4)))
-- (10, 2)
----

``Expr``에는 아직 절차 호출이나 ``if``의 꼬리 위치 최적화가 없으므로, 이 장난감 언어에서는 모든 이항 연산이 두 프레임을 쌓았다가 정확히 그만큼 되돌려받습니다 — 최대 깊이는 식의 트리 깊이에 비례합니다. SICP의 ``ev-sequence`` 최적화를 이 인터프리터에 실제로 이식해보려면, ``ifz``의 마지막 분기처럼 "이 값 다음에 더 할 일이 없는" 경우를 식별해 프레임을 아예 쌓지 않는 특수 케이스를 ``step``에 추가해야 합니다 — 이것이 정확히 SICP가 ``ev-sequence-last-exp``에서 하는 일이고, 그 특수 케이스 하나가 있고 없고가 위 절에서 본 ``factorialIter`` 대 ``factorialRec``의 차이를 만드는 바로 그 지점입니다.

'''

This closes the loop this series opened all the way back with SICP's substitution model: every subsequent evaluator — environment model, metacircular, lazy, nondeterministic, logic-programming, and now explicit-control — has been a progressively more honest answer to "what does it actually mean to evaluate an expression." Lean's contribution to that question, throughout this series, has never been a different evaluator so much as a different discipline: making termination, effects, ownership, and now control flow itself into things the type system and compiler check once, so that the rest of the program can build on top of them without re-deriving the argument every time.

이것으로 SICP의 치환 모델에서 시작한 이 시리즈의 여정이 한 바퀴 돌아 마무리됩니다 — 이후의 모든 평가기(환경 모델, 메타순환, 지연, 비결정적, 논리 프로그래밍, 그리고 이제 명시적 제어)는 "식을 평가한다는 것이 실제로 무엇을 뜻하는가"에 대해 점점 더 정직해지는 답이었습니다. 이 시리즈 내내 Lean이 이 질문에 기여한 바는 다른 평가기라기보다는 다른 규율이었습니다 — 종료성, 효과, 소유권, 그리고 이제 제어 흐름 자체까지도, 타입 시스템과 컴파일러가 한 번 검사해두는 것으로 만들어서, 나머지 프로그램이 매번 그 논증을 다시 끌어낼 필요 없이 그 위에 지을 수 있게 하는 것 말입니다.
// end::body[]
