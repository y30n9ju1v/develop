'''

Data abstraction hides _one_ representation behind an interface. But real systems often need to hide the fact that there's more than one representation at all — two teams building the same abstract notion in incompatible ways, and a third piece of code that needs to use either without caring which. SICP works this out with complex numbers: rectangular coordinates suit addition, polar coordinates suit multiplication, and neither is "the" representation.

데이터 추상화는 표현 _하나_를 인터페이스 뒤에 감춥니다. 하지만 실제 시스템에서는 표현이 하나가 아니라는 사실 자체를 감춰야 할 때가 많습니다 — 서로 다른 두 팀이 같은 추상 개념을 호환되지 않는 방식으로 구현하고, 그중 어느 쪽을 쓰든 상관없이 사용해야 하는 제3의 코드가 있는 경우입니다. SICP는 이를 복소수로 풀어냅니다 — 직교좌표는 덧셈에, 극좌표는 곱셈에 어울리고, 둘 중 어느 쪽도 "그" 표현은 아닙니다.

Scheme solves the "which representation is this pair?" problem by gluing a symbol onto the front of the data at run time — a _type tag_ that downstream code inspects before deciding what to do. Lean doesn't need that move, because an inductive type with multiple constructors already carries its tag as part of its definition, checked once at compile time rather than re-examined on every dispatch.

Scheme는 "이 쌍이 어느 표현이지?"라는 문제를, 실행 시점에 데이터 앞에 기호 하나를 붙여 해결합니다 — 이후 코드가 무엇을 할지 결정하기 전에 검사하는 _타입 태그_입니다. Lean은 이 과정이 필요 없습니다. 생성자가 여러 개인 귀납 타입은 이미 그 정의 자체에 태그를 포함하고 있고, 매 디스패치마다 다시 검사하는 게 아니라 컴파일 시점에 한 번 확인되기 때문입니다.

'''

== 2.4.1. 복소수의 표현

Rectangular form stores a real and an imaginary part directly, so addition is componentwise and easy, while magnitude and angle require a square root and an arctangent. Polar form stores a magnitude and an angle directly, so multiplication is componentwise and easy, while the real and imaginary parts require trigonometry. Neither structure is more "correct" than the other — they just make different operations cheap.

직교좌표 표현은 실수부와 허수부를 직접 저장하므로 덧셈이 성분별로 간단하지만, 크기와 각도를 구하려면 제곱근과 아크탄젠트가 필요합니다. 극좌표 표현은 크기와 각도를 직접 저장하므로 곱셈이 성분별로 간단하지만, 실수부와 허수부를 구하려면 삼각함수가 필요합니다. 둘 중 어느 쪽이 더 "옳은" 표현인 것은 아닙니다 — 그저 서로 다른 연산을 값싸게 만들어줄 뿐입니다.

Two engineers, working in isolation, might each build one of these as an ordinary Lean structure with its own constructor and its own set of accessors:

각자 따로 작업하는 두 엔지니어는, 이 둘을 각각 고유한 생성자와 접근자를 가진 평범한 Lean 구조체로 만들 수 있습니다.

[source,lean]
----
structure Rect where
  re : Float
  im : Float

def Rect.magnitude (z : Rect) : Float :=
  Float.sqrt (z.re * z.re + z.im * z.im)

def Rect.angle (z : Rect) : Float :=
  Float.atan2 z.im z.re

structure Polar where
  mag : Float
  ang : Float

def Polar.re (z : Polar) : Float := z.mag * Float.cos z.ang
def Polar.im (z : Polar) : Float := z.mag * Float.sin z.ang
----

Neither of these definitions recurses at all, so there is nothing for a termination checker to worry about here — the interesting question in this section isn't "does this function halt," it's "how does the type system let two independently-designed representations answer to the same interface."

이 정의들에는 재귀가 전혀 없으므로, 종료성 검사기가 신경 쓸 것도 없습니다 — 이 절에서 흥미로운 질문은 "이 함수가 멈추는가"가 아니라, "독립적으로 설계된 두 표현이 어떻게 같은 인터페이스에 응답하게 만드는가"입니다.

'''

== 2.4.2. 태그가 붙은 데이터

Scheme has to invent the notion of a tagged pair from scratch — ``attach-tag``, ``type-tag``, ``contents`` — because a bare Lisp pair carries no information about which representation it's supposed to be. Lean already has the mechanism SICP is reconstructing by hand: a _sum type_. Wrapping ``Rect`` and ``Polar`` under one inductive type gives every value of that type an in-built, compiler-verified tag, with no separate bookkeeping procedures required:

Scheme는 태그 붙은 쌍이라는 개념을 처음부터 직접 만들어야 합니다 — ``attach-tag``, ``type-tag``, ``contents`` — 왜냐하면 순수 Lisp 쌍은 자신이 어떤 표현이어야 하는지에 대한 정보를 전혀 담고 있지 않기 때문입니다. Lean에는 SICP가 손으로 재구성하고 있는 그 메커니즘이 이미 있습니다 — 바로 _합 타입(sum type)_입니다. ``Rect``와 ``Polar``를 하나의 귀납 타입으로 감싸면, 그 타입의 모든 값은 별도의 부기 절차 없이도 컴파일러가 검증하는 태그를 내장하게 됩니다.

[source,lean]
----
inductive Complex where
  | rect : Rect → Complex
  | polar : Polar → Complex

def Complex.realPart : Complex → Float
  | .rect z => z.re
  | .polar z => z.re

def Complex.imagPart : Complex → Float
  | .rect z => z.im
  | .polar z => z.im

def Complex.magnitude : Complex → Float
  | .rect z => z.magnitude
  | .polar z => z.mag

def Complex.angle : Complex → Float
  | .rect z => z.angle
  | .polar z => z.ang

def Complex.mkRectImag (x y : Float) : Complex := .rect ⟨x, y⟩
def Complex.mkMagAng (r a : Float) : Complex := .polar ⟨r, a⟩

def addComplex (z1 z2 : Complex) : Complex :=
  Complex.mkRectImag (z1.realPart + z2.realPart) (z1.imagPart + z2.imagPart)

def mulComplex (z1 z2 : Complex) : Complex :=
  Complex.mkMagAng (z1.magnitude * z2.magnitude) (z1.angle + z2.angle)

#eval addComplex (Complex.mkRectImag 3 4) (Complex.mkMagAng 5 0)
-- Complex.rect { re := 8.000000, im := 4.000000 }
----

[TIP]
.전수성 검사가 실제로 잡아주는 것
====
The ``match`` inside each selector _is_ the dispatch-on-type that SICP builds out of ``cond`` and ``eq?``, but here Lean's exhaustiveness checker guarantees at compile time that every constructor of ``Complex`` is handled — add a third representation later and every selector that forgot to handle it becomes a compile error instead of a silent ``error "Unknown type"`` at run time. That guarantee is the concrete payoff of trading a hand-rolled tag for a real sum type.

각 선택자 안의 ``match``가 바로 SICP가 ``cond``와 ``eq?``로 만든 "타입에 따른 디스패치"입니다. 다만 여기서는 Lean의 전수성(exhaustiveness) 검사기가 ``Complex``의 모든 생성자가 처리되었는지를 컴파일 시점에 보장해줍니다 — 나중에 세 번째 표현을 추가했을 때, 이를 처리하지 않은 선택자가 있다면 실행 시점의 ``"Unknown type"`` 에러 대신 컴파일 에러가 됩니다. 이것이 손으로 만든 태그를 진짜 합 타입으로 바꿨을 때 얻는 구체적인 이득입니다.
====

'''

== 2.4.3. 데이터 지향 프로그래밍과 추가 가능성

SICP's next move is to notice that hardcoding every representation into every selector doesn't scale: add a third representation and you must revisit every selector to add a clause. Its fix is a runtime operation-and-type table, populated by ``put`` and consulted by ``get``, so that adding a representation means adding table entries rather than editing existing procedures.

SICP가 다음으로 지적하는 문제는, 모든 표현을 모든 선택자에 하드코딩하는 방식은 확장되지 않는다는 것입니다 — 세 번째 표현을 추가하면 모든 선택자를 다시 찾아가 조건절을 추가해야 합니다. SICP의 해법은 ``put``으로 채우고 ``get``으로 조회하는 실행 시점 연산-타입 테이블입니다. 이렇게 하면 표현을 추가하는 일이 기존 절차를 수정하는 게 아니라 테이블에 항목을 추가하는 일이 됩니다.

Lean's answer to the same additivity problem is a _type class_: instead of one closed ``Complex`` sum type whose ``match``es must be revisited for every new representation, we describe what it _means_ to be complex-number-like, and let each representation supply its own instance. A brand-new representation added later needs only its own ``instance`` declaration — none of the code below is touched:

같은 확장성 문제에 대한 Lean의 답은 _타입클래스_입니다. 새 표현이 추가될 때마다 ``match``를 다시 찾아가야 하는 닫힌 ``Complex`` 합 타입 하나 대신, "복소수답다"는 것이 무엇을 뜻하는지를 서술하고 각 표현이 자신만의 인스턴스를 제공하게 합니다. 나중에 완전히 새로운 표현을 추가하려면 그것만의 ``instance`` 선언 하나만 있으면 되고, 아래 코드는 전혀 건드릴 필요가 없습니다.

[source,lean]
----
class ComplexLike (α : Type) where
  realPart : α → Float
  imagPart : α → Float
  magnitude : α → Float
  angle : α → Float

instance : ComplexLike Rect where
  realPart z := z.re
  imagPart z := z.im
  magnitude z := z.magnitude
  angle z := z.angle

instance : ComplexLike Polar where
  realPart z := z.re
  imagPart z := z.im
  magnitude z := z.mag
  angle z := z.ang

def genericAddComplex [ComplexLike α] [ComplexLike β]
    (z1 : α) (z2 : β) : Rect :=
  ⟨ComplexLike.realPart z1 + ComplexLike.realPart z2,
   ComplexLike.imagPart z1 + ComplexLike.imagPart z2⟩

#eval genericAddComplex (⟨3, 4⟩ : Rect) (⟨5, 0⟩ : Polar)
-- { re := 8.000000, im := 4.000000 }
----

[NOTE]
.합 타입과 타입클래스는 거울상 트레이드오프다
====
This is Lean's version of SICP's operation-and-type table — except the "table" is resolved by the compiler's instance search rather than looked up at run time by ``get``, so a call to a representation with no matching instance is a compile error, not a run-time ``"No method for these types"`` failure. The trade-off is the mirror image of the tagged-``Complex`` version: type classes make adding new _representations_ free (just write an ``instance``) but adding a new _operation_ to ``ComplexLike`` still means touching every existing instance, which is exactly the tension SICP's Exercise 2.76 asks you to name for ``cond``-dispatch, data-directed, and message-passing styles alike.

이는 SICP의 연산-타입 테이블에 해당하는 Lean 버전입니다 — 다만 그 "테이블"이 실행 시점에 ``get``으로 조회되는 게 아니라 컴파일러의 인스턴스 탐색으로 해소된다는 점이 다릅니다. 그래서 일치하는 인스턴스가 없는 표현을 호출하면 실행 시점의 ``"No method for these types"`` 실패가 아니라 컴파일 에러가 납니다. 이 트레이드오프는 태그 붙은 ``Complex`` 버전과 정확히 거울상입니다 — 타입클래스는 새 _표현_을 추가하는 일은 공짜로 만들어주지만(인스턴스 하나만 쓰면 됨), ``ComplexLike``에 새 _연산_을 추가하는 일은 여전히 기존 인스턴스를 전부 건드려야 합니다. 이것이 바로 SICP 연습문제 2.76이 ``cond`` 디스패치, 데이터 지향 방식, 메시지 패싱 방식 모두에 대해 짚어보라고 요구하는 바로 그 긴장 관계입니다.
====

*연습문제 2.76 (Lean 버전).* 새로운 _표현_이 자주 추가되는 시스템과, 새로운 _연산_이 자주 추가되는 시스템 중, 태그 붙은 합 타입(``inductive Complex``)과 타입클래스(``ComplexLike``) 중 어느 쪽이 각각에 더 잘 맞을까요? 이 트레이드오프는 프로그래밍 언어 이론에서 _the expression problem_이라는 이름으로 따로 연구되는 문제입니다 — 합 타입 쪽은 새 연산을 추가하기 쉽지만(``match``에 새 케이스를 얹으면 됨) 새 표현을 추가하려면 모든 기존 ``match``를 찾아 고쳐야 하고, 타입클래스 쪽은 그 반대입니다. 아래는 "새 연산 추가"가 합 타입 쪽에서 얼마나 쉬운지 보여주는 예시입니다 — ``conjugate``를 추가하는 데 기존 정의는 전혀 건드리지 않습니다.

[source,lean]
----
def Complex.conjugate : Complex → Complex
  | .rect z => .rect ⟨z.re, -z.im⟩
  | .polar z => .polar ⟨z.mag, -z.ang⟩

#eval (Complex.mkRectImag 3 4).conjugate
-- Complex.rect { re := 3.000000, im := -4.000000 }
----

반대로 ``ComplexLike``에 ``conjugate``를 추가하려면 ``Rect``와 ``Polar`` 인스턴스를 각각 찾아가 새 필드를 채워야 합니다 — 표현이 둘뿐인 지금은 사소해 보이지만, 표현이 수십 개로 늘어난 시스템에서는 이 방향의 비용이 정확히 뒤집힌다는 것이 이 연습문제의 핵심입니다.
