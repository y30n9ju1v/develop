== 왜 JavaScript로 충분하지 않은가

JavaScript는 타입을 안 써도 잘 돌아갑니다. 그런데 그게 문제입니다 — "잘 돌아간다"는 건 실행해보기 전까지는 알 수 없다는 뜻이기도 합니다.

[source,ts]
----
function double(x) {
  return x * 2;
}

console.log(double(5));       // 10
console.log(double("5"));     // 10 (문자열이 숫자로 강제 변환됨)
console.log(double("abc"));   // NaN — 실행해봐야 알 수 있음
----

`double("5")`는 우연히 그럴듯한 값(10)을 내놓고, `double("abc")`는 `NaN`을 내놓습니다. 둘 다 **실행하기 전까지는 컴퓨터도, 사람도 이게 잘못됐다는 걸 모릅니다.** 함수가 커지고 여러 파일에 흩어질수록, "이 함수에 뭘 넣어도 되는가"를 사람이 기억에 의존해 판단해야 하는 상황이 늘어납니다.

[NOTE]
====
이 예제를 `.js` 파일에 그대로 두면 아무 경고 없이 실행됩니다. 흥미롭게도 이걸 `.ts` 파일로 저장하고 이 책이 전제하는 `strict` 설정(서문에서 만든 Vite 프로젝트의 기본값)으로 검사하면, 매개변수 `x`에 타입을 하나도 안 적었다는 것 자체를 TypeScript가 이미 문제 삼습니다(`암시적으로 any 형식을 가집니다`) — "타입을 안 적으면 무엇이든 허용된 것으로 본다"는 게 아니라 "타입을 반드시 적으라고 요구한다"는 게 TypeScript의 기본 태도라는 걸 미리 보여주는 사례입니다.
====

TypeScript가 하는 일은 단순합니다 — **"이 함수는 숫자만 받는다"는 규칙을 코드에 직접 적어두고, 그 규칙을 어기는 코드는 실행되기도 전에 에러로 잡아냅니다.**

== 타입 주석: 값 옆에 규칙을 적어두기

[source,ts]
----
function double(x: number): number {
  return x * 2;
}

console.log(double(5));       // 10
----

`x: number`가 "이 매개변수는 숫자여야 한다"는 규칙이고, `): number`는 "이 함수는 숫자를 반환한다"는 규칙입니다. 이제 `double("abc")`라고 쓰면 어떻게 될까요.

[source,ts]
----
function double(x: number): number {
  return x * 2;
}

double("abc"); // 컴파일 에러: string 형식의 인수는 number 형식의 매개변수에 할당될 수 없습니다.
----

`npx tsc`로 이 코드를 검사하면 프로그램이 **실행되기도 전에** 에러가 납니다. 이게 TypeScript의 핵심 가치입니다 — 버그를 "실행해서 발견"하는 대신 "컴파일해서 발견"하는 쪽으로 옮기는 것입니다.

[NOTE]
====
TypeScript는 브라우저나 Node.js가 직접 실행하는 언어가 아닙니다 — TypeScript 컴파일러(`tsc`)가 타입 주석을 전부 지운 평범한 JavaScript로 바꿔준 다음, 그 JavaScript가 실행됩니다. 즉 타입은 **컴파일 시점에만** 존재하고, 실행 시점에는 완전히 사라집니다. "런타임에 타입을 검사해주는 도구"가 아니라 "코드를 실행하기 전에 미리 검토해주는 도구"라는 게 이 책 전체에서 반복해서 확인할 관점입니다.
====

== 타입 추론: 매번 타입을 적을 필요는 없다

[source,ts]
----
let count = 5;        // count: number로 자동 추론됨
count = "hello";       // 컴파일 에러: string 형식은 number 형식에 할당할 수 없습니다.
----

`count`에 타입을 명시하지 않았는데도 TypeScript는 `5`라는 값을 보고 "이건 `number`구나"를 스스로 알아냅니다 — 이걸 **타입 추론(type inference)**이라고 부릅니다. 그래서 그 뒤에 문자열을 대입하려 하면 에러가 납니다. 타입 주석을 항상 손으로 적어야 하는 게 아니라, TypeScript가 문맥에서 알아낼 수 있는 경우엔 생략해도 됩니다 — 정확히 언제 생략하고 언제 명시해야 하는지는 다음 장에서 다룹니다.

== 기본 타입 몇 가지

[source,ts]
----
let personName: string = "Ada";
let age: number = 36;
let isStudent: boolean = false;
let tags: string[] = ["math", "computing"];       // 문자열 배열
let pair: [string, number] = ["Ada", 36];          // 튜플: 길이와 각 자리 타입이 고정된 배열

console.log(personName, age, isStudent, tags, pair);
----

[NOTE]
====
변수 이름을 `name`이 아니라 `personName`으로 쓴 데는 이유가 있습니다 — 브라우저 환경에서는 전역 객체에 이미 `name`(창 이름)이라는 문자열 변수가 존재해서, 최상위 스코프에 `let name`을 선언하면 그 전역 선언과 충돌합니다. 사소해 보이지만, "타입스크립트가 브라우저의 기존 전역까지 다 알고 있다가 충돌을 잡아준다"는 것 자체가 이 언어가 그냥 문법 검사기가 아니라는 걸 보여주는 사례입니다.
====

`string[]`은 "문자열이 몇 개든 들어있는 배열"이고, `[string, number]`(튜플)은 "정확히 두 자리, 첫 번째는 문자열, 두 번째는 숫자"라는 훨씬 좁은 규칙입니다. 배열과 튜플을 구분해서 쓰는 이유는, "몇 번째 자리에 뭐가 있는지"가 의미 있는 데이터(예: `[x좌표, y좌표]`)는 튜플로 표현해야 그 자리가 뒤바뀌는 실수를 컴파일 시점에 잡아낼 수 있기 때문입니다.

== 직접 해보기

* `add(a: number, b: number): number` 함수를 만들고, `add(1, "2")`처럼 잘못된 인자를 넣었을 때 어떤 에러 메시지가 나오는지 확인해보세요.
* 튜플 `[string, number]` 대신 실수로 `[number, string]`으로 선언하면, `["Ada", 36]`을 대입할 때 에러가 나는지 확인해보세요.

.해답 보기
[%collapsible]
====
[source,ts]
----
function add(a: number, b: number): number {
  return a + b;
}
// add(1, "2"); // 컴파일 에러: string 형식의 인수는 number 형식의 매개변수에 할당될 수 없습니다.

const wrong: [number, string] = [36, "Ada"]; // 이 순서로는 통과 — 자리 순서를 실제로 바꿔야 에러가 남을 확인
console.log(add(1, 2), wrong);
----
====

== 요약

* JavaScript는 실행해보기 전까지 "이 값이 맞는 타입인가"를 알 수 없습니다 — TypeScript는 그 확인을 실행 전(컴파일 시점)으로 옮깁니다.
* 타입 주석(`x: number`)은 값 옆에 규칙을 적어두는 것이고, 이 규칙을 어기면 컴파일 에러가 납니다.
* 타입은 컴파일 시점에만 존재하고, 컴파일된 JavaScript에는 타입 정보가 전혀 남지 않습니다.
* 타입 추론 덕분에 모든 곳에 타입을 손으로 적을 필요는 없습니다 — 언제 생략해도 되는지는 다음 장에서 다룹니다.
