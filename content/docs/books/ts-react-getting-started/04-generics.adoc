== 문제: "아무 타입이나 받는 함수"를 어떻게 표현하나

배열의 첫 번째 원소를 돌려주는 함수를 만든다고 합시다. 숫자 배열에도, 문자열 배열에도 다 쓰고 싶습니다.

[source,ts]
----
function firstElement(arr: any[]) {
  return arr[0];
}

const n = firstElement([1, 2, 3]);
const s = firstElement(["a", "b"]);

n.toUpperCase(); // 컴파일 에러가 안 남! n은 사실 숫자인데 문자열 메서드를 호출해도 통과됨
----

`any[]`로 받으면 숫자 배열도 문자열 배열도 다 받을 수 있지만, 대가가 있습니다 — 반환값도 `any`가 되어버려서, `n`이 사실 숫자인데 `.toUpperCase()`(문자열 메서드)를 불러도 **컴파일러가 아무 말도 안 합니다.** `any`는 "이 값에 대해서는 타입 검사를 하지 마라"는 뜻이라, 1장에서 얻으려던 것(실행 전에 실수를 잡는 것)을 그 지점에서 완전히 포기하는 셈입니다.

== 해법: 타입을 매개변수로 받기

함수가 값을 매개변수로 받듯이, **타입도 매개변수로 받을 수 있습니다.**

[source,ts]
----
function firstElement<T>(arr: T[]): T {
  return arr[0];
}

const n = firstElement([1, 2, 3]);      // T가 number로 자동 추론됨 -> n: number
const s = firstElement(["a", "b"]);      // T가 string으로 자동 추론됨 -> s: string

console.log(n.toFixed(2));   // number 메서드 — 정상
console.log(s.toUpperCase()); // string 메서드 — 정상
----

`<T>`가 "이 함수는 `T`라는 이름의 타입을 하나 매개변수로 받는다"는 뜻입니다. `arr: T[]`는 "`T` 타입의 배열을 받는다", `: T`는 "`T` 타입 하나를 반환한다"는 뜻입니다. `firstElement([1, 2, 3])`을 호출하는 순간, TypeScript는 인자로 넘어온 배열이 `number[]`라는 걸 보고 `T`가 `number`라고 자동으로 채워 넣습니다 — 함수 인자를 넘기면 매개변수가 채워지는 것과 정확히 같은 방식으로, **타입 인자**가 채워지는 것입니다. 그래서 `n`은 진짜 `number`, `s`는 진짜 `string`이 되고, 잘못된 메서드를 부르면 이제 다시 에러가 납니다.

== any와 제네릭의 차이를 한 줄로

`any[]`로 받은 값은 반환될 때 **타입 정보가 사라집니다.** `T[]`로 받은 값은 반환될 때 **"들어온 것과 같은 타입"이라는 관계가 유지됩니다.** 제네릭이 하는 일은 "아무 타입이나 받아도 된다"가 아니라, **"입력 타입과 출력 타입 사이의 관계를 유지한 채로 아무 타입이나 받는다"**는 것입니다 — 이 관계 유지가 `any`에는 없는, 제네릭만의 가치입니다.

== 제네릭 인터페이스: 상자 모양은 같은데 안에 든 게 다를 때

[source,ts]
----
interface Box<T> {
  value: T;
}

const numberBox: Box<number> = { value: 42 };
const stringBox: Box<string> = { value: "hello" };

console.log(numberBox.value.toFixed(1), stringBox.value.toUpperCase());
----

`Box<T>`는 "상자 모양은 똑같지만 안에 뭘 담을지는 나중에 정한다"는 패턴입니다. `Box<number>`라고 쓰는 순간 `T` 자리가 전부 `number`로 채워집니다. React를 배우기 시작하면 API 응답을 감싸는 `ApiResponse<T>` 같은 패턴에서 이 모양을 계속 다시 만나게 됩니다.

== 제네릭 제약: "아무 타입"에서 "이런 성질을 가진 타입"으로 좁히기

[source,ts]
----
function printLength<T extends { length: number }>(item: T): T {
  console.log(item.length);
  return item;
}

printLength("hello");        // 문자열도 length가 있음
printLength([1, 2, 3]);      // 배열도 length가 있음
// printLength(42);          // 컴파일 에러: number에는 length가 없음
----

`T extends { length: number }`는 "`T`는 아무 타입이나 되는 게 아니라, 적어도 `length: number`라는 필드는 갖고 있어야 한다"는 제약입니다. 이렇게 하면 `item.length`를 함수 안에서 안전하게 쓸 수 있으면서도, 문자열이든 배열이든 "길이가 있는 것"이라면 뭐든 받을 수 있는 유연함을 동시에 가져갑니다.

== 직접 해보기

* `wrapInArray<T>(value: T): T[]`를 만들어, 숫자를 넣으면 `number[]`가, 문자열을 넣으면 `string[]`이 나오는지 확인해보세요.
* `Pair<A, B>` 인터페이스(타입 매개변수 두 개, `first: A`와 `second: B`)를 만들고 `Pair<string, number>` 값을 만들어보세요.

.해답 보기
[%collapsible]
====
[source,ts]
----
function wrapInArray<T>(value: T): T[] {
  return [value];
}

const nums = wrapInArray(5);
const strs = wrapInArray("hi");

interface Pair<A, B> {
  first: A;
  second: B;
}

const p: Pair<string, number> = { first: "Ada", second: 36 };

console.log(nums, strs, p);
----
====

== 요약

* `any`는 타입 검사를 끄는 것과 같아서, 편해 보여도 실수를 잡아주는 능력을 그 자리에서 잃습니다.
* 제네릭(`<T>`)은 타입을 함수 매개변수처럼 받아, "입력과 출력 타입 사이의 관계"를 유지하면서도 여러 타입에 재사용 가능한 코드를 만듭니다.
* 제네릭 인터페이스(`Box<T>`)로 "모양은 같지만 내용물 타입은 다른" 구조를 표현할 수 있습니다.
* `T extends { ... }`로 "아무 타입"이 아니라 "이런 필드를 가진 타입만"으로 제약을 걸 수 있습니다.
