== API 응답을 어떤 타입으로 받을 것인가

[source,tsx]
----
interface User {
  id: number;
  name: string;
}

async function fetchUser(id: number): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  const data = await res.json(); // data는 any
  return data as User; // "이 데이터는 User 모양일 것이다"라는 단언
}
----

`res.json()`은 서버가 실제로 뭘 돌려줄지 컴파일러가 알 방법이 없어 `any`를 반환합니다. `data as User`(타입 단언)로 "이건 `User` 모양이라고 믿어달라"고 컴파일러에게 말해주지만, 이건 **약속이지 검증이 아닙니다** — 서버가 실제로 다른 모양의 데이터를 보내도 TypeScript는 이 코드를 통과시킵니다. 이 책의 범위를 넘어서지만, 실전에서는 Zod 같은 런타임 검증 라이브러리로 "정말 이 모양이 맞는지"까지 확인하는 경우가 많습니다 — 지금은 "타입 단언은 컴파일러를 안심시킬 뿐, 실제 데이터를 검증하지는 않는다"는 것만 기억해둡니다.

== 로딩 상태를 판별 유니온으로 표현하기

API 호출은 "아직 안 끝남", "성공", "실패" 세 상태를 거칩니다. 5장에서 배운 판별 유니온이 정확히 이 상황을 위한 도구입니다.

[source,tsx]
----
type RequestState<T> =
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; message: string };

function useUser(id: number): RequestState<User> {
  const [state, setState] = useState<RequestState<User>>({ status: "loading" });

  useEffect(() => {
    setState({ status: "loading" });
    fetchUser(id)
      .then((data) => setState({ status: "success", data }))
      .catch((err) => setState({ status: "error", message: String(err) }));
  }, [id]);

  return state;
}
----

`RequestState<T>`가 4장의 제네릭과 5장의 판별 유니온을 합친 것입니다 — "로딩 중이거나, 성공해서 `T` 타입 데이터를 가졌거나, 실패해서 메시지를 가졌거나" 셋 중 하나입니다. 12장에서 배운 커스텀 훅(`useUser`)으로 이 로직을 감싸면, 컴포넌트 쪽 코드는 훨씬 단순해집니다.

[source,tsx]
----
function UserProfile({ userId }: { userId: number }) {
  const state = useUser(userId);

  if (state.status === "loading") {
    return <p>로딩 중...</p>;
  }
  if (state.status === "error") {
    return <p>에러: {state.message}</p>;
  }
  return <p>{state.data.name}</p>; // 여기서는 state가 success로 좁혀져 data에 안전하게 접근
}
----

5장에서 판별 유니온의 진짜 가치가 "새 상태를 추가했는데 처리를 빠뜨리면 컴파일 에러가 난다"는 것이라고 했는데, 여기서도 그대로 적용됩니다 — `success`가 아닌 두 경우를 먼저 걸러내야만, 컴파일러가 `state.data`에 접근하도록 허락합니다.

== 제어 컴포넌트: React가 입력값의 "유일한 진실"이 되게 하기

[source,tsx]
----
interface LoginFormValues {
  email: string;
  password: string;
}

function LoginForm({ onSubmit }: { onSubmit: (values: LoginFormValues) => void }) {
  const [values, setValues] = useState<LoginFormValues>({ email: "", password: "" });

  function handleChange(event: React.ChangeEvent<HTMLInputElement>) {
    const { name, value } = event.target;
    setValues((prev) => ({ ...prev, [name]: value }));
  }

  function handleSubmit(event: React.FormEvent<HTMLFormElement>) {
    event.preventDefault(); // 브라우저의 기본 폼 제출(페이지 새로고침)을 막음
    onSubmit(values);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input name="email" value={values.email} onChange={handleChange} />
      <input name="password" type="password" value={values.password} onChange={handleChange} />
      <button type="submit">로그인</button>
    </form>
  );
}
----

`<input value={values.email} onChange={handleChange} />`처럼 입력값을 State로 관리하고, 그 State를 다시 `value`에 그대로 넣어주는 패턴을 **제어 컴포넌트(controlled component)**라고 부릅니다. 사용자가 타이핑해도 브라우저가 알아서 입력창 내용을 바꾸는 게 아니라, `onChange` → `setValues` → 리렌더링 → `value`로 다시 표시라는 경로를 매번 거칩니다. 번거로워 보이지만, 이렇게 하면 **"지금 입력값이 무엇인가"에 대한 유일한 진실(source of truth)이 State**가 됩니다 — 7장에서 봤던 단방향 데이터 흐름을, 폼 입력에도 똑같이 적용한 것입니다. `{ ...prev, [name]: value }`는 이전 값들을 그대로 펼쳐 놓고 `name`에 해당하는 필드만 갈아 끼우는 것으로, 각 `input`마다 별도 핸들러를 안 만들어도 되게 해줍니다.

interface Product {
  id: number;
  name: string;
}

function useProducts(): RequestState<Product[]> {
  const [state, setState] = useState<RequestState<Product[]>>({ status: "loading" });

  useEffect(() => {
    fetch("/api/products")
      .then((res) => res.json())
      .then((data: Product[]) => setState({ status: "success", data }))
      .catch((err) => setState({ status: "error", message: String(err) }));
  }, []);

  return state;
}

function LoginFormWithValidation({ onSubmit }: { onSubmit: (values: LoginFormValues) => void }) {
  const [values, setValues] = useState<LoginFormValues>({ email: "", password: "" });
  const [error, setError] = useState<string | null>(null);

  function handleChange(event: React.ChangeEvent<HTMLInputElement>) {
    const { name, value } = event.target;
    setValues((prev) => ({ ...prev, [name]: value }));
  }

  function handleSubmit(event: React.FormEvent<HTMLFormElement>) {
    event.preventDefault();
    if (values.password.length < 8) {
      setError("비밀번호는 8자 이상이어야 합니다.");
      return;
    }
    setError(null);
    onSubmit(values);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input name="email" value={values.email} onChange={handleChange} />
      <input name="password" type="password" value={values.password} onChange={handleChange} />
      {error && <p>{error}</p>}
      <button type="submit">로그인</button>
    </form>
  );
}

== 요약

* API 응답은 `any`로 시작하고, 타입 단언(`as User`)은 컴파일러를 안심시킬 뿐 실제 데이터를 검증하지는 않습니다.
* 로딩/성공/실패라는 세 가지 상태는 5장의 판별 유니온으로 표현하면, 처리를 빠뜨렸을 때 컴파일 에러로 알 수 있습니다.
* 제어 컴포넌트는 입력값을 State로 관리해, "지금 입력값이 무엇인가"의 유일한 진실을 React 쪽에 두는 패턴입니다.
* 여기까지가 1부(TypeScript)와 2부(React)를 실제로 합친 모습입니다 — 새로운 개념은 거의 없고, 지금까지 배운 것들의 조합입니다.
