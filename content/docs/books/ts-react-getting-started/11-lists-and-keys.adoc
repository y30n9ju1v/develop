== key가 푸는 문제: "이전 항목과 새 항목이 같은 것인가"

9장에서 재조정이 "이전 트리와 새 트리를 비교해 달라진 부분만 반영한다"고 했습니다. 리스트에서는 이 비교가 특히 까다롭습니다 — 항목이 추가되거나 삭제되거나 순서가 바뀌면, React는 **"새 리스트의 이 항목이, 이전 리스트의 어느 항목과 같은 것인가"**를 알아야 "바뀐 부분만" 반영할 수 있습니다. `key`는 정확히 이 질문에 답하는 이름표입니다.

[source,tsx]
----
function ItemList({ items }: { items: { id: string; label: string }[] }) {
  return (
    <ul>
      {items.map((item) => (
        <li key={item.id}>{item.label}</li>
      ))}
    </ul>
  );
}
----

`key={item.id}`는 "이 `<li>`는 `id`가 이거인 항목을 나타낸다"는 걸 React에게 알려줍니다. 다음번 렌더링에서 이 `id`를 가진 항목이 여전히 있으면, React는 그 `<li>`의 실제 DOM 노드를 **재사용**합니다(9장에서 확인했던 그 재사용입니다) — 순서가 바뀌었어도, 삭제됐던 항목이 없어도, `id`만 같으면 "이건 그 항목"이라고 인식합니다.

== index를 key로 쓰면 왜 문제가 생기는가

`item.id`가 없어서 배열 인덱스를 `key`로 쓰는 경우가 흔합니다.

[source,tsx]
----
function TodoList() {
  const [todos, setTodos] = useState(["세탁", "장보기", "청소"]);

  return (
    <ul>
      {todos.map((todo, index) => (
        <li key={index}>
          <input type="checkbox" />
          {todo}
        </li>
      ))}
    </ul>
  );
}
----

각 항목에 체크박스가 있다고 해봅시다. "세탁" 항목의 체크박스를 체크한 다음, 맨 앞에 새 항목("설거지")을 추가하면 어떻게 될까요.

[source,text]
----
체크 전:      [세탁(index 0), 장보기(index 1), 청소(index 2)]
"세탁"을 체크: [세탁✓(index 0), 장보기(index 1), 청소(index 2)]
맨 앞에 추가:  [설거지(index 0), 세탁(index 1), 장보기(index 2), 청소(index 3)]
----

새 배열에서 `index 0`은 이제 "설거지"입니다. `key`가 `index`이므로 React는 "`key=0`인 `<li>`는 이전과 같은 항목"이라고 착각하고, **체크박스의 체크 상태(그 `<li>` DOM 노드에 남아있던 State)를 그대로 재사용**해버립니다. 그 결과 실제로는 **"설거지" 항목이 체크된 것처럼 보이고, "세탁"은 체크가 풀린 것처럼 보입니다** — 데이터는 정확한데(각 `todo` 문자열은 제자리에 있는데), 화면에 남아있던 부수적인 상태(체크박스 UI 상태)가 엉뚱한 항목에 눌러앉는 것입니다.

== 안정적인 key로 이 문제를 해결하기

[source,tsx]
----
interface Todo {
  id: string;
  label: string;
}

function TodoList() {
  const [todos, setTodos] = useState<Todo[]>([
    { id: "a", label: "세탁" },
    { id: "b", label: "장보기" },
    { id: "c", label: "청소" },
  ]);

  return (
    <ul>
      {todos.map((todo) => (
        <li key={todo.id}>
          <input type="checkbox" />
          {todo.label}
        </li>
      ))}
    </ul>
  );
}
----

`id`는 항목이 생성될 때 한 번 부여되고 그 항목이 사라질 때까지 절대 안 바뀌는 값입니다(순서가 바뀌어도 `id`는 그대로 그 항목을 따라다닙니다). 이제 맨 앞에 새 항목을 추가해도, React는 `key="a"`가 여전히 "세탁"이라는 걸 정확히 알고, 그 항목의 체크박스 상태를 "세탁"에 그대로 유지합니다.

== 그럼 index를 아예 쓰면 안 되나

리스트가 **절대 재정렬되지 않고, 항목 추가/삭제도 맨 끝에서만 일어나며, 각 항목이 체크박스처럼 자기만의 상태를 갖지 않는** 경우엔 `key={index}`도 실제로 문제가 없습니다. 정적으로 한 번 그려지고 다시 안 바뀌는 목록이 대표적입니다. 문제가 되는 건 정확히 "리스트 순서가 바뀔 수 있는데, 각 항목이 화면에 자기만의 흔적(입력값, 체크 상태, 애니메이션 진행도 등)을 남기는" 조합입니다 — 이 조건에 해당하지 않는다면 index도 실용적인 선택입니다.

== 직접 해보기

* 위의 `key={index}` 버전 `TodoList`를 실제로 브라우저에서 실행해, "세탁"을 체크한 뒤 새 항목을 맨 앞에 추가하면 체크 표시가 어디에 남는지 직접 확인해보세요.
* 같은 실험을 `key={todo.id}` 버전으로 다시 해보고, 이번엔 체크 표시가 "세탁"을 정확히 따라가는지 확인해보세요.

== 요약

* `key`는 재조정 과정에서 "이전 리스트의 이 항목과 새 리스트의 이 항목이 같은 것인가"를 React에게 알려주는 이름표입니다.
* `key={index}`는 리스트 순서가 바뀔 수 있고 각 항목이 자기만의 화면 상태(체크박스, 입력값 등)를 가질 때, 그 상태를 엉뚱한 항목에 붙여버리는 버그로 이어질 수 있습니다.
* 항목이 생성될 때 부여되고 절대 바뀌지 않는 고유 `id`를 `key`로 쓰면 이 문제가 사라집니다.
* 순서가 절대 안 바뀌고 항목이 자기만의 상태를 안 갖는 목록이라면 `key={index}`도 실용적인 선택입니다 — 모든 상황에서 무조건 나쁜 건 아닙니다.
