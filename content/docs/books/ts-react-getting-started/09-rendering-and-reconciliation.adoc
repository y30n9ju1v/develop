== "다시 렌더링"은 "화면을 다 지우고 새로 그린다"가 아니다

8장에서 `setCount`를 부르면 컴포넌트 함수가 다시 호출된다고 했습니다. 그런데 만약 그 말 그대로 "함수를 다시 호출해서 나온 JSX로 화면을 처음부터 다시 그린다"면, 이상한 일이 생겨야 합니다.

[source,tsx]
----
function App() {
  const [count, setCount] = useState(0);
  return (
    <div>
      <input placeholder="여기에 뭔가 입력해보세요" />
      <p>{count}</p>
      <button onClick={() => setCount(count + 1)}>+</button>
    </div>
  );
}
----

이 코드를 브라우저에서 실행해서, `input`에 글자를 몇 개 입력한 다음 `+` 버튼을 눌러보세요. `count`가 바뀌면 `App` 함수 전체가 다시 호출되는데도, **`input`에 입력해둔 텍스트는 그대로 남아 있고, 커서 위치도 그대로 유지됩니다.** 만약 화면을 정말로 "지우고 새로 그렸다"면, `input`도 새로 만들어졌을 것이고 입력값과 포커스는 사라졌어야 합니다.

== 왜 이게 중요한가: DOM은 무겁다

6장에서 DOM이 "브라우저가 HTML 문서를 메모리에 표현해두는 트리"라고 했습니다. 여기서 중요한 사실 하나를 더해야 합니다 — **DOM 노드는 평범한 JS 객체보다 훨씬 무겁습니다.** DOM 노드는 스타일 계산·레이아웃(각 요소가 화면 어디에 얼마나 크게 그려지는지)·이벤트 처리 등과 얽혀 있는 브라우저 내부 구조체라, DOM 노드를 추가·삭제·수정할 때마다 브라우저는 레이아웃을 다시 계산하고(reflow) 화면을 다시 그리는(repaint) 비용을 치릅니다.

그래서 만약 React가 State가 바뀔 때마다 "이전 화면을 지우고 처음부터 다시 그린다"는 식으로 동작했다면, `count` 하나 바뀌었다고 `<input>`까지 통째로 새로 만들고 다시 그리는 불필요하게 무거운 작업이 매번 벌어졌을 것입니다 — 그 과정에서 `input`에 입력해둔 값이나 포커스처럼 "실제 DOM 노드에 남아있던 상태"도 함께 사라졌을 것입니다. React가 이 무거움을 피하려고 택한 전략이 바로 재조정입니다.

== 재조정: 새 결과물과 이전 결과물을 비교해서 차이만 반영한다

React는 컴포넌트 함수를 다시 호출한 결과(새 JSX 트리)를 바로 화면에 반영하지 않습니다. 대신 **이전에 그렸던 트리와 새로 나온 트리를 비교**해서, **실제로 달라진 부분만** 진짜 DOM에 반영합니다. 이 비교·최소 반영 과정을 **재조정(reconciliation)**이라고 부릅니다.

방금 예제에서 `count`만 바뀌었으므로, React가 비교했을 때 `<p>{count}</p>`의 내용만 다르고 `<input>`은 똑같습니다. 그래서 React는 "`<p>` 안의 텍스트만 바꾸고, `<input>`은 원래 있던 그 DOM 노드를 그대로 둔다"는 최소한의 변경만 실제 화면에 적용합니다 — `input`의 값과 포커스가 그대로인 이유가 이것입니다. **화면에 보이는 DOM 노드가 실제로 같은 노드로 유지된다**는 걸, 아래에서 직접 확인해봅니다.

== DOM 노드가 재사용된다는 걸 직접 확인하기

[source,text]
----
1. count=0일 때 <input> DOM 노드의 참조를 저장해둔다
2. setCount(1)을 호출해 재렌더링을 일으킨다
3. 다시 <input> DOM 노드를 찾아 1번에서 저장해둔 것과 "===" 로 비교한다
4. 같은 노드라면(true), React가 새로 만들지 않고 재사용했다는 뜻이다
----

이 절차를 실제로 실행하면 3번의 비교가 **`true`**로 나옵니다 — `count`가 바뀌어 컴포넌트 함수가 다시 호출됐어도, `<input>`에 대응하는 실제 DOM 노드는 처음 만들어졌던 바로 그 객체입니다. React는 "새 트리를 그렸다"가 아니라 "이전 트리와 비교해서 `<p>` 노드의 텍스트 하나만 바꿨다"는 걸 이 결과가 보여줍니다.

== 재조정이 헷갈릴 때: 리스트의 순서가 바뀌면

[source,tsx]
----
function ItemList({ items }: { items: string[] }) {
  return (
    <ul>
      {items.map((item) => <li>{item}</li>)}
    </ul>
  );
}
----

이 코드는 사실 실행하면 콘솔에 경고가 뜹니다 — "리스트의 각 자식에게 고유한 `key` prop을 줘야 한다"는 경고입니다. `key`가 없으면 React는 "이전 트리의 `<li>` 세 개"와 "새 트리의 `<li>` 세 개"를 비교할 때, **각 `<li>`가 서로 같은 항목인지 아니면 다른 항목인지 구분할 방법이 없습니다** — 그냥 순서(위치)로 짐작할 수밖에 없습니다. 이게 왜 문제가 되는지, 그리고 `key`가 어떻게 이 문제를 해결하는지는 다음다음 장(11장)에서 자세히 다룹니다 — 지금은 "재조정이 각 항목을 구분할 단서가 필요하다"는 것만 기억해두면 됩니다.

== 렌더링과 커밋, 두 단계로 나눠 생각하기

지금까지 본 걸 정리하면 React의 재렌더링은 사실 두 단계입니다.

1. **렌더링(render) 단계**: 컴포넌트 함수를 호출해 "이번엔 이런 모양이어야 한다"는 새 트리를 계산합니다. 아직 화면은 하나도 안 바뀝니다.
2. **커밋(commit) 단계**: 그 새 트리를 이전 트리와 비교(재조정)해서, 실제로 달라진 부분만 진짜 DOM에 반영합니다.

[source,text]
----
setCount(1) 호출
      │
      ▼
[1. 렌더링] App() 함수를 다시 호출 → 새 트리 계산 (아직 화면 그대로)
      │
      ▼
[재조정] 이전 트리 vs 새 트리 비교 → <p>만 다르다고 판단
      │
      ▼
[2. 커밋] <p> 노드의 텍스트만 실제 DOM에 반영, <input>은 그대로 재사용
      │
      ▼
화면 갱신 완료
----

"State가 바뀌면 컴포넌트가 다시 렌더링된다"는 문장이 실제로 뜻하는 건 이 두 단계 전체입니다 — **함수는 매번 새로 호출되지만(1단계), 화면은 필요한 만큼만 바뀝니다(2단계).** 이 구분이 왜 중요한지는, 컴포넌트 함수 안에서 "화면을 직접 조작"하려는 시도(다음 장에서 다룰 `useEffect`가 필요해지는 지점)를 이해할 때 다시 등장합니다.

== 직접 해보기

* 8장의 `Counter` 컴포넌트 옆에 `<input>`을 하나 추가하고, 카운터를 눌러도 입력해둔 텍스트가 지워지지 않는다는 걸 브라우저에서 직접 확인해보세요.
* `items.map((item) => <li>{item}</li>)`를 `items.map((item, index) => <li key={index}>{item}</li>)`로 고쳐, 콘솔 경고가 사라지는지 확인해보세요(이 `key={index}`가 사실은 완전히 안전한 해법이 아니라는 것도 11장에서 다룹니다).

== 요약

* DOM 노드는 레이아웃·스타일 계산과 얽힌 무거운 브라우저 구조체라, 조작할 때마다 reflow·repaint 비용이 듭니다 — React가 재조정을 하는 근본적인 이유입니다.
* 컴포넌트 함수가 다시 호출되는 것(렌더링)과 화면(DOM)이 실제로 바뀌는 것(커밋)은 같은 일이 아닙니다 — React는 그 사이에서 이전 트리와 새 트리를 비교해 최소한의 변경만 실제로 반영합니다(재조정).
* 이 덕분에 관련 없는 State가 바뀌어도, `input`의 입력값·포커스처럼 화면에 남아 있어야 할 것들이 사라지지 않습니다.
* 리스트를 렌더링할 때 `key`가 없으면 React가 "이전 항목과 새 항목이 같은 것인지"를 판단할 단서가 없어져, 재조정이 엉뚱한 결과를 낼 수 있습니다.

다음 장에서는 "화면을 다시 그리는 것" 자체가 아니라 그 바깥의 일 — API 호출처럼 화면 그리기 규칙만으로는 표현할 수 없는 부수효과를 언제, 어떻게 다뤄야 하는지 `useEffect`로 살펴봅니다.
