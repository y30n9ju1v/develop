이 책 전체에서 쓸 예제를 준비합니다 — `torchvision`의 사전학습된 ResNet18을 ONNX로 export하고, 아무 최적화도 하지 않은 상태의 속도를 측정해서 앞으로의 모든 개선을 비교할 기준선을 세웁니다.

== ResNet18을 ONNX로 export하기

[source,python]
----
import torch, torchvision

m = torchvision.models.resnet18(weights=torchvision.models.ResNet18_Weights.DEFAULT)
m.eval()
x = torch.randn(1, 3, 224, 224)
torch.onnx.export(m, x, "resnet18.onnx", opset_version=17,
                   input_names=["input"], output_names=["output"])
----

[source]
----
$ python export.py
exported
$ ls -la resnet18.onnx
-rw-r--r--  1 user  staff  106736 resnet18.onnx
----

ImageNet 1000클래스로 사전학습된 표준 이미지 분류 모델입니다 — Conv, BatchNorm(export 시 Conv에 흡수됨), ReLU, MaxPool, 잔차 연결(Add)로 이루어진 18층짜리 CNN입니다. `onnx.checker`로 그래프 구조가 올바른지, `onnxruntime`으로 실제 추론이 되는지 먼저 확인합니다.

[source,python]
----
import numpy as np, onnxruntime as ort
sess = ort.InferenceSession("resnet18.onnx", providers=["CPUExecutionProvider"])
x = np.random.rand(1,3,224,224).astype(np.float32)
y = sess.run(None, {"input": x})[0]
print(y.shape, y.argmax())
----

[source]
----
(1, 1000) 111
----

1000개 클래스 중 하나(111번)로 분류됩니다 — 그래프가 실제로 끝까지 도는 걸 확인했습니다.

== 기준선 1: PyTorch eager 실행

최적화를 논하기 전에, "아무것도 안 하면 얼마나 걸리는가"부터 잽니다. 학습에 쓰던 PyTorch 모델을 그대로 추론에 쓰면 어떨까요 — 스레드 개수를 1개로 고정해서(멀티스레딩으로 인한 변수를 없애고 순수 계산량 차이만 보기 위해) 잽니다.

[source,python]
----
torch.set_num_threads(1)
with torch.no_grad():
    for _ in range(3):  # 워밍업
        m(x)
    t0 = time.perf_counter()
    for _ in range(50):
        m(x)
    t1 = time.perf_counter()
print(f"pytorch eager (1 thread): {(t1-t0)/50*1000:.3f}ms/inference")
----

[source]
----
pytorch eager (1 thread): 10.675ms/inference
----

== 기준선 2: 최적화를 끈 ONNX 실행

`onnxruntime`은 기본적으로 그래프를 최적화해서 실행합니다 — 최적화를 끄면(`ORT_DISABLE_ALL`) 어떻게 될까요.

[source,python]
----
so = ort.SessionOptions()
so.graph_optimization_level = ort.GraphOptimizationLevel.ORT_DISABLE_ALL
so.intra_op_num_threads = 1
sess = ort.InferenceSession("resnet18.onnx", sess_options=so, providers=["CPUExecutionProvider"])
----

[source]
----
DISABLE_ALL: 11.163ms/inference
----

PyTorch eager(10.675ms)와 거의 같습니다 — 둘 다 "그래프를 있는 그대로, 노드 하나하나를 순서대로" 실행하기 때문입니다. 이게 이 책 전체의 진짜 기준선입니다.

== 기준선 3: 기본 설정 ONNX 실행

이제 `onnxruntime`의 기본 동작(`ORT_ENABLE_ALL`, 무엇을 하는지는 2~3장에서 하나씩 풀어봅니다)으로 같은 그래프를 돌립니다.

[source,python]
----
so = ort.SessionOptions()
so.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
so.intra_op_num_threads = 1
sess = ort.InferenceSession("resnet18.onnx", sess_options=so, providers=["CPUExecutionProvider"])
----

[source]
----
ENABLE_ALL: 4.833ms/inference
----

세 기준선을 한 표로 모으면:

[cols="2,1"]
|===
|실행 방식 |지연시간

|PyTorch eager |10.675ms
|ONNX, 최적화 끔 |11.163ms
|ONNX, 최적화 기본값 |4.833ms
|===

**아무것도 안 한 그래프(약 11ms)와 `onnxruntime`이 기본으로 최적화한 그래프(4.83ms) 사이에 이미 2.3배 차이가 있습니다** — 이 책이 앞으로 다룰 "최적화"라는 말이 추상적인 게 아니라, `onnxruntime`이 이미 기본으로 하고 있는 일(2~3장에서 정확히 무엇인지 봅니다)조차 이 정도 효과를 낸다는 걸 보여줍니다. 이 책의 나머지 10개 장은 이 2.3배가 정확히 어디서 오는지 뜯어보고, 그 위에 양자화·MLIR 컴파일·커널 튜닝·알고리즘 자체의 최적화를 더 얹습니다.

== 직접 해보기

`intra_op_num_threads`를 1 대신 4로 바꾸면(이 환경의 CPU가 멀티코어이므로) `ORT_ENABLE_ALL` 설정의 지연시간이 어떻게 바뀔까요? "스레드를 늘리면 무조건 빨라진다"가 이렇게 작은 배치(1장 이미지 1장)에서도 성립하는지 확인해보세요.

.해답 보기
[%collapsible]
====
[source,python]
----
so = ort.SessionOptions()
so.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
so.intra_op_num_threads = 4
sess = ort.InferenceSession("resnet18.onnx", sess_options=so, providers=["CPUExecutionProvider"])
----

[source]
----
ENABLE_ALL, intra_op_num_threads=4: 6.233ms/inference
----

**오히려 느려졌습니다**(4.833ms → 6.233ms, 약 29% 손해) — "코어를 더 쓰면 빠르다"는 예상과 정반대입니다. 배치 크기가 1이라 병렬화할 "독립적인 작업"이 애초에 많지 않은데, `intra_op_num_threads=4`는 Conv 연산 **하나**를 4개 스레드로 쪼개려 시도합니다 — 이 정도로 작은 텐서(예: 마지막 레이어들은 채널 수는 많지만 공간 해상도가 7×7까지 줄어듭니다)에서는 스레드를 나누고 결과를 다시 합치는 조율 비용이 병렬화로 아끼는 계산 시간보다 커집니다. "일감을 나눠서 병렬로 처리하면 빠르다"는 직관은 나눌 일감 자체가 충분히 클 때만 성립합니다 — 일감이 작으면 나누고 다시 모으는 오버헤드가 병렬화로 아끼는 시간보다 커지고, 이 현상이 CPU 멀티스레딩에서도 그대로 나타난 겁니다. 실제 배포에서는 배치 크기를 키워서 병렬화할 일감 자체를 늘리거나(서버), 아예 스레드를 1개로 고정하는(모바일/엣지, 코어를 다른 프로세스와 나눠 써야 하므로) 두 전략이 이런 이유로 흔합니다.
====
