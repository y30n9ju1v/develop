== 기존 도구를 먼저 살펴본다

새 걸 만들기 전에 이미 있는 도구가 이 문제를 얼마나 풀어놨는지 확인하는 게 순서입니다. 조사해보면 업계 도구는 거의 전부 **OpenDRIVE → Lanelet2** 방향(시뮬레이터 맵을 실차 스택으로 가져오는 방향)만 다룹니다. TUM의 `opendrive2lanelet`이 대표적입니다.

이유는 명확합니다. OpenDRIVE → Lanelet2 변환기 내부를 들여다보면, 참조선(수식)을 촘촘히 샘플링해서 좌표점으로 뿌리는 것으로 끝납니다 — 수식에서 점을 뽑는 건 쉬운 방향입니다. 반대로 Lanelet2 → OpenDRIVE는 점 나열에서 수식을 **역추정**해야 하는데, 이건 일반적으로 답이 유일하지 않은 곡선 피팅 문제입니다. 그래서 이 방향의 도구가 생태계에 거의 없는 겁니다.

다만 이 조사가 헛수고는 아닙니다 — `opendrive2lanelet` 같은 성숙한 반대 방향 도구는 나중에 **라운드트립 검증**(10장)에 재활용할 수 있습니다: 우리가 만든 결과물을 다시 Lanelet2로 되돌려서 원본과 비교하면, 변환 전체를 검사하는 결정적인 회로가 하나 생깁니다.

== 왜 굳이 중간 표현이 필요한가

다음 갈림길로 넘어가기 전에, 더 근본적인 질문부터 짚어야 합니다 — 애초에 왜 `Lanelet2 XML → OpenDRIVE XML`을 바로 옮기는 함수 하나를 짜면 안 되는가?

처음 봐서는 중간 표현이 그냥 한 단계를 더 넣는 것처럼, 불필요한 복잡함으로 보일 수 있습니다. 이 프로젝트가 **한 번에 완성되지 않는다**는 걸 알기 전까지는요.

이 책의 2부(4~6장)를 미리 보면, 참조선을 계산하는 방법을 이 프로젝트 안에서 **세 번** 바꿉니다 — 처음엔 구간별로 따로 피팅했다가, 그게 이음새를 어긋나게 만든다는 걸 발견해서 전역 최적화로 바꾸고, 그다음엔 "중심선" 자체의 정의가 편향돼 있다는 걸 발견해서 경계에 직접 피팅하는 방식으로 또 바꿉니다. 3부·4부에서도 신호등·고도·교차로 같은 새 요소를 계속 추가합니다.

*IR 없이 직접 변환기를 짰다면* 이 변경 하나하나가 "곡선을 어떻게 계산할지"와 "그 결과를 OpenDRIVE XML 문법(`<geometry s="..." x="..." hdg="..." length="...">`)으로 어떻게 써낼지"가 뒤섞인 코드를 매번 건드려야 한다는 뜻입니다. 알고리즘을 바꿀 때마다 XML 직렬화 코드도 같이 손대야 하고, 결과가 이상하면 "수학이 틀렸나, XML 문법을 잘못 썼나"를 매번 다시 구분해야 합니다. 알고리즘 하나 바꾸는 데 파일 포맷 세부사항까지 같이 신경 쓰는 상황이 반복되는 겁니다.

중간에 IR을 두면 이 두 관심사가 갈라집니다.

[source]
----
Lanelet2 XML → (여기서 알고리즘이 계속 바뀐다: 4~9장 전체) → IR → (여기는 거의 안 바뀐다) → OpenDRIVE XML
----

한번 IR의 형태를 정해두면, "곡선을 어떻게 계산할지" 쪽 코드는 자유롭게 갈아엎으면서도 "IR을 OpenDRIVE XML로 써내는" 코드는 건드릴 필요가 없어집니다. 컴파일러가 소스 코드를 기계어로 바로 옮기지 않고 중간에 AST(추상 구문 트리)를 두는 것과 같은 이유입니다 — 파서(입력을 읽는 쪽)와 코드 생성기(출력을 쓰는 쪽)를 분리해두면, 한쪽이 아무리 복잡해져도 다른 쪽은 안정적으로 유지됩니다.

== IR의 뼈대를 정한다

이제 IR을 둔다는 것 자체는 정했으니, 그 IR의 형태를 정할 차례입니다. Lanelet2 → OpenDRIVE 사이에 중간 표현(Intermediate Representation, IR)을 하나 두고 "Lanelet2 → IR → OpenDRIVE" 2단계로 나눕니다.

문제는 IR을 설계할 때 첫 갈림길입니다 — **IR의 핵심 스키마를 Lanelet2 모델(좌표점 폴리라인)로 잡을 것인가, OpenDRIVE 모델(참조선+파라메트릭 단면)로 잡을 것인가?**

이 책은 **OpenDRIVE 모델을 IR의 뼈대로 선택**합니다. 이렇게 하면:

* IR → OpenDRIVE 익스포트는 손실 없는 직역에 가까워집니다. IR이 이미 참조선(수식)을 들고 있으니, OpenDRIVE의 `<geometry>`로 옮기는 건 그냥 필드 복사입니다.
* 어려운 작업(좌표점 나열에서 참조선을 역추정하는 곡선 피팅)이 **Lanelet2 → IR 한쪽 방향에만 집중**됩니다.

반대로 IR을 Lanelet2 모델(폴리라인)에 맞췄다면, 이번엔 IR → OpenDRIVE 방향에서 매번 곡선 피팅을 해야 해서 문제가 그대로 이동할 뿐 해결되지 않습니다. **어려운 문제를 없애는 게 아니라, 한 방향으로 몰아넣는다**는 게 이 설계 결정의 핵심입니다.

이 선택이 실제로 얼마나 도움이 됐는지는 이 책 뒷부분에서 몇 번이고 확인하게 됩니다 — 4~6장에 걸쳐 참조선 피팅 알고리즘을 세 번 갈아엎는데(독립 피팅 → 전역 최적화 → 경계 대칭 피팅), 그때마다 OpenDRIVE 익스포트 코드는 단 한 줄도 안 바뀝니다. IR이 이미 OpenDRIVE 네이티브 형태이기 때문입니다.

== IR 스키마 초안

지리/토폴로지를 표현하는 부분과, 변환 과정의 근거를 남기는 부분을 처음부터 분리해서 설계합니다. 왜 분리하는지는 바로 다음 절에서 설명합니다 — 먼저 스키마부터 보겠습니다.

[source]
----
Network
├── roads: [Road]
├── junctions: [Junction]
└── signals: [Signal]

Road
├── id
├── reference_line: ReferenceLine       # 참조선 (평면 형상)
├── elevation_profile: ElevationProfile # 고도 — 참조선과 독립적으로 관리 (9장)
├── superelevation: SuperelevationProfile  # 횡단 경사 (9장)
├── lane_sections: [LaneSection]        # s-구간별 차선 단면
└── predecessor / successor: RoadLink | JunctionLink

ReferenceLine
└── segments: [LineSeg | ArcSeg | ParamPoly3Seg]

LaneSection
├── s_start
└── lanes: [Lane]

Lane
├── id            # OpenDRIVE 규약: 0=참조선, 음수=우측, 양수=좌측
├── type          # driving/shoulder/...
├── width: PolyCoeffs(a, b, c, d)
├── road_mark: RoadMark
└── link: predecessor_id / successor_id

Junction
└── connections: [(incoming_road, connecting_road, lane_links)]

Signal
├── id
├── road_id, s, t            # 참조선 피팅이 선행돼야 계산 가능 (9장)
├── kind: "traffic_light" | "speed_limit" | ...
├── applicable_lane_ids: [int]
└── source_regulatory_element_id  # 이 Signal이 어느 원본 lanelet 규제요소에서 왔는지
----

`Road`, `ReferenceLine`, `LaneSection`, `Lane`은 2장에서 본 OpenDRIVE 구조를 거의 그대로 옮긴 것입니다. `elevation_profile`, `superelevation`, `Signal`은 처음부터 다 채워져 있지 않았습니다 — 실제로 변환 파이프라인을 만들다가 "z가 어디로 갔지?", "신호등은 어디 담지?" 하는 빈틈을 발견할 때마다 하나씩 추가한 것들입니다. 9장에서 그 발견 과정을 그대로 보여줍니다.

== 왜 프로버넌스를 따로 관리하는가

지리/토폴로지 정보와 별개로, 변환 결과 요소마다 "무엇으로부터 어떻게 만들어졌는지"를 구조화된 형태로 함께 냅니다.

[source]
----
RoadProvenance
├── road_id
├── source_lanelet_ids: [id]
├── fit_method: "arc" | "line" | "paramPoly3"
├── fit_residual_max_m / fit_residual_rms_m   # 참조선 피팅이 원본과 얼마나 벗어났는지
├── curvature_error_max                        # 위치 오차와 별개인 곡률 오차
├── joint_gap_max_m / joint_heading_jump_max_rad  # 세그먼트 이음새 불연속 (5장)
├── dropped_attributes: [string]
├── mark_defaulted_count: n
└── topology_warnings: [string]                # 알고리즘이 확신 못 한 부분
----

이 프로버넌스를 지리 정보와 분리해서 관리하는 이유는 **검증 전략과 직결**됩니다. 이 책은 정밀한 수치 계산은 결정적(deterministic) 코드가 담당하고, LLM은 그 결과를 검토하는 리뷰어 역할로 한정하는 원칙을 씁니다(10장에서 자세히 다룹니다). 이 역할 분담이 가능하려면, "이 변환이 얼마나 정확한가"를 나타내는 숫자들이 애초에 구조화된 형태로 어딘가에 모여 있어야 합니다 — 프로버넌스가 그 자리입니다.

그리고 실전에서는 이 프로버넌스 스키마가 계속 늘어납니다. 이 책의 4~9장을 진행하면서 이음새 불연속, 곡률 오차, pairing 편향, 횡가속도 점프 같은 지표를 새로 만날 때마다 프로버넌스에 필드를 하나씩 추가하게 됩니다. 처음부터 완벽하게 설계하려 하지 말고, **새로 발견하는 문제마다 측정 가능한 필드를 하나씩 얹는 습관**을 들이는 게 이 방식의 요점입니다.

다음 장부터는 이 IR을 실제로 채우는 작업 — 좌표점 나열을 참조선 수식으로 바꾸는 참조선 피팅을 시작합니다.
