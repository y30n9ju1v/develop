지금까지 6장에 걸쳐 lanelet **하나**를 참조선 하나로 바꾸는 문제를 풀었습니다. 그런데 OpenDRIVE의 `Road`는 lanelet 하나가 아니라, 여러 lanelet이 이어진 긴 도로 구간에 대응합니다. 이 장에서는 어떤 lanelet들을 하나의 `Road`로 묶을지 결정하는 문제 — **그룹핑(A)** — 를 다룹니다.

== 그룹핑이 필요한 이유

실측 지도 하나를 열어보면, 도로 하나가 여러 개의 짧은 lanelet으로 잘게 쪼개져 있는 걸 보게 됩니다. 좌우로는 차선 수만큼(같은 단면), 앞뒤로는 도로가 이어지는 방향으로 여러 개가 붙어 있습니다. 이 낱개들을 그대로 하나씩 `Road`로 만들면 참조선이 수백 미터짜리 도로가 아니라 몇 미터짜리 조각으로 쪼개져 나오고, 6장까지 애써 만든 매끄러운 전역 피팅의 장점도 반쯤 사라집니다. 두 단계가 필요합니다 — 좌우로 인접한 lanelet을 묶어 "차선 단면"(LaneSection)을 만들고, 그 단면들을 앞뒤로 이어 "Road"를 만드는 것.

== 첫 시도: node id로 연결을 판정한다

OSM 포맷은 연결된 lanelet들이 실제로 같은 `node` id를 공유합니다 — 앞 lanelet의 끝점과 뒤 lanelet의 시작점이 좌표만 비슷한 게 아니라 **id가 정확히 같습니다.** 그러니 좌표 근접 판정 대신 정확한 id 일치로 종방향 연결을 잡을 수 있습니다.

[source,python]
----
def lanelet_endpoints(ways, ll, sides=("left",)):
    starts, ends = set(), set()
    for side in sides:
        nodes = ways[ll[side]]
        starts.add(nodes[0]); ends.add(nodes[-1])
    return starts, ends

# 클러스터 i의 끝 node id가 클러스터 j의 시작 node id와 겹치면 i -> j로 연결
----

이 방식으로 왼쪽 경계선 id만 비교하면, 실제로는 이어져 있는데 오른쪽 경계선에서만 id가 일치하는 케이스를 놓칩니다. "왼쪽 또는 오른쪽 중 하나만 맞아도 연결"로 완화하면, 이번엔 교차로에서 서로 무관한 lanelet들이 좌표를 우연히 공유하는 스퓨리어스 매치가 급증합니다. "왼쪽 그리고 오른쪽 모두"로 엄격하게 하면 진짜 연결까지 놓칩니다. 세 기준 모두 실패입니다 — **정확한 id 매칭만으로는 부족하고, 근접 거리와 진행 방향(heading) 일치까지 함께 봐야 한다**는 게 결론입니다.

== 공식 도구로 해결한다: RoutingGraph

이 문제는 이미 Lanelet2 라이브러리 자체가 풀어놓은 문제입니다. `lanelet2.routing.RoutingGraph`가 정확히 근접 거리 + 진행 방향까지 고려해서 `following()`(종방향 연결)·`left()`/`right()`(횡방향 인접)를 계산해줍니다. 파이썬 바인딩은 `pip install lanelet2`로 설치되는데, macOS(Apple Silicon)에서는 소스 빌드가 무거워서 이 책에서는 Docker(`--platform linux/amd64`) 컨테이너에서 실행합니다.

[source,python]
----
import lanelet2
from lanelet2.projection import UtmProjector

origin = lanelet2.io.Origin(49.0, 8.4)
laneletMap = lanelet2.io.load("mapping_example.osm", UtmProjector(origin))

traffic_rules = lanelet2.traffic_rules.create(
    lanelet2.traffic_rules.Locations.Germany,
    lanelet2.traffic_rules.Participants.Vehicle,
)
routing_graph = lanelet2.routing.RoutingGraph(laneletMap, traffic_rules)

for ll in laneletMap.laneletLayer:
    following = routing_graph.following(ll)   # 종방향 successor
    lefts = routing_graph.left(ll)             # 횡방향 인접
----

이걸로 다시 그룹핑을 돌리면 확실히 나아집니다 — node id 방식이 만들던 스퓨리어스 매치가 사라지고 Road당 평균 클러스터 수가 늘어납니다.

== 그런데 "차량 경로"와 "물리적 연결"은 다르다

여기서 예상 밖의 발견이 나옵니다. `Participants.Vehicle` 교통규칙으로 만든 `RoutingGraph`는 자전거·보행자와 공유하는 저속 구간(예: `participant:bicycle: yes`가 붙은 혼합 통행로)을 표준 차량 경로 탐색에서 **제외**합니다. 그래서 물리적으로는 도로가 분명히 이어져 있는데도 `following()`에 안 잡히는 lanelet들이 나옵니다.

이 규칙은 "법규상 허용된 차량 경로가 뭔가"를 답하도록 설계된 것이지, "이 도로가 물리적으로 어떻게 생겼는가"를 답하도록 만들어진 게 아닙니다. 우리가 만드는 건 경로 탐색기가 아니라 **시뮬레이션용 도로 형상**입니다 — 혼합 통행 구간도 차량이 저속으로 지나갈 수 있는 구간이라면 지오메트리 상으로는 여전히 필요합니다.

수정은 간단합니다 — Vehicle 하나가 아니라 **Vehicle/Bicycle/Pedestrian 세 `RoutingGraph`의 합집합**으로 연결을 판정합니다. 자전거·보행자 공유 구간은 최소 하나의 참가자 그래프에서는 정상적으로 라우팅되기 때문입니다.

[source,python]
----
def build_graphs(lanelet_map):
    participants = [lanelet2.traffic_rules.Participants.Vehicle,
                    lanelet2.traffic_rules.Participants.Bicycle,
                    lanelet2.traffic_rules.Participants.Pedestrian]
    return [lanelet2.routing.RoutingGraph(
                lanelet_map,
                lanelet2.traffic_rules.create(lanelet2.traffic_rules.Locations.Germany, p))
            for p in participants]

def union_following(graphs, ll):
    result = {}
    for g in graphs:
        for f in g.following(ll):
            result[f.id] = f
    return list(result.values())
----

이렇게 바꾸니 스퓨리어스 매치를 다시 늘리지 않으면서(분기점·합류점 수는 거의 그대로) 물리적으로 이어진 구간을 더 많이 잡아냈습니다 — 원래 놓쳤던 고립 lanelet의 상당수가 회복됐습니다.

== 이 정도로도 완벽하지는 않다

세 그래프를 합쳐도 여전히 남는 고립 lanelet이 있었습니다. 조사해보니 남은 것들은 대부분 진짜 지도 데이터의 결측(도로 스캔이 끊긴 구간)이거나, 세 참가자 유형 어디에도 안 걸리는 진짜 예외적인 케이스였습니다. **모든 위상 문제를 알고리즘만으로 완벽히 풀려고 하는 대신**, 이런 남은 케이스는 3장에서 만든 `topology_warnings` 필드에 담아 사람이나 LLM이 검토하도록 넘기는 게 이 책이 택한 방향입니다.

[TIP]
====
*그룹핑 알고리즘의 세부 로직 하나가 뒤 단계 결과 전체를 좌우한 사례*

클러스터(단면)를 만든 뒤, 각 클러스터를 대표하는 lanelet 하나를 고르는 로직이 나중에 조용한 버그를 만든 적이 있습니다 — 대표를 그냥 "멤버 리스트의 첫 번째"로 골랐더니, 신호등과 무관한 lanelet이 우연히 대표로 뽑혀서 도로 중심선이 실제 정지선에서 5m 가까이 벌어졌습니다(9장에서 다루는 정지선 위치 계산에 영향을 줬습니다). 수정은 "대표 하나"가 아니라 **클러스터 멤버 전체의 평균 중심선**을 쓰는 것이었습니다. 그룹핑 단계의 사소해 보이는 설계 하나가 몇 단계 뒤(신호등 위치)에서 문제로 드러난 사례입니다 — 파이프라인의 앞 단계 결정을 가볍게 여기면 안 되는 이유입니다.
====
