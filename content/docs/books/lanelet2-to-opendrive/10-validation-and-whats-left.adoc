9장까지 IR을 채우는 방법을 다뤘습니다. 이 장은 두 가지를 묻습니다 — **만든 결과물이 정말 맞는지 어떻게 확인하는가**, 그리고 **이 파이프라인을 아무 Lanelet2 맵에나 써도 되는가**.

== 첫 번째 검증: 실제로 xodr을 만들어본다

지금까지는 잔차·오차 같은 숫자만 재왔지, 실제 `.xodr` 파일을 한 번도 만들지 않았습니다. IR이 이미 OpenDRIVE 네이티브 파라미터(3장에서 내린 결정)로 돼 있으니, 익스포트는 거의 직역입니다.

[source,python]
----
def road_xml(road_id, params, n_segs):
    x, y, h = params[0], params[1], params[2]
    kappas = params[3:3+n_segs]
    lengths = params[3+n_segs:3+2*n_segs]
    geoms, s = [], 0.0
    for k, L in zip(kappas, lengths):
        body = "<line/>" if abs(k) < 1e-4 else f'<arc curvature="{k:.10f}"/>'
        geoms.append(f'<geometry s="{s:.6f}" x="{x:.6f}" y="{y:.6f}" '
                      f'hdg="{h:.10f}" length="{L:.6f}">{body}</geometry>')
        if abs(k) < 1e-4:
            x, y = x + L*np.cos(h), y + L*np.sin(h)
        else:
            x = x + (np.sin(h+k*L) - np.sin(h)) / k
            y = y - (np.cos(h+k*L) - np.cos(h)) / k
            h = h + k*L
        s += L
    return f'<road id="{road_id}" length="{s:.4f}"><planView>{"".join(geoms)}</planView></road>'
----

== 두 번째 검증: 라운드트립

3장에서 미뤄둔 약속을 지킬 차례입니다 — 반대 방향(OpenDRIVE → Lanelet2) 도구인 TUM `opendrive2lanelet`으로 방금 만든 xodr을 **다시 Lanelet2로 되돌려서** 원본과 비교합니다. 전 구간이 결정적 코드로 이루어진 검증 회로라, 사람이 눈으로 훑어보는 것보다 신뢰도가 높습니다.

[source,python]
----
from opendrive2lanelet.opendriveparser.parser import parse_opendrive
from opendrive2lanelet.network import Network

odr = parse_opendrive(etree.parse("output.xodr").getroot())
net = Network(); net.load_opendrive(odr)
lanelets = net.export_commonroad_scenario().lanelet_network.lanelets

# 원본 Lanelet2 중심선과, 라운드트립으로 돌아온 참조선 사이 거리를 잰다
for original_centerline in originals:
    d = min(point_to_polyline_dist(original_centerline, np.asarray(l.left_vertices)).mean()
            for l in candidate_lanelets)
----

이렇게 여러 Road로 돌려보면(다른 Lanelet2 맵으로 검증한 이전 실측 기준), 이 end-to-end 오차가 4장에서 잰 피팅 잔차와 사실상 동일하게 나왔습니다 — 즉 **직렬화와 서드파티 파싱이 더하는 오차는 거의 없고**, 오차 예산 전체가 피팅 자체에서 나온다는 뜻입니다. "우리가 만든 xodr을 성숙한 외부 도구가 정상적으로 읽고, 기하가 보존된다"는 걸 확인하는 게 이 단계의 목적입니다. 이 책의 예제 맵(`lanelet2_map.osm`)으로 이 라운드트립을 다시 돌리는 건 아직 안 했습니다 — 4~9장의 수치는 전부 이 맵에서 새로 쟀지만, 라운드트립만은 재검증이 남은 항목입니다.

이 검증은 lanelet 단위 Road에서만 했습니다 — 8장의 Junction까지 반영한 라운드트립, 그리고 esmini나 CARLA 같은 **실제 시뮬레이터**에 로딩해보는 건 아직 안 했습니다. 파싱 성공은 "문법이 맞다"만 확인하지, 시뮬레이터가 그 위에서 차량을 정상 주행시키는지는 다른 문제입니다.

== 세 번째 검증: LLM을 리뷰어로 쓴다

수치 검증만으로는 안 잡히는 문제가 있습니다 — 예를 들어 렌더링 버그(색상 대비가 약해서 화면에서 안 보이는 것)는 잔차 숫자에 안 나타납니다. 여기서 이 책이 쓰는 원칙은 하나입니다: **정밀한 수치 계산은 결정적 코드가 담당하고, LLM은 그 결과를 검토하는 리뷰어로만 쓴다.** "숫자 정밀도 비교"는 LLM이 원래 취약한 영역이라, 애초에 그 역할을 맡기지 않습니다.

구체적으로는 파이프라인이 계산한 지표(잔차 분포, 이음새 위치)와, 원본 경계선·피팅 결과를 겹쳐 그린 시각화를 함께 LLM에 줍니다. 실제로 이렇게 해봤더니, 정량 지표로는 절대 안 잡히는 렌더링 버그 두 개(밝은 테마에서 원본 경계선 저대비, 확대 시 마커 크기 왜곡)를 시각 검토로 잡아냈습니다. 반대로 "지도가 듬성듬성해 보인다"는 것도 처음엔 버그로 의심했지만, 알고 보니 예제 맵 자체가 여러 시나리오를 모아둔 합성 맵이라 정상이라는 것도 확인했습니다 — LLM 판단과 정량 지표를 맞대봐야 이런 판단이 가능합니다.

이 역할 분담을 시각화 페이지에 명시적으로 반영하는 게 도움이 됩니다. 예를 들어 "선 두 개가 겹치는지 눈으로 비교하라"는 VL(vision-language) 모델이 원래 취약한 과제입니다. 참조선을 잔차 크기에 따라 색으로 인코딩(초록→빨강)하고, 이음새 불연속을 별도 마커로 찍고, 잔차 상위 케이스에 숫자 라벨을 직접 박아두면 — "선이 겹치나?"라는 어려운 질문이 "빨간 부분이 있나?"라는 쉬운 질문으로 바뀝니다. LLM이 잘하는 것(패턴 인식, 자연어 요약)만 쓰고 못하는 것(정밀 비교)은 원천적으로 안 시키는 설계입니다.

[IMPORTANT]
====
*로컬 LLM을 쓸 때의 주의*: 사내 GPU에 자체 호스팅한 비전 모델을 리뷰어로 쓰려는 경우, 반드시 **같은 요청을 여러 번 반복해서 응답이 일관되는지** 확인하세요. 실제로 테스트해보니 어떤 로컬 비전 모델은 같은 이미지·같은 프롬프트에도 정상 응답, 거짓 응답("이미지가 안 보인다"), 완전히 무관한 내용의 환각, 순수 타임아웃이 뒤섞여 나왔습니다. 특히 위험한 건 이미지를 사실상 무시하고 그럴듯한 답을 지어내는 패턴입니다 — "LLM이 이상 없다고 했으니 넘어가자"는 워크플로우에서 가장 위험한 실패 모드입니다. 응답에 최소한의 관련 키워드가 있는지 확인하는 값싼 가드레일과, 무작위 샘플에 대한 사람의 재검토를 병행하는 걸 권합니다.
====

== 이 파이프라인을 임의의 Lanelet2 맵에 써도 되는가

정직하게 답하면 — 아직입니다. 이 책은 `lanelet2_map.osm`(Autoware planning-simulator 샘플, lanelet 190개) 하나만 기준으로 모든 수치를 실측했습니다. 이 맵에서는 상당 부분 잘 작동했지만, 다음 이유로 **"이 맵과 비슷한 성격의 맵"** 정도까지만 자신 있게 말할 수 있습니다.

* *태그 관례 의존*: `turn_direction`(8장), `road_mark`의 `type`/`subtype`(9장) 같은 태그가 맵마다 있거나 없습니다. 없으면 지오메트리 휴리스틱으로 대체하는데, 태그가 있을 때만큼 신뢰도가 높지 않습니다.
* *그룹핑 스퓨리어스 매치*: 7장에서 처음 발견하고 8장 교차로 작업에서 다시 마주친 문제입니다 — 같은 문제가 두 번 나왔다는 건, 특정 맵의 특이 케이스가 아니라 그룹핑 방식 자체의 구조적 한계라는 뜻입니다. 반대로 7장에서 본 것처럼, "Vehicle 단독 vs 참가자 합집합" 같은 수정이 **이 맵에서는 아무 차이도 안 만들었다**는 것도 확인했습니다 — 어떤 보정이 유효한지조차 맵마다 직접 재봐야 한다는 뜻입니다.
* *허용치 미확정*: 6장의 jerk_weight, 8장의 회전반경 임계치 모두 "얼마면 충분한가"를 정할 회귀 테스트 허용치가 아직 없습니다. 이건 스파이크로 풀 수 있는 기술 문제가 아니라, 시뮬레이션이 감내할 정합 오차 예산에 대한 **도메인 판단**입니다.
* *규모 미검증*: 이 책에서 다룬 맵은 lanelet 190개 수준의 시뮬레이터 샘플맵입니다. 도시 단위의 실제 프로덕션 맵은 훨씬 크고, 4~6장의 반복 최적화가 그 규모에서 실행 시간이 감당될지는 검증한 적이 없습니다.
* *규제 요소 범위*: 신호등(정지선) 외의 규제 요소(속도 제한, 우선순위)는 이 책에서 다루지 않았습니다.

== 이 책이 남긴 것

이 책 전체를 관통하는 하나의 패턴이 있습니다 — **매 장마다 "이 정도면 됐다"고 생각했던 지점에서 새로운 문제가 드러났습니다.** 위치 잔차가 좋아 보였는데 이음새가 안 맞았고(4장), 이음새를 고쳤는데 중심선 정의 자체가 편향돼 있었고(5장), 편향을 없앴는데 곡률이 갑자기 튀었고(6장), 참조선을 다 맞췄는데 도로 여러 개를 묶는 그룹핑이 또 다른 문제였고(7장), 그룹핑을 개선했는데 교차로에서 같은 문제가 재발했습니다(8장).

이건 이 프로젝트가 특별히 운이 나빴다는 뜻이 아닙니다. **좌표점 나열과 파라메트릭 곡선이라는, 근본적으로 다른 두 세계관을 잇는 작업은 원래 이렇게 층층이 문제가 쌓여 있습니다.** 이 책이 준 가장 실용적인 도구는 특정 알고리즘 하나가 아니라, 그 층들을 하나씩 벗겨내는 방법 — **실측하고, 그 실측이 놓치는 게 뭔지 의심하고, 고친 뒤 다시 실측하는** 루틴 — 이었습니다. 다음에 이 파이프라인을 다른 맵에 적용할 사람에게 남기고 싶은 조언도 결국 같습니다: 숫자를 믿기 전에, 그 숫자가 무엇을 재고 있는지부터 의심하세요.
