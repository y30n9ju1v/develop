== Rust의 소유권: 선형 타입의 실전 근사

1장에서 이미 예고했듯, Rust의 소유권(ownership) 시스템은 이 책의 2~4장이 지은 것의 실전 버전입니다. 대응 관계를 정리하면 이렇습니다.

[cols="1,1,2"]
|===
| 이 책의 개념 | Rust의 대응 | 차이

| `HasType`의 `var` 규칙 (컨텍스트가 정확히 `[(x,τ)]`일 때만 유효)
| `move` 의미론 (값을 한 번 쓰면 원래 변수는 무효화)
| Rust는 컴파일 타임에 "정확히 한 번 쓰는지"가 아니라 "이동된 뒤에 다시 쓰지 않는지"를 검사합니다 — 결과적으로 같은 효과지만, 검사 방식은 데이터플로우 분석(빌림 검사기)에 가깝고, 이 책처럼 컨텍스트를 명시적으로 쪼개는 타입 규칙으로 표현되지는 않습니다.

| 2장의 `Disjoint (dom Γ1) (dom Γ2)`
| 빌림 검사기의 "가변 참조는 유일해야 한다" 규칙
| Rust는 선형성을 값 전체가 아니라 **참조**(`&`, `&mut`) 단위로도 적용합니다 — "읽기 전용 참조는 여러 개 동시에 있어도 되지만, 쓰기 참조는 유일해야 한다"는 더 섬세한 규칙(공유 vs 배타적 접근)으로, 이 책의 순수 선형(항상 정확히 한 번) 모델보다 실전적으로 유연합니다.

| 1장에서 다룬 "쓰지 않아도 되는" 값 (Unit 등)
| `Drop` 트레잇 + 스코프 종료 시 자동 호출
| 이 책의 시스템은 "정확히 한 번 써야 한다"만 다루고 "0번은 절대 안 된다"고 강제했습니다(2장의 `unit_ctx_gen`). Rust는 대신 "명시적으로 쓰지 않아도, 스코프가 끝나면 컴파일러가 자동으로 `drop`을 삽입한다"는 절충을 택합니다 — 이게 **아핀 타입(affine type)** 이라는, 선형 타입의 사촌입니다: "최대 한 번"(0번 또는 1번)까지만 허용하는 시스템입니다.
|===

마지막 줄이 중요한 절충입니다 — 이 책의 시스템은 "정확히 한 번"을 강제하는 순수 선형 타입이었지만, 실전 언어 대부분(Rust 포함)은 "최대 한 번"을 강제하는 **아핀 타입**을 씁니다. 이유는 단순합니다 — "이 값을 반드시 써야 한다"는 규칙은 프로그래머에게 지나치게 엄격합니다(에러 처리 경로에서 값을 무시하고 싶은 경우가 흔합니다). 2장의 `HasType.lam` 규칙에서 `x ∉ dom Γ`라는 조건만 유지하고 `var` 규칙의 "정확히 하나"를 "최대 하나"로 완화하면(그리고 "쓰지 않은 값은 자동으로 버려진다"는 규칙을 하나 추가하면) 이 책의 시스템도 아핀 시스템으로 바뀝니다 — 실은 이게 이 책이 다루지 않은, Rust에 더 가까운 확장입니다.

== 세션 타입 라이브러리: 타입 시스템이 아니라 타입 안의 인코딩

7장의 `session_progress`는 **타입 시스템 자체**의 정리였습니다 — `HasSType`이라는 판정을 만들고, 그 판정이 성립하면 교착이 없다는 걸 증명했습니다. 실전 언어 대부분은 세션 타입을 언어 코어에 내장하지 않습니다(예외: 세션 타입을 코어에 내장한 연구용 언어들이 있긴 하지만 널리 쓰이진 않습니다). 대신 **기존 타입 시스템 안에 세션 타입을 인코딩**하는 라이브러리 방식을 씁니다.

Rust의 `session_types` 크레이트가 대표적입니다 — 5장의 `SType`에 해당하는 `Send<T, S>`, `Recv<T, S>`, `Eps`(end) 같은 제네릭 타입을 정의하고, 채널 값 자체의 타입이 "다음에 뭘 해야 하는가"를 표현하도록 만듭니다. 이 책의 `HasSType S P` 같은 **별도의 판정**은 없습니다 — 대신 `send`/`recv` 함수의 타입 시그니처 자체가 `Chan<Env, Send<T, S>> → (T, Chan<Env, S>)` 식으로, 통신 한 번을 하면 채널의 타입이 `S`로 "다음 단계로 넘어가도록" 강제됩니다. 이건 이 책의 `HasSType.send`/`recv` 규칙이 하던 일과 본질적으로 같은 걸 Rust의 제네릭과 소유권으로 인코딩한 것입니다 — 채널 값이 선형(정확히 한 번 쓰고 다음 타입의 새 채널 값으로 "소비"됨)이라는 게 핵심이고, 이건 결국 이 책 2장의 선형성으로 되돌아갑니다.

Haskell 계열(`simple-typed-sessions` 등)도 비슷한 인코딩을 씁니다 — 다만 Haskell은 기본적으로 값을 자유롭게 복사할 수 있으므로(선형성이 코어에 없으므로), 채널이 실수로 두 번 쓰이지 않게 하려면 별도의 장치(예: 선형 타입 확장 `LinearTypes`, 또는 채널을 함수의 연속(continuation)으로만 노출해서 API 차원에서 재사용을 막는 방식)가 필요합니다 — 이 책의 `Disjoint` 조건이 타입 시스템 차원에서 자동으로 강제했던 것을, 라이브러리 설계자가 API 설계로 흉내 내는 셈입니다.

== 정리하면: 이 책이 "이론"을, 실전은 "인코딩"을 다룬다

이 장에서 본 대응 관계를 한 문장으로 요약하면 — **이 책이 지은 것은 이론의 핵심 골격**이고, Rust나 세션 타입 라이브러리는 그 골격을 **기존 언어의 타입 시스템(제네릭, 소유권, 트레잇) 안에 최대한 자연스럽게 인코딩**한 실전 버전입니다. 골격(정확히 한 번 쓴다, 통신 양쪽이 서로 듀얼이다)은 똑같지만, "정확히 한 번"이 "최대 한 번"으로 완화되거나(아핀), 별도의 타입 판정이 아니라 기존 타입 검사기가 이미 하는 일(제네릭 인스턴스화)로 재활용되는 식의 절충이 실전에서는 반복해서 나타납니다. 이 절충들을 알아보려면 먼저 절충되기 전의 이론이 정확히 뭘 보장하는지 알아야 하고, 그게 2~7장에서 한 일입니다.

== 요약

* Rust의 소유권 시스템은 이 책의 선형 타입을 "정확히 한 번"에서 "최대 한 번"(아핀)으로 완화하고, 값 단위 대신 참조(`&`/`&mut`) 단위로 더 섬세하게 적용한 실전 버전입니다.
* 세션 타입 라이브러리(Rust의 `session_types` 등)는 별도의 타입 판정을 만드는 대신, 채널 값 자체의 타입이 통신할 때마다 "다음 단계"로 바뀌도록 제네릭과 소유권을 조합해 인코딩합니다 — 이 책의 `HasSType`이 하던 일을 기존 타입 시스템 안에서 재현하는 것입니다.
* 실전 시스템들은 공통적으로 이 책이 지은 "순수한" 이론을 프로그래머 편의를 위해 절충하지만, 그 절충이 정확히 무엇을 완화하는지 이해하려면 먼저 완화되기 전의 원형(이 책의 2~7장)을 알아야 합니다.

마지막 장에서는 이 책의 이론을 이 사이트의 다른 책, `nand2npu-gpu`로 되돌려봅니다 — 그 책이 조작적 의미론으로 직접 증명했던 워프 동기화가, 세션 타입의 눈으로 보면 어떻게 보이는지 확인합니다.
