== induction은 어디서 왔을까

7~8장에서 `induction`, `simp`, ``omega``를 마치 언어에 원래 있던 명령어처럼 썼습니다. 그런데 이 책 서문에서 말했듯, Lean4는 자기 자신의 문법을 코드로 확장할 수 있게 설계되어 있습니다 — 실제로 ``induction``도 여러분이 3부에서 배울 도구로 다른 Lean4 개발자가 짠 평범한 프로그램입니다. 이 장에서는 그게 어떻게 가능한지, Lean4가 코드를 처리하는 과정부터 봅니다.

== 코드가 실행되기까지: 세 단계

여러분이 ``#eval double 21``을 누르면 Lean4 내부에서 대략 이런 일이 일어납니다.

1. **파싱**: 텍스트 ``double 21``을 문법 구조(`Syntax`)로 바꿉니다. 이 단계는 아직 ``double``이 뭔지, 타입이 맞는지 전혀 모릅니다 — 그냥 글자를 문법 트리로 조립할 뿐입니다.
2. **정교화(elaboration)**: ``Syntax``를 실제로 계산 가능한 `Expr`(내부 표현)로 바꾸면서, 동시에 타입을 확인합니다. ``double``이 실제로 정의돼 있는지, ``21``이 ``Nat``인지 확인하는 게 이 단계입니다. 1~8장에서 계속 봐온 "타입이 안 맞으면 컴파일 에러"가 나는 지점이 바로 여기입니다.
3. **평가/컴파일**: 확인이 끝난 ``Expr``을 실제로 계산하거나 실행 파일로 컴파일합니다.

이 세 단계가 각각 별도의 자료구조와 API를 갖는다는 게 중요합니다 — `Syntax`(문법 트리), `Expr`(정교화된 표현), 그리고 각 단계를 조작하는 `MacroM`, `MetaM` 같은 모나드들이 있습니다(5장에서 배운 모나드가 여기서 그대로 재활용됩니다). 3부의 나머지는 이 자료구조들을 직접 만져보는 게 전부입니다.

== macro: 파싱 단계에서 개입하기

가장 단순한 확장 지점은 macro입니다 — "이런 문법을 보면, 저런 문법으로 그대로 바꿔치기 하라"는 규칙입니다. 정교화가 시작되기 전, 순수하게 문법 수준에서 일어납니다.

[source,lean]
----
macro "twice " x:term : term => `($x + $x)

#eval twice 21  -- 42
----

규칙 왼쪽의 ``"twice " x:term``을 뜯어보면: ``"twice "``는 문자 그대로 매칭할 텍스트이고(끝의 공백은 ``twice21``처럼 다음 토큰과 그대로 붙어버리지 않도록 구분해주는 공백입니다), ``x:term``은 "그 뒤에 오는 조각을 `term`(식) 문법으로 파싱해서 ``x``라는 이름에 담아라"는 뜻입니다. 오른쪽의 `` `($x + $x) `` 안에서 ``$x``로 그 조각을 다시 꺼내 쓰는 것이죠.

``twice 21``을 파싱하다가 이 macro 규칙에 걸리면, Lean4는 정교화를 시작하기 전에 ``twice 21``을 통째로 ``21 + 21``로 바꿔치기합니다. 그래서 정교화 단계는 ``twice``라는 게 원래부터 존재하지 않았던 것처럼, ``21 + 21``만 보고 처리합니다. macro는 "새로운 표기법을 기존 문법의 조합으로 정의"하는 데 딱 맞습니다 — 새 개념을 추가하는 게 아니라, 기존 개념을 다르게 쓰는 지름길을 만드는 것입니다.

``$x``처럼 백틱(`` ` ``)과 `$`를 쓰는 문법을 "인용(quotation)"이라고 부릅니다. `` `($x + $x) ``는 "여기 실제 문법 조각을 조립해서 돌려준다"는 뜻이고, 이 인용 문법이 macro와 다음 장에서 볼 tactic 작성 전반에서 계속 나옵니다.

== elab: 정교화 단계에서 개입하기

macro로는 부족한 경우가 있습니다 — 단순 치환이 아니라 "지금 어떤 타입을 기대하고 있는지"처럼 정교화 중에만 알 수 있는 정보가 필요한 경우입니다. 이럴 땐 ``elab``으로 정교화 단계에 직접 개입합니다.

준비물이 하나 있습니다 — ``elab``은 Lean4 컴파일러 자신의 API를 쓰기 때문에, 파일 맨 위에 `import Lean` 한 줄이 필요합니다(위의 ``macro``까지는 없어도 됩니다). 이 한 줄을 빼먹으면 `Unknown identifier` 에러가 쏟아지니 기억해두세요.

[source,lean]
----
import Lean

elab "typeOf% " e:term : term => do
  let e' ← Lean.Elab.Term.elabTermAndSynthesize e none
  let t ← Lean.Meta.inferType e'
  Lean.logInfo m!"{t}"
  return e'

#eval typeOf% (1 + 2)  -- 정보 메시지: Nat
----

``elabTermAndSynthesize``가 받은 문법 조각(`Syntax`)을 실제 ``Expr``로 정교화하고, ``inferType``이 그 타입을 알아냅니다. ``elab``은 macro와 달리 ``MetaM``이라는 모나드 안에서 동작하며, 이렇게 지금까지 정교화된 표현의 타입을 물어보거나 새로운 표현을 만들어내는 등 macro보다 훨씬 많은 걸 할 수 있습니다. 대신 그만큼 더 저수준입니다.

== 이 장이 왜 중요한가

여러분이 7~8장에서 아무 의심 없이 썼던 `by induction n with | zero => ... | succ k ih => ...` 문법도 이 `Syntax` → 처리 → `Expr` 파이프라인의 산물입니다. ``induction``은 특별 취급되는 언어 내장 키워드가 아니라, 목표의 ``Expr``을 들여다보고 "이 타입이 어떤 방식들로 만들어질 수 있는지"(3장에서 본 `inductive` 정의)를 스스로 찾아내서 하위 목표를 만들어내는 프로그램입니다.

다음 장에서는 이 재료들을 가지고 아주 작은 나만의 tactic을 직접 만들어보면서, "전술을 짠다"는 게 실제로 어떤 느낌인지 확인합니다.

== 직접 해보기

* ``twice``를 참고해 `thrice x`(x를 세 번 더하기) macro를 만들어보세요. ``#eval thrice 5``는 15가 나와야 합니다.
* ``#eval twice (twice 10)``은 몇일까요? macro가 펼쳐지는 과정을 종이에 먼저 적어본 다음, 실행해서 확인해보세요.
* ``typeOf%``에 `"hello"`, `(fun n : Nat => n + 1)` 등 여러 식을 넣어 어떤 타입이 찍히는지 확인해보세요.

.해답 보기
[%collapsible]
====
[source,lean]
----
macro "thrice " x:term : term => `($x + $x + $x)

#eval thrice 5  -- 15

-- twice (twice 10)
--   → twice 10 + twice 10       (바깥 twice가 먼저 펼쳐진다)
--   → (10 + 10) + (10 + 10)
--   → 40

-- typeOf% "hello"                → 정보 메시지: String
-- typeOf% (fun n : Nat => n + 1) → 정보 메시지: Nat → Nat
----
====

== 요약

* 코드는 파싱(텍스트 → `Syntax`) → 정교화(`Syntax` → `Expr`, 타입 확인) → 평가/컴파일의 세 단계를 거친다.
* ``macro``는 정교화가 시작되기 전, 순수 문법 수준에서 "이 문법을 저 문법으로 바꿔치기"한다.
* ``elab``은 정교화 단계에 직접 개입해, 다른 표현의 타입을 물어보거나(`inferType`) 더 많은 정보를 활용할 수 있다 — 대신 더 저수준이다.
* `induction`, `simp` 같은 전술도 특별 취급되는 내장 키워드가 아니라 이 파이프라인 위에서 돌아가는 평범한 Lean4 프로그램이다.
