== 지금까지의 한계: transition은 항상 결정적이었다

4장부터 써온 `transition : State → Event → State`는 **함수**입니다 — 같은 상태에서 같은 이벤트를 받으면 항상 같은 다음 상태로 갑니다. 그런데 여러 층에서 동시에 호출이 왔을 때 "어느 요청부터 처리할지"는 배차 알고리즘의 정책에 달려있지, `transition` 하나로 결정되는 문제가 아닙니다. 이런 **"다음 상태가 여러 개 있을 수 있는"** 상황을 다루려면 함수 대신 **관계**가 필요합니다.

[source,lean]
----
inductive DispatchState where
  | idle
  | serving (current target : Nat) (rest : List Nat)  -- 지금 향하는 목표, 나머지 대기 큐
deriving DecidableEq, Repr

def successors (pending : List Nat) : List DispatchState :=
  pending.flatMap (fun target =>
    [.serving 0 target (pending.filter (· ≠ target))])

#eval successors [3, 7]
-- [serving 0 3 [7], serving 0 7 [3]]
----

`successors : List Nat → List DispatchState`가 "지금 대기 중인 요청들 중 하나를 골라 다음으로 처리한다면, 그 결과가 될 수 있는 상태들의 목록"을 반환합니다. `[3, 7]`(3층과 7층에서 동시에 호출이 옴)이 대기 중이면, "3층부터 간다"와 "7층부터 간다" 둘 다 가능한 다음 상태입니다 — 어느 쪽으로 갈지는 이 함수만으로는 결정되지 않습니다. 이런 시스템을 다루는 시제논리를 **CTL(Computation Tree Logic, 계산 트리 논리)**이라고 부릅니다 — 9장의 LTL이 "하나로 정해진 실행"을 다뤘다면, CTL은 "여러 갈래로 뻗어나가는 트리"를 다룹니다.

== EX와 AX: 한 스텝만큼의 두 가지 "다음"

[source,lean]
----
def EX (P : DispatchState → Prop) (pending : List Nat) : Prop :=
  ∃ s ∈ successors pending, P s

def AX (P : DispatchState → Prop) (pending : List Nat) : Prop :=
  ∀ s ∈ successors pending, P s

example : EX (fun s => s = .serving 0 3 [7]) [3, 7] :=
  ⟨.serving 0 3 [7], by decide, rfl⟩

example : ¬ AX (fun s => s = .serving 0 3 [7]) [3, 7] := by
  intro h
  have := h (.serving 0 7 [3]) (by decide)
  exact absurd this (by decide)
----

`EX`("Exists neXt")는 "다음 상태 중에 `P`를 만족하는 게 **하나라도** 있다"는 뜻이고, `AX`("for All neXt")는 "다음 상태 **전부**가 `P`를 만족한다"는 뜻입니다. `[3, 7]`이 대기 중일 때 `EX (· = serving 0 3 [7])`는 참입니다("3층부터 간다"가 가능한 배차 중 하나니까요) — 하지만 `AX (· = serving 0 3 [7])`는 거짓입니다("7층부터 간다"도 가능한 배차인데 그건 3층부터가 아니니까요). 이 둘의 차이가 CTL의 핵심입니다 — **"이럴 수도 있다"(EX)와 "무조건 이렇다"(AX)는 완전히 다른 주장**입니다.

== EF: 어떤 배차 순서를 고르면 결국 도달할 수 있다

9장의 `Eventually`는 하나로 정해진 실행 위에서 "언젠가"를 물었습니다. 여기서는 실행이 여러 갈래이므로, "언젠가 도달한다"도 "**어떤 배차 순서를 고르면** 결국 도달할 수 있는가"로 다시 정의해야 합니다.

[source,lean]
----
inductive Reachable : List Nat → DispatchState → Prop where
  | direct (pending : List Nat) (s : DispatchState) (h : s ∈ successors pending) :
      Reachable pending s

def EF (P : DispatchState → Prop) (pending : List Nat) : Prop :=
  ∃ s, Reachable pending s ∧ P s

example : EF (fun s => s = .serving 0 3 [7]) [3, 7] := by
  refine ⟨.serving 0 3 [7], ?_, rfl⟩
  exact Reachable.direct [3, 7] (.serving 0 3 [7]) (by decide)
----

`Reachable pending s`는 "`pending`이라는 대기 목록에서, 적절한 배차 선택을 하면 `s`에 도달할 수 있다"는 뜻입니다. `EF (· = serving 0 3 [7]) [3, 7]`을 증명한다는 건 **"3층과 7층이 동시에 대기 중일 때, 3층부터 처리하는 배차 결과가 실제로 가능하다"**는 뜻이고, 그 배차 선택을 구체적으로 제시해서 증명했습니다.

== AF는 왜 이 장에서 증명하지 않는가

`EF`의 짝인 `AF`("for All paths, eventually")는 "**어떤 배차 순서를 골라도** 결국 `P`에 도달한다"는 훨씬 강한 주장입니다. 이 예제에서 `AF (fun s => s = .serving 0 3 [7]) [3, 7]`이 참일까요 — 아닙니다. "7층부터 간다"를 고르면 `serving 0 3 [7]`이라는 상태에는 **절대 도달하지 않습니다**(대신 `serving 0 7 [3]`으로 갑니다). `EF`는 방금처럼 배차 선택 하나를 손으로 제시하는 것으로 증명할 수 있지만, `AF`는 "가능한 모든 배차 선택 각각에 대해" 증명해야 하므로 이 방식만으로는 다룰 수 없습니다 — 8~9장에서 본 생동성의 어려움이 여기서 "가능한 배차가 여러 개 있고, 그중 하나라도 나쁘면 `AF`가 거짓"이라는 형태로 다시 나타난 것입니다. 실전 엘리베이터라면 "배차 알고리즘이 어떤 선택을 하든 모든 요청이 결국 처리된다"(`AF`에 가까운 주장) 같은 성질이 실제로 중요하지만, 이건 이 책의 범위를 넘어서는 본격적인 모델체킹 이론이라 맺음말에서 그 방향만 안내합니다.

== EF와 Eventually의 관계

`EF`가 `Reachable`(관계)을 쓰고 9장의 `Eventually`가 `trace`(함수)를 썼다는 차이가 있지만, 근본 아이디어는 같습니다 — **"어떤 조건을 만족하는 시점/상태가 존재한다"는 존재 양화**입니다. 시스템이 결정적(transition이 함수)이라면 "경로"가 하나뿐이라 `EF`와 `Eventually`가 사실상 같은 것을 묻게 되고, 비결정적(successors가 여러 개)이라면 `EF`가 "그 여러 경로 중 최소한 하나는 원하는 배차에 도달한다"는, LTL만으로는 표현 못 하는 질문을 추가로 물을 수 있게 해줍니다.

== 요약

* 여러 요청이 동시에 대기 중일 때 "다음에 무엇을 처리할지"는 `transition` 함수 대신 `successors : List Nat → List DispatchState` 같은 관계로 표현합니다.
* `EX`("다음 중 하나라도")와 `AX`("다음 전부가")는 서로 다른 주장입니다 — 비결정적 배차에서는 이 둘이 갈립니다.
* `EF`("어떤 배차를 고르면 결국")는 구체적인 선택 하나를 제시하는 것으로 증명할 수 있지만, `AF`("어떤 배차를 골라도 결국")는 모든 가능한 배차에 대한 주장이라 이 방식으로는 다룰 수 없습니다 — 본격적인 모델체킹이 필요한 지점입니다.

3부의 마지막 장에서는 지금까지 배운 모든 도구(sum/product, transition, 합성, LTL, CTL)를 동원해 엘리베이터 프로젝트를 하나의 완결된 시스템으로 조립합니다.
