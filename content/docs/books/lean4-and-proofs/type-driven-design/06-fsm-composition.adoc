== 두 상태 기계를 합치는 두 가지 방법

지금까지 엘리베이터 하나만 다뤘습니다. 이제 이걸 두 가지 방향으로 넓혀야 합니다 — "서로 다른 건물에 있는 독립된 두 엘리베이터를 **동시에, 서로 신경 쓰지 않고** 시뮬레이션하고 싶다"거나, "한 엘리베이터가 **평상시 모드 아니면 점검 모드**, 둘 중 하나로만 동작한다"거나. 낯익은 질문입니다 — 1장에서 본 "항상 같이 있어야 하는 것"(product)과 "동시에 있을 수 없는 것 중 하나"(sum)가 상태 기계에도 그대로 적용됩니다.

== product 합성: 두 엘리베이터를 동시에, 독립적으로

[source,lean]
----
def parallelStep (a b : ElevatorState) (e : ElevatorEvent) : ElevatorState × ElevatorState :=
  (a.transition e, b.transition e)

#eval parallelStep ⟨0, .idle⟩ ⟨5, .idle⟩ (.callFloor 2)
example : parallelStep ⟨0, .movingTo 3⟩ ⟨5, .movingTo 1⟩ .tick
    = (⟨1, .movingTo 3⟩, ⟨4, .movingTo 1⟩) := by native_decide
----

`ElevatorState × ElevatorState`가 "두 엘리베이터가 항상 함께 존재한다"는 product입니다. `parallelStep`은 이벤트 하나가 들어올 때마다 **두 엘리베이터를 각각 한 스텝씩** 진행시킵니다 — 같은 `tick`을 받아도 `a`는 3층을 향해, `b`는 1층을 향해 각자의 목적지대로 움직입니다. 이게 product 합성의 핵심입니다 — **두 기계가 서로의 상태를 전혀 참조하지 않고, 나란히 독립적으로 진행**합니다. 실전에서는 서로 다른 건물의 엘리베이터, 혹은 완전히 분리된 두 시스템을 한 시뮬레이션 안에서 같이 돌리고 싶을 때 이 패턴을 씁니다.

== coproduct 합성: 지금 어느 모드인가

한 엘리베이터가 **평상시엔 정상적으로 호출에 반응하지만, 점검 모드에 들어가면 어떤 호출도 무시**해야 한다면 이야기가 다릅니다.

[source,lean]
----
inductive Mode where
  | normal (s : ElevatorState)
  | maintenance (s : ElevatorState)
deriving DecidableEq, Repr

inductive ModeEvent where
  | elevEvent (e : ElevatorEvent)
  | enterMaintenance
  | exitMaintenance

def Mode.step : Mode → ModeEvent → Mode
  | .normal s, .elevEvent e => .normal (s.transition e)
  | .normal s, .enterMaintenance => .maintenance s
  | .normal s, .exitMaintenance => .normal s
  | .maintenance s, .exitMaintenance => .normal s
  | .maintenance s, _ => .maintenance s  -- 점검 모드에선 어떤 elevEvent도 무시
----

`Mode`가 `ElevatorState`를 두 벌 들고 있는 product가 아니라 **"지금 정상인지 점검 중인지"**를 표현하는 sum(coproduct) 타입입니다 — `normal s`이면 `s`가 실제로 동작 중인 엘리베이터 상태이고, `maintenance s`이면 그 `s`가 **그대로 얼어붙어** 있습니다. `Mode.step`의 마지막 줄(`.maintenance s, _ => .maintenance s`)이 핵심입니다 — 점검 모드에서는 `exitMaintenance` 말고 어떤 이벤트가 와도(심지어 `elevEvent (.callFloor 3)`처럼 호출이 와도) 상태가 그대로입니다.

[source,lean]
----
#eval Mode.normal ⟨0, .idle⟩ |>.step (.elevEvent (.callFloor 3))
-- Mode.normal { floor := 0, phase := movingTo 3 }

#eval Mode.normal ⟨0, .idle⟩ |>.step .enterMaintenance
    |>.step (.elevEvent (.callFloor 3))
-- Mode.maintenance { floor := 0, phase := idle } -- 호출이 무시됨

example : ((Mode.normal ⟨0, .idle⟩).step .enterMaintenance).step (.elevEvent (.callFloor 3))
    = .maintenance ⟨0, .idle⟩ := by native_decide
----

평상시 모드에서 3층 호출을 받으면 정상적으로 움직이기 시작하지만, 점검 모드로 들어간 뒤에 같은 호출을 보내면 **완전히 무시되고 상태가 그대로**입니다 — `Mode`라는 하나의 타입이 "지금 이 엘리베이터가 어느 모드로 동작하고 있는지"까지 전부 표현합니다.

== 어느 쪽을 골라야 하는가

1장의 질문이 여기서도 그대로 적용됩니다 — **"두 기계가 동시에 존재해야 하는가, 아니면 항상 둘 중 하나로만 존재하는가?"** 동시에 존재해야 한다면 product(`A × B`)로, 정확히 하나로만 존재한다면 sum(`A ⊕ B`, Lean에서는 이 장의 `Mode`처럼 `inductive`로)으로 합칩니다. 이 질문을 건너뛰고 아무렇게나 합치면, 1장에서 본 "표현 가능하지만 실제로는 무의미한 조합"이 상태 기계 수준에서 다시 나타납니다 — 예를 들어 "점검 모드 여부"를 `Bool`로 따로 두고 `ElevatorState`와 독립된 product로 관리했다면, 그 `Bool`을 깜빡하고 안 확인하는 실수 하나로 점검 중에도 엘리베이터가 움직여버릴 수 있습니다. `Mode`처럼 sum으로 묶으면 "점검 중인데 움직이는 로직"을 아예 별도로 짤 방법이 없습니다.

== 직접 해보기

* 3장에서 만든 것과 비슷하게, `Mode`에 "화재 시 관제 모드"(`fireOverride`, 무조건 1층으로 이동한 뒤 문을 열고 얼어붙는)를 세 번째 생성자로 추가해보세요.
* 평상시 모드에서 화재 이벤트를 받으면 `fireOverride`로 전환되고, 그 안에서는 어떤 일반 호출도 무시된다는 걸 확인해보세요.

.해답 보기
[%collapsible]
====
[source,lean]
----
inductive Mode2 where
  | normal2 (s : ElevatorState)
  | fireOverride (s : ElevatorState)
deriving DecidableEq, Repr

inductive Mode2Event where
  | elevEvent2 (e : ElevatorEvent)
  | fireAlarm

def Mode2.step : Mode2 → Mode2Event → Mode2
  | .normal2 s, .elevEvent2 e => .normal2 (s.transition e)
  | .normal2 s, .fireAlarm => .fireOverride s
  | .fireOverride s, _ => .fireOverride s  -- 화재 모드에서는 무엇을 받아도 얼어붙음

example : (Mode2.normal2 ⟨3, .idle⟩).step .fireAlarm = .fireOverride ⟨3, .idle⟩ := by native_decide
example : ((Mode2.normal2 ⟨3, .idle⟩).step .fireAlarm).step (.elevEvent2 (.callFloor 7))
    = .fireOverride ⟨3, .idle⟩ := by native_decide
----
====

== 요약

* 두 상태 기계가 항상 함께, 서로 독립적으로 진행돼야 한다면 product(`A × B`)로 합성합니다 — 각 기계는 상대방을 신경 쓰지 않고 자기 규칙대로 전이합니다.
* 정확히 하나만 활성 상태여야 한다면 coproduct(sum, `inductive`)로 합성합니다 — "지금 어느 모드인가"까지 상태 타입 하나가 표현합니다.
* 이 선택은 1장의 "product인가 sum인가" 질문과 완전히 같은 질문입니다 — 잘못 고르면 실제로는 불가능한 조합(점검 중인데 움직이는 등)이 다시 표현 가능해집니다.

다음 장에서는 지금까지 배운 걸 전부 동원해, 엘리베이터에 "과부하 안전장치"를 추가하는 사례 연구를 합니다.
