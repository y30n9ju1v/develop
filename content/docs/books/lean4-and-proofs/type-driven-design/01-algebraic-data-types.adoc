이 책은 처음부터 끝까지 **엘리베이터 하나**를 함께 설계·구현·증명합니다. 매 장이 이전 장에서 만든 것 위에 새 도구를 얹는 식으로 진행되니, 지금 만드는 타입이 나중에 그대로 재사용된다는 걸 염두에 두고 읽어주세요.

== 나쁜 설계: 불가능한 조합이 표현되는 상태

[source,lean]
----
structure BadElevator where
  isMoving : Bool
  doorsOpen : Bool

def dangerous : BadElevator := { isMoving := true, doorsOpen := true }
----

`BadElevator`는 필드 두 개짜리 평범한 구조체입니다. 그런데 `isMoving := true, doorsOpen := true`(**문이 열린 채로 움직이고 있다**는 조합)처럼 **실제로는 절대 일어나서는 안 되는 상태도 타입 시스템이 아무 제지 없이 허용**합니다. 컴파일러는 이 조합이 위험하다는 걸 모릅니다 — `isMoving`과 `doorsOpen`이 서로 독립된 두 개의 `Bool`이라, 둘을 곱한 4가지 조합이 전부 "합법적인 타입"이기 때문입니다.

== product: "항상 같이 있어야 하는 것"

`BadElevator` 같은 구조체(`structure`)가 바로 **product 타입**입니다. 필드 두 개를 곱집합(cartesian product)처럼 조합해서, 가능한 값의 개수가 각 필드가 가진 값의 개수를 곱한 만큼 나옵니다 — `Bool × Bool`은 정확히 2 × 2 = 4가지 값을 가집니다. product는 "이 필드들은 항상 함께 존재해야 한다"는 뜻을 표현하는 데는 적합하지만, "이 필드들 중 일부 조합은 의미가 없다"는 제약은 표현하지 못합니다.

== sum: "동시에 있을 수 없는 것"

[source,lean]
----
inductive ElevatorPhase where
  | idle
  | movingTo (dest : Nat)
  | doorsOpen
deriving DecidableEq, Repr
----

`inductive`로 만든 `ElevatorPhase`가 **sum 타입**입니다. `idle`, `movingTo`, `doorsOpen` 세 생성자 중 **정확히 하나**만 골라 값을 만들 수 있습니다 — "움직이는 중이면서 동시에 문이 열려있다"는 값은 애초에 만들 방법이 없습니다. `movingTo dest`라는 생성자 자체가 "지금 움직이고 있다면, 그 목적지가 무엇인지"라는 정보만 들고 있을 뿐, "문이 열려있는가"라는 질문 자체가 이 값에는 성립하지 않습니다. `BadElevator`가 실패한 지점이 정확히 이것입니다 — sum이어야 할 관계("움직이는 중 / 멈춰서 문이 열린 중 / 그냥 대기 중, 이 셋 중 하나")를 독립된 product(`Bool × Bool`)로 잘못 표현한 것입니다.

== 다시 조합하기: product 안에 sum을 담기

[source,lean]
----
structure ElevatorState where
  floor : Nat
  phase : ElevatorPhase
deriving DecidableEq, Repr

example : (ElevatorState.mk 3 .doorsOpen).phase = ElevatorPhase.doorsOpen := rfl
----

`ElevatorState`는 다시 product입니다 — "지금 몇 층에 있는가"(`floor`)와 "지금 무슨 국면인가"(`phase`)는 항상 함께 있어야 하는 정보이니까요. 다만 이번엔 그 안에 담긴 `phase` 필드 자체가 sum 타입(`ElevatorPhase`)이라, "엘리베이터에는 항상 층수와 국면이 있다"는 사실과 "그 국면은 세 경우 중 하나이지 절대 두 개가 동시에 성립하지 않는다"는 사실을 둘 다 타입만으로 표현합니다. 대수적 데이터 타입(ADT)이라는 이름 자체가 이 두 연산 — product(곱)와 sum(합) — 의 조합으로 타입을 짓는다는 뜻입니다. `ElevatorState`가 이 책 전체에서 계속 확장해나갈 핵심 타입입니다.

== 설계에 적용하기: 타입으로 불가능한 상태를 지우기

핵심 질문은 항상 이것입니다 — **"이 값들의 조합 중 일부가 실제로는 의미가 없는가?"** 의미가 없다면, 그 무의미한 조합이 애초에 타입으로 표현되지 않도록 sum으로 다시 설계합니다. 이렇게 하면 "이 값이 유효한지 런타임에 검사하는 코드"가 아예 필요 없어집니다 — 컴파일러가 무효한 값을 만드는 것 자체를 막아주기 때문입니다. `ElevatorPhase`를 이렇게 설계해둔 덕분에, "문이 열린 채로 움직인다"는 사고 상황은 4장에서 실제 동작을 구현할 때 **아예 코드로 표현할 방법이 없습니다** — 나중에 안전성을 "증명"하기 훨씬 전에, 타입 설계만으로 이미 절반은 막아둔 셈입니다.

== 직접 해보기

* "출입문 잠금 표시등"을 나쁘게 설계한 버전(`isMoving : Bool`, `destination : Option Nat`처럼 서로 독립된 필드 — `isMoving = false`인데 `destination`이 `some`인 모순 조합이 가능)을 만들고, 어떤 조합이 의미가 없는지 찾아보세요.
* 그 상태를 sum 타입으로 다시 설계해, 의미 없는 조합이 표현조차 안 된다는 걸 확인해보세요(힌트: 이미 위에서 `ElevatorPhase`로 정확히 이 문제를 풀었습니다).

.해답 보기
[%collapsible]
====
[source,lean]
----
-- 나쁜 설계: isMoving=false인데 destination이 some인 모순 조합이 가능
structure BadElevator2 where
  isMoving : Bool
  destination : Option Nat

def confused : BadElevator2 := { isMoving := false, destination := some 5 }
-- "안 움직이는데 목적지가 5층으로 남아있다"는 의미 없는 상태

-- 좋은 설계: ElevatorPhase가 이미 이 문제를 풀어둠
-- idle(목적지 없음) / movingTo dest(목적지가 정확히 하나) 중 하나만 표현 가능
example : ElevatorPhase.idle ≠ ElevatorPhase.movingTo 5 := by decide
----
====

== 요약

* `structure`(product)는 "항상 같이 있어야 하는 것"을, `inductive`(sum)는 "동시에 있을 수 없는 것 중 하나"를 표현합니다.
* 서로 독립된 여러 `Bool`/필드로 상태를 표현하면, 실제로는 불가능한 조합(예: 문이 열린 채로 움직이는 엘리베이터)까지 타입이 허용해버립니다.
* sum과 product를 조합(product 안에 sum을 담는 식)하면, "불가능한 상태를 표현조차 못 하게" 만들 수 있습니다 — 런타임 검사 없이 컴파일 타임에 무효한 값을 차단합니다.
* 이 장에서 만든 `ElevatorPhase`와 `ElevatorState`가 이 책 전체를 관통하는 엘리베이터 프로젝트의 뼈대입니다.

다음 장에서는 이렇게 다듬은 타입들을 다루는 함수를 어떻게 "상태를 직접 조작"하는 대신 "작은 함수들의 합성"으로 짤 것인지 다룹니다.
