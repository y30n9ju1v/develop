== 12장에서 미뤄둔 것: "번갈아 끼어든다"는 모델

12장에서 "이 책의 모든 엘리베이터는 한 번에 이벤트 하나만 처리했다"며 동시성을 범위 밖으로 뒀습니다. 여기서 조금 더 나가봅니다 — 완전한 동시성 이론 대신, **"두 대의 엘리베이터가 각자 진행하지만, 어느 쪽이 다음에 한 스텝 나아갈지는 스케줄러가 임의로 정한다"**는 인터리빙(interleaving) 모델 하나만 다룹니다. 이것만으로도 병렬 프로그래밍에서 가장 흔한 버그(레이스 컨디션)를 정확히 재현하고, 그걸 막는 설계까지 증명할 수 있습니다.

== 문제 상황: 같은 층 호출을 두 카가 동시에 배정받으려 한다

건물에 엘리베이터가 두 대 있고, 어느 층에서 호출이 오면 **두 카 중 하나에만** 배정돼야 합니다(둘 다 동시에 같은 손님을 태우러 가면 낭비니까요). 각 카는 "대기 중(`idle`) → 이 호출을 배정받고 싶음(`wantsClaim`) → 배정받아 서비스 중(`claimed`)"이라는 간단한 흐름을 따른다고 합시다.

[source,lean]
----
inductive ClaimState where
  | idle | wantsClaim | claimed
deriving DecidableEq, Repr

inductive GlobalEvent where
  | moveCar1 | moveCar2   -- "다음엔 1호기가(또는 2호기가) 한 스텝 나아간다"는 스케줄러의 선택
deriving DecidableEq, Repr
----

`GlobalEvent`가 이 장의 핵심 장치입니다 — 6장의 product 합성에서는 이벤트 하나가 들어오면 **두 기계가 동시에** 한 스텝씩 나아갔는데, 여기서는 `moveCar1`/`moveCar2` 중 **하나만** 골라 그 카만 나아갑니다. 이벤트 목록이 `[moveCar1, moveCar2, moveCar1, ...]`처럼 어떤 순서로도 섞일 수 있다는 게 "임의 순서로 번갈아 끼어든다"는 걸 표현합니다.

== 순진한 버전: 조율 없이 각자 판단

[source,lean]
----
def ClaimState.localStep : ClaimState → ClaimState
  | .idle => .wantsClaim
  | .wantsClaim => .claimed
  | .claimed => .idle

def unsafeStep : (ClaimState × ClaimState) → GlobalEvent → (ClaimState × ClaimState)
  | (a, b), .moveCar1 => (a.localStep, b)
  | (a, b), .moveCar2 => (a, b.localStep)

def unsafeTrace (schedule : List GlobalEvent) : ClaimState × ClaimState :=
  schedule.foldl unsafeStep (.idle, .idle)

#eval unsafeTrace [.moveCar1, .moveCar1, .moveCar2, .moveCar2]
example : unsafeTrace [.moveCar1, .moveCar1, .moveCar2, .moveCar2] = (.claimed, .claimed) := by
  native_decide
----

각 카가 서로를 전혀 신경 쓰지 않고 자기 판단대로만 진행합니다. `[moveCar1, moveCar1, moveCar2, moveCar2]`라는 스케줄(1호기가 `idle → wantsClaim → claimed`까지 먼저 두 번 나아간 뒤, 2호기도 같은 식으로 두 번 나아가는 순서)을 실제로 실행하면 **둘 다 동시에 `claimed`**가 됩니다 — 같은 호출을 두 카가 동시에 배정받는 사고입니다. 11장의 "정상 모드/점검 모드"에서 상태가 서로 엇갈리지 않도록 조율했던 것과 정확히 같은 종류의 실패가, 이번엔 "락 없이 같은 자원(호출)에 접근"하는 형태로 재현됐습니다.

== 안전한 버전: "호출이 비어있는가"를 공유 상태로

11장에서 배운 교훈을 다시 적용합니다 — 두 부분이 서로 조율돼야 한다면, 독립된 product 대신 **공유 정보를 상태 자체에 포함**시킵니다.

[source,lean]
----
structure ClaimSystem where
  car1 : ClaimState
  car2 : ClaimState
  callFree : Bool
deriving DecidableEq, Repr

def claimStep (c : ClaimState) (callFree : Bool) : ClaimState × Bool :=
  match c, callFree with
  | .idle, cf => (.wantsClaim, cf)
  | .wantsClaim, true => (.claimed, false)     -- 비어있으면 배정받음
  | .wantsClaim, false => (.wantsClaim, false)  -- 이미 배정됐으면 대기
  | .claimed, _ => (.idle, true)                -- 서비스 완료, 호출 반납

def safeStep : ClaimSystem → GlobalEvent → ClaimSystem
  | ⟨a, b, cf⟩, .moveCar1 =>
      let (a', cf') := claimStep a cf
      ⟨a', b, cf'⟩
  | ⟨a, b, cf⟩, .moveCar2 =>
      let (b', cf') := claimStep b cf
      ⟨a, b', cf'⟩

def safeTrace (schedule : List GlobalEvent) : ClaimSystem :=
  schedule.foldl safeStep ⟨.idle, .idle, true⟩

#eval safeTrace [.moveCar1, .moveCar1, .moveCar2, .moveCar2]
-- { car1 := claimed, car2 := wantsClaim, callFree := false }
----

`callFree`가 두 카 모두 접근할 수 있는 **공유 상태**입니다 — `claimStep`이 `wantsClaim`에서 `claimed`로 가려 할 때 `callFree`를 확인하고, 이미 배정됐으면 그 자리에 멈춥니다(`wantsClaim`에 그대로 남음). 방금 전과 똑같은 스케줄을 이 버전으로 돌리면, 2호기는 `wantsClaim`에서 멈추고 `claimed`에 못 들어갑니다 — 1호기가 아직 그 호출을 쥐고 있기 때문입니다.

== 안전성 증명: 8~9장의 패턴을 그대로 재사용

이제 "**어떤 스케줄을 고르든** 절대 두 카가 동시에 같은 호출을 배정받을 수 없다"는 걸 증명합니다. 이 증명은 8장(엘리베이터의 층수 범위 불변식)과 완전히 같은 구조입니다.

[source,lean]
----
def Invariant (s : ClaimSystem) : Prop :=
  ¬ (s.car1 = .claimed ∧ s.car2 = .claimed) ∧
  (s.callFree = false ↔ (s.car1 = .claimed ∨ s.car2 = .claimed))

theorem invariant_init : Invariant ⟨.idle, .idle, true⟩ := by
  unfold Invariant; simp

theorem invariant_preserved (s : ClaimSystem) (e : GlobalEvent) (h : Invariant s) :
    Invariant (safeStep s e) := by
  obtain ⟨hne, hiff⟩ := h
  cases s with
  | mk a b cf =>
    cases e <;> cases a <;> cases b <;> cases cf <;>
      simp_all [safeStep, claimStep, Invariant]

theorem invariant_holds_after_schedule (schedule : List GlobalEvent) :
    Invariant (safeTrace schedule) := by
  suffices h : ∀ s, Invariant s → Invariant (schedule.foldl safeStep s) by
    exact h ⟨.idle, .idle, true⟩ invariant_init
  intro s hs
  induction schedule generalizing s with
  | nil => exact hs
  | cons e es ih => exact ih (safeStep s e) (invariant_preserved s e hs)
----

`Invariant`는 "두 카가 동시에 `claimed`가 아니다"에 더해 "`callFree`가 실제로 배정 상태와 일치한다"(누가 호출을 배정받았으면 `callFree`는 거짓이어야 하고, 그 역도 성립)는 조건을 함께 묶었습니다 — 두 번째 조건이 없으면 `callFree`가 거짓말을 하는 경우까지 허용돼서 첫 번째 조건 자체를 귀납적으로 지킬 수 없습니다. `cases e <;> cases a <;> cases b <;> cases cf`가 가능한 모든 (이벤트, 상태) 조합을 나열하고, 그 각각에서 불변식이 유지된다는 걸 확인합니다 — `ClaimState`가 세 값, `Bool`이 두 값이니 유한한 경우의 수라 전부 확인 가능합니다. `invariant_holds_after_schedule`이 8~9장에서 본 것과 똑같은 귀납 구조(한 스텝 보존 + 목록 길이에 대한 귀납법)로, **임의 길이의 스케줄**에 대해 이 성질을 증명합니다.

[source,lean]
----
example : ¬ ((safeTrace [.moveCar1, .moveCar1, .moveCar2, .moveCar2]).car1 = .claimed ∧
    (safeTrace [.moveCar1, .moveCar1, .moveCar2, .moveCar2]).car2 = .claimed) :=
  (invariant_holds_after_schedule _).1
----

이 성질은 방금 검사한 그 스케줄만이 아니라 **그 어떤 인터리빙에도** 성립합니다 — 스케줄러가 어떤 순서로 두 카를 끼워넣든, `callFree`라는 락이 그 순서와 무관하게 "같은 호출을 두 번 배정하지 않는다"는 걸 지켜줍니다.

== 이 장이 실전에 주는 것

`callFree : Bool`이라는 필드 하나와 "상태를 확인하고 조건부로만 전진한다"는 규칙이, 실제 뮤텍스(mutex)·세마포어가 하는 일의 핵심입니다. 이 장이 보여주려 한 건 새로운 동시성 이론이 아니라, **지금까지 배운 도구(sum/product 설계, transition 함수, 불변식 귀납 증명)가 인터리빙이라는 새 상황에도 그대로 적용된다**는 것입니다 — "두 부분이 조율돼야 하면 공유 상태로 묶는다"(6장·11장)와 "한 스텝 보존을 증명하고 귀납법으로 확장한다"(8~9장)는 이 책 전체에서 반복된 패턴이, 병렬 프로그래밍의 가장 기본적인 안전성 문제에도 다시 등장했습니다.

물론 진짜 동시성(진짜로 동시에 실행되는 다중 코어, 메모리 가시성 문제, 락-프리 알고리즘)은 이 인터리빙 모델보다 훨씬 복잡합니다 — 이 장은 그 세계로 가는 첫걸음일 뿐, 12장에서 언급한 모델체킹 도구(TLA+ 등)가 정확히 그 복잡성을 다루기 위해 만들어진 것입니다.

== 직접 해보기

* 이 장의 `unsafeStep`(락 없는 버전)에 대해, "두 카가 동시에 같은 호출을 배정받을 수 있는 스케줄이 존재한다"(방금 확인한 그 반례)를 10장의 `EF`로 표현할 수 있는지 생각해보세요 — `successors`를 어떻게 정의해야 할까요?
* `safeStep`에 엘리베이터를 하나 더 추가해(`car3 : ClaimState`, `moveCar3` 이벤트) 세 카가 하나의 호출을 공유하도록 확장하고, `Invariant`도 세 카 버전으로 고쳐 여전히 "동시에 둘 이상이 배정받지 않는다"는 게 지켜지는지 확인해보세요.

== 요약

* "이벤트가 임의 순서로 번갈아 끼어든다"는 인터리빙 모델(`GlobalEvent = moveCar1 | moveCar2`)만으로도 레이스 컨디션을 정확히 재현할 수 있습니다 — 조율 없는 설계는 실제로 두 카가 동시에 같은 호출을 배정받는 스케줄이 존재합니다.
* 배정 여부를 공유 상태(`callFree`)로 표현하고 각 카의 전이가 그 상태를 확인·갱신하게 하면, "같은 호출은 한 카에만" 이라는 상호 배제를 설계로 보장할 수 있습니다.
* 이 안전성은 8~9장에서 쓴 것과 완전히 같은 증명 패턴(한 스텝 보존 + 귀납법)으로, 가능한 모든 인터리빙에 대해 증명됩니다 — 병렬 프로그래밍도 결국 이 책이 다룬 같은 도구로 다뤄지는 하나의 사례입니다.
