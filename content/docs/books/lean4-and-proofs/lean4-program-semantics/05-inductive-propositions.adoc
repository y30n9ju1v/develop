4장의 `Star`가 이미 귀납적으로 정의된 명제였습니다. 이 장에서는 이 패턴을 정면으로 다룹니다 — "어떤 값이 어떤 성질을 만족한다"는 걸 **`Bool`을 반환하는 함수**로 표현하는 대신, **그 성질이 성립한다는 증거 자체를 재귀적으로 짓는 방법**으로 표현하는 법입니다.

== 정렬돼 있다는 걸 어떻게 표현할까

리스트가 오름차순으로 정렬돼 있다는 걸 표현하는 흔한 방법은 `Bool`을 반환하는 검사 함수입니다 — "인접한 두 원소를 계속 비교해서, 전부 통과하면 `true`". 그런데 이 장에서는 다른 방법을 봅니다.

[source,lean]
----
inductive Sorted : List Nat → Prop where
  | nil : Sorted []
  | single (x : Nat) : Sorted [x]
  | cons (x y : Nat) (ys : List Nat) (hxy : x ≤ y) (hrest : Sorted (y :: ys)) :
      Sorted (x :: y :: ys)
----

`Sorted`는 `List Nat → Prop`이지만, `Bool` 검사 함수와 근본적으로 다릅니다 — **`Sorted xs`의 증명 자체가 "왜 정렬돼 있는지"를 재귀적으로 보여주는 증거**입니다. 빈 리스트와 원소 하나짜리 리스트는 항상 정렬된 것으로 칩니다(`nil`, `single`). `x :: y :: ys`가 정렬되려면 "`x ≤ y`라는 증거"와 "`y :: ys`도 정렬됐다는 증거"(재귀적으로 이 `Sorted` 자신을 다시 씀)가 둘 다 있어야 합니다 — 정확히 3장에서 본 `∧`(곱)와 재귀 정의가 합쳐진 모양입니다.

[source,lean]
----
example : Sorted [1, 2, 3] :=
  Sorted.cons 1 2 [3] (by omega) (Sorted.cons 2 3 [] (by omega) (Sorted.single 3))

example : ¬ Sorted [3, 1, 2] := by
  intro h
  cases h with
  | cons x y ys hxy hrest => omega
----

`[1, 2, 3]`이 정렬됐다는 증거는 `cons` 생성자를 두 번 겹쳐 지은 것입니다 — "1이 2보다 작다"는 증거와, "`[2, 3]`도 정렬됐다"는(다시 `cons`로 지은) 증거를 묶은 것입니다. 반대로 `[3, 1, 2]`가 정렬되지 않았다는 걸 증명할 때는, "만약 정렬됐다는 증거가 있다면"(`intro h`) 그 증거를 `cases`로 열어봅니다 — `Sorted (3 :: 1 :: [2])`의 증거는 `cons` 생성자로만 지을 수 있는데, 그 생성자가 요구하는 `3 ≤ 1`이라는 조건이 거짓이라 모순이 됩니다(`omega`가 그 모순을 확인합니다).

== 증거를 가지고 다른 걸 증명하기

[source,lean]
----
theorem sorted_head_le (x : Nat) (xs : List Nat) (h : Sorted (x :: xs)) :
    ∀ y ∈ xs, x ≤ y := by
  induction xs generalizing x with
  | nil => intro y hy; cases hy
  | cons z zs ih =>
    intro y hy
    cases h with
    | cons x' z' zs' hxz hrest =>
      cases hy with
      | head => exact hxz
      | tail _ hmem => exact Nat.le_trans hxz (ih z hrest y hmem)
----

`sorted_head_le`는 "정렬된 리스트의 맨 앞 원소는 나머지 모든 원소보다 작거나 같다"는 걸 증명합니다. `h : Sorted (x :: xs)`라는 **증거를 손에 쥐고 있으니**, 그 증거를 `cases`로 열어서 안에 든 `x ≤ y`(바로 다음 원소와의 비교)와 `Sorted (y :: ys)`(나머지가 정렬됐다는 증거)를 꺼내 쓸 수 있습니다. `Bool` 함수였다면 "`isSortedB xs = true`"라는 사실만 있고, 그 사실이 **왜** 참인지에 대한 구조는 없어서 이런 재귀적 증명을 하기가 훨씬 번거로웠을 것입니다.

== 그래도 Bool 버전과 정확히 같다

`Sorted`가 `Bool` 함수보다 다루기 편하다고 해서, 그 둘이 다른 걸 말하는 건 아닙니다 — 같은 사실을 표현하는 두 가지 방법일 뿐입니다.

[source,lean]
----
def isSortedB : List Nat → Bool
  | [] => true
  | [_] => true
  | x :: y :: ys => x ≤ y && isSortedB (y :: ys)

theorem sorted_iff_isSortedB (xs : List Nat) : Sorted xs ↔ isSortedB xs = true := by
  constructor
  · intro h
    induction h with
    | nil => rfl
    | single x => rfl
    | cons x y ys hxy hrest ih => simp [isSortedB, hxy, ih]
  · intro h
    induction xs with
    | nil => exact Sorted.nil
    | cons x xs ih =>
      cases xs with
      | nil => exact Sorted.single x
      | cons y ys =>
        simp only [isSortedB, Bool.and_eq_true, decide_eq_true_eq] at h
        exact Sorted.cons x y ys h.1 (ih h.2)
----

`sorted_iff_isSortedB`가 두 표현이 동치라는 걸 증명합니다 — `→` 방향은 `Sorted`의 증거(귀납적 명제)에 대한 귀납법으로, `←` 방향은 리스트 자체에 대한 귀납법으로 풉니다. 실전에서 어느 쪽을 쓸지는 **무엇을 하고 싶은가**에 달려있습니다 — 실제로 정렬 여부를 실행해서 확인하고 싶다면(`#eval`) `Bool` 함수가, "정렬됐다는 사실을 가지고 다른 정리를 증명하고 싶다면"(`sorted_head_le`처럼) 귀납적 명제가 다루기 편합니다.

== 왜 이게 3부의 기반인가

3부에서 "이 프로그램이 이 결과로 평가된다"는 것 자체를 `Bool` 함수가 아니라 **귀납적으로 정의된 관계**로 표현할 것입니다 — 이유는 이 장에서 본 것과 같습니다. 반복문이 있는 언어는 "항상 종료하는 함수"로 평가 결과를 계산하기 어렵지만(반복문이 영원히 안 끝날 수도 있으니까요), "이 프로그램이 이 결과에 도달한다는 증거"는 관계로 자연스럽게 표현되고, 그 증거를 가지고 이 장의 `sorted_head_le`처럼 다른 성질들을 증명해나갈 수 있습니다.

== 직접 해보기

* `AllPositive : List Nat → Prop`을 귀납적으로 정의해보세요(빈 리스트는 항상 성립, `x :: xs`는 `x > 0`이고 `xs`도 `AllPositive`이면 성립).
* `AllPositive (xs ++ ys) → AllPositive xs`(이어붙인 리스트가 전부 양수면, 앞부분만 떼어내도 전부 양수다)를 증명해보세요.

.해답 보기
[%collapsible]
====
[source,lean]
----
inductive AllPositive : List Nat → Prop where
  | nil : AllPositive []
  | cons (x : Nat) (xs : List Nat) (hx : x > 0) (hxs : AllPositive xs) :
      AllPositive (x :: xs)

theorem allPositive_append_left (xs ys : List Nat) (h : AllPositive (xs ++ ys)) :
    AllPositive xs := by
  induction xs with
  | nil => exact AllPositive.nil
  | cons x xs ih =>
    simp only [List.cons_append] at h
    cases h with
    | cons x' xs' hx hxs => exact AllPositive.cons x xs hx (ih hxs)
----
====

== 요약

* 귀납적으로 정의된 명제(`inductive ... : ... → Prop`)는 "이 값이 이 성질을 만족한다"는 사실 자체가 아니라, **왜 만족하는지에 대한 재귀적 증거**를 짓습니다.
* 이 증거는 `cases`/`induction`으로 열어서 안에 든 정보(예: `Sorted`의 `x ≤ y`)를 꺼내 다른 정리를 증명하는 데 쓸 수 있습니다.
* `Bool`을 반환하는 결정 가능한 함수와 귀납적 명제는 종종 동치이고, 무엇을 증명하고 싶은가에 따라 어느 쪽이 다루기 편한지가 갈립니다.
* 3부에서 다룰 "프로그램이 이 결과로 평가된다"는 것도 함수가 아니라 이 장의 패턴을 따르는 관계로 표현됩니다.
