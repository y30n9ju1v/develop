== 4.1.1. 평가기의 핵심: ``eval``과 ``apply``

모든 표현식은 몇 안 되는 구문 범주 중 하나에 속하고, 복합 표현식을 평가하는 것은 재귀적으로 그 조각들을 평가하고 어느 범주에 속하는지에 따라 결과를 결합하는 것으로 환원됩니다. SICP는 모든 표현식을 타입 없는 리스트로 표현하고, 각 범주마다 술어(``self-evaluating?``, ``quoted?``, ``assignment?``, …)와 몇 개의 선택자를 작성해서, ``eval``의 ``cond``가 표현식의 모양이 실제로 어떻게 저장되어 있는지에 매이지 않고 그 모양에 따라 분기할 수 있게 합니다.

[source,text]
----
 [eval과 apply의 메타순환(Metacircular) 상호 재귀]

                 표현식(Expr) + 환경(Env)
                           │
                           ▼
                  ┌─────────────────┐
                  │    eval(e, env) │◄──────────────────────┐
                  └────────┬────────┘                       │
                           │                                │
            (함수 적용 .app f args 분기)                    │
                           │                                │
                           ▼                                │ (본문 body 평가)
                  ┌─────────────────┐                       │
                  │ apply(proc, args) ──────────────────────┘
                  └─────────────────┘
                    (인자 확장 환경 생성)
----

Lean은 범주와 디스패치 메커니즘을 하나의 선언으로 줍니다. 구문 형식마다 생성자 하나씩을 가진 ``inductive Expr``가 곧 SICP의 추상 구문입니다 — 각 생성자는 동시에 술어(어느 생성자가 쓰였는지)이자 선택자(그 필드들)이고, Lean의 ``match`` 전수성 검사가 Scheme에서 ``else (error "Unknown expression type: EVAL" exp)``가 하는 역할을 대신합니다. 다만 프로그램이 실행되기 전에 강제된다는 점이 다릅니다.

[source,lean]
----
inductive Expr where
  | num : Int → Expr
  | bool : Bool → Expr
  | var : String → Expr
  | quote : Expr → Expr
  | ifE : Expr → Expr → Expr → Expr
  | assign : String → Expr → Expr
  | defineE : String → Expr → Expr
  | lambdaE : List String → List Expr → Expr
  | beginE : List Expr → Expr
  | app : Expr → List Expr → Expr
  deriving Repr
----

값은 자기만의 타입이 필요합니다 — ``Expr``를 평가한다고 일반적으로 또 다른 ``Expr``가 나오는 게 아니기 때문입니다. ``lambdaE``는 _클로저_로 평가되는데, 이는 SICP의 ``make-procedure``가 하듯 매개변수·본문·생성될 때의 환경을 함께 묶습니다. 여기서 SICP를 그대로 옮기면 걸려 넘어지는 지점이 하나 있습니다 — Scheme의 ``lambda``는 자기 자신을 담을 수 있는 환경을 자유롭게 참조하고, Scheme의 원시 절차는 그냥 호스트 함수를 담습니다. Lean의 귀납 타입은 그 두 자기 참조를 있는 그대로 표현하는 것을 거부합니다 — ``Value``가 ``Env``를 담고 ``Env``가 다시 ``Value``를 담는 순환은 커널이 받아들이는 형태로 지어야 하고, ``Value``의 한 생성자가 ``List Value → Value``처럼 자기 타입이 함수 인자 자리(비양성 위치)에 나타나는 것도 마찬가지로 거부됩니다.

link:../3-3-modeling-with-mutable-data/[3.3절]에서 순환 셀을 ``IO.Ref``로 직접 엮는 대신 id 아레나로 표현했던 것과 같은 우회가 여기서도 통합니다 — 환경을 ``Env`` 귀납 타입으로 만드는 대신, 프레임들을 ``Nat`` id로 색인된 아레나에 두고 ``Env``는 그저 "지금 보이는 프레임 id들의 사슬"인 ``List Nat``로 표현합니다. 원시 절차도 함수 자체를 값 안에 담는 대신 _이름_만 담고, 적용 시점에 이름으로 디스패치합니다 — Scheme의 원시 절차가 어차피 "밑바탕 Lisp이 알아서 처리하는 태그"였다는 점을 떠올리면, 이는 SICP의 그림에서 크게 벗어난 것도 아닙니다.

[source,lean]
----
abbrev Env := List Nat  -- 보이는 프레임 id들의 사슬, 안쪽에서 바깥쪽 순서

inductive Value where
  | num : Int → Value
  | bool : Bool → Value
  | sym : String → Value
  | nil : Value
  | pair : Value → Value → Value
  | closure : List String → List Expr → Env → Value
  | primitive : String → Value  -- 함수 자체가 아니라 이름만 담고, 적용 시점에 디스패치합니다
  deriving Repr, Inhabited

abbrev Frame := List (String × Value)

structure EvalCtx where
  frames : IO.Ref (Std.HashMap Nat Frame)
  nextId : IO.Ref Nat
----

[source,text]
----
 [아레나 기반 환경(Env)과 프레임(Frame) 참조 구조]

   Env: [fid 2, fid 0]  (내부 스코프 ──► 전역 스코프)
           │        │
           ▼        ▼
   EvalCtx.frames (아레나: Std.HashMap Nat Frame)
     fid 2: [("n", Value.num 5)]                   (확장된 매개변수 프레임)
     fid 1: [("make-counter", Value.closure ...)]
     fid 0: [("+", Value.primitive "+"), ...]      (전역 프레임)
----

``EvalCtx``는 모든 프레임이 실제로 사는 곳입니다 — 아레나 하나와, 새 프레임에 매길 다음 id를 기억하는 카운터입니다. ``Env``는 그 아레나를 어떤 순서로 훑을지 말해주는 지도일 뿐, 값을 직접 담지 않습니다. SICP의 프레임 사슬이 ``IO.Ref`` 하나짜리 링크드 리스트로 존재하는 대신, 여기서는 아레나 하나와 그 위의 인덱스 리스트로 나뉘어 존재합니다 — 링크드 리스트를 Lean의 커널이 받아들이는 방식으로 다시 지은 것뿐, SICP가 그리는 그림 자체는 바뀌지 않습니다.

이 두 타입이 갖춰지면, ``eval``과 ``apply``는 SICP의 ``cond`` 기반 디스패치를 이제 Lean ``match``로 거의 그대로 옮긴 것에 가깝습니다. 준비물이 하나 필요합니다 — ``quote``된 표현식을 평가 없이 데이터로 돌려주는 ``exprToValue``로, Scheme의 인용이 리스트 구조를 그대로 값으로 돌려주는 것에 대응합니다.

[source,lean]
----
partial def exprToValue : Expr → Value
  | .num n => .num n
  | .bool b => .bool b
  | .var x => .sym x
  | .app f args => (f :: args).foldr (fun e acc => .pair (exprToValue e) acc) .nil
  | _ => .nil  -- 나머지 형식의 인용은 이 글의 언어에서 다루지 않습니다
----

환경 연산(``lookupVariable``/``setVariable``/``defineVariable``/``extendEnvironment``)은 아레나를 다루는 함수이므로 4.1.3절에서 먼저 소개하고, ``eval``/``apply``는 그것들을 호출하는 쪽입니다.

[source,lean]
----
def extendEnvironment (ctx : EvalCtx) (params : List String) (args : List Value)
    (base : Env) : IO Env := do
  let id ← ctx.nextId.get
  ctx.nextId.set (id + 1)
  ctx.frames.modify (·.insert id (params.zip args))
  pure (id :: base)

def lookupVariable (ctx : EvalCtx) (x : String) : Env → IO Value
  | [] => throw (IO.userError s!"Unbound variable: {x}")
  | fid :: rest => do
    match ((← ctx.frames.get).getD fid []).find? (·.1 == x) with
    | some (_, v) => pure v
    | none => lookupVariable ctx x rest

def setVariable (ctx : EvalCtx) (x : String) (v : Value) : Env → IO Unit
  | [] => throw (IO.userError s!"Unbound variable: SET! {x}")
  | fid :: rest => do
    let frame := (← ctx.frames.get).getD fid []
    if frame.any (·.1 == x) then
      ctx.frames.modify (·.insert fid (frame.map fun (k, old) =>
        if k == x then (k, v) else (k, old)))
    else
      setVariable ctx x v rest

def defineVariable (ctx : EvalCtx) (x : String) (v : Value) : Env → IO Unit
  | [] => pure ()
  | fid :: _ => do
    let frame := (← ctx.frames.get).getD fid []
    let frame' := if frame.any (·.1 == x) then
        frame.map fun (k, old) => if k == x then (k, v) else (k, old)
      else
        (x, v) :: frame
    ctx.frames.modify (·.insert fid frame')

def applyPrimitive : String → List Value → Except String Value
  | "+", [.num a, .num b] => .ok (.num (a + b))
  | "-", [.num a, .num b] => .ok (.num (a - b))
  | "*", [.num a, .num b] => .ok (.num (a * b))
  | "=", [.num a, .num b] => .ok (.bool (a == b))
  | "cons", [a, d] => .ok (.pair a d)
  | "car", [.pair a _] => .ok a
  | "cdr", [.pair _ d] => .ok d
  | name, _ => .error s!"Unknown primitive or bad arguments: {name}"
----

이제 ``eval``/``apply``/``evalSequence``는 세 함수가 서로를 부르므로 ``mutual`` 블록으로 묶습니다.

[source,lean]
----
mutual
partial def eval (ctx : EvalCtx) (e : Expr) (env : Env) : IO Value := do
  match e with
  | .num n => pure (.num n)
  | .bool b => pure (.bool b)
  | .var x => lookupVariable ctx x env
  | .quote q => pure (exprToValue q)
  | .assign x v => do
      let val ← eval ctx v env
      setVariable ctx x val env
      pure (.sym "ok")
  | .defineE x v => do
      let val ← eval ctx v env
      defineVariable ctx x val env
      pure (.sym "ok")
  | .ifE p c a => do
      match ← eval ctx p env with
      | .bool false => eval ctx a env
      | _ => eval ctx c env
  | .lambdaE params body => pure (.closure params body env)
  | .beginE exprs => evalSequence ctx exprs env
  | .app op args => do
      let f ← eval ctx op env
      let argVals ← args.mapM (eval ctx · env)
      apply ctx f argVals

partial def apply (ctx : EvalCtx) (f : Value) (args : List Value) : IO Value := do
  match f with
  | .primitive name => IO.ofExcept (applyPrimitive name args)
  | .closure params body clEnv => do
      let newEnv ← extendEnvironment ctx params args clEnv
      evalSequence ctx body newEnv
  | _ => throw (IO.userError "Unknown procedure type: APPLY")

partial def evalSequence (ctx : EvalCtx) (exprs : List Expr) (env : Env) : IO Value :=
  match exprs with
  | [] => pure (.bool false)
  | [e] => eval ctx e env
  | e :: rest => do
      let _ ← eval ctx e env
      evalSequence ctx rest env
end
----

SICP와 다른 두 지점을 짚을 만합니다. 첫째, "해석되는 언어에서의 참"을 "구현 언어에서의 참"으로 번역하는 ``eval-if``의 일(SICP의 ``true?``)이 하나의 패턴으로 뭉개집니다 — ``.bool false``만이 유일한 거짓 값이고 직접 매치되며, 별도의 번역 절차가 필요 없습니다. ``Value``가 이미 Lean 자신이 검사할 바로 그 경우들을 갖고 있기 때문입니다. 둘째, ``list-of-values``는 ``args.mapM (eval ctx · env)``가 됩니다 — 연습문제 4.1이 다루는 "왼쪽에서 오른쪽으로 평가하는지, 오른쪽에서 왼쪽으로 평가하는지 알 수 없다"는 문제 자체가 사라집니다. ``List.mapM``의 평가 순서는 Lean 표준 라이브러리에 명시되어 있고(왼쪽에서 오른쪽), 근본 Lisp 구현의 ``cons`` 인자 평가 순서에 우연히 기대는 게 아니기 때문입니다.

``eval``/``apply``에 ``partial``이 필요한 이유는 이 시리즈에서 이미 여러 번 본 것과 같습니다 — 재귀가 ``Expr``의 하위 항으로만 내려간다면 구조적이겠지만, ``.app`` 분기의 ``apply``가 클로저 본문으로 재귀하면서 _새로 만들어진_ 표현식(``body``)에 대해 ``evalSequence``를 부르고, 그 ``body``가 원래 표현식보다 구조적으로 작다는 것을 Lean이 자동으로 볼 방법이 없기 때문입니다 — 인터프리터가 스스로 무한 루프에 빠지는 프로그램을 평가하도록 요청받을 수도 있다는 사실은 언어와 무관하게 참이고, link:../5-2-a-register-machine-simulator/[5.2절]의 ``execute``가 그랬던 것과 같은 종류의 근본적 ``partial``입니다.

'''

== 4.1.2. 표현식 표현하기: 추상 구문이 타입이 될 때

SICP는 4.1.2절 대부분을 ``assignment?``/``definition?``/``if?`` 같은 술어와 ``assignment-variable``/``if-predicate`` 같은 선택자를 작성하는 데 씁니다 — ``eval``의 ``cond``가 "``set!`` 심볼로 시작하는 리스트"를 다른 곳에서의 표현 방식에 매이지 않고 독립된 구문 범주로 다룰 수 있게 해주는 연결 조직입니다. 그 절차들 하나하나는 이미 위의 ``Expr`` 생성자들이 함축하고 있습니다 — ``.assign x v``의 패턴 매치가 곧 ``assignment?``이자 동시에 ``assignment-variable``/``assignment-value``입니다. SICP가 손으로 만들어야 하는 것 — 구체적인 리스트 표현과 분리된 추상 구문 계층 — 을 Lean의 귀납 타입은 공짜로 줍니다. 대가는 파일 곳곳에 흩어진 형식별 술어-선택자 쌍 대신, AST의 모양을 하나의 선언에서 한 번에 고정해야 한다는 것입니다.

SICP가 공짜로 얻지만 여기서는 대가를 치르는 지점이 하나 있습니다 — ``cond``나 ``let`` 같은 _파생 표현식(derived expression)_입니다. SICP는 이를 평가기가 이미 이해하는 표현식으로의 구문적 재작성(``cond->if``)으로 구현하고, ``eval`` 자체는 건드리지 않습니다. 우리의 ``Expr``는 닫힌 귀납 타입이므로, ``condE`` 생성자를 직접 추가하고 ``eval``에 새 분기를 줄 수도 있습니다 — 하지만 그건 정확히 데이터 지향 디스패치와 파생 표현식이 둘 다 피하려는, ``eval``을 건드리는 대가입니다. SICP의 정신에 충실한 대안은 전처리 패스 ``Expr → Expr``입니다 — ``eval``이 보기 전에 ``cond``를 중첩된 ``.ifE``로 펼쳐두는 것으로, ``eval`` 안의 새 경우가 아니라 같은 닫힌 타입 위의 변환입니다.

[source,lean]
----
def condToIf (clauses : List (Expr × List Expr)) : Expr :=
  match clauses with
  | [] => .bool false
  | (.var "else", actions) :: _ => .beginE actions
  | (pred, actions) :: rest => .ifE pred (.beginE actions) (condToIf rest)
----

(여기서는 ``else`` 절을 ``.var "else"``라는 관례로 표시했습니다 — 진짜 파서가 있었다면 별도의 마커 타입을 뒀겠지만, 이 글에는 파서가 없으므로 관례로 대신합니다.)

'''

== 4.1.3. 평가기의 자료구조: 환경

환경은 프레임의 사슬이고, 각 프레임은 가변적인 바인딩 표입니다. 변수 조회는 현재 프레임을 훑고, 실패하면 감싸는 프레임으로 옮겨갑니다 — link:../3-2-environment-model-of-evaluation/[3.2절]의 환경 모델에서 다룬 프레임 사슬 걷기와 정확히 같습니다. 4.1.1절에서 이미 정의한 ``lookupVariable``/``setVariable``/``defineVariable``/``extendEnvironment``가 바로 이 사슬 걷기입니다 — ``Env``라는 ``List Nat``가 사슬이고, ``EvalCtx.frames``라는 아레나가 각 프레임의 실제 내용물이 사는 곳입니다.

SICP는 ``lookup-variable-value``를 바깥쪽 ``env-loop``와 안쪽 ``scan``으로 나누는데, Scheme이 프레임을 (변수 리스트, 값 리스트) 두 개의 병렬 리스트로 표현해서 발맞춰 훑어야 하기 때문입니다. 프레임을 ``List (String × Value)``로 곧바로 표현하면 그 안쪽 스캔이 ``List.find?`` 하나로 뭉개지고, 남는 재귀는 프레임을 넘나드는 바깥 루프뿐입니다 — ``Expr``가 ``eval``에게 줬던 것과 같은 종류의 더 작은 단순화입니다. ``lookupVariable``/``setVariable``의 이 바깥 루프는 ``Env``의 꼬리에 대한 평범한 구조적 재귀이므로 ``partial``이 필요 없습니다 — 아레나 자체는 재귀 대상이 아니라 매 단계에서 한 번 조회되는 값일 뿐입니다.

(SICP의 프레임은 문자 그대로 ``set-car!``/``set-cdr!``로 변경되는 두 리스트의 쌍인데, 우리의 아레나 기반 프레임은 이를 단순화한 것입니다 — 그 대가로 SICP의 ``add-binding-to-frame!``이 갖는 "기존 바인딩의 저장소를 건드리지 않고 바인딩을 추가한다"는 성질까지 그대로 보존하지는 않습니다. 전체 논의를 흐리지 않기 위한 의도적 단순화입니다.)

'''

== 4.1.4~4.1.5. 평가기를 프로그램으로 돌리기, 그리고 데이터로서의 프로그램

실제로 뭔가를 돌리려면, ``eval``/``apply``에는 ``car``, ``cdr``, ``cons``, ``+`` 등의 원시 연산이 채워진 전역 환경이 필요합니다 — 각각 ``applyPrimitive``가 이름으로 알아보는 ``Value.primitive``로 감싸집니다.

[source,lean]
----
def setupGlobalEnv (ctx : EvalCtx) : IO Env :=
  extendEnvironment ctx ["+", "-", "*", "=", "cons", "car", "cdr"]
    [.primitive "+", .primitive "-", .primitive "*", .primitive "=",
     .primitive "cons", .primitive "car", .primitive "cdr"] []
----

SICP의 ``driver-loop``는 ``read``로 텍스트를 읽고, 평가하고, 결과를 출력합니다 — S-표현식 구문을 위한 진짜 리더는 이 글의 범위 밖이므로, SICP가 프롬프트에 ``(factorial 5)``라고 타이핑하는 자리에서 우리는 그에 대응하는 ``Expr``를 생성자로 직접 만들어 ``eval``에 건네고, 대화형 루프 대신 이 시리즈 전체에서 그래왔듯 ``#eval``을 씁니다.

[source,lean]
----
def factorialExpr : Expr :=
  .defineE "factorial"
    (.lambdaE ["n"]
      [.ifE (.app (.var "=") [.var "n", .num 1])
            (.num 1)
            (.app (.var "*") [.var "n", .app (.var "factorial") [.app (.var "-") [.var "n", .num 1]]])])

#eval show IO Unit from do
  let ctx : EvalCtx := ⟨← IO.mkRef ∅, ← IO.mkRef 0⟩
  let globalEnv ← setupGlobalEnv ctx
  let _ ← eval ctx factorialExpr globalEnv
  let result ← eval ctx (.app (.var "factorial") [.num 5]) globalEnv
  IO.println (repr result)
-- Value.num 120
----

``EvalCtx``를 매개변수로 실어 나르는 것이 SICP 원문과 겉으로 가장 다른 부분입니다 — Scheme의 ``eval``은 전역 상태를 암묵적으로 참조하지만, 여기서는 아레나가 어디에 사는지가 타입 시그니처(``EvalCtx → …``)에 그대로 드러납니다. 이는 이 시리즈 전체가 반복해온 것과 같은 무늬입니다 — 숨겨진 가변 상태를 쓰려면 그것을 값으로 만들어 명시적으로 실어 날라야 합니다.

이 평가기가 SICP의 환경 모델을 정말로 구현하고 있다는 것은, 클로저 본문 안의 ``set!``이 그 클로저가 포획한 프레임을 실제로 변경하는지 시험해보면 확인됩니다 — link:../3-1-assignment-and-local-state/[3.1절]의 ``makeWithdraw``와 같은 모양을, 이번에는 우리 자신의 인터프리터 _안에서_ 재현합니다.

[source,lean]
----
-- (define (make-counter) (begin (define n 0) (lambda () (begin (set! n (+ n 1)) n))))
def makeCounterExpr : Expr :=
  .defineE "make-counter"
    (.lambdaE []
      [.defineE "n" (.num 0),
       .lambdaE [] [.beginE [.assign "n" (.app (.var "+") [.var "n", .num 1]), .var "n"]]])

#eval show IO Unit from do
  let ctx : EvalCtx := ⟨← IO.mkRef ∅, ← IO.mkRef 0⟩
  let globalEnv ← setupGlobalEnv ctx
  let _ ← eval ctx makeCounterExpr globalEnv
  let _ ← eval ctx (.defineE "c" (.app (.var "make-counter") [])) globalEnv
  let _ ← eval ctx (.app (.var "c") []) globalEnv
  let r ← eval ctx (.app (.var "c") []) globalEnv
  IO.println (repr r)
-- Value.num 2
----

``c``를 두 번 호출하면 ``1``이 아니라 ``2``가 나옵니다 — ``make-counter``가 만들어낸 프레임이 두 호출 사이에 살아남아 있고, ``set!``이 그 프레임을 진짜로 변경한다는 뜻입니다. 이것이 정확히 4.1.1절에서 아레나로 우회하며 잃지 않으려 했던 것입니다 — ``Env``가 그저 id 리스트로 뭉개졌더라도, 그 id가 가리키는 프레임은 여전히 아레나 안에서 진짜로 공유되는 가변 셀입니다.

인용도 확인해 볼 수 있습니다 — ``.quote``가 감싼 표현식은 평가되지 않고 데이터로 되돌아옵니다.

[source,lean]
----
#eval show IO Unit from do
  let ctx : EvalCtx := ⟨← IO.mkRef ∅, ← IO.mkRef 0⟩
  let globalEnv ← setupGlobalEnv ctx
  let r ← eval ctx (.quote (.app (.var "a") [.num 1, .num 2])) globalEnv
  IO.println (repr r)
-- Value.pair (Value.sym "a") (Value.pair (Value.num 1) (Value.pair (Value.num 2) (Value.nil)))
----

``a``는 여기서 한 번도 변수로 조회되지 않습니다 — ``exprToValue``가 ``.var "a"``를 심볼 ``.sym "a"``로 그대로 데이터화할 뿐입니다. 이것이 link:../2-3-symbolic-data/[2.3절]에서 짚었던 것과 같은 지점입니다 — Lean에서는 인용이라는 별도의 구문적 장치가 필요 없다고 했지만, _인터프리터가 인터프리터하는 언어_ 안에서는 SICP의 Scheme과 똑같이 여전히 필요합니다. ``quote``가 만드는 "평가하지 않고 데이터로" 라는 구분은 우리가 짓는 언어의 성질이지, 그 언어를 담는 Lean의 성질이 아니기 때문입니다.

SICP는 이 절을 평가기가 _보편 기계(universal machine)_라는 관찰로 마칩니다 — 다른 기계의 기술(Lisp 코드로서)이 주어지면, 스스로를 그 기계처럼 동작하도록 구성하는 프로그램입니다. 위의 ``eval``/``apply``는 이를 이 시리즈가 제공한 것 중 가장 문자 그대로의 방식으로 구체화합니다 — 그것들은 평범한 Lean 함수이고, Lean 자신의 런타임 위에서 실행되며, 방금 작은 Lisp 하나를 흉내 내는 걸 마쳤습니다. 재귀는 SICP의 "Scheme으로 쓰인 Scheme" 이야기보다 한 겹 더 나아가기도 합니다 — 이 시리즈의 모든 글에서 ``def``, ``structure``, ``inductive`` 하나하나를 이해해준 Lean 자신의 elaborator도 Lean으로 쓰여 있고, 이전 버전의 자기 자신으로 컴파일됩니다. 방금 만든 메타순환 평가기는, 우리가 그것을 만드는 데 썼던 바로 그 언어를 애초에 가능하게 만드는 것과 같은 아이디어의 작고 손으로 만든 사례입니다.

== 정리

[cols="1,1,1",options="header"]
|===
|SICP 개념 |Scheme |Lean 4
|추상 구문 |술어(``assignment?``) + 선택자(``assignment-variable``) 쌍 |``inductive Expr``의 생성자 하나로 통합
|알 수 없는 표현식 |런타임 ``error`` |컴파일 시점 ``match`` 전수성
|``true?`` 변환 |별도 절차 |``.bool false`` 패턴 하나로 흡수
|인자 평가 순서 |밑바탕 Lisp의 ``cons`` 평가 순서에 좌우됨(연습문제 4.1) |``List.mapM``의 명시된 왼쪽-오른쪽 순서
|파생 표현식(``cond``) |``eval``을 안 건드리는 구문적 재작성 |``Expr → Expr`` 전처리 패스로 동일하게 유지
|환경 |프레임(변수 리스트·값 리스트 쌍)의 사슬 |``List Nat`` 사슬 + ``EvalCtx.frames`` id 아레나
|원시 절차 |밑바탕 Lisp 절차를 감싼 태그 리스트 |``Value.primitive``가 담은 이름 + ``applyPrimitive`` 디스패치
|===

메타순환 평가기가 SICP 전체에서 하는 역할은, 그동안 산문으로 설명해온 "평가란 무엇인가"를 실행 가능한 코드로 만드는 것입니다. Lean에서는 ``Expr``라는 귀납 타입 하나가 SICP의 흩어진 술어-선택자 쌍들을 흡수하지만, ``Value``/``Env``의 자기 참조는 SICP의 Scheme이 공짜로 허락하는 형태로 그대로 옮겨지지 않았습니다 — 커널이 받아들이는 형태로 다시 짜야 했고, 그 다시 짜기(원시 절차를 이름으로, 환경을 id 아레나로)가 이 글에서 SICP 원문과 진짜로 갈라지는 지점입니다. 다음 글에서는 4.2절 — 지연 평가를 언어의 기본 평가 전략으로 바꾸는 것과, 비결정적 계산(nondeterministic computing)을 위한 ``amb`` 평가기 — 를 다룹니다.
