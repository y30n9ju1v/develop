이 글은 _컴퓨터 프로그램의 구조와 해석_(SICP)의 아이디어를 다시 훑어보되, 모든 Scheme 코드를 Lean 4로 다시 작성해 보는 시리즈의 첫 번째 글입니다. SICP의 원래 예제는 동적 타입의 Lisp 위에서 동작하는데, 같은 아이디어를 정적 타입 시스템과 증명 보조기가 깔려 있는 언어로 표현하면 무엇이 달라지고 무엇이 그대로인지 살펴봅니다.

'''

== 왜 프로그래밍 언어는 세 가지 축으로 이해할 수 있는가

언어는 단순히 컴퓨터에게 지시를 내리는 수단이 아니라, 우리가 프로세스에 대한 생각을 정리하는 틀이기도 합니다. SICP는 "강력하다"고 부를 만한 언어라면 세 가지를 제공해야 한다고 말합니다 — 언어가 인식하는 가장 단순한 단위인 *원시 표현식(primitive expressions)*, 단순한 것들을 묶어 복합적인 것을 만드는 *조합 수단(means of combination)*, 그리고 복합적인 것에 이름을 붙여 이후로는 하나의 단위로 다룰 수 있게 하는 *추상화 수단(means of abstraction)*입니다. 언어의 나머지 부분은 어떤 의미에서 이 세 가지 재료를 두 종류의 대상 — 데이터를 다루는 규칙인 _절차(procedure)_와, 다뤄지는 대상인 _데이터_ — 에 적용해서 만들어진 것입니다.

Lean에서도 같은 세 가지 축을 찾을 수 있는데, 다만 원시 계층이 더 엄격합니다. 숫자 리터럴과 내장 타입이 원시 표현식이고, 함수 적용과 ``def``/``let``이 조합·명명 수단이며, 여기에 SICP가 처음부터 신경 쓸 필요가 없었던 네 번째 요소 — 표현식이 _어떤 종류_의 값이어야 하는지를 미리 선언하고 나중에 검사할 수 있는 타입 시스템 — 가 더해집니다.

'''

== 1.1.1. 표현식과 조합

인터프리터에게 건넬 수 있는 가장 단순한 것은 숫자이고, 인터프리터는 그 숫자를 그대로 돌려줍니다. 숫자는 ``+``, ``*`` 같은 원시 절차와 결합해 _조합(combination)_을 이루는데, 이는 연산자 뒤에 피연산자들이 오고 전체가 괄호로 감싸인 표현식입니다. Scheme은 항상 연산자를 맨 앞에 쓰는데(_전위 표기법_), 일반적인 수학 표기법에 익숙하다면 낯설어 보이지만 실질적인 이득이 있습니다 — 연산자가 몇 개의 피연산자를 받든 모호함이 전혀 없고, 조합이 아무리 깊이 중첩되어도 구조를 구분하기 위한 별도의 구두점이 필요 없습니다.

Lean에서는 ``+`` 같은 연산자를 전위로 조합하는 형태가 그대로 있지는 않습니다 — Lean은 일반적인 중위 연산자를 씁니다 — 하지만 함수 적용 자체는 전위이고, 중첩되는 방식은 완전히 동일합니다. Scheme 스타일의 산술 예제를 그대로 옮기면 다음과 같습니다.

[source,lean]
----
#eval 486
-- 486

#eval 137 + 349
-- 486

#eval 1000 - 334
-- 666

#eval 5 * 99
-- 495

#eval (10 : Float) / 5
-- 2.000000

#eval (2.7 : Float) + 10
-- 12.700000
----

SICP가 전위 표기법의 장점을 보여줄 때 쓰는 중첩 조합 예제도 그대로 옮겨집니다. Lean의 ``+``/``*``/``-``도 Scheme과 똑같이 얼마든지 중첩될 수 있기 때문입니다.

[source,lean]
----
#eval 3 * 5 + (10 - 6)
-- 19

#eval 3 * (2 * 4 + (3 + 5)) + (10 - 7 + 6)
-- 57
----

Lean에도 자기만의 *읽고-평가하고-출력하는 루프(read-eval-print loop)*가 있습니다 — 에디터에서 ``#eval``은 그 자리에 쓴 표현식을 바로 평가해 결과를 인라인으로 보여주고, "이제 이걸 출력해라"라고 따로 말할 필요가 없습니다.

'''

== 1.1.2. 이름 짓기와 환경

계산 결과에 이름을 붙이는 것은 언어가 제공할 수 있는 가장 단순한 형태의 추상화입니다. 일단 ``size``가 2를 의미하게 되면, 2를 써야 할 자리 어디에나 ``size``를 대신 쓸 수 있고, 원의 둘레처럼 더 복잡한 계산도 이전에 이름 붙인 결과들을 바탕으로 그 세부 사항을 반복하지 않고 만들 수 있습니다.

Scheme의 ``define``은 Lean에서 ``def``가 됩니다 — 다만 Lean은 새로 도입하는 이름에 타입을(대개는 추론해서) 함께 요구한다는 점이 다릅니다.

[source,lean]
----
def size : Nat := 2

#eval 5 * size
-- 10

def pi : Float := 3.14159
def radius : Float := 10

#eval pi * (radius * radius)
-- 314.159000

def circumference : Float := 2 * pi * radius

#eval circumference
-- 62.831800
----

인터프리터(Lean이라면 elaborator)는 나중에 이름을 찾아볼 수 있도록 어떤 이름이 어떤 값을 가리키는지 계속 기록해 두어야 합니다 — SICP는 이 기록을 _환경(environment)_이라고 부릅니다. Lean에도 정확히 같은 개념이 있습니다. ``def`` 하나하나가 현재 파일의 환경을 확장하고, 이후의 표현식들은 그렇게 누적된 환경을 기준으로 처리됩니다.

'''

== 1.1.3. 조합을 평가하는 규칙

조합을 평가하는 과정 자체가 하나의 작은 절차로 기술됩니다 — 모든 하위 표현식을 먼저 평가한 다음, 가장 왼쪽 하위 표현식이 가리키는 절차를 나머지 값들에 적용합니다. 하위 표현식을 평가하는 과정 자체가 또 다른 조합을 평가하는 일일 수 있으므로, 이 규칙은 _재귀적_입니다 — 자기 자신을 호출하는 단계를 스스로 포함하고 있습니다. 깊이 중첩된 표현식이라면 이를 트리로 그려볼 수 있습니다. 값은 말단(leaf)에서 계산되어 위로 스며 올라가며, 각 내부 노드에서 결합되어 마지막에는 하나의 값이 뿌리(root)에 도달합니다.

Lean의 elaborator도 정확히 같은 형태의 규칙을 따릅니다. ``#eval (2 + 4 * 6) * (3 + 5 + 7)``은 각 하위 항을 먼저 축약한 다음 그 결과를 결합해서 평가됩니다.

[source,lean]
----
#eval (2 + 4 * 6) * (3 + 5 + 7)
-- 390
----

이 재귀의 기저 사례는 _원시_ 표현식입니다 — 숫자 리터럴은 그것이 가리키는 수로 평가되고, 그 밖의 이름은 현재 환경이 그 이름에 연결해 둔 값으로 평가됩니다. ``define``/``def`` 자체는 이 규칙의 예외입니다 — 일반적인 조합이 아니라 _특수 형식(special form)_인데, 그 목적 자체가 환경에서 값을 찾아오는 것이 아니라 환경에 새로운 연결을 만드는 것이기 때문입니다. Lean에도 ``def`` 말고 ``let``, ``fun``, ``if``/``then``/``else``, ``match`` 같은 다양한 특수 형식이 있고, 각각 자기만의 평가 규칙을 가지고 있습니다 — SICP가 Scheme 문법의 특수 형식에 부여하는 것과 똑같은 역할입니다.

'''

== 1.1.4. 복합 절차

값에 이름을 붙이는 것은 약한 형태의 추상화이고, _연산_에 이름을 붙이는 것이 훨씬 강력합니다. 복합적인 계산 전체를 하나의 단위로 지칭하고, 서로 다른 입력에 재사용할 수 있게 해주기 때문입니다. "무언가를 제곱하려면 그것을 자신과 곱한다"는, 나중에 무엇에 적용될지를 대신 나타내는 형식 매개변수를 가진 절차가 됩니다.

[source,lean]
----
def square (x : Float) : Float := x * x

#eval square 21
-- 441.000000

#eval square (2 + 5)
-- 49.000000

#eval square (square 3)
-- 81.000000
----

Scheme에서와 마찬가지로, 복합 절차는 또 다른 절차를 만드는 재료가 됩니다 — ``sum-of-squares``는 순전히 ``square``만으로 정의되고, 절차 ``f``는 순전히 ``sum-of-squares``만으로 정의됩니다. "원시" 절차를 호출하는 것과 방금 만든 절차를 호출하는 것 사이에 겉으로 드러나는 차이는 없습니다.

[source,lean]
----
def sumOfSquares (x y : Float) : Float :=
  square x + square y

#eval sumOfSquares 3 4
-- 25.000000

def f (a : Float) : Float :=
  sumOfSquares (a + 1) (a * 2)

#eval f 5
-- 136.000000
----

'''

== 1.1.5. 절차 적용을 위한 치환 모델

복합 절차를 적용하려면, 절차의 본문을 평가하되 각 형식 매개변수를 대응하는 인자로 치환합니다. ``f 5``를 손으로 추적해 보면 전체 연쇄가 드러납니다 — ``f``의 본문을 가져오고, ``a``를 ``5``로 치환하면, ``5 + 1``과 ``5 * 2``에 적용된 ``sum-of-squares`` 조합이 만들어지며, 이것이 단계적으로 축약되어 결국 하나의 숫자로 떨어집니다. 이것이 _치환 모델(substitution model)_입니다 — 절차 적용이 실제로 무엇을 의미하는지 추론하는 방법이지, 실제 인터프리터가 내부적으로 이렇게 구현되어 있다는 주장은 아닙니다(실제 인터프리터는 프로그램 텍스트를 문자 그대로 다시 쓰는 대신 환경을 사용합니다).

[source,text]
----
                       f 5
                        │ (f 본문 적용: a ↦ 5)
                        ▼
            sumOfSquares (5 + 1) (5 * 2)
              │                    │
        (인자 5 + 1 평가)    (인자 5 * 2 평가)
              ▼                    ▼
           square 6     +      square 10
              │                    │
         (6 * 6 계산)        (10 * 10 계산)
              ▼                    ▼
             36         +         100
                        │
                        ▼
                       136
----

[source,lean]
----
-- f 5
-- ⇒ sumOfSquares (5 + 1) (5 * 2)
-- ⇒ square 6 + square 10
-- ⇒ 6 * 6 + 10 * 10
-- ⇒ 36 + 100
-- ⇒ 136
----

SICP는 또한 _적용적 순서(applicative-order)_ 평가(인자를 먼저 평가한 다음 적용하는 방식 — 실제로 Scheme이 하는 방식)와 _정상 순서(normal-order)_ 평가(완전히 치환부터 한 다음 축약하며, 인자는 실제로 필요할 때만, 그리고 쓰일 때마다 다시 평가될 수 있는 방식)를 대비합니다. Lean의 ``#eval``도 Scheme과 정확히 같은 의미에서 적용적 순서입니다 — ``def``로 정의된 함수에 진입하기 전에 인자들이 정규형으로 평가됩니다. Lean도 ``Thunk``를 통해 진짜 지연 평가 값을 지원하기는 하지만, 이는 정상 순서의 "필요할 때까지 평가하지 않는다"는 개념에 가장 가까운 선택적 데이터 타입일 뿐, 언어의 기본 평가 전략은 아닙니다.

'''

== 1.1.6. 조건 표현식과 술어

조합과 명명만으로 이루어진 언어로는 "테스트를 통과하면 이것을, 아니면 저것을 한다"를 표현할 수 없습니다. SICP는 다중 분기 사례 분석을 위한 ``cond``와 그 두 갈래 특수 사례인 ``if``를 도입하는데, 둘 다 참인 술어를 찾는 즉시 멈추고 모든 절을 평가하지는 않습니다.

[source,lean]
----
def absCond (x : Float) : Float :=
  if x > 0 then x
  else if x < 0 then -x
  else 0
----

Lean에는 임의 개수의 절을 받는 ``cond`` 특수 형식이 그대로 있지는 않지만, ``if``/``else if`` 연쇄가 정확히 같은 역할을 하며, 참인 첫 번째 테스트에서 멈춥니다. SICP가 함께 보여주는 두 갈래 ``if`` 버전도 그대로 옮겨집니다.

[source,lean]
----
def absIf (x : Float) : Float :=
  if x < 0 then -x else x
----

``and``, ``or``, ``not``이 논리 어휘를 완성합니다. Scheme의 버전과 마찬가지로 Lean의 ``&&``, ``||``도 _단락 평가(short-circuiting)_됩니다 — 필요할 때만 두 번째 인자를 평가한다는 점에서 사실상 특수 형식을 가장한 것입니다.

[source,lean]
----
def inRange (x : Float) : Bool :=
  x > 5 && x < 10

def gte (x y : Float) : Bool :=
  x > y || x == y

def gte' (x y : Float) : Bool :=
  !(x < y)
----

*연습문제 1.1 (Lean 버전)*: 아래 정의들을 ``#eval``로 실제 평가해보고, ``a``, ``b``가 어떤 값을 가지는지, 그리고 ``if``/``cond``에 해당하는 각 분기가 실제로 어떤 값을 내는지 직접 확인해 보세요.

[source,lean]
----
def a : Float := 3
def b : Float := a + 1

#eval a + b + a * b
#eval a == b
#eval if b > a && b < a * b then b else a
----

*연습문제 1.3 (Lean 버전)*: 세 개의 숫자를 받아 그중 큰 두 수의 제곱의 합을 반환하는 절차를 작성하세요. ``if``로 가장 작은 값을 걸러내고, 나머지 두 값에 ``sumOfSquares``를 적용하면 됩니다.

[source,lean]
----
def sumSquaresOfTwoLargest (x y z : Float) : Float :=
  if x <= y && x <= z then sumOfSquares y z
  else if y <= x && y <= z then sumOfSquares x z
  else sumOfSquares x y
----

'''

== 1.1.7. 예제: 뉴턴법으로 제곱근 구하기

수학 함수는 값이 _무엇_인지를 기술하고, 절차는 그것을 _어떻게_ 계산하는지를 기술합니다. "stem:[y^2 = x]를 만족하는 stem:[y \geq 0]"은 제곱근을 수학적 대상으로서 완벽하게 정의하지만, 인터프리터에게 그 stem:[y]를 실제로 찾아낼 방법은 전혀 알려주지 않습니다. 뉴턴법은 이 선언적인 기술을 명령적인 기술로 바꿔줍니다 — 임의의 추측값에서 시작해, 추측값과 (피제수를 그 추측값으로 나눈 값)의 평균을 내면 반드시 더 나은 추측값이 됩니다. 이를 충분히 좋아질 때까지 반복합니다.

[source,text]
----
                      ┌───────────────────────────────────────┐
                      │              초기 추측값              │
                      │             (guess = 1.0)             │
                      └──────────────────┬────────────────────┘
                                         │
                                         ▼
                             ┌───────────────────────┐
                             │  goodEnough? (검사)   │
                             │ |guess² - x| < 0.001? │
                             └───────────┬───────────┘
                                         │
                      ┌──────────────────┴──────────────────┐
                   아니오 (False)                         예 (True)
                      │                                     │
                      ▼                                     ▼
        ┌───────────────────────────┐             ┌───────────────────┐
        │      improve (개선)       │             │   최종 제곱근값   │
        │ average(guess, x / guess) │             │    guess 반환     │
        └─────────────┬─────────────┘             └───────────────────┘
                      │                                     ▲
                      └─────────────────(재귀 호출)──────────┘
----

[NOTE]
.부동소수점 비교는 구조적으로 감소하는 인자가 아닙니다
====
Lean 4의 커널은 모든 함수가 반드시 종료함을 정적으로 증명해야 합니다. 그러나 `sqrtIter`의 종료 판정인 `goodEnough`는 부동소수점 오차 검사(`|guess² - x| < 0.001`)로 이루어져 있어, 컴파일러가 인자의 크기가 단조 감소(well-founded recursion)함을 자동으로 확인할 수 없습니다(부동소수점 반올림 오차로 인해 진동하거나 무한 루프에 빠질 가능성을 정적으로 배제할 수 없음). 따라서 Lean에서는 전역성(totality) 보장을 명시적으로 해제하는 `partial` 키워드를 붙여야 컴파일을 통과할 수 있습니다.
====

[source,lean]
----
def average (x y : Float) : Float :=
  (x + y) / 2

def improve (guess x : Float) : Float :=
  average guess (x / guess)

def goodEnough (guess x : Float) : Bool :=
  Float.abs (square guess - x) < 0.001

partial def sqrtIter (guess x : Float) : Float :=
  if goodEnough guess x then guess
  else sqrtIter (improve guess x) x

def sqrt (x : Float) : Float :=
  sqrtIter 1.0 x

#eval sqrt 9
-- 3.000092

#eval sqrt (100 + 37)
-- 11.704700

#eval sqrt (sqrt 2 + sqrt 3)
-- 1.773928

#eval square (sqrt 1000)
-- 1000.000370
----

여기 어디에도 전용 반복 구문이 쓰이지 않았다는 점에 주목하세요. ``sqrtIter``는 개선된 추측값으로 자기 자신을 호출할 뿐이고, 이 평범한 자기 호출 자체가 반복입니다 — Lisp이 반복을 표현하기 위해 전용 루프 문법을 필요로 하지 않는다는, SICP가 짚는 바로 그 지점입니다.

'''

== 1.1.8. 블랙박스 추상화로서의 절차

``sqrtIter``는 우리가 처음 만난, 자기 자신을 재귀적으로 참조하는 절차입니다. 이것이 순환 논리로 무너지지 않는 이유는 매 호출이 (구성상 점점 나아지는) 서로 다른 인자에 적용되기 때문입니다 — 재귀적 프로세스가 실제로 어떻게 펼쳐지는지 더 자세히 들여다볼 때 이를 엄밀하게 다룰 것입니다. 지금 더 중요한 교훈은 _분해(decomposition)_입니다 — 제곱근을 계산하는 문제는 "이 추측값이 충분히 좋은가?", "추측값을 어떻게 개선하는가?", "두 수의 평균을 어떻게 내는가?"로 자연스럽게 쪼개지고, 각각이 하나의 이름 붙은 절차가 되어 원래 문제의 모양을 그대로 반영하는 작은 절차 군집을 이룹니다.

이 분해가 가치 있는 이유는 단순히 프로그램이 조각으로 나뉘었기 때문이 아닙니다 — 어떤 프로그램이든 임의로 잘라낼 수 있습니다. 중요한 것은 각 조각이 식별 가능한 하나의 작업을 수행하고, 그것을 호출하는 절차 입장에서는 _블랙박스_로 다룰 수 있다는 점입니다. ``goodEnough``는 ``square``가 결과를 _어떻게_ 계산하는지 신경 쓰지 않고, 제곱을 계산한다는 사실만 신경 씁니다. 다음 두 구현은 ``goodEnough``의 관점에서 완전히 서로 바꿔 쓸 수 있습니다.

[source,lean]
----
def square1 (x : Float) : Float := x * x
def square2 (x : Float) : Float := Float.exp (2 * Float.log x)
----

호출하는 쪽에서 절대로 관찰할 수 없어야 하는 구현 세부 사항 중 하나가 구현자가 고른 매개변수 이름입니다. ``square (x : Float)``와 ``square (y : Float)``는 동일하게 동작해야 하며, 이는 형식 매개변수의 이름이 그 절차 자신의 본문에 _국한(local)_ — 그 안에 _묶여(bound)_ — 있고, 본문 전체에서 일관되게 이름을 바꿔도 절차의 의미가 달라지지 않는다는 뜻입니다. 어떤 둘러싼 매개변수나 ``let``에도 묶이지 않은 이름은 _자유(free)_입니다. ``goodEnough``에서 ``guess``와 ``x``는 묶여 있고, ``Float.abs``와 ``square``는 자유입니다. 그리고 정확히 ``square``가 자유롭기 때문에, 다른 ``square``로 바꿔 끼워도 ``goodEnough`` 자신의 의미는 달라지지 않습니다.

Lean은 이 시점의 SICP Scheme이 제공할 필요가 없던 도구를 하나 더 줍니다 — ``square1``, ``square2``를 최상위 환경에서 아예 감춰서, 실제로 필요로 하는 절차 안에 ``let``으로 중첩시킬 수 있습니다. 그러면 오직 ``sqrt``만 신경 쓰는 보조 절차 군집이 다른 어떤 것의 이름공간으로도 새어 나가지 않습니다.

[source,lean]
----
partial def sqrt' (x : Float) : Float :=
  let square (x : Float) : Float := x * x
  let average (x y : Float) : Float := (x + y) / 2
  let improve (guess : Float) : Float := average guess (x / guess)
  let goodEnough (guess : Float) : Bool :=
    Float.abs (square guess - x) < 0.001
  let rec iter (guess : Float) : Float :=
    if goodEnough guess then guess else iter (improve guess)
  iter 1.0
----

이것이 바로 SICP가 이 절 마지막에 도달하는 _블록 구조(block structure)_입니다 — 감싸는 절차 안에 국한되어, 필요한 곳에서만 보이고, 바깥의 동명의 무언가를 자동으로 가리는 내부 정의입니다. 중첩된 ``define`` 대신 ``let``으로 쓴다는 점만 다를 뿐, 아이디어는 똑같습니다.

'''

SICP 1.1절이 보여주는 세 가지 축 — 원시 요소, 조합, 추상화 — 은 Lean에서도 형태만 다를 뿐 그대로 유지됩니다. 다만 Lean은 여기에 타입이라는 네 번째 축을 더하고, "재귀가 정말로 끝나는가"를 언어가 확인하려 든다는 점에서 SICP의 자유분방한 Scheme과 갈라지기 시작합니다. 다음 글에서는 1.2절의 주제 — 재귀 프로세스와 반복 프로세스의 차이, 그리고 그 차이가 Lean의 종료성 증명 요구와 어떻게 부딪히는지 — 를 다룹니다.
