.초보자 이정표
====
*선수지식:* 2.3절의 귀납 타입과 4.1절의 작은 언어 평가기. 의존 타입을 처음 보는 독자도 따라갈 수 있습니다.

*이번 장의 도착점:* 항의 타입을 데이터 구조에 함께 적어, "참을 함수처럼 호출하기" 같은 프로그램을 실행 전에 아예 만들 수 없게 합니다.

*핵심 낱말:* 정적 타입(static type), 인덱스된 타입(indexed type), ``Term``, 타입 안전성(type safety). 먼저 ``badProgram``은 실행되어 실패하고 ``badTerm``은 작성 자체가 거부되는 대비만 확인하세요.
====

link:../4-1-the-metacircular-evaluator/[4.1절]에서 지은 평가기를 돌아봅시다. ``Expr``는 귀납 타입이었지만, 그 안의 어떤 표현식이 "말이 되는지"는 평가기가 실행되는 그 순간까지 알 수 없었습니다 — 참을 함수처럼 적용하면, ``apply``는 그 순간에야 잘못된 값을 만나 실패합니다. 이 시리즈 서문이 내내 던진 질문 — "정적 타입 시스템이 SICP의 원래 논의에 무엇을 더하는가" — 를 여기서 가장 직접적으로 캐물어 볼 수 있습니다. 지금까지의 모든 글은 Lean의 타입 시스템을 이용해 SICP의 코드를 옮겨 적었지만, 정작 SICP가 해석하는 _언어 자체_에는 타입을 준 적이 없습니다. 이 글은 그 마지막 한 걸음을 마저 밟습니다.

== 6.1.1. SICP 쪽에서는 실패가 실행 시점에 도착한다

먼저 4.1절의 정신에 더 가깝게, 아직 타입이 없는 작은 언어로 문제를 재현해봅시다. 불리언과 조건문, 그리고 (아주 단순화한) 함수 적용만 가진 언어입니다.

[source,lean]
----
inductive SExpr where
  | bool (b : Bool)
  | ite (c t e : SExpr)
  | app (f a : SExpr)
deriving Repr

inductive SValue where
  | bool (b : Bool)
  | closure (body : SExpr)
deriving Repr

def sApply : SValue → SValue → Option SValue
  | .closure _, arg => some arg   -- 여기서는 그냥 항등함수인 척한다
  | .bool _, _ => none            -- 함수가 아닌 걸 적용하려는 시도 → 실패

partial def sEval : SExpr → Option SValue
  | .bool b => some (.bool b)
  | .ite c t e => do
      match ← sEval c with
      | .bool true => sEval t
      | .bool false => sEval e
      | .closure _ => none        -- 조건 자리에 함수가 온 경우
  | .app f a => do
      let fv ← sEval f
      let av ← sEval a
      sApply fv av
----

[source,lean]
----
def badProgram : SExpr := .app (.bool true) (.bool false)

#eval sEval badProgram
----

[source]
----
none
----

``badProgram``은 ``SExpr``로서는 완벽하게 유효한 값입니다 — 귀납 타입의 생성자 규칙을 하나도 어기지 않습니다. 잘못된 건 그 _의미_뿐이고, 그 사실은 ``sEval``이 실제로 실행되어 ``.app (.bool true) ...`` 분기를 밟는 순간에야 ``none``으로 드러납니다. SICP도, 그리고 4.1절에서 옮겨 적은 Lean 버전도 이런 동적 오류를 실행 시점에 다룹니다. 다만 4.1절의 ``partial def eval``이 필요한 직접 이유는 잘못된 타입의 항이 존재해서가 아니라, 클로저 본문을 다시 평가하는 일반 평가기가 종료하지 않는 프로그램도 해석해야 하기 때문입니다. 동적 오류와 종료성은 별개의 문제입니다.

== 6.1.2. 항을 그 타입으로 색인하기

이제 같은 언어를 다시 짓되, 이번엔 ``Term``이라는 타입 자체에 "이 항의 타입이 무엇인지"를 미리 새겨 넣습니다. 이런 표현을 _본질적으로 타입이 매겨졌다(intrinsically-typed)_고 부릅니다 — 타입 검사가 항을 짓고 나서 나중에 검사하는 별도의 단계가 아니라, 애초에 그 타입의 항이 아니면 지을 수조차 없다는 뜻입니다.

[source,lean]
----
inductive Ty where
  | bool
  | arrow (a b : Ty)
deriving DecidableEq, Repr

abbrev Ty.denote : Ty → Type
  | .bool => Bool
  | .arrow a b => Ty.denote a → Ty.denote b

inductive Ctx where
  | nil
  | cons (τ : Ty) (Γ : Ctx)

inductive Var : Ctx → Ty → Type where
  | here  : Var (.cons τ Γ) τ
  | there : Var Γ τ → Var (.cons τ' Γ) τ

inductive Term : Ctx → Ty → Type where
  | var : Var Γ τ → Term Γ τ
  | tt  : Term Γ .bool
  | ff  : Term Γ .bool
  | ite : Term Γ .bool → Term Γ τ → Term Γ τ → Term Γ τ
  | lam : Term (.cons a Γ) b → Term Γ (.arrow a b)
  | app : Term Γ (.arrow a b) → Term Γ a → Term Γ b
----

....
 [ Term Γ τ 를 읽는 법 ]

   Term Γ τ  =  "컨텍스트 Γ(주변에 보이는 변수들과 그 타입) 아래에서,
                 타입 τ를 갖는 항"

   예: Term (.cons .bool .nil) .bool
        └─ 변수 하나(타입 bool)가 스코프에 있고,
           결과 타입도 bool인 항의 집합
....

``Var Γ τ``는 3.2절의 프레임 사슬을 흉내 낸 de Bruijn 색인입니다 — ``.here``는 "가장 최근에 스코프에 들어온 변수"를, ``.there``는 "한 프레임 바깥으로 나가서 찾는다"를 뜻합니다. 중요한 건 ``Var``의 두 생성자 모두 _자신이 몇 번째 타입의 변수인지_(``τ``)를 타입 자체에 실어 나른다는 점입니다 — 그래서 ``Term``의 ``.var`` 생성자는 "존재하는 변수 중 아무거나"가 아니라 "정확히 그 타입을 갖는다고 컨텍스트가 약속한 변수"만 받을 수 있습니다.

평가기는 4.1절의 ``eval``과 모양은 같지만, 이번엔 리턴 타입이 ``Option Value``가 아니라 그 항의 타입이 실제로 가리키는 Lean 타입(``τ.denote``) 그 자체입니다.

[source,lean]
----
def Env : Ctx → Type
  | .nil => Unit
  | .cons τ Γ => τ.denote × Env Γ

def Var.eval : Var Γ τ → Env Γ → τ.denote
  | .here, (v, _) => v
  | .there x, (_, env) => x.eval env

def Term.eval : Term Γ τ → Env Γ → τ.denote
  | .var x, env => x.eval env
  | .tt, _ => true
  | .ff, _ => false
  | .ite c t e, env => if c.eval env then t.eval env else e.eval env
  | .lam body, env => fun x => body.eval (x, env)
  | .app f a, env => (f.eval env) (a.eval env)
----

[source,lean]
----
def notFn : Term .nil (.arrow .bool .bool) :=
  .lam (.ite (.var .here) .ff .tt)

#eval notFn.eval () true    -- false
#eval notFn.eval () false   -- true
#eval (Term.app notFn .tt).eval ()   -- false
----

[source]
----
false
true
false
----

== 6.1.3. 스턱 상태를 짓는 문법 자체가 없다

이제 6.1.1절의 ``badProgram``(참을 함수처럼 적용하기)과 똑같은 실수를 이 언어로 저질러 봅시다.

[source,text]
----
def badTerm : Term .nil .bool := .app .tt .ff
----

[source]
----
error: Application type mismatch: The argument
  Term.tt
has type
  Term ?m.4 Ty.bool
but is expected to have type
  Term Ctx.nil (Ty.bool.arrow Ty.bool)
in the application
  Term.tt.app
----

``sEval badProgram``이 실행된 뒤에야 ``none``을 돌려줬던 것과 달리, 이번엔 ``badTerm``이라는 _정의 자체가_ 성립하지 않습니다. ``.app``은 첫 번째 인자로 ``Term Γ (.arrow a b)``를 요구하는데 ``.tt : Term Γ .bool``을 건넸으니, Lean의 커널이 항을 짓는 시점에 바로 거절합니다. ``sEval``의 ``.closure _ => none`` 같은 "스턱을 감지하는 분기"를 이 평가기 어디에서도 찾을 수 없는 이유가 바로 이겁니다 — 그런 분기를 쓸 일이 원천적으로 없습니다. 잘못 타입이 매겨진 항은 ``Term``의 어떤 생성자 조합으로도 조립되지 않기 때문입니다.

[NOTE]
.타입 안전성을 증명하는 두 가지 길
====
전통적인 방식(TAPL류 교재에서 흔히 보는 방식)은 항을 타입 없이 짓고, 별도의 ``typeOf`` 함수와 조작적 의미론(``Step``)을 정의한 뒤, **진행(Progress)**("잘 타입이 매겨진 항은 값이거나 한 걸음 나아갈 수 있다")과 **보존(Preservation)**("한 걸음 나아가도 타입은 그대로다")이라는 두 정리를 각각 증명합니다. 이 방식은 강력하지만 치환 보조정리(substitution lemma)처럼 다루기 번거로운 부분이 따라옵니다.

이 글이 쓴 본질적 타이핑(intrinsic typing)은 다른 길입니다 — ``typeOf``와 ``Step``을 따로 만드는 대신, 애초에 ``Term Γ τ``라는 _타입_에 "이 항은 Γ 아래에서 τ 타입을 갖는다"는 사실 자체를 새겨 넣습니다. 그러면 ``Term.eval``이 (``partial`` 없이) 전역 함수로 정의된다는 사실 그 자체가 곧 타입 안전성입니다 — 스턱 상태로 갈 수 있는 값이 애초에 ``Term Γ τ``의 원소가 아니므로, 커버해야 할 "나쁜 경우"가 없습니다. 대가는 있습니다 — 파서가 만들어내는 타입 없는 구문 트리를 이 표현으로 바꾸려면 별도의 타입 검사·변환 단계(elaboration)가 필요하고, 이 글은 그 단계는 다루지 않습니다.
====

== 6.1.4. 왜 이게 이 시리즈 전체의 답인가

1장부터 이 시리즈가 반복해온 질문은 "SICP의 Scheme이 암묵에 맡기는 것을 Lean의 타입 시스템은 무엇으로 드러내게 만드는가"였습니다. 종료성(1.2절의 ``termination_by``), 효과(3.1절의 ``IO.Ref``), 자료구조의 모양(2장의 귀납 타입)까지는 전부 답했지만, "이 프로그램이 실행 중에 스턱 상태에 빠지지 않는다"는 가장 근본적인 약속만은 4장 내내 답하지 않은 채 남아 있었습니다. 본질적 타이핑은 그 답입니다 — SICP의 ``apply``가 실행 중에 값을 검사해서 걸러내던 일을, Lean의 커널이 항을 짓는 순간에 대신 해줍니다.

== 정리

[cols="1,1,1",options="header"]
|===
|개념 |동적 타입 (SICP/4.1절 스타일) |본질적으로 타입이 매겨진 항 (이 글)
|잘못된 프로그램 |``SExpr``의 유효한 값으로 지어짐 |``Term Γ τ``의 원소로 지어지지 않음
|오류가 드러나는 시점 |``sEval`` 실행 중 (``none``) |``def`` 작성 시점 (컴파일 오류)
|평가기의 반환 타입 |``Option Value`` |``τ.denote`` (그 항의 타입이 가리키는 실제 Lean 타입)
|평가기의 종료성 표시 |``partial``(스턱을 감지하는 분기가 필요) |전역 구조적 재귀(스턱 분기 자체가 불필요)
|안전성 증명 방식 |진행 + 보존(별도 정리 두 개) |``Term.eval``의 전역성 자체가 증명
|===

이 언어는 불리언과 함수뿐이라 계산할 수 있는 게 많지 않습니다. 다음 보너스 글에서는 3.4절의 뮤텍스로 돌아가, 이번엔 반대로 _증명하지 않고 넘어갔던 안전성 주장_ 자체를 형식적으로 증명해봅니다.

=== 직접 해보기

``Ty``에 ``.nat`` 생성자를, ``Term``에 자연수 리터럴(``.lit``)과 덧셈(``.add``)을 추가해보세요. ``Ty.denote``와 ``Term.eval``에 필요한 분기를 채우고 나면, ``(λx:Nat. x + 1)`` 같은 항을 지을 수 있어야 합니다. 그런 다음 ``.add .tt (.lit 1)``처럼 불리언에 숫자를 더하려는 항을 일부러 지어보고, 어떤 오류 메시지가 나오는지 확인해보세요 — 6.1.3절의 ``badTerm``과 같은 종류의 거절인지 살펴보는 게 이 연습문제의 핵심입니다.
