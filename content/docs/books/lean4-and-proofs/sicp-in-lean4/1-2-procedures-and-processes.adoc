[TIP]
.초보자 이정표
====
*선수지식:* 1.1절의 함수 정의와 ``#eval``. 재귀를 아직 몰라도 됩니다.

*이번 장의 도착점:* 같은 계산 결과라도 함수가 만들어 내는 과정은 재귀적일 수도 반복적일 수도 있음을, 팩토리얼 추적으로 구분합니다.

*핵심 낱말:* 절차(procedure), 프로세스(process), 재귀(recursion), 반복(iteration). ``termination_by``는 Lean의 종료성 확인을 위한 표기이므로 처음에는 "인자가 줄어든다"만 확인하세요.
====

link:../1-1-elements-of-programming/[이전 글]에서는 언어의 원재료 — 원시 요소, 조합, 추상화 — 를 다뤘습니다. 재료를 안다고 해서 절차가 실제로 실행될 때 _무엇을 하는지_까지 예측할 수 있는 건 아닙니다. 두 절차가 정확히 같은 수학 함수를 계산하면서도, 프로세스로서는 완전히 다르게 동작하며 서로 다른 시간과 메모리를 쓸 수 있습니다. 이 글은 SICP 2절을 따라 같은 질문을 Lean에서 던져보는데, 여기에 더해지는 새로운 변수는 타입 검사기 자신이 "이 프로세스가 언젠가 끝난다는 걸 확인할 수 있는가"에 대한 의견을 갖고 있다는 점입니다.

절차는 계산의 한 단계가 다음 단계로 어떻게 이어지는지에 대한 _지역적(local)_ 규칙만을 기술합니다. 그 규칙을 반복 적용했을 때 펼쳐지는 _전역적(global)_ 모양 — 팽창했다가 수축하는지, 평평하게 유지되는지, 나무처럼 가지를 치는지 — 은 따로 눈여겨볼 만한 별개의 것입니다. 여기서 SICP가 쓰는 예제들은 일부러 단순한데, 사진에서 테스트 차트가 하는 역할과 같습니다 — 그 자체로 실용적인 프로그램이 아니라, 프로세스의 모양이 뚜렷이 드러날 만큼 단순한 패턴입니다.

'''

== 1.2.1. 선형 재귀와 선형 반복

팩토리얼에는 뚜렷한 재귀적 정의가 있습니다 — stem:[n!]은 stem:[n] 곱하기 stem:[(n-1)!]입니다 — 그리고 이는 더 작은 인자로 자기 자신을 호출하는 절차로 곧바로 옮겨집니다.

[source,lean]
----
def factorial : Nat → Nat
  | 0 => 1
  | n + 1 => (n + 1) * factorial n

#eval factorial 6
-- 720
----

각 호출의 인자가 바로 앞 호출보다 구조적으로 더 작기 때문에 — ``n + 1``이 ``factorial n``을 호출합니다 — Lean의 종료성 검사기는 ``partial`` 키워드 없이도 이 정의를 자동으로 받아들입니다. 이 점은 눈여겨볼 만합니다 — 이 시리즈에서 처음으로, 타입 검사기가 SICP의 치환 모델 추적이 비형식적으로만 보여주던 것 — 미뤄진 곱셈의 사슬이 유한하다는 것 — 을 독립적으로 확인해주는 절차입니다.

이를 손으로 추적해보면 _팽창 후 수축_하는 모양이 드러납니다 — 기저 사례에 도달할 때까지 미뤄진 곱셈의 사슬이 쌓이다가, 각 곱셈이 실제로 수행되면서 그 사슬이 다시 접혀 들어갑니다. 이런 모양의 프로세스를 _재귀적 프로세스(recursive process)_라고 부르는데, 여기서 사슬이 stem:[n]에 정비례해서 자라나므로 특히 _선형 재귀 프로세스(linear recursive process)_입니다.

[source,text]
----
[선형 재귀 프로세스: factorial 6]         [선형 반복 프로세스: factIter 1 1 6]
 (미뤄진 연산의 사슬이 팽창 후 수축)        (고정된 상태 변수 갱신, 공간 O(1))

 (factorial 6)                           (factIter  1  1  6)
 6 * (factorial 5)                       (factIter  1  2  6)
 6 * (5 * (factorial 4))                 (factIter  2  3  6)
 6 * (5 * (4 * (factorial 3)))           (factIter  6  4  6)
 6 * (5 * (4 * (3 * (factorial 2))))     (factIter 24  5  6)
 6 * (5 * (4 * (3 * (2 * 1))))           (factIter 120 6  6)
 6 * (5 * (4 * (3 * 2)))                 (factIter 720 7  6)  -- 종료!
 6 * (5 * (4 * 6))                       => 720
 6 * (5 * 24)
 6 * 120
 => 720
    ▲                                         ▲
    │ 스택 깊이 O(n)                           │ 스택 깊이 O(1)
----

같은 함수를 계산하는 두 번째 방법이 있는데, 이번에는 어떤 사슬도 전혀 쌓지 않습니다 — 누적곱과 카운터를 유지하면서, 카운터가 stem:[n]을 넘을 때까지 매 단계마다 둘을 동시에 갱신합니다.

[source,lean]
----
partial def factIter (product counter maxCount : Nat) : Nat :=
  if counter > maxCount then product
  else factIter (counter * product) (counter + 1) maxCount

def factorialIter (n : Nat) : Nat := factIter 1 1 n

#eval factorialIter 6
-- 720
----

여기서는 ``counter``가 0을 향해 내려가는 대신 ``maxCount``를 향해 _올라가므로_, Lean은 구조적으로 감소하는 인자를 찾지 못하고 정의를 ``partial``로 표시해야 합니다(이전 글에서 ``sqrtIter``에 썼던 것과 같은 탈출구입니다). 이것이 정확히 SICP가 _반복적(iterative)_이라고 부르는 프로세스입니다 — 어느 시점에서든 중요한 상태 전체가 ``product``, ``counter``, ``maxCount``라는 세 개의 고정된 변수에 담기고, 그와 함께 자라나는 숨은 미뤄진 작업의 사슬이 없습니다.

[IMPORTANT]
.``partial``은 프로세스가 아니라 절차에 대한 신호입니다
====
SICP가 강조하는 결정적인 구분은 "재귀적"과 "반복적"이 _절차(procedure)_가 아니라 _프로세스(process)_를 기술한다는 점입니다 — ``factIter``는 구문적으로는 재귀적 절차입니다(자기 정의 안에서 자기 이름을 언급합니다), 하지만 그것이 만들어내는 프로세스는 반복적입니다. Lean의 ``partial`` 키워드는 절차에 대한 구문적 신호이고(종료성 검사기가 증명을 포기했다는 뜻), 이걸 프로세스 자체가 어딘가 덜 정돈됐다는 의미로 착각하기 쉽습니다. SICP가 짚는 핵심은 이 둘이 서로 독립적이라는 것입니다.
====

이를 직접 확인해볼 수 있는 방법이 두 가지 있습니다. 첫째, ``counter``가 올라가는 대신 ``n``이 내려가도록 상태를 다시 짜면 — 잠시 뒤 1.2.2절의 ``fibIter``에서 다시 보게 될 방향 전환입니다 — Lean은 ``partial`` 없이도 구조적 재귀로 받아들입니다.

[source,lean]
----
def factIterDown : Nat → Nat → Nat
  | product, 0 => product
  | product, n + 1 => factIterDown (product * (n + 1)) n

def factorialIterDown (n : Nat) : Nat := factIterDown 1 n

#eval factorialIterDown 6
-- 720
----

둘째, 원래 방향(카운트업)을 그대로 유지하면서, ``maxCount + 1 - counter``가 매 호출마다 줄어든다는 것을 ``termination_by``로 직접 알려줄 수도 있습니다.

[source,lean]
----
def factIterMeasured (product counter maxCount : Nat) : Nat :=
  if counter > maxCount then product
  else factIterMeasured (counter * product) (counter + 1) maxCount
termination_by maxCount + 1 - counter
----

두 방식 모두 ``partial``을 떼어내지만, 만들어내는 프로세스의 모양(반복적, stem:[\Theta(1)] 공간)은 전혀 달라지지 않습니다 — 정확히 SICP가 짚는 지점입니다. (Lean/Mathlib 버전에 따라 ``termination_by`` 뒤에 ``decreasing_by omega`` 같은 보조 증명이 추가로 필요할 수 있습니다. ``omega``는 임의의 정성적 통찰 없이도 ``maxCount + 1 - counter``처럼 자연수·정수에 대한 선형 부등식(linear arithmetic)만으로 이루어진 감소 조건을 기계적으로 검증하는 결정 절차(decision procedure)입니다 — "이 측정값이 매 호출마다 실제로 줄어드는가"라는 산술적 사실을 사람이 증명할 필요 없이 ``omega``가 대신 풀어줍니다.)

*연습문제 1.9 (Lean 버전)*: 아래 두 절차는 각각 ``inc``(1 증가)와 ``dec``(1 감소)만으로 두 양의 정수를 더하는 방법을 정의합니다. 각각이 ``4 + 5``를 계산할 때 어떤 모양의 프로세스를 만드는지 손으로 추적해 보고, 재귀적인지 반복적인지 판단해 보세요.

[source,lean]
----
def incNat (n : Nat) : Nat := n + 1
def decNat (n : Nat) : Nat := n - 1

def addA : Nat → Nat → Nat
  | 0, b => b
  | a + 1, b => incNat (addA a b)

partial def addB (a b : Nat) : Nat :=
  if a = 0 then b else addB (decNat a) (incNat b)
----

``addA``는 미뤄진 ``incNat`` 호출의 사슬을 쌓으므로 선형 재귀 프로세스이고, Lean도 이를 구조적 재귀로 자동 인정합니다. ``addB``는 ``a``가 0에 도달할 때까지 상태 두 개(``a``, ``b``)만 유지하므로 선형 반복 프로세스이지만, ``a``가 구조적으로 감소하는데도 ``decNat``을 거쳐가는 형태라 Lean의 기본 종료성 검사기는 이를 곧바로 받아들이지 못해 ``partial``이 필요합니다.

'''

== 1.2.2. 트리 재귀

피보나치 수열은 진짜로 다른 모양의 프로세스를 보여줍니다. 각 피보나치 수는 그 앞의 두 수로 정의되므로, 정의를 그대로 옮기면 한 단계마다 자기 자신을 _두 번_ 호출하게 됩니다.

[source,lean]
----
def fib : Nat → Nat
  | 0 => 0
  | 1 => 1
  | n + 2 => fib (n + 1) + fib n

#eval fib 10
-- 55
----

두 재귀 호출 모두 구조적으로 더 작은 인자에 대한 것이므로, 이번에도 Lean은 ``partial`` 없이 받아들입니다. 하지만 호출을 추적해보면 사슬이 아니라 _트리_가 드러납니다 — ``fib 5``는 ``fib 4``와 ``fib 3``을 호출하고, ``fib 4``는 ``fib 3``과 ``fib 2``를 호출하며, ``fib 3``에 대한 서브트리 전체가 이전 계산에 대한 기억 없이 독립적으로 두 번 계산됩니다. 이 트리의 잎(leaf) 개수 — 곧 단계 수 — 는 stem:[n]에 대해 지수적으로 자라나지만, 어느 순간에 필요한 공간(현재 가지가 얼마나 깊이 내려갔는지)은 선형으로만 자랍니다.

[source,text]
----
                                  fib 5
                              ┌─────┴─────┐
                            fib 4       fib 3 (중복 계산!)
                          ┌───┴───┐   ┌───┴───┐
                        fib 3   fib 2 fib 2   fib 1
                        ┌─┴─┐   ┌─┴─┐ ┌─┴─┐     │
                      fib 2 fib 1 ... ... ...   1
                      ┌─┴─┐   │
                    fib 1 fib 0 1
                      │     │
                      1     0
----

같은 수는 가지를 치는 대신 값의 쌍을 앞으로 밀고 나가는 반복적 프로세스로도 만들어낼 수 있습니다.

[source,lean]
----
def fibIter : Nat → Nat → Nat → Nat
  | a, _, 0 => a
  | a, b, n + 1 => fibIter b (a + b) n

def fib' (n : Nat) : Nat := fibIter 0 1 n

#eval fib' 10
-- 55
----

``fibIter``는 마지막 인자에 대해 패턴 매칭하는데, 이 인자는 매 호출마다 구조적으로 실제로 감소하므로 Lean은 이번에도 ``partial`` 없이 받아들입니다 — 카운트업 방향이 자동 검사기를 방해했던 앞 절의 ``factIter``와 좋은 대조를 이룹니다. 여기서 얻는 교훈은 일반화됩니다 — Lean의 종료성 검사기가 정의를 스스로 꿰뚫어 볼 수 있는지는 흔히 프로세스가 "진짜로" 반복적인지가 아니라, 상태 변수가 어느 방향으로 움직이는지에 달려 있습니다.

=== 예제: 거스름돈의 경우의 수

거스름돈의 경우의 수를 세는 것은 트리 재귀의 두 번째, 그리고 덜 명백한 예입니다 — 금액 stem:[a]를 stem:[n]종류의 동전으로 바꾸는 방법의 수는 "첫 번째 종류의 동전을 쓰지 않는 방법들"과 "쓰는 방법들"로 나뉘고, 세 가지 퇴화 기저 사례(금액이 정확히 0, 금액이 음수, 남은 동전 종류가 없음)를 가집니다.

계산 도중 금액이 정말로 음수가 될 수 있으므로(그렇게 해서 "0보다 작다"는 기저 사례가 트리거됩니다), 이는 Lean의 ``Nat``(뺄셈을 음수로 내려가지 않고 0에서 잘라내는 타입)를 쓰면 알고리즘이 조용히 망가지는 경우입니다. 대신 금액에는 ``Int``를 씁니다.

[source,lean]
----
def firstDenomination : Nat → Int
  | 1 => 1
  | 2 => 5
  | 3 => 10
  | 4 => 25
  | _ => 50

partial def cc (amount : Int) (kindsOfCoins : Nat) : Nat :=
  if amount == 0 then 1
  else if amount < 0 || kindsOfCoins == 0 then 0
  else cc amount (kindsOfCoins - 1)
       + cc (amount - firstDenomination kindsOfCoins) kindsOfCoins

def countChange (amount : Int) : Nat := cc amount 5

#eval countChange 100
-- 292
----

두 재귀 호출이 서로 다른 것을 줄입니다 — 하나는 ``kindsOfCoins``를, 다른 하나는 ``amount``를 줄입니다 — 그래서 Lean이 붙잡을 수 있는 단일한 구조적 감소 인자가 없고, 여기서는 ``partial``이 정직한 선택입니다. 이는 원본의 ``count-change``를 그대로 반영합니다 — 올바르게 서술하기는 쉽지만 실제로 실행하기에는 뼈아플 만큼 중복이 많은 트리 재귀 프로세스입니다.

'''

== 1.2.3. 증가 차수

구현의 세부 사항에 빠지지 않고 프로세스를 비교하기 위해, SICP는 _증가 차수(order of growth)_를 도입합니다 — 크기 stem:[n]의 문제에 대해 어떤 자원(단계 수, 메모리)이 stem:[R(n)]만큼 필요한 프로세스가 있을 때, 충분히 큰 모든 stem:[n]에 대해 stem:[R(n)]이 어떤 상수 stem:[k_1, k_2]에 대해 stem:[k_1 f(n)]과 stem:[k_2 f(n)] 사이에 낀다면 stem:[R(n) = \Theta(f(n))]이라고 씁니다. 이는 일부러 거친 도구입니다 — stem:[n^2] 단계와 stem:[1000n^2] 단계를 구분하지 못합니다 — 하지만 문제가 커질 때 프로세스의 자원 사용이 어떻게 변할지 예측하는 데는 정확히 딱 필요한 만큼만 정밀합니다.

지금까지 만든 프로세스들만 해도 유용한 범위를 아우릅니다 — ``factorial``의 선형 재귀는 단계와 공간 모두 stem:[\Theta(n)]이고, ``factIter``의 선형 반복은 단계는 stem:[\Theta(n)]이지만 공간은 stem:[\Theta(1)]뿐이며, ``fib``의 트리 재귀는 단계 수는 stem:[\Theta(\varphi^n)](stem:[\varphi]는 황금비)이지만 공간은 stem:[\Theta(n)]뿐입니다. 어느 순간이든 트리의 현재 가지만 기억하면 되기 때문입니다.

'''

== 1.2.4. 거듭제곱

거듭제곱은 재귀 규칙을 조금만 바꿔도 프로세스 전체가 선형에서 로그로 옮겨갈 수 있음을 보여주는 압축된 사례 연구를 제공합니다. 뻔한 정의인 stem:[b^n = b \cdot b^{n-1}]은 선형 재귀를 만들어냅니다.

[source,lean]
----
def expt : Nat → Nat → Nat
  | _, 0 => 1
  | b, n + 1 => b * expt b n

#eval expt 2 10
-- 1024
----

하지만 stem:[b^n]은 _반복 제곱(successive squaring)_으로도 계산할 수 있습니다 — stem:[n]이 짝수면 stem:[b^n = (b^{n/2})^2]이고, stem:[n]이 홀수면 stem:[b^n = b \cdot b^{n-1}]입니다. 각 재귀 호출이 지수를 최소 절반으로 줄이므로, 필요한 곱셈 횟수는 stem:[n]이 아니라 stem:[\log n]에 비례해서만 자랍니다 — stem:[n = 1000]이라면 1000번이 아니라 대략 14번의 곱셈이면 됩니다.

[source,text]
----
  [b¹⁰ 계산: 이진 분할 파이프라인]
  
   b¹⁰ = (b⁵)²              (10은 짝수: n / 2)
           │
           ▼
         b⁵ = b * (b⁴)      (5는 홀수: n - 1)
                    │
                    ▼
                  b⁴ = (b²)² (4는 짝수: n / 2)
                         │
                         ▼
                       b² = (b¹)² (2는 짝수: n / 2)
                              │
                              ▼
                            b¹ = b * b⁰ (1은 홀수: n - 1)
                                       │
                                       ▼
                                     b⁰ = 1  (기저 사례)

  총 10번의 순차 곱셈 대신 단 5번의 곱셈(재귀 단계 6회)으로 완료!
----

[source,lean]
----
def square (x : Nat) : Nat := x * x

partial def fastExpt (b n : Nat) : Nat :=
  if n = 0 then 1
  else if n % 2 = 0 then square (fastExpt b (n / 2))
  else b * fastExpt b (n - 1)

#eval fastExpt 2 10
-- 1024
----

``n / 2``와 ``n - 1`` 모두 ``n > 0``일 때 ``n``을 줄이므로, ``termination_by n``이라는 하나의 측정값으로 두 분기를 동시에 커버해 검사기가 직접 종료성을 증명하게 할 수 있습니다.

[source,lean]
----
def fastExpt' (b n : Nat) : Nat :=
  if n = 0 then 1
  else if n % 2 = 0 then square (fastExpt' b (n / 2))
  else b * fastExpt' b (n - 1)
termination_by n
----

(Lean/Mathlib 버전에 따라 ``termination_by n`` 뒤에 ``decreasing_by omega`` 같은 보조 증명이 추가로 필요할 수 있습니다.)

``n / 2``는 (successor 패턴 위의 ``n - 1``과 달리) Lean의 구조적 재귀가 자동으로 인식하는 패턴이 아니므로, 이 정의가 기술하는 프로세스가 선형 버전보다 극적으로 효율적임에도 ``partial``이 필요합니다. _프로세스_의 효율성과 _종료성_의 증명 가능성은 여기서도 서로 다른 두 축입니다 — 빠른 버전은 우연히 한쪽에서는 더 좋은 점수를, 다른 쪽에서는(기본적으로는) 더 나쁜 점수를 받습니다.

'''

== 1.2.5. 최대공약수

유클리드 알고리즘은 두 정수의 최대공약수를, 두 번째 원소가 0에 도달할 때까지 stem:[(a, b)] 쌍을 stem:[(b, a \bmod b)]로 계속 바꿔가며 계산합니다 — 그 시점에서 첫 번째 원소가 답입니다. 지금도 쓰이는 알고리즘 중 가장 오래된 축에 속한다고 흔히 인용됩니다.

[source,lean]
----
partial def gcd (a b : Nat) : Nat :=
  if b = 0 then a else gcd b (a % b)

#eval gcd 206 40
-- 2
----

Lean 표준 라이브러리에는 이미 ``Nat.gcd``가 있는데, 같은 방식으로 정의되어 있고 ``b > 0``일 때 ``a % b < b``라는 사실을 이용해 종료성이 증명되어 있습니다 — 구조적 재귀가 아니라 진짜 정초 재귀(well-founded recursion)이며, 이런 알고리즘이 ``partial`` 키워드를 완전히 떼어낼 수 있게 해주는 ``termination_by``/``decreasing_by`` 증명의 좋은 실제 사례입니다.

'''

== 1.2.6. 예제: 소수 판정

소수를 판정하는 직접적인 방법은 1보다 큰 가장 작은 약수를 찾는 것인데, 후보 약수의 제곱이 stem:[n]을 넘는 순간 멈춥니다(stem:[n]이 stem:[\sqrt{n}]까지 약수를 갖지 않는다면, 아예 약수가 없는 것입니다).

[source,lean]
----
def divides (a b : Nat) : Bool := b % a == 0

partial def findDivisor (n testDivisor : Nat) : Nat :=
  if testDivisor * testDivisor > n then n
  else if divides testDivisor n then testDivisor
  else findDivisor n (testDivisor + 1)

def smallestDivisor (n : Nat) : Nat := findDivisor n 2

def isPrime (n : Nat) : Bool := n == smallestDivisor n

#eval isPrime 97
-- true
----

이는 stem:[\Theta(\sqrt{n})] 단계로 동작합니다. 완전히 다른, 훨씬 빠른 접근은 페르마의 소정리에서 나옵니다 — stem:[n]이 소수라면 모든 stem:[a < n]에 대해 stem:[a^n \bmod n = a]입니다. 무작위로 고른 몇 개의 stem:[a]에 대해 이를 확인하면 _아마도_ 맞는 테스트를 얻는데(카마이클 수라고 불리는 일부 합성수는 모든 stem:[a]에 대해 이 테스트를 속입니다), 검사 자체는 ``fastExpt``와 같은 반복 제곱 기법을 통해 stem:[\Theta(\log n)]으로 동작합니다.

[source,lean]
----
partial def expmod (base exp m : Nat) : Nat :=
  if exp = 0 then 1
  else if exp % 2 = 0 then
    (expmod base (exp / 2) m) ^ 2 % m
  else
    (base * expmod base (exp - 1) m) % m
----

``fastExpt``와 정확히 같은 이유로, ``exp``를 측정값으로 주면 ``partial``을 뗄 수 있습니다.

[source,lean]
----
def expmod' (base exp m : Nat) : Nat :=
  if exp = 0 then 1
  else if exp % 2 = 0 then
    (expmod' base (exp / 2) m) ^ 2 % m
  else
    (base * expmod' base (exp - 1) m) % m
termination_by exp
----

Scheme의 ``fermat-test``는 원시 절차 ``random``을 별생각 없이 그대로 씁니다. Scheme은 무작위성(과 다른 부수 효과들)을 주변 환경의 일부로 취급하기 때문입니다. Lean의 타입 시스템은 "실행할 때마다 다른 값을 낸다"는 효과가 순수한 ``Nat → Bool`` 시그니처 안에 숨어드는 것을 허용하지 않습니다 — 무작위성은 ``IO``를 통해 타입에 드러나야 하는데, 이는 link:../functional-programming-in-lean/[Functional Programming in Lean 시리즈]에서 봤던 ``IO`` 액션과 정확히 같은 움직임입니다.

[source,lean]
----
def fermatTest (n : Nat) : IO Bool := do
  let a ← IO.rand 1 (n - 1)
  pure (expmod a n n == a)

partial def fastPrime (n times : Nat) : IO Bool := do
  if times = 0 then pure true
  else if ← fermatTest n then fastPrime n (times - 1)
  else pure false

#eval fastPrime 97 10
----

타입을 눈여겨보세요 — ``smallestDivisor`` 기반의 ``isPrime``은 ``Nat → Bool``이며, 어떤 단서도 없이 이전 글의 치환 모델로 추론할 수 있는 순수 함수입니다. ``fastPrime``은 ``Nat → Nat → IO Bool``인데, 이 ``IO``는 이 절차의 답이 실행할 때마다 달라질 수 있다는 것을 Lean이 정직하게 드러내는 방식이며, 이것이 바로 페르마 테스트를 애초에 _확률적_으로만 만드는 성질입니다. 타입 시스템은 사실상 SICP가 글로 그리는 것과 같은 구분(보장된 답 대 아마도 맞는 답)이 함수 시그니처에서 눈에 보이는 차이로 드러나도록 강제하고 있는 셈입니다.

'''

== 정리

|===
|SICP 개념 |프로세스 모양 |Lean 예시 |Lean에서 ``partial``이 필요한 이유
|선형 재귀 |팽창 후 수축, stem:[\Theta(n)] 공간 |``factorial`` |불필요 — ``n → n-1``이 구조적
|선형 반복 |상태 변수 고정, stem:[\Theta(1)] 공간 |``factIter`` |필요 — ``counter``가 위로 셈
|트리 재귀 |가지치는 트리, stem:[\Theta(\varphi^n)] 단계 |``fib``, ``countChange`` |``fib``는 불필요, ``countChange``는 필요(두 인자가 각각 감소)
|로그 프로세스 |반복 제곱 |``fastExpt``, ``expmod`` |필요 — ``n / 2``는 구조적 패턴이 아님
|정초 재귀 |감소하는 측정값으로 증명 |``Nat.gcd`` |표준 라이브러리에서 이미 증명됨
|확률적 프로세스 |실행마다 다른 결과 |``fastPrime`` |``partial`` + ``IO``, 타입 자체가 비결정성을 드러냄
|===

이 절에서 SICP가 강조하는 재귀 프로세스와 반복 프로세스의 구분은 Lean에서 한 겹 더 날카로워집니다 — 프로세스가 반복적인지 아닌지는 Lean의 ``partial`` 키워드가 붙는지와 별개의 질문이지만, 실제로 어떤 방향으로 상태를 셈하느냐에 따라 자동 종료성 검사기가 통과시켜 주는지가 갈립니다. 다음 글에서는 1.3절 — 절차를 값으로 다루는 고차 절차(higher-order procedures)와, ``lambda``/익명 함수, ``let``이 Lean의 ``fun``과 어떻게 맞물리는지 — 를 다룹니다.
