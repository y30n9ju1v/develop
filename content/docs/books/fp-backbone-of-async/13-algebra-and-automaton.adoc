== 인트로: 12장이 남겨둔 질문

12장은 "우리의 여정은 여기서 끝나지만, 여러분의 코드는 이제 막 시작되었습니다"라는 말로 책을 마무리했습니다. 그런데 정직하게 말하면, 그 문장 뒤에는 아직 답하지 않은 질문이 하나 숨어 있습니다.

이 책은 3장부터 줄곧 async/await를 **대수(algebra)**로 읽어왔습니다. ``Functor``의 ``map``, ``Monad``의 ``flatMap``, ``Applicative``의 ``gather`` — 전부 "이 연산들이 결합법칙과 항등원을 만족하는가"라는 대수적 질문에 대한 답이었습니다. 그런데 12장의 Continuation 절에서 잠깐, ``async/await``가 실제로는 제너레이터가 멈췄다가 재개되는 **상태 기계**라는 걸 봤습니다. 이건 지금까지와는 완전히 다른 질문입니다 — "이 실행이 실제로 어떻게 한 단계씩 진행되는가."

이 마지막 장은 이 두 질문이 서로 경쟁하는 이론이 아니라, **정확히 같은 현상을 설명하는 두 개의 렌즈**라는 걸 보여줍니다.

'''

== 1. 두 가지 질문, 두 가지 수학

같은 코루틴 하나를 두고 완전히 다른 두 가지 질문을 던질 수 있습니다.

* *대수적 질문*: "``await``를 아무리 복잡하게 체이닝해도 결과가 예측 가능한가?" 이 질문의 답은 ``flatMap``이 결합법칙(``m.flat_map(f).flat_map(g) == m.flat_map(lambda x: f(x).flat_map(g))``)과 항등원(``of(x).flat_map(f) == f(x)``)을 만족한다는 **대수적 증명**입니다. 이게 지켜지면 체이닝 순서를 어떻게 괄호로 묶든 결과는 항상 같습니다.
* *오토마타적 질문*: "이 코루틴은 지금 정확히 어떤 상태에 있고, 다음 값을 받으면 어디로 가는가?" 이 질문의 답은 대수가 아니라 **실행 모델**입니다 — 코루틴은 ``(현재 상태, 입력) → (다음 상태, 출력)``이라는 결정론적 규칙을 따르는 오토마타입니다.

두 질문 모두 타당하고, 둘 다 같은 코루틴 객체 하나를 설명합니다. 다만 하나는 "합성이 안전한가"를, 다른 하나는 "실행이 어떻게 진행되는가"를 답할 뿐입니다.

== 2. 코루틴을 오토마타로 다시 쓰기

12장이 보여준 것처럼, 파이썬의 코루틴은 제너레이터 위에 구축됩니다. 이걸 오토마타의 언어로 다시 쓰면 대응 관계가 정확히 드러납니다.

[source,python]
----
async def fetch_user_flow(user_id):
    user = await fetch_user(user_id)       # <1>
    posts = await fetch_posts(user["id"])  # <2>
    return summarize(user, posts)          # <3>
----
<1> 상태 A: ``user`` 대기
<2> 상태 B: ``posts`` 대기
<3> 상태 C: 완료

이 함수 하나가 실제로는 세 개의 상태를 가진 오토마타입니다.

[cols="1,2,2"]
|===
|상태 |의미 |전이 트리거

|상태 A |``fetch_user``의 결과를 기다리는 중 |이벤트 루프가 ``send(user_result)``를 호출
|상태 B |``fetch_posts``의 결과를 기다리는 중 |이벤트 루프가 ``send(posts_result)``를 호출
|상태 C (종료) |``summarize``를 계산하고 값을 반환 |``StopIteration(return_value)``로 오토마타가 종료
|===

이벤트 루프가 하는 일이 정확히 **전이 함수를 반복 호출하는 것**입니다 — ``coro.send(value)``는 "지금 상태에서 이 입력을 받으면 다음 상태로 가라"는 오토마타 전이 그 자체입니다. 예외가 발생하면 ``coro.throw(exc)``가 같은 역할을 하는 또 다른 전이 함수가 됩니다. 12장이 "Continuation은 멈춘 지점부터 다시 시작하는 능력"이라고 표현했던 게, 오토마타 언어로는 "현재 상태를 저장해뒀다가, 다음 입력이 오면 그 상태에서 전이를 재개한다"는 뜻입니다.

이 오토마타의 상태 공간이 왜 딱 그 코루틴 함수 하나로 한정되는지도 이제 정확히 설명할 수 있습니다 — 12장에서 짚었듯 이건 얕은/스택리스 컨티뉴에이션이기 때문입니다. 상태가 "그 프레임 하나"에 갇혀 있으니, 오토마타의 상태 집합도 딱 그만큼만 존재합니다. 만약 파이썬이 일급/한정 컨티뉴에이션을 지원했다면, 상태 공간은 코루틴 하나가 아니라 호출 스택 전체에 걸쳐 정의됐을 것이고, 오토마타는 지금보다 훨씬 복잡해졌을 겁니다.

== 3. 왜 두 렌즈 다 필요한가

오토마타 렌즈만으로는 부족한 지점이 있습니다. 위 표는 "이 코루틴 하나가 어떻게 진행되는가"는 정확히 설명하지만, "이 코루틴을 다른 코루틴과 안전하게 이어붙여도 되는가"는 답해주지 못합니다. 예를 들어 ``fetch_user_flow``의 결과를 다른 비동기 함수에 다시 넘겨 체이닝했을 때, 그 결과가 "어떤 순서로 묶어도 항상 같다"는 보장은 오토마타의 상태 전이 표가 아니라 **Monad 법칙**이 해줍니다.

반대로 대수 렌즈만으로는 "이벤트 루프 위에서 실제로 몇 개의 코루틴이 어떻게 인터리빙되는가"를 설명하지 못합니다. ``flatMap``이 결합법칙을 만족한다는 사실은 실행 순서가 안전하다는 걸 보장하지만, 그 실행이 실제로 언제 어떤 스레드/이벤트 루프 tick에서 일어나는지는 오토마타의 몫입니다.

이걸 이 책의 흐름 위에 겹쳐 보면 이렇게 정리됩니다.

* *3~7장 (Functor/Monad/Applicative/Observable)* → "무엇을 합성해도 안전한가"에 대한 **대수**
* *12장 (Continuation)* → "그 합성이 실제로 어떻게 한 단계씩 실행되는가"에 대한 **오토마타**

둘 중 하나만 있었다면 이 책은 반쪽짜리였을 것입니다 — 대수만 있었다면 "안전하다"는 건 알아도 "무슨 일이 일어나는지"는 몰랐을 것이고, 오토마타만 있었다면 "무슨 일이 일어나는지"는 알아도 그걸 마음 놓고 조합해도 되는지는 몰랐을 것입니다.

== 4. TaskGroup: 여러 오토마타를 하나로 묶는 곱 구조

이 이중 렌즈가 가장 선명하게 드러나는 지점이 6장에서 다룬 구조적 동시성, ``asyncio.TaskGroup``입니다.

[source,python]
----
async def fetch_dashboard(user_id):
    async with asyncio.TaskGroup() as tg:
        user_task = tg.create_task(fetch_user(user_id))
        posts_task = tg.create_task(fetch_posts(user_id))
        profile_task = tg.create_task(fetch_profile(user_id))
    # 여기 도달하면 세 작업 모두 완료(또는 취소)된 상태
    return combine(user_task.result(), posts_task.result(), profile_task.result())
----

각 자식 태스크는 그 자체로 하나의 오토마타이고, 상태는 ``Pending | Done | Failed`` 중 하나입니다. ``TaskGroup``이 관리하는 건 이 세 개의 개별 오토마타가 아니라, **세 상태의 조합 하나**입니다.

[source,python]
----
(Pending, Pending, Pending)  # 시작
(Done,    Pending, Pending)  # user_task 완료
(Done,    Done,    Pending)  # posts_task도 완료
(Done,    Done,    Done)     # 전체 완료 -> async with 블록 탈출
----

이게 바로 **곱 오토마타(product automaton)**입니다 — 여러 개의 독립적인 상태 기계를, 각 상태의 튜플을 하나의 새로운 상태로 갖는 더 큰 오토마타로 합친 것입니다. 구조적 동시성이 강제하는 규칙("부모 스코프는 모든 자식이 끝나야만 빠져나갈 수 있다")은 정확히 이 곱 오토마타에 건 **전이 제약**입니다 — ``(Done, Done, Done)`` 이외의 상태에서는 ``async with`` 블록을 빠져나가는 전이가 아예 존재하지 않습니다.

그리고 이 곱 구조를 대수적으로 표현한 것이 바로 7장의 ``Applicative``와 ``gather``입니다. ``gather(fetch_user(...), fetch_posts(...), fetch_profile(...))``가 "독립적인 값들을 조합한다"고 말할 때, 그 조합이 실제로 실행되는 방식이 위의 곱 오토마타이고, 그 조합이 항상 안전하다고 보장하는 게 Applicative 법칙입니다. 다시 한번, 같은 현상의 두 얼굴입니다.

== 13장 요약: 이 책이 진짜로 끝나는 곳

* 비동기 프로그래밍은 **대수**(무엇을 합성해도 안전한가)와 **오토마타**(그 합성이 실제로 어떻게 실행되는가)라는 두 개의 수학으로 동시에 설명됩니다. 어느 하나가 다른 하나를 대체하지 않습니다.
* 코루틴은 ``(상태, 입력) → (다음 상태, 출력)``을 따르는 결정론적 오토마타이고, ``send()``/``throw()``가 그 전이 함수입니다.
* ``TaskGroup``은 자식 태스크들의 상태를 튜플로 묶은 **곱 오토마타**이고, 구조적 동시성은 그 위에 건 전이 제약이며, 7장의 Applicative/``gather``는 이 곱 구조의 대수적 표현입니다.

이제 여러분은 코드를 두 가지 언어로 동시에 읽을 수 있습니다 — 이 합성이 왜 안전한지는 대수로, 이 실행이 실제로 무엇을 하고 있는지는 오토마타로. 이 두 렌즈를 겹쳐 볼 수 있을 때, 비로소 이 책이 처음부터 하려던 이야기가 끝납니다.

이제 여러분의 손에는 강력한 무기가 들려 있습니다. 복잡성이라는 파도는 여전히 거세지만, 이제 여러분은 그 파도에 휩쓸리는 대신 **체계적으로 대응할 수 있는 기술**을 가졌습니다.

코드가 복잡해질 때마다 기억하세요.

*나누고(Divide), 정복하고(Conquer), 합성하라(Compose).*

우리의 여정은 여기서 끝나지만, 여러분의 코드는 이제 막 시작되었습니다.
부디 여러분의 코드가 어제보다 조금 더 **순수(Pure)**하고, **합성 가능(Composable)**하기를 바랍니다.

감사합니다.

[source,python]
----
# 에필로그: 멈추지 않는 성장
# (이것은 의사 코드입니다 - 개념적 표현)

from typing import TypeVar

T = TypeVar('T')

class Developer: pass
class Wisdom: pass

def developer_journey(you: Developer) -> Future[Wisdom]:
    """
    당신의 성장은 멈추지 않는 비동기 여정입니다.
    """
    return (
        read_book(you)
        .flat_map(practice_coding)
        .flat_map(share_knowledge)
        .map(lambda experience: Wisdom(experience))
    )

# 이 Future는 영원히 완료되지 않습니다.
# 배움에는 끝이 없으니까요.
