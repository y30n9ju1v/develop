'''

== 타입만으로는 충분하지 않다

link:../09-type-systems-and-fp/[9장]에서 우리는 타입 시스템으로 수많은 버그를 컴파일 타임에 잡아냈습니다. ``User ++|++ None``으로 None 체크를 강제했고, ``Result++[++T, E++]++``로 에러 처리를 명시적으로 만들었고, Literal 타입으로 잘못된 상태를 표현 불가능하게 만들었습니다. 타입 시스템은 **구조적 정확성(structural correctness)**을 보장합니다.

하지만 타입 시스템은 **논리적 정확성(logical correctness)**을 보장하지 못합니다. link:../09-type-systems-and-fp/[9장]에서 봤던 이 예제를 기억하시나요?

[source,python]
----
def calculate_discount(price: float, rate: float) -> float:
    # 타입은 맞지만 로직이 틀림
    return price * rate  # ❌ price * (1 - rate)가 정답
----

mypy는 통과하지만, 프로그램은 틀린 값을 반환합니다. 타입 시스템은 "float를 받아서 float를 반환한다"는 것만 확인할 뿐, "할인 로직이 올바른가?"는 검증하지 못합니다.

이제 비동기 코드를 생각해봅시다. 상황은 더 복잡해집니다.

[source,python]
----
async def transfer_money(
    from_account: str,
    to_account: str,
    amount: float
) -> Result[None, str]:
    """계좌 이체 (타입은 완벽하지만 버그가 있음)"""
    balance = await get_balance(from_account)

    # ❌ 경쟁 조건! 두 이체가 동시에 실행되면?
    await set_balance(from_account, balance - amount)
    await set_balance(to_account, await get_balance(to_account) + amount)

    return Ok(None)
----

mypy는 통과합니다. 타입은 완벽합니다. 하지만 이 코드는 *돈이 사라지거나 복제될 수 있습니다.* 두 개의 이체가 동시에 같은 계좌에서 출금하면, 둘 다 같은 잔액을 읽고, 각각 차감해서, 결국 한 번만 차감된 것처럼 보입니다.

이것이 바로 테스트가 필요한 이유입니다. *타입은 "무엇을"을 검증하고, 테스트는 "어떻게"를 검증합니다.* 타입과 테스트는 상호 보완적입니다.

[width="100%",cols="32%,51%,17%",options="header",]
|===
|검증 방법 |무엇을 보장하는가? |예시
|*타입 시스템* |구조적 정확성 |``User ++\++{vbar} None``은 None 체크를 강제
|*단위 테스트* |개별 함수의 논리적 정확성 |``calculate++_++discount(100, 0.1) == 90``
|*통합 테스트* |여러 컴포넌트의 상호작용 |DB {plus} API {plus} 캐시가 함께 작동
|*속성 기반 테스트* |법칙과 불변성 |Monad 법칙, 교환 법칙 등
|===

그러나 놀라운 사실이 있습니다. *함수형으로 작성된 비동기 코드는 테스트하기 훨씬 쉽습니다.* link:../01-functional-thinking/[1장]에서 "참조 투명성이 테스트 가능성을 높인다"고 했던 것을 기억하시나요? 이 장에서는 그 약속이 어떻게 실현되는지 확인합니다.

순수 함수는 외부 상태에 의존하지 않고, 같은 입력에 항상 같은 출력을 내므로 테스트가 단순해집니다. link:../08-practical-patterns/[8장]에서 배운 의존성 주입을 사용하면 실제 네트워크 호출이나 데이터베이스 접근을 테스트용 구현으로 쉽게 교체할 수 있습니다. Result와 Maybe 같은 타입은 에러 케이스를 명시적으로 표현하므로, 모든 경로를 체계적으로 테스트할 수 있습니다.

더 중요한 것은 이것입니다: 우리가 link:../08-practical-patterns/[8장]에서 효과(effect)를 값으로 표현했기 때문에, 테스트에서 그 효과를 실제로 실행하지 않고도 검증할 수 있습니다. 데이터베이스에 저장하는 함수를 테스트할 때 실제 데이터베이스가 필요 없습니다. 의존성으로 주입된 ``save++_++user`` 함수를 테스트용 구현으로 교체하면 됩니다.

이 장에서는 비동기 함수형 코드를 체계적으로 테스트하는 방법을 배울 것입니다. 단위 테스트부터 시작해서 통합 테스트까지, 그리고 속성 기반 테스트로 추상화의 법칙(Monad 법칙 등)을 검증하는 방법까지 다룰 것입니다. 테스트는 단순히 버그를 찾는 도구가 아니라, 코드의 정확성을 입증하고 리팩토링의 안전망을 제공하는 강력한 수단임을 발견하게 될 것입니다.

== 순수 함수의 테스트: 단순함의 힘

순수 함수를 테스트하는 것은 수학 함수를 테스트하는 것과 같습니다. 입력을 주고 출력을 확인하면 됩니다. 외부 상태를 설정할 필요도 없고, 부수 효과를 확인할 필요도 없습니다. 단순히 함수를 호출하고 결과를 검증하면 됩니다.

link:../05-error-handling-as-types/[5장]에서 만든 Result 타입의 함수들을 테스트해봅시다. 먼저 간단한 순수 함수부터 시작하겠습니다.

[source,python]
----
# src/validation.py
from result import Result, Ok, Err

def validate_email(email: str) -> Result[str, str]:
    """이메일 형식을 검증합니다"""
    if not email:
        return Err("이메일이 비어있습니다")
    
    if "@" not in email:
        return Err("이메일에 @가 없습니다")
    
    parts = email.split("@")
    if len(parts) != 2:
        return Err("이메일 형식이 올바르지 않습니다")
    
    local, domain = parts
    if not local or not domain:
        return Err("이메일 형식이 올바르지 않습니다")
    
    return Ok(email.lower())

def validate_age(age_str: str) -> Result[int, str]:
    """나이를 검증합니다"""
    try:
        age = int(age_str)
    except ValueError:
        return Err(f"'{age_str}'는 숫자가 아닙니다")
    
    if age < 0:
        return Err("나이는 0 이상이어야 합니다")
    
    if age > 150:
        return Err("나이가 너무 큽니다")
    
    return Ok(age)
----

이 함수들은 순수합니다. 외부 상태를 읽거나 수정하지 않고, 같은 입력에 항상 같은 출력을 반환합니다. 테스트를 작성해봅시다.

[source,python]
----
# tests/test_validation.py
import pytest
from src.validation import validate_email, validate_age
from src.result import Ok, Err

class TestValidateEmail:
    """이메일 검증 테스트"""
    
    def test_valid_email(self):
        """올바른 이메일은 소문자로 변환되어 Ok로 반환됩니다"""
        result = validate_email("User@Example.COM")
        
        assert result.is_ok()
        assert result.unwrap() == "user@example.com"
    
    def test_empty_email(self):
        """빈 이메일은 Err를 반환합니다"""
        result = validate_email("")
        
        assert result.is_err()
        assert result.error == "이메일이 비어있습니다"
    
    def test_email_without_at(self):
        """@가 없는 이메일은 Err를 반환합니다"""
        result = validate_email("userexample.com")
        
        assert result.is_err()
        assert result.error == "이메일에 @가 없습니다"
    
    def test_email_with_multiple_at(self):
        """@가 여러 개인 이메일은 Err를 반환합니다"""
        result = validate_email("user@@example.com")
        
        assert result.is_err()
        assert result.error == "이메일 형식이 올바르지 않습니다"
    
    def test_email_with_empty_local(self):
        """로컬 부분이 비어있으면 Err를 반환합니다"""
        result = validate_email("@example.com")
        
        assert result.is_err()
        assert result.error == "이메일 형식이 올바르지 않습니다"
    
    def test_email_with_empty_domain(self):
        """도메인 부분이 비어있으면 Err를 반환합니다"""
        result = validate_email("user@")
        
        assert result.is_err()
        assert result.error == "이메일 형식이 올바르지 않습니다"

class TestValidateAge:
    """나이 검증 테스트"""
    
    def test_valid_age(self):
        """올바른 나이는 정수로 변환되어 Ok로 반환됩니다"""
        result = validate_age("25")
        
        assert result.is_ok()
        assert result.unwrap() == 25
    
    def test_non_numeric_age(self):
        """숫자가 아닌 입력은 Err를 반환합니다"""
        result = validate_age("twenty")
        
        assert result.is_err()
        assert "'twenty'는 숫자가 아닙니다" in result.error
    
    def test_negative_age(self):
        """음수 나이는 Err를 반환합니다"""
        result = validate_age("-5")
        
        assert result.is_err()
        assert result.error == "나이는 0 이상이어야 합니다"
    
    def test_too_large_age(self):
        """너무 큰 나이는 Err를 반환합니다"""
        result = validate_age("200")
        
        assert result.is_err()
        assert result.error == "나이가 너무 큽니다"
    
    def test_boundary_values(self):
        """경계값들을 테스트합니다"""
        assert validate_age("0").is_ok()
        assert validate_age("150").is_ok()
        assert validate_age("151").is_err()
----

이 테스트들은 매우 간단합니다. 함수를 호출하고 결과를 검증합니다. 설정(setup)이나 정리(teardown)가 필요 없고, 모킹(mocking)도 필요 없습니다.

순수 함수의 테스트는 빠르고, 결정적이며, 독립적입니다. 어떤 순서로 실행해도, 몇 번을 실행해도 결과가 같습니다. 이것이 link:../01-functional-thinking/[1장]에서 말한 참조 투명성의 실질적인 혜택입니다.

== 속성 기반 테스트: 예제에서 법칙으로

지금까지 우리는 "예제 기반 테스트(Example-based Testing)"를 작성했습니다. ``validate++_++age("25")``는 ``Ok(25)``여야 한다는 식이죠. 하지만 예제만으로는 모든 케이스를 다룰 수 없습니다. 우리가 생각하지 못한 경계값이나 특이한 입력은 어떡할까요?

함수형 프로그래밍은 **속성(Property)**을 중시합니다. 특정 입력값에 대한 결과가 아니라, **모든 입력값에 대해 성립해야 하는 법칙**을 정의하는 것입니다.

Python에는 **Hypothesis**라는 강력한 라이브러리가 있습니다.

[source,bash]
----
pip install hypothesis
----

먼저 가장 쉬운 예제로 시작해봅시다. 초등학교 때 배운 "덧셈의 교환법칙"을 테스트해볼까요?
``x {plus} y``는 항상 ``y {plus} x``와 같아야 합니다.

[source,python]
----
from hypothesis import given, strategies as st

@given(st.integers(), st.integers())
def test_addition_commutativity(x, y):
    """어떤 정수 x, y에 대해서도 교환법칙은 성립해야 한다"""
    assert x + y == y + x
----

Hypothesis는 이 코드를 실행할 때 우리가 상상하기 힘든 숫자들(매우 큰 수, 음수, 0 등)을 마구 집어넣어 봅니다. 그래도 통과한다면, 이 법칙은 참이라고 믿을 수 있죠.

이제 비즈니스 로직에 적용해봅시다.

    result = validate_email(email)

def test_age_round_trip(age):
    """
    속성: 유효한 나이를 문자열로 변환했다가 다시 검증하면 
    원래 값이 나와야 함 (Round-trip)

        # 유효한 범위의 나이라면
        age_str = str(age)
        result = validate_age(age_str)
        
        # 반드시 성공하고 원래 값과 같아야 함
        assert result.is_ok()
        assert result.unwrap() == age
    else:
        # 유효하지 않은 범위라면 실패해야 함
        result = validate_age(str(age))
        assert result.is_err()
----

Hypothesis는 우리가 놓치기 쉬운 엣지 케이스(예: ``-1``, ``0``, ``151``, 빈 문자열, 특수 문자 등)를 자동으로 찾아서 테스트가 실패하게 만듭니다.

더 놀라운 점은 *축소(Shrinking)* 기능입니다. Hypothesis가 에러를 발견하면, 가장 이해하기 쉬운 **최소 반례(Minimal Counterexample)**를 찾아줍니다. 예를 들어, 길이가 1000인 리스트에서 에러가 발생했다면, Hypothesis는 리스트를 하나씩 줄여가면서 에러가 발생하는 가장 짧은 리스트(예: 길이 1)를 리포트합니다. 덕분에 디버깅이 매우 쉬워집니다.

이것이 가능한 이유는 우리가 **순수 함수**를 작성했기 때문입니다. 외부 상태가 없고 부작용이 없으므로, 수천 번의 자동 생성된 입력으로 마음껏 테스트해도 안전합니다. 이것이 바로 "타입과 법칙"을 강조하는 함수형 프로그래밍의 진짜 위력입니다.

=== Monad 법칙 검증하기

link:../05-error-handling-as-types/[5장]에서 우리는 Result 타입이 Monad라고 배웠습니다. Monad는 단순히 ``flat++_++map``이 있는 타입이 아니라, **세 가지 법칙을 만족하는 타입**입니다. 이론적으로 법칙을 안다고 해도, 실제 구현이 법칙을 지키는지 검증하지 않으면 신뢰할 수 없습니다.

Hypothesis를 사용하면 Monad 법칙을 속성 기반 테스트로 검증할 수 있습니다.

[source,python]
----
# tests/test_result_monad_laws.py
from hypothesis import given, strategies as st
from src.result import Result, Ok, Err

# 테스트용 순수 함수들
def double(x: int) -> Result[int, str]:
    """x를 2배로 만듭니다"""
    return Ok(x * 2)

def to_string(x: int) -> Result[str, str]:
    """정수를 문자열로 변환합니다"""
    return Ok(str(x))

def add_ten(x: int) -> Result[int, str]:
    """x에 10을 더합니다"""
    return Ok(x + 10)

@given(st.integers())
def test_monad_left_identity(x):
    """
    왼쪽 항등 법칙: Ok(x).flat_map(f) == f(x)

    "값을 Ok로 감싼 후 flat_map하는 것"은
    "그냥 함수를 적용하는 것"과 같아야 합니다.
    """
    left = Ok(x).flat_map(double)
    right = double(x)

    assert left.is_ok() == right.is_ok()
    if left.is_ok():
        assert left.unwrap() == right.unwrap()

@given(st.integers())
def test_monad_right_identity(x):
    """
    오른쪽 항등 법칙: m.flat_map(Ok) == m

    "Result를 Ok로 다시 감싸는 것"은 아무 일도 하지 않는 것과 같습니다.
    """
    m = Ok(x)
    result = m.flat_map(lambda v: Ok(v))

    assert result.is_ok()
    assert result.unwrap() == m.unwrap()

@given(st.integers())
def test_monad_associativity(x):
    """
    결합 법칙: m.flat_map(f).flat_map(g) == m.flat_map(lambda x: f(x).flat_map(g))

    "flat_map을 두 번 연속 호출"하는 것은
    "한 번에 합성해서 호출"하는 것과 같아야 합니다.
    """
    m = Ok(x)

    # 왼쪽: 순차적으로 두 번 flat_map
    left = m.flat_map(double).flat_map(to_string)

    # 오른쪽: 합성된 함수를 한 번에 flat_map
    right = m.flat_map(lambda v: double(v).flat_map(to_string))

    assert left.is_ok() == right.is_ok()
    if left.is_ok():
        assert left.unwrap() == right.unwrap()

@given(st.text())
def test_monad_laws_with_errors(error_msg):
    """
    에러의 경우에도 Monad 법칙이 성립해야 합니다.

    Err는 flat_map을 호출해도 그대로 전파되어야 합니다.
    """
    err: Result[int, str] = Err(error_msg)

    # Err에 flat_map을 적용해도 계속 Err
    result = err.flat_map(double).flat_map(to_string)

    assert result.is_err()
    assert result.unwrap_err() == error_msg

@given(st.integers(), st.integers(), st.integers())
def test_monad_composition_associativity(x, y, z):
    """
    세 개 이상의 연산도 결합 법칙을 만족해야 합니다.

    이것이 우리가 파이프라인을 자유롭게 조합할 수 있는 이유입니다.
    """
    m = Ok(x)

    # 다양한 결합 순서
    result1 = m.flat_map(double).flat_map(add_ten).flat_map(to_string)
    result2 = m.flat_map(lambda v: double(v).flat_map(add_ten)).flat_map(to_string)
    result3 = m.flat_map(lambda v: double(v).flat_map(lambda w: add_ten(w).flat_map(to_string)))

    # 모두 같은 결과여야 함
    assert result1.unwrap() == result2.unwrap() == result3.unwrap()
----

이 테스트들은 **수학적 법칙을 코드로 증명**합니다. Hypothesis가 자동으로 수천 개의 입력을 생성해서 모든 경우에 법칙이 성립하는지 검증합니다.

만약 우리가 Result 구현을 잘못 작성했다면 (예: ``flat++_++map``에서 에러를 잘못 전파), 이 테스트가 실패할 것입니다. 법칙을 코드로 검증함으로써, 우리는 추상화가 올바르게 구현되었다는 **형식적 증명(Formal Proof)**에 가까운 확신을 얻을 수 있습니다.

*왜 이것이 중요한가?*

[arabic]
. *리팩토링 안전성*: Result의 내부 구현을 변경해도, 법칙 테스트가 통과하면 안전합니다.
. *인터페이스 계약*: Monad 법칙은 Result 타입의 **공개 계약(Public Contract)**입니다. 사용자는 이 법칙에 의존할 수 있습니다.
. *합성 가능성 증명*: 결합 법칙이 성립하므로, 우리는 안심하고 복잡한 파이프라인을 조합할 수 있습니다.

이것이 바로 함수형 프로그래밍에서 "법칙"을 중시하는 이유입니다. 법칙은 단순한 이론이 아니라, **코드의 정확성을 검증하는 실용적 도구**입니다.

*주의: '동치성'의 정의가 동기와 비동기에서 다릅니다.* 위 테스트들이 안전한 이유는, 사실 ``Result``가 **동기적** 타입이기 때문입니다 — ``left.unwrap() == right.unwrap()``은 이미 계산이 끝난 두 값을 즉시 비교하므로 타이밍이 끼어들 여지가 없습니다. 만약 검증 대상이 ``Future``나 코루틴처럼 **비동기적** Monad라면 얘기가 달라집니다. 두 ``Future`` 객체 자체를 비교하거나, 아직 완료되지 않은 상태에서 값을 꺼내려 하면 네트워크 지연이나 스케줄링 순서에 따라 테스트가 실패했다 성공했다 하는 **플래키(flaky) 테스트**가 됩니다. 비동기 Monad 법칙을 속성 기반 테스트로 검증할 때 지켜야 할 원칙은 하나입니다 — **항상 완료될 때까지 기다린 뒤(``await``), 그 결과값끼리 비교한다.** 이걸 "Future가 같다"가 아니라 "**최종적으로 수렴하는 값이 같다(eventual/semantic equivalence)**"라고 부릅니다. 다음 절에서 다룰 ``pytest-asyncio``와 ``asyncio.run``이 바로 이 "끝까지 기다렸다가 비교한다"는 원칙을 강제하는 도구입니다 — 테스트 함수 자체가 이벤트 루프를 완주할 때까지 블로킹되므로, 결과를 꺼내는 시점에는 이미 타이밍이라는 변수가 사라져 있습니다.

== pytest-asyncio: 비동기 함수 테스트하기

비동기 함수를 테스트하려면 특별한 도구가 필요합니다. pytest-asyncio는 pytest에서 비동기 함수를 테스트할 수 있게 해주는 플러그인입니다.

먼저 설치합니다.

[source,bash]
----
pip install pytest-asyncio
----

간단한 비동기 함수를 테스트해봅시다.

[source,python]
----
# src/user_service.py
import asyncio
from typing import Optional
from src.result import Result, Ok, Err

class User:
    def __init__(self, id: int, name: str, email: str):
        self.id = id
        self.name = name
        self.email = email

async def fetch_user(user_id: int) -> Result[User, str]:
    """사용자를 비동기로 조회합니다 (시뮬레이션)"""
    await asyncio.sleep(0.1)  # 네트워크 지연 시뮬레이션
    
    if user_id < 0:
        return Err("유효하지 않은 사용자 ID")
    
    if user_id == 999:
        return Err("사용자를 찾을 수 없습니다")
    
    return Ok(User(
        id=user_id,
        name=f"사용자{user_id}",
        email=f"user{user_id}@example.com"
    ))
----

테스트를 작성합니다.

[source,python]
----
# tests/test_user_service.py
import pytest
from src.user_service import fetch_user

@pytest.mark.asyncio
async def test_fetch_user_success():
    """올바른 사용자 ID로 조회하면 성공합니다"""
    result = await fetch_user(123)
    
    assert result.is_ok()
    
    user = result.unwrap()
    assert user.id == 123
    assert user.name == "사용자123"
    assert user.email == "user123@example.com"

@pytest.mark.asyncio
async def test_fetch_user_invalid_id():
    """음수 ID로 조회하면 실패합니다"""
    result = await fetch_user(-1)
    
    assert result.is_err()
    assert result.error == "유효하지 않은 사용자 ID"

@pytest.mark.asyncio
async def test_fetch_user_not_found():
    """존재하지 않는 사용자를 조회하면 실패합니다"""
    result = await fetch_user(999)
    
    assert result.is_err()
    assert result.error == "사용자를 찾을 수 없습니다"
----

핵심은 ``@pytest.mark.asyncio`` 데코레이터입니다. 이것은 pytest에게 이 테스트 함수가 비동기라는 것을 알려주고, 적절한 이벤트 루프에서 실행하도록 합니다. 테스트 함수는 ``async def``로 정의되고, 비동기 함수를 ``await``로 호출할 수 있습니다.

테스트를 실행하면 pytest-asyncio가 자동으로 이벤트 루프를 관리합니다. 각 테스트는 독립적인 이벤트 루프에서 실행되므로, 테스트 간 간섭이 없습니다.

[source,bash]
----
pytest tests/test_user_service.py -v
----

비동기 테스트는 동기 테스트와 거의 같은 방식으로 작성합니다. await 키워드를 추가하고 데코레이터를 붙이는 것만 다릅니다. 나머지는 동일합니다.

== 의존성 주입: 테스트 가능한 구조 만들기

실제 애플리케이션에서는 외부 시스템에 의존하는 경우가 많습니다. 데이터베이스, API, 파일 시스템 같은 것들이죠. 이런 의존성을 테스트하기 위해 보통 모킹(mocking)을 사용합니다. 하지만 link:../08-practical-patterns/[8장]에서 배운 것처럼, 의존성 주입을 사용하면 모킹 없이도 테스트할 수 있습니다.

실제 데이터베이스를 사용하는 서비스를 생각해봅시다.

[source,python]
----
# src/user_repository.py
from typing import Optional, Callable, Awaitable
from src.user_service import User
from src.result import Result, Ok, Err
import uuid

# 데이터베이스 함수의 타입 별칭
FindUser = Callable[[int], Awaitable[Optional[User]]]
FindUserByEmail = Callable[[str], Awaitable[Optional[User]]]
SaveUser = Callable[[User], Awaitable[None]]

def make_user_service(
    find_user: FindUser,
    find_user_by_email: FindUserByEmail,
    save_user: SaveUser
):
    """의존성을 주입받아 사용자 서비스를 생성합니다"""

    async def create_user(name: str, email: str) -> Result[User, str]:
        """새 사용자를 생성합니다"""
        # 이메일 중복 확인
        existing = await find_user_by_email(email)
        if existing:
            return Err("이미 존재하는 이메일입니다")

        # 사용자 생성
        user = User(id=int(uuid.uuid4().int % 1000000), name=name, email=email)
        await save_user(user)

        return Ok(user)

    async def get_user(user_id: int) -> Result[User, str]:
        """사용자를 조회합니다"""
        user = await find_user(user_id)

        if user is None:
            return Err("사용자를 찾을 수 없습니다")

        return Ok(user)

    return {
        "create_user": create_user,
        "get_user": get_user
    }
----

이 서비스는 find++_++user와 save++_++user를 의존성으로 받습니다. 실제 환경에서는 실제 데이터베이스 함수를 주입하고, 테스트에서는 메모리 기반 구현을 주입합니다.

(참고: 기존 레거시 코드나 라이브러리 등 의존성 주입이 어려운 경우에는 ``unittest.mock.AsyncMock``을 사용할 수 있습니다. ``await`` 가능한 모의 객체를 생성해주므로 비동기 함수도 쉽게 모킹할 수 있습니다. 하지만 가능한 의존성 주입을 사용하는 것이 더 명확하고 유지보수하기 좋습니다.)

테스트를 작성해봅시다.

[source,python]
----
# tests/test_user_repository.py
import pytest
from src.user_repository import make_user_service, User
from typing import Dict

class InMemoryUserDB:
    """테스트용 메모리 데이터베이스"""

    def __init__(self):
        self.users: Dict[int, User] = {}
        self.emails: Dict[str, User] = {}
        self.next_id = 1

    async def find_user(self, user_id: int) -> User | None:
        """사용자를 ID로 조회합니다"""
        return self.users.get(user_id)

    async def find_user_by_email(self, email: str) -> User | None:
        """사용자를 이메일로 조회합니다"""
        return self.emails.get(email)

    async def save_user(self, user: User) -> None:
        """사용자를 저장합니다"""
        if user.id == 0:
            user.id = self.next_id
            self.next_id += 1

        self.users[user.id] = user
        self.emails[user.email] = user

@pytest.fixture
def user_service():
    """테스트용 사용자 서비스를 생성합니다"""
    db = InMemoryUserDB()

    service = make_user_service(
        find_user=db.find_user,
        find_user_by_email=db.find_user_by_email,
        save_user=db.save_user
    )

    return service, db

@pytest.mark.asyncio
async def test_get_user_success(user_service):
    """사용자를 성공적으로 조회합니다"""
    service, db = user_service
    
    # 테스트 데이터 준비
    test_user = User(id=1, name="철수", email="chulsoo@example.com")
    await db.save_user(test_user)
    
    # 조회
    result = await service["get_user"](1)
    
    assert result.is_ok()
    
    user = result.unwrap()
    assert user.id == 1
    assert user.name == "철수"

@pytest.mark.asyncio
async def test_get_user_not_found(user_service):
    """존재하지 않는 사용자를 조회하면 실패합니다"""
    service, db = user_service
    
    result = await service["get_user"](999)
    
    assert result.is_err()
    assert result.error == "사용자를 찾을 수 없습니다"

@pytest.mark.asyncio
async def test_create_user_success(user_service):
    """사용자를 성공적으로 생성합니다"""
    service, db = user_service
    
    result = await service["create_user"]("영희", "younghee@example.com")
    
    assert result.is_ok()
    
    user = result.unwrap()
    assert user.name == "영희"
    assert user.email == "younghee@example.com"
    
    # 데이터베이스에 저장되었는지 확인
    saved_user = await db.find_user(user.id)
    assert saved_user is not None
    assert saved_user.name == "영희"
----

이 접근의 장점은 명확합니다. 실제 데이터베이스를 사용하지 않으므로 테스트가 빠르고, 독립적이며, 결정적입니다. InMemoryUserDB는 간단하고 예측 가능하므로 테스트하기 쉽습니다. 그리고 모킹 라이브러리가 필요 없습니다. 단순한 클래스와 함수만으로 충분합니다.

fixture를 사용하면 테스트 간에 설정을 재사용할 수 있습니다. user++_++service fixture는 각 테스트마다 새로운 데이터베이스와 서비스를 생성하므로, 테스트 간 격리가 보장됩니다.

== 비동기 Fixture: 설정과 정리

때로는 fixture 자체도 비동기여야 할 때가 있습니다. 예를 들어, 테스트 데이터베이스 연결을 설정하거나, 외부 서비스를 준비하거나, 비동기 리소스를 초기화해야 할 수 있습니다.

pytest-asyncio는 비동기 fixture를 지원합니다.

[source,python]
----
# tests/conftest.py
import pytest
import asyncio
from src.database import Database

@pytest.fixture(scope="function")
async def db_connection():
    """테스트용 데이터베이스 연결을 생성합니다"""
    # 설정 (setup)
    db = Database("test.db")
    await db.connect()
    await db.init_schema()
    
    # 테스트에 전달
    yield db
    
    # 정리 (teardown)
    await db.clear_all()
    await db.disconnect()

@pytest.mark.asyncio
async def test_user_crud(db_connection):
    """사용자 CRUD 테스트"""
    db = db_connection
    
    # Create
    user_id = await db.create_user("테스트", "test@example.com")
    assert user_id > 0
    
    # Read
    user = await db.get_user(user_id)
    assert user["name"] == "테스트"
    
    # Update
    await db.update_user(user_id, name="수정됨")
    updated = await db.get_user(user_id)
    assert updated["name"] == "수정됨"
    
    # Delete
    await db.delete_user(user_id)
    deleted = await db.get_user(user_id)
    assert deleted is None
----

비동기 fixture는 ``async def``로 정의하고, await를 사용해서 비동기 작업을 수행할 수 있습니다. yield 이전은 설정 단계이고, yield 이후는 정리 단계입니다. pytest-asyncio가 자동으로 올바른 순서로 실행해줍니다.

scope 파라미터로 fixture의 생명주기를 제어할 수 있습니다. "function"은 각 테스트마다 새로 생성하고, "class"는 테스트 클래스마다, "module"은 모듈마다, "session"은 전체 테스트 세션에 한 번만 생성합니다.

[source,python]
----
@pytest.fixture(scope="session")
async def app():
    """테스트 세션 전체에서 공유되는 애플리케이션"""
    app = create_app(test_config)
    await app.startup()

    yield app

    await app.shutdown()
----

=== 비동기 Fixture의 주의사항

``scope="session"`` 같은 넓은 범위의 비동기 fixture를 사용할 때는 이벤트 루프 불일치 문제를 주의해야 합니다. pytest-asyncio는 기본적으로 각 테스트마다 새로운 이벤트 루프를 생성하는데, 세션 범위의 fixture는 하나의 이벤트 루프에서만 유효합니다.

[source,python]
----
# conftest.py에서 이벤트 루프 범위 설정
import pytest

@pytest.fixture(scope="session")
def event_loop():
    """세션 범위의 이벤트 루프를 생성합니다"""
    import asyncio
    loop = asyncio.get_event_loop_policy().new_event_loop()
    yield loop
    loop.close()

@pytest.fixture(scope="session")
async def shared_db_connection(event_loop):
    """세션 전체에서 공유되는 DB 연결"""
    db = await Database.connect("test.db")
    yield db
    await db.disconnect()
----

이렇게 하면 세션 범위의 비동기 fixture가 올바른 이벤트 루프에서 실행됩니다. 하지만 가능하면 ``scope="function"``을 사용해서 각 테스트가 독립적으로 실행되도록 하는 것이 더 안전합니다.

비동기 fixture는 비동기 테스트의 복잡성을 캡슐화하는 강력한 도구입니다. 설정과 정리 로직을 한 곳에 모아서 재사용하고, 각 테스트는 비즈니스 로직에만 집중할 수 있습니다.

== 통합 테스트: 전체 흐름 검증하기

단위 테스트는 개별 함수를 검증하지만, 통합 테스트는 여러 컴포넌트가 함께 작동하는 것을 검증합니다. 비동기 시스템에서 통합 테스트는 특히 중요합니다. 여러 비동기 작업이 올바른 순서로 조율되는지, 에러가 적절히 전파되는지, 타임아웃이 제대로 작동하는지 확인해야 하기 때문입니다.

사용자 등록 흐름의 통합 테스트를 작성해봅시다. 이 흐름은 여러 단계를 거칩니다. 이메일 검증, 중복 확인, 사용자 생성, 환영 이메일 발송입니다.

[source,python]
----
# src/registration.py
import asyncio
from typing import Callable, Awaitable
from src.validation import validate_email, validate_age
from src.result import Result, Ok, Err
from src.user_service import User

# 의존성 타입
CheckEmailExists = Callable[[str], Awaitable[bool]]
SaveUser = Callable[[User], Awaitable[None]]
SendEmail = Callable[[User], Awaitable[None]]

def make_registration_service(
    check_email_exists: CheckEmailExists,
    save_user: SaveUser,
    send_email: SendEmail
):
    """사용자 등록 서비스를 생성합니다"""
    
    async def register_user(
        name: str,
        email: str,
        age_str: str
    ) -> Result[User, str]:
        """사용자를 등록합니다"""
        
        # 1. 이메일 검증
        email_result = validate_email(email)
        if email_result.is_err():
            return email_result
        
        validated_email = email_result.unwrap()
        
        # 2. 나이 검증
        age_result = validate_age(age_str)
        if age_result.is_err():
            return age_result
        
        validated_age = age_result.unwrap()
        
        # 3. 중복 확인 (비동기)
        exists = await check_email_exists(validated_email)
        if exists:
            return Err("이미 존재하는 이메일입니다")
        
        # 4. 사용자 생성 및 저장 (비동기)
        user = User(
            id=0,  # 데이터베이스가 할당
            name=name,
            email=validated_email
        )
        
        try:
            await save_user(user)
        except Exception as e:
            return Err(f"사용자 저장 실패: {e}")
        
        # 5. 환영 이메일 발송 (비동기, 실패해도 무시)
        try:
            await send_email(user)
        except Exception as e:
            # 이메일 발송 실패는 로그만 남기고 무시
            print(f"이메일 발송 실패: {e}")
        
        return Ok(user)
    
    return {"register_user": register_user}
----

통합 테스트는 단위 테스트보다 복잡하지만, 실제 시스템이 어떻게 작동하는지 더 잘 보여줍니다. 여러 컴포넌트가 함께 작동하는 것을 검증하고, 에러가 올바르게 전파되는지 확인하며, 부분 실패 시나리오를 테스트합니다.

의존성 주입 덕분에 통합 테스트도 빠르고 결정적입니다. 실제 SMTP 서버나 데이터베이스를 사용하지 않고, 메모리 기반 구현을 사용합니다. 이것은 CI/CD 파이프라인에서 매우 중요합니다. 테스트가 외부 시스템에 의존하지 않으므로 언제든 실행할 수 있습니다.

== 경쟁 조건 테스트하기

서론에서 비동기 코드의 경쟁 조건(race condition)이 테스트를 어렵게 만든다고 했습니다. 경쟁 조건은 타이밍에 의존적이고 비결정적이어서 테스트로 잡아내기 매우 어렵습니다. 하지만 ``asyncio.gather``를 활용해 동시성(concurrency)을 시뮬레이션하면, 멀티스레드 환경 없이도 경쟁 조건을 의도적으로 유발하고 테스트할 수 있습니다.

카운터를 증가시키는 작업을 동시에 실행하는 테스트를 생각해봅시다. 만약 카운터가 안전하게 구현되지 않았다면(Lock을 사용하지 않음), 최종 값은 100보다 작을 것입니다.

먼저 두 가지 카운터 구현을 봅시다:

[source,python]
----
# src/counter.py
import asyncio

class UnsafeCounter:
    """Lock 없는 카운터 (경쟁 조건 있음)"""
    def __init__(self):
        self.value = 0

    async def increment(self):
        """
        위험: 읽기-수정-쓰기가 원자적(atomic)이지 않음

        두 개의 코루틴이 동시에 실행되면:
        1. 코루틴 A가 value를 읽음 (0)
        2. 코루틴 B가 value를 읽음 (0)  ← 아직 A가 쓰지 않았음!
        3. 코루틴 A가 1을 씀
        4. 코루틴 B가 1을 씀  ← 증가가 한 번 손실됨!
        """
        temp = self.value
        await asyncio.sleep(0)  # 다른 코루틴에 실행 기회를 양보
        self.value = temp + 1

class SafeCounter:
    """Lock을 사용하는 카운터 (경쟁 조건 없음)"""
    def __init__(self):
        self.value = 0
        self._lock = asyncio.Lock()

    async def increment(self):
        """
        안전: Lock으로 임계 영역(critical section)을 보호

        async with 블록 안에서는 한 번에 하나의 코루틴만 실행됩니다.
        다른 코루틴들은 Lock이 해제될 때까지 대기합니다.
        """
        async with self._lock:
            temp = self.value
            await asyncio.sleep(0)  # Lock 안이므로 안전
            self.value = temp + 1
----

# tests/test_race_condition.py
import pytest
import asyncio
from src.counter import UnsafeCounter, SafeCounter

@pytest.mark.asyncio
async def test_unsafe_counter_has_race_condition():
    """경쟁 조건으로 인해 UnsafeCounter는 올바르지 않은 결과를 냅니다"""
    counter = UnsafeCounter()

    # 100개의 동시 증가 작업
    await asyncio.gather(*[counter.increment() for _ in range(100)])

    # 경쟁 조건으로 인해 100보다 작을 수 있음
    # 이 테스트는 경쟁 조건을 "발견"하거나 "입증"하는 것이 목적
    print(f"UnsafeCounter 결과: {counter.value} (기대값: 100)")

@pytest.mark.asyncio
async def test_safe_counter_no_race_condition():
    """Lock을 사용하는 SafeCounter는 경쟁 조건이 없습니다"""
    counter = SafeCounter()

    # 100개의 동시 증가 작업
    # 100개의 코루틴을 동시에(concurrently) 스케줄링합니다.
    await asyncio.gather(*[counter.increment() for _ in range(100)])

    # Lock으로 보호되므로 항상 정확히 100
    assert counter.value == 100
----

[source,python]
----
@pytest.mark.asyncio
async def test_concurrent_user_creation(user_service):
    """같은 이메일로 동시에 사용자를 생성하면 하나만 성공해야 합니다"""
    
    # 같은 이메일로 10개의 동시 생성 요청
    results = await asyncio.gather(
        *[user_service.create_user("test@example.com") for _ in range(10)]
    )

    # 성공은 정확히 하나만
    success_count = sum(1 for r in results if r.is_ok())
    assert success_count == 1, f"성공 횟수: {success_count} (기대: 1)"

    # 나머지는 모두 중복 에러
    error_count = sum(1 for r in results if r.is_err())
    assert error_count == 9
----

경쟁 조건 테스트의 핵심은 ``asyncio.gather``입니다. 여러 비동기 작업을 동시에 루프에 등록(Schedule)하여 실행 순서가 섞이게 만들고, 그 결과가 일관된지 확인합니다. 함수형 프로그래밍에서는 상태 변경을 최소화하므로(불변성), 이런 경쟁 조건 문제에서 비교적 자유롭습니다. **공유 상태를 없애는 것**이 테스트보다 더 근본적인 해결책임을 기억하세요.

== 타임아웃과 재시도 테스트하기

비동기 시스템에서 타임아웃과 재시도 로직은 필수적입니다. 외부 시스템이 응답하지 않거나 느릴 때 프로그램이 무한정 기다리지 않도록 해야 합니다. 이런 로직은 시간에 의존적이라 테스트하기 까다롭지만, 적절한 방법을 사용하면 검증할 수 있습니다.

``retry++_++async``라는 함수가 있다고 가정해봅시다. 이 함수는 실패한 작업(Result.Err 반환)을 정해진 횟수만큼 재시도합니다.

[source,python]
----
# tests/test_retry.py
import pytest
import asyncio
import time
from src.retry import retry_async
from src.result import Ok, Err

@pytest.mark.asyncio
async def test_retry_succeeds_after_failures():
    """실패 후 재시도에서 성공합니다"""
    call_count = 0
    
    async def succeeds_on_third():
        nonlocal call_count
        call_count += 1
        
        if call_count < 3:
            return Err(f"시도 {call_count} 실패")
        
        return Ok("성공")
    
    start = time.time()
    
    # 3번 시도하고, 시도 간격은 0.1초
    result = await retry_async(
        succeeds_on_third,
        max_attempts=3,
        delay_seconds=0.1
    )
    elapsed = time.time() - start
    
    assert result.is_ok()
    assert result.unwrap() == "성공"
    assert call_count == 3
    
    # 두 번의 재시도 사이에 delay가 있었는지 확인
    # 0.1초 × 2번 = 0.2초 이상이어야 함
    assert elapsed >= 0.2
----

타임아웃 로직은 ``asyncio.wait++_++for``를 래핑한 ``with++_++timeout`` 함수를 사용한다고 가정하고 테스트합니다.

[source,python]
----
# tests/test_timeout.py
import pytest
import asyncio
from src.timeout import with_timeout
from src.result import Ok

@pytest.mark.asyncio
async def test_times_out():
    """타임아웃이 발생하면 Err를 반환합니다"""
    
    async def slow_operation():
        await asyncio.sleep(2.0)
        return Ok("완료")
    
    # 0.1초 안에 완료되지 않으면 타임아웃
    result = await with_timeout(slow_operation, timeout_seconds=0.1)
    
    assert result.is_err()
    assert "타임아웃" in result.error
----

타임아웃과 재시도 테스트에서 중요한 것은 실제 시간을 기다리면서 타이밍을 검증하는 것입니다. ``delay++_++seconds``나 ``timeout++_++seconds``를 작게 설정(0.01~0.1초)해서 테스트가 빨리 실행되도록 하면서도, 타이밍 로직을 검증할 수 있을 만큼 충분한 시간을 줘야 합니다.

== 코드 커버리지: 테스트의 완전성 측정

테스트를 작성했다면, 다음 질문은 이것입니다: *"코드의 몇 퍼센트가 테스트되었는가?"*

코드 커버리지(Code Coverage)는 테스트가 실행하는 코드의 비율을 측정하는 도구입니다. 100% 커버리지가 버그가 없다는 것을 보장하지는 않지만, 테스트되지 않은 코드 영역을 발견할 수 있습니다.

=== 커버리지 100%를 목표로 해야 할까?

*짧은 답*: 아니요.

*긴 답*: 커버리지는 *품질의 필요 조건이지 충분 조건이 아닙니다*.

[source,python]
----
def divide(a: float, b: float) -> float:
    """100% 커버리지지만 버그가 있는 코드"""
    return a / b  # b가 0이면 ZeroDivisionError

def test_divide():
    """이 테스트는 커버리지 100%를 달성합니다"""
    assert divide(10, 2) == 5  # ✅ 통과

# 하지만 divide(10, 0)은 테스트하지 않았으므로 버그 발견 못 함!
----

*권장 사항*:

[arabic]
. *핵심 비즈니스 로직*: 80~100% 커버리지를 목표로 하세요. 사용자 등록, 결제, 권한 검사 등 중요한 코드는 철저히 테스트해야 합니다.
. *에러 처리 경로*: Result 타입의 Err 경로도 테스트하세요. 많은 팀이 "정상 경로"만 테스트하고 에러 경로를 놓칩니다.
+
[source,python]
----
# ❌ 나쁜 예: Ok 경로만 테스트
def test_validate_email_success():
    assert validate_email("user@example.com").is_ok()

# ✅ 좋은 예: Err 경로도 테스트
def test_validate_email_failure():
    assert validate_email("invalid").is_err()
    assert validate_email("").is_err()
    assert validate_email("@example.com").is_err()
----
. *분기문과 경계값*: if/else, match/case의 모든 분기를 테스트하고, 경계값(0, -1, 최대값 등)을 확인하세요.
. *보일러플레이트는 무시*: ``++__++init++__++``, ``++__++repr++__++`` 같은 단순 메서드는 낮은 우선순위입니다. 비즈니스 로직에 집중하세요.
. *커버리지 ++<++ 테스트 품질*: 라인을 "실행"하는 것보다 **의미 있는 assertion**을 작성하는 것이 중요합니다.
+
[source,python]
----
# ❌ 커버리지는 높지만 의미 없는 테스트
def test_register_user():
    register_user("Alice", "alice@example.com")  # assertion 없음!

# ✅ 커버리지도 높고 의미도 있는 테스트
def test_register_user():
    result = register_user("Alice", "alice@example.com")
    assert result.is_ok()
    user = result.unwrap()
    assert user.name == "Alice"
    assert user.email == "alice@example.com"
----

=== 커버리지를 CI/CD에 통합하기

프로젝트가 커지면 커버리지를 자동으로 추적해야 합니다. GitHub Actions 예제:

[source,yaml]
----
# .github/workflows/test.yml
name: Tests

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-python@v4
        with:
          python-version: '3.11'

      - name: Install dependencies
        run: |
          pip install -e .
          pip install pytest pytest-cov pytest-asyncio

      - name: Run tests with coverage
        run: |
          pytest --cov=src --cov-report=term --cov-report=xml tests/

      - name: Upload coverage to Codecov
        uses: codecov/codecov-action@v3
        with:
          file: ./coverage.xml
          fail_ci_if_error: true
----

이렇게 하면 Pull Request마다 커버리지 리포트가 자동으로 생성되고, 커버리지가 떨어지면 경고를 받을 수 있습니다.

*핵심 교훈*: 커버리지는 도구일 뿐입니다. *"어떤 코드가 실행되었는가?"* 보다 *"올바른 assertion으로 검증했는가?"* 가 더 중요합니다. 함수형 프로그래밍의 순수 함수와 타입 안전성이 있다면, 적은 수의 테스트로도 높은 신뢰도를 얻을 수 있습니다.

== 테스트는 문서이자 명세다

좋은 테스트는 단순히 버그를 찾는 도구가 아닙니다. 테스트는 코드가 **어떻게 사용되어야 하는지**를 보여주는 살아있는 문서이고, 코드가 **무엇을 해야 하는지**를 정의하는 명세입니다.

새로운 팀원이 프로젝트에 합류했을 때, 테스트를 읽으면 각 함수가 무엇을 하는지, 어떤 경계 케이스가 있는지, 어떤 에러가 발생할 수 있는지 빠르게 이해할 수 있습니다. 주석이나 문서는 오래되거나 부정확할 수 있지만, 테스트는 실행되므로 항상 최신이고 정확합니다.

=== 함수형 설계가 테스트를 쉽게 만드는 이유

함수형 프로그래밍의 각 원칙이 테스트 가능성에 어떻게 기여하는지 정리해봅시다.

[cols=",",options="header",]
|===
|함수형 원칙 |테스트에 미치는 영향
|*순수 함수* (link:../01-functional-thinking/[1장]) |설정/정리 불필요, 결정적 결과
|*참조 투명성* (link:../01-functional-thinking/[1장]) |같은 입력 → 같은 출력, 테스트 반복 가능
|*함수 합성* (link:../01-functional-thinking/[1장]) |작은 단위로 독립 테스트 가능
|*효과를 값으로* (link:../08-practical-patterns/[8장]) |실제 효과 없이 로직 검증 가능
|*의존성 주입* (link:../08-practical-patterns/[8장]) |Mock 없이 테스트용 구현 주입
|*Result 타입* (link:../05-error-handling-as-types/[5장]) |모든 에러 경로를 명시적으로 테스트
|===

link:../08-practical-patterns/[8장]에서 우리가 효과(데이터베이스 저장, 이메일 발송)를 함수로 추상화했기 때문에, 테스트에서는 그 함수를 단순한 구현으로 교체할 수 있었습니다. 이것이 함수형 설계의 핵심 이점입니다. 비즈니스 로직과 부수 효과가 분리되어 있으므로, 테스트는 비즈니스 로직만 검증하면 됩니다.

[source,python]
----
# 8장의 의존성 주입 패턴이 테스트를 가능하게 합니다
def make_registration_service(check_email, save_user, send_email):
    """의존성이 외부에서 주입되므로 테스트용 구현으로 교체 가능"""
    async def register(name, email):
        # 비즈니스 로직만 담당
        # 실제 DB/이메일은 주입된 함수가 처리
        pass
    return register

# 테스트: 실제 DB/이메일 없이 로직만 검증
test_service = make_registration_service(
    check_email=lambda e: False,      # 항상 "없음"
    save_user=lambda u: None,          # 아무것도 안 함
    send_email=lambda u: None          # 아무것도 안 함
)
----

테스트는 리팩토링의 안전망이기도 합니다. 코드를 개선하거나 구조를 바꿀 때, 테스트가 있으면 기존 동작이 깨지지 않았다는 확신을 가질 수 있습니다. 테스트가 모두 통과하면 리팩토링이 성공한 것입니다. 테스트가 실패하면 무언가를 놓쳤다는 신호입니다.

*기본 문제*: ``asyncio.sleep``을 사용하는 함수를 ``hypothesis``로 테스트하려면 어떻게 해야 할까요?

== 10장 요약: 테스트는 살아있는 명세다

이번 장에서는 함수형 프로그래밍이 어떻게 **테스트 용이성(Testability)**을 극대화하는지 확인했습니다.

[arabic]
. *순수 함수*: 설정(Setup)과 정리(Teardown) 없는 *단순하고 빠른 테스트*.
. *의존성 주입*: 모킹 지옥(Mock Hell)에서 벗어나 **가짜 구현체(Fake Implementation)**로 교체.
. *속성 기반 테스트*: 예제 몇 개가 아니라, **수학적 법칙(Property)**으로 코드의 정확성을 증명.
. *비동기 통합 테스트*: ``asyncio.gather`` 등으로 **경쟁 조건(Race Condition)**과 타이밍 이슈 검증.

=== 1장 → 10장까지의 여정: 논리적 오류 제거

우리는 타입 시스템(link:../09-type-systems-and-fp/[9장])으로 **컴파일 타임 오류**를 잡고, 테스트(link:../10-testing-async-code/[10장])로 **논리적 오류**를 잡았습니다. 이제 우리의 코드는 수학적으로 증명되었고(Type), 경험적으로 검증되었습니다(Test). 하지만 실제 운영 환경에서는 예상치 못한 성능 문제나 자원 누수가 발생할 수 있습니다.
