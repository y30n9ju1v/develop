=== MLIR/CIRCT

CIRCT는 LLVM/MLIR 위에 하드웨어 dialect를 얹은 프로젝트입니다. 소스 빌드는 30분~1시간 이상 걸리므로, 미리 빌드된 릴리스를 받는 것을 권합니다.

[source,bash]
----

circt-opt --version    # 정상 설치되면 버전 정보 출력

# Linux — CIRCT GitHub 릴리스에서 사전 빌드된 tarball 사용

tar xzf circt.tar.gz
export PATH="$PWD/circt/bin:$PATH"
circt-opt --version

[TIP]
====
*Lean4 속성 가이드 — 이 책에서 반복해서 쓰는 문법만 추려둔 것입니다. Lean4를 처음 본다면 앞으로 계속 참고하세요.*

- `def f (a b : T) : U := ...` — 함수 정의. `:=` 뒤가 본문입니다.
- `theorem name : P := proof` — 명제 `P`를 `proof`로 증명합니다. `by tac1; tac2`처럼 `by`로 시작하면 *전술(tactic)* 모드로, 사람이 증명 절차를 단계별로 지시합니다.
- `decide` — 명제가 유한한 경우의 수(예: `Bool` 몇 개의 조합)로 환원되면, 그 경우를 전부 기계적으로 확인해 증명을 끝냅니다. 입력 폭이 넓어지면(2장에서 16비트) 계산량이 폭발해 못 씁니다.
- `simp [lemma1, lemma2, ...]` — 주어진 보조정리들로 식을 최대한 단순화합니다. 여러 곳에서 "이 정리로 `simp`하면 닫힌다"는 식으로 등장합니다.
- `induction n with | zero => ... | succ k ih => ...` — 자연수(또는 리스트, `Vector`)에 대한 귀납법. `ih`(induction hypothesis)가 "한 단계 작은 경우엔 이미 참"이라는 가정이고, `succ`/`cons` 갈래에서 그 가정을 이용해 한 단계 큰 경우를 증명합니다. `decide`가 계산량 때문에 막히는 지점(2장부터)에서 이걸로 갈아탑니다.
- `Fin n` — 0부터 `n-1`까지의 값만 표현 가능한 타입. "범위를 벗어난 값"이라는 카테고리 자체가 타입에 없다는 게 핵심(1장 6절, 3장 5절에서 반복 등장).
- `Vector Bool n` — 길이가 정확히 `n`인 `Bool` 리스트. 16비트 워드, 8비트 정수 등을 표현하는 데 계속 씁니다. `v[i]`로 인덱싱, `v.set i x`로 갱신.
- `inductive T where | c1 (args) | c2 (args) ...` — 귀납적 타입(대수적 데이터 타입). "이 생성자들 중 하나로만 만들 수 있다"는 것이 "정의되지 않은 값"을 배제하는 핵심 도구입니다(2장의 `AluOp` 18개 생성자 등).
- `namespace Foo ... end Foo` — 이름공간. `Foo.bar`로 그 안의 정의에 접근합니다.
- `#eval expr` — 식을 즉시 실행해 결과를 봅니다. VS Code의 Lean4 확장을 쓰면 파일 안에서 바로 결과가 보입니다.

막히면 각 장의 코드에 이 목록을 다시 대입해보세요 — 이 책에 나오는 Lean4 문법의 대부분은 이 열 줄 안에 있습니다.
====

== 2. 게이트 명세와 증명 (`Gates/Basic.lean`)

NAND를 유일한 원시 연산으로 두고, 나머지 게이트를 그 위에 정의합니다. 함수 완전성(functional completeness) 증명 — NAND 하나로 NOT/AND/OR/XOR/Mux를 전부 만들 수 있다는 것 — 을 이 절에서 끝까지 닫습니다.

[source,lean]
----
-- Gates/Basic.lean
namespace Nand2Npu

/-- 유일한 원시 게이트. 이후 모든 게이트가 이 함수만으로 정의됩니다. -/
def nandGate (a b : Bool) : Bool := !(a && b)

def notGate (a : Bool) : Bool := nandGate a a
def andGate (a b : Bool) : Bool := nandGate (nandGate a b) (nandGate a b)
def orGate (a b : Bool) : Bool := nandGate (notGate a) (notGate b)
def xorGate (a b : Bool) : Bool :=
  let d := nandGate a b
  nandGate (nandGate a d) (nandGate b d)
def muxGate (a b sel : Bool) : Bool :=
  orGate (andGate a (notGate sel)) (andGate b sel)

/-- 4가지 선택지 중 하나를 고르는 멀티플렉서. sel : Bool × Bool로 4가지를 표현합니다. -/
def mux4Gate (a b c d : Bool) (sel : Bool × Bool) : Bool :=
  muxGate (muxGate a b sel.2) (muxGate c d sel.2) sel.1

-- 명세: 각 게이트가 "해야 하는 일"을 가장 단순한 형태로 적습니다.
def notSpec (a : Bool) : Bool := !a
def andSpec (a b : Bool) : Bool := a && b
def orSpec (a b : Bool) : Bool := a || b
def xorSpec (a b : Bool) : Bool := a != b
def muxSpec (a b sel : Bool) : Bool := if sel then b else a
def mux4Spec (a b c d : Bool) (sel : Bool × Bool) : Bool :=
  match sel with
  | (false, false) => a
  | (false, true)  => b
  | (true, false)  => c
  | (true, true)   => d

-- 정확성 증명. Bool은 원소가 둘뿐인 유한 타입이라 `decide`가 모든 입력 조합을 자동으로 확인합니다.
theorem notGate_correct : ∀ a, notGate a = notSpec a := by decide
theorem andGate_correct : ∀ a b, andGate a b = andSpec a b := by decide
theorem orGate_correct  : ∀ a b, orGate a b = orSpec a b := by decide
theorem xorGate_correct : ∀ a b, xorGate a b = xorSpec a b := by decide
theorem muxGate_correct : ∀ a b sel, muxGate a b sel = muxSpec a b sel := by decide
theorem mux4Gate_correct : ∀ a b c d sel, mux4Gate a b c d sel = mux4Spec a b c d sel := by decide

end Nand2Npu
----

[TIP]
====
*확인*: `lake env lean Gates/Basic.lean`을 실행했을 때 에러 없이 끝나면(출력이 아무것도 없으면) 6개 정리가 전부 증명된 것입니다. 하나라도 `sorry`가 남아있었다면 `declaration uses 'sorry'` 경고가 뜹니다.
====

`decide`가 왜 이걸 자동으로 해내는지 짚어둘 만합니다 — `∀ a b, andGate a b = andSpec a b`는 원칙적으로 무한히 많은 증명 대상처럼 보이지만, `Bool`이 `{true, false}` 두 값뿐인 `DecidableEq` 타입이라 Lean4는 이 전칭 명제를 "2×2=4가지 조합을 전부 계산해서 확인"하는 결정 절차로 바꿀 수 있습니다. 이 트릭은 입력 폭이 좁을 때(여기서는 최대 4비트)만 통하고, 2장에서 16비트 폭으로 넘어가면 `decide`가 2^16^가지를 전부 도는 건 현실적이라도(수 초 내로 끝남), 2^32^ 이상으로 커지면 `induction`으로 넘어가야 합니다 — 이건 2장에서 실제로 마주치게 됩니다.

== 3. MLIR 텍스트 방출기 (`Gates/Emit.lean`)

게이트 정의를 실제 MLIR 텍스트로 바꾸는 함수를 작성합니다. CIRCT의 `comb`/`hw` dialect 문법을 그대로 문자열로 조립합니다 — Lean4에서 MLIR C++ API를 FFI로 직접 호출하는 대신, *텍스트를 생성해 파일로 쓰고 그 파일을 CIRCT 도구에 넘기는* 방식을 씁니다. 이 방식이 `lean4-mlir-codegen` 시리즈 3편에서 다룬 접근이고, 실습 관점에서도 훨씬 간단합니다 — Lean4 쪽 신뢰 기반이 "문자열을 올바르게 조립했는가"로 좁혀지기 때문입니다.

[source,lean]
----
-- Gates/Emit.lean
namespace Nand2Npu

def emitAndGate : String :=
"hw.module @and_gate(in %a: i1, in %b: i1, out y: i1) {
  %0 = comb.and %a, %b : i1
  hw.output %0 : i1
}"

def emitOrGate : String :=
"hw.module @or_gate(in %a: i1, in %b: i1, out y: i1) {
  %0 = comb.or %a, %b : i1
  hw.output %0 : i1
}"

def emitXorGate : String :=
"hw.module @xor_gate(in %a: i1, in %b: i1, out y: i1) {
  %0 = comb.xor %a, %b : i1
  hw.output %0 : i1
}"

def emitMuxGate : String :=
"hw.module @mux_gate(in %a: i1, in %b: i1, in %sel: i1, out y: i1) {
  %0 = comb.mux %sel, %b, %a : i1
  hw.output %0 : i1
}"

/-- 네 모듈을 하나의 MLIR 텍스트 파일로 합칩니다. -/
def emitAll : String :=
  String.intercalate "\n\n" [emitAndGate, emitOrGate, emitXorGate, emitMuxGate]

end Nand2Npu
----

`comb.and`/`comb.or`/`comb.xor`/`comb.mux`는 CIRCT가 이미 제공하는 조합 논리 연산자입니다 — 우리가 `andGate`를 NAND 두 번으로 정의했던 것과 달리, 방출 단계에서는 CIRCT의 표준 연산자를 직접 씁니다. 이게 안전한 이유는 2절의 `andGate_correct` 정리가 "게이트 *구현*"이 아니라 "게이트 *동작*"을 명세와 묶어뒀기 때문입니다 — NAND 두 번이든 `comb.and` 하나든, 진리표가 `andSpec`과 일치하기만 하면 방출 결과로는 등가입니다.

`Main.lean`에서 이 문자열을 표준출력으로 냅니다.

[source,lean]
----
-- Main.lean
import Gates.Emit

def main : IO Unit := IO.println Nand2Npu.emitAll
----

== 5. CIRCT로 SystemVerilog 방출하기

[source,bash]
----
circt-opt mlir/gates.mlir --export-verilog -o mlir/gates.sv
cat mlir/gates.sv
----

`--export-verilog`가 없는 구버전 CIRCT라면 두 단계로 나눠 실행합니다.

[source,bash]
----
circt-opt mlir/gates.mlir --lower-comb-to-hw --hw-legalize-modules -o mlir/gates.lowered.mlir
circt-translate mlir/gates.lowered.mlir --export-verilog -o mlir/gates.sv
----

결과로 나오는 `mlir/gates.sv`는 대략 다음과 같은 모습입니다.

[source,systemverilog]
----
module and_gate(
  input  a,
  input  b,
  output y
);
  assign y = a & b;
endmodule

module or_gate(
  input  a,
  input  b,
  output y
);
  assign y = a | b;
endmodule

module xor_gate(
  input  a,
  input  b,
  output y
);
  assign y = a ^ b;
endmodule

module mux_gate(
  input  a,
  input  b,
  input  sel,
  output y
);
  assign y = sel ? b : a;
endmodule
----

[TIP]
====
*확인*: 4개 `module` 선언이 있고, `assign` 문이 각각 `&`, `|`, `^`, `? :`로 나옵니다. CIRCT 버전에 따라 포트에 `logic` 타입 키워드가 붙거나 안 붙을 수 있는데, 동작에는 차이가 없습니다.
====

== 6. Verilator로 진리표 검증하기

방출된 SystemVerilog가 실제로 `andSpec`(2절)과 같은 진리표를 내는지, Lean4 증명과 별개로 시뮬레이터로도 직접 확인합니다. 이게 5장에서 본격적으로 쓸 "번역 검증"의 가장 단순한 형태 — 전수 조사 시뮬레이션입니다.

[source,cpp]
----
// sim/tb_and_gate.cpp
#include "Vand_gate.h"
#include "verilated.h"
#include <cstdio>
#include <cstdlib>

int main(int argc, char** argv) {
    Verilated::commandArgs(argc, argv);
    auto* dut = new Vand_gate;
    int failures = 0;

    for (int a = 0; a <= 1; ++a) {
        for (int b = 0; b <= 1; ++b) {
            dut->a = a;
            dut->b = b;
            dut->eval();
            int expected = a & b;
            if (dut->y != expected) {
                std::printf("FAIL: a=%d b=%d expected=%d got=%d\n", a, b, expected, dut->y);
                ++failures;
            } else {
                std::printf("ok:   a=%d b=%d -> y=%d\n", a, b, dut->y);
            }
        }
    }
    delete dut;
    if (failures > 0) { std::printf("%d FAILURES\n", failures); return 1; }
    std::printf("ALL 4 CASES PASSED\n");
    return 0;
}
----

[source,bash]
----
cd sim
verilator --cc --exe --build ../mlir/gates.sv tb_and_gate.cpp \
  --top-module and_gate -Mdir obj_dir_and
./obj_dir_and/Vand_gate
----

기대되는 출력:

[source,text]
----
ok:   a=0 b=0 -> y=0
ok:   a=0 b=1 -> y=0
ok:   a=1 b=0 -> y=0
ok:   a=1 b=1 -> y=1
ALL 4 CASES PASSED
----

`or_gate`, `xor_gate`, `mux_gate`도 같은 패턴(`tb_or_gate.cpp` 등)으로 테스트벤치를 복사해 `expected` 계산식만 바꾸면 됩니다. `mux_gate`는 입력이 3개(`a`, `b`, `sel`)라 반복문이 하나 더 필요합니다.

[TIP]
====

== 7. 왜 이 전수 조사가 "번역 검증"인가

2절의 Lean4 증명(`andGate_correct` 등)은 *Lean4 안에서 정의한 함수들* 사이의 동치를 보장합니다. 하지만 `circt-opt`가 MLIR 텍스트를 SystemVerilog로 바꾸는 과정, 그리고 Verilator가 그 SystemVerilog를 C++ 시뮬레이션 코드로 바꾸는 과정은 Lean4 증명의 사정거리 밖에 있습니다 — 둘 다 우리가 작성하지 않은 외부 도구입니다. 6절의 전수 조사는 정확히 이 간극, 즉 "Lean4가 옳다고 증명한 것을 CIRCT와 Verilator가 실제로도 같은 것으로 만들어냈는가"를 검사합니다. 입력이 1~3비트뿐인 이 장에서는 전수 조사가 몇 줄짜리 반복문으로 충분하지만, 2장에서 16비트 가산기로 넘어가면 2^33^가지 조합을 전부 도는 건 현실적이지 않습니다 — 5장에서 무작위 샘플링과 SMT 기반 검증으로 이 방법을 확장합니다.

== 이 장에서 확정한 것

* Lean4/CIRCT/Verilator 툴체인을 설치하고, `lake` 프로젝트 구조를 세웠습니다.
* NAND 하나에서 NOT/AND/OR/XOR/Mux/4-way Mux까지, `sorry` 없이 `decide`로 끝까지 증명했습니다.
* 게이트 정의를 MLIR 텍스트로 방출하고, `circt-opt`로 실제 SystemVerilog 파일을 만들어냈습니다.
* Verilator 테스트벤치로 방출된 회로의 진리표를 전수 조사해, Lean4 증명 밖에 있는 CIRCT·Verilator 두 도구에 대한 최소한의 신뢰를 확보했습니다.

다음 장에서는 이 게이트들을 조합해 비트를 더하는 회로 — 반가산기, 전가산기, 16비트 가산기, ALU — 를 만듭니다. 입력 폭이 커지면서 `decide`가 더 이상 통하지 않는 지점을 마주치고, 귀납 증명으로 넘어갑니다.
