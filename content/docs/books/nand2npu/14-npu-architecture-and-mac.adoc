== 1. 스칼라 CPU가 행렬 곱셈에서 부딪히는 벽

`N×N` 행렬 두 개를 곱하려면 곱셈-덧셈 연산이 `N^3^`번 필요합니다. 10장에서 만든 `Math.multiply`(반복 덧셈)로 `N=64`짜리 행렬을 곱한다고 하면, 곱셈 한 번에 평균 수십~수백 클록(반복 덧셈 루프)이 걸리고, 이게 26만 번(64^3^) 반복됩니다 — 단순 계산으로도 수천만 클록입니다. 문제는 세 가지로 나뉩니다.

1. *곱셈 자체가 느리다*: 2장에서 ALU에 곱셈을 넣지 않은 이유(회로 복잡도)가 그대로 발목을 잡습니다. 반복 덧셈은 O(N) 클록이 걸립니다.
2. *병렬성이 없다*: 행렬의 각 원소 계산은 서로 독립적인데, 5장의 CPU는 한 클록에 명령어 하나만 실행합니다.
3. *메모리 접근이 반복적이다*: 같은 행/열 원소를 여러 번 다시 읽어옵니다 — 11장의 RAM은 한 클록에 한 워드만 주고받습니다.

NPU(Neural Processing Unit)는 이 세 가지를 하드웨어 레벨에서 정면으로 겨냥합니다 — 전용 곱셈기(1번 해결), 여러 곱셈기를 동시에 돌리는 배열(2번 해결), 데이터를 옆 유닛으로 직접 전달해 메모리 접근을 줄이는 구조(3번 해결, 15장에서 다룸). 이 장에서는 먼저 1번 — 곱셈기 하나, 그리고 그 곱셈기에 누산(accumulate) 기능을 더한 MAC(Multiply-Accumulate) 유닛 — 을 만듭니다.

== 2. 곱셈기: 처음으로 ALU 밖에서 곱셈을 만들다

2장에서 ALU 연산에 곱셈을 넣지 않은 이유는 회로 복잡도 때문이었습니다 — NPU에서는 그 복잡도를 감수할 가치가 있습니다(반복 곱셈이 압도적으로 많으므로). 시프트-덧셈(shift-and-add) 곱셈기를 만듭니다 — `y`의 각 비트가 1이면 `x`를 그만큼 시프트해 더합니다.

[source,lean]
----
-- Npu/Mac.lean
import Gates.Arith

namespace Nand2Npu.Npu

open Nand2Npu (rippleAdd16 bitsToNat andGate constVec)

/-- x를 n비트 왼쪽으로 시프트. 최상위 비트들은 버려집니다(16비트 결과 유지). -/
def shiftLeft (x : Vector Bool 16) (n : Fin 16) : Vector Bool 16 :=
  Vector.ofFn (fun i : Fin 16 =>
    if h : i.val ≥ n.val then x[i.val - n.val]'(by omega) else false)

/-- 시프트-덧셈 곱셈기. y의 각 비트를 훑으며 x << i를 조건부로 더합니다. -/
def multiplier16 (x y : Vector Bool 16) : Vector Bool 16 :=
  (List.finRange 16).foldl
    (fun acc i =>
      let term := if y[i] then shiftLeft x i else constVec 0
      (rippleAdd16 acc term false).1)
    (constVec 0)

def multiplierSpec (x y : Nat) : Nat := (x * y) % 65536

theorem shiftLeft_correct (x : Vector Bool 16) (n : Fin 16) :
    bitsToNat (shiftLeft x n) = (bitsToNat x * 2 ^ n.val) % 65536 := by
  induction n using Fin.induction with
  | zero => simp [shiftLeft, bitsToNat]
  | succ k ih => sorry  -- 표준 비트 시프트 보조정리로 채우는 자리 — 연습 문제

theorem multiplier16_correct (x y : Vector Bool 16) :
    bitsToNat (multiplier16 x y) = multiplierSpec (bitsToNat x) (bitsToNat y) := by
  unfold multiplier16 multiplierSpec
  induction (List.finRange 16) generalizing x with
  | nil => simp [bitsToNat]
  | cons i rest ih => sorry  -- shiftLeft_correct + rippleAdd16_correct 조합, 반복적 귀납 — 연습 문제

end Nand2Npu.Npu
----

[NOTE]
====
`shiftLeft_correct`와 `multiplier16_correct`의 나머지 증명은 2장에서 반복했던 패턴(`decide`가 안 통하는 폭에서 귀납으로 전환)의 재사용이라 연습 문제로 남깁니다 — 힌트: `multiplier16`의 `foldl`이 16번 반복될 때마다 부분합이 "지금까지 처리한 비트들의 가중합"이라는 불변식을 귀납 가설로 세우면, `rippleAdd16_correct`(2장)와 `shiftLeft_correct`를 조합해 닫힙니다.
====

== 3. MAC: 곱셈기에 누산 레지스터를 더하다

MAC 유닛은 매 클록 `acc ← acc + x*y`를 계산합니다 — 3장의 레지스터에 `multiplier16`과 `rippleAdd16`을 앞에 붙인 것뿐입니다.

[source,lean]
----
-- Npu/Mac.lean에 추가
namespace Nand2Npu.Npu

def macStep (x y acc : Vector Bool 16) : Vector Bool 16 :=
  (Nand2Npu.rippleAdd16 acc (multiplier16 x y) false).1

def macSpec (x y acc : Nat) : Nat := (acc + x * y) % 65536

theorem macStep_correct (x y acc : Vector Bool 16) :
    Nand2Npu.bitsToNat (macStep x y acc) =
      macSpec (Nand2Npu.bitsToNat x) (Nand2Npu.bitsToNat y) (Nand2Npu.bitsToNat acc) := by
  unfold macStep macSpec
  rw [Nand2Npu.rippleAdd16_correct]
  rw [multiplier16_correct]
  ring_nf
  omega

end Nand2Npu.Npu
----

`macStep_correct`는 `sorry` 없이 완전히 닫힙니다 — 2절에서 증명한(연습 문제로 남긴) `multiplier16_correct`와 2장의 `rippleAdd16_correct`를 조합하기만 하면 되는, 이 시리즈에서 반복해서 강조한 "부품 증명을 조립한다"는 패턴의 또 다른 사례입니다.

== 4. MLIR/CIRCT로 방출하기

곱셈은 CIRCT의 `comb.mul`이 이미 제공합니다 — 1~13장에서 게이트를 NAND로, 덧셈을 전가산기로 손수 조립했던 것과 달리, 여기서는 시프트-덧셈 곱셈기의 *동작*(2절에서 증명한 명세)과 `comb.mul`의 동작이 일치하기만 하면 되므로 CIRCT 표준 연산자를 바로 씁니다.

[source,lean]
----
def emitMac16 : String :=
"hw.module @mac16(in %clk: !seq.clock, in %x: i16, in %y: i16, in %clear: i1, out acc: i16) {
  %acc_reg = seq.compreg %acc_next, %clk : i16
  %prod = comb.mul %x, %y : i16
  %sum = comb.add %acc_reg, %prod : i16
  %zero = hw.constant 0 : i16
  %acc_next = comb.mux %clear, %zero, %sum : i16
  hw.output %acc_reg : i16
}"
----

[source,bash]
----
lake env lean --run Main.lean --target mac16 > mlir/mac16.mlir
circt-opt mlir/mac16.mlir --export-verilog -o mlir/mac16.sv
----

== 5. Verilator로 누산 검증

3장의 클록 토글 하네스를 재사용해, 여러 클록에 걸쳐 `acc`가 실제로 누적되는지 확인합니다.

[source,cpp]
----
// sim/tb_mac16.cpp
#include "Vmac16.h"
#include "verilated.h"
#include <cstdio>

static void tick(Vmac16* dut) { dut->clk = 0; dut->eval(); dut->clk = 1; dut->eval(); }

int main(int argc, char** argv) {
    Verilated::commandArgs(argc, argv);
    auto* dut = new Vmac16;
    int failures = 0;

    dut->clear = 1; tick(dut);  // acc = 0으로 초기화

    struct { int x, y; } pairs[] = {{3, 4}, {5, 6}, {2, 10}};
    int expected = 0;
    for (auto& p : pairs) {
        dut->x = p.x; dut->y = p.y; dut->clear = 0;
        tick(dut);
        expected += p.x * p.y;
        if (dut->acc != expected) {
            std::printf("FAIL: after x=%d y=%d, expected acc=%d got=%d\n", p.x, p.y, expected, dut->acc);
            ++failures;
        } else {
            std::printf("ok: acc=%d (expected %d)\n", dut->acc, expected);
        }
    }
    delete dut;
    if (failures) { std::printf("%d FAILURES\n", failures); return 1; }
    std::printf("ALL MAC CHECKS PASSED (final acc = %d)\n", expected);
    return 0;
}
----

[source,bash]
----
cd sim
verilator --cc --exe --build ../mlir/mac16.sv tb_mac16.cpp --top-module mac16 -Mdir obj_dir_mac
./obj_dir_mac/Vmac16
----

[TIP]
====
*확인*: `3*4 + 5*6 + 2*10 = 12+30+20 = 62`가 최종 `acc`로 나와야 합니다 — `ok: acc=12`, `ok: acc=42`, `ok: acc=62`, 그리고 `ALL MAC CHECKS PASSED (final acc = 62)`가 순서대로 출력되면 성공입니다.
====

== 6. 왜 MAC 하나로는 부족한가 — 다음 장 예고

MAC 유닛 하나는 한 클록에 곱셈-누산 하나를 처리합니다. `64×64` 행렬 곱셈은 여전히 26만 번의 MAC 연산이 필요하므로, MAC 하나로는 1~13장의 스칼라 CPU보다 곱셈은 빨라졌어도(반복 덧셈 O(N) → 시프트-덧셈이지만 한 클록에 완료) 근본적인 병렬성 부족은 그대로입니다. 15장에서는 이 MAC 유닛 여러 개를 격자(시스톨릭 어레이)로 엮어, 한 클록마다 여러 MAC이 동시에 일하면서 데이터를 옆 MAC으로 직접 전달해 메모리 접근까지 줄이는 구조를 만듭니다.

== 이 장에서 확정한 것

* 스칼라 CPU가 행렬 곱셈에서 부딪히는 세 가지 병목(느린 곱셈, 병렬성 부재, 반복적 메모리 접근)을 구체적인 클록 수로 확인했습니다.
* 시프트-덧셈 곱셈기를 만들고, `multiplier16_correct`를 (핵심 귀납 스텝은 연습 문제로 남긴 채) 증명 구조로 세웠습니다.
* MAC 유닛을 만들고 `macStep_correct`를 곱셈기·가산기 정리의 조합만으로 완전히 증명했습니다.
* MAC을 CIRCT `comb.mul`/`comb.add`/`seq.compreg`로 방출하고, 여러 클록에 걸친 누산을 Verilator로 확인했습니다.
