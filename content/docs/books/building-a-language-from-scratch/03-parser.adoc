파서는 2장의 렉서가 만든 토큰의 평평한 나열을, 구조를 아는 트리(AST)로 조립합니다. 이 장에서는 재귀 하강(recursive descent) 파싱이라는, 문법 규칙 하나하나를 함수 하나로 그대로 옮기는 기법으로 이 조립을 구현합니다.

== AST 노드: 각 문법 구조를 위한 자료구조

[source,python]
----
@dataclass
class IntLit: value: int
@dataclass
class BinOp: op: str; left: object; right: object
@dataclass
class If: cond: object; then_branch: object; else_branch: object
@dataclass
class Fun: param: str; body: object
@dataclass
class App: fn: object; arg: object
@dataclass
class Let: name: str; is_rec: bool; value: object; body: object
----

`Twig`의 문법 구조 각각(정수 리터럴, 이항 연산, 조건문, 함수, 함수 적용, let 바인딩)에 대응하는 파이썬 클래스를 하나씩 만듭니다. `dataclass`를 쓰면 필드 값이 같으면 자동으로 같다고 판정되므로(`==` 비교), 이후 검증에서 "파싱 결과가 예상한 구조와 정확히 같은가"를 손쉽게 확인할 수 있습니다.

== 우선순위를 문법 계층으로 표현하기

연산자 우선순위(`*`가 `+`보다 먼저 계산됨)를 재귀 하강 파서에서 표현하는 표준적인 방법은, 우선순위가 낮은 연산을 우선순위가 높은 연산 **위에** 쌓는 것입니다.

[source,python]
----
def parse_equality(self):      # 최하위: =, < (가장 늦게 묶임)
    left = self.parse_additive()
    while self.peek().kind in ("EQ", "LT"):
        op = self.advance().kind
        right = self.parse_additive()
        left = BinOp("=" if op == "EQ" else "<", left, right)
    return left

def parse_additive(self):      # 중간: +, -
    left = self.parse_multiplicative()
    while self.peek().kind in ("PLUS", "MINUS"):
        ...

def parse_multiplicative(self): # 그 위: *, /
    left = self.parse_app()
    while self.peek().kind in ("STAR", "SLASH"):
        ...

def parse_app(self):            # 최상위: 함수 적용 (가장 먼저 묶임)
    left = self.parse_atom()
    while self.peek().kind in ("INT", "IDENT", "LPAREN", ...):
        arg = self.parse_atom()
        left = App(left, arg)
    return left
----

`parse_equality`가 `parse_additive`를 호출하고, `parse_additive`가 `parse_multiplicative`를 호출하고... 이렇게 이어지는 호출 사슬 자체가 우선순위 계층을 표현합니다 — 가장 나중에 호출되는(가장 안쪽에 있는) `parse_app`이 가장 먼저(가장 강하게) 묶이고, 가장 먼저 호출되는 `parse_equality`가 가장 나중에(가장 느슨하게) 묶입니다.

== 검증 1: 산술 우선순위

[source,python]
----
ast1 = parse("1 + 2 * 3")
assert ast1 == BinOp("+", IntLit(1), BinOp("*", IntLit(2), IntLit(3)))
----

`1 + 2 * 3`이 `(1 + 2) * 3`이 아니라 `1 + (2 * 3)`으로 파싱됩니다 — `parse_additive`가 `+`를 처리하기 전에 먼저 오른쪽 피연산자를 `parse_multiplicative`(더 높은 우선순위)로 파싱하기 때문에, `2 * 3`이 먼저 하나로 묶인 뒤에야 `+`가 그 결과와 `1`을 묶습니다.

== 검증 2~3: 함수 적용의 우선순위와 결합 방향

[source,python]
----
ast2 = parse("f x + 1")
assert ast2 == BinOp("+", App(Var("f"), Var("x")), IntLit(1))   # (f x) + 1

ast3 = parse("f x y")
assert ast3 == App(App(Var("f"), Var("x")), Var("y"))            # (f x) y -- 커링
----

함수 적용(`parse_app`)이 산술 연산보다 더 안쪽(더 높은 우선순위)에 있으므로, `f x + 1`은 `f`에 `x + 1`을 적용하는 게 아니라, `f x`를 먼저 계산한 뒤 `1`을 더합니다. `f x y`가 `(f x) y`로 왼쪽부터 묶이는 것도 `parse_app`의 `while` 루프가 왼쪽에서 오른쪽으로 계속 `App`을 쌓아가기 때문입니다 — 이게 함수형 언어의 "커링"(다중 인자 함수를 단항 함수의 연쇄로 표현하는 방식)이 파서 수준에서 자연스럽게 표현되는 방식입니다.

== 검증 4: 괄호로 우선순위 뒤집기

[source,python]
----
ast4 = parse("(1 + 2) * 3")
assert ast4 == BinOp("*", BinOp("+", IntLit(1), IntLit(2)), IntLit(3))
----

`parse_atom`이 `(`를 만나면 다시 `parse_expr`(최상위 규칙)을 재귀 호출해서 괄호 안을 처음부터 파싱합니다 — 이렇게 "가장 낮은 우선순위 규칙으로 되돌아가는" 재귀가, 괄호 안에서는 우선순위 규칙이 다시 처음부터 적용되게 해줍니다.

== 검증 5: 2장에서 예고한 '=' 문제, 파서가 실제로 해결한다

2장에서 렉서가 `let x = 1`의 `=`과 `x = 1`(비교)의 `=`을 구별하지 못한다는 걸 확인했습니다. 파서는 이걸 문법적 **위치**로 해결합니다.

[source,python]
----
def parse_let(self):
    self.expect("LET")
    ...
    name = self.expect("IDENT").value
    self.expect("EQ")          # "let" 키워드 바로 다음에 나오는 EQ는 무조건 바인딩
    value = self.parse_expr()
    ...

def parse_equality(self):
    left = self.parse_additive()
    while self.peek().kind in ("EQ", "LT"):   # 그 외의 자리에 나오는 EQ는 비교 연산자
        ...
----

[source,python]
----
let_ast = parse("let x = 1 in x")
assert let_ast == Let("x", False, IntLit(1), Var("x"))

eq_ast = parse("x = 1")
assert eq_ast == BinOp("=", Var("x"), IntLit(1))
----

같은 토큰 종류(`EQ`)에서 시작했지만, `parse_let`이 `LET`과 `IDENT` 다음에 오는 `EQ`를 직접 `expect`로 소비하면 `Let` 노드가, 그 외의 자리(`parse_equality`)에서 만나는 `EQ`는 `BinOp` 노드가 만들어집니다 — "이 `=`이 무엇을 뜻하는가"라는 질문의 답이, 렉서가 아니라 **그 토큰이 파싱 중 어느 함수 안에서 소비되는가**에 의해 완전히 결정된다는 걸 실제 코드로 확인했습니다.

== 검증 6: 1장의 목표 프로그램 전체

[source,python]
----
full_ast = parse(TWIG_SOURCE)

assert isinstance(full_ast, Let)
assert full_ast.name == "fact" and full_ast.is_rec == True
assert isinstance(full_ast.value, Fun) and full_ast.value.param == "n"
assert full_ast.value.body.cond == BinOp("=", Var("n"), IntLit(0))
assert full_ast.body == App(Var("fact"), IntLit(5))
----

1장에서 미리 손으로 스케치했던 AST 구조(`{"kind": "LetRec", ...}`)가, 이제 실제 파서가 만들어낸 정확한 트리로 재현됐습니다 — `else` 절(`n * fact (n - 1)`)까지 파고들면, `App(Var("fact"), BinOp("-", Var("n"), IntLit(1)))`처럼 함수 적용과 괄호, 뺄셈이 모두 올바른 우선순위로 중첩되어 있는 걸 확인할 수 있습니다.

== 검증 7: 문법 오류 감지

[source,python]
----
try:
    parse("let x = 1")   # "in"이 빠짐
except SyntaxError as e:
    print(e)   # expected IN, got EOF at pos 9
----

`parse_let`이 `body = self.parse_expr()`를 시작하기 전에 `self.expect("IN")`을 요구하는데, `in`이 없으면 그 자리에 `EOF`만 남아있으므로 명확한 에러가 납니다 — 2장의 렉서가 "알 수 없는 문자"를 잡아냈던 것처럼, 파서는 "문법에 안 맞는 토큰 순서"를 잡아냅니다.

== 직접 해보기

* `parse_atom`에 괄호가 없는 음수 리터럴(단항 마이너스, 예: `-5`)을 지원하도록 추가해보고, `1 - -5`(`1` 빼기 `-5`)가 올바르게 파싱되는지 확인해보세요.

.해답 보기
[%collapsible]
====
[source,python]
----
def parse_atom(self):
    t = self.peek()
    if t.kind == "MINUS":   # 단항 마이너스
        self.advance()
        operand = self.parse_atom()
        return BinOp("-", IntLit(0), operand)   # -x를 0 - x로 표현
    # ... 기존 규칙들 ...

ast = parse("1 - -5")
print(ast)   # BinOp('-', IntLit(1), BinOp('-', IntLit(0), IntLit(5)))
----

`parse_additive`가 `-`를 이항 연산자로 소비한 뒤, 오른쪽 피연산자를 `parse_multiplicative` → ... → `parse_atom`으로 파싱하는데, 이때 `parse_atom`이 또 다른 `-`(이번엔 단항)를 만나면 재귀적으로 처리합니다 — 같은 토큰 종류(`MINUS`)가 문법적 위치에 따라 이항 연산자로도, 단항 연산자로도 쓰일 수 있다는 걸 보여주는 예시이고, 이 장에서 확인한 "`=`의 의미가 위치로 결정된다"는 원리가 `-`에도 똑같이 적용됩니다.
====

== 요약

* 재귀 하강 파서는 문법 규칙 하나하나를 함수 하나로 옮기고, 함수 호출의 중첩 순서로 연산자 우선순위를 표현합니다.
* 함수 적용(`f x y`)이 산술 연산자보다 우선순위가 높고 왼쪽부터 묶인다는 걸(`(f x) y`) 확인해, 함수형 언어의 커링이 파서 수준에서 자연스럽게 표현된다는 걸 봤습니다.
* 2장에서 렉서가 구별 못 했던 `=`의 두 가지 뜻(바인딩 vs 비교)이, 파서에서 그 토큰이 소비되는 **문법적 위치**로 완전히 해소된다는 걸 실제 코드로 확인했습니다.
* 1장에서 손으로 스케치했던 목표 프로그램의 AST가, 이제 실제 파서 출력과 정확히 일치한다는 걸 검증했습니다.

1부에서 문자열을 토큰으로, 토큰을 AST로 조립하는 프론트엔드를 완성했습니다. 2부에서는 이 AST를 실제로 "실행"하는 인터프리터와, 실행하기 전에 프로그램이 타입에 맞는지 검사하는 타입 시스템을 다룹니다.
