렉서(lexer, 또는 스캐너)는 소스 코드라는 하나의 긴 문자열을, 언어의 "단어"에 해당하는 토큰들의 나열로 쪼갭니다 — `"let x = 1"`이라는 문자열을 `[LET, IDENT("x"), EQ, INT(1)]`처럼 분류된 조각들로 바꾸는 일입니다. 이 장에서는 이 변환을 정규식으로 실제 구현합니다.

== 토큰 명세: 각 종류의 토큰이 어떻게 생겼는지

[source,python]
----
TOKEN_SPEC = [
    ("WS",      r"[ \t\n]+"),
    ("COMMENT", r"--[^\n]*"),
    ("ARROW",   r"->"),
    ("INT",     r"\d+"),
    ("IDENT",   r"[a-zA-Z_][a-zA-Z0-9_]*"),
    ("EQ",      r"="),
    ("PLUS",    r"\+"),
    ("MINUS",   r"-"),
    # ...
]
----

순서가 중요합니다 — `ARROW`(`->`)가 `MINUS`(`-`)보다 먼저 검사돼야, `->`를 보고 `MINUS` 하나와 알 수 없는 문자로 잘못 쪼개지 않습니다. 여러 패턴을 하나의 정규식으로 합쳐서(`"|".join(...)`), 매 위치에서 가장 먼저 매치되는 규칙을 고릅니다.

== 키워드는 식별자의 특별한 경우

[source,python]
----
KEYWORDS = {"let", "rec", "in", "fun", "if", "then", "else", "true", "false"}

if kind == "IDENT" and text in KEYWORDS:
    kind = text.upper()   # "let" -> LET, "if" -> IF, ...
----

`let`, `if` 같은 키워드를 위한 별도의 정규식을 만들지 않고, 일단 `IDENT`(식별자) 규칙에 매치시킨 뒤 그 텍스트가 키워드 집합에 있으면 종류만 바꿔치기합니다 — 이렇게 하면 `IDENT`와 키워드 규칙 사이의 순서 문제(둘 다 알파벳으로 시작하니 정규식만으로는 겹칠 수 있음)를 아예 피할 수 있습니다.

== 검증 1: 단순한 프로그램

[source,python]
----
toks = tokenize("1 + 2")
print(toks)   # [INT(1), PLUS('+'), INT(2), EOF(None)]
assert [t.kind for t in toks] == ["INT", "PLUS", "INT", "EOF"]
----

모든 토큰 나열 끝에 `EOF`(파일 끝) 토큰을 하나 더 붙여둡니다 — 3장의 파서가 "더 이상 토큰이 없다"는 걸 명시적으로 알 수 있게 해주는 장치입니다.

== 검증 2: 키워드로 시작하지만 키워드가 아닌 식별자

[source,python]
----
toks2 = tokenize("let letter = if5")
print(toks2)
# [LET('let'), IDENT('letter'), EQ('='), IDENT('if5'), EOF(None)]
assert toks2[1].kind == "IDENT"   # "letter"는 "let"으로 시작하지만 식별자
assert toks2[3].kind == "IDENT"   # "if5"도 "if"로 시작하지만 식별자
----

`letter`가 `LET` + `ter`로 잘못 쪼개지지 않는 이유는, 정규식 `[a-zA-Z_][a-zA-Z0-9_]*`이 **가능한 한 긴** 매치를 우선하기 때문입니다 — `let`까지만 매치하고 멈추는 게 아니라 `letter` 전체를 하나의 토큰으로 소비한 뒤에야 그 결과가 키워드 집합에 있는지 검사합니다.

== 검증 3: 1장의 목표 프로그램을 실제로 토큰화하기

[source,python]
----
tokens = tokenize(TWIG_SOURCE)
kinds = [t.kind for t in tokens]
print(kinds)
----

[source]
----
['LET', 'REC', 'IDENT', 'EQ', 'FUN', 'IDENT', 'ARROW', 'IF', 'IDENT', 'EQ', 'INT',
 'THEN', 'INT', 'ELSE', 'IDENT', 'STAR', 'IDENT', 'LPAREN', 'IDENT', 'MINUS', 'INT',
 'RPAREN', 'IN', 'IDENT', 'INT', 'EOF']
----

== 1장의 미리보기가 틀렸던 지점

1장에서는 `let ... =`의 `=`를 `EQ`로, `if n = 0`의 `=`(같음 비교)를 `EQEQ`로 서로 다른 토큰인 것처럼 미리 적어뒀습니다. 하지만 실제로 렉서를 구현하면서 확인해보니 — 이건 애초에 렉서가 구별할 수 없는 구분이었습니다.

[source,python]
----
num_eq = kinds.count("EQ")
print(num_eq)                    # 2
assert "EQEQ" not in kinds        # 1장의 EQEQ는 실제로는 존재하지 않는 토큰이었다
----

렉서는 소스 코드를 **글자 단위로만** 봅니다 — `let x = 1`의 `=`과 `if n = 0`의 `=`은 둘 다 그냥 문자 `=` 하나일 뿐이고, "이게 바인딩인지 비교인지"는 그 `=`이 문장의 어느 위치에 있는지(문법적 맥락)를 알아야만 판단할 수 있습니다. 렉서는 아직 문법(구조)을 전혀 모르는 단계이므로, 이 구별은 원리적으로 렉서의 책임이 아닙니다. 실제 ML 계열 언어(OCaml 등)도 정확히 이렇게 설계합니다 — `=`는 항상 같은 토큰이고, `let ... = ...`와 `a = b`(비교)를 구별하는 건 3장에서 만들 파서(문법 규칙)의 몫입니다. 1장의 "미리보기"가 아직 구현하기 전이라 이런 세부사항을 놓쳤던 것이고, 실제로 만들어보고서야 이 사실이 드러났습니다 — 이 책에서 반복해서 강조하는, 미리 그려둔 설계도가 실제 구현 앞에서 틀렸다고 밝혀지는 흔한 경우입니다.

== 검증 4: 주석 처리

[source,python]
----
toks_comment = tokenize("1 -- this is a comment\n+ 2")
assert [t.kind for t in toks_comment] == ["INT", "PLUS", "INT", "EOF"]
----

`--`로 시작해서 줄바꿈까지 이어지는 주석이 토큰 목록에서 완전히 사라집니다 — `WS`(공백)와 마찬가지로, 매치되면 토큰을 만들지 않고 건너뜁니다.

== 검증 5: 알 수 없는 문자에서 명확한 에러

[source,python]
----
try:
    tokenize("1 @ 2")
    assert False
except SyntaxError as e:
    print(e)   # lexer error at position 2: '@ 2'
----

`@`는 어떤 토큰 규칙에도 매치되지 않으므로, 조용히 무시하거나 이상한 토큰을 만드는 대신 명확한 `SyntaxError`를 냅니다 — 그리고 정확히 몇 번째 위치에서 문제가 생겼는지도 함께 알려줍니다. 이런 명확한 에러 위치 보고가, 나중에 이 언어로 실제 프로그램을 짤 때 오타를 빠르게 찾는 데 중요합니다.

== 직접 해보기

* `TOKEN_SPEC`에 `>=`, `<=` 같은 두 글자짜리 비교 연산자를 추가해보고, `<`(이미 있는 `LT`)와 순서 충돌 없이 잘 동작하는지 확인해보세요.

.해답 보기
[%collapsible]
====
[source,python]
----
TOKEN_SPEC_EXT = [
    ("WS", r"[ \t\n]+"), ("COMMENT", r"--[^\n]*"), ("ARROW", r"->"),
    ("GE", r">="), ("LE", r"<="),   # 반드시 GT/LT보다 먼저 와야 함
    ("INT", r"\d+"), ("IDENT", r"[a-zA-Z_][a-zA-Z0-9_]*"),
    ("EQ", r"="), ("LT", r"<"), ("GT", r">"),
    # ...
]
----

`>=`와 `<=`를 `GT`/`LT`보다 **먼저** 등록해야 합니다 — 그렇지 않으면 `>=`를 만났을 때 `GT`(`>`) 규칙이 먼저 매치되어 `>`와 `=` 두 개의 토큰으로 잘못 쪼개집니다. 이건 2장 서두에서 `ARROW`를 `MINUS`보다 먼저 둔 것과 정확히 같은 원리입니다 — **여러 글자로 된 토큰은 항상 그 접두사가 되는 짧은 토큰보다 먼저 검사돼야** 합니다. 이 순서 규칙을 잊으면, 렉서가 에러 없이 조용히 잘못된 토큰을 만들어내는(그래서 나중에 파서 단계에서야 이상한 에러로 나타나는) 까다로운 버그가 생깁니다.
====

== 요약

* 정규식 여러 개를 하나로 합쳐서, 매 위치에서 가장 먼저 매치되는 규칙으로 소스 문자열을 토큰으로 쪼갰습니다.
* 키워드는 별도 규칙이 아니라 식별자 규칙에 매치된 뒤 텍스트로 재분류하는 방식으로, 정규식 순서 문제를 피했습니다.
* 1장에서 미리 상상했던 `EQ`/`EQEQ` 구분이 실제로는 렉서가 할 수 없는 일이라는 걸 발견했고, 그 구별은 파서의 책임이라는 걸 깨달았습니다 — 실제 ML 계열 언어들의 설계와 일치하는 결론입니다.
* 여러 글자로 된 토큰(`->`, `>=`)은 그 접두사가 되는 짧은 토큰보다 항상 먼저 검사해야 한다는 실전 규칙도 확인했습니다.
