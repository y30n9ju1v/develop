== 1. 서문의 약속을 지킬 시간

서문에서 이렇게 적었습니다 — "그 유연성의 대가가 어디서, 왜 생기는지를 9장에서 구조적으로 짚어볼 것입니다." 이 장에서 그 약속을 지킵니다 — 다만 8장에서 이미 "워크로드에 따라 다르다"는 걸 봤으니, 이 장은 그 절반(분기 없는 반복 연산에서는 NPU가 왜 항상 이기는가)에 집중합니다 — 3권 2장의 `3×3` 행렬 곱셈(`A × I = A`, 단위행렬 검증)을 이 2권의 GPU 코어로도 똑같이 돌린다고 했을 때, 3권의 고정 기능 시스톨릭 어레이와 클록 수가 왜 근본적으로 갈릴 수밖에 없는지를 짚습니다. 정확한 배수를 재는 실측 벤치마크(구체적인 파이프라인 깊이, 실제 Verilator 사이클 카운트)는 이 시리즈의 범위 밖으로 남기고, 그 대신 *구조적으로 항상 이 방향일 수밖에 없는 이유*를 정리로 못박는 데 집중합니다.

== 2. 같은 문제, 두 가지 하드웨어

[cols="1,2,2"]
|===
| |3권의 NPU(고정 기능) |이 2권의 GPU(프로그램 가능)

|무엇을 실행하는가
|`matmul` 전용 회로 — 명령어 페치·디코드 없음
|커널 프로그램(7장의 `tiledMatmul`) — 매 스텝 명령어를 페치·디코드

|데이터가 도착하는 방법
|이웃 PE에서 배선으로 직접 전달(3권 2장의 시스톨릭 흐름)
|공유 메모리에서 명시적으로 읽음(4장의 `scatterWrite`/`read`)

|`3×3` 곱셈에 걸리는 클록(대략)
|`2N-1 = 5`클록(3권 2장에서 유도한 `T = i+j+N-1`)
|명령어 페치·디코드·마스크 평가가 매 MAC 앞에 붙어, 같은 연산 하나당 수 클록씩 추가 — 9개 MAC이면 대략 그 몇 배
|===

정확한 배수는 이 SIMT 코어의 파이프라인 깊이(명령어 페치에 몇 클록이 걸리는지)에 달려 있어 이 시리즈에서 고정된 숫자로 못박지는 않습니다 — 대신 *왜* GPU 쪽이 항상 더 걸릴 수밖에 없는지를 구조적으로 짚습니다.

== 3. 왜 항상 GPU가 느릴 수밖에 없는가: 오버헤드의 위치

[source,lean]
----
namespace Nand2Npu.Gpu

/-- GPU 경로에서 MAC 연산 하나에 드는 총 클록 = 오버헤드(페치+디코드+마스크 평가) + MAC 자체.
    NPU 경로에서는 오버헤드가 0입니다(회로가 애초에 MAC만 함). -/
def gpuMacCycles (overhead : Nat) : Nat := overhead + 1  -- MAC 자체는 1클록(3권 1장)
def npuMacCycles : Nat := 1  -- 오버헤드 없음, MAC만

/-- overhead가 0보다 크기만 하면(실전에서는 명령어 페치 자체가 최소 1클록이므로 항상 그렇습니다),
    같은 개수의 MAC을 실행할 때 GPU 경로가 NPU 경로보다 항상 더 걸립니다. -/
theorem npu_always_faster_for_pure_matmul (n overhead : Nat) (hn : n > 0) (hover : overhead > 0) :
    n * npuMacCycles < n * gpuMacCycles overhead := by
  unfold gpuMacCycles npuMacCycles
  nlinarith

end Nand2Npu.Gpu
----

이 정리 자체는 산술적으로 아주 단순합니다 — 요점은 수식의 어려움이 아니라, *이 오버헤드가 어디서 오는지*입니다. GPU 코어는 "다음에 무슨 명령어를 실행할지"를 매번 다시 물어야 합니다(그래야 `vectorAdd`든 `tiledMatmul`이든 *어떤* 커널이든 돌릴 수 있으니까요). NPU는 그 질문 자체가 없습니다 — 회로가 태어날 때부터 "항상 MAC만 한다"고 배선되어 있기 때문입니다. **유연성은 "다음에 뭘 할지 매번 다시 결정할 수 있다"는 능력이고, 그 결정 자체가 시간을 씁니다.** 이게 서문에서 예고했던 대가의 정체입니다.

[NOTE]
====
이 비교가 "그러니 GPU는 쓸모없다"는 뜻은 전혀 아닙니다 — `npu_always_faster_for_pure_matmul`의 전제가 정확히 "*순수 행렬 곱셈만* 반복할 때"입니다. 커널이 `vectorAdd`, 조건 분기가 있는 필터링, 서로 다른 크기의 연산이 섞인 파이프라인처럼 *바뀔 수 있다*면, NPU는 아예 그 일을 못 하거나(회로가 그 연산을 지원하지 않으므로) 매번 새 칩을 다시 만들어야 합니다. 이 장이 보여주는 건 "특화가 항상 이긴다"가 아니라 "**워크로드가 고정되어 있고 반복적일수록** 특화의 이득이 커진다"는, 훨씬 좁고 정확한 주장입니다.
====

== 4. 이 2권에서 새로 TCB에 들어온 것

[cols="1,3,1"]
|===
|층 |무엇을 확인했나(또는 가정/연습 문제로 남겼나) |1권 13장 대비 새로운 성격

|1장 (레인)
|`lane_result_independent_of_others`는 완전 증명
|여러 개의 독립된 상태 기계를 동시에 다루는 첫 사례 — 아직은 서로 무관해 증명이 쉬움

|2장 (발산)
|`divergent_if_correct`는 완전 증명
|정확성은 증명되지만 **성능**은 증명 대상이 아니라는 것이 처음 명시적으로 갈라짐

|3장 (워프 스케줄러)
|`no_warp_starves`는 뼈대 증명(모듈러 산술은 연습 문제)
|이 시리즈에서 처음 등장하는 "여러 클록에 걸친(liveness)" 성질

|4장 (공유 메모리)
|`scatterWrite_correct`는 조건부 증명(뱅크 충돌 없음을 가정)
|자원 공유가 시작되며 레인 간 독립성이 더 이상 공짜가 아니게 됨

|6장 (배리어)
|`divergent_barrier_deadlocks`는 완전 증명 — 이번엔 "안전하지 않음"을 증명
|증명이 처음으로 "이 프로그램은 교착된다"는 부정적 결론에 쓰임

|7장 (커널 컴파일러)
|마스크가 달린 새 IR 설계는 연습 문제로 남김
|기존 IR을 재사용할 수 없어 처음으로 새 중간 표현이 필요해짐

|8장 (에지 검출 캡스톤)
|새 정리 없음 — 이미 검증된 부품(2·4장)의 조립만으로 완결
|이 시리즈에서 처음으로 "새 증명이 필요 없다는 것 자체"가 결론인 장 — 부품 증명이 충분히 쌓이면 조립만으로 새 워크로드를 얻는다는 걸 실증
|===

== 5. 1권부터 여기까지, 그리고 3권으로

1권 13장의 원칙 — "작은 폭은 전수 조사, 큰 폭은 귀납", "작은 층부터 검증해 올라간다" — 은 이 2권에서도 그대로였습니다. 다만 이 2권에서 처음 두드러진 건 **증명의 방향이 두 갈래로 갈렸다는 것**입니다 — `no_warp_starves`처럼 "이건 항상 안전하다"를 보여주는 증명과, `divergent_barrier_deadlocks`처럼 "이건 항상 위험하다"를 보여주는 증명이 이 2권 안에 나란히 있습니다. 1권과 3권은 거의 전부 전자(안전성 증명)였는데, 프로그램 가능한 하드웨어를 다루는 순간부터 "프로그래머가 무엇을 잘못 쓸 수 있는가"도 증명 가능한 질문이 된다는 걸 이 2권이 보여줍니다.

그리고 2절의 비교와 8장의 에지 검출을 나란히 놓으면 이 2권의 결론이 완성됩니다 — "GPU가 낫다"도 "NPU가 낫다"도 아니라, **워크로드의 모양이 승자를 결정한다**는 것입니다. 분기 없이 같은 연산을 반복하는 작업(행렬 곱셈)은 고정 기능이 항상 이기고, 데이터에 따라 매번 다르게 갈리는 작업(에지 검출)은 애초에 고정 기능으로는 표현조차 안 됩니다. 프로젝트 이름(nand2npu)이 가리키는 진짜 종착점은 그중 전자 — *행렬 곱셈 하나에 극한까지 특화된* 고정 기능 하드웨어입니다. 이 2권에서 "왜 범용으로는 이 워크로드에서 손해를 보는가"를 직접 짚어봤으니, link:../../nand2npu-vision/[3권]에서 그 손해를 없애기 위해 유연성을 걷어낸 NPU를 만드는 이유가 이제 구조적으로 뒷받침됩니다.

이 2권은 여기서 마칩니다. 1권의 스칼라 CPU 위에서 여러 레인이 동시에 일하는 법, 발산과 스케줄링과 동기화를 다루는 법을 게이트에서부터 증명·방출·검증했습니다. 3권에서는 그 유연성을 의도적으로 버리고, 이 2권이 정량화한 바로 그 오버헤드를 제거하는 데까지 나아갑니다.
