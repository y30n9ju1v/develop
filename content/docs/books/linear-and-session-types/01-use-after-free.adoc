== 타입 시스템이 못 잡는 버그

`lean4-program-semantics`나 `type-driven-design` 같은 이 사이트의 다른 책들이 다룬 타입 시스템은 전부 **"값이 몇 번 쓰이는가"에 관심이 없습니다.** 정수 하나를 두 번 읽어도, 함수 인자를 세 번 참조해도, 아예 한 번도 안 써도 타입 시스템은 신경 쓰지 않습니다. 이게 보통은 아무 문제가 없습니다 — 정수를 두 번 읽는다고 뭐가 잘못되지는 않으니까요.

문제는 값이 **자원(resource)** 을 표현할 때 생깁니다. 파일 핸들, 소켓, 뮤텍스 락, 한 번 쓰고 버려야 하는 메모리 블록 같은 것들입니다. 의사 코드로 다음을 봅시다.

[source,python]
----
f = open("data.txt")
close(f)
read(f)          # 버그: 이미 닫힌 파일을 또 읽음 (use-after-free 계열)
----

[source,python]
----
lock(mutex)
unlock(mutex)
unlock(mutex)    # 버그: 이미 풀린 락을 또 풂 (double-free 계열)
----

두 버그 모두 "값 `f`(또는 `mutex`)를 정해진 횟수보다 더 많이 썼다"는 공통점이 있습니다. `f`는 `close` 이후로는 **더 이상 존재하지 않는 것**으로 취급되어야 하는데, 변수 이름은 여전히 스코프에 남아 있어서 프로그램이 계속 그걸 참조할 수 있습니다 — 컴파일러가 "이 변수, 이미 다 썼는데요"라고 말해줄 방법이 보통의 타입 시스템에는 없습니다.

== 반대 방향의 버그: 아예 안 쓰는 것

값을 너무 많이 쓰는 것만 문제가 아닙니다. 값을 **아예 쓰지 않는 것**도 실제 버그입니다.

[source,python]
----
conn = open_connection()
result = compute(42)
return result
# conn을 한 번도 close하지 않음 — 연결이 계속 열려 있는 자원 누수(leak)
----

`conn`이 스코프를 벗어나도 아무도 그걸 닫아주지 않습니다(파이썬의 가비지 컬렉터는 메모리는 회수해도, "닫아야 한다"는 자원의 의미는 모릅니다). 이것도 "변수 사용 횟수"에 대한 규칙으로 잡을 수 있는 종류의 버그입니다 — 이번엔 "0번 이하로 쓰였다"는 게 문제입니다.

== 이 책이 세울 규칙: 정확히 한 번

두 버그를 하나의 규칙으로 묶을 수 있습니다.

> 선형 타입을 가진 값은 정확히 한 번 쓰여야 한다 — 두 번 이상도, 0번도 안 된다.

이 규칙을 타입 체커가 강제하면, `close(f)` 다음에 `read(f)`를 쓰는 프로그램은 **타입 검사 단계에서 거부됩니다** — 실행해서 크래시가 나거나, 운 좋게 넘어가거나 하는 게 아니라, 컴파일이 안 됩니다. `conn`을 안 닫고 반환하는 프로그램도 마찬가지로 거부됩니다.

이게 Rust의 소유권 시스템이 하는 일의 이론적 핵심입니다 — `let f = File::open(...)`; 다음에 `drop(f)`(또는 스코프 종료)가 일어나면 `f`는 "이동(move)"되어 더 이상 쓸 수 없는 값이 되고, 컴파일러가 이후의 모든 사용을 컴파일 타임에 거부합니다. Rust는 이 아이디어를 실전 언어 수준으로 정교하게 다듬었지만(빌림 `&`/`&mut`, 라이프타임 등), 그 밑바탕에 있는 이론은 이 책에서 지을 것보다 그리 복잡하지 않습니다.

== "정확히 한 번"을 어떻게 타입 시스템에 새길까

핵심 아이디어는 단순합니다 — **변수 컨텍스트(context)를 쪼갠다.** 보통의 람다계산법에서 `f a`(함수 `f`를 인자 `a`에 적용)를 타입 검사할 때는, `f`와 `a`가 **같은** 변수 컨텍스트 `Γ` 아래서 각각 타입 검사됩니다 — `x`가 `Γ`에 있으면 `f`도, `a`도 자유롭게 `x`를 쓸 수 있습니다.

선형 타입 시스템에서는 다릅니다. `f a`를 타입 검사하려면, 전체 컨텍스트 `Γ`를 **서로 겹치지 않는 두 조각** `Γ1`과 `Γ2`로 쪼개서, `f`는 `Γ1`만 갖고 타입 검사하고 `a`는 `Γ2`만 갖고 타입 검사합니다. `x`가 `Γ1`에 있다면 `Γ2`에는 없으므로, `f`와 `a` **둘 다**가 `x`를 쓰는 건 애초에 불가능합니다 — 컨텍스트를 나눠 가진 시점에 이미 "겹쳐 쓰기"가 봉쇄됩니다.

이 "컨텍스트 쪼개기"가 이 책 전체의 핵심 메커니즘입니다. 다음 장에서 이걸 실제 타이핑 규칙으로 씁니다.

== 요약

* 보통의 타입 시스템은 "값이 몇 번 쓰이는가"에 관심이 없어서, 자원을 두 번 쓰거나(use-after-free, double-free 계열) 아예 안 쓰는(leak) 버그를 잡지 못합니다.
* 이 두 버그는 "선형 타입을 가진 값은 정확히 한 번 쓰여야 한다"는 하나의 규칙으로 묶을 수 있습니다.
* 이 규칙을 타입 체커에 새기는 핵심 메커니즘은 **컨텍스트 쪼개기** — 함수와 인자처럼 나란히 놓인 두 부분식이 변수 컨텍스트를 서로 겹치지 않게 나눠 가지도록 강제하는 것입니다.
