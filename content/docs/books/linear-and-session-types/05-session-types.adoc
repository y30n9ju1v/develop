1~4부에서 지은 선형 타입 시스템은 "값 하나"의 사용 횟수를 추적했습니다. 이 장부터는 그 아이디어를 확장합니다 — 값 하나 대신, **채널 하나 위에서 오가는 메시지들의 전체 순서**를 타입으로 추적합니다. 이게 **세션 타입(session type)** 입니다.

== 프로토콜도 타입이다

클라이언트-서버 통신을 상상해봅시다 — "클라이언트가 숫자를 보내면, 서버가 그걸 두 배로 만들어 돌려보내고, 끝난다." 이건 자연어로는 명확하지만, 보통의 타입 시스템으로는 표현할 방법이 마땅치 않습니다 — 소켓의 타입은 그냥 "정수를 보내고 받을 수 있는 것" 정도일 뿐, **순서**(먼저 보내고 그다음 받는다)는 타입에 전혀 나타나지 않습니다. 순서를 지키는지는 순전히 개발자의 머릿속과 문서에만 있습니다 — 정확히 1장에서 다룬 "규칙은 있지만 컴파일러가 강제 안 해주는" 상황의 또 다른 사례입니다.

세션 타입은 이 순서 자체를 타입으로 만듭니다.

[source,lean]
----
-- payload type fixed to Nat for every message, to keep this development small;
-- a real system indexes each send/recv with its own payload type (see chapters 1-2).
inductive SType where
  | send (cont : SType)
  | recv (cont : SType)
  | «end»
----

`SType`은 "이 채널의 한쪽 끝에서, 다음에 무슨 일이 일어나야 하는가"를 말합니다 — `.send S`는 "메시지 하나를 보내고, 그다음엔 `S`가 명세하는 대로 계속한다", `.recv S`는 "메시지 하나를 받고, 그다음엔 `S`", `.end`는 "더 이상 아무 일도 없다, 끝"입니다. (이 책에서는 메시지의 페이로드 타입을 전부 `Nat`으로 고정해서 Lean 개발 분량을 줄입니다 — 실전 세션 타입은 `send`/`recv`마다 서로 다른 페이로드 타입을 붙일 수 있고, 2장에서 지은 `Ty`를 그대로 끼워 넣으면 직접 확장할 수 있습니다.)

클라이언트-서버 예제의 클라이언트 쪽 타입은 이렇게 씁니다.

[source,lean]
----
def ProtoS : SType := .send (.recv .end)   -- "보내고, 그다음 받고, 끝"
----

== 듀얼리티: 통신의 양쪽은 서로의 거울

`ProtoS`는 클라이언트가 지켜야 할 규칙입니다. 그런데 **서버**가 지켜야 할 규칙은 정확히 그 반대여야 합니다 — 클라이언트가 보낼 때 서버는 받아야 하고, 클라이언트가 받을 때 서버는 보내야 합니다. 이 "정확히 반대"라는 관계를 함수로 씁니다.

[source,lean]
----
def dual : SType → SType
  | .send S => .recv (dual S)
  | .recv S => .send (dual S)
  | .end => .end
----

`dual`은 `send`와 `recv`를 맞바꾸면서 재귀적으로 안으로 파고듭니다. `dual ProtoS`를 손으로 계산해보면 `.recv (.send .end)`가 나옵니다 — "받고, 그다음 보내고, 끝". 정확히 서버가 해야 할 일입니다.

듀얼리티에서 반드시 확인해야 할 성질이 하나 있습니다 — **두 번 뒤집으면 원래대로 돌아온다**는 것입니다(그렇지 않으면 "duality"라는 이름이 무색해집니다).

[source,lean]
----
theorem dual_involutive : ∀ S, dual (dual S) = S
  | .send S => by simp [dual, dual_involutive S]
  | .recv S => by simp [dual, dual_involutive S]
  | .end => rfl
----

`SType`의 구조를 그대로 따라가는 구조적 귀납법으로, 각 생성자마다 `dual`의 정의를 한 번 펼치고 재귀적으로 안쪽에 귀납 가설을 적용하면 끝입니다 — `SType`에는 우리가 2~4장에서 계속 씨름했던 "컨텍스트를 쪼개는" 복잡함이 전혀 없어서(세션 타입은 변수 컨텍스트가 아니라 채널 하나의 프로토콜만 추적하므로), 증명이 훨씬 짧고 매끄럽습니다. 이 정리는 Lean이 `sorryAx` 없이 그대로 받아들였습니다.

== 다음 장 예고

`SType`은 아직 "명세"일 뿐입니다 — 실제로 이 명세를 지키며 통신하는 **프로그램**(프로세스)이 있어야 하고, 그 프로그램이 명세를 어기면 타입 검사에서 거부되어야 합니다. 다음 장에서 이걸 만듭니다.

== 요약

* 세션 타입(`SType`)은 채널 하나 위에서 "다음에 보낼지 받을지, 그리고 그다음엔 뭘 하는지"라는 프로토콜 전체를 타입으로 명세합니다.
* `dual` 함수가 통신의 양쪽 끝이 서로 정확히 반대(보내면 받고, 받으면 보내는) 관계여야 한다는 걸 표현하고, `dual_involutive` 정리로 "두 번 뒤집으면 원래대로"라는 성질을 증명했습니다.
* 컨텍스트 쪼개기가 필요 없는 세션 타입의 증명이, 2~4장의 선형 람다계산법보다 훨씬 매끄럽게 Lean으로 완성됐다는 것도 확인했습니다.

다음 장에서는 이 `SType`을 실제로 지키며 실행되는 프로세스(`Proc`)와 타입 판정(`HasSType`)을 짓고, 두 프로세스가 채널로 실제 통신하는 것을 리덕션 규칙으로 모델링합니다.
