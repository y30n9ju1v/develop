Progress는 "아직 안 죽었다"는 것만 말해줍니다. 실행이 실제로 **의미 있는** 방향으로 나아간다는 걸 보이려면, 한 스텝 실행해도 타입이 바뀌지 않는다는 **Preservation**(타입 보존)이 필요합니다.

> Preservation: `HasType Γ e τ`이고 `Step e e'`이면, `HasType Γ e' τ`이다.

== 왜 이게 선형 시스템에서 특히 어려운가

`beta` 규칙(`Step (.app (.lam x τ body) v) (subst x v body)`)의 타입 보존을 증명하려면, "몸체에 인자를 대입해도 타입이 유지된다"는 **대입 보조정리(substitution lemma)** 가 필요합니다. 보통의(선형이 아닌) 람다계산법이라면 이렇게 씁니다.

> `Γ, x:τ1 ⊢ e : τ2`이고 `Γ ⊢ v : τ1`이면, `Γ ⊢ [v/x]e : τ2`이다.

`Γ`가 양쪽에 그대로 남아있다는 게 핵심입니다 — 보통의 시스템은 컨텍스트를 자유롭게 공유(weakening)할 수 있으니, `e`와 `v`가 같은 `Γ`를 나눠 갖든 말든 상관없습니다.

선형 시스템은 다릅니다. `x`의 바인딩이 `(x,τ1)::Γ`라는 컨텍스트 **어딘가**(꼭 맨 앞이 아니어도 됩니다 — `e`가 다시 `lam`이나 `letpair`로 새 바인더를 열면, 원래 `x`는 그 새 바인더 뒤로 밀려납니다) 에 있고, 이걸 떼어내면서 `Γ`의 나머지를 온전히 보존해야 합니다. 게다가 `v`를 대입해 넣는 자리가 `e`의 어느 서브텀인지(`app f a`라면 `f` 쪽인지 `a` 쪽인지)에 따라 컨텍스트가 어느 쪽으로 쪼개졌는지도 함께 추적해야 합니다.

이 장에서는 이 어려움을 실제로 시도하면서 확인합니다 — 정직하게 말하면, **완전히 일반적인 형태의 증명은 이 책에서 끝까지 마무리하지 않습니다.** 대신 두 가지를 합니다: (1) 증명을 실제로 얼마나 진행했고 정확히 어디서 케이스가 폭발하는지 보여주고, (2) 구체적인 두 프로그램(함수 호출과 순서쌍 분해)에 대해 실행 전후의 타입이 실제로 같다는 걸 Lean으로 직접 검증합니다.

== 시도: 일반적인 대입 보조정리

`x`가 컨텍스트의 아무 위치에나 있을 수 있다는 걸 표현하려면, "리스트를 세 조각으로 쪼갠다"는 형태가 필요합니다.

[source,lean]
----
theorem subst_gen : ∀ {Γ0 : Ctx} {e : Term} {τ : Ty}, HasType Γ0 e τ →
    ∀ {Γa Γb : Ctx} {x : String} {τ1 : Ty}, Γ0 = Γa ++ (x, τ1) :: Γb →
    x ∉ dom Γa → x ∉ dom Γb →
    ∀ {v : Term}, HasType [] v τ1 → HasType (Γa ++ Γb) (subst x v e) τ
----

`e`의 타이핑 유도 구조를 따라 귀납법을 돌리면, `lam` 갈래에서는 예상대로 잘 풀립니다 — 새 바인더 `(y,τa)`를 컨텍스트 맨 앞에 붙이기만 하면 `x`의 위치는 그대로 한 칸 뒤로 밀리고, `(y,τa)::Γa ++ (x,τ1)::Γb`와 `(y,τa)::(Γa++(x,τ1)::Γb)`가 `List.cons_append`로 정확히 같은 모양임을 이용해 귀납 가설을 곧바로 적용할 수 있습니다.

문제는 `app`(그리고 `pair`, `letpair`) 갈래입니다. `Γ0 = Γ1 ++ Γ2`이고 동시에 `Γ0 = Γa ++ (x,τ1)::Γb`이므로, **`x`가 `Γ1`과 `Γ2` 중 어느 쪽에 있었는지**를 먼저 알아내야 합니다. 이건 리스트 등식 하나를 분해하는 별도의 보조정리가 필요합니다.

[source,lean]
----
theorem append_eq_append_cons {Γ1 Γ2 Γa Γb : Ctx} {x : String} {τ1 : Ty}
    (h : Γ1 ++ Γ2 = Γa ++ (x, τ1) :: Γb) :
    (∃ Γa1, Γa = Γ1 ++ Γa1 ∧ Γ2 = Γa1 ++ (x, τ1) :: Γb) ∨
    (∃ Γb1, Γ1 = Γa ++ (x, τ1) :: Γb1 ∧ Γb = Γb1 ++ Γ2) := by
  induction Γ1 generalizing Γa with
  | nil => left; exact ⟨Γa, by simpa using h, by simpa using h⟩
  | cons hd tl ih =>
      cases Γa with
      | nil => right; refine ⟨tl, ?_, ?_⟩ <;> simp_all
      | cons hd' tl' =>
          simp only [List.cons_append, List.cons.injEq] at h
          obtain ⟨heq, htail⟩ := h
          subst heq
          rcases ih htail with ih' | ih'
          · left; obtain ⟨Γa1, e1, e2⟩ := ih'; exact ⟨Γa1, by simp [e1], e2⟩
          · right; obtain ⟨Γb1, e1, e2⟩ := ih'; exact ⟨Γb1, by simp [e1], e2⟩
----

이 보조정리는 `Γ1` 위에서 리스트 귀납으로 실제로 증명됩니다(정직하게 말해 이 자체는 완성했습니다). 진짜 벽은 `app` 갈래를 마저 완성하려는 순간에 나타납니다 — `x`가 예를 들어 `Γ2`(인자 `a`) 쪽에 있었다고 결정됐다면, 함수 `f`는 `x`와 무관하니 **`subst x v f = f`여야** 하는데, `subst`는 항 구조를 그냥 재귀적으로 훑기 때문에 이 사실 자체가 별도의 보조정리입니다.

> Substitution 무관성: `HasType Γ e τ`이고 `x ∉ dom Γ`이면, 임의의 `v`에 대해 `subst x v e = e`이다.

이것도 `e`의 구조를 따라가는 또 하나의 귀납 증명이고, 그 증명 안에서 다시 `app`/`pair`/`letpair`를 만나면 또 컨텍스트를 어느 쪽으로 쪼갰는지 따라가야 합니다 — 결국 **세 개의 상호 얽힌 귀납 증명**(대입 보조정리, 리스트 분해 보조정리, 대입 무관성 보조정리)이 서로를 필요로 하는 구조가 됩니다. 이건 실제로 선형/구조 제한 타입 시스템(substructural type system) 문헌에서 표준으로 다뤄지는 결과입니다(Walker의 substructural type systems 챕터, 또는 Wadler의 "Propositions as Sessions" 부록 등) — 하지만 지금 이 세 보조정리를 전부 Lean으로 끝까지 완성하는 건 이 한 장의 분량을 훌쩍 넘는 별도의 프로젝트가 됩니다. 여기서는 정직하게 이 지점에서 멈추고, 대신 구체적인 사례로 Preservation을 검증합니다.

== 검증: 함수 호출 하나

[source,lean]
----
def fact_like : Term := .app (.lam "x" .unit (.var "x")) .unit

example : HasType [] fact_like .unit := by
  apply HasType.app [] [] _ _ .unit .unit (by intro _ h; cases h)
  · exact HasType.lam "x" .unit .unit [] (.var "x") (by simp [dom]) (HasType.var "x" .unit)
  · exact HasType.unit

example : Step fact_like .unit :=
  Step.beta "x" .unit (.var "x") .unit rfl

-- 실행 전: HasType [] fact_like .unit   (위에서 보임)
-- 실행 후: HasType [] .unit .unit       (HasType.unit, 자명)
example : HasType [] .unit .unit := HasType.unit
----

`(λx:Unit. x) ()`은 타입 `Unit`을 갖고, `beta` 규칙으로 `()`(타입도 `Unit`)로 한 스텝 나아갑니다 — 실행 전후 타입이 똑같이 `Unit`입니다.

== 검증: 순서쌍을 분해하는 프로그램

이번엔 `letpair`가 관여하는, `x`와 `y` **둘 다** 실제로 쓰는 프로그램으로 확인합니다.

[source,lean]
----
-- letpair (x, y) = (identity, unit) in (x y)
def pair_prog : Term :=
  .letpair "x" "y" (.pair (.lam "z" .unit (.var "z")) .unit) (.app (.var "x") (.var "y"))

example : HasType [] pair_prog .unit := by
  apply HasType.letpair [] [] "x" "y" _ (.app (.var "x") (.var "y")) (.arrow .unit .unit) .unit .unit
    (by simp [dom]) (by simp [dom]) (by decide) (by intro _ h; cases h)
  · exact HasType.pair [] [] _ .unit (.arrow .unit .unit) .unit (by intro _ h; cases h)
      (HasType.lam "z" .unit .unit [] (.var "z") (by simp [dom]) (HasType.var "z" .unit)) HasType.unit
  · have := HasType.app [("x", .arrow .unit .unit)] [("y", .unit)] (.var "x") (.var "y") .unit .unit
      (by intro w hw; simp_all [dom]) (HasType.var "x" (.arrow .unit .unit)) (HasType.var "y" .unit)
    simpa using this

example : Step pair_prog
    (subst "y" .unit (subst "x" (.lam "z" .unit (.var "z")) (.app (.var "x") (.var "y")))) :=
  Step.letpairBeta "x" "y" (.lam "z" .unit (.var "z")) .unit (.app (.var "x") (.var "y")) rfl rfl

-- 두 번의 대입을 실제로 계산해보면 정확히 (λz.z) () 가 나옵니다 (`rfl`로 확인)
example : subst "y" .unit (subst "x" (.lam "z" .unit (.var "z")) (.app (.var "x") (.var "y")))
    = .app (.lam "z" .unit (.var "z")) .unit := rfl

-- 그리고 그 항은 위에서 이미 타입 Unit을 가진다는 걸 보인 fact_like와 (이름만 다를 뿐) 똑같습니다.
example : HasType [] (.app (.lam "z" .unit (.var "z")) .unit) .unit := by
  apply HasType.app [] [] _ _ .unit .unit (by intro _ h; cases h)
  · exact HasType.lam "z" .unit .unit [] (.var "z") (by simp [dom]) (HasType.var "z" .unit)
  · exact HasType.unit
----

`letpair`로 순서쌍을 분해해서 `x`(항등 함수)와 `y`(`()`) 둘 다 몸체(`x y`)에서 실제로 쓴 뒤, `letpairBeta`로 한 스텝 나아가면 두 번의 대입이 겹쳐 실행되어 정확히 `(λz. z) ()`가 됩니다(`rfl`로 계산이 맞다는 걸 확인) — 이건 3장에서 이미 다룬 `fact_like`와 이름만 다를 뿐 똑같은 항이므로, 타입 `Unit`을 유지한다는 게 곧바로 따라옵니다. 이 프로그램은 `x`와 `y`를 **둘 다** 정확히 한 번씩 쓰기 때문에(2장의 규칙을 지키므로) 애초에 타입 검사를 통과했다는 것도 다시 짚어둘 만합니다.

== 요약

* Preservation(실행해도 타입이 안 변한다)의 증명은 일반적으로 대입 보조정리가 필요한데, 선형 타입 시스템에서는 "대입할 변수가 컨텍스트의 어느 쪽 조각에 있었는지"까지 추적해야 해서 보통의 람다계산법보다 근본적으로 더 까다롭습니다.
* 이 어려움을 실제로 파고들어, 리스트를 세 조각으로 분해하는 보조정리(`append_eq_append_cons`, 이건 완전히 증명했습니다)까지는 도달했지만, 대입 보조정리 자체가 요구하는 "대입 무관성" 보조정리까지 합쳐 세 개의 상호 얽힌 귀납 증명이 필요하다는 걸 확인하고, 이 지점은 표준 문헌을 인용하는 것으로 정직하게 남겨뒀습니다.
* 대신 함수 호출 하나(`fact_like`)와 순서쌍을 분해해 두 변수를 모두 쓰는 프로그램(`pair_prog`)에 대해, 실행 전후의 타입이 정확히 같다는 걸 Lean으로 구체적으로 검증했습니다.

Progress(3장)와 이 장의 구체적인 Preservation 검증을 합치면, 2장에서 지은 타입 시스템이 "정확히 한 번 쓴다"는 약속을 실행 내내 지킨다는 그림이 완성됩니다. 3부에서는 이 선형성을 값 하나가 아니라 **두 프로세스 사이의 통신 프로토콜 전체**로 확장합니다 — 세션 타입입니다.
