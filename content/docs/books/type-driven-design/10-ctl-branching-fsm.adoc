== 지금까지의 한계: transition은 항상 결정적이었다

4장부터 써온 `transition : State → Event → State`는 **함수**입니다 — 같은 상태에서 같은 이벤트를 받으면 항상 같은 다음 상태로 갑니다. 그런데 실전의 많은 시스템은 이렇지 않습니다 — 네트워크 요청을 보내면 성공할 수도 유실될 수도 있고, 스레드 스케줄러가 다음에 어느 스레드를 돌릴지는 프로그램 코드만으로 결정되지 않습니다. 이런 **"다음 상태가 여러 개 있을 수 있는"** 시스템을 다루려면 함수 대신 **관계**가 필요합니다.

[source,lean]
----
inductive NetState where
  | idle | sent | acked | lost
deriving DecidableEq, Repr

def successors : NetState → List NetState
  | .idle => [.sent]
  | .sent => [.acked, .lost]   -- 전송하면 성공할 수도, 유실될 수도 있음
  | .acked => [.acked]
  | .lost => [.sent]
----

`successors : NetState → List NetState`가 "다음 상태가 될 수 있는 것들의 목록"을 반환합니다. `sent`에서는 `acked`도 `lost`도 다음 상태가 될 수 있다는 게 `[.acked, .lost]`에 드러나 있습니다 — 어느 쪽으로 갈지는 이 함수만으로는 결정되지 않습니다. 이런 시스템을 다루는 시제논리를 **CTL(Computation Tree Logic, 계산 트리 논리)**이라고 부릅니다 — 9장의 LTL이 "하나로 정해진 실행"을 다뤘다면, CTL은 "여러 갈래로 뻗어나가는 트리"를 다룹니다.

== EX와 AX: 한 스텝만큼의 두 가지 "다음"

[source,lean]
----
def EX (P : NetState → Prop) (s : NetState) : Prop :=
  ∃ s' ∈ successors s, P s'

def AX (P : NetState → Prop) (s : NetState) : Prop :=
  ∀ s' ∈ successors s, P s'

example : EX (· = .acked) .sent := ⟨.acked, by decide, rfl⟩
example : ¬ AX (· = .acked) .sent := by
  intro h
  have := h .lost (by decide)
  exact absurd this (by decide)
----

`EX`("Exists neXt")는 "다음 상태 중에 `P`를 만족하는 게 **하나라도** 있다"는 뜻이고, `AX`("for All neXt")는 "다음 상태 **전부**가 `P`를 만족한다"는 뜻입니다. `sent`에서 `EX (· = .acked)`는 참입니다(`acked`가 가능한 다음 상태 중 하나니까요) — 하지만 `AX (· = .acked)`는 거짓입니다(`lost`도 가능한 다음 상태인데 `acked`가 아니니까요). 이 둘의 차이가 CTL의 핵심입니다 — **"이럴 수도 있다"(EX)와 "무조건 이렇다"(AX)는 완전히 다른 주장**입니다.

== EF: 어떤 경로를 고르면 결국 도달할 수 있다

9장의 `Eventually`는 하나로 정해진 실행 위에서 "언젠가"를 물었습니다. 여기서는 실행이 여러 갈래이므로, "언젠가 도달한다"도 "**어떤 경로를 고르면** 결국 도달할 수 있는가"로 다시 정의해야 합니다.

[source,lean]
----
inductive Reachable : NetState → NetState → Prop where
  | refl (s : NetState) : Reachable s s
  | step (s s' target : NetState) (h1 : s' ∈ successors s) (h2 : Reachable s' target) :
      Reachable s target

def EF (P : NetState → Prop) (s : NetState) : Prop :=
  ∃ t, Reachable s t ∧ P t

example : EF (· = .acked) .idle := by
  refine ⟨.acked, ?_, rfl⟩
  apply Reachable.step .idle .sent .acked (by decide)
  apply Reachable.step .sent .acked .acked (by decide)
  exact Reachable.refl .acked
----

`Reachable s t`는 "`s`에서 출발해서 `successors`를 몇 번 따라가면 `t`에 도달할 수 있는 경로가 있다"는 뜻입니다 — `refl`이 "0번 이동"(이미 도착), `step`이 "한 번 이동하고 나머지는 재귀적으로"입니다. `EF (· = .acked) .idle`을 증명한다는 건 **"idle에서 시작해서, 적절한 선택을 하면 결국 acked에 도달하는 구체적인 경로가 존재한다"**는 뜻이고, 실제로 `idle → sent → acked`라는 경로를 손으로 제시해서 증명했습니다.

== AF는 왜 이 장에서 증명하지 않는가

`EF`의 짝인 `AF`("for All paths, eventually")는 "**어떤 경로를 골라도** 결국 `P`에 도달한다"는 훨씬 강한 주장입니다. 이 시스템에서 `AF (· = .acked) .sent`가 참인지 생각해봅시다 — `sent → lost → sent → lost → ...`처럼 **영원히 `lost`와 `sent`만 오가며 `acked`를 피하는 경로**를 매번 선택할 수 있습니다. 이 경로는 유한한 `Reachable` 증명(구체적인 경로 하나를 손으로 제시하는 것)으로는 다룰 수 없습니다 — 8~9장에서 본 생동성의 어려움이 여기서 "무한히 이어지는 경로가 여러 개 있고, 그중 하나라도 나쁘면 `AF`가 거짓"이라는 형태로 다시 나타난 것입니다. `AF`를 제대로 다루려면 "모든 무한 경로에 대한 정량화"가 필요한데, 이건 이 책의 범위를 넘어서는 본격적인 모델체킹 이론이라 맺음말에서 그 방향만 안내합니다.

== EF와 Eventually의 관계

`EF`가 `Reachable`(관계)을 쓰고 9장의 `Eventually`가 `trace`(함수)를 썼다는 차이가 있지만, 근본 아이디어는 같습니다 — **"어떤 조건을 만족하는 시점/상태가 존재한다"는 존재 양화**입니다. 시스템이 결정적(transition이 함수)이라면 "경로"가 하나뿐이라 `EF`와 `Eventually`가 사실상 같은 것을 묻게 되고, 비결정적(successors가 여러 개)이라면 `EF`가 "그 여러 경로 중 최소한 하나는 성공한다"는, LTL만으로는 표현 못 하는 질문을 추가로 물을 수 있게 해줍니다.

== 직접 해보기

* `NetState`에 새로운 상태 `giveUp`(포기)을 추가하고, `lost`에서 재전송(`sent`) 대신 `giveUp`으로도 갈 수 있게(`successors .lost = [.sent, .giveUp]`) 바꿔보세요.
* 그 수정된 시스템에서 `EF (· = .giveUp) .idle`이 참이라는 걸 증명해보세요(idle → sent → lost → giveUp 경로).

.해답 보기
[%collapsible]
====
[source,lean]
----
inductive NetState2 where
  | idle | sent | acked | lost | giveUp
deriving DecidableEq, Repr

def successors2 : NetState2 → List NetState2
  | .idle => [.sent]
  | .sent => [.acked, .lost]
  | .acked => [.acked]
  | .lost => [.sent, .giveUp]
  | .giveUp => [.giveUp]

inductive Reachable2 : NetState2 → NetState2 → Prop where
  | refl (s : NetState2) : Reachable2 s s
  | step (s s' target : NetState2) (h1 : s' ∈ successors2 s) (h2 : Reachable2 s' target) :
      Reachable2 s target

def EF2 (P : NetState2 → Prop) (s : NetState2) : Prop :=
  ∃ t, Reachable2 s t ∧ P t

example : EF2 (· = .giveUp) .idle := by
  refine ⟨.giveUp, ?_, rfl⟩
  apply Reachable2.step .idle .sent .giveUp (by decide)
  apply Reachable2.step .sent .lost .giveUp (by decide)
  apply Reachable2.step .lost .giveUp .giveUp (by decide)
  exact Reachable2.refl .giveUp
----
====

== 요약

* 다음 상태가 여러 개일 수 있는 비결정적 시스템은 `transition` 함수 대신 `successors : State → List State` 같은 관계로 표현합니다.
* `EX`("다음 중 하나라도")와 `AX`("다음 전부가")는 서로 다른 주장입니다 — 비결정적 시스템에서는 이 둘이 갈립니다.
* `EF`("어떤 경로를 고르면 결국")는 구체적인 유한 경로 하나를 제시하는 것으로 증명할 수 있지만, `AF`("어떤 경로를 골라도 결국")는 모든 무한 경로에 대한 주장이라 이 방식으로는 다룰 수 없습니다 — 본격적인 모델체킹이 필요한 지점입니다.

3부의 마지막 장에서는 지금까지 배운 모든 도구(sum/product, transition, 합성, LTL, CTL)를 동원해 새 FSM 하나를 처음부터 끝까지 설계·명세·증명하는 프로젝트를 진행합니다.
