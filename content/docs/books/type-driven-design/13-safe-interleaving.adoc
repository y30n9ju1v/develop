== 12장에서 미뤄둔 것: "번갈아 끼어든다"는 모델

12장에서 "이 책의 모든 FSM은 한 번에 이벤트 하나만 처리했다"며 동시성을 범위 밖으로 뒀습니다. 여기서 조금 더 나가봅니다 — 완전한 동시성 이론 대신, **"두 프로세스가 각자 진행하지만, 어느 쪽이 다음에 한 스텝 나아갈지는 스케줄러가 임의로 정한다"**는 인터리빙(interleaving) 모델 하나만 다룹니다. 이것만으로도 병렬 프로그래밍에서 가장 흔한 버그(레이스 컨디션)를 정확히 재현하고, 그걸 막는 설계까지 증명할 수 있습니다.

== 각 프로세스의 로컬 상태

두 프로세스가 공유 자원(임계 구역, critical section)에 접근하려 한다고 합시다. 각 프로세스는 세 상태를 오갑니다 — 안 씀(`idle`), 쓰고 싶음(`wantsCS`), 쓰는 중(`inCS`).

[source,lean]
----
inductive ProcState where
  | idle | wantsCS | inCS
deriving DecidableEq, Repr

inductive GlobalEvent where
  | move1 | move2   -- "다음엔 프로세스 1이(또는 2가) 한 스텝 나아간다"는 스케줄러의 선택
deriving DecidableEq, Repr
----

`GlobalEvent`가 이 장의 핵심 장치입니다 — 6장의 product 합성에서는 이벤트 하나가 들어오면 **두 기계가 동시에** 한 스텝씩 나아갔는데, 여기서는 `move1`/`move2` 중 **하나만** 골라 그 프로세스만 나아갑니다. 이벤트 목록이 `[move1, move2, move1, move1, ...]`처럼 어떤 순서로도 섞일 수 있다는 게 "임의 순서로 번갈아 끼어든다"는 걸 표현합니다.

== 순진한 버전: 락 없이 각자 진행

[source,lean]
----
def ProcState.localStep : ProcState → ProcState
  | .idle => .wantsCS
  | .wantsCS => .inCS
  | .inCS => .idle

def unsafeStep : (ProcState × ProcState) → GlobalEvent → (ProcState × ProcState)
  | (p1, p2), .move1 => (p1.localStep, p2)
  | (p1, p2), .move2 => (p1, p2.localStep)

def unsafeTrace (schedule : List GlobalEvent) : ProcState × ProcState :=
  schedule.foldl unsafeStep (.idle, .idle)

#eval unsafeTrace [.move1, .move1, .move2, .move2]
example : unsafeTrace [.move1, .move1, .move2, .move2] = (.inCS, .inCS) := by native_decide
----

각 프로세스가 서로를 전혀 신경 쓰지 않고 자기 규칙대로만 진행합니다. `[move1, move1, move2, move2]`라는 스케줄(프로세스 1이 `idle → wantsCS → inCS`까지 먼저 두 번 나아간 뒤, 프로세스 2도 같은 식으로 두 번 나아가는 순서)을 실제로 실행하면 **둘 다 동시에 `inCS`**가 됩니다 — 이게 레이스 컨디션입니다. 11장의 교차로에서 "동시 초록"이 사고였던 것과 정확히 같은 종류의 실패가, 이번엔 "락 없이 공유 자원에 접근"하는 형태로 재현됐습니다.

== 안전한 버전: 락을 상태에 포함시키기

11장에서 배운 교훈을 다시 적용합니다 — 두 부분이 서로 조율돼야 한다면, 독립된 product 대신 **공유 정보를 상태 자체에 포함**시킵니다.

[source,lean]
----
structure GlobalState where
  p1 : ProcState
  p2 : ProcState
  lockFree : Bool
deriving DecidableEq, Repr

def step1 (p : ProcState) (lockFree : Bool) : ProcState × Bool :=
  match p, lockFree with
  | .idle, lf => (.wantsCS, lf)
  | .wantsCS, true => (.inCS, false)    -- 락이 비어있으면 잡고 들어감
  | .wantsCS, false => (.wantsCS, false) -- 락이 잠겨있으면 대기(제자리)
  | .inCS, _ => (.idle, true)            -- 나가면서 락 반납

def safeStep : GlobalState → GlobalEvent → GlobalState
  | ⟨p1, p2, lf⟩, .move1 =>
      let (p1', lf') := step1 p1 lf
      ⟨p1', p2, lf'⟩
  | ⟨p1, p2, lf⟩, .move2 =>
      let (p2', lf') := step1 p2 lf
      ⟨p1, p2', lf'⟩

def safeTrace (schedule : List GlobalEvent) : GlobalState :=
  schedule.foldl safeStep ⟨.idle, .idle, true⟩

#eval safeTrace [.move1, .move1, .move2, .move2]
-- { p1 := inCS, p2 := wantsCS, lockFree := false }
----

`lockFree`가 두 프로세스 모두 접근할 수 있는 **공유 상태**입니다 — `step1`이 `wantsCS`에서 `inCS`로 가려 할 때 `lockFree`를 확인하고, 잠겨있으면 그 자리에 멈춥니다(`wantsCS`에 그대로 남음). 방금 전과 똑같은 스케줄(`[move1, move1, move2, move2]`)을 이 버전으로 돌리면, 프로세스 2는 `wantsCS`에서 멈추고 `inCS`에 못 들어갑니다 — 락을 프로세스 1이 아직 쥐고 있기 때문입니다.

== 안전성 증명: 8~9장의 패턴을 그대로 재사용

이제 "**어떤 스케줄을 고르든** 절대 둘 다 동시에 `inCS`일 수 없다"는 걸 증명합니다 — 방금 확인한 한 가지 스케줄이 아니라, 가능한 모든 인터리빙에 대해서입니다. 놀랍게도 이 증명은 8장(도어록의 불변식)과 완전히 같은 구조입니다.

[source,lean]
----
def Invariant (s : GlobalState) : Prop :=
  ¬ (s.p1 = .inCS ∧ s.p2 = .inCS) ∧
  (s.lockFree = false ↔ (s.p1 = .inCS ∨ s.p2 = .inCS))

theorem invariant_init : Invariant ⟨.idle, .idle, true⟩ := by
  unfold Invariant; simp

theorem invariant_preserved (s : GlobalState) (e : GlobalEvent) (h : Invariant s) :
    Invariant (safeStep s e) := by
  obtain ⟨hne, hiff⟩ := h
  cases s with
  | mk p1 p2 lf =>
    cases e <;> cases p1 <;> cases p2 <;> cases lf <;>
      simp_all [safeStep, step1, Invariant]

theorem invariant_holds_after_schedule (schedule : List GlobalEvent) :
    Invariant (safeTrace schedule) := by
  suffices h : ∀ s, Invariant s → Invariant (schedule.foldl safeStep s) by
    exact h ⟨.idle, .idle, true⟩ invariant_init
  intro s hs
  induction schedule generalizing s with
  | nil => exact hs
  | cons e es ih => exact ih (safeStep s e) (invariant_preserved s e hs)
----

`Invariant`는 "둘 다 동시에 `inCS`가 아니다"에 더해 "`lockFree`가 실제로 락 상태와 일치한다"(누가 임계 구역에 있으면 락은 잠겨있어야 하고, 그 역도 성립)는 조건을 함께 묶었습니다 — 두 번째 조건이 없으면 `lockFree`가 거짓말을 하는 경우까지 허용돼서 첫 번째 조건 자체를 귀납적으로 지킬 수 없습니다. `cases e <;> cases p1 <;> cases p2 <;> cases lf`가 가능한 모든 (이벤트, 상태) 조합을 나열하고, 그 각각에서 불변식이 유지된다는 걸 확인합니다 — `ProcState`가 세 값, `Bool`이 두 값이니 유한한 경우의 수라 전부 확인 가능합니다. `invariant_holds_after_schedule`이 8~9장에서 본 것과 똑같은 귀납 구조(한 스텝 보존 + 목록 길이에 대한 귀납법)로, **임의 길이의 스케줄**에 대해 이 성질을 증명합니다.

[source,lean]
----
example : ¬ ((safeTrace [.move1, .move1, .move2, .move2]).p1 = .inCS ∧
    (safeTrace [.move1, .move1, .move2, .move2]).p2 = .inCS) :=
  (invariant_holds_after_schedule _).1
----

이 성질은 방금 검사한 그 스케줄만이 아니라 **그 어떤 인터리빙에도** 성립합니다 — 스케줄러가 어떤 순서로 두 프로세스를 끼워넣든, 락이 그 순서와 무관하게 상호 배제를 지켜줍니다.

== 이 장이 실전에 주는 것

`lockFree : Bool`이라는 필드 하나와 "상태를 확인하고 조건부로만 전진한다"는 규칙이, 실제 뮤텍스(mutex)·세마포어가 하는 일의 핵심입니다. 이 장이 보여주려 한 건 새로운 동시성 이론이 아니라, **지금까지 배운 도구(sum/product 설계, transition 함수, 불변식 귀납 증명)가 인터리빙이라는 새 상황에도 그대로 적용된다**는 것입니다 — "두 부분이 조율돼야 하면 공유 상태로 묶는다"(11장)와 "한 스텝 보존을 증명하고 귀납법으로 확장한다"(8~9장)는 이 책 전체에서 반복된 패턴이, 병렬 프로그래밍의 가장 기본적인 안전성 문제에도 다시 등장했습니다.

물론 진짜 동시성(진짜로 동시에 실행되는 다중 코어, 메모리 가시성 문제, 락-프리 알고리즘)은 이 인터리빙 모델보다 훨씬 복잡합니다 — 이 장은 그 세계로 가는 첫걸음일 뿐, 12장에서 언급한 모델체킹 도구(TLA+ 등)가 정확히 그 복잡성을 다루기 위해 만들어진 것입니다.

== 직접 해보기

* 이 장의 `unsafeStep`(락 없는 버전)에 대해, "둘 다 동시에 `inCS`가 될 수 있는 스케줄이 존재한다"(방금 확인한 그 반례)를 `EF`(10장)로 표현할 수 있는지 생각해보세요 — `successors`를 어떻게 정의해야 할까요?
* `safeStep`에 프로세스를 하나 더 추가해(`p3 : ProcState`, `move3` 이벤트) 세 프로세스가 하나의 락을 공유하도록 확장하고, `Invariant`도 세 프로세스 버전으로 고쳐 여전히 상호 배제가 지켜지는지 확인해보세요.

== 요약

* "이벤트가 임의 순서로 번갈아 끼어든다"는 인터리빙 모델(`GlobalEvent = move1 | move2`)만으로도 레이스 컨디션을 정확히 재현할 수 있습니다 — 락 없는 설계는 실제로 두 프로세스가 동시에 임계 구역에 들어가는 스케줄이 존재합니다.
* 락을 공유 상태(`lockFree`)로 표현하고 각 프로세스의 전이가 그 상태를 확인·갱신하게 하면, 상호 배제를 설계로 보장할 수 있습니다.
* 이 안전성은 8~9장에서 쓴 것과 완전히 같은 증명 패턴(한 스텝 보존 + 귀납법)으로, 가능한 모든 인터리빙에 대해 증명됩니다 — 병렬 프로그래밍도 결국 이 책이 다룬 같은 도구로 다뤄지는 하나의 사례입니다.
