== 요구사항: 3회 실패하면 영구히 잠긴다

이번 사례는 실무에서 흔한 요구사항입니다 — 비밀번호를 3번 연속 틀리면, 도어록이 아예 반응을 멈춥니다(재부팅이나 관리자 개입 없이는 절대 안 풀림). 4장의 `DoorState`(locked/unlocked 둘뿐)로는 "몇 번 틀렸는지"를 셀 수 없으니, 상태를 다시 설계해야 합니다.

[source,lean]
----
inductive LockState where
  | locked (attempts : Nat)   -- 누적 실패 횟수를 상태 안에 담음
  | unlocked
  | jammed                    -- 3회 실패하면 도달, 여기서는 절대 못 빠져나옴
deriving DecidableEq, Repr

inductive LockEvent where
  | tryCode (code : Nat)
  | lock
----

`locked`가 이제 `attempts : Nat`를 담습니다 — 1장에서 배운 대로, "실패 횟수"는 `locked` 상태에서만 의미가 있으므로(unlocked나 jammed에는 "실패 횟수"라는 개념 자체가 없습니다) sum 타입의 생성자 안에 담는 게 정확합니다. 만약 `attempts`를 `LockState`와 별개의 필드로(product로) 뒀다면, "unlocked인데 attempts가 2"처럼 의미 없는 조합이 다시 표현 가능해졌을 것입니다.

== transition 설계

[source,lean]
----
def theCode : Nat := 4242

def LockState.transition : LockState → LockEvent → LockState
  | .locked attempts, .tryCode code =>
      if code = theCode then .unlocked
      else if attempts + 1 >= 3 then .jammed
      else .locked (attempts + 1)
  | .locked attempts, .lock => .locked attempts
  | .unlocked, .lock => .locked 0
  | .unlocked, .tryCode _ => .unlocked
  | .jammed, _ => .jammed  -- jammed에서는 어떤 이벤트를 받아도 벗어나지 못함
----

`locked attempts`에서 `tryCode`를 받았을 때 세 갈래로 나뉩니다 — 맞으면 `unlocked`, 틀렸는데 이번이 세 번째 실패면 `jammed`, 아니면 실패 횟수를 하나 늘린 `locked (attempts + 1)`. 마지막 줄 `.jammed, _ => .jammed`가 이 설계의 핵심입니다 — **어떤 이벤트가 들어와도** `jammed`는 자기 자신으로만 갑니다.

[source,lean]
----
#eval LockState.locked 0 |>.transition (.tryCode 1111)  -- locked 1
#eval LockState.locked 1 |>.transition (.tryCode 1111)  -- locked 2
#eval LockState.locked 2 |>.transition (.tryCode 1111)  -- jammed
#eval LockState.locked 0 |>.transition (.tryCode 4242)  -- unlocked
----

== 성질 1: 3연속 실패는 반드시 jammed로 이어진다

[source,lean]
----
def runEvents (init : LockState) (events : List LockEvent) : LockState :=
  events.foldl LockState.transition init

example : runEvents (.locked 0) [.tryCode 1, .tryCode 1, .tryCode 1] = .jammed := by
  native_decide
----

`runEvents`는 5장에서 만든 `MealyMachine.run`의 단순화 버전입니다 — `List.foldl`로 이벤트 목록을 순서대로 접어나가며 최종 상태를 계산합니다(이 `foldl`이 5장에서 말한 "algebra" 방향입니다). 틀린 코드(`1`)를 세 번 연속 넣으면 정말로 `jammed`에 도달한다는 걸 `native_decide`로 확인했습니다 — 손으로 세 번 실행해보고 눈으로 확인하는 대신, **이 특정 이벤트 시퀀스에 대해서는** 컴파일러가 그 사실을 보증합니다.

== 성질 2: jammed는 진짜로 탈출구가 없다

방금 건 "이 특정 시퀀스"에 대한 확인이었습니다. 더 강한 주장 — **"jammed 상태에서는 어떤 이벤트를 받아도 절대 jammed를 벗어나지 못한다"**(가능한 모든 `LockEvent`에 대해)는 것도 증명할 수 있습니다.

[source,lean]
----
example (e : LockEvent) : LockState.jammed.transition e = .jammed := by
  cases e <;> rfl
----

`cases e`가 `e`로 가능한 모든 생성자(`tryCode _`, `lock`)로 증명을 나누고, `<;> rfl`이 그 각각에 대해 "정의를 그대로 펼치면 참"이라는 걸 확인합니다. `<;>`는 "바로 앞 전술이 만들어낸 모든 갈래 각각에, 뒤에 오는 전술을 똑같이 적용하라"는 결합자입니다 — `cases e`가 두 갈래(`tryCode _`인 경우와 `lock`인 경우)를 만들면, `<;> rfl`이 그 두 갈래 각각에 `rfl`을 적용합니다. 갈래마다 똑같은 전술을 반복해서 적는 대신 한 줄로 줄여 쓰는 것뿐입니다. 이 증명이 통과했다는 건 **`LockEvent`로 표현 가능한 모든 이벤트**에 대해 이 성질이 성립한다는 뜻입니다 — `native_decide`로 확인한 성질 1이 "이 하나의 시나리오"였다면, 이건 "일어날 수 있는 모든 시나리오"에 대한 증명입니다.

== 성질 3: 올바른 코드는 실패 횟수와 무관하게 항상 통과한다

[source,lean]
----
example (attempts : Nat) :
    (LockState.locked attempts).transition (.tryCode theCode) = .unlocked := by
  simp [LockState.transition]
----

`attempts`가 몇이든(`Nat` 전체에 대해) 올바른 코드를 넣으면 항상 `unlocked`로 간다는 걸 증명했습니다 — `transition`의 첫 번째 분기(`if code = theCode then .unlocked`)가 실패 횟수를 확인하기도 전에 먼저 검사되기 때문입니다. 실무에서 이런 성질은 "정상적인 사용자가 우연히 실수로 잠겨버리는 일이 없는가"를 보증하는 것과 같은 종류의 주장입니다.

== 이 장이 보여주는 것

세 성질을 나란히 놓고 보면 증명의 "범위"가 다르다는 걸 알 수 있습니다 — 성질 1은 구체적인 시나리오 하나, 성질 2와 3은 가능한 모든 경우에 대한 보편적 주장입니다. 실전에서 모든 성질을 성질 2·3 수준(전체 증명)으로 끌어올릴 필요는 없습니다 — 다만 "이 시스템이 실제로 안전하다고 확신하려면 어떤 성질이 전체 증명이어야 하는가"를 구분하는 감각이, 4~6장에서 배운 설계 도구(sum 타입, `transition` 함수, product/coproduct 합성)를 실전에 옮길 때 실질적인 가치를 만듭니다.

== 직접 해보기

== 요약

* 상태 안에 담아야 할 데이터(예: 실패 횟수)는 그 데이터가 의미 있는 상태의 생성자 안에 두어야, 의미 없는 조합(unlocked인데 실패 횟수가 있는)이 표현되지 않습니다.
* `native_decide`로 "이 시나리오에서는 성립한다"를, `cases ... <;> rfl`이나 `simp`로 "가능한 모든 경우에 성립한다"를 증명할 수 있습니다 — 둘은 증명의 범위가 다릅니다.
* 어떤 성질이 "전체 증명"이어야 안심할 수 있는지 판단하는 게, 설계 도구를 실전에 옮기는 핵심 감각입니다.

2부(4~7장)가 여기서 끝났습니다. 3부에서는 "한 시점의 상태"가 아니라 "시간에 걸친 상태의 흐름"에 대한 성질 — 예를 들어 "언젠가는 unlocked에 도달한다" 같은 것 — 을 어떻게 명세하고 증명하는지, 시제논리로 다룹니다.
