== 요구사항: 3회 연속 과부하가 감지되면 멈춘다

실제 엘리베이터에는 중량 센서가 있습니다 — 문이 열린 채로 승객이 너무 많이 타서 과부하가 감지되면 경고음이 울리고 문이 안 닫힙니다. 그런데 만약 승객이 못 알아듣고 **3번 연속** 과부하 상태로 다시 타려 한다면, 안전을 위해 관리자가 올 때까지 아예 멈춰야 합니다. 4~6장의 `ElevatorState`는 이 "과부하 횟수를 세는" 요구사항을 표현할 수 없으니, 상태를 다시 설계합니다.

[source,lean]
----
inductive SafeState where
  | doorsOpen (overloadCount : Nat)   -- 누적 과부하 횟수를 상태 안에 담음
  | movingTo (dest : Nat)
  | idle
  | emergency
deriving DecidableEq, Repr

inductive SafeEvent where
  | overloadDetected
  | weightOk
  | tick
  | callFloor (dest : Nat)
deriving DecidableEq, Repr
----

`doorsOpen`이 이제 `overloadCount : Nat`를 담습니다 — 1장에서 배운 대로, "과부하 횟수"는 문이 열려있는 동안에만 의미가 있으므로(움직이거나 대기 중일 땐 그런 개념 자체가 없습니다) sum 타입의 생성자 안에 담는 게 정확합니다. 만약 `overloadCount`를 `SafeState`와 별개의 필드로(product로) 뒀다면, "이동 중인데 overloadCount가 2"처럼 의미 없는 조합이 다시 표현 가능해졌을 것입니다.

== transition 설계

[source,lean]
----
def SafeState.transition : SafeState → SafeEvent → SafeState
  | .doorsOpen count, .overloadDetected =>
      if count + 1 >= 3 then .emergency else .doorsOpen (count + 1)
  | .doorsOpen _, .weightOk => .doorsOpen 0
  | .doorsOpen _, .tick => .idle
  | .doorsOpen count, .callFloor _ => .doorsOpen count
  | .idle, .callFloor dest => .movingTo dest
  | .idle, _ => .idle
  | .movingTo _, .tick => .doorsOpen 0  -- 단순화: 한 틱 뒤 도착
  | .movingTo dest, _ => .movingTo dest
  | .emergency, _ => .emergency  -- 관리자 개입 전엔 절대 못 벗어남
----

`doorsOpen count`에서 `overloadDetected`를 받았을 때 세 갈래로 나뉩니다 — 이번이 세 번째 감지면 `emergency`, 아니면 카운트를 하나 늘린 `doorsOpen (count + 1)`. `weightOk`(무게가 정상으로 돌아옴)를 받으면 카운트가 리셋됩니다. 마지막 줄 `.emergency, _ => .emergency`가 이 설계의 핵심입니다 — **어떤 이벤트가 들어와도** `emergency`는 자기 자신으로만 갑니다.

[source,lean]
----
def runEvents (init : SafeState) (events : List SafeEvent) : SafeState :=
  events.foldl SafeState.transition init

#eval runEvents (.doorsOpen 0) [.overloadDetected, .overloadDetected, .overloadDetected]
-- SafeState.emergency
----

== 성질 1: 3연속 과부하는 반드시 emergency로 이어진다

[source,lean]
----
example : runEvents (.doorsOpen 0) [.overloadDetected, .overloadDetected, .overloadDetected]
    = .emergency := by native_decide
----

`runEvents`는 5장에서 만든 `MealyMachine.run`의 단순화 버전입니다 — `List.foldl`로 이벤트 목록을 순서대로 접어나가며 최종 상태를 계산합니다(이 `foldl`이 5장에서 말한 "algebra" 방향입니다). 과부하 이벤트를 세 번 연속 넣으면 정말로 `emergency`에 도달한다는 걸 `native_decide`로 확인했습니다.

== 성질 2: emergency는 진짜로 탈출구가 없다

방금 건 "이 특정 시퀀스"에 대한 확인이었습니다. 더 강한 주장 — **"emergency 상태에서는 어떤 이벤트를 받아도 절대 emergency를 벗어나지 못한다"**(가능한 모든 `SafeEvent`에 대해)는 것도 증명할 수 있습니다.

[source,lean]
----
example (e : SafeEvent) : SafeState.emergency.transition e = .emergency := by
  cases e <;> rfl
----

`cases e`가 `e`로 가능한 모든 생성자(`overloadDetected`, `weightOk`, `tick`, `callFloor _`)로 증명을 나누고, `<;> rfl`(7장부터는 이 결합자를 계속 씁니다 — "앞 전술이 만든 모든 갈래 각각에 뒤 전술을 반복 적용하라"는 뜻입니다)이 그 각각에 대해 "정의를 그대로 펼치면 참"이라는 걸 확인합니다. 이 증명이 통과했다는 건 **`SafeEvent`로 표현 가능한 모든 이벤트**에 대해 이 성질이 성립한다는 뜻입니다 — `native_decide`로 확인한 성질 1이 "이 하나의 시나리오"였다면, 이건 "일어날 수 있는 모든 시나리오"에 대한 증명입니다.

== 성질 3: 무게가 정상으로 돌아오면 카운트가 리셋된다

[source,lean]
----
example : (SafeState.doorsOpen 5).transition .weightOk = .doorsOpen 0 := by native_decide
----

과부하 카운트가 몇이든(`5`처럼 실제로는 3에 도달해 `emergency`로 갔어야 할 이상한 값이라도) `weightOk`를 받으면 항상 `0`으로 리셋된다는 걸 확인했습니다 — 물론 실제로는 `emergency`로 먼저 갔을 상태라 `doorsOpen 5`라는 값 자체가 정상적인 흐름에서는 도달 불가능하지만, `transition` 함수 자체는 그런 입력에 대해서도 정의돼 있고 예측 가능하게 동작한다는 걸 보여줍니다.

== 이 장이 보여주는 것

세 성질을 나란히 놓고 보면 증명의 "범위"가 다르다는 걸 알 수 있습니다 — 성질 1과 3은 구체적인 시나리오 하나, 성질 2는 가능한 모든 경우에 대한 보편적 주장입니다. 실전에서 모든 성질을 성질 2 수준(전체 증명)으로 끌어올릴 필요는 없습니다 — 다만 "이 시스템이 실제로 안전하다고 확신하려면 어떤 성질이 전체 증명이어야 하는가"를 구분하는 감각이, 4~6장에서 배운 설계 도구(sum 타입, `transition` 함수, product/coproduct 합성)를 실전에 옮길 때 실질적인 가치를 만듭니다.

== 요약

* 상태 안에 담아야 할 데이터(예: 과부하 횟수)는 그 데이터가 의미 있는 상태의 생성자 안에 두어야, 의미 없는 조합(이동 중인데 과부하 횟수가 있는)이 표현되지 않습니다.
* `native_decide`로 "이 시나리오에서는 성립한다"를, `cases ... <;> rfl`로 "가능한 모든 경우에 성립한다"를 증명할 수 있습니다 — 둘은 증명의 범위가 다릅니다.
* 어떤 성질이 "전체 증명"이어야 안심할 수 있는지 판단하는 게, 설계 도구를 실전에 옮기는 핵심 감각입니다.

2부(4~7장)가 여기서 끝났습니다. 3부에서는 "한 시점의 상태"가 아니라 "시간에 걸친 상태의 흐름"에 대한 성질 — 예를 들어 "문이 열린 채로는 절대 움직이지 않는다"나 "언젠가는 호출한 층에 도착한다" 같은 것 — 을 어떻게 명세하고 증명하는지, 시제논리로 다룹니다.
