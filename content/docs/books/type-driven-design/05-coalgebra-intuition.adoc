== 4장의 transition에 출력을 더하기

4장의 `transition : State → Event → State`는 "다음 상태가 뭔지"만 알려줬습니다. 그런데 실제 엘리베이터는 상태가 바뀌는 것과 별개로 **뭔가를 보여줍니다** — 층수 표시판의 숫자, 그리고 위/아래를 가리키는 방향 화살표입니다. 이걸 반영하면 함수의 모양이 이렇게 바뀝니다.

[source,lean]
----
inductive Direction where
  | up | down
deriving DecidableEq, Repr

def ElevatorState.directionArrow (s : ElevatorState) : Option Direction :=
  match s.phase with
  | .movingTo dest =>
      if dest > s.floor then some .up
      else if dest < s.floor then some .down
      else none
  | _ => none

#eval (ElevatorState.mk 2 (.movingTo 5)).directionArrow  -- some up
#eval (ElevatorState.mk 2 .idle).directionArrow           -- none
----

`directionArrow`는 `movingTo dest`일 때만 방향을 계산합니다 — 목적지가 지금 층보다 높으면 `up`, 낮으면 `down`, 같으면(도착 직전 순간, 아직 `doorsOpen`으로 안 바뀐 찰나) `none`입니다. `idle`이나 `doorsOpen`일 때는 화살표를 켤 이유가 없으니 `none`입니다.

[NOTE]
====
처음에 이 함수를 "`dest > s.floor`면 `up`, 아니면 무조건 `down`"으로 짰더니, 목적지에 막 도착해서 `dest = s.floor`가 된 그 찰나에 방향이 `down`으로 잘못 표시되는 버그가 있었습니다(아래로 안 가는데 아래 화살표가 켜짐). `dest = s.floor`인 경우를 `none`으로 따로 처리해야 실제로 옳은 동작입니다 — 이런 "경계에서 하나 놓치는" 실수는 직접 실행해보지 않으면 눈에 잘 안 띕니다.
====

== 왜 coalgebra라고 부르는가: algebra와 정반대 방향

`List.foldl`처럼 여러 값을 하나로 **모으는** 함수를 생각해봅시다 — `(Acc, Elem) → Acc`라는 모양으로, "여러 조각을 안으로 접어 들어가 하나의 결과를 만든다"는 방향입니다. 이런 "여러 개를 하나로 모으는" 구조를 범주론에서 **algebra**라고 부릅니다.

방금 만든 `directionArrow`와 4장의 `transition`을 합친 모양은 정확히 **반대 방향**입니다 — `State → (Output × State)`라는 모양은 "하나의 상태에서 시작해서, 관찰 가능한 조각(출력)을 하나씩 밖으로 꺼내며 다음 상태로 나아간다"는 뜻입니다. 안으로 접어 들어가는 게 아니라 **밖으로 펼쳐나가는** 방향이라, algebra의 반대라는 뜻에서 **coalgebra**라고 부릅니다.

[cols="1,2,2"]
|===
|구분 |algebra |coalgebra

|방향
|여러 조각 → 하나로 모음
|하나의 상태 → 조각을 하나씩 꺼냄(밖으로 펼침)

|전형적인 모양
|`(Acc, Elem) → Acc` (예: `List.foldl`)
|`State → (Output × State)` (예: 엘리베이터의 한 스텝)

|대표 예시
|리스트를 접어 합계를 구하기
|엘리베이터를 한 스텝씩 움직이며 표시판을 관찰하기
|===

== coalgebra를 값으로: MealyMachine 구조체

이 "carrier 타입에서 관찰 가능한 것을 꺼내는 함수"라는 패턴 자체를 값으로 만들어봅시다.

[source,lean]
----
structure MealyMachine (State Event Output : Type) where
  step : State → Event → (Output × State)

def elevatorStep (s : ElevatorState) (e : ElevatorEvent) : (Nat × Option Direction) × ElevatorState :=
  let s' := s.transition e
  ((s'.floor, s'.directionArrow), s')

def elevatorMachine : MealyMachine ElevatorState ElevatorEvent (Nat × Option Direction) :=
  { step := elevatorStep }
----

`MealyMachine`(입력 이벤트에 따라 출력이 달라지는 이런 종류의 기계를 전통적으로 Mealy 기계라고 부릅니다)은 "상태 타입, 이벤트 타입, 출력 타입, 그리고 그 셋을 잇는 `step` 함수"를 하나로 묶은 구조체입니다. `elevatorStep`은 이벤트를 적용해 다음 상태 `s'`를 얻은 뒤, 그 새 상태에서 표시판에 보여줄 값(층수, 방향)을 꺼내 함께 반환합니다.

== 엘리베이터를 구동하기: 이벤트 목록을 접어 출력 목록으로

[source,lean]
----
def MealyMachine.run (m : MealyMachine State Event Output)
    (init : State) : List Event → List Output × State
  | [] => ([], init)
  | e :: es =>
    let (o, s') := m.step init e
    let (os, sFinal) := m.run s' es
    (o :: os, sFinal)

#eval elevatorMachine.run ⟨0, .idle⟩ [.callFloor 3, .tick, .tick, .tick, .tick]
-- ([(0,up), (1,up), (2,up), (3,none), (3,none)], { floor := 3, phase := doorsOpen })

example : (elevatorMachine.run ⟨0, .idle⟩ [.callFloor 3, .tick, .tick, .tick, .tick]).2
    = ⟨3, .doorsOpen⟩ := by native_decide
----

`run`은 이벤트 목록을 하나씩 소비하며 `step`을 반복 호출하는 **구동기(driver)**입니다. 출력 목록을 보면 엘리베이터가 3층을 향해 `up` 화살표를 켜고 올라가다가, 3층에 도착한 순간(그리고 문이 열리는 순간)엔 화살표가 꺼진다(`none`)는 걸 확인할 수 있습니다 — NOTE에서 고친 버그가 실제로 사라졌다는 뜻입니다. 흥미로운 지점은 `run` 자체가 이 장의 처음에 정의한 "algebra"(여러 이벤트를 접어 하나의 결과로 모으는 구조)라는 것입니다 — **coalgebra로 정의한 기계 하나를 반복 실행하는 일 자체는 algebra**입니다. 이 두 방향이 나란히 맞물려야 상태 기계가 "정의된 것"에서 "실제로 돌아가는 것"이 됩니다.

== 실전에서 이 관점이 주는 것

"coalgebra"라는 용어 자체를 실무 코드에 쓸 일은 거의 없습니다. 이 관점이 주는 실질적인 가치는 두 가지입니다.

* *상태 기계를 다른 것과 구분해서 볼 수 있게 해줍니다* — "지금 갖고 있는 게 여러 값을 하나로 모으는 문제(algebra)인지, 하나의 상태에서 관찰 가능한 것들을 계속 꺼내는 문제(coalgebra)인지"를 구분하면, 왜 어떤 로직은 `foldl` 하나로 깔끔히 끝나는데 어떤 로직은 자꾸 상태를 들고 다녀야 하는지가 분명해집니다.
* *합성의 실마리를 줍니다* — `MealyMachine`이 `State`, `Event`, `Output`이라는 세 타입 매개변수를 가진 구조체라는 걸 명확히 하면, "엘리베이터 두 대를 어떻게 합칠까"라는 질문이 "두 `State`를 어떻게 합칠까"(product나 sum으로, 1장에서 배운 바로 그 도구로)라는 훨씬 구체적인 질문으로 바뀝니다 — 다음 장의 주제입니다.

== 직접 해보기

* `directionArrow`처럼, `doorsOpen`일 때 "문 열림" 표시등이 켜지는 `doorLamp : ElevatorState → Bool`을 만들어보세요.
* `elevatorStep`을 확장해 `(Nat × Option Direction × Bool)`(층수, 방향, 문 열림 표시등)을 함께 출력하도록 고쳐보세요.

.해답 보기
[%collapsible]
====
[source,lean]
----
def ElevatorState.doorLamp (s : ElevatorState) : Bool :=
  match s.phase with
  | .doorsOpen => true
  | _ => false

def elevatorStep2 (s : ElevatorState) (e : ElevatorEvent) :
    (Nat × Option Direction × Bool) × ElevatorState :=
  let s' := s.transition e
  ((s'.floor, s'.directionArrow, s'.doorLamp), s')

example : (elevatorStep2 ⟨2, .movingTo 3⟩ .tick).1 = (3, none, false) := by native_decide
-- 아직 doorsOpen이 아니라 movingTo(도착 직전)이므로 문 열림 표시등은 false
----
====

== 요약

* algebra가 "여러 조각을 하나로 접어 모으는" 구조(`(Acc, Elem) → Acc`)라면, coalgebra는 그 반대로 "하나의 상태에서 관찰 가능한 조각을 계속 꺼내며 펼쳐나가는" 구조(`State → (Output × State)`)입니다.
* 엘리베이터의 한 스텝(`step`)이 coalgebra이고, 그 기계를 여러 이벤트에 대해 반복 실행하는 `run`은 다시 algebra입니다.
* 경계 조건(목적지에 막 도착한 찰나)을 놓치면 실제로 잘못된 출력이 나온다는 걸, 이 장에서 직접 잡은 버그가 보여줍니다 — 코드를 실행해보지 않고 "그럴듯하다"고 넘어가면 놓치기 쉬운 종류의 실수입니다.

다음 장에서는 이렇게 값이 된 엘리베이터 하나를 어떻게 다른 것과 합쳐 더 큰 시스템을 만드는지 다룹니다.
