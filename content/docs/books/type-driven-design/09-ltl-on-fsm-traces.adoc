== 무한히 이어지는 실행을 값으로: trace

8장에서 "생동성은 무한히 이어지는 실행 전체를 봐야 한다"고 했습니다. 이걸 코드로 다루려면, 먼저 "무한히 이어지는 실행"을 유한한 정의로 표현할 방법이 필요합니다.

[source,lean]
----
def traceFrom (init : ElevatorState) (events : Nat → ElevatorEvent) : Nat → ElevatorState
  | 0 => init
  | n + 1 => (traceFrom init events n).transition (events n)
----

`traceFrom : ElevatorState → (Nat → ElevatorEvent) → Nat → ElevatorState`가 그 답입니다 — "`n`번째 스텝에 상태가 무엇인가"를 계산하는 함수 자체가 곧 "무한히 이어지는 실행"입니다. `events : Nat → ElevatorEvent`가 **이벤트 스트림**입니다 — "매 순간 무슨 일이 일어나는가"를 무한히 정해주는 함수입니다.

== Always와 Eventually: 시제 연산자를 그대로 정의로

[source,lean]
----
def Always {α} (P : α → Prop) (s : Nat → α) : Prop := ∀ n, P (s n)
def Eventually {α} (P : α → Prop) (s : Nat → α) : Prop := ∃ n, P (s n)
----

이게 이 장의 핵심입니다 — "**항상**"(Always)은 "**모든** 시점 `n`에 대해 성질 `P`가 성립한다"(`∀ n`)는 뜻이고, "**언젠가**"(Eventually)는 "**어떤** 시점 `n`이 존재해서 그때 `P`가 성립한다"(`∃ n`)는 뜻입니다. 특별한 새 논리가 아니라, Lean4가 원래 가진 전칭(`∀`)과 존재(`∃`) 양화사를 "무한 수열 위의 성질"이라는 맥락에 맞게 이름 붙인 것뿐입니다. 8장에서 안전성/생동성으로 나눴던 구분이 정확히 이 둘에 대응합니다 — 안전성은 `Always`, 생동성은 `Eventually`입니다.

== 안전성을 trace 전체로 확장하기

8장에서 "문이 열려있는 동안엔 층이 안 바뀐다"를 한 스텝에 대해 증명했습니다. `Always`로 감싸면 이게 **모든 시점**에 대한 주장이 됩니다.

[source,lean]
----
theorem always_doors_open_floor_stable (init : ElevatorState) (events : Nat → ElevatorEvent) :
    Always (fun s => s.phase = .doorsOpen → ∀ e, (s.transition e).floor = s.floor)
      (traceFrom init events) := by
  intro n h e
  exact doors_open_floor_unchanged _ e h
----

이 증명이 짧은 이유가 중요합니다 — `doors_open_floor_unchanged`가 이미 **어떤 상태·어떤 이벤트에 대해서도** 증명됐으니, `traceFrom init events n`도 결국 `ElevatorState` 값 하나일 뿐이라 그 성질이 자동으로 적용됩니다. 좋은 한 스텝 증명이 시간에 걸친 증명으로 거의 공짜로 확장되는 걸 보여줍니다.

== 생동성: 이벤트 스트림이 결과를 바꾼다

이제 흥미로운 대조를 봅시다. **`tick`이 한 번도 안 오고 `callFloor`만 계속 오는 스트림**이면 어떻게 될까요.

[source,lean]
----
def onlyCalls : Nat → ElevatorEvent := fun _ => .callFloor 3

theorem never_arrives_without_ticks :
    Always (fun s => s.phase ≠ .doorsOpen) (traceFrom ⟨0, .idle⟩ onlyCalls) := by
  have key : ∀ n, traceFrom ⟨0, .idle⟩ onlyCalls n = ⟨0, .idle⟩ ∨
      traceFrom ⟨0, .idle⟩ onlyCalls n = ⟨0, .movingTo 3⟩ := by
    intro n
    induction n with
    | zero => exact Or.inl rfl
    | succ n ih =>
      rcases ih with h | h
      · right; simp [traceFrom, h, onlyCalls, ElevatorState.transition]
      · right; simp [traceFrom, h, onlyCalls, ElevatorState.transition]
  intro n
  rcases key n with h | h <;> simp [h]
----

`tick`이 없으면 4장의 `transition`은 `movingTo` 국면에서 절대 층을 안 움직입니다(움직임은 오직 `tick`에 반응해서 일어나니까요) — 그래서 이 스트림 아래에서는 "idle이거나 movingTo 3에 멈춰 있거나" 둘 중 하나로 **영원히** 고정되고, `doorsOpen`(도착)에는 **절대** 도달하지 못합니다. `rcases ih with h | h` 같은 문법은 8장의 `obtain`과 같은 역할입니다 — 이미 갖고 있는 증명(`ih`, 어느 한쪽이 성립한다는 사실)을 열어서 그 안의 정보를 이름 붙여 꺼내 씁니다.

대조적으로, **`tick`이 실제로 오는 스트림**이면 도착에 성공합니다.

[source,lean]
----
example : Eventually (· = ElevatorState.mk 3 .doorsOpen)
    (traceFrom ⟨0, .idle⟩ (fun n => if n = 0 then .callFloor 3 else .tick)) := by
  refine ⟨5, ?_⟩
  native_decide
----

첫 스텝에 `callFloor 3`을 보내고 그다음부터는 `tick`만 계속 보내는 스트림에서는, 5번째 시점에 정확히 `⟨3, doorsOpen⟩`에 도달합니다(`callFloor`로 움직이기 시작하고, 세 번의 `tick`으로 0→1→2→3층까지 이동한 뒤, 네 번째 `tick`에서 도착을 확인하고 문을 엽니다). **같은 `transition` 함수인데도, 이벤트 스트림이 무엇이냐에 따라 생동성 성질의 참/거짓이 완전히 갈립니다.** 8장에서 "tick이 계속 온다는 전제가 있어야 생동성이 성립한다"고 말한 게 바로 이것입니다.

== 이 장이 보여주는 것

`Always`와 `Eventually`는 새로운 논리 체계가 아니라 **`∀`/`∃`를 무한 수열에 적용한 것**입니다. 이 관점의 실전 가치는, "이 시스템이 안전한가"와 "이 시스템이 결국 원하는 결과를 내는가"를 **같은 도구(양화사)로, 다만 서로 다른 대상(모든 시점 vs 어떤 시점)에 대해** 정확히 구분해서 물을 수 있게 해준다는 것입니다. 그리고 생동성은 시스템 자체만으로는 결정되지 않고, **시스템에 주어지는 입력(이벤트 스트림)에 대한 가정과 함께라야** 비로소 참/거짓이 결정된다는 것도 이 예제가 보여줍니다.

== 직접 해보기

* `onlyCalls`를 "`tick`과 `callFloor 3`가 번갈아 오는" 스트림으로 바꿔, 여전히 언젠가는 도착하는지(다만 더 오래 걸리는지) `native_decide`로 확인해보세요.
* 처음 두 번은 `callFloor 3`가 오고(두 번째는 이동 중이라 4장의 설계대로 무시되고) 그 뒤로 `tick`만 오는 스트림을 만들어, 도착 시점이 원래보다 정확히 한 스텝 늦춰지는지(5번째가 아니라 6번째) 확인해보세요 — 무시된 이벤트도 "한 틱만큼의 시간"은 그대로 소비한다는 뜻입니다.

== 요약

* `traceFrom : State → (Nat → Event) → Nat → State`로 무한히 이어지는 실행을 유한한 함수 정의로 표현할 수 있습니다.
* `Always P s := ∀ n, P (s n)`, `Eventually P s := ∃ n, P (s n)`가 안전성과 생동성을 정확히 대응시키는 정의입니다 — 새 논리가 아니라 익숙한 전칭·존재 양화사입니다.
* 좋은 한 스텝 증명(8장)은 `Always`로 거의 공짜로 확장됩니다.
* 생동성은 시스템 하나만으로는 결정되지 않습니다 — 어떤 이벤트 스트림이 주어지느냐(예: `tick`이 실제로 오는가)에 따라 참일 수도 거짓일 수도 있습니다.

다음 장에서는 지금까지 다룬 결정적(deterministic) 엘리베이터를 넘어, "다음 상태가 여러 개일 수 있는" 비결정적 상황 — 여러 층에서 동시에 호출이 왔을 때 어느 것부터 처리할지 — 에서 이 시제논리가 어떻게 갈래를 나눠 생각해야 하는지(CTL) 봅니다.
