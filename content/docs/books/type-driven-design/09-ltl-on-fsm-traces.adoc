== 무한히 이어지는 실행을 값으로: trace

8장에서 "생동성은 무한히 이어지는 실행 전체를 봐야 한다"고 했습니다. 이걸 코드로 다루려면, 먼저 "무한히 이어지는 실행"을 유한한 정의로 표현할 방법이 필요합니다.

[source,lean]
----
def TrafficLight.trace (start : TrafficLight) : Nat → TrafficLight
  | 0 => start
  | n + 1 => (TrafficLight.trace start n).next
----

`trace : Nat → TrafficLight`가 그 답입니다 — "`n`번째 스텝에 상태가 무엇인가"를 계산하는 함수 자체가 곧 "무한히 이어지는 실행"입니다. 함수는 유한한 정의이지만, `Nat`이 무한하므로 `trace`가 표현하는 실행은 실질적으로 무한히 이어집니다. `trace start 0`은 시작 상태, `trace start 1`은 한 스텝 뒤, 이런 식으로 원하는 시점을 얼마든지 물어볼 수 있습니다.

== Always와 Eventually: 시제 연산자를 그대로 정의로

[source,lean]
----
def Always {α} (P : α → Prop) (s : Nat → α) : Prop := ∀ n, P (s n)
def Eventually {α} (P : α → Prop) (s : Nat → α) : Prop := ∃ n, P (s n)
----

이게 이 장의 핵심입니다 — "**항상**"(Always)은 "**모든** 시점 `n`에 대해 성질 `P`가 성립한다"(`∀ n`)는 뜻이고, "**언젠가**"(Eventually)는 "**어떤** 시점 `n`이 존재해서 그때 `P`가 성립한다"(`∃ n`)는 뜻입니다. 특별한 새 논리가 아니라, Lean4가 원래 가진 전칭(`∀`)과 존재(`∃`) 양화사를 "무한 수열 위의 성질"이라는 맥락에 맞게 이름 붙인 것뿐입니다. 8장에서 안전성/생동성으로 나눴던 구분이 정확히 이 둘에 대응합니다 — 안전성은 `Always`, 생동성은 `Eventually`입니다.

== 안전성 예시: sum 타입 덕분에 공짜로 증명되는 성질

[source,lean]
----
theorem light_always_valid : Always (fun s => s = .red ∨ s = .green ∨ s = .yellow)
    (TrafficLight.trace .green) := by
  intro n
  cases TrafficLight.trace .green n <;> simp
----

"신호등 색은 항상 red/green/yellow 중 하나"라는 안전성 성질이 거의 자동으로 증명됩니다 — 1장에서 배운 대로 `TrafficLight`가 이 세 값만 가능한 sum 타입이니, 애초에 다른 값이 나올 수가 없어서 증명이랄 것도 없이 참입니다. **좋은 타입 설계는 증명해야 할 안전성 성질의 수를 줄여줍니다** — 이 장 이전에 배운 1~7장이 헛되지 않았다는 걸 보여주는 지점입니다.

== 생동성 예시: 도어록, 그리고 "환경 가정"이 결과를 바꾼다

7~8장의 도어록으로 더 흥미로운 사례를 봅니다. **공격자가 항상 틀린 코드(`1`)만 시도하는 이벤트 스트림**을 만들어봅시다.

[source,lean]
----
def LockState.traceFrom (init : LockState) (events : Nat → LockEvent) : Nat → LockState
  | 0 => init
  | n + 1 => (LockState.traceFrom init events n).transition (events n)

def alwaysWrong : Nat → LockEvent := fun _ => .tryCode 1
----

`traceFrom`은 `TrafficLight.trace`와 같은 패턴인데, 이번엔 "다음 상태가 이벤트에 따라 달라지므로" **이벤트 스트림**(`events : Nat → LockEvent`)까지 함께 받습니다. 이 스트림 아래에서 "절대 unlocked가 안 된다"는 안전성을 증명합니다.

[NOTE]
====
아래 증명에서 두 가지 표기가 새로 나옵니다. `⟨값, 증명⟩`은 **익명 생성자**입니다 — "`∃ a, P a`(어떤 `a`가 있어서 `P a`가 성립한다)를 증명하려면, 그 `a`가 구체적으로 무엇인지와 왜 `P a`가 성립하는지를 순서대로 짝지어 내놓으면 된다"는 뜻입니다. `⟨0, Or.inl rfl⟩`은 "그 `a`는 `0`이고, `Or.inl rfl`이 그 증거다"라는 말입니다. `obtain ⟨a, ha | ha⟩ := ih`는 그 반대 방향입니다 — 이미 갖고 있는 증명 `ih`(어떤 `a`가 존재하고, 그 `a`에 대해 두 가능성 중 하나가 성립한다는 증명)를 열어서, 그 안의 `a`와 어느 쪽 가능성인지(`ha`)를 이름 붙여 꺼내 씁니다.
====

[source,lean]
----
theorem wrong_step (a : Nat) : (LockState.locked a).transition (.tryCode 1)
    = if a + 1 ≥ 3 then LockState.jammed else LockState.locked (a + 1) := by
  simp [LockState.transition, theCode]

theorem never_unlocked_key :
    ∀ n, ∃ a, LockState.traceFrom (.locked 0) alwaysWrong n = .locked a ∨
      LockState.traceFrom (.locked 0) alwaysWrong n = .jammed := by
  intro n
  induction n with
  | zero => exact ⟨0, Or.inl rfl⟩
  | succ n ih =>
    obtain ⟨a, ha | ha⟩ := ih
    · simp only [LockState.traceFrom, ha, alwaysWrong]
      rw [wrong_step]
      split
      · exact ⟨a, Or.inr rfl⟩
      · exact ⟨a + 1, Or.inl rfl⟩
    · simp only [LockState.traceFrom, ha]
      exact ⟨0, Or.inr rfl⟩

theorem never_unlocked_under_attack :
    Always (· ≠ LockState.unlocked) (LockState.traceFrom (.locked 0) alwaysWrong) := by
  intro n
  obtain ⟨a, ha | ha⟩ := never_unlocked_key n <;> simp [ha]
----

증명 구조는 8장의 `invariant_holds_after_run`과 같은 모양입니다 — "지금 상태가 `locked` 아니면 `jammed`"라는 보조 사실(`never_unlocked_key`)을 귀납법으로 확립하고, 거기서 "그럼 절대 `unlocked`가 아니다"를 이끌어냅니다. 이 성질은 `alwaysWrong`이라는 **특정 이벤트 스트림에 대해서만** 성립한다는 걸 눈여겨보세요 — 만약 이벤트 스트림이 다르다면, 결과는 달라집니다.

[source,lean]
----
def eventuallyCorrect : Nat → LockEvent := fun n => if n = 2 then .tryCode theCode else .tryCode 1

example : Eventually (· = LockState.unlocked) (LockState.traceFrom (.locked 0) eventuallyCorrect) := by
  exact ⟨3, by native_decide⟩
----

`eventuallyCorrect`는 세 번째 시도(인덱스 2)에서만 올바른 코드를 넣는 스트림입니다 — 이 스트림 아래에서는 `Eventually (· = unlocked)`가 참입니다(`n = 3`일 때 도달). **같은 시스템, 같은 `transition` 함수인데도, 이벤트 스트림이 무엇이냐에 따라 생동성 성질의 참/거짓이 완전히 갈립니다.** 8장에서 "정상 사용자가 결국 올바른 코드를 넣는다는 가정이 있어야 생동성이 성립한다"고 말한 게 바로 이것입니다 — 그 가정이 정확히 "이벤트 스트림이 `eventuallyCorrect`처럼 생겼다"는 조건입니다.

== 이 장이 보여주는 것

`Always`와 `Eventually`는 새로운 논리 체계가 아니라 **`∀`/`∃`를 무한 수열에 적용한 것**입니다. 이 관점의 실전 가치는, "이 시스템이 안전한가"와 "이 시스템이 결국 원하는 결과를 내는가"를 **같은 도구(양화사)로, 다만 서로 다른 대상(모든 시점 vs 어떤 시점)에 대해** 정확히 구분해서 물을 수 있게 해준다는 것입니다. 그리고 생동성은 시스템 자체만으로는 결정되지 않고, **시스템에 주어지는 입력(이벤트 스트림)에 대한 가정과 함께라야** 비로소 참/거짓이 결정된다는 것도 이 예제가 보여줍니다.

== 직접 해보기

* `alwaysWrong` 대신 "처음 두 번은 틀리고 세 번째부터는 계속 맞는" 스트림을 만들어, `Eventually (· = .unlocked)`가 성립하는 가장 이른 시점이 몇 번째인지 확인해보세요.
* `TrafficLight.trace`에 대해 `Always (Eventually ...)` 같은 걸 굳이 정의하지 않고도, "순환하는 시스템은 항상 결국 같은 색으로 돌아온다"는 걸 어떻게 표현할 수 있을지 생각해보세요(힌트: `∀ n, ∃ m > n, ...`).

== 요약

* `trace : Nat → State`(또는 이벤트 스트림을 추가로 받는 `traceFrom`)로 무한히 이어지는 실행을 유한한 함수 정의로 표현할 수 있습니다.
* `Always P s := ∀ n, P (s n)`, `Eventually P s := ∃ n, P (s n)`가 안전성과 생동성을 정확히 대응시키는 정의입니다 — 새 논리가 아니라 익숙한 전칭·존재 양화사입니다.
* 좋은 타입 설계(1장)는 일부 안전성 성질을 거의 공짜로 만들어줍니다.
* 생동성은 시스템 하나만으로는 결정되지 않습니다 — 어떤 이벤트 스트림이 주어지느냐(환경 가정)에 따라 참일 수도 거짓일 수도 있습니다.

다음 장에서는 지금까지 다룬 결정적(deterministic) FSM을 넘어, "다음 상태가 여러 개일 수 있는" 비결정적 시스템에서 이 시제논리가 어떻게 갈래를 나눠 생각해야 하는지(CTL) 봅니다.
