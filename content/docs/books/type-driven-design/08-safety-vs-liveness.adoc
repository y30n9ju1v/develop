== 두 종류의 "옳음"

7장에서 도어록에 대해 두 종류의 성질을 증명했습니다 — "3연속 틀리면 jammed가 된다"(성질 1)와 "jammed는 절대 못 벗어난다"(성질 2)입니다. 이 둘은 겉보기엔 비슷하지만 근본적으로 다른 종류의 주장입니다.

* **"jammed는 절대 못 벗어난다"**는 "**나쁜 일이 절대 일어나지 않는다**"는 주장입니다 — 이런 성질을 **안전성(safety)**이라고 부릅니다.
* 만약 이 시스템에 "언젠가는 정상 사용자가 반드시 문을 연다"는 요구사항이 있다면, 그건 "**좋은 일이 결국은 일어난다**"는 주장입니다 — 이런 성질을 **생동성(liveness)**이라고 부릅니다.

이 구분이 왜 중요한지는, 두 성질을 증명하는 방식이 근본적으로 다르다는 데서 드러납니다.

== 안전성: 상태를 통한 귀납으로 증명 가능

7장에서 다루지 않은 더 일반적인 안전성 성질 하나를 봅시다 — **"실패 횟수(`attempts`)는 절대 3을 넘지 않는다"**는 불변식입니다.

[source,lean]
----
def LockState.attemptsInvariant : LockState → Prop
  | .locked a => a < 3
  | .unlocked => True
  | .jammed => True

theorem invariant_preserved (s : LockState) (e : LockEvent) (h : s.attemptsInvariant) :
    (s.transition e).attemptsInvariant := by
  match s, e with
  | .locked a, .tryCode code =>
    simp only [LockState.transition]
    split
    · trivial
    · split
      · trivial
      · simp only [LockState.attemptsInvariant] at *; omega
  | .locked a, .lock => exact h
  | .unlocked, .lock => simp [LockState.transition, LockState.attemptsInvariant]
  | .unlocked, .tryCode _ => trivial
  | .jammed, _ => trivial
----

`invariant_preserved`가 증명하는 건 "**한 스텝**"에 대한 주장입니다 — "지금 이 불변식이 성립하면, 어떤 이벤트를 받아도 다음 상태에서도 여전히 성립한다." 이것만 증명되면, **몇 스텝을 실행하든** 이 불변식이 유지된다는 걸 귀납법으로 확장할 수 있습니다.

[source,lean]
----
def runEvents (init : LockState) (events : List LockEvent) : LockState :=
  events.foldl LockState.transition init

theorem invariant_holds_after_run (events : List LockEvent) :
    (runEvents (.locked 0) events).attemptsInvariant := by
  suffices h : ∀ s, s.attemptsInvariant → (events.foldl LockState.transition s).attemptsInvariant by
    exact h (.locked 0) (by simp [LockState.attemptsInvariant])
  intro s hs
  induction events generalizing s with
  | nil => exact hs
  | cons e es ih =>
    simp only [List.foldl_cons]
    exact ih (s.transition e) (invariant_preserved s e hs)
----

`suffices h : P by ...`는 "`P`라는 더 일반적인 명제를 증명하는 것으로 충분하다(그걸로 원래 목표를 이끌어낼 수 있다)"고 먼저 선언하고, `by` 블록에서 그 유도를 보여준 다음, 그 아래에서 `P` 자체를 증명하는 전술입니다. 여기서는 "이벤트 10개 이후에 성립한다"는 원래 목표 대신 "**어떤 시작 상태에서 출발하든** 이벤트를 접었을 때 성립한다"는 더 일반적인 명제(`∀ s, ...`)를 증명하는 쪽을 택했습니다 — 원래 목표는 시작 상태가 `.locked 0`으로 고정돼 있어 귀납법을 돌리기에 너무 좁고, 일반화된 형태라야 `induction events`가 각 단계에서 "그 시점의 상태가 무엇이든" 다룰 수 있기 때문입니다. `invariant_holds_after_run`은 이렇게 **임의 길이의 이벤트 목록**(`events`)에 대해 증명됩니다 — 이벤트가 10개든 10만 개든, 목록의 길이에 대한 수학적 귀납법(`induction events`)만으로 증명이 끝납니다. 안전성 성질이 이렇게 증명 가능한 이유는, "나쁜 일이 안 일어난다"는 주장이 사실 **"각 스텝에서 지켜야 할 조건을 매 순간 확인하면 되는 주장"**이기 때문입니다 — 유한한 각 단계를 하나씩 확인하는 걸로 충분합니다.

== 생동성: 왜 같은 방식으로는 증명이 안 되는가

이제 "정상 사용자는 언젠가 반드시 문을 연다"는 생동성 성질을 생각해봅시다. 얼핏 "안전성처럼 귀납법으로 증명하면 되지 않을까"라고 생각할 수 있지만, 여기엔 근본적인 장벽이 있습니다.

안전성은 "지금까지의 **유한한** 실행 전부에 대해, 각 단계가 조건을 만족하는가"를 묻습니다 — 반례가 있다면 **유한한** 시점에 나타납니다("여기, 이 스텝에서 나쁜 일이 일어났다"). 하지만 생동성("언젠가는 문이 열린다")은 **"지금까지 안 열렸다"는 사실만으로는 절대 반증할 수 없습니다** — 사용자가 지금까지 9999번 틀렸어도, "다음 시도에 맞을 수도 있다"는 가능성이 항상 남아있는 한 "언젠가"는 여전히 참일 수 있습니다. 반대로 이 성질이 참이라는 것도 유한한 실행 하나를 관찰하는 걸로는 증명할 수 없습니다 — **무한히 이어지는 실행 전체**를 봐야만 "정말로 언젠가 일어나는지"를 판단할 수 있습니다.

정리하면 이렇습니다.

[cols="1,2,2"]
|===
|구분 |안전성(safety) |생동성(liveness)

|주장의 형태
|"나쁜 일이 절대 안 일어난다"
|"좋은 일이 언젠가 일어난다"

|반례의 형태
|유한한 시점에 나타남("여기서 나쁜 일이 일어났다")
|무한히 이어지는 실행 전체를 봐야 판단 가능("영원히 안 일어난다")

|증명 방법
|한 스텝 보존(`invariant_preserved`) + 귀납법
|유한한 스텝 나열만으로는 부족 — 실행이 무한히 이어진다는 전제 위에서 성립을 논해야 함
|===

== 왜 이 구분이 실전에서 중요한가

"테스트를 충분히 돌려봤으니 안전하다"는 흔한 주장은 사실 안전성 성질에만 통합니다 — 테스트가 몇 번을 돌든, 그중 한 실행이라도 나쁜 상태에 도달했다면 그 즉시 반례를 잡은 것입니다. 그런데 "언젠가는 응답이 온다"거나 "언젠가는 락이 풀린다" 같은 생동성 성질은, 테스트를 아무리 오래 돌려도 "아직 안 일어났다"는 것 이상을 증명해주지 않습니다 — 프로세스가 영원히 멈춰있는(deadlock) 버그와, 그냥 느린 정상 동작을 유한한 관찰만으로는 구분할 수 없기 때문입니다. 실전에서 "타임아웃을 걸고 응답이 없으면 실패로 간주" 같은 관행이 생기는 이유가 정확히 이 한계 때문입니다 — 진짜 생동성은 증명하지 못하고, "충분히 긴 시간 안에"라는 안전성 비슷한 조건으로 타협하는 것입니다.

== 다음 장으로: 무한한 실행을 값으로 다루기

생동성을 제대로 다루려면 "무한히 이어지는 실행"을 유한한 코드 안에서 다룰 방법이 필요합니다. 다음 장에서는 이걸 **무한 수열(스트림)**로 표현하고, 그 위에 "언젠가"(eventually)와 "항상"(always) 같은 연산자를 정의하는 **선형 시제논리(LTL)**를 도입합니다 — 안전성과 생동성이라는 이 장의 구분이, LTL에서는 실제로 서로 다른 연산자(`Always`와 `Eventually`)로 정확히 대응됩니다.

== 직접 해보기

* 4장의 `TrafficLight`에 대해 "색이 절대 `red`도 `green`도 `yellow`도 아닌 값이 될 수 없다"는 성질이 왜 자명하게 참인지(증명이 필요조차 없는 이유를) 1장의 sum 타입 관점에서 설명해보세요.
* 이 장의 `LockState`에 "정상 사용자가 결국 언젠가 올바른 코드를 넣는다"는 가정을 추가로 달면, "언젠가는 unlocked에 도달한다"는 생동성 성질이 성립할 것 같습니다. 이 가정 자체가 왜 "무한히 이어지는 실행"에 대한 이야기인지 설명해보세요.

== 요약

* 안전성(나쁜 일이 절대 안 일어남)은 "한 스텝 보존 + 귀납법"으로 임의 길이의 유한한 실행에 대해 증명할 수 있습니다.
* 생동성(좋은 일이 언젠가 일어남)은 유한한 실행 관찰만으로는 증명도 반증도 완결되지 않습니다 — 무한히 이어지는 실행 전체를 두고 논해야 합니다.
* "테스트를 많이 돌렸다"는 안전성의 반례를 잡는 데는 유효하지만, 생동성을 증명해주지는 않습니다.

다음 장에서는 무한 수열로 실행을 표현하고, 그 위에서 안전성과 생동성을 정확히 표현하는 선형 시제논리(LTL)를 도입합니다.
