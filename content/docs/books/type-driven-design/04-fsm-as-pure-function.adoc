== 이벤트: 엘리베이터에 일어날 수 있는 일

1장에서 `ElevatorState`(층수 + 국면)를 설계했습니다. 이제 이 상태가 시간에 따라 어떻게 바뀌는지 정의할 차례입니다. 먼저 "무슨 일이 일어날 수 있는가"부터 sum 타입으로 정합니다.

[source,lean]
----
inductive ElevatorEvent where
  | callFloor (dest : Nat)   -- 누군가 dest층 버튼을 눌렀다
  | tick                      -- 시간이 한 단위 흘렀다(움직임/문 상태 갱신의 계기)
deriving DecidableEq, Repr
----

`callFloor`는 외부에서 오는 요청이고, `tick`은 "시간이 흐른다"는 사실 자체를 나타내는 이벤트입니다 — 엘리베이터가 한 층 움직이거나 문이 닫히는 일은 전부 이 `tick`에 반응해서 일어납니다(실제 하드웨어라면 초 단위 타이머가 이 이벤트를 계속 보내는 셈입니다).

== transition: 상태와 이벤트를 받아 다음 상태를 계산하는 순수 함수

[source,lean]
----
def ElevatorState.transition : ElevatorState → ElevatorEvent → ElevatorState
  | ⟨floor, .idle⟩, .callFloor dest =>
      if dest = floor then ⟨floor, .doorsOpen⟩ else ⟨floor, .movingTo dest⟩
  | ⟨floor, .idle⟩, .tick => ⟨floor, .idle⟩
  | ⟨floor, .movingTo dest⟩, .tick =>
      if floor = dest then ⟨floor, .doorsOpen⟩
      else if floor < dest then ⟨floor + 1, .movingTo dest⟩
      else ⟨floor - 1, .movingTo dest⟩
  | s@⟨_, .movingTo _⟩, .callFloor _ => s   -- 이동 중엔 새 요청 무시(단순화)
  | ⟨floor, .doorsOpen⟩, .tick => ⟨floor, .idle⟩  -- 한 틱 뒤 문 닫힘(단순화)
  | s@⟨_, .doorsOpen⟩, .callFloor _ => s
----

한 줄씩 짚어봅니다.

* *대기 중에 호출을 받으면*: 이미 그 층이면 곧장 문을 열고(`doorsOpen`), 아니면 그 층을 향해 움직이기 시작합니다(`movingTo dest`).
* *이동 중에 틱을 받으면*: 목적지에 도착했으면 문을 열고, 아직이면 목적지 방향으로 한 층 움직입니다(`floor < dest`면 위로, 아니면 아래로).
* *이동 중이거나 문이 열려있는 동안 새 호출이 오면*: 지금 하던 일을 그대로 유지합니다 — 이 책에서는 "새 요청을 큐에 쌓는" 로직 없이 단순화했습니다.
* *문이 열려있다가 틱을 받으면*: 대기 상태로 돌아갑니다(문이 닫힌다는 뜻으로 단순화했습니다).

`mutable` 필드가 어디에도 없습니다 — 지금 상태와 이벤트를 받아서, 다음 상태를 **계산**해 반환하는 순수 함수입니다.

== 여러 틱을 접어 실행하기

[source,lean]
----
def runEvents (init : ElevatorState) (events : List ElevatorEvent) : ElevatorState :=
  events.foldl ElevatorState.transition init

#eval runEvents ⟨0, .idle⟩ [.callFloor 3, .tick, .tick, .tick, .tick]
-- { floor := 3, phase := ElevatorPhase.doorsOpen }

example : runEvents ⟨0, .idle⟩ [.callFloor 3, .tick, .tick, .tick, .tick]
    = ⟨3, .doorsOpen⟩ := by native_decide
----

0층에서 대기하다가 3층 호출을 받고 틱을 네 번 받으면 정확히 3층에서 문이 열립니다 — 처음 세 틱은 한 층씩 올라가고(0→1→2→3), 네 번째 틱에서 "이미 목적지"라는 걸 확인하고 문을 엽니다. 3층에 도착하는 데 정확히 몇 틱이 걸리는지, 그 결과 국면이 무엇인지를 **손으로 세어보지 않고 컴파일러가 계산해서 확인**해줬다는 게 이 증명의 의미입니다.

== 왜 순수 함수로 표현하는 게 중요한가

mutable 객체로 엘리베이터를 만들면, "지금 상태가 뭔지"는 그 객체를 실행 중에 들여다봐야만 알 수 있습니다. `transition`을 순수 함수로 뽑아내면 세 가지가 달라집니다.

* *테스트가 쉬워집니다* — 엘리베이터 객체를 만들고 여러 메서드를 호출해 부작용을 확인하는 대신, `ElevatorState.transition ⟨0, .idle⟩ (.callFloor 3)`처럼 입력과 출력만으로 테스트를 짤 수 있습니다.
* *성질을 증명할 수 있습니다* — 이후 8장에서 "문이 열린 채로는 절대 층이 바뀌지 않는다"는 안전성을, 9장에서 "언젠가는 호출한 층에 도착한다"는 생동성을 증명합니다 — 둘 다 `transition`이 mutable이 아니라 순수 함수이기 때문에 가능한 증명입니다.
* *합성할 수 있습니다* — `transition` 자체가 값(함수)이라, 6장에서 볼 것처럼 여러 엘리베이터의 `transition` 함수를 조합해 더 큰 시스템을 만들 수 있습니다.

== 직접 해보기

* 5층에서 대기 중인 엘리베이터가 2층 호출을 받았을 때, 몇 번의 틱만에 2층에서 문이 열리는지 `runEvents`로 확인해보세요(내려가는 경우도 똑같이 동작하는지 확인하는 것입니다).
* "이동 중에 새 호출이 오면 무시한다"는 설계를 실제로 확인해보세요 — 0층에서 5층으로 이동을 시작한 뒤, 이동 중간에 `callFloor 2`를 보내도 여전히 5층으로 향하는지 확인해보세요.

== 요약

* 상태(`ElevatorState`)와 이벤트(`ElevatorEvent`)를 sum/product로 설계한 뒤, `transition : State → Event → State`라는 순수 함수로 전이 규칙을 표현합니다.
* `foldl`로 이벤트 목록을 접으면 "여러 틱 뒤 최종 상태가 무엇인가"를 계산할 수 있고, 그 계산 결과를 `native_decide`로 검증할 수 있습니다.
* 순수 함수로 표현한 상태 기계는 테스트하기 쉽고, 성질을 증명할 수 있고, 다른 상태 기계와 합성할 수 있습니다.

다음 장에서는 이 `transition` 패턴이 범주론적으로 왜 "coalgebra"라고 불리는지, 그리고 엘리베이터가 실제로 무엇을 "보여주는지"(층수 표시, 방향 화살표) 출력까지 포함해 다룹니다.
