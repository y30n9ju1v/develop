== 나쁜 설계: mutable 필드로 표현한 상태 기계

[source,lean]
----
structure BadLight where
  color : String := "red"

def BadLight.next (l : BadLight) : BadLight :=
  if l.color = "red" then { l with color := "green" }
  else if l.color = "green" then { l with color := "yellow" }
  else { l with color := "red" }
----

신호등의 "다음 색으로 넘어간다"는 로직을 `color : String` 필드와 `next` 메서드로 짰습니다. 1장에서 본 문제가 그대로 재발합니다 — `color`가 `"red"`, `"green"`, `"yellow"` 셋 중 하나이길 기대하지만, 타입 시스템은 `"blue"`나 `"오류"` 같은 임의의 문자열도 전부 허용합니다. `next` 함수의 `else` 분기(`color`가 `"green"`도 `"red"`도 아닐 때 `"red"`로 되돌리는)가 사실은 "이런 잘못된 상태가 들어올 수 있다"는 걸 코드가 스스로 자백하고 있는 셈입니다.

== 좋은 설계: 상태는 sum 타입, 전이는 순수 함수

[source,lean]
----
inductive TrafficLight where
  | red
  | green
  | yellow
deriving DecidableEq, Repr

def TrafficLight.next : TrafficLight → TrafficLight
  | .red => .green
  | .green => .yellow
  | .yellow => .red
----

1장에서 배운 대로, 가능한 상태 세 개를 `inductive`(sum)로 표현하면 "네 번째 상태"가 애초에 존재하지 않습니다 — `next` 함수는 `red`, `green`, `yellow` 세 경우만 처리하면 되고, `TrafficLight`에 새 생성자를 추가하지 않는 한 그 외의 경우는 아예 나타날 수 없습니다. `next`는 **상태를 받아 다음 상태를 반환하는 순수 함수**입니다 — `mutable` 필드를 "갈아치우는" 게 아니라, 새로운 값을 계산해서 반환합니다.

[source,lean]
----
#eval TrafficLight.red.next          -- green
#eval TrafficLight.red.next.next     -- yellow
#eval TrafficLight.red.next.next.next -- red

example : TrafficLight.red.next.next.next = TrafficLight.red := by native_decide
----

`red.next.next.next`가 다시 `red`로 돌아온다는 걸 **증명**할 수 있다는 게, 이 상태 기계가 "값"이 되었다는 것의 실질적 의미입니다 — mutable 객체였다면 "세 번 호출하면 원래대로 돌아온다"는 성질은 테스트로 몇 번 확인해볼 수는 있어도, 이렇게 증명 대상이 되지는 않습니다.

== 이벤트가 있는 FSM: 상태만으로는 부족할 때

신호등은 "다음"이 항상 하나로 정해져 있었지만, 대부분의 실전 FSM은 **외부 이벤트에 따라 다른 상태로 갑니다**. 문 잠금장치를 생각해봅시다 — 잠긴 상태에서 올바른 비밀번호로 "잠금 해제" 이벤트가 와야 열립니다.

[source,lean]
----
inductive DoorState where
  | locked
  | unlocked
deriving DecidableEq, Repr

inductive DoorEvent where
  | unlock (code : Nat)
  | lock
  | tryUnlock (code : Nat)

def correctCode : Nat := 1234

def DoorState.transition : DoorState → DoorEvent → DoorState
  | .locked, .unlock code => if code = correctCode then .unlocked else .locked
  | .locked, .tryUnlock _ => .locked
  | .locked, .lock => .locked
  | .unlocked, .lock => .locked
  | .unlocked, _ => .unlocked

example : DoorState.locked.transition (.unlock 1234) = .unlocked := by native_decide
example : DoorState.locked.transition (.unlock 9999) = .locked := by native_decide
----

`transition : State → Event → State`가 이 장의 핵심 패턴입니다 — "지금 상태"와 "무슨 일이 일어났는가"를 받아 "다음 상태"를 계산하는 **순수 함수**입니다. 어디에도 `mutable` 필드가 없습니다. 잠긴 문에 틀린 비밀번호(`unlock 9999`)를 넣으면 `locked`로 그대로 남고, 맞는 비밀번호(`unlock 1234`)를 넣으면 `unlocked`가 됩니다 — 이 두 사실이 `native_decide`로 확인 가능한 명제입니다.

== 왜 순수 함수로 표현하는 게 중요한가

mutable 객체로 FSM을 만들면, "지금 상태가 뭔지"는 그 객체를 실행 중에 들여다봐야만 알 수 있습니다. `transition`을 순수 함수로 뽑아내면 세 가지가 달라집니다.

* *테스트가 쉬워집니다* — 객체를 생성하고 메서드를 호출해 부작용을 확인하는 대신, `DoorState.transition .locked (.unlock 1234)`처럼 입력과 출력만으로 테스트를 짤 수 있습니다.
* *성질을 증명할 수 있습니다* — 방금 본 것처럼 "세 번 전이하면 원래대로 돌아온다"나 "틀린 비밀번호로는 절대 안 열린다" 같은 성질을 코드 전체에 대해 증명할 수 있습니다.
* *합성할 수 있습니다* — `transition` 자체가 값(함수)이라, 6장에서 볼 것처럼 여러 FSM의 `transition` 함수를 조합해 더 큰 FSM을 만들 수 있습니다. mutable 객체 여러 개를 "합성"하는 것보다 함수 두 개를 합성하는 게 훨씬 명확합니다.

== 직접 해보기

* 자판기 FSM을 만들어보세요 — 상태는 `idle`(대기)과 `hasCoin`(동전 투입됨), 이벤트는 `insertCoin`과 `selectItem`입니다. `idle`에서 `insertCoin`을 받으면 `hasCoin`으로, `hasCoin`에서 `selectItem`을 받으면 다시 `idle`로 돌아가야 합니다.
* "idle 상태에서 selectItem 이벤트를 받으면 아무 일도 안 일어난다(idle에 그대로 남는다)"는 성질을 `native_decide`로 확인해보세요.

.해답 보기
[%collapsible]
====
[source,lean]
----
inductive VendingState where
  | idle
  | hasCoin
deriving DecidableEq, Repr

inductive VendingEvent where
  | insertCoin
  | selectItem

def VendingState.transition : VendingState → VendingEvent → VendingState
  | .idle, .insertCoin => .hasCoin
  | .idle, .selectItem => .idle
  | .hasCoin, .selectItem => .idle
  | .hasCoin, .insertCoin => .hasCoin

example : VendingState.idle.transition .selectItem = .idle := by native_decide
example : VendingState.idle.transition .insertCoin = .hasCoin := by native_decide
----
====

== 요약

* mutable 필드 + `if`/`else` 체인으로 상태 기계를 만들면, 타입 시스템이 막아주지 못하는 무의미한 상태가 새어 들어갈 여지가 남습니다.
* 상태를 sum 타입으로, 전이를 `transition : State → Event → State`라는 순수 함수로 표현하면 그 여지가 사라집니다.
* 순수 함수로 표현한 상태 기계는 테스트하기 쉽고, 성질을 증명할 수 있고, 다른 상태 기계와 합성할 수 있습니다.

다음 장에서는 이 `transition` 패턴이 범주론적으로 왜 "coalgebra"라고 불리는지, 그리고 그 관점이 실전에 어떤 도움을 주는지 다룹니다.
