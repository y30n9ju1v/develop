'''

`linear-and-session-types` 5~7장의 핵심 아이디어를 한 문장으로 되짚으면 — **"다음에 무엇을 할 수 있는가"를 타입으로 표현하면, 프로토콜을 어긴 프로그램은 타입이 안 맞아서 거부된다**는 것이었습니다. 이 장에서는 2장의 `Connection` 클래스를 이 아이디어로 다시 짜서, 순서를 어긴 호출이 실제로 컴파일 에러가 되는지 확인합니다.

== 핵심 아이디어: 상태마다 다른 타입, 메서드는 다음 상태를 반환한다

[source,cpp]
----
class Connected;  // 전방 선언

class Disconnected {
public:
  [[nodiscard]] Connected connect() &&;   // Disconnected에는 send()가 없다!
};

class Connected {
public:
  Connected(int) {}
  [[nodiscard]] Connected send(const std::string& msg) && {
    std::cout << "sent: " << msg << "\n";
    return Connected(0);
  }
  void close() && { std::cout << "closed\n"; }  // Connected에는 connect()가 없다!
};

Connected Disconnected::connect() && {
  std::cout << "connected\n";
  return Connected(0);
}
----

2장의 `Connection`과 결정적으로 다른 점이 셋 있습니다.

1. **`send`는 `Disconnected`에 아예 없습니다.** "연결 안 된 상태에서 보내려는" 실수는 이제 "그런 멤버 함수가 없다"는 컴파일 에러가 됩니다 — `if (!connected_)`라는 런타임 방어 코드가 필요 없어집니다.
2. **모든 메서드가 `&&`로 한정되어 있습니다**(rvalue-qualified member function) — `Disconnected` **값**(lvalue, 즉 이름 붙은 변수)에는 이 메서드들을 직접 부를 수 없고, 반드시 `std::move`로 "이 값을 소비하겠다"는 의사를 명시해야 부를 수 있습니다.
3. **`connect()`와 `send()`는 다음 상태를 반환합니다** — `Disconnected::connect()`는 `Connected`를, `Connected::send()`는 새 `Connected`를 돌려줍니다. `linear-and-session-types` 6장의 `HasSType`에서 `send` 규칙이 "그다음 명세 `S`를 지키는 `k`가 있어야 한다"고 요구했던 것과 같은 모양입니다 — 한 스텝 진행할 때마다 "그다음에 뭘 할 수 있는지"를 담은 새 타입이 나옵니다.

== 검증 1: 올바른 순서는 통과한다

[source,cpp]
----
int main() {
  Disconnected d;
  auto c1 = std::move(d).connect();
  auto c2 = std::move(c1).send("hello");
  std::move(c2).close();
}
----

[source]
----
$ clang++ -std=c++23 -O0 typestate1.cpp -o typestate1 && ./typestate1
connected
sent: hello
closed
----

정확히 의도한 순서대로 컴파일되고 실행됩니다.

== 검증 2: `connect()` 전에 `send()`를 부르면 — 컴파일이 안 된다

[source,cpp]
----
int main() {
  Disconnected d;
  auto bad = std::move(d).send("hello"); // 버그: Disconnected에는 send()가 없다
}
----

[source]
----
$ clang++ -std=c++23 -O0 typestate1_bad.cpp -o /tmp/x
typestate1_bad.cpp:18:27: error: no member named 'send' in 'Disconnected'
   18 |   auto bad = std::move(d).send("hello");
      |              ~~~~~~~~~~~~ ^
1 error generated.
----

2장에서는 이 실수가 조용히 컴파일되고 런타임에 (운이 좋으면) 방어 코드에 걸렸습니다. 이번엔 **컴파일 자체가 실패**합니다 — 정확히 이 책이 처음부터 원했던 것입니다.

== 검증 3: `\[[nodiscard]]`로 반환값을 무시하는 실수도 잡는다

`connect()`가 돌려준 `Connected`를 안 받고 버리면 어떻게 될까요 — 그 상태를 나타내는 값 자체가 사라지므로, 사실상 "연결은 했는데 그다음엔 아무것도 할 수 없는" 죽은 코드가 됩니다.

[source,cpp]
----
int main() {
  Disconnected d;
  std::move(d).connect(); // 반환값을 버림 — Connected 상태를 잃어버림
}
----

[source]
----
$ clang++ -std=c++23 -O0 -Wall typestate1_discard.cpp -o /tmp/z
typestate1_discard.cpp:18:3: warning: ignoring return value of function
declared with 'nodiscard' attribute [-Wunused-result]
----

기본은 경고입니다 — 하지만 `-Werror`(경고를 에러로 승격)를 켜면 하드 에러가 됩니다.

[source]
----
$ clang++ -std=c++23 -O0 -Wall -Werror typestate1_discard.cpp -o /tmp/z
typestate1_discard.cpp:18:3: error: ignoring return value of function
declared with 'nodiscard' attribute [-Werror,-Wunused-result]
1 error generated.
----

실전 C++ 프로젝트 대부분이 `-Werror`를 CI에서 켜두는 이유가 바로 이겁니다 — `\[[nodiscard]]`처럼 "이 경고는 사실 버그"인 것들을 빌드 실패로 확실히 승격시킵니다.

== 정직하게 짚어야 할 구멍: 같은 변수에 `std::move`를 두 번 부르면

이 패턴이 완벽하지는 않습니다. 다음 코드를 봅시다.

[source,cpp]
----
int main() {
  Disconnected d;
  auto c1 = std::move(d).connect();
  auto c2 = std::move(d).connect(); // 버그: 이미 소비된 d를 다시 connect()!
}
----

[source]
----
$ clang++ -std=c++23 -O0 -Wall typestate1_reuse.cpp -o /tmp/y
typestate1_reuse.cpp:18:8: warning: unused variable 'c1'
typestate1_reuse.cpp:19:8: warning: unused variable 'c2'
2 warnings generated.
----

**이건 컴파일됩니다.** `d`는 `std::move`로 "이동됐다"고 해도, C++에서 이동은 변수 `d` 자체를 없애지 않습니다 — `d`는 여전히 스코프 안에 살아 있는(그저 "이동된 뒤라 내용이 비어 있을 수 있는") 유효한 변수입니다. `Disconnected`는 멤버 변수가 없는 빈 클래스라서 "이동된 뒤"와 "이동되기 전"이 구별조차 안 됩니다 — 두 번째 `connect()` 호출도 똑같이 잘 작동해버립니다.

이게 `linear-and-session-types` 2장이 컨텍스트 쪼개기로 정확히 막았던("변수를 두 번 쓰면 `Disjoint` 조건이 깨진다") 바로 그 버그입니다 — C++의 이동 의미론은 **"이동한 뒤에도 원래 변수를 계속 쓸 수 있다"** 는 전제 위에 있어서, "정확히 한 번"을 완벽하게 강제하지는 못합니다. 이 구멍을 얼마나 메울 수 있는지는 다음 장에서 다룹니다.

== 팁 박스: C++17 환경이라면

[NOTE]
====
이 장의 핵심 기법 — rvalue 한정 멤버 함수(`&&`)와 `\[[nodiscard]]` — 는 사실 **둘 다 C++11(rvalue 한정)과 C++17(`\[[nodiscard]]`가 표준 속성으로)** 부터 있었습니다. 그러니 이 장의 타입 상태 패턴 자체는 C++17에서도 한 글자도 안 바꾸고 그대로 씁니다 — 이 책에서 "C++23이 필요하다"고 짚을 만한 기능은 아직 등장하지 않았습니다.

다만 컴파일러 지원의 실전적인 차이가 하나 있습니다 — `\[[nodiscard]]`를 **함수 선언**이 아니라 **타입 자체**에 붙이는 `\[[nodiscard]] class Connected { ... };` 형태도 C++17부터 쓸 수 있는데, 이러면 그 타입을 반환하는 모든 함수가 자동으로 `\[[nodiscard]]`가 됩니다 — 이 책의 `Connected`/`Disconnected`처럼 상태 클래스가 여러 개인 설계에서는, 함수마다 일일이 `\[[nodiscard]]`를 안 붙이고 타입 선언 한 번으로 끝내는 이 방식이 실수를 줄이는 데 더 안전합니다.
====

== 요약

* 상태마다 다른 타입(`Disconnected`, `Connected`)을 만들고, 메서드를 rvalue 한정(`&&`)으로 선언해서 다음 상태를 반환하게 만들면, "순서를 어긴 호출"은 "그런 멤버 함수가 없다"는 실제 컴파일 에러가 됩니다.
* `\[[nodiscard]]`로 반환값(다음 상태)을 무시하는 실수도 경고로 잡고, `-Werror`로 하드 에러까지 승격시킬 수 있다는 걸 실제로 확인했습니다.
* 이 패턴에도 진짜 구멍이 있습니다 — C++의 이동은 원래 변수를 없애지 않으므로, 같은(빈) 상태 변수에 `std::move`를 두 번 불러 이미 "소비된" 상태를 재사용하는 건 여전히 컴파일됩니다. 이건 정직하게 인정하고 다음 장에서 얼마나 메울 수 있는지 다룹니다.

다음 장에서는 상태를 더 늘리고(예: 메시지를 몇 개 보낼지까지 타입에 새기는 것), 이 구멍을 부분적으로 메우는 실전 관용구(멤버 변수를 둬서 이동 후 상태를 구별 가능하게 만들기)를 다룹니다.
