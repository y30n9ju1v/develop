9장에서 `std::optional`/`std::expected`가 Functor·Monad라는 걸 확인했습니다. 이 장에서는 그걸로 **진짜 병렬로 실행되는** 두 작업을 안전하게 합성합니다.

== 두 작업을 병렬로 실행하고, 실패 가능성까지 함께 합성하기

[source,cpp]
----
std::expected<int, std::string> fetch_a() {
  std::this_thread::sleep_for(std::chrono::milliseconds(20));
  return 10;
}
std::expected<int, std::string> fetch_b() {
  std::this_thread::sleep_for(std::chrono::milliseconds(20));
  return 32;
}

int main() {
  auto start = std::chrono::steady_clock::now();

  std::future<std::expected<int, std::string>> fa = std::async(std::launch::async, fetch_a);
  std::future<std::expected<int, std::string>> fb = std::async(std::launch::async, fetch_b);

  std::expected<int, std::string> a = fa.get();
  std::expected<int, std::string> b = fb.get();

  auto combined = a.and_then([&](int av) {
    return b.and_then([av](int bv) -> std::expected<int, std::string> {
      return av + bv;
    });
  });

  auto elapsed = std::chrono::duration_cast<std::chrono::milliseconds>(
      std::chrono::steady_clock::now() - start).count();

  std::cout << "combined = " << *combined << "\n";
  std::cout << "elapsed ~" << elapsed << "ms\n";
}
----

[source]
----
$ clang++ -std=c++23 -O0 -pthread pipeline.cpp -o pipeline && ./pipeline
combined = 42
elapsed ~24ms (should be ~20ms, not ~40ms, if truly parallel)
----

`fetch_a`와 `fetch_b`는 각각 20ms씩 걸리지만, `std::async(std::launch::async, ...)`로 각자 별도 스레드에서 시작하므로 **총 걸린 시간은 40ms가 아니라 24ms**입니다(스레드 생성 오버헤드를 빼면 사실상 20ms) — 실제로 병렬 실행됐다는 걸 시간으로 측정해 확인했습니다. `and_then`으로 두 결과를 합치는 부분은 9장 그대로입니다 — 병렬로 실행됐다는 사실과, 결과를 안전하게 합성하는 방법은 서로 독립적인 관심사입니다.

== 실패가 병렬 경로 중 하나에서 나면

[source,cpp]
----
std::expected<int, std::string> fetch_a() { return 10; }
std::expected<int, std::string> fetch_b() { return std::unexpected("network error"); }
----

[source]
----
$ clang++ -std=c++23 -O0 -pthread pipeline_fail.cpp -o pipeline_fail && ./pipeline_fail
has_value: 0
error: network error
----

`fetch_b`가 실패하면, `and_then` 체인이 자동으로 그 실패를 전파해서 `combined`도 실패 상태(`"network error"`)가 됩니다 — `fetch_a`가 성공했다는 사실은 조용히 버려집니다. 이게 9장에서 확인한 Monad의 자동 전파를, 순차 코드가 아니라 **병렬로 실행된 두 결과를 합치는** 상황에 그대로 적용한 것입니다. `if (!a.has_value()) return a; if (!b.has_value()) return b; return a.value() + b.value();`를 손으로 쓰는 대신, `and_then` 체인 하나로 같은 일을 합니다.

== 정직하게 짚어야 할 한계: `std::future`엔 표준 `.then()`이 없다

이 장의 예제가 `fa.get()`과 `fb.get()`을 **먼저 부르고 나서야** `and_then`을 시작한다는 걸 눈치챘을 수도 있습니다 — `std::future<T>` 자체에는 9장의 `std::optional::and_then`에 대응하는 **표준 콤비네이터가 없습니다.** `get()`은 결과가 준비될 때까지 그 스레드를 블록시키는 동기적 연산입니다 — "이 퓨처가 끝나면 자동으로 다음 작업을 잇는다"는 진짜 비동기 체이닝은 C++23 표준에 없습니다.

직접 흉내는 낼 수 있습니다.

[source,cpp]
----
// std::future에는 표준 .then()/.and_then()이 C++23까지도 없다 -- 직접 만든다.
// 주의: 내부적으로 fut.get()으로 블록하는 새 async 작업을 또 만드는 것이라,
// "진짜" 논블로킹 합성은 아니다 (진짜 실행기가 있어야 가능하다 -- 아래 참고).
template <typename T, typename F>
auto then_async(std::future<T> fut, F f) {
  return std::async(std::launch::async, [fut = std::move(fut), f]() mutable {
    return f(fut.get());
  });
}

int main() {
  std::future<int> f = std::async(std::launch::async, [] { return 21; });
  std::future<int> g = then_async(std::move(f), [](int x) { return x * 2; });
  std::cout << "chained future result: " << g.get() << "\n";
}
----

[source]
----
$ clang++ -std=c++23 -O0 -pthread future_then.cpp -o future_then && ./future_then
chained future result: 42
----

동작은 합니다 — 하지만 `then_async`가 하는 일은 **"결과가 나올 때까지 블록하는 새 스레드를 하나 더 만드는 것"** 입니다. 체인이 길어질수록 블록된 채로 대기하는 스레드가 계속 늘어납니다 — 진짜 논블로킹 비동기 합성(스레드를 계속 만드는 대신, 콜백을 등록해두고 결과가 준비되면 그 콜백이 실행되는 방식)이 아닙니다.

이게 서문에서 미리 짚었던 지점입니다 — **C++23에는 `std::execution`(P2300, 센더/리시버)이 들어 있지 않습니다.** 그건 C++26에 채택됐습니다. 이 책이 지은 `then_async`는 그 표준 실행기 프레임워크가 정식으로 제공했을 때 나올 진짜 논블로킹 콤비네이터(`sender.then(f)`처럼, 스레드를 새로 안 만들고도 체이닝되는 것)의 아주 거친 근사일 뿐입니다 — 이 책의 다른 모든 장이 그랬듯, 이것도 "완벽한 이식이 아니라 인코딩"이라는 걸 마지막까지 정직하게 짚어둡니다.

== 이 장이 이 책 전체를 묶는 방식

이 장의 파이프라인 하나에 이 책 전체가 다 들어 있습니다.

* `std::async`로 작업을 실행하는 것 자체는 1장이 확인한 "스레드 안전성"의 영역입니다 — `fetch_a`/`fetch_b`가 전역 상태를 공유했다면 1장의 데이터 경쟁이 그대로 재현됐을 것입니다.
* `std::future`가 `then_async`에서 이동만 되고 복사되지 않는다는 것(`fut = std::move(fut)`)은 3부의 이동 전용 타입 원리입니다.
* `and_then`으로 실패를 자동 전파하는 것은 방금 이 장과 9장이 다룬 Monad입니다.

세 이론이 각자 다른 C++ 기능(스레드 동기화 도구, 이동 의미론, concepts 기반 인터페이스)으로 나타나 한 파이프라인 안에서 함께 동작한다는 것이, 이 책이 처음부터 약속한 "이론을 실전 언어로 인코딩한다"는 말의 실제 모습입니다.

== 팁 박스: C++17 환경이라면

[NOTE]
====
`std::async`와 `std::future`는 **C++11**부터 있었으므로 이 장의 병렬 실행 자체는 C++17에서 문제없이 동작합니다. 다만 `std::expected`가 **C++23**부터라서, 9장 팁 박스와 같은 이유로 C++17에서는 실패를 표현할 다른 타입이 필요합니다 — `boost::outcome`이나 직접 만든 `Result<T, E>` 유니온 타입(태그된 유니온, `std::variant<T, E>`는 C++17에 이미 있으므로 `std::variant`로 손수 `Result`를 만들 수 있습니다)이 실전에서 흔히 쓰는 대안입니다. `and_then`처럼 자동으로 전파해주는 메서드가 없으니, `std::variant`에 `std::visit`을 조합해 직접 짜야 합니다 — 이 책의 9~10장이 "공짜로" 얻은 것(멤버 함수 하나로 실패 전파)이, C++17에서는 그만큼의 보일러플레이트 코드로 되돌아간다는 게 이 책 전체를 통틀어 반복해서 확인한 패턴의 또 다른 사례입니다.
====

== 요약

* `std::async`로 두 작업을 진짜 병렬로 실행하고(실측 시간으로 확인), `std::expected`의 `and_then`으로 그 결과를 안전하게 합성해 한쪽이 실패하면 전체가 자동으로 실패로 전파된다는 걸 확인했습니다.
* `std::future`에는 표준 `.then()`이 C++23까지도 없다는 걸 정직하게 짚고, 직접 만든 `then_async`가 "블록하는 새 스레드를 만드는" 거친 근사일 뿐이며, 진짜 논블로킹 콤비네이터는 C++26의 `std::execution`을 기다려야 한다는 것까지 확인했습니다.
* 이 장 하나의 파이프라인 안에 이 책의 세 이론(스레드 안전성, 이동 전용 타입, Monad)이 각자 다른 C++ 기능으로 함께 나타난다는 것으로, 이 책 전체의 결론을 매듭지었습니다.

맺음말에서는 이 책 전체를 돌아보고, C++26의 `std::execution`과 실전 락프리 자료구조 같은 이 책이 다루지 않은 것들을 정리합니다.
