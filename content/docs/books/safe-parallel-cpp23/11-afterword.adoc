== 지나온 길

1부에서는 데이터 경쟁을 실제로 일으켜 ThreadSanitizer로 검출하고, `std::jthread`가 소멸자로 "join을 잊는" 버그를 막는다는 걸 확인한 뒤, 순서가 있는 API가 순서를 어겨도 컴파일된다는 것으로 이 책 전체가 채울 세 개의 빈칸(타입 상태, 이동 전용 타입, concepts)에 대한 지도를 그렸습니다.

2부에서는 타입 상태 패턴으로 `linear-and-session-types`의 세션 타입을 흉내냈습니다 — 상태마다 다른 타입, rvalue 한정 메서드, `requires` 절로 프로토콜을 어긴 호출이 실제로 컴파일 실패가 되는 걸 여러 번 확인했고, `std::lock_guard`가 이미 같은 원리를 쓰고 있다는 것과 `std::promise`가 같은 계약을 런타임에만 강제한다는 대비도 확인했습니다.

3부에서는 이동 전용 타입으로 `linear-and-session-types`의 선형 타입을 흉내냈습니다 — `std::unique_ptr`와 손으로 짠 `FileHandle`이 복사를 컴파일 타임에 거부하고, 이동 후 원본이 안전한 무효 상태가 된다는 걸 AddressSanitizer로 확인했고, Rule of Zero로 합성이, 스택 되감기로 예외 안전성이 "공짜로" 따라온다는 것까지 확인했습니다.

4부에서는 concepts로 범주론적 인터페이스를 짜서, `std::optional`/`std::expected`가 실제로 Functor·Monad라는 걸 `static_assert`로 확인하고, `std::async`로 진짜 병렬 실행되는 두 작업을 `and_then`으로 안전하게 합성했습니다 — 그리고 `std::future`엔 표준 `.then()`이 없다는 한계를, 직접 만든 근사와 함께 정직하게 마주했습니다.

== 이 책을 관통한 하나의 패턴

거의 모든 장에서 같은 구조가 반복됐습니다 — **(1) 이론이 무엇을 약속하는지 짚고, (2) 그 약속을 어기는 C++ 코드를 실제로 컴파일해서 통과하거나 실패하는지 확인하고, (3) 어디까지 흉내 낼 수 있고 어디서부터 못 미치는지 정직하게 선을 긋는 것.** 3장의 "같은 변수에 `std::move`를 두 번" 구멍, 4장의 "제약이 정말로 프로토콜을 지키는지는 프로그래머 책임" 지적, 9장의 "concept은 문법만 강제하지 법칙까지는 강제 안 한다"는 짚음, 10장의 "표준 `.then()`이 없다"는 인정까지 — 이 책은 C++23이 이론을 완벽하게 이식했다고 주장한 적이 한 번도 없습니다. 대신 **정확히 어디까지 인코딩되고 어디서부터 다시 프로그래머의 책임으로 돌아가는지**를 매번 실제 컴파일러 출력으로 보여주는 것에 집중했습니다.

== 이 책이 다루지 않은 것

* **`std::execution`(C++26, P2300)** — 10장에서 짚었듯, 진짜 논블로킹 비동기 콤비네이터(센더/리시버)는 C++26에야 표준이 됩니다. 이 책의 `then_async`는 그 프레임워크가 정식으로 풀어줄 문제의 아주 거친 근사였습니다.
* **락프리(lock-free) 자료구조** — `std::atomic`의 `compare_exchange`류 연산으로 뮤텍스 없이 동시 접근을 다루는 기법은 이 책에서 전혀 다루지 않았습니다. 메모리 순서(`memory_order`)의 미묘함까지 포함하면 그 자체로 책 한 권 분량입니다.
* **다자간 세션 타입의 C++ 인코딩** — `linear-and-session-types` 9장이 예고했던, 참여자 셋 이상인 프로토콜을 타입 상태로 인코딩하는 건 이 책에서 다루지 않았습니다.
* **실제 벤치마크와 스케일링** — 이 책의 모든 예제는 "정확성"(데이터 경쟁 없음, 프로토콜 위반 시 컴파일 실패)만 검증했지, 실제 성능(락 경합, 캐시 라인 튐, false sharing)은 다루지 않았습니다.

== 시리즈에서의 위치

이 책은 `linear-and-session-types`의 세 이론(선형 타입, 세션 타입 — 그리고 이 책 자체에서 추가로 다룬 범주론)을 Lean4의 형식 증명에서 C++23의 실무 코드로 옮기는 다리였습니다. 두 책을 나란히 읽으면 "이 정리가 왜 성립하는가"(Lean4 쪽의 증명)와 "이 보장이 실전 코드에서 정확히 어디까지 유지되고 어디서 무너지는가"(이 책의 컴파일러 출력)를 함께 볼 수 있습니다 — 이론과 실무 사이의 그 간극을 눈으로 확인하는 게, 이론만 배우거나 실무 관용구만 외우는 것보다 오래 남는 이해라고 믿습니다.

이 책을 이해했다는 건 `requires (N == 0)`이라는 문법이나 Rule of Five의 다섯 함수 시그니처를 외웠다는 뜻이 아니라, 새로운 병렬 프로그래밍 문제를 마주쳤을 때 "이걸 타입 상태로 표현할 수 있는가, 이 자원은 이동 전용으로 만들 수 있는가, 이 실패 가능한 계산은 Monad로 합성할 수 있는가"를 순서대로 짚어보고, 그 답이 정말인지 컴파일러에게 직접 물어볼 수 있게 되는 것입니다. 이 책이 그 습관의 첫걸음을 놓아줬다면, 그것으로 충분합니다.
