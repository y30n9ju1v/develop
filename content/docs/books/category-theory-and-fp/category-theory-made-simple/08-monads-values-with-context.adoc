3부는 범주론이 실전에서 무엇을 해내는지 보는 부입니다. 첫 번째 사례는 프로그래밍 세계에서 특히 유명해진 개념, **모나드(monad)**입니다.

== 값을 상자에 담기

"어떤 값이 있을 수도, 없을 수도 있다"는 상황을 생각해봅시다 — 예를 들어 "이름으로 사람을 검색했는데, 그런 사람이 있을 수도 없을 수도 있다"는 상황입니다. 이걸 표현하는 자연스러운 방법은, 값을 **상자**에 담아서 "상자 안에 값이 있음" 또는 "상자가 비어 있음"이라는 두 가지 상태 중 하나로 나타내는 것입니다.

이 "상자에 담기"는 정확히 3장에서 배운 함수자입니다 — `A`라는 대상을 "`A`의 값이 있거나 없는 상자"라는 새로운 대상으로 옮기고, `A`에서 `B`로 가는 함수도 "상자 안의 값에 적용하는 함수"로 옮깁니다(상자가 비어 있으면 그냥 빈 상자로 둡니다). 이런 함수자를 종종 `Maybe`나 `Optional`이라고 부릅니다.

[source]
----
     A                    Maybe(A) = "A값이 있거나 없는 상자"
     |                              |
     f                          Maybe(f)
     |                              |
     v                              v
     B                    Maybe(B) = "B값이 있거나 없는 상자"
----

== 상자를 두 번 씌우면 생기는 문제

여기서 실전적인 문제가 하나 생깁니다 — "이름으로 사람을 찾는" 함수와 "그 사람의 생일을 조회하는" 함수를 이어붙이고 싶다고 합시다. 두 함수 모두 "찾았을 수도, 못 찾았을 수도 있다"는 상자를 반환합니다. 그런데 "이름 → 상자에 담긴 사람"이라는 함수의 결과에, "사람 → 상자에 담긴 생일"이라는 함수를 그냥 이어붙이려 하면, 상자 안에 **다시 상자를 넣게** 됩니다 — "상자 안에 든 상자"라는 어색한 이중 포장이 생기는 것입니다.

[source]
----
    이름 --찾기--> Maybe(사람) --생일조회--> Maybe(Maybe(생일))
                                              ↑ 상자 안에 상자!
----

== 구체적인 예시로 이중 포장 문제 확인하기

`이름부 = {"철수": 존재함, "영희": 없음}`인 작은 명부가 있고, "이름 → 상자에 담긴 사람"이라는 함수 `찾기`가 `찾기("철수") = "철수라는 사람이 담긴 상자"`, `찾기("영희") = "빈 상자"`를 돌려준다고 합시다. 그리고 "사람 → 상자에 담긴 생일" 함수 `생일조회`가 있어서, `생일조회(철수) = "3월 5일이 담긴 상자"`를 돌려준다고 합시다.

`"철수"`에 `찾기`를 적용하면 `"철수가 담긴 상자"`가 나옵니다. 여기에 `생일조회`를 그냥 적용하려 하면 문제가 생깁니다 — `생일조회`는 "사람"을 받는 함수인데, 지금 손에 있는 건 "사람이 담긴 상자"이지 사람 그 자체가 아닙니다. 3장에서 배운 함수자의 방식대로 상자 안에 있는 값에 함수를 "옮겨서" 적용하면(`Maybe(생일조회)`), `"철수가 담긴 상자"`가 `"(3월 5일이 담긴 상자)가 담긴 상자"`로 바뀝니다 — 상자 안에 다시 상자가 든, 어색한 이중 포장입니다.

== 모나드: 상자를 납작하게 펴는 방법

**모나드**는 정확히 이 문제를 푸는 도구입니다 — 함수자(상자에 담기)에, 두 가지 추가 규칙을 더한 것입니다.

* **값 하나를 상자에 담는 방법**(`pure` 또는 `return`이라고 부릅니다): 평범한 값 하나를 받아서, "그 값이 들어있는" 가장 단순한 상자를 만듭니다.
* **상자 안의 상자를 납작하게 펴는 방법**(`join` 또는 `flatten`이라고 부릅니다): "상자 안에 든 상자"를 받아서, 그 안의 값을 꺼내 바깥 상자 하나로 다시 포장합니다 — 이중 포장을 한 겹으로 줄입니다.

[source]
----
    Maybe(Maybe(생일)) --join--> Maybe(생일)
----

이 `join`이 있으면, "이름 → 상자에 담긴 사람"과 "사람 → 상자에 담긴 생일"을 이어붙일 때마다 자동으로 생기는 이중 포장을, 매번 손으로 까지 않고 `join` 하나로 정리할 수 있습니다. 앞서 본 `"철수"` 예시에 이어서, `"(3월 5일이 담긴 상자)가 담긴 상자"`에 `join`을 적용하면 정확히 `"3월 5일이 담긴 상자"`가 나옵니다 — `"영희"`처럼 애초에 `찾기`에서 빈 상자가 나왔다면, `Maybe(생일조회)`를 적용해도 여전히 빈 상자이고(빈 상자에는 적용할 값이 없으니까요), `join`을 적용해도 빈 상자 그대로입니다. "찾기 다음 생일조회"라는 두 단계가 어느 지점에서 실패하든, 최종 결과는 자연스럽게 빈 상자로 이어지고, 성공하는 경우엔 이중 포장 없이 깔끔하게 값 하나만 남습니다.

실전에서는 "함수자로 옮기고 나서 `join`으로 편다"는 이 두 단계를 한 번에 묶은 `bind`(또는 `flatMap`)라는 연산을 더 자주 씁니다 — `찾기("철수")`의 결과에 `생일조회`를 `bind`로 바로 이어붙이면, 중간의 이중 포장 단계를 거치지 않고 곧바로 `"3월 5일이 담긴 상자"`를 얻습니다. `bind`는 사실 "함수자로 옮기기"와 "`join`으로 펴기"를 합쳐놓은 줄임표기일 뿐이라, 이 장에서 배운 두 재료(함수자의 이동, `join`)만 있으면 `bind`가 무엇을 하는지 완전히 설명됩니다.

그리고 이 `pure`와 `join`은 아무렇게나 정해도 되는 게 아니라, 몇 가지 정합성 조건(예를 들어 "빈 포장을 붙였다 떼도 원래 값이 그대로여야 한다")을 만족해야 진짜 모나드가 됩니다 — 이 조건들은 2장에서 본 결합법칙·항등 조건과 결이 같은, "포장을 아무리 반복해도 일관성이 무너지지 않는다"는 요구입니다.

== 리스트도 상자다

"값이 있거나 없다"는 `Maybe` 말고, "값이 여러 개일 수 있다"는 리스트도 똑같은 틀로 확인해볼 수 있습니다. `한국의도시("서울") = ["강남구", "종로구"]`(서울 안의 구 목록)이고, `맛집(구) = 그 구의 맛집 목록`을 돌려주는 함수가 있다고 합시다. `"서울"`에 `한국의도시`를 적용하면 `["강남구", "종로구"]`가 나오고, 여기에 `맛집`을 함수자의 방식으로 옮겨 적용하면 `[["강남집", "역삼분식"], ["광화문냉면", "인사동떡볶이"]]`처럼 **리스트의 리스트**가 됩니다 — 이게 리스트 버전의 "상자 안의 상자"입니다. 여기에 `join`을 적용하면 바깥 리스트를 걷어내고 안의 리스트들을 전부 하나로 이어붙여 `["강남집", "역삼분식", "광화문냉면", "인사동떡볶이"]`라는 평평한 목록 하나가 됩니다 — "서울의 모든 구의 모든 맛집을 하나의 목록으로 모은다"는, 실전에서 아주 흔히 마주치는 작업이 정확히 리스트 모나드의 `join`입니다.

== 상자는 "가능함(Maybe)"만이 아니다

이 "상자"라는 그림은 "값이 있거나 없다"는 상황에만 쓰이는 게 아닙니다 — "값이 여러 개일 수 있다"(리스트), "값을 계산하려면 시간이 걸린다"(비동기 작업), "값을 계산하는 과정에서 오류가 날 수 있다"(예외 처리), "값이 외부 세계와 상호작용해야 나온다"(입출력) 같은 상황들도 전부 같은 틀 — 함수자로 값에 어떤 **맥락**을 씌우고, `pure`와 `join`으로 그 맥락을 이어붙이는 방식 — 으로 표현됩니다. "값이 있을 수도 없을 수도 있다"는 것도, "값이 여러 개다"는 것도, "값을 얻으려면 부작용이 필요하다"는 것도 전부 **맥락**의 한 종류이고, 모나드는 이 서로 다른 맥락들을 **하나의 공통된 방식으로 이어붙이는 법**을 알려줍니다. 이게 왜 프로그래밍 언어들이 모나드라는 범주론 개념을 그대로 실전 도구로 받아들였는지의 이유입니다.

== 요약

* 값에 "맥락"(있을 수도 없음, 여러 개일 수 있음, 오류가 날 수 있음 등)을 씌우는 함수자가 모나드의 출발점입니다.
* 맥락을 씌운 결과를 계속 이어붙이면 "상자 안의 상자"라는 이중 포장 문제가 생깁니다.
* 모나드는 값 하나를 상자에 담는 `pure`와, 이중 포장을 한 겹으로 펴는 `join`을 갖춘 함수자이고, 이 둘은 정합성 조건을 만족해야 합니다.
* "가능함", "여러 개", "오류", "부작용" 같은 서로 다른 맥락들이 전부 이 하나의 틀로 통일됩니다.

다음 장에서는 이 모나드가 실제로 살고 있는 세계, 즉 프로그래밍 언어의 타입과 함수 자체가 하나의 범주를 이룬다는 걸 확인합니다.
