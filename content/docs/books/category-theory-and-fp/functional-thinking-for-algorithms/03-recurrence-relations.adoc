== 재귀 정의를 그대로 시간 계산식으로 옮기기

1장에서 팩토리얼을 재귀적으로 정의했습니다.

....
    0! = 1
    n! = n × (n-1)!
....

여기서 흥미로운 사실이 하나 있습니다 — 이 정의를 그대로 옮기면, `factorial(n)`이 **얼마나 걸리는지**도 함께 정의됩니다. `factorial(n)`을 계산하려면 곱셈 한 번(`n ×`)과, `factorial(n-1)`을 계산하는 시간이 필요합니다. 이걸 `T(n)`(입력 크기 `n`에 대한 실행 시간)이라는 기호로 적어봅시다.

....
    T(0) = O(1)                (기저 사례: 상수 시간)
    T(n) = T(n-1) + O(1)       (재귀 사례: 부분 문제 + 곱셈 한 번)
....

이렇게 함수 자신을 이용해 실행 시간을 정의한 식을 **재귀 관계(recurrence relation)**라고 부릅니다. 정의 자체가 재귀적이니, 그 정의를 실행하는 데 걸리는 시간도 자연스럽게 재귀적으로 적히는 것뿐입니다.

== 재귀 관계 풀어보기: 펼쳐 적기

`T(n) = T(n-1) + O(1)`이 정확히 얼마인지 알아내려면, 이 식을 계속 펼쳐 적어봅니다.

....
    T(n) = T(n-1) + O(1)
         = (T(n-2) + O(1)) + O(1) = T(n-2) + O(1)×2
         = T(n-3) + O(1)×3
         ⋮
         = T(0) + O(1)×n
         = O(1) + O(1)×n
         = O(n)
....

`n`번 펼치면 기저 사례 `T(0)`에 도달하고, 그 사이 `O(1)`짜리 작업이 `n`번 더해집니다. 그래서 `T(n) = O(n)`, 즉 **입력이 두 배로 커지면 시간도 두 배로 커지는** 선형 시간입니다. `length`, `sum_list`도 재귀 관계 모양이 완전히 같으니(`T(n) = T(n-1) + O(1)`) 전부 `O(n)`입니다.

== 그런데 모든 재귀가 선형은 아니다: 피보나치의 함정

이번엔 피보나치 수열을 정의 그대로 코드로 옮겨봅시다.

....
    fib(0) = 0
    fib(1) = 1
    fib(n) = fib(n-1) + fib(n-2)      (n ≥ 2)
....

[source,python]
----
def fib_naive(n):
    if n <= 1:
        return n
    return fib_naive(n - 1) + fib_naive(n - 2)
----

정의를 그대로 옮겼을 뿐인데, 재귀 관계를 적어보면 팩토리얼과 모양이 다릅니다.

....
    T(n) = T(n-1) + T(n-2) + O(1)
....

`T(n-1)` 하나만 있는 게 아니라 `T(n-1)`과 `T(n-2)`, **재귀 호출이 두 갈래**로 갈라집니다. 이게 얼마나 큰 차이를 만드는지 직접 실행해서 확인해봅시다. 재귀 호출이 정확히 몇 번 일어나는지 세어보겠습니다.

[source,python]
----
calls = 0

def fib_count(n):
    global calls
    calls += 1
    if n <= 1:
        return n
    return fib_count(n - 1) + fib_count(n - 2)

for n in [5, 10, 20, 30]:
    calls = 0
    fib_count(n)
    print(f"n={n}: 호출 횟수={calls}")
----

[source]
----
n=5: 호출 횟수=15
n=10: 호출 횟수=177
n=20: 호출 횟수=21891
n=30: 호출 횟수=2692537
----

`n`이 `10`에서 `20`으로(딱 두 배) 늘었을 뿐인데 호출 횟수는 `177`에서 `21891`로, 약 `124`배 뛰었습니다. `20`에서 `30`으로 `1.5`배 늘었는데 호출 횟수는 또 `123`배 뛰었습니다. 실행 시간도 그대로 따라갑니다.

[source,python]
----
import time

for n in [10, 20, 30, 32, 34]:
    t0 = time.perf_counter()
    result = fib_naive(n)
    t1 = time.perf_counter()
    print(f"fib_naive({n}) = {result}, {(t1 - t0) * 1000:.2f}ms")
----

[source]
----
fib_naive(10) = 55, 0.01ms
fib_naive(20) = 6765, 0.51ms
fib_naive(30) = 832040, 54.41ms
fib_naive(32) = 2178309, 135.39ms
fib_naive(34) = 5702887, 361.67ms
----

`n`이 `2`씩 늘 때마다 걸리는 시간이 대략 `2.5`~`2.7`배씩 뛰고 있습니다. `T(n) = T(n-1) + T(n-2) + O(1)`이라는 재귀 관계를 실제로 풀면 `T(n) = O(φⁿ)`(황금비 `φ ≈ 1.618`)이 나오는데, `n`이 `2` 늘 때 `φ² ≈ 2.618`배 늘어난다는 계산과 방금 실측한 배율이 정확히 들어맞습니다. 지수적으로 폭발하니, `n = 50`쯤이면 이미 계산이 끝나기를 기다리기 힘든 수준이 됩니다.

[NOTE]
====
**왜 이렇게 느려지는가**: `fib_naive(5)`를 계산하는 과정을 그려보면, `fib_naive(3)`이 `fib_naive(5)` 안에서도, `fib_naive(4)` 안에서도 각각 따로 계산됩니다 — **같은 부분 문제를 몇 번이고 처음부터 다시 계산**하는 것입니다. 재귀 사례가 갈라지는 두 갈래(`fib(n-1)`, `fib(n-2)`)가 서로 겹치는 부분 문제를 공유하는데도, 이 코드는 그 사실을 전혀 활용하지 않습니다. 8장(메모이제이션)에서 바로 이 낭비를 없애는 법을 다룹니다.
====

== 세 번째 모양: 나누면서 합치기

재귀 관계에는 세 번째로 중요한 모양이 있습니다. 다음 장에서 다룰 병합 정렬을 미리 살짝 보면, 재귀 관계가 이렇게 생겼습니다.

....
    T(n) = 2·T(n/2) + O(n)
....

`n-1`씩 줄어드는 게 아니라 **절반으로** 줄어들고, 갈래는 두 개(`2·T(n/2)`)입니다. 이걸 재귀 트리로 그려보면 감이 잡힙니다.

....
[ T(n) = 2·T(n/2) + O(n)의 재귀 트리 ]

  레벨 0:            [ n ]                     작업량 O(n)
                    /       \
  레벨 1:      [n/2]         [n/2]              작업량 O(n/2) + O(n/2) = O(n)
              /    \        /    \
  레벨 2:  [n/4] [n/4]   [n/4] [n/4]             작업량 O(n)
             ⋮      ⋮       ⋮      ⋮
  레벨 log₂n:  [1][1] ... [1][1]                작업량 O(n)

  ==> 레벨마다 작업량은 항상 O(n)으로 똑같고,
      레벨 개수는 n이 1이 될 때까지 절반씩 줄어드니 O(log n)개.
      총 작업량 = O(n) × O(log n) = O(n log n)
....

핵심 관찰은 이겁니다 — **한 레벨(가로줄) 전체의 작업량은 항상 `O(n)`으로 똑같습니다.** 아래로 내려갈수록 문제는 더 작아지지만 그만큼 개수가 늘어나서, 곱은 항상 `n`으로 일정합니다. 그리고 `n`이 절반씩 줄어들어 `1`에 도달하려면 `log₂n`번 절반을 밟아야 하니, 레벨은 `O(log n)`개입니다. 그래서 총 작업량은 `O(n) × O(log n) = O(n log n)`입니다.

`O(n)`, `O(n²)`, `O(nⁿ)`(순진한 피보나치처럼 지수적으로) 사이에 있는 이 `O(n log n)`이라는 중간 지대가, 2부에서 볼 병합 정렬과 퀵 정렬이 왜 `O(n²)` 정렬보다 훨씬 빠른지를 설명하는 열쇠입니다.

[TIP]
====
방금 쓴 "레벨마다 작업량을 세고, 레벨 개수를 곱한다"는 방법은 사실 **재귀 트리법(recursion tree method)**이라는 정식 기법이고, 이걸 일반화해서 `T(n) = a·T(n/b) + O(nᵈ)` 모양의 재귀 관계를 공식으로 바로 풀어주는 것이 **마스터 정리(Master Theorem)**입니다. 이 책에서는 공식을 암기하기보다 재귀 트리를 직접 그려보는 감각을 우선하지만, 다양한 재귀 관계를 빠르게 분류하고 싶다면 마스터 정리를 별도로 찾아보는 것도 좋습니다.
====

== 직접 해보기

이진 탐색(정렬된 리스트를 절반씩 좁혀가며 찾는 방법)의 재귀 관계를 직접 세워보세요. 한 번 호출될 때마다 리스트를 절반으로 줄이고, 비교는 딱 한 번만 합니다.

* `T(n)`을 `T(n/2)`를 이용한 재귀 관계로 적어보세요.
* 재귀 트리를 그려서(혹은 펼쳐 적어서) `T(n)`이 몇 차수인지 구해보세요.

.해답 보기
[%collapsible]
====
....
    T(n) = T(n/2) + O(1)
....

이번엔 갈래가 하나뿐이라 앞의 재귀 트리보다 훨씬 단순합니다. 펼쳐 적으면:

....
    T(n) = T(n/2) + O(1)
         = T(n/4) + O(1)×2
         = T(n/8) + O(1)×3
         ⋮
         = T(1) + O(1)×log₂n
         = O(log n)
....

매번 문제 크기가 절반이 되고, 매번 상수만큼만 일하니, `n`이 `1`에 도달할 때까지 걸리는 단계 수(`log₂n`)만큼만 상수 작업이 쌓입니다. 그래서 이진 탐색은 `O(log n)`입니다 — 2부 5장에서 볼 실제 이진 탐색 코드도 정확히 이 재귀 관계를 따릅니다.

== 요약

* 재귀 함수의 실행 시간은 그 함수의 정의를 그대로 따라, **재귀 관계**(자기 자신을 이용해 시간을 정의하는 식)로 적을 수 있습니다.
* `T(n) = T(n-1) + O(1)`(팩토리얼, 리스트 순회)은 펼쳐 적으면 `O(n)`, 즉 선형 시간입니다.
* `T(n) = T(n-1) + T(n-2) + O(1)`(순진한 피보나치)처럼 갈래가 두 개로 겹치면서 갈라지면 `O(φⁿ)`, 지수적으로 폭발합니다 — 실측으로 `n`이 `2` 늘 때마다 시간이 약 `2.6`배씩 뛰는 걸 확인했습니다.
* `T(n) = 2·T(n/2) + O(n)`(나누고 합치는 재귀)은 재귀 트리의 각 레벨이 항상 `O(n)`이고 레벨이 `O(log n)`개라서, 총 `O(n log n)`이 됩니다.

다음 장에서는 바로 이 `2·T(n/2) + O(n)` 모양을 실제 정렬 알고리즘으로 만들어봅니다. 병합 정렬을 재귀적으로 정의하고, 2장의 구조적 귀납으로 "정말 정렬이 되는가"를 증명한 뒤, 이 장의 재귀 트리로 "왜 `O(n log n)`인가"를 확인합니다.
