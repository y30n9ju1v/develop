이 책은 내내 "재귀는 반복문의 사촌이 아니라 정의를 정의로 푸는 방법"이라고 강조했습니다. 그런데 1장의 NOTE에서 살짝 짚었듯, 파이썬 같은 언어에서는 재귀가 반복문보다 느리고 함수 호출 스택 깊이에도 한계가 있다는 실전 문제가 있습니다. 이 장에서는 재귀적으로 **생각한** 알고리즘을, 실행할 땐 반복문으로 **바꾸는** 기계적인 방법을 다룹니다.

== 팩토리얼을 다시, 이번엔 "할 일을 남기지 않고"

1장의 `factorial`을 다시 봅시다.

[source,python]
----
def factorial(n):
    if n == 0:
        return 1
    return n * factorial(n - 1)
----

`return n * factorial(n - 1)`을 자세히 보면, 재귀 호출(`factorial(n-1)`)이 끝난 **뒤에도** `n`을 곱하는 일이 남아있습니다. 이렇게 재귀 호출 뒤에 처리할 일이 남아있으면, 그 호출이 끝날 때까지 "곱하기를 잊지 않고 기다려야" 하므로 각 단계의 상태를 어딘가에 쌓아둬야 합니다.

이걸 바꿔서, 재귀 호출이 **정말 마지막으로 하는 일**이 되도록 고쳐봅시다. "지금까지 곱한 값"을 매개변수로 들고 다니면 됩니다.

[source,python]
----
def factorial_tail(n, acc=1):
    if n == 0:
        return acc
    return factorial_tail(n - 1, acc * n)
----

`acc`(누산기, accumulator)가 "지금까지의 곱셈 결과"를 들고 다니고, `return factorial_tail(n - 1, acc * n)`은 재귀 호출을 한 뒤 **아무것도 더 할 일이 없습니다** — 재귀 호출의 결과가 곧 이 함수의 결과입니다. 이런 모양의 재귀를 **꼬리 재귀(tail recursion)**라고 부릅니다.

[source]
----
factorial(10)       -> 3628800
factorial_tail(10)  -> 3628800   (같은 값)
----

== 그런데 파이썬은 이걸 최적화해주지 않는다

많은 함수형 언어(스킴, 하스켈, 얼랭 등)는 꼬리 재귀를 발견하면 **꼬리 호출 최적화(tail-call optimization, TCO)**라는 걸 자동으로 적용해서, 이전 호출의 스택 공간을 재사용합니다 — 사실상 반복문처럼 실행되어, 스택이 쌓이지 않습니다. 파이썬에서 이게 어떻게 되는지 확인해봅시다.

[source,python]
----
import sys
print(sys.getrecursionlimit())  # 파이썬 기본 재귀 한도

for name, f in [("factorial", factorial), ("factorial_tail", factorial_tail)]:
    try:
        f(3000)
        print(f"{name}(3000) 성공")
    except RecursionError:
        print(f"{name}(3000) -> RecursionError")
----

[source]
----
1000
factorial(3000) -> RecursionError
factorial_tail(3000) -> RecursionError
----

`factorial_tail`이 "이론적으로는" 꼬리 재귀인데도, **파이썬은 TCO를 지원하지 않기 때문에** 여전히 호출마다 스택 프레임을 쌓고, 결국 똑같이 `RecursionError`가 납니다. 이건 중요한 현실입니다 — **"꼬리 재귀로 고쳤다"는 것과 "실제로 반복문처럼 실행된다"는 것은 언어에 따라 다른 이야기**입니다. 파이썬에서 재귀 깊이 문제를 정말로 해결하려면, 꼬리 재귀를 한 걸음 더 밀어붙여 **직접 반복문으로 바꿔야** 합니다.

[NOTE]
====
**왜 파이썬은 TCO를 안 할까**
파이썬을 만든 귀도 반 로섬은 TCO를 의도적으로 넣지 않았다고 밝힌 적이 있습니다 — TCO가 적용되면 스택 트레이스(에러가 났을 때 "어디서 어디를 거쳐 여기까지 왔는지" 보여주는 정보)에서 중간 호출들이 사라져서, 디버깅이 오히려 어려워질 수 있다는 이유입니다. 언어마다 이런 설계 선택이 다르므로, "꼬리 재귀는 항상 빠르다"고 단정하지 말고 **쓰는 언어가 TCO를 실제로 지원하는지** 확인하는 습관이 필요합니다.
====

== 꼬리 재귀를 반복문으로: 기계적인 변환

다행히 꼬리 재귀를 반복문으로 바꾸는 건 아주 기계적인 작업입니다. 매개변수를 **반복문의 지역 변수**로, 재귀 호출을 **반복문의 한 바퀴**로 바꾸면 됩니다.

....
[ 꼬리 재귀 → 반복문 변환 규칙 ]

  def f(n, acc):              acc = 초기값
      if 기저 조건:              while not 기저 조건:
          return acc                 (acc, n) = 갱신된 값들
      return f(갱신된 n, 갱신된 acc)
                               return acc
....

[source,python]
----
def factorial_loop(n):
    acc = 1
    while n > 0:
        acc = acc * n
        n = n - 1
    return acc
----

[source]
----
factorial_loop(10)    -> 3628800   (앞의 두 버전과 동일)
factorial_loop(3000)  -> 성공 (RecursionError 없음, 재귀 깊이 제한과 무관)
----

`acc * n`이 꼬리 재귀 버전의 `acc * n`(두 번째 인자로 넘기던 식)과 글자 그대로 같고, `n = n - 1`이 첫 번째 인자로 넘기던 `n - 1`과 같습니다. 재귀 호출이 있던 자리가 그냥 `while` 루프의 다음 바퀴로 바뀌었을 뿐입니다.

이 변환은 사실 5장의 "직접 해보기"(이진 탐색을 반복문으로)에서 이미 한 번 해봤던 것과 똑같습니다 — 이진 탐색의 `binary_search(lst, target, mid+1, hi)`도 꼬리 재귀였고, 그걸 `while lo <= hi:`로 바꾼 게 바로 이 변환입니다.

== 모든 재귀가 이렇게 쉽게 바뀌지는 않는다

여기서 중요한 전제를 짚어야 합니다 — **꼬리 재귀만** 이렇게 간단히 반복문으로 바뀝니다. 1장의 원래 `factorial`(꼬리 재귀가 아닌)이나, 4장의 병합 정렬(재귀 호출이 두 번, 그것도 재귀 호출 뒤에 `merge`라는 할 일이 남아있는)처럼 "재귀 호출 뒤에 할 일이 남아있는" 함수는, 그 "남은 할 일"을 어딘가에 저장해둬야 합니다. 이럴 때 반복문으로 바꾸려면 10장에서 본 것처럼 **명시적인 스택**을 직접 관리해야 합니다 — 재귀 호출이 암묵적으로 콜 스택에 쌓아뒀던 "돌아와서 할 일"을, 이번엔 우리가 손으로 쌓아야 하는 것입니다.

즉 재귀를 반복문으로 바꾸는 데는 두 단계가 있습니다.

* **꼬리 재귀** → **단순 반복문**: 누산기를 지역 변수로, 재귀 호출을 루프 한 바퀴로. (이 장에서 다룬 방법)
* **일반 재귀**(꼬리가 아닌) → **명시적 스택 + 반복문**: 10장에서 DFS를 스택으로 바꿨던 방법.

== 직접 해보기

리스트를 뒤집는 함수를 꼬리 재귀로 짜고, 그걸 다시 반복문으로 바꿔보세요.

.해답 보기
[%collapsible]
====
[source,python]
----
def reverse_tail(lst, acc=None):
    if acc is None:
        acc = []
    if lst == []:
        return acc
    return reverse_tail(lst[1:], [lst[0]] + acc)

def reverse_loop(lst):
    acc = []
    while lst != []:
        acc = [lst[0]] + acc
        lst = lst[1:]
    return acc
----

[source]
----
reverse_tail([1, 2, 3, 4, 5])  -> [5, 4, 3, 2, 1]
reverse_loop([1, 2, 3, 4, 5])  -> [5, 4, 3, 2, 1]
----

`reverse_tail`의 재귀 호출(`reverse_tail(lst[1:], [lst[0]] + acc)`) 뒤에 아무 할 일도 남아있지 않으므로 꼬리 재귀이고, 이 장의 변환 규칙을 그대로 적용해 `while` 루프로 바꿀 수 있었습니다.
====

== 요약

* 재귀 호출 뒤에 더 할 일이 없는 재귀를 **꼬리 재귀**라고 부릅니다. 누산기(지금까지의 결과를 담는 추가 매개변수)를 도입하면 많은 재귀 함수를 꼬리 재귀 형태로 고칠 수 있습니다.
* 파이썬은 꼬리 호출 최적화(TCO)를 지원하지 않으므로, 꼬리 재귀로 고쳐도 여전히 `RecursionError`가 날 수 있다는 걸 실측으로 확인했습니다. 이론적인 꼬리 재귀와 실제 실행 방식은 언어에 따라 다릅니다.
* 꼬리 재귀는 누산기를 지역 변수로, 재귀 호출을 루프 한 바퀴로 바꾸는 기계적인 변환을 통해 반복문으로 바뀝니다. 꼬리 재귀가 아닌 일반 재귀는 10장에서 본 명시적 스택이 필요합니다.
