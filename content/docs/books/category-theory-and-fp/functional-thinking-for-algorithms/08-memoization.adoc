== 다시 피보나치로: 무엇이 낭비였는가

3장에서 순진한 피보나치가 지수적으로 느려지는 걸 실측했습니다.

[source,python]
----
def fib_naive(n):
    if n <= 1:
        return n
    return fib_naive(n - 1) + fib_naive(n - 2)
----

왜 이렇게 느린지, `fib_naive(5)`가 호출하는 부분 문제들을 트리로 그려보면 원인이 보입니다.

....
[ fib_naive(5)의 재귀 호출 트리 ]

                        fib(5)
                      /        \
                 fib(4)          fib(3)
                /      \        /      \
           fib(3)     fib(2)  fib(2)   fib(1)
          /     \    /    \  /    \
     fib(2)  fib(1) fib(1) fib(0) fib(1) fib(0)
    /    \
 fib(1) fib(0)

   ==> fib(3)이 2번, fib(2)가 3번, fib(1)이 5번 등장!
....

`fib(3)`이 트리 안에 **두 번** 나타납니다. 한 번은 `fib(5)`의 왼쪽 가지에서, 또 한 번은 `fib(4)`의 왼쪽 가지에서 — 완전히 똑같은 계산을 처음부터 다시 하고 있습니다. `fib(2)`는 세 번, `fib(1)`은 다섯 번이나 반복됩니다. `n`이 커질수록 이 중복이 기하급수적으로 불어나는 게 3장에서 본 지수적 폭발의 정체입니다.

== 기억해두면 다시 계산할 필요가 없다

해결책은 단순합니다 — **한 번 계산한 값은 어딘가에 적어두고, 다음에 같은 값이 필요하면 계산 대신 그 기록을 그대로 꺼내 쓰는 것**입니다. 이걸 **메모이제이션(memoization)**이라고 부릅니다("메모"해둔다는 뜻입니다).

[source,python]
----
def fib_memo(n, cache=None):
    if cache is None:
        cache = {}
    if n in cache:
        return cache[n]          # 이미 계산했으면 캐시에서 바로 꺼낸다
    if n <= 1:
        return n
    result = fib_memo(n - 1, cache) + fib_memo(n - 2, cache)
    cache[n] = result             # 계산한 값을 캐시에 적어둔다
    return result
----

바뀐 부분은 딱 두 줄입니다 — 시작할 때 캐시에 있는지 확인하는 줄, 끝날 때 캐시에 적어두는 줄. 재귀의 몸통(`fib_memo(n-1, cache) + fib_memo(n-2, cache)`)은 원래 정의 그대로입니다.

== 실측: O(φⁿ)이 O(n)으로

[source,python]
----
import time

for n in [30, 40, 50, 100]:
    t0 = time.perf_counter()
    result = fib_memo(n)
    t1 = time.perf_counter()
    print(f"fib_memo({n}) = {result}, {(t1 - t0) * 1000:.4f}ms")
----

[source]
----
fib_memo(30)  = 832040,                          0.0067ms
fib_memo(40)  = 102334155,                       0.0062ms
fib_memo(50)  = 12586269025,                     0.0066ms
fib_memo(100) = 354224848179261915075,           0.0118ms
----

`fib_naive(30)`이 걸렸던 시간(3장에서 `54.41ms`)과 비교해보면, `fib_memo(30)`은 `0.0067ms` — 대략 **8000배** 빠릅니다. `fib_memo(100)`은 순진한 방법으로는 우주 나이를 훌쩍 넘길 계산인데도 즉시 끝납니다.

호출 횟수를 세어봐도 그 이유가 분명합니다.

[source]
----
n=10: 호출 횟수=19
n=20: 호출 횟수=39
n=30: 호출 횟수=59
----

3장에서 `fib_naive`는 `n=10`에 `177`번, `n=30`에 `269`만 번 호출됐습니다. `fib_memo`는 `n=10`에 `19`번, `n=30`에 `59`번뿐입니다. `n`이 두 배가 돼도 호출 횟수는 대략 두 배씩만 늘어나는, **선형**에 가까운 패턴입니다.

== 재귀 관계가 왜 바뀌었는가

3장에서 순진한 피보나치의 재귀 관계는 `T(n) = T(n-1) + T(n-2) + O(1)`이었고, 이걸 풀면 `O(φⁿ)`이었습니다. 메모이제이션을 쓰면 이 재귀 관계 자체가 더 이상 적용되지 않습니다. **서로 다른 부분 문제는 `fib(0)`부터 `fib(n)`까지 딱 `n+1`개뿐**이고, 캐시 덕분에 각 부분 문제는 **정확히 한 번씩만** 실제로 계산됩니다. 한 번의 실제 계산에 드는 일(캐시 조회, 덧셈)이 `O(1)`이므로, 전체 시간은 `(부분 문제 개수) × (한 번당 일) = O(n) × O(1) = O(n)`입니다.

[NOTE]
====
**메모이제이션이 정당성을 바꾸지는 않는다**
`fib_memo`가 여전히 맞는 값을 낸다는 걸 새로 증명할 필요는 없습니다 — 캐시는 계산 **순서와 횟수**만 바꿀 뿐, `fib_memo(n)`이 최종적으로 계산하는 값의 정의(`fib(n-1) + fib(n-2)`)는 원래 재귀 정의와 완전히 같습니다. "이미 계산해둔 정답을 다시 꺼내 쓰는 것"이 "틀린 답을 만들어낼" 방법은 없습니다. 2장의 구조적 귀납으로 세운 정당성은 그대로 유지되고, 메모이제이션은 순수하게 **속도**만 바꾸는 최적화입니다.
====

파이썬에는 이 패턴을 한 줄로 대신해주는 도구도 있습니다.

[source,python]
----
from functools import lru_cache

@lru_cache(maxsize=None)
def fib_lru(n):
    if n <= 1:
        return n
    return fib_lru(n - 1) + fib_lru(n - 2)
----

[source]
----
fib_lru(50)  -> 12586269025
fib_lru(100) -> 354224848179261915075
----

`@lru_cache` 데코레이터가 방금 손으로 짠 `cache` 딕셔너리와 정확히 같은 일(인자별로 결과를 기억해뒀다 재사용하는 것)을 대신 해줍니다.

== 메모이제이션이 통하는 조건

모든 재귀 함수에 메모이제이션이 도움이 되는 건 아닙니다. 1장의 `factorial`이나 `length`를 떠올려보세요 — `factorial(5)`를 계산하는 동안 `factorial(3)`은 **딱 한 번**만 나타납니다(`5! → 4! → 3! → ...`처럼 사슬 하나로 곧장 내려가니까요). 겹치는 부분 문제가 애초에 없으니 캐시에 넣어봐야 다시 꺼내 쓸 일이 없습니다.

메모이제이션이 효과를 보려면 **같은 부분 문제가 여러 경로로 반복해서 나타나야** 합니다. 이런 성질을 **중복 부분 문제(overlapping subproblems)**라고 부르고, 이 조건을 만족하는 문제들을 다루는 분야가 바로 **동적 계획법(dynamic programming)**입니다.

== 직접 해보기

계단을 오르는데 한 번에 `1`칸 또는 `2`칸씩 오를 수 있다면, `n`칸짜리 계단을 오르는 방법의 수는 몇 가지일까요? (`0`칸 남았을 때는 "이미 다 올라온 것"으로 `1`가지 방법이라고 셉니다.)

* 마지막으로 오른 한 걸음이 `1`칸이었다면, 그 직전은 `n-1`칸 계단을 오르는 문제와 같습니다.
* 마지막 한 걸음이 `2`칸이었다면, 그 직전은 `n-2`칸 계단을 오르는 문제와 같습니다.

이 두 갈래를 재귀 관계로 세우고, 메모이제이션을 적용해보세요.

.해답 보기
[%collapsible]
====
[source,python]
----
def climb_stairs(n, cache=None):
    if cache is None:
        cache = {}
    if n in cache:
        return cache[n]
    if n == 0:
        return 1
    if n < 0:
        return 0
    result = climb_stairs(n - 1, cache) + climb_stairs(n - 2, cache)
    cache[n] = result
    return result
----

[source]
----
climb_stairs(1)  -> 1
climb_stairs(2)  -> 2
climb_stairs(3)  -> 3
climb_stairs(4)  -> 5
climb_stairs(5)  -> 8
climb_stairs(10) -> 89
----

`climb_stairs(n) = climb_stairs(n-1) + climb_stairs(n-2)`라는 재귀 관계가 피보나치와 완전히 같은 모양이라는 걸 눈치채셨나요(`climb_stairs(n)`은 사실 `fib(n+1)`과 같은 수열입니다)? 서로 다른 문제처럼 보여도, 재귀 관계의 모양이 같으면 같은 해결책(메모이제이션)이 그대로 통합니다.
====

== 요약

* 순진한 재귀가 느린 이유는 재귀 자체가 아니라, **같은 부분 문제를 여러 번 다시 계산하는 중복** 때문입니다. `fib_naive(5)`의 재귀 트리를 그려보면 `fib(3)`이 두 번, `fib(1)`이 다섯 번씩 반복되는 걸 눈으로 확인할 수 있습니다.
* **메모이제이션**은 이미 계산한 부분 문제의 답을 캐시에 기억해뒀다가 재사용하는 것으로, 함수의 정의(따라서 정당성)는 전혀 바꾸지 않고 속도만 바꿉니다. `fib_naive(30)`의 `54ms`가 `fib_memo(30)`에서 `0.007ms`로, 약 8000배 줄어드는 걸 실측했습니다.
* 메모이제이션은 **중복 부분 문제**가 있는 재귀에서만 효과가 있습니다 — `factorial`처럼 사슬 하나로만 내려가는 재귀에는 캐시할 만한 중복이 애초에 없습니다.

다음 장에서는 메모이제이션을 한 걸음 더 밀어붙입니다. "위에서 아래로 내려가며 필요할 때마다 캐시를 채우는" 지금 방식 대신, "아래(기저 사례)에서 시작해서 위로 차근차근 표를 채워 올라가는" **타뷸레이션**을 봅니다. 사실 이건 2장에서 배운 귀납의 방향을 그대로 뒤집은 것뿐이라는 걸 보게 됩니다.
