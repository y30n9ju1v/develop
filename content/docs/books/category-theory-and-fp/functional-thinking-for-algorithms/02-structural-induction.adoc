== 몇 개를 테스트해봤다고 항상 맞는 건 아니다

1장에서 `factorial(0)`부터 `factorial(5)`까지 결과를 확인했습니다. 전부 맞았습니다. 그런데 이게 "`factorial`이 **모든** `n`에 대해 맞는다"는 증명이 될까요? 아닙니다. `n = 1000000`에 대해서도 맞는지는 여전히 모릅니다. 유한한 개수의 테스트로는 무한히 많은 입력 전체를 확인할 수 없습니다.

이 문제를 도미노에 비유해봅시다. 도미노가 끝없이 줄지어 서 있습니다. 이걸 전부 넘어뜨리려면 두 가지만 확인하면 됩니다.

....
[ 도미노 비유 ]

  1번 도미노가 넘어진다.               (기저 사례)
        │
        ▼
  k번 도미노가 넘어지면
  k+1번 도미노도 반드시 넘어진다.       (재귀 사례 / 귀납 단계)
        │
        ▼
  ==> 1번, 2번, 3번, ... 전부 넘어진다.
....

1번이 넘어지고, "어떤 도미노든 넘어지면 바로 다음 것도 넘어진다"는 규칙만 확인되면, 두 가지 사실만으로 **무한히 많은** 도미노가 전부 넘어진다는 게 보장됩니다. 도미노를 하나하나 밀어서 확인할 필요가 없습니다. 이게 바로 **수학적 귀납법(mathematical induction)**입니다.

== 재귀적 정의는 이미 귀납법의 모양을 하고 있다

여기서 1장의 내용을 다시 보면 흥미로운 사실이 있습니다. 재귀적 정의의 두 부품 — 기저 사례와 재귀 사례 — 이 도미노의 두 조건과 **정확히 같은 모양**입니다.

....
[ 재귀적 정의 ]                        [ 귀납적 증명 ]

기저 사례: 0! = 1                       1번 도미노가 넘어진다
재귀 사례: n! = n × (n-1)!              k번이 넘어지면 k+1번도 넘어진다
....

즉 `n! = n × (n-1)!`이라는 **정의** 자체가, 이미 "`(n-1)!`이 맞다면 `n!`도 맞다"는 **증명의 재료**를 담고 있습니다. 재귀적으로 함수를 정의하는 순간, 그 함수가 왜 맞는지 증명하는 방법(구조적 귀납, structural induction)도 사실상 거저 따라옵니다. 이게 이 책이 재귀를 "정의를 정의로 푸는 방법"이라고 부르는 이유입니다 — 정의와 증명이 같은 틀 위에 있습니다.

`length` 함수로 직접 증명해봅시다.

[source,python]
----
def length(lst):
    if lst == []:
        return 0
    return 1 + length(lst[1:])
----

**증명하고 싶은 것**: 모든 리스트 `lst`에 대해, `length(lst)`는 `lst`의 실제 원소 개수와 같다.

**기저 사례**: `lst = []`일 때. `length([])`는 정의에 의해 `0`을 반환합니다. 빈 리스트의 실제 원소 개수도 `0`입니다. 일치합니다.

**귀납 단계**: 길이가 `k`인 어떤 리스트에 대해 `length`가 맞게 동작한다고 **가정**합시다(이걸 **귀납 가정**이라고 부릅니다). 이제 길이가 `k+1`인 리스트 `lst`를 봅시다. 정의에 따라 `length(lst) = 1 + length(lst[1:])`입니다. `lst[1:]`는 길이가 `k`인 리스트이므로, 귀납 가정에 의해 `length(lst[1:])`는 `lst[1:]`의 실제 원소 개수(`k`)와 같습니다. 따라서 `length(lst) = 1 + k`이고, 이는 정확히 `lst`의 실제 원소 개수(`k+1`)와 같습니다.

기저 사례와 귀납 단계가 둘 다 확인됐으므로, 도미노 논증에 의해 **모든 길이의 리스트에 대해** `length`가 맞다는 게 증명됩니다. `length([1,2,...,1000000])`을 실제로 실행해보지 않고도, 100만 개짜리 리스트에서도 맞는다는 걸 알 수 있습니다.

== 기저 사례를 틀리면 무슨 일이 벌어지는가

증명에서 기저 사례와 귀납 단계는 **둘 다** 필요합니다. 하나라도 틀리면 전체가 무너집니다. 재귀 사례는 완벽히 그럴듯해 보이는데 기저 사례 하나가 틀린 경우를 봅시다.

[source,python]
----
def product_ok(lst):
    """리스트의 모든 원소를 곱한 값"""
    if lst == []:
        return 1
    return lst[0] * product_ok(lst[1:])

def product_buggy(lst):
    if lst == []:
        return 0  # 잘못된 기저 사례 — 곱셈의 항등원은 0이 아니라 1
    return lst[0] * product_buggy(lst[1:])
----

[source]
----
lst          product_ok   product_buggy
[]           1            0
[5]          5            0
[2, 3]       6            0
[2, 3, 4]    24           0
----

재귀 사례(`lst[0] * product_buggy(lst[1:])`)는 두 함수가 완전히 똑같습니다. 곱하는 로직 자체는 흠잡을 데가 없어 보입니다. 그런데 기저 사례 하나가 `1` 대신 `0`으로 잘못 적힌 순간, **길이가 몇이든 상관없이 모든 리스트에서** 결과가 `0`이 되어버립니다. 도미노에 비유하면, 1번 도미노가 애초에 넘어져 있지 않은 상태(잘못된 방향으로 서 있는 상태)라, 그다음 도미노가 아무리 정직하게 규칙을 따라도 전부 잘못된 채로 넘어지는 것과 같습니다.

이 예시가 보여주는 교훈은 이겁니다 — **재귀 사례가 그럴듯해 보인다고 안심하면 안 됩니다.** 기저 사례가 그 함수가 다루는 연산의 항등원(덧셈이면 `0`, 곱셈이면 `1`, 리스트 이어붙이기면 빈 리스트)과 맞는지 항상 따로 확인해야 합니다.

[NOTE]
====
**"몇 번 테스트해봤는데 잘 되던데요?"라는 반박에 대해**
`product_buggy([])`, 즉 빈 리스트만 테스트해봤다면 `0`이 나오는 게 맞는지 틀린지조차 헷갈릴 수 있습니다(빈 곱은 관례적으로 `1`이어야 합니다 — 아무것도 곱하지 않은 값이니 곱셈의 항등원이 나와야 합니다). 만약 원소가 하나 이상인 리스트로만 테스트했다면, 그 어떤 테스트도 항상 `0`을 반환하니 "버그가 있다"는 신호 자체는 빠르게 알아챌 수 있습니다. 하지만 이 예시의 요점은 "테스트하면 걸린다"가 아니라, **기저 사례 하나가 전체 증명의 출발점이라서, 거기가 틀리면 재귀 사례가 아무리 옳아도 전부 틀린다**는 구조적 사실입니다. 테스트는 버그를 우연히 발견하게 해줄 뿐, 왜 항상 맞는지는 증명해주지 않습니다.
====

== 재귀 사례를 틀리는 경우

이번엔 반대로 기저 사례는 맞는데 재귀 사례가 실제 값과 어긋나는 경우도 봅시다. 리스트의 합을 구하되, 실수로 원소를 두 번씩 더하는 함수입니다.

[source,python]
----
def sum_ok(lst):
    if lst == []:
        return 0
    return lst[0] + sum_ok(lst[1:])

def sum_buggy(lst):
    if lst == []:
        return 0
    return lst[0] + lst[0] + sum_buggy(lst[1:])  # lst[0]을 두 번 더함
----

[source]
----
lst          sum_ok   sum_buggy
[]           0        0
[3]          3        6
[3, 4]       7        13
[3, 4, 5]    12       22
----

기저 사례는 둘 다 `0`으로 같아서 빈 리스트에서는 차이가 안 드러납니다. 하지만 원소가 하나라도 있는 순간부터 어긋나기 시작합니다. 귀납 단계를 다시 밟아보면 왜 그런지 바로 보입니다 — `sum_buggy(lst)`가 `lst[1:]`의 정확한 합에 의존하는 게 아니라, `lst[1:]`의 합이 **틀린 채로 누적**되기 때문에, 리스트가 길어질수록 오차가 계속 쌓입니다(`3` → `+3` 오차, `3,4` → `+3+4=+7` 오차, 이런 식으로).

== 직접 해보기

`find_max` (1장의 직접 해보기에서 만든 함수)가 정말로 모든 길이 1 이상의 리스트에 대해 최댓값을 정확히 찾는지, 구조적 귀납으로 직접 증명해보세요.

* 기저 사례는 무엇이고, 왜 맞나요?
* 귀납 가정은 무엇이라고 세워야 할까요? ("길이 `k`인 리스트에 대해 `find_max`가 ___라고 가정하자"의 빈칸을 채워보세요.)
* 귀납 단계에서, 길이 `k+1`인 리스트에 대해 `find_max`가 맞다는 걸 어떻게 보이나요?

.해답 보기
[%collapsible]
====
[source,python]
----
def find_max(lst):
    if len(lst) == 1:
        return lst[0]
    rest_max = find_max(lst[1:])
    return lst[0] if lst[0] > rest_max else rest_max
----

**기저 사례**: 길이가 `1`인 리스트 `[x]`. `find_max([x])`는 `x`를 반환하고, 원소가 하나뿐인 리스트의 최댓값은 당연히 그 원소 자신이므로 맞습니다.

**귀납 가정**: 길이가 `k`인 어떤 리스트에 대해, `find_max`가 그 리스트의 실제 최댓값을 정확히 반환한다고 가정합니다.

**귀납 단계**: 길이가 `k+1`인 리스트 `lst`를 봅시다. `find_max(lst)`는 `lst[1:]`(길이 `k`)에 대해 재귀 호출을 하고, 귀납 가정에 의해 이 호출은 `lst[1:]`의 실제 최댓값(`rest_max`)을 정확히 반환합니다. `lst`의 실제 최댓값은 `lst[0]`이거나 `lst[1:]`의 최댓값 중 더 큰 쪽인데, 함수는 정확히 `lst[0]`과 `rest_max`를 비교해서 더 큰 쪽을 반환하므로, `lst`(길이 `k+1`)에 대해서도 맞습니다.

기저 사례와 귀납 단계가 모두 확인되었으므로, 길이 1 이상인 모든 리스트에 대해 `find_max`가 맞다는 게 증명됩니다.
====

== 요약

* 몇 개의 입력으로 테스트해서 맞았다는 건, 그 함수가 **모든** 입력에 대해 맞는다는 증명이 아닙니다. 무한히 많은 경우를 유한한 테스트로 다 확인할 수는 없습니다.
* **구조적 귀납**은 기저 사례(가장 작은 경우가 맞는지)와 귀납 단계(더 작은 경우가 맞다고 가정했을 때 더 큰 경우도 맞는지)만 확인하면, 무한히 많은 모든 경우에 대해 증명이 완성되는 논증법입니다.
* 재귀적 정의는 이미 귀납적 증명과 같은 모양(기저 사례 + 재귀 사례)을 하고 있어서, 함수를 재귀적으로 정의하는 순간 그 정당성을 증명할 틀도 함께 따라옵니다.
* 기저 사례와 재귀 사례는 **둘 다** 맞아야 합니다. 재귀 사례가 아무리 그럴듯해도 기저 사례 하나가 틀리면(예: 곱셈의 항등원 자리에 `0`을 넣는 것) 모든 결과가 틀어집니다.

다음 장에서는 이 재귀적 정의를 이용해 **알고리즘이 얼마나 걸리는가**를 계산하는 법 — 재귀 관계(recurrence relation) — 을 다룹니다. 재귀 호출이 몇 번, 얼마나 작아지면서 일어나는지가 곧 실행 시간을 결정한다는 걸 보게 됩니다.
