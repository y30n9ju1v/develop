== 메모이제이션이 실제로 채우는 순서

8장의 `fib_memo(5)`가 캐시를 채워가는 순서를 따라가 봅시다. `fib_memo(5)`는 `fib_memo(4)`를 부르고, 그건 `fib_memo(3)`을, 그건 `fib_memo(2)`를... 이렇게 **`5`에서 시작해서 `1`, `0`(기저 사례)까지 내려간 다음에야** 첫 번째 실제 계산이 일어나고, 그 결과들이 다시 위로 올라오면서 캐시에 쌓입니다.

....
[ 메모이제이션의 진행 방향 ]

  호출:  fib(5) → fib(4) → fib(3) → fib(2) → fib(1), fib(0)   (위 → 아래로 내려감)
  캐시:                                        fib(1)=1, fib(0)=0
                                       fib(2)=1 ←
                              fib(3)=2 ←
                     fib(4)=3 ←
            fib(5)=5 ←                                          (아래 → 위로 값이 채워짐)
....

여기서 자연스러운 질문이 떠오릅니다 — 어차피 `fib(0)`과 `fib(1)`부터 채워야 한다면, **처음부터 `0`에서 시작해서 `5`까지 순서대로 채워 올라가면 안 될까요?** 재귀 호출로 아래까지 내려갔다가 다시 올라오는 과정 자체를 건너뛰는 겁니다. 이게 바로 **타뷸레이션(tabulation)**입니다.

[source,python]
----
def fib_tab(n):
    table = [0] * (n + 1)
    table[0] = 0
    if n >= 1:
        table[1] = 1
    for i in range(2, n + 1):
        table[i] = table[i - 1] + table[i - 2]
    return table[n]
----

[source]
----
fib_tab(0)  -> 0
fib_tab(1)  -> 1
fib_tab(5)  -> 5
fib_tab(10) -> 55
fib_tab(30) -> 832040
fib_tab(50) -> 12586269025
----

재귀 호출이 단 한 번도 없습니다. `for` 반복문 하나로 표(`table`)를 왼쪽에서 오른쪽으로 채워나갈 뿐입니다.

== 이게 왜 2장의 귀납과 같은 것인가

`fib_tab`의 코드를 2장에서 배운 구조적 귀납의 언어로 다시 읽어봅시다.

....
[ 2장: 구조적 귀납 증명 ]                    [ 9장: 타뷸레이션 코드 ]

기저 사례가 참임을 확인                     table[0], table[1]을 직접 채움
      │                                            │
      ▼                                            ▼
귀납 단계: k, k-1이 참이면                   table[i] = table[i-1] + table[i-2]
k+1도 참임을 보임                           (i가 2부터 n까지 차례로)
....

구조적 귀납으로 "`fib`가 맞다"는 걸 증명할 때, 우리는 항상 **작은 경우부터 시작해서 큰 경우로** 정당성을 물려주는 순서로 논증을 폈습니다(기저 사례 → 귀납 단계). 타뷸레이션은 바로 그 증명의 순서를 **그대로 실행 순서로 옮긴 것**입니다. 증명에서 "`k`가 참이라고 가정하면"이라고 썼던 자리가, 코드에서는 "`table[k]`에 이미 계산된 값이 들어있으니 그걸 읽어서 쓴다"로 바뀐 것뿐입니다.

반대로 메모이제이션(8장)은 재귀 호출을 따라 **큰 경우에서 작은 경우로 내려갔다가**, 기저 사례에 도달한 뒤에야 값이 위로 채워집니다 — 증명의 순서와는 반대 방향으로 실행되다가, 마지막에 결과만 증명의 순서(작은 것 → 큰 것)대로 조립되는 셈입니다.

[NOTE]
====
**둘 중 뭘 써야 하는가**
메모이제이션과 타뷸레이션은 계산하는 값도, 걸리는 시간의 차수(`O(n)`)도 같습니다. 차이는 스타일과 몇 가지 실전 디테일입니다. 메모이제이션은 원래 재귀적 정의를 거의 그대로 두고 캐시만 얹기 때문에 코드가 더 직관적으로 읽히는 경우가 많고, **필요한 부분 문제만** 계산합니다(예: `fib_memo(5)`를 부르면 `fib(6)`, `fib(7)`은 아예 계산하지 않습니다). 타뷸레이션은 재귀 호출이 없어서(따라서 파이썬의 재귀 깊이 제한에 걸릴 일도 없어서) `n`이 아주 클 때 더 안전하고, 보통 조금 더 빠릅니다. 다만 기저 사례부터 목표까지 **모든** 중간값을 순서대로 계산해야 합니다.
====

== 실전 동적 계획법: 동전 교환 문제

메모이제이션·타뷸레이션이 왜 유용한지 감을 잡기 위해, 조금 더 실전에 가까운 문제를 봅시다.

....
    문제: 동전 종류가 coins = [1, 3, 4]처럼 주어졌을 때(각 동전은 무한히 쓸 수 있다),
         목표 금액 amount를 만드는 데 필요한 최소 동전 개수는?
....

이 문제도 재귀적으로 정의할 수 있습니다. "금액 `a`를 만드는 최소 동전 수"를 `f(a)`라고 하면:

....
    f(0) = 0                                            (기저 사례: 이미 다 만들었다)
    f(a) = 1 + min( f(a - c) for c in coins if c <= a )  (재귀 사례: 동전 하나를 골라 쓴다)
....

이걸 타뷸레이션으로 짜면, `0`부터 `amount`까지 표를 채우면서 각 금액마다 "어떤 동전을 마지막으로 썼을 때 가장 적은 개수가 나오는지"를 확인합니다.

[source,python]
----
def coin_change(coins, amount):
    table = [float("inf")] * (amount + 1)
    table[0] = 0
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a:
                table[a] = min(table[a], table[a - c] + 1)
    return table[amount] if table[amount] != float("inf") else -1
----

[source]
----
coin_change([1, 3, 4], 6)         -> 2    (3 + 3)
coin_change([2], 3)               -> -1   (홀수는 짝수 동전만으론 못 만듦)
coin_change([1, 5, 10, 25], 63)   -> 6    (25 + 25 + 10 + 1 + 1 + 1)
----

`table[a]`를 채울 때 `table[a - c]`(이미 채워진, `a`보다 작은 금액)를 참조합니다. 이건 `fib_tab`의 `table[i-1]`, `table[i-2]`와 똑같은 패턴입니다 — **지금 채우려는 칸이, 이미 채워진 더 작은 칸들만 참조한다**는 것이 타뷸레이션이 성립하기 위한 조건입니다. 이 조건은 사실 재귀적 정의가 "더 작은 부분 문제로 향해야 한다"는 1장의 조건과 동일합니다.

== 직접 해보기

동전 교환 문제를 살짝 바꿔서, "amount를 만드는 최소 동전 수"가 아니라 "amount를 만드는 **방법의 가짓수**"를 구하는 `coin_ways` 함수를 타뷸레이션으로 짜보세요. (힌트: `table[0] = 1`로 시작합니다 — "아무 동전도 안 쓰는 방법 1가지"가 금액 `0`을 만드는 방법이라고 봅니다. 그리고 동전 종류별로 바깥 루프를 돌면서 안쪽에서 금액을 채우면, 같은 동전 조합이 순서만 바뀌어 중복으로 세지는 걸 막을 수 있습니다.)

.해답 보기
[%collapsible]
====
[source,python]
----
def coin_ways(coins, amount):
    table = [0] * (amount + 1)
    table[0] = 1
    for c in coins:
        for a in range(c, amount + 1):
            table[a] += table[a - c]
    return table[amount]
----

[source]
----
coin_ways([1, 2, 5], 5)   -> 4   (5 / 1+2+2 / 1+1+1+2 / 1+1+1+1+1)
coin_ways([2], 3)         -> 0   (홀수는 만들 수 없음)
coin_ways([1, 3, 4], 6)   -> 4
----

`coin_change`와 코드 모양은 비슷하지만 루프 순서가 다릅니다 — 동전 종류를 바깥 루프로 두면, "이 동전을 쓸지 말지"가 조합마다 한 번씩만 결정되어 `1+2+2`와 `2+1+2`처럼 순서만 다른 조합이 따로 세지지 않습니다. 두 함수 모두 `table[a]`가 `table[a - c]`(더 작은 금액)에만 의존한다는, 이 장에서 강조한 조건은 그대로 지키고 있습니다.
====

== 요약

* 타뷸레이션은 기저 사례부터 시작해서 목표까지 표를 순서대로 채워 올라가는 방식입니다. 재귀 호출이 없어서 파이썬의 재귀 깊이 제한에서도 자유롭습니다.
* 타뷸레이션이 하는 일은 2장의 구조적 귀납 증명을 **그대로 실행 순서로 옮긴 것**입니다 — 기저 사례를 먼저 확정하고, 그 위에서 한 칸씩 더 큰 경우로 다리를 놓는 순서가 증명과 코드에서 똑같습니다.
* 동전 교환 문제처럼 실전 동적 계획법 문제도 "기저 사례가 뭔가, 더 작은 부분 문제를 어떻게 참조하는가"라는 같은 두 질문으로 풀립니다.

다음 장에서는 지금까지 리스트와 트리에 썼던 재귀를 그래프로 확장합니다. 그래프 탐색(DFS/BFS)이 재귀로는 어떻게 짜이고, 명시적인 스택·큐로는 어떻게 짜이는지, 그리고 그 둘이 왜 같은 것의 다른 얼굴인지를 봅니다.
