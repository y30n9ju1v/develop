== 인트로: 13장까지가 파이썬 이야기였다면

이 책은 지금까지 철저히 파이썬 이야기였습니다. `await`가 Monad의 `flatMap`이라는 것, `asyncio.gather`가 Applicative Functor라는 것, `TaskGroup`이 구조적 동시성이라는 것 — 전부 파이썬 문법으로 확인했습니다. 그런데 서문이 던진 질문을 다시 떠올려보면("최신 비동기 기술들이 사실은 50년 전 함수형 프로그래밍의 철학 위에서 탄생했다"), 이 주장이 진짜라면 **파이썬이 아닌 언어에서도 같은 패턴이 보여야 합니다.**

2장이 콜백 지옥의 원조로 지목한 언어는 사실 파이썬이 아니라 JavaScript였습니다 — Node.js의 콜백 기반 API들이 콜백 지옥이라는 용어 자체를 유명하게 만들었고, `Promise`도 파이썬의 `asyncio`보다 먼저(ES2015, 2015년) 표준이 됐습니다. 이 장은 그 JavaScript(정확히는 타입까지 확인할 수 있는 TypeScript)로 지금까지 배운 패턴을 다시 확인합니다 — 새 개념을 배우는 장이 아니라, **이미 아는 개념이 언어를 갈아 끼워도 그대로 성립하는지 검증하는 장**입니다.

== `.then`은 정말 `flatMap`인가

4장에서 `flatMap`의 정의는 "컨테이너 안의 값에 `T -> Container<U>` 함수를 적용했을 때, `Container<Container<U>>`가 아니라 `Container<U>`로 자동 평탄화되는 것"이었습니다. TypeScript의 `Promise.prototype.then`이 정확히 이 규칙을 따르는지 확인해봅니다.

[source,typescript]
----
function fetchUser(id: number): Promise<{ id: number; name: string }> {
  return Promise.resolve({ id, name: `user-${id}` });
}

function fetchOrders(userId: number): Promise<string[]> {
  return Promise.resolve([`order-${userId}-1`, `order-${userId}-2`]);
}

async function main() {
  // .then에 넘긴 콜백이 Promise를 반환하면, 결과는 Promise<Promise<T>>가 아니라
  // Promise<T>로 자동 평탄화된다 -- 이게 정확히 4장의 flatMap이 하던 일이다.
  const orders = await fetchUser(1).then((user) => fetchOrders(user.id));
  console.log("orders:", orders);

  // async/await는 이 .then 체인을 그대로 문법으로 감싼 것뿐이다.
  const user = await fetchUser(2);
  const orders2 = await fetchOrders(user.id);
  console.log("orders2 (await 버전):", orders2);
}

main();
----

[source]
----
$ npx tsc --strict --target es2020 --module commonjs then_flatmap.ts && node then_flatmap.js
orders: [ 'order-1-1', 'order-1-2' ]
orders2 (await 버전): [ 'order-2-1', 'order-2-2' ]
----

`fetchUser(1).then(user => fetchOrders(user.id))`의 콜백은 `Promise<string[]>`을 반환합니다. 만약 `.then`이 `map`(4장에서 구분했던, 평탄화하지 않는 연산)이었다면 결과 타입은 `Promise<Promise<string[]>>`가 되어야 하는데, TypeScript 컴파일러가 추론한 `orders`의 타입은 그냥 `string[]`입니다 — 자동으로 한 겹 평탄화됩니다. `await` 문법은 이 `.then` 체인을 감싼 문법 설탕일 뿐이라는 것도 `orders2`가 정확히 같은 결과를 내는 것으로 확인됩니다. **파이썬에서 `await`가 `flatMap`이었던 것과 같은 이유로, TypeScript의 `.then`도 `flatMap`입니다** — 두 언어 모두 "실패할 수 있는 비동기 계산을 값으로 다루면서도, 중첩되지 않게 이어붙인다"는 같은 문제를 같은 방식으로 풀었습니다.

== `Promise.all`은 정말 Applicative인가

6장에서 `asyncio.gather`를 Applicative Functor로 읽은 근거는 "서로 의존하지 않는 작업들을 동시에 시작하고, 결과를 한 번에 모은다"는 것이었습니다. `Promise.all`도 정확히 같은 계약을 갖습니다.

[source,typescript]
----
function delay<T>(ms: number, value: T): Promise<T> {
  return new Promise((resolve) => setTimeout(() => resolve(value), ms));
}

async function main() {
  const start = Date.now();
  // 세 작업 모두 즉시 시작된다 -- 순차로 await하면 300ms, all이면 100ms.
  const [a, b, c] = await Promise.all([
    delay(100, "a"),
    delay(100, "b"),
    delay(100, "c"),
  ]);
  console.log(`Promise.all: [${a}, ${b}, ${c}] in ${Date.now() - start}ms`);

  // Python asyncio.gather(return_exceptions=True)에 대응하는 건 allSettled다.
  // all은 하나라도 실패하면 즉시 reject하고 나머지 결과는 버린다.
  const settled = await Promise.allSettled([
    delay(20, "ok"),
    Promise.reject(new Error("boom")),
  ]);
  console.log("allSettled:", settled.map((r) => r.status));
}

main();
----

[source]
----
$ npx tsc --strict --target es2020 --module commonjs applicative_all.ts && node applicative_all.js
Promise.all: [a, b, c] in 101ms
allSettled: [ 'fulfilled', 'rejected' ]
----

100ms짜리 작업 세 개가 순차 실행이었다면 300ms 근처가 나와야 하는데, 실측 101ms — 세 작업이 동시에 시작됐다는 뜻입니다. 그리고 5장에서 다룬 `asyncio.gather(return_exceptions=True)`(부분 실패를 허용하고 전부 모으는 방식)에 대응하는 게 `Promise.all`이 아니라 `Promise.allSettled`라는 것도 실측으로 갈립니다 — `Promise.all`은 "전부 성공해야 결과가 있다"는 Applicative의 원래 계약대로, 하나만 실패해도 즉시 전체가 reject됩니다.

== 구조적 동시성: TypeScript에는 `TaskGroup`이 없다

지금까지는 "파이썬에 있는 게 TypeScript에도 있다"는 이야기였습니다. 이번엔 반대입니다 — 6장에서 다룬 Python 3.11 `TaskGroup`(자식 태스크 하나가 실패하면 나머지를 **자동으로 취소**하는 구조적 동시성)에 대응하는 게 TypeScript/JavaScript에는 없습니다. 실측으로 그 차이를 봅니다.

[source,typescript]
----
function delay(ms: number, label: string): Promise<string> {
  return new Promise((resolve) => {
    setTimeout(() => {
      console.log(`  [백그라운드] ${label} 완료 (취소되지 않음!)`);
      resolve(label);
    }, ms);
  });
}

async function main() {
  console.log("Promise.all 시작");
  try {
    await Promise.all([
      delay(50, "slow-task"),
      Promise.reject(new Error("fast failure")),
    ]);
  } catch (e) {
    console.log(`await 즉시 반환: ${(e as Error).message}`);
  }
  console.log("main() 종료 -- 그런데 slow-task는 아직 안 끝났다");
  await delay(80, "wait-to-observe");
}

main();
----

[source]
----
$ npx tsc --strict --target es2020 --module commonjs structured_gap.ts && node structured_gap.js
Promise.all 시작
await 즉시 반환: fast failure
main() 종료 -- 그런데 slow-task는 아직 안 끝났다
  [백그라운드] slow-task 완료 (취소되지 않음!)
  [백그라운드] wait-to-observe 완료 (취소되지 않음!)
----

`fast failure`가 즉시 `Promise.all`을 reject시키고 `main()`의 `catch`가 실행되지만, `slow-task`는 취소되지 않고 백그라운드에서 계속 돌다가 `main()`이 이미 "종료"라고 찍은 뒤에 완료됩니다 — 리소스 누수, 좀비 태스크, 예상치 못한 부수 효과의 전형적인 원인입니다. 같은 상황을 파이썬 `TaskGroup`으로 다시 만들어보면 대조가 분명해집니다.

[source,python]
----
import asyncio

async def slow_task():
    try:
        await asyncio.sleep(0.05)
        print("  [백그라운드] slow-task 완료")
    except asyncio.CancelledError:
        print("  [백그라운드] slow-task 취소됨 (TaskGroup이 자동으로 취소)")
        raise

async def fast_failure():
    await asyncio.sleep(0)
    raise ValueError("fast failure")

async def main():
    print("TaskGroup 시작")
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(slow_task())
            tg.create_task(fast_failure())
    except* ValueError as eg:
        print(f"ExceptionGroup 수신: {[str(e) for e in eg.exceptions]}")
    print("main() 종료")

asyncio.run(main())
----

[source]
----
$ python3 taskgroup_check.py
TaskGroup 시작
  [백그라운드] slow-task 취소됨 (TaskGroup이 자동으로 취소)
ExceptionGroup 수신: ['fast failure']
main() 종료
----

`fast_failure`가 예외를 던지자마자 `TaskGroup`이 `slow_task`에 `CancelledError`를 주입해 실제로 멈춥니다 — TypeScript 버전과 정반대로, "main() 종료"가 찍히기 *전에* 모든 자식 태스크의 운명이 결정됩니다. TypeScript/JavaScript 생태계가 이 간극을 완전히 놓친 건 아닙니다 — `AbortController`와 `AbortSignal`을 수동으로 배선하면 비슷한 효과를 낼 수 있지만, 이건 언어/런타임이 보장해주는 게 아니라 **개발자가 매번 직접 조립해야 하는 패턴**입니다. 6장이 `TaskGroup`을 "함수형의 Resource Scoping이 언어 기능으로 승격된 것"이라고 부른 이유가 여기서 다시 확인됩니다 — 모든 언어가 이 승격을 이룬 게 아닙니다.

== 정리: 패턴은 언어를 넘어서지만, 보장 수준은 아니다

이 장이 실제로 컴파일하고 실행해 확인한 것은 세 가지입니다.

* **`.then`은 `flatMap`이다** — `Promise<Promise<T>>`가 아니라 `Promise<T>`로 자동 평탄화되는 것을 타입 추론과 실행 결과로 확인했습니다. `async/await`는 이 위에 얹힌 문법일 뿐입니다.
* **`Promise.all`은 Applicative다** — 서로 독립적인 작업을 동시에 시작하고, 전부 성공해야 결과가 있다는 계약을 실측 타이밍(101ms vs 300ms)으로 확인했고, "부분 실패 허용"에 대응하는 건 `Promise.all`이 아니라 `Promise.allSettled`라는 것도 갈렸습니다.
* **구조적 동시성은 언어 계약이지, 패턴 자체의 필연적 귀결이 아니다** — Python은 `TaskGroup`으로 이걸 언어가 보장하지만, TypeScript/JavaScript는 같은 문제를 겪으면서도(좀비 태스크가 실제로 관찰됩니다) 아직 언어 차원의 해법이 없습니다.

이 책의 핵심 주장 — "우리가 매일 쓰는 비동기 도구들은 사실 함수형 프로그래밍의 오래된 개념 위에 서 있다" — 은 파이썬만의 이야기가 아니었습니다. 다만 이 장이 동시에 보여준 건, **같은 패턴이 언어마다 다른 "보장 수준"으로 구현된다**는 것입니다. Functor/Monad/Applicative라는 대수적 구조는 언어를 넘어 보편적이지만, 그 구조가 얼마나 안전하게 언어 차원에서 강제되는지는 각 언어와 런타임의 설계 선택에 달려 있습니다. 13장까지 배운 게 "무엇이 필연적인가"였다면, 이 장이 보여준 건 "무엇이 아직 선택의 영역으로 남아 있는가"입니다.
