'''
프로그래머들은 모나드를 둘러싼 온갖 신화를 만들어냈습니다. 프로그래밍에서 가장 추상적이고 어려운 개념 중 하나라고들 하죠. 모나드를 "이해한" 사람과 "그렇지 못한" 사람으로 나뉜다고 합니다. 많은 이에게 모나드를 깨닫는 순간은 마치 신비한 체험에 가깝습니다. 모나드는 너무나 다양한 구조의 본질을 추상화하기 때문에, 일상에서 적절한 비유를 찾기란 거의 불가능합니다. 우리는 어둠 속에서 손으로 더듬거리는 장님들처럼, 코끼리의 각 부분을 만져보고는 "이건 밧줄이야!", "이건 나무줄기야!", 또는 "이건 부리토야!"라고 의기양양하게 외칠 수밖에 없습니다.

분명히 말씀드리자면, 모나드를 둘러싼 이 모든 신비주의는 오해에서 비롯된 것입니다. 모나드 자체는 대단히 간단한 개념입니다. 혼란의 원인은 모나드가 워낙 다양한 영역에 응용된다는 데 있습니다.

이 글을 쓰기 위해 자료를 찾다가 덕트 테이프(일명 덕 테이프)의 활용 사례를 보게 되었습니다. 덕트 테이프로 할 수 있는 일들을 몇 가지 꼽아보자면 다음과 같습니다.

- 배관(duct) 밀봉
- 아폴로 13호의 이산화탄소 여과기(scrubber) 수리
- 사마귀 치료
- 아이폰 4의 수신 결함 문제 해결
- 무도회용 드레스 제작
- 현수교 건설

이제 덕트 테이프가 뭔지 모르는 사람이 이 목록만 보고 그 정체를 알아내려 한다고 상상해 보세요. 행운을 빕니다!

그래서 저도 "모나드는 ~와 같다"라는 진부한 비유 컬렉션에 하나를 더 보태고자 합니다. 바로 "모나드는 덕트 테이프와 같다"는 것입니다. 응용 분야는 놀라울 만큼 다양하지만, 원리는 무척 단순합니다. 무언가를 서로 붙여주는 것이죠. 좀 더 정확히 말하면, 무언가를 *합성(compose)*합니다.

명령형 언어 배경을 가진 많은 프로그래머가 모나드를 이해하는 데 어려움을 겪는 이유도 여기서 어느 정도 설명됩니다. 우리는 프로그래밍을 함수 합성의 관점에서 사고하는 데 익숙하지 않습니다. 충분히 이해할 만합니다. 우리는 종종 중간 값을 다음 함수로 직접 넘기기보다는 명시적으로 이름을 붙여 저장합니다. 또한 짧은 연결 코드를 헬퍼 함수로 추상화하기보다 인라인으로 넣어버리곤 하죠. 다음은 C로 작성된 벡터 길이 계산 함수입니다.

[source,c]
----
double vlen(double * v) {
  double d = 0.0;
  int n;
  for (n = 0; n < 3; ++n)
    d += v[n] * v[n];
  return sqrt(d);
}
----

함수 합성을 명시적으로 드러낸 하스켈 버전과 비교해 보세요.

[source,haskell]
----
vlen = sqrt . sum . fmap (flip (^) 2)
----

(좀 더 암호같아 보이도록, 거듭제곱 연산자 ``(^)``의 두 번째 인자를 2로 고정해 부분 적용했습니다.)

하스켈의 포인트 프리 스타일이 항상 더 낫다고 주장하는 것은 아닙니다. 다만 우리가 프로그래밍에서 하는 모든 일의 밑바닥에는 함수 합성이 자리 잡고 있다는 점을 강조하고 싶습니다. 우리가 실제로는 함수를 합성하고 있음에도, 하스켈은 모나드 합성을 위해 명령형 스타일의 구문인 ``do`` 표기법을 제공하려고 많은 노력을 기울입니다. ``do`` 표기법의 사용법은 나중에 보기로 하고, 먼저 애초에 왜 모나드 합성이 필요한지부터 설명하겠습니다.

== 클라이슬리 카테고리

이전에 우리는 일반 함수에 '장식(embellishment)'을 더해 라이터(Writer) 모나드를 만들어 냈습니다. 그 장식은 반환 값을 문자열, 더 일반적으로는 모노이드의 원소와 쌍으로 묶는 것이었습니다. 이제 이런 장식이 곧 함자(functor)임을 알 수 있습니다.

[source,haskell]
----
newtype Writer w a = Writer (a, w)

instance Functor (Writer w) where
  fmap f (Writer (a, w)) = Writer (f a, w)
----

그다음 우리는 이렇게 장식된 함수들, 즉 *클라이슬리 화살표(Kleisli arrow)*를 합성하는 방법을 찾아냈습니다. 클라이슬리 화살표는 다음 형태의 함수입니다.

[source,haskell]
----
a -> Writer w b
----

로그 누적은 바로 이 합성 내부에서 구현되었습니다.

이제 클라이슬리 카테고리의 보다 일반적인 정의를 내릴 준비가 되었습니다. 카테고리 stem:[C]와 자기함자(endofunctor) stem:[m]이 있다고 합시다. 이에 대응하는 클라이슬리 카테고리 stem:[K]는 stem:[C]와 동일한 객체들을 갖지만, 모피즘이 다릅니다. stem:[K]에서 두 객체 stem:[a]와 stem:[b] 사이의 모피즘은 원래 카테고리 stem:[C]에서 다음과 같은 모피즘으로 구현됩니다.

[source,haskell]
----
a -> m b
----

여기서 중요한 점은, stem:[K]의 클라이슬리 화살표를 stem:[a]에서 stem:[m b]로 가는 모피즘이 아니라, *stem:[a]에서 stem:[b]로 가는 모피즘*으로 취급한다는 것입니다.

우리의 예시에서 stem:[m]은 어떤 고정된 모노이드 stem:[w]에 대한 ``Writer w``로 특수화되었습니다.

클라이슬리 화살표들이 적절한 합성을 정의할 수 있을 때에만 카테고리를 형성합니다. 만약 결합 법칙을 만족하고 모든 객체마다 항등 화살표가 존재하는 합성이 가능하다면, 함자 stem:[m]을 *모나드(monad)*라 부르고, 이렇게 만들어지는 카테고리를 클라이슬리 카테고리라 부릅니다.

하스켈에서 클라이슬리 합성은 물고기 연산자(fish operator) ``>=>``로 정의되며, 항등 화살표는 ``return``이라는 다형 함수입니다. 클라이슬리 합성으로 모나드를 정의하면 다음과 같습니다.

[source,haskell]
----
class Monad m where
  (>=>) :: (a -> m b) -> (b -> m c) -> (a -> m c)
  return :: a -> m a
----

모나드를 정의하는 방법에는 여러 동치인 방법이 있으며, 위 정의가 하스켈 생태계에서 주로 쓰이는 방식은 아님을 명심하세요. 저는 이 방식이 개념적으로 간결하고 직관적이라 좋아하지만, 프로그래밍할 때는 더 편리한 다른 정의들이 있습니다. 이제 곧 그 이야기를 하겠습니다.

이 형식에서는 모나드 법칙을 매우 쉽게 표현할 수 있습니다. 하스켈에서 이 법칙들을 강제할 수는 없지만, 등식 추론(equational reasoning)에 사용할 수 있습니다. 이 법칙들은 단순히 클라이슬리 카테고리의 표준 합성 법칙일 뿐입니다.

[source,haskell]
----
(f >=> g) >=> h = f >=> (g >=> h) -- 결합 법칙
return >=> f = f                  -- 왼쪽 단위 법칙 (left unit)
f >=> return = f                  -- 오른쪽 단위 법칙 (right unit)
----

이런 정의는 모나드가 진정 무엇인지를 명확히 드러냅니다. 즉 모나드는 *장식된 함수들을 합성하는 방법*입니다. 부작용이나 상태에 관한 것이 아닙니다. 합성에 관한 것입니다. 나중에 보겠지만, 장식된 함수를 통해 다양한 효과나 상태를 표현할 수는 있습니다. 하지만 그것이 모나드의 목적은 아닙니다. 모나드는 한 장식된 함수의 끝을 다른 장식된 함수의 시작에 이어주는 끈끈한 덕트 테이프입니다.

다시 ``Writer`` 예시로 돌아가 봅시다. 로깅 함수들(``Writer`` 함자에 대한 클라이슬리 화살표들)이 카테고리를 형성하는 이유는 ``Writer``가 모나드이기 때문입니다.

[source,haskell]
----
instance Monoid w => Monad (Writer w) where
    f >=> g = \a -> 
        let Writer (b, s)  = f a
            Writer (c, s') = g b
        in Writer (c, s `mappend` s')
    return a = Writer (a, mempty)
----

``Writer w``의 모나드 법칙은 ``w``가 모노이드 법칙을 만족하는 한 성립합니다. (물론 하스켈은 모노이드 법칙도 강제할 수 없습니다.)

``Writer`` 모나드를 위해 정의된 유용한 클라이슬리 화살표로 ``tell``이 있습니다. 이 함수의 유일한 목적은 인수를 로그에 추가하는 것입니다.

[source,haskell]
----
tell :: w -> Writer w ()
tell s = Writer ((), s)
----

나중에 이것을 다른 모나드 함수를 만드는 빌딩 블록으로 사용할 것입니다.

== 물고기 연산자의 해부

서로 다른 모나드에 대해 물고기 연산자를 구현하다 보면, 많은 코드가 반복되며 쉽게 분리해 낼 수 있다는 사실을 금세 알아차리게 됩니다. 우선 두 함수의 클라이슬리 합성은 그 자체로 함수를 반환해야 하므로, 타입 ``a``의 인자를 받는 람다로 구현을 시작할 수 있습니다.

[source,haskell]
----
(>=>) :: (a -> m b) -> (b -> m c) -> (a -> m c)
f >=> g = \a -> ...
----

이 인자를 가지고 할 수 있는 일이라곤 ``f``에 넘기는 것뿐입니다.

[source,haskell]
----
f >=> g = \a -> let mb = f a
                in ...
----

이 시점에서 우리는 ``m c`` 타입의 결과를 만들어야 하는데, 손에 있는 것은 ``m b`` 타입의 값과 ``g \:: b -> m c`` 함수입니다. 이 일을 대신해 줄 함수를 정의합시다. 이 함수를 *바인드(bind)*라 부르며, 보통 중위 연산자 형태로 씁니다.

[source,haskell]
----
(>>=) :: m a -> (a -> m b) -> m b
----

모든 모나드마다 물고기 연산자를 정의하는 대신, 바인드만 정의해도 됩니다. 실제로 하스켈의 표준 모나드 정의는 바인드를 사용합니다.

[source,haskell]
----
class Monad m where
    (>>=) :: m a -> (a -> m b) -> m b
    return :: a -> m a
----

다음은 ``Writer`` 모나드의 바인드 정의입니다.

[source,haskell]
----
(Writer (a, w)) >>= f = let Writer (b, w') = f a
                        in  Writer (b, w `mappend` w')
----

물고기 연산자 정의보다 확실히 짧습니다.

``m``이 함자라는 사실을 활용하면 바인드를 더 분해할 수 있습니다. ``fmap``으로 ``a -> m b`` 함수를 ``m a``의 내용물에 적용할 수 있습니다. 그러면 ``a``가 ``m b``로 바뀝니다. 따라서 적용 결과의 타입은 ``m (m b)``입니다. 우리가 원하는 ``m b`` 타입과는 정확히 같지 않지만 거의 다 왔습니다. 이제 이중으로 적용된 ``m``을 평탄화(flatten)하거나 합쳐주는(collapse) 함수만 있으면 됩니다. 이 함수를 *조인(join)*이라 부릅니다.

[source,haskell]
----
join :: m (m a) -> m a
----

``join``을 사용하면 바인드를 이렇게 다시 쓸 수 있습니다.

[source,haskell]
----
ma >>= f = join (fmap f ma)
----

이것이 모나드를 정의하는 세 번째 방법입니다.

[source,haskell]
----
class Functor m => Monad m where
    join :: m (m a) -> m a
    return :: a -> m a
----

여기서는 ``m``이 ``Functor``여야 함을 명시적으로 요구했습니다. 앞의 두 모나드 정의에서는 그럴 필요가 없었습니다. 물고기나 바인드 연산자를 지원하는 모든 타입 생성자 ``m``은 자동으로 함자이기 때문입니다. 예를 들어 ``fmap``을 바인드와 ``return``만으로 정의할 수 있습니다.

[source,haskell]
----
fmap f ma = ma >>= \a -> return (f a)
----

완결성을 위해, ``Writer`` 모나드의 ``join``은 다음과 같습니다.

[source,haskell]
----
join :: Monoid w => Writer w (Writer w a) -> Writer w a
join (Writer ((Writer (a, w')), w)) = Writer (a, w `mappend` w')
----

== ``do`` 표기법

모나드를 사용한 코드를 작성하는 한 가지 방법은 클라이슬리 화살표로 작업하며 물고기 연산자로 합성하는 것입니다. 이런 프로그래밍 방식은 포인트 프리 스타일의 일반화입니다. 포인트 프리 코드는 간결하고 종종 꽤 우아합니다. 하지만 일반적으로 이해하기 어려울 수 있고, 암호 같다는 느낌을 줄 수도 있습니다. 그래서 대부분의 프로그래머는 함수 인자와 중간 값에 이름을 붙이는 것을 선호합니다.

모나드를 다룰 때 이는 물고기보다 바인드 연산자를 선호함을 의미합니다. 바인드는 모나드 값을 받아 모나드 값을 반환합니다. 프로그래머는 이 값들에 이름을 붙일 수 있습니다. 하지만 이것만으로는 그다지 개선이 아닙니다. 우리가 진짜 원하는 것은 그 값들을 감싸는 모나드 컨테이너가 아니라 일반 값을 다루는 것처럼 가장하는 것입니다. 그것이 명령형 코드가 작동하는 방식입니다—전역 로그를 업데이트하는 것과 같은 부작용은 대부분 시야에서 숨겨져 있습니다. 하스켈의 ``do`` 표기법이 바로 이것을 흉내 냅니다.

그렇다면 애초에 왜 모나드를 쓰는지 궁금할 수 있습니다. 부작용을 보이지 않게 만들고 싶다면 명령형 언어를 그냥 쓰면 안 되는 걸까요? 답은 모나드가 부작용을 훨씬 더 잘 제어할 수 있게 해준다는 것입니다. 예를 들어 ``Writer`` 모나드의 로그는 함수에서 함수로 전달될 뿐 절대 전역적으로 노출되지 않습니다. 로그를 뒤섞거나 데이터 경합을 만들 가능성이 없습니다. 또한 모나드 코드는 프로그램의 나머지 부분과 명확히 구별되고 격리됩니다.

``do`` 표기법은 모나드 합성을 위한 구문 설탕일 뿐입니다. 표면적으로는 명령형 코드와 매우 비슷해 보이지만, 일련의 바인드와 람다 표현식으로 직접 번역됩니다.

예를 들어, 이전에 ``Writer`` 모나드에서 클라이슬리 화살표 합성을 설명하는 데 사용했던 예시를 가져와 봅시다. 현재의 정의를 사용하면 이렇게 다시 쓸 수 있습니다.

[source,haskell]
----
process :: String -> Writer String [String]
process = upCase >=> toWords
----

이 함수는 입력 문자열의 모든 문자를 대문자로 바꾸고 단어들로 분리하며, 동시에 수행한 작업의 로그를 만듭니다.

``do`` 표기법으로는 이렇게 보입니다.

[source,haskell]
----
process s = do
    upStr <- upCase s
    toWords upStr
----

여기서 ``upStr``은 ``String``입니다. ``upCase``가 ``Writer``를 만드는데도 말이죠.

[source,haskell]
----
upCase :: String -> Writer String String
upCase s = Writer (map toUpper s, "upCase ")
----

이것이 가능한 이유는 컴파일러가 ``do`` 블록을 다음과 같이 탈당화(desugaring)하기 때문입니다.

[source,haskell]
----
process s = 
   upCase s >>= \ upStr ->
       toWords upStr
----

``upCase``의 모나드 결과는 ``String``을 받는 람다에 바인드됩니다. ``do`` 블록에 나타나는 것이 바로 이 문자열의 이름입니다. 이 줄을 읽을 때,

[source,haskell]
----
upStr <- upCase s
----

우리는 ``upStr``이 ``upCase s``의 결과를 받는다고 말합니다.

가짜 명령형 스타일은 ``toWords``를 인라인으로 펼칠 때 더욱 두드러집니다. 문자열 ``"toWords "``를 로그에 남기는 ``tell`` 호출로 대체하고, 그 뒤에 문자열 ``upStr``을 ``words``로 쪼갠 결과를 ``return``합니다. 여기서 ``words``는 문자열에 작동하는 일반 함수입니다.

[source,haskell]
----
process s = do
    upStr <- upCase s
    tell "toWords "
    return (words upStr)
----

여기서 ``do`` 블록의 각 줄은 탈당화된 코드에서 새로운 중첩 바인드를 도입합니다.

[source,haskell]
----
process s =
    upCase s >>= \upStr ->
      tell "toWords " >>= \() ->
        return (words upStr)
----

``tell``은 유닛 값을 생성하므로 다음 람다로 전달할 필요가 없습니다. 모나드 결과의 내용은 무시하되 그 효과(여기서는 로그 기여분)는 챙기는 경우가 꽤 흔하기 때문에, 그런 경우에 바인드를 대체하는 특별한 연산자가 있습니다.

[source,haskell]
----
(>>) :: m a -> m b -> m b
m >> k = m >>= (\_ -> k)
----

실제로 우리 코드가 탈당화되면 이렇게 됩니다.

[source,haskell]
----
process s =
    upCase s >>= \upStr ->
      tell "toWords " >>
        return (words upStr)
----

일반적으로 ``do`` 블록은 왼쪽 화살표를 사용해 새 이름을 도입하는 줄들(이 이름은 나머지 코드에서 사용 가능)이나 순전히 부작용을 위해 실행되는 줄들로 구성됩니다. 코드의 줄들 사이에 바인드 연산자가 암묵적으로 들어갑니다. 참고로 하스켈에서는 ``do`` 블록의 형식을 중괄호와 세미콜론으로 대체할 수 있습니다. 모나드를 세미콜론을 오버로딩하는 방법이라고 설명하는 근거가 여기 있습니다.

``do`` 표기법을 탈당화할 때 람다와 바인드 연산자가 중첩된다는 점에 주목하세요. 이는 각 줄의 결과에 따라 ``do`` 블록의 나머지 실행에 영향을 미치는 효과를 갖습니다. 이 속성을 사용해 복잡한 제어 구조를 도입할 수 있습니다. 예를 들어 예외를 시뮬레이션하는 데 쓸 수 있습니다.

흥미롭게도, ``do`` 표기법의 등가물이 명령형 언어, 특히 C++에서 활용되고 있습니다. 바로 재개 가능 함수(resumable function) 또는 코루틴(coroutine)입니다. C++ 퓨처(future)가 모나드를 형성한다는 것은 비밀이 아닙니다. 이는 곧 다룰 계속 모나드(continuation monad)의 예입니다. 계속의 문제는 합성하기가 매우 어렵다는 것입니다. 하스켈에서는 ``do`` 표기법을 사용해 "내 핸들러가 네 핸들러를 호출할 거야" 식의 스파게티를 순차적 코드처럼 보이는 형태로 바꿉니다. 재개 가능 함수는 C++에서 같은 변환을 가능하게 합니다. 그리고 같은 메커니즘을 중첩 루프의 스파게티를 리스트 컴프리헨션이나 "제너레이터"로 바꾸는 데 적용할 수 있습니다. 이들은 본질적으로 리스트 모나드에 대한 ``do`` 표기법입니다. 모나드라는 통일된 추상화 없이는, 이런 문제들을 보통 언어에 맞춤 확장을 제공하는 식으로 각각 해결합니다. 하스켈에서는 이 모든 것이 라이브러리를 통해 처리됩니다.
