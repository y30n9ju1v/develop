'''
다양한 예시를 연구해야 카테고리에 대한 진정한 감각을 기를 수 있습니다. 카테고리는 형태와 크기가 천차만별이며, 전혀 예상치 못한 곳에서 불쑥 나타나곤 합니다. 가장 단순한 것부터 시작해 봅시다.

== 대상이 없는 카테고리 (No Objects)

가장 자명한(trivial) 카테고리는 대상도 없고, 따라서 모피즘도 없는 카테고리입니다. 그 자체로는 매우 허전한 카테고리지만, 다른 카테고리들과의 맥락—예를 들어 '모든 카테고리의 카테고리'(네, 그런 것도 있습니다)—에서는 중요한 역할을 할 수 있습니다. 공집합이 의미 있다면, 빈 카테고리 역시 존재할 수 있지 않을까요?

== 단순 그래프 (Simple Graphs)

대상들을 화살표로 연결하는 것만으로도 카테고리를 만들 수 있습니다. 임의의 방향 그래프(directed graph)에서 출발해 화살표를 추가해가며 카테고리로 만드는 과정을 상상해 봅시다. 먼저 각 노드에 항등 모피즘(identity arrow)을 추가합니다. 그런 다음, 한 화살표의 끝과 다른 화살표의 시작이 일치하는 모든 경우(즉, 합성 가능한 두 화살표)에 대해 그들의 합성을 나타내는 새로운 화살표를 추가합니다. 새 화살표를 추가할 때마다 (항등 모피즘을 제외한) 다른 화살표 및 자기 자신과의 합성도 고려해야 합니다. 이 과정을 반복하면 보통 무한히 많은 화살표가 생겨나지만, 그래도 괜찮습니다.

이 과정을 다른 관점에서 보면, 그래프의 모든 노드를 대상으로 하고, 합성 가능한 그래프 에지들의 모든 체인(chain)을 모피즘으로 갖는 카테고리를 만드는 것입니다. 여기서 항등 모피즘은 길이가 0인 체인의 특수한 경우로 간주할 수 있습니다.

이렇게 만들어진 카테고리를 주어진 그래프로부터 생성된 *자유 카테고리(free category)*라고 부릅니다. 이는 '자유 구성(free construction)'의 한 예로, 주어진 구조에 최소한의 항목을 추가해 해당 구조의 법칙(여기서는 카테고리의 법칙)을 만족하도록 완성하는 과정입니다. 앞으로 자유 구성의 더 많은 예를 만나게 될 것입니다.

== 순서 (Orders)

이제 완전히 다른 예를 살펴봅시다! 모피즘이 대상들 간의 관계인 카테고리입니다. 바로 '작거나 같다(≤)'는 관계 말이죠. 이것이 과연 카테고리인지 확인해 봅시다. 항등 모피즘이 있을까요? 모든 대상은 자기 자신보다 작거나 같습니다. 확인! 합성이 가능할까요? 만약 a ≤ b이고 b ≤ c이면, a ≤ c입니다. 확인! 합성이 결합법칙을 만족할까요? 확인! 이런 관계를 가진 집합을 *원순서(preorder)*라고 부르므로, 원순서는 실제로 카테고리입니다.

여기에 "a ≤ b이고 b ≤ a이면 a는 b와 같아야 한다"는 조건을 추가하면 *부분 순서(partial order)*가 됩니다.

마지막으로, "임의의 두 대상은 어떤 식으로든 반드시 서로 관계를 맺고 있다"는 조건을 추가하면 *선형 순서(linear order)* 또는 *전순서(total order)*가 됩니다.

이러한 순서 집합들을 카테고리의 관점에서 특징지어 봅시다. 원순서는 임의의 대상 a에서 b로 가는 모피즘이 기껏해야 하나만 존재하는 카테고리입니다. 이런 카테고리를 *얇은(thin)* 카테고리라고 부릅니다. 즉, 원순서는 얇은 카테고리입니다.

카테고리 C에서 대상 a에서 b로 가는 모피즘들의 집합을 *홈-집합(hom-set)*이라 하고 C(a, b) (또는 Hom_C(a, b))라고 씁니다. 원순서에서는 모든 홈-집합이 비어 있거나 단일 원소(singleton)만을 갖습니다. 여기에는 a에서 a로 가는 모피즘들의 집합 C(a, a)도 포함되는데, 어떤 원순서에서든 이는 항등 모피즘만을 포함하는 단원소 집합이어야 합니다. 그러나 원순서에는 사이클(cycle)이 존재할 수 있습니다. 반면 부분 순서에서는 사이클이 금지됩니다.

원순서, 부분 순서, 전순서를 구분할 수 있어야 하는 이유는 정렬(sorting) 때문입니다. 퀵소트, 버블 정렬, 병합 정렬 등의 정렬 알고리즘은 전순서에 대해서만 올바르게 작동합니다. 부분 순서는 위상 정렬(topological sort)을 사용해 정렬할 수 있습니다.

== 집합으로서의 모노이드 (Monoid as Set)

모노이드(Monoid)는 당혹스러울 정도로 단순하면서도 놀라울 만큼 강력한 개념입니다. 기초 산술의 근간을 이루는 개념이기도 합니다. 덧셈과 곱셈 모두 모노이드를 형성합니다. 모노이드는 프로그래밍 도처에 존재합니다. 문자열, 리스트, 접을 수 있는(foldable) 데이터 구조, 동시성 프로그래밍의 퓨처(future), 함수형 반응형 프로그래밍의 이벤트 등 모두가 모노이드로 나타납니다.

전통적으로 모노이드는 이항 연산을 가진 집합으로 정의됩니다. 이 연산이 만족해야 할 조건은 결합법칙뿐이고, 그 연산에 대해 단위원(unit)처럼 행동하는 특별한 원소가 하나 있어야 합니다.

예를 들어, 0을 포함한 자연수는 덧셈에 대해 모노이드를 이룹니다. 결합법칙이란 다음을 의미합니다:

[source]
----
(a + b) + c = a + (b + c)
----

(다시 말해, 숫자를 더할 때 괄호를 생략할 수 있습니다.)

중립 원소는 0입니다. 왜냐하면:

[source]
----
0 + a = a
----

그리고

[source]
----
a + 0 = a
----

덧셈은 교환법칙(a + b = b + a)이 성립하므로 두 번째 식은 중복처럼 보이지만, 교환법칙은 모노이드의 정의에 포함되지 않습니다. 예를 들어 문자열 연결은 교환법칙을 만족하지 않지만 여전히 모노이드를 형성합니다. 참고로 문자열 연결의 중립 원소는 빈 문자열로, 문자열의 어느 쪽에 붙이든 원래 문자열을 바꾸지 않습니다.

하스켈에서는 모노이드를 위한 타입 클래스(type class)를 정의할 수 있습니다. 중립 원소 ``mempty``와 이항 연산 ``mappend``를 가진 타입입니다:

[source,haskell]
----
class Monoid m where
    mempty  :: m
    mappend :: m -> m -> m
----

두 인자를 받는 함수의 타입 시그니처 ``m -> m -> m``이 처음에는 낯설 수 있지만, 커링(currying)을 다룬 후에는 완전히 자연스럽게 느껴질 것입니다. 여러 개의 화살표가 있는 시그니처는 기본적으로 두 가지 방식으로 해석할 수 있습니다. 첫째, 여러 인자를 받아 가장 오른쪽 타입을 반환하는 함수로 볼 수 있고, 둘째, 하나의 인자(가장 왼쪽)를 받아 함수를 반환하는 함수로 볼 수 있습니다. 후자를 강조하려면 괄호를 추가해 ``m -> (m -> m)``로 쓸 수 있습니다(중복이긴 하지만, 화살표가 오른쪽 결합이므로). 이 해석에 대해서는 곧 다시 이야기하겠습니다.

하스켈에서는 ``mempty``와 ``mappend``의 모노이드 속성(``mempty``가 중립 원소이고 ``mappend``가 결합법칙을 만족한다는 사실)을 표현할 방법이 없다는 점에 주목하세요. 이를 보장하는 것은 프로그래머의 책임입니다.

하스켈 클래스는 C++ 클래스만큼 침습적이지 않습니다. 새로운 타입을 정의할 때 처음부터 클래스를 명시할 필요가 없습니다. 나중에 미루다가 훨씬 나중에 해당 타입을 어떤 클래스의 인스턴스로 선언해도 됩니다. 예를 들어, ``String``을 모노이드로 선언하면서 ``mempty``와 ``mappend``의 구현을 제공해 봅시다(사실 표준 Prelude에 이미 정의되어 있습니다):

[source,haskell]
----
instance Monoid String where
    mempty = ""
    mappend = (++)
----

여기서는 ``String``이 단지 문자의 리스트이므로 리스트 연결 연산자 ``(++)``를 재사용했습니다.

하스켈 문법에 대한 한마디: 모든 중위 연산자는 괄호로 감싸서 두 인자 함수로 만들 수 있습니다. 두 문자열이 주어졌을 때, 그 사이에 ``++``를 넣어서 연결할 수 있습니다:

[source,haskell]
----
"Hello " ++ "world!"
----

또는 괄호로 감싼 ``(++)``에 두 인자를 전달할 수도 있습니다:

[source,haskell]
----
(++) "Hello " "world!"
----

함수 인자는 쉼표로 구분하지 않고 괄호로 감싸지도 않는다는 점에 유의하세요. (하스켈을 배울 때 익숙해지기 가장 어려운 부분일 것입니다.)

하스켈이 다음과 같이 함수의 동등성을 표현하도록 허용한다는 점은 강조할 가치가 있습니다:

[source,haskell]
----
mappend = (++)
----

개념적으로 이것은 함수가 생성한 값들의 동등성을 표현하는 것과는 다릅니다:

[source,haskell]
----
mappend s1 s2 = (++) s1 s2
----

전자는 카테고리 Hask(또는 끝나지 않는 계산인 bottom을 무시하면 Set)에서 모피즘 간의 동등성으로 변환됩니다. 이런 식은 더 간결할 뿐 아니라 종종 다른 카테고리로 일반화할 수 있습니다. 후자는 *확장적 동등성(extensional equality)*이라 하며, 임의의 두 입력 문자열에 대해 ``mappend``와 ``(++)``의 출력이 동일하다는 사실을 명시합니다. 인자의 값을 때때로 포인트(point)라고 부르므로(예: x 포인트에서의 f의 값), 이를 *포인트별(point-wise) 동등성*이라고 합니다. 인자를 명시하지 않는 함수 동등성은 *포인트 프리(point-free)*로 표현됩니다. (우연히도 포인트 프리 식에는 종종 함수 합성이 포함되는데, 함수 합성은 점으로 표시되므로 초보자에게는 다소 혼란스러울 수 있습니다.)

C++에서 모노이드를 선언하는 방식은 (제안된) 컨셉 문법을 사용하는 것이 가장 근접합니다.

[source,cpp]
----
template<class T>
  T mempty = delete;

template<class T>
  T mappend(T, T) = delete;

template<class M>
  concept bool Monoid = requires (M m) {
    { mempty<M> } -> M;
    { mappend(m, m); } -> M;
  };
----

첫 번째 정의는 (역시 제안된) 값 템플릿을 사용합니다. 다형적 값은 값의 패밀리로, 모든 타입마다 다른 값을 갖습니다.

``delete`` 키워드는 기본값이 정의되지 않았다는 것을 의미합니다. 케이스별로 구체화해야 합니다. ``mappend``도 마찬가지로 기본값이 없습니다.

컨셉 ``Monoid``는 술어(predicate)로(따라서 bool 타입), 주어진 타입 M에 대해 ``mempty``와 ``mappend``의 적절한 정의가 존재하는지 테스트합니다.

``Monoid`` 컨셉의 인스턴스화는 적절한 특수화와 오버로드를 제공함으로써 이루어질 수 있습니다:

[source,cpp]
----
template<>
std::string mempty<std::string> = {""};

std::string mappend(std::string s1, std::string s2) {
    return s1 + s2;
}
----

== 카테고리로서의 모노이드 (Monoid as Category)

지금까지는 집합의 원소 관점에서 모노이드를 "익숙하게" 정의했습니다. 하지만 아시다시피, 카테고리 이론에서는 집합과 그 원소에서 벗어나 대신 대상과 모피즘에 대해 이야기하려고 합니다. 그러니 관점을 조금 바꿔서, 이항 연산의 적용을 집합 주위에서 무언가를 "이동"시키거나 "이전"시키는 것으로 생각해 봅시다.

예를 들어, 모든 자연수에 5를 더하는 연산이 있습니다. 0을 5로, 1을 6으로, 2를 7로 매핑하는 식입니다. 이것은 자연수 집합에서 정의된 함수입니다. 좋습니다. 우리에게 함수와 집합이 있습니다. 일반적으로, 임의의 숫자 n에 대해 n을 더하는 함수—즉 n의 "가산기(adder)"가 있습니다.

가산기들은 어떻게 합성될까요? 5를 더하는 함수와 7을 더하는 함수의 합성은 12를 더하는 함수입니다. 따라서 가산기의 합성을 덧셈 규칙과 동등하게 만들 수 있습니다. 역시 좋습니다. 덧셈을 함수 합성으로 대체할 수 있습니다.

그런데 더 있습니다. 중립 원소인 0에 대한 가산기도 있습니다. 0을 더해도 아무것도 이동하지 않으므로, 자연수 집합에서의 항등 함수입니다.

전통적인 덧셈 규칙 대신 가산기를 합성하는 규칙을 줘도 정보 손실이 없습니다. 가산기의 합성이 결합법칙을 만족하는 것은 함수의 합성이 결합법칙을 만족하기 때문이고, 0-가산기는 항등 함수에 대응합니다.

예리한 독자라면 정수를 가산기로 매핑하는 것이 ``mappend``의 타입 시그니처를 ``m -> (m -> m)``로 두 번째로 해석한 것에서 비롯된다는 것을 알아챘을 것입니다. 이는 ``mappend``가 모노이드 집합의 원소를 해당 집합에 작용하는 함수로 매핑한다는 것을 알려줍니다.

이제 여러분이 자연수 집합을 다루고 있다는 사실을 잊으세요. 그저 단일 대상으로, 여러 모피즘—가산기들—이 달린 덩어리로 생각하세요. 모노이드는 단일 대상 카테고리입니다. 사실 모노이드라는 이름은 '하나'를 의미하는 그리스어 mono에서 유래했습니다. 모든 모노이드는 적절한 합성 규칙을 따르는 모피즘의 집합을 가진 단일 대상 카테고리로 설명될 수 있습니다.

문자열 연결은 흥미로운 경우입니다. 오른쪽 덧붙이기(right appender)와 왼쪽 덧붙이기(또는 앞에 붙이기, left appender/prepender)를 정의할 수 있는 선택지가 있기 때문입니다. 두 모델의 합성표는 서로 거울상입니다. "foo" 뒤에 "bar"를 덧붙이는 것이 "bar"를 앞에 붙인 후 "foo"를 앞에 붙이는 것에 대응한다는 것을 쉽게 확인할 수 있을 것입니다.

그렇다면 모든 카테고리 이론적 모노이드—단일 대상 카테고리—가 유일한 집합-이항-연산 모노이드를 정의하는지 궁금할 것입니다. 사실은 단일 대상 카테고리에서 항상 집합을 추출할 수 있습니다. 이 집합은 모피즘의 집합입니다. 우리 예제에서는 가산기입니다. 다시 말해, 카테고리 M의 단일 대상 m에 대한 홈-집합 M(m, m)이 있습니다. 이 집합에서 이항 연산을 쉽게 정의할 수 있습니다. 두 집합 원소의 모노이드 곱은 대응하는 모피즘의 합성에 해당하는 원소입니다. M(m, m)의 f와 g에 해당하는 두 원소를 주면, 그들의 곱은 합성 g∘f에 대응할 것입니다. 이 모피즘들의 소스와 타겟이 같은 대상이므로 합성은 항상 존재하고, 카테고리의 규칙에 의해 결합법칙을 만족합니다. 항등 모피즘은 이 곱의 중립 원소입니다. 따라서 카테고리 모노이드에서 집합 모노이드를 항상 복구할 수 있습니다. 모든 의도와 목적에 있어서 둘은 같은 것입니다.

*모피즘으로 본 모노이드 홈-집합과 집합의 점으로 본 모노이드 홈-집합*

수학자들이 지적할 만한 작은 문제가 하나 있습니다. 모피즘이 반드시 집합을 형성할 필요는 없습니다. 카테고리의 세계에는 집합보다 큰 것들이 있습니다. 임의의 두 대상 사이의 모피즘이 집합을 형성하는 카테고리를 *국소적으로 작다(locally small)*고 합니다. 약속한 대로 이런 미묘함은 대부분 무시하겠지만, 기록을 위해 언급해 둡니다.

카테고리 이론의 많은 흥미로운 현상은 홈-집합의 원소를 합성 규칙을 따르는 모피즘으로도 볼 수 있고 집합의 점으로도 볼 수 있다는 사실에 뿌리를 두고 있습니다. 여기서 M의 모피즘 합성은 집합 M(m, m)의 모노이드 곱으로 변환됩니다.
