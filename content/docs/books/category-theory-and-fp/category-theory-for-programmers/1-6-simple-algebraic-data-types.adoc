우리는 타입을 결합하는 두 가지 기본 방법을 살펴봤습니다. 곱(product)과 여곱(coproduct)이죠. 일상적인 프로그래밍에서 사용하는 수많은 데이터 구조를 이 두 메커니즘만으로 만들 수 있습니다. 이 사실은 실용적으로 중요한 의미를 갖습니다. 데이터 구조의 많은 속성들이 합성 가능(composable)하기 때문입니다. 예를 들어, 기본 타입의 값을 동등성 비교하는 방법을 알고, 이 비교를 곱 타입과 여곱 타입으로 일반화하는 방법을 안다면, 복합 타입에 대한 동등성 연산자의 도출을 자동화할 수 있습니다. 하스켈에서는 동등성, 비교, 문자열 변환 등을 복합 타입의 큰 부분에 대해 자동으로 도출할 수 있습니다.

이제 프로그래밍에 나타나는 곱 타입과 합 타입을 더 자세히 살펴봅시다.

== 곱 타입 (Product Types)

프로그래밍 언어에서 두 타입의 곱(Product)을 구현하는 전형적인 방법은 *쌍(pair)*입니다. 하스켈에서 쌍은 원시 타입 생성자이며, C++에서는 표준 라이브러리(``std\::pair``)에 정의된 템플릿입니다.

image::https://y30n9ju1v.github.io/develop/images/books/category-theory-for-programmers/pair.jpg[]

쌍은 엄밀히 가환적이지 않습니다. ``(Int, Bool)`` 쌍을 ``(Bool, Int)`` 쌍으로 대체할 수 없습니다. 비록 같은 정보를 담고 있지만요. 하지만 이들은 동형 모피즘까지는 가환적입니다. 동형 모피즘은 ``swap`` 함수(자신의 역함수이기도 한)로 주어집니다:

[source,haskell]
----
swap :: (a, b) -> (b, a)
swap (x, y) = (y, x)
----

두 쌍은 같은 데이터를 저장하는 다른 형식을 사용한다고 생각할 수 있습니다. 빅 엔디안 대 리틀 엔디안처럼요.

임의 개수의 타입을 곱으로 결합하려면 쌍 안에 쌍을 중첩할 수 있지만, 더 쉬운 방법이 있습니다. 중첩된 쌍은 튜플과 동등합니다. 이는 쌍을 중첩하는 다양한 방법이 동형이라는 사실의 귀결입니다. 세 타입 a, b, c를 이 순서대로 곱으로 결합하려면 두 가지 방법이 있습니다:

[source,haskell]
----
((a, b), c)
----

또는

[source,haskell]
----
(a, (b, c))
----

이 타입들은 다릅니다. 하나를 기대하는 함수에 다른 하나를 전달할 수 없습니다. 하지만 그 원소들은 일대일 대응 관계에 있습니다. 하나를 다른 하나로 매핑하는 함수가 있습니다:

[source,haskell]
----
alpha :: ((a, b), c) -> (a, (b, c))
alpha ((x, y), z) = (x, (y, z))
----

그리고 이 함수는 가역적(reversible)입니다:

[source,haskell]
----
alpha_inv :: (a, (b, c)) -> ((a, b), c)
alpha_inv  (x, (y, z)) = ((x, y), z)
----

따라서 이는 동형 모피즘입니다. 단지 같은 데이터를 다시 포장하는 다른 방법일 뿐입니다.

곱 타입의 생성을 타입에 대한 이항 연산으로 해석할 수 있습니다. 이 관점에서 보면 위 동형 모피즘은 모노이드에서 봤던 결합 법칙과 매우 유사합니다:

[source]
----
(a * b) * c = a * (b * c)
----

다만 모노이드의 경우 두 합성 방법이 동등한 반면, 여기서는 "동형 모피즘까지만" 동등합니다.

동형 모피즘을 받아들이고 엄격한 동등성을 고집하지 않는다면, 더 나아가 단위 타입 ``()``가 1이 곱셈의 단위인 것과 같은 방식으로 곱의 단위임을 보일 수 있습니다. 실제로 타입 a의 값과 단위를 쌍으로 만들어도 정보가 추가되지 않습니다. 타입:

[source,haskell]
----
(a, ())
----

는 a와 동형입니다. 동형 모피즘은 다음과 같습니다:

[source,haskell]
----
rho :: (a, ()) -> a
rho (x, ()) = x
----

[source,haskell]
----
rho_inv :: a -> (a, ())
rho_inv x = (x, ())
----

이러한 관찰을 Set(집합의 카테고리)가 모노이드 카테고리라고 말하면서 공식화할 수 있습니다. 객체를 곱할 수 있다는(여기서는 카르테시안 곱을 취한다는) 의미에서 모노이드이기도 한 카테고리입니다. 모노이드 카테고리에 대해서는 나중에 더 이야기하고 완전한 정의를 제시하겠습니다.

하스켈에서 곱 타입을 정의하는 더 일반적인 방법이 있습니다. 특히 곧 보겠지만 합 타입과 결합할 때 유용합니다. 여러 인자를 가진 명명된 생성자를 사용하는 것입니다. 예를 들어 쌍을 다음과 같이 정의할 수 있습니다:

[source,haskell]
----
data Pair a b = P a b
----

여기서 ``Pair a b``는 두 타입 a와 b로 매개변수화된 타입의 이름이고, ``P``는 데이터 생성자의 이름입니다. 두 타입을 Pair 타입 생성자에 전달해서 쌍 타입을 정의합니다. 적절한 타입의 두 값을 생성자 P에 전달해서 쌍 값을 구성합니다. 예를 들어 String과 Bool의 쌍으로 값 stmt를 정의해 봅시다:

[source,haskell]
----
stmt :: Pair String Bool
stmt = P "This statement is" False
----

첫 번째 줄은 타입 선언입니다. Pair의 제네릭 정의에서 a와 b를 String과 Bool로 대체한 타입 생성자 Pair를 사용합니다. 두 번째 줄은 구체적인 문자열과 구체적인 불리언을 데이터 생성자 P에 전달해서 실제 값을 정의합니다. 타입 생성자는 타입을 구성하는 데 사용되고, 데이터 생성자는 값을 구성하는 데 사용됩니다.

하스켈에서는 타입 생성자와 데이터 생성자의 이름 공간(namespace)이 분리되어 있으므로, 다음과 같이 동일한 이름을 사용하는 경우가 많습니다:

[source,haskell]
----
data Pair a b = Pair a b
----

눈을 가늘게 뜨고 보면 내장 쌍 타입도 이런 종류의 선언의 변형으로 볼 수 있습니다. Pair라는 이름이 이항 연산자 ``(,)``로 대체된 것이죠. 실제로 ``(,)``를 다른 명명된 생성자처럼 사용해서 전위 표기법으로 쌍을 만들 수 있습니다:

[source,haskell]
----
stmt = (,) "This statement is" False
----

마찬가지로 ``(,,)``를 사용하면 3-튜플을 만들 수 있습니다.

제네릭 쌍이나 튜플을 사용하는 대신, 다음과 같이 특정한 명명된 곱 타입을 정의할 수도 있습니다:

[source,haskell]
----
data Stmt = Stmt String Bool
----

이것은 단지 String과 Bool의 곱이지만 자체 이름과 생성자를 가집니다. 이런 선언 스타일의 장점은 같은 내용을 가지지만 의미와 기능이 다르고 서로 대체될 수 없는 많은 타입을 정의할 수 있다는 것입니다.

튜플과 다중 인자 생성자로 프로그래밍하면 어수선해지고 오류가 발생하기 쉽습니다. 어느 구성 요소가 무엇을 나타내는지 추적해야 하니까요. 구성 요소에 이름을 붙이는 것이 더 좋은 경우가 많습니다. 명명된 필드를 가진 곱 타입을 하스켈에서는 레코드(record)라 하고, C에서는 구조체(struct)라 합니다.

=== 레코드 (Records)

간단한 예를 봅시다. 두 문자열(이름과 기호)과 정수(원자 번호)를 결합해서 화학 원소를 설명하고 싶습니다. 튜플 ``(String, String, Int)``를 사용하고 어느 구성 요소가 무엇을 나타내는지 기억할 수 있습니다. 패턴 매칭으로 구성 요소를 추출할 수 있습니다. 예를 들어 원소의 기호가 이름의 접두사인지(He가 Helium의 접두사인 것처럼) 확인하는 함수는 다음과 같습니다:

[source,haskell]
----
startsWithSymbol :: (String, String, Int) -> Bool
startsWithSymbol (name, symbol, _) = isPrefixOf symbol name
----

이 코드는 오류가 발생하기 쉽고, 읽고 유지하기 어렵습니다. 레코드를 정의하는 것이 훨씬 낫습니다:

[source,haskell]
----
data Element = Element { name         :: String
                       , symbol       :: String
                       , atomicNumber :: Int }
----

두 표현은 동형입니다. 이는 서로의 역인 다음 두 변환 함수가 증명합니다:

[source,haskell]
----
tupleToElem :: (String, String, Int) -> Element
tupleToElem (n, s, a) = Element { name = n
                                , symbol = s
                                , atomicNumber = a }
----

[source,haskell]
----
elemToTuple :: Element -> (String, String, Int)
elemToTuple e = (name e, symbol e, atomicNumber e)
----

레코드 필드의 이름이 이 필드에 접근하는 함수로도 사용된다는 점에 주목하세요. 예를 들어 ``atomicNumber e``는 e에서 atomicNumber 필드를 가져옵니다. atomicNumber를 다음 타입의 함수로 사용합니다:

[source,haskell]
----
atomicNumber :: Element -> Int
----

Element에 대한 레코드 구문으로 startsWithSymbol 함수가 더 읽기 쉬워집니다:

[source,haskell]
----
startsWithSymbol :: Element -> Bool
startsWithSymbol e = isPrefixOf (symbol e) (name e)
----

심지어 함수 isPrefixOf를 백쿼트로 감싸 중위 연산자로 만드는 하스켈 트릭을 사용하면 거의 문장처럼 읽히게 할 수 있습니다:

[source,haskell]
----
startsWithSymbol e = symbol e `isPrefixOf` name e
----

중위 연산자가 함수 호출보다 우선순위가 낮으므로 이 경우 괄호를 생략할 수 있습니다.

== 합 타입 (Sum Types)

집합의 카테고리에서 곱이 곱 타입을 낳듯이, 여곱은 합 타입을 낳습니다. 하스켈에서 합 타입의 표준 구현은 다음과 같습니다:

[source,haskell]
----
data Either a b = Left a | Right b
----

쌍과 마찬가지로 ``Either`` 역시 (동형 모피즘 수준에서) 교환 법칙이 성립하며, 여러 번 중첩하더라도 그 중첩 순서가 중요하지 않습니다(결합 법칙 성립). 따라서 다음과 같이 세 타입 중 하나를 선택하는 합 타입을 정의할 수도 있습니다:

[source,haskell]
----
data OneOfThree a b c = Sinistral a | Medial b | Dextral c
----

집합 카테고리(``Set``) 역시 여곱에 대해 (대칭) 모노이드 카테고리 구조를 가집니다. 이때 이항 연산의 역할은 서로소 합(disjoint sum)이 맡고, 단위원의 역할은 *초기 객체(initial object)* 가 맡습니다. 타입 시스템의 관점에서 보면 ``Either``는 모노이드 연산자이고, 비어있는 타입인 *``Void``* 는 그 항등원 역할을 합니다. 즉, ``Either``를 '덧셈'으로, ``Void``를 '0'으로 생각할 수 있습니다. 실제로 어떤 타입 stem:[a]에 ``Void``를 더해도 그 내용은 변하지 않습니다:

[source,haskell]
----
Either a Void
----

이 타입은 stem:[a]와 동형입니다. 왜냐하면 ``Right`` 생성자를 통해 값을 만들 방법이 전혀 없기 때문입니다(``Void`` 타입의 값은 존재하지 않으니까요). 따라서 ``Either a Void``의 유일한 거주자는 ``Left`` 생성자로 만들어진 값뿐이며, 이는 단순히 타입 stem:[a]의 값을 감싸고 있는 것에 불과합니다. 이를 기호로 표현하면 stem:[a + 0 = a]가 됩니다.

합 타입은 하스켈에서 매우 흔하게 쓰이지만, C++의 대응물인 ``union``이나 ``variant``는 상대적으로 덜 쓰이는 편입니다. 여기에는 몇 가지 이유가 있습니다.

우선 가장 단순한 형태의 합 타입인 *열거형(enumeration)* 을 살펴봅시다. C++에서는 이를 ``enum``으로 구현합니다. 하스켈의 합 타입 선언이:

[source,haskell]
----
data Color = Red | Green | Blue
----

라면, C++에서는 다음과 같이 작성하는 것과 같습니다:

[source,cpp]
----
enum { Red, Green, Blue };
----

더 간단한 경우인 불리언(Boolean)은 다음과 같습니다:

[source,haskell]
----
data Bool = True | False
----

이는 C++의 기본 타입인 ``bool``에 해당하죠.

값의 존재 유무를 인코딩하는 간단한 합 타입의 경우, C++에서는 빈 문자열, 음수, 널 포인터(null pointer) 같은 '특별한 값'이나 '유효하지 않은 값'을 활용하는 트릭을 자주 씁니다. 반면 하스켈에서는 이러한 의도적인 선택성을 *``Maybe``* 타입을 통해 명시적으로 표현합니다:

[source,haskell]
----
data Maybe a = Nothing | Just a
----

사실 ``Maybe`` 타입은 두 타입의 합으로 볼 수 있습니다. 생성자들을 각각 독립적인 타입으로 분리해 보면 이를 명확히 알 수 있습니다. 우선 ``Nothing`` 부분은:

[source,haskell]
----
data NothingType = Nothing
----

값 하나(``Nothing``)만 가지는 열거형이며, 이는 싱글턴(singleton) 또는 단위 타입 ``()``와 동등합니다. 그리고 ``Just`` 부분은:

[source,haskell]
----
data JustType a = Just a
----

단순히 타입 stem:[a]를 캡슐화한 것입니다. 따라서 ``Maybe``를 다음과 같이 정의할 수도 있었을 것입니다:

[source,haskell]
----
type Maybe a = Either () a
----

더 복잡한 합 타입들은 C++에서 주로 포인터를 사용하여 '흉내'를 냅니다. 포인터는 널(null)일 수도 있고, 특정 객체를 가리킬 수도 있기 때문입니다. 예를 들어 재귀적인 합 타입으로 정의되는 하스켈의 리스트(list)를 봅시다:

[source,haskell]
----
List a = Nil | Cons a (List a)
----

C++에서는 널 포인터 트릭을 사용하여 이를 다음과 같이 번역할 수 있습니다:

[source,cpp]
----
template<class A> 
class List {
    Node<A> * _head;
public:
    List() : _head(nullptr) {}  // Nil
    List(A a, List<A> l)        // Cons
      : _head(new Node<A>(a, l))
    {}
};
----

여기서 하스켈의 두 생성자 ``Nil``과 ``Cons``가 C++의 오버로드된 생성자(인수가 없는 것과 값과 리스트를 받는 것)로 대응된다는 점을 주목하세요. C++의 ``List`` 클래스는 합 타입의 두 구성 요소를 구분하기 위한 별도의 태그(tag)가 필요 없습니다. 대신 ``_head``를 위한 특수한 ``nullptr`` 값으로 ``Nil``을 인코딩합니다.

하지만 하스켈과 C++ 타입 시스템의 가장 근본적인 차이점은 *불변성(Immutability)* 에 있습니다. 하스켈의 데이터 구조는 한 번 생성되면 그 상태가 영원히 유지됩니다. 특정 생성자로 객체를 만들면, 객체는 자신이 어떤 생성자로 만들어졌는지, 어떤 인수를 받았는지를 영원히 기억합니다. ``Just "energy"``로 생성된 ``Maybe`` 객체가 갑자기 ``Nothing``으로 변하는 일은 결코 일어나지 않습니다. 마찬가지로 빈 리스트는 영원히 비어 있고, 세 원소를 가진 리스트는 영원히 그 세 원소만을 가집니다.

이러한 불변성 덕분에 생성 과정을 '역으로' 되짚는 것이 가능해집니다. 즉, 완성된 객체를 다시 구성 부품들로 분해할 수 있죠. 이 분해 작업을 바로 *패턴 매칭(pattern matching)* 이라고 부르며, 이때 생성자를 패턴으로 다시 활용합니다. 생성자의 인수 자리에는 변수(혹은 또 다른 패턴)가 들어갑니다.

``List`` 데이터 타입은 두 개의 생성자를 가지므로, 리스트를 분해할 때는 각 생성자에 대응하는 두 가지 패턴을 사용합니다. 하나는 빈 리스트(``Nil``)일 때, 다른 하나는 원소가 연결된 리스트(``Cons``)일 때의 로직을 작성하는 식입니다. 예를 들어 리스트의 나머지 부분(tail)을 가져오는 함수는 다음과 같이 정의할 수 있습니다:

[source,haskell]
----
maybeTail :: List a -> Maybe (List a)
maybeTail Nil = Nothing
maybeTail (Cons _ t) = Just t
----

여기서 ``maybeTail``의 첫 번째 정의는 ``Nil`` 생성자를 패턴으로 사용하고 ``Nothing``을 반환합니다. 두 번째 정의는 ``Cons`` 생성자를 패턴으로 사용합니다. 첫 번째 생성자 인수는 관심이 없으므로 와일드카드로 대체합니다. 두 번째 인수는 변수 ``t``에 바인딩됩니다(이런 것들을 변수라고 부르겠습니다. 엄밀히 말하면 결코 변하지 않지만요. 한번 표현식에 바인딩되면 변수는 절대 변하지 않습니다). 반환 값은 ``Just t``입니다. 이제 리스트가 어떻게 생성되었는지에 따라 해당하는 절과 매칭됩니다. ``Cons``로 생성되었다면 전달된 두 인수가 추출되고(첫 번째는 버려집니다).

더 정교한 합 타입들은 C++에서 다형성 클래스 계층 구조를 통해 구현되기도 합니다. 공통 조상을 공유하는 클래스 패밀리들은 ``vtable``이라는 숨겨진 태그를 가진 일종의 변형 타입으로 볼 수 있습니다. 하스켈에서 패턴 매칭과 생성자별 특수 코드로 처리하는 작업을, C++에서는 ``vtable`` 포인터를 기반으로 한 가상 함수 호출(virtual function dispatch)로 수행하는 셈입니다.

C++에서 ``union``이 합 타입으로 거의 쓰이지 않는 이유는 ``union``에 들어갈 수 있는 것에 심각한 제약이 있기 때문입니다. 복사 생성자가 있는 ``std\::string`` 같은 것조차 ``union``에 넣을 수 없습니다.

== 타입의 대수 (Algebra of Types)

곱 타입과 합 타입은 각각 단독으로도 유용하지만, 진정한 힘은 이 둘을 결합할 때 발휘됩니다. 여기서 다시 한번 '합성의 힘'을 실감하게 되죠.

지금까지 발견한 사실들을 정리해 봅시다. 우리는 타입 시스템의 기초가 되는 두 개의 가환 모노이드(commutative monoid) 구조를 발견했습니다. 하나는 ``Void``를 단위원으로 갖는 합 타입이고, 다른 하나는 단위 타입 ``()``를 단위원으로 갖는 곱 타입입니다. 이들을 각각 산술 연산의 '덧셈'과 '곱셈'에 비유하면, ``Void``는 0에, 단위 타입 ``()``는 1에 대응됩니다.

이 비유를 조금 더 확장해 볼까요? 예를 들어 임의의 숫자에 0을 곱하면 0이 되듯이, 한 구성 요소가 ``Void``인 곱 타입도 ``Void``와 동형일까요? 즉, ``Int``와 ``Void``의 쌍을 만드는 것이 가능할까요?

쌍을 만들려면 두 값이 모두 필요합니다. 정수는 얼마든지 얻을 수 있지만, ``Void`` 타입의 값은 세상에 존재하지 않습니다. 따라서 어떤 타입 stem:[a]에 대해서도 타입 ``(a, Void)``의 거주자(값)는 존재할 수 없으며, 결과적으로 ``Void``와 동등해집니다. 기호로 쓰면 stem:[a \cdot 0 = 0]이 성립하며, 이는 곧 stem:[a \times 0 = 0]과 같은 의미입니다.

덧셈과 곱셈을 연결하는 또 다른 중요한 법칙은 *분배 법칙(distributive law)* 입니다:

[source]
----
a * (b + c) = a * b + a * c
----

이 법칙이 곱 타입과 합 타입 사이에도 성립할까요? 네, 역시 (동형 모피즘 수준에서) 성립합니다. 좌변은 다음 타입에 해당하고:

[source,haskell]
----
(a, Either b c)
----

우변은 다음 타입에 해당합니다:

[source,haskell]
----
Either (a, b) (a, c)
----

한 방향으로의 변환 함수는 다음과 같이 작성할 수 있습니다:

[source,haskell]
----
prodToSum :: (a, Either b c) -> Either (a, b) (a, c)
prodToSum (x, e) = 
    case e of
      Left  y -> Left  (x, y)
      Right z -> Right (x, z)
----

반대 방향으로 향하는 함수는 다음과 같습니다:

[source,haskell]
----
sumToProd :: Either (a, b) (a, c) -> (a, Either b c)
sumToProd e = 
    case e of
      Left  (x, y) -> (x, Left  y)
      Right (x, z) -> (x, Right z)
----

하스켈의 ``case of`` 문은 함수 내부에서 패턴 매칭을 수행할 때 쓰입니다. 각 패턴 뒤에 화살표(``->``)를 적고, 해당 패턴이 매칭될 때 실행될 표현식을 작성합니다. 예를 들어 ``prodToSum``을 다음과 같은 인수로 호출한다고 해 봅시다:

[source,haskell]
----
prod1 :: (Int, Either String Float)
prod1 = (2, Left "Hi!")
----

그러면 ``case e of``의 ``e``는 ``Left "Hi!"``가 되고, ``Left y`` 패턴과 매칭되어 ``y``에 ``"Hi!"``가 바인딩됩니다. ``x``는 앞서 2와 매칭되었으므로, 전체 결과는 예상대로 ``Left (2, "Hi!")``가 됩니다.

이 두 함수가 서로 역함수 관계임을 일일이 증명하지는 않겠지만, 직관적으로 보아도 당연히 그래야만 합니다 단순히 데이터를 다른 상자에 옮겨 담는 '재포장' 과정일 뿐이니까요.

[source,text]
----
  [ 대수적 자료형의 분배 법칙 동형 다이어그램 ]

                 (a, Either b c)
                   /          \
      prodToSum   /            \   sumToProd
                 v              v
        Either (a, b) (a, c) ────> (a, Either b c)
          (a × (b + c) ≅ a × b + a × c)
----

수학자들은 이처럼 곱셈과 덧셈이 얽혀 있는 구조를 *세미링(semiring)* 이라고 부릅니다. 다만 타입의 세계에서는 '뺄셈'을 정의할 수 없기 때문에 완전한 링(Ring)은 아닙니다. 그래서 음수(stem:[n]egative)가 없는 링이라는 뜻에서 *리그(rig)* 라고 부르기도 하죠. 어쨌든 이 대수적 구조 덕분에 자연수에 대한 수학적 진술들을 타입에 대한 진술로 번역하여 많은 통찰을 얻을 수 있습니다. 아래는 그 번역표입니다:

|숫자|타입|
|---|---|
|0|Void|
|1|()|
|a + b|Either a b = Left a \| Right b|
|a * b|(a, b) 또는 Pair a b = Pair a b|
|2 = 1 + 1|data Bool = True \| False|
|1 + a|data Maybe = Nothing \| Just a|

특히 리스트(List) 타입은 방정식의 해로 정의된다는 점이 매우 흥미롭습니다. 리스트의 정의를 다시 보면 자기 자신이 정의의 양쪽에 나타나죠:

[source,haskell]
----
List a = Nil | Cons a (List a)
----

여기에 앞서 만든 번역 규칙을 적용하고 ``List a``를 미지수 stem:[x]로 치환하면 다음과 같은 방정식을 얻습니다:

[source]
----
x = 1 + a * x
----

[source,text]
----
  [ 재귀적 리스트의 대수적 전개 (Taylor Series of List) ]

   List a  = 1 + a * (List a)
           = 1 + a * (1 + a * (1 + ...))
           = 1 + a + a² + a³ + a⁴ + ... + aⁿ + ...

   [ ]     : 1 (Nil, 빈 리스트 - 유닛 타입 ())
   [a]     : a (원소 1개)
   [a, a]  : a² (원소 2개 곱 타입 (a, a))
   [a, a, a]: a³ (원소 3개 곱 타입 (a, a, a))
----

물론 타입을 빼거나 나누는 연산은 없기에 일반적인 대수학처럼 풀 수는 없습니다. 하지만 우변의 stem:[x]를 다시 stem:[(1 + a \cdot x)]로 계속해서 치환(substitution)해 나가는 기법을 쓸 수 있습니다:

[source]
----
x = 1 + a*x
x = 1 + a*(1 + a*x) = 1 + a + a*a*x
x = 1 + a + a*a*(1 + a*x) = 1 + a + a*a + a*a*a*x
...
x = 1 + a + a*a + a*a*a + a*a*a*a...
----

그 결과, 리스트는 무한한 '곱 타입(튜플)'들의 '합 타입'이 됩니다. 이를 해석하면 리스트란 "비어있거나(stem:[1])", "원소가 하나(stem:[a])", "둘(stem:[a^2])", "셋(stem:[a^3])"... 인 상태들의 집합이라는 뜻이 됩니다. 우리가 알고 있는 리스트, 즉 임의의 길이를 가진 'stem:[a]들의 나열'과 정확히 일치하죠!

리스트에는 이보다 훨씬 더 많은 이야기가 담겨 있습니다. 함자(Functor)와 고정점(Fixed Point)에 대해 배운 후에 리스트를 비롯한 재귀적 자료구조를 다시 다루겠습니다.

방정식을 세우고 기호 변수를 사용하여 문제를 푸는 것, 그것이 바로 대수학(Algebra)입니다. 우리가 이 타입들을 *대수적 자료형(Algebraic Data Type)* 이라고 부르는 이유가 여기에 있습니다.

마지막으로 타입 대수의 매우 중요한 해석 하나를 언급하겠습니다. 두 타입 stem:[a]와 stem:[b]의 곱은 stem:[a] 타입의 값과 stem:[b] 타입의 값을 *모두* 포함해야 하므로, 두 타입 모두 거주되어야 합니다(inhabited, 즉 값이 존재해야 합니다). 반면 두 타입의 합은 stem:[a] 타입의 값 *또는* stem:[b] 타입의 값을 포함하므로, 둘 중 하나만 거주되어 있으면 충분합니다. 논리적 ``and``와 ``or`` 역시 세미링을 형성하며, 타입 이론과 매핑될 수 있습니다:

|논리|타입|
|---|---|
|false|Void|
|true|()|
|a \|\| b|Either a b = Left a \| Right b|
|a && b|(a, b)|

이 비유는 더 깊이 파고들어갈 수 있으며, 논리와 타입 이론 사이의 커리-하워드 동형성(Curry-Howard isomorphism)의 기초가 됩니다. 함수 타입에 대해 이야기할 때 이것으로 다시 돌아오겠습니다.
