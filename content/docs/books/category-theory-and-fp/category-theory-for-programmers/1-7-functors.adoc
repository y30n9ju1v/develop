'''
같은 말을 반복하는 것 같지만, 함자(Functor)에 대해 다시 한번 강조하고 싶습니다. 함자는 매우 단순하면서도 강력한 개념입니다. 카테고리 이론은 이처럼 단순하지만 강력한 아이디어들로 가득 차 있습니다. 함자는 카테고리 간의 매핑(Mapping)입니다. 두 카테고리 stem:[C]와 stem:[D]가 있을 때, 함자 stem:[F]는 stem:[C]의 객체를 stem:[D]의 객체로 매핑합니다. 즉, 객체에 작용하는 함수라고 볼 수 있습니다. stem:[a]가 stem:[C]의 객체라면, stem:[D]에서의 그 이미지는 stem:[F\ a]라고 씁니다(괄호는 생략합니다). 하지만 카테고리는 객체로만 구성되지 않습니다. 객체와 그들을 연결하는 모피즘도 포함되죠. 함자는 모피즘 또한 매핑합니다. 즉, 모피즘에 작용하는 함수이기도 합니다. 하지만 함자는 모피즘을 무작위로 매핑하지 않고, 연결 구조를 보존합니다. 만약 stem:[C]의 모피즘 stem:[f]가 객체 stem:[a]에서 stem:[b]를 연결한다면:

[source,haskell]
----
f :: a -> b
----

``f``의 D에서의 이미지인 ``F f``는 ``a``의 이미지를 ``b``의 이미지에 연결할 것입니다:

[source,haskell]
----
F f :: F a -> F b
----

(수학 표기법과 하스켈 표기법을 혼용합니다. 함자를 객체나 모피즘에 적용할 때는 괄호를 생략합니다.) 보시다시피 함자는 카테고리의 구조를 보존합니다. 한 카테고리에서 연결된 것은 다른 카테고리에서도 그대로 연결됩니다. 하지만 카테고리의 구조에는 더 중요한 것이 있습니다. 바로 모피즘의 합성(Composition)입니다. 만약 stem:[h]가 stem:[f]와 stem:[g]의 합성이라면:

[source,haskell]
----
h = g . f
----

함자에 의한 이미지에서도 합성이 그대로 유지되길 바랍니다:

[source,haskell]
----
F h = F g . F f
----

마지막으로 stem:[C]의 모든 항등 모피즘은 stem:[D]의 항등 모피즘으로 매핑되어야 합니다:

[source,haskell]
----
F ida = idF a
----

여기서 stem:[id_a]는 객체 stem:[a]에서의 항등 모피즘이고, stem:[id_{F\ a}]는 stem:[F\ a]에서의 항등 모피즘입니다.

이러한 조건 때문에 함자는 일반적인 함수보다 훨씬 제한적입니다. 함자는 반드시 카테고리의 구조를 보존해야 합니다. 카테고리를 모피즘이라는 그물망으로 엮인 객체들의 집합으로 상상해 보세요. 함자는 이 그물망을 절대 찢지 않습니다. 여러 객체를 하나로 뭉치거나 여러 모피즘을 하나로 합칠 수는 있어도, 연결을 끊을 수는 없습니다. 이러한 "찢어지지 않음"은 미적분학에서 배우는 연속성(Continuity) 조건과 비슷합니다. 이런 의미에서 함자는 "연속적"입니다(물론 카테고리 이론에는 함자에 대한 더 엄밀한 연속성 개념이 따로 존재합니다). 함수와 마찬가지로 함자도 함몰(Collapsing)과 매립(Embedding)을 수행할 수 있습니다. 매립의 측면은 출발 카테고리가 대상 카테고리보다 훨씬 작을 때 두드러집니다. 극단적으로 출발 카테고리가 객체 하나와 모피즘 하나(항등 모피즘)만 있는 싱글톤(Singleton) 카테고리인 경우를 생각해 봅시다. 싱글톤 카테고리에서 다른 카테고리로 가는 함자는 단순히 그 카테고리에서 객체 하나를 선택하는 것과 같습니다. 이는 싱글톤 집합에서의 모피즘이 대상 집합에서 요소를 선택하는 속성과 완전히 일치합니다. 반대로 가장 극단적으로 함몰시키는 함자는 *상수 함자(Constant Functor)* stem:[\Delta_c]입니다. 이는 출발 카테고리의 모든 객체를 대상 카테고리의 특정 객체 stem:[c]로 매핑하며, 모든 모피즘을 항등 모피즘 stem:[id_c]로 매핑합니다. 마치 모든 것을 하나의 특이점으로 빨아들이는 블랙홀처럼 작동하죠. 리미트(Limit)와 코리미트(Colimit)를 다룰 때 이 함자를 다시 보게 될 것입니다.

== 프로그래밍에서의 함자

이제 실용적인 프로그래밍 이야기로 들어가 보겠습니다. 우리에게는 타입과 함수의 카테고리가 있습니다. 이 카테고리를 자기 자신에게 매핑하는 함자를 *자기 함자(Endofunctor)*라고 부릅니다. 그렇다면 타입 카테고리에서의 자기 함자란 무엇일까요? 우선 타입을 타입으로 매핑해야 합니다. 여러분은 이미 이런 매핑을 수없이 보셨을 텐데, 단지 그것이 함자라는 사실을 깨닫지 못했을 뿐일 겁니다. 바로 다른 타입에 의해 매개변수화된 타입(Generic types)의 정의가 그 예입니다. 몇 가지 예를 살펴보죠.

=== Maybe 함자

``Maybe``의 정의는 타입 stem:[a]를 타입 ``Maybe a``로 보내는 매핑입니다:

[source,haskell]
----
data Maybe a = Nothing | Just a
----

여기서 중요한 구별이 있습니다. ``Maybe`` 그 자체는 타입이 아니라 타입 생성자(Type constructor)입니다. ``Int``나 ``Bool`` 같은 타입 인수를 채워넣어야 비로소 실제 타입이 됩니다. 즉, 인수가 없는 ``Maybe``는 타입을 인자로 받아 타입을 내놓는 함수와 같습니다. 그렇다면 이 ``Maybe``를 함자로 만들 수 있을까요? (앞으로는 프로그래밍 맥락에서 '함자'라고 하면 보통 엔도함자를 뜻합니다.) 함자가 되려면 객체(타입)뿐만 아니라 모피즘(함수)도 매핑해야 합니다. 만약 stem:[a]에서 stem:[b]로 가는 함수 stem:[f]가 있다면:

[source,haskell]
----
f :: a -> b
----

우리는 ``Maybe a``에서 ``Maybe b``로 가는 함수를 만들어야 합니다. 이 함수를 정의하려면 ``Maybe``의 두 생성자에 맞춰 두 가지 경우를 생각해야 하죠. ``Nothing`` 케이스는 간단합니다. 그냥 ``Nothing``을 반환하면 됩니다. 인자가 ``Just``인 경우에는 그 안의 내용물에 함수 stem:[f]를 적용하면 됩니다. 따라서 함자에 의한 stem:[f]의 이미지는 다음과 같은 함수가 됩니다:

[source,haskell]
----
f’ :: Maybe a -> Maybe b
f’ Nothing = Nothing
f’ (Just x) = Just (f x)
----

(참고로 하스켈은 변수 이름에 작은따옴표(')를 사용할 수 있어 이런 경우에 매우 편리합니다.) 하스켈에서 모피즘을 매핑하는 함자의 기능은 ``fmap``이라는 고차 함수로 구현됩니다. ``Maybe``의 경우 시그니처는 다음과 같습니다:

[source,haskell]
----
fmap :: (a -> b) -> (Maybe a -> Maybe b)
----

우리는 흔히 ``fmap``이 함수를 *리프팅(Lift)*한다고 표현합니다. 이렇게 들어올려진 함수는 ``Maybe`` 값에 작용할 수 있게 되죠. 하스켈의 특징인 커링(Currying) 덕분에 이 시그니처는 두 가지로 해석될 수 있습니다. 하나는 함수 ``(a -> b)``를 받아 ``(Maybe a -> Maybe b)``라는 새로운 함수를 내놓는 단일 인자 함수로 보는 것이고, 다른 하나는 함수와 ``Maybe a``를 모두 받아 ``Maybe b``를 결과로 주는 두 인자 함수로 보는 것입니다:

[source,haskell]
----
fmap :: (a -> b) -> Maybe a -> Maybe b
----

이전 논의에 따라 ``Maybe``에 대한 ``fmap`` 구현은 다음과 같습니다:

[source,haskell]
----
fmap _ Nothing = Nothing
fmap f (Just x) = Just (f x)
----

[source,text]
----
  [ 함자 (Functor)의 객체 매핑과 모피즘 리프팅 ]

    카테고리 C                            카테고리 D (또는 엔도함자의 경우 C)
    ──────────                            ──────────────────────────────────
        a                                                F a
        │                                                 │
        │ f                                               │ F f (fmap f)
        ▼                                                 ▼
        b                                                F b

    * 객체 매핑:   a  ───F───> F a
    * 모피즘 매핑: f  ───F───> F f  (하스켈: fmap f)

    [ 함자 공리 (Functor Laws) 가환 다이어그램 ]

    1. 항등 사상 보존:                 2. 사상 합성 보존:
          F(id_a) = id_{F a}               F(g ∘ f) = F g ∘ F f

           id_a                                  f           g
        a ↺ ───F───> F a ↺ id_{F a}         a ──────> b ──────> c
                                             \                 /
                                              \───── g ∘ f ───/
                                                      │
                                                      │ F (함자 매핑)
                                                      ▼
                                                     F f         F g
                                            F a ──────> F b ──────> F c
                                             \                     /
                                              \──── F(g ∘ f) ─────/
                                                (= F g ∘ F f)
----

타입 생성자 ``Maybe``와 함수 ``fmap``이 함자를 이루려면, ``fmap``이 항등원과 합성을 보존함을 증명해야 합니다. 이를 "함자 법칙(Functor laws)"이라고 부르지만, 이는 단순히 카테고리의 구조가 보존됨을 보장하는 장치일 뿐입니다.

=== 등식적 추론 (Equational Reasoning)

함자 법칙을 증명하기 위해 하스켈에서 자주 쓰이는 '등식적 추론(Equational Reasoning)' 기법을 사용하겠습니다. 하스켈 함수가 등식(=)으로 정의된다는 점을 이용하는 것인데, 왼쪽과 오른쪽이 정말로 같다는 뜻입니다. 변수 이름만 겹치지 않는다면 언제든 한쪽을 다른 쪽으로 갈아 끼울 수 있습니다. 코드를 인라인화(Inlining)하거나 반대로 공통 부분을 함수로 묶어내는 리팩토링 과정과 비슷하다고 생각하면 됩니다. 항등 함수 ``id``를 예로 들어보죠:

[source,haskell]
----
id x = x
----

코드에서 ``id y``를 보면 그냥 ``y``로 바꿀 수 있습니다(인라인화). 마찬가지로 ``id (y + 2)`` 같은 표현식도 그냥 ``y + 2``로 인라인화할 수 있죠. 이 작업은 거꾸로도 가능해서, 어떤 표현식 ``e``를 ``id e``로 감싸는 리팩토링도 할 수 있습니다. 함수가 패턴 매칭으로 정의된 경우라면 각 정의를 개별적인 사실로 활용합니다. 예를 들어 앞서 정의한 ``fmap``에 따라 ``fmap f Nothing``을 보면 망설임 없이 ``Nothing``으로 바꿀 수 있죠. 자, 이제 본격적으로 증명을 시작해 봅시다. 우선 항등성 보존 법칙입니다:

[source,haskell]
----
fmap id = id
----

고려해야 할 두 가지 경우가 있습니다: ``Nothing``과 ``Just``. 첫 번째 경우는 다음과 같습니다 (왼쪽을 오른쪽으로 변환하기 위해 하스켈 의사 코드를 사용하고 있습니다):

[source,haskell]
----
fmap id Nothing 
= { definition of fmap }
  Nothing 
= { definition of id }
  id Nothing
----

마지막 단계에서 ``id`` 정의를 거꾸로 적용해 ``Nothing``을 ``id Nothing``으로 바꾼 부분에 주목해 주세요. 실제 증명에서는 양쪽에서 시작해 가운데에서 만나도록 변형하는 방식을 자주 사용합니다. 똑같은 중간 결과물(``Nothing``)에 도달하면 증명이 끝나는 것이죠. ``Just`` 케이스도 간단합니다:

[source,haskell]
----
fmap id (Just x) 
= { definition of fmap }
  Just (id x) 
= { definition of id }
  Just x
= { definition of id }
  id (Just x)
----

다음으로 ``fmap``이 합성을 보존하는지 확인해 봅시다:

[source,haskell]
----
fmap (g . f) = fmap g . fmap f
----

먼저 ``Nothing`` 경우입니다:

[source,haskell]
----
fmap (g . f) Nothing 
= { definition of fmap }
  Nothing 
= { definition of fmap }
  fmap g Nothing
= { definition of fmap }
  fmap g (fmap f Nothing)
----

그리고 ``Just`` 경우입니다:

[source,haskell]
----
fmap (g . f) (Just x)
= { definition of fmap }
  Just ((g . f) x)
= { definition of composition }
  Just (g (f x))
= { definition of fmap }
  fmap g (Just (f x))
= { definition of fmap }
  fmap g (fmap f (Just x))
= { definition of composition }
  (fmap g . fmap f) (Just x)
----

한 가지 강조하고 싶은 점은, 이런 등식적 추론은 부작용(Side effect)이 있는 C++ 스타일의 "함수"에는 통하지 않는다는 것입니다. 아래 코드를 보시죠:

[source,cpp]
----
int square(int x) {
    return x * x;
}

int counter() {
    static int c = 0;
    return c++;
}

double y = square(counter());
----

등식적 추론을 사용한다면 ``square``를 인라인화하여 다음을 얻을 수 있을 것입니다:

[source,cpp]
----
double y = counter() * counter();
----

이는 명백히 잘못된 변환이며, 다른 결과를 만듭니다. 그럼에도 불구하고 만약 ``square``를 매크로로 구현했다면, C++ 컴파일러는 등식적 추론을 하듯 무턱대고 인라인화하여 재앙 같은 결과를 초래할 수 있습니다.

=== Optional

함자는 하스켈에서 아주 자연스럽게 표현되지만, 제네릭(Generic) 프로그래밍과 고차 함수를 지원하는 언어라면 어디서든 정의할 수 있습니다. ``Maybe``의 C++ 버전이라 할 수 있는 ``optional`` 템플릿 타입을 통해 함자 개념을 살펴봅시다. 아래는 핵심 구현 요약입니다(실제 표준 라이브러리의 ``optional``은 복사 의미론이나 자원 관리 때문에 훨씬 복잡합니다):

[source,cpp]
----
template<class T>
class optional {
    bool _isValid; // the tag
    T    _v;
public:
    optional()    : _isValid(false) {}         // Nothing
    optional(T x) : _isValid(true) , _v(x) {}  // Just
    bool isValid() const { return _isValid; }
    T val() const { return _v; }
};
----

이 템플릿은 함자의 첫 번째 조건인 타입 매핑(T -> ``optional<T>``)을 수행합니다. 이제 함수에 대한 작용(모피즘 매핑)을 정의해 보죠:

[source,cpp]
----
template<class A, class B>
std::function<optional<B>(optional<A>)> 
fmap(std::function<B(A)> f) 
{
    return [f](optional<A> opt) {
        if (!opt.isValid())
            return optional<B>{};
        else
            return optional<B>{ f(opt.val()) };
    };
}
----

이것은 함수를 인자로 받아 새로운 함수를 반환하는 고차 함수입니다. 아래는 커링하지 않은(uncurried) 버전입니다:

[source,cpp]
----
template<class A, class B>
optional<B> fmap(std::function<B(A)> f, optional<A> opt) {
    if (!opt.isValid())
        return optional<B>{};
    else
        return optional<B>{ f(opt.val()) };
}
----

``fmap``을 ``optional`` 멤버 함수로 구현하는 방법도 있을 겁니다. C++에서는 이처럼 구현 선택지가 너무 다양하다 보니, 함자 패턴을 일관되게 추상화하기가 참 어렵습니다. 함자를 인터페이스 상속으로 정의해야 할까요? (하지만 C++은 가상 함수 템플릿을 지원하지 않죠.) 아니면 커링되거나 언커링된 전역 템플릿 함수로 만들어야 할까요? 컴파일러가 타입 추론을 완벽하게 수행할 수 있을지도 걱정입니다. 가령 정수를 불리언으로 바꾸는 함수 stem:[f]가 있을 때, ``g``의 타입을 컴파일러가 제대로 알 수 있을까요?

[source,cpp]
----
auto g = fmap(f);
----

나중에 ``fmap``을 오버로딩하는 또 다른 함자들이 생기면 문제는 더 복잡해질 겁니다. (함자는 아주 많으니까요.)

=== 타입클래스

그렇다면 하스켈은 함자를 어떻게 추상화할까요? 바로 '타입클래스(Typeclass)'를 사용합니다. 타입클래스는 공통 인터페이스를 공유하는 타입들의 집합(family)을 정의합니다. 예를 들어, 값의 동등성 비교를 지원하는 ``Eq`` 타입클래스는 이렇게 정의됩니다:

[source,haskell]
----
class Eq a where
    (==) :: a -> a -> Bool
----

이 정의는 타입 stem:[a]가 동일한 타입의 인자 두 개를 받아 ``Bool``을 반환하는 ``(==)`` 연산자를 지원할 때 ``Eq`` 클래스의 일원이 될 수 있음을 뜻합니다. 어떤 타입을 ``Eq``로 만들고 싶다면, 해당 클래스의 '인스턴스(Instance)'로 선언하고 구체적인 ``(==)`` 구현을 제공하면 됩니다. 가령 두 개의 실수를 갖는 ``Point`` 타입을 정의했다면:

[source,haskell]
----
data Point = Pt Float Float
----

점의 동등성을 정의할 수 있습니다:

[source,haskell]
----
instance Eq Point where
    (Pt x y) == (Pt x' y') = x == x' && y == y'
----

두 패턴 ``(Pt x y)``와 ``(Pt x' y')`` 사이에 중위 연산자 ``(==)``를 배치하여 구현했습니다. 이제 ``Point``는 ``Eq``의 인스턴스가 되었고, 점끼리 직접 동등성 비교를 할 수 있게 되었습니다. C++나 자바와 달리 타입을 정의할 때 미리 인터페이스를 지정할 필요 없이, 나중에 필요할 때 인스턴스로 만들 수 있다는 게 하스켈의 장점입니다. 또한 타입클래스는 하스켈에서 함수(또는 연산자)를 오버로딩하는 유일한 수단이기도 합니다. 다양한 함자에 대해 ``fmap``을 오버로딩하려면 이 기능이 꼭 필요하죠. 그런데 한 가지 까다로운 점이 있습니다. 함자는 단순히 '타입'이 아니라 타입을 타입으로 보내는 '매핑(타입 생성자)'에 대해 정의된다는 것입니다. 즉, ``Eq``처럼 타입들의 집합이 아니라 '타입 생성자'들의 집합을 다루는 타입클래스가 필요합니다. 다행히 하스켈의 타입클래스는 타입 생성자와도 아주 잘 작동합니다. ``Functor`` 클래스의 정의를 보시죠:

[source,haskell]
----
class Functor f where
    fmap :: (a -> b) -> f a -> f b
----

이 정의는 시그니처에 맞는 ``fmap`` 함수가 정의되어 있다면 ``f``를 함자로 인정한다는 뜻입니다. 여기서 소문자 ``f``는 타입 변수입니다. 컴파일러는 ``f a``, ``f b``처럼 쓰인 것을 보고 ``f``가 단순한 타입이 아니라 타입 생성자임을 알아챕니다. 따라서 함자 인스턴스를 선언할 때는 ``Maybe``처럼 타입 생성자를 지정해 주면 됩니다:

[source,haskell]
----
instance Functor Maybe where
    fmap _ Nothing = Nothing
    fmap f (Just x) = Just (f x)
----

참고로 ``Functor`` 클래스는 하스켈 표준 라이브러리인 ``Prelude``에 포함되어 있으며, ``Maybe``를 비롯한 많은 데이터 타입들이 이미 함자로 정의되어 있습니다.

=== C++의 함자

C++에서도 같은 접근 방식을 시도해 볼 수 있을까요? 타입 생성자는 ``optional`` 같은 템플릿 클래스에 해당하므로, ``fmap``을 템플릿의 템플릿 매개변수(Template template parameter) ``F``로 매개변수화할 수 있을 겁니다. 그 구문은 다음과 같습니다:

[source,cpp]
----
template<template<class> F, class A, class B>
F<B> fmap(std::function<B(A)>, F<A>);
----

우리는 이 템플릿을 다양한 함자들에 대해 특수화(Specialization)하고 싶을 것입니다. 하지만 안타깝게도 C++에서는 템플릿 함수의 부분 특수화(Partial specialization)가 금지되어 있습니다. 즉, 다음과 같은 코드는 작성할 수 없습니다:

[source,cpp]
----
template<class A, class B>
optional<B> fmap<optional>(std::function<B(A)> f, optional<A> opt)
----

대신 함수 오버로딩에 의존해야 하는데, 이는 결국 처음에 보았던 언커링된 ``map`` 정의로 우리를 되돌려 놓습니다:

[source,cpp]
----
template<class A, class B>
optional<B> fmap(std::function<B(A)> f, optional<A> opt) 
{
    if (!opt.isValid())
        return optional<B>{};
    else
        return optional<B>{ f(opt.val()) };
}
----

이 정의는 작동하긴 하지만, ``fmap``의 두 번째 인자가 어떤 오버로딩을 쓸지 결정하는 구조입니다. 이는 더 일반적인 함자 정의를 통한 추상화와는 거리가 있습니다.

=== List 함자

함자가 프로그래밍에서 어떤 역할을 하는지 감을 잡기 위해 더 많은 예시를 들어보겠습니다. 다른 타입에 의해 매개변수화된 모든 타입은 함자의 후보입니다. 제네릭 컨테이너들은 보통 저장되는 요소의 타입에 의해 매개변수화되므로, 가장 단순한 컨테이너인 리스트를 살펴보죠:

[source,haskell]
----
data List a = Nil | Cons a (List a)
----

여기 ``List``라는 타입 생성자가 있습니다. 타입 stem:[a]를 ``List a``라는 타입으로 매핑하죠. ``List``가 함자임을 입증하려면 함수의 리프팅(Lifting)을 정의해야 합니다. 즉, 함수 stem:[a \to b]가 주어졌을 때 리스트 타입에 작용하는 함수 ``List a -> List b``를 만들어야 합니다:

[source,haskell]
----
fmap :: (a -> b) -> (List a -> List b)
----

``List a``에 작용하는 함수는 두 개의 리스트 생성자에 맞춰 정의해야 합니다. ``Nil`` 케이스는 자명합니다. 빈 리스트로는 할 수 있는 게 없으니 그냥 ``Nil``을 반환하면 됩니다. ``Cons`` 케이스는 재귀가 들어가서 조금 더 까다롭습니다. 우리가 하려는 일을 다시 정리해 보죠. stem:[a]의 리스트와 stem:[a]를 stem:[b]로 바꾸는 함수 stem:[f]가 있을 때, stem:[b]의 리스트를 새로 만들면 됩니다. 가장 확실한 방법은 stem:[f]를 리스트의 모든 요소에 적용해 stem:[a]들을 stem:[b]로 갈아끼우는 것입니다. (비어 있지 않은) 리스트가 머리(Head)와 꼬리(Tail)를 잇는 ``Cons``로 정의된다는 점을 이용하면, 머리에는 stem:[f]를 적용하고 꼬리에는 이미 리프트된(``fmap``된) stem:[f]를 재귀적으로 적용하면 됩니다:

[source,haskell]
----
fmap f (Cons x t) = Cons (f x) (fmap f t)
----

식의 오른쪽에 있는 ``fmap f``는 현재 다루는 리스트보다 짧은 리스트(꼬리)에 적용됩니다. 재귀가 거듭될수록 리스트는 짧아지고 결국 빈 리스트 ``Nil``에 도달할 것입니다. 앞서 정한 대로 ``Nil``에 대한 ``fmap f``는 ``Nil``을 반환하며 재귀를 끝내죠. 최종 결과는 ``Cons`` 생성자를 사용해 새로운 머리(``f x``)와 새로운 꼬리(``fmap f t``)를 다시 이어 붙여 만듭니다. 이를 종합하면 리스트 함자의 인스턴스 선언은 다음과 같습니다:

[source,haskell]
----
instance Functor List where
    fmap _ Nil = Nil
    fmap f (Cons x t) = Cons (f x) (fmap f t)
----

C++에 익숙하신 분이라면 가장 대표적인 컨테이너인 ``std\::vector``를 떠올려 보세요. ``std\::vector``에 대한 ``fmap``은 ``std\::transform``을 얇게 감싸는 것만으로도 구현할 수 있습니다:

[source,cpp]
----
template<class A, class B>
std::vector<B> fmap(std::function<B(A)> f, std::vector<A> v)
{
    std::vector<B> w;
    std::transform( std::begin(v)
                  , std::end(v)
                  , std::back_inserter(w)
                  , f);
    return w;
}
----

예를 들어 숫자 시퀀스를 제곱하는 데 쓸 수도 있죠:

[source,cpp]
----
std::vector<int> v{ 1, 2, 3, 4 };
auto w = fmap([](int i) { return i*i; }, v);
std::copy( std::begin(w)
         , std::end(w)
         , std::ostream_iterator(std::cout, ", "));
----

대부분의 C++ 컨테이너는 ``std\::transform``에 넘길 수 있는 이터레이터(Iterator)를 지원하므로 함자라고 볼 수 있습니다. ``std\::transform``은 ``fmap``의 조금 더 투박한 사촌인 셈이죠. 다만 안타깝게도 함자의 단순함이 C++ 특유의 이터레이터와 임시 객체들의 복잡함 속에 묻혀버리곤 합니다(위의 ``fmap`` 구현만 봐도 알 수 있죠). 다행히 새로운 ``Ranges`` 라이브러리가 도입되면서 C++에서도 카테고리의 함자적 특성이 훨씬 더 뚜렷하게 드러나기 시작했습니다.

=== Reader 함자

"함자는 일종의 컨테이너"라는 직관이 생겼을 텐데, 이번에는 전혀 다른 예시를 보여드리겠습니다. 타입 stem:[a]를 "stem:[a]를 반환하는 함수 타입"으로 매핑하는 경우를 생각해 봅시다. 아직 함수 타입에 대해 깊이 있게 다루지는 않았습니다. 엄밀한 카테고리 이론적 설명은 나중에 하겠지만, 프로그래머로서의 감각으로 이미 알고 계신 부분이 있을 겁니다. 하스켈에서 함수 타입은 인자 타입과 결과 타입을 인자로 받는 화살표 타입 생성자 ``(->)``를 사용해 만듭니다. 중위(Infix) 형태로 ``a -> b``라고 쓰는 걸 이미 보셨을 텐데, 괄호를 치면 접두(Prefix) 형태로도 쓸 수 있습니다:

[source,haskell]
----
(->) a b
----

일반 함수처럼 타입 함수도 인자를 하나만 먼저 넘기는 '부분 적용'이 가능합니다. 화살표에 인자 하나만 주면 아직 채워지지 않은 나머지 하나를 기다리는 상태가 되죠. 그래서:

[source,haskell]
----
(->) a
----

이것 또한 하나의 '타입 생성자'입니다. 완성된 타입인 ``a -> b``가 되려면 타입 하나가 더 필요하죠. 현재로서는 stem:[r]로 고정된 타입 생성자들의 집합을 정의하고 있습니다. 이것이 함자가 될 수 있는지 확인해 봅시다. 인자 두 개를 다루는 게 헷갈릴 수 있으니 이름을 정리하죠. 인자 타입을 stem:[r], 결과 타입을 stem:[a]라고 하겠습니다. 이제 우리 타입 생성자는 타입 stem:[a]를 받아 타입 stem:[r \to a]로 보냅니다. 함수 stem:[a \to b]를 받아 stem:[r \to a]에서 stem:[r \to b]로 가는 함수로 '리프트'할 수 있어야 함자가 됩니다. 이 시그니처를 ``fmap``에 적용해 보면 다음과 같습니다:

[source,haskell]
----
fmap :: (a -> b) -> (r -> a) -> (r -> b)
----

작은 퍼즐을 풀어봅시다. 함수 stem:[f: a \to b]와 stem:[g: r \to a]가 있을 때 stem:[r \to b] 타입의 함수를 어떻게 만들 수 있을까요? 두 함수를 합성(Composition)하는 것 말고는 다른 방법이 없죠. 바로 그 합성이 우리가 원하는 결과입니다. 따라서 ``fmap`` 구현은 다음과 같습니다:

[source,haskell]
----
instance Functor ((->) r) where
    fmap f g = f . g
----

정말 간단하죠! 더 간결한 표기법을 원하신다면 합성을 접두(Prefix) 형태로 써서 이렇게 줄일 수도 있습니다:

[source,haskell]
----
fmap f g = (.) f g
----

인자들을 생략하면 함수끼리 완전히 같다는 것을 더 명확히 볼 수 있습니다:

[source,haskell]
----
fmap = (.)
----

타입 생성자 ``(->) r``과 위 ``fmap`` 구현의 조합을 *리더 함자(Reader Functor)*라고 부릅니다.

== 컨테이너로서의 함자

지금까지 범용 컨테이너를 정의하거나, 최소한 매개변수화된 타입의 값을 포함하는 객체로서의 함자 예시들을 살펴보았습니다. 리더 함자는 함수를 데이터로 생각하지 않는 우리 관습 때문에 조금 예외처럼 느껴질 수 있습니다. 하지만 순수 함수는 메모이제이션할 수 있고, 함수 실행을 테이블 검색으로 대체할 수 있다는 점을 기억하세요. 테이블은 곧 데이터입니다. 반대로 하스켈의 지연 평가(Laziness) 덕분에 리스트와 같은 전형적인 컨테이너도 실제로는 함수처럼 구현될 수 있습니다. 예를 들어 자연수의 무한 리스트는 다음과 같이 간결하게 정의됩니다:

[source,haskell]
----
nats :: [Integer]
nats = [1..]
----

첫 번째 줄의 대괄호 ``[]``는 리스트를 위한 하스켈 내장 타입 생성자이고, 두 번째 줄의 대괄호는 리스트 리터럴을 만드는 데 사용되었습니다. 당연하게도 이런 무한한 리스트를 메모리에 전부 담아둘 수는 없습니다. 컴파일러는 이를 필요할 때마다 정수를 생성하는 함수로 구현합니다. 이처럼 하스켈에서는 데이터와 코드의 경계가 모호합니다. 리스트는 함수가 될 수 있고, 함수는 인자와 결과를 매핑하는 테이블로 볼 수 있습니다. 물론 ``strlen`` 같은 함수를 테이블로 만드는 건 문자열이 무한히 많으니 불가능하겠지만요. 프로그래머는 무한을 꺼리지만, 카테고리 이론에서는 무한을 일상처럼 다룹니다. 모든 문자열의 집합이든, 우주의 과거·현재·미래에 걸친 가능한 모든 상태의 집합이든 무엇이든 다룰 수 있습니다! 그래서 저는 (자기 함자에 의해 생성된 타입의 객체인) 함자 객체를, 비록 물리적으로 존재하지 않더라도 해당 타입의 값을 '포함'하고 있는 무언가로 생각하는 것을 좋아합니다. C++의 ``std\::future``가 좋은 예입니다. 이 객체는 지금 당장은 아니더라도 어느 시점에 값을 포함하게 될 것이며, 접근하려 하면 값이 준비될 때까지 기다려야 할 수도 있습니다. 하스켈의 ``IO`` 객체도 마찬가지입니다. 사용자 입력이나 화면에 "Hello World!"가 출력된 우리 우주의 미래 모습을 담고 있다고 볼 수 있습니다. 이 해석에 따르면 함자 객체는 어떤 값을 담고 있거나 그 값을 만들어낼 레시피를 가진 그 무엇입니다. 우리가 실제 그 값에 접근할 수 있는지 여부는 중요한 게 아닙니다. 그것은 선택 사항이며 함자의 관심사 밖입니다. 우리가 관심 있는 것은 오직 그 값을 함수를 통해 조작할 수 있느냐는 것입니다. 값을 꺼낼 수 있다면 조작 결과를 확인하면 되고, 꺼낼 수 없다면 조작이 올바르게 합성되는지와 항등 함수를 썼을 때 아무 일도 일어나지 않는지만 보장하면 됩니다. 함자 객체 속의 값에 얼마나 무관심할 수 있는지 보여주는 극단적인 예로, 타입 인자 stem:[a]를 완전히 무시해버리는 타입 생성자가 있습니다:

[source,haskell]
----
data Const c a = Const c
----

``Const`` 타입 생성자는 두 개의 타입 stem:[c]와 stem:[a]를 받습니다. 화살표 생성자처럼 하나만 먼저 적용하여 함자를 만들 수 있습니다. 데이터 생성자(이름도 똑같이 ``Const``입니다)는 stem:[c] 타입의 값 하나만 가집니다. stem:[a]에 대해서는 아무것도 알 필요가 없죠. 이 타입 생성자에 대한 ``fmap`` 시그니처는 다음과 같습니다:

[source,haskell]
----
fmap :: (a -> b) -> Const c a -> Const c b
----

함자가 타입 인자를 무시하므로 ``fmap`` 구현도 함수 인자를 무시합니다. 적용할 대상이 없기 때문입니다:

[source,haskell]
----
instance Functor (Const c) where
    fmap _ (Const v) = Const v
----

C++에서는 이 상황이 조금 더 명확하게 보입니다. C++은 컴파일 타임의 타입과 런타임의 값이 엄격하게 구분되기 때문입니다:

[source,cpp]
----
template<class C, class A>
struct Const {
    Const(C v) : _v(v) {}
    C _v;
};
----

``fmap`` 구현 역시 함수 인자를 무시하고, 단순히 ``Const`` 값을 타입만 바꿔서 다시 돌려줍니다:

[source,cpp]
----
template<class C, class A, class B>
Const<C, B> fmap(std::function<B(A)> f, Const<C, A> c) {
    return Const<C, B>{c._v};
}
----

조금 이상해 보일 수 있지만, ``Const`` 함자는 여러 구조에서 아주 중요한 역할을 수행합니다. 카테고리 이론에서 이는 앞서 언급한 stem:[\Delta_c] 함자의 특수한 사례인 자기 함자 버전이며, 앞으로 자주 보게 될 것입니다.

== 함자 합성 (Functor Composition)

카테고리 간의 함자가 집합 간의 함수처럼 합성된다는 사실을 이해하는 건 어렵지 않습니다. 두 함자의 합성은 단순히 객체 매핑의 합성이자 모피즘 매핑의 합성일 뿐입니다. 함자 합성을 거쳐도 항등 모피즘은 항등 모피즘으로 남고, 모피즘의 합성은 합성으로 유지됩니다. 특별할 것 없는 자연스러운 성질이죠. 특히 자기 함자끼리의 합성은 더욱 쉽습니다. 앞서 보았던 ``maybeTail`` 함수를 하스켈 표준 리스트를 써서 다시 써보겠습니다:

[source,haskell]
----
maybeTail :: [a] -> Maybe [a]
maybeTail [] = Nothing
maybeTail (x:xs) = Just xs
----

(하스켈에서 빈 리스트 생성자는 ``[]``이고, ``Cons`` 연산자는 중위 연산자인 콜론 ``:``입니다.) ``maybeTail``의 결과 타입은 ``Maybe``와 ``[]``(리스트)라는 두 함자가 stem:[a]에 작용하여 합성된 타입입니다. 각 함자는 자신만의 ``fmap``을 가지고 있는데, 만약 합성된 구조인 ``Maybe list`` 안의 값에 함수 stem:[f]를 적용하려면 어떻게 해야 할까요? 두 겹의 함자 껍질을 뚫고 들어가야 합니다. 바깥쪽 ``Maybe``를 뚫기 위해 ``fmap``을 쓰되, 그 안의 리스트에 작용할 수 있도록 ``(fmap f)``를 다시 넘겨줘야 합니다. 예를 들어 정수 시퀀스가 들어있는 ``Maybe`` 리스트의 요소를 제곱하는 코드를 보시죠:

[source,haskell]
----
square x = x * x

mis :: Maybe [Int]
mis = Just [1, 2, 3]

mis2 = fmap (fmap square) mis
----

컴파일러는 타입을 분석해 바깥쪽 ``fmap``에는 ``Maybe`` 인스턴스의 구현을, 안쪽 ``fmap``에는 리스트 함자의 구현을 찾아 적용할 것입니다. 위 코드가 아래처럼 더 간결하게 써질 수 있다는 사실이 처음엔 낯설 수도 있습니다:

[source,haskell]
----
mis2 = (fmap . fmap) square mis
----

하지만 ``fmap``을 인자 하나만 받는 함수로 생각하면 금방 이해될 것입니다:

[source,haskell]
----
fmap :: (a -> b) -> (f a -> f b)
----

여기서 ``(fmap . fmap)``의 뒤쪽 ``fmap``은 다음 함수를 인자로 받습니다:

[source,haskell]
----
square :: Int -> Int
----

그러면 다음 타입의 함수를 반환하죠:

[source,haskell]
----
[Int] -> [Int]
----

첫 번째 ``fmap``은 이 함수를 다시 받아 최종적으로 다음 함수를 내놓습니다:

[source,haskell]
----
Maybe [Int] -> Maybe [Int]
----

마지막으로 이 함수가 ``mis``에 적용되는 것이죠. 결론적으로 두 함자의 합성은 각 함자의 ``fmap``을 합성한 새로운 ``fmap``을 가진 함자가 됩니다. 카테고리 이론의 관점에서 보면 함자의 합성은 결합 법칙을 만족하며(객체 매핑과 모피즘 매핑 모두 결합적입니다), 모든 카테고리에는 자기 자신을 그대로 유지하는 항등 함자(Identity Functor)가 존재합니다. 따라서 함자들은 어떤 카테고리의 '모피즘' 역할을 할 수 있습니다. 그렇다면 이 카테고리의 객체는 무엇일까요? 바로 카테고리들입니다. 카테고리가 객체가 되고 함자가 모피즘이 되는 '카테고리들의 카테고리'인 셈이죠. 물론 "모든 집합의 집합"에서 겪었던 역설을 피하기 위해 조심해야 합니다. 그래서 우리는 '작은 카테고리(Small categories)'들을 객체로 갖는 카테고리 ``Cat``을 정의합니다. (카테고리 이론에서는 셀 수 없을 만큼 큰 무한 집합조차 '작다'고 치부하곤 합니다.) 이런 추상화의 층위마다 비슷한 구조가 반복되는 모습이 참 놀랍지 않나요? 나중에 알게 되겠지만, 함자들끼리도 카테고리를 형성할 수 있습니다.
