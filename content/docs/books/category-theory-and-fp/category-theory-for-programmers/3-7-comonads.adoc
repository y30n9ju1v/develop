'''
이제 모나드에 대해 충분히 다루었으므로, 화살표를 뒤집어 반대 카테고리에서 작업하는 쌍대성(duality)의 이점을 누릴 수 있습니다. 이를 통해 '코모나드(comonad)'를 공짜로 얻을 수 있죠.

가장 기본적인 수준에서 모나드가 클라이슬리 화살표(Kleisli arrow)를 합성하는 것에 관한 것임을 기억해 봅시다.

[source,haskell]
----
a -> m b
----

여기서 ``m``은 모나드인 함자(functor)입니다. 코모나드에 대해서는 ``m``을 거꾸로 뒤집은 글자인 ``w``를 사용하겠습니다. 그러면 다음과 같은 타입의 모피즘(morphism)을 '코클라이슬리 화살표(co-Kleisli arrow)'로 정의할 수 있습니다.

[source,haskell]
----
w a -> b
----

코클라이슬리 화살표에 대응하는 피쉬 연산자(fish operator)는 다음과 같이 정의됩니다.

[source,haskell]
----
(=>=) :: (w a -> b) -> (w b -> c) -> (w a -> c)
----

코클라이슬리 화살표가 카테고리를 형성하려면 항등 코클라이슬리 화살표인 ``extract``가 있어야 합니다.

[source,haskell]
----
extract :: w a -> a
----

이는 모나드의 ``return``에 대응하는 쌍대 개념입니다. 또한 결합 법칙(associativity)과 좌우 항등 법칙(identity)도 만족해야 합니다. 이 모든 것을 종합하면 하스켈에서 코모나드를 다음과 같이 정의할 수 있습니다.

[source,haskell]
----
class Functor w => Comonad w where
    (=>=) :: (w a -> b) -> (w b -> c) -> (w a -> c)
    extract :: w a -> a
----

실제로는 잠시 후에 보겠지만 약간 다른 기본 프리미티브(primitive)를 사용합니다.

그렇다면 프로그래밍에서 코모나드는 어디에 쓰일까요?

== 코모나드를 사용한 프로그래밍

모나드와 코모나드를 비교해 봅시다. 모나드는 ``return``을 사용하여 값을 컨테이너에 넣는 방법을 제공합니다. 하지만 컨테이너 안에 저장된 값에 직접 접근하는 방법은 제공하지 않습니다. 물론 모나드를 구현하는 특정 데이터 구조가 내용물에 접근하는 수단을 제공할 수도 있지만, 이는 부가적인 기능으로 간주됩니다. 즉, 모나드에서 값을 추출하기 위한 공통 인터페이스는 존재하지 않습니다. 우리가 살펴본 ``IO`` 모나드처럼 내용물을 절대 노출하지 않는 것을 자랑으로 여기는 경우도 있죠.

반면 코모나드는 컨테이너에서 단일 값을 추출하는 수단을 제공합니다. 대신 값을 삽입하는 수단은 제공하지 않습니다. 따라서 코모나드를 컨테이너로 생각한다면, 그 컨테이너는 항상 내용물로 가득 차 있으며 우리는 그 내부를 들여다볼 수만 있는 셈입니다.

클라이슬리 화살표가 값을 받아 컨텍스트(context)가 추가된 '장식된 결과'를 내놓는 것처럼, 코클라이슬리 화살표는 값과 '전체 컨텍스트'를 함께 받아 결과를 생성합니다. 즉, 코모나드는 *컨텍스트 내 계산(contextual computation)*을 구체화한 것입니다.

== 곱 코모나드(Product Comonad)

리더 모나드(reader monad)를 기억하시나요? 우리는 어떤 읽기 전용 환경 ``e``에 접근해야 하는 계산을 구현하기 위해 리더 모나드를 도입했습니다. 이러한 계산은 다음과 같은 형태의 순수 함수로 표현할 수 있습니다.

[source,haskell]
----
(a, e) -> b
----

우리는 커링(currying)을 사용하여 이를 클라이슬리 화살표로 변환했습니다.

[source,haskell]
----
a -> (e -> b)
----

하지만 이 함수들은 이미 코클라이슬리 화살표의 형태를 띠고 있다는 점에 주목해 봅시다. 인자들을 더 편리한 함자 형태로 다듬어 보겠습니다.

[source,haskell]
----
data Product e a = Prod e a
  deriving Functor
----

합성하려는 화살표들이 동일한 환경을 공유하게 함으로써 합성 연산자를 쉽게 정의할 수 있습니다.

[source,haskell]
----
(=>=) :: (Product e a -> b) -> (Product e b -> c) -> (Product e a -> c)
f =>= g = \(Prod e a) -> let b = f (Prod e a)
                          c = g (Prod e b)
                       in c
----

``extract``의 구현은 단순히 환경을 무시합니다.

[source,haskell]
----
extract (Prod e a) = a
----

놀랍지 않게도, 곱 코모나드는 리더 모나드와 정확히 동일한 계산을 수행하는 데 사용될 수 있습니다. 어떤 면에서는 환경을 다루기에 코모나드 방식의 구현이 "컨텍스트 내 계산"이라는 정신에 더 잘 부합하므로 더 자연스럽습니다. 반면 모나드는 ``do`` 표기법이라는 편리한 구문 설탕(syntactic sugar)을 제공한다는 장점이 있습니다.

리더 모나드와 곱 코모나드 사이의 연결은 더 깊은 의미가 있습니다. 리더 함자가 곱 함자의 *우수반(right adjoint)*이라는 사실과 관련이 있죠. 하지만 일반적으로 코모나드는 모나드와는 다른 계산 개념들을 다룹니다. 이에 대해서는 나중에 더 많은 예를 보겠습니다.

``Product`` 코모나드는 튜플이나 레코드를 포함한 임의의 곱 타입(product type)으로 쉽게 일반화할 수 있습니다.

== 합성 해부하기

쌍대화 과정을 계속 진행하여 모나드의 ``bind``와 ``join``을 쌍대화할 수도 있습니다. 혹은 모나드에서 그랬던 것처럼 피쉬 연산자의 해부를 통해 그 구조를 연구할 수도 있습니다. 후자의 접근 방식이 더 통찰력을 줄 것입니다.

시작점은 합성 연산자가 ``w a``를 받아 ``c``를 반환하는 코클라이슬리 화살표를 만들어야 한다는 사실입니다. ``c``를 만드는 유일한 방법은 두 번째 함수 ``g``를 ``w b`` 타입의 인자에 적용하는 것뿐입니다.

[source,haskell]
----
(=>=) :: (w a -> b) -> (w b -> c) -> (w a -> c)
f =>= g = g ...
----

하지만 ``g``에게 전달할 ``w b`` 타입의 값은 어떻게 만들 수 있을까요? 우리에게 주어진 것은 ``w a`` 타입의 인자와 ``f \:: w a -> b``라는 함수입니다. 해결책은 ``bind``의 쌍대인 ``extend``를 정의하는 것입니다.

[source,haskell]
----
extend :: (w a -> b) -> w a -> w b
----

``extend``를 사용하면 합성을 다음과 같이 구현할 수 있습니다.

[source,haskell]
----
f =>= g = g . extend f
----

다음으로 ``extend``를 더 해부해 볼까요? 함수 ``w a -> b``를 인수 ``w a``에 바로 적용하고 싶겠지만, 그렇게 해서 얻은 ``b``를 ``w b``로 변환할 방법이 없다는 것을 금방 깨닫게 될 것입니다. 코모나드는 값을 들어 올리는(lifting) 수단을 제공하지 않는다는 점을 기억하세요. 모나드의 경우 이 시점에서 ``fmap``을 사용했습니다. 여기서 ``fmap``을 사용하려면 우리에게 ``w (w a)`` 타입의 무언가가 있어야 합니다. ``w a``를 ``w (w a)``로 바꿀 수만 있다면 되는 것이죠. 그리고 편리하게도 이것은 정확히 ``join``의 쌍대 개념입니다. 우리는 이를 ``duplicate``라고 부릅니다.

[source,haskell]
----
duplicate :: w a -> w (w a)
----

따라서 모나드와 마찬가지로 코모나드도 코클라이슬리 화살표, ``extend``, ``duplicate``를 사용하는 세 가지 동등한 정의를 가집니다. 다음은 ``Control.Comonad`` 라이브러리에서 가져온 하스켈 정의입니다.

[source,haskell]
----
class Functor w => Comonad w where
  extract :: w a -> a
  duplicate :: w a -> w (w a)
  duplicate = extend id
  extend :: (w a -> b) -> w a -> w b
  extend f = fmap f . duplicate
----

``extend``를 ``duplicate``로, 또는 그 반대로 정의하는 기본 구현이 제공되어 있으므로 실제로는 둘 중 하나만 재정의하면 됩니다.

이 함수들에 대한 직관은 일반적으로 코모나드를 타입 ``a``의 값들로 가득 찬 컨테이너로 생각하는 데서 나옵니다(곱 코모나드는 값이 하나뿐인 특별한 경우였습니다). ``extract``를 통해 쉽게 접근할 수 있는 "현재(current)" 값이라는 개념이 있습니다. 코클라이슬리 화살표는 현재 값에 초점을 맞춰 계산을 수행하지만, 주변의 모든 값에도 접근할 수 있습니다. 콘웨이의 생명 게임(Conway's Game of Life)을 예로 들어 봅시다. 각 셀은 값(보통 ``True`` 또는 ``False``)을 담고 있습니다. 생명 게임에 대응하는 코모나드는 "현재" 셀에 초점이 맞춰진 셀들의 격자(grid)가 될 것입니다.

그렇다면 ``duplicate``는 무엇을 할까요? ``duplicate``는 코모나드 컨테이너 ``w a``를 받아 컨테이너의 컨테이너인 ``w (w a)``를 만듭니다. 여기서 각 내부 컨테이너는 원래 ``w a`` 안에 있는 서로 다른 ``a``들을 각각의 초점으로 가집니다. 생명 게임에서는 격자의 격자가 만들어지는데, 외부 격자의 각 셀은 서로 다른 셀에 초점이 맞춰진 내부 격자를 포함하게 됩니다.

이제 ``extend``를 살펴봅시다. ``extend``는 코클라이슬리 화살표와 ``a``들로 가득 찬 코모나드 컨테이너 ``w a``를 받습니다. 그리고 이 모든 ``a``에 계산을 적용하여 ``b``들로 바꿉니다. 결과는 ``b``로 가득 찬 코모나드 컨테이너입니다. ``extend``는 초점을 하나의 ``a``에서 다른 ``a``로 옮겨가며 각각에 코클라이슬리 화살표를 차례로 적용합니다. 생명 게임에서 코클라이슬리 화살표는 현재 셀의 새로운 상태를 계산할 것입니다. 이를 위해 컨텍스트, 즉 아마도 가장 가까운 이웃 셀들을 살펴보겠죠. ``extend``의 기본 구현이 이 과정을 잘 보여줍니다. 먼저 ``duplicate``를 호출하여 가능한 모든 초점들을 생성한 뒤, 각각에 ``f``를 적용하는 것입니다.

== 스트림 코모나드(Stream Comonad)

컨테이너의 한 요소에서 다른 요소로 초점을 이동하는 이 과정은 무한 스트림(infinite stream) 예제에서 가장 잘 드러납니다. 스트림은 리스트와 비슷하지만, 비어 있는 상태(empty constructor)가 없습니다.

[source,haskell]
----
data Stream a = Cons a (Stream a)
----

이는 자명하게 함자(Functor)입니다.

[source,haskell]
----
instance Functor Stream where
    fmap f (Cons a as) = Cons (f a) (fmap f as)
----

스트림의 초점은 첫 번째 요소이므로, ``extract``는 다음과 같이 구현됩니다.

[source,haskell]
----
extract (Cons a _) = a
----

``duplicate``는 스트림의 스트림을 생성하며, 각 내부 스트림은 서로 다른 요소를 초점으로 가집니다.

[source,haskell]
----
duplicate (Cons a as) = Cons (Cons a as) (duplicate as)
----

첫 번째 요소는 원래 스트림이고, 두 번째 요소는 원래 스트림의 꼬리(tail), 세 번째 요소는 그 꼬리의 꼬리... 이런 식으로 무한히 이어집니다.

완성된 인스턴스는 다음과 같습니다.

[source,haskell]
----
instance Comonad Stream where
    extract (Cons a _) = a
    duplicate (Cons a as) = Cons (Cons a as) (duplicate as)
----

이는 스트림을 바라보는 매우 함수적인 방식입니다. 명령형 언어라면 아마도 스트림을 한 위치씩 이동시키는 ``advance`` 메서드부터 시작했을 것입니다. 하지만 여기서는 ``duplicate``가 이동된 모든 스트림을 단번에(in one fell swoop) 만들어냅니다. 하스켈의 지연 평가 덕분에 이런 방식이 가능할 뿐만 아니라 바람직하기까지 합니다. 물론 ``Stream``을 실용적으로 쓰기 위해 다음과 같이 ``advance``에 대응하는 함수를 구현할 수도 있습니다.

[source,haskell]
----
tail :: Stream a -> Stream a
tail (Cons a as) = as
----

하지만 이는 코모나드 인터페이스의 필수 요소는 아닙니다.

디지털 신호 처리 경험이 있다면, 스트림에 대한 코클라이슬리 화살표가 곧 디지털 필터이고 ``extend``는 필터링된 스트림을 생성한다는 것을 즉시 알아챌 수 있을 것입니다.

간단한 예로 이동 평균(moving average) 필터를 구현해 보겠습니다. 다음은 스트림의 ``n``개 요소를 합하는 함수입니다.

[source,haskell]
----
sumS :: Num a => Int -> Stream a -> a
sumS n (Cons a as) = if n <= 0 then 0 else a + sumS (n - 1) as
----

이제 스트림 앞부분 ``n``개 요소의 평균을 구하는 함수를 만듭니다.

[source,haskell]
----
average :: Fractional a => Int -> Stream a -> a
average n stm = (sumS n stm) / (fromIntegral n)
----

부분 적용된 ``average n``은 코클라이슬리 화살표이므로, 이를 전체 스트림에 대해 확장(``extend``)할 수 있습니다.

[source,haskell]
----
movingAvg :: Fractional a => Int -> Stream a -> Stream a
movingAvg n = extend (average n)
----

그 결과로 이동 평균들이 담긴 스트림을 얻게 됩니다.

스트림은 단방향 1차원 코모나드의 예시입니다. 이를 양방향으로 만들거나 2차원 이상의 다차원으로 확장하는 것도 어렵지 않습니다.

== 카테고리적 코모나드(Comonad Categorically)

카테고리 이론에서 코모나드를 정의하는 것은 쌍대성을 활용한 간단한 연습입니다. 모나드와 마찬가지로 자기함자(endofunctor) ``T``로부터 시작합니다. 모나드를 정의하는 두 자연 변환 ``η``와 ``μ``는 코모나드에서 단순히 방향이 뒤집힙니다.

[source,haskell]
----
ε :: T -> I
δ :: T -> T2
----

이들 변환의 성분(component)이 ``extract``와 ``duplicate``에 대응합니다. 코모나드 법칙은 모나드 법칙의 거울상입니다. 별로 놀라운 일은 아니죠.

수반(adjunction)으로부터 모나드를 도출하는 과정도 있었습니다. 쌍대성은 수반을 뒤집습니다. 좌수반(left adjoint)은 우수반(right adjoint)이 되고, 그 역도 성립합니다. 합성 ``R ∘ L``이 모나드를 정의했으므로, ``L ∘ R``은 코모나드를 정의해야 합니다. 수반의 코단위(counit)는

[source]
----
ε :: L ∘ R -> I
----

인데, 실제로 코모나드 정의에서 보았던 바로 그 ``ε``이며, 성분으로는 하스켈의 ``extract``입니다. 수반의 단위(unit)를 사용할 수도 있습니다.

[source]
----
η :: I -> R ∘ L
----

이를 ``L ∘ R``의 중간에 삽입하여 ``L ∘ R ∘ L ∘ R``을 만들 수 있습니다. ``T``로부터 ``T²``을 만드는 것이 ``δ``를 정의하며, 이로써 코모나드의 정의가 완성됩니다.

우리는 또한 모나드가 모노이드임을 보았습니다. 이 명제의 쌍대는 *코모노이드(comonoid)*를 필요로 합니다. 그렇다면 코모노이드란 무엇일까요? 단일 객체 카테고리로서의 모노이드 원래 정의는 흥미로운 쌍대를 만들어내지 않습니다. 모든 자기 모피즘(endomorphism)의 방향을 뒤집으면 또 다른 모노이드를 얻을 뿐입니다. 하지만 모나드를 다룰 때 우리는 모노이드 카테고리(monoidal category)에서의 객체로서 더 일반적인 모노이드 정의를 사용했습니다. 그 구성은 다음 두 모피즘에 기반했죠.

[source,haskell]
----
μ :: m ⊗ m -> m
η :: i -> m
----

이 모피즘들의 방향을 뒤집으면 모노이드 카테고리 내의 코모노이드가 됩니다.

[source,haskell]
----
δ :: m -> m ⊗ m
ε :: m -> i
----

하스켈로 코모노이드 정의를 작성해 볼 수 있습니다.

[source,haskell]
----
class Comonoid m where
  split   :: m -> (m, m)
  destroy :: m -> ()
----

하지만 이는 상당히 자명합니다. 분명히 ``destroy``는 인자를 무시하고,

[source,haskell]
----
destroy _ = ()
----

``split``은 단지 두 함수의 쌍일 뿐입니다.

[source,haskell]
----
split x = (f x, g x)
----

이제 모노이드의 단위 법칙(unit law)에 대응하는 코모노이드 법칙을 살펴봅시다.

[source,haskell]
----
lambda . bimap destroy id . split = id
rho . bimap id destroy . split = id
----

여기서 ``lambda``와 ``rho``는 각각 좌측 및 우측 단위자(unitor)입니다(모노이드 카테고리의 정의를 참고하세요). 정의를 대입하면 다음과 같습니다.

[source,haskell]
----
lambda (bimap destroy id (split x))
= lambda (bimap destroy id (f x, g x))
= lambda ((), g x)
= g x
----

따라서 ``g = id``임이 증명됩니다. 마찬가지로 두 번째 법칙을 통해 ``f = id``임도 알 수 있습니다. 결론적으로,

[source,haskell]
----
split x = (x, x)
----

가 되며, 이는 하스켈에서(그리고 일반적으로 카테고리 ``Set``에서) 모든 객체가 자명한 코모노이드임을 보여줍니다.

다행히 코모노이드를 정의할 수 있는 훨씬 더 흥미로운 모노이드 카테고리들이 있습니다. 그중 하나가 바로 자기함자들의 카테고리입니다. 그리고 모나드가 자기함자 카테고리의 모노이드인 것처럼,

*코모나드는 자기함자 카테고리의 코모노이드입니다.*

== 스토어 코모나드(Store Comonad)

코모나드의 또 다른 중요한 예시는 상태 모나드(state monad)의 쌍대인 *코스테이트 코모나드(costate comonad)*입니다. 흔히 *스토어 코모나드(store comonad)*라고도 부릅니다.

상태 모나드는 지수(exponential)를 정의하는 수반에 의해 생성된다는 것을 이전에 보았습니다.

[source,haskell]
----
L z = z × s
R a = s ⇒ a
----

동일한 수반을 사용하여 스토어 코모나드를 정의해 봅시다. 코모나드는 합성 ``L ∘ R``로 정의됩니다.

[source,haskell]
----
L (R a) = (s ⇒ a) × s
----

이를 하스켈로 옮기면, 왼쪽의 Product 함자와 오른쪽의 Reader 함자 사이의 수반에서 시작합니다. Product를 Reader 뒤에 합성하면 다음 정의와 동등합니다.

[source,haskell]
----
data Store s a = Store (s -> a) s
----

객체 ``a``에서의 수반의 코단위는 다음과 같은 모피즘입니다.

[source,haskell]
----
εa :: ((s ⇒ a) × s) -> a
----

하스켈 표기법으로는 다음과 같습니다.

[source,haskell]
----
counit (Prod (Reader f) s) = f s
----

이것이 바로 우리의 ``extract``가 됩니다.

[source,haskell]
----
extract (Store f s) = f s
----

수반의 단위는 다음과 같습니다.

[source,haskell]
----
unit :: a -> Reader s (Product a s)
unit a = Reader (\s -> Prod a s)
----

이제 ``δ`` 즉 ``duplicate``를 수평 합성(horizontal composition)으로 구성해 봅시다.

[source,haskell]
----
δ :: L ∘ R -> L ∘ R ∘ L ∘ R
δ = L ∘ η ∘ R
----

``η``를 가장 왼쪽의 ``L``, 즉 Product 함자를 통해 밀어넣어야 합니다. 이는 쌍의 왼쪽 성분에 ``η``(또는 ``Store f``)를 작용시키는 것을 의미합니다(Product에 대한 ``fmap``이 하는 일이죠). 그 결과는 다음과 같습니다.

[source,haskell]
----
duplicate (Store f s) = Store (Store f) s
----

(``δ`` 공식에서 ``L``과 ``R``은 성분이 항등 모피즘인 항등 자연 변환을 나타낸다는 점을 기억하세요.)

전체 ``Store`` 코모나드 정의는 다음과 같습니다.

[source,haskell]
----
instance Comonad (Store s) where
  extract (Store f s) = f s
  duplicate (Store f s) = Store (Store f) s
----

Store의 Reader 부분을 타입 ``s``의 원소들로 키가 지정된(keyed) ``a``들의 일반화된 컨테이너로 생각할 수 있습니다. 예를 들어 ``s``가 ``Int``라면, ``Reader Int a``는 무한 양방향 ``a`` 스트림입니다. Store는 이 컨테이너를 키 타입의 값과 짝지어줍니다. 예를 들어 ``Reader Int a``가 ``Int``와 짝지어진 경우, ``extract``는 이 정수를 사용해 무한 스트림으로 인덱싱합니다. Store의 두 번째 성분을 현재 위치로 생각할 수 있습니다.

이 예를 계속하면, ``duplicate``는 ``Int``로 인덱싱된 새로운 무한 스트림을 생성합니다. 이 스트림은 스트림들을 원소로 담고 있습니다. 특히 현재 위치에는 원래의 스트림이 담겨 있습니다. 하지만 다른 ``Int``(양수든 음수든)를 키로 사용하면, 그 새로운 인덱스로 위치가 이동된(positioned) 스트림을 얻게 됩니다.

일반적으로, 중복된 Store에 extract를 적용하면 원래의 Store가 나온다는 것을 스스로 확인할 수 있습니다(실제로 코모나드의 항등 법칙 ``extract . duplicate = id``가 이를 명시합니다).

Store 코모나드는 Lens 라이브러리의 이론적 기반으로서 중요한 역할을 합니다. 개념적으로 ``Store s a`` 코모나드는 타입 ``s``를 인덱스로 사용하여 데이터 타입 ``a``의 특정 하위 구조에 (렌즈처럼) "초점을 맞추는(focusing)" 아이디어를 캡슐화합니다. 특히 다음 타입의 함수는

[source,haskell]
----
a -> Store s a
----

다음 두 함수의 쌍과 동등합니다.

[source,haskell]
----
set :: a -> s -> a
get :: a -> s
----

만약 ``a``가 곱 타입이라면, ``set``은 ``a`` 내부의 ``s`` 타입 필드를 설정하면서 수정된 버전의 ``a``를 반환하도록 구현할 수 있습니다. 비슷하게, ``get``은 ``a``로부터 ``s`` 필드의 값을 읽도록 구현할 수 있습니다. 다음 섹션에서 이러한 아이디어들을 더 탐구하겠습니다.
