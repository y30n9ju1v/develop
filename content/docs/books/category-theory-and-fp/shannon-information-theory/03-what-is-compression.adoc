2부가 시작됩니다.

여러분이 컴퓨터에서 대용량 파일을 ZIP으로 압축하면 용량이 절반 이하로 뚝 떨어집니다. 이 마법 같은 일은 도대체 어떤 원리로 가능한 것일까요?

== 모스 부호가 이미 100년 전에 알고 있었던 비밀

19세기 전신 기사들이 사용하던 **모스 부호(Morse Code)**를 살펴봅시다.

* 영어에서 가장 빈번하게 쓰이는 알파벳 **`E`**: 점 하나 (**`·`**, 가장 짧음)
* 아주 드물게 쓰이는 알파벳 **`Q`**: 대시와 점의 긴 조합 (**`--·-`**, 훨씬 김)

이것은 우연이 아닙니다. 전신 기사들은 **"자주 나오는 글자에는 가장 짧은 부호를 주고, 드물게 나오는 글자에는 긴 부호를 주면, 전체 전송 시간이 획기적으로 줄어든다"**는 사실을 본능적으로 꿰뚫고 있었습니다.

압축의 모든 비밀이 바로 이 한 문장에 담겨 있습니다.

== 손으로 직접 해보는 허프만 압축

작은 예시로 압축의 기적을 눈으로 확인해 봅시다.

어떤 문서가 오직 **`A`, `B`, `C`, `D`** 네 글자로만 이루어져 있다고 해봅시다.

만약 모든 글자에 똑같이 2비트씩 고정 길이를 배정한다면(`A=00, B=01, C=10, D=11`), 글자 하나당 무조건 **2.0비트**가 소비됩니다.

하지만 문서 안에서 글자들의 등장 빈도가 다음과 같이 치우쳐 있다면 어떨까요?
* `A`: **50%** (매우 자주 나옴)
* `B`: **25%**
* `C`: **12.5%**
* `D`: **12.5%** (매우 드묾)

자주 나오는 글자에 짧은 비트를 주는 **허프만 부호화(Huffman Coding)** 트리를 설계해 봅시다.

....
                   [ 허프만 접두어 부호(Prefix Code) 트리 ]

                                   (루트)
                                    /  \
                           [0]     /    \    [1]
                                  /      \
                             【 A 】     (중간 노드)
                            (코드: 0)     /   \
                                 [0]    /     \   [1]
                                       /       \
                                  【 B 】     (중간 노드)
                                 (코드: 10)    /   \
                                       [0]   /     \   [1]
                                            /       \
                                       【 C 】     【 D 】
                                     (코드: 110)  (코드: 111)
....

* `A` (50% 확률) $\rightarrow$ **`0`** (길이 1비트)
* `B` (25% 확률) $\rightarrow$ **`10`** (길이 2비트)
* `C` (12.5% 확률) $\rightarrow$ **`110`** (길이 3비트)
* `D` (12.5% 확률) $\rightarrow$ **`111`** (길이 3비트)

이제 글자 하나당 소비되는 **평균 비트 수**를 계산해 봅시다.

$$\text{평균 부호 길이} = (0.5 \times 1) + (0.25 \times 2) + (0.125 \times 3) + (0.125 \times 3) = \mathbf{1.75\text{ 비트}}$$

고정 길이(2.0비트)를 썼을 때보다 용량이 **12.5%나 즉시 절약**되었습니다

== 엔트로피와의 놀라운 일치

놀랍게도 방금 계산한 **`1.75`비트**라는 숫자는, 2장에서 배운 공식으로 이 확률 분포의 **엔트로피**를 계산한 값($H = 1.75$)과 **소수점 하나 틀리지 않고 100% 완벽히 일치**합니다

좋은 압축 알고리즘이란, **각 데이터의 부호 길이를 그 데이터가 가진 본래의 정보량($\log_2(1/p)$)에 정확히 맞추어 주는 것**입니다.

== 띄어쓰기 없이도 헷갈리지 않는 이유: 접두어 부호

`A=0`, `B=10`일 때, `AB`를 압축하면 `010`이 됩니다. 받는 쪽 컴퓨터는 띄어쓰기 없이 붙어있는 `010`을 어떻게 헷갈리지 않고 정확히 `A`와 `B`로 쪼개어 읽을 수 있을까요?

그 비밀은 위의 허프만 트리 구조에 있습니다.  
어떤 글자의 부호도 **다른 글자 부호의 '앞부분(접두어)'이 되지 않도록(접두어 부호, Prefix-Free Code)** 설계되었기 때문입니다.

....
                   [ 접두어 부호의 실시간 해독 과정 ]

   수신된 비트열: [ 0 1 0 1 1 0 ]
                  │
                  ▼ 첫 번째 비트 '0'을 읽는 순간 ──► "0은 A밖에 없다" 【 A 확정 】
                    [ 1 0 1 1 0 ]
                      │
                      ▼ '1' 다음에 '0'을 읽는 순간 ──► "10은 B다" 【 B 확정 】
                          [ 1 1 0 ]
                            │
                            ▼ '1', '1', '0'을 읽는 순간 ──► "110은 C다" 【 C 확정 】
                                  │
                                  ▼
                     [ 해독 완료: A -> B -> C ]
....

컴퓨터는 비트를 한 글자씩 읽어나가다가 트리의 끝(잎 노드)에 도달하는 즉시 망설임 없이 단어를 확정할 수 있습니다.

== 도로 표지판에 비유하기

....
                       [ 도로 표지판 비유 ]

   【 대도시 (서울, 부산): 하루 수십만 대 통행 】
   • 표지판 글씨를 아주 큼직하고 짧게 표시 ──► 【 서울 (짧은 부호) 】

   【 작은 시골 마을: 하루 2~3대 통행 】
   • 길고 자세한 설명이 붙어도 전체 교통에 지장 없음 ──► 【 OO군 OO면 OO리 (긴 부호) 】
....

고속도로 표지판이 운전자들의 빈도를 감안해 글자 크기와 길이를 배분하듯, 압축 프로그램은 데이터의 발생 확률을 감안해 비트 길이를 배분합니다.

[NOTE]
====
**압축 프로그램은 데이터를 무조건 줄여주는 요술봉인가요?**  
그렇지 않습니다. 압축은 **데이터 안에 존재하는 '확률의 불균형(특정 패턴이 자주 나옴)'을 이용하는 기술**일 뿐입니다. 만약 100% 순수한 무작위 난수처럼 모든 기호가 완전히 균등하게 나온다면, 세상 그 어떤 천재적인 압축 프로그램도 파일 크기를 단 1비트조차 줄일 수 없습니다.
====

== 요약

* **압축의 본질**: 자주 나오는 기호에는 짧은 비트를, 드물게 나오는 기호에는 긴 비트를 배정하여 평균 길이를 줄이는 것입니다.
* **허프만 부호화**: 접두어 성질을 만족하면서 평균 부호 길이를 엔트로피에 정확히 일치시키는 최적의 압축 기법입니다.
* **엔트로피 수렴**: 압축된 데이터의 평균 비트 수는 해당 정보 소스의 엔트로피에 도달합니다.

[TIP]
====
**확인 질문**: 모스 부호에서 왜 `E`에는 짧은 점 하나(`·`)를 주고, `Q`에는 긴 부호(`--·-`)를 주는 것이 전체 전송 시간을 줄이는 최고의 선택이 되는지, 평균 부호 길이의 관점에서 설명해 보세요
====
