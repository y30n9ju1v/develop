== 이 책이 하려는 것

3DGS 기반 자율주행 E2E 모델을 실제로 운영해본 팀이라면 익숙한 장면이 있습니다 — 새 체크포인트가 나옵니다. 데이터셋이 조금 바뀌었거나, 학습 하이퍼파라미터를 손봤거나, 의존성 라이브러리를 업데이트했거나, 그냥 재학습을 한 번 더 돌렸을 뿐입니다. 누군가는 이 체크포인트를 몇 개의 대표 장면에 대해 렌더링해보고, 이전 버전과 나란히 놓고 눈으로 비교합니다. 오늘은 괜찮아 보입니다. 그런데 그 "괜찮아 보인다"는 판단이 정말 믿을 만한가요? 사람이 매번 수백 개의 장면, 수천 프레임을 눈으로 검수할 수는 없습니다. 미묘한 흐림, 특정 조건(야간, 역광, 밀집 교통)에서만 나타나는 품질 저하, 포즈 추정의 작은 드리프트는 몇 장면만 훑어봐서는 놓치기 쉽습니다. 그리고 사람의 "오늘은 괜찮아 보인다"는 어제의 "괜찮아 보인다"와 정량적으로 비교할 방법이 없습니다.

이 책은 이 문제 — **체크포인트가 나올 때마다 품질이 실제로 나빠졌는지, 사람이 눈으로 보지 않고도 자동으로, 반복 가능하게, 신뢰할 수 있게 판단하는 것** — 을 처음부터 끝까지 다루는 실무 지향적인 책입니다. 소프트웨어 엔지니어링에서 "회귀 테스트"는 익숙한 개념이지만, 렌더링 품질이나 주행 거동처럼 연속적이고 노이즈가 섞인 출력을 대상으로 하는 회귀 테스트는 `assert x == y` 한 줄로 끝나지 않습니다. 이 책은 그 간극을 메우는 파이프라인을 처음부터 설계하고 구현합니다 — 무엇을 "회귀"라고 부를지 정의하는 것(1부)에서 시작해, 그 판단을 자동으로 반복 실행할 수 있는 인프라(2부: `kind` 클러스터 위의 Argo Workflows DAG)를 세우고, 실제 지표 계산·통계적 판정·시각화를 그 위에 얹고(3부), 마지막으로 노이즈·비용·클라우드 스케일링 같은 운영 현실을 다룹니다(4부).

== 이 책이 딛고 서는 두 권의 책

이 파이프라인은 진공 상태에서 만들어지지 않습니다. 두 가지 핵심 구성 요소를 이 시리즈의 앞선 책들에서 그대로 가져와 씁니다.

첫째, **무엇을 잴 것인가**입니다. "닮았다는 걸 어떻게 잴까"(이미지 품질 평가) 책에서 PSNR·SSIM·지각적 유사도 지표를 처음부터 구현하고 각 지표가 언제 속는지(픽셀 단위로는 멀쩡한데 지각적으로는 다른 경우, 그 반대의 경우)까지 검증했습니다. 이 책은 그 지표 계산 코드를 그대로 파이프라인의 "렌더링 품질 측정" 단계에 꽂아 넣습니다.

둘째, **좋은 렌더링이 나오려면 무엇이 정확해야 하는가**입니다. "흔들리는 로그를 선명한 3DGS로"(시간 정렬과 extrinsic 재최적화) 책에서 카메라 자세가 조금만 틀려도 재투영 오차가 커지고, 그것이 흐림·고스팅으로 이어진다는 것을 정량적으로 다뤘습니다. 이 책은 그 포즈/기하 오차 지표를 렌더링 품질 지표와 나란히 두어, "렌더링이 나빠 보이는 이유가 모델 자체의 문제인지, 아니면 입력 포즈가 흔들린 탓인지" 구분할 수 있는 회귀 리포트를 만듭니다.

이 두 책을 읽지 않았어도 이 책을 따라올 수 있도록 필요한 부분은 다시 요약하지만, 먼저 읽었다면 "지표가 왜 이렇게 계산되는가"를 훨씬 깊이 이해한 채로 이 책의 파이프라인을 읽게 될 것입니다.

== 왜 하필 kind + Argo Workflows + Rerun인가

이 책은 특정 도구 조합을 고집하지 않지만, 그 조합이 실무에서 왜 흔히 선택되는지는 짚고 넘어갈 만합니다. **`kind`**(Kubernetes-in-Docker)는 실제 프로덕션 클러스터의 오케스트레이션 방식을 로컬/CI 환경에서 거의 그대로 재현할 수 있는 가장 가벼운 방법입니다 — 노트북에서도, GitHub Actions 러너에서도 몇 분 안에 클러스터 하나를 띄우고 지울 수 있습니다. **Argo Workflows**는 "베이스라인 가져오기 → 새 체크포인트로 렌더링 → 지표 계산 → 비교 → 게이트 판정"처럼 명확한 의존관계를 가진 다단계 파이프라인을 Kubernetes 네이티브 방식(각 단계가 컨테이너, 전체가 DAG)으로 표현하기에 알맞습니다. **Rerun**은 이 모든 자동 판정이 "회귀 있음"이라고 깃발을 들었을 때, 사람이 왜 그런지 3D 장면과 궤적을 인터랙티브하게 들여다보며 확인할 수 있게 해주는 도구입니다 — 자동화가 사람의 판단을 완전히 대체하는 게 아니라, 사람이 봐야 할 순간을 정확히 짚어주는 역할입니다.

12장에서는 이 로컬 `kind` 기반 파이프라인을 실제 클라우드 GPU 클러스터(EKS/GKE 같은)로 옮기는 법도 다룹니다 — 매니페스트 대부분이 그대로 포팅된다는 것, 그리고 무엇이 달라지는지가 핵심입니다.

== 이 책의 구조

1부(문제 정의)는 "회귀"라는 말이 이 도메인에서 정확히 무엇을 뜻하는지 정의합니다. 2부(파이프라인 아키텍처)는 `kind` 클러스터, 베이스라인 데이터셋, 컨테이너화된 평가 잡, Argo Workflow DAG까지 인프라를 세웁니다. 3부(자동화·비교·시각화)는 지표 계산, 통계적 회귀 판정, CI/CD 연동, Rerun 시각화를 다룹니다. 4부(운영과 실전)는 플레이키(flaky) 테스트, 클라우드 스케일링, 새 체크포인트 하나가 들어와 실제로 회귀를 잡아내고 머지를 막는 전 과정을 처음부터 끝까지 따라가는 종합 실전 장, 그리고 렌더링 품질을 넘어 충돌률·TTC·궤적 오차·jerk 같은 폐루프 주행 평가 지표를 같은 게이트에 편입시키는 장으로 마무리합니다.

== 이 책이 보여주는 출력 중 무엇이 실측이고 무엇이 예시인가

이 시리즈의 다른 책들은 대부분 코드를 실제로 실행하고 그 출력을 그대로 싣습니다. 이 책도 지표 계산·통계적 검정처럼 순수 Python으로 재현 가능한 부분(2·7·8·11장 등)은 이 세션에서 실제로 실행해 얻은 값을 싣습니다. 다만 `kind` 클러스터 생성, `argo submit` 실행, GitHub Actions 워크플로, 클라우드 GPU 노드 프로비저닝처럼 **실제 클러스터·CI 환경·클라우드 계정이 있어야 실행되는 부분**(3·6·9·12·13장의 명령어 출력 대부분)은 이 세션에서 그 인프라를 띄워 실행한 것이 아니라, 해당 도구의 실제 동작 방식에 기반해 재구성한 예시 출력입니다. 각 장에서 이 구분이 헷갈릴 수 있는 지점마다 다시 짚어두지만, 기본 원칙은 여기 적어둔 대로입니다 — 인프라 명령어의 출력은 "이런 파이프라인을 실제로 돌리면 이렇게 나온다"는 예시로 읽어주세요.

== 누구를 위한 책인가

3DGS나 E2E 자율주행 모델을 실제로 반복해서 학습·배포해본 적이 있거나, ML 시스템에 CI/CD 감각을 붙이고 싶은 엔지니어를 대상으로 합니다. Python에 익숙하고 Docker/Kubernetes의 기본 개념(파드, 컨테이너, YAML 매니페스트)을 어느 정도 접해봤다면 충분합니다. Argo Workflows나 Rerun을 한 번도 써본 적이 없어도, 이 책 안에서 필요한 만큼 문법과 개념을 함께 설명합니다. PSNR/SSIM 같은 지표나 SE(3) 포즈 최적화를 몰라도 따라올 수 있지만, 두 권의 앞선 책("닮았다는 걸 어떻게 잴까", "흔들리는 로그를 선명한 3DGS로")을 먼저 읽었다면 이 책이 재사용하는 코드의 배경을 훨씬 깊이 이해하게 됩니다.
