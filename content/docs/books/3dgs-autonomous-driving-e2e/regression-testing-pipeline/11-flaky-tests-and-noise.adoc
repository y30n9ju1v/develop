8장에서 통계적 검정으로 노이즈와 진짜 회귀를 구분하는 방법을 만들었습니다. 하지만 그 통계적 검정 자체가 전제하는 "노이즈의 크기"가 시간이 지나며 바뀌거나, 특정 시퀀스만 유독 불안정한 경우가 실무에서는 흔합니다. 이 장은 그 노이즈의 근원을 짚고, 파이프라인을 실제로 운영하며 겪는 플레이키니스(flakiness)를 다루는 정책을 세웁니다.

== GPU 렌더링/학습의 비결정성 원천

1장에서 비결정성을 언급했지만, 이 장에서는 그 원천을 구체적으로 나눠봅니다.

* **부동소수점 리덕션 순서** — GPU의 병렬 합산(예: 3DGS 래스터라이저가 여러 가우시안의 기여를 누적하는 연산)은 스레드 스케줄링에 따라 덧셈 순서가 실행마다 달라질 수 있고, 부동소수점 덧셈은 결합법칙이 정확히 성립하지 않으므로 아주 작은 수치 차이가 생깁니다.
* **비동기 커널 실행과 경쟁 조건** — 여러 스트림에서 동시에 실행되는 CUDA 커널의 완료 순서가 실행마다 미세하게 달라질 수 있습니다.
* **데이터 로더 셔플/증강 시드** — 평가 자체는 보통 고정 시드를 쓰지만, 학습 과정에서 쓰인 시드가 체크포인트 품질에 영향을 미쳤을 수 있고, 이는 "노이즈"가 아니라 "체크포인트 간 실제 차이"라 회귀 판정과는 별개로 다뤄야 합니다.
* **클러스터 스케줄링 변동** — 같은 GPU 모델이라도 열 스로틀링, 다른 파드와의 자원 경합으로 커널 실행 타이밍이 달라지고, 드물게는 수치 결과에도 영향을 줄 수 있습니다.
* **입력 파이프라인의 부동소수점 캐스팅** — 이미지 디코딩·리사이즈 라이브러리 버전 차이로 아주 작은 픽셀값 차이가 생기고, 이는 5장에서 이미지 고정으로 상당 부분 제거되지만 완전히 사라지지는 않습니다.

이 원천들은 대부분 "고쳐야 할 버그"가 아니라 GPU 병렬 연산의 근본적인 특성입니다. 파이프라인의 목표는 이 노이즈를 없애는 것이 아니라, 그 크기를 알고 통계적 검정(8장)에 정확히 반영하는 것입니다.

== 노이즈 크기를 지속적으로 재측정하기

4장에서 골든런 승격 시 노이즈를 한 번 측정했지만, 이 값은 시간이 지나며 바뀔 수 있습니다(예: 클러스터의 GPU 세대가 바뀌거나, 래스터라이저 버전이 업그레이드되면). 이 책의 파이프라인은 별도의 **노이즈 감시 워크플로**를 주기적으로(예: 매주) 돌려, 동일 체크포인트를 N회 반복 평가하고 그 변동 폭을 다시 추정합니다.

[source,python]
----
# monitoring/measure_noise.py
import json
from pathlib import Path
import numpy as np

def measure_current_noise(repeat_reports: list[dict], metric_name: str = "psnr_db") -> dict:
    values = np.array([r["overall"][metric_name]["mean"] for r in repeat_reports])
    return {
        "metric_name": metric_name,
        "n_repeats": len(values),
        "std": float(values.std(ddof=1)),
        "mean": float(values.mean()),
        "measured_at": None,   # 실제로는 타임스탬프를 채워 넣음
    }


def compare_to_tolerance_config(current_noise: dict, configured_min_effect: float) -> list[str]:
    warnings = []
    # 경험칙: min_effect가 실측 표준편차의 2배 미만이면 오탐 위험이 커짐 (8장의 표준오차 논의와 연결)
    if configured_min_effect < 2 * current_noise["std"]:
        warnings.append(
            f"{current_noise['metric_name']}: 설정된 min_effect({configured_min_effect})가 "
            f"실측 표준편차({current_noise['std']:.3f})의 2배보다 작습니다 — tolerance_bands.yaml 갱신을 검토하세요."
        )
    return warnings
----

이 감시 워크플로가 경고를 내면, 8장의 `tolerance_bands.yaml`을 갱신할 시점이라는 신호입니다 — 노이즈 대역을 방치하면 오탐(설정값이 지나치게 타이트)이나 미탐(지나치게 느슨)이 서서히 쌓입니다.

== 플레이키 시퀀스 격리하기

전체 노이즈와 별개로, 특정 시퀀스 하나만 유독 불안정한 경우가 있습니다 — 예를 들어 반사가 많은 젖은 노면 장면은 3DGS 재구성 자체가 조건에 민감해서, 같은 체크포인트를 여러 번 돌려도 그 시퀀스의 PSNR만 표준편차가 크게 나옵니다. 이런 시퀀스를 회귀 판정에 그대로 포함시키면 8장의 통계적 검정이 계속 불안정한 신호를 냅니다.

[source,python]
----
# monitoring/quarantine.py
QUARANTINE_STD_THRESHOLD_DB = 0.6   # 이 표준편차를 넘으면 격리 후보

def detect_flaky_sequences(per_sequence_noise: dict[str, float]) -> list[str]:
    return [
        seq_id for seq_id, std in per_sequence_noise.items()
        if std > QUARANTINE_STD_THRESHOLD_DB
    ]
----

격리(quarantine)는 "이 시퀀스를 영원히 무시한다"는 뜻이 아닙니다 — 격리된 시퀀스는 별도의 "불안정 시퀀스" 그룹으로 옮겨, 전체 게이트 판정에서는 제외하되 계속 지표를 수집하고 별도의 추적 대시보드에는 남깁니다. 왜 불안정한지 원인을 찾아 재구성 파이프라인 자체를 개선하거나(예: 반사 처리를 다루는 별도 하이퍼파라미터), 근본 원인을 못 찾으면 그 조건 자체를 별도 슬라이스로 명확히 분리해 더 관대한 허용 오차 대역을 적용합니다.

== 재시도 정책

렌더링 잡이 GPU 메모리 부족이나 일시적인 클러스터 문제로 실패하는 것과, 지표가 노이즈로 흔들리는 것은 다른 문제입니다. 전자는 재시도가 적절한 해법이고, Argo Workflow는 태스크 단위로 재시도 정책을 선언할 수 있습니다.

[source,yaml]
----
    - name: render-candidate-tpl
      retryStrategy:
        limit: 2
        retryPolicy: "OnTransientError"     # 노드 장애/일시적 오류만 재시도, 로직 오류는 재시도 안 함
        backoff:
          duration: "30s"
          factor: 2
      # ... (6장의 기존 정의 나머지는 동일)
----

`retryPolicy: "OnTransientError"`는 컨테이너가 명확한 애플리케이션 오류(예: 체크포인트 파일 손상)로 실패한 경우까지 무의미하게 재시도하지 않도록 구분합니다 — 재시도가 능사가 아니라, "일시적 인프라 문제"와 "결정적 실패"를 구분하는 것이 핵심입니다.

지표 계산 자체(8장의 통계적 검정)에는 재시도를 적용하지 않습니다 — 8장에서 이미 N회 반복 실행으로 노이즈를 흡수하도록 설계했으므로, 여기에 재시도를 더 얹으면 "몇 번을 반복해야 통과하는가"라는 원치 않는 게임(gaming)의 여지가 생깁니다.

== 변동 예산: 노이즈를 명시적인 계약으로 만들기

이 장의 개념들을 하나로 묶으면, 파이프라인은 각 지표에 대해 명시적인 **변동 예산(variance budget)**을 갖습니다 — "이 지표는 정상적으로 이 정도까지 흔들릴 수 있다"는 계약입니다. 이 계약은 다음 세 곳에 동시에 반영되어야 일관성이 유지됩니다.

* 8장의 `tolerance_bands.yaml`(`min_effect`, `confidence`)
* 이 장의 노이즈 감시 워크플로가 재측정하는 실제값
* 4장의 골든런 승격 체크리스트(`validate_golden_run_candidate`)의 반복 실행 변동 검사

변동 예산이 세 곳에서 따로 관리되면 시간이 지나며 서로 어긋나기 쉬우므로, 실무에서는 이 값들을 하나의 설정 소스(`tolerance_bands.yaml`)로 통합하고, 나머지 두 곳은 그 값을 읽기만 하도록 설계하는 것이 바람직합니다.

== 요약

* GPU 렌더링/학습의 비결정성은 부동소수점 리덕션 순서, 비동기 커널 경쟁, 클러스터 스케줄링 변동 등 근본적인 원천에서 옵니다 — 없앨 대상이 아니라 크기를 알고 통계 검정에 반영할 대상입니다.
* 노이즈 크기는 시간이 지나며 바뀔 수 있으므로, 주기적인 노이즈 감시 워크플로로 재측정하고 `tolerance_bands.yaml`을 갱신해야 합니다.
* 특정 시퀀스만 유독 불안정하면 격리(quarantine)해 게이트 판정에서 제외하되, 지표 수집과 트렌드 추적은 계속 유지합니다.
* 인프라 수준의 일시적 실패(재시도로 해결 가능)와 지표 노이즈(통계 검정으로 흡수)는 서로 다른 문제이며, 재시도 정책은 전자에만 적용해야 합니다.
* 변동 예산을 하나의 설정 소스로 통합해, 8장의 통계 검정과 4장의 골든런 검증, 이 장의 노이즈 감시가 서로 어긋나지 않게 유지합니다.
