2장에서 회귀 판정에는 "무엇과 비교할 것인가" — 베이스라인 — 이 필요하다고 했습니다. 이 장은 그 베이스라인을 실제로 어떻게 만들고, 어디에 저장하고, 어떻게 버전을 관리하는지 다룹니다.

== 베이스라인 데이터셋에 들어가야 하는 것

베이스라인 데이터셋은 단순히 "평가에 쓸 장면 목록"이 아닙니다. 회귀 파이프라인이 매 체크포인트마다 재사용할 수 있도록, 다음 세 가지가 함께 고정되어야 합니다.

1. **입력 시퀀스** — 카메라 이미지, 라이다 포인트클라우드, 포즈 로그(추정치, 완벽하지 않아도 됩니다 — 오히려 실제 로그 수준의 노이즈를 포함해야 1장 시나리오 B 같은 회귀를 잡을 수 있습니다) 등 모델에 넣을 원본 데이터.
2. **참조 출력(골든런)** — 신뢰할 수 있는(사람이 검수한) 체크포인트로 이 입력을 한 번 처리한 결과 — 렌더링 이미지, 재구성된 3D 표현, 추정 궤적. 이후 모든 신규 체크포인트는 이 참조 출력과 비교됩니다.
3. **메타데이터** — 각 시퀀스가 어떤 슬라이스(날씨, 시간대, 도로 유형, 속도 구간)에 속하는지 태그. 2장에서 강조했듯 슬라이스별 회귀 탐지에 필수적입니다.

== 슬라이스 설계

베이스라인 데이터셋은 무작위로 고른 장면들의 모음이 아니라, 의도적으로 다양한 조건을 커버하도록 구성해야 합니다.

[source,python]
----
# baseline_manifest.py — 베이스라인 시퀀스 메타데이터 스키마
from dataclasses import dataclass, field

@dataclass
class BaselineSequence:
    sequence_id: str
    source_log: str            # 원본 주행 로그 식별자
    frame_range: tuple[int, int]
    slices: dict[str, str] = field(default_factory=dict)
    # 예: {"weather": "clear", "time_of_day": "day",
    #      "road_type": "highway", "speed_bucket": "60-80kmh"}

MANIFEST = [
    BaselineSequence("seq-0001", "log-2026-05-12-a", (1200, 1500),
                      {"weather": "clear", "time_of_day": "day",
                       "road_type": "highway", "speed_bucket": "60-80kmh"}),
    BaselineSequence("seq-0002", "log-2026-05-14-b", (300, 600),
                      {"weather": "rain", "time_of_day": "day",
                       "road_type": "urban", "speed_bucket": "0-30kmh"}),
    BaselineSequence("seq-0003", "log-2026-05-20-c", (0, 400),
                      {"weather": "clear", "time_of_day": "night",
                       "road_type": "highway", "speed_bucket": "80-100kmh"}),
    # 실전에서는 각 (weather × time_of_day × road_type × speed_bucket)
    # 조합이 최소 2~3개 시퀀스는 있도록 목표 커버리지를 정해 채웁니다.
]
----

최소 목표는 "각 슬라이스 축의 각 값이 최소 몇 개 이상의 독립된 시퀀스로 대표되는가"입니다. 야간 장면이 전체 100개 시퀀스 중 하나뿐이라면, 그 슬라이스의 평균은 노이즈에 극도로 취약해 통계적 판정(8장)이 사실상 불가능합니다.

== 골든런: 누가, 언제, 어떻게 고정하는가

골든런은 "지금 이 체크포인트의 출력을 최저 품질 기준으로 삼는다"는 사람의 결정입니다. 이 결정은 되돌리기 쉬워야 하지만(더 나은 체크포인트가 검증되면 골든런을 갱신), 아무나 자동으로 바꿀 수 있어서는 안 됩니다 — 그러면 회귀가 조금씩 골든런에 스며들어 2장에서 경고한 "베이스라인 자체의 누적 드리프트"가 일어납니다.

실무적으로는 다음과 같은 절차를 둡니다.

1. 후보 체크포인트가 기존 골든런보다 모든 슬라이스에서 회귀 없이 동등하거나 낫다는 것을 이 파이프라인 자체로 확인한다(8장의 통계적 검정을 골든런 승격에도 재사용).
2. 사람이 Rerun으로 대표 장면 몇 개를 눈으로 검수한다(10장).
3. 승인되면 골든런 태그를 새 체크포인트로 옮기고, 이전 골든런은 보관(archive)한다 — 삭제하지 않습니다. 나중에 "언제부터 특정 실패 모드가 생겼는가"를 역추적할 때 이전 골든런들이 필요합니다.

== MinIO 저장 레이아웃과 버저닝

베이스라인 데이터와 골든런 산출물은 MinIO(3장에서 배치)에 다음과 같은 레이아웃으로 저장합니다.

[source]
----
s3://regression-baselines/
├── manifests/
│   └── v2026.05.20.json              # 위 MANIFEST의 스냅샷 (불변)
├── inputs/
│   └── seq-0001/
│       ├── images/frame_0000.png ...
│       ├── lidar/frame_0000.pcd ...
│       └── poses.jsonl                # 프레임별 추정 포즈 (실제 로그 수준 노이즈 포함)
└── golden-runs/
    └── checkpoint-2026-05-18-rc3/      # 골든런으로 승격된 체크포인트 식별자
        ├── seq-0001/
        │   ├── render_0000.png ...
        │   └── metrics_vs_input.json   # 이 골든런 자체의 자기 검증 결과 (아래 참고)
        └── MANIFEST_REF -> v2026.05.20.json
----

`manifests/`는 절대 덮어쓰지 않고 날짜가 박힌 새 파일로만 추가합니다 — 베이스라인 시퀀스 구성 자체가 바뀌면(새 슬라이스 추가 등), 예전 회귀 리포트가 참조하던 매니페스트가 그대로 남아 있어야 과거 실행을 재현할 수 있습니다. `golden-runs/`도 체크포인트 식별자별 디렉터리로 쌓이기만 하고, "현재 활성 골든런"은 별도의 포인터(예: `golden-runs/ACTIVE` 파일에 현재 디렉터리명을 적어둠)로만 가리킵니다.

[source,python]
----
# 활성 골든런을 가리키는 포인터를 읽는 헬퍼
import json

def resolve_active_golden_run(s3_client, bucket: str = "regression-baselines") -> str:
    obj = s3_client.get_object(Bucket=bucket, Key="golden-runs/ACTIVE")
    return obj["Body"].read().decode("utf-8").strip()
----

== 베이스라인 자체를 검증해야 하는 이유

"흔들리는 로그를 선명한 3DGS로" 책이 반복해서 강조한 습관 — 정답을 안다고 믿기 전에 직접 검증한다 — 이 여기서도 그대로 적용됩니다. 골든런은 "사람이 눈으로 봤을 때 괜찮아 보였다"는 이유만으로 신뢰할 수 없습니다. 최소한 다음을 확인해야 합니다.

* **입력 포즈가 실제로 그 시퀀스에 맞게 정합적인가** — 포즈 로그가 손상되거나 오프셋이 섞여 들어간 채로 골든런을 만들면, 그 골든런 자체가 나쁜 재투영 오차를 "정상"으로 고정해버립니다. 이 검증은 "흔들리는 로그를 선명한 3DGS로" 책 5장(정렬 품질을 수치로 검증하기)의 도구를 그대로 재사용합니다.
* **골든런 산출물이 재현 가능한가** — 같은 입력, 같은 체크포인트로 다시 렌더링했을 때 지표가 크게 흔들리지 않는지(1장의 비결정성 문제) 최소 3회 반복 실행으로 확인합니다.
* **슬라이스 커버리지가 실제 목표와 맞는가** — 야간·우천처럼 드문 조건이 충분한 시퀀스 수로 대표되는지 재확인합니다.

[source,python]
----
# 골든런 승격 전 자기 검증 체크리스트 (개념 스케치)
def validate_golden_run_candidate(candidate_metrics: dict, repeat_runs: list[dict]) -> list[str]:
    problems = []
    # 1) 반복 실행 간 변동이 지나치게 크지 않은가
    psnr_values = [r["psnr_db"] for r in repeat_runs]
    if (max(psnr_values) - min(psnr_values)) > 0.5:
        problems.append("반복 실행 간 PSNR 변동이 0.5dB를 넘습니다 — 비결정성이 과도합니다.")
    # 2) 슬라이스별 시퀀스 수가 최소 기준을 만족하는가
    for slice_key, count in candidate_metrics.get("slice_counts", {}).items():
        if count < 3:
            problems.append(f"슬라이스 '{slice_key}'의 시퀀스가 {count}개뿐입니다(최소 3개 권장).")
    return problems
----

== 요약

* 베이스라인 데이터셋은 입력 시퀀스, 골든런(참조 출력), 슬라이스 메타데이터 세 요소가 함께 고정되어야 합니다.
* 슬라이스는 무작위가 아니라 날씨·시간대·도로 유형·속도 구간 같은 축을 의도적으로 커버하도록 설계해야, 특정 조건에서만 나타나는 회귀를 잡을 수 있습니다.
* 골든런 승격은 사람의 검수와 파이프라인 자체의 통계적 검정을 함께 거치는 절차로 관리하고, 이전 골든런은 삭제하지 않고 보관합니다.
* MinIO의 매니페스트·골든런 레이아웃은 불변 스냅샷 방식으로 쌓아, 과거 회귀 리포트를 나중에도 재현할 수 있게 합니다.
* 골든런 자체도 포즈 정합성, 재현성, 슬라이스 커버리지를 검증받아야 하며, "사람이 눈으로 봤을 때 괜찮았다"만으로는 충분하지 않습니다.
