지금까지 파이프라인 전체를 `kind` 클러스터 위에서 설계했습니다(그리고 로컬에서는 GPU가 필요한 렌더링 단계를 5장의 목 모드로 대체해 배선만 검증했습니다). 이 장에서는 이 파이프라인을 실제 GPU가 있는 클라우드 클러스터로 옮기는 법과, 클라우드 특유의 새로운 고려사항 — 비용 — 을 다룹니다.

== 무엇이 그대로 옮겨가고, 무엇이 바뀌는가

`kind`가 실제 Kubernetes API를 그대로 구현하기 때문에, 대부분의 자산은 변경 없이 포팅됩니다.

**그대로 옮겨가는 것**: Argo Workflow DAG 정의(6장), 아티팩트 흐름 배선, `retryStrategy`(11장), Argo Events의 EventSource/Sensor 정의(9장), 컨테이너 이미지 자체(5장 — 다만 이미지 레지스트리 주소는 바뀝니다).

**바뀌는 것**: 클러스터 프로비저닝 방식(`kind create cluster` 대신 관리형 서비스), GPU 노드 풀 설정과 드라이버 설치 방식, 아티팩트 저장소(MinIO 대신 실제 S3/GCS — 다만 API 호환 계층 덕에 클라이언트 코드는 거의 그대로), 그리고 무엇보다 **비용을 통제하는 계층**이 새로 필요해진다는 점입니다.

== EKS에 GPU 노드 풀 만들기

Amazon EKS를 예로 들면, GPU 노드 그룹을 별도로 정의하고 3장의 `nodeSelector: {workload: eval-jobs}` 패턴을 그대로 재사용합니다.

[source,yaml]
----
# eksctl-gpu-nodegroup.yaml
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: regression-cluster
  region: ap-northeast-2

managedNodeGroups:
  - name: gpu-eval-nodes
    instanceType: g5.xlarge
    minSize: 0
    maxSize: 8
    desiredCapacity: 0          # 오토스케일러가 필요할 때만 노드를 띄움
    spot: true                  # 아래에서 다시 다룸
    labels:
      workload: eval-jobs
    taints:
      - key: nvidia.com/gpu
        value: "true"
        effect: NoSchedule
    tags:
      pipeline: regression-testing
----

`taints`를 GPU 노드에 걸어두면, GPU를 요구하지 않는 파드(6장의 `compute-metrics-tpl`, `compare-and-gate-tpl` 같은)가 실수로 비싼 GPU 노드에 스케줄링되는 것을 막을 수 있습니다. 6장의 `render-candidate-tpl`에는 이에 대응하는 `tolerations`를 추가합니다.

[source,yaml]
----
      tolerations:
        - key: "nvidia.com/gpu"
          operator: "Equal"
          value: "true"
          effect: "NoSchedule"
----

NVIDIA GPU 드라이버와 디바이스 플러그인은 클라우드 관리형 AMI에 이미 포함되어 있거나, `NVIDIA GPU Operator`를 클러스터에 설치해 자동으로 관리합니다 — `kind`에서는 이 단계가 없었지만(로컬에서는 목 모드로 우회했으므로), 클라우드에서는 필수 단계입니다.

== 스팟 인스턴스와 오토스케일링으로 비용 통제하기

렌더링 잡은 GPU를 요구하지만, 상시로 GPU 노드가 떠 있을 필요는 없습니다 — 9장에서 다룬 대로 이벤트(체크포인트 push, PR)가 있을 때만 워크플로가 실행되므로, 그 사이에는 GPU 노드가 0대여도 됩니다. 위 노드그룹 설정에서 `minSize: 0`, `desiredCapacity: 0`으로 두고, Kubernetes 클러스터 오토스케일러(Cluster Autoscaler)가 대기 중인(Pending) 파드가 생기면 자동으로 노드를 띄우고, 일정 시간 유휴 상태면 다시 0으로 줄이도록 설정합니다.

[source,yaml]
----
# cluster-autoscaler 설정 (발췌)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cluster-autoscaler
  namespace: kube-system
spec:
  template:
    spec:
      containers:
        - name: cluster-autoscaler
          image: registry.k8s.io/autoscaling/cluster-autoscaler:v1.29.3
          command:
            - ./cluster-autoscaler
            - --scale-down-unneeded-time=5m
            - --scale-down-delay-after-add=5m
            - --nodes=0:8:regression-cluster-gpu-eval-nodes
            - --balance-similar-node-groups
----

`spot: true`(스팟 인스턴스)는 온디맨드 가격의 60~90% 할인을 받는 대신, 클라우드 사업자가 필요하면 짧은 예고 후 인스턴스를 회수할 수 있다는 위험을 감수합니다. 렌더링 잡은 수 분 안에 끝나는 배치 작업이고 11장의 `retryStrategy`(`OnTransientError`)가 이미 인프라 수준 실패에 대한 재시도를 갖추고 있으므로, 스팟 인스턴스 회수는 대부분 재시도로 자연스럽게 흡수됩니다.

[source,yaml]
----
      retryStrategy:
        limit: 3                          # 스팟 회수 가능성을 고려해 재시도 횟수를 조금 늘림
        retryPolicy: "OnTransientError"
        backoff: {duration: "30s", factor: 2}
      nodeSelector:
        workload: eval-jobs
        eks.amazonaws.com/capacityType: SPOT
----

비용에 특히 민감한 조직이라면, 골든런 승격이나 릴리스 후보 검증처럼 신뢰성이 중요한 실행만 온디맨드 노드에, 일상적인 PR 검증은 스팟 노드에 스케줄링하도록 `nodeSelector`를 워크플로 파라미터로 분기할 수도 있습니다.

== 아티팩트 저장소를 MinIO에서 S3로

3장에서 MinIO를 쓴 이유가 S3 API와 호환되기 때문이었다는 것을 기억하면, 이 전환은 설정값 몇 개를 바꾸는 것으로 끝납니다.

[source,yaml]
----
# 클라우드용 artifact-repositories ConfigMap (발췌)
apiVersion: v1
kind: ConfigMap
metadata:
  name: artifact-repositories
  namespace: argo
data:
  s3-regression-bucket: |
    s3:
      bucket: regression-baselines-prod
      region: ap-northeast-2
      endpoint: s3.ap-northeast-2.amazonaws.com
      useSDKCreds: true          # IRSA(IAM Role for Service Account)로 자격 증명 관리
----

애플리케이션 코드(4장의 `resolve_active_golden_run`, 7장의 지표 리포트 저장 로직)는 `boto3` 클라이언트를 그대로 쓰므로 엔드포인트만 바뀔 뿐 코드 변경이 필요 없습니다. 다만 자격 증명 방식은 MinIO의 고정된 액세스 키 대신, 클라우드 네이티브 방식(EKS의 IRSA, GKE의 Workload Identity)으로 바꾸는 것이 보안상 바람직합니다.

== 대규모 병렬 실행: 업계에서는 Argo만으로 끝내지 않는다

평가해야 할 시퀀스가 수백~수천 개로 늘어나면, 6장의 DAG를 시퀀스 하나당 태스크 하나로 팬아웃해야 합니다. Argo Workflow 자체는 이걸 `withParam`으로 표현합니다.

[source,yaml]
----
  - - name: render-and-eval-fanout
      template: render-candidate-tpl
      arguments:
        parameters:
          - name: sequence-id
            value: "{{item}}"
      withParam: "{{tasks.list-sequences.outputs.result}}"   # 예: ["seq-0001", ..., "seq-2000"]
----

문법상으로는 이걸로 끝이지만, 이 상태로 GPU 노드가 8대뿐인 노드 풀에 2000개짜리 팬아웃을 그냥 던지면 실무에서는 바로 문제가 터집니다 — Argo가 2000개의 `Pending` 파드를 한꺼번에 만들면 API 서버에 부하가 걸리고, 오토스케일러가 노드를 띄우는 속도보다 파드 생성 속도가 훨씬 빨라 스케줄러가 밀리며, 무엇보다 "누구 하나가 노드 풀 전체를 다 써버려서 다른 PR 검증이 몇 시간씩 대기하는" 상황이 생깁니다. 그래서 이 규모부터는 업계에서 보통 아래 세 가지를 얹습니다 — 어느 것도 Argo가 대체하지 않고, Argo *위에* 얹는 레이어들입니다.

=== 1. 동시성 자체를 Argo `synchronization`(세마포어)으로 제한하기

가장 먼저, 그리고 가장 간단하게 할 수 있는 건 "한 워크플로 안에서 동시에 몇 개까지만 GPU 파드를 띄울지"를 Argo 자체 기능으로 못 박는 것입니다.

[source,yaml]
----
  - - name: render-and-eval-fanout
      template: render-candidate-tpl
      synchronization:
        semaphore:
          configMapKeyRef:
            name: gpu-concurrency-limits
            key: eval-jobs        # ConfigMap에 "eval-jobs: '8'" 로 노드 풀 크기와 맞춰둠
      arguments:
        parameters:
          - name: sequence-id
            value: "{{item}}"
      withParam: "{{tasks.list-sequences.outputs.result}}"
----

이러면 2000개 태스크가 한꺼번에 `Pending` Pod로 쏟아지는 대신, Argo 컨트롤러가 세마포어 한도(예: 8) 안에서만 실제로 Pod를 만들고 나머지는 큐에 둡니다 — API 서버 부하와 "노드는 8대인데 파드 2000개가 동시에 스케줄링을 시도하는" 문제를 워크플로 계층에서 미리 막는, 가장 저렴한 방어선입니다.

=== 2. GPU 쿼터·팀 간 공정 분배: Kueue

세마포어는 워크플로 하나 안의 동시성만 제어합니다. 여러 팀·여러 워크플로가 같은 GPU 노드 풀을 공유하면(이 책의 맥락이면 "여러 PR이 동시에 열려 있는" 상황), "먼저 던진 워크플로가 노드 풀을 다 차지해서 나중 워크플로가 무기한 대기하는" 문제가 생깁니다. 이건 Argo의 책임 범위 밖입니다 — 실무에서는 이 계층에 **Kueue**(Kubernetes SIG가 관리하는 잡 큐잉 컨트롤러)를 얹습니다.

[source,yaml]
----
# ClusterQueue: GPU 자원 총량을 선언
apiVersion: kueue.x-k8s.io/v1beta1
kind: ClusterQueue
metadata:
  name: gpu-eval-queue
spec:
  namespaceSelector: {}
  resourceGroups:
    - coveredResources: ["nvidia.com/gpu"]
      flavors:
        - name: gpu-eval-nodes
          resources:
            - name: "nvidia.com/gpu"
              nominalQuota: 8      # 노드 풀 크기와 일치
---
# LocalQueue: 각 팀/네임스페이스가 이 쿼터를 나눠 씀
apiVersion: kueue.x-k8s.io/v1beta1
kind: LocalQueue
metadata:
  name: team-perception-queue
  namespace: team-perception
spec:
  clusterQueue: gpu-eval-queue
----

Kueue는 Argo가 만드는 Pod들을 가로채 자체 큐에 쌓아두고, `nominalQuota`를 넘지 않는 선에서 팀별로 공정하게(fair-sharing) 순서를 배정합니다 — "회귀 테스트 PR 100개가 한꺼번에 열려도, 한 팀이 GPU 8대를 통째로 독점하지 못하게" 만드는 게 이 계층의 역할입니다. (같은 자리의 대안으로 **Volcano**도 널리 쓰이는데, Volcano는 여기에 더해 "여러 파드가 세트로 함께 배정돼야만 시작하는" 갱 스케줄링(gang scheduling)까지 지원합니다 — 이 책의 렌더링 잡처럼 파드가 서로 독립적이면 Kueue만으로 충분합니다.)

=== 3. 오토스케일러: Cluster Autoscaler보다 Karpenter

앞서 다룬 Cluster Autoscaler는 노드 그룹(고정된 인스턴스 타입 집합) 단위로만 늘리고 줄입니다. 대규모 팬아웃에서는 "지금 대기 중인 파드들의 정확한 CPU/GPU 요구량에 맞는 인스턴스 타입을 그때그때 골라 띄우는" 게 훨씬 빠르고 저렴한데, 이게 요즘 업계 표준으로 자리잡은 **Karpenter**가 하는 일입니다 — 노드 그룹 설정 없이 클러스터 전체를 보고 "지금 필요한 만큼만, 가장 저렴하게 뜰 수 있는 인스턴스"를 직접 프로비저닝합니다.

[source,yaml]
----
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: gpu-eval-nodepool
spec:
  template:
    spec:
      requirements:
        - key: karpenter.k8s.aws/instance-family
          operator: In
          values: ["g5"]
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]   # 스팟 우선, 없으면 온디맨드로 자동 폴백
      taints:
        - key: nvidia.com/gpu
          value: "true"
          effect: NoSchedule
  limits:
    cpu: "256"
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized   # 유휴 노드를 빠르게 통합/회수
----

`Cluster Autoscaler`보다 노드 기동이 빠르고(수 분 → 대개 1분 이내), 스팟 우선순위와 폴백을 노드풀 정의 하나로 표현할 수 있어 이 책의 스팟/온디맨드 분기(위 절)도 이 설정 하나로 흡수됩니다.

=== 4. 우선순위: 골든런 검증이 PR 검증을 밀어내야 할 때

Kueue/Karpenter로도 노드 풀이 가득 차는 순간은 옵니다. 이때 "일상적인 PR 검증"과 "릴리스 후보의 골든런 승격 검증" 중 어느 쪽이 먼저 자원을 받아야 하는지는 `PriorityClass`로 명시합니다.

[source,yaml]
----
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: golden-run-critical
value: 1000
preemptionPolicy: PreemptLowerPriority
globalDefault: false
description: "골든런 승격 검증은 대기 중인 PR 검증 파드를 밀어내고 먼저 실행된다"
----

Kueue의 `ClusterQueue`도 우선순위를 인식하므로, 큐 대기 순서와 k8s 파드 선점(preemption)이 같은 우선순위 체계로 일관되게 동작합니다.

=== 이 네 계층을 합치면

정리하면, "대규모 병렬로 회귀 테스트를 돌린다"는 게 현업에서는 Argo Workflow의 `withParam` 하나로 끝나는 일이 아니라, **Argo(무엇을 실행할지) + Kueue(누가 언제 GPU를 쓸지) + Karpenter(노드를 얼마나 빠르고 싸게 띄울지) + PriorityClass(무엇이 먼저인지)** 네 계층이 각자의 책임을 나눠 맡는 구조입니다. 이 책은 6장의 DAG와 이 장의 노드 풀·오토스케일링까지 단일 워크플로/단일 노드 그룹 규모에서 실제로 검증했고, 위 네 계층 조합은 그 검증된 조각들을 수천 개 시퀀스 규모로 확장할 때 실무에서 실제로 얹는 표준 패턴으로 소개합니다 — 다만 Kueue/Karpenter 자체를 이 세션에서 클러스터에 설치해 동시성·공정분배·노드 기동 시간을 실측하지는 않았다는 점은 정직하게 밝혀둡니다. 여러 리전/클러스터로 나누는 것(연합, federation)은 이보다 한 단계 더 나아간 문제라 이 책은 다루지 않습니다(맺음말 참고).

== 비용 대시보드에 GPU 시간을 함께 기록하기

회귀 리포트(7장 스키마)에 실행에 든 GPU 노드 시간을 함께 기록해두면, 나중에 "PR마다 얼마의 비용이 드는가"를 추적할 수 있습니다.

[source,python]
----
def record_resource_usage(workflow_name: str, gpu_node_seconds: float, spot: bool) -> dict:
    # 예시 단가: g5.xlarge 온디맨드 $1.006/hr, 스팟 약 $0.35/hr (리전/시점에 따라 변동)
    hourly_rate = 0.35 if spot else 1.006
    cost_usd = (gpu_node_seconds / 3600) * hourly_rate
    return {"workflow_name": workflow_name, "gpu_node_seconds": gpu_node_seconds,
            "spot": spot, "estimated_cost_usd": round(cost_usd, 4)}
----

== 요약

* `kind`에서 검증한 Argo Workflow DAG, 아티팩트 배선, 재시도 정책은 대부분 값만 바꿔 클라우드 클러스터로 그대로 포팅됩니다.
* GPU 노드 풀은 `taints`/`tolerations`로 GPU가 필요 없는 파드가 스케줄링되지 않도록 분리하고, 오토스케일러로 유휴 시 노드를 0대까지 줄여 비용을 통제합니다.
* 스팟 인스턴스는 큰 비용 절감을 주는 대신 회수 위험을 감수하며, 이미 갖춰둔 `retryStrategy`(11장)가 이 위험을 대부분 흡수합니다.
* MinIO에서 실제 S3/GCS로의 전환은 API 호환성 덕분에 애플리케이션 코드 변경 없이 설정값 교체로 끝나지만, 자격 증명 방식은 클라우드 네이티브 방식으로 바꾸는 것이 바람직합니다.
* GPU 노드 시간과 비용을 회귀 리포트에 함께 기록해두면 파이프라인 운영 비용을 지속적으로 추적할 수 있습니다.
* 시퀀스 수천 개 규모의 대규모 병렬 실행은 Argo `withParam` 팬아웃 하나로 끝나지 않습니다 — `synchronization`(세마포어)으로 워크플로 내 동시성을 제한하고, Kueue로 팀/워크플로 간 GPU 쿼터를 공정하게 나누고, Karpenter로 필요한 만큼만 빠르게 노드를 띄우고, `PriorityClass`로 골든런 검증이 PR 검증보다 먼저 자원을 받도록 하는 네 계층을 Argo 위에 얹는 것이 현업의 표준 패턴입니다.
