6~8장에서 완성한 DAG는 `argo submit`을 손으로 실행해야 돌아갑니다. 이 장에서는 새 체크포인트가 저장소에 올라오거나 PR이 열릴 때 이 워크플로가 자동으로 시작되고, 그 결과가 다시 CI 상태로 반영되게 만듭니다.

== 두 가지 트리거 경로

이 파이프라인은 트리거 소스가 두 종류입니다.

1. **코드 변경(PR)** — 평가 스크립트, 지표 계산 로직, DAG 정의 자체가 바뀌었을 때. 이 경우 GitHub Actions가 직접 워크플로를 트리거하기 좋습니다 — 이미 코드 저장소 이벤트에 반응하도록 만들어진 도구이기 때문입니다.
2. **체크포인트 변경(모델 아티팩트 push)** — 학습 파이프라인이 새 체크포인트를 오브젝트 스토리지에 올렸을 때. 이 이벤트는 GitHub 저장소 밖에서 일어나므로, 클러스터 안에서 이벤트를 직접 감지하는 **Argo Events**가 더 자연스럽습니다.

두 경로 모두 최종적으로는 6장의 `regression-workflow.yaml`을 서로 다른 파라미터로 제출하는 지점으로 수렴합니다.

== 경로 1: GitHub Actions에서 워크플로 트리거

PR이 열리거나 갱신될 때, GitHub Actions 러너 안에서 `kind` 클러스터를 띄우고(3장의 설정을 그대로 재사용) 워크플로를 제출한 뒤 결과를 기다립니다.

[source,yaml]
----
# .github/workflows/regression-test.yml
name: regression-test

on:
  pull_request:
    paths:
      - "eval/**"
      - "compare/**"
      - "regression-workflow.yaml"
  workflow_dispatch:
    inputs:
      checkpoint-uri:
        description: "평가할 체크포인트 S3 URI"
        required: true

jobs:
  regression-gate:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v4

      - name: kind 클러스터 생성
        uses: helm/kind-action@v1.10.0
        with:
          config: kind-config.yaml
          cluster_name: regression-ci

      - name: Argo Workflows 설치
        run: |
          kubectl create namespace argo
          kubectl apply -n argo -f https://github.com/argoproj/argo-workflows/releases/download/v3.5.8/install.yaml
          kubectl -n argo wait --for=condition=available --timeout=120s deployment/argo-server

      - name: MinIO 및 아티팩트 저장소 설정 배치
        run: kubectl apply -n argo -f k8s/minio-deployment.yaml

      - name: 평가/비교 이미지 빌드 및 로드
        run: |
          docker build -t regression-eval:${{ github.sha }} -f Dockerfile.render-eval .
          docker build -t regression-compare:${{ github.sha }} -f Dockerfile.compare .
          kind load docker-image regression-eval:${{ github.sha }} --name regression-ci
          kind load docker-image regression-compare:${{ github.sha }} --name regression-ci

      - name: 회귀 테스트 워크플로 제출 및 대기
        run: |
          CHECKPOINT="${{ github.event.inputs.checkpoint-uri || 's3://model-checkpoints/pr-preview.pt' }}"
          argo submit regression-workflow.yaml -n argo \
            --parameter checkpoint-uri="${CHECKPOINT}" \
            --parameter image-tag="${{ github.sha }}" \
            --wait --log

      - name: 회귀 리포트를 PR 코멘트로 게시
        if: always()
        run: |
          argo get @latest -n argo -o json | \
            python scripts/post_pr_comment.py --pr=${{ github.event.pull_request.number }}
----

`--wait` 옵션은 워크플로가 끝날 때까지 `argo submit`이 종료 코드를 반환하지 않게 하고, 6장에서 만든 `compare-and-gate-tpl`이 회귀 감지 시 종료 코드 1을 반환하도록 했으므로, 워크플로 전체가 `Failed`가 되면 이 GitHub Actions 잡도 실패로 끝나 PR이 자동으로 빨간 체크를 받습니다.

== 경로 2: Argo Events로 체크포인트 push 감지

학습 파이프라인이 MinIO(또는 실제 클라우드에서는 S3)에 새 체크포인트를 올릴 때마다 자동으로 워크플로를 트리거하려면, Argo Events의 **EventSource**(이벤트를 감지)와 **Sensor**(이벤트에 반응해 워크플로 제출)를 조합합니다.

[source,yaml]
----
# argo-events/checkpoint-eventsource.yaml
apiVersion: argoproj.io/v1alpha1
kind: EventSource
metadata:
  name: checkpoint-uploads
  namespace: argo-events
spec:
  minio:
    checkpoint-bucket:
      bucket:
        name: model-checkpoints
      endpoint: minio.argo.svc.cluster.local:9000
      accessKey:
        name: minio-creds
        key: accesskey
      secretKey:
        name: minio-creds
        key: secretkey
      events:
        - "s3:ObjectCreated:Put"
      filter:
        prefix: "checkpoints/"
        suffix: ".pt"
----

[source,yaml]
----
# argo-events/checkpoint-sensor.yaml
apiVersion: argoproj.io/v1alpha1
kind: Sensor
metadata:
  name: checkpoint-upload-sensor
  namespace: argo-events
spec:
  dependencies:
    - name: checkpoint-dep
      eventSourceName: checkpoint-uploads
      eventName: checkpoint-bucket

  triggers:
    - template:
        name: submit-regression-workflow
        argoWorkflow:
          operation: submit
          source:
            resource:
              apiVersion: argoproj.io/v1alpha1
              kind: Workflow
              metadata:
                generateName: regression-test-auto-
                namespace: argo
              spec:
                entrypoint: regression-dag
                arguments:
                  parameters:
                    - name: checkpoint-uri
                      value: "placeholder"   # 아래 parameters로 실제 이벤트 데이터에서 덮어씀
          parameters:
            - src:
                dependencyName: checkpoint-dep
                dataKey: "s3.object.key"
              dest: spec.arguments.parameters.0.value
----

이 Sensor는 `checkpoints/` 경로에 `.pt` 확장자 파일이 새로 올라올 때마다, 방금 올라온 파일 경로를 `checkpoint-uri` 파라미터로 채워 6장의 `regression-workflow.yaml`과 동일한 구조의 워크플로를 자동 제출합니다. 학습 파이프라인 쪽에서는 "회귀 테스트가 있다"는 사실조차 몰라도 됩니다 — 체크포인트를 정해진 경로에 올리기만 하면 됩니다.

== 게이트 결과를 머지/배포 정책에 연결하기

GitHub Actions 경로에서는 워크플로 실패가 곧 PR 체크 실패이므로, 저장소의 브랜치 보호 규칙(branch protection rule)에 이 체크를 필수로 지정하기만 하면 자동으로 머지가 막힙니다.

Argo Events 경로(자동 체크포인트 감지)에서는 "머지"라는 개념이 없는 대신, 체크포인트를 실제 서빙 환경에 승격하는 별도의 배포 파이프라인이 이 게이트 결과를 조회해야 합니다.

[source,python]
----
# scripts/check_gate_before_deploy.py
import argparse
import json
import subprocess
import sys

def get_latest_regression_report(checkpoint_uri: str) -> dict:
    result = subprocess.run(
        ["argo", "list", "-n", "argo", "-o", "json",
         "--selector", f"checkpoint-uri={checkpoint_uri}"],
        capture_output=True, text=True, check=True,
    )
    workflows = json.loads(result.stdout)
    if not workflows:
        raise RuntimeError(f"체크포인트 {checkpoint_uri}에 대한 회귀 테스트 기록이 없습니다.")
    latest = sorted(workflows, key=lambda w: w["metadata"]["creationTimestamp"])[-1]
    # 실제로는 아티팩트 저장소에서 regression_report.json을 내려받아 파싱합니다.
    return fetch_report_artifact(latest)


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--checkpoint-uri", required=True)
    args = parser.parse_args()

    report = get_latest_regression_report(args.checkpoint_uri)
    if report["overall_gate_result"] != "PASS":
        print(f"게이트 실패: {args.checkpoint_uri}는 배포할 수 없습니다.", file=sys.stderr)
        sys.exit(1)
    print(f"게이트 통과: {args.checkpoint_uri} 배포를 진행합니다.")


if __name__ == "__main__":
    main()
----

이 스크립트를 배포 파이프라인의 첫 단계로 두면, "회귀 테스트를 통과하지 않은 체크포인트는 애초에 배포 파이프라인에 들어갈 수 없다"는 규칙이 코드로 강제됩니다.

== 알림과 가시성

게이트가 실패했을 때 사람이 바로 알아야 합니다. Sensor의 트리거 뒤에 알림용 트리거를 하나 더 붙일 수 있습니다.

[source,yaml]
----
    - template:
        name: notify-on-failure
        conditions: "checkpoint-dep"
        http:
          url: "https://hooks.slack.example.com/services/T000/B000/XXXX"
          method: POST
          payload:
            - src: {dependencyName: checkpoint-dep, dataKey: "s3.object.key"}
              dest: text
----

10장에서는 이 알림에 Rerun 시각화 링크를 함께 실어, 회귀가 감지된 순간 사람이 곧바로 어떤 장면이 왜 나빠졌는지 눈으로 확인할 수 있게 만듭니다.

== 요약

* PR 등 코드 변경은 GitHub Actions가, 클러스터 밖 체크포인트 업로드 같은 이벤트는 Argo Events(EventSource + Sensor)가 각각 워크플로를 트리거하는 자연스러운 경로입니다.
* `argo submit --wait`와 6장에서 만든 게이트 잡의 0이 아닌 종료 코드 조합으로, 회귀 감지가 곧바로 CI 체크 실패로 이어집니다.
* 브랜치 보호 규칙에 이 체크를 필수로 지정하면 PR 머지가, 배포 파이프라인 앞단에 게이트 조회 스크립트를 두면 배포가 각각 자동으로 막힙니다.
* 게이트 실패는 Slack 같은 알림 채널로 즉시 전파되어야 하며, 10장에서 이 알림에 시각적 진단 링크를 덧붙입니다.
