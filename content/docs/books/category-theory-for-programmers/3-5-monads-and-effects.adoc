작성자: 바르토슈 미레프스키

이제 모나드가 무엇을 위한 것인지 알게 되었습니다. 모나드는 '장식된 함수(embellished function)'를 합성할 수 있게 해줍니다. 여기서 정말 흥미로운 질문은, 왜 함수형 프로그래밍에서 이 장식된 함수가 그토록 중요한가 하는 점입니다. 우리는 이미 하나의 예로 Writer 모나드를 보았습니다. 장식(엠벨리시먼트)을 통해 여러 함수 호출에 걸쳐 로그를 생성하고 축적할 수 있었죠. 평소라면 불순 함수(예: 전역 상태에 접근하여 수정하는 방식)로 해결했을 문제를, 모나드를 통해 순수 함수만으로 해결해낸 것입니다.

== 문제 (The Problem)

여기에 에우제니오 모기(Eugenio Moggi)의 기념비적인 논문에서 발췌한 문제 목록이 있습니다. 이들은 전통적으로 함수의 순수성을 포기해야만 해결할 수 있다고 여겨져 온 문제들입니다.

- *부분성(Partiality)*: 계산이 종료되지 않을 수 있는 경우
- *비결정성(Nondeterminism)*: 계산이 여러 결과를 반환할 수 있는 경우
- *부수 효과(Side effects)*: 상태에 접근하거나 수정하는 계산
    - 읽기 전용 상태(환경)
    - 쓰기 전용 상태(로그)
    - 읽기/쓰기 상태
- *예외(Exceptions)*: 실패할 수 있는 부분 함수(partial functions)
- *컨티뉴에이션(Continuations)*: 프로그램의 상태를 저장했다가 필요할 때 복원하는 능력
- *대화형 입력(Interactive Input)*
- *대화형 출력(Interactive Output)*

정말 놀라운 사실은, 이 모든 문제들을 '장식된 함수로의 전환'이라는 동일하고 영리한 트릭으로 해결할 수 있다는 점입니다. 물론 각 경우마다 장식의 구체적인 형태는 완전히 다를 것입니다.

여기서 한 가지 짚고 넘어가야 할 점이 있습니다. 이 단계에서는 장식이 반드시 모나드적일 필요가 없다는 것입니다. 모나드가 필요해지는 시점은 우리가 '합성 가능성'을 요구할 때입니다. 즉 하나의 거대한 장식된 함수를 더 작은 장식된 함수들로 분해하고 다시 조립하고 싶을 때죠. 각 경우마다 장식 방식이 다르므로 모나드 합성의 구현도 서로 다릅니다. 하지만 전체적인 패턴은 동일합니다. 매우 단순한 패턴이죠. 바로 '결합 법칙을 만족하고 항등원을 갖춘 합성'입니다.

다음 섹션은 하스켈 예제가 많이 등장합니다. 카테고리 이론 본론으로 빨리 돌아가고 싶거나 하스켈의 모나드 구현에 이미 익숙하다면 가볍게 읽거나 건너뛰어서도 좋습니다.

== 해결책 (The Solution)

먼저 Writer 모나드를 사용했던 방식을 다시 분석해 봅시다. 우리는 특정 인수를 받아 특정 출력을 내놓는 순수 함수로 시작했습니다. 그리고 로깅 문제를 해결하기 위해, 원래의 출력값에 문자열을 짝지어 반환하는 장식된 함수로 이 함수를 교체했습니다.

하지만 거기서 멈출 수 없었습니다. 우리는 보통 거대하고 단일한(monolithic) 해결책을 원하지 않기 때문입니다. 하나의 로그 생성 함수를 더 작은 로그 생성 함수들로 분해할 수 있어야 했습니다. 그리고 이러한 작은 함수들을 다시 합성하려는 시도가 우리를 모나드라는 개념으로 이끌었습니다.

함수의 반환 타입을 장식하는 이 동일한 패턴이, 보통 순수성을 포기해야 하는 수많은 문제에 그대로 적용된다는 점은 정말 놀랍습니다. 이제 목록을 하나씩 살펴보고, 각 문제에 어떤 장식이 적용되는지 식별해 봅시다.

=== 부분성 (Partiality)

종료되지 않을 수 있는 모든 함수의 반환 타입을 "리프트된(lifted)" 타입으로 변경합니다. 리프트된 타입이란 원래 타입의 모든 값에 특수한 "바닥(bottom)" 값 ``⊥``을 추가한 타입을 의미합니다. 예를 들어 ``Bool`` 타입은 집합으로서 ``True``와 ``False`` 두 요소를 가지지만, 리프트된 ``Bool``은 세 요소를 가집니다. 리프트된 ``Bool``을 반환하는 함수는 ``True``나 ``False``를 생성할 수도 있지만, 영원히 실행될 수도 있습니다.

재미있는 점은 하스켈처럼 지연 평가(lazy)를 하는 언어에서는 종료되지 않는 함수도 실제로 값을 반환할 수 있고, 이 값이 다음 함수로 전달될 수 있다는 것입니다. 우리는 이 특수 값을 '바닥(bottom)'이라고 부릅니다. 이 값이 명시적으로 필요해지기 전까지는(예: 패턴 매칭에 사용되거나 최종 출력으로 내보낼 때), 프로그램 실행을 멈추지 않고도 이곳저곳으로 전달될 수 있습니다. 모든 하스켈 함수는 잠재적으로 비종료 가능성이 있으므로, 모든 하스켈 타입은 리프트된 것으로 간주됩니다. 우리가 단순한 ``Set`` 대신 리프트된 타입과 함수들의 카테고리인 ``Hask``를 자주 언급하는 이유가 바로 이것입니다. 다만 ``Hask``가 엄밀한 의미의 카테고리인지에 대해서는 link:http://math.andrej.com/2016/08/06/hask-is-not-a-category/[안드레이 바우어(Andrej Bauer)의 포스트]에서 보듯 논란의 여지가 있습니다.

=== 비결정론 (Nondeterminism)

함수가 여러 결과를 반환할 수 있다면, 그 결과들을 한꺼번에 반환하면 어떨까요? 의미론적으로 비결정적 함수는 결과 값들의 리스트를 반환하는 함수와 같습니다. 이는 지연 평가와 가비지 컬렉션을 지원하는 언어에서 매우 합리적인 접근입니다. 예를 들어 값이 하나만 필요하다면 리스트의 헤드(head)만 취하면 되고, 나머지 꼬리 부분은 평가조차 되지 않을 것입니다. 무작위 값이 필요하다면 난수 생성기로 리스트의 n번째 요소를 뽑으면 됩니다. 지연 평가 덕분에 무한한 결과 리스트를 반환하는 것도 가능합니다.

하스켈의 비결정적 계산 구현체인 리스트 모나드에서, ``join``은 ``concat``으로 구현됩니다. ``join``이 컨테이너 내부의 컨테이너를 평탄화(flatten)하는 역할임을 기억하신다면, 리스트의 리스트를 단일 리스트로 합치는 ``concat``이 왜 적절한지 이해하실 수 있을 것입니다. ``return``은 요소를 하나만 담은 싱글톤 리스트를 생성합니다.

[source,haskell]
----
instance Monad [] where
    join = concat
    return x = [x]
----

리스트 모나드의 ``bind`` 연산자는 ``fmap`` 후에 ``join``을 수행하는 일반 공식에 따라 다음과 같이 정의됩니다.

[source,haskell]
----
as >>= k = concat (fmap k as)
----

여기서 직접 리스트를 반환하는 함수 ``k``는 리스트 ``as``의 모든 요소에 적용됩니다. 그 결과로 만들어진 '리스트의 리스트'는 ``concat``을 거쳐 하나로 합쳐집니다.

프로그래머 입장에서는 루프 안에서 비결정적 함수를 호출하거나 이터레이터를 반환하는 함수를 만드는 것보다 리스트를 다루는 편이 훨씬 쉽습니다. (물론 현대 C++에서도 지연 평가를 하는 범위를 반환하면 하스켈의 리스트 반환과 거의 비슷하게 동작합니다.)

비결정성을 창의적으로 활용한 좋은 예는 게임 프로그래밍입니다. 예를 들어 체스 AI는 상대방의 다음 수를 예측할 수 없지만, 대신 가능한 모든 수의 리스트를 생성하여 하나씩 분석할 수 있습니다. 비슷하게 비결정적 파서(parser)는 주어진 표현식에 대해 가능한 모든 구문 분석 결과 리스트를 만들어낼 수 있습니다.

리스트를 반환하는 함수를 반드시 비결정성으로 해석할 필요는 없습니다. 리스트 모나드의 활용 범위는 훨씬 넓습니다. 리스트를 생성하는 계산들을 엮어내는 방식은 명령형 프로그래밍의 반복 구조(루프)를 함수형으로 대체하는 완벽한 수단이 되기 때문입니다. 단일 루프는 종종 리스트의 각 요소에 루프 본문을 적용하는 ``fmap``으로 바꿀 수 있고, 복잡한 중첩 루프는 리스트 모나드의 ``do`` 표기법으로 깔끔하게 대체할 수 있습니다.

제가 가장 좋아하는 예제는 피타고라스 삼중쌍(직각 삼각형의 세 변이 될 수 있는 양의 정수 조합)을 생성하는 프로그램입니다.

[source,haskell]
----
triples = do
    z <- [1..]
    x <- [1..z]
    y <- [x..z]
    guard (x^2 + y^2 == z^2)
    return (x, y, z)
----

첫 번째 줄은 ``z``가 양의 정수 무한 리스트 ``[1..]``에서 값을 하나씩 가져옴을 의미합니다. 그 다음 ``x``는 1부터 ``z`` 사이의 리스트 ``[1..z]``에서 값을 가져오고, ``y``는 ``x``부터 ``z`` 사이에서 값을 가져옵니다. 이제 우리에게는 ``1 <= x <= y <= z`` 조건을 만족하는 세 숫자 세트가 생겼습니다. ``guard`` 함수는 ``Bool`` 표현식을 받아 유닛(unit) 리스트를 반환합니다.

[source,haskell]
----
guard :: Bool -> [()]
guard True  = [()]
guard False = []
----

``MonadPlus``라고 불리는 더 큰 클래스의 멤버이기도 한 이 함수는, 여기에서 피타고라스 정리를 만족하지 않는 삼중쌍을 걸러내는 필터 역할을 합니다. 실제로 ``bind``(또는 관련 연산자 ``>>``)의 구현을 보면, 빈 리스트가 주어질 경우 빈 리스트를 반환한다는 것을 알 수 있습니다. 반면 비어 있지 않은 리스트(여기서는 유닛을 담은 리스트 ``[()]``)가 전달되면, ``bind``는 후속 과정인 ``return (x, y, z)``를 호출하여 검증된 삼중쌍을 담은 리스트를 만듭니다. 이 모든 싱글톤 리스트들은 바깥쪽의 ``bind``들에 의해 하나로 합쳐져 최종적인 (무한한) 결과 리스트가 됩니다. 물론 ``triples`` 호출자가 무한 리스트 전체를 소비할 수는 없겠지만, 하스켈은 지연 평가를 하므로 전혀 문제 되지 않습니다.

원래라면 세 개의 중첩 루프가 필요했을 문제가 리스트 모나드와 ``do`` 표기법 덕분에 비약적으로 단순화되었습니다. 하스켈은 여기서 한 걸음 더 나아가 '리스트 내포(list comprehension)' 문법을 제공하여 코드를 더 줄여줍니다.

[source,haskell]
----
triples = [(x, y, z) | z <- [1..]
                     , x <- [1..z]
                     , y <- [x..z]
                     , x^2 + y^2 == z^2]
----

이것은 리스트 모나드(엄밀히 말하면 ``MonadPlus``)를 위한 또 다른 구문 설탕(syntactic sugar)일 뿐입니다. 다른 함수형이나 명령형 언어에서는 제너레이터(generator)나 코루틴(coroutine)이라는 이름으로 이와 유사한 구조를 보실 수 있을 것입니다.

=== 읽기 전용 상태 (Read-Only State)

외부 상태나 환경에 읽기 전용으로 접근하는 함수는 언제나 그 환경을 추가 인수로 받는 함수로 바꿀 수 있습니다. 순수 함수 ``(a, e) -> b`` (여기서 ``e``는 환경의 타입)는 언뜻 보기에 클라이슬리 화살표처럼 보이지 않습니다. 하지만 이를 ``a -> (e -> b)``로 커링(curry)하는 순간, 이 장식이 우리의 오랜 친구인 Reader 함자임을 알아챌 수 있습니다.

[source,haskell]
----
newtype Reader e a = Reader (e -> a)
----

Reader를 반환하는 함수는 일종의 '미니 실행 프로그램'을 생성하는 것으로 해석할 수 있습니다. 즉, 환경이 주어지면 원하는 결과를 내놓는 액션(action)인 셈입니다. 이 액션을 실행하기 위해 ``runReader``라는 도우미 함수를 사용합니다.

[source,haskell]
----
runReader :: Reader e a -> e -> a
runReader (Reader f) e = f e
----

환경값에 따라 서로 다른 결과를 생성할 수 있습니다. 여기서 중요한 것은 Reader를 반환하는 함수도, Reader 액션 자체도 모두 순수하다는 점입니다.

Reader 모나드의 ``bind``를 구현하려면 먼저 환경 ``e``를 받아 ``b``를 생성하는 함수를 만들어야 합니다.

[source,haskell]
----
ra >>= k = Reader (\e -> ...)
----

람다 내부에서는 먼저 ``ra`` 액션을 실행하여 ``a``를 얻을 수 있습니다.

[source,haskell]
----
ra >>= k = Reader (\e -> let a = runReader ra e
                         in ...)
----

그 다음 얻어낸 ``a``를 후속 함수 ``k``에 전달하여 새로운 액션 ``rb``를 얻습니다.

[source,haskell]
----
ra >>= k = Reader (\e -> let a  = runReader ra e
                             rb = k a
                         in ...)
----

마지막으로 이 ``rb`` 액션을 동일한 환경 ``e``로 실행합니다.

[source,haskell]
----
ra >>= k = Reader (\e -> let a  = runReader ra e
                             rb = k a
                         in runReader rb e)
----

``return``은 환경을 무시하고 원래 값을 그대로 반환하는 액션을 만듭니다. 이 과정을 종합하고 몇 가지 단순화를 거치면 다음과 같은 정의가 나옵니다.

[source,haskell]
----
instance Monad (Reader e) where
    ra >>= k = Reader (\e -> runReader (k (runReader ra e)) e)
    return x = Reader (\e -> x)
----

=== 쓰기 전용 상태 (Write-Only State)

이것은 처음에 보았던 로깅 예제와 정확히 같습니다. 장식은 Writer 함자에 의해 이루어집니다.

[source,haskell]
----
newtype Writer w a = Writer (a, w)
----

완결성을 위해, 데이터 생성자를 풀어주는 간단한 도우미 함수 ``runWriter``도 있습니다.

[source,haskell]
----
runWriter :: Writer w a -> (a, w)
runWriter (Writer (a, w)) = (a, w)
----

이전에 살펴보았듯, Writer를 합성 가능하게 만들려면 ``w``가 반드시 모노이드여야 합니다. ``bind`` 연산자를 이용한 Writer의 모나드 인스턴스는 다음과 같습니다.

[source,haskell]
----
instance (Monoid w) => Monad (Writer w) where 
    (Writer (a, w)) >>= k = let (a', w') = runWriter (k a)
                            in Writer (a', w `mappend` w')
    return a = Writer (a, mempty)
----

=== 상태 (State)

상태에 읽고 쓸 수 있는 함수는 Reader와 Writer의 장식을 결합한 형태입니다. 상태를 추가 인수로 받고, 결과로 (값, 새로운 상태) 쌍을 반환하는 순수 함수 ``(a, s) -> (b, s)``로 생각할 수 있습니다. 커링을 거치면 ``a -> (s -> (b, s))`` 형식이 되며, 여기서 장식 부분은 State 함자로 추상화됩니다.

[source,haskell]
----
newtype State s a = State (s -> (a, s))
----

마찬가지로 클라이슬리 화살표가 액션을 반환한다고 보고, 이를 실행할 ``runState``를 정의합니다.

[source,haskell]
----
runState :: State s a -> s -> (a, s)
runState (State f) s = f s
----

초기 상태에 따라 결과 값뿐만 아니라 최종 상태도 달라질 수 있습니다. State 모나드의 ``bind`` 구현은 Reader와 매우 비슷하지만, 각 단계마다 변화된 상태를 올바르게 전달하는 데 주의를 기울여야 합니다.

[source,haskell]
----
sa >>= k = State (\s -> let (a, s') = runState sa s
                            sb = k a
                        in runState sb s')
----

전체 인스턴스 코드는 다음과 같습니다.

[source,haskell]
----
instance Monad (State s) where
    sa >>= k = State (\s -> let (a, s') = runState sa s 
                            in runState (k a) s')
    return a = State (\s -> (a, s))
----

또한 상태를 조작하기 위한 두 가지 도우미 클라이슬리 화살표가 있습니다. ``get``은 현재 상태를 확인하기 위해 꺼내오는 용도이고,

[source,haskell]
----
get :: State s s
get = State (\s -> (s, s))
----

``put``은 상태를 완전히 새로운 값으로 교체할 때 사용합니다.

[source,haskell]
----
put :: s -> State s ()
put s' = State (\s -> ((), s'))
----

=== 예외 (Exceptions)

예외를 던지는 명령형 함수는 실제로는 '부분 함수(partial function)'입니다. 특정 인수 값에 대해서는 결과가 정의되지 않기 때문입니다. 예외를 순수한 전함수(total function)로 구현하는 가장 간단한 방법은 Maybe 함자를 사용하는 것입니다. 부분 함수를 전함수로 확장하되, 계산이 의미 있을 때는 ``Just a``를 반환하고 그렇지 않을 때는 ``Nothing``을 반환하게 하는 것이죠. 실패 원인에 대한 정보까지 함께 반환하고 싶다면 Either 함자를 사용하면 됩니다(예: 첫 번째 타입을 ``String``으로 고정).

Maybe의 모나드 인스턴스는 다음과 같습니다.

[source,haskell]
----
instance Monad Maybe where
    Nothing >>= k = Nothing
    Just a  >>= k = k a
    return a = Just a
----

Maybe의 모나드 합성은 오류를 감지하는 즉시 계산을 올바르게 단락시킨다는 점에 주목하십시오. 후속 함수 ``k``는 절대 호출되지 않습니다. 이것이 바로 우리가 예외 처리 메커니즘에서 기대하는 동작입니다.

=== 컨티뉴에이션 (Continuations)

"우리에게 전화하지 마세요, 우리가 연락할게요!(Don't call us, we'll call you!)"라는 상황을 떠올려 보십시오. 구직 면접 후 흔히 듣는 말이죠. 직접적인 답변 대신 결과를 처리할 핸들러 함수를 넘겨주어야 하는 형태입니다. 이런 프로그래밍 방식은 호출 시점에 결과를 알 수 없을 때, 예를 들어 다른 스레드에서 계산이 진행 중이거나 원격 웹사이트에서 데이터를 가져오는 중일 때 특히 유용합니다. 이 경우 클라이슬리 화살표는 "나머지 계산 과정"을 의미하는 핸들러를 매개변수로 받는 함수를 반환합니다.

[source,haskell]
----
data Cont r a = Cont ((a -> r) -> r)
----

핸들러 ``a -> r``은 최종적으로 호출되면 타입 ``r``의 결과를 생성하며, 이 결과가 함수의 반환값이 됩니다. 컨티뉴에이션은 결과 타입 ``r``에 의해 매개변수화됩니다. (실제로 이 타입은 종종 어떤 종류의 상태 지시자로 쓰입니다.)

클라이슬리 화살표가 반환한 액션을 실행하는 도우미 함수도 있습니다. 이 함수는 핸들러를 받아서 컨티뉴에이션에 전달합니다.

[source,haskell]
----
runCont :: Cont r a -> (a -> r) -> r
runCont (Cont k) h = k h
----

컨티뉴에이션의 합성은 악명 높을 정도로 다루기 어렵기에, 모나드를 통해, 특히 ``do`` 표기법을 활용해 관리할 수 있다는 것은 엄청난 장점입니다.

``bind`` 구현을 파헤쳐 봅시다. 먼저 핵심만 추린 시그니처를 보겠습니다.

[source,haskell]
----
(>>=) :: ((a -> r) -> r) -> 
         (a -> (b -> r) -> r) -> 
         ((b -> r) -> r)
----

우리의 목표는 핸들러 ``(b -> r)``를 받아 최종 결과 ``r``을 만들어내는 함수를 정의하는 것입니다.

[source,haskell]
----
ka >>= kab = Cont (\hb -> ...)
----

람다 내부에서는 함수 ``ka``를 호출해야 하는데, 이때 "나머지 계산 전체"를 나타내는 적절한 핸들러를 넘겨줘야 합니다. 이 핸들러를 람다로 구현해 봅시다.

[source,haskell]
----
runCont ka (\a -> ...)
----

이 경우 "나머지 계산"이란 먼저 ``kab``를 ``a``로 호출하고, 그 결과로 나온 액션 ``kb``에 최종 핸들러 ``hb``를 전달하는 과정입니다.

[source,haskell]
----
runCont ka (\a -> let kb = kab a
                  in runCont kb hb)
----

보시다시피 컨티뉴에이션은 안쪽에서 바깥쪽으로 합성됩니다. 최종 핸들러 ``hb``는 계산의 가장 깊숙한 층에서 호출됩니다. 전체 인스턴스는 다음과 같습니다.

[source,haskell]
----
instance Monad (Cont r) where
    ka >>= kab = Cont (\hb -> runCont ka (\a -> runCont (kab a) hb))
    return a = Cont (\ha -> ha a)
----

=== 대화형 입력 (Interactive Input)

가장 까다롭고 혼란스러운 문제입니다. 키보드에서 입력된 문자를 반환하는 ``getChar`` 같은 함수는 명백히 순수할 수 없습니다. 하지만 만약 문자를 직접 반환하는 대신 '문자를 담은 컨테이너'를 반환한다면 어떨까요? 그 컨테이너에서 문자를 꺼낼 방법이 원천적으로 없다면, 우리는 이 함수를 순수하다고 주장할 수 있습니다. ``getChar``를 호출할 때마다 정확히 동일한 컨테이너가 반환될 테니까요. 개념적으로 이 컨테이너는 가능한 모든 문자들의 중첩(superposition)을 담고 있다고 볼 수 있습니다.

양자역학에 익숙하시다면 이 비유를 이해하는 데 어려움이 없을 것입니다. 마치 슈뢰딩거의 고양이가 든 상자와 같습니다. 단, 이 상자는 절대로 열어보거나 안을 들여다볼 수 없습니다. 이 상자는 특수한 내장 함자인 ``IO``로 정의됩니다. 우리 예제의 ``getChar``는 다음과 같은 클라이슬리 화살표로 선언할 수 있습니다.

[source,haskell]
----
getChar :: () -> IO Char
----

(실제로 유닛 타입에서의 함수는 반환 타입의 값을 선택하는 것과 같으므로, 단순히 ``getChar \:: IO Char``로 줄여 씁니다.)

``IO``는 함자이므로 ``fmap``으로 내부 내용을 조작할 수 있습니다. 그리고 함자로서 문자뿐만 아니라 어떤 타입의 값도 저장할 수 있습니다. 하지만 이 접근법의 진정한 효용은 하스켈에서 ``IO``가 모나드라는 점에서 나타납니다. 이는 ``IO`` 객체를 생성하는 클라이슬리 화살표들을 합성할 수 있다는 의미입니다.

클라이슬리 합성을 사용하면 ``IO`` 객체의 내용을 들여다볼 수 있을 거라 생각할 수도 있습니다. (양자역학 비유를 계속하자면 "파동 함수를 붕괴"시키는 셈이겠죠.) 실제로 ``getChar``를 문자를 받아 정수로 변환하는 다른 클라이슬리 화살표와 합성할 수 있습니다. 하지만 여기 함정이 있습니다. 이 두 번째 클라이슬리 화살표는 정수를 ``IO Int``로만 반환할 수 있다는 것입니다. 결국 다시 가능한 모든 정수들의 중첩 상태로 돌아갑니다. 이렇게 계속됩니다. 슈뢰딩거의 고양이는 결코 상자 밖으로 나오지 않습니다. 일단 ``IO`` 모나드 안으로 들어가면 빠져나올 방법이 없습니다. ``IO`` 모나드에는 ``runState``나 ``runReader``에 해당하는 함수가 없습니다. ``runIO`` 같은 것은 존재하지 않습니다!

그렇다면 클라이슬리 화살표의 결과물인 ``IO`` 객체로 무엇을 할 수 있을까요? 다른 클라이슬리 화살표와 합성하는 것 외에는요? 답은 ``main``에서 그것을 반환하는 것입니다. 하스켈에서 ``main``의 시그니처는 다음과 같습니다.

[source,haskell]
----
main :: IO ()
----

이를 클라이슬리 화살표로 생각하면 다음과 같습니다.

[source,haskell]
----
main :: () -> IO ()
----

이런 관점에서 보면 하스켈 프로그램은 그저 ``IO`` 모나드 안의 거대한 클라이슬리 화살표 하나입니다. 더 작은 클라이슬리 화살표들을 모나드 합성으로 엮어서 만드는 것이죠. 그리고 최종 결과물인 ``IO`` 객체(일명 IO 액션)로 무언가를 하는 것은 런타임 시스템의 책임입니다.

여기서 주목할 점은 화살표 자체는 순수 함수라는 것입니다. 끝까지 순수 함수들로만 이루어져 있습니다. 더러운 작업은 시스템으로 격리됩니다. 시스템이 최종적으로 ``main``에서 반환된 IO 액션을 실행할 때, 비로소 사용자 입력을 읽고, 파일을 수정하고, 불쾌한 메시지를 출력하고, 디스크를 포맷하는 등 온갖 더러운 일들을 처리합니다. 하스켈 프로그램 자체는 결코 손을 더럽히지 않습니다. (물론 ``unsafePerformIO``를 호출하는 경우는 예외지만, 그것은 다른 이야기입니다.)

물론 하스켈은 지연 평가를 하므로, ``main``은 거의 즉시 반환되고 더러운 작업은 곧바로 시작됩니다. IO 액션이 실행되는 동안 순수 계산의 결과가 요청되면 그때그때 필요에 따라 평가됩니다. 따라서 실제로 프로그램은 순수한 코드(하스켈)와 더러운 코드(시스템)가 서로 교차하며 실행됩니다.

``IO`` 모나드에 대한 또 다른 해석도 있는데, 훨씬 더 기괴하지만 수학적 모델로는 완벽하게 말이 됩니다. 온 우주(Universe)를 프로그램 내의 객체로 취급하는 것입니다. 주목할 점은, 개념적으로 명령형 모델은 우주를 외부의 전역 객체로 취급하기에, I/O를 수행하는 프로시저는 이 객체와 상호작용함으로써 부수 효과를 발생시킨다는 것입니다. 우주의 상태를 읽거나 수정할 수 있으니까요.

함수형 프로그래밍에서 상태를 다루는 법은 이미 알고 있습니다. State 모나드를 사용하면 됩니다. 다만 단순한 상태와 달리, 우주의 상태는 표준 데이터 구조로 쉽게 기술할 수 없습니다. 하지만 직접 상호작용하지 않는 한 그럴 필요도 없습니다. ``RealWorld``라는 타입이 존재하고, 우주 공학의 기적으로 런타임이 이 타입의 객체를 제공할 수 있다고 가정하는 것만으로 충분합니다. 그러면 IO 액션은 그저 다음과 같은 함수가 됩니다.

[source,haskell]
----
type IO a  =  RealWorld -> (a, RealWorld)
----

또는 State 모나드의 관점에서 이렇게 쓸 수도 있습니다.

[source,haskell]
----
type IO = State RealWorld
----

단, ``IO`` 모나드의 ``>=>`` 및 ``return``은 언어에 내장되어 있어야 합니다.

=== 대화형 출력 (Interactive Output)

대화형 출력 역시 같은 ``IO`` 모나드로 캡슐화됩니다. ``RealWorld``가 모든 출력 장치를 포함한다고 가정하는 것이죠. 하스켈에서 출력 함수를 그냥 호출하고 아무 일도 하지 않는 척할 수 없는 이유가 궁금할 수 있습니다. 왜 다음과 같이 하지 않는 걸까요.

[source,haskell]
----
putStr :: String -> IO ()
----

대신 더 간단하게:

[source,haskell]
----
putStr :: String -> ()
----

두 가지 이유가 있습니다. 첫째, 하스켈은 지연 평가를 하므로, 출력값(여기서는 유닛 객체)이 어디에도 사용되지 않는 함수는 절대 호출하지 않습니다. 둘째, 지연 평가가 아니더라도 컴파일러가 이런 호출들의 순서를 자유롭게 바꿔버려 출력이 뒤섞일 수 있습니다. 하스켈에서 두 함수를 순차적으로 실행하도록 강제하는 유일한 방법은 데이터 의존성입니다. 한 함수의 입력이 다른 함수의 출력에 의존해야 하는 것이죠. ``RealWorld``를 IO 액션들 사이에서 주고받게 하면 순차성이 강제됩니다.

개념적으로 다음 프로그램을 살펴봅시다.

[source,haskell]
----
main :: IO ()
main = do
    putStr "Hello "
    putStr "World!"
----

"World!"를 출력하는 액션은 입력으로 "Hello "가 이미 화면에 있는 우주를 받습니다. 그리고 출력으로 "Hello World!"가 화면에 있는 새로운 우주를 내놓습니다.

== 결론 (Conclusion)

물론 저는 모나드 프로그래밍의 겉만 핥은 것에 불과합니다. 모나드는 명령형 프로그래밍에서 통상 부수 효과로 처리하던 일들을 순수 함수로도 할 수 있게 해줄 뿐만 아니라, 높은 수준의 제어와 타입 안전성까지 제공합니다. 하지만 단점이 없지는 않습니다. 모나드에 대한 주요 불만은 서로 쉽게 합성되지 않는다는 점입니다. 물론 모나드 변환기(monad transformer) 라이브러리를 사용하면 대부분의 기본 모나드들을 결합할 수 있습니다. 예를 들어 상태와 예외를 결합한 모나드 스택을 만드는 것은 비교적 쉽습니다. 하지만 임의의 모나드들을 함께 쌓아 올리는 공식은 존재하지 않습니다.
