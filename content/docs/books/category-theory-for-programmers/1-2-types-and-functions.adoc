'''
타입과 함수로 이루어진 카테고리는 프로그래밍에서 매우 중요한 역할을 합니다. 이번 장에서는 타입이란 무엇인지, 그리고 왜 타입이 필요한지에 대해 이야기해 보겠습니다.

== 누가 타입을 필요로 하는가?

정적 타입 대 동적 타입(static vs. dynamic), 강한 타입 대 약한 타입(strong vs. weak)의 장단점에 대한 논쟁은 끊이지 않습니다. 이러한 선택이 갖는 의미를 한 가지 사고 실험으로 알아보겠습니다. 수백만 마리의 원숭이가 컴퓨터 키보드 앞에서 행복하게 무작위로 키를 두드리며 프로그램을 만들고, 컴파일하고, 실행한다고 상상해 봅시다.

image::https://y30n9ju1v.github.io/develop/images/books/category-theory-for-programmers/img_1329.jpg[원숭이와 타자기]

기계어라면 원숭이가 만들어낸 그 어떤 바이트 조합이라도 일단 받아들여져 실행될 것입니다. 하지만 고수준 언어를 사용하는 우리는 컴파일러가 어휘 오류와 문법 오류를 감지해 준다는 사실을 매우 고맙게 생각합니다. 덕분에 수많은 원숭이가 바나나를 얻지 못하겠지만, 남은 프로그램들이 유용할 가능성은 훨씬 높아집니다. 타입 검사(type checking)는 말도 안 되는 프로그램의 탄생을 막는 또 하나의 강력한 장벽입니다. 더욱이, 동적 타입 언어에서는 타입 불일치가 런타임(runtime)에야 발견되는 반면, 정적 타입 언어에서는 컴파일 타임에 발견됩니다. 이를 통해 수많은 잘못된 프로그램이 채 실행되기도 전에 걸러집니다.

결국 질문은 이것입니다. 우리는 원숭이들에게 마구잡이로 프로그램을 만들게 할 것인가, 아니면 올바른 프로그램을 만들 것인가?

타자 치는 원숭이 사고 실험의 궁극적인 목표는 보통 셰익스피어 전집을 완성하는 것입니다. 여기에 맞춤법 검사기와 문법 검사기를 도입한다면 성공 확률은 비약적으로 높아질 것입니다. 타입 검사기는 여기서 한 걸음 더 나아갑니다. 예를 들어 로미오가 일단 '인간'으로 선언되었다면, 갑자기 나뭇잎이 돋아나거나 강력한 중력장으로 광자를 끌어들이는 블랙홀로 변신하지 않도록 보장합니다.

== 타입은 합성 가능성에 관한 것입니다

카테고리 이론은 화살표(모피즘, morphism)를 합성하는 학문입니다. 하지만 모든 화살표를 무턱대고 합성할 수는 없습니다. 한 화살표의 대상 객체(target object)가 다음 화살표의 시작 객체(source object)와 일치해야 합니다. 프로그래밍에서도 마찬가지입니다. 우리는 한 함수의 결과를 다른 함수로 전달합니다. 만약 뒤에 오는 함수가 앞선 함수가 생성한 데이터를 제대로 해석하지 못한다면 프로그램은 정상적으로 작동하지 않을 것입니다. 합성이 성립하려면 두 끝점이 서로 맞물려야 합니다. 언어의 타입 시스템이 강력할수록 이러한 맞물림을 더 정확하게 기술하고 기계적으로 검증할 수 있습니다.

강한 정적 타입 검사에 반대하는 논리 중 그나마 진지한 주장은, 의미론적으로는 아무런 문제가 없는 프로그램조차 타입 시스템이 거부할 수 있다는 점입니다. 하지만 실제로 이런 일이 발생하는 경우는 극히 드뭅니다. 게다가 대부분의 언어는 정말 필요한 경우 타입 시스템을 우회할 수 있는 '뒷문'을 마련해 둡니다. 하스켈의 ``unsafeCoerce``가 대표적인 예입니다. 물론 이런 도구는 매우 신중하게 사용해야 합니다. 프란츠 카프카의 소설 속 인물인 그레고르 잠자(Gregor Samsa)는 거대한 벌레로 변신하면서 스스로의 타입 시스템을 파괴했고, 우리 모두는 그 결말이 어떠했는지 잘 알고 있습니다.

또 다른 흔한 주장은 타입을 일일이 지정하는 것이 프로그래머에게 너무 큰 부담이라는 것입니다. C++에서 복잡한 반복자(iterator) 선언을 직접 써본 사람이라면 이 말에 어느 정도 공감할 것입니다. 하지만 다행히도 *타입 추론(type inference)* 이라는 기술이 있습니다. 컴파일러가 주변 맥락을 통해 타입을 스스로 알아내는 것입니다. C++에서도 이제 ``auto`` 키워드를 사용하여 컴파일러에게 타입 결정을 맡길 수 있습니다.

하스켈에서는 아주 예외적인 경우를 제외하면 타입 주석(type annotation)이 선택 사항입니다. 그럼에도 불구하고 하스켈 프로그래머들은 타입 주석을 적극적으로 사용합니다. 타입이 코드의 의미(semantics)를 명확히 드러내며, 컴파일 오류를 훨씬 이해하기 쉽게 만들어 주기 때문입니다. 하스켈에서 프로젝트를 시작할 때 타입을 먼저 설계하는 것은 매우 흔한 관행입니다. 이렇게 작성한 타입 주석은 구현을 이끄는 가이드가 되며, 컴파일러가 강제하는 살아있는 주석의 역할을 수행합니다.

강한 정적 타입 시스템이 오히려 테스트를 소홀히 하는 핑계로 사용되기도 합니다. 가끔 하스켈 프로그래머들이 "컴파일만 되면 이미 정확하다"라고 호기롭게 말하는 것을 들을 수 있습니다. 물론 타입이 올바르다고 해서 프로그램이 의도한 결과를 정확히 낸다는 보장은 없습니다. 이런 낙관적인 태도 탓인지, 여러 연구에 따르면 하스켈의 코드 품질이 기대만큼 압도적으로 높지는 않았다고 합니다. 상업적인 환경에서 버그 수정 압박은 대개 특정 품질 수준까지만 주어지며, 이는 프로그래밍 언어나 방법론보다는 소프트웨어 개발의 경제성이나 최종 사용자의 인내심과 더 깊은 관련이 있습니다. 더 공정한 기준은 프로젝트가 일정을 얼마나 잘 지키는지, 혹은 기능 축소 없이 의도한 대로 완성되었는지를 측정하는 것일 겁니다.

단위 테스트가 강한 타입을 대체할 수 있다는 주장도 있습니다. 하지만 리팩토링 시 함수 인자의 타입을 변경하는 상황을 생각해 보십시오. 강한 타입 언어에서는 함수 선언을 수정하고 컴파일 에러가 발생하는 지점을 모두 고치면 충분합니다. 반면 약한 타입 언어에서는 함수가 요구하는 데이터 형식이 바뀌었다는 사실이 호출부로 전파되지 않습니다. 단위 테스트로 일부 오류를 잡아낼 수는 있겠지만, 테스트는 근본적으로 확률적인 과정일 뿐 결정론적이지 않습니다. 테스트는 '증명'을 대신하기에는 역부족입니다.

== 타입이란 무엇인가?

타입에 대한 가장 간단한 직관은 '값들의 집합(set of values)'이라는 것입니다. ``Bool`` 타입(하스켈에서 구체적인 타입은 대문자로 시작합니다)은 ``True``와 ``False``라는 두 원소를 가진 집합입니다. ``Char`` 타입은 'a'나 'ą' 같은 모든 유니코드 문자의 집합입니다.

집합은 유한할 수도, 무한할 수도 있습니다. 문자열을 뜻하는 ``String`` 타입(하스켈에서 ``Char``의 리스트인 ``[Char]``의 별칭)은 무한 집합의 한 예입니다.

다음과 같이 ``x``를 ``Integer``로 선언한다면,

[source,haskell]
----
x :: Integer
----

이는 ``x``가 정수 집합의 원소라는 뜻입니다. 하스켈의 ``Integer``는 가변 정밀도 산술을 지원하는 무한 집합입니다. C++의 ``int``처럼 하드웨어 사양에 맞춘 유한 집합인 ``Int`` 타입도 별도로 존재합니다.

물론 타입과 집합을 완벽히 동일시하기에는 몇 가지 까다로운 수학적 문제들이 얽혀 있습니다. 가령 다형성 함수(polymorphic function)의 순환 정의 문제나 "모든 집합을 포함하는 집합은 존재할 수 없다"는 러셀의 역설 등이 그것입니다. 하지만 앞서 약속했듯이 수학적인 엄격함에 너무 매몰되지는 않겠습니다. 다행히 *Set*이라 불리는 '집합의 카테고리'가 존재하며, 우리는 이를 활용할 것입니다. *Set* 카테고리에서 대상(object)은 집합이고, 모피즘(morphism 또는 arrow)은 함수입니다.

*Set*은 매우 특별한 카테고리입니다. 우리는 객체 내부(집합의 원소들)를 직접 들여다보며 유용한 직관을 얻을 수 있습니다. 예를 들어, 빈 집합에는 원소가 없다는 점, 원소가 하나뿐인 특별한 집합들이 존재한다는 점 등을 알고 있습니다. 또한 함수가 한 집합의 원소를 다른 집합의 원소로 연결한다는 사실도 압니다. 함수는 두 원소를 하나의 원소로 보낼 수는 있지만, 하나의 원소를 두 개로 쪼개어 보낼 수는 없습니다. 모든 원소를 자기 자신에게 연결하는 항등 함수도 알고 있습니다. 우리의 계획은 이러한 개별 원소에 대한 정보를 점진적으로 잊어버리고, 그 모든 개념을 객체와 화살표라는 '순수 카테고리 이론적 관점'에서 다시 정의하는 것입니다.

이상적인 세계에서는 하스켈 타입을 집합으로, 하스켈 함수를 집합 간의 수학적 함수로 간주해도 무방합니다. 하지만 실무적으로는 한 가지 작은 걸림돌이 있습니다. 수학적 함수는 계산 과정을 거치지 않고 오직 정해진 결괏값만 가집니다. 반면 하스켈 함수는 실제로 답을 계산해야 합니다. 단계가 아무리 많더라도 유한한 시간 내에 답을 낼 수 있다면 큰 문제가 없습니다. 하지만 재귀 호출이 포함된 계산처럼 결코 끝나지 않을 가능성이 있는 함수가 문제입니다. 유명한 '정지 문제(halting problem)'에서 알 수 있듯이, 함수가 멈출지 아닐지를 미리 판단하는 것은 불가능하므로 하스켈에서 이를 아예 금지할 수도 없습니다. 이를 해결하기 위해 컴퓨터 과학자들은 모든 타입에 *바텀(bottom)* 이라 불리는 특별한 값을 추가하기로 했습니다. 기호로는 ``_|_`` 또는 유니코드 ``⊥``로 표기합니다. 이 '값'은 종료되지 않는 계산을 의미합니다. 따라서 다음과 같이 선언된 함수는,

[source,haskell]
----
f :: Bool -> Bool
----

``True``, ``False`` 뿐만 아니라 절대 종료되지 않는다는 의미의 ``⊥``를 반환할 수도 있습니다.

흥미롭게도 바텀을 타입 시스템의 일부로 수용하면, 모든 런타임 에러를 바텀으로 간주할 수 있고 심지어 함수가 명시적으로 바텀을 반환하도록 할 수도 있습니다. 보통 ``undefined``라는 표현식을 사용하여 다음과 같이 구현합니다.

[source,haskell]
----
f :: Bool -> Bool
f x = undefined
----

``undefined``는 모든 타입의 원소인 바텀(``⊥``)으로 평가되기 때문에 위 코드는 성공적으로 타입 검사를 통과합니다. 심지어 인자 ``x``를 생략하고 다음과 같이 쓸 수도 있습니다.

[source,haskell]
----
f :: Bool -> Bool
f = undefined
----

바텀은 함수 타입인 ``Bool -> Bool``의 원소이기도 하기 때문입니다.

결코 종료되지 않거나 에러를 발생시켜 바텀을 반환할 수 있는 함수를 *부분 함수(partial function)* 라고 하며, 모든 인자에 대해 항상 유효한 결과를 내놓는 함수를 *전체 함수(total function)* 라고 부릅니다.

이 바텀의 존재 때문에 하스켈 타입과 함수의 카테고리는 엄밀히 말해 *Set*이 아니라 *Hask*라고 불립니다. 이론적으로 들어가면 이는 끝도 없는 복잡함의 원천이 되기에, 여기서는 정육점 도끼를 휘둘러 이 논의를 깔끔하게 자르겠습니다. 실용적인 관점에서는 무한 루프나 바텀을 잠시 무시하고 *Hask*를 진정한 *Set*으로 취급하며 논의를 진행해도 충분합니다(자세한 내용은 마지막 참고문헌을 확인하세요).

== 왜 수학적 모델이 필요한가?

프로그래머는 자신이 사용하는 언어의 구문(syntax)과 문법(grammar)에 매우 친숙합니다. 이러한 정보는 명세서 맨 처음에 형식적인 표기법으로 잘 설명되어 있기 때문입니다. 하지만 언어의 실제 의미인 *의미론(semantics)* 을 설명하는 일은 훨씬 까다롭습니다. 수백 페이지에 달하는 설명이 필요하며, 대개 형식적이지도 않고 불완전합니다. 그러다 보니 명세의 미묘한 차이를 두고 전문가들 사이에서 끝없는 논쟁이 벌어지고, 언어 표준의 세부 사항을 해석하는 수많은 책이 쏟아져 나오게 됩니다.

언어의 의미론을 기술하는 형식적인 도구들이 없는 것은 아닙니다. 하지만 그 복잡성 때문에 대개 실무용 거대 언어보다는 단순화된 학술용 언어에 적용되곤 합니다. 그중 *동작 의미론(operational semantics)* 은 프로그램 실행의 메커니즘을 기술하며, 일종의 '형식화되고 이상화된 인터프리터'를 정의합니다. C++ 같은 산업계 언어의 의미론은 대개 '추상 기계'에 기반한 비정형적이고 절차적인 추론을 통해 설명됩니다.

동작 의미론의 문제는 이를 가지고 프로그램의 속성을 증명하기가 매우 어렵다는 점입니다. 특정 속성을 증명하려면 결국 이상화된 인터프리터를 통해 프로그램을 직접 '돌려봐야' 하기 때문입니다.

프로그래머들이 평소에 엄격한 수학적 증명을 하지 않는다는 사실은 그리 중요하지 않습니다. 우리는 항상 자신이 올바른 프로그램을 작성하고 있다고 '생각'합니다. 아무도 "그냥 대충 몇 줄 던져보고 무슨 일이 생기는지 보자"는 마음으로 키보드를 잡지 않습니다. 우리는 우리가 쓴 코드가 특정 동작을 수행하여 원하는 결과를 낼 것이라고 믿습니다. 그리고 그것이 빗나갈 때 깜짝 놀라곤 합니다. 즉, 우리는 항상 머릿속에서 인터프리터를 실행하며 프로그램에 대해 추론하고 있는 셈입니다. 다만 수많은 변수를 한꺼번에 추적하는 것이 인간에게는 너무 가혹할 뿐입니다. 컴퓨터는 프로그램 실행을 잘하고, 인간은 추론을 잘해야 합니다. 만약 우리가 프로그램 실행을 완벽하게 할 수 있었다면 애초에 컴퓨터가 필요하지 않았을 겁니다.

하지만 주효한 대안이 있습니다. 바로 수학에 기반한 *지시 의미론(denotational semantics)* 입니다. 지시 의미론에서는 모든 프로그래밍 구조에 상응하는 수학적 해석(denotation)이 부여됩니다. 이 방식에서는 프로그램의 속성을 증명하는 일이 곧 수학 정리를 증명하는 일이 됩니다. 정리 증명이라고 하면 지레 겁을 먹을 수도 있겠지만, 인류는 수천 년 동안 수학적 방법론을 다듬어 왔으며 활용할 수 있는 지식의 양은 어마어마합니다. 또한 전문 수학자들이 증명하는 정리에 비해 우리가 프로그래밍에서 마주하는 문제들은 대개 훨씬 단순하고 명확합니다.

지시 의미론을 적용하기 좋은 하스켈의 팩토리얼 함수 정의를 살펴봅시다.

[source,haskell]
----
fact n = product [1..n]
----

``[1..n]``은 1부터 n까지의 정수 리스트이고, ``product``는 리스트의 모든 요소를 곱하는 함수입니다. 이는 수학 교과서에 나오는 팩토리얼의 정의와 거의 일치합니다. 이제 이를 C 언어와 비교해 봅시다.

[source,c]
----
int fact(int n) {
    int i;
    int result = 1;
    for (i = 2; i <= n; ++i)
        result *= i;
    return result;
}
----

더 설명이 필요할까요?

물론 이것이 다소 편파적인 예시라는 점은 저도 인정합니다! 팩토리얼이야 워낙 수학적인 성격이 강하니까요. 기민한 독자라면 이렇게 물을 수도 있습니다. "키보드에서 문자를 입력받거나 네트워크로 패킷을 보내는 행위의 수학적 모델은 무엇인가?"라고 말입니다. 한동안 이 질문은 매우 답하기 까다로웠고, 복잡하고 억지스러운 설명이 뒤따라야 했습니다. 실용적인 프로그램 작성에 필수적인 상당수 작업이 동작 의미론으로는 쉽게 다룰 수 있지만 지시 의미론으로는 잘 맞지 않는 것처럼 보였습니다.

하지만 카테고리 이론에서 돌파구가 마련되었습니다. 에우제니오 모기(Eugenio Moggi)는 '계산 효과(computational effect)'를 *모나드(monad)* 에 매핑할 수 있다는 사실을 발견했습니다. 이 통찰은 지시 의미론에 새로운 생명을 불어넣었을 뿐만 아니라, 순수 함수형 프로그램을 실용적으로 만들었고 전통적인 프로그래밍 방식을 바라보는 새로운 시각을 제시했습니다. 모나드에 대해서는 나중에 카테고리 이론적 도구들을 더 많이 배운 뒤에 자세히 다루겠습니다.

프로그래밍을 위한 수학적 모델을 갖는다는 것의 가장 큰 이점 중 하나는 소프트웨어의 정확성을 '형식적으로 증명'할 수 있다는 점입니다. 일반 사용자용 소프트웨어를 만들 때는 그리 중요하지 않게 느껴질 수도 있겠지만, 조그마한 실수로 엄청난 비용이 발생하거나 인명이 위태로워지는 분야에서는 이야기가 달라집니다. 혹은 의료 시스템용 웹 애플리케이션을 개발할 때라도, 하스켈 표준 라이브러리의 함수들과 알고리즘이 수학적으로 검증되어 정확성이 증명되었다는 사실을 안다면 마음이 한결 가벼워질 것입니다.

== 순수 함수와 지저분한 함수 (Pure and Dirty Functions)

C++ 같은 명령형 언어에서 말하는 '함수'는 수학자가 말하는 '함수'와 다릅니다. 수학적 함수는 그저 값과 값을 연결하는 대응 관계(mapping)일 뿐입니다.

프로그래밍 언어에서 수학적 함수를 구현할 수 있습니다. 이런 함수는 입력값이 주어지면 출력값을 계산합니다. 어떤 수의 제곱을 계산하는 함수는 아마도 입력값을 그 자신과 곱할 것입니다. 함수가 호출될 때마다 매번 이 계산을 수행하며, 같은 입력에 대해서는 항상 같은 출력을 내놓습니다. 어떤 숫자의 제곱은 달의 위상에 따라 바뀌지 않으니까요.

또한 숫자의 제곱을 계산하는 도중에 강아지에게 간식을 내보내는 부수 효과가 발생해서는 안 됩니다. 그런 일을 하는 '함수'는 수학적 함수로 쉽게 모델링할 수 없습니다.

프로그래밍 언어에서 같은 입력에 대해 항상 같은 결과를 내놓고 부수 효과(side effect)가 없는 함수를 *순수 함수(pure function)* 라고 부릅니다. 하스켈 같은 순수 함수형 언어에서는 모든 함수가 순수합니다. 덕분에 이러한 언어들은 지시 의미론을 부여하고 카테고리 이론으로 모델링하기가 훨씬 수월합니다. 다른 언어를 사용할 때라도 순수한 부분만 골라 사용하거나 부수 효과를 별도로 관리하며 추론할 수 있습니다. 나중에 모나드를 통해 순수 함수만으로 어떻게 모든 종류의 효과를 모델링하는지 보게 될 것입니다. 즉, 우리 자신을 수학적 함수로 제한한다고 해서 실제로 잃는 것은 아무것도 없습니다.

== 타입의 다양한 형태들

타입이 곧 집합임을 이해했다면, 조금 독특한 타입들도 생각해 볼 수 있습니다. 예를 들어, 원소가 하나도 없는 '빈 집합'에 해당하는 타입은 무엇일까요? C++의 ``void``일까요? 아니요, 하스켈에서는 이 타입을 ``Void``라고 부르며 C++의 ``void``와는 전혀 다른 개념입니다. ``Void``는 어떤 값도 가질 수 없는 타입입니다. 이를 인자로 받는 함수를 정의할 수는 있지만, 호출할 방법은 없습니다. 호출하려면 ``Void`` 타입의 값을 넘겨줘야 하는데 세상에 그런 값은 존재하지 않기 때문입니다.

이 함수가 무엇을 반환하는지에 대해서는 아무런 제약이 없습니다. 어떤 타입이든 반환할 수 있습니다(물론 호출 자체가 불가능하니 실제로 반환될 일도 없겠지만요). 즉, 반환 타입에 대해 *다형적(polymorphic)* 인 함수가 됩니다. 하스켈 개발자들은 이를 다음 이름으로 부릅니다.

[source,haskell]
----
absurd :: Void -> a
----

(``a``는 모든 타입을 대신할 수 있는 타입 변수입니다.) 이 이름은 우연이 아닙니다. '커리-하워드 동형 모피즘(Curry-Howard isomorphism)'이라 불리는 논리학적 관점에서 타입과 함수를 해석하는 방식이 있는데, 여기서 ``Void``는 '거짓(falsity)'을 뜻합니다. ``absurd`` 함수의 타입은 "거짓으로부터는 어떤 결론도 도출할 수 있다(ex falso sequitur quodlibet)"는 라틴어 격언에 대응됩니다.

다음은 *단원소 집합(singleton set)*, 즉 원소가 딱 하나뿐인 집합에 대응하는 타입입니다. 이 타입은 단 하나의 값만 가질 수 있으며, 그 값은 그저 '존재'할 뿐입니다. 눈치채기 어려울 수도 있겠지만 이것이 바로 C++의 ``void``입니다.

이 타입을 주고받는 함수를 상상해 보십시오. ``void``로부터 시작하는 함수는 언제나 호출 가능합니다. 만약 순수 함수라면 매번 똑같은 결과를 내놓겠죠. 예를 들면 이렇습니다.

[source,cpp]
----
int f44() { return 44; }
----

이 함수가 '아무것도' 받지 않는다고 생각할 수도 있지만, 앞서 보았듯이 정말로 '아무것도(Nothing)' 받지 않는 함수는 호출조차 불가능합니다. 그렇다면 이 함수는 무엇을 받는 걸까요? 개념적으로 이 함수는 '더미 값(dummy value)'을 받는데, 이 값은 오직 하나의 인스턴스만 존재하기 때문에 명시적으로 언급할 필요가 없는 것입니다. 하스켈에서는 이 값을 나타내는 기호가 있습니다. 바로 빈 괄호 쌍 ``()``입니다. 재미있게도(혹은 우연일까요?) C++와 하스켈 모두 ``void`` 함수를 호출할 때 빈 괄호를 사용합니다. 또한 하스켈의 극도의 간결함 추구 정신 덕분에 ``()``라는 기호는 타입, 생성자, 그리고 단원소 집합에 대응하는 유일한 값 모두를 나타냅니다. 하스켈로 위 함수를 작성하면 다음과 같습니다.

[source,haskell]
----
f44 :: () -> Integer
f44 () = 44
----

첫 번째 줄은 ``f44``가 '유닛(unit)'이라 읽는 ``()`` 타입을 받아 ``Integer`` 타입을 내놓는다는 선언입니다. 두 번째 줄은 유닛의 유일한 생성자인 ``()``를 패턴 매칭하여 숫자 44를 반환하도록 정의한 것입니다. 이 함수를 호출할 때는 유닛 값 ``()``를 제공합니다.

[source,haskell]
----
f44 ()
----

주목할 점은 유닛으로부터의 모든 함수가 대상 타입에서 하나의 원소를 '선택'하는 행위와 동등하다는 것입니다(여기서는 ``Integer`` 44를 선택했습니다). 사실 ``f44``를 숫자 44의 또 다른 표현 방식이라고 봐도 무방합니다. 이는 집합의 원소를 직접 언급하는 대신 함수(화살표)로 표현할 수 있음을 보여주는 사례입니다. 유닛에서 임의의 타입 ``A``로 가는 함수들은 집합 ``A``의 원소들과 일대일로 대응됩니다.

반대로 ``void``를 반환하거나 하스켈에서 유닛을 반환하는 함수는 어떨까요? C++에서 이런 함수는 보통 부수 효과를 위해 사용되지만, 수학적인 의미의 순수 함수는 아닙니다. 유닛을 반환하는 순수 함수는 사실상 아무것도 하지 않습니다. 인자를 받아서 그저 버릴 뿐입니다.

수학적으로 보면 어떤 집합 ``A``에서 단원소 집합으로 가는 함수는 ``A``의 모든 원소를 단원소 집합의 유일한 그 원소로 매핑합니다. 모든 집합 ``A``에 대해 이러한 함수는 오직 하나뿐입니다. ``Integer``를 예로 들면 이렇습니다.

[source,haskell]
----
fInt :: Integer -> ()
fInt x = ()
----

어떤 정수를 주든 결과는 항상 유닛(``()``)입니다. 간결함을 위해 하스켈에서는 버려지는 인자에 와일드카드인 밑줄(``_``)을 사용할 수 있습니다. 이렇게 하면 변수 이름을 지을 필요가 없습니다.

[source,haskell]
----
fInt :: Integer -> ()
fInt _ = ()
----

주목할 점은 이 함수의 구현이 전달받는 값뿐만 아니라 인자의 타입에도 전혀 의존하지 않는다는 것입니다.

모든 타입에 대해 동일한 수식으로 구현될 수 있는 함수를 *매개변수적 다형성(parametrically polymorphic)* 을 가졌다고 말합니다. 구체적인 타입 대신 타입 매개변수를 사용하면 이러한 함수들을 하나의 식으로 정의할 수 있습니다. 모든 타입에서 유닛 타입으로 가는 이 다형성 함수를 무엇이라 부를까요? 당연히 ``unit``이라 부릅니다.

[source,haskell]
----
unit :: a -> ()
unit _ = ()
----

C++로는 다음과 같이 표현할 수 있습니다.

[source,cpp]
----
template<class T>
void unit(T) {}
----

타입의 유형을 더 살펴보면 이제 두 원소를 가진 집합이 나옵니다. C++에서는 ``bool``, 하스켈에서도 예상대로 ``Bool``입니다. 차이점은 C++에서 ``bool``은 내장 타입이지만 하스켈에서는 다음과 같이 직접 정의할 수 있다는 점입니다.

[source,haskell]
----
data Bool = True | False
----

(이 정의를 읽는 방법은 "Bool은 True 또는 False이다"입니다.) 원칙적으로 C++에서도 열거형(enum)을 사용하여 부울 타입을 정의할 수 있을 것입니다.

[source,cpp]
----
enum bool {
    true,
    false
};
----

하지만 C++의 ``enum``은 속으로는 정수입니다. C++11의 ``enum class``를 쓸 수도 있겠지만, 사용할 때마다 ``bool\::true``나 ``bool\::false``처럼 클래스 이름으로 한정해야 하고, 사용하는 모든 파일에 적절한 헤더를 포함시켜야 하니 번거롭습니다.

``Bool`` 타입으로부터 출발하는 순수 함수는 대상 타입에서 두 개의 값을 선택하는 것과 같습니다. 하나는 ``True``에 대응하고, 다른 하나는 ``False``에 대응합니다.

반대로 ``Bool``을 반환하는 함수를 *술어(predicate)* 라고 합니다. 하스켈의 ``Data.Char`` 라이브러리는 ``isAlpha``나 ``isDigit`` 같은 술어들로 가득합니다. C++에도 비슷한 ``<cctype>`` 라이브러리가 있는데, ``isalpha``와 ``isdigit`` 같은 함수들을 정의하지만 이들은 부울이 아닌 ``int``를 반환합니다. 실제 술어는 ``std\::ctype``에 정의되어 있으며 ``ctype\::is(alpha, c)``, ``ctype\::is(digit, c)`` 같은 형태를 취합니다.

== 도전 과제

1. 좋아하는 언어로 고차 함수(또는 함수 객체) ``memoize``를 구현해 보십시오. 이 함수는 순수 함수 ``f``를 인자로 받아 ``f``와 거의 똑같이 동작하는 함수를 반환합니다. 단, 메모이제이션된 함수는 각 인자에 대해 원본 함수를 딱 한 번만 호출하고 그 결과를 내부 저장소에 보관했다가, 이후 같은 인자로 호출될 때마다 저장된 값을 즉시 반환해야 합니다. 계산 시간이 매우 오래 걸리는 함수를 메모이제이션해 보십시오. 처음 호출할 때는 결과를 기다려야 하지만, 같은 인자로 다시 호출하면 즉시 결과를 얻을 수 있을 것입니다. 성능 차이를 직접 관찰하여 메모이제이션된 함수와 원본 함수를 구분할 수 있습니다.
2. 각 언어의 표준 라이브러리에서 제공하는 난수 생성 함수를 대상으로 ``memoize``를 적용해 보십시오. 의도한 대로 작동합니까?
3. 대부분의 난수 생성기는 시드(seed)로 초기화할 수 있습니다. 시드 값을 인자로 받아 난수 생성기를 해당 시드로 호출하고 그 결과를 반환하는 함수를 작성한 뒤, 이를 메모이제이션해 보십시오. 이번에는 잘 작동합니까?
4. 다음 C++ 함수 중 어떤 것이 순수 함수입니까? 직접 메모이제이션해 본 뒤, 여러 번 호출했을 때(원본과 메모이제이션 버전) 어떤 일이 벌어지는지 관찰하십시오.
    - 본문에 나온 팩토리얼 함수
    - ``std\::getchar()``
    - ``bool f() { std\::cout << "Hello!" << std\::endl; return true; }``
    - ``int f(int x) { static int y = 0; y += x; return y; }``
5. ``Bool``에서 ``Bool``로 가는 서로 다른 함수의 개수는 모두 몇 개입니까? 그 함수들을 모두 구현할 수 있습니까?
6. ``Void``, ``()`` (유닛), ``Bool`` 세 객체로만 구성된 카테고리를 그려보십시오. 이들 사이의 가능한 모든 함수(화살표)를 그려 넣고 각 화살표에 함수의 이름을 붙여 보십시오.
