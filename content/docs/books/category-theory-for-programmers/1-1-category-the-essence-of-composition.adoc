작성자: 바르토슈 미레프스키(Bartosz Milewski)

이전 글인 "프로그래머를 위한 카테고리 이론: 서문"에 보내주신 뜨거운 반응에 정말 깜짝 놀랐습니다. 기쁜 마음 한편으로, 독자분들이 저에게 거는 기대가 얼마나 높은지 깨닫고는 덜컥 겁이 나기도 했습니다. 제가 어떤 내용을 써도 많은 독자가 실망할 것 같아 걱정스럽습니다. 어떤 분은 더 실무적인 내용을, 어떤 분은 더 추상적인 내용을 원하실 테니까요. C++를 싫어해서 모든 예제가 하스켈로 작성되기를 바라는 분도 있고, 하스켈을 싫어해서 자바 예제를 요구하는 분도 있을 겁니다. 또한 누군가에게는 설명 속도가 너무 느리고, 누군가에게는 너무 빠를 수도 있습니다. 이 책은 완벽한 책이 되지는 못할 것이며, 어느 정도 타협의 산물이 될 것입니다. 제가 바라는 것은 제가 느꼈던 수많은 "아하!" 하는 깨달음의 순간들을 독자 여러분과 함께 나눌 수 있기를 바랄 뿐입니다. 이제 기초부터 시작해 보겠습니다.

카테고리(category)는 당황스러울 정도로 단순한 개념입니다. 카테고리는 객체(object)와 그 객체들 사이를 잇는 화살표(arrow)로 구성됩니다. 그래서 그림으로 표현하기가 아주 쉽습니다. 객체는 원이나 점으로 그리고, 화살표는... 말 그대로 화살표로 그리면 됩니다. (변화를 주기 위해 가끔 객체를 돼지로, 화살표를 불꽃놀이로 그리기도 할 겁니다.) 하지만 카테고리의 본질은 *합성(composition)*에 있습니다. 다르게 말하면, 합성의 본질이 곧 카테고리라고도 할 수 있죠. 화살표는 합성될 수 있습니다. 객체 A에서 객체 B로 가는 화살표가 있고, 객체 B에서 객체 C로 가는 또 다른 화살표가 있다면, 반드시 A에서 C로 직접 가는 화살표—즉, 두 화살표의 합성—가 존재해야 합니다.

image::https://y30n9ju1v.github.io/develop/images/books/category-theory-for-programmers/img_1330.jpg[]

카테고리에서 A에서 B로 가는 화살표와 B에서 C로 가는 화살표가 있다면, 반드시 A에서 C로 직접 가는 화살표도 있어야 하며, 이것이 바로 두 화살표의 합성입니다. 참고로 위 그림은 항등 모피즘(identity morphism)이 빠져 있어 완전한 카테고리는 아닙니다(항등 모피즘은 잠시 후에 설명하겠습니다).

== 함수로서의 화살표
(Arrows as Functions)

벌써 너무 추상적이라고 느껴지나요? 낙담하지 마세요. 구체적인 이야기를 해봅시다. 화살표를 모피즘(morphism)이라고도 부르는데, 이를 함수로 이해하면 더 쉽습니다. 타입 A의 인자를 받아 B를 반환하는 함수 ``f``가 있고, B를 받아 C를 반환하는 또 다른 함수 ``g``가 있습니다. ``f``의 결과를 ``g``에 전달하면 두 함수를 합성할 수 있습니다. 이렇게 하면 A를 받아 C를 반환하는 새로운 함수가 정의됩니다.

수학에서는 이러한 합성을 함수 사이에 작은 원을 넣어 ``g ∘ f``로 표기합니다. 합성 순서가 오른쪽에서 왼쪽이라는 점에 주목하세요. 이게 헷갈릴 수 있습니다. 유닉스에서 다음과 같은 파이프 표기법에 익숙하신 분들도 있을 겁니다.

[source,bash]
----
lsof | grep Chrome
----

F#의 쉐브론 ``>>``도 왼쪽에서 오른쪽으로 진행됩니다. 하지만 수학과 하스켈에서 함수는 오른쪽에서 왼쪽으로 합성됩니다. ``g ∘ f``를 "f 다음의 g(g after f)"라고 읽으면 이해가 쉬워집니다.

C 코드로 더 명확하게 표현해 봅시다. 타입 A의 인자를 받아 타입 B의 값을 반환하는 함수 ``f``가 있습니다.

[source,c]
----
B f(A a);
----

그리고 또 다른 함수가 있습니다.

[source,c]
----
C g(B b);
----

이 둘의 합성은 다음과 같습니다.

[source,c]
----
C g_after_f(A a)
{
    return g(f(a));
}
----

여기서도 오른쪽에서 왼쪽으로의 합성을 볼 수 있습니다. C에서는 ``g(f(a))``처럼 표현됩니다.

C++ 표준 라이브러리에 두 함수를 받아 그 합성을 반환하는 템플릿이 있다면 좋겠지만, 아쉽게도 없습니다. 그러니 기분 전환 삼아 하스켈을 살펴봅시다. 다음은 A에서 B로 가는 함수의 선언입니다.

[source,haskell]
----
f :: A -> B
----

마찬가지로:

[source,haskell]
----
g :: B -> C
----

이 둘의 합성은 다음과 같이 씁니다.

[source,haskell]
----
g . f
----

하스켈로 이렇게 간단히 표현할 수 있다는 걸 보면, C++에서는 이런 기본적인 함수형 개념조차 표현하기 까다롭다는 사실이 다소 민망하게 느껴집니다. 하스켈은 유니코드 문자도 지원하기 때문에 합성을 다음과 같이 쓸 수도 있습니다.

[source,haskell]
----
g ∘ f
----

유니코드 이중 콜론이나 화살표도 사용할 수 있죠.

[source,haskell]
----
f ∷ A → B
----

자, 첫 번째 하스켈 수업입니다. 이중 콜론(``\::``)은 "...의 타입이다"라는 뜻입니다. 함수 타입은 두 타입 사이에 화살표(``->``)를 넣어서 만듭니다. 두 함수를 합성하려면 함수 사이에 마침표(``.``) 또는 유니코드 원(``∘``)을 넣으면 됩니다.

== 합성의 성질
(Properties of Composition)

모든 카테고리의 합성이 만족해야 하는 매우 중요한 두 가지 성질이 있습니다.

1. *합성은 결합법칙(associativity)을 만족합니다.* 세 개의 모피즘 ``f``, ``g``, ``h``가 합성 가능하다면(즉, 각 모피즘의 시작과 끝 객체가 연쇄적으로 일치한다면), 합성할 때 괄호가 필요 없습니다. 수학 표기법으로는 다음과 같습니다.
+
[source,haskell]
----
    h ∘ (g ∘ f) = (h ∘ g) ∘ f = h ∘ g ∘ f
----
+
(의사) 하스켈로는 다음과 같습니다.
+
[source,haskell]
----
    f :: A -> B
    g :: B -> C
    h :: C -> D
    h . (g . f) == (h . g) . f == h . g . f
----
+
("의사"라는 표현을 쓴 이유는 하스켈에서 함수 간의 동등성(``==``)이 정의되어 있지 않기 때문입니다.)
+
함수를 다룰 때 결합법칙은 매우 자명해 보이지만, 다른 카테고리에서는 그렇지 않을 수도 있습니다.
2. *모든 객체 A에 대해 합성의 단위 원소(unit) 역할을 하는 화살표가 존재합니다.* 이 화살표는 객체에서 자기 자신으로 향하는 루프입니다. 합성의 단위 원소라는 것은, A에서 시작하거나 A에서 끝나는 임의의 화살표와 합성했을 때 원래의 화살표를 그대로 돌려준다는 뜻입니다. 객체 A에 대한 단위 화살표를 stem:[\text{id}_A](A의 항등 모피즘, identity on A)라고 부릅니다. 수학 표기법으로 ``f``가 A에서 B로 가는 화살표라면 다음이 성립합니다.
+
[source,haskell]
----
    f ∘ idA = f
----
+
그리고
+
[source,haskell]
----
    idB ∘ f = f
----
+
함수의 세계에서 항등 모피즘은 단순히 인자를 그대로 반환하는 *항등 함수(identity function)*로 구현됩니다. 모든 타입에 대해 구현 방식이 같으므로, 이 함수는 보편적으로 *다형적(universally polymorphic)*입니다. C++에서는 이를 템플릿으로 정의할 수 있습니다.
+
[source,cpp]
----
    template<class T> T id(T x) { return x; }
----
+
물론 C++에서는 전달하는 값뿐만 아니라 전달 방식(값, 참조, const 참조, 이동 등)까지 고려해야 하므로 실제로는 이보다 복잡합니다.
+
하스켈에서 항등 함수는 표준 라이브러리(``Prelude``)의 일부입니다. 다음은 그 선언과 정의입니다.
+
[source,haskell]
----
    id :: a -> a
    id x = x
----
+
보시다시피 하스켈에서 다형적 함수를 만드는 것은 매우 쉽습니다. 선언에서 타입을 *타입 변수(type variable)*로 바꾸기만 하면 됩니다. 여기서 한 가지 요령: 구체적인 타입 이름은 항상 대문자로 시작하고, 타입 변수 이름은 소문자로 시작합니다. 따라서 여기서 ``a``는 모든 타입을 나타냅니다.
+
하스켈의 함수 정의는 함수 이름 다음에 형식 매개변수가 오는 형태입니다. 여기서는 ``x`` 하나만 있습니다. 함수 본문은 등호(``=``) 다음에 위치합니다. 이런 간결함이 처음에는 낯설 수 있지만, 곧 자연스럽게 느껴질 겁니다. 함수 정의와 호출은 함수형 프로그래밍의 근간이기 때문에 문법이 최소한으로 축소되어 있습니다. 인자 목록을 감싸는 괄호도 없고, 인자를 구분하는 쉼표도 없습니다(나중에 여러 인자를 받는 함수를 정의할 때 보게 됩니다).
+
함수 본문은 항상 *표현식(expression)*입니다. 함수 안에 문장(statement)은 없습니다. 함수의 결과는 바로 이 표현식의 값입니다. 여기서는 단순히 ``x``죠.
+
이것으로 두 번째 하스켈 수업을 마칩니다.
+
항등 조건은 (다시 한번 의사 하스켈로) 다음과 같이 쓸 수 있습니다.

[source,haskell]
----
    f . id == f
    id . f == f
----

    "아무것도 하지 않는 항등 함수가 왜 필요하지?"라는 의문이 들 수 있습니다. 그렇다면 "왜 숫자 0이 필요한가?"라는 질문도 해봅시다. 0은 '아무것도 없음'을 나타내는 기호입니다. 고대 로마인들은 0이 없는 숫자 체계로도 훌륭한 도로와 수로를 건설했고, 그중 일부는 오늘날까지 남아 있습니다.

    하지만 0이나 ``id`` 같은 중립값(neutral value)은 기호 변수를 다룰 때 매우 유용합니다. 로마인들이 대수학에 약했던 반면, 0의 개념을 알았던 아랍인과 페르시아인들이 대수학을 크게 발전시킬 수 있었던 이유이기도 합니다. 항등 함수는 고차 함수(higher-order function)의 인자로 전달되거나 반환값으로 사용될 때 진가를 발휘합니다. 고차 함수는 함수를 기호적으로 조작할 수 있게 해주며, 이것이 바로 함수의 대수학입니다.

    요약하자면: 카테고리는 객체와 화살표(모피즘)로 구성됩니다. 화살표는 합성할 수 있으며, 합성은 결합법칙을 따릅니다. 모든 객체는 합성의 단위 원소 역할을 하는 항등 모피즘을 가집니다.

== 합성은 프로그래밍의 본질이다
(Composition is the Essence of Programming)

함수형 프로그래머들은 문제를 접근하는 방식이 독특합니다. 매우 선(禪, Zen)적인 질문을 던지는 것부터 시작하죠. 예를 들어, 대화형 프로그램을 설계할 때는 "상호작용이란 무엇인가?"를 묻고, 콘웨이의 생명 게임(Conway's Game of Life)을 구현할 때는 생명의 의미를 숙고합니다. 같은 맥락에서 저도 질문을 하나 던져보겠습니다. "프로그래밍이란 무엇인가?"

가장 기본적인 수준에서 프로그래밍은 컴퓨터에게 무엇을 할지 명령하는 것입니다. "메모리 주소 x의 내용을 가져와서 레지스터 EAX에 더하라"처럼 말이죠. 하지만 어셈블리로 프로그래밍할 때조차도, 우리가 내리는 명령은 더 의미 있는 무언가를 표현하는 수단입니다. 우리는 사소하지 않은(non-trivial) 문제를 풀고 있는 것입니다(사소한 문제라면 컴퓨터의 도움이 필요 없겠죠). 그렇다면 문제를 어떻게 해결할까요? 큰 문제를 더 작은 문제들로 분해(decompose)합니다. 작은 문제가 여전히 크다면 더 잘게 쪼개고, 이 과정을 반복합니다. 최종적으로 우리는 모든 작은 문제를 해결하는 코드를 작성하게 됩니다.

그리고 여기서 프로그래밍의 본질이 나타납니다. 우리는 그 코드 조각들을 *합성(compose)*하여 더 큰 문제에 대한 해결책을 만들어냅니다. 조각들을 다시 조립할 수 없다면 분해는 의미가 없습니다.

이러한 계층적 분해와 재합성 과정은 컴퓨터가 강요한 것이 아니라 인간 두뇌의 한계를 반영한 것입니다. 우리 뇌는 한 번에 소수의 개념만 다룰 수 있습니다. 심리학에서 가장 많이 인용되는 논문 중 하나인 *The Magical Number Seven, Plus or Minus Two*(마법의 숫자 7, 더하기 빼기 2)는 우리가 한 번에 7 ± 2개의 정보 덩어리(chunk)만 머릿속에 담을 수 있다고 제안했습니다. 인간의 단기 기억에 대한 세부적인 이해는 변할 수 있지만, 그것이 제한적이라는 사실만은 확실합니다.

결론적으로 우리는 객체들이 뒤죽박죽 섞인 수프나 스파게티 코드를 감당할 수 없습니다. 우리에게 구조가 필요한 이유는 잘 짜인 프로그램이 보기 좋아서가 아니라, 구조 없이는 우리 뇌가 효율적으로 처리할 수 없기 때문입니다. 우리는 흔히 어떤 코드를 '우아하다'거나 '아름답다'고 표현하지만, 이는 실상 제한된 인지 능력으로 처리하기 쉽다는 의미입니다. 우아한 코드는 우리의 정신적 소화 기관이 받아들이기에 적절한 크기와 개수의 덩어리를 만들어냅니다.

그렇다면 프로그램 합성에 적합한 덩어리는 무엇일까요? 덩어리의 표면적이 부피보다 느리게 증가해야 합니다. (이 비유가 좋은 이유는 기하학적 객체의 표면적은 크기의 제곱에 비례해서 증가하고 부피는 세제곱에 비례해서 증가한다는 직관 때문입니다.) 표면적은 덩어리들을 합성하는 데 필요한 정보이고, 부피는 덩어리를 구현하는 데 필요한 정보입니다. 핵심은, 일단 덩어리가 구현되면 세부 구현 내용은 잊어버리고 다른 덩어리와 어떻게 상호작용하는지에만 집중할 수 있어야 한다는 것입니다. 객체 지향 프로그래밍에서 표면은 클래스 선언 또는 추상 인터페이스이고, 함수형 프로그래밍에서는 함수 선언입니다. (다소 단순화했지만, 이것이 핵심입니다.)

카테고리 이론은 객체 내부를 들여다보는 것을 적극적으로 막는다는 점에서 극단적입니다. 카테고리 이론에서 객체는 추상적이고 모호한 존재입니다. 객체에 대해 알 수 있는 유일한 정보는 다른 객체와의 관계, 즉 화살표로 어떻게 연결되어 있는지뿐입니다. 이는 인터넷 검색 엔진이 웹사이트 순위를 매길 때 들어오고 나가는 링크를 분석하는 것과 비슷합니다(물론 검색 엔진이 부정행위를 하지 않는다는 전제하에). 객체 지향 프로그래밍에서도 이상화된 객체는 추상 인터페이스(순수한 표면, 부피 없음)를 통해서만 드러나야 하며, 메서드가 화살표 역할을 합니다. 다른 객체와 합성하기 위해 객체의 내부 구현을 들여다봐야 한다면, 여러분은 이미 그 프로그래밍 패러다임이 주는 이점을 상실한 것입니다.
