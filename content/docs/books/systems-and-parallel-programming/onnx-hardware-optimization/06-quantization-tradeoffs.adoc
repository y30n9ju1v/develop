5장은 동적 양자화가 17배 느려지는 걸 봤습니다 — 하지만 "양자화 = 느림"이라고 결론 내리기 전에 확인해야 할 게 남았습니다. 양자화에는 여러 방식이 있고, `onnxruntime`이 표준으로 제공하는 또 다른 방식(정적 양자화)이 완전히 다른 결과를 낼 수도 있습니다.

== 동적 양자화 vs 정적 양자화

5장에서 쓴 **동적 양자화**는 가중치만 미리 INT8로 바꾸고, 활성값(레이어 출력)의 스케일은 추론 중에 매번 새로 계산합니다 — 유연하지만, 그 "매번 계산"이 오버헤드입니다. **정적 양자화**는 반대입니다 — 실제 배포 환경과 비슷한 데이터(보정 데이터, calibration data)를 몇 번 흘려보고 활성값의 범위를 미리 통계로 구해서, 가중치와 활성값을 **둘 다** 미리 고정된 스케일로 양자화합니다. 그 결과 그래프에 `QuantizeLinear`/`DequantizeLinear`(QDQ) 노드 쌍이 미리 삽입되고, 추론 중에는 그 고정된 스케일만 쓰면 됩니다.

[source,python]
----
from onnxruntime.quantization import quantize_static, QuantType, QuantFormat, CalibrationDataReader

class RandCalib(CalibrationDataReader):
    def __init__(self, n=20):
        self.data = iter([{"input": (np.random.randn(1,3,224,224).astype(np.float32)*0.5+0.5)}
                           for _ in range(n)])
    def get_next(self):
        return next(self.data, None)

quantize_static("resnet18.onnx", "resnet18_static_int8.onnx", RandCalib(),
                 quant_format=QuantFormat.QDQ, weight_type=QuantType.QInt8,
                 activation_type=QuantType.QInt8)
----

보정 데이터로 무작위 텐서를 썼다는 점을 짚어둡니다 — 실전에서는 실제 배포 환경에서 나올 법한 데이터(예: 실제 사진들)를 써야 활성값 범위 추정이 정확해집니다. 이 장은 "정적 양자화가 속도에 미치는 영향"을 보는 게 목적이라 이 정도로 충분하지만, 6장 마지막 절에서 이 선택의 한계를 다시 짚습니다.

== 실측: 정적 양자화는 얼마나 빠른가

[source]
----
fp32:                 4.735ms/inference   (46.75 MB)
int8 (동적, 5장):     82.519ms/inference  (11.74 MB)
int8 (정적 QDQ):       2.546ms/inference  (11.75 MB)
----

**정적 양자화는 FP32보다 오히려 1.86배 빠릅니다.** 크기는 동적 양자화와 거의 같은데(11.75MB vs 11.74MB), 속도는 정반대입니다 — 동적 양자화 대비 무려 32배 빠릅니다. 5장의 "양자화는 이 환경에서 느리다"는 결론은 **틀렸던 게 아니라 불완전했습니다** — 정확히는 "5장에서 쓴 동적 양자화 방식은 이 환경에서 느리다"였어야 합니다.

== 왜 방식에 따라 이렇게 다른가

5장에서 `ConvInteger`라는 연산자가 최적화된 경로를 못 탄다고 진단했습니다. 정적 양자화(QDQ 형식)는 다른 전략을 씁니다 — Conv 앞뒤에 `QuantizeLinear`/`DequantizeLinear`를 넣어서 그래프 자체는 "FP32 Conv를 QDQ 노드로 감싼" 형태를 유지합니다. `onnxruntime`은 이 패턴(Conv를 QDQ가 감싼 형태)을 인식해서, 3장에서 본 것과 비슷한 **융합**을 적용해 QDQ+Conv를 하나로 합친 하드웨어 최적화 커널로 대체할 수 있습니다 — 반면 5장의 `ConvInteger`는 애초에 다른 연산자라서 이 융합 경로를 못 탑니다. 즉 이 환경에서의 진짜 차이는 "몇 비트를 쓰는가"가 아니라 **"그 비트 수를 어떤 연산자 패턴으로 표현하는가"** 였습니다 — 하드웨어 벤더가 어떤 패턴에 최적화된 커널을 제공하느냐가 실제 속도를 결정합니다.

== 정확도는: 이 책이 검증할 수 없는 것

크기와 속도는 확실하게 측정했지만, **정확도**는 이 책이 정직하게 한계를 인정해야 하는 부분입니다. ImageNet 검증셋 같은 레이블 있는 실제 데이터가 이 세션 환경에는 없어서, 무작위 텐서로 두 모델의 출력이 얼마나 일치하는지만 볼 수 있습니다.

[source,python]
----
agree = 0
for _ in range(30):
    xi = np.random.randn(1,3,224,224).astype(np.float32)*0.5+0.5
    yf = sess_fp32.run(None, {"input": xi})[0]
    ys = sess_static.run(None, {"input": xi})[0]
    if yf.argmax() == ys.argmax(): agree += 1
print(f"top1 agreement: {agree}/30")
----

[source]
----
top1 agreement: 17/30  (56.7%)
----

**이 숫자를 "정적 양자화가 정확도를 43% 깎는다"로 읽으면 안 됩니다.** 입력이 진짜 사진이 아니라 무작위 노이즈이기 때문입니다 — ResNet18은 자연 이미지의 통계(가장자리, 질감, 색상 분포)로 학습됐지, 순수 노이즈로 학습되지 않았습니다. 노이즈를 넣으면 애초에 FP32 모델 자체도 "확신 없는" 애매한 출력(여러 클래스의 확률이 비슷하게 낮은)을 내놓기 쉽고, 그런 상황에서는 아주 작은 수치 차이(양자화든 뭐든)로도 최댓값(top-1)이 쉽게 뒤집힙니다. 진짜 정확도 손실을 재려면 실제 이미지와 정답 레이블(ImageNet 검증셋 같은)이 필요하고, 이 세션 환경에는 그게 없습니다 — 그래서 이 책은 "정적 양자화가 이 환경에서 크기 4분의 1, 속도 1.86배 개선을 실측으로 보여줬다"까지만 확인했다고 밝히고, 정확도에 대해서는 **검증하지 못했다**고 명시적으로 인정합니다. 실전 배포 전에는 반드시 실제 검증 데이터로 정확도 저하를 따로 측정해야 합니다.

== 3부 정리

[cols="2,1,1"]
|===
|방식 |크기 |속도(FP32=4.735ms 대비)

|동적 양자화(5장) |11.74MB(1/4) |82.519ms (17배 느림)
|정적 QDQ 양자화(6장) |11.75MB(1/4) |2.546ms (1.86배 빠름)
|===

같은 "INT8 양자화"라는 이름 아래 정반대의 결과가 나올 수 있다는 게 3부의 결론입니다 — 그리고 이 책이 정직하게 검증하지 못한 축(정확도)이 있다는 것도 함께 남겨둡니다. 4부에서는 그래프 최적화·양자화 다음 단계 — 이 그래프가 실제로 하드웨어의 명령어로 어떻게 낮아지는지(MLIR lowering) — 로 넘어갑니다.

== 직접 해보기

정적 양자화의 `activation_type`을 `QInt8` 대신 `QUInt8`(부호 없는 8비트)로 바꾸면 속도나 크기가 달라질까요? 부호 유무가 표현 범위(대칭 vs 비대칭)에 영향을 준다는 걸 감안해서 예상해보고 확인해보세요.

.해답 보기
[%collapsible]
====
[source,python]
----
quantize_static("resnet18.onnx", "resnet18_static_uint8.onnx", RandCalib(),
                 quant_format=QuantFormat.QDQ, weight_type=QuantType.QInt8,
                 activation_type=QuantType.QUInt8)
----

[source]
----
static QDQ uint8 activation: 3.059ms/inference   (size: 11.75 MB)
----

크기는 거의 같지만(11.75MB, `QInt8` 버전과 사실상 동일), 속도는 뜻밖에 **더 느려졌습니다**(2.546ms → 3.059ms, 약 20%) — "부호 없는 타입이 표현 범위를 더 알차게 써서 유리하다"는 통념은 정확도 얘기였지, 속도가 좋아진다는 보장은 아니었습니다. ReLU를 많이 쓰는 ResNet18은 활성값이 대부분 음수가 안 나와서(ReLU 출력은 항상 ≥0) `QUInt8`이 표현 범위를 더 알차게 쓸 수 있어 정확도 면에서는 유리하다고 알려져 있지만, 이 환경에서는 그 자료형 선택이 하드웨어가 가장 최적화한 커널 경로와 정확히 안 맞아떨어진 것으로 보입니다 — 5장에서 본 "패턴이 하드웨어의 최적화 경로와 맞아떨어지는가"가 여기서도 반복됩니다, 다만 이번엔 그 차이가 17배가 아니라 20%로 훨씬 작을 뿐입니다. 이 선택은 결국 (이 책이 검증하지 못한) 정확도와 이 장이 실측한 속도 사이의 트레이드오프이고, 실전에서는 둘 다 실측해서 정해야 한다는 뜻입니다.
