== 지나온 길

1부에서는 TaskGrid의 가장 naive한 버전 — 코디네이터와 워커가 공유 ``int progress``를 동기화 없이 두들기는 코드 — 로 데이터 경쟁을 실제로 일으켜 ThreadSanitizer로 검출하고, ``std::jthread``가 소멸자로 "join을 잊는" 버그를 막는다는 걸 확인한 뒤, 순서가 있는 API(`WorkerConnection`)가 순서를 어겨도 컴파일된다는 것으로 이 책 전체가 채울 다섯 개의 빈칸(타입 상태, 이동 전용 타입, concepts, 분리 논리, CRDT)에 대한 지도를 그렸습니다.

2부에서는 타입 상태 패턴으로 세션 타입을 흉내냈습니다 — 상태마다 다른 타입, rvalue 한정 메서드, `requires` 절로 프로토콜을 어긴 호출이 실제로 컴파일 실패가 되는 걸 여러 번 확인했고, ``std::lock_guard``가 이미 같은 원리를 쓰고 있다는 것과 ``std::promise``가 같은 계약을 런타임에만 강제한다는 대비도 확인했습니다.

3부에서는 이동 전용 타입으로 선형 타입을 흉내냈습니다 — ``std::unique_ptr``와 손으로 짠 ``DataSegmentHandle``이 복사를 컴파일 타임에 거부하고, 이동 후 원본이 안전한 무효 상태가 된다는 걸 AddressSanitizer로 확인했고, ``WorkerConnection``과 합쳐 ``WorkerSession``을 이룬 뒤 Rule of Zero로 합성이, 스택 되감기로 예외 안전성이 "공짜로" 따라온다는 것까지 확인했습니다 — 그리고 이 부의 마지막 장(9장)에서는 ``WorkerSession``이 완성된 뒤에야 나올 수 있는 실전 문제로 넘어가, 락이 하나가 아니라 둘 이상일 때는 타입 상태도 이동 전용 타입도 못 막는 새로운 종류의 실수(AB-BA 교착 상태)를 코디네이터의 재분배 로직에서 실제로 재현하고, ``std::scoped_lock``과 전역 락 순서 규칙으로 고쳤습니다 — 이 세션의 TSan이 lock-order-inversion 자체는 진단하지 못한다는 플랫폼 한계를 정직하게 확인한 것도 이 장이었습니다.

4부에서는 concepts로 범주론적 인터페이스를 짜서, `std::optional`/``std::expected``가 실제로 Functor·Monad라는 걸 ``static_assert``로 확인하고, `WorkerSession` 두 개를 ``std::async``로 진짜 병렬 처리시켜 그 결과를 ``and_then``으로 안전하게 합성했습니다 — 그리고 ``std::future``엔 표준 ``.then()``이 없다는 한계를, 직접 만든 근사와 함께 정직하게 마주했습니다. 이 부의 마지막 장(12장)에서는 손으로 짠 `Task<T>` 코루틴 타입으로 같은 `.and_then()` 체인을 `co_await` 순차 문법으로 다시 써보면서, 이것도 실행기와 취소 전파가 없는 또 다른 거친 근사라는 걸 정직하게 짚었습니다.

5부에서는 동시성 분리 논리의 "겹치지 않으면 안전하다"는 발상을 ``std::span``을 쪼개는 ``split_at``으로 인코딩해, 코디네이터가 공유 입력 버퍼를 워커들에게 겹치지 않게 나눠주는 문제를 풀었습니다 — ``split_at``을 거치지 않고 손으로 겹치게 만들면 TSan이 실제로 경쟁을 잡아낸다는 것도 확인했고, 그 과정에서 TSan 자체가 "실제로 일어난 접근만 잡는" 동적 도구라 짧게 스쳐 가는 겹침은 놓칠 수 있다는 것까지, 처음 시도한 예제가 실패하면서 정직하게 배웠습니다.

6부에서는 지금까지와 정반대의 전략인 CRDT를 다뤘습니다 — 동시 접근을 막는 대신 각 워커가 자기만의 진행률 칸을 동기화 없이 갱신하게 두고, 코디네이터가 merge할 때 결합·교환·멱등 법칙을 지키기만 하면 항상 수렴한다는 걸 ``GCounter``로 확인했습니다 — 1장의 그 위험했던 ``progress``가 이렇게 마침내 안전해졌고, 멱등하지 않은 순진한 병합이 실제로 잘못된 값을 낸다는 것과도 대조했습니다.

== 다섯 이론을 하나의 표로

이 책이 다룬 다섯 이론과, C{pp}23의 인코딩, 그리고 각 이론을 **언어 코어에 직접 채용한 실전 언어**(대부분 Rust)를 나란히 정리합니다.

[cols="2,3,3,3"]
|===
| 이론 | 막으려는 버그 | 이 책의 C{pp}23 인코딩 | Rust의 채용 여부

| 선형/아핀 타입
| 자원을 두 번 쓰거나(이중 해제) 안 쓰는 것(누수)
| 3부: 이동 전용 타입, `unique_ptr`, Rule of Five/Zero
| **직접 채용.** 소유권과 이동 시맨틱스가 언어 코어 규칙입니다 — 다만 "안 써도 스코프 끝에서 자동 정리된다"는 점에서 순수 선형이 아니라 **아핀** 타입에 더 가깝습니다(7장에서 짚은 것과 같은 구분).

| 세션 타입
| 통신 프로토콜의 순서 위반, 교착 상태
| 2부: 타입 상태 패턴, `requires` 절
| **간접 채용.** 언어 코어엔 없고, `session_types` 같은 크레이트가 제네릭과 소유권을 조합해 라이브러리 수준에서 인코딩합니다 — 이 책의 2부가 한 일과 원리가 같습니다.

| 동시성 분리 논리 (13장)
| 겹치는 메모리 영역에 대한 데이터 경쟁
| 5부: ``std::span``을 쪼개는 `split_at`
| **직접 채용, 그리고 형식 증명까지 있음.** 빌림 검사기의 핵심 규칙("가변 참조는 유일해야 한다", aliasing XOR mutability)이 바로 이 원리이고, RustBelt 프로젝트(Jung 외, 2018)가 분리 논리 기반 증명 도구 Iris로 이 규칙이 실제로 메모리 안전성을 보장한다는 걸 형식적으로 증명했습니다.

| 범주론: Functor/Monad (10~11장)
| 실패 가능한 계산의 안전한 합성
| 4부: concepts, `std::optional`/``std::expected``의 `.transform()`/`.and_then()`
| **부분 채용.** `Option`/``Result``에 `.map()`/``.and_then()``이 있어 이 책의 10~11장과 거의 같은 방식으로 씁니다. 다만 Rust의 트레잇 시스템에는 고차종 타입(higher-kinded types)이 없어서, "임의의 Functor/Monad"를 하나의 트레잇으로 일반화하는 건 언어 차원에서 안 됩니다(`frunk` 같은 크레이트가 매크로로 일부 흉내 냅니다) — C{pp}의 concepts도 마찬가지 한계가 있다는 걸 10장에서 짚었습니다.

| CRDT: join-semilattice (14장)
| 동시 갱신 후 병합 시 비수렴·충돌
| 6부: `JoinSemilattice` concept, `GCounter`
| **해당 없음 — 애초에 "언어 기능"으로 채용할 대상이 아닙니다.** CRDT는 타입 시스템이나 컴파일러 규칙이 아니라 순수한 데이터 구조 설계 기법이라, 어떤 언어에서든(C{pp}이든 Rust든 파이썬이든) 이 장의 ``GCounter``와 똑같은 방식으로 손으로 짤 수 있습니다. Rust 생태계에도 `rust-crdt` 같은 라이브러리가 있지만, 이건 언어 코어의 지원이 필요해서가 아니라 그냥 널리 쓰이는 패턴이라 있는 것입니다.
|===

이 표에서 가장 대조적인 두 줄은 세 번째(분리 논리)와 다섯 번째(CRDT)입니다 — 둘 다 "동시 접근을 안전하게 만든다"는 같은 목표를 향하지만, 분리 논리는 Rust가 **언어 규칙**으로 승격시키고 RustBelt가 **형식 증명**까지 한 반면, CRDT는 애초에 언어가 도와줄 필요가 없는 **순수 알고리즘/자료구조 설계 기법**입니다 — "타입으로 막을 것인가, 알고리즘으로 애초에 안 막아도 되게 만들 것인가"라는 이 책 14장의 관찰이, 언어 설계 차원에서도 그대로 반복되는 셈입니다.

== 완성된 TaskGrid

1장부터 14장까지 한 조각씩 얹어온 TaskGrid를 이제 한자리에 모아볼 수 있습니다.

[source,cpp]
----
// 2~4장: 코디네이터가 워커에게 연결을 맺는 타입 상태 프로토콜
Idle conn;
Connected connection = std::move(conn).connect();

// 7장: 워커가 처리할 데이터 세그먼트 (이동 전용 핸들)
// 13장: 코디네이터가 std::span으로 쪼갠 공유 입력 버퍼 중 이 워커의 몫
DataSegmentHandle handle(/*segment_id=*/worker_id);

// 8장: 연결과 자원을 하나로 합친 워커 세션
WorkerSession session(std::move(connection), std::move(handle));

// 14장: 이 워커만의 진행률 칸 (CRDT, 동기화 없이 증가)
GCounter<kWorkerCount> progress;

// 10장: 처리 결과를 Functor/Monad로 감싸고, 검증하고, 5장의 ResultChannel로 보고
auto outcome = process_batch(session, worker_id, segment_id)
                   .and_then(validate)
                   .and_then([&](BatchResult r) {
                     progress.increment(worker_id);   // 자기 칸만 늘린다 -- 락 없음
                     return report(r, ResultChannel{});
                   });

// 11장: 여러 워커를 std::async로 실제 병렬 실행하고, 5장의 std::jthread/stop_token으로
//       필요하면 협조적으로 취소하고, 결과는 and_then으로 안전하게 합성한다.
// 12장: 같은 and_then 체인을 손수 짠 Task<T> 코루틴으로 co_await 순차 문법으로도 표현할 수 있다.
// 9장: 코디네이터가 바쁜 워커에서 한가한 워커로 재분배할 때는 std::scoped_lock으로
//      코디네이터 쪽 pending_mu_ 두 개를 한 번에, 데드락 없이 잠근다.
// 14장: 코디네이터는 각 워커의 GCounter를 동기화 없이 merge해서 총 진행률을 얻는다.
----

이 한 덩어리 안에 이 책의 모든 장이 들어 있습니다 — `Idle`/`Connected`(2~4장, 세션 타입), `DataSegmentHandle`(6~7장, 선형/아핀 타입), `WorkerSession`(8장, 그 둘의 합성), ``process_batch``의 `std::expected` 체인(10~11장, 범주론), 코디네이터의 재분배 락 순서(9장, AB-BA 교착 상태와 그 수정), `std::span` 분할로 나눠 받은 입력(13장, 동시성 분리 논리), `GCounter`(14장, CRDT)까지 — 그리고 이 모든 것의 출발점은 1장의 그 위험한 두 줄, ``int progress``를 여러 스레드가 동기화 없이 두들기던 코드였습니다. 그 코드가 이 책의 끝에서는 컴파일 타임에 프로토콜을 강제하고, 자원을 이동 전용으로 관리하고, 실패를 자동으로 전파하고, 메모리를 안전하게 나누고, 진행률을 동기화 없이도 정확히 합치는 시스템으로 자라났습니다 — 이론 하나하나가 인코딩이 아니라, 실제로 맞물려 돌아가는 하나의 프로그램이 됐다는 게 이 책이 마지막으로 보여주고 싶었던 것입니다.

== 이 책을 관통한 하나의 패턴

거의 모든 장에서 같은 구조가 반복됐습니다 — **(1) 이론이 무엇을 약속하는지 짚고, (2) 그 약속을 어기는 C{pp} 코드를 실제로 컴파일해서 통과하거나 실패하는지 확인하고, (3) 어디까지 흉내 낼 수 있고 어디서부터 못 미치는지 정직하게 선을 긋는 것.** 3장의 "같은 변수에 ``std::move``를 두 번" 구멍, 4장의 "제약이 정말로 프로토콜을 지키는지는 프로그래머 책임" 지적, 10장의 "concept은 문법만 강제하지 법칙까지는 강제 안 한다"는 짚음, 13장의 "TSan은 실제로 일어난 접근만 잡는다"는 인정, 14장의 "멱등성 없는 병합은 실제로 틀린 값을 낸다"는 대조까지 — 이 책은 C{pp}23이 이론을 완벽하게 이식했다고 주장한 적이 한 번도 없습니다. 대신 **정확히 어디까지 인코딩되고 어디서부터 다시 프로그래머의 책임으로 돌아가는지**를 매번 실제 컴파일러·도구 출력으로 보여주는 것에 집중했습니다.

== 이 책이 다루지 않은 것

* **`std::execution`(C{pp}26, P2300)** — 11장에서 짚었듯, 진짜 논블로킹 비동기 콤비네이터(센더/리시버)는 그 표준이 돼서야 정식으로 들어옵니다. 이 책은 그 프레임워크가 정식으로 풀어줄 문제에 대해 두 가지 거친 근사를 보여줬습니다 — 11장의 `then_async`(블록하는 새 스레드를 만드는 방식)와 12장의 손수 짠 `Task<T>` 코루틴(실행기도 취소 전파도 없는 즉시 실행 방식)입니다. 둘 다 시퀀싱을 표현하는 문법만 오늘 당장 제공할 뿐, 실제 실행기·스케줄러·구조적 취소 전파는 여전히 그 표준을 기다려야 합니다. (아래에 미리보기 스케치를 덧붙였습니다.)
* **일반적인 데드락-프리 증명과 락프리(lock-free) 자료구조** — 9장은 재분배라는 한 가지 구체적인 시나리오에서 두 락을 잠그는 순서가 뒤바뀌어 생기는 교착 상태를 ``std::scoped_lock``과 락 순서 규칙으로 고치는 법을 다뤘지만, 임의의 프로그램이 어떤 락 획득 패턴을 쓰든 절대 교착에 빠지지 않는다는 걸 형식적으로 증명하는 일반 이론은 다루지 않았습니다. ``std::atomic``의 ``compare_exchange``류 연산으로 뮤텍스 자체를 없애는 락프리 기법도 이 책에서 전혀 다루지 않았습니다 — 메모리 순서(`memory_order`)의 미묘함까지 포함하면 그 자체로 책 한 권 분량입니다.
* **다자간 세션 타입의 C{pp} 인코딩** — 참여자가 셋 이상인 프로토콜을 타입 상태로 인코딩하는 건 이 책에서 다루지 않았습니다.
* **`split_at` 이상의 일반적인 분리 논리 인코딩** — 13장은 "인덱스로 앞뒤를 가른다"는 한 가지 패턴만 다뤘습니다. 조건에 따라 나누거나 셋 이상으로 쪼개는 일반적인 경우는 훨씬 정교한 타입이 필요합니다.
* **G-Counter를 넘어서는 CRDT** — 14장은 grow-only 카운터 하나만 다뤘습니다. 실전에서 흔한 CRDT(감소도 가능한 PN-Counter, 삭제 가능한 집합인 OR-Set, 텍스트 편집을 위한 시퀀스 CRDT)는 훨씬 정교한 메타데이터(삭제 표시, 벡터 시계)가 필요합니다.
* **실제 벤치마크와 스케일링** — 이 책의 모든 예제는 "정확성"(데이터 경쟁 없음, 프로토콜 위반 시 컴파일 실패, 병합 수렴)만 검증했지, 실제 성능은 다루지 않았습니다. 14장에서 ``GCounter``를 공유할 때 생길 수 있는 false sharing 같은 성능 문제를 이름만 짚고 넘어가긴 했지만, 락 경합이나 캐시 라인 튐을 실제로 측정하는 벤치마크는 이 책 어디에도 없습니다 — 그건 link:../cpp23-performance-engineering/[후속편]의 몫입니다.

=== 미리보기: TaskGrid가 ``std::execution``으로 다시 쓰인다면

[NOTE]
====
**이 세션에는 C{pp}26/P2300 구현체(예: `stdexec`)가 설치되어 있지 않아, 아래 코드는 실제로 컴파일해 확인하지 못한 스케치입니다** — 이 책의 다른 모든 코드와 달리 "실행해서 확인했다"는 증거가 없다는 걸 분명히 해둡니다. P2300 초안 문서의 센더/리시버 어댑터 이름을 기준으로, 11장의 `then_async`(블록하는 새 스레드 방식)와 12장의 `Task<T>`(즉시 실행 코루틴)가 최종적으로 표준화되면 어떤 모양으로 대체될지에 대한 대략적인 그림입니다.

[source,cpp]
----
// 11장의 then_async(블록하는 새 스레드) 대신:
auto pipeline =
    stdexec::schedule(pool_scheduler)
    | stdexec::then([&] { return process_batch(session, worker_id, segment_id); })
    | stdexec::let_value([](auto result) {
        return result
             ? stdexec::just(validate(*result))
             : stdexec::just_error(result.error());
      })
    | stdexec::then([&](BatchResult r) { return report(r, ResultChannel{}); });

auto [reported] = stdexec::sync_wait(std::move(pipeline)).value();
----

``schedule(pool_scheduler)``가 11장의 "새 스레드를 만드는" 대신 실행기(스케줄러)에게 작업을 맡기고, `then`/``let_value``가 10장의 `.transform()`/``.and_then()``과 같은 역할(성공 시에만 다음 단계로, 실패는 자동 전파)을 하되 **지연 실행(lazy)** 됩니다 — ``sync_wait``를 부르기 전까지는 아무 코드도 실행되지 않는다는 점이 12장 ``Task<T>``의 즉시 실행(eager)과 가장 크게 다른 지점입니다. 취소도 ``stop_token``을 손으로 넘길 필요 없이 ``sync_wait``를 감싸는 구조적 동시성 범위가 자동으로 전파합니다 — 이게 이 책 11~12장이 정직하게 "거친 근사일 뿐"이라고 부른 지점을, ``std::execution``이 정식으로 메워주는 방식입니다.
====

== 이론과 실무 사이의 간극

이 책 전체가 다섯 이론(선형 타입, 세션 타입, 범주론, 분리 논리, CRDT)을 형식적으로 증명하는 대신 C{pp}23의 실무 코드로 인코딩하는 여정이었습니다. 매 장에서 "이 이론이 무엇을 약속하는가"와 "그 약속이 C{pp} 코드에서 실제로 어디까지 지켜지고 어디서 무너지는가" 사이의 간극을 실제 컴파일러·도구 출력으로 확인했습니다 — 그리고 이 맺음말의 표가 보여줬듯, 그 간극이 어디쯤 있는지는 이론마다 다릅니다. **Rust처럼 이론을 언어 코어로 승격시키고 RustBelt처럼 그걸 다시 형식 증명하는** 경우도 있고, **CRDT처럼 애초에 언어의 도움 자체가 필요 없는** 경우도 있습니다. 이 간극(과 때로는 간극이 아예 없다는 사실)을 눈으로 확인하는 게, 이론만 배우거나 실무 관용구만 외우는 것보다 오래 남는 이해라고 믿습니다.

이 책을 이해했다는 건 ``requires (N == 0)``이라는 문법이나 Rule of Five의 다섯 함수 시그니처를 외웠다는 뜻이 아니라, 새로운 병렬 프로그래밍 문제를 마주쳤을 때 "이걸 타입 상태로 표현할 수 있는가, 이 자원은 이동 전용으로 만들 수 있는가, 이 메모리 영역들은 서로 안 겹치는가, 이 실패 가능한 계산은 Monad로 합성할 수 있는가, 아니면 애초에 동기화 자체가 필요 없도록 데이터 구조를 다시 설계할 수 있는가"를 순서대로 짚어보고, 그 답이 정말인지 컴파일러와 도구에게 직접 물어볼 수 있게 되는 것입니다. 이 책이 그 습관의 첫걸음을 놓아줬다면, 그것으로 충분합니다.

이렇게 안전해진 TaskGrid를 이제 **얼마나 빠르게 만들 수 있는지**가 궁금하다면, 같은 TaskGrid를 이어받아 `std::mdspan`, `deducing this`, `consteval`, PMR 아레나 같은 C{pp}23의 성능 관련 기능들을 실제로 벤치마크하는 후속편 link:../../cpp23-performance-engineering/[『안전을 넘어 성능으로: C{pp}23 최적화 기법』]을 참고하세요.
