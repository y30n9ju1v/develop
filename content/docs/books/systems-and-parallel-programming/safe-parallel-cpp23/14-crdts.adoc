'''

지금까지 이 책의 모든 이론(타입 상태, 이동 전용 타입, 분리 논리)은 전략이 하나였습니다 — **동시 접근을 막는다.** 순서를 강제하거나, 소유권을 유일하게 만들거나, 메모리를 안 겹치게 나누는 식입니다. 이 장의 이론은 정반대 전략을 씁니다 — **아예 안 막습니다.** 동기화 없이 각자 마음대로 갱신하게 놔두고, 나중에 결과를 합칠 때 항상 같은 값에 수렴한다는 걸 순전히 대수(algebra)로 보장합니다. 이게 **CRDT**(Conflict-free Replicated Data Type)입니다.

그리고 이 장은 이 책의 첫 장으로 돌아가는 장이기도 합니다 — 1장에서 코디네이터와 워커가 공유 `int progress` 하나를 동기화 없이 두들겨서 데이터 경쟁을 냈던 바로 그 문제를, `std::atomic`으로 "막는" 대신 이번엔 **애초에 안 막아도 되도록** 다시 설계해서 고칩니다.

== 이론: join-semilattice

CRDT의 핵심은 **merge**라는 이항 연산이 다음 세 법칙을 지킨다는 것입니다 — 이런 대수 구조를 **join-semilattice** 라고 부릅니다.

* **결합법칙**: `merge(merge(a, b), c) == merge(a, merge(b, c))` — 셋을 어떤 순서로 합쳐도 결과가 같습니다.
* **교환법칙**: `merge(a, b) == merge(b, a)` — 누가 먼저 합쳤는지가 결과에 안 나타납니다.
* **멱등법칙**: `merge(a, a) == a` — 같은 걸 두 번 합쳐도 결과가 안 바뀝니다.

세 법칙을 합치면 정확히 이렇게 됩니다 — **여러 복제본(replica)이 동기화 없이 각자 갱신되다가, 어떤 순서로, 몇 번을 다시 합쳐지든, 결국 모두 같은 값에 수렴한다.** 락도, 원자적 연산도, 순서 있는 채널도 필요 없습니다 — merge 함수 하나가 이 세 법칙만 지키면 됩니다.

== concept으로 join-semilattice 표현하기

[source,cpp]
----
template <typename S>
concept JoinSemilattice = requires(S a, S b) {
  { a.merge(b) } -> std::same_as<S>;
};
----

10장의 `Functor`와 정확히 같은 형태입니다 — 문법적 요구사항(`.merge()`가 있고 같은 타입을 돌려준다)만 강제하고, 그 뒤의 세 법칙(결합·교환·멱등)은 `concept`이 검사해주지 않습니다. 이것도 10장에서 이미 짚은 "concept은 문법만 강제하지 의미론적 법칙까지는 강제 안 한다"는 한계가 그대로 적용됩니다 — 그래서 이 장은 세 법칙을 실제 코드로 하나씩 확인합니다.

== GCounter: 동기화 없이 각자 늘리다가 나중에 합치는 카운터

[source,cpp]
----
template <std::size_t N>
class GCounter {
  std::array<int, N> counts_{};  // counts_[worker_id] = 그 워커가 처리한 배치 수
public:
  void increment(std::size_t worker_id) { counts_[worker_id]++; }
  int value() const { int sum = 0; for (int c : counts_) sum += c; return sum; }
  GCounter merge(const GCounter& other) const {
    GCounter result;
    for (std::size_t i = 0; i < N; i++) result.counts_[i] = std::max(counts_[i], other.counts_[i]);
    return result;
  }
  bool operator==(const GCounter&) const = default;
};

static_assert(JoinSemilattice<GCounter<2>>);
----

`GCounter`(Grow-only Counter)는 복제본(워커)마다 **자기 칸**(`counts_[worker_id]`)만 증가시킵니다 — 1장의 `progress++`처럼 여러 워커 스레드가 **같은** 변수를 두들기는 게 아니라, 각자 **자기 칸**만 두들깁니다. `merge`는 칸마다 더 큰 값을 취하는(`std::max`) 것뿐입니다 — `max`가 결합·교환·멱등을 모두 만족하는 연산이라는 게, 이 카운터가 CRDT인 이유의 전부입니다.

== 검증 1: 동시에 늘려도 동기화가 필요 없다

[source,cpp]
----
int main() {
  GCounter<2> worker0_progress, worker1_progress;
  std::thread w1([&] { for (int i = 0; i < 100000; i++) worker0_progress.increment(0); });
  std::thread w2([&] { for (int i = 0; i < 100000; i++) worker1_progress.increment(1); });
  w1.join();
  w2.join();

  auto merged1 = worker0_progress.merge(worker1_progress); // 코디네이터가 워커0 기준으로 합침
  auto merged2 = worker1_progress.merge(worker0_progress); // 코디네이터가 워커1 기준으로 합침

  std::cout << "merge(w0,w1).value() = " << merged1.value() << "\n";
  std::cout << "merge(w1,w0).value() = " << merged2.value() << "\n";
  std::cout << "commutative: " << (merged1 == merged2) << "\n";

  auto merged_again = merged1.merge(worker1_progress); // 진행률 보고가 중복 도착했다고 가정
  std::cout << "idempotent (merge again with worker1): " << (merged_again == merged1) << "\n";
}
----

[source]
----
$ clang++ -std=c++23 -O0 -pthread -fsanitize=thread gcounter.cpp -o gcounter_tsan
$ ./gcounter_tsan
worker0_progress.value() = 100000
worker1_progress.value() = 100000
merge(w0,w1).value() = 200000
merge(w1,w0).value() = 200000
commutative: 1
idempotent (merge again with worker1): 1
----

`w1`은 `worker0_progress`만, `w2`는 `worker1_progress`만 건드립니다 — **뮤텍스도, `std::atomic`도 안 씁니다.** 두 워커 스레드가 물리적으로 같은 메모리를 만질 방법이 없기 때문입니다(13장의 분리 논리와 같은 발상이 여기서도 배경에 깔려 있습니다 — 다만 이 장에서는 그게 목적이 아니라 전제 조건입니다). ThreadSanitizer를 켜도 경고가 없고, `merge(w0,w1)`와 `merge(w1,w0)`가 정확히 같은 값(`200000`, 즉 전체 진행률)에 수렴한다는 것과, 이미 합친 결과에 `worker1_progress`를 또 합쳐도 값이 안 바뀐다는 것(멱등)까지 실제로 확인됩니다 — 이게 1장의 `std::atomic<int> progress`가 원자적 연산으로 매번 경합했던 것과 정반대로, **코디네이터가 원할 때 각 워커의 로컬 카운터를 동기화 없이 읽어다 합치기만 하면 되는** 진행률 집계입니다.

== 실전 팁: 카운터를 하나만 공유하면 False Sharing이 생긴다

위 검증은 `worker0_progress`와 `worker1_progress`를 **완전히 별도의 객체**로 뒀습니다 — 그래서 `w1`과 `w2`가 물리적으로 같은 메모리조차 만지지 않습니다. 하지만 `GCounter<N>` **하나**를 여러 워커가 공유하며 각자 `counts_[worker_id]`만 건드리는 식으로 바꾸고 싶어질 수 있습니다(merge를 나중에 한 번만 하면 되니 코디네이터 쪽 코드가 단순해집니다). 정확성만 보면 이것도 데이터 경쟁은 아닙니다 — 서로 다른 인덱스니까요. 하지만 `std::array<int, N>`의 원소들은 메모리에 연속으로 붙어 있어서, `counts_[0]`과 `counts_[1]`이 같은 **CPU 캐시 라인**(보통 64바이트)에 들어갑니다. 그러면 워커 0이 `counts_[0]`을 쓸 때마다 워커 1의 코어가 들고 있는 `counts_[1]`의 캐시 라인까지 무효화되고, 그 반대도 마찬가지입니다 — 이게 **거짓 공유(false sharing)**입니다. 데이터 경쟁처럼 결과가 틀리는 건 아니지만, 코어끼리 캐시 라인을 서로 뺏고 뺏기느라 실제 멀티코어 성능이 락을 쓴 것과 비슷한 수준까지 떨어질 수 있습니다.

[source,cpp]
----
#include <new>  // std::hardware_destructive_interference_size

template <std::size_t N>
class GCounterPadded {
  struct alignas(std::hardware_destructive_interference_size) PaddedInt {
    int value = 0;
  };
  std::array<PaddedInt, N> counts_{};  // 원소마다 캐시 라인 하나를 통째로 차지
public:
  void increment(std::size_t worker_id) { counts_[worker_id].value++; }
  int value() const { int sum = 0; for (auto& c : counts_) sum += c.value; return sum; }
};
----

`std::hardware_destructive_interference_size`(C++17)는 "이 값보다 떨어뜨려 두면 거짓 공유가 안 생긴다"고 표준 라이브러리가 보장하는 크기(대부분의 x86-64/ARM64 플랫폼에서 `64`)입니다. `alignas`로 각 워커의 칸을 그 크기만큼 정렬하면, `counts_[0]`과 `counts_[1]`이 서로 다른 캐시 라인에 놓여 물리적으로도 간섭하지 않습니다 — 대신 `GCounter<N>`이 차지하는 메모리는 `N * 64`바이트로 늘어나므로(캐시 라인 하나에 `int` 하나만 쓰는 셈), 이 트레이드오프는 워커 수가 아주 많지 않은 한(그리고 실제로 `increment`가 뜨거운 경로일 때만) 적용할 가치가 있습니다.

== 왜 멱등성이 진짜 중요한가: 순진한 병합과 대조하기

멱등법칙이 그냥 이론적 장식이 아니라는 걸, 멱등하지 않은 "그럴듯한" merge와 대조해서 보여줍니다.

[source,cpp]
----
// 그럴듯해 보이는 순진한 merge: 두 총합을 그냥 더한다. 멱등하지 않다!
struct NaiveCounter {
  int total = 0;
  NaiveCounter merge(const NaiveCounter& other) const { return {total + other.total}; }
};

int main() {
  NaiveCounter a{100}, b{50};
  auto merged = a.merge(b);
  std::cout << "first merge: " << merged.total << "\n"; // 150, 맞음

  // 실전 분산 시스템은 네트워크 메시지가 중복 전달될 수 있다(at-least-once delivery) --
  // 그러면 같은 merge가 실수로 두 번 적용될 수 있다.
  auto merged_again = merged.merge(b);
  std::cout << "merged again with the same b: " << merged_again.total << "\n"; // 틀림
}
----

[source]
----
$ clang++ -std=c++23 -O0 naive_counter.cpp -o naive_counter && ./naive_counter
first merge: 150
merged again with the same b (simulating a duplicate message): 200
----

`150`이 나와야 할 자리에 `200`이 나옵니다 — `b`가 실수로 두 번 반영됐습니다. 이건 억지 시나리오가 아닙니다 — TaskGrid처럼 워커가 코디네이터에게 진행률을 주기적으로 보고하는 시스템에서는 같은 보고가 네트워크나 재시도 로직 때문에 중복 도착하는 일이 흔합니다(at-least-once delivery). "같은 갱신이 두 번 적용돼도 결과가 안 바뀐다"는 멱등성은 이론적 우아함이 아니라 **실전에서 거의 항상 필요한 안전장치**입니다. `GCounter`의 `max` 기반 merge는 이 시나리오에서도(검증 1의 마지막 줄, "merge again with worker1") 멀쩡했습니다 — `NaiveCounter`의 `+` 기반 merge는 그렇지 않았습니다. 만약 1장의 `progress`를 `NaiveCounter`처럼 "그냥 더하는" 방식으로 고치려 했다면, 진행률 보고가 중복되는 순간 실제보다 부풀려진 값을 보고했을 것입니다.

== 실전 팁: `constexpr`로 컴파일 타임에도 법칙을 검증하기

지금까지의 두 검증(`main()`에서 스레드를 돌리고 콘솔 출력을 눈으로 확인)은 **실행해야만** 알 수 있는 런타임 검증입니다. `GCounter`의 메서드가 스레드나 I/O를 전혀 안 쓴다는 점(순수하게 `std::array`와 `std::max`만 다룬다는 점)을 이용하면, 세 법칙을 컴파일 타임에 `static_assert`로 직접 확인할 수도 있습니다 — 메서드에 `constexpr`만 붙이면 됩니다.

[source,cpp]
----
template <std::size_t N>
class GCounter {
  std::array<int, N> counts_{};
public:
  constexpr void increment(std::size_t worker_id) { counts_[worker_id]++; }
  constexpr int value() const { int sum = 0; for (int c : counts_) sum += c; return sum; }
  constexpr GCounter merge(const GCounter& other) const {
    GCounter result;
    for (std::size_t i = 0; i < N; i++) result.counts_[i] = std::max(counts_[i], other.counts_[i]);
    return result;
  }
  constexpr bool operator==(const GCounter&) const = default;

  static constexpr bool test_associative() {
    GCounter a, b, c;
    a.increment(0);
    b.increment(1);
    c.increment(0);
    c.increment(1);
    return a.merge(b).merge(c) == a.merge(b.merge(c));
  }
  static constexpr bool test_commutative() {
    GCounter a, b;
    a.increment(0);
    b.increment(1);
    return a.merge(b) == b.merge(a);
  }
  static constexpr bool test_idempotent() {
    GCounter a;
    a.increment(0);
    a.increment(1);
    return a.merge(a) == a;
  }
};

static_assert(GCounter<3>::test_associative());
static_assert(GCounter<2>::test_commutative());
static_assert(GCounter<2>::test_idempotent());
----

이 `static_assert` 세 줄은 실제로 프로그램을 실행하지 않고도 **컴파일이 끝나는 순간** 세 법칙이 성립함을 확정합니다 — 실패하면 `./gcounter`를 돌려보기 전에 컴파일 자체가 깨집니다. `test_idempotent`를 뒤에 나올 `NaiveCounter`의 `+` 기반 merge로 바꿔서 똑같이 `constexpr`을 붙이고 `static_assert`를 걸어보면:

[source]
----

'NaiveCounter::test_idempotent()': merge should be idempotent
   12 | static_assert(NaiveCounter::test_idempotent(), "merge should be idempotent");
      |               ^~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

----

바로 다음 절에서 런타임으로 확인할 "`150`이 아니라 `200`이 나온다"는 바로 그 버그가, 여기서는 실행 파일을 만들기도 전에 컴파일 에러로 잡힙니다. 물론 이 방식이 런타임 검증을 대체하지는 않습니다 — 두 워커 스레드가 정말로 동시에 서로 다른 메모리를 두들겨도 안전한지(검증 1의 요점)는 `constexpr`이 아니라 ThreadSanitizer로만 확인할 수 있는 성질이기 때문입니다. 하지만 merge의 **대수적 법칙 자체**는 스레드와 무관한 순수 계산이므로, 컴파일 타임 검증으로 옮겨서 "법칙이 깨진 CRDT는 애초에 빌드조차 안 되게" 만들 수 있다는 것은 이 책이 반복해온 "컴파일 타임으로 옮길 수 있는 안전성은 최대한 옮긴다"는 주제와 정확히 맞닿아 있습니다.

== 이게 지금까지의 장들과 어떻게 다른가

1~13장은 전부 "이 프로그램이 특정 실수를 저지르면 컴파일이 실패하거나(2~5장, 6~8장) 도구가 실행 중 잡아낸다(1장, 9장, 13장)"는 형태였습니다. 이 장은 다릅니다 — `GCounter`를 쓰는 프로그램이 **동시 접근 자체를 막지 않고도** 안전합니다. 컴파일 에러도, TSan 경고도 나올 여지가 애초에 없습니다(각 워커가 자기 칸만 건드리므로) — 안전성이 "이 시점에 이 접근을 거부한다"는 방어가 아니라, **"애초에 순서가 안 중요하도록 데이터 구조를 설계한다"** 는 다른 층위에서 나옵니다. 이 책이 지금까지 보여준 "이론마다 안전을 얻는 방식이 다르다"는 주제의 가장 극단적인 사례가 이 장입니다 — 그리고 정확히 이 다른 층위 덕분에, 1장에서 `std::atomic`으로 "막아야만" 했던 `progress`가 이 장에서는 애초에 막을 필요조차 없어졌습니다.

== 팁 박스: C++17 환경이라면

[NOTE]
====
`concept`(C++20)이 없으니 10장과 같은 `void_t` SFINAE 트레잇으로 대신합니다.

[source,cpp]
----
template <typename S, typename = void>
struct is_join_semilattice : std::false_type {};

template <typename S>
struct is_join_semilattice<S, std::void_t<decltype(std::declval<S>().merge(std::declval<S>()))>>
    : std::is_same<decltype(std::declval<S>().merge(std::declval<S>())), S> {};

static_assert(is_join_semilattice<GCounter<2>>::value, "GCounter should be a join-semilattice");
----

`GCounter` 자체는 `std::array`, `std::max`, 스레드만 쓰므로 (`operator==`를 C++20의 `= default` 대신 직접 써주면) `-std=c++17`로도 그대로 컴파일되고, 교환법칙 검증도 동일하게 통과한다는 걸 실제로 확인했습니다 — CRDT 자체는 C++ 표준 버전과 무관한 순수 대수적 설계이기 때문입니다. 이 책에서 "C++23 없이는 아예 흉내조차 안 되는" 유일한 후보였던 게 4부의 `.transform()`/`.and_then()`(10장 팁 박스) 정도였고, 이 장은 그 반대 극단 — 어떤 C++ 버전에서도 똑같이 동작하는 이론 — 이라는 것도 흥미로운 대조입니다.
====

== 요약

* CRDT는 지금까지의 모든 장과 반대 전략을 씁니다 — 동시 접근을 막는 대신, merge 연산이 결합·교환·멱등 법칙(join-semilattice)을 지키기만 하면 동기화 없이 갱신해도 항상 같은 값에 수렴한다는 걸 대수로 보장합니다.
* `GCounter`로 두 워커가 뮤텍스도 원자 연산도 없이 각자의 진행률 칸만 늘리고, 코디네이터가 반대 순서로 합쳐도 같은 값에 수렴하며 이미 합친 걸 또 합쳐도 안 바뀐다는 걸 TSan까지 켜서 실제로 확인했습니다 — 1장의 그 위험했던 공유 `int progress`가 이렇게 마침내 안전해졌습니다.
* 멱등하지 않은 "그럴듯한" 병합(`NaiveCounter`)이 중복 병합 시 실제로 잘못된 값을 낸다는 걸 대조해서, 세 법칙 중 멱등성이 왜 장식이 아니라 실전 안전장치인지 확인했습니다.
* 안전성이 "접근을 거부한다"가 아니라 "순서가 안 중요하도록 설계한다"는 전혀 다른 층위에서 나올 수 있다는 것으로, 이 책이 반복해온 "이론마다 안전을 얻는 방식이 다르다"는 주제의 마지막 사례를 보탰습니다.
* 실전 성능 팁으로 `counts_[worker_id]`를 여러 워커가 한 `GCounter`에서 공유하면 캐시 라인을 두고 다투는 거짓 공유(false sharing)가 생길 수 있다는 것과, `alignas(std::hardware_destructive_interference_size)`로 이를 피하는 법을 짚었습니다. 또한 merge가 스레드와 무관한 순수 계산이라는 점을 이용해 `constexpr`과 `static_assert`로 세 법칙을 컴파일 타임에 직접 검증하는 방법도 확인했습니다.

맺음말에서는 이 CRDT까지 포함해 이 책이 다룬 다섯 이론 전체를 다시 정리하고, 1장부터 이 장까지 조립해온 TaskGrid 전체를 한자리에 모아 봅니다.
