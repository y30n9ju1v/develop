'''

5장에서는 `std::lock_guard`가 "생성자가 잠그고 소멸자가 푼다"는 타입 상태 원리로 락 하나를 안전하게 다룬다는 걸 확인했습니다. 8장에서는 `WorkerConnection`과 `DataSegmentHandle`을 합쳐 `WorkerSession`을 완성했습니다. 이 장은 그 둘을 이어서 한 단계 더 밀어붙입니다 — **뮤텍스가 하나가 아니라 둘 이상일 때**는 무슨 일이 생길까요? `lock_guard`는 락 하나를 잊거나 두 번 푸는 실수는 원천 봉쇄하지만, "두 락을 서로 다른 순서로 잠그는" 실수는 전혀 막지 않습니다 — 그리고 그 실수는 컴파일도, (운이 나쁘면) 대부분의 테스트 실행도 통과하면서 실전에서만 조용히 프로그램을 멈춰 세웁니다.

== TaskGrid에 재분배가 필요해지는 순간

지금까지 각 `WorkerSession`은 자기 배치만 처리하고 끝났습니다. 하지만 실전 코디네이터는 종종 **재분배(rebalancing)** 를 해야 합니다 — 한 워커가 유난히 무거운 배치를 붙들고 있는 동안 다른 워커가 이미 일을 끝내고 놀고 있다면, 코디네이터가 바쁜 워커에서 대기 중인 배치 일부를 떼어 한가한 워커로 옮겨줘야 합니다.

이 상태는 `WorkerSession` **안이 아니라 코디네이터 쪽**에 둡니다 — 8장에서 확인했듯 `WorkerSession`은 `connection_`과 `handle_` 두 멤버만 가진 Rule-of-Zero 타입이고, 그 이동 가능성(움직일 수 있다는 것 자체)이 3부 전체의 핵심이었습니다. 여기에 `std::mutex` 멤버를 새로 얹으면 `WorkerSession`의 컴파일러 생성 이동 생성자가 그 자리에서 조용히 삭제됩니다 — `std::mutex`는 이동조차 안 되는 타입이기 때문입니다. 그러면 8장이 보여준 `WorkerSession s2 = std::move(s1);`이 더는 컴파일되지 않습니다. 그래서 재분배 대상 상태(대기 중인 배치 큐)는 `WorkerSession` 목록을 감독하는 **코디네이터** 쪽에, `WorkerSession`과는 별도인 `std::vector<std::mutex>`로 둡니다 — 사실 실전 재분배 코드도 대부분 이 모양입니다: 잠기는 건 세션 객체 자체가 아니라 코디네이터가 들고 있는 부기(book-keeping) 구조입니다.

[source,cpp]
----
class Coordinator {
public:
  Coordinator()
      : pending_mus_(kWorkerCount), pending_batches_per_worker_(kWorkerCount) {}

  // 코디네이터가 대기 중인 배치를 워커 worker_id의 큐에 밀어 넣는다.
  void enqueue_batch(int worker_id, int batch_id) {
    std::lock_guard<std::mutex> g(pending_mus_[worker_id]);
    pending_batches_per_worker_[worker_id].push_back(batch_id);
  }

  // 재분배: 워커 from이 붙든 배치 하나를 꺼내서 워커 to에게 넘긴다.
  // 두 워커의 큐를 모두 건드려야 하므로 두 뮤텍스를 동시에 잠가야 한다.
  void rebalance_one(int from, int to) {
    std::lock_guard<std::mutex> mine(pending_mus_[from]);    // (A) 먼저 from을 잠그고
    std::lock_guard<std::mutex> theirs(pending_mus_[to]);    // (B) 그다음 to를 잠근다
    auto& from_q = pending_batches_per_worker_[from];
    if (from_q.empty()) return;
    int batch = from_q.back();
    from_q.pop_back();
    pending_batches_per_worker_[to].push_back(batch);
  }

private:
  std::vector<std::mutex> pending_mus_;                       // 워커별 뮤텍스 (WorkerSession 밖)
  std::vector<std::vector<int>> pending_batches_per_worker_;  // 워커별 대기 큐
};
----

`enqueue_batch`는 락 하나만 잠그니 5장의 이야기 그대로 안전합니다. 문제는 `rebalance_one`입니다 — **두 워커의 뮤텍스를 동시에** 잠가야 재분배 중간 상태(배치가 어느 큐에서도 안 보이거나, 두 큐 모두에 보이는 상태)를 다른 스레드가 못 보게 막을 수 있습니다.

== 실제로 재현되는 AB-BA 교착 상태

코디네이터가 두 방향으로 동시에 재분배를 시도한다고 해봅시다 — 워커 0이 워커 1에게 배치를 넘기는 스레드와, 워커 1이 워커 0에게 배치를 넘기는 스레드가 동시에 돕니다(실전에서는 "양쪽 다 바쁘다고 서로 오판"하는 경우에 흔히 생깁니다).

[source,cpp]
----
int main() {
  Idle c0, c1;
  std::vector<WorkerSession> sessions;
  sessions.emplace_back(std::move(c0).connect(), DataSegmentHandle(0));
  sessions.emplace_back(std::move(c1).connect(), DataSegmentHandle(1));

  Coordinator coord;
  coord.enqueue_batch(0, 100);
  coord.enqueue_batch(1, 200);

  std::thread t1([&] {
    for (int i = 0; i < 100000; i++) coord.rebalance_one(0, 1);  // 0 먼저, 1 나중 (A->B)
  });
  std::thread t2([&] {
    for (int i = 0; i < 100000; i++) coord.rebalance_one(1, 0);  // 1 먼저, 0 나중 (B->A)
  });
  t1.join();
  t2.join();
  std::cout << "done\n";
}
----

`t1`은 `pending_mus_[0]`을 먼저 잠그고 `pending_mus_[1]`을 나중에 잠급니다. `t2`는 정반대 순서로 잠급니다 — 이게 **AB-BA 순서**입니다. 운이 나쁘면 `t1`이 워커 0의 락을 잠근 채로 워커 1의 락을 기다리고, 동시에 `t2`가 워커 1의 락을 잠근 채로 워커 0의 락을 기다리는 상황이 벌어집니다 — 둘 다 서로가 들고 있는 락을 기다리므로, **영원히 아무도 진행하지 못합니다.** `done`이 출력되지 않고 프로그램이 그냥 멈춥니다.

$ ./rebalance_tsan
(응답 없음 — CPU 사용량이 곧바로 0%로 떨어진 채 멈춘다)
----

`ps`로 확인하면 프로세스가 살아 있지만 CPU 시간이 전혀 늘지 않는 채로(spin이 아니라 진짜 블록) 영원히 멈춰 있습니다 — 실제 AB-BA 교착 상태가 재현된 것입니다. 이 장을 준비하며 정직하게 확인해야 했던 사실이 하나 있습니다: **이 세션에 설치된 Apple Clang 21의 ThreadSanitizer(Darwin 런타임)는 다른 데이터 경쟁 리포트(1장, 13장)와 달리, 뮤텍스의 lock-order-inversion(잠재적 교착 상태) 진단을 내지 않았습니다.** `TSAN_OPTIONS=verbosity=1`로 확인해보면 TSan이 정상적으로 계측되어 동작 중인 것은 분명하지만(인터셉터가 실제로 걸려 있고, 억제 규칙도 정상 로드됩니다), 위 `rebalance.cpp`뿐 아니라 표준 라이브러리 뮤텍스 두 개만으로 만든 최소한의 AB-BA 예제(`std::mutex a, b`를 두 스레드가 반대 순서로 잠그는 코드)로도 같은 결과였습니다 — 실제로 멈추기는 하지만, `WARNING: ThreadSanitizer: lock-order-inversion` 리포트는 나오지 않습니다. 이건 Darwin용 TSan 런타임이 Linux 빌드와 달리 뮤텍스 교착 상태 검출기를 갖추지 않은 것으로 보이는 플랫폼 제약입니다 — 이 책의 다른 모든 장이 "도구가 실제로 무엇을 보여주는가"를 있는 그대로 보여주는 걸 원칙으로 삼아온 만큼, 여기서도 나오지 않은 리포트를 나온 것처럼 지어내는 대신 이 한계를 그대로 적습니다.

대신 이 장이 확실하게 보여줄 수 있는 것은 **실제 교착 상태 자체**입니다 — TSan 없이 컴파일해도(`clang++ -std=c++23 -O0 -pthread rebalance.cpp -o rebalance_plain`) 정확히 같은 방식으로 멈춥니다. 즉 이건 TSan 계측이 만들어낸 인공물이 아니라, 코드 자체의 진짜 버그입니다. 그리고 아래 "고치기" 절의 두 해법을 적용하면 — 코드는 딱 락을 잠그는 방식만 바뀌는데 — 같은 프로그램이 멈추지 않고 `done`을 출력하며 끝난다는 것도 실제로 컴파일하고 실행해서 확인했습니다. **"고치기 전엔 실제로 멈추고, 고치고 나면 실제로 안 멈춘다"** 는 이 대비가, lock-order-inversion 리포트 문구 한 줄보다 오히려 더 직접적인 증거입니다.

== 고치기 1: `std::scoped_lock` — 여러 뮤텍스를 원자적으로

가장 먼저 권할 해법은 `std::scoped_lock`입니다 — 가변 인자 템플릿으로 뮤텍스를 몇 개든 받아서, 데드락을 피하는 알고리즘(내부적으로 `std::lock()`과 같은 방식)으로 **한꺼번에** 잠급니다.

[source,cpp]
----
void rebalance_one(int from, int to) {
  std::scoped_lock lock(pending_mus_[from], pending_mus_[to]);  // 순서와 무관하게 항상 안전
  auto& from_q = pending_batches_per_worker_[from];
  if (from_q.empty()) return;
  int batch = from_q.back();
  from_q.pop_back();
  pending_batches_per_worker_[to].push_back(batch);
}
----

[source]
----
$ clang++ -std=c++23 -O0 -fsanitize=thread -g -pthread rebalance_fixed.cpp -o rebalance_fixed_tsan && ./rebalance_fixed_tsan
coordinator connected to worker
acquired segment 0
coordinator connected to worker
acquired segment 1
done
released segment 1
released segment 0
----

이건 실제로 캡처한 출력입니다 — 앞 절의 미수정 버전은 이 시점까지 응답 없이 멈춰 있었던 반면, `std::scoped_lock`으로 바꾼 버전은 매번 `done`까지 정상적으로 도달하고 TSan도 아무 경고 없이 깨끗하게 종료됩니다. `std::scoped_lock`은 `coord.rebalance_one(0, 1)`과 `coord.rebalance_one(1, 0)`가 각각 `(pending_mus_[from], pending_mus_[to])`를 서로 다른 텍스트 순서로 넘겨도, 내부적으로 **락을 실제로 잡는 순서를 알아서 조율**해서 두 스레드가 서로를 기다리는 순환이 생기지 않게 합니다(전형적으로 `std::lock()`의 시행착오형(try-and-backoff) 알고리즘 — 하나를 잡고, 나머지를 논블로킹으로 시도하다 실패하면 이미 잡은 것도 풀고 다시 시도하는 방식 — 을 씁니다). 코드를 짜는 사람은 "어느 순서로 넘겼는가"를 신경 쓸 필요가 없다는 게 핵심입니다.

== 고치기 2: 전역 락 순서 — `scoped_lock`이 안 맞을 때

`std::scoped_lock`은 뮤텍스에만 씁니다. 재분배 대상이 뮤텍스가 아니라 서로 다른 종류의 자원(예: 파일 핸들 두 개, 또는 이미 각자 잠겨 있는 락을 나중에 또 다른 락과 엮어야 하는 경우)이라 한 번에 묶어서 넘길 수 없다면, 대안은 **일관된 전역 순서**를 정해서 항상 그 순서로만 잠그는 것입니다 — TaskGrid라면 "항상 `worker_id`가 작은 쪽을 먼저 잠근다"는 규칙입니다.

[source,cpp]
----
void rebalance_one(int from, int to) {
  int first  = (from < to) ? from : to;
  int second = (from < to) ? to : from;
  std::lock_guard<std::mutex> a(pending_mus_[first]);
  std::lock_guard<std::mutex> b(pending_mus_[second]);
  auto& from_q = pending_batches_per_worker_[from];
  if (from_q.empty()) return;
  int batch = from_q.back();
  from_q.pop_back();
  pending_batches_per_worker_[to].push_back(batch);
}
----

`coord.rebalance_one(0, 1)`과 `coord.rebalance_one(1, 0)` 모두 이제 **항상 `worker_id`가 더 작은 쪽을 먼저** 잠급니다 — 두 스레드가 같은 순서로 줄을 서므로 AB-BA 순환이 구조적으로 생길 수 없습니다. `std::scoped_lock`이 "순서를 신경 안 써도 되게" 만든다면, 이 방식은 "모두가 같은 순서를 지키게" 만드는 것입니다 — 원리는 다르지만 목표(순환 방지)는 같습니다. 실제로 컴파일해서 실행해봐도(`rebalance_ordered.cpp`) `rebalance_fixed_tsan`과 똑같이 매번 `done`으로 정상 종료합니다.

== 이 도구의 한계: 어디서부터 다시 프로그래머 책임인가

4장에서는 "`requires` 절이 프로토콜을 정말로 지키는지는 결국 그 절을 쓴 프로그래머의 책임"이라는 걸 짚었습니다. `std::scoped_lock`에도 정확히 같은 종류의 한계가 있습니다.

`std::scoped_lock(a, b)`는 **그 호출 한 번에 동시에 넘겨진 락들 사이에서만** 데드락을 막아줍니다. 만약 두 뮤텍스가 물리적으로 떨어진 두 호출 지점에서 각각 따로 잠긴다면 — 예를 들어 `rebalance_one`이 `pending_mus_[from]`을 `scoped_lock`으로 안전하게 잡은 **채로**, 그 안에서 어떤 콜백을 호출했는데 그 콜백이 다시 `pending_mus_[to]`를 (이번엔 `scoped_lock`이 아니라 별도로) 잠그려 한다면 — `scoped_lock`의 보장은 전혀 미치지 않습니다. 아래 코드는 컴파일도 되고, 각 락 각각은 `lock_guard`/`scoped_lock`으로 "정상적으로" 관리되지만, 여전히 교착 상태를 일으킬 수 있습니다.

[source,cpp]
----
void unsafe_variant(int from, int to) {
  std::lock_guard<std::mutex> mine(pending_mus_[from]);
  notify_and_maybe_relock(to);  // "알 수 없는 코드" 호출 -- 락을 쥔 채로
}
----

`notify_and_maybe_relock()`이 내부에서 `pending_mus_[to]`를 다시 잠그려 시도한다면(또는 그 함수가 다시 우리 락을 필요로 하는 다른 함수를 부른다면), `scoped_lock`이나 락 순서 규칙 그 자체는 이 상황을 전혀 못 막습니다 — 둘 다 "지금 이 순간 동시에 잠그려는 락들"에 대해서만 작동하는 도구이기 때문입니다. 그래서 실전 규율은 도구 위에 하나 더 필요합니다 — **락을 쥔 채로 자기가 뭘 하는지 모르는 코드(콜백, 가상 함수, 다른 모듈의 함수)를 부르지 않는다**는 원칙, 또는 모든 자원(뮤텍스든 아니든)에 대해 앞서 정한 전역 순서를 예외 없이 지킨다는 원칙입니다. `std::scoped_lock`은 "같은 자리에서 여러 락을 잡을 때"의 실수를 도구로 없애주지만, "설계 전체에 걸쳐 일관된 락 순서를 지킬 것"이라는 더 큰 책임까지 대신 져주지는 않습니다 — 이 책이 4장에서 짚은 "도구의 보장은 정확히 여기서 끝나고, 그다음부터는 다시 프로그래머의 몫"이라는 패턴이 여기서도 그대로 반복됩니다. (13장에서는 이 패턴을 또 다른 도구 — TSan 자체 — 의 한계로 다시 만나게 됩니다.)

== 팁 박스: C++17 환경이라면

[NOTE]
====
`std::scoped_lock`은 **C++17에서 새로 추가**됐습니다(이 책의 다른 장들이 다루는 C++20/23 기능과 달리, 이건 오히려 C++17부터 이미 있습니다) — 그러니 C++17 프로젝트라면 이 장의 1차 해법을 그대로 쓸 수 있습니다. 정말로 C++17 이전(C++11/14)까지 내려가야 한다면, `std::scoped_lock`이 내부적으로 하는 일을 `std::lock()`(C++11부터 있는, 가변 인자 뮤텍스를 데드락 없이 한꺼번에 잠그는 자유 함수)과 `std::adopt_lock`(이미 잠근 뮤텍스를 소유권만 넘겨받아 `lock_guard`로 감싸는 태그)으로 직접 조립하면 됩니다.

[source,cpp]
----
void rebalance_one(int from, int to) {
  std::lock(pending_mus_[from], pending_mus_[to]);  // 두 뮤텍스를 데드락 없이 한꺼번에 잠근다
  std::lock_guard<std::mutex> mine(pending_mus_[from], std::adopt_lock);   // 이미 잠긴 걸 소유권만 인수
  std::lock_guard<std::mutex> theirs(pending_mus_[to], std::adopt_lock);
  auto& from_q = pending_batches_per_worker_[from];
  if (from_q.empty()) return;
  int batch = from_q.back();
  from_q.pop_back();
  pending_batches_per_worker_[to].push_back(batch);
}
----

[source]
----
$ clang++ -std=c++17 -O0 -fsanitize=thread -g -pthread rebalance_cpp17.cpp -o rebalance_cpp17 && ./rebalance_cpp17
coordinator connected to worker
acquired segment 0
coordinator connected to worker
acquired segment 1
done
released segment 1
released segment 0
----

이것도 실제로 컴파일하고 실행해서 확인한 출력입니다. `std::lock(pending_mus_[from], pending_mus_[to])`가 `scoped_lock`과 똑같은 데드락 회피 알고리즘으로 두 뮤텍스를 잠그고 나면, 그 둘을 각각 `std::adopt_lock`을 붙인 `lock_guard`로 감쌉니다 — "이미 잠겨 있으니 새로 잠그지 말고, 소멸자에서 풀어주는 책임만 맡아라"는 뜻입니다. `std::lock`/`std::adopt_lock` 둘 다 C++11부터 있었으므로 이 코드는 C++11까지도 그대로 컴파일됩니다 — `std::scoped_lock`이 하던 일을 두 줄로 풀어 쓴 것뿐이라, 잃는 건 딱 하나 — 뮤텍스 개수가 늘어날 때마다 `lock_guard` 줄도 하나씩 손으로 추가해야 한다는(가변 인자 템플릿 하나로 안 끝난다는) 타이핑 부담뿐입니다.
====

== 요약

* 코디네이터가 바쁜 워커에서 한가한 워커로 배치를 재분배하려면 두 워커의 뮤텍스를 동시에 잠가야 한다는 걸 확인했고, 그 상태(`pending_batches_per_worker_`, `pending_mus_`)는 `WorkerSession` 자체가 아니라 코디네이터 쪽에 둬야 `WorkerSession`이 계속 이동 가능하게 남는다는 것도 짚었습니다.
* 두 스레드가 그 두 락을 서로 다른 순서(A→B, B→A)로 잠그면 실제로 AB-BA 교착 상태가 재현된다는 걸 실제로 컴파일하고 실행해서(TSan을 켜든 안 켜든) 확인했습니다.
* 이 세션 환경의 Apple Clang 21 / Darwin ThreadSanitizer는 뮤텍스 lock-order-inversion 진단을 내지 않는다는 걸 최소 재현 예제로 직접 검증하고 정직하게 밝혔습니다 — 대신 "고치기 전엔 실제로 멈추고, 고치고 나면 실제로 안 멈춘다"는 재현 가능한 전후 대비로 버그와 수정을 증명했습니다.
* `std::scoped_lock`(여러 뮤텍스를 데드락 회피 알고리즘으로 한 번에 잠그는 1차 해법)과, 뮤텍스가 아닌 자원에도 적용되는 전역 락 순서 규칙(2차 해법) 모두 실제로 컴파일·실행해서 더는 멈추지 않는다는 걸 확인했습니다.
* `std::scoped_lock`의 보장은 **그 호출 한 번에 동시에 넘겨진 락들 사이에서만** 유효하고, 락을 쥔 채로 다른 곳에서 또 락을 잡는 코드까지는 못 막는다는 걸 정직하게 짚었습니다 — 4장이 짚어온 "도구의 보장은 정확히 여기서 끝난다"는 패턴이 여기서도 그대로 반복됩니다.

4부에서는 이 책의 세 번째 이론 — 범주론 — 을 concepts로 인코딩합니다. 8장에서 완성한 `WorkerSession`이 배치를 처리한 **결과**를 `std::optional`/`std::expected` 기반 Functor/Monad 인터페이스로 감싸는 것부터 시작합니다.
