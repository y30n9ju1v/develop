'''

11장은 ``std::future``에 표준 ``.then()``이 없다는 한계를 짚으며, 진짜 논블로킹 비동기 콤비네이터는 C{pp}26의 `std::execution`(P2300, 센더/리시버)이 정식으로 채택되기 전까지는 없다고 정직하게 인정했습니다. 그리고 이 책이 지은 `then_async`(블록하는 새 스레드를 하나 더 만드는 방식)를 그 표준 프레임워크의 "아주 거친 근사"라고 불렀습니다.

이 장은 **오늘 당장 쓸 수 있는 다른 근사** — C{pp}20 코루틴 — 를 보여줍니다. ``std::execution``처럼 실행기(executor)나 스케줄러까지 표준으로 갖춘 프레임워크는 아니지만, 코루틴은 "여러 단계를 순서대로 잇는 계산"을 `.and_then()` 체인이 아니라 **평범한 순차 코드처럼 보이는 문법**으로 쓸 수 있게 해줍니다 — 그리고 그 밑바탕에서 하는 일은 10장이 `concept Functor`/``Monad``로 인코딩했던 bind/then 구조와 정확히 같습니다. 문법이 다를 뿐, 이론은 똑같습니다.

== 최소한의 `Task<T>`: 코루틴 프리미티브를 손으로 짜기

C{pp}20 코루틴은 언어가 `co_await`/`co_return` 문법과 컴파일러 변환 규칙만 정의하고, "이 함수가 코루틴일 때 실제로 무슨 일이 일어나는가"는 전부 사용자가 정의하는 ``promise_type``에 맡깁니다 — 이 책이 지금까지 `GCounter`(14장), `ResultChannel`(5장), `DataSegmentHandle`(7장)을 손으로 짰던 것과 같은 자리에, 이번엔 코루틴 타입 자체를 손으로 짭니다.

[source,cpp]
----
#include <coroutine>
#include <exception>
#include <optional>
#include <utility>

template <typename T>
class Task {
public:
  struct promise_type {
    std::optional<T> value_;
    std::exception_ptr error_;

    Task get_return_object() {
      return Task{std::coroutine_handle<promise_type>::from_promise(*this)};
    }
    std::suspend_never initial_suspend() noexcept { return {}; }  // 만들자마자 바로 실행 시작
    std::suspend_always final_suspend() noexcept { return {}; }   // 끝나도 핸들을 살려둔다 (결과를 꺼내야 하므로)
    void return_value(T v) { value_ = std::move(v); }
    void unhandled_exception() { error_ = std::current_exception(); }
  };

  explicit Task(std::coroutine_handle<promise_type> h) : handle_(h) {}
  Task(Task&& other) noexcept : handle_(std::exchange(other.handle_, {})) {}
  Task& operator=(Task&& other) noexcept {
    if (this != &other) {
      if (handle_) handle_.destroy();               // 지금 갖고 있던 핸들부터 정리하고
      handle_ = std::exchange(other.handle_, {});    // 새 핸들을 넘겨받고 원본을 비운다
    }
    return *this;
  }
  Task(const Task&) = delete;
  Task& operator=(const Task&) = delete;
  ~Task() { if (handle_) handle_.destroy(); }

  T result() {
    if (handle_.promise().error_) std::rethrow_exception(handle_.promise().error_);
    return std::move(*handle_.promise().value_);
  }

private:
  std::coroutine_handle<promise_type> handle_;
};
----

이 ``Task<T>``는 정말로 필요한 것만 갖췄습니다 — ``promise_type``이 코루틴의 반환값(`return_value`)과 예외(`unhandled_exception`)를 저장하고, ``get_return_object``가 그 상태를 가리키는 핸들을 감싼 ``Task<T>``를 돌려줍니다. 복사는 7장의 ``DataSegmentHandle``과 같은 이유로 삭제했고, 이동 생성자와 **이동 대입 연산자**를 짝으로 갖췄습니다 — 이동 대입은 자기 대입을 걸러내고, 지금 갖고 있던 핸들(있다면)을 먼저 정리한 뒤에야 새 핸들의 소유권을 넘겨받습니다. ``std::coroutine_handle``도 결국 자원 하나(코루틴 프레임)를 가리키는 핸들이므로, 7장이 세운 "이동은 원본을 무효 상태로 만들고, 소멸자는 몇 번 불려도 안전해야 한다"는 원칙이 여기서도 그대로 적용됩니다. ``initial_suspend()``가 ``std::suspend_never``라는 게 이 구현의 핵심 성격을 결정합니다 — **코루틴이 만들어지자마자 첫 `co_await`/``co_return``을 만날 때까지 즉시, 동기적으로 실행됩니다.** 이건 ``std::execution``이 지향하는 "지연 실행(lazy)되다가 실행기가 스케줄링할 때 시작"하는 모델과 다릅니다 — 이 장의 ``Task<T>``는 그런 실행기가 없으므로, 호출한 순간 그 스레드 위에서 곧바로 실행되기 시작하는 **즉시 실행(eager)** 코루틴입니다. 뒤에서 이 차이가 정확히 무엇을 잃는지 다시 짚습니다.

``co_await``로 다른 ``Task<T>``를 기다리게 하려면 awaiter도 필요합니다.

[source,cpp]
----
template <typename T>
auto operator co_await(Task<T>&& t) {
  struct Awaiter {
    Task<T> task;
    bool await_ready() const noexcept { return true; }  // eager라 이미 끝나 있다
    void await_suspend(std::coroutine_handle<>) const noexcept {}
    T await_resume() { return task.result(); }
  };
  return Awaiter{std::move(t)};
}
----

``await_ready()``가 ``true``라는 것도 같은 이유입니다 — ``Task<T>``가 ``initial_suspend``에서 즉시 실행되므로, ``co_await``가 그 ``Task``를 받는 시점엔 이미 계산이 끝나 있습니다. 그래서 이 awaiter는 실제로는 절대 서스펜드하지 않고 곧바로 결과를 꺼내옵니다 — "코루틴을 기다린다"는 문법을 쓰지만, 진짜 비동기 대기는 아닙니다.

== ``process_batch``를 코루틴으로 다시 쓰기

9~10장의 `process_batch` → `validate` → `report` 파이프라인을 `.and_then()` 체인 대신 ``co_await``로 이어봅니다.

[source,cpp]
----
Task<std::expected<BatchResult, std::string>> process_batch_task(
    const WorkerSession& session, int worker_id, int segment_id) {
  if (segment_id < 0) co_return std::unexpected("corrupt segment id");
  co_return BatchResult{worker_id, static_cast<long>(segment_id) * 31};
}

Task<std::expected<Reported, std::string>> process_batch_async(
    const WorkerSession& session, int worker_id, int segment_id) {
  auto processed = co_await process_batch_task(session, worker_id, segment_id);
  if (!processed) co_return std::unexpected(processed.error());

  auto validated = validate(*processed);
  if (!validated) co_return std::unexpected(validated.error());

  co_return report(*validated, ResultChannel{});
}
----

[source,cpp]
----
int main() {
  Idle conn;
  WorkerSession session(std::move(conn).connect(), DataSegmentHandle(7));
  auto outcome = process_batch_async(session, 1, 7).result();
  std::cout << "coroutine pipeline succeeded: " << outcome.has_value() << "\n";

  WorkerSession bad_session(std::move(Idle{}).connect(), DataSegmentHandle(-99));
  auto bad_outcome = process_batch_async(bad_session, 2, -99).result();
  std::cout << "bad pipeline succeeded: " << bad_outcome.has_value()
            << " (" << bad_outcome.error() << ")\n";
}
----

[source]
----
$ clang++ -std=c++23 -O0 -fcoroutines coroutine_pipeline.cpp -o coroutine_pipeline && ./coroutine_pipeline
coordinator connected to worker
acquired segment 7
coroutine pipeline succeeded: 1
coordinator connected to worker
acquired segment -99
bad pipeline succeeded: 0 (corrupt segment id)
----

10장의 ``process_batch(session, ...).and_then(validate).and_then(...)``와 이 ``process_batch_async``가 하는 일은 **정확히 같습니다** — 앞 단계가 실패하면 뒤 단계를 건너뛰고 실패를 그대로 전파합니다. 다른 건 오직 문법입니다: ``.and_then(f)``가 "성공하면 ``f``를 호출해서 이어 붙인다"는 걸 **함수 합성**으로 표현하는 반면, ``co_await ...; if (!ok) co_return ...;``는 같은 걸 **순차적인 명령문**으로 표현합니다. 둘 다 결국 "실패하면 즉시 중단하고 그 실패를 결과로 감싸서 돌려준다"는 같은 bind 연산을 서로 다른 표면 문법으로 감싼 것뿐입니다 — 10장에서 `concept Functor`/``Monad``로 짚었던 그 구조가, 언어 차원의 코루틴 변환으로도 똑같이 인코딩될 수 있다는 걸 이 예제가 보여줍니다.

== 코루틴 안에서 협조적으로 취소하기

5장에서 ``std::stop_token``으로 워커를 작업 도중 협조적으로 취소하는 걸 봤습니다. 코루틴에 ``stop_token``을 넘기면, 서스펜드 지점(여기서는 `co_await` 직전)마다 취소 여부를 확인해서 조기 종료할 수 있습니다.

[source,cpp]
----
Task<std::expected<Reported, std::string>> process_batch_cancelable(
    const WorkerSession& session, int worker_id, int segment_id, std::stop_token tok) {
  if (tok.stop_requested()) co_return std::unexpected("cancelled before start");

  auto processed = co_await process_batch_task(session, worker_id, segment_id);
  if (!processed) co_return std::unexpected(processed.error());

  if (tok.stop_requested()) co_return std::unexpected("cancelled after process_batch");  // 협조적 취소 지점

  auto validated = validate(*processed);
  if (!validated) co_return std::unexpected(validated.error());

  co_return report(*validated, ResultChannel{});
}
----

[source,cpp]
----
int main() {
  std::stop_source src;
  Idle conn;
  WorkerSession session(std::move(conn).connect(), DataSegmentHandle(7));

  src.request_stop();  // process_batch_task가 끝난 뒤, 다음 확인 지점에서 잡힌다
  auto outcome = process_batch_cancelable(session, 1, 7, src.get_token()).result();
  std::cout << "cancelled run: " << outcome.has_value()
            << " (" << outcome.error() << ")\n";
}
----

[source]
----
$ clang++ -std=c++23 -O0 -fcoroutines coroutine_cancel.cpp -o coroutine_cancel && ./coroutine_cancel
coordinator connected to worker
acquired segment 7
cancelled run: 0 (cancelled after process_batch)
----

`tok.stop_requested()` 확인이 `co_await` 사이사이에 박혀 있으므로, 이 코루틴은 "지금 서스펜드 지점에 도달했는데 취소 요청이 들어와 있다면 더는 진행하지 않는다"는 5장과 똑같은 협조적 취소 원리를 그대로 따릅니다 — 다른 점은 이 확인이 스레드 루프의 매 반복이 아니라, **코루틴이 논리적으로 한 단계씩 진행하는 지점마다** 박혀 있다는 것뿐입니다.

== 정직하게 짚어야 할 한계: 이 ``Task<T>``가 실제로 하지 않는 일

이 장의 ``Task<T>``가 정확히 무엇을 하고 무엇을 안 하는지 분명히 해둘 필요가 있습니다.

* **실행기(executor)가 없습니다.** ``initial_suspend``가 ``std::suspend_never``이므로, 이 ``Task<T>``는 지연 실행되거나 스레드 풀에 스케줄링되지 않습니다 — 호출한 스레드 위에서 그 자리에서 즉시, 동기적으로 실행됩니다. `std::async`(11장)처럼 실제로 다른 스레드에서 병렬로 돌리려면 여전히 ``std::async``나 ``std::jthread``로 이 코루틴 호출 자체를 감싸야 합니다 — ``co_await``를 쓴다고 저절로 병렬이 되는 게 아닙니다.
* **취소가 전파되지 않습니다.** ``stop_token``을 명시적으로 넘기고, 코드 안에서 매 지점마다 손으로 ``stop_requested()``를 확인해야 합니다 — 상위 ``Task``가 취소되면 그 안에서 ``co_await``하는 하위 ``Task``까지 자동으로 취소 신호가 흘러 들어가는 구조적 전파는 이 구현에 없습니다. ``std::execution``이 정식으로 제공할 구조적 동시성(structured concurrency)의 핵심 약속 중 하나가 바로 이 자동 취소 전파인데, 이 장의 ``Task<T>``는 그 약속의 아주 얕은 겉모습(`co_await` 문법)만 흉내 냅니다.
* **에러가 예외로만 전파됩니다(그리고 이 예제에선 ``std::expected``로 한 번 더 감쌌습니다).** ``unhandled_exception``이 예외를 저장했다가 ``result()``를 부를 때 다시 던지는 정도의 최소 구현이라, ``std::execution``의 리시버가 값/에러/취소 세 가지 완료 경로를 명시적으로 구분하는 것과 달리 이 ``Task<T>``는 그런 세분화가 없습니다.

11장이 ``then_async``를 "거친 근사"라고 불렀던 것과 같은 자리에, 이 장의 ``Task<T>``도 정확히 같은 종류의 근사입니다 — 문법은 ``std::execution``이 최종적으로 제공할 코루틴 통합과 겉보기엔 비슷하지만, 그 밑을 받쳐줄 실행기·취소 전파·구조적 동시성 보장은 전혀 없습니다. 코루틴은 **시퀀싱을 표현하는 문법**을 오늘 당장 제공하지만, 그 문법 아래에서 실제로 스케줄링과 취소를 안전하게 관리하는 일까지는 대신해주지 않습니다 — 그 일은 여전히 (이 장의 ``Task<T>``처럼) 직접 짜거나, ``std::execution``이 표준화될 때까지 기다려야 합니다.

== 팁 박스: C{pp}17 환경이라면

[NOTE]
====
코루틴(`co_await`/`co_return`/`co_yield`, `<coroutine>` 헤더, `promise_type` 프로토콜)은 **순수 C{pp}20 언어 기능**입니다 — C{pp}17에는 이에 대응하는 언어 차원의 문법이 전혀 없습니다. 팁 박스가 늘 그랬듯 "C{pp}17로 어떻게 흉내 내는가"를 보여드리고 싶지만, 이번엔 정직하게 말씀드릴 것은 **C{pp}17에는 진짜 코루틴이 없다**는 사실 그 자체입니다 — 흉내를 낼 수 있는 게 아니라, 이 장이 통째로 건너뛰어야 할 기능입니다.

C{pp}17 프로젝트에서 이 장과 같은 "여러 단계를 순서대로 잇는 계산"이 필요하다면, 가장 가까운 대체물은 11장의 `.and_then()` 체인(또는 ``then_async``처럼 콜백/퓨처를 체이닝하는 스타일)입니다 — 문법은 ``co_await``보다 장황해지지만(중첩된 람다, 명시적인 `.and_then()` 호출), 이 장에서 확인했듯 **이론적으로 표현하는 구조(bind/then)는 완전히 같습니다.** 즉 C{pp}17 환경이라면 이 장 전체를 "코루틴 문법으로 쓸 수 없으니, 11장의 `.and_then()` 체인으로 같은 시퀀싱을 표현한다"로 요약해서 건너뛰면 됩니다 — 잃는 건 코드의 겉모양(중첩 대신 순차적으로 읽히는 문법)뿐이고, 이 장의 ``Task<T>``가 어차피 실행기도 취소 전파도 없는 즉시 실행 근사였다는 걸 감안하면, `.and_then()` 체인이 놓치는 것도 딱 그만큼입니다.
====

== 요약

* `promise_type`, `get_return_object`, `initial_suspend`/`final_suspend`, `co_await` 연산자를 손으로 짜서 최소한의 `Task<T>` 코루틴 타입을 만들고, 이게 ``std::suspend_never``를 쓰는 **즉시 실행(eager)** 코루틴이라는 걸 확인했습니다.
* `process_batch` → `validate` → `report` 파이프라인을 `co_await` 체인으로 다시 써서, 10장의 `.and_then()` 체인과 정확히 같은 실패 전파 구조를 다른 문법(순차적인 명령문 vs 함수 합성)으로 표현한다는 걸 실행 결과로 확인했습니다.
* 5장의 ``std::stop_token``을 코루틴에 넘겨 `co_await` 사이사이의 확인 지점에서 협조적으로 취소하는 걸 실제로 구현했습니다.
