'''

타입 시스템이 보통 신경 쓰지 않는 것 중 하나가 "값이 몇 번, 누구에 의해 쓰이는가"입니다. 이 책은 그중에서도 **여러 스레드가 동시에** 값을 건드릴 때 생기는 문제로 시작합니다 — 그리고 이 책 전체에서 계속 키워나갈 예제 시스템 **TaskGrid**의 가장 초라한 첫 버전으로 시작합니다.

TaskGrid는 이런 걸 하는 시스템입니다 — 코디네이터(coordinator) 하나가 작업 배치(batch) 여러 개를 워커(worker) 스레드들에게 나눠주고, 각 워커가 배치를 처리하면서 전체 진행률을 갱신합니다. 진행률을 어떻게 세는지부터 잘못 짜면 무슨 일이 생기는지, 가장 단순하게 만들어봅시다.

== 두 워커가 같은 진행률 변수를 동시에 증가시키면

[source,cpp]
----
#include <thread>
#include <iostream>

int progress = 0;  // 코디네이터가 워커들과 공유하는 "처리한 작업 개수" 카운터

void worker_process_batches() {
  for (int i = 0; i < 100000; i++) progress++;  // 배치 하나 처리할 때마다 진행률 +1
}

int main() {
  std::thread w1(worker_process_batches), w2(worker_process_batches);
  w1.join();
  w2.join();
  std::cout << "total progress: " << progress << "\n"; // 기대: 200000
}
----

두 워커가 각각 10만 개씩 배치를 처리하며 `progress`를 증가시키니 최종값은 `200000`이어야 할 것 같습니다. 실제로 `clang++ -std=c++23 -pthread`로 컴파일해서 세 번 돌려봤습니다.

[source]
----
$ ./race
100372
$ ./race
103367
$ ./race
111361
----

**매번 다른, 그리고 항상 `200000`보다 작은 값**이 나옵니다. `progress++`는 겉보기엔 한 줄이지만 실제로는 "읽고, 더하고, 쓴다"는 세 단계입니다 — 두 워커가 동시에 같은 값을 읽어서 각자 더한 뒤 쓰면, 한쪽의 증가분이 사라집니다. 이게 **데이터 경쟁(data race)** 입니다 — 코디네이터가 "지금까지 몇 개나 처리됐는지" 알고 싶을 뿐인데, 그 숫자 자체가 거짓말을 하는 셈입니다.

== 컴파일러가 아무 말도 안 해준다

주목할 점 — 이 코드는 경고 하나 없이 컴파일됩니다. `int progress`는 지극히 평범한 전역 변수이고, `progress++`도 지극히 평범한 증가 연산입니다. C++ 타입 시스템의 눈에는 "두 워커 스레드가 이 변수를 동시에 건드릴 수 있다"는 사실이 **전혀 보이지 않습니다** — `int`라는 타입은 "누가 언제 접근하는가"를 아무것도 표현하지 않기 때문입니다. 이건 잠긴 문을 다시 여는 것과 같은 종류의 버그입니다 — 실수가 실수라는 게 타입에 전혀 안 나타납니다.

== 도구로 검출하기: ThreadSanitizer

C++ 타입 시스템은 이걸 못 잡지만, 컴파일러에 내장된 **런타임 검출 도구**는 잡을 수 있습니다. 같은 코드를 `-fsanitize=thread`(ThreadSanitizer, TSan)를 켜서 다시 빌드하고 실행했습니다.

[source]
----
$ clang++ -std=c++23 -O0 -pthread -fsanitize=thread taskgrid_naive.cpp -o taskgrid_naive_tsan
$ ./taskgrid_naive_tsan
==================
WARNING: ThreadSanitizer: data race (pid=34604)
  Write of size 4 at 0x000100db8000 by thread T1:
    #0 worker_process_batches() ...
  Previous write of size 4 at 0x000100db8000 by thread T2:
    #0 worker_process_batches() ...
  Location is global 'progress' at 0x000100db8000 (taskgrid_naive_tsan+0x10000c000)
  ...
SUMMARY: ThreadSanitizer: data race (taskgrid_naive_tsan:arm64+0x100000728) in worker_process_batches()+0x50
==================
100000
----

TSan이 정확히 `progress`라는 전역 변수를 두 스레드(`T1`, `T2`)가 동기화 없이 동시에 쓰고 있다는 걸 짚어냅니다. 이건 이 책 전체에서 반복해서 쓸 도구입니다 — **타입 시스템이 컴파일 타임에 막지 못하는 것을, 최소한 런타임에 확실하게 검출**해주는 안전망입니다. (2부부터는 타입 시스템 자체가 컴파일 타임에 막는 기법을 다룹니다 — TSan은 "실행해봐야 안다"는 한계가 있지만, 2부의 타입 상태 패턴은 "실행 전에 이미 안다"는 더 강한 보장을 목표로 합니다.)

== 고치기: `std::atomic`

[source,cpp]
----
#include <thread>
#include <atomic>
#include <iostream>

std::atomic<int> progress{0};
void worker_process_batches() {
  for (int i = 0; i < 100000; i++) progress.fetch_add(1, std::memory_order_relaxed);
}

int main() {
  std::thread w1(worker_process_batches), w2(worker_process_batches);
  w1.join();
  w2.join();
  std::cout << "total progress: " << progress.load() << "\n";
}
----

`std::atomic<int>`로 바꾸고 `fetch_add`로 증가시키면, TSan을 켜도 경고가 사라지고 항상 `200000`이 나옵니다(세 번 실행해서 확인).

[source]
----
$ ./taskgrid_naive_fixed
total progress: 200000
$ ./taskgrid_naive_fixed
total progress: 200000
$ ./taskgrid_naive_fixed
total progress: 200000
----

`std::atomic<int>`는 "읽고 더하고 쓰는" 세 단계를 하드웨어 수준에서 **쪼갤 수 없는 한 동작**으로 만듭니다 — 두 스레드가 동시에 `fetch_add`를 호출해도 한쪽이 끝난 뒤 다른 쪽이 시작하는 것처럼 동작합니다.

`std::atomic<int>`가 이 장의 최종 답은 아닙니다 — 진행률 하나를 여러 워커가 공유하는 설계 자체가 코디네이터·워커 수가 늘어날수록 매번 원자적 연산으로 경합하게 만드는 구조입니다. 14장에서 워커마다 **자기만의 진행률 칸**을 갖고 동기화 없이 갱신한 뒤 나중에 합치는 완전히 다른 전략(CRDT)으로 이 같은 문제를 다시 풉니다 — 이 장의 `std::atomic<int> progress`는 그 여정의 출발점으로 계속 참조됩니다.

== 또 다른 흔한 버그: join을 잊는 것

데이터 경쟁만 병렬 프로그래밍의 문제가 아닙니다. 워커 스레드를 만들어놓고 `join()`(또는 `detach()`)을 잊으면 어떻게 될까요.

[source,cpp]
----
#include <thread>
#include <chrono>

void worker_process_one_batch() { std::this_thread::sleep_for(std::chrono::milliseconds(10)); }

int main() {
  std::thread w(worker_process_one_batch);  // join()도 detach()도 안 함
}
----

[source]
----
$ ./taskgrid_raw_thread_terminate
libc++abi: terminating
$ echo $?
134
----

`std::thread`의 소멸자는 "이 스레드가 아직 join도 detach도 안 됐다면, `std::terminate()`를 호출한다"고 명세되어 있습니다 — 프로그램이 그냥 죽어버립니다. 이것도 타입 시스템이 못 잡는 종류의 버그입니다: `std::thread` 변수를 선언해놓고 `join()`을 안 부르는 게 문법적으로 전혀 이상하지 않으니까요.

C++20은 이걸 `std::jthread`(joining thread)로 고칩니다.

[source,cpp]
----
#include <thread>
#include <iostream>
#include <chrono>

void worker_process_one_batch() { std::this_thread::sleep_for(std::chrono::milliseconds(10)); }

int main() {
  std::jthread w(worker_process_one_batch); // 소멸자가 자동으로 join한다 — 잊을 방법이 없다
  std::cout << "coordinator continues; worker jthread will auto-join at scope exit\n";
}
----

[source]
----
$ ./taskgrid_jthread_demo
coordinator continues; worker jthread will auto-join at scope exit
----

`std::jthread`의 소멸자는 (아직 join/detach 안 됐다면) **자동으로 `join()`을 호출**합니다 — RAII 원칙(자원 획득이 초기화다, 소멸자가 정리를 책임진다)을 스레드에 적용한 것입니다. 이게 이 책 3부에서 다룰 "이동 전용 타입과 RAII로 자원을 정확히 한 번 다룬다"는 주제의 첫 예고편입니다 — `std::jthread`는 "스레드를 안 정리하는" 버그 하나를 **소멸자 설계**로 원천 봉쇄합니다.

== 팁 박스: C++17 환경이라면

[NOTE]
====
**`std::atomic`은 C++17에서도 그대로 씁니다** — `std::atomic<T>`와 `fetch_add`는 C++11부터 있었으니 이 장의 핵심 수정은 C++17에서도 한 글자도 안 바뀝니다.

**`std::jthread`는 C++20부터입니다.** C++17에는 없으므로, 직접 RAII 래퍼를 만들어 흉내 내는 게 흔한 방식입니다.

[source,cpp]
----
class joining_thread {
  std::thread t_;
public:
  template <class F> explicit joining_thread(F&& f) : t_(std::forward<F>(f)) {}
  ~joining_thread() { if (t_.joinable()) t_.join(); }
  joining_thread(const joining_thread&) = delete;
  joining_thread& operator=(const joining_thread&) = delete;
};
----

이렇게 만든 `joining_thread`는 `std::jthread`와 똑같이 소멸자에서 자동으로 `join()`합니다 — 다만 진짜 `std::jthread`가 주는 **협조적 취소**(`std::stop_token`으로 "이제 그만 멈춰라"라고 신호를 보내는 것)는 없습니다. C++17에서 취소 신호를 보내려면 `std::atomic<bool>` 플래그를 직접 만들어 작업 함수가 주기적으로 그 플래그를 확인하게 짜야 합니다 — 5장에서 워커를 작업 도중에 협조적으로 취소하는 예제를 만들며, 바로 이 수동 플래그 방식과 `std::stop_token`을 나란히 놓고 비교합니다.
====

== 요약

* 두 워커 스레드가 동기화 없이 같은 진행률 변수(`progress`)를 동시에 증가시키면, 컴파일은 경고 없이 되지만 실행 결과는 매번 다르고 틀립니다 — 이게 데이터 경쟁입니다.
* `-fsanitize=thread`(ThreadSanitizer)로 이 경쟁을 실제로 검출했고, `std::atomic<int>`로 고쳐서 `fetch_add`가 항상 정확히 `200000`을 낸다는 걸 세 번 실행해 확인했습니다.
* `std::thread`를 join하지 않으면 소멸자가 `std::terminate()`를 불러 프로그램이 죽는다는 것도 실제로 재현했고, `std::jthread`가 소멸자에서 자동으로 join해서 이 버그를 원천 봉쇄한다는 걸 확인했습니다.
* C++17에는 `std::jthread`가 없지만, RAII 원칙을 그대로 살린 얇은 래퍼로 "자동 join"만큼은 흉내 낼 수 있습니다 — 다만 협조적 취소는 직접 만들어야 합니다.
* 이 책은 여기서부터 TaskGrid라는 하나의 예제 시스템을 계속 키워나갑니다 — 이 장의 `progress`는 14장에서 CRDT로 다시 등장해서, 지금까지 배운 "동기화로 막는다"는 전략과 완전히 다른 방식으로 안전해집니다.
