2부에서는 세션 타입을 타입 상태 패턴으로 흉내냈습니다. 3부에서는 **선형 타입(linear type)** — "값은 정확히 한 번 쓰여야 한다" — 을 C++의 **이동 전용 타입(move-only type)** 으로 흉내냅니다.

== raw pointer는 아무 제약이 없다

[source,cpp]
----
int main() {
  int* p = new int(42);
  int* q = p; // 그냥 복사 -- 아무것도 막지 않는다
  delete p;
  delete q;   // 버그: 이중 해제 (double free)
}
----

`int*`는 얼마든지 자유롭게 복사할 수 있는 평범한 값입니다 — `p`를 `q`에 대입하는 순간 둘 다 **같은 메모리**를 가리키게 되고, 둘 다에 대고 `delete`를 부르면 같은 메모리를 두 번 해제하는 겁니다. AddressSanitizer(`-fsanitize=address`, ASan)로 실제 확인해봅시다.

[source]
----
$ clang++ -std=c++23 -O0 -fsanitize=address double_free.cpp -o double_free_asan
$ ./double_free_asan
==34830==ERROR: AddressSanitizer: attempting double-free on 0x6020000000f0 in thread T0:
    #0 ... in main+0xbc
0x6020000000f0 is located 0 bytes inside of 4-byte region [0x6020000000f0,0x6020000000f4)
freed by thread T0 here: ...
previously allocated by thread T0 here: ...
SUMMARY: AddressSanitizer: double-free ...
==34830==ABORTING
----

1장의 ThreadSanitizer가 데이터 경쟁을 잡았듯, AddressSanitizer는 메모리 오용(이중 해제, 버퍼 오버런, use-after-free)을 잡습니다 — 이것도 **런타임에** 잡는 안전망입니다. 1장에서 데이터 경쟁을 이야기했던 것과 같은 종류의 버그(닫힌 자원을 또 쓰는 것)의 메모리 버전입니다.

== `std::unique_ptr`: 복사 자체가 컴파일 에러

[source,cpp]
----
int main() {
  std::unique_ptr<int> p = std::make_unique<int>(42);
  std::unique_ptr<int> q = p; // 버그 시도: unique_ptr를 복사
}
----

[source]
----
$ clang++ -std=c++23 -O0 uptr_nocopy.cpp -o /tmp/u
uptr_nocopy.cpp:4:24: error: call to implicitly-deleted copy constructor of 'std::unique_ptr<int>'
    4 |   std::unique_ptr<int> q = p;
      |                        ^   ~
.../unique_ptr.h:211:55: note: copy constructor is implicitly deleted because
'unique_ptr<int>' has a user-declared move constructor
----

`std::unique_ptr`의 복사 생성자는 **명시적으로 삭제**되어 있습니다(`unique_ptr(const unique_ptr&) = delete;`, 표준 라이브러리 안에 이렇게 정의되어 있습니다). raw pointer였다면 조용히 컴파일되고 런타임에 ASan이 잡아야 했던 실수가, `unique_ptr`에서는 **그 줄을 적는 순간** 컴파일이 거부됩니다 — 선형 타입 이론이 "이 값을 두 번 참조하는" 시도 자체를 타입 규칙으로 봉쇄하는 것과 같은 효과를, C++은 복사 생성자를 지우는 것으로 냅니다.

== 이동은 허용된다 — 그리고 원본은 안전해진다

`unique_ptr`가 아예 옮길 수 없는 건 아닙니다. **이동(move)** 은 명시적으로 허용됩니다.

[source,cpp]
----
int main() {
  std::unique_ptr<int> p = std::make_unique<int>(42);
  std::unique_ptr<int> q = std::move(p); // 진짜 이동
  std::cout << "p.get() after move: " << p.get() << "\n";
  std::cout << "*q after move: " << *q << "\n";
}
----

[source]
----
$ clang++ -std=c++23 -O0 -fsanitize=address uptr_moved.cpp -o uptr_moved && ./uptr_moved
p.get() after move: 0
*q after move: 42
----

이동 후 `p.get()`은 `0`(즉 `nullptr`)입니다 — `unique_ptr`의 이동 생성자는 소유권만 `q`로 넘기고 `p`의 내부 포인터를 명시적으로 `nullptr`로 리셋합니다. `p`와 `q`가 각자 스코프를 벗어날 때 둘 다 소멸자가 호출되지만, `p`의 소멸자는 "`nullptr`를 delete하라"는 요청을 받는데 **`delete nullptr`는 C++ 표준이 명시적으로 안전하다고 보장하는(아무 일도 안 일어나는) 연산**입니다 — 그래서 ASan을 켜도 아무 경고가 안 뜹니다. 진짜 메모리 해제는 `q`의 소멸자가 한 번만 합니다.

이건 3장에서 정직하게 인정했던 구멍 — "이동 후에도 원래 변수는 살아 있다" — 이 여전히 사실이라는 걸 보여주면서도, `unique_ptr`가 그 구멍을 **자원 관점에서는 안전하게 메운다**는 걸 보여줍니다. `p`라는 변수 자체는 이동 후에도 스코프에 남아 있지만, 그 안에 든 값이 스스로 "나는 이제 빈 상태다"라고 표시하고, 빈 상태에 대한 연산(소멸)이 안전하도록 설계되어 있습니다. 3장의 `Disconnected`(빈 클래스)와 정확히 대비됩니다 — `Disconnected`는 "이동됐다"와 "안 됐다"를 구별할 상태 자체가 없었지만, `unique_ptr`는 내부 포인터라는 구별 가능한 상태가 있고 그 상태에 대한 "빈 경우의 동작"까지 미리 정의해뒀습니다.

== 팁 박스: C++17 환경이라면

[NOTE]
====
`std::unique_ptr`, 이동 생성자/이동 대입, `= delete`는 전부 **C++11**부터 있었습니다 — 이 장은 C++17에서 한 글자도 안 바뀝니다. 오히려 C++17이 이 장의 이야기에 보태는 건 `std::make_unique`(C++14부터)가 이미 있다는 전제 위에서, **강제된 평가 순서**입니다 — C++17부터는 함수 인자 평가 순서에 대한 규칙이 강화되어, `f(std::unique_ptr<T>(new T), g())`처럼 `new`와 다른 인자의 평가가 뒤섞여서 `g()`가 예외를 던지면 갓 만든 `T`가 아무에게도 소유되지 못한 채 새는(leak) 유명한 함정이 C++17부터는 사라졌습니다(다만 애초에 `std::make_unique`를 쓰면 이 함정 자체가 발생하지 않으므로, 이 책의 예제처럼 `make_unique`를 쓰는 코드에는 해당하지 않는 이야기입니다).
====

== 요약

* raw pointer를 복사해서 두 번 `delete`하는 이중 해제 버그를 실제로 만들고, AddressSanitizer로 검출했습니다 — 1장의 ThreadSanitizer와 짝을 이루는, "런타임에라도 확실히 잡는" 안전망입니다.
* `std::unique_ptr`는 복사 생성자가 삭제되어 있어서, 같은 실수(복사해서 이중 해제)를 시도하는 순간 컴파일이 실패한다는 걸 실제 에러 메시지로 확인했습니다.
* 이동은 허용되고, 이동 후 원본은 안전한 `nullptr` 상태가 되어 소멸자가 자동으로 아무 일도 안 하게 된다는 것도 확인했습니다 — 3장에서 지적한 "이동 후에도 변수는 살아 있다"는 구멍이, 빈 상태의 동작을 안전하게 정의해두는 것으로 메워질 수 있다는 걸 보여줍니다.

다음 장에서는 `unique_ptr`가 감싸는 게 메모리가 아니라 **우리가 만든 자원**(예: 파일 핸들, 락)일 때 이 패턴을 직접 손으로 짜봅니다 — `unique_ptr`를 그대로 쓰거나, 필요하면 커스텀 이동 전용 클래스를 직접 만드는 두 가지 방법을 다룹니다.
