2~3부는 세션 타입과 선형 타입을 옮겼습니다. 4부는 세 번째 이론 — 범주론(category theory)의 Functor, Monad — 를 C++23의 **concepts** 로 옮깁니다.

== concept으로 "Functor"를 정의하기

범주론에서 Functor는 "구조를 보존하면서 안의 값에 함수를 적용하는 것"이라고 정의됩니다. C++로 옮기면 — "`transform`이라는, 안의 값에 함수를 적용해서 같은 모양의 새 컨테이너를 돌려주는 메서드가 있는 것"입니다.

[source,cpp]
----
template <typename M>
concept Functor = requires(M m) {
  { m.transform([](auto x) { return x; }) };
};
----

`concept`은 "이 요구사항(`requires` 블록 안의 표현식이 실제로 컴파일되는가)을 만족하는 타입만 이 이름으로 부를 수 있다"는 컴파일 타임 술어입니다. `Functor<M>`은 "`M` 타입의 값에 `.transform(함수)`를 부를 수 있다"는 뜻입니다.

== 검증 1: `std::optional`과 `std::expected`가 실제로 Functor다

[source,cpp]
----
static_assert(Functor<std::optional<int>>);
static_assert(Functor<std::expected<int, std::string>>);
static_assert(!Functor<int>); // 평범한 int에는 .transform()이 없다 -- Functor가 아니다
----

세 `static_assert` 모두 통과합니다 — 컴파일 시점에 확인됩니다. C++23의 `std::optional`과 `std::expected`는 **둘 다 새로 `.transform()` 멤버 함수를 얻었습니다**(이전 C++ 표준에는 없었습니다 — 아래 팁 박스에서 다시 다룹니다). 이제 이걸 8장에서 완성한 `WorkerSession`에 실제로 적용해봅시다 — 워커가 배치를 처리한 결과를 감쌀 타입부터 정의합니다.

[source,cpp]
----
struct BatchResult {
  int worker_id;
  long checksum;  // 처리한 배치 내용의 간단한 체크섬
};

// WorkerSession이 붙든 세그먼트를 실제로 "처리"하는 연산.
// 세그먼트 ID가 음수면 손상된 배치로 보고 실패를 표현한다.
std::expected<BatchResult, std::string> process_batch(const WorkerSession& session, int worker_id, int segment_id) {
  if (segment_id < 0) return std::unexpected("corrupt segment id");
  return BatchResult{worker_id, static_cast<long>(segment_id) * 31};
}
----

[source,cpp]
----
Idle conn;
WorkerSession session(std::move(conn).connect(), DataSegmentHandle(7));
auto result = process_batch(session, /*worker_id=*/1, /*segment_id=*/7);
auto doubled = result.transform([](BatchResult r) { r.checksum *= 2; return r; });
std::cout << "checksum: " << doubled->checksum << "\n";

WorkerSession bad_session(std::move(Idle{}).connect(), DataSegmentHandle(-99));
auto bad_result = process_batch(bad_session, 2, -99);
auto bad_doubled = bad_result.transform([](BatchResult r) { r.checksum *= 2; return r; });
std::cout << "error propagated: " << (bad_doubled.has_value() ? "has value" : bad_doubled.error()) << "\n";
----

[source]
----
$ clang++ -std=c++23 -O0 functor_concept.cpp -o functor_concept && ./functor_concept
coordinator connected to worker
acquired segment 7
checksum: 434
coordinator connected to worker
acquired segment -99
error propagated: corrupt segment id
----

`bad_result`(에러 상태)에 `.transform()`을 걸면, 함수는 아예 호출되지 않고 에러가 **그대로 전파**됩니다(`bad_doubled.error()`가 원래 `"corrupt segment id"`를 그대로 갖고 있습니다) — 범주론이 Functor를 "구조를 보존한다"고 정의하는 바로 그 성질입니다. 배치 처리가 성공했으면 값에 함수를 적용하고, 실패했으면 그 "실패"라는 구조 자체는 그대로 유지됩니다.

== Functor 법칙을 실제로 확인하기

Functor는 아무 `transform`이나 다 되는 게 아니라 법칙을 지켜야 합니다 — 그중 항등 법칙(identity law): `m.transform(항등함수)`는 `m` 자신과 같아야 합니다.

[source,cpp]
----
std::expected<BatchResult, std::string> r = BatchResult{1, 217};
auto r2 = r.transform([](BatchResult v) { return v; });
std::cout << "functor identity law holds: "
          << (r->worker_id == r2->worker_id && r->checksum == r2->checksum) << "\n";
----

[source]
----
functor identity law holds: 1
----

`r2`가 정말로 `r`과 같은 값(`worker_id`, `checksum` 둘 다)이라는 걸 확인합니다 — `concept Functor`가 요구하는 건 "`.transform()`이 존재한다"는 문법적 조건뿐이지만, 그 뒤에 있는 **의미론적 법칙**(항등, 결합)까지는 `concept`이 검사해주지 않는다는 것도 짚어둘 만합니다. 이건 2장에서 이미 짚은 "인코딩이지 이식이 아니다"의 또 다른 사례입니다 — `concept`은 "이 함수가 있다"는 걸 컴파일 타임에 강제하지만, "이 함수가 Functor 법칙을 지킨다"는 건 여전히 프로그래머의 책임이자, 테스트로 확인해야 할 몫입니다.

== Monad: `and_then`으로 실패를 자동으로 전파하기

Functor보다 한 단계 더 나가면 Monad입니다 — "효과를 값으로 만들고 합성하는" 도구입니다. `std::expected::and_then`이 정확히 이 역할을 합니다. 워커가 배치를 처리한 뒤, 그 결과를 검증하고, 검증된 결과를 5장의 `ResultChannel`로 보고까지 잇는 두 단계 파이프라인을 만들어봅시다.

[source,cpp]
----
std::expected<BatchResult, std::string> validate(BatchResult r) {
  if (r.checksum == 0) return std::unexpected("checksum is zero -- suspicious batch");
  return r;
}

std::expected<Reported, std::string> report(BatchResult r, ResultChannel ch) {
  return std::move(ch).send(static_cast<int>(r.checksum));
}

Idle conn;
WorkerSession session(std::move(conn).connect(), DataSegmentHandle(7));
auto pipeline = process_batch(session, 1, 7)
                    .and_then(validate)
                    .and_then([](BatchResult r) { return report(r, ResultChannel{}); });
std::cout << "pipeline succeeded: " << pipeline.has_value() << "\n";

WorkerSession bad_session(std::move(Idle{}).connect(), DataSegmentHandle(-99));
auto bad_pipeline = process_batch(bad_session, 2, -99)
                        .and_then(validate)
                        .and_then([](BatchResult r) {
                          std::cout << "this must not print\n";
                          return report(r, ResultChannel{});
                        });
std::cout << "bad pipeline succeeded: " << bad_pipeline.has_value() << " (" << bad_pipeline.error() << ")\n";
----

[source]
----
pipeline succeeded: 1
bad pipeline succeeded: 0 (corrupt segment id)
----

정상 경로는 `process_batch` → `validate` → `report`까지 이어져 성공합니다. 실패 경로는 `process_batch`에서 이미 `"corrupt segment id"`로 실패하고, **그다음 `and_then`들의 람다는 아예 실행되지 않습니다**("this must not print"가 실제로 출력되지 않았습니다) — 이게 Monad의 핵심 힘입니다. 각 단계가 `std::expected<T, std::string>`를 돌려주므로 `.transform()`을 썼다면 중첩된 `expected`가 됐을 텐데, `and_then`은 그 중첩을 자동으로 "평평하게(flatten)" 만들어서 매번 `if (!result) return result;`를 손으로 안 써도 실패가 자동으로 전파되게 합니다.

== 팁 박스: C++17 환경이라면

[NOTE]
====
**`std::optional::transform`/`and_then`은 C++23의 라이브러리 추가분입니다** — `concept`(언어 기능, C++20)과는 별개로, 표준 라이브러리 자체가 C++23이 되기 전까지는 이 멤버 함수들이 아예 없었습니다. 그러니 C++17 환경이라면 두 가지를 따로 흉내 내야 합니다.

`concept`이 없으니 `void_t` 기반 SFINAE 트레잇으로 "이 타입에 `.transform()`이 있는가"를 검사합니다.

[source,cpp]
----
struct identity_fn { template <typename T> T operator()(T x) const { return x; } };

template <typename M, typename = void>
struct is_functor : std::false_type {};

template <typename M>
struct is_functor<M, std::void_t<decltype(std::declval<M>().transform(identity_fn{}))>>
    : std::true_type {};
----

(람다는 C++17에서 "평가되지 않는 문맥"(`decltype` 안)에 못 들어가므로, 대신 함수 객체 구조체 `identity_fn`을 씁니다 — 실제로 람다를 넣어 컴파일해보면 "lambda expression in an unevaluated operand"라는 에러가 나는 걸 확인했습니다.) 그리고 재미있게도 이 트레잇을 `std::optional<int>`에 적용하면 — **C++17 환경에서는 `false`가 나옵니다.** `std::optional` 자체는 C++17부터 있었지만 `.transform()` 멤버는 C++23이 되어서야 붙었기 때문입니다.

[source,cpp]
----
static_assert(!is_functor<std::optional<int>>::value, "pre-C++23 std::optional has no .transform()");

template <typename T>
struct MyBox {
  T value;
  template <typename F>
  auto transform(F f) const { return MyBox<decltype(f(value))>{f(value)}; }
};
static_assert(is_functor<MyBox<int>>::value, "MyBox has .transform() so it counts");
----

우리가 직접 `.transform()`을 가진 `MyBox`를 만들면 그건 트레잇을 통과합니다 — `is_functor`라는 검사 메커니즘 자체는 C++17에서도 똑같이 동작하지만, **검사 대상(`std::optional`)이 그 시절엔 아직 Functor가 아니었다**는 게 이 팁 박스의 진짜 요점입니다. C++17 프로젝트에서 `std::optional`을 Functor처럼 쓰고 싶다면, `.transform()`을 흉내 내는 자유 함수(`transform_optional(opt, f)`)를 직접 만들어야 합니다.
====

== 요약

* `concept Functor`로 "`.transform()`이 있는 타입"을 정의하고, C++23의 `std::optional`/`std::expected`가 실제로 그 요구사항을 만족한다는 걸 `static_assert`로 컴파일 타임에 확인했습니다.
* 8장에서 완성한 `WorkerSession`이 배치를 처리한 결과(`BatchResult`)를 `std::expected<BatchResult, std::string>`으로 감싸, `.transform()`이 에러 상태에서는 함수를 호출하지 않고 그 상태를 그대로 보존한다는 것(Functor의 구조 보존)과, 항등 법칙이 실제로 성립한다는 것도 코드로 검증했습니다 — 다만 `concept`은 문법만 강제하지 의미론적 법칙까지는 강제하지 않는다는 것도 짚었습니다.
* `.and_then()`(Monad의 bind)으로 `process_batch` → `validate` → (5장의) `ResultChannel`로의 `report`까지 잇는 파이프라인을 짜서, 중간 단계가 실패하면 그다음 단계가 정말로 스킵된다는 걸 실행 결과로 확인했습니다.
* C++17에는 `.transform()`/`.and_then()` 자체가 없어서, `concept` 대신 `void_t` SFINAE 트레잇으로 검사 메커니즘은 흉내 낼 수 있지만 `std::optional`은 그 시절엔 진짜로 Functor가 아니었다는 것까지 실제 코드로 확인했습니다.

다음 장에서는 이 Functor/Monad 인터페이스로 **병렬** 파이프라인을 합성합니다 — 여러 `WorkerSession`을 `std::async`로 동시에 돌리고, 이 장의 `and_then`으로 그 결과들을 안전하게 합성해서, 실패가 안전하게 전파되는 병렬 작업 체인을 짭니다.
