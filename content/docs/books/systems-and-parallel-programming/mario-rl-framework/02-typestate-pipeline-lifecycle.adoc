'''

이 책이 조립할 파이프라인은 순서가 있습니다 — 환경을 설정하지 않고 정책을 로드할 수 없고, 정책 없이 학습을 시작할 수 없고, 학습 없이 체크포인트를 저장할 수 없습니다. link:../../safe-parallel-cpp23/03-typestate-basics/[전작]이 ``WorkerConnection``에 썼던 것과 같은 도구 — 단계마다 다른 타입, rvalue 한정 전이 메서드 — 로 이 순서를 컴파일 타임 보장으로 만듭니다.

== 다섯 단계, 다섯 타입

[source,cpp]
----
class Unconfigured {
public:
  [[nodiscard]] EnvReady configure_env(std::string rom) &&;
};

class EnvReady {
  std::string rom_;
public:
  explicit EnvReady(std::string rom) : rom_(std::move(rom)) {}
  [[nodiscard]] PolicyLoaded load_policy(int num_actions) &&;
};

class PolicyLoaded {
  std::string rom_;
  int num_actions_;
public:
  [[nodiscard]] Training start_training() &&;
};

class Training {
  std::string rom_;
  int num_actions_;
  int step_ = 0;
public:
  void step();                          // 반복 호출되므로 소비하지 않는 평범한 메서드
  [[nodiscard]] Checkpointed checkpoint() &&;
};

class Checkpointed {
  int steps_;
public:
  int steps() const { return steps_; }
};
----

``Unconfigured → EnvReady → PolicyLoaded → Training → Checkpointed``로 한 방향으로만 진행합니다. 앞의 네 전이(``configure_env``, ``load_policy``, ``start_training``, ``checkpoint``)는 전작의 ``load_weights``/``compile``처럼 rvalue 한정입니다 — 한 번 쓰면 그 값을 다시 못 씁니다. ``Training::step()``만 예외입니다 — 학습 루프 안에서 수백만 번 반복 호출되므로, 매번 새 객체를 만들며 소비하는 건 말이 안 됩니다(9장의 ``TinyRT::Ready::infer()``와 같은 이유입니다).

== 검증: 이어붙이면 되고, 순서를 어기면 안 됩니다

[source,cpp]
----
Unconfigured u;
Training t = std::move(u).configure_env("SuperMarioBros-v0")
                          .load_policy(7)
                          .start_training();
for (int i = 0; i < 1000; i++) t.step();
Checkpointed c = std::move(t).checkpoint();
----

[source]
----
$ clang++ -std=c++23 -O0 -Wall typestate_pipeline.cpp -o typestate_pipeline && ./typestate_pipeline
checkpointed after 1000 steps
----

체인 전체가 한 번에 이어지고, ``1000``번 반복한 뒤 정확히 그 값이 체크포인트에 남습니다. ``EnvReady`` 상태에서 실수로 ``t.step()``을 부르려 하면 — ``EnvReady``에는 애초에 ``step()``이라는 이름의 메서드가 없으므로 컴파일이 안 됩니다. "환경만 설정하고 정책은 안 불러온 채로 학습을 돌리려는" 실수가, 런타임 널 체크가 아니라 컴파일 타임에 막힙니다.

== 왜 ``Training``만 예외인가

나머지 네 타입은 "한 번 쓰고 버리는" 전작의 ``WorkerSession`` 패턴 그대로입니다. ``Training``은 다릅니다 — 안에 담긴 ``step_`` 카운터가 매 스텝 바뀌는 **가변 상태**이고, 이 상태를 계속 들고 있는 게 이 타입의 존재 이유입니다. 3~10장에서 이 클래스가 실제 환경 핸들, 정책망 파라미터, 롤아웃 버퍼를 하나씩 얻어가며 이 책의 나머지를 채웁니다 — 지금은 뼈대만 세웠습니다.

== 요약

* ``Unconfigured``/``EnvReady``/``PolicyLoaded``/``Training``/``Checkpointed`` 다섯 타입으로 MarioRL 파이프라인의 생명주기를 인코딩했습니다.
* 앞 네 전이는 rvalue 한정 메서드로 "한 번만 쓸 수 있다"를 강제하고, ``Training::step()``만 반복 호출을 허용하는 평범한 메서드로 남겨뒀습니다.
* 순서를 어긴 호출(예: 정책 로드 전에 스텝을 부르는 것)이 그 이름의 메서드 자체가 없어서 컴파일 에러가 된다는 걸 확인했습니다.

다음 장에서는 ``EnvReady``가 실제로 감쌀 것 — CPython을 임베딩해서 ``nes-py`` 마리오 환경을 프레임 단위로 부르는 다리 — 를 만듭니다.
