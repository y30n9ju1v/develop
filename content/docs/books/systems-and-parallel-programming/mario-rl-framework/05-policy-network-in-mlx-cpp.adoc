'''

link:../../mlx-apple-silicon-optimization/[『복사 없는 GPU 프로그래밍』]은 MLX의 **Python** API를 썼습니다. 이 장은 MLX의 **C++ API**(``mlx::core``, ``#include <mlx/mlx.h>``)를 씁니다 — Python 바인딩이 감싸고 있는 그 아래 계층입니다.

== 중요한 사실 하나: C++ MLX에는 ``nn.Module``이 없습니다

Python의 ``mlx.nn``(``nn.Linear``, ``nn.Module`` 같은 고수준 계층)은 ``mlx.core`` 위에 얹은 **Python 전용** 편의 계층입니다 — C++ 쪽 헤더를 뒤져보면 ``conv2d``, ``matmul``, ``maximum``(ReLU) 같은 저수준 연산(``mlx::core::ops``)만 있고, 레이어 클래스는 없습니다. 즉 이 장은 link:../../tinyrt-cpu-gpu-inference/[『TinyRT』]가 그랬듯 CNN을 파라미터 구조체 하나와 순전파 함수 하나로 **손으로** 짭니다.

[source,cpp]
----
#include <mlx/mlx.h>
namespace mx = mlx::core;

struct PolicyParams {
  mx::array W1, W2, Wfc;
};

mx::array policy_forward(const mx::array& x, const PolicyParams& p) {
  // x: (1,84,84,4) NHWC
  auto h1 = mx::maximum(mx::conv2d(x, p.W1, {4,4}, {0,0}), mx::array(0.0f));   // 8x8 stride4 -> 16채널
  auto h2 = mx::maximum(mx::conv2d(h1, p.W2, {2,2}, {0,0}), mx::array(0.0f)); // 4x4 stride2 -> 32채널
  auto flat = mx::reshape(h2, {1, -1});
  return mx::matmul(flat, p.Wfc);
}
----

1장이 프로파일링했던 그 정책망과 정확히 같은 구조(``84×84×4`` 입력, ``8×8``/``4×4`` 컨볼루션, 완전연결)입니다 — 다른 건 순전파를 파이썬 반복문 대신 MLX의 컴파일된 연산 그래프로 짰다는 것뿐입니다.

== 검증: 크기가 맞는가

[source]
----
$ clang++ -std=c++23 -O2 -I mlx/include -L mlx/lib -lmlx policy_forward.cpp -o policy_forward && ./policy_forward
h1 shape: 1x20x20x16
h2 shape: 1x9x9x32
logits shape: 1x7
----

``84×84`` 입력이 ``8×8`` stride 4 컨볼루션을 거쳐 ``20×20``, 다시 ``4×4`` stride 2를 거쳐 ``9×9``로 줄어들고, 완전연결을 지나 ``7``개 행동(``SIMPLE_MOVEMENT``의 행동 개수)에 대한 로짓이 나옵니다 — 크기가 손으로 계산한 값과 정확히 일치합니다.

== 실측: 1장의 병목이 얼마나 줄었는가

[source]
----
$ ./policy_forward
mlx policy forward: 0.5841 ms/call
mlx policy forward (compiled): 0.3907 ms/call
----

1장이 잰 순수 파이썬 루프 컨볼루션(``2.674ms``)과 나란히 놓으면:

[cols="2,2"]
|===
|구현 |순전파 시간

|1장: NumPy, 파이썬 루프 conv |2.674ms
|이 장: MLX C++, 컴파일 없음 |0.584ms
|이 장: MLX C++, ``mx::compile`` |0.391ms
|===

**컴파일 없이도 4.6배, ``mx::compile``을 더하면 6.9배 빨라졌습니다.** link:../../mlx-apple-silicon-optimization/04-compile-fusion/[『복사 없는 GPU 프로그래밍』 4장]이 확인했던 것과 같은 이유입니다 — ``conv2d``/``maximum``/``matmul`` 세 연산을 그래프로 한 번에 스케줄링하면 반복 호출에서 파이썬(여기서는 C++이니 그래프 재구성) 오버헤드가 줄어듭니다. 1장의 병목(75%가 순전파)이 이 정도로 줄었다는 게, 4장까지 쌓아온 프레임워크가 실제로 뭘 벌어들이는지 보여주는 첫 증거입니다.

== 요약

* MLX의 C++ API에는 ``nn.Module``이 없다는 걸 실제 헤더로 확인하고, CNN을 파라미터 구조체 + 순전파 함수로 손으로 짰습니다.
* 1장과 같은 구조의 정책망을 MLX C++로 다시 짜서, 순전파가 4.6배(컴파일 없이) ~ 6.9배(``mx::compile``) 빨라진다는 걸 실측했습니다.
* 1장이 진단한 병목(순전파가 전체 시간의 75%)이 이 장의 결과로 크게 줄어든다는 것도 확인했습니다.

다음 장에서는 이 정책망을 실제로 학습시킵니다 — MLX의 C++ 자동미분(``mx::grad``)으로 PPO를 구현하고, 손으로 미분한 결과와 대조 검증합니다.
