9장은 "배치를 키우면 GPU가 이긴다"는 걸 정책망(컨볼루션 두 겹)으로 확인했습니다. 이 장은 그 결론을 4장의 프레임 전처리(그레이스케일)에 그대로 적용해보면 어떻게 되는지 재봅니다 — link:../../heterogeneous-computing-opencl/06-tiling-and-cache/[『OpenCL로 배우는 헤테로지니어스 컴퓨팅』]이 반복해서 확인한 산술 강도(연산 하나당 메모리 접근량)가 이 답을 가릅니다.

== 같은 배치 크기, 다른 연산

4장의 ``grayscale_resize_cpu``(``mdspan`` 기반 반복문)와, 같은 일을 하는 MLX 텐서 연산(``mx::mean``으로 채널 축을 접는 것)을 배치 1/16/64에서 나란히 잽니다.

[source]
----
$ clang++ -std=c++23 -O2 -I mlx/include -L mlx/lib -lmlx preprocess_dispatch.cpp -o preprocess_dispatch && ./preprocess_dispatch
batch=  1  cpu(mdspan loop)=0.0218ms  gpu(mlx)=0.2405ms  gpu/cpu=11.02x
batch= 16  cpu(mdspan loop)=0.0897ms  gpu(mlx)=0.8846ms  gpu/cpu=9.87x
batch= 64  cpu(mdspan loop)=0.3718ms  gpu(mlx)=2.1151ms  gpu/cpu=5.69x
----

**배치 ``64``에서도 GPU가 5.7배 느립니다.** 9장의 정책망은 정확히 이 배치 크기에서 GPU가 3.4배 **이겼는데**, 같은 배치로 전처리를 돌리면 정반대입니다.

== 왜 정반대인가: 산술 강도

정책망의 컨볼루션은 출력 픽셀 하나를 만드는 데 ``8×8×4=256``번(1층)과 ``4×4×16=256``번(2층)의 곱셈-덧셈을 합니다 — 메모리에서 값 하나를 읽을 때마다 계산을 많이 합니다. 그레이스케일 변환은 픽셀 하나당 ``RGB`` 세 값을 읽어서 평균 한 번 내는 게 전부입니다 — 메모리 접근 대비 계산량이 극히 적습니다. link:../../heterogeneous-computing-opencl/06-tiling-and-cache/[전작]이 컨볼루션과 완전연결에서 확인했던 것과 정확히 같은 구분선이, 여기서는 "정책망 vs 전처리"라는 서로 다른 두 연산 사이에 그어집니다 — **배치가 크다고 전부 GPU로 보낼 이유가 되지 않습니다. 그 배치 안에서 각 연산이 실제로 얼마나 계산을 하는지가 관건입니다.**

== 이 책의 파이프라인에 반영하면

9~10장을 합치면 결론이 명확해집니다 — **프레임 전처리는 항상 CPU에, 정책망 추론은 배치가 충분히 크면(9장 기준 16개 이상) GPU에.** 이건 link:../../tinyrt-cpu-gpu-inference/09-capstone-tinyrt-pipeline/[『TinyRT』 9장]이 "맥스풀은 CPU, 컨볼루션과 완전연결은 GPU"로 정했던 것과 완전히 같은 구조의 결정입니다 — TinyRT는 연산 종류로 나눴고, 이 책은 그 원칙이 강화학습의 전처리/추론 경계에서도 그대로 성립한다는 걸 다시 확인했습니다.

== 요약

* 4장의 그레이스케일 전처리를 9장과 같은 배치 크기(1/16/64)로 CPU/GPU 비교했더니, 배치 64에서도 GPU가 5.7배 느렸습니다.
* 정책망(9장)과 전처리(이 장)가 같은 배치 크기에서 정반대 결론이 나온 이유가 산술 강도(연산당 메모리 접근량) 차이라는 걸 확인했습니다.
* "배치를 키우면 GPU가 유리하다"가 아니라 "그 배치 안에서 이 연산이 계산을 얼마나 하는가"가 진짜 기준이라는 걸, TinyRT의 결론과 나란히 재확인했습니다.
