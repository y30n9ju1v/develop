이 책을 시작하기 전에 먼저 확인해야 할 게 있습니다 — link:../../../machine-learning-and-rl/reward-only-rl-from-scratch/[전작]이 느렸다면, 정확히 **어디서** 느렸을까요? "GPU가 없어서"라고 뭉뚱그리면 이 책이 뭘 고쳐야 하는지도 흐려집니다.

== 세 단계로 쪼개서 재기

전작의 학습 루프는 매 스텝마다 세 가지 일을 합니다 — 환경을 한 칸 진행시키고(``env.step``), 그 프레임을 전처리하고(그레이스케일+리사이즈), 정책망에 통과시켜 행동을 고릅니다(순수 NumPy 순전파, 파이썬 반복문으로 짠 컨볼루션). 셋을 따로 잽니다.

[source,python]
----
def conv_forward(x, W, stride):
    H, Wd, Cin = x.shape
    kh, kw, _, Cout = W.shape
    OH, OW = (H-kh)//stride+1, (Wd-kw)//stride+1
    out = np.zeros((OH, OW, Cout), dtype=np.float32)
    for oy in range(OH):
        for ox in range(OW):
            patch = x[oy*stride:oy*stride+kh, ox*stride:ox*stride+kw, :]
            out[oy, ox, :] = np.maximum(0, np.tensordot(patch, W, axes=([0,1,2],[0,1,2])))
    return out
----

이게 전작이 실제로 쓴 컨볼루션입니다 — NumPy 배열 연산이긴 하지만, 출력 픽셀 위치마다 파이썬 ``for`` 루프를 돕니다. ``84×84×4`` 입력, ``8×8`` 컨볼루션(stride 4, 16채널) → ``4×4`` 컨볼루션(stride 2, 32채널) → 완전연결(4개 행동) 구조로 30번 반복 실측합니다.

[source]
----
$ python3 profile_baseline.py
env.step:        0.470 ms
preprocess:       0.416 ms
policy forward:   2.674 ms (NumPy 순수 파이썬 루프 conv)
total per env-step cycle: 3.560 ms  (75.1% forward, 13.2% env, 11.7% preprocess)
----

**시간의 75%가 정책망 순전파에서 샙니다.** 에뮬레이터 자체(``env.step``, 13.2%)나 프레임 전처리(11.7%)가 아니라, 파이썬 반복문으로 짠 두 겹의 컨볼루션이 병목의 3/4를 차지합니다. 이건 link:../../cpp23-performance-engineering/[『안전을 넘어 성능으로』]가 반복해서 확인한 것과 같은 종류의 결과입니다 — 병목은 추측이 아니라 재봐야 압니다, 그리고 "GPU가 없어서 느리다"는 흔한 진단은 이 경우 절반만 맞습니다(GPU도 없었지만, 애초에 있는 CPU조차 순전파 하나에서 제대로 못 썼습니다).

== 이 발견이 이 책의 우선순위를 정합니다

병목이 정책망 순전파(그리고 짐작건대 역전파도 비슷하거나 더 심할 겁니다 — PPO는 업데이트마다 순전파+역전파를 둘 다 합니다)에 있다는 게 확인됐으니, 이 책이 가장 먼저 고쳐야 할 건 "환경을 더 병렬로 돌리는 것"이 아니라 **정책망 자체를 제대로 컴파일된 실행 경로로 옮기는 것**입니다(3부, MLX). 환경 병렬화(4부)는 그다음입니다 — 정책망이 여전히 느리면, 환경을 아무리 병렬로 굴려도 그 결과를 소비하는 쪽이 병목이 됩니다.

== 요약

* 전작의 학습 루프를 env 스텝/프레임 전처리/정책망 순전파 세 단계로 나눠 각각 실측했습니다.
* 시간의 75%가 순수 파이썬 반복문으로 짠 컨볼루션 순전파에서 새고 있다는 걸 확인했습니다 — 에뮬레이터 자체는 병목의 작은 부분(13.2%)이었습니다.
* 이 결과가 이 책의 순서를 정합니다 — 정책망을 먼저 고치고(3부), 그다음 환경 병렬화(4부)로 갑니다.
