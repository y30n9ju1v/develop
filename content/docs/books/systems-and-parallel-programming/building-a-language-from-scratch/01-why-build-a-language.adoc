프로그래밍 언어는 마법이 아닙니다 — 문자열이 들어가서, 몇 단계의 기계적인 변환을 거쳐, 결국 숫자(또는 다른 값)가 나오는 파이프라인입니다. 이 장에서는 코드를 짜기 전에, 이 책 전체가 만들 파이프라인의 각 단계를 미리 손으로(진짜 구현 없이) 흉내내보면서, 앞으로 `13`개 장에서 채울 빈칸이 무엇인지 확정해둡니다.

== 목표 프로그램: 재귀로 팩토리얼 계산하기

이 책 전체가 마지막(`14`장)에 실제로 실행할 프로그램입니다 — `Twig`라는 이 책의 언어로 쓴, 재귀 함수로 `5!`를 계산하는 코드입니다.

[source]
----
let rec fact = fun n ->
  if n = 0 then 1 else n * fact (n - 1)
in fact 5
----

이 짧은 프로그램 안에 이 책이 다룰 거의 모든 언어 기능이 들어있습니다 — 이름 바인딩(`let`), 재귀(`rec`), 함수(`fun`), 조건문(`if`), 산술 연산, 함수 호출까지.

== 1단계: 렉서가 볼 토큰들 (2장)

[source,python]
----
tokens_preview = [
    ("LET", "let"), ("REC", "rec"), ("IDENT", "fact"), ("EQ", "="),
    ("FUN", "fun"), ("IDENT", "n"), ("ARROW", "->"),
    ("IF", "if"), ("IDENT", "n"), ("EQEQ", "="), ("INT", 0),
    # ...
]
print(len(tokens_preview))   # 25
----

렉서는 이 소스 코드 문자열을 `25`개의 토큰(의미 있는 최소 단위)으로 쪼갭니다 — `let`이라는 문자열 그대로가 아니라, "이건 `LET` 키워드다"라는 분류가 붙습니다. 2장에서 이 변환을 실제로 구현합니다.

== 2단계: 파서가 만들 AST (3장)

[source,python]
----
ast_preview = {
    "kind": "LetRec",
    "name": "fact",
    "value": {"kind": "Fun", "param": "n", "body": "..."},
    "body": {"kind": "App", "fn": "fact", "arg": 5},
}
----

토큰의 평평한 나열은 아직 "구조"를 모릅니다 — `if`가 어디서 끝나고 `else`가 어디에 걸리는지, 함수 호출의 인자가 무엇인지는 괄호와 우선순위 규칙에 따라 트리 구조로 조립해야 알 수 있습니다. 이 트리(AST, 추상 구문 트리)가 이후 모든 단계(평가, 타입 추론, 코드 생성)가 공통으로 다루는 자료구조입니다. 3장에서 이 조립을 실제로 구현합니다.

== 3단계: 인터프리터가 계산할 정답 (4장)

[source,python]
----
def fact_reference(n):
    if n == 0:
        return 1
    return n * fact_reference(n - 1)

expected_result = fact_reference(5)
print(expected_result)   # 120
----

`Twig`로 짠 프로그램이 최종적으로 내야 할 답은 `120`입니다 — 이건 그냥 순수 Python 함수로 미리 계산해둔 "정답"입니다. 4장에서 만들 트리-워킹 인터프리터가 AST를 직접 실행해서 이 값을 실제로 만들어내는지 검증하게 됩니다.

== 4단계: 타입 추론이 알아낼 타입 (5~6장)

[source]
----
inferred_type_preview = "int"
----

`Twig`는 타입 표기 없이 `let rec fact = fun n -> ...`라고만 썼는데도, 언어 스스로 `fact`가 `int -> int` 함수이고 `fact 5`가 `int`라는 걸 알아내야 합니다 — 사람이 타입을 일일이 안 적어도 되는 이 능력이 Hindley-Milner 타입 추론이고, 6장에서 다룹니다.

== 5단계: MLIR로 방출될 코드 (10~11장)

[source]
----
mlir_signature_preview = "func.func @fact(%n: i64) -> i64"
----

이 책의 마지막 부에서는, `Twig`의 `int` 타입이 MLIR의 `i64`(64비트 정수) 타입과 대응되고, `fact` 함수가 실제 MLIR 함수로 방출됩니다 — 그리고 이 IR을 실제 `mlir-opt`로 낮추고 `mlir-runner`로 실행해서, 정말로 `120`이 나오는지 확인합니다.

== 검증: 지금까지 적어둔 "정답"들이 서로 앞뒤가 맞는가

[source,python]
----
assert "i64" in mlir_signature_preview     # 정수 타입이 MLIR의 i64와 대응
assert inferred_type_preview == "int"       # Twig의 int가 MLIR의 i64로 이어짐
print("expected final answer:", expected_result)   # 120
----

이 다섯 단계가 서로 이어지는 하나의 파이프라인이라는 걸, 아직 구현은 하나도 안 했지만 미리 확인해뒀습니다 — 이후 각 장에서 이 빈칸들을 하나씩 실제 코드로 채우면서, 매번 "지금까지 만든 것이 이 미리 적어둔 정답과 일치하는가"를 검증하게 됩니다.

== 이 책의 진행 방식

각 장은 이전 장의 출력을 입력으로 받습니다 — 2장의 렉서 출력(토큰 리스트)이 3장 파서의 입력이 되고, 3장의 파서 출력(AST)이 4장 인터프리터와 5~6장 타입 추론의 공통 입력이 되고, 그 AST가 다시 10장에서 MLIR IR로 방출됩니다. 같은 AST 자료구조가 책 전체에서 재사용된다는 걸 기억해두면, 뒤로 갈수록 "이미 아는 것 위에 새로운 걸 얹는다"는 느낌으로 편하게 따라갈 수 있습니다.

== 직접 해보기

* `TWIG_SOURCE`를 `fact 5`가 아니라 `fact 6`으로 바꾸면, `fact_reference`로 미리 계산한 정답이 어떻게 바뀌는지, 그리고 그 값이 `i64`(약 `922`경까지 표현 가능) 범위 안에 여전히 들어오는지 확인해보세요.

.해답 보기
[%collapsible]
====
[source,python]
----
print(fact_reference(6))    # 720
print(fact_reference(20))   # 2432902008176640000 -- i64 최대값(약 9.2 x 10^18) 근처
print(fact_reference(21))   # 51090942171709440000 -- i64 범위를 벗어남 (오버플로우)
----

`fact_reference(20)`까지는 결과가 `i64`가 표현할 수 있는 최댓값(`2^63 - 1 ≈ 9.2 × 10^18`) 안에 들어오지만, `fact_reference(21)`부터는 그 범위를 넘어섭니다 — Python은 임의 정밀도 정수라 신경 쓸 필요가 없지만, `Twig`가 실제로 MLIR의 `i64`로 컴파일되면 이 오버플로우가 실제 문제가 됩니다. 10~11장에서 실제로 MLIR을 방출하고 실행할 때, 이런 오버플로우가 실제로 어떻게 나타나는지(조용히 잘못된 값을 내는지, 아니면 명확히 감지되는지) 직접 확인해볼 만한 주제입니다 — 정적 타입 언어가 "타입은 맞지만 값의 범위는 보장 못 하는" 흔한 함정입니다.
====

== 요약

* 언어 구현은 문자열 → 토큰 → AST → (평가 또는 타입 또는 IR)이라는 몇 단계의 기계적인 변환으로 이루어집니다.
* 이 책 전체가 향하는 목표 프로그램(재귀 팩토리얼)과 그 정답(`120`)을 미리 확정해뒀고, 이후 모든 장에서 이 정답과 실제 구현의 결과를 대조하게 됩니다.
* 같은 AST 자료구조가 평가, 타입 추론, MLIR 방출이라는 서로 다른 목적에 재사용된다는 것도 미리 확인했습니다.
