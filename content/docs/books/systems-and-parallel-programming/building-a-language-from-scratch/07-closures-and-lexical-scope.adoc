'''

4장에서 클로저를 "코드 + 정의 시점의 환경"이라고 정의하고, 함수 호출 시 그 환경을 부모로 삼는다고 짧게 다뤘습니다. 이 장에서는 이 선택이 정확히 무엇을 의미하는지 깊이 파고듭니다 — 클로저가 서로 다른 값을 정말로 "기억"하는지, 그리고 만약 클로저 환경 대신 호출부의 환경을 썼다면(동적 스코프) 어떻게 달라졌을지, 일부러 틀리게 구현해서 나란히 비교합니다.

== 함수를 만드는 함수: 클로저가 값을 기억하는지 확인하기

[source,python]
----
source1 = """
let make_adder = fun x -> fun y -> x + y in
let add5 = make_adder 5 in
let add10 = make_adder 10 in
add5 3 + add10 3
"""
print(run(source1))
----

[source]
----
add5 3 + add10 3 = 21
----

`make_adder`는 함수를 **만들어내는** 함수입니다 — `make_adder 5`를 호출하면 `fun y -> x + y`라는 `Closure`가 만들어지는데, 이때 `x=5`가 이미 채워진 환경이 함께 붙잡힙니다. `add5`와 `add10`은 같은 코드(`fun y -> x + y`)에서 나왔지만, 각자 다른 `x` 값을 캡처한 서로 다른 `Closure` 객체입니다 — `add5 3`은 `5+3=8`, `add10 3`은 `10+3=13`, 합쳐서 `21`입니다.

== 검증: 반복 호출해도 캡처된 값이 오염되지 않는다

[source,python]
----
source2 = """
let make_adder = fun x -> fun y -> x + y in
let add5 = make_adder 5 in
let a = add5 1 in
let b = add5 100 in
a + b
"""
print(run(source2))   # 111 = (5+1) + (5+100)
----

`add5`를 두 번 다른 인자로 호출해도, 두 호출 모두 `x=5`를 정확히 기억합니다 — `App` 처리에서 `call_env = fn.env.child()`로 **매 호출마다 새로운 자식 환경**을 만들기 때문에, 한 호출에서 만든 바인딩이 다음 호출에 새어 들어가지 않습니다.

== 일부러 틀리게 구현하기: 동적 스코프

4장에서 "호출하는 쪽의 환경이 아니라 클로저가 정의될 때 붙잡아둔 환경을 부모로 삼는다"고 했던 그 선택이 정말 중요한지 확인하려면, 반대로 구현해보는 게 가장 확실합니다.

[source,python]
----
def eval_dynamic(node, env):
    if isinstance(node, App):
        fn = eval_dynamic(node.fn, env)
        arg = eval_dynamic(node.arg, env)
        call_env = env.child()   # 버그: fn.env가 아니라 지금 호출부의 env를 그대로 이어씀
        call_env.set(fn.param, arg)
        return eval_dynamic(fn.body, call_env)
    # ... 나머지는 4장의 eval_expr와 동일 ...
----

단 한 줄(`env.child()` vs `fn.env.child()`)만 다릅니다 — 새 환경의 부모를 클로저가 기억하는 환경이 아니라, **지금 이 함수를 호출하고 있는 곳의 환경**으로 삼습니다. 이게 "동적 스코프"입니다.

== 두 스코프 규칙이 실제로 다른 답을 내는 프로그램

[source,python]
----
tricky_source = """
let make_adder = fun x -> fun y -> x + y in
let add5 = make_adder 5 in
let x = 999 in
add5 1
"""
----

`add5`를 만든 뒤, 우연히 `x`라는 같은 이름의 변수를 `999`로 다시 바인딩하고 나서 `add5 1`을 호출합니다.

[source,python]
----
lexical_result = eval_expr(parse(tricky_source), Env())
print(lexical_result)   # 6

dynamic_result = eval_dynamic(parse(tricky_source), Env())
print(dynamic_result)   # 1000
----

[source]
----
lexical scoping result:                    6
dynamic scoping result (일부러 틀리게 구현): 1000
----

렉시컬 스코프(4장의 진짜 구현)는 `6`(`= 5 + 1`)을 냅니다 — `add5`가 만들어질 때 붙잡은 `x=5`를 정확히 기억하기 때문에, 그 이후에 바깥에서 `x`가 `999`로 다시 바인딩되든 말든 전혀 영향을 받지 않습니다. 반면 동적 스코프(일부러 틀리게 만든 구현)는 `1000`(`= 999 + 1`)을 냅니다 — `add5`의 몸체(`x + y`)를 실행하는 시점에 **호출부에서 우연히 보이는** `x`(`999`)를 엉뚱하게 주워 쓰기 때문입니다. 완전히 같은 소스 코드, 완전히 같은 AST를 두 가지 다른 규칙으로 실행했을 뿐인데 결과가 극적으로 다릅니다 — 이게 "클로저가 정의 시점의 환경을 붙잡는다"는 4장의 선택이 실제로 프로그램의 의미를 결정하는 근본적인 설계라는 걸 증명합니다.

== 왜 렉시컬 스코프가 표준이 됐는가

동적 스코프의 결과(`1000`)가 왜 문제인지 생각해보면 명확합니다 — `add5`를 만든 사람은 `x=5`인 상태에서 "5를 더하는 함수"를 만들 생각이었는데, 그 함수를 실제로 호출하는 쪽에서 우연히 `x`라는 이름을 다른 용도로 쓰고 있었다는 이유만으로 함수의 동작이 바뀌어버립니다. 이건 함수를 마치 매크로처럼, 호출되는 곳의 문맥에 따라 다르게 동작하는 것으로 만들어버려서, 함수의 동작을 그 정의만 보고는 예측할 수 없게 만듭니다 — 대부분의 현대 언어(그리고 `Twig`)가 렉시컬 스코프를 표준으로 채택한 이유가 바로 이 예측 가능성입니다.

== 검증: 섀도잉이 스코프를 벗어나면 원래대로 돌아온다

[source,python]
----
shadow_source = """
let x = 1 in
let y = (let x = 2 in x * 100) in
x + y
"""
print(run(shadow_source))   # 201 = 1 + 200
----

안쪽 `let x = 2 in x * 100`이 만드는 새 환경은 바깥의 `x=1`을 가리는(shadow) 것뿐이지, 덮어쓰는 게 아닙니다 — `Env.child()`가 매번 **새로운** 환경을 만들고 그 안에 새 바인딩만 추가하기 때문에, 안쪽 스코프가 끝나고 바깥으로 돌아오면(`x + y`를 계산하는 시점) `x`는 다시 `1`입니다. `y`를 계산할 때 쓰인 `x=2`짜리 환경은 그 계산이 끝나는 순간 더 이상 쓰이지 않고 버려집니다.

== 직접 해보기

* `make_adder`를 세 번 중첩해서(`fun x -> fun y -> fun z -> x + y + z`) 커링된 3항 함수를 만들고, 부분적으로만 적용한 함수(`let add_xy = make_adder3 1 2 in add_xy 3`, `add_xy 10`처럼 두 번만 호출)가 남은 인자를 받을 준비가 된 채로 재사용 가능한지 확인해보세요.

.해답 보기
[%collapsible]
====
[source,python]
----
source = """
let make_adder3 = fun x -> fun y -> fun z -> x + y + z in
let add_xy = make_adder3 1 2 in
add_xy 3 + add_xy 10
"""
print(run(source))   # (1+2+3) + (1+2+10) = 6 + 13 = 19
----

`make_adder3 1 2`까지만 호출하면, `z`를 아직 받지 않은 `Closure`(`fun z -> x + y + z`, `x=1, y=2`가 이미 캡처된 상태)가 만들어집니다 — 이게 `add_xy`입니다. `add_xy`를 여러 번(`3`, `10`) 다른 인자로 호출해도, 앞서 검증한 것과 마찬가지로 매번 새 호출 환경이 만들어지므로 `x=1, y=2`는 항상 그대로 유지되면서 `z`만 매번 바뀝니다 — 이게 "부분 적용(partial application)"이며, 함수를 커링된 형태로 설계하면 이런 재사용 가능한 부분 적용 함수를 자연스럽게 만들 수 있다는 걸 보여줍니다.
====

== 요약

* 클로저는 정의 시점의 환경을 붙잡고, 같은 코드에서 나온 서로 다른 클로저(`add5`, `add10`)는 서로 독립적인 캡처값을 유지합니다 — 여러 번 호출해도 그 값은 오염되지 않습니다.
* 클로저 환경 대신 호출부 환경을 쓰는 동적 스코프를 일부러 구현해서, 완전히 같은 프로그램이 렉시컬 스코프에서는 `6`, 동적 스코프에서는 `1000`이라는 다른 답을 낸다는 걸 직접 증명했습니다.
* 동적 스코프는 함수의 동작이 호출되는 곳의 우연한 문맥에 좌우되어 예측하기 어렵게 만들기 때문에, 대부분의 현대 언어가 렉시컬 스코프를 표준으로 채택했습니다.
* 섀도잉은 바깥 바인딩을 덮어쓰는 게 아니라 가리는 것뿐이라, 안쪽 스코프를 벗어나면 원래 값으로 돌아온다는 것도 확인했습니다.

다음 장에서는 지금까지 `int`와 `bool`, 함수뿐이었던 `Twig`의 타입 시스템에, 여러 값을 하나로 묶거나 여러 경우 중 하나를 표현하는 대수적 데이터 타입과, 그 값을 분해하는 패턴 매칭을 추가합니다.
