이제 이 책 전체에서 만든 것을 하나로 묶습니다. 새로운 개념은 없습니다 — 1~13장에서 만든 렉서, 파서, 인터프리터, 타입 추론, 클로저, ADT, MLIR 코드 생성, 표준 라이브러리를 그대로 가져와서, 이 책에서 아직 한 번도 다루지 않았던 **새로운** 프로그램(피보나치수열)으로 두 백엔드(인터프리터와 실제 MLIR JIT)가 정말로 일치하는지 마지막으로 확인합니다.

== 실험 1: 완전히 새로운 예제로 두 백엔드를 대조하기

지금까지 MLIR 백엔드(4부)를 검증할 때 계속 `fact`(팩토리얼)만 썼습니다 — 혹시 그 방출기가 우연히 `fact`라는 특정 프로그램에만 맞게 짜였을 가능성을 배제하기 위해, 이번엔 전혀 다른 재귀 함수인 피보나치수열로 확인합니다.

[source,python]
----
FIB_SOURCE = """
let rec fib = fun n ->
  if n < 2 then n else fib (n - 1) + fib (n - 2)
in fib 10
"""

interp_result = run(FIB_SOURCE)                       # 4장의 트리-워킹 인터프리터
mlir_result = compile_and_run(FIB_SOURCE, call_arg=10)  # 10~12장의 MLIR 방출 + 낮추기 + JIT
----

`fib`는 `fact`와 달리 **두 번** 재귀 호출을 합니다(`fib(n-1) + fib(n-2)`) — 12장의 `FuncEmitter`가 재귀 호출을 하나만 처리하도록 짜여 있었다면 여기서 실패했을 것입니다.

[source]
----
1. interpreter: fib(10) = 55
   MLIR JIT:    fib(10) = 55
----

인터프리터와 실제 MLIR 컴파일+JIT 실행이 완전히 새로운 프로그램에서도 정확히 같은 답(`55`)을 냅니다 — 12장의 방출 로직이 `fact`라는 특정 사례에만 우연히 맞았던 게 아니라, "재귀 함수를 `func.call`로, `if`를 `scf.if`로 방출한다"는 **일반적인 규칙**이었다는 걸 증명합니다.

== 실험 2: 표준 라이브러리 + ADT + 재귀를 모두 쓰는 프로그램

[source,python]
----
LIST_PROGRAM = """
let rec range = fun lo -> fun hi ->
  if lo = hi then Nil else Cons lo (range (lo + 1) hi)
in
let squares = map (fun x -> x * x) (range 1 6) in
fold (fun acc -> fun x -> acc + x) 0 squares
"""
list_result = run_with_list_module(LIST_PROGRAM)
print(list_result)   # 55
----

이 프로그램은 4장(재귀로 `range`를 정의), 8장(`Cons`/`Nil`로 리스트를 만듦), 13장(`map`, `fold`를 표준 라이브러리에서 가져옴)을 모두 동원합니다 — `1`부터 `5`까지의 제곱의 합(`1+4+9+16+25`)을 계산하면 `55`입니다. `fib(10)`도 우연히 `55`인데, 이 둘은 완전히 무관한 계산(재귀 함수 하나 vs 리스트 파이프라인)이 우연히 같은 답을 낸 것뿐입니다 — 이런 우연은 검증에서 흔히 벌어지므로, 숫자가 같다고 검증이 뭔가 잘못됐다고 의심할 필요는 없습니다(각 검증은 자신만의 손으로 계산한 정답과 비교했지, 서로를 비교한 게 아니었습니다).

이 프로그램은 이 장의 MLIR 백엔드로는 실행할 수 없습니다 — `range`가 만드는 리스트(`Cons`/`Nil`)를 MLIR의 `i64` 하나로 표현할 방법이 없기 때문입니다(12장에서 미리 밝혔듯, 클로저와 ADT를 MLIR로 낮추는 건 이 책의 범위를 넘어서는 주제입니다). 인터프리터는 `Twig`의 모든 기능을 지원하지만, MLIR 백엔드는 정수 산술과 재귀라는 부분집합만 지원한다는 게, 이 책이 두 백엔드를 나란히 유지해온 이유입니다.

== 이 책 전체 파이프라인

[source,python]
----
pipeline_stages = [
    ("1부", "렉서/파서", "소스 문자열 -> 토큰 -> AST"),
    ("2부", "인터프리터/타입 추론", "AST -> 값 / AST -> 타입(HM 추론)"),
    ("3부", "클로저/ADT/다형성", "렉시컬 스코프, 패턴 매칭, let-다형성"),
    ("4부", "MLIR 코드 생성", "AST -> MLIR IR -> LLVM IR -> 실제 기계어 JIT 실행"),
    ("5부", "표준 라이브러리", "Twig로 쓴 라이브러리를 사용자 프로그램에 이어붙임"),
]
----

`Twig` 소스 코드 문자열 하나가, 이 다섯 단계를 거쳐 (인터프리터를 통해) 즉시 값이 되거나, (MLIR 백엔드를 통해) 실제 기계어로 컴파일되어 실행됩니다. 어느 경로를 택하든 같은 AST(1부)에서 출발하고, 3부(클로저·ADT·다형성)는 인터프리터의 표현력을 키우는 데, 4부(MLIR)는 그중 정수 산술이라는 부분집합을 실제로 컴파일하는 데 쓰입니다.

== 지나온 길을 돌아보며

1장에서 `fact 5 = 120`이라는 목표를 세우고, 그 목표에 도달하는 과정에서 여러 번 "미리 그려둔 계획이 틀렸다"는 걸 발견했습니다 — 2장에서 `EQ`/`EQEQ` 구분이 렉서의 일이 아니었다는 것, 5장에서 반환 타입 주석 없이는 재귀 함수를 검사할 수 없다는 벽, 11장에서 컴파일러가 상수식을 이미 계산해버린다는 것, 13장에서 `match` 절이 `if`를 못 받아들이던 파서 버그까지 — 이런 발견들은 모두 "일단 만들어보고, 실제로 실행해서, 틀린 부분을 고친다"는 이 책의 반복된 습관에서 나왔습니다. 언어를 설계하는 건 처음부터 완벽한 명세를 세우는 일이 아니라, 이렇게 실제로 짜보면서 부딪히는 벽들을 하나씩 넘어가는 일이라는 걸, 이 책 전체가 실증했습니다.

예를 들어 "가변 참조"(`ref`, 값을 나중에 바꿀 수 있는 상자)를 추가한다면:

* **1부**: 렉서에 `ref`, `:=`(대입), `!`(역참조) 토큰을 추가하고, 파서에 해당 문법 규칙을 추가합니다.
* **2부**: 인터프리터에서 `Ref` 값 타입(파이썬의 가변 리스트나 객체로 감싼 상자)을 추가하고, `eval_expr`에 대입·역참조 처리를 더합니다. 타입 검사/추론(5~6장)에는 `TRef` 타입을 추가해야 합니다.
* **3부**: 7장에서 다룬 클로저가 이제 "불변 값"뿐 아니라 "가변 상자에 대한 참조"도 캡처할 수 있다는 뜻이 되므로, 클로저가 캡처한 참조를 통해 함수 밖에서 상태를 공유하는 시나리오(예: 카운터 함수)를 새로 검증해야 합니다.
* **4부**: MLIR에는 `memref` 다이얼렉트(메모리 참조)가 있어서, `ref`를 `memref.alloc`으로, 대입을 `memref.store`로, 역참조를 `memref.load`로 방출할 수 있습니다 — 이 책에서 다룬 "AST를 MLIR로 방출한다"는 원리가 그대로 확장됩니다.
* **9장의 다형성**: 가변 참조가 있는 언어에서 let-다형성을 그대로 허용하면 타입 안전성이 깨지는 유명한 문제(value restriction)가 있습니다 — 이건 이 책이 다루지 않은, 실전 언어 설계의 흥미로운 함정 중 하나입니다.

이렇게 기능 하나를 추가하는 것만으로도 책의 거의 모든 장에 걸쳐 파급 효과가 있다는 걸 알 수 있습니다 — 언어 설계의 각 부분이 독립적이지 않고 서로 얽혀 있다는 걸 보여주는 좋은 연습입니다.

== 요약

* 완전히 새로운 프로그램(피보나치)으로, 인터프리터와 실제 MLIR 컴파일+JIT 실행이라는 두 독립적인 실행 경로가 정확히 같은 답을 낸다는 걸 다시 한번 확인해, 4부의 코드 생성이 특정 예제에만 맞춰진 우연이 아니었다는 걸 증명했습니다.
* 표준 라이브러리·ADT·재귀를 모두 쓰는 프로그램을 인터프리터로 실행해, 이 책에서 만든 언어 기능들이 실제로 서로 조합 가능하다는 걸 확인했습니다.
* 이 책 전체가 렉서/파서 → 평가/타입 → 클로저/ADT/다형성 → MLIR 코드 생성 → 표준 라이브러리라는 다섯 단계로 이루어진 하나의 파이프라인이었다는 걸 정리했습니다.
* 이 책 곳곳에서 "미리 세운 계획이 실제 구현 앞에서 틀렸다고 밝혀지고, 그걸 고쳐가는" 과정이 반복됐다는 것이, 언어 설계라는 작업의 본질에 가깝다는 것도 되짚었습니다.

이것으로 문자열 하나가 토큰이 되고, 트리가 되고, 값이 되거나 실제 기계어가 되는 전체 여정을 처음부터 끝까지 손으로 짓고 검증했습니다. `Twig`는 장난감 언어지만, 그걸 만드는 데 쓴 도구들(재귀 하강 파싱, 트리-워킹 평가, Hindley-Milner 추론, 그리고 진짜 MLIR 컴파일러 인프라)은 전혀 장난감이 아닙니다 — 실전 언어와 컴파일러가 이 도구들을 더 크고 정교한 규모로 쓸 뿐, 원리는 이 책에서 다룬 것과 다르지 않습니다.
