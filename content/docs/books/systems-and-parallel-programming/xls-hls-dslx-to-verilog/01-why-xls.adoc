== 세 가지 추상화 수준

같은 8탭 FIR 필터를 세 방식으로 적는다고 해봅시다.

[cols="1,3", options="header"]
|===
| 방식 | 여러분이 직접 정하는 것

| **RTL (Verilog)**
| 곱셈기 8개를 쓸지 1개를 재사용할지, 각 곱의 결과를 어느 레지스터에 담을지, 상태 기계의 상태, 파이프라인 단계, valid/ready 배선 — 전부.

| **전통 HLS (C 기반)**
| 알고리즘을 C 루프로 적고, `#pragma`로 "이 루프를 언롤해라", "이 배열을 BRAM에 넣어라"를 지시. 도구가 나머지를 채우지만, 프래그마 튜닝이 곧 마이크로아키텍처 설계.

| **XLS (DSLX)**
| 알고리즘을 순수 함수로 적고, 목표 클럭 주기 또는 파이프라인 단계 수만 준다. 도구가 지연 모델을 보고 어디를 자를지 계산.
|===

XLS의 특징은 입력 언어가 **처음부터 하드웨어를 위해 설계**됐다는 점입니다. C 기반 HLS는 포인터·재귀·동적 할당처럼 하드웨어로 옮길 수 없는 기능을 "쓰지 마세요"로 막습니다. DSLX는 그런 기능이 애초에 없습니다. 대신 임의 폭 정수, 고정 크기 배열, 파라메트릭 폭처럼 하드웨어에 필요한 것을 언어 문법으로 올려놓습니다.

== DSLX가 금지하는 것과 그 이유

[cols="1,3", options="header"]
|===
| 없는 기능 | 왜

| 가변 변수 (`x = x + 1`)
| 회로에는 "재대입"이 없습니다. 값은 배선을 타고 흐를 뿐입니다. DSLX의 `let`은 새 이름을 묶는 것이지 기존 이름을 덮는 게 아닙니다.

| 재귀
| 하드웨어는 깊이가 컴파일 타임에 정해져야 펼칠 수 있습니다. `factorial(n)`을 재귀로 적으면 `n`이 런타임 값일 때 회로 크기가 정해지지 않습니다.

| 무한/동적 루프
| `for`의 반복 범위는 상수입니다. 도구가 루프를 완전히 펼쳐 조합 논리로 만들거나, 스케줄러가 시간축으로 접습니다.

| 동적 크기 자료구조
| 힙이 없습니다. 모든 배열은 `u32[16]`처럼 크기가 타입에 박혀 있습니다.

| 포인터·별칭
| 메모리 별칭이 없으므로 데이터플로 그래프가 명확합니다. 이것이 최적화와 형식 검증을 쉽게 만듭니다.
|===

이 제약들은 불편함이 아니라 **분석 가능성의 대가**입니다. 호출 그래프가 완전히 정적이고 모든 크기가 고정이므로, XLS는 전체 설계를 하나의 데이터플로 그래프로 펼쳐 놓고 마음대로 재배치할 수 있습니다.

== "타임리스": 시간을 언어에서 걷어내기

가장 중요한 개념입니다. DSLX 함수에는 **클럭도, 단계도, 지연도 없습니다.** 여러분은 순수한 입출력 관계만 적습니다.

[source,dslx]
----
fn mac4(a: s32[4], b: s32[4]) -> s32 {
    let p0 = a[0] * b[0];
    let p1 = a[1] * b[1];
    let p2 = a[2] * b[2];
    let p3 = a[3] * b[3];
    (p0 + p1) + (p2 + p3)
}
----

이 함수가 1 사이클에 조합 논리로 계산될지, 4단 파이프라인으로 펼쳐질지는 **함수 안에 적혀 있지 않습니다.** 그 결정은 나중에 `codegen_main`에 `--clock_period_ps=500`을 주느냐 `--pipeline_stages=4`를 주느냐로 내려집니다. 같은 소스에서 조합 회로도, 3단 파이프라인도, 5단 파이프라인도 나옵니다.

RTL에서는 파이프라인 단계가 코드 구조에 박혀 있습니다. 단계를 바꾸려면 레지스터 선언과 상태 기계를 다시 씁니다. XLS에서는 알고리즘(`mac4`)과 스케줄(플래그)이 분리돼 있어, 스케줄만 바꾸면 됩니다. 스케줄러는 지연 모델로 각 연산의 소요 시간을 알기에, 목표 주기를 넘지 않도록 그래프를 잘라 레지스터를 끼웁니다 — 이 과정을 9장에서 다룹니다.

== proc: 시간이 필요할 때만 시간을 들인다

타임리스 함수만으로는 "매 사이클 입력을 하나씩 받아 누적하는 모듈"처럼 상태가 필요한 것을 표현할 수 없습니다. 그때 쓰는 것이 **proc**입니다. proc는 채널로 값을 주고받고(`recv`/`send`), 사이클마다 갱신되는 상태를 가지며, `next` 함수가 "이번 사이클의 상태에서 다음 사이클의 상태로" 가는 한 걸음을 기술합니다. 이것이 "시간에 대한 귀납"입니다. proc는 4부(12–13장)에서 봅니다.

정리하면 XLS의 사고 모델은 이렇습니다.

* **조합/파이프라인 논리** → 타임리스 `fn`으로 적고, 스케줄은 플래그로 뽑는다.
* **상태 기계·스트리밍 모듈** → `proc`로 적고, 채널로 잇는다.
* **마이크로아키텍처(단계 수, 레지스터 위치)** → 소스가 아니라 스케줄러가 정한다.

[source,bash]
----
# XLS 저장소를 받았다면, 딸려 있는 예제 하나를 IR로 변환해 본다
ir_converter_main --top=main xls/examples/dot_product.x | head -40

# 같은 IR을 파이프라인으로 스케줄링/합성하면 단계가 생긴다 (10~11장에서 자세히)
# codegen_main --generator=pipeline --delay_model=unit --pipeline_stages=3 ...
----
