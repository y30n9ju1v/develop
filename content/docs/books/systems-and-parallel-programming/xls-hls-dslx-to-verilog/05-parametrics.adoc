같은 로직을 8비트, 16비트, 32비트로 각각 적는 것은 낭비입니다. DSLX의 파라메트릭은 폭·크기 같은 **컴파일 타임 값**을 타입/함수의 파라미터로 받아, 호출할 때마다 그 폭에 맞는 회로를 찍어냅니다. C++ 템플릿이나 Rust 제네릭과 감각이 비슷하되, 파라미터가 대개 "타입"이 아니라 "숫자(폭)"라는 점이 다릅니다.

== 값 파라미터 붙이기

[source,dslx]
----
// N 비트 무부호 최댓값
fn umax<N: u32>(a: uN[N], b: uN[N]) -> uN[N] {
    if a > b { a } else { b }
}

#[test]
fn umax_test() {
    assert_eq(umax(u8:10, u8:20), u8:20);      // N=8 은 인자에서 추론
    assert_eq(umax(u32:5, u32:3), u32:5);      // N=32
    assert_eq(umax<u32:12>(u12:1, u12:4000), u12:4000);  // 명시도 가능
}
----

* `<N: u32>` — `N`은 `u32` 타입의 컴파일 타임 상수입니다.
* `uN[N]` — "폭이 `N`인 무부호 정수". `N=8`이면 `u8`.
* 호출 시 `N`은 대개 인자 타입에서 **추론**됩니다. `umax(u8:10, u8:20)`을 보면 XLS가 `N=8`로 못 박습니다.

== 파생 파라미터: 출력 폭을 계산하기

두 `N`비트 수를 더하면 캐리 때문에 `N+1`비트가 필요합니다. 이 관계를 타입에 적을 수 있습니다.

[source,dslx]
----
fn add_widen<N: u32, M: u32 = {N + u32:1}>(a: uN[N], b: uN[N]) -> uN[M] {
    (a as uN[M]) + (b as uN[M])
}

#[test]
fn widen_test() {
    // N=8 -> M=9. u8:255 + u8:255 = 510, 9비트에 딱 들어간다
    assert_eq(add_widen(u8:255, u8:255), u9:510);
}
----

`M: u32 = {N + u32:1}`은 "기본값이 `N+1`인 파생 파라미터"입니다. 중괄호 안은 컴파일 타임에 계산됩니다. 호출자는 `M`을 신경 쓸 필요가 없고, 반환 타입 `uN[M]`이 알아서 `N+1`비트가 됩니다.

== 파라메트릭 타입

구조체와 별칭도 파라메트릭이 됩니다.

[source,dslx]
----
struct Fifo<DEPTH: u32, W: u32> {
    data: uN[W][DEPTH],
    count: u32,
}

type Vec<N: u32> = s16[N];

fn dot<N: u32>(a: Vec<N>, b: Vec<N>) -> s32 {
    // (합산 루프는 6장에서 for 로 제대로 적는다)
    let acc = s32:0;
    for (i, acc): (u32, s32) in u32:0..N {
        acc + (a[i] as s32) * (b[i] as s32)
    }(acc)
}

#[test]
fn dot_test() {
    let a = s16[3]:[1, 2, 3];
    let b = s16[3]:[4, 5, 6];
    assert_eq(dot(a, b), s32:32);   // 4 + 10 + 18
}
----

`dot<N>`은 길이 `N`인 벡터 두 개의 내적입니다. `dot(a, b)`에서 `a: s16[3]`이므로 `N=3`으로 특수화되고, 루프가 3번 펼쳐진 조합 회로가 나옵니다. `s16[8]` 벡터로 부르면 같은 소스에서 8번 펼쳐진 회로가 나옵니다.

== 파라메트릭의 제약

* 파라미터는 **컴파일 타임에 확정**돼야 합니다. 런타임 값으로 폭을 정할 수 없습니다(그러면 회로 크기가 안 정해집니다).
* 파라메트릭 함수는 호출되기 전까지 완전히 타입 검사되지 않는 부분이 있습니다. `dslx_interpreter_main`은 `#[test]`에서 실제로 특수화된 인스턴스를 검사합니다. 그래서 파라메트릭 코드일수록 여러 폭으로 부르는 테스트를 남기는 게 중요합니다.
* `assert!`나 `const_assert!`로 "이 파라미터 조합은 금지"를 컴파일 타임에 못 박을 수 있습니다. 예: `const_assert!(N > u32:0);`

== 왜 이게 하드웨어에서 유용한가

RTL에서 "폭 파라미터화된 모듈"은 `parameter WIDTH = 8` + `generate` 블록으로 흉내 냅니다. DSLX 파라메트릭은 타입 시스템이 폭 산술(`N+1`, `clog2(N)`)을 검사해 주므로, "가산기 출력 폭을 하나 덜 잡아 캐리를 흘리는" 류의 버그가 컴파일 타임에 걸립니다. 그리고 특수화된 각 인스턴스가 독립적으로 최적화·스케줄링되므로, 8비트 버전과 64비트 버전이 서로 다른 파이프라인 단계 수를 가질 수 있습니다.

== 직접 확인하기

[source,bash]
----
dslx_interpreter_main parametrics.x

# dot 를 s16[8] 벡터로 부르는 테스트를 추가하고, 여전히 통과하는지 본다
# add_widen 의 M 기본값을 {N} 으로 (일부러) 잘못 바꿔, 오버플로가 assert 로 걸리는지 본다
----
