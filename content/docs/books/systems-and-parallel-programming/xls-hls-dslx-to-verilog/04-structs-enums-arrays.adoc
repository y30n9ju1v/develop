스칼라 비트만으로는 설계가 금방 지저분해집니다. DSLX는 값을 묶는 네 가지 방법 — tuple, struct, enum, array — 을 주며, 넷 다 **고정 크기**입니다. 즉 각각이 정확히 몇 비트인지 컴파일 타임에 정해집니다.

== 튜플: 이름 없는 묶음

[source,dslx]
----
fn divmod(x: u32, d: u32) -> (u32, u32) {
    (x / d, x % d)
}

#[test]
fn divmod_test() {
    let (q, r) = divmod(u32:17, u32:5);   // 튜플 패턴으로 분해
    assert_eq(q, u32:3);
    assert_eq(r, u32:2);
}
----

튜플은 그냥 필드를 이어 붙인 비트입니다. `(u32, u32)`는 64비트, `(u8, u1)`은 9비트. 함수가 값을 여러 개 돌려줄 때 가장 가볍습니다.

== 구조체: 이름 있는 묶음

[source,dslx]
----
struct Pixel {
    r: u8,
    g: u8,
    b: u8,
}

fn grayscale(p: Pixel) -> u8 {
    // 근사: (r + 2g + b) / 4
    let sum = (p.r as u10) + (p.g as u10) + (p.g as u10) + (p.b as u10);
    (sum >> u10:2) as u8
}

#[test]
fn gray_test() {
    let white = Pixel { r: u8:255, g: u8:255, b: u8:255 };
    assert_eq(grayscale(white), u8:255);

    // 필드 일부만 바꾼 새 값: `..기존값`
    let dim = Pixel { r: u8:10, ..white };
    assert_eq(dim.r, u8:10);
    assert_eq(dim.g, u8:255);
}
----

* `Pixel { r: ..., g: ..., b: ... }` — 모든 필드를 채워 생성.
* `Pixel { r: u8:10, ..white }` — `white`에서 `r`만 바꾼 새 구조체. `white` 자체는 그대로입니다(불변).
* `p.r` — 필드 접근. 회로로는 24비트 배선에서 특정 8비트를 뽑는 것.

구조체는 비트 레이아웃일 뿐이라, `Pixel`은 정확히 24비트입니다.

== enum: 폭이 정해진 이름 집합

[source,dslx]
----
enum Op : u2 {
    ADD = 0,
    SUB = 1,
    AND = 2,
    OR  = 3,
}

fn alu(op: Op, a: u32, b: u32) -> u32 {
    match op {
        Op::ADD => a + b,
        Op::SUB => a - b,
        Op::AND => a & b,
        Op::OR  => a | b,
    }
}

#[test]
fn alu_test() {
    assert_eq(alu(Op::ADD, u32:2, u32:3), u32:5);
    assert_eq(alu(Op::AND, u32:0b1100, u32:0b1010), u32:0b1000);
}
----

`enum Op : u2`의 `: u2`가 핵심입니다 — enum의 표현 폭을 못 박습니다. 값이 4개이므로 2비트면 충분합니다. `Op`는 2비트 배선이고, `match`는 그 2비트로 갈라지는 멀티플렉서가 됩니다.

== match: 값으로 갈라지는 표현식

`match`는 문이 아니라 **표현식**입니다. 모든 갈래가 같은 타입의 값을 내야 하고, 갈래가 모든 경우를 덮어야 합니다.

[source,dslx]
----
fn classify(x: s32) -> u2 {
    match x {
        s32:0 => u2:0,                       // 정확히 0
        y if y > s32:0 => u2:1,              // 가드 조건
        _ => u2:2,                           // 나머지 (음수)
    }
}
----

* 리터럴 패턴 (`s32:0`), 가드 (`y if y > s32:0`), 와일드카드 (`_`)를 섞을 수 있습니다.
* enum을 match할 때 갈래가 하나라도 빠지면 컴파일 오류입니다. `_`로 얼버무리기보다 모든 변형을 나열하면, 나중에 enum에 값을 추가했을 때 컴파일러가 빠진 곳을 알려줍니다.

== 배열: 고정 크기 인덱스 묶음

[source,dslx]
----
fn sum4(xs: u16[4]) -> u18 {
    (xs[0] as u18) + (xs[1] as u18) + (xs[2] as u18) + (xs[3] as u18)
}

#[test]
fn arr_test() {
    let xs = u16[4]:[10, 20, 30, 40];
    assert_eq(sum4(xs), u18:100);

    // 한 원소만 바꾼 새 배열
    let ys = update(xs, u32:1, u16:99);
    assert_eq(ys[1], u16:99);
    assert_eq(xs[1], u16:20);   // 원본 불변
}
----

* `u16[4]` — 16비트 원소 4개, 총 64비트.
* `u16[4]:[10, 20, 30, 40]` — 배열 리터럴. 원소 리터럴의 타입은 원소 타입에서 추론됩니다.
* `xs[i]` — 인덱싱. `i`가 런타임 값이면 이것은 멀티플렉서 회로가 됩니다.
* `update(xs, i, v)` — `i`번째만 `v`로 바꾼 **새 배열**. 원본은 그대로. 회로로는 "인덱스 `i`에서만 새 값을 고르는" 4-way 먹스 4개.

배열은 조합 논리로 펼쳐지므로, 크기가 커지면 인덱싱 먹스도 커집니다. 큰 저장소가 필요하면 proc + 메모리 채널(13장 이후)이나 codegen의 RAM 옵션을 씁니다.

== 타입 별칭

[source,dslx]
----
type Word = u32;
type Rgb = Pixel;
type Vec3 = s16[3];
----

`type`은 새 타입을 만들지 않고 이름만 붙입니다. 폭·의미는 그대로입니다. 설계 전반에서 `u32` 대신 `Word`를 쓰면 나중에 폭을 바꾸기 쉽습니다.
