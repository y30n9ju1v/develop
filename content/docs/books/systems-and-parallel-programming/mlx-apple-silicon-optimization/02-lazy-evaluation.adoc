1장의 모든 예제 코드에 ``mx.eval``이 등장했습니다 — 매번 필요했던 이유가 있습니다. MLX의 연산은 **지연 평가**됩니다: ``a @ b``를 쓰는 순간 실제로 행렬곱이 실행되는 게 아니라, "이 연산을 하겠다"는 그래프 노드 하나가 쌓일 뿐입니다.

== 그래프 구성과 실제 실행은 다른 일입니다

[source,python]
----
a = mx.random.normal((4096, 4096))
b = mx.random.normal((4096, 4096))

t0 = time.perf_counter()
c = a @ b              # 아직 계산 안 함
t1 = time.perf_counter()

t2 = time.perf_counter()
mx.eval(c)              # 여기서 진짜로 실행
t3 = time.perf_counter()
----

[source]
----
$ python3 mlx_lazy_timing.py
그래프만 구성(연산 없음): 0.0052 ms
mx.eval로 실제 실행: 79.3098 ms
----

``c = a @ b``가 걸린 시간(``0.005ms``)과 ``mx.eval(c)``가 걸린 시간(``79ms``)의 차이는 1만 배가 넘습니다 — ``4096×4096`` 행렬곱이 정말로 ``0.005ms``에 끝날 리가 없으므로, 첫 줄에서는 계산이 **전혀 일어나지 않았다는** 뜻입니다. ``c``는 이 시점에 "숫자가 든 배열"이 아니라 "``a @ b``를 계산하라"는 명령이 담긴 그래프 노드입니다. ``mx.eval``이 그 그래프를 실제로 GPU에 보내서 실행시키고, 그제서야 ``c``가 진짜 숫자를 갖게 됩니다.

== 왜 이렇게 만들었을까 — 중간 결과를 실체화하지 않는다

[source,python]
----
def chain_eager(x):
    y = x * 2;   mx.eval(y)   # 단계마다 즉시 실행
    y = y + 1;   mx.eval(y)
    y = mx.sin(y); mx.eval(y)
    y = y * y;   mx.eval(y)
    return y

def chain_lazy(x):
    y = x * 2
    y = y + 1
    y = mx.sin(y)
    y = y * y
    return y            # 끝에서 딱 한 번만 eval
----

800만 개 원소 배열로 두 방식을 비교하면:

[source]
----
$ python3 mlx_lazy_vs_eager.py
단계마다 즉시 eval(중간 결과 매번 실체화): 5.538 ms
끝에서 한 번만 eval(그래프를 다 쌓은 뒤 한꺼번에 실행): 3.493 ms
speedup: 1.59x
----

**1.59배** 차이가 납니다. ``chain_eager``는 매 단계마다 결과를 GPU 메모리에 실제로 써넣고, 그 배열 전체를 다시 읽어서 다음 연산을 시작합니다 — 곱셈 결과를 쓰고, 덧셈이 그걸 다시 읽고 쓰고, ``sin``이 또 읽고 쓰고... 네 번의 왕복입니다. ``chain_lazy``는 그래프 전체를 한 번에 스케줄링하므로, 이 네 연산 사이의 GPU 디스패치/동기화 왕복 횟수 자체가 줄어듭니다 — link:../../heterogeneous-computing-opencl/[전작] 5~6장이 로컬 메모리로 전역 메모리 왕복을 줄였던 것과 같은 정신입니다. 다만 이것만으로 네 연산이 정말 **하나의 GPU 커널**로 합쳐지는지(레지스터에서 레지스터로 직접 넘어가는지)까지는 이 시점에서 보장되지 않습니다 — 그 보장은 다음 장의 ``mx.compile``이 명시적으로 줍니다.

== 그래서 언제 ``mx.eval``을 불러야 하는가

이 장의 예제들처럼 **결과가 실제로 필요한 지점**(출력을 찍거나, 다음 반복에서 그 값에 의존하는 분기가 있거나, 이 책 뒤에서 볼 학습 루프처럼 파라미터를 갱신해야 할 때)에서만 부르면 됩니다. 그래프를 너무 오래 안 쌓고 자주 ``eval``하면 이 장이 보여준 융합 기회를 잃고, 반대로 한 번도 ``eval``하지 않으면 그래프가 무한정 커져서 메모리를 낭비합니다 — 6장의 학습 루프에서 매 에폭 끝에 ``mx.eval``을 부르는 이유가 바로 이 균형점입니다.

== 요약

* ``a @ b`` 같은 연산은 즉시 실행되지 않고 그래프 노드로만 쌓이며, ``mx.eval``을 불러야 실제 계산이 일어난다는 걸 두 시점의 실측 타이밍(``0.005ms`` vs ``79ms``)으로 확인했습니다.
* 중간 결과를 매번 ``mx.eval``로 실체화하는 것보다, 그래프를 다 쌓은 뒤 한 번에 실행하는 쪽이 1.59배 빨랐습니다 — GPU 디스패치/동기화 왕복 횟수가 줄어들기 때문입니다. 이 이득을 "커널 하나로의 완전한 퓨전"까지 명시적으로 보장하는 건 다음 장의 ``mx.compile``입니다.
* ``mx.eval``을 부를 시점의 기준(결과가 실제로 필요할 때)도 짚었습니다 — 이후 장의 학습 루프에서 이 기준을 그대로 씁니다.

다음 장에서는 MLX의 또 다른 핵심 도구 — 손으로 미분하지 않고 ``mx.grad``로 자동 미분하는 법 — 을 손으로 짠 그래디언트와 직접 대조해 검증합니다.
