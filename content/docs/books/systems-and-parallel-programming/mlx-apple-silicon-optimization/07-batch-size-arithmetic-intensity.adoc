'''

1장은 통합 메모리가 **전송 비용**은 없애도 **디스패치 오버헤드**까지 없애지는 않는다고 짚었습니다. 이 장은 그 오버헤드를 실측으로 드러냅니다 — link:../../heterogeneous-computing-opencl/[전작] 2장이 "작은 데이터에서는 GPU가 CPU보다 손해"라는 걸 확인한 것과 같은 질문을, 호스트-디바이스 전송이 아예 없는 MLX에서 다시 던져봅니다.

== 같은 행렬곱, CPU와 GPU를 오가며 재기

[source,python]
----
for n in [64, 512, 1024, 2048, 4096]:
    a_np = np.random.randn(n, n).astype(np.float32)
    b_np = np.random.randn(n, n).astype(np.float32)

    mx.set_default_device(mx.cpu)
    a_cpu, b_cpu = mx.array(a_np), mx.array(b_np)
    mx.eval(a_cpu @ b_cpu)                    # 워밍업
    # ... 10회 반복 측정 ...

    mx.set_default_device(mx.gpu)
    a_gpu, b_gpu = mx.array(a_np), mx.array(b_np)
    mx.eval(a_gpu @ b_gpu)
    # ... 10회 반복 측정 ...
----

1장에서 확인한 그대로, ``mx.set_default_device``를 바꾸는 것만으로 같은 넘파이 배열을 CPU 연산과 GPU 연산 양쪽에 그대로 넘길 수 있습니다 — 데이터를 다시 만들거나 복사할 필요가 없습니다.

== 실측: 교차점은 정확히 어디인가

[source]
----
$ python3 mlx_batch_crossover.py
n=   64  numpy=  0.0020ms  mlx-cpu=  0.0186ms  mlx-gpu=  0.3520ms  gpu/cpu=18.95x
n=  512  numpy=  0.1630ms  mlx-cpu=  0.1714ms  mlx-gpu=  1.0849ms  gpu/cpu=6.33x
n= 1024  numpy=  1.1720ms  mlx-cpu=  1.1821ms  mlx-gpu=  3.3272ms  gpu/cpu=2.81x
n= 2048  numpy=  9.3027ms  mlx-cpu=  9.1339ms  mlx-gpu=  6.5147ms  gpu/cpu=0.71x
n= 4096  numpy= 75.0148ms  mlx-cpu= 74.4219ms  mlx-gpu= 48.4021ms  gpu/cpu=0.65x
----

``n=64``에서는 GPU가 CPU보다 **19배 느립니다.** ``n=1024``까지도 GPU가 계속 집니다(2.81배 느림). ``n=2048``에서 처음으로 역전하고(``0.71배``, GPU가 더 빠름), ``n=4096``에서는 GPU가 CPU보다 35% 빠릅니다. 통합 메모리라서 전송 비용이 없는데도 이 정도로 뚜렷한 교차점이 있다는 게 이 장의 핵심 발견입니다 — 남은 원인은 순수하게 **GPU에 작업을 올리고 커널을 스케줄링하는 고정 비용**입니다. ``n=64`` 행렬곱은 원소 몇천 개짜리 연산이라 계산 자체는 마이크로초 단위로 끝나는데, Metal 커널을 디스패치하는 오버헤드가 그보다 훨씬 큽니다 — link:../../tinyrt-cpu-gpu-inference/[『TinyRT』] 7장이 확인한 "작은 모델은 CPU가 80배 빠르다"는 결론과 정확히 같은 현상이, OpenCL의 명시적 전송도 없는 MLX에서 원인만 좁혀진 채로 재현됩니다.

또 하나 눈에 띄는 건 ``mlx-cpu``가 ``numpy``와 거의 모든 구간에서 사실상 동률이라는 점입니다 — 둘 다 이 하드웨어의 CPU 코어와 최적화된 BLAS 루틴을 쓰기 때문에 당연한 결과지만, "MLX-CPU 백엔드가 NumPy 대비 손해를 보지는 않는다"는 것도 이 표가 실측으로 보여줍니다.

== 6장의 학습 루프라면

6장의 나선형 데이터는 ``(600, 2)`` 크기입니다 — 이 장의 기준으로 보면 ``n=64``보다도 작은 축에 속합니다. ``mx.default_device()``가 GPU를 가리키는 채로 6장을 돌렸어도 별문제 없었던 이유는, MLP 학습에서 진짜 계산량을 차지하는 건 입력 크기가 아니라 은닉층 크기(``64×64`` 가중치 행렬 몇 개)이기 때문입니다 — 그래도 이 크기는 여전히 이 장의 표에서 CPU가 이기는 구간에 걸쳐 있습니다. 10장에서 이 사실이 실제로 학습 전체 시간에 어떤 영향을 주는지 CPU 백엔드와 나란히 재봅니다.

== 요약

* ``mx.set_default_device``로 같은 행렬곱을 CPU/GPU 양쪽에서 실측해, ``n=1024``까지는 CPU가 이기고 ``n=2048``부터 GPU가 역전하는 교차점을 직접 찾았습니다.
* 통합 메모리로 전송 비용이 없는 MLX에서도 이 교차점이 뚜렷하게 존재한다는 게, "GPU가 작은 작업에서 손해인 이유"가 전송이 아니라 **디스패치 오버헤드 자체**라는 걸 좁혀서 보여줍니다.
* ``MLX-CPU`` 백엔드가 ``NumPy``와 거의 동률이라는 것도 확인해, MLX를 CPU 전용으로 써도 손해가 없다는 걸 짚었습니다.

다음 장에서는 계산량이 아니라 **메모리 크기**를 줄이는 최적화 — 4비트 양자화 — 를 이 책의 MLP에 실제로 적용해 압축률과 속도를 함께 잽니다.
