'''

2장에서 지연 평가가 여러 연산을 하나의 GPU 커널로 묶을 **기회**를 연다는 걸 확인했습니다. 이 장의 ``mx.compile``은 그 기회를 매번 새로 찾는 대신, 한 번 찾아서 재사용합니다.

== 같은 연산을 반복할 때

[source,python]
----
def slow_fn(x):
    for _ in range(5):
        x = mx.sin(x) + mx.cos(x)
    return x

compiled_fn = mx.compile(slow_fn)

x = mx.random.normal((1000, 1000))
mx.eval(slow_fn(x)); mx.eval(compiled_fn(x))   # 워밍업

for _ in range(20): mx.eval(slow_fn(x))
for _ in range(20): mx.eval(compiled_fn(x))
----

[source]
----
$ python3 mlx_compile_bench.py
uncompiled: 47.92ms  compiled: 10.47ms  speedup: 4.58x
----

**4.58배** 빨라졌습니다. ``slow_fn``을 20번 부르면, MLX는 매번 파이썬 함수를 처음부터 실행하면서 ``sin``/``cos``/``+``로 이루어진 그래프를 새로 구성하고, 그 그래프를 어떻게 GPU 커널로 묶을지 매번 다시 분석합니다. ``mx.compile(slow_fn)``은 **첫 호출에서 딱 한 번** 그 분석(추적, tracing)을 하고, 그 뒤로는 같은 모양의 입력이 들어오면 미리 만들어둔 컴파일 결과를 그대로 재사용합니다 — 그래프 구성과 커널 스케줄링에 드는 파이썬 쪽 오버헤드가 반복 호출에서 사라지는 것입니다.

== 실전 시나리오: 학습 스텝

신경망 학습은 정확히 "같은 연산을 반복하는" 상황입니다 — 매 에폭마다 순전파, 그래디언트, 옵티마이저 갱신을 같은 순서로 되풀이합니다. 다만 파라미터가 매번 바뀌므로, ``mx.compile``에게 "이 상태(모델 파라미터, 옵티마이저 상태)는 호출마다 달라진다"고 알려줘야 합니다.

[source,python]
----
state = [model.state, opt.state]

def step(x, y):
    loss, grads = loss_and_grad(model, x, y)
    opt.update(model, grads)
    return loss

step = mx.compile(step, inputs=state, outputs=state)
----

``inputs``/``outputs``에 ``state``를 넘기면, ``mx.compile``이 "이 함수는 ``model``과 ``opt``의 상태를 읽고 쓴다"는 걸 알고, 매 호출마다 최신 파라미터 값으로 컴파일된 그래프를 다시 실행합니다(그래프를 다시 만드는 게 아니라, 같은 그래프에 새 값만 흘려보냅니다). 6장에서 만들 나선형 분류기 학습 루프를 200번 반복하며 비교하면:

[source]
----
$ python3 mlx_compile_training.py
uncompiled: 132.8 ms  compiled: 99.3 ms  speedup: 1.34x
----

**1.34배** — 4.58배보다 훨씬 작습니다. 이유는 이 학습 스텝 하나(작은 행렬곱 몇 개 + Adam 갱신)가 애초에 계산량 자체는 크지 않아서, 파이썬 오버헤드가 차지하는 비중이 처음 예제(단순 ``sin``/``cos`` 연쇄)만큼 크지 않기 때문입니다 — link:../../heterogeneous-computing-opencl/[전작] 6장이 "산술 강도가 낮으면 최적화 이득도 작다"고 확인한 것과 같은 패턴이, 여기서는 "고정 오버헤드가 원래 작으면 그걸 없애는 최적화의 이득도 작다"는 형태로 다시 나타납니다.

== 요약

* ``mx.compile``이 그래프 추적과 커널 스케줄링을 첫 호출에서 한 번만 하고 재사용한다는 걸, 단순 연산 반복(4.58배)으로 확인했습니다.
* ``inputs``/``outputs``에 ``state``를 넘겨 모델·옵티마이저 상태가 매번 바뀌는 학습 스텝도 컴파일할 수 있다는 걸 확인했고, 그 이득(1.34배)이 단순 예제보다 작다는 것도 실측으로 짚었습니다.
* "컴파일이 항상 큰 이득을 준다"가 아니라 "파이썬 오버헤드가 큰 자리일수록 이득이 크다"는 더 정확한 결론을 이 두 숫자의 대조로 얻었습니다.
