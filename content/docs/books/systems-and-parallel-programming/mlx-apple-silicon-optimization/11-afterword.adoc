== 이 책에서 확인한 것

[source,python]
----
model = MLP(2, 64, 3)                                # 5장: nn.Module, 파라미터 트리
opt = optim.Adam(learning_rate=1e-2)                  # 6장
loss_and_grad = nn.value_and_grad(model, loss_fn)     # 3장: mx.grad를 감싼 버전
step = mx.compile(step, inputs=state, outputs=state)  # 4장: 커널 퓨전

for epoch in range(200):
    loss = step(Xm, ym)          # 1장: 통합 메모리, CPU/GPU 구분 없음
    mx.eval(state, loss)          # 2장: 여기서 실제로 실행

nn.quantize(model, bits=4, group_size=32, class_predicate=predicate)   # 8장
----

``mx.array``를 만드는 순간 이미 GPU에서 쓸 준비가 끝나 있다는 것(1장), 연산이 즉시 실행되지 않고 그래프로 쌓이다가 ``mx.eval``에서 한꺼번에 실행된다는 것(2장), 그 지연이 손 미분과 정확히 같은 결과를 내는 자동 미분(3장)과 반복되는 그래프를 재사용하는 컴파일(4장)의 기반이 된다는 것, 그리고 이 모든 게 ``nn.Module``의 파라미터 트리(5장)와 옵티마이저(6장) 위에서 실제로 나선형 데이터를 99.7% 정확도까지 학습시킨다는 것(9장)을 실제로 확인했습니다. 7장과 10장은 이 편의가 공짜가 아니라는 것도 함께 보여줬습니다 — 통합 메모리가 전송 비용을 없애도, GPU 디스패치 오버헤드는 여전히 실재해서 작은 문제에서는 NumPy와 MLX-CPU가 MLX-GPU를 이깁니다.

== 전작들과 무엇이 같고 무엇이 다른가

link:../../heterogeneous-computing-opencl/[『OpenCL로 배우는 헤테로지니어스 컴퓨팅』]과 link:../../tinyrt-cpu-gpu-inference/[『TinyRT』]가 확인한 "작은 작업에서는 GPU가 손해"라는 결론은 이 책에서도 그대로 재현됩니다(10장) — 다만 그 책들의 원인 중 하나였던 "호스트-디바이스 전송 비용"이 이 책에는 애초에 없습니다(1장). 그런데도 같은 현상이 나타난다는 것 자체가, 그 현상의 진짜 원인이 전송이 아니라 **디스패치 오버헤드**라는 걸 오히려 더 선명하게 보여줍니다 — 변수를 하나 없앴더니 남은 변수의 역할이 더 뚜렷해진 셈입니다. link:../../cpp23-performance-engineering/[『안전을 넘어 성능으로』]의 ``consteval`` 조회 테이블과 이 책의 4비트 양자화(8~9장)도 같은 구조의 트레이드오프입니다 — 둘 다 "약간의 정밀도를 속도/메모리와 맞바꾼다"는 결정을, 검증 가능한 오차로 정직하게 드러냅니다.

== 이 책이 다루지 않은 것

* **``mx.fast``의 커스텀 Metal 커널** — ``mx.fast.metal_kernel``로 직접 Metal 셰이딩 언어 커널을 짜 넣는 것은 다루지 않았습니다. 이 책은 MLX가 기본으로 제공하는 연산(행렬곱, ``sin``/``cos`` 같은 원소별 함수, ``nn.Linear``)만 썼습니다 — link:../../heterogeneous-computing-opencl/[전작]이 OpenCL C로 커널을 직접 짰던 것과 대응하는 자리이지만, 이 책은 그 경계 안쪽(MLX가 이미 최적화해둔 연산을 어떻게 조합하는가)에 머물렀습니다.
* **분산 학습** — ``mx.distributed``(``all_sum``, ``all_gather`` 등 여러 기기에 걸친 집합 통신 API)가 실제로 존재한다는 것만 확인했을 뿐, 이 세션 환경은 기기가 하나뿐이라 여러 Apple Silicon 기기에 걸친 학습은 시도하지 않았습니다.
* **실제 데이터셋** — 이 책은 의도적으로 나선형이라는 합성 데이터를 썼습니다(다운로드나 전처리 없이, 매 실행마다 재현 가능하게 만들기 위해서입니다). 실제 이미지·텍스트 데이터셋에서 이 책의 기법들(특히 8장의 양자화가 정확도에 미치는 영향)이 어떻게 나타나는지는 이 책의 범위를 넘어섭니다.
* **``mlx.nn``의 더 큰 레이어들** — 어텐션, 트랜스포머 블록, 컨볼루션(``nn.Conv1d``/``nn.Conv2d``)처럼 이 책의 ``MLP``보다 복잡한 레이어는 다루지 않았습니다. 이 책이 확인한 원리(통합 메모리, 지연 평가, 자동 미분, 컴파일, 양자화)는 그 레이어들에도 그대로 적용되지만, 실측 수치 자체는 다시 재봐야 합니다.

== 다음 단계

이 책의 나선형 분류기는 일부러 작게 잡은 예제입니다 — 다음으로 볼 만한 자리는 정확히 그 반대 방향입니다. 이 책이 다루지 않은 실제 크기의 데이터셋과 레이어로 옮겨서, 7장과 10장이 찾은 CPU/GPU 교차점이 어디로 움직이는지, 8장의 양자화가 그때도 정확도를 지켜주는지 직접 재보는 것입니다. 그 방향으로 이미 한 걸음 나간 사례가 link:../../onnx-hardware-optimization/12-mlx-native-runtime/[『학습이 끝난 모델을 하드웨어에 맞게 다시 깎는다』 12장]입니다 — 이 나선형 분류기보다 훨씬 큰 실제 ResNet18을 PyTorch에서 이 책의 방식 그대로 MLX로 이식해서, onnxruntime·IREE와 나란히 벤치마크합니다. 어느 쪽으로 가든, 이 책이 반복해서 확인한 한 가지는 유효합니다 — **편의가 공짜인지는 언제나 실측해야 압니다.**
