``Coordinator``는 이제 진행률(`progress_`, 5장)과 상태 레지스트리(`registry_`, 8장)를 둘 다 갖고 있습니다. 이 장에서는 이 둘을 묶어서 보고하는 ``report()``를 추가하고, 그 과정에서 C{pp}23의 나머지 두 작은 도구 — `std::views::zip`(중간 컨테이너 없는 순회)과 `\[[assume]]`/`std::unreachable()`(컴파일러 힌트) — 를 씁니다.

== ``views::zip``으로 ID와 진행률을 짝지어 순회하기

[source,cpp]
----
#include <ranges>

static const char* status_name(WorkerStatus st) {
  switch (st) {
    case WorkerStatus::Idle: return "idle";
    case WorkerStatus::Running: return "running";
    case WorkerStatus::Done: return "done";
  }
  std::unreachable();  // WorkerStatus는 이 세 값뿐이라, switch가 다 처리했다고 컴파일러에게 알려준다
}

void report() {
  std::vector<int> ids;
  for (std::size_t w = 0; w < num_workers_; w++) ids.push_back(static_cast<int>(w));
  std::vector<int> progresses;
  for (std::size_t w = 0; w < num_workers_; w++) progresses.push_back(progress_of(w));

  for (auto&& [id, prog] : std::views::zip(ids, progresses)) {
    std::printf("worker %d: %s (progress=%d)\n", id, status_name(status_of(id)), prog);
  }
}
----

[source]
----
$ clang++ -std=c++23 -O2 -pthread ch09.cpp -o ch09 && ./ch09
worker 0: done (progress=1000)
worker 1: done (progress=1000)
worker 2: done (progress=1000)
worker 3: done (progress=1000)
----

``ids``와 ``progresses``를 ``std::pair``로 짝지은 임시 벡터를 새로 만드는 대신, ``std::views::zip(ids, progresses)``가 두 벡터를 즉석에서 짝지어 순회하는 뷰를 돌려줍니다 — 원소 하나하나를 튜플로 복사해 담는 중간 컨테이너가 없습니다. 7장의 ``TransformWorker``가 임시 버퍼 할당을 줄였던 것과 같은 정신입니다 — 여기서는 애초에 할당할 컨테이너 자체가 없습니다.

== `std::unreachable()`: "이 분기는 절대 안 온다"고 컴파일러에게 알리기

``status_name``의 ``switch``는 ``WorkerStatus``의 세 값(`Idle`, `Running`, `Done`)을 전부 다뤘으므로, `switch` 밖으로 빠져나올 방법이 논리적으로 없습니다. 그런데 컴파일러 입장에서는 "이 함수가 값을 안 돌려주고 끝날 수도 있다"는 경고를 낼 여지가 있습니다. `std::unreachable()`(C{pp}23)을 그 자리에 두면, "여기는 절대 실행되지 않는다"는 걸 컴파일러에게 명시적으로 알려줍니다 — 이 정보는 경고를 없애는 것을 넘어, 컴파일러가 이 분기를 위한 코드를 아예 생성하지 않게 최적화할 근거가 됩니다. 다만 ``WorkerStatus``에 네 번째 값이 나중에 추가되고 이 ``switch``를 안 고치면, ``unreachable()``이 실제로 실행되는 정의되지 않은 동작(undefined behavior)이 됩니다 — "정말로 도달 못 한다"는 확신이 있을 때만 써야 하는 도구입니다.

== `\[[assume]]`: 컴파일러에게 불변조건을 알려주기

[source,cpp]
----
void run() {
  std::size_t chunk = buf_.segments() / num_workers_;
  [[assume(chunk > 0)]];  // 세그먼트 수가 워커 수보다 항상 많다고 가정
  // ...
}
----

``\[[assume(chunk > 0)]]``은 "이 시점에 ``chunk > 0``이 참이라고 믿어도 된다"는 걸 컴파일러에게 알리는 C{pp}23 속성입니다. 이 조건이 실제로 성립하는지는 **컴파일러가 검사해주지 않습니다** — 검사 없이 그냥 믿고 최적화합니다(예: ``chunk == 0``이면 의미가 이상해지는 코드 경로를 아예 제거할 수 있습니다). 만약 실제로 ``buf_.segments() < num_workers_``인 상황이 생겨서 ``chunk``가 ``0``이 된다면, ``\[[assume]]``이 틀린 가정을 근거로 최적화된 코드가 정의되지 않은 동작을 일으킬 수 있습니다 — ``std::unreachable()``과 마찬가지로, "확실히 참인 불변조건"에만 써야 합니다.

== 요약

* ``std::views::zip``으로 ``Coordinator``의 워커 ID와 진행률을 중간 컨테이너 없이 짝지어 순회하는 ``report()``를 완성했습니다.
* ``std::unreachable()``은 논리적으로 도달할 수 없는 코드 경로를 컴파일러에게 알려 경고를 없애고 최적화 근거를 주지만, 실제로 도달하면 정의되지 않은 동작이 된다는 것도 짚었습니다.
* ``\[[assume(...)]]``은 컴파일러가 검사하지 않고 그대로 믿는 불변조건 힌트라서, 둘 다 "확실할 때만" 쓰는 도구라는 공통점이 있습니다.

이제 `BatchBuffer`(1~2장), `TransformWorker`(3~4, 7장), `Coordinator`(5, 8~9장)까지 PerfGrid의 모든 조각이 갖춰졌습니다. 다음 장에서는 이 전체를, 최적화를 하나도 적용하지 않은 순진한 버전과 나란히 벤치마크합니다.

== 팁 박스: C{pp}17 환경이라면

이 장은 C{pp}17에서 세 가지를 각각 대체해야 합니다.

``std::views::zip``은 **C{pp}23**부터입니다(ranges 자체도 C{pp}20이라 C{pp}17에는 애초에 없습니다). C{pp}17에는 두 컨테이너를 나란히 순회하는 표준 어댑터가 없으므로, 인덱스 하나로 양쪽을 동시에 접근하는 게 유일한 방법입니다.

[source,cpp]
----
int report(const std::vector<int>& ids, const std::vector<int>& progress) {
    int sum = 0;
    for (std::size_t i = 0; i < ids.size(); ++i) {
        sum += ids[i] + progress[i];
    }
    return sum;
}
----

``\[[assume]]``과 ``std::unreachable()``도 둘 다 **C{pp}23**부터입니다. C{pp}17에는 표준 문법이 없으므로 컴파일러별 내장 함수를 매크로로 감싸서 씁니다 — Clang/GCC의 ``{us}{us}builtin_unreachable()``, MSVC의 ``{us}{us}assume()``이 흔한 조합입니다.

[source,cpp]
----
#if defined(__clang__) || defined(__GNUC__)
#define ASSUME(cond) do { if (!(cond)) __builtin_unreachable(); } while (0)
#define UNREACHABLE() __builtin_unreachable()
#elif defined(_MSC_VER)
#define ASSUME(cond) __assume(cond)
#define UNREACHABLE() __assume(0)
#else
#define ASSUME(cond) ((void)0)
#define UNREACHABLE() ((void)0)
#endif
----

두 스니펫 모두 ``-std=c{pp}17 -Wall -Wextra``로 경고 없이 컴파일되고, ``report()``와 `ASSUME`/``UNREACHABLE``을 쓰는 ``classify()``가 기대한 값을 낸다는 것도 실행해서 확인했습니다.

잃는 건 두 층위입니다. 인덱스 기반 루프는 ``views::zip``이 주는 파이프 문법(``\|``로 다른 range 어댑터와 이어붙이는 것)을 전혀 못 쓰고, 인덱스 변수 하나를 양쪽 컨테이너에 동시에 맞춰 관리해야 해서 한쪽만 길이가 어긋나면 곧바로 버그가 됩니다. 컴파일러 내장 함수는 컴파일러마다 이름과 문법이 달라 이식성이 없고, 매크로로 감싸더라도 표준이 보장하는 문법이 아니라 "이 컴파일러가 이렇게 동작한다"는 관례에 기대는 것이라 새 컴파일러를 지원할 때마다 분기를 추가해야 합니다.
