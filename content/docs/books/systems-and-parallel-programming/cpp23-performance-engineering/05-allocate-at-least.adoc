'''

메모리 할당자(malloc, `operator new`)는 요청받은 크기를 그대로 주지 않는 경우가 흔합니다 — 내부적으로 정해둔 버킷 크기(예: 16, 32, 48바이트 단위)에 맞춰 올림하기 때문에, `40`바이트를 요청해도 실제로는 `48`바이트짜리 블록을 통째로 내주는 식입니다. 문제는 이전까지 C++에는 "내가 요청한 것보다 실제로 얼마나 받았는지" 알아낼 표준 방법이 없었다는 점입니다 — `std::vector`가 재할당을 피하려고 남는 용량을 파악하고 싶어도 방법이 없었습니다. C++23의 **`allocate_at_least`**가 이 자리를 채웁니다.

== `allocate_at_least`: "적어도 이만큼"을 요청하고 실제 크기를 돌려받기

[source,cpp]
----
#include <memory>

std::allocator<int> alloc;
auto result = alloc.allocate_at_least(10);
// result.ptr: 할당된 메모리
// result.count: 실제로 사용 가능한 원소 개수 (>= 10)
----

[source]
----
$ clang++ -std=c++23 -O0 allocate_at_least.cpp -o allocate_at_least && ./allocate_at_least
requested: 10, actually got count: 10
----

`allocate_at_least(n)`은 `std::allocation_result<T*>{ptr, count}`를 돌려줍니다 — `count`는 `n` **이상**이어도 됩니다. 그런데 이 세션에 설치된 `libc++`의 `std::allocator<int>`로 실제로 실행해보면 `count`가 요청한 `10` 그대로 나옵니다 — **이 표준 할당자 구현은 여유분을 전혀 보고하지 않습니다.** `operator new`가 내부적으로 더 큰 블록을 줬을 수도 있지만, `std::allocator`는 그 정보를 조회해서 돌려주는 일을 안 합니다. 이 책의 다른 장들이 그래왔듯, 여기서도 "표준이 허용하는 것"과 "이 세션의 구현이 실제로 하는 것"은 다르다는 걸 있는 그대로 적습니다.

== 진짜 여유분을 얻으려면: 플랫폼 API와 연결하기

`allocate_at_least`가 진짜 쓸모 있으려면, 할당자가 **실제로 내부 힙 구현에게 "이 블록이 진짜로는 몇 바이트냐"고 물어봐야** 합니다. macOS/Darwin에는 `malloc_size()`라는 함수가 있습니다 — 포인터 하나를 주면, malloc이 그 포인터에 실제로 얼마나 큰 블록을 내줬는지(요청한 크기가 아니라, 내부 버킷에 맞춰 올림된 진짜 크기) 돌려줍니다.

[source,cpp]
----
#include <malloc/malloc.h>

template <typename T>
struct UsableSizeAllocator {
  using value_type = T;

  std::allocation_result<T*> allocate_at_least(std::size_t n) {
    std::size_t bytes = n * sizeof(T);
    void* p = ::operator new(bytes);
    std::size_t usable = malloc_size(p);         // 실제로 확보된 바이트 수
    return {static_cast<T*>(p), usable / sizeof(T)};
  }
  T* allocate(std::size_t n) { return allocate_at_least(n).ptr; }
  void deallocate(T* p, std::size_t) { ::operator delete(p); }
};
----

[source]
----
$ clang++ -std=c++23 -O0 allocate_at_least2.cpp -o allocate_at_least2 && ./allocate_at_least2
requested: 10 ints (40 bytes), actually usable: 12 ints
----

`int` 10개(`40`바이트)를 요청했는데, `malloc_size()`가 알려준 실제 확보량은 `12`개치(macOS의 malloc 버킷 크기 정책상 `40`바이트 요청이 더 큰 버킷으로 올림된 것)였습니다 — **이미 그 메모리에 대한 비용을 지불했는데, 표준 할당자를 썼다면 몰랐을 여유분**입니다. 이 여유분을 안다는 게 왜 중요한지는, `std::vector` 같은 컨테이너가 재할당을 언제 해야 하는지 결정할 때 정확히 드러납니다 — 벡터가 자기 용량을 다 썼다고 판단해서 더 큰 메모리로 재할당(복사 + 해제)하는 대신, 실제로는 이미 여유 공간이 있으니 그 자리에서 몇 개를 더 채울 수 있는 상황을 놓치지 않게 됩니다.

== 왜 리눅스가 아니라 macOS 예제인가

`malloc_usable_size()`(glibc/리눅스에서 흔히 쓰는 동등한 함수)가 이 시리즈의 다른 예제처럼 리눅스 환경에서 더 자주 언급되지만, 이 세션의 실제 실행 환경은 Darwin(macOS)이므로 `<malloc/malloc.h>`의 `malloc_size()`를 그대로 썼습니다 — 이름은 플랫폼마다 다르지만(`malloc_usable_size` vs `malloc_size`), "malloc이 실제로 내준 블록 크기를 사후에 조회한다"는 개념 자체는 두 플랫폼에서 동일합니다. 실전에서 이식 가능한 할당자를 짤 때는 플랫폼별로 이 조회 함수를 `#ifdef`로 갈라 써야 합니다.

== 요약

* `allocate_at_least(n)`은 요청한 크기 이상의 메모리를 확보하고, 실제로 사용 가능한 개수를 함께 돌려주는 C++23 API지만, 이 세션의 `std::allocator<int>`는 그 여유분을 보고하지 않는다는 걸 실측으로 확인했습니다 — 표준이 허용하는 최적화와 특정 구현이 실제로 하는 일이 다를 수 있다는 걸 여기서도 짚었습니다.
* macOS의 `malloc_size()`(플랫폼별 malloc 내부 조회 API)를 연결한 커스텀 할당자로, 요청보다 실제로 20% 더 큰 블록이 확보돼 있었다는 걸 실제로 확인했습니다 — 이미 비용을 지불한 여유 메모리를 낭비하지 않게 해줍니다.
* 이런 조회 함수의 이름과 존재 여부는 플랫폼마다 다르므로, 이식 가능한 코드에서는 플랫폼별 분기가 필요합니다.

다음 장에서는 할당 크기가 아니라 할당 **경합**(여러 스레드가 같은 힙을 두고 다투는 문제)을, PMR 스레드 로컬 아레나로 없애는 법을 다룹니다.
