== 이 책에서 조립한 것: PerfGrid

[source,cpp]
----
class BatchBuffer { /* 1장: mdspan 뷰. 2장: layout_stride 타일 */ };

struct TransformWorker {                    // 3장: deducing this
  std::pmr::memory_resource* arena;          // 7장: PMR 아레나
  void process(this auto&& self, tile) { ... self.transform(...) ... }
  double transform(double x) { return fast_sin(x); }  // 4장: consteval 조회 테이블
};

class Coordinator {
  std::vector<int> progress_;                 // 5장: atomic_ref로 추적
  std::flat_map<int, WorkerStatus> registry_;  // 8장: flat_map 레지스트리
  void run() { /* std::thread로 TransformWorker 분배 */ }
  void report() { /* 9장: views::zip + assume/unreachable */ }
};
----

이 한 덩어리 안에 이 책의 조립 장들이 들어 있습니다. ``std::mdspan``으로 캐시 친화적인 뷰를 만들고(1장), ``layout_stride``로 워커마다 겹치지 않는 구간을 복사 없이 나눠주고(2장), ``deducing this``로 CRTP 없이 정적 다형성을 얻고(3장), ``consteval``로 반복 계산을 컴파일 타임 조회 테이블로 옮기고(4장), ``atomic_ref``로 워커 진행률을 락 없이 추적하고(5장), ``allocate_at_least``로 할당자의 여유분을 들여다본 뒤(6장) PMR 스레드 로컬 아레나로 반복 할당의 경합을 없애고(7장), ``flat_map``으로 캐시 친화적인 워커 레지스트리를 만들고(8장), ``views::zip``과 `\[[assume]]`/``unreachable()``로 보고 경로를 마무리한(9장) 결과가, 11장에서 재구성 없이 그대로 실행되어 순진한 버전보다 일관되게 4배 안팎 빠르다는 걸 확인했습니다. 10장의 SIMD 실험은 이 파이프라인에 다시 끼워 넣지 않았습니다 — 그 장이 확인한 것 자체가 "``BatchBuffer``/``TransformWorker``가 이미 자동 벡터화되고 있어서 명시적 SIMD가 별 차이를 못 만든다"였으므로, PerfGrid 조립에 새로 넣을 게 없었기 때문입니다.

전작과 마찬가지로 이 책의 모든 벤치마크는 이 세션의 Apple Clang 21(`-std=c{pp}23`, `-O2`)로 실제로 컴파일하고 실행한 실측치입니다. 벤치마크 숫자는 전작의 컴파일 성공/실패나 TSan 리포트처럼 재현 가능한 참/거짓이 아니라 **이 머신, 이 순간의 상대적 차이**라는 것도 매 장마다 반복 실행으로 확인한 뒤에야 실었습니다.

== 안전과 성능은 같은 코드베이스에서 만난다

전작이 TaskGrid를 안전하게 만드는 데 집중했다면, 이 책은 같은 문제를 빠르게 만드는 데 집중했습니다 — 그런데 이 둘은 서로 다른 코드베이스가 아닙니다. 전작 8장의 `WorkerSession`(타입 상태 + 이동 전용 핸들의 합성)이 감싸는 자리에, 이 책의 ``TransformWorker``가 하는 처리 로직을 그대로 끼워 넣을 수 있습니다. 전작 9장의 락 순서 규칙은 이 책 7장의 PMR 아레나처럼 "애초에 공유 자원을 안 만든다"는 전략과 상충하지 않고, 전작 14장의 `GCounter`(나중에 합침)와 이 책 5장의 `atomic_ref`(즉시 읽고 씀)는 5장에서 짚었듯 같은 문제의 서로 다른 해법입니다. **정확성을 인코딩하는 타입과 성능을 결정하는 메모리 접근 패턴은 서로 다른 층위의 관심사**이기 때문에, 두 책의 기법은 한 시스템 안에서 자연스럽게 겹쳐 쓸 수 있습니다.

== 이 책이 다루지 않은 것

* **GPU 오프로딩** — ``TransformWorker``의 처리를 GPU로 옮기는 것(CUDA, SYCL, 또는 ``std::execution``의 GPU 실행기)은 다루지 않았습니다.
* **`views::chunk`/`slide`/`stride`, `std::start_lifetime_as`** — C{pp}23/26 표준에는 있지만 이 세션의 ``libc{pp}``에는 아직 구현되지 않은 기능들을 실제 컴파일 에러로 확인하고 넘어갔습니다. 구현이 따라잡으면 다시 살펴볼 만합니다 — 특히 ``start_lifetime_as``는 원시 바이트 버퍼를 복사 없이 구조체로 재해석하는 용도라, ``BatchBuffer``가 네트워크나 파일에서 받은 바이트를 다룰 일이 생기면 유용했을 도구입니다. (``std::submdspan``도 같은 이유로 아직 없지만, 2장에서 Kokkos 레퍼런스 구현으로 실제로 메워서 썼습니다 — 표준 라이브러리에 없다고 항상 손 조립만이 답은 아니라는 것도 이 책이 확인한 것 중 하나입니다.)
* **다른 컴파일러/플랫폼과의 비교** — 이 책의 모든 숫자는 Apple Clang 21, Darwin, `libc{pp}` 조합 하나에서만 나왔습니다. GCC/libstdc{pp}나 MSVC, 리눅스 환경에서는 같은 코드가 다른 절대 수치(그리고 어쩌면 다른 상대적 순위)를 낼 수 있습니다.
+
[NOTE]
====
**"그럼 리눅스에서 GCC로는 되나?"를 실제로 확인해봤습니다** — Docker로 Ubuntu 24.04 컨테이너를 띄우고 GCC 14/15와 Clang 18/20을 설치해, 이 책이 쓰는 헤더들이 실제로 있는지 하나씩 컴파일해봤습니다. 결과가 직관과 반대였습니다 — **GCC는 14도, 최신 15도 ``<mdspan>``이 아예 구현되어 있지 않습니다**(``__cpp_lib_mdspan``이 정의조차 안 됨). 이 책은 1장부터 ``std::mdspan``을 씁니다 — 즉 GCC로는 이 책의 코드 대부분이 **컴파일조차 안 됩니다.** 반대로 Clang 계열(`libc{pp}`)은 버전 20부터 ``mdspan``과 ``flat_map``을 둘 다 갖췄는데, 이건 이 책이 실제로 검증에 쓴 Apple Clang 21과 정확히 같은 조합(둘 다 LLVM의 `libc{pp}` 기반)입니다.

정리하면 — 이 세션 환경(Apple Clang 21)은 "어쩌다 손에 잡힌 컴파일러"가 아니라, 이 책이 실제로 쓰는 기능 기준으로는 **지금 자유롭게 구할 수 있는 툴체인 중 가장 완비된 축**에 듭니다. "GCC/리눅스로 옮기면 더 표준적일 것"이라는 흔한 직관이 이 책에는 그대로 적용되지 않는다는 것도, 실제로 여러 컴파일러를 설치하고 나서야 확인할 수 있었던 사실입니다.
====
* **프로파일러 기반 분석** — 이 책은 ``std::chrono``로 전체 실행 시간만 쟀습니다. `perf`, Instruments, VTune으로 캐시 미스 횟수나 분기 예측 실패율을 직접 측정하는 것은 다루지 않았습니다 — 1장과 7장에서 "캐시 미스 때문일 것"이라고 설명한 부분은 실행 시간 차이로부터의 합리적 추론이지, 프로파일러로 캐시 미스 카운터를 직접 읽은 것은 아닙니다.

== 다음 단계

전작과 이 책을 함께 읽었다면, 하나의 시스템은 이제 컴파일 타임에 프로토콜을 강제하고, 자원을 안전하게 이동하고, 실패를 자동으로 전파하고, 메모리 레이아웃이 접근 패턴과 맞고, 워커끼리 할당 경합 없이, 반복 계산을 조회 테이블로 대신하며, 그 진행 상황을 락 없이도 캐시 친화적으로 조회할 수 있는 코드베이스가 됐습니다(10장에서 확인했듯 이 루프들은 이미 컴파일러가 자동으로 SIMD 벡터화하고 있기도 합니다 — 다만 이건 10장이 검증만 했을 뿐, 위 클래스들에 새로 심은 것은 아닙니다). 다음으로 볼 만한 자리는 정확히 이 책이 다루지 않은 것들 — 프로파일러로 확인하는 실제 캐시 동작, 그리고 두 책 모두 계속 미뤄온 C{pp}26의 `std::execution`(전작 맺음말의 스케치를 실제 구현으로 확인하는 것)입니다.
