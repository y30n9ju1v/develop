'''

PerfGrid의 코디네이터는 `BatchBuffer` 하나를 여러 워커에게 나눠줘야 합니다 — 각 워커는 전체 버퍼가 아니라 자기가 맡은 세그먼트 구간만 봐야 하고, 그 구간은 다른 워커의 구간과 절대 겹치면 안 됩니다(전작 13장의 `std::span` 분할과 같은 요구입니다). 이 장에서는 ``BatchBuffer``에 그 구간 하나만 가리키는 비소유 뷰를 돌려주는 ``tile()``을 추가합니다.

== `BatchBuffer::tile()`: 복사 없는 부분 뷰

C{pp}23 표준에는 이런 부분 뷰를 자동으로 뽑아주는 ``std::submdspan``(C{pp}26 예정)이 있지만, 이 세션의 ``libc{pp}``(Apple Clang 21)에는 아직 구현되어 있지 않습니다 — 실제로 써보면 ``no member named 'submdspan'`` 컴파일 에러가 납니다. 표준 라이브러리에 없다고 해서 손 조립 말고는 방법이 없는 건 아닙니다 — https://github.com/kokkos/mdspan[Kokkos mdspan 레퍼런스 구현]은 ``std::mdspan``이 표준화되기 전 바탕이 된 원본 구현체이자, ``submdspan``(P2630)의 레퍼런스 구현이기도 합니다. 헤더 하나(``<experimental/mdspan>``)만 받으면 되고, 이미 ``std::mdspan``이 있는 툴체인 위에서는 그 표준 타입을 그대로 재사용하도록 만들어져 있어서 ``std::submdspan``이라는 이름으로 바로 쓸 수 있습니다.

[source,cpp]
----
#include <experimental/mdspan>  // Kokkos mdspan 레퍼런스 구현: github.com/kokkos/mdspan

class BatchBuffer {
  // ... 1장의 data_, segments_, elements_, view() ...

  // 세그먼트 축으로 [seg0, seg0+n_segs) 구간만 가리키는 비소유 타일 뷰
  auto tile(std::size_t seg0, std::size_t n_segs) {
    return std::submdspan(view(), std::pair{seg0, seg0 + n_segs}, std::full_extent);
  }
};
----

``std::submdspan``에 ``std::pair{seg0, seg0+n_segs}``를 넘기면 그 차원은 그 구간만 남고, ``std::full_extent``를 넘기면 그 차원은 전체를 그대로 유지합니다 — 원본과 같은 스트라이드를 유지하는 부분 뷰를, 오프셋과 스트라이드를 손으로 계산할 필요 없이 얻습니다. 이 레퍼런스 구현을 쓰면 ``-I`` 하나만 추가하면 되고(빌드에 새 의존성을 하나 들이는 정도의 비용), 반환 타입도 표준이 정의한 ``submdspan``의 결과 타입 그대로라 다른 ``mdspan`` 기반 코드와 계속 호환됩니다.

== 검증: 겹치지 않는 두 타일, 그리고 진짜 뷰라는 증거

[source,cpp]
----
BatchBuffer buf(10, 4);
auto v = buf.view();
for (std::size_t i = 0; i < 10; i++)
  for (std::size_t j = 0; j < 4; j++) v[i, j] = static_cast<double>(i * 100 + j);

auto worker1_tile = buf.tile(0, 5);   // 워커 0이 맡는 세그먼트 0~4
auto worker2_tile = buf.tile(5, 5);   // 워커 1이 맡는 세그먼트 5~9
----

[source]
----
$ clang++ -std=c++23 -O2 -I kokkos-mdspan/include ch02.cpp -o ch02 && ./ch02
worker1 tile[0,0]=0 tile[4,3]=403 (extents 5x4)
worker2 tile[0,0]=500 tile[4,3]=903 (extents 5x4)
----

``worker1_tile``은 세그먼트 `0~4`(값이 ``0``부터 ``403``까지), ``worker2_tile``은 `5~9`(값이 ``500``부터 ``903``까지)를 정확히 가리킵니다 — 두 타일이 원본 버퍼의 서로 다른, 겹치지 않는 구간을 가리킨다는 걸 확인했습니다. 이 뷰가 정말로 **복사가 아니라는** 것도 확인해봅니다.

[source,cpp]
----
worker2_tile[0, 0] = -1.0;
std::printf("original buf[5,0] after writing through tile = %.0f\n", v[5, 0]);
----

[source]
----
original buf[5,0] after writing through tile = -1
----

``worker2_tile``을 통해 쓴 값이 원본 ``buf``에도 그대로 반영됩니다 — ``tile_ptr``가 가리키는 메모리가 ``data_``와 **완전히 같은 메모리**이기 때문입니다. 이게 PerfGrid가 워커에게 데이터를 "나눠주는" 방식입니다 — 버퍼를 복사해서 각 워커에게 보내는 게 아니라, 같은 메모리의 서로 다른 구간을 가리키는 뷰만 나눠줍니다.

== 요약

* ``BatchBuffer::tile(seg0, n_segs)``는 ``std::submdspan``으로 원본과 같은 스트라이드를 물려받는 부분 뷰를 만들어, 세그먼트 구간 하나만 복사 없이 가리킵니다.
* ``std::submdspan``은 이 세션의 ``libc{pp}``(Apple Clang 21)에 아직 구현되어 있지 않지만, https://github.com/kokkos/mdspan[Kokkos mdspan 레퍼런스 구현]을 헤더만 받아 ``-I``로 추가하면 표준과 동일한 API로 바로 쓸 수 있다는 걸 실제 컴파일로 확인했습니다 — 오프셋/스트라이드를 손으로 계산할 필요가 없어집니다.
* 타일을 통한 쓰기가 원본 ``BatchBuffer``까지 그대로 반영된다는 걸 실제로 확인해, 이게 복사가 아니라 진짜 뷰라는 걸 검증했습니다 — 이후 장에서 워커들이 이 타일을 나눠 받아 병렬로 처리합니다.

다음 장에서는 이 타일을 실제로 처리하는 ``TransformWorker``를, ``deducing this``로 CRTP 없이 만듭니다.

== 팁 박스: 레퍼런스 구현도, C{pp}17도 못 쓴다면

Kokkos 레퍼런스 구현을 빌드에 새로 들이고 싶지 않거나 C{pp}17 환경이라면, ``std::layout_stride``를 손으로 조립하는 방법도 여전히 유효합니다. 원본과 **같은 스트라이드**(각 차원으로 한 칸 이동할 때 메모리에서 몇 칸을 건너뛰는지)를 물려받되, 시작 위치와 크기만 바꾼 새 뷰를 만드는 것입니다.

[source,cpp]
----
#include <array>

std::mdspan<double, std::dextents<std::size_t, 2>, std::layout_stride>
tile_manual(std::mdspan<double, std::dextents<std::size_t, 2>> full,
            std::size_t seg0, std::size_t n_segs, std::size_t elements) {
  double* ptr = &full[seg0, 0];
  std::array<std::size_t, 2> strides{full.stride(0), full.stride(1)};
  return std::mdspan<double, std::dextents<std::size_t, 2>, std::layout_stride>(
      ptr, std::layout_stride::mapping{std::dextents<std::size_t, 2>{n_segs, elements}, strides});
}
----

이건 C{pp}23 자체(``std::mdspan``/``layout_stride``)는 있지만 ``submdspan``이라는 편의 함수만 없는 경우의 대안입니다. 정말 C{pp}17까지 내려가서 ``std::mdspan`` 자체가 없는 경우라면, 1장에서 짚었듯 대체 표준 타입도 없으므로 ``offset``/``extents``/``strides``를 직접 들고 있는 ``StridedView2D`` 구조체 하나면 이 장의 ``tile()``이 하는 일을 그대로 흉내 낼 수 있습니다.

[source,cpp]
----
struct StridedView2D {
    double* data;
    std::size_t offset;
    std::size_t rows, cols;
    std::size_t row_stride, col_stride;

    double& operator()(std::size_t r, std::size_t c) {
        return data[offset + r * row_stride + c * col_stride];
    }
};

StridedView2D tile(double* base, std::size_t total_cols,
                    std::size_t seg0, std::size_t n_segs, std::size_t cols) {
    return StridedView2D{base, seg0 * total_cols, n_segs, cols, total_cols, 1};
}
----

이 함수로 만든 타일에 값을 쓰면 원본 버퍼에도 그대로 반영됩니다 — 이 장이 확인한 "복사가 아니라 진짜 뷰"라는 성질은 그대로 유지됩니다. ``-std=c{pp}17``로 경고 없이 컴파일되는 것도 확인했습니다.

잃는 건 두 가지입니다. 첫째, ``std::layout_stride``는 ``std::mdspan``의 `layout_policy` 슬롯에 끼워 넣을 수 있는 표준 정책 타입이라 다른 레이아웃(행 우선, 열 우선)과 같은 인터페이스로 맞바꿀 수 있지만, ``StridedView2D``는 그 자체로 고정된 하나의 타입이라 정책을 바꾸려면 새 구조체를 또 만들어야 합니다. 둘째, ``mdspan``을 인자로 받는 표준/서드파티 알고리즘과 호환되는 어휘 타입(vocabulary type)이 아니라서, 이런 손으로 짠 뷰는 그 프로젝트 안에서만 통용됩니다.
