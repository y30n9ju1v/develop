이 책은 전작의 TaskGrid와 같은 문제(코디네이터가 워커에게 배치를 나눠주고, 워커가 처리한다)를 성능 관점에서 다시 짭니다 — 이 시스템을 **PerfGrid**라고 부르겠습니다. 첫 조각은 워커들이 실제로 만지는 데이터, 즉 배치 버퍼 그 자체입니다.

== `BatchBuffer`: mdspan으로 감싼 평평한 버퍼

PerfGrid의 배치는 논리적으로 "세그먼트 여러 개, 세그먼트마다 원소 여러 개"인 2차원 구조지만, 실제 메모리는 `std::vector<double>` 하나로 평평하게 저장됩니다. C{pp}23의 **`std::mdspan`**으로 이 둘을 잇습니다.

[source,cpp]
----
#include <mdspan>
#include <vector>

class BatchBuffer {
  std::vector<double> data_;
  std::size_t segments_, elements_;
public:
  BatchBuffer(std::size_t segments, std::size_t elements)
      : data_(segments * elements), segments_(segments), elements_(elements) {}

  std::mdspan<double, std::dextents<std::size_t, 2>> view() {
    return std::mdspan<double, std::dextents<std::size_t, 2>>(data_.data(), segments_, elements_);
  }
  std::size_t segments() const { return segments_; }
  std::size_t elements() const { return elements_; }
};
----

``BatchBuffer``는 실제 메모리(`data_`)를 소유하는 유일한 곳이고, ``view()``가 그 메모리 위에 "이건 ``segments_``행 ``elements_``열짜리 2차원 배열이다"라는 해석을 얹은 **비소유 뷰**를 돌려줍니다. ``v[i, j]``처럼 콤마로 구분한 여러 첨자를 한 번에 쓰는 다중 첨자 ``operator[]``도 C{pp}23에서 새로 들어온 문법입니다. 이 책의 나머지 모든 장은 이 `BatchBuffer` 위에 기능을 하나씩 얹습니다.

== 순회 순서가 저장 순서와 어긋나면

``std::mdspan``의 기본 레이아웃(`layout_right`)은 마지막 차원이 메모리에서 연속입니다 — ``BatchBuffer``는 세그먼트가 바깥 차원, 원소가 안쪽 차원이므로, **세그먼트 하나를 통째로 훑는 순회**가 메모리 연속 방향과 일치합니다.

[source,cpp]
----
BatchBuffer buf(4000, 4000);
auto v = buf.view();
for (std::size_t i = 0; i < 4000; i++)
  for (std::size_t j = 0; j < 4000; j++) v[i, j] = 1.0;

// 저장 순서와 일치: 세그먼트(i)를 바깥, 원소(j)를 안쪽에 두고 순회
double s1 = 0;
for (std::size_t i = 0; i < 4000; i++)
  for (std::size_t j = 0; j < 4000; j++) s1 += v[i, j];

// 저장 순서와 어긋남: 원소(j)를 바깥, 세그먼트(i)를 안쪽에 두고 순회
double s2 = 0;
for (std::size_t j = 0; j < 4000; j++)
  for (std::size_t i = 0; i < 4000; i++) s2 += v[i, j];
----

[source]
----
$ clang++ -std=c++23 -O2 ch01.cpp -o ch01 && ./ch01
segment-major (matches storage): 15.15 ms (sum=16000000)
element-major (against storage): 35.40 ms (sum=16000000)
----

똑같은 합계를 내지만, 저장 순서와 일치하는 순회가 그렇지 않은 순회보다 두 배 넘게 빠릅니다 — 어긋난 순회는 안쪽 루프 한 번마다 `4000 * 8바이트`(약 32KB)씩 건너뛰므로, 캐시 라인(보통 64바이트) 하나를 가져와서 double 하나만 쓰고 버리는 셈입니다. ``BatchBuffer``의 워커들이 앞으로 "세그먼트 하나를 통째로 처리"하는 패턴을 쓸 것이므로, 이 기본 레이아웃(세그먼트가 바깥, 원소가 안쪽)이 자연스럽게 유리합니다.

== 요약

* ``BatchBuffer``는 `std::vector<double>` 하나를 실제로 소유하고, ``std::mdspan``으로 그 위에 2차원 해석을 얹는 비소유 ``view()``를 제공합니다 — 이 책의 모든 장이 이 클래스를 확장합니다.
* 순회 순서가 메모리의 실제 저장 순서와 어긋나면 캐시 라인 낭비로 실행 시간이 두 배 넘게 늘어난다는 걸 실측으로 확인했고, ``BatchBuffer``의 기본 레이아웃은 "세그먼트 단위 처리"에 자연스럽게 맞습니다.

다음 장에서는 이 ``BatchBuffer``에, 워커마다 겹치지 않는 구간만 가리키는 `tile()` 메서드를 ``layout_stride``로 추가합니다.

== 팁 박스: C{pp}17 환경이라면

``std::mdspan``은 **C{pp}23**부터입니다. C{pp}17에는 다차원 뷰를 표현하는 표준 타입이 아예 없으므로, 원시 포인터와 스트라이드 산술을 손으로 감싼 작은 뷰 구조체를 직접 만드는 게 실무에서 가장 흔한 대체법입니다.

[source,cpp]
----
struct View2D {
    double* data;
    std::size_t rows, cols;

    double& operator()(std::size_t r, std::size_t c) {
        return data[r * cols + c];
    }
    double operator()(std::size_t r, std::size_t c) const {
        return data[r * cols + c];
    }
};
----

`view(1, 2) = 42.0;`처럼 써보면 ``storage[1 * 4 + 2]``가 그대로 바뀝니다 — ``BatchBuffer::view()``가 하는 일과 결과는 동일합니다. `-std=c{pp}17 -Wall -Wextra`로 경고 없이 컴파일되는 것도 확인했습니다.

잃는 것도 명확합니다. ``std::mdspan``은 `extents`(정적/동적 차원)와 `layout_policy`(행 우선/열 우선/스트라이드)를 타입 수준에서 조합할 수 있지만, 손으로 짠 `View2D`는 그 조합이 전부 하드코딩된 `operator()` 하나뿐입니다. 차원 수가 컴파일 타임에 검사되지도 않고(잘못된 인자 개수로 불러도 그냥 다른 원소를 가리킬 뿐), ``std::submdspan``처럼 라이브러리가 제공하는 부분 뷰 조합도 없어서 다음 장의 `tile()` 같은 걸 만들려면 스트라이드 계산을 처음부터 다시 손으로 짜야 합니다.
