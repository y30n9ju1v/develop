2장에서 워커마다 겹치지 않는 타일을 나눠주는 법을 만들었으니, 이제 그 타일을 실제로 처리하는 워커 자체를 만들 차례입니다. 워커 종류가 여러 개(단순 변환, 체크섬 계산 등)로 늘어날 걸 대비해 "공통 실행 흐름은 한 곳에, 실제 동작은 각 워커가"라는 구조를 갖고 싶습니다. C{pp}에서는 전통적으로 이걸 가상 함수 없이 **CRTP**로 해결했는데, C{pp}23의 **`deducing this`**가 더 단순한 대안을 줍니다.

== 옛 방식과 새 방식을 나란히

[source,cpp]
----
// 옛 방식: CRTP로 정적 다형성 흉내
template <typename Derived>
struct OldWorkerBase {
  void process(std::mdspan<double, std::dextents<std::size_t, 2>, std::layout_stride> tile) {
    for (std::size_t s = 0; s < tile.extent(0); s++)
      for (std::size_t e = 0; e < tile.extent(1); e++)
        tile[s, e] = static_cast<Derived*>(this)->transform(tile[s, e]);
  }
};
struct OldTransformWorker : OldWorkerBase<OldTransformWorker> {
  double transform(double x) { return x * 2.0; }
};

// 새 방식: deducing this
struct TransformWorker {
  void process(this auto&& self,
               std::mdspan<double, std::dextents<std::size_t, 2>, std::layout_stride> tile) {
    for (std::size_t s = 0; s < tile.extent(0); s++)
      for (std::size_t e = 0; e < tile.extent(1); e++)
        tile[s, e] = self.transform(tile[s, e]);
  }
  double transform(double x) { return x * 2.0; }
};
----

``OldWorkerBase<Derived>``는 ``this``를 ``static_cast<Derived*>``로 강제 변환해서 ``transform``을 호출합니다 — 가상 함수 없이 다형성을 흉내 내지만, 템플릿 베이스 클래스를 매번 만들어야 합니다. ``TransformWorker::process(this auto&& self, ...)``는 첫 매개변수 자리에 ``this``를 명시해서, ``self``의 실제 타입이 호출된 객체의 타입으로 추론되게 합니다 — ``self.transform(...)``이 그 타입 위에서 정적으로 해소됩니다. 베이스 클래스가 아예 없다는 점만 다르고, 컴파일 타임에 다형성이 해소된다는 성질은 동일합니다.

== 검증: 둘이 같은 결과를 내는가

[source,cpp]
----
BatchBuffer buf1(4, 3), buf2(4, 3);
// buf1, buf2에 같은 값 채움 ...

OldTransformWorker old_worker;
old_worker.process(buf1.tile(0, 4));

TransformWorker new_worker;
new_worker.process(buf2.tile(0, 4));
----

[source]
----
$ clang++ -std=c++23 -O2 ch03.cpp -o ch03 && ./ch03
CRTP result buf1[2,1]=6.0, deducing-this result buf2[2,1]=6.0 (same=1)
----

두 워커가 같은 입력에 같은 변환(`x * 2.0`)을 적용해 정확히 같은 결과를 냅니다 — ``deducing this``가 CRTP의 자리를 문법만 단순하게 대신할 뿐, 동작은 동일하다는 걸 확인했습니다. 앞으로 PerfGrid는 `TransformWorker`(CRTP 버전이 아니라)를 계속 확장해 나갑니다.

== 왜 이게 성능과 관련 있는가

이 장의 검증은 실행 시간 비교가 아닙니다 — CRTP와 `deducing this` 둘 다 **정적으로 해소**되므로(가상 함수 테이블 조회가 없으므로), `-O2` 이상에서는 둘 다 인라인될 가능성이 가상 함수보다 훨씬 높습니다. 이 장이 확인한 건 "문법이 단순해지면서도 해소 시점(컴파일 타임)은 그대로 유지된다"는 것입니다 — 실제 어셈블리 수준 인라인 여부는 컴파일러 구현에 달려 있어 이 장에서 별도로 확인하지 않았습니다.

== 요약

* `deducing this`(`this auto&& self`)로 CRTP와 같은 컴파일 타임 정적 다형성을, 템플릿 베이스 클래스 없이 얻을 수 있다는 걸 두 버전을 나란히 컴파일해 확인했습니다.
* ``TransformWorker``가 이제 PerfGrid의 실제 처리 로직을 담당하는 워커 타입이 되었고, 다음 장부터 그 `transform()` 구현을 바꿔가며 확장합니다.

다음 장에서는 ``transform()``의 몸통(지금은 ``x * 2.0``이라는 자리표시자)을, `consteval` 조회 테이블을 쓰는 실제 계산으로 바꿉니다.

== 팁 박스: C{pp}17 환경이라면

`deducing this`(`this auto&& self`)는 **C{pp}23**부터입니다. 하지만 이 장이 `deducing this`로 대신한 원래 기법 — CRTP(Curiously Recurring Template Pattern) — 자체는 C{pp}17은 물론 C{pp}11보다도 훨씬 오래된 관용구입니다. 그러니 C{pp}17 환경이라면 이 장의 "새 방식"이 아니라 "옛 방식"을 그대로 씁니다.

[source,cpp]
----
template <typename Derived>
struct TransformWorkerBase {
    void process(double* data, int n) {
        auto& self = static_cast<Derived&>(*this);
        for (int i = 0; i < n; ++i) {
            data[i] = self.transform(data[i]);
        }
    }
};

struct DoubleWorker : TransformWorkerBase<DoubleWorker> {
    double transform(double x) { return x * 2.0; }
};
----

`DoubleWorker{}.process(data, 3)`를 불러보면 이 장의 `deducing this` 버전과 정확히 같은 결과(`x * 2.0`)가 나옵니다. `-std=c{pp}17`로 경고 없이 컴파일되는 것도 확인했습니다.

잃는 건 문법적 보일러플레이트입니다. CRTP는 파생 클래스가 자기 자신을 템플릿 인자로 다시 넘겨줘야 하고(``struct DoubleWorker : TransformWorkerBase<DoubleWorker>``처럼 이름을 두 번 반복), 베이스 클래스 안에서는 매번 `static_cast<Derived&>(*this)`로 다운캐스트해야 `transform()`을 호출할 수 있습니다. `deducing this`는 이 캐스트와 반복을 문법 차원에서 없애줄 뿐 아니라, `self`가 값 범주(lvalue/rvalue)까지 그대로 전달받으므로 "이 워커가 임시 객체일 때와 아닐 때 다르게 동작해야 한다"처럼 더 정교한 오버로딩이 필요해지면 CRTP보다 훨씬 깔끔하게 확장됩니다 — 이 장의 단순한 `transform()` 예제에서는 그 차이가 드러나지 않지만요.
