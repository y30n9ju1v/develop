'''

지금까지 TinyRT는 요청 하나를 처리하는 데 걸리는 시간(지연시간)만 쟀습니다. 실전 서비스는 요청이 한 번에 하나씩 오지 않습니다 — 여러 요청이 동시에 몰릴 때 얼마나 많이 처리할 수 있는지(처리량)가 진짜 질문입니다. 이 장은 link:../../safe-parallel-cpp23/[『이론을 C{pp}23으로 옮기다』]의 안전 기법과 link:../../cpp23-performance-engineering/[『안전을 넘어 성능으로』]의 성능 기법을 다시 꺼내, TinyRT가 요청을 동시에 처리해도 **빠르면서 정확한지** 확인합니다.

== CPU 경로: 스레드 풀로 요청을 나눠 처리하기

9장의 CPU-only 파이프라인은 상태가 없는 순수 함수입니다(입력을 받아 결과를 돌려줄 뿐, 공유 자원을 안 건드립니다) — 그래서 여러 스레드가 동시에 불러도 서로 간섭할 일이 없습니다. 2만 건의 요청을 스레드 개수를 늘려가며 나눠 처리해봅니다.

[source,cpp]
----
std::vector<std::jthread> threads;
int per_thread = N / nthreads;
for (int t = 0; t < nthreads; t++)
  threads.emplace_back([&, per_thread] {
    for (int i = 0; i < per_thread; i++) infer_cpu(input, weights);
  });
// threads가 스코프를 벗어나며 소멸자가 자동으로 join (전작 1장의 std::jthread)
----

[source]
----
$ clang++ -std=c++23 -O2 cpu_concurrent.cpp -o cpu_concurrent && ./cpu_concurrent
single request latency: 0.0272 ms
sequential 20000 requests: 293.15 ms (68223 req/s)
concurrent 2 threads, 20000 requests: 130.76 ms (152956 req/s, 2.24x vs sequential)
concurrent 4 threads, 20000 requests: 73.60 ms (271751 req/s, 3.98x vs sequential)
concurrent 8 threads, 20000 requests: 47.61 ms (420103 req/s, 6.16x vs sequential)
----

4스레드까지는 거의 선형으로 늘고(3.98배), 8스레드에서는 조금 처집니다(6.16배 — 이 세션 환경이 물리 코어 10개라서, 스레드를 늘릴수록 스케줄링 비용과 캐시 경합이 조금씩 늘어납니다). ``std::jthread``를 쓴 이유도 전작과 같습니다 — 소멸자가 자동으로 ``join``하므로, 예외가 나거나 스코프를 일찍 빠져나가도 스레드를 두고 나가는 실수(그리고 그로 인한 정의되지 않은 동작)가 원천 봉쇄됩니다.

== GPU 경로: 커널 오브젝트를 공유하면 무슨 일이 생기는가

CPU 경로는 공유 상태가 없어서 쉬웠습니다. GPU 경로는 다릅니다 — 이 장에서 새로 만드는 ``FcKernelContext``는 4장의 ``GpuContext``(컨텍스트/커맨드 큐를 이동 전용 RAII로 관리)와 5장의 ``GpuConvLayer``(``cl_kernel``까지 클래스 안에 들고 있는 것)를 합친 모양입니다 — 여기서 문제가 되는 건 그 ``cl_kernel``입니다. ``cl_kernel``은 **인자 값을 자기 안에 저장하는 가변 상태**입니다(``clSetKernelArg``로 넣은 값이 그 커널 오브젝트에 남아 있다가, ``clEnqueueNDRangeKernel``이 실행될 때 쓰입니다). 여러 스레드가 같은 커널 오브젝트에 동시에 인자를 설정하면 어떻게 될까요?

[source,cpp]
----
void run_fc_unsafe(FcKernelContext& gpu, const std::vector<float>& in, const std::vector<float>& w,
                    std::vector<float>& out) {
  // ... 버퍼 생성 ...
  clSetKernelArg(gpu.kernel(), 0, sizeof(cl_mem), &in_buf);   // 락 없음
  clSetKernelArg(gpu.kernel(), 1, sizeof(cl_mem), &w_buf);
  // ...
  clEnqueueNDRangeKernel(gpu.queue(), gpu.kernel(), 1, nullptr, &global, nullptr, 0, nullptr, nullptr);
  clEnqueueReadBuffer(gpu.queue(), out_buf, CL_TRUE, 0, out.size()*sizeof(float), out.data(), 0, nullptr, nullptr);
}
----

같은 입력으로 8개 스레드를 동시에 돌리면 — 입력이 전부 같으므로 결과도 전부 같아야 정상입니다.

[source]
----
$ clang++ -std=c++23 -O2 -framework OpenCL gpu_race_unsafe.cpp -o gpu_race_unsafe && ./gpu_race_unsafe
errors (unsynchronized shared queue, 8 threads): 0
all outputs match: false
----

**OpenCL API는 에러를 하나도 안 냅니다.** ``clSetKernelArg``도, ``clEnqueueNDRangeKernel``도 전부 ``CL_SUCCESS``를 돌려줍니다 — 그런데 8개 스레드가 낸 결과를 비교하면 서로 다릅니다. 여러 번 반복 실행해보면 이 결과 자체가 실행마다 다릅니다(어떤 실행은 우연히 다 맞고, 어떤 실행은 틀립니다) — 스레드 A가 인자를 다 설정하기 전에 스레드 B가 자기 인자로 덮어쓰고, A는 그 뒤섞인 상태로 커널을 실행시키는 경쟁 상태(race condition)입니다. 이게 link:../../safe-parallel-cpp23/[전작]이 반복해서 강조한 것과 정확히 같은 위험입니다 — **컴파일도 되고, API 에러도 없고, 대부분은 심지어 맞는 값이 나오다가, 가끔씩만 조용히 틀린 값을 냅니다.**

=== ThreadSanitizer가 이 레이스를 못 잡는 이유

전작이 병렬 버그를 잡을 때 항상 꺼내던 도구를 여기서도 시도해봅니다.

[source]
----
$ clang++ -std=c++23 -O0 -g -fsanitize=thread -framework OpenCL gpu_race_unsafe.cpp -o gpu_race_unsafe_tsan && ./gpu_race_unsafe_tsan
errors (unsynchronized shared queue, 8 threads): 0
all outputs match: true
----

TSan은 아무 경고도 안 냅니다 — 이번엔 결과도 우연히 다 맞았습니다. 이유는 정직하게 짚어야 합니다: ``clSetKernelArg``/``clEnqueueNDRangeKernel``은 애플의 닫힌 소스 OpenCL 프레임워크 안에서 실행되는데, TSan은 자신이 계측(instrument)한 코드의 접근만 추적할 수 있습니다 — 시스템 프레임워크 내부의 상태 변경까지는 보지 못합니다. 이 레이스는 **실재하지만, 이 세션 환경의 TSan으로는 검증할 수 없는** 종류입니다. 그래서 이 장의 정답성 검증은 TSan 리포트가 아니라, **같은 입력을 여러 번 동시 실행해서 결과가 매번 일치하는지 직접 비교**하는 방법을 씁니다 — "도구가 조용하다"와 "안전하다"는 다른 말이라는 걸, 이 장이 몸소 보여준 셈입니다.

== 고치기 1: ``std::scoped_lock``으로 감싸면 — 정답은 돌아오지만

전작이 가장 먼저 배운 도구를 그대로 씁니다.

[source,cpp]
----
void run_fc(const std::vector<float>& in, const std::vector<float>& w, std::vector<float>& out) {
  // ... 버퍼 생성 ...
  {
    std::scoped_lock lock(kernel_mutex_);
    clSetKernelArg(kernel_, 0, sizeof(cl_mem), &in_buf);
    // ... 나머지 인자 설정 ...
    clEnqueueNDRangeKernel(queue_, kernel_, 1, nullptr, &global, nullptr, 0, nullptr, nullptr);
    clEnqueueReadBuffer(queue_, out_buf, CL_TRUE, 0, out.size()*sizeof(float), out.data(), 0, nullptr, nullptr);
  }
}
----

인자 설정부터 결과를 다 읽어올 때까지를 하나의 임계 구역으로 묶었습니다 — 커널 오브젝트의 인자 상태가 "누군가 다 쓸 때까지" 다른 스레드에게 안 보이게 막는 것입니다.

[source]
----
$ clang++ -std=c++23 -O2 -framework OpenCL gpu_race_safe.cpp -o gpu_race_safe && ./gpu_race_safe
trial 0: all outputs match = true
trial 1: all outputs match = true
trial 2: all outputs match = true
trial 3: all outputs match = true
trial 4: all outputs match = true
sequential 2000 fc calls: 897.98 ms (2227 req/s)
concurrent 8 threads, 2000 calls (mutex-protected): 963.73 ms (2075 req/s, 0.93x vs sequential)
----

5번 반복 모두 정답이 일치합니다 — 락이 실제로 레이스를 없앴습니다. 그런데 **처리량은 늘지 않았습니다**(``0.93x``, 오히려 살짝 손해). 이유는 명확합니다 — 임계 구역 안에 인자 설정뿐 아니라 커널 실행과 결과 읽기(``clEnqueueReadBuffer``의 ``CL_TRUE``, 즉 끝날 때까지 블로킹)까지 다 들어가 있어서, 사실상 스레드 8개가 이 함수를 **한 번에 하나씩만** 통과합니다 — 겉보기엔 "동시 실행"인데 실제로는 락 하나가 전부 직렬화하고 있는 것입니다. 이 장이 여기서 멈추면 "정확하지만 병렬화의 의미가 없는" 코드가 됩니다.

== 고치기 2: 스레드마다 독립된 커맨드 큐와 커널

레이스의 진짜 원인은 큐 자체가 아니라 **커널 오브젝트를 공유했다는 것**이었습니다 — 그럼 커널(그리고 그와 짝지어 쓰는 커맨드 큐)을 스레드마다 하나씩 따로 만들면 어떨까요? 같은 ``cl_context``와 ``cl_program``(컴파일된 커널 코드 자체)은 계속 공유하되(둘 다 읽기 전용이라 공유해도 안전합니다), 인자 상태를 갖는 ``cl_kernel``과 그걸 실행시키는 ``cl_command_queue``만 스레드 전용으로 둡니다.

[source,cpp]
----
struct ThreadLocalGpu {
  cl_command_queue queue;
  cl_kernel kernel;      // 스레드마다 독립된 커널 오브젝트 — 인자 상태를 안 나눠 씀
  ThreadLocalGpu(cl_context ctx, cl_device_id dev, cl_program prog) {
    queue = clCreateCommandQueue(ctx, dev, 0, nullptr);
    kernel = clCreateKernel(prog, "fc", nullptr);
  }
  void run_fc(...) { /* 락 없이 그대로, 이제 공유 자원이 없으므로 안전 */ }
};
----

[source]
----
$ clang++ -std=c++23 -O2 -framework OpenCL gpu_per_thread_queue.cpp -o gpu_per_thread_queue && ./gpu_per_thread_queue
per-thread queue/kernel: all outputs match = true
concurrent 8 threads, 2000 calls (per-thread queue): 235.51 ms (8492 req/s)
----

정답도 여전히 맞고(``all outputs match: true``), 처리량은 순차 실행(``2227 req/s``)의 **약 3.8배**, 락으로 막았던 버전(``2075 req/s``)의 **약 4배**입니다. 잠금(lock)이 아니라 **공유 자체를 없애는 것**(전작 link:../../safe-parallel-cpp23/[『이론을 C{pp}23으로 옮기다』] 전체를 관통한 원칙 — "락을 잘 거는 것보다, 애초에 공유 자원을 안 만드는 게 낫다")이 여기서도 정답이었습니다.

== 9장의 ``Ready``는 이 그림에 어떻게 들어맞는가

9장은 ``Ready``가 ``GpuContext`` **하나**(컨텍스트, 큐, 커널 전부 합쳐 하나)를 들고 있는 걸 "GPU 프로그램까지 준비된 상태"의 증거로 삼았습니다. 이 장의 결론(커널·큐는 스레드마다 따로 있어야 안전하다)과 정면으로 맞부딪힙니다 — ``Ready`` 하나가 여러 스레드에서 동시에 ``infer()``를 받는다면, 9장의 설계 그대로는 이 장이 재현한 바로 그 레이스에 걸립니다. 실제로 합치려면 ``Ready``가 ``GpuContext`` 하나 대신 **스레드 수만큼의 ``FcKernelContext``** (또는 요청이 들어올 때마다 풀에서 하나씩 꺼내 쓰는 오브젝트 풀)를 들고 있어야 합니다 — ``Loaded::compile()``이 GPU 프로그램을 한 번만 빌드하고 그 결과(``cl_program``)를 여러 스레드 전용 큐/커널에 나눠주는 형태로 바뀌는 것입니다. 이 책은 그 재설계까지는 하지 않았습니다 — 9장의 타입 상태와 이 장의 동시성 해법은 아직 같은 클래스 안에 합쳐지지 않은, 나란히 검증된 두 조각으로 남아 있습니다.

== 요약

* CPU 경로(상태 없는 순수 함수)는 ``std::jthread`` 풀로 나누기만 해도 8스레드에서 6.16배 처리량이 났습니다.
* 공유된 ``cl_kernel``에 락 없이 동시 접근하면 API 에러 없이 결과만 조용히 틀어진다는 걸 재현했고, 이 레이스가 시스템 프레임워크 내부 상태라서 ThreadSanitizer로는 검증되지 않는다는 것도 정직하게 확인했습니다 — 결과를 직접 대조하는 것만이 이 경우의 유일한 검증 수단이었습니다.
* ``std::scoped_lock``으로 임계 구역을 감싸면 정답은 돌아오지만, 임계 구역이 너무 넓어서(인자 설정+실행+결과 읽기 전부) 사실상 직렬화되어 처리량이 그대로였다는 것도 실측으로 확인했습니다.
* 스레드마다 독립된 커맨드 큐와 커널 오브젝트로 애초에 공유 자원을 없애자, 정답을 유지하면서 락 버전 대비 4배 처리량을 얻었습니다 — "잠그기"보다 "안 나누기"가 이겼습니다.
* 9장의 ``Ready``가 ``GpuContext`` 하나만 들고 있는 설계로는 이 장의 동시성 해법(스레드별 큐/커널)을 그대로 못 담는다는 것도 정직하게 짚었습니다 — 실제로 합치려면 ``Ready``가 스레드별 자원 풀을 들고 있도록 재설계해야 하는데, 이 책은 거기까지는 하지 않았습니다.

맺음말에서는 이 장까지 포함해 TinyRT 전체가 확인한 것을 다시 정리합니다.

== 팁 박스: 이 장이 검증하지 않은 것

이 장은 **추론 전용**(파라미터를 안 바꾸는) 상황만 다뤘습니다. 학습처럼 파라미터를 실제로 갱신하면서 동시에 추론도 해야 하는 상황(예: 온라인 학습)은 이 장의 결론이 그대로 적용되지 않습니다 — 그 경우엔 link:../../cpp23-performance-engineering/05-atomic-ref-progress/[전작의 ``atomic_ref``]나, 갱신 중에는 추론을 잠시 막는 읽기-쓰기 락 같은 추가 장치가 필요합니다.
