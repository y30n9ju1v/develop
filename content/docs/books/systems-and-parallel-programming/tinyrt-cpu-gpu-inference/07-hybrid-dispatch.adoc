== 전체 파이프라인을 CPU-only와 Hybrid로 나란히

TinyRT의 작은 CNN(입력 `66×66`, 3×3 컨볼루션+ReLU, 2×2 맥스풀, 완전연결, 소프트맥스)을 두 가지 방식으로 실행합니다 — 모든 레이어를 CPU로만 돌리는 버전과, 컨볼루션과 완전연결을 GPU로 보내는 버전(맥스풀·소프트맥스는 계산량이 작아 CPU에 남겨둡니다).

[source]
----
$ clang++ -std=c++23 -O2 -framework OpenCL full_pipeline.cpp -o full_pipeline && ./full_pipeline
CPU-only:  0.035 ms
Hybrid:    2.850 ms
max softmax diff CPU vs Hybrid: 0
----

**CPU-only가 80배 넘게 빠릅니다.** 출력(소프트맥스 확률 분포)은 정확히 일치하므로 GPU 경로가 틀린 건 아닙니다 — 그저 이 모델 크기에서는 GPU로 보내는 비용 자체가 손해입니다. `Hybrid` 시간 안에는 OpenCL 컨텍스트/프로그램 준비, 버퍼 생성과 호스트↔디바이스 복사, 커널 디스패치가 전부 들어 있는데, 이 모델의 계산량(`64×64` 컨볼루션 한 번, `1024×16` 행렬곱 한 번)은 그 고정 비용을 상쇄할 만큼 크지 않습니다.

== 같은 완전연결 레이어를 훨씬 크게 키우면

계산량이 아니라 정말로 오버헤드 때문인지 확인하려면, 같은 종류의 레이어를 계산량만 훨씬 키워서 다시 재보면 됩니다. 6장에서 쓴 `512×512×512` 크기의 행렬곱(완전연결 레이어를 그 정도로 키운 것과 같습니다)을 CPU 나이브 삼중 루프로 돌려봅니다.

[source]
----
$ clang++ -std=c++23 -O2 cpu_matmul_512.cpp -o cpu_matmul_512 && ./cpu_matmul_512
CPU naive matmul 512^3: 117.96 ms (C[0]=12196.75)
----

6장에서 이미 잰 GPU 타일링 버전(`0.876ms`)과 비교하면, 이번엔 **GPU가 130배 넘게 빠릅니다.** 같은 종류의 레이어인데 크기 하나 바뀌었다고 승자가 완전히 뒤집혔습니다 — 이게 이 장이 증명하려는 핵심입니다: **GPU가 유리한지는 레이어 종류가 아니라 그 레이어의 실제 계산량에 달려 있고, 그 경계는 미리 짐작하지 말고 실측해야 합니다.**

== `flat_map` 레지스트리로 레이어별 실행 위치 정하기

전작 link:../../cpp23-performance-engineering/[『안전을 넘어 성능으로』] 8장의 ``std::flat_map``으로, 레이어 이름과 그 레이어가 실행될 장치를 묶는 레지스트리를 만듭니다.

[source,cpp]
----
enum class Device { CPU, GPU };

class LayerRegistry {
  std::flat_map<std::string, Device> placement_;
public:
  void place(std::string layer_name, Device device) {
    placement_[std::move(layer_name)] = device;
  }
  Device device_of(const std::string& layer_name) const {
    return placement_.at(layer_name);
  }
};
----

레지스트리 자체는 단순합니다 — 진짜 문제는 ``place()``를 어떤 기준으로 부르느냐입니다. 이 장의 결론대로, TinyRT는 레이어 종류가 아니라 **그 레이어의 실제 입력 크기로 계산한 예상 연산량**을 기준 삼습니다.

[source,cpp]
----
Device choose_device(std::size_t estimated_flops) {
  // 6~7장의 실측 교차점: 이 정도 연산량 아래에서는 GPU 디스패치 비용이
  // 계산 이득을 넘어선다는 걸 이 세션 환경에서 직접 쟀습니다.
  constexpr std::size_t kGpuBreakEvenFlops = 50'000'000;  // 5천만 FLOP 안팎
  return estimated_flops >= kGpuBreakEvenFlops ? Device::GPU : Device::CPU;
}
----

``kGpuBreakEvenFlops``는 이론값이 아니라, 이 장 앞부분의 실측(작은 모델 전체 ≈ ``1.3M FLOP``대에서 CPU 승, ``512³×2 ≈ 268M FLOP``에서 GPU 승) 사이 어딘가에 그은 실용적인 경계선입니다 — 정확한 경계를 찾으려면 이 사이의 여러 크기에서 실제로 더 재봐야 하지만, 이 책의 작은 CNN과 훨씬 큰 완전연결 레이어를 가르는 데는 이 정도로 충분합니다.

== ``atomic_ref``로 레이어별 실행 시간 기록하기

전작 5장의 ``atomic_ref``를 재사용해, 여러 레이어를 병렬로 미리 보정(calibration)할 때 —즉 "이 레이어를 CPU로 돌리면 몇 ms, GPU로 돌리면 몇 ms인지" 여러 후보를 동시에 재는 단계에서— 결과를 락 없이 기록합니다.

[source,cpp]
----
class Calibrator {
  std::vector<double> gpu_times_ms_;  // 레이어 인덱스별 GPU 실측 시간
public:
  explicit Calibrator(std::size_t num_layers) : gpu_times_ms_(num_layers, 0.0) {}

  void record_gpu_time(std::size_t layer_idx, double ms) {
    // double은 atomic_ref로 안전하게 store할 수 있다 (읽는 쪽도 atomic_ref를 써야 함, 7장의 안전 조건)
    std::atomic_ref<double>(gpu_times_ms_[layer_idx]).store(ms);
  }
  double gpu_time_of(std::size_t layer_idx) {
    return std::atomic_ref<double>(gpu_times_ms_[layer_idx]).load();
  }
};
----

여러 워커 스레드가 서로 다른 레이어를 동시에 보정하며 각자 자기 인덱스에만 기록하므로, 전작 5장과 똑같은 이유로 락이 필요 없습니다 — 인덱스별 ``atomic_ref``가 그 순간의 원자성만 보장하면 충분합니다.

== 요약

* 작은 CNN 전체를 CPU-only와 Hybrid GPU로 나란히 벤치마크해서, 이 모델 크기에서는 **CPU가 80배 넘게 빠르다**는 걸 확인했습니다 — GPU 디스패치 오버헤드(컨텍스트 준비, 버퍼 복사, 커널 실행)가 계산 이득보다 큽니다.
* 같은 종류의 레이어(행렬곱)를 계산량만 크게 키우면 승자가 뒤집혀 **GPU가 130배 넘게 빠르다**는 것도 실측으로 확인했습니다 — 레이어 종류가 아니라 실제 계산량이 기준이라는 걸 보여줍니다.
* `std::flat_map` 레지스트리로 레이어별 실행 장치를 관리하고, 이 장의 실측 교차점을 근거로 한 계산량 기준(`choose_device`)으로 배치를 정하는 구조를 만들었습니다.
* ``atomic_ref``로 여러 레이어의 GPU 보정 시간을 락 없이 동시에 기록하는 법도 전작 5장을 그대로 재사용했습니다.
