== 이 책이 지은 것

1부에서 `maturin new`로 PyO3 프로젝트를 셋업하고, `riir-json-parser`의 파서를 가져와 `Cow<str>`로 이스케이프까지 정직하게 처리하며 파이썬 `dict`/`list`로 재귀 변환하는 함수를 짰습니다(1~2장). 2부에서는 Rust의 `Result`를 파이썬 `ValueError`로 매핑해 실제 예외 처리 흐름을 만들고, 5만 개짜리 배열로 파이썬 표준 `json`과 정확성이 일치한다는 걸 확인했습니다(3~4장). 3부가 이 책의 핵심이었습니다 — `release` 빌드로 처음 잰 벤치마크에서 파이썬 표준 `json`이 오히려 19% 더 빨랐다는 걸 그대로 실었고(5장), 파싱과 파이썬 객체 변환을 실측으로 쪼개 진짜 병목이 파싱(9.9ms, 오히려 파이썬보다 훨씬 빠름)이 아니라 파이썬 객체를 만드는 비용(약 14ms)이라는 걸 찾아냈습니다(6장). 그리고 GIL을 실제로 다뤄, 기본 상태(GIL 유지)에서는 4스레드가 0.99배(사실상 무의미)였던 게 `Python::detach`로 GIL을 놓자 3.14배로 뛰는 걸 확인했습니다(7장). 4부에서는 `pyproject.toml`을 다듬고 `maturin build`로 wheel을 만들어(8장), Rust 컴파일러가 전혀 없는 새 가상환경에 설치해 정말 독립적으로 동작하는지 검증하고(9장), `abi3`로 파이썬 버전 여러 개를 wheel 하나로 커버하는 것까지 실제로 확인했습니다(10장).

== 이 책이 확인한 것: 두 개의 다른 "느림"

이 책은 실은 서로 다른 두 가지 "언어 경계를 넘는 비용"을 확인했습니다. 하나는 5~6장의 **PyObject 생성 비용**입니다 — Rust 코어 로직 자체는 여전히 빨랐지만(파이썬 `json`의 절반 이하), 그 결과를 파이썬 객체로 옮기는 순간 이점이 사라지고 오히려 역전됐습니다. 다른 하나는 7장의 **GIL**입니다 — 파이썬 객체를 만들지 않는 순수 계산 구간은 GIL을 놓아 진짜 병렬성을 얻을 수 있었지만, PyObject를 만드는 구간(6장)은 애초에 GIL 없이는 할 수 없는 일이라 이 최적화가 적용되지 않습니다. 두 발견을 합치면 하나의 그림이 됩니다 — **이 파서를 파이썬에서 정말 빠르게 쓰려면, "Rust로 파싱한 결과를 파이썬 객체로 전부 바꾸는" 지금의 설계 자체를 재고해야 한다**는 것입니다(예를 들어 필요한 필드만 지연 변환하거나, PyObject 대신 파이썬이 이해하는 다른 표현으로 넘기는 방법들이 있을 수 있습니다) — 이건 이 책이 진단은 했지만 풀지는 않은 다음 과제입니다.

== 이 책이 다루지 않은 것

* **6장에서 찾은 PyObject 생성 비용을 실제로 줄이는 시도** — 병목을 진단만 하고, 고쳐서 다시 재보지는 않았습니다. `riir-json-parser` 10장이 원인을 찾은 뒤 실제로 고쳐서 검증까지 했던 것과 달리, 이 책은 진단에서 멈췄습니다.
* **운영체제·아키텍처별 빌드와 CI 자동화** — 10장에서 밝혔듯 이 세션은 macOS/arm64 하나에서만 검증했습니다. Linux, Windows, x86_64용 빌드나 `maturin-action` 기반 CI 매트릭스는 다루지 않았습니다.
* **PyPI 공개 배포** — 9장에서 로컬 wheel 설치까지만 검증했고, 실제 공개 배포 절차(`twine`/`maturin publish`, 되돌리기 어려운 공개 행위)는 의도적으로 범위 밖에 뒀습니다.
* **`#[pyclass]`로 파서 자체를 파이썬 클래스로 노출하기** — 이 책은 함수 하나(`parse_json`)만 노출했습니다. 파서 상태를 유지하며 스트리밍으로 파싱하는 클래스 기반 API는 다루지 않았습니다.

== 다음 단계

이 책이 준 가장 큰 교훈은 `riir-json-parser`의 교훈과 정확히 같은 모양입니다 — **"빠른 코어 언어로 짰다"는 사실이, 그걸 호출하는 전체 파이프라인의 속도를 보장하지 않는다**는 것입니다. 다른 언어에서 온 값을 받거나 돌려주는 경계(이 책의 경우 PyObject 변환)가 새로운 병목이 될 수 있다는 걸 실측으로 확인했습니다. 다음으로 볼 만한 방향은 6장의 병목을 실제로 줄여보는 것(예: `orjson` 같은 실전 라이브러리가 이 문제를 어떻게 풀었는지 코드를 읽어보는 것), `#[pyclass]`로 상태를 가진 파서를 만들어보는 것, 혹은 실제 CI 매트릭스로 여러 플랫폼 wheel을 자동 빌드해보는 것입니다.
