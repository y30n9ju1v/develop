'''

== 이 책이 지은 것

1부에서 JSON 값을 `enum`으로 모델링하고, 일부러 안전하지 않게 짠 첫 파서가 잘린 입력에서 실제로 크래시하는 걸 확인했습니다. 2부에서는 이 문제를 정면으로 풀었습니다 — 라이프타임을 명시해 복사 없는 슬라이스를 안전하게 돌려주고(3장), `Result`와 `?`로 크래시 대신 명확한 에러를 전파하고(4장), 배열·객체까지 완성해 `cargo test`로 검증했습니다(5장). 3부에서는 `Display` 트레잇으로 직렬화를 완성하고(6장), 클로저와 이터레이터 콤비네이터로 JSON 트리를 함수형 스타일로 변환했습니다(7장) — 서문에서 예고한 함수형 프로그래밍과의 연결이 여기서 실제 코드로 확인됐습니다. 4부에서는 C의 `cJSON`과 정면으로 대조했습니다 — 정확성은 일치했지만(8장), 첫 벤치마크에서는 **C가 16% 더 빨랐습니다**(9장). 여기서 멈추지 않고, `cpp23-performance-engineering` 책의 기법(PMR 아레나, 정렬 없는 flat 컬렉션, 제로카피 `string_view`)을 C++23으로 재현해 C와 동률까지 따라잡은 뒤, 같은 설계를 Rust에도 그대로 적용하자 Rust가 C와 C++23 둘 다보다 약 2배 빨라졌습니다. 그 2배라는 숫자에 만족하지 않고 더 파고들어, 문자 분류 함수와 PMR 제거라는 그럴듯한 가설 두 개를 실측으로 기각한 뒤, 프로그램을 읽기/파싱 단계로 쪼개 진짜 원인이 **C++23의 파일 읽기 방식**(`std::ostringstream`)이었다는 걸 찾아냈고, 고치자 격차가 2.05배에서 1.22배로 줄었습니다(10장) — 그리고 빌림 체커가 실제로 막아준 댕글링 참조 버그를 재현했습니다(11장). 5부에서는 `rayon`과 `Arc`로 안전하게 병렬 파싱해 약 4.9배의 실측 속도 향상을 얻었고(12장), 동기화 없는 병렬 코드가 네 가지 다른 컴파일 에러로 거부되는 걸 확인했습니다(13장).

== 서문의 주장이 실제로 확인됐는가

서문은 "Rust의 속도는 병렬처리 때문이 아니라 GC 없는 메모리 안전 때문이고, Fearless Concurrency는 별도의 추가 이점"이라고 주장했습니다. 이 책의 실측이 이 주장을 뒷받침하되, 예상보다 훨씬 굴곡진 과정을 거쳐 확인됐습니다 — 9장에서 첫 버전 Rust는 C보다 느렸지만, 그 차이는 언어의 한계가 아니라 설계 선택(해시맵, 문자열 할당)의 결과였습니다. 10장에서 그 설계를 C++23과 맞추자 Rust가 앞섰는데, 이번엔 그 승리의 이유조차 처음 짐작(`std::variant`, PMR)과 달랐습니다 — 진짜 이유는 파서 로직과 무관한, C++ 쪽의 파일 읽기 방식이었습니다. 두 언어의 **파싱 로직 자체**는 최종적으로 거의 동률(10.4ms vs 9.6ms)이었습니다. 즉 "GC 없는 메모리 안전이 속도의 상한을 낮추지 않는다"는 주장은 확인됐지만, 그 확인 과정 자체가 이 책의 더 중요한 교훈이 됐습니다 — **벤치마크 숫자 하나를 언어의 우열로 성급하게 해석하면 안 된다**는 것입니다. 그리고 13장에서 데이터 경쟁을 일으키는 코드는 Rust에서 애초에 컴파일조차 되지 않았습니다 — 속도와 병렬 안전성은 서로 다른 축이라는 게, 추상적인 주장이 아니라 이 책 안의 실제 벤치마크와 실제 컴파일 에러로 드러났습니다.

== 이 책이 다루지 않은 것

* **표준 완전 준수** — 이 책의 파서는 유니코드 이스케이프(`\uXXXX`), 지수 표기의 모든 경계 케이스, 깊은 중첩에 대한 스택 오버플로 방지 같은 RFC 8259의 세부 사항을 전부 구현하지 않았습니다. 10장의 최적화 버전은 이스케이프 처리 자체를 아예 생략했습니다(공정 비교를 위한 축소였다는 걸 그 장에서 명시했습니다). `cJSON`은 이런 부분에서 훨씬 성숙합니다.
* **남은 1.22배 격차를 명령어 수준까지 확정하기** — 파일 읽기 문제를 고친 뒤에도 C++23이 Rust보다 근소하게 느린데, 이게 `std::variant`의 태그 접근 방식인지 `std::pmr::vector`의 성장 전략인지는 `perf`나 `flamegraph` 없이는 확정할 수 없어 그럴듯한 추정으로 남겼습니다.
* **`unsafe` Rust** — `simdjson` 같은 프로젝트가 쓰는 SIMD 가속이나, 안전성 검사를 우회하는 저수준 최적화는 이 책의 범위 밖입니다.
* **`serde`와의 비교** — Rust 생태계의 사실상 표준 직렬화 프레임워크인 `serde_json`이 이 책의 손으로 짠 파서와 어떻게 다른지(매크로 기반 코드 생성, 스트리밍 파싱 등)는 다루지 않았습니다.

== 다음 단계

RIIR을 실제로 해보고 싶다면, 이 책이 준 가장 큰 교훈은 두 가지입니다. 하나는 "다시 쓰기 전에 벤치마크 기준선을 먼저 만들고, 실망스러운 결과가 나와도 거기서 멈추지 말라"는 것 — 9장의 첫 결과만 보고 멈췄다면 "Rust가 딱히 안 빠르다"는 잘못된 결론으로 끝났을 것입니다. 다른 하나는 "좋은 결과가 나와도 그 이유를 검증 없이 믿지 말라"는 것 — 10장에서 Rust가 이긴 이유를 처음엔 파서 설계 차이라고 짐작했지만, 실제로는 파서와 무관한 파일 읽기 방식이었습니다. 두 경우 모두 **추측을 멈추고 프로그램을 쪼개 실제로 재보는 것**이 정답이었습니다. 다음으로 볼 만한 방향은 이 책의 파서를 `serde_json`과 비교해보는 것, `perf`로 남은 1.22배 격차를 명령어 수준까지 프로파일링해보는 것, 혹은 유니코드 이스케이프 같은 표준 준수 항목을 하나씩 채워나가는 것입니다.
