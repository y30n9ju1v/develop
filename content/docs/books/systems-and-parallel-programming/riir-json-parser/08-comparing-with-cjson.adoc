4부에서는 이 책이 만든 Rust 파서를 C의 대표 JSON 라이브러리 `cJSON`과 나란히 놓고 검증합니다. 먼저 정확성부터입니다.

== 같은 입력, 같은 결과인가

[source,c]
----
// c_ref/main.c
#include <cjson/cJSON.h>

int main() {
    const char *json = "[1,2,{\"a\":true,\"b\":null}]";
    cJSON *parsed = cJSON_Parse(json);
    char *out = cJSON_PrintUnformatted(parsed);
    printf("%s\n", out);
    free(out);
    cJSON_Delete(parsed);
    return 0;
}
----

[source]
----
$ clang -I/opt/homebrew/opt/cjson/include -L/opt/homebrew/opt/cjson/lib -lcjson main.c -o main
$ ./main
[1,2,{"a":true,"b":null}]
----

같은 입력을 6장에서 만든 Rust 파서 + `Display`로도 처리해봅니다.

[source]
----
$ cargo run
파싱->직렬화: [1,2,{"a":true,"b":null}]
----

문자 그대로 동일합니다 — 키 순서(`a`, `b`)까지 우연히 일치했습니다(`HashMap`은 순서를 보장하지 않으므로, 이건 이 실행에서 그렇게 나왔다는 것이지 항상 보장되는 성질은 아닙니다).

== 대용량 파일로도 확인하기

5만 개짜리 객체 배열(약 4.3MB)을 만들어, 양쪽 모두 배열 길이를 세게 했습니다.

[source]
----
$ ./target/release/parse_file big.json
파싱된 배열 길이: 50000

$ ./c_ref/parse_file big.json
파싱된 배열 길이: 50000
----

두 구현이 5만 개짜리 배열에 대해서도 정확히 같은 개수를 세었습니다 — 작은 예제뿐 아니라 실제 크기의 파일에서도 두 파서가 같은 것을 같은 방식으로 이해한다는 걸 확인했습니다.

== 이 비교가 증명하지 않는 것

이 장이 확인한 건 "이 두 특정 입력에 대해 결과가 일치한다"는 것뿐입니다 — `cJSON`은 RFC 8259 표준을 훨씬 폭넓게 준수하는 성숙한 라이브러리(유니코드 이스케이프, 다양한 숫자 형식의 경계 케이스 등)이고, 이 책의 파서는 그 일부만 구현했습니다. 정확성 비교는 "같은 입력 집합에서 같은 결과가 나온다"까지만 말해줄 뿐, "이 파서가 표준을 완전히 준수한다"는 걸 증명하지 않습니다 — 이 한계는 13장에서 다시 정리합니다.

== 요약

* 작은 예제(`[1,2,{"a":true,"b":null}]`)와 5만 개짜리 대용량 배열 양쪽 모두, C의 `cJSON`과 이 책의 Rust 파서가 정확히 같은 결과를 낸다는 걸 실제로 컴파일·실행해 확인했습니다.
* 이 일치가 "표준 완전 준수"를 뜻하지 않는다는 것도 정직하게 밝혔습니다 — 이 책의 파서는 `cJSON`이 다루는 경계 케이스의 일부만 구현했습니다.

다음 장에서는 이 두 구현의 속도를 `hyperfine`으로 실측합니다 — 결과가 항상 예상대로 나오지는 않습니다.
