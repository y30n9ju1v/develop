성능을 재기 전에, 정확성부터 확인합니다 — 8장에서 `cJSON`과 비교했던 것과 같은 원칙입니다.

== 같은 파일, 두 파서

[source,python]
----
import json, riirjson

with open("big.json") as f:
    text = f.read()

py_result = json.loads(text)
rust_result = riirjson.parse_json(text)

print("길이 일치:", len(py_result) == len(rust_result))
print("첫 원소 일치:", py_result[0] == rust_result[0])
----

[source]
----
$ python check_correctness.py
길이 일치: True
첫 원소 일치: True
----

5만 개짜리 객체 배열(8~9장에서 썼던 것과 같은 생성 데이터)을 양쪽에 넣었더니, 원소 개수와 내용이 정확히 일치했습니다. 파이썬의 `==` 비교가 `dict`/`list`까지 재귀적으로 비교해주므로, `py_result[0] == rust_result[0]`이 `True`라는 건 첫 객체의 모든 필드(`id`, `name`, `active`, `score`, `tags`)가 타입까지 정확히 일치한다는 뜻입니다.

== 숫자 타입에 대한 주의

파이썬의 `json.loads`는 정수처럼 보이는 숫자(`42`)를 실제 `int`로, 소수점이 있는 숫자(`3.5`)를 `float`로 구분해서 돌려줍니다. 반면 이 책의 `riirjson.parse_json`은 `Value::Number(f64)`를 그대로 쓰므로, **모든 숫자가 `float`로 나옵니다**(`42`도 `42.0`이 됩니다) — 16장의 실행 예시에서 `[1.0, 2.0, ...]`으로 나온 게 이 때문입니다. `py_result[0] == rust_result[0]`이 그럼에도 `True`인 이유는, 파이썬에서 `42 == 42.0`이 `True`이기 때문입니다(값 비교가 타입을 가리지 않습니다) — 다만 `type(py_result[0]["id"]) == type(rust_result[0]["id"])`처럼 타입까지 비교하면 다를 수 있습니다. 이건 이 책의 파서가 JSON 표준(숫자는 그냥 "숫자"이지 정수/실수 구분이 없습니다)을 따른 결과이지 버그는 아니지만, 파이썬 라이브러리로 배포한다면 사용자에게 문서로 분명히 밝혀야 할 차이입니다.

== 요약

* 5만 개짜리 배열을 파이썬 표준 `json.loads`와 `riirjson.parse_json` 양쪽에 넣어, 길이와 내용이 정확히 일치한다는 걸 확인했습니다.
* 이 책의 파서가 모든 숫자를 `float`로 돌려준다는 것(JSON 표준을 그대로 따른 결과)과, 파이썬의 값 비교(`==`)가 이 차이를 가려서 `True`가 나온다는 것도 정직하게 짚었습니다.
