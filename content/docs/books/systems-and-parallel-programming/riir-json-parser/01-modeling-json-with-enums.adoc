JSON 표준(RFC 8259)이 정의하는 값은 정확히 여섯 종류입니다 — `null`, 불리언, 숫자, 문자열, 배열, 객체. C의 `cJSON`은 이걸 태그가 붙은 `union`(`cJSON_Type`이라는 정수 필드로 어느 종류인지 표시)으로 표현합니다. Rust는 이걸 훨씬 직접적으로 표현할 수 있는 언어 기능을 갖고 있습니다.

== `enum`으로 여섯 종류를 표현하기

[source,rust]
----
use std::collections::HashMap;

#[derive(Debug, Clone, PartialEq)]
pub enum Value {
    Null,
    Bool(bool),
    Number(f64),
    String(String),
    Array(Vec<Value>),
    Object(HashMap<String, Value>),
}
----

C의 태그된 유니온과 근본적으로 같은 아이디어지만, C에서는 "지금 이 값이 `Bool`인데 실수로 `.number` 필드를 읽는" 실수를 컴파일러가 막아주지 않습니다 — 태그(타입 필드)와 실제로 저장된 데이터가 일치하는지는 프로그래머가 직접 책임져야 합니다. Rust의 `enum`은 각 변형(variant)이 자기만의 데이터를 직접 갖고 있어서, `Value::Bool(true)`라는 값에서 `Number`의 `f64`를 꺼내려는 코드는 애초에 컴파일되지 않습니다 — 나중에 4장에서 패턴 매칭으로 이 값들을 다룰 때 이 안전성이 실제로 어떻게 작동하는지 봅니다.

`Array(Vec<Value>)`와 `Object(HashMap<String, Value>)`처럼 `Value`가 자기 자신을 담는 재귀적 정의도 문제없이 컴파일됩니다 — `Vec`과 `HashMap`이 내부적으로 힙에 데이터를 저장하기 때문에, `Value` 자체의 크기가 무한히 커지는 문제(재귀적 구조체를 값으로 직접 담으면 생기는 문제)가 생기지 않습니다.

== `#[derive(...)]`가 실제로 만들어주는 것

`#[derive(Debug, Clone, PartialEq)]`는 파생 매크로입니다 — `Value`에 대해 세 가지 트레잇 구현을 컴파일러가 자동으로 만들어줍니다.

* `Debug` — `{:?}` 형식으로 값을 출력할 수 있게 해줍니다(`println!("{:?}", value)`).
* `Clone` — `.clone()`으로 깊은 복사본을 만들 수 있게 해줍니다.
* `PartialEq` — `==`로 두 `Value`가 같은지 비교할 수 있게 해줍니다(중첩된 `Array`/`Object`까지 재귀적으로 비교합니다).

이 세 가지를 손으로 구현하려면 각각 `match`로 여섯 변형을 전부 처리하는 코드를 짜야 합니다 — `derive`는 그 반복적인 코드를 컴파일 타임에 대신 생성해줍니다. 5장에서 테스트를 짤 때 `assert_eq!(parsed, expected)`가 그냥 동작하는 이유가 바로 이 `PartialEq` 파생입니다.

== 요약

* JSON의 여섯 가지 값 종류를, C의 태그된 유니온과 달리 컴파일러가 태그-데이터 불일치를 원천 차단하는 Rust `enum`으로 표현했습니다.
* `Value`가 `Vec`/`HashMap`을 통해 자기 자신을 재귀적으로 담을 수 있다는 것도 확인했습니다.
* `#[derive(Debug, Clone, PartialEq)]`가 반복적인 트레잇 구현 코드를 컴파일 타임에 자동 생성해준다는 것도 짚었습니다 — 이 파생들은 뒤에 나올 거의 모든 장에서 그대로 쓰입니다.

다음 장에서는 이 `Value` 타입을 실제로 채우는 가장 단순한 — 그리고 일부러 안전하지 않게 짠 — 첫 번째 파서를 만듭니다.
