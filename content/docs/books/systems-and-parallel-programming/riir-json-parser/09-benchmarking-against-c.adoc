서문에서 예고한 대로, 이 장의 결과는 "Rust가 당연히 이긴다"는 기대와 다르게 나왔습니다. 미리 밝혀두는 게 정직합니다.

== 벤치마크 설정

`--release`로 최적화 빌드한 Rust 바이너리와, `-O2`로 최적화한 C 바이너리 양쪽에 8장의 5만 개짜리 배열(`big.json`, 약 4.3MB)을 10번 이상 반복해서 파싱시켰습니다.

[source]
----
$ hyperfine --warmup 3 \
    -n "rust (재귀 하강, HashMap)" "./target/release/parse_file big.json" \
    -n "c (cJSON)" "./c_ref/parse_file big.json"
----

== 결과

[source]
----
Benchmark 1: rust (재귀 하강, HashMap)
  Time (mean ± σ):      30.9 ms ±   0.6 ms    [User: 25.2 ms, System: 5.0 ms]
  Range (min … max):    29.8 ms …  34.6 ms    92 runs

Benchmark 2: c (cJSON)
  Time (mean ± σ):      26.5 ms ±   1.2 ms    [User: 23.2 ms, System: 2.9 ms]
  Range (min … max):    25.3 ms …  36.0 ms    104 runs

Summary
  c (cJSON) ran
    1.16 ± 0.06 times faster than rust (재귀 하강, HashMap)
----

**C의 `cJSON`이 이 책의 Rust 파서보다 16% 더 빨랐습니다.** 이건 실제로 측정한 결과이고, 고치지 않고 그대로 싣습니다.

== 왜 이런 결과가 나왔을까

몇 가지 그럴듯한 원인이 있습니다.

* **`cJSON`은 수년간 다듬어진 성숙한 라이브러리**이고, 이 책의 파서는 이 세션에서 처음 짠 코드입니다. "Rust로 짰다"는 것 자체가 속도를 보장하지 않습니다 — 알고리즘과 구현의 완성도가 언어보다 훨씬 크게 작용합니다.
* **`std::collections::HashMap`은 기본적으로 DoS 공격에 강한 해시 함수(SipHash)를 씁니다** — 이건 신뢰할 수 없는 입력을 다룰 때는 안전한 선택이지만, 이 벤치마크의 객체들처럼 필드가 2~4개뿐인 작은 맵에서는 해시 계산 자체의 오버헤드가 상대적으로 크게 작용할 수 있습니다. `cJSON`은 애초에 해시맵이 아니라 연결 리스트로 객체 필드를 저장합니다 — 필드가 적을 때는 이쪽이 더 유리할 수 있습니다.
* **문자열마다 `String`을 새로 할당**합니다(3장에서 라이프타임을 다뤘지만, 최종 `Value`는 `String`을 소유하는 구조로 남겨뒀습니다) — `cJSON`도 문자열을 복사하지만, 할당자 자체의 특성 차이가 있을 수 있습니다.

이 원인들 중 무엇이 실제로 지배적인지는 이 책에서 프로파일링까지 하지는 않았습니다 — "Rust가 C보다 느렸다"는 결과 자체를 정직하게 보고하는 것과, "왜 그런지 확정적으로 안다"고 주장하는 것은 다른 일입니다.

== 이 결과가 이 책의 결론을 뒤집는가

아닙니다 — 이 책의 핵심 주장은 "Rust가 항상 더 빠르다"가 아니라 "Rust는 안전을 위해 속도를 크게 희생하지 않는다"는 것이었습니다. 16% 차이는 "크게 희생"하는 수준이 아니라, 성숙도가 다른 두 구현체 사이의 정상적인 편차에 가깝습니다. 오히려 이 결과는 RIIR을 하려는 사람에게 실용적인 교훈을 줍니다 — **"Rust로 다시 쓰면 자동으로 빨라진다"는 기대 없이, 실제로 벤치마크해서 확인해야 한다**는 것입니다.

== 요약

* 5만 개짜리 배열 파싱에서 C의 `cJSON`이 이 책의 Rust 파서보다 실측 16%(`1.16배`) 더 빨랐다는 결과를 그대로 실었습니다.
* `HashMap`의 해시 알고리즘, 문자열 할당 방식, 그리고 무엇보다 `cJSON`의 성숙도 차이를 그럴듯한 원인으로 짚었지만, 확정적으로 프로파일링하지는 않았다는 것도 밝혔습니다.
* "RIIR을 하면 자동으로 빨라진다"는 기대를 이 결과가 직접 반박합니다 — 실제로 벤치마크해서 확인하는 것이 항상 필요합니다.

이 결과로 끝내지 않고, 다음 장에서는 실제로 원인을 하나씩 손봐서 다시 벤치마크합니다.
