9장은 원인을 **진단만 하고** 멈췄습니다 — `HashMap`의 해시 알고리즘, 문자열마다의 `String` 할당을 그럴듯한 원인으로 짚었지만, 실제로 고쳐서 다시 재보지는 않았습니다. 이 장에서 그 진단이 맞는지 직접 확인합니다.

== 먼저 C++23으로 가설을 검증한다

이 시리즈의 다른 책 `cpp23-performance-engineering`이 다룬 기법 셋을 그대로 적용한 C++23 버전을 만들었습니다.

* **PMR 아레나**(그 책 7장) — `std::pmr::monotonic_buffer_resource`로 모든 `Value`·벡터 할당을 하나의 아레나에서 순서대로 떼어줍니다. `malloc`/`free`를 값마다 부르는 대신, 할당은 포인터를 앞으로 미는 수준이고 해제는 아레나가 통째로 사라질 때 한 번뿐입니다.
* **flat 컬렉션**(그 책 8장의 `flat_map` 교훈) — 객체를 해시맵이 아니라 정렬 없는 `std::pmr::vector<std::pair<...>>`로 저장합니다. `cJSON`도 정확히 이 방식(연결 리스트)입니다 — 필드가 2~4개뿐인 작은 객체에서는 해시 계산보다 선형 탐색이 더 쌉니다.
* **`string_view`로 제로카피** — 이스케이프 없는 문자열은 원본 버퍼를 그대로 가리키고, 복사하지 않습니다.

[source]
----
$ hyperfine --warmup 5 --min-runs 30 \
    -n "c (cJSON)" "./c_ref/parse_file big.json" \
    -n "c++23 (PMR+flat vector+string_view)" "./cpp23/parse_file big.json"

Benchmark 1: c (cJSON)                                        28.4 ms
Benchmark 2: c++23 (PMR+flat vector+string_view)              28.8 ms

Summary
  c (cJSON) ran
    1.01 ± 0.04 times faster than c++23 (PMR+flat vector+string_view)
----

C++23 버전이 `cJSON`과 사실상 동률(1.01배 차이, 오차 범위 안)까지 따라잡았습니다 — 9장의 진단이 맞았다는 뜻입니다. `cJSON`이 빨랐던 건 "C라서"가 아니라, 아레나 할당·flat 저장·제로카피라는 **설계** 덕분이었습니다.

== 같은 설계를 Rust로

이제 같은 세 가지를 Rust에 적용합니다. `Value`를 라이프타임을 가진 버전으로 다시 정의합니다 — 3장에서 이미 다룬 패턴을 최종 타입에도 적용하는 것입니다.

[source,rust]
----
// String 대신 &'a str: 3장의 라이프타임을 최종 타입에도 적용한다
#[derive(Debug, Clone, PartialEq)]
pub enum FastValue<'a> {
    Null,
    Bool(bool),
    Number(f64),
    Str(&'a str),
    Array(Vec<FastValue<'a>>),
    Object(Vec<(&'a str, FastValue<'a>)>), // HashMap 대신 정렬 없는 Vec
}
----

[source,rust]
----
// 이스케이프가 없다는 전제로, 원본 input을 복사 없이 슬라이스로 돌려준다 (3장과 같은 패턴)
fn parse_string_slice(&mut self) -> FResult<&'a str> {
    self.expect(b'"')?;
    let start = self.pos;
    while self.peek()? != b'"' {
        self.pos += 1;
    }
    let s = &self.input[start..self.pos];
    self.pos += 1;
    Ok(s)
}
----

객체 파싱도 `HashMap::new()` 대신 `Vec::new()`로 바뀌고, 키를 `push`로 순서대로 쌓기만 합니다(정렬하지 않습니다 — cJSON, C++23 버전과 같습니다).

NOTE: 이 버전은 이스케이프 문자(`\"`, `\\` 등) 처리를 아예 생략했습니다 — C++23 버전과 공정하게 비교하기 위한 축소입니다. 이 장의 벤치마크 데이터(`big.json`)에는 애초에 이스케이프가 없으므로 결과에는 영향이 없지만, 실전에서 쓰려면 이스케이프가 있는 문자열만 예외적으로 `String`을 새로 할당하는 하이브리드 방식이 필요합니다 — 이건 이 책이 다루지 않는 다음 과제로 남겨둡니다.

최적화한 Rust가 원본 대비 **2.39배**, C보다 **2.06배**, 같은 기법을 적용한 C++23 버전보다도 **2.13배** 빨랐습니다. 원본 Rust가 C보다 느렸던 게 "Rust이기 때문"이 아니었다는 9장의 결론이 다시 확인됐을 뿐 아니라, 예상보다 더 나아갔습니다. 다만 이 2.13배라는 숫자를 그대로 결론으로 남기지 않고, 실제로 어디서 나는 차이인지 더 파봤습니다.

== 틀린 가설 두 개

먼저 그럴듯해 보이는 원인 두 가지를 시도했습니다.

**가설 1: `std::isspace`/`std::isdigit`가 로케일 인식 함수라 느릴 것이다.** 순수 ASCII 범위 비교(`c >= '0' && c <= '9'`)로 바꿔봤습니다.

[source]
----
c++23 v1 (원본, isspace/isdigit):     27.9 ms
c++23 v2 (+ASCII 범위 체크):          28.2 ms   -- 차이 없음, 오차 범위 안
----

차이가 없었습니다 — 컴파일러가 이 문맥에서 이미 충분히 최적화하고 있었다는 뜻입니다.

**가설 2: PMR의 가상 함수 호출(`memory_resource::do_allocate`)이 오버헤드일 것이다.** 아레나를 걷어내고 그냥 전역 할당자를 쓰는 평범한 `std::vector`로 바꿔봤습니다.

[source]
----
c++23 v3 (+PMR 제거, 일반 std::vector):  30.0 ms   -- 오히려 더 느려짐
----

**더 느려졌습니다.** PMR 아레나가 범인이 아니라 오히려 도움을 주고 있었다는 뜻입니다 — 가상 호출 오버헤드보다, 애초에 `malloc`/`free`를 값마다 안 부르는 이득이 더 컸습니다. 두 가설 다 기각됐습니다.

== 단계별로 시간을 쪼개보다

추측을 더 쌓는 대신, 프로그램을 "파일 읽기"와 "파싱"으로 나눠 각각 시간을 재봤습니다.

[source,cpp]
----
auto t0 = std::chrono::steady_clock::now();
std::ifstream f(argv[1], std::ios::binary);
std::ostringstream ss;
ss << f.rdbuf();
std::string content = ss.str();
auto t1 = std::chrono::steady_clock::now();

Parser parser(content, &arena);
Value v = parser.parse();
auto t2 = std::chrono::steady_clock::now();
// t1-t0: 읽기, t2-t1: 파싱
----

[source]
----
$ ./cpp23/parse_file_timed big.json
read: 11.441ms parse: 10.358ms
----

Rust 쪽도 똑같이 쪼개봤습니다.

[source]
----
$ ./target/release/parse_file_fast_timed big.json
read: 0.517ms parse: 9.609ms
----

**파싱 자체는 C++23이 10.4ms, Rust가 9.6ms로 사실상 동률입니다.** 격차는 파서가 아니라 **파일 읽기**에서 났습니다 — C++이 11.4ms, Rust가 0.5ms로 **20배 넘게** 차이가 났습니다.

== 진짜 원인: `std::ostringstream`

C++ 버전은 파일을 이렇게 읽고 있었습니다.

[source,cpp]
----
std::ifstream f(argv[1], std::ios::binary);
std::ostringstream ss;
ss << f.rdbuf();       // 스트림 버퍼를 한 글자씩(또는 청크 단위로) 밀어 넣는다
std::string content = ss.str();
----

`ostringstream`에 `<<`로 스트림을 흘려 넣는 방식은 내부적으로 로케일 인식 포맷팅 계층을 거치며, 여러 번의 버퍼 재할당·복사가 일어날 수 있습니다 — 익히 알려진 C++ 성능 함정입니다. 파일 크기를 미리 알아내고 한 번에 읽는 방식으로 바꿨습니다.

[source,cpp]
----
std::ifstream f(argv[1], std::ios::binary);
f.seekg(0, std::ios::end);
size_t size = f.tellg();
f.seekg(0);
std::string content(size, '\0');   // 정확한 크기로 미리 할당
f.read(content.data(), size);       // 한 번에 읽는다
----

    -n "c++23 v4 (+seekg/read 직접 읽기)"      "./cpp23/parse_file_v4 big.json" \
    -n "rust (최적화, Vec+&str)"               "./target/release/parse_file_fast big.json" \
    -n "c (cJSON)"                             "./c_ref/parse_file big.json"

Benchmark 1: c++23 v1 (원본, ostringstream 읽기)    27.6 ms
Benchmark 2: c++23 v4 (+seekg/read 직접 읽기)       16.5 ms
Benchmark 3: rust (최적화, Vec+&str)                13.4 ms
Benchmark 4: c (cJSON)                              27.5 ms

Summary
  rust (최적화, Vec+&str) ran
    1.22 ± 0.04 times faster than c++23 v4 (+seekg/read 직접 읽기)
    2.05 ± 0.08 times faster than c (cJSON)
    2.05 ± 0.07 times faster than c++23 v1 (원본, ostringstream 읽기)
----

파일 읽기 방식 하나를 고친 것만으로 27.6ms → 16.5ms — **격차(2.05배)의 대부분이 사라지고 1.22배로 줄었습니다.** 남은 1.22배는 파싱 단계 자체의 미세한 차이(`std::variant`의 태그 접근 방식, `std::pmr::vector`의 성장 전략 등)로 설명 가능한 수준이고, 이 책은 여기서 더 파고들지는 않습니다.

== 이 장이 남긴 방법론

이 장에서 실제로 배운 건 특정 최적화 기법이 아니라 **진단 순서**입니다 — "느리다"는 결과를 보고 바로 그럴듯한 원인(해시맵, 가상 함수)을 추측해 고치는 대신, 프로그램을 단계별로 쪼개 **어디서** 시간이 가는지부터 재야 합니다. 이 장에서 세운 첫 두 가설(문자 분류 함수, PMR)은 전부 틀렸고, 실제 원인(파일 읽기 방식)은 처음엔 의심조차 하지 않았던 곳에 있었습니다 — 파서 코드를 아무리 들여다봐도 찾을 수 없었던 이유입니다.

== 요약

* 9장에서 진단만 했던 원인(해시맵, 문자열 할당)을, `cpp23-performance-engineering` 책의 기법(PMR 아레나, flat 컬렉션, `string_view`)으로 C++23에서 먼저 검증했고, C와 사실상 동률까지 따라잡았습니다.
* 같은 설계를 Rust에 적용해 처음엔 C++23보다 2.13배 빠른 결과를 얻었지만, 문자 분류 함수와 PMR 제거라는 두 가설을 실측으로 기각한 뒤, 프로그램을 읽기/파싱 단계로 쪼개 진짜 원인이 `std::ostringstream`의 느린 파일 읽기(파싱 자체가 아니라)라는 걸 찾아냈습니다.
* 파일 읽기 방식을 고치자 격차가 2.05배에서 1.22배로 줄었습니다 — "왜 느린지 모르겠으면 추측하지 말고 단계를 쪼개 재라"는 게 이 장이 남긴 가장 큰 교훈입니다.
