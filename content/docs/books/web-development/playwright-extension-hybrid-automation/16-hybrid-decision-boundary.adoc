15장의 파이프라인은 로그인·대기열은 Playwright, 좌석 선택은 익스텐션+LLM으로 나눴습니다. 이 장은 그 경계선을 명시적인 기준으로 정리합니다.

== 판단 기준

[cols="1,1,1"]
|===
|기준 |Playwright |익스텐션 + LLM

|성공 조건을 코드로 정확히 쓸 수 있는가
|예 (`if position <= 0`, `if 필드가 비었으면 실패`)
|아니오 (`좋은 자리`라는 게 코드로 표현 안 됨)

|입력이 구조화된 데이터인가
|예 (JSON API 응답, 텍스트 필드)
|아니오 (색으로만 구분된 캔버스 픽셀)

|매 실행마다 같은 규칙이 통하는가
|예
|아니오 (선호도가 매번 다른 자연어)

|속도·비용
|수 ms, 무료
|LLM 호출 1회당 수백 ms~수 초, API 비용 발생
|===

로그인·대기열·재시도(3~5장)는 왼쪽 칸 전부에 "예"가 나옵니다 — Playwright만으로 충분하고, 오히려 LLM을 썼다면 매번 API 비용과 지연을 감수해야 했을 것입니다. 좌석 판단(13장)은 오른쪽 칸에 해당합니다 — "3루측 그늘"이라는 조건을 좌표로 바꾸는 규칙을 코드로 미리 쓸 수 없기 때문입니다.

== 애매한 경계 사례

모든 경우가 이렇게 깔끔하게 갈리지는 않습니다. 예를 들어 "매진되지 않은 좌석 중 아무거나"는 어느 쪽일까요? 이건 사실 `seats[r][c] === 'open'`이라는 규칙 하나로 표현되니, 굳이 LLM을 쓸 필요가 없습니다 — 13장의 `/api/seats` 응답을 그대로 필터링하면 됩니다(캔버스 색만으로는 이 조건을 코드로 못 봤을 뿐, API 응답 자체엔 이미 구조화된 정보가 있었습니다). 반대로 "이 사이트가 처음 보는 구조로 완전히 개편됐다"면, 정해둔 셀렉터 자체가 깨지므로 오히려 "지금 화면에서 다음 버튼이 뭔지" 판단하는 데 LLM이 쓰일 여지가 생깁니다 — 다만 이 책은 이 확장까지는 다루지 않습니다(19장 참고).

== 비용을 실측으로 가늠하기

15장의 실행 로그에서, 대기열 폴링 6번은 전부 로컬 요청이라 거의 즉시 끝났지만, 팝업의 좌석 판단 한 번은 캔버스 캡처 + `fetch` 왕복 + JSON 파싱까지 거쳤습니다 — 실제 LLM(모크가 아니라 진짜 API)을 썼다면 여기에 수백 ms~수 초의 네트워크 지연이 추가로 붙습니다. "이 작업에 LLM이 꼭 필요한가"를 먼저 따지고, 필요하다면 **한 번의 호출로 여러 후보를 한꺼번에** 받아서(13장에서 예고한 확장) 호출 횟수 자체를 줄이는 게 실전에서 중요합니다.

== 요약

* "성공 조건을 코드로 정확히 쓸 수 있는가"가 Playwright와 LLM을 가르는 가장 실용적인 질문입니다.
* 캔버스 색상처럼 구조화되지 않은 입력, 자연어 선호도처럼 매번 달라지는 조건이 LLM이 필요해지는 지점입니다.
* LLM 호출은 공짜가 아닙니다 — 호출 횟수를 줄이는 설계(한 번에 여러 후보 받기)가 실전에서 속도와 비용을 함께 잡습니다.

4부가 여기서 끝났습니다. 5부에서는 이 파이프라인이 실제로 얼마나 견고한지, 2장의 트랩을 더 가혹하게 만들어 실측합니다.
