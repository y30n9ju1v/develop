1장에서 만든 사이트는 이미 두 가지 함정을 갖고 있습니다 — 좌석맵이 캔버스로만 그려진다는 것(DOM 셀렉터 무력화), 대기열 순번이 호출마다 무작위로 준다는 것(정확한 완료 시점 예측 불가). 이 장에서는 세 번째 함정을 추가합니다 — **좌석을 보는 사이에 다른 사람이 채간다**는, 실제 인기 경기 예매에서 가장 흔한 상황입니다.

== 트랩: 몇 초마다 무작위로 좌석이 팔린다

[source,javascript]
----
// site/server.js
let queuePosition = 37;

// 다른 사람이 계속 좌석을 채가는 것처럼, 몇 초마다 무작위 좌석을 하나씩 매진시킨다.
setInterval(() => {
  const r = Math.floor(Math.random() * SEAT_ROWS);
  const c = Math.floor(Math.random() * SEAT_COLS);
  seats[r][c] = 'sold';
}, 4000);
----

이 한 줄이 이 책 뒷부분(특히 5장의 재시도 전략, 18장의 견고성 검증)이 실제로 필요해지는 이유를 만듭니다. 실측으로 확인해봅니다.

[source]
----
$ curl -s http://localhost:4100/api/seats | python3 -c "import json,sys; d=json.load(sys.stdin); print(sum(r.count('sold') for r in d))"
13
$ sleep 3
$ curl -s http://localhost:4100/api/seats | python3 -c "import json,sys; d=json.load(sys.stdin); print(sum(r.count('sold') for r in d))"
15
----

3초 사이에 매진 좌석이 13개에서 15개로 늘었습니다 — `/api/seats`로 스냅샷을 받은 시점과 실제로 `/api/reserve`를 호출하는 시점 사이에 그 좌석이 이미 팔렸을 수 있다는 뜻입니다. 이건 버그가 아니라 **의도적으로 심은 경쟁 조건(race condition)**입니다.

== 이 트랩이 앞으로 어떤 장에 영향을 주는가

* **3부(익스텐션+LLM)**: LLM이 스크린샷을 보고 판단을 내리는 그 짧은 시간에도 좌석이 팔릴 수 있습니다 — 판단과 실제 클릭 사이의 지연이 있는 만큼, 이 트랩이 실패를 만들어낼 확률이 올라갑니다.
* **5장(재시도 전략)**: `/api/reserve`가 `{ok: false, message: "이미 매진된 좌석입니다"}`를 돌려주는 상황을 실제로 마주치므로, "실패하면 다시 판단을 요청한다"는 재시도 로직이 장식이 아니라 실제로 발동하는 코드가 됩니다.
* **18장(견고성 검증)**: 이 인터벌 값을 짧게 줄이면(예: 4000ms → 500ms) 파이프라인이 훨씬 가혹한 조건에서도 버티는지 실측할 수 있습니다 — 이 트랩 자체가 이후 장의 스트레스 테스트 손잡이가 됩니다.

== 요약

* 몇 초마다 무작위 좌석을 매진시키는 `setInterval` 하나로, "좌석 정보를 조회한 시점"과 "실제로 예매를 확정하는 시점" 사이의 경쟁 조건을 재현했습니다.
* 이 트랩은 실측으로 확인됩니다 — 3초 사이 매진 좌석 수가 13에서 15로 실제로 늘었습니다.
* 이 경쟁 조건이 뒤에서 다룰 재시도 전략(5장)과 견고성 검증(18장)이 왜 필요한지를 만드는 근거가 됩니다.
