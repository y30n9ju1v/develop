== 이 책이 확인한 것

1부에서 대기열·캔버스 좌석맵·경쟁 조건까지 갖춘 연습용 사이트를 지었습니다. 2부에서 로그인·대기열·재시도처럼 규칙이 명확한 작업을 Playwright로 자동화했습니다. 3부에서 Manifest V3 익스텐션을 처음부터 지으며 content script의 격리된 world(그리고 그 때문에 실제로 겪은 실패), 메시지 패싱의 두 가지 패턴, API 키를 service worker 밖으로 새어나가지 않게 하는 경계 설계, 캔버스 스크린샷을 LLM에 보내 판단을 받는 전체 왕복, 그리고 스트리밍까지 실제로 돌려 확인했습니다. 4부에서 이 둘을 하나의 파이프라인으로 잇고, "언제 Playwright, 언제 LLM"이라는 판단 기준을 정리했습니다. 5부에서 이 파이프라인이 재시도 로직 유무에 따라 20%와 80%로 성공률이 갈린다는 걸 실측했고, 헤드리스 CI 환경에서도 재현 가능하다는 걸 확인했습니다.

== 이 기술을 실제 예매 사이트에 적용하면 안 되는 이유 (다시)

서문에서 밝혔던 걸 마지막으로 한 번 더 명확히 합니다. 이 책이 가르친 건 **Playwright와 크로미움 익스텐션, 그 안에서 LLM을 호출하는 일반적인 기술**입니다. 이 기술 자체는 QA 자동화, 접근성 테스트, 반복 작업 보조처럼 합법적이고 유용한 곳에 쓰입니다. 하지만 이걸 실제 티켓 플랫폼에 겨냥하는 순간, 이야기가 달라집니다 — 거의 모든 플랫폼의 이용약관이 자동화 프로그램을 통한 예매를 명시적으로 금지하고, 한국은 2024년 공연법 개정으로 부정한 방법의 예약 선점 프로그램을 제재하는 방향으로 법이 강화됐습니다. 개인적으로 볼 표를 사려는 목적이라도, 약관 위반과 업무방해 소지는 별개로 남습니다. 이 책의 모든 실습은 그래서 직접 만든 가짜 사이트 위에서만 이뤄졌습니다.

== 이 책이 다루지 않은 것

* **실제 LLM API와의 검증** — 이 세션엔 API 키가 없어 OpenAI 호환 모크 서버로 검증했습니다. 실제 API로 바꾸면 응답 지연·비용·때때로 다른 형식의 답변(프롬프트를 아무리 단단히 짜도 완벽하게 구조화된 JSON만 돌아온다는 보장은 없습니다) 같은 새로운 변수가 생깁니다.
* **side panel, options 페이지** — 8장에서 존재만 언급하고 실제로 만들지는 않았습니다.
* **Chrome Web Store 배포** — 이 익스텐션은 로컬 개발/테스트용으로만 다뤘고, 실제 스토어 심사·게시 절차는 다루지 않았습니다.
* **사이트 구조가 완전히 바뀌는 상황에 대한 대응** — 16장에서 가능성만 언급했습니다. 셀렉터가 깨졌을 때 LLM이 "지금 화면에서 다음 버튼이 뭔지" 판단하게 하는 확장은 이 책의 범위 밖입니다.

== 다음 단계

이 책이 다진 걸 바탕으로, 정말로 무언가를 자동화하고 싶다면 먼저 **그 대상이 자동화를 허용하는지**부터 확인하는 습관을 들이는 게 좋습니다 — 공개 API를 제공하는 서비스, 스스로 운영하는 사이트, 명시적으로 자동화를 허용한 도구라면 이 책의 기술을 그대로 옮겨 쓸 수 있습니다. 기술 자체는 중립적입니다 — 어디에 겨냥하느냐가 그 기술을 유용하게도, 문제가 되게도 만듭니다.
