== 이 책이 시작된 질문

"야구 표를 자동으로 예매하고 싶은데, 어떤 건 Playwright가 낫고 어떤 건 익스텐션에서 LLM을 부르는 게 나을 것 같다" — 이게 이 책의 출발점이었습니다. 실제로 파고들어보면 이 직감은 정확합니다. 대기열을 뚫고, 정해진 시각에 새로고침하고, 폼을 채우는 건 규칙이 명확한 작업이라 Playwright의 셀렉터·대기 전략만으로 충분합니다. 반면 "캔버스로만 그려진 좌석맵에서 3루측 그늘, 4인이 붙어 앉을 수 있는 자리를 찾아라" 같은 건 규칙으로 짜기 어렵습니다 — 이런 판단이 필요한 지점에서 LLM이 실질적인 도움이 됩니다.

== 다만 이 책은 실제 예매 사이트를 겨냥하지 않습니다

먼저 분명히 해둘 게 있습니다. 대부분의 티켓 플랫폼 이용약관은 매크로·자동화 프로그램을 통한 예매를 명시적으로 금지하고, 한국은 2024년 공연법 개정으로 "부정한 방법으로 예약을 선점하는 프로그램" 사용을 제재하는 방향으로 법이 강화됐습니다. 재판매 목적이 아니어도, 약관 위반과 업무방해 소지는 남습니다. 그래서 이 책은 **실제 예매 사이트가 아니라, 직접 만든 연습용 가짜 예매 사이트**를 대상으로 합니다 — 대기열, 캔버스 좌석맵, 랜덤 매진까지 실제 사이트의 성가신 특징들을 흉내 낸 작은 웹앱을 1장에서 직접 짓고, 그 위에서만 자동화를 연습합니다. 이 책이 가르치는 건 "Playwright와 크로미움 익스텐션, 그 안에서 LLM을 호출하는 법"이라는 일반적인 기술이지, 특정 사이트를 뚫는 법이 아닙니다. 이 기술을 실제 예매 사이트에 그대로 옮기지 말아야 하는 이유는 19장(맺음말)에서 다시 한번 짚습니다.

== 이 책의 구조

*1부(1~2장)* 는 연습 대상 자체를 만듭니다 — Node/Express로 대기열·캔버스 좌석맵·랜덤 매진을 갖춘 가짜 예매 사이트를 짓습니다.

*2부(3~5장)* 는 규칙이 명확한 부분을 Playwright로 자동화합니다 — 로그인·폼, 대기열 진입 타이밍, 실패를 전제로 한 재시도까지.

*3부(6~14장)* 는 이 책의 핵심입니다 — Manifest V3 익스텐션을 처음부터 짓고(manifest, service worker, content script, popup), 그 안에서 실제로 LLM API를 호출해(스트리밍 포함) 캔버스 좌석맵을 판단하게 만듭니다. API 키를 content script에 노출하지 않는 경계 설계도 이 부에서 다룹니다.

*4부(15~16장)* 는 Playwright가 이 익스텐션 자체를 구동해서, "쉬운 부분은 Playwright, 어려운 부분은 익스텐션+LLM"이 하나의 파이프라인으로 이어지는 걸 확인합니다.

*5부(17~18장)* 는 이 파이프라인이 실제로 견고한지 — 무작위 지연·매진·구조 변경에도 버티는지 — 실측하고, CI에서 재현 가능하게 만듭니다.

== 실측 원칙

이 책의 모든 코드는 실제로 돌려서 검증합니다. 다만 한 가지 예외가 있습니다 — 이 세션에는 실제 OpenAI/Anthropic API 키가 없어서, LLM 호출 부분은 같은 HTTP 계약(`/v1/chat/completions`, SSE 스트리밍)을 구현한 로컬 모크 서버로 검증했습니다. 클라이언트 코드(익스텐션의 service worker)는 base URL과 키만 바꾸면 실제 API에도 그대로 동작합니다 — 이 경계가 정확히 어디인지는 11장에서 명시적으로 다시 짚습니다.

== 사전 지식

JavaScript 기본 문법과 브라우저 개발자 도구를 다뤄본 경험이면 충분합니다. Playwright나 크로미움 익스텐션을 한 번도 안 써봤어도, 이 책 안에서 필요한 만큼 문법과 개념을 함께 설명합니다.

== 어떤 언어로 쓰는가

크로미움 익스텐션(manifest.json, service worker, content script, popup)은 규격상 JavaScript로만 작성할 수 있습니다 — 이건 선택의 여지가 없습니다. 반면 **Playwright를 구동하는 스크립트(2·4·5·15·17·18장)는 Python(`playwright-python`)으로 씁니다** — Python API는 JavaScript판과 메서드 이름까지 거의 1:1로 대응해서 기능 손실이 없고, 익스텐션 코드와 언어가 섞이는 대신 "이 파일은 익스텐션, 이 파일은 자동화 스크립트"라는 경계가 파일 확장자(`.js` vs `.py`)만으로도 분명해집니다.
