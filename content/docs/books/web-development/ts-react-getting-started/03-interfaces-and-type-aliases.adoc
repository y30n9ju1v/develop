== 객체 타입에 이름이 필요한 이유

[source,ts]
----
function printUser(user: { name: string; age: number }) {
  console.log(`${user.name} (${user.age})`);
}

printUser({ name: "Ada", age: 36 });
----

객체의 모양(shape)도 이렇게 그 자리에서 바로 적을 수 있습니다. 그런데 같은 모양의 객체를 여러 함수가 받는다면, 매번 `{ name: string; age: number }`를 반복해서 적어야 합니다 — 오타 하나로 두 함수의 "같은 모양이어야 할" 타입이 슬쩍 어긋날 수 있습니다. 그래서 이 모양에 이름을 붙여 재사용합니다. TypeScript는 이름을 붙이는 방법을 두 가지 제공합니다.

== interface

[source,ts]
----
interface User {
  name: string;
  age: number;
}

function printUser(user: User) {
  console.log(`${user.name} (${user.age})`);
}

printUser({ name: "Ada", age: 36 });
----

`interface User { ... }`가 방금 그 객체 모양에 `User`라는 이름을 붙인 것입니다. 이제 이 모양이 필요한 곳마다 `User`라고만 쓰면 됩니다.

== type alias (타입 별칭)

[source,ts]
----
type User = {
  name: string;
  age: number;
};

function printUser(user: User) {
  console.log(`${user.name} (${user.age})`);
}

printUser({ name: "Ada", age: 36 });
----

`type`으로 쓴 이 코드는 겉보기에 `interface` 버전과 거의 똑같은 일을 합니다 — 실제로 이 정도 단순한 객체 모양에서는 둘이 사실상 바꿔 써도 차이가 없습니다. 그런데 이 두 문법은 "그냥 같은 걸 두 가지로 쓸 수 있게 해준다"가 아니라, 원래 하는 일 자체가 다릅니다.

== 진짜 차이: interface는 "확장"되고, type은 "조합"된다

`interface`는 나중에 같은 이름으로 다시 열어서 필드를 추가할 수 있습니다(선언 병합, declaration merging).

[source,ts]
----
interface User {
  name: string;
}

interface User {
  age: number; // 같은 이름으로 다시 선언 — 필드가 합쳐짐
}

const u: User = { name: "Ada", age: 36 }; // name과 age 둘 다 필요
console.log(u);
----

`type`은 이게 안 됩니다 — 같은 이름으로 두 번 `type`을 선언하면 에러가 납니다. 대신 `type`은 **객체가 아닌 것도 이름 붙일 수 있습니다** — 유니온(다음 장에서 다룰 "이거 아니면 저거"), 튜플, 함수 타입처럼 interface로는 표현할 수 없는 것들입니다.

[source,ts]
----
type ID = string | number;          // 유니온: interface로는 표현 불가능
type Point = [number, number];      // 튜플
type Transform = (x: number) => number; // 함수 타입

function printId(id: ID) {
  console.log(id);
}

printId("abc");
printId(42);
----

== 실무 기준: 객체 모양이면 interface, 그 외엔 type

이 책은 다음 기준을 따릅니다 — **"이게 객체의 모양을 나타내는가?"** 라면 `interface`, 그렇지 않고 유니온·튜플·함수 타입처럼 조합이 필요하다면 `type`. React의 Props 타입(2부에서 다룹니다)은 거의 항상 객체 모양이라 이 책에서는 `interface`를 기본으로 쓰지만, 실무에서는 팀 컨벤션에 따라 항상 `type`만 쓰는 곳도 흔합니다 — 이 정도 단순한 경우엔 둘 다 정답이라는 뜻입니다. 중요한 건 "선언 병합이 필요한가"와 "유니온처럼 interface가 표현 못 하는 걸 다루는가"라는 두 질문이지, 어느 쪽이 절대적으로 우월한가가 아닙니다.

== 선택적 필드와 읽기 전용

[source,ts]
----
interface User {
  name: string;
  age: number;
  nickname?: string;       // ?: 있어도 되고 없어도 되는 필드
  readonly id: number;     // readonly: 한 번 만들어지면 다시 대입 불가능
}

const u: User = { name: "Ada", age: 36, id: 1 }; // nickname 없이도 통과
// u.id = 2; // 컴파일 에러: 읽기 전용 속성이므로 'id'에 할당할 수 없습니다.
console.log(u);
----

`nickname?`처럼 물음표를 붙이면 "있을 수도, 없을 수도 있는 필드"가 되고, `readonly`를 붙이면 처음 만들어질 때 말고는 값을 다시 바꿀 수 없습니다. 둘 다 "이 객체가 실제로 어떻게 쓰이는지"를 타입에 더 정확히 새겨 넣는 방법입니다.

== 왜 굳이 interface가 따로 필요했을까

`type`도 객체 모양을 표현할 수 있는데, 왜 TypeScript는 `interface`라는 문법을 따로 두고 있을까요? 사실 역사적으로는 순서가 반대입니다 — `interface`는 TypeScript가 처음 공개된 2012년부터 있었던 반면, `type` alias는 그보다 나중인 1.4(2015년)에야 추가됐습니다(참고로 TypeScript 1.0 정식 출시는 2014년입니다). 다만 `type` alias는 도입된 시점부터 이미 객체 모양을 포함한 임의의 타입을 별칭할 수 있었으므로, "객체를 표현하는 능력이 나중에 추가됐다"는 건 아닙니다 — 처음부터 `interface`와 상당 부분 겹치는 문법이었던 셈입니다. 그런데도 지금까지 `interface`가 남아있는 데는 실질적인 이유가 있습니다.

* *익숙한 문법*: TypeScript는 애초에 "이미 존재하는 대규모 JS 코드베이스에 타입을 얹는다"는 목표로 설계됐고, 그 사용자층 상당수가 Java/C# 같은 언어 출신이었습니다. `interface X { ... }`는 그들에게 이미 익숙한 개념(계약)을 그대로 옮겨온 문법입니다.
* *선언 병합이 실무에서 필요하다*: 이 장에서 본 "다시 열어 필드 추가"는 장난이 아니라, 서드파티 라이브러리의 타입을 확장할 때 실질적으로 쓰입니다 — 예를 들어 Express의 `Request` 타입에 내 미들웨어가 추가한 필드를 얹을 때, 원래 라이브러리의 `interface Request`를 내 프로젝트에서 다시 열어 필드를 추가하는 식으로 씁니다. `type`은 재선언 자체가 에러라 이 방식이 불가능합니다.
* *깊은 상속에서 더 안정적이다*: 객체 계층이 깊게 `extends`될 때 `interface`는 컴파일러가 더 안정적으로 캐싱·검사하는 경향이 있고, 에러 메시지도 더 명확한 편입니다 — 복잡한 `type` 교차(`\&`) 체인은 에러 메시지가 읽기 힘들어지는 경우가 실제로 있습니다.

정리하면 `type`이 나중에 강력해지면서 단순한 경우엔 둘 다 쓸 수 있게 됐지만, "라이브러리 타입을 확장해야 한다"는 선언 병합의 필요성 때문에 `interface`는 도태되지 않고 남아있습니다.

== 다른 언어의 struct와 비교하기

C, Go, Rust 같은 언어를 접해봤다면 "`interface`나 `type`이 결국 struct 아닌가?"라는 생각이 들 수 있습니다. 목적(값의 모양에 이름을 붙인다)은 비슷하지만, 실제로는 근본적으로 다른 것입니다. (아래 표는 세 언어를 크게 뭉뚱그린 단순화입니다 — 특히 Go는 인터페이스 만족 여부를 구조적으로 검사하는 등 언어마다 세부는 꽤 다르지만, TypeScript와의 핵심적인 차이를 보는 데는 이 정도 단순화로 충분합니다.)

[cols="1,2,2"]
|===
|비교 기준 |struct (C/Go/Rust) |interface / type (TypeScript)

|런타임 존재 여부
|메모리에 실제로 존재하는 값 — 인스턴스를 만들면 그 필드들이 실제 메모리를 차지함
|컴파일 시점에만 존재 — 컴파일되면 완전히 사라짐(`tsc`로 컴파일한 JS 결과물에 흔적이 없음)

|타입 판별 방식
|이름으로 판별(nominal typing) — 같은 필드를 가져도 다른 이름의 struct면 다른 타입
|모양으로 판별(structural typing) — 이름이 달라도 필드 모양이 같으면 같은 타입으로 통과(예: 03장 서두의 `{ name, age }` 객체가 `User`로 바로 통과)

|재선언(확장)
|한 번 정의하면 끝 — 다시 열어 필드를 추가하는 개념이 없음
|`interface`는 선언 병합으로 다시 열어 필드 추가 가능. `type`은 재선언 불가하지만 유니온·교차(`\&`)로 조합 가능

|표현 범위
|필드들의 묶음(객체 모양)만 표현
|`interface`는 객체 모양만. `type`은 객체뿐 아니라 유니온(`string \| number`), 튜플, 함수 타입까지 표현 가능 — struct라는 개념 자체가 다루지 못하는 범위
|===

한 줄로 요약하면: struct가 "메모리에 실제로 존재하는 필드 묶음의 설계도"라면, `interface`와 `type`은 "컴파일러가 값의 모양을 검사하기 위해 쓰고 버리는 이름표"입니다 — 이 차이 때문에 struct에서는 자연스러운 "인스턴스 생성"이라는 개념이 TypeScript의 `interface`/`type`에는 아예 없습니다(둘 다 값이 아니라 값에 대한 제약이기 때문입니다).

== 직접 해보기

* `Product` 인터페이스(`name: string`, `price: number`, 선택적 필드 `discount?: number`)를 만들고, `discount` 없이 객체를 만들어도 통과하는지 확인해보세요.
* `type Status = "pending" | "done" | "failed"`처럼 문자열 리터럴의 유니온을 만들고, 이 셋 중 하나가 아닌 값을 넣으면 에러가 나는지 확인해보세요.

.해답 보기
[%collapsible]
====
[source,ts]
----
interface Product {
  name: string;
  price: number;
  discount?: number;
}

const p: Product = { name: "Keyboard", price: 100 };

type Status = "pending" | "done" | "failed";

function printStatus(status: Status) {
  console.log(status);
}

printStatus("done");
// printStatus("cancelled"); // 컴파일 에러

console.log(p);
----
====

== 요약

* 객체 모양을 반복해서 적지 않으려고 `interface`나 `type`으로 이름을 붙입니다.
* `interface`는 같은 이름으로 다시 열어 필드를 추가(선언 병합)할 수 있고, `type`은 유니온·튜플·함수 타입처럼 객체가 아닌 것도 이름 붙일 수 있습니다.
* `interface`가 `type`보다 먼저 있었고, 지금도 남아있는 이유는 선언 병합이 라이브러리 타입 확장에 실무적으로 필요하기 때문입니다.
* 이 책은 객체 모양엔 `interface`, 그 외의 조합엔 `type`을 기본으로 씁니다 — 다만 이 정도 단순한 경우엔 팀 컨벤션에 따라 어느 쪽을 골라도 됩니다.
* `?`(선택적 필드)와 `readonly`(읽기 전용)로 객체가 실제로 어떻게 쓰이는지를 타입에 더 정확히 표현할 수 있습니다.
* 다른 언어의 struct와 달리, `interface`/`type`은 런타임에 존재하지 않고 이름이 아니라 모양으로 판별됩니다(구조적 타이핑) — struct가 실제 메모리 위의 설계도라면, 이쪽은 컴파일러만 보고 사라지는 이름표입니다.
