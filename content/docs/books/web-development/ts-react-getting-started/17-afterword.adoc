== 이 책이 일부러 건너뛴 것들

15개 장에 걸쳐 TypeScript와 React를 훑었지만, react.dev와 TypeScript Handbook 안에는 이 책이 다루지 않은 내용이 훨씬 많습니다. 몇 가지만 짚어봅니다.

1부(TypeScript)에서는 조건부 타입, 매핑된 타입, `infer` 같은 고급 타입 연산, 클래스와 데코레이터, 모듈 시스템의 세부(namespace, 선언 파일)를 다루지 않았습니다. 2부(React)에서는 `useReducer`, `useMemo`/`useCallback`(성능 최적화), `useRef`, Context API(전역 상태를 Props 없이 전달하기), Suspense와 서버 컴포넌트를 다루지 않았습니다. 3부(실전)에서는 라우팅(React Router), 전역 상태 관리 라이브러리, 테스트(Testing Library) 도구를 다루지 않았습니다.

이 생략은 실수가 아니라 선택입니다 — 이 책의 목표는 "react.dev와 Handbook을 처음부터 끝까지 옮기는 것"이 아니라 "왜 이렇게 생겼는가"라는 질문으로 입구를 여는 것이었습니다. 위에 나열한 것들은 전부 이 책에서 다진 기초(타입 추론, Props/State, 재조정, 훅 규칙) 위에서 훨씬 수월하게 이해됩니다.

== 더 깊이 들어가고 싶다면

* *TypeScript의 고급 타입을 더 파고들고 싶다면* → https://www.typescriptlang.org/docs/handbook/2/types-from-types.html[TypeScript Handbook의 "Types from Types" 섹션]. 이 책의 4~5장(제네릭, 유니온)이 그 입구입니다.
* *React의 나머지 훅과 성능 최적화가 궁금하다면* → https://react.dev/reference/react[react.dev의 API 레퍼런스]. 이 책의 8~10장(State, 렌더링, useEffect)이 `useMemo`/`useCallback`이 왜 필요한지 이해하는 전제가 됩니다.
* *실제 프로젝트에 라우팅과 전역 상태가 필요해지면* → React Router, 그리고 Zustand/Jotai 같은 가벼운 상태 관리 라이브러리부터 살펴보는 걸 권합니다. Redux 같은 무거운 도구는 실제로 필요해졌을 때(여러 화면에 걸쳐 공유해야 할 State가 뚜렷해졌을 때) 고려해도 늦지 않습니다.

== 다음 프로젝트로: Refine.dev

이 책을 쓴 진짜 동기는 자율주행 회귀 테스트를 위한 웹 대시보드를 만드는 것이었습니다 — 지도·시나리오를 고르고, 실행 현황을 보고, 결과를 종합하는 화면들입니다. 이런 "목록 + 필터 + 폼"으로 이뤄진 어드민 도구를 매번 밑바닥부터 짜는 대신, **Refine.dev**가 그 반복 작업(API 연동, 테이블, 폼 검증, 라우팅)을 대신해줍니다.

Refine을 시작하면 이 책의 개념들이 곧바로 다시 등장합니다 — Refine의 `useTable()`, `useForm()` 같은 훅은 결국 8장의 `useState`, 10장의 `useEffect`, 13장의 커스텀 훅 패턴 위에 지어진 것이고, Refine이 자동으로 만들어주는 리소스 타입은 14장에서 정리한 Props/이벤트 타이핑 규칙을 그대로 따릅니다. 이 책이 다진 기초가 없었다면, Refine이 감춰준 것들이 "왜 이렇게 동작하는지" 궁금할 때 답을 찾기 어려웠을 것입니다.

[source,bash]
----
npm create refine-app@latest my-dashboard
----

이 한 줄이면 TypeScript + React + Refine이 이미 연결된 프로젝트가 생깁니다. 다음 목적지는 이 책이 아니라, 여러분이 실제로 만들 그 대시보드입니다.
