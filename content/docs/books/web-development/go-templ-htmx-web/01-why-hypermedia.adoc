이 책을 시작하기 전에, "왜 React 같은 프레임워크 대신 이 조합을 쓰는가"라는 질문에 먼저 답해야 합니다. 이 장은 코드보다 개념이 중심이지만, 마지막에 이 책 전체에서 반복될 패턴 — **서버가 완성된 HTML을 내려준다** — 을 실제로 작동하는 코드로 확인합니다.

== 두 가지 웹 아키텍처

=== SPA + API: 클라이언트가 화면을 그린다

React/Vue 같은 SPA(Single Page Application) 구조에서는, 서버가 데이터(보통 JSON)만 내려주고 브라우저의 자바스크립트가 그 데이터를 받아 HTML을 그립니다.

[source]
----
브라우저: GET /api/users/42 요청
서버:     { "id": 42, "name": "김민준" } 응답 (JSON)
브라우저: JSON을 파싱해서 <div>...</div> 같은 HTML을 직접 생성 (React 컴포넌트)
----

이 구조는 강력합니다 — 서버 API를 웹, 모바일 앱, 다른 서비스가 함께 재사용할 수 있고, 화면 전환이 매끄럽습니다. 대가도 있습니다 — 서버의 데이터 모델과 클라이언트의 화면 로직을 별도로 유지해야 하고, 클라이언트 상태 관리(지금 화면에 무엇이 표시돼야 하는가)가 그 자체로 복잡한 문제가 됩니다.

=== 하이퍼미디어 지향(HDA): 서버가 화면을 그린다

이 책이 다루는 접근은 다릅니다 — 서버가 데이터가 아니라 **완성된 HTML 조각**을 내려주고, 브라우저는 그 조각을 화면의 정해진 자리에 끼워 넣기만 합니다.

[source]
----
브라우저: GET /users/42/card 요청
서버:     <div class="card"><h2>김민준</h2><p>가입일: 2026-01-15</p></div> 응답 (HTML)
브라우저: 이 HTML을 화면의 정해진 위치에 그대로 삽입
----

"지금 화면에 무엇이 있어야 하는가"라는 상태를 클라이언트가 별도로 들고 있을 필요가 없습니다 — 서버가 응답한 HTML 그 자체가 상태입니다. 이 아이디어의 뿌리는 사실 새롭지 않습니다 — 전통적인 서버 렌더링 웹(폼을 제출하면 페이지 전체가 새로 로드되는 방식)이 정확히 이 원리로 동작했습니다. htmx는 여기에 "페이지 전체가 아니라 필요한 부분만 갱신한다"는 능력을 얹은 것입니다(4장부터 직접 다룹니다).

== 언제 어느 쪽이 맞는가

이 책이 SPA 구조가 틀렸다고 주장하는 게 아닙니다. 여러 클라이언트(웹, iOS, Android)가 하나의 API를 공유해야 하거나, 오프라인 동작이 중요하거나, 화면 전환에 매우 정교한 애니메이션이 필요하다면 SPA + API가 더 적합할 수 있습니다. 반대로, 대부분의 화면이 서버의 데이터를 그대로 보여주고, 팀 규모가 작아 프런트엔드·백엔드를 분리할 여유가 크지 않고, 빠르게 반복해서 화면을 바꿔야 하는 서비스(사내 도구, 대시보드, 전통적인 CRUD 웹앱)라면 이 책의 접근이 개발 속도와 단순성에서 이점이 있습니다. 실제로 이 두 접근을 한 서비스 안에서 섞어 쓰는 경우도 흔합니다 — "이 화면은 HTML로, 저 화면은 API로"라는 선택은 프로젝트마다 다를 수 있습니다.

== 첫 서버: Go가 HTML을 직접 응답한다

이 책 전체에서 반복될 가장 기본적인 패턴을 먼저 실행해봅니다 — Go의 표준 라이브러리 `net/http`만으로 HTML을 응답하는 서버입니다.

[source,go]
----
package main

import (
	"fmt"
	"net/http"
)

func helloHandler(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintf(w, "<h1>Hello, %s!</h1>", r.URL.Query().Get("name"))
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /hello", helloHandler)
	http.ListenAndServe(":8080", mux)
}
----

`go run main.go`로 서버를 띄우고, 다른 터미널에서 요청을 보내봅니다.

[source,bash]
----
curl "http://localhost:8080/hello?name=World"
----

[source]
----
<h1>Hello, World!</h1>
----

서버가 JSON이 아니라 **완성된 HTML 조각**(`<h1>...</h1>`)을 그대로 응답했습니다. 지금은 `fmt.Fprintf`로 문자열을 직접 조립했지만, 이렇게 하면 HTML 태그를 닫는 걸 깜빡하거나, 사용자 입력을 이스케이프하지 않아 XSS(크로스사이트 스크립팅) 취약점이 생기는 실수를 하기 쉽습니다. 3장에서 다룰 templ이 이 문제를 컴파일 타임에 막아줍니다 — 하지만 그 전에 2장에서 `net/http`의 라우팅과 요청 처리를 조금 더 깊이 다집니다.

== 직접 해보기

* `r.URL.Query().Get("name")`이 비어 있을 때(즉 `curl "http://localhost:8080/hello"`처럼 `name` 파라미터 없이 요청했을 때) 응답이 어떻게 나오는지 확인하고, 빈 문자열 대신 `"손님"`이라는 기본값을 보여주도록 코드를 고쳐보세요.

.해답 보기
[%collapsible]
====
[source,go]
----
func helloHandler(w http.ResponseWriter, r *http.Request) {
	name := r.URL.Query().Get("name")
	if name == "" {
		name = "손님"
	}
	fmt.Fprintf(w, "<h1>Hello, %s!</h1>", name)
}
----

`name` 파라미터가 없으면 `Get`이 빈 문자열을 돌려주므로, 이를 확인해 기본값으로 바꿔치기합니다. 사소해 보이지만, 실전에서는 "파라미터가 없을 때 무엇을 보여줄 것인가"를 매번 명시적으로 결정해야 한다는 걸 보여주는 예시입니다 — 이 책 전체에서 반복해서 마주칠 패턴입니다.
====

== 요약

* SPA + API 구조는 서버가 데이터(JSON)를, 클라이언트가 화면(HTML)을 만들지만, 하이퍼미디어 지향 구조(HDA)는 서버가 완성된 HTML을 직접 내려주고 클라이언트는 그것을 화면에 끼워 넣기만 합니다.
* 이 접근은 클라이언트 상태 관리 부담을 크게 줄이지만, 여러 클라이언트가 하나의 API를 공유해야 하는 경우 등에는 SPA + API가 더 적합할 수 있습니다.
* Go의 `net/http`만으로도 HTML을 직접 응답하는 서버를 만들 수 있다는 것을 실제로 실행해 확인했습니다.
* 다음 장에서는 `net/http`의 라우팅, 여러 핸들러, 미들웨어를 조금 더 깊이 다뤄 이 책 나머지 부분의 기초를 다집니다.
