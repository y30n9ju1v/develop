10장까지의 파이프라인을 거치면 대부분의 시퀀스는 3DGS에 넣기 좋은 상태가 됩니다. 하지만 "대부분"이지 "항상"은 아닙니다 — 신호등에 멈춰 서서 수십 프레임이 거의 같은 위치에서 찍혔거나, 프레임 하나가 통째로 유실돼 그 앞뒤 간격이 비정상적으로 벌어졌거나, 특징 매칭이 잘못돼 포즈 그래프에 나쁜 제약 하나가 섞여 들어갔을 수 있습니다. 이 장에서는 사람이 렌더링 결과를 일일이 보기 전에, 데이터 자체의 통계로 이런 문제를 자동으로 걸러내는 게이트를 만듭니다.

== 점검 1: 프레임 간 이동 거리(베이스라인)

연속된 두 프레임 사이의 카메라 이동 거리(베이스라인)가 너무 작으면 그 프레임 쌍은 삼각측량에 거의 정보를 더해주지 못하고(거의 같은 시점에서 찍은 사진 두 장), 너무 크면 겹치는 영역이 부족해 특징 매칭 자체가 어려워지고 포즈 추정이 불안정해집니다. 신호 대기로 멈춘 구간과, 프레임 하나가 유실돼 간격이 벌어진 구간을 섞은 가상의 로그를 만듭니다.

[source,python]
----
import numpy as np

rng = np.random.default_rng(11)
n = 40

baselines = np.full(n - 1, 0.3) + rng.normal(0, 0.02, n - 1)   # 평소 이동 거리 ~0.3m
baselines[10:14] = rng.normal(0.01, 0.005, 4)                    # 신호 대기: 거의 정지
baselines[25] = 2.5                                               # 프레임 유실: 큰 공백
----

[source,python]
----
low_baseline = baselines < 0.05     # 너무 가까움(정보가 거의 없음)
high_baseline = baselines > 1.5     # 너무 멂(겹침 부족)

print("베이스라인 부족 프레임:", np.where(low_baseline)[0])
print("베이스라인 과다 프레임:", np.where(high_baseline)[0])
----

[source]
----
베이스라인 부족 프레임: [10 11 12 13]
베이스라인 과다 프레임: [25]
----

임계값(`0.05m`, `1.5m`)을 정해두면, `40`프레임을 일일이 눈으로 확인하지 않아도 문제가 될 만한 구간을 정확히 짚어낼 수 있습니다. 정차 구간(`10~13`)은 나중에 다운샘플링(일부 프레임만 남기기)의 후보가 되고, 유실 구간(`25`)은 그 앞뒤로 포즈 그래프의 신뢰도가 떨어질 수 있다는 경고 신호입니다.

== 점검 2: 포즈 그래프 잔차의 이상치

7~9장의 포즈 그래프 최적화가 끝난 뒤에도, 각 제약(엣지)이 최종적으로 얼마나 잘 만족됐는지(잔차)를 따로 살펴볼 수 있습니다. 특징 매칭이 잘못된 엣지 하나가 섞여 있다면, 최적화가 그럭저럭 수렴했더라도 그 엣지의 잔차만은 다른 엣지들보다 훨씬 크게 남아 있을 가능성이 높습니다.

[source,python]
----
residuals = np.abs(rng.normal(0.001, 0.0005, n - 1))   # 평소 잔차는 매우 작음
residuals[30] = 0.05                                     # 잘못된 매칭이 섞인 엣지
----

== MAD 기반 이상치 탐지: 평균·표준편차 대신 중앙값을 쓰는 이유

평범한 이상치 탐지(평균에서 표준편차 몇 배 이상 벗어나면 이상치)는, 이상치 자기 자신이 평균과 표준편차를 크게 왜곡시킨다는 문제가 있습니다 — 극단값 하나가 평균을 끌어당기고 표준편차를 부풀려서, 오히려 그 극단값 자신이 "정상"처럼 보이게 만들 수 있습니다. **MAD(Median Absolute Deviation, 중앙값 절대편차)**는 평균 대신 중앙값을, 표준편차 대신 "각 값이 중앙값에서 벗어난 정도의 중앙값"을 씁니다 — 중앙값은 극단값 하나둘에 거의 흔들리지 않는 통계량이라, 이런 왜곡에 훨씬 강합니다.

[source,python]
----
def mad_outliers(x, thresh=5.0):
    med = np.median(x)
    mad = np.median(np.abs(x - med)) * 1.4826   # 1.4826: 정규분포를 가정했을 때 표준편차와 같은 스케일로 맞추는 상수
    z = np.abs(x - med) / (mad + 1e-12)
    return z > thresh, z

is_outlier, z_scores = mad_outliers(residuals)
print("잔차 이상치 프레임:", np.where(is_outlier)[0])
print("해당 z-점수:", z_scores[is_outlier])
----

[source]
----
잔차 이상치 프레임: [30]
해당 z-점수: [110.24498446]
----

잘못된 매칭이 섞였던 `30`번 엣지가 정확히 잡혔고, 그 "이상함의 정도"(`z`-점수)가 `110`이나 됩니다 — 다른 엣지들의 전형적인 편차보다 `110`배나 벗어나 있다는 뜻으로, 명백한 이상치입니다. `thresh=5.0`처럼 일반적인 이상치 탐지에서 흔히 쓰는 기준으로도 확실하게 걸러집니다.

== 왜 이 자동화가 실전에서 중요한가

수천~수만 프레임 규모의 실전 로그에서는 사람이 렌더링 결과를 일일이 보고 "여기가 흐리네, 저기가 이상하네"라고 판단하는 게 현실적으로 불가능합니다. 이 장에서 만든 것 같은 게이트를 회귀 테스트 파이프라인에 넣어두면, 3DGS 렌더링을 시작하기도 전에 "이 로그의 `10~13`번, `25`번, `30`번 프레임(또는 엣지)에 문제가 있다"는 걸 자동으로 알 수 있습니다 — 문제가 있는 시퀀스를 애초에 걸러내거나(품질 게이트로 차단), 문제 구간만 별도로 표시해 재구성 결과를 볼 때 그 구간의 저품질을 감안하고 해석하거나, 자동으로 해당 프레임을 제외하고 다시 최적화를 돌리는 등의 후속 조치를 취할 수 있습니다. 다음 장에서 이 책의 여러 도구를 하나로 모아 "이 로그가 3DGS에 넣을 준비가 됐는가"를 종합 판정하는 파이프라인을 완성할 때, 이 장의 게이트들이 그 판정의 한 축을 이룹니다.

== 직접 해보기

* `mad_outliers`의 `thresh`를 `5.0`에서 `3.0`으로 낮추면, 원래는 정상으로 분류됐던 다른 엣지들 중 일부가 새롭게 이상치로 잡히는지 확인해보세요. 임계값을 너무 낮추면 어떤 실무적 문제가 생길지도 생각해보세요.

.해답 보기

----
is_outlier_strict, z_strict = mad_outliers(residuals, thresh=3.0)
print("thresh=3.0일 때 이상치:", np.where(is_outlier_strict)[0])
print("이상치 개수:", is_outlier_strict.sum())
----

[source]
----
thresh=3.0일 때 이상치: [30]
이상치 개수: 1
----

이 예제에서는 `thresh`를 `3.0`으로 낮춰도 여전히 `30`번만 잡힙니다 — 나머지 엣지들의 잔차가 정규분포에 가깝게 조용히 흩어져 있어서, `3`배 기준으로도 우연히 튀는 값이 없었기 때문입니다. 하지만 실전 데이터에서는 이렇게 깨끗하지 않은 경우가 많습니다 — 임계값을 지나치게 낮추면(예: `2.0` 이하), 정상적인 통계적 흔들림까지 "이상치"로 오탐하게 되어, 멀쩡한 프레임들이 불필요하게 파이프라인에서 걸러지거나 사람이 검토해야 할 목록에 쌓이게 됩니다(이른바 "알람 피로"). 반대로 임계값을 너무 높이면(`10` 이상) 실제 문제를 놓칠 수 있습니다. `5.0` 근방이 실무에서 자주 쓰이는 균형점이지만, 최종적으로는 각 조직의 데이터 특성에 맞춰 오탐률과 미탐률을 직접 재보고 조정해야 하는 값입니다.

== 요약

* 연속 프레임 간 이동 거리(베이스라인)가 너무 작으면 정보가 부족하고 너무 크면 매칭이 불안정해지므로, 임계값으로 두 극단을 모두 자동 점검할 수 있습니다.
* 포즈 그래프 최적화 후 남은 엣지별 잔차를 살펴보면, 잘못된 매칭이 섞인 엣지를 나머지와 구분해 찾아낼 수 있습니다.
* MAD(중앙값 절대편차) 기반 이상치 탐지는 평균·표준편차 기반 방법과 달리 이상치 자신에 의한 왜곡에 강건해, 극단값이 섞인 실전 데이터에 더 적합합니다.
* 이런 자동화된 게이트는 수천~수만 프레임 규모의 실전 로그에서 사람이 일일이 검토할 수 없는 문제를 걸러내는 첫 방어선이 됩니다.
* 다음 장에서는 이 책의 모든 도구(시간 정렬, extrinsic 재최적화, 품질 게이트)를 하나로 묶어, 흔들린 원시 로그를 정제된 3DGS 입력으로 만드는 전체 과정을 처음부터 끝까지 실행합니다.
